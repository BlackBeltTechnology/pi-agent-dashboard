Tool-result error cards

Six error surfaces in the chat transcript still use raw Tailwind red literals instead of the --severity-* tokens. Those literals are dark-mode-tuned, so all six fail in light mode and all six pass in dark — the signature of a palette that was only ever eyeballed against a dark background. Toggle the theme and watch the left column disappear.

Three defects, one card. (1) contrast — the measurable one; (2) the body is a flat red wash even where it passes; (3) the markdown is never rendered. The body is emitted through LinkifiedText, which linkifies URLs/paths only — so the ```shell fence and the Exit code / stdout / stderr structure show as raw text.

The fix is not invented — it is what the success path of the same component already does. CtxToolRenderer.tsx:239 renders fenced code through CodeBlock → SyntaxHighlighter, and splitHeadingBlocks splits the body into sections. The error path throws all of it away and dumps parsed.message into one flat <pre>. So a passing ctx call is syntax-highlighted and sectioned; a failing one — the case you most need to read — is a raw wall. The “after” column runs the error body through the same machinery: fence → highlighted command block, then exit / stdout / stderr as their own sections.

3 · Measured — computed, not eyeballed

Ratios computed by compositing each declared alpha over the chat surface (--bg-primary: #ffffff light / #0a0a0a dark), then WCAG 2.x relative luminance. The floor is 3:1, the same one tests/e2e/severity-contrast.spec.ts already enforces for every other severity surface.

4 · Why this keeps happening

The --severity-* triples are color-mix()-derived against the theme's own --text-primary / --bg-tertiary, so they re-derive per theme automatically. A raw red-400 cannot: it is one fixed value, and it was chosen while looking at a dark background. Every future raw literal will reproduce this bug, which is why the spec's requirement is a ban on raw literals in error surfaces, not a list of six fixes.
