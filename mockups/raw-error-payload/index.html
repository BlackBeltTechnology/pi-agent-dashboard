errorMessage is an opaque string — show it, then any JSON inside it

pi's protocol types errorMessage as Type.TOptional<Type.TString> — a string, with no structure at all. Providers set it from String(error), so its content is unconstrained. Humanizing is dropped. What we keep is the structured output of JSON parsing: a collapsible tree of whatever shape is there, and — when the payload happens to carry one — error.message as a readable collapsed headline. Nothing is invented, nothing is concatenated, and raw is always preserved.

1 · the value pi actually sends is not valid JSON

Straight from docs/rpc.md. Note the 529 and the space before the brace — JSON.parse() throws on this.

So humanizeProviderError — which bails unless the string startsWith("{") — does nothing at all on the common case. It only fires on a pure-JSON payload. It is simultaneously lossy and mostly inert.

2 · collapsed — readable, without inventing anything

If the string contains JSON carrying a error.message string, that is the headline — a runtime check, not an assumed schema. Otherwise the first line of the raw string. Never concatenated with type, never prefixed, never reworded — and raw is never destroyed.

3 · expanded — full string, then any JSON found inside it

Raw is always shown first and always complete. Parsed appears only when a JSON value could be located — here by scanning to the first { or [ and balance-matching to its close. The tree assumes no keys whatsoever; it renders whatever is there.

4 · every documented shape, one code path

All five are real values from pi's docs or a plausible String(error). Same renderer, zero provider-awareness, zero assumed keys.
