# sqlite-store.ts — index

Default KbStore backend over node:sqlite. FTS5. WAL + `PRAGMA busy_timeout=5000` (concurrent reader waits for a batch commit, not `SQLITE_BUSY`). Zero runtime deps. Requires --experimental-sqlite. better-sqlite3 drop-in fallback. `readonly dbPath`. `checkpointAndClose()`: TRUNCATE-checkpoint + close BEFORE the install (WAL ordering load-bearing); install itself lives in `index-run.ts` (`installIndex`). `closeAndUnlink()`: close + unlink db + `-wal`/`-shm` (failed first-index cleanup). `expandParent` collapses `h.parent` to `{ headingPath }` (dropped root/path/docType/chunkId/score/snippet — same-file dups/constants). `search()` pipeline: body-hash collapse → **source dedup** (one hit per `(root,path)`, rep = best BM25, rest counted in `suppressedSections`) → MMR → optional coverage rerank → **lane interleave**. `limit` bounds distinct SOURCES (BREAKING); candidate pool `limit*6` when source dedup is on, capped 4000. Lane quota runs a SECOND FTS pass restricted to `doc_type='agents'` (shallow pool `limit*share*2`) and interleaves — `doc_type` is an UNINDEXED FTS5 column so that pass is a full match scan and is the change's main latency cost (~25→53 ms median at 31k chunks). Explicit `docType` bypasses the quota. **Lead-slot rule**: the running-share test `(taken+1)/(out.length+1) <= share` is structurally false at slot 1 for every share < 1, so `laneLeadMargin > 0` adds a separate slot-1 contest — reserved leads when `r0 - m0 <= margin * \|m0\|` on RAW BM25(+proximity) bests captured BEFORE `coverageRerank` re-sorts a lane (MMR reorders only). Sign-safe because scores are negative/ascending-better; at margin 1 it degenerates to an unconditional lead. The lead pick is an ordinary reserved take (increments `taken`, populates `seen`), so slot 2 reads `2/2 > share` and yields. See change: fix-kb-search-lane-composition. `coverageRerank()` = IDF-weighted coverage of ORIGINAL query terms (appended PRF terms at 0.5x) with BM25 tiebreak; `prfTerms()` = RM3 mining gated on `MIN_FEEDBACK_DOCS` 5. df/IDF from a lazily created `chunks_vocab` fts5vocab shadow table keyed by exact porter stems (`stems()` temp-table `kb_stem` mapping; exact df, not prefix-range estimate; read-only-DB safe). `getChunk(root,path)` without a heading now reports `suppressedSections`; `getChunks()` returns the whole file. See change: fix-kb-index-feedback; harden-kb-index-failure-atomicity; slim-kb-search-output; fix-kb-search-retrieval-quality. `init()` runs `migrateChunksSchema()` FIRST: `PRAGMA table_info(chunks)` without `start_line`/`end_line` ⇒ `DROP TABLE chunks` + clear `files`/`nodes`/`edges`/`properties`, because `CREATE VIRTUAL TABLE IF NOT EXISTS` is a NO-OP on an existing table and FTS5 has no ALTER ADD COLUMN — without it every `insertChunk` on a pre-change store throws "no column named start_line" and the store is permanently un-reindexable. Clearing `files` is load-bearing: the next INCREMENTAL walk would otherwise skip every unchanged file and leave the rebuilt table empty.
