# capability-issuance.ts — index

Who is issued a prompt capability (design D1a, tasks 2b.1/3.5). `shouldIssuePromptCapability(headers, corsOpts)` + `UpgradeHeaders`. `isOriginAdmitted` returns true for an ABSENT Origin (`cors-origin.ts:244`) so non-browser local clients keep working, which is exactly why admission alone cannot gate issuance. Requires ALL of: a non-absent, non-empty Origin that `isOriginAdmitted` admits (same-origin-by-Host, or configured with the zrok wildcard DISABLED); `Sec-Fetch-Site` of `same-origin` or `cross-site` (`cross-site` exists for the `pi-dashboard.dev` shell and qualifies only because the admission rule already admitted its Origin; `same-site`/`none`/absent refuse). The UI credential tier is enforced by the upgrade gate BEFORE the socket exists (`server.ts:2938-2950`), so it is not re-derived. Repeated (array) headers refuse. Fail-closed on anything missing. These are PROVENANCE SIGNALS, NOT AN AUTHENTICATION BOUNDARY: a same-machine process can forge them (design D1b R-A/R-C). Honest caveat, tested: a DNS-rebound page is same-origin-by-Host, so in `report` mode it IS issued a capability; what stops it is `maySuspend`'s `enforce` requirement, not issuance. Under `enforce` it is not issued one. See change: add-access-grant-dialog. Condition 2 now a DERIVED site relation (`siteRelation`: same-origin by Host / same-site = same hostname other port or loopback-to-loopback / cross-site), because Chrome sends no `Sec-Fetch-Site` on WS upgrades; a present header must still qualify; unparseable Host refused. See change: add-access-grant-dialog (E2E finding, user decision A).
