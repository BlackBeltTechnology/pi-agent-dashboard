# prompt-channel.ts — index

Per-connection prompt capabilities (design D1/D1a/D2, tasks 3.1/3.3/3.4). `issuePromptChannel` / `resolvePromptChannel` / `releasePromptChannel` / `promptChannelCount` / `isPromptEligible` / `maySuspend` + `GRANT_CHANNEL_HEADER` (`x-pi-grant-channel`). The browser gateway issues each socket a 256-bit value, the browser echoes it, and a denial is prompt-eligible by resolving back to the issuing socket. Memory only, NEVER persisted (a restart issues fresh values); `releasePromptChannel` on socket close makes a capability die with its connection; comparison is `timingSafeEqual` over the whole scan with NO early `break`, so lookup cost does not depend on where the match is; absent, empty, wrong, and non-string all resolve to the SAME `null`, so a caller cannot distinguish "sent nothing" from "guessed wrong". Eligibility consults the capability and NOTHING ELSE — not auth, not the CORS decision, not `Sec-Fetch-*`, not an `Origin`/`Host` compare (the four recorded defeats). `maySuspend(request, mode)` additionally requires `enforce` and takes the mode as an ARGUMENT so it cannot mutate it; the caller resolves the live mode via `resolveHostGateMode` at the denial site. See change: add-access-grant-dialog.

`hasPromptChannel(socketId)`: is that socket's capability still live. Backs gateway `holdsLiveCapability(ws)`. See change: add-access-provisioning.
