# How we did it: Stop OpenSpec reads from auto-attaching the session card — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened in explore mode with a real bug: browsing OpenSpec changes for
analysis silently glued the dashboard session card to whatever change file got read.

> _"/skill:openspec-explore — When using skill and reading openspec list - for
> example analzis - i the card set to that readed openspec. Check how can be avoid
> that without causeing regression in the proposal create after an explore"_

The **real objective**, sharpened by the first steering turn, was not "gate on explore
phase" but a cleaner distinction: **reading a change is passive browsing and must not
attach; writing a change file or running an `openspec` CLI command is active work and
must keep attaching.** Fix the false-attach without regressing any active workflow,
then carry it through the full OpenSpec loop (proposal → apply → verify → archive →
commit).

## 2. TL;DR playbook

1. Enter `/skill:openspec-explore` and point it at the exact symptom ("reading a change
   attaches the card"). Let it trace the detection path, not guess it.
2. Make the AI find the culprit: `detectOpenSpecActivity` / `DetectedActivity` in
   `packages/shared`, consumed by the auto-attach block in
   `packages/server/src/event-wiring.ts` (the `openspecChange && !attachedProposal`
   gate).
3. **Steer the framing early**: the axis is read-vs-write, not phase. Add an
   `isActive` boolean to `DetectedActivity` — `false` for reads, `true` for
   writes + bash CLI.
4. Approve the design, then `/opsx:ff` to fast-forward all artifacts
   (proposal → design → specs → tasks) for `openspec-read-only-no-attach`.
5. `/opsx:apply` with strict TDD: edit the test file first, watch it fail, then
   patch the detector + gate the auto-attach on `detected.isActive`.
6. If `npm test` hangs, tell it to move on ("tests stuck, ignore it") — the scoped
   detector suite already passed.
7. `/opsx:verify` (map each spec scenario to test evidence), then `/opsx:archive`
   (sync the delta into the existing `proposal-attachment` main spec, not a new one).
8. `commit changes` — stage ONLY the change's files, since the tree had unrelated work.

## 3. How the collaboration unfolded

**Discovery (explore).** The AI entered explore mode and traced the chain instead of
patching blindly: reading any `openspec/changes/<name>/` file sets `changeName`, which
`event-wiring.ts:141-142` turns into `attachedProposal` whenever nothing is attached
yet — regardless of phase. It produced a Mermaid sequence diagram of the bug. *Why it
worked:* it located the exact lines and consumer before proposing a fix.

**Reframe (the key decision point).** The AI's first instinct was "don't auto-attach
when `openspecPhase === 'explore'`." The human corrected the axis: attach when the
user says "create proposal", skip when `spec-coherence-check` just reads. The AI
rebuilt its mental model into a read-vs-write truth table and landed on the `isActive`
flag — a much cleaner invariant than phase-sniffing.

**Design + generate.** The user ran the `/opsx:ff` prompt to fast-forward artifact
creation. The AI scaffolded the change, then produced proposal, design, specs (2
requirements / 7 scenarios), and tasks (7 tasks / 3 groups), pausing to ask "does this
approach look right?" before implementing.

**Implement (TDD).** `/opsx:apply` drove it: update the 31-test detector suite first,
confirm failure, then add `isActive` to `DetectedActivity` (reads `false`, writes/bash
`true`) and gate the auto-attach. Full `npm test` hung; the user said ignore it and the
scoped suite carried the proof.

**Verify + archive + commit.** `/opsx:verify` mapped every spec scenario to concrete
file:line evidence. Archive required a judgment call: the delta lived under
`openspec-activity-detection`, but the matching main spec was the existing
`proposal-attachment/spec.md`, so it synced there rather than creating a new capability.
Commit staged only the 9 related files out of a dirty multi-feature tree.

## 4. Prompts that worked

- **The goal prompt** (`/skill:openspec-explore` + symptom): effective because it named
  the observable bug ("reading a change attaches the card") and set a guardrail
  ("without causing regression in proposal-create"). Explore mode + a concrete symptom
  beats "fix the attach logic".
- **High-leverage reframe** — _"In explore when asking to create proposal and I answer
  Create proposal... have to attach, but when skills like spec-coherence-check executed
  doesn't"_. This one sentence flipped the whole design from phase-gating to
  read/write-gating. Short, decisive, saved a wrong implementation.
- **`Is there anything to clarify?`** — a cheap check that let the AI confirm scope was
  small before burning apply cycles.
- **`tests stuck, ignore it`** — unblocked a hang without abandoning the change.
- **`commit changes`** — trusted the AI to scope the commit; it correctly staged only
  the 9 relevant files.

Stronger rewrite of the goal prompt for next time: _"/skill:openspec-explore — reading
an OpenSpec change file (e.g. spec-coherence-check) auto-attaches the session card.
Trace detectOpenSpecActivity → event-wiring auto-attach and propose a fix that still
attaches when the user actively creates/edits a change. Distinguish read vs write."_

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Gate the fix on `openspecPhase === "explore"` | "attach on *create proposal*, skip on *spec-coherence-check*" — i.e. read vs write, not phase | State the invariant up front: passive read = no attach, active write/CLI = attach |
| Want to implement immediately | asking "Is there anything to clarify?" before apply | Pause for a one-line design confirm on any behavior-changing gate |
| Risk stalling on a hung `npm test` | "tests stuck, ignore it" | Run the *scoped* suite (`npx vitest run <detector test>`) as the source of truth; treat full-suite hang as non-blocking |

## 7. Pitfalls & dead ends

- **Phase-gating is the wrong axis.** If you reach for `openspecPhase`, stop — the
  correct distinction is read vs write. Phase would still mis-attach when a write skill
  runs outside explore.
- **`npm test` can hang** in this repo. Don't wait it out; run the targeted
  `npx vitest run packages/extension/src/__tests__/openspec-activity-detector.test.ts`
  and move on.
- **Delta-spec / main-spec mismatch.** The delta was named
  `openspec-activity-detection`, but no such main spec existed; the real home was
  `proposal-attachment/spec.md`. Don't blindly create a new capability spec on archive.
- **Dirty working tree.** The repo had other in-flight features. A blanket `git add`
  would have polluted the commit — stage by explicit path.
