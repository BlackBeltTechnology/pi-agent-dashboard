# How we did it: Turn a raw provider-error banner into a real ErrorBanner component — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator pasted a single screenshot with one word of context — **"Bug:"** — showing
the dashboard chat view surfacing a raw provider error: *"Expected double-quoted property
name in JSON at position 1321"*. The real objective, once the AI had diagnosed it, was
**not** to fix a repo bug (there was none — the model itself had emitted malformed JSON in
a tool call and the provider rejected it) but to **make that unavoidable error render as a
usable UI element**: a reusable `ErrorBanner` component with show-more/less truncation, a
copy-to-clipboard control, and a wired retry action — then update the spec and commit.

## 2. TL;DR playbook

1. **Give the AI the error + a "Bug:" screenshot.** Let it trace the string, not guess.
2. **Have it locate the source** — here `extractAgentEndError` in
   `packages/client/src/lib/event-reducer.ts` feeds a flat banner in `ChatView.tsx`.
3. **Accept the reframe:** the error is provider-side (malformed model JSON), so the fix is
   *UX*, not a code-path repair. Pick the UX improvements to build.
4. **Extract the inline banner JSX into a new `ErrorBanner.tsx`** with: 240-char
   show-more/less toggle, `CopyButton` reuse, optional `onRetry`, preserved dismiss.
5. **Keep the test-id contract** (`error-banner`, `error-banner-dismiss`) so existing
   ChatView tests stay green; add a dedicated `ErrorBanner.test.tsx`.
6. **Wire it up:** `ChatView` forwards `onRetryAfterError`; `App.tsx` maps Retry →
   `handleResumeSession(selectedId, "continue")`.
7. **Verify:** `npx vitest run` (from `packages/client`), `tsc --noEmit`, `npm run lint`.
8. **"update specs":** reflect the new behavior in `openspec/specs/error-detection/spec.md`.
9. **"commit changes":** stage ONLY the error-banner files, leave unrelated work untouched.

## 3. How the collaboration unfolded

**Phase 1 — Diagnosis (root-cause before code).** From just the screenshot, the AI grepped
for the error string and `JSON.parse`, then walked from the banner render back to
`extractAgentEndError` (`event-reducer.ts:289`) and the `agent_end` event forwarder. It
concluded the failure was the model emitting single-quoted JSON in a tool-use args blob —
the dashboard was merely displaying what the provider returned. *Why it worked:* the AI
refused to "fix" a non-bug and instead reframed the task as UX. Decision point: the human
implicitly accepted the reframe by letting it proceed to build controls.

**Phase 2 — Component design.** The AI extracted the inline banner into `ErrorBanner.tsx`,
reusing the existing `CopyButton` and mdi icons already imported in ChatView, and preserved
the `data-testid` contract so it didn't break the existing ChatView test.

**Phase 3 — Wiring.** `ChatView` became a thin renderer of `<ErrorBanner>` plus a new
optional `onRetryAfterError` prop; `App.tsx` wired Retry to resume the session in
`"continue"` mode — the natural "nudge the model to try again" path.

**Phase 4 — Verify.** 31 tests pass; `tsc` showed only pre-existing errors; lint clean for
the touched files.

**Phase 5 — Specs & commit (steered).** On "update specs" the AI edited
`error-detection/spec.md` (new requirements for collapse-toggle and retry). On "commit
changes" it staged *only* the five error-banner files and left all unrelated dirty files
alone, landing `e95491b` on `develop`.

## 4. Prompts that worked

- **Goal prompt — "Bug:" + screenshot.** Terse but sufficient *because the screenshot
  carried the exact error string.* A stronger version states the desired outcome too:
  *"This provider error shows as a raw banner — make it a proper component with
  copy/retry/collapse and update the spec."*
- **"update specs"** — high-leverage two words that triggered a full spec reconciliation
  once the implementation existed. Effective because the code was already done and
  verified, so the AI had concrete behavior to encode.
- **"commit changes"** — worked *only because the AI self-imposed scope discipline*
  (stage related files, ignore unrelated dirt). To be safe, say *"commit ONLY the
  error-banner files"* explicitly.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat the ask as a code-path bug fix | Providing only "Bug:" + image, letting the AI reframe to a UX fix | Say up front "the error is unavoidable — improve how it's shown" |
| Stop after implementation | "update specs" | Name spec updates as part of the definition of done |
| Potentially commit the whole dirty tree | "commit changes" (AI self-scoped to related files) | Say "commit ONLY <these files>" to remove ambiguity |

The repo had many unrelated dirty/untracked files (openspec changes, editor-pid-registry,
docs). The key guardrail: **never `git add -A` in a messy tree** — stage the exact files
the change touched.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session. The workflow *is* repeatable, though —
consider a small project skill **"surface-provider-error-as-component"**: capture the
diagnosis path (`extractAgentEndError` → `agent_end`), the test-id contract to preserve,
and the "Retry = resume in continue mode" convention. It would remove the re-discovery of
where the banner originates and how retry is wired.

Reusable conventions worth remembering:
- **Test-id contract preservation** (`error-banner`, `error-banner-dismiss`) lets you
  refactor banner JSX into a component without touching existing ChatView tests.
- **Retry semantics** = `handleResumeSession(selectedId, "continue")`.

## 7. Pitfalls & dead ends

- **Vitest environment:** running the test from the repo root failed on jsdom/environment
  resolution; the AI re-ran from **`packages/client`** where the vitest config applies. If a
  client test can't find its DOM env, `cd packages/client` first.
- **`openspec validate error-detection --strict` reports a missing `## Purpose` section.**
  This is **pre-existing**, not introduced by the spec edit — don't chase it.
- **`tsc --noEmit` shows errors:** confirm they're pre-existing (unrelated files) before
  assuming your change broke the build.
