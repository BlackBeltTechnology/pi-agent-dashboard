# How we did it: Fixing dashboard OAuth login (unregistered redirect URI) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The user hit a hard wall trying to log into Anthropic from the dashboard's Settings,
in the Electron app:

> `/skill:openspec-explore` — "Claude login does not work in settings. I'm tried with
> Electron APP — Authorization failed. Redirect URI
> `http://localhost:8000/api/provider-auth/callback/anthropic` is not supported by client."

The *real* objective, once discovery clarified it: the dashboard reuses pi CLI's
Anthropic OAuth **client ID**, but that client only whitelists pi's own registered
redirect URI (`http://localhost:53692/callback`). The dashboard invented its own
port/path, which Anthropic rejects server-side. The fix had to work for **all four
OAuth providers** (Anthropic, OpenAI Codex, Gemini CLI, Antigravity) and in **both**
the Electron app and a plain browser — landing as a properly-specced, tested,
archived OpenSpec change on `develop`.

## 2. TL;DR playbook

1. **Open in explore mode with the exact error text.** `/skill:openspec-explore` +
   paste the verbatim "Redirect URI ... is not supported by client" message — the
   error string *is* the root cause.
2. **Find the registered URIs from the source of truth.** Grep the installed
   `@mariozechner/pi-ai` OAuth modules for each provider's `REDIRECT_URI`/port. Don't
   guess ports — read them: Anthropic `53692/callback`, Codex `1455/auth/callback`,
   Gemini CLI `8085/oauth2callback`, Antigravity `51121/oauth-callback`.
3. **`/opsx:ff` to scaffold the change** (proposal → design → specs → tasks) once the
   approach is understood.
4. **Force a clarification pass before coding**: ask "Is there anything to clarify?"
   This surfaced the cross-origin `postMessage` fragility and pivoted the design to a
   **system-browser + temp callback server** (server-side token exchange, client
   polls status) — simpler and popup-free.
5. **`/opsx:apply` with TDD**: write `oauth-callback-server.test.ts` first, then the
   temp HTTP server (listen on the registered port → receive code → run `onCode` →
   serve HTML → close).
6. **Build + deploy locally**: `npm run build` → `curl -X POST .../api/restart` →
   `npm run reload`. Test the real OAuth login manually in Electron.
7. **`/opsx:verify`, fix the WARNINGs, re-verify**: wire `closeAllCallbackServers()`
   into shutdown, align spec text with the polling reality, clean up React timers.
8. **`/opsx:archive`** (syncs the new `oauth-callback-server` capability spec) →
   commit **only** the change's files.

## 3. How the collaboration unfolded

**Phase 1 · Discovery (root-cause the error).** The AI grepped the dashboard's
`provider-auth` code and the installed pi-ai OAuth modules, then drew the exact
mismatch: dashboard sends `localhost:8000/api/provider-auth/callback/anthropic`;
Anthropic's client only whitelists `localhost:53692/callback`. *Why it worked:* the
error message named the failing URI, so the whole investigation was "find where each
URI comes from" — a deterministic grep, not speculation. The AI proactively pulled
the other three providers' registered URIs from their pi-ai modules, pre-empting a
provider-by-provider whack-a-mole.

**Phase 2 · Proposal.** On "make proposal" the AI wrote the initial fix: spin up a
temporary HTTP server on each provider's registered callback port, catch the redirect,
serve a relay HTML, shut down.

**Phase 3 · Design pivot (the important one).** When asked "Is there anything to
clarify?", the AI stress-tested its own relay design and found the flaw: the popup
relay used `postMessage` (cross-origin OK) plus `BroadcastChannel`/`localStorage`
(both **same-origin only** — silently dead across `:53692` ↔ `:8000`), and Electron
popups make `window.opener` unreliable. The human's nudge — "callback seemed missed,
maybe for auth better to call the system browser?" — unlocked the clean design: **open
the system browser, let the temp server do the full token exchange server-side, and
have the client just poll `/api/provider-auth/status`.** No cross-origin relay at all.

**Phase 4 · Apply (TDD).** `/opsx:apply` drove 12 tasks: add `callbackPort`/
`callbackPath` to the handler interface + all four handlers, create
`oauth-callback-server.ts` test-first, rewrite `/authorize` to start the temp server +
open the system browser, delete the popup relay and `/callback/:provider` route, and
simplify `ProviderAuthSection.tsx` to poll. The bulk of the effort was fighting a
`server.close()`-races-the-response socket bug (see Pitfalls).

**Phase 5 · Build, deploy, verify.** `npm run build` → `/api/restart` → `npm run
reload`; user confirmed the real Electron login worked. `/opsx:verify` flagged three
WARNINGs (shutdown cleanup, spec-vs-implementation drift, React timer leaks); "fix"
resolved all three; re-verify came back 13/13 scenarios, no issues.

**Phase 6 · Archive + commit.** `/opsx:archive` synced the new `oauth-callback-server`
capability spec into `openspec/specs/`. On commit, the AI noticed unrelated files from
another change (`ask-user-message-body`) in the working tree and committed **only** the
oauth-redirect-fix files — `6e15150` on `develop`.

- **Goal prompt (strong):** `/skill:openspec-explore` + the *verbatim* error including
  the rejected redirect URI. Pasting the exact failing string turned root-causing into
  a grep. *Reuse this:* always paste the literal error, not a paraphrase.
- **"Is there anything to clarify?"** (used twice) — a high-leverage forcing function.
  It made the AI audit its own design *before* writing code, which is exactly when the
  fragile cross-origin relay got caught and replaced. Cheap prompt, huge payoff.
- **"yes, callback seemed missed. Maybe for auth better idea to call the system
  browser?"** — a one-line domain hint that unlocked the whole cleaner architecture.
  *Reuse this:* when the AI's design feels fragile, name the alternative mechanism you
  suspect ("use the system browser") rather than just saying "fix it".
- **`build and deploy`, `I've tested it works`, `fix`, `commit changes`** — terse
  drivers that worked because the workflow (build→restart→reload, verify→fix→re-verify)
  was already well-defined by the OpenSpec skills.

## 7. Pitfalls & dead ends

- **`server.close()` races the HTTP response → socket hang up / ECONNRESET.** The temp
  callback server closed before the response flushed, killing keep-alive connections.
  Six failed `vitest` runs chasing it. *Fixes that stuck:* wait for `res.on('finish')`
  before closing, and give the port-conflict/onCode-error tests their **own port** so a
  previous test's `afterEach` (`closeAllCallbackServers`) can't kill a shared keep-alive
  socket. If you see intermittent ECONNRESET in a "start server → hit it → close" test,
  suspect cross-test port reuse before your own logic.
- **Port-in-use detection false-negative:** a blocker server bound `0.0.0.0` while the
  callback server bound `127.0.0.1`, so the conflict wasn't detected. Bind both to the
  same interface, and register the `error` handler *before* `listen`.
- **`BroadcastChannel`/`localStorage` relays silently fail cross-port** — they're
  same-origin only. `localhost:53692` ≠ `localhost:8000`. Don't rely on them for an
  OAuth relay that lands on a different port than the opener.
- **`npx tsc --noEmit` noise:** stale `dist` files produced `TS6305`/`TS6306` — filter
  them out (`grep "error TS" | grep -v "TS6305\|TS6306"`) to see real type errors.
- **Verify caught a shutdown leak:** `closeAllCallbackServers()` existed but wasn't
  wired into the server stop path — a restart mid-flow would hold the port for the
  5-minute timeout. Always wire cleanup into the shutdown sequence.
