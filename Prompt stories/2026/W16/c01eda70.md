# How we did it: Fixing the Windows/arm64 Electron release — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened tiny — *"There is not committed files which was created the recent
sessions. Commit them"* — but that was only the doormat. The **real** objective emerged
across a dozen steering turns: **get the pi-agent-dashboard GitHub Release to actually
ship working binaries for every platform/arch it claims to support.** By the end that
meant: fill the gaps in the release matrix (deb arm64, Windows portable/zip for x64 **and**
arm64), and — the hard part — fix the reason the Windows builds *installed but wouldn't
launch*. Two distinct root causes in the packaging/runtime code had to be found and fixed,
each verified against a fresh release tag.

## 2. TL;DR playbook

1. **Commit the orphaned work first** — `git status --short`, stage all, write a real
   fe_at:-scoped message. Clear the tree before touching CI.
2. **Map the release matrix before editing it** — read `.github/workflows/publish.yml`
   plus `packages/electron/scripts/{docker-make,patch-appimage-fix,bundle-server}.sh` and
   list which (runner × arch × maker) combos exist vs. are missing.
3. **Add the missing artifacts by runner, not by hack** — native `ubuntu-24.04-arm` for
   Linux arm64 DEB; cross-package Windows arm64 on the x64 runner. Name portables per-arch
   (`PI-Dashboard-{arch}-portable.exe`).
4. **When "installs but won't start", suspect path resolution, not the maker.** Grep the
   Electron package for `new URL(import.meta.url).pathname` — on Windows it returns
   `/C:/…` and silently breaks `fs.existsSync`. Replace with `fileURLToPath`.
5. **Trace runtime `serverRoot` by counting directory levels**, not by eye — use a throwaway
   `node -e` that resolves the real bundled `cli.ts` path. The bug was 2-levels-up vs. the
   required 3-levels-up to reach `node_modules/`.
6. **Scope CI workarounds to the exact runner that needs them.** `--ignore-scripts` for
   phantomjs belongs on **linux+arm64 only** — applying it to macOS arm64 broke the DMG
   maker's `macos-alias`/`volume.node`.
7. **Ship each fix as its own version bump + tag** (`npm version … --workspaces
   --include-workspace-root`, commit, `git tag vX.Y.Z`, push both) so every release run is
   traceable to one change.
8. **Confirm CI == local Docker build** before assuming the fix landed everywhere — both
   paths share `server-lifecycle.ts`, so a single runtime line fix covers zip + portable +
   docker.

## 3. How the collaboration unfolded

**Phase 1 — Housekeeping commit.** The AI ran `git status`, saw the uncommitted "known
servers management + network discovery" feature (24 files), staged it, and wrote a
descriptive `feat:` commit. Clean start; nothing clever, but it cleared the tree so later
release commits stayed atomic.

**Phase 2 — Fill the release matrix.** Prompted with the missing artifact list, the AI read
the whole build pipeline first, then produced a concrete matrix (what exists, what's
missing, which runner supplies each). It added `ubuntu-24.04-arm` for Linux arm64 DEB,
cross-packaged Windows arm64, made `patch-appimage-fix.sh` detect arch dynamically instead
of hardcoding `x86_64`, and taught `docker-make.sh` about arm64. **Decision point:** Linux
arm64 *skips* AppImage (appimagetool has no ARM build) — DEB only. Windows arm64 bundles an
**x64** Node.js because `node-pty` ships no arm64 prebuild and Windows runs x64 under WoW64
emulation.

**Phase 3 — "Installs but won't start" (root cause #1).** A screenshot of the failing
Windows app redirected the work. The AI grepped for the `import.meta.url` pattern and found
`forge.config.ts` computing `__dirname` via `new URL(import.meta.url).pathname` — which on
Windows yields `/C:/Users/…` (leading slash), so `fs.existsSync("resources/server")`
returned false and **the bundled server + Node binary were never packaged**. Fix:
`fileURLToPath`. It verified no other file used the broken pattern.

**Phase 4 — CI whack-a-mole (scoping workarounds).** `npm ci` on arm64 died on
`phantomjs-prebuilt` (no arm64 binary, pulled in transitively by the icon builder). The AI
added `--ignore-scripts` — then the next steering turn showed it had **over-applied it to
macOS arm64**, breaking the DMG maker's native `macos-alias`. It re-scoped the flag to
`linux + arm64` only. Then Windows arm64 `electron-forge make --arch=arm64` produced no
packaged dir (NSIS can't cross-compile), so it switched Windows arm64 to `electron-forge
package` + manual zip/portable. Each fix = its own version bump (v0.2.6 → v0.2.9).

**Phase 5 — "Still won't start" (root cause #2).** Another failure screenshot: the server
couldn't resolve `@blackbelt-technology/pi-dashboard-shared`. The AI traced `serverRoot` in
`server-lifecycle.ts` with a `node -e` path calculation and found it went **2 levels up**
from `cli.ts` (landing on `resources/server/packages`) when `node_modules/` lives **3 levels
up** (`resources/server`). One-line fix. **Decision point:** the user asked *"Is the CI build
same way as local docker electron builder?"* — the AI confirmed both share the runtime code,
so the single fix covers every build path.

## 4. Prompts that worked

- **The goal prompt** (*"commit them"*) was deceptively small. A stronger kickoff would
  have stated the true objective: *"Audit the GitHub Release matrix, add the missing
  platform/arch artifacts, and fix why the Windows builds install but won't launch."* That
  front-loads the real scope instead of discovering it over 12 turns.
- **High-leverage follow-up: pasting the raw CI/PowerShell error verbatim** (prompts 6, 7,
  9). Every time the user pasted the exact `npm ci` warning wall or the `Compress-Archive`
  path error, the AI jumped straight to the offending dependency/line. Raw error text >
  prose description.
- **High-leverage follow-up: the failure screenshots** (prompts 4, 11, 13). "Windows
  version does not start [image]" was enough to pivot from CI plumbing to the real
  packaging bug.
- **The architectural check** (*"Is the CI build same way as local docker electron
  builder?"*) — a single question that prevented a duplicate fix and confirmed one line
  covered all outputs.
- **The repeated `"increase version, commit push and tag release"`** was an effective
  *unlock* prompt: it let the user drive the release cadence without re-typing the
  procedure, one tag per fix.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session — and that's the gap worth closing. This
session rediscovered two **highly reproducible, non-obvious Windows-Electron traps** the
hard way. Recommended skills to create:

- **`electron-windows-path-traps`** (project scope): captures the two root causes — (1)
  `new URL(import.meta.url).pathname` → `/C:/…` breaks `fs.existsSync` on Windows, use
  `fileURLToPath`; (2) `serverRoot` must count **3 levels** up from bundled `cli.ts` to
  reach `node_modules/`. Invoke whenever a packaged Windows Electron app installs but won't
  launch. Removes an entire screenshot-driven debug loop.
- **`electron-release-matrix`** (project scope): the runner×arch×maker table — native
  `ubuntu-24.04-arm` for Linux arm64 DEB, `--ignore-scripts` **only** on linux+arm64 for
  phantomjs, Windows arm64 = `package` (not `make`) + x64 Node via WoW64. Invoke when adding
  or auditing release artifacts.

## 7. Pitfalls & dead ends

- **`--ignore-scripts` on the wrong runner.** Applying it to *all* arm64 killed the macOS
  DMG maker (`Cannot find module '../build/Release/volume.node'` from `macos-alias`). If you
  hit this: scope the flag to `linux + arm64` only; macOS arm64 needs normal `npm ci`.
- **`electron-forge make --arch=arm64` on a Windows x64 runner** produces no packaged dir
  (NSIS can't cross-compile). If you hit "path … does not exist" from `Compress-Archive`:
  switch Windows arm64 to `electron-forge package` + manual zip/portable, drop NSIS there.
- **`new URL(import.meta.url).pathname` is silently wrong on Windows** — no error, just a
  `/C:/…` path that fails `existsSync`, so bundled resources vanish from the package. Always
  `fileURLToPath(import.meta.url)`.
- **Eyeballing directory-level math.** The `serverRoot` bug (2-up vs 3-up) was only nailed
  by a throwaway `node -e` resolving the actual bundled path. Count with code, not by
  reading the string.
- **A failed grep** (`new URL(import.meta.url).pathname` with `--include`) returned nothing
  because of quoting; the broader `new URL.*import.meta` pattern found it. Loosen the regex
  before concluding the pattern is absent.
