# How we did it: Fixing the `ask_user` dialog that vanished in production — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff was one line plus a screenshot: **"The ask_user does not show the question dialog."** The `ask_user` tool call rendered in the dashboard chat as a red-dotted, errored step with a raw JSON dump — but no interactive question dialog ever appeared for the user to answer.

Once the investigation clarified it, the *real* objective was: **find why the interactive prompt renders in dev but not in the production build, fix the root cause, and make `ask_user` a first-class citizen in the dashboard** — a proper rich card, tolerant of the malformed arguments LLMs actually send (`question` instead of `title`, `options` as a JSON string), with a clean select/cancel UX.

## 2. TL;DR playbook

1. **Reproduce against the built artifact, not the dev server.** Confirm `/api/health` mode is `production` — the bug only exists in the esbuild output.
2. **Grep the *built* JS for the message type**, not the source: `rg -c "prompt_request" packages/client/dist/assets/*.js`. Finding it absent (or only as `architect_prompt_request`) is the smoking gun.
3. **Root cause:** `prompt_request` / `prompt_dismiss` / `prompt_cancel` were missing from the `ServerToBrowserMessage` union, so the `case "…" as any:` switch arms were dead-code-eliminated by esbuild in prod.
4. **Fix the type, not the cast:** add the three message interfaces to `browser-protocol.ts`, add them to the union, then delete every `as any` from the switch cases in `useMessageHandler.ts`.
5. **Add a compile-time regression test** (`browser-protocol-types.test.ts`) that asserts those types belong to the union, so the arms can never be stripped again.
6. **Rebuild + restart + reload**, then verify live in the *same session* with a real `ask_user` call.
7. **Then iterate on UX** in tight steered loops: dedicated `AskUserToolRenderer`, optional `title`, `prepareArguments` to coerce stringified `options`, `Array.isArray` guards, and Select cancel-button dedup.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (long, code-reading heavy).** The AI spent a *lot* of turns reading the bridge, PromptBus, adapters, reducer, and ChatView, forming and discarding hypotheses (TUI adapter answering first, timeout, race, dedup by title, `message` passthrough loss). Effective in the end, but slow — most of the 288 commands were exploratory reads. **The decision point that broke it open:** stop reasoning about *source* and interrogate the *build output*.

**Phase 2 — Root cause via the built JS.** `rg -c prompt_request` over `dist/assets/*.js` returned only the unrelated `architect_prompt_request`; `prompt_dismiss` and `prompt_cancel` returned zero. That proved esbuild had stripped the `as any` switch arms because TypeScript could prove they never matched the union. This is the *why-dev-but-not-prod* answer.

**Phase 3 — Fix + guard.** Added `BrowserPromptRequestMessage` / `…Dismiss` / `…Cancel` to `browser-protocol.ts`, added them to the union, removed the `as any` casts, and wrote a compile-time test locking the invariant in. Also fixed the `message` field being dropped by the patched `ctx.ui.input` (it ignored its `_opts` argument) so the question body flows through PromptBus `metadata`.

**Phase 4 — Verify live.** Rebuilt client, `curl -X POST /api/restart`, reloaded the bridge, then triggered a real `ask_user` in the running session and confirmed the dialog rendered.

**Phase 5 — UX iteration (steered).** A series of short human corrections each drove one focused change: give `ask_user` a rich renderer instead of the generic JSON dump; make `title` optional; handle `options` arriving as a JSON string; guard `.map` with `Array.isArray`; add `prepareArguments` to coerce args before TypeBox validation; and refine `SelectRenderer` (hide body pills while pending, highlight the chosen option when answered, suppress the default Cancel button when "Cancel" is already an option).

## 4. Prompts that worked

- **The goal prompt** — *"The ask_user does not show the question dialog" + screenshot.* Effective because the screenshot pinned the exact symptom (errored tool, no dialog). Stronger version: add the one fact that would have saved an hour — *"works in dev, broken in the production build"* — which points straight at the build toolchain.
- **"vitests stucked. Ignore full test"** — high-leverage: unblocked the loop by telling the AI to stop waiting on a hung full suite and run scoped tests instead.
- **"Give me a question with ask_user to test the tool in this session"** — turned the fix into a live, in-session verification instead of a claimed fix.
- **"Maybe title be not mandatory. And expand that type by default"** — a two-in-one steering nudge that set both a schema-tolerance rule and a display default.
- **"When in asking do not render the buttons in body. When answered … showed what option was selected. … when Cancel is in option does not render default cancel button"** — a precise, itemized UX spec; each clause maps to one code change. This is the model prompt for UX polish: enumerate observable behaviors, not vibes.

## 6. Skills, tools & memory created — and why they're effective

No skill was created, but this session is a textbook candidate for two:

- **`diagnose-prod-only-client-bug`** — *When a dashboard behavior works in `--dev` but breaks in the built client, grep `packages/client/dist/assets/*.js` for the message/type in question before reading source. Absence ⇒ esbuild dead-code-eliminated an `as any` switch arm; the fix is to add the type to its union, not to keep the cast.* This removes the multi-hour source-reading detour that dominated Phase 1.
- **`harden-ask_user-args`** — *LLMs send `ask_user` args loosely (`question` for `title`, stringified `options`). Coerce in `prepareArguments` before TypeBox validation; guard array access with `Array.isArray`.*

Artifacts worth reusing directly: the compile-time union test (`packages/shared/src/__tests__/browser-protocol-types.test.ts`) is the reusable guard pattern — assert every server→browser message type is a member of `ServerToBrowserMessage` so no future handler arm can be silently stripped.

## 7. Pitfalls & dead ends

- **Dead end: source-only reasoning for a prod-only bug.** Hours went into TUI-adapter-races, timeout, and dedup theories. None were the cause. *If a bug is prod-only, inspect the build output first.*
- **Pitfall: `as any` in a discriminated-union switch.** It compiles, works in dev, and gets silently eliminated by esbuild in production. *If a case must exist, its discriminant must be in the union type.*
- **Pitfall: hung full test suite.** Don't block the fix loop on it — run scoped vitest paths; save the full run for the end.
- **Pitfall: `prepareArguments` "not being called."** It *does* run before validation, but a tool re-registers at `session_start`; an already-running session won't see the new definition until reload/new session. Test the coercion fix in a fresh session.
- **Pitfall: `options.map is not a function`.** The LLM sent `options` as a JSON string. Guard with `Array.isArray` (and parse when it's a string) in both the renderer and the tool's execute.
- **Pitfall: committing a dirty tree.** Unrelated `known-servers` changes were mixed in; commit only the fix's files by explicit path.
