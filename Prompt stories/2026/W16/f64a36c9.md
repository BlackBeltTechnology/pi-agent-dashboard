# How we did it: Known-servers management — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened in explore mode with a loosely-worded feature idea:

> "/skill:openspec-explore — Change server management. Currently serverlist populated from current mDns list. In [I] would like to create a settings panel where the known remote servers — which displays the added servers and localhost — and in the server manager panel can be the mDns discovered servers displayed and it can be added as known server. I later would like to add key exchange for new servers."

The **real objective**, once the steering turns sharpened it: replace the *ephemeral, mDNS-only* server list with a **persisted "known servers"** model. Localhost + user-added remote servers live in config and survive restarts/offline peers; mDNS discovery becomes a *scan-and-add* tool inside a new Settings → Servers tab; adding a discovered server prompts for a label; and the whole thing works in the Electron shell too. Key exchange was explicitly deferred ("later").

## 2. TL;DR playbook

1. **Explore first** (`/skill:openspec-explore`) — let the AI map the *current* data flow (mDNS browser → `servers_updated`/`servers_discovered` → `ServerSelector` dropdown; only `lastServer` persisted) before touching design. Ask for a Mermaid diagram of "current vs. wanted".
2. **Create the proposal** with the one decisive constraint stated up front: *"When I add a discovered server I can give the label."*
3. **Fast-forward the artifacts** (`/opsx:ff`) → proposal → design → specs (`known-servers` NEW, `server-selector` MODIFIED) → tasks. 18 tasks in 6 groups (config types → server API → selector refactor → settings UI → Electron → docs).
4. **Ask the clarifying questions before applying**, not during. The two that mattered: *does Electron need it too?* and *probe-on-add or save-blindly?* Answers folded straight into design + tasks.
5. **Apply** (`/opsx:apply`) task-by-task, running the *scoped* `tsc --noEmit -p <pkg>` and the *single* new vitest file after each group — never the full suite.
6. **Verify** (`/opsx:verify`) against the spec; treat divergences as WARNING/SUGGESTION and fix immediately (state-sync gap, undocumented endpoints, spec wording).
7. **Prove it live**: restart the server, hit `POST /api/discover-servers`, wait a few seconds for mDNS to resolve remote peers, confirm a real machine shows up.
8. **Verify again → sync specs → archive** (`/opsx:verify`, sync delta→main, `/opsx:archive`).

## 3. How the collaboration unfolded

**Phase A — Discovery (explore mode).** The AI grepped the client/server/shared packages for `mdns|ServerSelector|known.*server`, read `App.tsx`, `browser-protocol.ts`, `config.ts`, and produced a Mermaid diagram of the *current* ephemeral flow plus a "what you want" split into two concepts (persisted Known Servers vs. transient discovery). *Why it worked:* grounding the design in the real message names (`servers_updated`, `servers_discovered`) and the real persistence gap (`lastServer` only) meant the proposal described a delta, not a greenfield.

**Phase B — Proposal + fast-forward.** With the label constraint given, the AI drafted proposal → design → two spec deltas → tasks.md. Design decisions were numbered so verification could reference them later. *Decision point:* the human deferred key exchange, keeping scope tight.

**Phase C — Pre-apply clarification.** Before writing code the AI surfaced two genuine ambiguities (Electron support; probe-on-add). The human answered crisply: *"1. Modify electron app too. 2. Save regardless availability. But on scan probe it."* Both were folded into a new task group + a numbered design decision — no rework later.

**Phase D — Implementation.** 18 tasks, marched in order: `KnownServer` config type + parser → REST types → `known-servers-routes.ts` (GET/POST/DELETE + `POST /api/discover-servers`) → route registration → client fetch helpers → `ServerSelector` refactored to read `/api/known-servers` → new `KnownServersSection` + `NetworkDiscoverySection` wired into a "Servers" tab → Electron loading-page fallback → AGENTS.md + architecture docs. Each group ended with scoped `tsc` + its own test file.

**Phase E — Verify / steer / re-verify.** First verification found a **state-sync gap** (`KnownServersSection` didn't notify the parent, so "Already added" badges went stale) plus undocumented endpoints and a spec-wording mismatch. Human said "fix"; AI added an `onChange` callback, documented the 4 endpoints, corrected the spec. Two later steering turns added the **"Manage servers…" dropdown shortcut** (`/settings?tab=servers`) and a live network sanity check. A final verify came back clean → sync delta specs to main → archive.

## 4. Prompts that worked

- **Goal prompt (`/skill:openspec-explore` + description).** Effective because it invoked explore mode *before* proposing — the AI mapped reality first. It could have been stronger by naming the constraint (label-on-add) and Electron scope in the very first message instead of leaking them across three steering turns.
- **"create proposal. When I add a discovered server I can give the label"** — a high-leverage one-liner: it committed to the artifact *and* pinned the single UX rule that shaped the whole add-flow.
- **"1. Modify electron app too. 2. Save regardless availability. But on scan probe it."** — the highest-leverage turn in the session. Two numbered answers closed the two real ambiguities and defined the probe/persist policy in one breath.
- **"fix"** (×2) — worked only because verification had already produced a precise, file-referenced findings list. The short prompt rode on the AI's own report.
- **"The scan shows mDns discovered server. Currently in network a macbook delegates itself in mDns"** — grounded the AI in a real-world test target, prompting the live restart-and-probe validation.

**Rewrite for next time:** fold the goal + label rule + "Electron too" + "save-blind, probe-on-scan" into the *first* explore prompt so the clarification round-trip is unnecessary.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Scope the feature to the web client only | "Modify electron app too" | State cross-shell scope (web + Electron loading page) in the proposal up front |
| Leave probe/persist policy implicit | "Save regardless availability. But on scan probe it." | Write the persistence-vs-reachability rule as a numbered design decision before apply |
| Ship UI sections that don't cross-talk | Verify caught stale "Already added" badges → "fix" | Add an `onChange`/refresh contract whenever two sibling panels share one data source |
| Implement extras outside the spec | Late request: "dropdown button navigates to server settings" → later folded into spec | Capture every UX shortcut as a spec scenario *when requested*, not post-hoc |
| Trust an empty discovery result | "a macbook delegates itself in mDns" | Restart server, then **wait several seconds** for mDNS to resolve remote peers before judging |
| Get stuck on the full test suite | "the full tests stuck. Ignore it" | Run only scoped `tsc -p <pkg>` + the single new vitest file per task group |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created in this session — it was a straight application of the existing OpenSpec chain (`openspec-explore` → `-ff` → `-apply` → `-verify` → `-archive`).

**Recommended skill to create:** a **"two-panel shared-state" checklist** for the client — whenever two Settings sections read the same list (here Known Servers + Network Discovery), require an explicit parent-owned refresh counter and an `onChange` callback on each child. This exact gap surfaced in verification and cost a fix round-trip; encoding it would let a future build ship it right the first time.

## 7. Pitfalls & dead ends

- **Full test suite hangs.** `npm test` (whole repo) stalled; the human said "ignore it." *Do:* run scoped `npx vitest run packages/<x>/src/__tests__/<file>.test.ts` and `npx tsc --noEmit -p packages/<x>/tsconfig.json` per group instead.
- **`tsc` noise from project refs.** Filter `TS6306`/`TS6307` build-info errors: `... | grep -v "TS6306" | head`.
- **Electron has no tsconfig.** `packages/electron` transpiles via its own bundler — `tsc -p` won't apply. Validate syntax by a plain parse instead of type-checking, and note it in the task.
- **Empty discovery right after restart.** `POST /api/discover-servers` returned `[]` because the mDNS browser started fresh and hadn't resolved peers yet — and local instances are filtered out. *Do:* wait, and cross-check with a raw mDNS scan of `_pi-dashboard._tcp` before concluding it's broken.
- **Spec/impl wording drift.** The spec said GET returns "plus a localhost entry" but the route returns only `config.knownServers` (client prepends localhost). Fixed by correcting the spec wording, not the code — behavior was already right.
- **Post-hoc features escape the spec.** The "Manage servers…" shortcut was built directly, then had to be back-filled into `specs/server-selector/spec.md` at verify time.
