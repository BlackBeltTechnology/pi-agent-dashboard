# How we did it: Thread the `ask_user` message body through the whole pipeline — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator hit a concrete UX bug and dropped the evidence in the first prompt:

> `/skill:openspec-explore` — "The input does not show the question in ask_user."
> followed by a real `ask_user({title, question, method: "input"})` payload where only
> the `title` rendered in the dashboard and the detailed `question` markdown vanished.

The *real* objective, once the exploration clarified it: **make the `ask_user` tool's
`message`/question body render for every method (input, select, multiselect) in the
dashboard**, the same way `ConfirmRenderer` already shows a markdown body under its title.
That meant tracing a three-layer data flow (tool schema → ui-proxy → client renderers),
writing an OpenSpec change for it, implementing it, and verifying it live in the browser.

## 2. TL;DR playbook

1. Kick off with `/skill:openspec-explore` **and paste the failing payload verbatim** —
   the concrete JSON is what lets the AI trace the exact layer that drops the field.
2. Let the AI map the full data flow first (tool `execute` → `ctx.ui.input()` → ui-proxy
   `extension_ui_request` → client renderer). Confirm the *root cause is multi-layered*
   before touching code.
3. `create a proposal`, then fast-forward the remaining artifacts
   (`/opsx:ff` → design → specs → tasks). Three capability specs here:
   `ask-user-tool`, `ui-proxy`, `interactive-renderers`.
4. `/opsx:apply` the change: broaden the `message` schema description to "all methods",
   pass `message` through the untyped `opts` bag in the tool, extract it in ui-proxy, and
   render `<MarkdownContent>` under the title in all three renderers (mirror ConfirmRenderer).
5. Add tests that assert `message` **is** forwarded (the old tests asserted it was absent).
6. `build and deploy`: `npm run build` → `curl -X POST /api/restart` → `npm run reload`.
7. **When the live check fails, suspect a stale browser cache first** — hard-refresh
   (Cmd+Shift+R) before debugging code.
8. `/opsx:verify`, then archive + sync specs. Commit, push, done.

## 3. How the collaboration unfolded

**Phase 1 — Explore & root-cause (02:07–02:54).** The AI grepped for `ask_user`/`ui-proxy`
across `packages/`, read the renderers, and produced a layered diagram: the tool schema
described `message` as "Additional context (for confirm)" so the LLM never used it for
`input` (it invented `question`, which was ignored); the tool `execute` for `input` only
forwarded `title`+`placeholder`; and `InputRenderer` had no body slot. *Why it worked:*
the pasted payload anchored the trace to a reproducible case, and the AI recognized
`ConfirmRenderer` as the working template to copy.

**Phase 2 — Author the OpenSpec change (02:54–03:21).** `create a proposal` → then the
operator ran the fast-forward and apply skill prompts to build design → 3 specs → tasks.
A side change, `fix-light-mode-button-contrast`, got applied in the same window (the
`/opsx:apply` with no name auto-selected it — see Pitfalls).

**Phase 3 — Implement (03:31–03:34).** 14 tasks across 4 groups: broaden schema
description, thread `message` through `opts`, add the `<MarkdownContent>` body to
Input/Select/Multiselect renderers, and add 11 tests. Full suite: 47/47 green.

**Phase 4 — Live verify & the cache trap (03:43–03:49).** The AI triggered real
`ask_user` calls to show the rendering. It *didn't* show — a multi-step debug ensued
(is the proxy patched? is `multiselect` patched? TUI-vs-dashboard race?) before the true
cause surfaced: `npm run build` writes to `packages/client/dist/` but a stale `dist/client/`
plus a **cached browser bundle** was being served. A hard-refresh fixed it instantly.

**Phase 5 — Verify, archive, ship (03:49–04:24).** `/opsx:verify` confirmed 14/14 tasks
and 6/6 requirements; the delta specs were corrected from `## MODIFIED` to `## ADDED`
before archive/sync. Then a git housekeeping tail: commit, confirm nothing uncommitted,
push 16 commits, and correctly identify a pre-monorepo `src/` stash as stale/unrelated.

## 4. Prompts that worked

- **The goal prompt** (`/skill:openspec-explore` + the failing JSON payload) — pasting the
  exact tool call is the single highest-leverage move. It turned a vague "input doesn't
  show the question" into a traceable, layer-by-layer root cause.
- **`create a proposal`** — short, decisive; converts an exploration into a durable
  OpenSpec artifact chain without over-specifying.
- **`oka, show every type with new fields in this session to be able to check it`** —
  forced the AI to audit whether protocol *types* needed changing (answer: no, `message`
  piggybacks on existing untyped `Record<string, unknown>` bags). A great "prove it"
  follow-up that prevents silent assumptions.
- **`ok. Show me with ask_user to be able to check now`** — demanding a *live* demo of the
  feature, not just green tests, is what surfaced the stale-cache bug.

Rewrite of a weak prompt: instead of `build and deploy` (ambiguous in a 3-component repo),
say **"rebuild client + restart server + reload bridge, then hard-refresh my browser"** —
it names all three rebuild targets and pre-empts the cache trap.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Auto-select the wrong change on a bare `/opsx:apply` (grabbed `fix-light-mode-button-contrast`) | Re-running apply with the intended change | Always name the change: `/opsx:apply ask-user-message-body` |
| Run the full test suite (which stalled the session) | "ignore full tests it stops session" | Scope tests to touched files: `npx vitest run <files>`, not the whole suite |
| Declare success on green tests alone | "Show me with ask_user to be able to check now" | Require a live browser demo before calling a UI change done |
| Assume the build was served (ignored stale `dist/`) | Debugging until the cache was found | Hard-refresh (Cmd+Shift+R) + verify the served bundle hash before deep debugging |
| Assume "nothing uncommitted" was the whole story | "there are changes not committed" / "check git" / "check the staged files" | Run `git status` + `git log --oneline origin/develop..HEAD` explicitly before claiming clean |

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created this session — it was pure feature work driven by
existing OpenSpec skills (`openspec-explore`, `/opsx:ff`, `/opsx:apply`, `/opsx:verify`).

**Skill worth creating:** a `debug-stale-client-bundle` note capturing the exact trap hit
here — `npm run build` → `packages/client/dist/`, server serves `../../client/dist`, an old
`dist/client/` and browser cache can both mask a fresh build; fix = restart + hard-refresh +
grep the served `index-*.js` hash. This recurs whenever a client change "doesn't show up".

## 7. Pitfalls & dead ends

- **Bare `/opsx:apply` auto-selected the wrong change.** Always pass the change name.
- **Full `npm test` stalled the session.** Scope vitest to the changed test files.
- **Stale build served two ways at once:** an old `dist/client/index-ChETYyJ9.js` on disk
  *and* a cached bundle in the browser. Neither reflected the new renderers. Verify the
  served hash (`grep -l MarkdownContent dist/.../index-*.js`) and hard-refresh.
- **`ask_user` can't demo `select`/`multiselect` from the agent's own invocation** — pi's
  tool harness won't pass the `options` array, so the dialog renders with no buttons. Use
  the `input` method to demo the message body live.
- **Delta specs used `## MODIFIED Requirements` for brand-new spec files** — archive/sync
  needs `## ADDED Requirements`. Fix before archiving.
