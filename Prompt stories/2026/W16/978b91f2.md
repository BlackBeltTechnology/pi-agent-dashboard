# How we did it: Make dashboard content views mutually exclusive — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened in explore mode with a rough bug report:

> "/skill:openspec-explore — There is a lot of contents are routed, but there are
> problems. When navigating to session opened resources, spec contents are not closed.
> When navigation happens in the content browser…"

Decoded: the dashboard's central **content area** shows one of many views (specs
browser, archive browser, README preview, OpenSpec preview, file diff, flow YAML,
pi-resources, flow/architect detail). Opening a *new* view failed to dismiss the
*previous* one. Because the views render through a first-truthy-wins `if/else if`
priority chain, a stale earlier view could mask the one the user just requested. The
real objective: make content views **mutually exclusive** — opening any one clears all
the others — without a heavy refactor.

## 2. TL;DR playbook

1. **Map the state, don't guess.** `grep` every content-view `useState` in `App.tsx`
   and trace the render priority chain. There were ~10 independent state slots.
2. **Name the root cause in one sentence:** openers set their own state but never clear
   siblings; only the session-change effect cleared some (incompletely).
3. **Choose the surgical fix** (user steered here): one `clearAllContentViews()` helper
   in `App.tsx` + an `onBeforeOpen` callback threaded into the hooks — no state
   consolidation, no context/reducer rewrite.
4. **Write the test first (TDD).** Add `useContentViews.test.ts` covering `clearAll`,
   `onBeforeOpen` firing on top-level opens, and the sub-navigation exemption. Watch it
   fail.
5. **Implement across 3 files:** `useContentViews.ts` (add `clearAll` + `onBeforeOpen`),
   `useOpenSpecActions.ts` (accept `clearAllContentViews` dep), `App.tsx` (define the
   helper, wire it into every opener).
6. **Exempt sub-navigation.** `handleViewPiResourceFile` drills *within* pi-resources —
   it must NOT clear siblings. Encode that as an explicit test + comment.
7. **Verify:** targeted vitest green → `tsc --noEmit` → `npm run build`. Confirm the
   pre-existing unrelated test failures are pre-existing.
8. **Update specs** (steered): add a "Content View Management" section to
   `docs/architecture.md` and refresh the `AGENTS.md` rows for the two hooks.
9. **Commit surgically** (steered): `git reset HEAD` the auto-staged noise, then
   `git add` only the 6 touched files and commit.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (grep-first, read-second).** The AI never opened a file blind.
It ran a broad `find`, then a wide `grep` for every content-view symbol
(`specsBrowserCwd`, `archiveBrowserCwd`, `previewState`, `readmePreview`,
`flowYamlPreview`, `diffViewSessionId`, `piResourcesState`, `architectDetailOpen`,
`flowDetailAgent`, …). It reconstructed the full `if/else if` render chain and located
the *only* place that cleared views (the session-change effect, lines 277-281) —
proving it cleared an incomplete subset. **Why it worked:** the model produced a
labelled inventory of all 10 state slots and the exact failure mechanism before
proposing any edit.

**Phase 2 — Design under a "surgical" constraint.** The AI's first instinct leaned
toward a broader restructure. The human's one-word steer — *"try surgical"* — pinned it
to the minimal design: a single `clearAllContentViews()` in `App.tsx` (where the state
lives) plus an `onBeforeOpen` hook callback so the extracted hooks can clear App-level
state without owning it.

**Phase 3 — TDD.** The AI wrote `useContentViews.test.ts` first, hit a missing-jsdom
error, inspected sibling tests + `vitest.config.ts` to learn the config expects a
`packages/client`-relative run, then got a clean red. It implemented until 4/4 green.

**Phase 4 — Wire every entry point.** The tedious part: every opener (sidebar
Specs/Archive, diff view, three *identical* inline `onViewAgentSource` JSX callbacks,
the OpenSpec actions hook) had to call the clear helper. The three identical inline
callbacks defeated unique-match edits, so the AI fell back to a `sed` global
replacement. It reasoned explicitly that `handleViewPiResourceFile`,
`onAgentClick`, and the architect toggle are **sub-navigation** already inside an active
content view and must be exempt.

**Phase 5 — Verify.** Targeted test green → `tsc --noEmit` → `npm run build`. Full
client suite showed 3 unrelated red files (`useSidebarState`, `useTheme`,
`TunnelButton`); the AI spot-checked and declared them pre-existing rather than laundering
them into the diff.

**Phase 6 — Specs + commit (steered).** *"update specs"* → new architecture section +
`AGENTS.md` row refresh. *"commit changes"* → the AI noticed a dirty index full of
unrelated changes, ran `git reset HEAD`, then staged only the 6 relevant files.
Result: commit `30ac3db`, 6 files, +128/-21.

## 4. Prompts that worked

- **Goal prompt (weak but salvageable):** the original bug report was typo-ridden and
  half-finished, yet it named the symptom ("spec contents are not closed") and the
  surface (content browser). That was enough because the AI front-loaded discovery.
  *Stronger version:* "In the dashboard content area, opening a new content view
  (specs/archive/readme/diff/flow-yaml) doesn't close the previously open one — they
  should be mutually exclusive. Find all the view-state slots and make opening any one
  clear the rest. Keep it surgical."
- **"try surgical"** — the highest-leverage token in the session. Two words redirected
  the design from a refactor to a single helper + callback. Bake scope constraints in
  early.
- **"update specs"** / **"commit changes"** — terse phase gates that worked *because*
  the repo's doctrine (architecture.md + AGENTS.md rows; surgical commits) was already
  known to the model.

## 7. Pitfalls & dead ends

- **jsdom missing:** the first vitest run failed on environment. Fix: run from
  `packages/client` (`cd packages/client && npx vitest run src/hooks/__tests__/...`) —
  the config expects relative paths and provides jsdom there.
- **Three identical inline callbacks:** exact-text `edit` can't uniquely match repeated
  identical lines. Fall back to a `sed` global substitution when the same snippet
  appears 3×.
- **`git add -A` trap:** the working tree had unrelated staged changes. `git reset HEAD`
  first, then add only your files, or the commit balloons.
- **Pre-existing red tests:** `useSidebarState`, `useTheme`, `TunnelButton` were already
  failing. Don't chase them — spot-check, confirm unrelated, move on.
- **Don't over-clear:** `handleViewPiResourceFile`, `onAgentClick`, and the architect
  toggle are sub-navigation inside an already-active view; clearing siblings there would
  kick the user out of the view they're browsing.
