# How we did it: Build & deploy `develop`, then unblock CI on the platform/exec ban — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff was terse: **"I switched branch to develop. build all and deploy."** The
*real* objective, once the steering turns clarified it, was broader: get a freshly
switched `develop` checkout building cleanly (a brand-new workspace package,
`subagents-plugin`, had appeared and broken the client build), deploy it to the local
dashboard, then chase down and fix the three CI failures that `develop` was red on —
all while keeping unrelated survivor-fix WIP out of the commit. It ended with a
recovery: the repo had gone into a **detached HEAD** after a rebase-and-push, and the
last steering turn ("the repo became headless") asked to reattach cleanly.

## 2. TL;DR playbook

1. On a fresh branch switch, run `npm run build 2>&1 | tail -30` first — let it tell you what's missing rather than guessing.
2. When the client build fails on a missing workspace symlink for a **new** package, fix the toolchain, not the code: `nvm use 22`, wipe `node_modules` + `package-lock.json`, `npm install --ignore-scripts`, rebuild.
3. Deploy via `POST /api/restart`. If it returns `{ok:true}` but the server never comes up (known recurring 10s-timeout bug), kill the stale PID file and spawn `node packages/server/bin/pi-dashboard.mjs start` directly; confirm `mode: production` on `/api/health`.
4. Run `npm run reload` to bump connected pi sessions (zero connected = fine, bridges auto-reconnect).
5. Before committing, `git status` + `git diff --stat` and **separate your build artifacts from pre-existing WIP**. Name exactly which files your change touched.
6. For the CI ban-rule failure, read the test that enforces it (`no-direct-child-process.test.ts`) to learn the exact required import path, then add the missing wrapper export (`execFileSync` in `platform/exec.ts`) before migrating callers.
7. For the self-heal test failures, make the conflict *real*: `fs.writeFileSync(oldPath, …)` into `tmpDir` so the existing bridge path exists on disk.
8. Verify locally with a scoped `vitest run` on just the failing files + `tsc --noEmit` on touched files; commit only the 6 fix files by explicit path.
9. Rebase onto origin, stashing unrelated WIP first (`git stash push -u`), push, then `git stash pop`.
10. If HEAD detaches after rebase/push, `git checkout develop` to reattach — WIP files carry over.

## 3. How the collaboration unfolded

**Phase 1 — Build recovery (Discovery → Fix toolchain).** The AI ran `npm run build`
and read the failure: the client was missing a workspace symlink for the brand-new
`@blackbelt-technology/pi-dashboard-subagents-plugin` package, which had never been
installed into `node_modules`. Rather than patch the client, it diagnosed this as a
stale install: switched to Node 22 (satisfies `engines`), wiped `node_modules` +
`package-lock.json`, ran `npm install --ignore-scripts`, then rebuilt clean (50-file
web bundle, 9.14 MB → 2.65 MB gzipped). *Why it worked:* a missing symlink for a new
workspace package is a lockfile/install problem, not a source problem — the fastest
fix is a clean reinstall on the right Node.

**Phase 2 — Deploy through a known-flaky restart.** `POST /api/restart` returned
`{ok:true}` but the new server never bound. The AI recognized this as a recurring
orchestrator bug (six prior failures in `restart.log` back to 2026-05-07), killed the
stale PID file, and spawned the server directly — up on :8000, `mode: production`, 7
plugins. `npm run reload` found no connected sessions (expected). *Decision point:* the
AI flagged the restart bug as **pre-existing and unrelated**, so it didn't rabbit-hole.

**Phase 3 — Commit scoping (the human slows it down).** On "commit", the AI found 27
changed files but correctly identified that **most were pre-existing survivor-fix WIP**,
not its build. It refused to blindly commit and instead enumerated exactly the three
build-artifact files. When the interactive `ask_user` prompt didn't return, it offered
a numbered menu of commit strategies rather than choosing silently.

**Phase 4 — CI fix (Diagnose → Migrate → Make-conflict-real → Verify).** The three red
tests were: (A) a ban-rule forbidding direct `node:child_process` imports outside
`platform/exec.ts`, and (B/C) two bridge-register conflict tests. The AI root-caused
both: `platform/exec.ts` had **no `execFileSync` export**, so the three electron
callers had nowhere to migrate — it added the wrapper (matching the existing
`execSync`/`spawnSync` pattern, `windowsHide:true`) first, then migrated the imports.
For B/C, the tests used fake `/old/bridge.js` paths that don't exist on disk, which
tripped the recently-added self-heal that silently downgrades conflict→ok — the fix was
to `fs.writeFileSync` the existing bridge into `tmpDir` so the conflict is *real*. It
verified with a scoped vitest run (all 32 tests pass) + `tsc --noEmit` on the three
touched electron files.

**Phase 5 — Push & recover from detached HEAD.** Rebased onto two incoming commits,
stashing unrelated WIP first, pushed `e2d3ae9b..c0cae13f`, restored the stash. Later,
the last steering turn ("the repo became headless") revealed HEAD had detached; the AI
confirmed `c0cae13f` was in `origin/develop` history with 4 more commits on top, then
`git checkout develop` reattached cleanly.

## 4. Prompts that worked

- **The goal prompt — "I switched branch to develop. build all and deploy."** Terse but
  effective *because it named the branch state and the two verbs (build, deploy).* A
  stronger version bakes in the guardrails learned later: *"I just switched to develop.
  Build (a new workspace package may need a clean reinstall) and deploy to the local
  dashboard. Don't commit anything — there's unrelated survivor-fix WIP in the tree."*
- **"On CI build" + pasted failure log.** High-leverage: pasting the raw vitest
  assertion (with the exact required import path and the three offender files) let the
  AI root-cause without a discovery loop. Always paste the full failing assertion, not a
  summary.
- **"What are the changes?"** A good verification checkpoint — forced the AI to produce
  a per-file diff table (+43/-12 across 6 files) before pushing.
- **"commit and push" / "commit".** Short, but the AI's own discipline (enumerate files,
  separate WIP) is what made them safe. Better: *"commit ONLY the 6 CI-fix files, leave
  the survivor WIP uncommitted."*
- **"the repo became headless."** Effective one-liner — the plain-language symptom was
  enough for the AI to diagnose detached HEAD and reattach.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat "commit" as commit-everything (27 files) | Implicitly, via the AI's own caution + the menu it offered | State up front: "commit only what my change touched; there's unrelated WIP" |
| Wait on a non-returning `ask_user` prompt | Nothing (the AI fell back to a numbered menu) | Prefer explicit instructions in-prompt over interactive prompts in headless/steered flows |
| Risk chasing the flaky `/api/restart` timeout | The AI flagged it as pre-existing/unrelated | Note known-flaky infra in AGENTS/memory so it's not re-investigated |
| Leave HEAD detached after rebase+push | "the repo became headless" | After any rebase-then-push, `git checkout <branch>` to reattach the local ref |

The quality bar the human imposed throughout: **surgical, scoped changes** — the AI
repeatedly stated net line counts and "nothing else touched," which matches the repo's
surgical-changes doctrine.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created in this session, but two patterns are clearly
repeatable and worth capturing:

- **"New workspace package broke the client build" → clean-reinstall recipe.** The
  `nvm use 22` → wipe `node_modules`+lockfile → `npm install --ignore-scripts` → rebuild
  sequence is a reliable fix any time a new monorepo package appears. Worth a project
  skill (or a row in the build FAQ).
- **"Ban-rule CI failure" → read-the-enforcing-test-first.** For any lint-as-test rule
  (`no-direct-child-process.test.ts`), the test itself names the exact migration target
  import. Adding the missing wrapper export *before* migrating callers is the ordering
  that avoids a broken intermediate state.

Recommend saving a project memory: *"/api/restart has a recurring 10s-timeout bug
(restart.log history since 2026-05-07); on failure, kill the stale PID file and spawn
`node packages/server/bin/pi-dashboard.mjs start` directly."*

## 7. Pitfalls & dead ends

- **`POST /api/restart` returns `{ok:true}` but server never binds** → don't retry; kill
  `~/.pi/dashboard/server.pid` and spawn the server directly, confirm on `/api/health`.
- **`platform/exec.ts` missing the wrapper you need to migrate to** → add the export
  first (match the `execSync`/`spawnSync` shape, default `windowsHide:true`); migrating
  callers before the wrapper exists leaves you with nowhere to point them.
- **Self-heal masks a conflict test** → the `add-plugin-activation-ui` self-heal
  silently downgrades conflict→ok when the existing path doesn't exist on disk; fake
  paths like `/old/bridge.js` never trigger a real conflict. Write the file into
  `tmpDir` first.
- **Rebase-then-push detaches HEAD** → local `develop` ref doesn't follow the rebased
  HEAD forward; `git checkout develop` reattaches, WIP carries over.
- **Committing on a dirty tree with survivor WIP** → always `git stash push -u` the
  unrelated WIP before a rebase, and add fix files by explicit path (never `git add -A`).
