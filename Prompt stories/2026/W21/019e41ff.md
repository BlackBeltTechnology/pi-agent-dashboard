# How we did it: Turning a 404-crash debug session into hardened install proposals — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a raw crash paste — no question, just a stack trace:

```
Failed to start dashboard: Error: listen EADDRINUSE: address already in use 0.0.0.0:8000
[tunnel-watchdog] recycling tunnel after 2 consecutive failures
```

The literal ask was "my dashboard won't start." But the **real objective** — which only surfaced through 17 steering turns — was much bigger: *prove whether `pi-dashboard` can be installed and run as a plain npm package with no Electron and no pre-installed pi, and if not, feed the exact failure modes back into the two open OpenSpec proposals* (`enable-standalone-npm-install`, `eliminate-electron-runtime-install`). The debugging was the vehicle; hardening the standalone-install spec was the destination.

## 2. TL;DR playbook

1. **Triage the port conflict first.** `lsof -nP -iTCP:8000 -sTCP:LISTEN` to find the holder; prefer `curl -X POST http://localhost:8000/api/restart` over hard kills.
2. **Separate "server up" from "UI served."** Health can be `200` while `GET /` is `404` — that split is the whole diagnosis. Always probe both.
3. **Trace the static-serve path** when `/` 404s: the server resolves the client bundle relative to its own `__dirname`; a re-extracted Electron bundle can wipe the `@blackbelt-technology` namespace out from under a running process.
4. **Escape the broken layout** — launch the server from the self-contained app bundle (`/Applications/PI-Dashboard.app/Contents/Resources/server/`) to confirm the code is fine and only packaging is broken.
5. **Get to a true standalone** via `pi-dashboard start`; fix the `bin` symlink if it points at `cli.ts` instead of `bin/pi-dashboard.mjs`.
6. **Reproduce against the published tarball** (`npm i -g …`) — this is where the real bugs live, not in the workspace.
7. **Cross-check every "bug" against a clean Docker baseline** before writing it into a proposal — local stale state masquerades as tarball bugs.
8. **Fold verified findings into the proposals** as new tasks/phases, then `openspec validate` both changes.

## 3. How the collaboration unfolded

**Phase 1 — Port triage (prompts 1–2).** The AI read the `EADDRINUSE` trace, found PID 1890 already on 8000, and offered restart-vs-reuse. `restart` returned `{ok:true}` but nothing respawned. Effective move: never trust the restart ACK — verify with `lsof` after.

**Phase 2 — The 404 hunt (prompts 3–7).** The user pasted screenshots of a stale error dialog repeatedly. The AI correctly separated the *stale launch-race dialog* from the *real bug*: server `200` on `/api/health` but `404` on `/`. It traced the static-serve lookup and discovered the Electron re-extract was wiping the `~/.pi-dashboard/node_modules/@blackbelt-technology/` namespace, leaving the running process alive only from in-memory modules. Symlink workarounds bridged the legacy layout but then fastify couldn't resolve. **Key decision point:** the user cut the loop with "Okay start dashboard server. No electron."

**Phase 3 — Escape to standalone (prompts 8–9).** Launching from the app-bundle copy (`/Applications/PI-Dashboard.app/Contents/Resources/server/`) finally gave `GET / → 200`. This proved the code was sound and only the user-dir extraction was broken. Then `pi-dashboard start` exposed a broken `bin` symlink (pointed at `cli.ts`, not the `.mjs` jiti wrapper) — repointing it got a clean `starter: Standalone` daemon.

**Phase 4 — Understanding the install contract (prompts 10–12).** The user pivoted to conceptual questions: does `pi-dashboard` bootstrap pi? register the bridge in `settings.json`? dedup old paths? The AI answered by *quoting `docs/faq.md` verbatim* and reading `bridge-register.ts` — discovering existence-based (not identity-based) cleanup, plus bridge over-registration across 4 install paths. It also caught its own mistake: pruning had wrongly matched a sibling `flows-anthropic-bridge` plugin.

**Phase 5 — True-standalone reproduction (prompt 13).** Fresh `npm i -g` against the published v0.5.3 surfaced four packaging bugs (missing `.mjs` wrapper, missing postinstall script, undeclared `jiti`, disagreeing jiti-name lists). Each got a workaround.

**Phase 6 — Fold into proposals + reality-check (prompts 14–18).** The AI mapped findings A–G into both proposals as new tasks/phases and validated. Then the crucial correction: a **Docker clean-baseline refuted several findings** (A and B were stale local state, not tarball bugs; D was already fixed by the archived earendil migration). The final "Remove ohmypi jitty" directive scrubbed obsolete `@oh-my-pi/jiti` from the *proposed* fix while retaining historical mentions.

## 4. Prompts that worked

- **The goal prompt (a raw stack trace).** Weak as a kickoff — it stated a symptom, not intent. It worked only because the AI triaged well. **Stronger version:** *"pi-dashboard crashed with EADDRINUSE on 8000. Triage the port, then I want to verify the full standalone npm-install path works end to end and feed findings into the two open proposals."*
- **"Frontend not found on 8000 = 404 Not Found"** — high-leverage: it forced the health-vs-static split that became the entire root cause.
- **"Okay start dashboard server. No electron"** — cut a multi-cycle relaunch loop dead. When a workaround loop stalls, name the constraint.
- **"Check proposal … because these proposals can be effected with the new findings"** — the turn that converted debugging into durable spec work.
- **"Is that will work on windows too (symlink?)"** — a single skeptical question that caught a Unix-only hack leaking into a cross-platform proposal.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was persisted this session, but the workflow is highly repeatable and **two skills should be created**:

- **`verify-standalone-npm-install`** (project) — captures: install published tarball → `pi-dashboard start` → probe `/api/health` AND `GET /` → cross-check against Docker clean baseline. Removes the trap of debugging stale local state and re-deriving the health-vs-static split every time.
- **`debug-dashboard-404`** — already partially covered by the existing `debug-dashboard` skill; extend it with the "health 200 + `/` 404 = static-serve path resolves to a wiped bundle" signature and the app-bundle escape hatch.

The session leaned effectively on existing assets: quoting `docs/faq.md` verbatim for the install contract, and reading `bridge-register.ts` for the real dedup semantics.

## 7. Pitfalls & dead ends

- **`curl -X POST /api/restart` returned `{ok:true}` but nothing respawned.** Don't trust the ACK — verify with `lsof` after.
- **Symlink workarounds bridged paths but fastify still couldn't resolve** — the real `node_modules` (with fastify) lived in the app bundle, not the user dir. Path-fixing ≠ dependency-resolving.
- **Bridge pruning regex over-matched** a sibling `flows-anthropic-bridge` plugin (parent dir `pi-agent-dashboard`). Restore from the `.bak` and scope the match tightly.
- **Findings A, B, D turned out false** against a clean Docker baseline — stale `npm link`, npm cache corruption, and an already-shipped migration fix respectively. Never write a "published bug" into a proposal without a clean-machine reproducer.
- **Electron always re-extracts and wipes the namespace**, so any user-dir symlink fix is temporary. The durable answer is the standalone/npm path, not patching the extract layout.
