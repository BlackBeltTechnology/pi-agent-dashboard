# How we did it: Scaffolding the "Automation plugin" OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened in **explore mode** (`openspec-explore`) — "think, don't implement" —
to design a new dashboard feature: **Automations**, background agent runs fired on a
trigger (schedule first) instead of a human clicking "New Session". The stated model was
"OpenSpec's plumbing carrying Codex's payload": clone the repo's existing folder-backed
OpenSpec feature (folder → watcher → poll → broadcast → content view) as the *structure*,
and steal OpenAI Codex Automations (triggers → background run → triage inbox) as the
*behavior*. The real objective, once steering clarified it, was **not code** but a
complete, validated OpenSpec **change proposal** (proposal + design + 4 spec deltas +
tasks + attached research) captured, committed, and pushed to `develop`.

## 2. TL;DR playbook

1. Enter `openspec-explore` — hold the "capture thinking as artifacts, never implement" stance.
2. **Gather both templates in parallel**: one `Explore` subagent to harvest the in-repo
   OpenSpec feature wiring; one `web_search` + `fetch_content` on the authoritative Codex
   Automations doc.
3. Lay the two side by side (STRUCTURE from OpenSpec ‖ BEHAVIOR from Codex); ask the human
   the ~5 open design decisions in one `ask_user` batch.
4. **Ground every decision that leans on existing machinery** before designing on top of it
   — spawn a second `Explore` to confirm the hidden-session + `@`-role selector patterns exist.
5. Run the pre-scaffold **coherence check** against active/archived OpenSpec changes —
   catch in-flight architectural direction that contradicts a decision.
6. `openspec new change add-automation-plugin`; write proposal → design → spec deltas →
   tasks; `openspec validate` after each pass.
7. Capture the research as an **attached `research.md`** inside the change and link it from
   proposal → References.
8. Commit **only the staged change files** (leave pre-existing unrelated edits alone);
   `git pull --rebase` when `develop` advanced, then push.

## 3. How the collaboration unfolded

**Phase 1 — Dual-template discovery (parallel).** The AI refused to theorize first. It
grounded itself in two references *at once*: an `Explore` subagent mapped how OpenSpec is
wired in *this* repo (the 6-concern spine), while `web_search` + `fetch_content` pulled the
canonical Codex Automations doc. Running both halves in parallel is the effective move —
the design started from evidence, not imagination.

**Phase 2 — Side-by-side framing + decision batch.** The AI drew STRUCTURE (OpenSpec) next
to BEHAVIOR (Codex) and surfaced the open decisions as a single `ask_user` batch. The human
answered tersely (`1. Core / 2. central / 3. match / 4. both … / 5. …`), which is exactly
what a batch enables — five design forks resolved in one turn.

**Phase 3 — Ground-before-build.** Two of the decisions (hidden-but-monitored sessions,
`@`-style model selector) leaned on machinery the AI wasn't sure existed. It spawned a
*second* `Explore` to confirm the patterns, which exposed a real gap: there is **no
"spawned-as-hidden" session class today** → automation runs need a new session `kind`, not
the existing hidden tier. Confirming the substrate before designing on it prevented a design
built on a false assumption.

**Phase 4 — The coherence check that forced a pivot.** Before scaffolding, the AI checked
active/archived OpenSpec changes and found `extract-openspec-as-plugin` — the team is
actively moving OpenSpec *out* of core into a plugin. The human had said **"core"**
(decision #1), but the repo's direction was the opposite. The AI surfaced this contradiction
*before* writing anything and the plan pivoted to **build Automation as a plugin**, mirroring
the slot architecture. This single check "earned its keep."

**Phase 5 — Generate + validate.** With the plugin contract grounded
(`packages/<name>-plugin/`, `pi-dashboard-plugin` manifest, `registerPlugin(ctx)`), the AI
wrote proposal, design, 4 spec deltas, and tasks — running `openspec validate` after each
pass and checking `git status` to confirm `openspec validate` didn't auto-mutate
`groups.json`.

**Phase 6 — Refine, attach research, ship.** Steering turns threaded "run visibility is a
setting, not forced-hidden" through all artifacts, then captured the research as an attached
`research.md` linked from the proposal. Final commit took **only** the staged change files,
rebased onto an advanced `develop`, and pushed — carefully stashing/restoring a pre-existing
unrelated `directory-service.ts` edit around the rebase.

## 4. Prompts that worked

- **The goal prompt** (the `openspec-explore` skill preamble): effective because it *fixed
  the stance* — "capture thinking as OpenSpec artifacts, never implement" — so the AI
  produced a validated proposal instead of drifting into code.
- **High-leverage follow-up — the terse decision list** (`1. Core / 2. central / 3. match /
  4. both, and can select the model … / 5. create spawning session which hidden …`):
  five design forks answered in one line. Batching decisions this way is the single biggest
  accelerator in the session.
- **"capture as an attached doc in related proposal"** — one short sentence that turned
  ephemeral research into a durable, linked `research.md`.
- **Rewrite of a weak prompt:** instead of "answer #4: both", prefer stating the constraint
  *and* the seam — "support both per-folder and global scope; expose a Create Automation
  button like New Session" — so the AI threads it through every artifact without a second pass.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted, but the session *exercised* three reusable moves worth
codifying:

- **`Explore` subagent for template harvest** — isolates a "map how X is wired here" read into
  its own context and returns only the skeleton. Invoke whenever a new feature must clone an
  existing in-repo pattern.
- **Pre-scaffold coherence check** (against active/archived OpenSpec changes) — the highest-ROI
  step here; it caught an in-flight architecture pivot before a single artifact was written.
  Invoke *before* `openspec new change`, always.
- **Parallel dual-grounding** (subagent + web fetch in one turn) — start any "clone structure
  from A, behavior from B" design by gathering both references simultaneously.

> **Recommended skill to create:** an `openspec-scaffold-from-template` skill that codifies
> *parallel dual-grounding → decision batch → coherence check → new change → validate-per-pass*.

## 7. Pitfalls & dead ends

- **"Core" was the wrong default.** If a feature seems to belong in core, first check active
  changes — the repo may be migrating that exact concept *out* to a plugin. Skipping the
  coherence check would have shipped a proposal contradicting the team's direction.
- **`openspec validate` can auto-mutate `groups.json`** and pick up unrelated edits — check
  `git status --short openspec/` after validating; here it was clean, but assume it isn't.
- **Push rejected because `develop` advanced.** `git pull --rebase origin develop` then push;
  no conflicts here.
- **A pre-existing unstaged edit sat in the tree** (`directory-service.ts`, not the AI's).
  Stash it before rebasing, restore after, and commit only the staged change files so unrelated
  work never rides along.
