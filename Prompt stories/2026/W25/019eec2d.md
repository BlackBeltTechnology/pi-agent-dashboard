# How we did it: Hunt zombie pi processes, then close a package-release gap — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a hunch, not a spec: _"Maybe there are zombie session - hidden but
active"_. The real objective — clarified by the AI's investigation — was **prove or disprove
the existence of hidden-but-active pi sessions, and if RAM is leaking, reclaim it safely
without killing real work.** The answer flipped the framing: the dashboard's records were
clean; the zombies were **OS-level orphaned `pi` processes** (`ppid==1`, no TTY) invisible to
the dashboard. The session then branched into a second, unrelated goal after the cleanup:
**find which workspace packages are unreleased, publish the one that was missing, and audit
that it's wired into every reference surface** (CI allowlist, client registry, Electron
bundle).

## 2. TL;DR playbook

1. **Don't trust the dashboard count alone.** Cross-reference `/api/health` live heartbeats
   against raw `ps` output — the gap *is* the zombie set.
2. **Classify before killing.** Filter to `command==pi`, `ppid==1`, `tty==??`; confirm age
   (`etime`) and RSS. Live-parent processes (recent `etime`, `ppid≠1`) are real work — leave
   them.
3. **Two-phase kill.** SIGTERM all, wait ~4s, SIGKILL only survivors. Then re-check
   `/api/health` `activeSessions`/`liveAgents` are unchanged.
4. **Capture the procedure as a skill** the moment it works — `reap-orphaned-pi-processes`
   with a bundled `reap.mjs` (dry-run default, `--kill`, `--older-than`).
5. **For the release audit:** compare local `package.json` versions against the npm registry
   for every workspace package; the diff is your "unreleased" set (excluding `private:true`).
6. **Before an irreversible publish, dry-run it** (`npm publish --dry-run`) and confirm
   tarball contents + version + access; then publish with explicit `--workspace` + `--access
   public`.
7. **Never assume "published = fully wired."** Audit the new package against a known-good
   sibling across CI allowlist, client registry, server refs, and the Electron
   `BUNDLED_PLUGINS` list — sync any surface the sibling has that yours lacks.

## 3. How the collaboration unfolded

**Phase A — Diagnosis (zombie hunt).** The AI queried `/api/sessions` and `/api/health`,
hit a jq failure on control-char titles, and switched to JS processing (`ctx_execute`). It
found 733 sessions total / 11 non-ended (matching health), then compared against 47 bare
`pi` OS processes — isolating **34 orphaned** (`ppid==1`, no TTY, up to 21 days old, ~4 GB
RAM). _Why it worked:_ it treated the dashboard and the OS as two independent sources of
truth and diffed them, instead of believing either alone.

**Phase B — Safe cleanup.** Two-phase SIGTERM→SIGKILL, then verified dashboard health
(`ok=true`, 11 sessions still heartbeating, 79% memory free). _Decision point:_ the human's
"create a skill for that" turned a one-off into a durable asset.

**Phase C — Skill hardening.** Built `reap.mjs`, dry-ran it, hit a real trap: the script
reused `PI_DASHBOARD_URL` (a `ws://` endpoint `fetch` can't use). Fixed to a dedicated
`PI_DASHBOARD_HTTP` var with `ws→http` normalization, and **recorded the gotcha in the skill**
so it isn't rediscovered.

**Phase D — Release gap analysis.** New goal: "what pi packages not released yet?" The AI
diffed all 17 public packages (all at 0.5.4) against npm and found exactly one never-published:
`pi-dashboard-automation-plugin`.

**Phase E — Manual publish.** Dry-run (45 files, 40.1 kB, tag `latest`, public), confirmed
irreversibility, published, verified live on the registry.

**Phase F — Reference audit + sync.** Compared the new plugin against the honcho-plugin
sibling. Found it correct everywhere (package.json manifest, CI `publish.yml` allowlist +
passing contract test, client `plugin-registry.tsx`, server refs) **except** the Electron
`BUNDLED_PLUGINS` list. Added `automation`, `goal`, and `subagents` plugins there. Root
cause: the npm publish allowlist has a completeness test; the Electron bundle list does not,
so drift went unnoticed.

## 4. Prompts that worked

- **Goal prompt** — _"Maybe there are zombie session - hidden but active"_: effective because
  it stated a **hypothesis to test**, not a fix to apply. This let the AI investigate and
  correct the framing (dashboard clean → OS-level orphans) rather than blindly killing things.
- **High-leverage follow-up** — _"create a skill for that"_: a 4-word prompt that converted a
  successful ad-hoc cleanup into a reusable, tested tool. Say this the moment any diagnostic
  procedure works.
- **Scope pivot** — _"what pi packages not released yet?"_: opened a clean second goal; the AI
  answered with a registry-vs-local diff table.
- **Guarded action** — _"I would like to publish manually to npmjs with 0.5.4"_: naming the
  exact version + "manually" told the AI to bypass CI deliberately, and it still dry-ran first.
- **Audit prompt** — _"Check that plugin referenced in proper way. Check CI and package json,
  and sync"_: the word **sync** licensed the AI to actually edit the drift it found, not just
  report it.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stop at a successful one-off cleanup | "create a skill for that" | Auto-offer to capture any repeatable diagnostic as a skill |
| Treat "publish to npmjs" as ambiguous (everything already at 0.5.4) | "publish manually to npmjs with **0.5.4**" | State the exact version + manual-vs-CI intent up front |
| Report the reference gap and ask | "…and **sync**" | Say "audit **and fix**" so the AI closes drift in one pass |
| Reuse an existing env var (`PI_DASHBOARD_URL` = `ws://`) | (self-caught during dry-run) | Use dedicated vars; never overload the bridge's WS URL for `fetch` |

Quality bars the human imposed implicitly: **safety before destruction** (confirm before
kill / publish), and **completeness** (don't declare "released" until every surface is wired).

## 6. Skills, tools & memory created — and why they're effective

**`reap-orphaned-pi-processes`** (global skill, `~/.pi/agent/pi-hermes-memory/skills/`):
- **Captures:** cross-referencing `/api/health` live heartbeats against `ps` to isolate true
  zombies (`command==pi`, `ppid==1`, `tty==??`), two-phase kill, then health re-verify.
- **Why effective:** removes the risky manual `ps | grep | kill` guesswork and guarantees real
  sessions (live-parent, heartbeating) are never touched. Ships `reap.mjs` so future runs are
  one command (`node reap.mjs --kill --older-than 7d`).
- **When to invoke:** any mention of zombie / hidden / stale / orphaned pi sessions, or RAM
  pressure from `pi` processes. It also encodes the `PI_DASHBOARD_HTTP` (not `PI_DASHBOARD_URL`)
  env-var trap so the next operator doesn't rediscover it.

**Missing skill worth creating:** a `release-reference-audit` procedure that, given a new
workspace package, diffs it against a known-good sibling across CI allowlist, client registry,
server refs, and Electron `BUNDLED_PLUGINS` — and flags any surface lacking a completeness
test. This session did it by hand; the Electron drift proves it's needed.

## 7. Pitfalls & dead ends

- **jq breaks on control-char session titles** → process JSON in JS (`ctx_execute`) instead.
- **`PI_DASHBOARD_URL` is a `ws://` endpoint** the bridge uses — `fetch` can't consume it.
  Use a dedicated `PI_DASHBOARD_HTTP` var and normalize `ws→http`.
- **zsh sandbox mangles `--include` globs** in `rg` → re-run the search in bash.
- **Contract test needs an ephemeral HOME** → run `publish-allowlist-complete.test.ts` with
  a temp HOME or it fails on your real config.
- **npm 0.5.4 is now permanently unpublishable** for every package — republishing an existing
  version is rejected. Bump to 0.5.5/0.6.0 to push anything new.
- **Electron `BUNDLED_PLUGINS` has no completeness test** — unlike the publish allowlist — so
  new plugins silently miss the desktop bundle. Add them manually until a guard test exists.
