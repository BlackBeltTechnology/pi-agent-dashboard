# How we did it: Retire the sidebar "View README.md" button — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **OpenSpec explore mode** (a thinking-only stance — investigate,
never implement). The user's real objective, though, was concrete: *remove the "README
button" and everything that hangs off it.* The word "README" was ambiguous — the
codebase has **two** README surfaces — so the true objective only crystallized after
the AI surfaced the ambiguity and the user picked one: retire the **project README
button** (the per-folder "View README.md" chip in the sidebar) and its full supporting
chain — overlay route, fetch hook, server endpoint, spec requirements — captured as an
OpenSpec change proposal, not as code.

## 2. TL;DR playbook

1. Enter explore mode (`/skill:openspec-explore`) so the session stays in
   think-and-capture, never implement.
2. Ask the AI to **map, not fix**: "find the README button and everything it touches."
3. When "README" is ambiguous, make the AI **name each candidate** (project README vs
   npm package README) and pick one before any tracing.
4. Have the AI trace the **full blast radius** of the chosen candidate — client props,
   state, routes, hooks, server endpoint, spec files, test files — as a dependency map.
5. Check OpenSpec conventions first: read a sibling change (`selectable-tool-output-links`)
   for the exact `.openspec.yaml` + `proposal.md` + delta-header format.
6. Scaffold the change by hand (no `openspec scaffold` subcommand exists): proposal,
   tasks, and spec deltas that **quote the exact requirement text** being REMOVED/MODIFIED.
7. Run `openspec validate <change> --strict` and fix header/intro mismatches until valid.
8. Commit **only** the proposal's own files — `git add openspec/changes/<change>` — and
   leave unrelated staged work untouched.

## 3. How the collaboration unfolded

**Discovery (disambiguate).** The AI immediately `grep`-ed for `readme` across
`src/client` and `packages/`, and found two independent features. Instead of guessing,
it drew two labeled candidate boxes (A = project README button → `/folder/:cwd/readme`
→ `/api/readme`; B = npm package README dialog) and asked the user which one. *Why it
worked:* one ASCII candidate map converted a vague noun into a binary choice.

**Trace (blast radius).** Once the user chose Candidate A, the AI produced a complete
dependency map — `SessionList.tsx` (prop, probe state, button), `App.tsx` (import,
`ReadmePreviewRoute`, route match, render branches), `hooks/useReadmeFetch.ts` (delete
whole file), `useContentViews.ts`, `route-builders.ts`, `back-target.ts`, and the
server `/api/readme` route. *Why it worked:* it read the real source ranges (`sed -n`)
rather than trusting grep line counts, so the map was exhaustive and surgical.

**Convention check.** Before scaffolding, the AI read a sibling change to copy the exact
`.openspec.yaml` schema, proposal structure, and delta-header style — and discovered
there is **no scaffold subcommand**, so files had to be written manually.

**Generate.** The AI wrote proposal.md, tasks.md (6 groups, 19 checkboxes), and two spec
deltas. It quoted the precise upstream requirement text so REMOVED/MODIFIED blocks match
the source spec verbatim.

**Verify.** `openspec validate --strict` initially failed on a wrong requirement header
("Depth-aware back action" vs the real "Back navigation button") and a missing intro
paragraph. The AI re-read the source spec, fixed the header + intro, re-validated → valid.

**Commit.** On the user's one-word "commit", the AI staged only `openspec/changes/
remove-project-readme-button`, deliberately leaving unrelated staged changes alone, and
committed `a8d0d374`.

## 4. Prompts that worked

- **The goal prompt** — the explore-mode skill preamble plus "find and remove the README
  button." A stronger kickoff would name the surface up front: *"In explore mode, scope a
  change to remove the **project** README button (the sidebar 'View README.md' chip), not
  the npm package README dialog."* — it removes the disambiguation round-trip.
- **High-leverage follow-up: "commit"** — one word, because the AI had already established
  the surgical-commit rule (only the proposal's files). Short works when scope is already
  pinned.
- The mid-session candidate pick (choosing A) was the highest-leverage decision: it
  collapsed the whole investigation onto one chain.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — the session rode existing project skills:

- **`openspec-explore`** kept the session in capture-not-implement mode, which is exactly
  right for a removal you want reviewed as a proposal before any code moves.
- **`openspec validate --strict`** was the quality gate that caught the header/intro drift.

*Recommended skill to create:* a **"scope a deletion as an OpenSpec change"** procedure —
grep → disambiguate candidates → trace blast radius via `sed` source reads → copy sibling
change format → write spec deltas with verbatim requirement text → validate strict →
surgical commit. This session is a clean template for it.

## 7. Pitfalls & dead ends

- **`openspec list --json` failed** (the one failed command) — don't rely on it; inspect
  `openspec/changes/` and `openspec/specs/` directly with `ls`/`grep`.
- **No `openspec scaffold` subcommand** — you must write `.openspec.yaml`, `proposal.md`,
  `tasks.md`, and `specs/*/spec.md` by hand. Copy a sibling change as the template.
- **Guessing a requirement header fails `--strict`** — the delta's MODIFIED block must
  reproduce the real header and intro paragraph exactly. Always `sed -n` the source spec
  first.
- **Ambiguous nouns waste a round-trip** — "README button" matched two features; naming
  the surface up front would have saved the disambiguation step.
