# How we did it: Scope a sidebar drag-reorder feature into a self-contained OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — a thinking-partner stance, not an
implementation run. The first prompt loaded the `openspec-explore` skill:

> "Enter explore mode. Think deeply… You may read files, search code, and
> investigate the codebase, but you must NEVER write code or implement features…
> You MAY create OpenSpec artifacts (proposals, designs, specs) if the user asks."

The *real* objective, once the steering turns landed, was: **turn a vague "the
sidebar can't reorder workspaces or folders" itch into a validated, self-contained
OpenSpec change proposal** — one that (a) mapped exactly which layers already
existed, (b) resolved collisions with other active changes, and (c) got committed
to `develop` with no stray files. The headline discovery: **the entire backend was
already built and unit-tested; only the client wiring was missing.**

## 2. TL;DR playbook

1. **Start in explore mode** (`openspec-explore` skill). State the "thinking, not
   implementing" contract so the AI grounds before it writes.
2. **Ground in the real code first.** Have the AI `grep`/`find` the DnD mechanism
   (`@dnd-kit`), the sidebar component (`SessionList.tsx`), and the server store
   before proposing anything.
3. **Trace the full pipeline per feature**: protocol message → handler → gateway
   route → store method → tests → client send. This is what surfaced that
   `reorder_workspaces` + `reorder_workspace_folders` were *already wired and
   tested* server-side, client-never-sends.
4. **Answer scope questions tersely** (the human used `1. / 2. / B` style numbered
   replies) to lock the four sortable surfaces: workspace, workspace-folder,
   pinned-group, session.
5. **Run the pre-scaffold coherence sweep** (grep active + archived changes for
   `drag|reorder|workspace`) *before* writing artifacts — it caught two colliding
   active changes.
6. **Scaffold with `openspec new change <name>`**, then write proposal.md,
   design.md, tasks.md, and `specs/<capability>/spec.md`.
7. **`openspec validate <name> --strict`** until it passes.
8. **Fold external dependencies into the change** when the human asks for
   self-containment (steering #4), then re-validate.
9. **Commit only your files** — inspect `git status`, exclude any pre-existing
   working-tree changes, commit with `git commit -F /tmp/commit-msg.txt`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding (Prompt 1).** The AI resisted the urge to
brainstorm and instead ran ~10 targeted greps to map reality: no existing DnD →
found `@dnd-kit` → found `SessionList.tsx` → traced the workspace mutation path
down to the websocket send. *Why it worked:* it refused to speculate about code it
hadn't opened, so every later claim was code-backed. **Decision point:** the AI
discovered `reorderWorkspaces` already existed server-side and reframed the whole
feature as "pure client work on a finished backend."

**Phase 2 — Scope lock (Prompts 2–3).** The human answered four scope questions
with a terse `1. dragged only / 2. B / 3. workspace and directories too / 4.
folders inside a workspace also stay reorderable`. The AI verified each answer
against code (e.g. confirmed "sessions stick to their folder" was *already* the
behavior in `handleDragEnd` at `SessionList.tsx:476`). It also separated two axes
the human had conflated: **movement scope** (where can a thing drop) vs.
**indicator visual** (does the dashed-slot highlight draw on this type).

**Phase 3 — Coherence gate (Prompt 4: "create proposal").** Per project
convention, the AI ran a pre-scaffold coherence sweep before writing. It found two
active changes colliding with scope: `fix-expanded-pinned-group-drag` (HARD overlap
— same `DndContext`/`handleDragEnd`, introduces `sameTypeClosestCenter`) and
`accordion-workspace-folders` (SOFT). It housed everything in one new capability
`sidebar-drag-reorder` to avoid delta-collision, then wrote all four artifacts and
passed `--strict`.

**Phase 4 — Self-containment (Prompt 5: "Ignore fix-expanded-pinned-group-drag,
accordion-workspace-folders").** The human wanted no external sequencing. The AI
promoted the `sameTypeClosestCenter` collision fix from a *dependency* to
*first-class task §1* in this change and dropped the adjacency note — then
re-validated `--strict`.

**Phase 5 — Clean commit (Prompt 6: "commit changes").** The AI spotted an
unexpected modified file (`directory-service.ts`, a `TICK_SLOW_WARN_MS` tweak it
didn't make), diffed it, confirmed it was pre-existing, and committed **only** the
5 proposal files (`c8ef0624`, 266 insertions), leaving the stray change in the
working tree.

## 4. Prompts that worked

- **The goal prompt (explore-mode skill load).** Effective because it set an
  explicit *no-implementation* contract, which pushed the AI into grounding-first
  behavior instead of premature code. A future operator should keep this stance for
  any "should we build X?" scoping session.
- **High-leverage follow-up — the numbered scope reply** (`1. dragged only / 2. B /
  3. … / 4. …`). Four decisions in one terse message. This is the ideal way to
  answer an AI's multi-question checkpoint: index your answers to its questions,
  no prose.
- **"create proposal"** — two words that triggered the whole scaffold+validate
  pipeline because the groundwork was already laid.
- **"Ignore fix-expanded-pinned-group-drag, accordion-workspace-folders"** — a
  single steering line that converted a dependency-coupled proposal into a
  self-contained one. High leverage because the AI already understood the coupling.

*Weak→strong rewrite:* Prompt 3 ("The sessions sticks to folders… Is this clarify
the open question?") was a question back to the AI. Stronger: state the constraint
as a decision — *"Sessions stay locked to their folder; that's not in scope.
Confirm the code already enforces this and move on."*

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The workflow leaned on existing
ones: **`openspec-explore`** (thinking stance) and the **project coherence-gate
convention** (sweep active/archived changes before scaffolding).

**Recommended skill to create:** a *"pipeline-gap audit"* procedure —
systematically trace `protocol message → handler → gateway route → store method →
tests → client send` for a feature, and report which layers exist vs. are missing.
This session's single biggest win (discovering the backend was 100% done) came from
exactly that trace; codifying it would make "is this front-end-only?" answerable in
minutes on any similar feature.

## 7. Pitfalls & dead ends

- **`openspec change new` is wrong** — the CLI verb is `openspec new change <name>`
  (the first form failed). If a scaffold command errors, run `openspec --help` /
  `openspec new --help` before guessing.
- **Several greps returned nonzero** (5 of 33 commands "failed") — mostly empty
  `grep` matches signalling *absence*, which was itself the signal (client wiring
  missing). Don't treat an empty grep as an error; treat it as evidence.
- **Stray working-tree file** (`directory-service.ts`, `TICK_SLOW_WARN_MS`
  5000→15000) was **not** part of the work. If `git status` shows a file you didn't
  touch, `git diff` it and exclude it — don't blanket `git add .`.
- **Delta-collision risk**: writing spec deltas that touch a requirement another
  active change already modifies causes merge churn. Housing everything in a *new*
  capability (`sidebar-drag-reorder`) sidestepped it.
