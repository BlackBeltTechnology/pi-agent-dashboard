# How we did it: Planning a directory home page (proposal → doubt-review → mockups) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance, not an implementation task. The real objective that crystallized: **plan a new
OpenSpec change** that adds a bare `/folder/:encodedCwd` **directory home page** for
pinned directories — a vertically-centered `CommandInput` prompt whose *send* spawns a
session (`initialPrompt = typed text`) and navigates to it, plus a folder header, an
existing-session list, and terminals/editor/settings quick actions. It doubles as the
folder's empty state. The deliverable was a **complete, doubt-reviewed planning package**
(proposal + design + specs + tasks + test-plan) *and* a token-grounded UX mockup — all
stopping at the `plan-proposal` worktree boundary, no implementation.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) to think without implementing, then let the
   `plan-proposal` orchestrator drive artifact creation.
2. **Ground first, propose second.** `kb_search` + targeted `grep` to confirm the transport
   already exists (`spawn_session { cwd, initialPrompt }`) and there's no route collision.
3. **Run a coherence check** against active + archived changes before scaffolding — avoid
   duplicating `new-spec-spawn`, `accordion-workspace-folders`, `directory-settings-page`.
4. **Scaffold** with `openspec new change add-directory-home-page`, write `proposal.md`.
5. **Doubt-review every load-bearing artifact** (`doubt-driven-review`): single-model pass,
   then a **cross-model** second opinion (`@propose-review-1` → non-Claude `glm-5.2`). Fold
   findings; **verify claims against source** before trusting them.
6. **Write `design.md`**, doubt-review it too — this is where a code-verified finding can
   *overturn* an earlier decision (it disproved the model picker → deferred).
7. **`scenario-design` → `test-plan.md` (12 scenarios) → fold into `tasks.md` (19 tasks)**,
   each test task carrying a copy-from exemplar pointer + its (input · trigger · observable) Triple.
8. **Mockup** with `frontend-mockup-loop-dashboard`: ground in real `index.css` tokens +
   `CommandInput`/`SessionCard` idioms, build a standalone token-driven HTML mockup, serve
   it live, iterate on the human's visual steering, write `ux-review.md` + `ui-plan.md`.
9. **Commit only the change directory** to `develop`; stop at the worktree boundary.

## 3. How the collaboration unfolded

**Phase A — Discovery & grounding (explore mode).** The AI ran `kb_search` per the
docs-first protocol, then `grep`/`find` to locate the real components: no `PromptView`
exists — the prompt is `CommandInput`; routes are `/folder/:encodedCwd/...` but there's
**no bare index page**; `spawn_session` already carries `initialPrompt`. *Why it worked:*
the proposal was grounded in verified code facts, not assumptions, so "send → create
session with prompt" needed **zero backend work**.

**Phase B — Decision-forcing questions + coherence check.** Before scaffolding, the AI used
`ask_user` to nail testable decisions (which directories are selectable, layout, quick
actions, model picker), then ran the mandatory pre-scaffold check against active/archived
changes. *Decision point:* the human's answers (pinned-only + empty-state + session list +
quick actions + model picker) revealed this was a **full directory home page**, not just a
centered prompt — captured in the design.

**Phase C — Doubt-driven review (the value-add phase).** Every artifact got an adversarial
pass: a single-model reviewer with **ARTIFACT + CONTRACT only** (no claim, no reasoning),
then a **cross-model** reviewer on a deliberately non-Claude-family model (`glm-5.2` via the
`@propose-review-1` role). Both converged and caught real bugs. *Why it worked:* fresh-context,
claim-free reviewers can't be anchored by the author's framing, and cross-model catches
family-correlated blind spots.

**Phase D — Specs, scenarios, tasks.** `scenario-design` produced a `test-plan.md` manifest
(12 scenarios), folded into a **parser-safe** `tasks.md` (19 vanilla checkboxes = 19 parsed
tasks), each test task pointing at the nearest harness exemplar (`FolderSpawnButtons.test.tsx`,
`LandingPage.test.tsx`, `editor-pane.spec.ts`).

**Phase E — Mockup & iterative visual steering.** The AI built a token-grounded standalone
HTML mockup (5 states × dark/light), served it live, and iterated through 6 visual steering
turns from the human (see §5). It even opened the **live running dashboard in a browser** to
study the real `FolderCard`/`SessionCard` sophistication, then read the actual `SessionCard.tsx`
source to reproduce its language 1:1. *Decision point:* the human demanded the **exact** rich
card format in both the sidebar and the content pane → the AI recorded a promote directive:
"one `SessionCard`, rendered in both places."

**Phase F — Commit.** Only the change directory (9 files) staged and committed to `develop`
(`728077368`); stopped at the worktree boundary per `plan-proposal`.

## 4. Prompts that worked

- **Goal prompt (explore-mode skill invocation).** Effective because it set a *stance*
  (think, don't implement) and let the `plan-proposal` orchestrator own the sequence. A
  future operator can skip straight to: *"Plan an OpenSpec change for a directory home page
  at `/folder/:encodedCwd`; ground it in the existing `spawn_session` transport; doubt-review
  proposal + design; produce specs/tasks/test-plan + a token-grounded mockup."*
- **"create mockups and ux review"** — a short, high-leverage unlock that pivoted from
  planning into the `frontend-mockup-loop-dashboard`, producing three concrete deliverables.
- **"use browser to get more sophisticated card design from current running dashboard"** —
  extremely high-leverage: instead of inventing card styling, it directed the AI to mine the
  *real shipped component* for fidelity. Bake this in: *"ground the mockup in the real
  components' source, not invented styling."*
- **"add the exact card format to left side session card list"** — forced 1:1 reuse and a
  promote directive, preventing UI divergence in the eventual implementation.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |

| Commit to `develop` without asking | The AI paused and confirmed before committing | Confirm the commit target when writing to a shared branch. |

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were *created*, but the session is a textbook execution of several
existing ones — the reusable assets are the **workflow compositions**:

- **`plan-proposal` orchestration.** Chains scaffold → doubt-review → scenario-design → fold
  → commit, stopping at the worktree boundary. Invoke whenever a change needs a complete,
  reviewed planning package before any code is written.
- **`doubt-driven-review` with cross-model second opinion.** The single-most-valuable move:
  a fresh-context reviewer sees **ARTIFACT + CONTRACT only** (no author claim), then a
  **non-Claude-family** model (`@propose-review-1` → `glm-5.2`) runs a second pass. It caught
  a `handleSpawnSession` signature bug and *overturned* the model-picker mechanism against
  source. Invoke on any irreversible/high-stakes decision before it stands.
- **`frontend-mockup-loop-dashboard`** grounded in real tokens + component source. Produces
  `index.html` + `ux-review.md` + `ui-plan.md` (surfaces → tokens → states control plane with
  a promote directive), so the eventual React implementation maps 1:1 with zero divergence.
- **`scenario-design`** → parser-safe `tasks.md`. Each test task carries a copy-from exemplar
  pointer + its (input · trigger · observable) Triple, making the tasks directly implementable.

*Recommendation:* a `ground-mockup-in-real-components` micro-skill would capture the
browser-inspect + read-source loop that gave the mockup its fidelity.

## 7. Pitfalls & dead ends

- **Edit batch aborted on a whitespace mismatch** (2 edit errors). When a multi-edit batch
  aborts on one `oldText` mismatch (e.g. the D3 whitespace), **re-read the exact region and
  reapply the whole batch** rather than guessing.
- **Playwright headless shell not installed** — `score_mockup` couldn't screenshot. Fallback:
  use the **`browser` tool** to open the live `serve_mockup` URL and capture states directly.
- **Browser scroll container wouldn't move** when studying the live dashboard's cards. Instead
  of fighting the browser, the AI **read the component source** (`SessionCard.tsx`) to extract
  styling precisely — faster and more accurate than screenshotting.
- **"Client-only, no server changes" is a claim to verify, not assume.** The model picker
  looked client-only but `pi.setModel()` is process-local and `spawn_session` has no `model`
  field — deferring it was the correct call.
- **Dashed-border layout shift.** Selecting a folder nudged the row until base rows were given
  a `1px dashed transparent` border of equal width. Add the transparent placeholder border
  from the start to avoid layout shift on selection.
