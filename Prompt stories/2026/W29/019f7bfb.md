# How we did it: Federate CodeGraph as a code-plane package family — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
no implementation. The real objective surfaced through steering: **decide how to bring
CodeGraph (a tree-sitter code-symbol indexer) into the dashboard given that our own `kb`
package already does the same *technique* on a different substrate — and capture the
decision as an apply-ready OpenSpec change.** The user wanted CodeGraph triggered
"same way as kb" (per-worktree lazy index, command-callable), but as a **separated**
extension/plugin family rather than folded into kb. The output is a fully-scaffolded
`add-codegraph-code-plane` change (proposal + design + spec + tasks) that supersedes an
existing, conflicting backlog change.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) — commit to thinking, not coding.
2. **Ground before opining**: fetch the external tool docs (`ctx_fetch_and_index` on the
   CodeGraph repo) *and* map the local analog (`kb` package internals) **in parallel**.
3. **Name the real axis**: same machinery (SQLite + FTS5 + graph, pull-based), different
   *substrate* (docs plane vs code plane). This reframes "integrate?" into "which
   architecture wins?".
4. **Search the backlog before scaffolding** (`openspec list`, read adjacent changes) —
   here it surfaced `add-kb-code-symbol-index`, the opposite ("absorb into kb") plan.
5. **Let the human pick the architecture**: federate (standalone family) vs absorb. The
   user chose federate + mirror kb's *3-slot* shape (core / extension / UI plugin).
6. **Scaffold via the CLI**: `openspec change new`, write `proposal.md`, add a spec delta,
   `openspec validate` until green; drop a **SUPERSEDED** banner on the conflicting change.
7. **Fold each follow-up question into the artifacts** (lazy lifecycle, Docker carry,
   Electron binary bundling) rather than answering in chat only — re-validate each time.
8. **Fast-forward** the remaining artifacts (`openspec-ff-change`) → `design.md` (9
   decisions) + `tasks.md` (9 dependency-ordered groups).
9. **Commit only your own files** — stage explicitly, exclude unrelated untracked work.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / Ground (parallel).** The AI fetched CodeGraph's docs and read
kb's `types.ts`, sqlite schema, and `extension.ts` tool-registration surface **at the
same time** via `ctx_batch_execute`. It refused to opine until both sides were mapped.
The payoff: it could state precisely that the two share machinery but index different
planes — the insight that drove every later decision.

**Phase 2 — Reframe & surface the conflict.** Before scaffolding anything, the AI ran
`openspec list` and read the adjacent `add-kb-code-symbol-index` change. That change was
the *opposite* direction (absorb tree-sitter into kb). Surfacing it turned the question
from "how to integrate" into "which architecture wins" — the highest-leverage move of the
session. **Decision point:** the human chose **federate** (standalone) over **absorb**.

**Phase 3 — Design the shape.** The human pushed twice: first "trigger like kb, per-
worktree lazy" (steering #1), then "don't integrate into kb — mirror it as a separate
plugin" (steering #2). The AI grounded each in the real kb layout, discovered kb is
actually **three** packages (core / extension / UI plugin), and mirrored all three as a
`codegraph-driver` / `codegraph-extension` / `codegraph-plugin` family — kb left 100%
untouched.

**Phase 4 — Explore open threads.** On "explore open threads" (steering #3) the AI
grounded three dormant facts (kb's unused `entity` node type, single-DB CTE graph walk,
the Docker peer-binary pattern) and folded sharpened stances into the proposal instead of
leaving bare "maybe later" bullets: read-time name-keyed cross-ref (not materialized
edges), measure-first unified explore, Docker `ARG CODEGRAPH_ENABLED=0` build-arg.

**Phase 5 — Fast-forward artifacts.** `openspec-ff-change` (steering #6) drove the
remaining `design.md` (9 decisions) and `tasks.md` (9 groups), each `openspec validate`d.

**Phase 6 — Two more folded questions.** "Ship the binary with electron build?" (steering
#7) became **decision D9 + a 5-rung resolution ladder** (`CODEGRAPH_BIN` → bundled →
PATH → `npm install -g` → hint), reusing the repo's proven `extraResource` + per-arch
download machinery. Then **commit** (steering #8): the AI checked `git status`, found
unrelated untracked work, and staged **only its 6 files**.

## 4. Prompts that worked

- **The goal prompt** (`openspec-explore` skill invocation): effective because it set a
  hard *thinking-only* stance — the AI investigated deeply and produced artifacts without
  prematurely writing code. Reproduce by explicitly entering explore mode for any
  "should we / how should we" architecture question.
- **"trigger like kb … per-project/worktree lazy index, command-callable"** (steering #1)
  — a high-leverage constraint. It anchored the whole lifecycle design to an existing,
  proven pattern instead of CodeGraph's default always-on watcher.
- **"don't integrate into kb — mirror it as a separate plugin"** (steering #2) — short,
  decisive, and *better* than the AI's own earlier "router inside kb-extension" idea. It
  unlocked the clean 3-package family.
- **"Explore open threads"** (steering #3) — a compact prompt that told the AI to harden
  the deferred/hand-wavy parts of the proposal. Weak-prompt rewrite: *"Ground and sharpen
  each deferred/Open-Questions item against the real codebase, then fold the stance in."*
- **"commit"** (steering #8) — worked because the AI already knew to isolate its own
  files. Stronger version: *"commit ONLY the files this session created; leave unrelated
  untracked work alone."*

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created — this was pure OpenSpec artifact production. The

## 7. Pitfalls & dead ends

- **Conflicting backlog change:** an existing `add-kb-code-symbol-index` proposed the
  *opposite* architecture. If you hit an adjacent change, resolve direction explicitly
  (here: **SUPERSEDE** + a one-line banner on the old proposal) so nobody implements both.
- **Ambiguous "Option B":** there was no open A/B/C fork, and the selection came back
  empty. The AI correctly declined to edit on a guess — mirror that: confirm intent before
  touching artifacts.
- **Task-group renumbering drift:** inserting new task groups renumbered headings but left
  sub-task numbers mismatched; a fixup pass was needed. After reordering `tasks.md`,
  re-check internal numbering and re-`openspec validate`.
- **Mixed working tree at commit:** unrelated untracked dirs (`scripts/ab-context/`,
  another change, a `groups.json` edit) were present. Stage explicitly by path; don't
  `git add -A`.
