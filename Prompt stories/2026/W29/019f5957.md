# How we did it: Root-causing "paired device stuck Offline" down to a one-line WS routing bug — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
no implementation allowed. The real objective, which only sharpened across the steering
turns: *figure out why every paired/remote device (phone browser, installed PWA) can
successfully complete QR pairing but then shows **"Offline"** and never receives session
data over the zrok tunnel — and capture the finding as an OpenSpec change proposal.*
Three symptoms were on the table at the start (P1 paired-but-no-backend, P2 PWA has no
pairing/key, P3 confirm code "sometimes hidden"); the whole exercise was to decide whether
these were three bugs or one, and to prove it before writing a single line of fix.

## 2. TL;DR playbook

1. Enter `openspec-explore` — think/investigate only, no code. Ground every theory in the
   actual pairing code and specs (`kb_search` + targeted `rg`/`read`) before theorizing.
2. Build the full mental model first: map QR mint → redeem → approve → bearer → `mintWsTicket`
   → `/ws?ticket=` upgrade, and mark *where each of the three symptoms could break*.
3. Trace the auth chain link by link (`bearer-auth.ts`, `paired-devices.ts`, `auth-plugin.ts`,
   `validateWsUpgrade`). Keep concluding "this code is correct" — that is a real result: it
   pushes the bug out of logic and into the **runtime transport layer**.
4. Let the human correct the app model ("it's a PWA, not Electron"; "browser WITH the key
   also fails"; "Android shares storage") — each correction collapses the three symptoms
   toward **one** root cause.
5. Stop reading code once static analysis is exhausted; **reproduce the failure live** against
   the running server's own zrok tunnel (mint a ticket over loopback, present it to `/ws`
   over zrok).
6. Compare ticketless vs ticketed upgrades: ticketless `/ws` → clean 401; **ticketed
   `/ws?ticket=…` → fails even on localhost**. That isolates the query-string as the trigger.
7. Read the upgrade handler: `server.ts` routes on `request.url === "/ws"` (exact match) →
   `/ws?ticket=…` falls through to `else { socket.destroy() }`. One-line bug found.
8. Scaffold the OpenSpec change with the CLI (`npx openspec new change …`), write proposal +
   delta spec (against `bearer-device-auth`) + design + TDD-first tasks, `validate`, commit
   **only** the change artifacts.

## 3. How the collaboration unfolded

**Phase 1 — Ground before theorizing (Discovery).** The AI resisted guessing. It ran
`kb_search` + a burst of scoped `rg`/`read` over `packages/server`, `packages/client`,
`packages/electron`, `docker/` to reconstruct the *entire* pairing/auth/WS-ticket flow, then
drew an ASCII map of the three device paths and annotated where each symptom could originate.
*Why it worked:* the map turned "three vague symptoms" into a small set of falsifiable code
paths.

**Phase 2 — Trace the auth chain, keep finding it correct (Analysis).** Link by link it
verified: bearer hook registered *before* the auth-plugin 401; registry persists to
`~/.pi/dashboard/paired-devices.json` (survives restart); `validateWsUpgrade` accepts a valid
ticket over the tunnel; `bearer-auth.ts` uses `deps.registry.verify` matching `server.ts`.
Repeatedly concluding "this is sound" was the key move — it *ruled out* auth and forced the
bug into the transport/runtime layer.

**Phase 3 — Human corrections reframe the whole picture (Decision points).** Three short
steering turns each collapsed the problem: "PWA, not Electron" removed the storage-isolation
theory; "browser WITH the key also can't connect" killed "the code is sound, just needs logs";
"Android shares storage" merged P2 into P1. The AI updated its model each time instead of
defending prior conclusions.

**Phase 4 — Reproduce live, not by inspection (Verify).** With static analysis exhausted, the
AI found the live standalone server on this very machine (v0.5.4, port 8000, zrok active),
minted a WS ticket over loopback, and drove real upgrades through zrok. Ticketless `/ws` → 401
(clean), `/api/health` etc → 200 (zrok proxies fine), but a **valid ticketed** `/ws` → failed —
including on localhost. That asymmetry (`?ticket=` present ⇒ reset) was the smoking gun.

**Phase 5 — One-line root cause + capture (Generate).** `server.ts:~1801` routes the main
browser socket with `request.url === "/ws"` while sibling routes use `startsWith`. `/ws?ticket=…`
misses the exact match, passes auth, then hits `else { socket.destroy() }` → client sees a bare
error → banner "Offline". The AI scaffolded the OpenSpec change (proposal, delta spec against
`bearer-device-auth`, design, TDD tasks), validated, and committed only the artifacts.

**Phase 6 — Correct a secondary claim (Integrity).** On the "reinstall zrok?" question the AI
first leaned "wrong version", then re-read the actual status codes (502/503/504 + 500 from
`api-v1.zrok.io`) and corrected itself: transient upstream zrok.io outage, **not** a client
version problem; zrok v1.1.11 is current. It amended the proposal/tasks and the commit.

## 4. Prompts that worked

- **The goal prompt** (`openspec-explore` invocation): effective because it fixed the *stance* —
  investigate and capture thinking, never implement — which kept the session in disciplined
  root-cause mode instead of jumping to a patch.
- **"but browser also cannot connect which have the key"** — a single high-leverage correction
  that destroyed the "code is sound" conclusion and forced the live reproduction that found the bug.
- **"No electron tested yet" / "PWA is the app, not Electron I tested"** — scope-narrowing
  corrections that collapsed three symptoms toward one.
- **"ws log check"** — unlocked the whole verification phase by pushing the AI from *reading* to
  *reproducing* against the live tunnel.
- **"What means reinstall zrock? Wrong version?"** — a skeptical challenge that caught and reversed
  a wrong secondary claim before it shipped in the proposal.

*Rewrite for next time:* front-load the environment facts the AI kept having to be told —
e.g. *"Target is the installed PWA on Android (shares Chrome storage); Electron is out of scope;
a normal browser tab that already holds the paired bearer also fails."* That one sentence would
have skipped several steering rounds.

## 7. Pitfalls & dead ends

- **Indexer-garbled greps.** Several `rg` outputs came back garbled; the fix was two clean `read`s
  of the specific file instead of trusting the search dump. *If your grep looks mangled, read the
  file directly.*
- **Chasing the zrok interstitial.** The top early suspect (interstitial hiding the WS) was ruled
  out fast — there was no interstitial. *Don't over-invest in the first plausible infra suspect.*
- **"Ticketless probe" red herrings.** Hand-rolled HTTP-upgrade probes returned confusing "ERROR []"
  results; switching to a proper WebSocket client (and comparing ticketless vs ticketed) is what made
  the signal clean. *Use a real WS client for upgrade tests.*
- **`npx openspec change new …` is the wrong subcommand** — it errored; the correct form is
  `npx openspec new change <name>`. Check `--help` when a CLI verb fails.
- **Attributing a 5xx to the client.** 502/503/504 = upstream gateway/service errors from
  `api-v1.zrok.io`, not a client version mismatch. *Read the status codes before blaming the local install.*
- **Don't sweep unrelated working-tree edits into the commit.** `openspec/groups/groups.json` had
  pre-existing local edits; they were deliberately left out so the commit contained only the change.
