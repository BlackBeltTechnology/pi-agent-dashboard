# How we did it: Bootstrap-publish the unreleased monorepo packages, then make CI report Trusted-Publisher gaps — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a scoping question: *"Is there any extension, plugin, skill
package in this monorepo which is not released to npmjs?"* That was an audit, not the
real objective. The follow-up made the intent concrete: *"make release npmjs byhand to
be able to access bi ci based release as trusted publisher which is not yet
published."* The real goal was a **two-part bootstrap**: (1) manually publish the
handful of public-but-never-published workspace packages to npmjs at the current
version so the package names exist on the registry, which is the precondition for
configuring GitHub OIDC **Trusted Publisher** per package; then (2) make the release
CI pipeline visibly report which packages still lack a Trusted Publisher, so the
remaining npmjs.com-side config is discoverable instead of silent.

## 2. TL;DR playbook

1. **Audit registry reality, not local flags.** For every workspace `package.json`,
   read `private` + `publishConfig.access`, then cross-check each public one with
   `npm view <pkg> version` — a package can be `"private": false` yet 404 on the
   registry (never actually published).
2. **Confirm auth** (`npm whoami`) before any write action.
3. **Dry-run first.** `npm publish --dry-run` each candidate to validate tarball
   contents; note which need a `prepublishOnly` build (here only `bus-client`).
4. **Publish in dependency order**, deps first so consumers resolve — root
   metapackage last.
5. **Verify with a delay.** New scoped packages have write-master vs read-CDN lag;
   an immediate `npm view` 404 does **not** mean the publish failed. An E403 *"cannot
   publish over the previously published versions"* on retry is *proof it succeeded*.
6. **Read the CI publish job** (`.github/workflows/publish.yml`) before patching —
   it may already be correctly wired for `--provenance` + `id-token: write` +
   `environment`.
7. **Audit Trusted-Publisher status via provenance attestations** (the only public
   signal) since the config itself is Cloudflare-walled and not exposed by the CLI.
8. **Enhance the publish loop** to classify each failure (OIDC/trusted-publisher vs
   generic) and emit a `$GITHUB_STEP_SUMMARY` gap report.
9. **Guard with the contract tests** (`publish-allowlist-complete`,
   `publish-workflow-contract`) — run them with an ephemeral `HOME`, and re-run after
   the edit to prove nothing broke.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / audit.** The AI enumerated all 35 workspace packages, split
them into *deliberately private* (`"private": true`), *public-but-unpublished* (404 on
`npm view`), and already-live. The key discipline: it did **not** trust the local
`private` flag — it queried the registry to find the 9 packages that claimed public
but had never shipped.

**Phase 2 — Bootstrap publish.** After confirming `npm whoami` (`robertcsakany`), the
AI ran `--dry-run` packs on all 9, then published for real in dependency order.
Decision point: the human's steering turns here were just *"go on"* — a signal the plan
was sound and only needed to proceed.

**Phase 3 — The `bus-client` scare.** One package's immediate verify returned 404. The
AI resisted the reflex to republish; it probed the packument, hit an E403 *"cannot
publish over previously published versions: 0.5.4"*, and correctly diagnosed **CDN
propagation lag**, not a failure. This is the single most valuable reasoning moment in
the session.

**Phase 4 — Read the CI wiring.** The AI inspected `publish.yml` and found it already
had `--provenance`, `id-token: write`, `environment: npm-publish`, npm ≥ 11.5.1, and an
idempotent skip-if-published guard. Conclusion: **no patch needed** for the mechanics.

**Phase 5 — Trusted-Publisher audit.** The human asked which packages still lacked a
Trusted Publisher. Every direct read was blocked (no CLI command; registry token
404/403; Cloudflare wall against curl *and* the automated browser). The AI pivoted to
**provenance attestations** as the public proxy — a version published via OIDC carries
one, a token publish does not — and audited all 32 published packages.

**Phase 6 — Ship the gap report.** The AI enhanced the publish loop to classify
failures and write a Markdown gap report to the job summary, verified the YAML +
shell locally, re-ran the two contract tests (21 pass), and committed **only**
`publish.yml` to `develop` (leaving unrelated untracked files alone).

## 4. Prompts that worked

- **The goal prompt** — *"Is there any extension, plugin, skill package... not released
  to npmjs?"* Good because it's a concrete, verifiable audit. It could have been
  stronger by stating the *downstream intent* (trusted publishing) up front, which
  only emerged in prompt 2.
- **High-leverage follow-up** — *"make release npmjs byhand to be able to access ci
  based release as trusted publisher which is not yet published."* This one sentence
  set the whole two-part objective and the safety bar (manual publish is a real write
  action).
- **The unlocking short prompts** — *"go on"* × 4, *"ok"*, *"yes"*. These worked because
  the AI had already laid out a clear ordered plan; the human only needed to authorize
  each safe step. Cheap steering when the plan is trustworthy.
- **The scoping redirect** — *"I set some. Is there any which does not have Trusted
  Publisher?"* Turned a done task into the real remaining question and triggered the
  provenance audit.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session, but two workflows are clearly
repeatable and *should* be captured:

- **`bootstrap-publish-unpublished-workspaces`** — audit workspaces against the live
  registry, dry-run, publish in dependency order, and correctly interpret CDN lag /
  E403-over-version. Removes the two biggest hazards (false 404 panic, wrong publish
  order) and makes the bootstrap safe to hand off.
- **`audit-npm-trusted-publisher-via-provenance`** — since Trusted-Publisher config is
  unreadable via CLI/token/browser, use provenance attestations as the public proxy to
  tell which package versions were OIDC-published. Reusable every release to spot
  packages that silently fell back to token publish.

## 7. Pitfalls & dead ends

- **Immediate `npm view` after publish returns 404** → do **not** republish. New scoped
  packages lag on the read CDN. Wait; an E403 *"cannot publish over previously
  published versions"* on retry confirms the write already landed.
- **Reading a piped `exit=` from `head`** misreported success/failure → run the publish
  with full unfiltered output when the status is ambiguous.
- **Trusted-Publisher config is not programmatically readable** → npm CLI has no
  command, a registry bearer token gets 404/403 on OIDC endpoints, and www.npmjs.com is
  Cloudflare-walled against both curl and the automated browser (loops the human-verify
  challenge). Don't burn time there — use provenance attestations instead.
- **Contract tests need an ephemeral HOME** → run vitest with `HOME=$(mktemp -d)` or the
  harness safety guard fails.
