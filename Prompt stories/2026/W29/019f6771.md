# How we did it: Toast card color — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened **explore mode** (`openspec-explore`) on a nagging UI bug: a
*successful* session spawn was rendering in a **red toast**. The literal first prompt
was the explore-mode skill banner ("Enter explore mode. Think deeply… you must NEVER
write code"), so the goal was framed as *investigate and think*, not *fix*.

The real objective, once the steering clarified it: **diagnose why message colors no
longer map to severity across the dashboard, prove it with a visual mockup, and — if
the direction lands — capture it as a fully-planned OpenSpec change ready for
implementation.** The end state was two commits on `develop`: a validated proposal
plus a doubt-reviewed, scenario-folded plan stopping at the git-worktree boundary.

## 2. TL;DR playbook

1. **Open explore mode** on the symptom, not the fix: `openspec-explore` → "why is a
   successful spawn showing red?" Let the AI audit before proposing anything.
2. **Make it find the smoking gun in code first** — `rg` every `showToast(` call site
   and the function's default variant. The root cause here: `showToast(text, variant =
   "error")` — any unmarked toast defaults to red.
3. **Demand a live visual mockup** (`serve_mockup`) showing current-state vs proposed
   scale side-by-side. A rendered before/after is what let the operator say "it seems ok"
   in one glance.
4. **Say "it seems ok" only after seeing it** — a one-word confirm is enough *because*
   the mockup carried the argument.
5. **"Save mockups to proposal"** — turn the design record into a scaffolded OpenSpec
   change (`openspec new change`), copying the mockup into `<change>/mockups/`.
6. **Run a coherence check before scaffolding** — grep archived changes so you don't
   duplicate already-shipped work (the archived `fix-session-status-colors` only touched
   card dots, not toasts).
7. **"commit"** — stage only your change dir, leave unrelated untracked files alone.
8. **Invoke `plan-proposal`** to run the planning phase: 3 doubt-review cycles
   (fresh-context + cross-model GLM), scenario-design HARD gate, category-fold into
   `tasks.md`, then stop at the worktree boundary.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / Audit (explore mode).** The AI followed the project's
docs-first protocol (`kb_search`), then `rg`'d every `showToast(` call site, the toast
component, and the status-color CSS tokens. It found the mechanical bug in seconds:
`SessionList.tsx:304` passes a *success* message with no variant, and `showToast`'s
signature defaults to `error`. It also mapped **three parallel color systems** (session-
status tokens, toast variants, raw Tailwind classes) that had drifted apart. *Why it
worked:* grounding the audit in exact file:line evidence made every later design claim
falsifiable.

**Phase 2 — Visual proof (`serve_mockup`).** The AI built a three-section HTML mockup —
current state (three red toasts, two of them lying), a proposed 5-tier severity scale,
and a migration view — and served it live. The human reviewed and replied "it seems ok".
*Decision point:* two open design questions (warning = orange vs yellow; default =
info-blue vs neutral-gray) were surfaced **before** scaffolding, then locked to orange
`#f97316` + neutral gray.

**Phase 3 — Capture as OpenSpec (`openspec new change`).** On "save mockups to proposal",
the AI ran a coherence check against archived changes, scaffolded
`unify-message-severity-colors`, read the *stale* `toast-notifications` spec (said
bottom-right; code is top-right), and authored proposal + design + two delta specs +
tasks, copying the mockup into the change. Validated `--strict`. Committed only its own
files on "commit".

**Phase 4 — Plan-proposal (doubt-review + scenario-design).** The big lift. Three
bounded doubt cycles, each pairing a Claude fresh-context reviewer with a cross-model
GLM (`@propose-review-1`) pass:
- **Cycle 1** killed the AI's *own* D3 claim — `notifyError` and two `SessionList` sites
  rely on the red default, so a naive default-flip would silently gray-out real errors.
  Also surfaced a duplicate `ToastVariant`, a 4th toast system (`ToastSlot`), and the
  single-accent-vs-muted-box gap.
- **Cycle 2** found blockers *in the cycle-1 fixes*: `--bg-card` doesn't exist
  (`--bg-tertiary` is the card token), one `color-mix` failed AA in light mode (~1.6:1),
  and a `:304` ternary can't take a trailing arg.
- **Cycle 3** caught `neutral` defined two incompatible ways (its `--text-muted` mix
  failed AA) → pinned to literal base tokens. Load-bearing tech (color-mix syntax,
  `CSS_VAR_KEYS`, hue retention) verified clean.

Then **scenario-design as a HARD gate** forced two `ask_user` decisions where the spec
had unfillable observable slots (AA across all 9 themes × light+dark; the still-working
info toast → neutral). Both closed, 15 automated scenarios folded into `tasks.md` with
harness-exemplar pointers, parser-safety verified (28 vanilla `- [ ]`), committed
`d0fc5acda`. Stopped at the worktree boundary.

## 4. Prompts that worked

- **The goal prompt (explore-mode banner).** Effective *because* it framed the work as
  "investigate, don't fix". That stance produced an evidence-grounded audit and a mockup
  before any spec was written. A future operator should open the same way: *"Explore
  mode: why is a successful spawn rendering as a red toast? Audit the color systems, don't
  fix yet."*
- **"it seems ok"** — a high-leverage one-word confirm. It only works because the mockup
  did the persuading. Lesson: invest in the artifact so the approval can be cheap.
- **"And save mockuops to proposal"** — short, unlocked the entire scaffold→author→validate
  chain. Stronger version: *"Turn this into an OpenSpec change; the section-3 migration
  becomes tasks.md, and copy the mockup into the change."*
- **"commit"** — trusted the AI to stage surgically. It did (only the change dir).
- **`plan-proposal` skill invocation** — one skill banner triggered the full doubt-review
  + scenario-design planning phase. High leverage: the orchestration skill composed the
  sub-skills faithfully without further prompting.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| stay in pure "think" mode | "it seems ok" → implicit go-ahead to capture | state up front: "if the direction lands, capture it as a proposal" |
| offer to stop the preview server / park it | "And save mockups to proposal" | say "capture it" directly rather than being offered park/quick-fix/capture |
| trust its own design claim (D3: default-flip is safe) | invoking `plan-proposal` (which ran doubt-review) | always route a proposal through doubt-review before implementing — the AI's own claims need adversarial checking |
| assume token names exist (`--bg-card`) | doubt cycle 2 caught it against real CSS | verify every referenced CSS var against the theme files before spec'ing it |
| define `neutral` two incompatible ways | doubt cycle 3 + AA check | pin passive tiers to proven literal tokens, not derived mixes, when contrast is load-bearing |

The dominant guardrail: **the AI's own reasoning was the biggest risk**, not the code.
Each doubt cycle found defects the AI had introduced in the *previous* cycle. The human's
job was mostly to keep the loop running (and approve the cross-model offer) rather than to
supply facts.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were saved this session — it was a *consumer* of existing
orchestration skills, and that's the reusable lesson:

- **`openspec-explore`** — the "think, don't implement" stance that produced an audit +
  mockup instead of a premature fix. Invoke when a bug's *shape* is unclear.
- **`serve_mockup`** — a live before/after HTML mockup turned a subjective color argument
  into a one-glance "it seems ok". Invoke whenever a design decision is visual.
- **`plan-proposal`** — the composed planning orchestrator (doubt-review × 3 →
  scenario-design HARD gate → category-fold → stop at worktree boundary). Invoke to take a
  scaffolded proposal to implementation-ready without hand-driving each sub-skill.
- **`doubt-driven-review` + cross-model reviewers** (`@propose-review-1` = GLM) — the
  engine that repeatedly caught the author-model's own blind spots. Its convergence signal
  ("both models converged hard") is strong evidence a finding is real, not noise.

*If anything should be saved:* a project memory that **`showToast`'s default variant is
`error`** — the single mechanical root cause worth never rediscovering.

## 7. Pitfalls & dead ends

- **Trusting the author-model's design claim.** D3 ("default-flip is safe") was false;
  real error sites relied on the red default. *If you flip a default, first grep who
  depends on the old one.*
- **Referencing CSS vars that don't exist.** `--bg-card` was assumed; the real card token
  is `--bg-tertiary`. *Verify every var against the theme CSS before spec'ing.*
- **`color-mix` toward the wrong anchor fails WCAG.** One formula hit ~1.6:1 in light mode.
  *Mix `fg` toward `--text-primary` (theme-flips) so one formula passes AA in both modes.*
- **Ternary can't carry a trailing arg.** `showToast(...)` at `:304` needed an explicit
  `if/else`, not a ternary, to pass the variant. *Watch for call sites that need a shape
  change, not just a value change.*
- **Stale specs mislead.** The `toast-notifications` spec said bottom-right; the code
  renders top-right. *Read the spec AND the code before writing a delta.*
- **Doubt theater risk.** The operator stopped the loop at 3 cycles once findings were only
  detail-tuning. *Bound the loop; don't run cycles that only rubber-stamp.*
