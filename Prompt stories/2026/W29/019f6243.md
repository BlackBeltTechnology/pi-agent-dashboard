# How we did it: Scoping "Reset override to npm" as an OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance, no implementation. The operator's real objective: capture, as a validated
OpenSpec change, a new Packages-settings feature that lets a user reset a
locally/git-installed extension back to its published npm version. The initial premise
was that the dashboard *doesn't detect* source overrides — but the codebase already had
`isSourceOverride()` driving an informational "override" pill. The true ask, once the AI
surfaced that fact, narrowed to: **add the missing *action* (Reset to published version)
on top of the existing detection, and capture it as a proposal + design + specs + mockup
+ tasks** — all without writing any application code.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) so the AI investigates before proposing.
   Explore mode's guardrail — "capture thinking, never implement" — is exactly right for
   spec work.
2. **Let the AI ground the premise in real code first.** It grep-walked the classifier,
   `PackageRow`, the operations API, and `RECOMMENDED_EXTENSIONS` and discovered detection
   already ships — reframing "build detection" into "add the action."
3. **Anchor the new op on prior art.** The AI found `/api/packages/move` (atomic
   install-new + remove-old) and modeled the new `reset-to-npm` op on it.
4. **Scaffold the change** with `npx openspec new change <name>` (not the wrong
   `openspec change new`), then write `proposal.md` + `design.md` capturing the two
   decisions: atomic install-first, confirm-gated.
5. **Validate early and often** (`npx openspec validate <name>`) — it forces a real spec
   delta and catches invented capability names.
6. **Add a faithful mockup** — ask "create a mockup, part of the proposal." The AI built
   a self-contained dark-theme `mockup/index.html` from real `PackageRow` theme tokens,
   served it, screenshotted it, and wired a `## Mockup` section into the proposal.
7. **Steer the scope explicitly** when you want it broader ("extend to installed
   extensions, show npm/git link on local rows"). The AI renamed the wire field and
   updated proposal + design + spec together.
8. **Commit each milestone** ("commit") — scoped to just the change dir + `groups.json`
   bookkeeping, leaving unrelated files alone.
9. **Finish the artifact set** with `openspec-continue-change` → `tasks.md`
   (dependency-ordered, TDD-first). Commit. 4/4 artifacts done.

## 3. How the collaboration unfolded

**Phase 1 · Discovery (grounding the premise).** The AI opened by refusing to take the
"detection is missing" premise at face value. It ran a series of scoped greps
(`recommendedPlugin`, `isSourceOverride`, `override`, `RECOMMENDED_EXTENSIONS`) across
`packages/client` and `packages/server`, read `package-classifier.ts` and `PackageRow.tsx`,
and inspected the operations API. **Why it worked:** it discovered `isSourceOverride()`
already renders the amber override pill — so the gap was the *action*, not detection. This
reframing saved the whole change from re-building existing behavior.

**Phase 2 · Design (anchor on prior art).** The AI found `/api/packages/move` — an
existing atomic install-new-then-remove-old route — and proposed the new `reset-to-npm`
op as a sibling of it. It locked two decisions with the operator: **atomic install-first**
(never leave the user with neither source) and **confirm-gated** (overrides are often
intentional dev-checkout links). Decision point: the human accepted both.

**Phase 3 · Scaffold + validate.** First attempt `openspec change new` failed; the AI
checked `--help` and used the correct `openspec new change`. It wrote `proposal.md` and
`design.md`, then let `openspec validate` drive it: validation demanded a real spec delta,
and flagged that the AI had invented a non-existent capability (`dashboard-packages-api`).
The AI corrected course — the op belonged in the existing `package-management` capability
(where `move` lives) — and re-validated clean.

**Phase 4 · Mockup (make it visual).** On "create a mockup," the AI read the real
`PackageRow` render + theme tokens and built a faithful dark-theme `mockup/index.html`
walking six labeled states (override row → ⋮ menu → confirm → in-progress → success →
partial success). It served it (`serve_mockup`), screenshotted via the browser tool, saved
`states.png`, and wired a `## Mockup` section into the proposal.

**Phase 5 · Scope expansion (human-driven).** The operator steered broader: show the
npm/git link on local rows, and extend detection beyond *recommended* extensions to **any**
local install with a resolvable published variant. The AI treated this as a genuine design
change — renamed the wire field `recommendedNpmSource` → `publishedVariantSource`, added a
new "Installed Extensions" scope state to the mockup, and propagated the change across
proposal + design + spec, flagging the npm-name-collision risk for implementation time.

**Phase 6 · Commit + finish.** Two "commit" turns; each time the AI scoped the commit to
just the change dir + auto-regenerated `groups.json`, leaving unrelated `.bak` files and a
separate change untouched. A final `openspec-continue-change` turn produced the last
artifact, `tasks.md` (8 dependency-ordered, TDD-first groups). Committed. 4/4 done.

## 4. Prompts that worked

- **Goal prompt — `openspec-explore` skill invocation.** Effective because it set an
  explicit *stance* (investigate, don't implement) that made the AI ground the premise in
  real code before proposing anything. This is what caught the "detection already exists"
  reframe.
- **"Create mockup which part of proposal"** — terse but high-leverage: it unlocked a full
  faithful visual + screenshot + proposal wiring in one phase. Stronger version: *"Build a
  faithful mockup from the real PackageRow theme tokens, screenshot it, and attach it to the
  proposal's ## Mockup section."*
- **"When local is installed show the npm / git link also. And extend the scope the
  installed extensions…"** — a precise scope expansion. It named both the UI change and the
  detection-scope change, so the AI propagated it across all artifacts consistently.
- **"attach to proposal" / "commit"** — short unlock prompts that moved milestones forward
  once the AI had the context.

The session had **no hard corrections** — the value was in the AI's own grounding discipline
plus one deliberate human scope expansion. The guardrail worth internalizing: **describe the
full scope (which row types, which install sources) in the first prompt** so the mockup and
specs don't need a second pass.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The workflow leaned on **existing** skills
that proved effective and are worth re-invoking:

- **`openspec-explore`** — its "capture thinking, never implement" stance is what forced the
  code-grounding that reframed the whole change. Invoke it whenever a feature idea's premise
  might be wrong or partially built.
- **`openspec-continue-change`** — produced the final `tasks.md` from already-loaded context.
  Invoke it to fill the remaining artifact in a change without re-deriving the design.

**Recommended skill to create:** an *openspec-mockup* helper that, given a change name and a
target component, reads the real theme tokens + component render, builds a self-contained
`mockup/index.html`, serves + screenshots it, and wires the `## Mockup` proposal section —
the exact 5-step dance this session did by hand.

## 7. Pitfalls & dead ends

- **Wrong CLI verb.** `npx openspec change new <name>` fails — the correct form is
  `npx openspec new change <name>`. If scaffolding errors, check `openspec new --help`.
- **Inventing a capability name.** The AI first put the op in a non-existent
  `dashboard-packages-api` capability; `openspec validate` (indirectly) exposed it. Fix:
  place spec deltas in the *existing* capability that owns the neighboring op (here
  `package-management`, home of `move`) — don't mint a new capability for a sibling op.
- **Validation demands a real spec delta.** A proposal without a `MODIFIED`/`ADDED` spec
  delta won't validate. Copy the delta format from an existing spec before writing.
- **Commit scope creep.** `openspec new` auto-regenerates `groups.json`; a stray `.bak` and
  an unrelated change were also in the tree. Stage only the change dir + `groups.json`.
