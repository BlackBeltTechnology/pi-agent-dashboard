# How we did it: Hardening the scenario-design gate in `plan-proposal` — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The operator opened with:

> "Update plan-purpose skill to call scenario-design skill to add scenario based test tasks"

The literal ask ("make plan-X call scenario-design") was already satisfied — `plan-proposal`
already had a Step 3 that ran `scenario-design` and folded its rows into `tasks.md`. Once the
AI surfaced that, the *real* objective clarified: not to *add* the call, but to **make the
existing call mandatory and enforceable** — a hard gate that blocks the worktree/commit
boundary unless scenario-derived test tasks actually exist. The deliverable was a single
tightened `.pi/skills/plan-proposal/SKILL.md`, committed to `develop`.

## 2. TL;DR playbook

1. Locate the real skill first: `ls .pi/skills/ | grep -i plan` and
   `grep -rl "scenario-design" .pi/skills/*/SKILL.md`. ("plan-purpose" was a typo for
   `plan-proposal`.)
2. Read the target SKILL.md and check whether the requested behavior **already exists**
   before editing.
3. When it exists but is weak, reframe the task as *enforcement*, not *addition* — confirm
   this with one `ask_user` before changing anything.
4. Strengthen at three coordinated points: (a) the step header/intro → "MANDATORY — never
   skip"; (b) a new completeness gate before the boundary step; (c) a precondition on the
   boundary step + matching Guardrail bullets.
5. Make each gate **verifiable**, not aspirational: "if `test-plan.md` doesn't exist,
   re-invoke"; "every manifest row maps to exactly one task, count-checked".
6. Commit narrowly: `git add .pi/skills/plan-proposal/SKILL.md` + a message that names the
   three reinforcement points.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (don't trust the skill name).** The AI ran one `bash` recon command
(`ls | grep plan` + `grep -rl scenario-design`), discovered there is no `plan-purpose`, and
read `plan-proposal/SKILL.md`. It found Step 3 already invoked `scenario-design`. *Why it
worked:* one cheap grep prevented building a redundant "new" integration on top of an
existing one.

**Phase 2 — Confirm intent (the pivot).** Instead of silently editing, the AI used
`ask_user` to confirm: the behavior already exists, so what do you actually want? This turned
a vague "add a call" into a concrete "harden the existing call into a gate." *Decision point:*
the human confirmed enforcement was the goal.

**Phase 3 — Coordinated edits.** Two `edit` calls tightened three interlocking spots so the
gate can't be sidestepped: the step became "MANDATORY — never skip" with a re-invoke check,
a new fold-completeness gate was inserted before the boundary step, and the boundary step
gained a precondition plus two Guardrail bullets ("no `test-plan.md`, no commit" / "fold
every manifest row"). *Why it worked:* a rule is only a gate if the enforcement lives at the
choke point (the commit/worktree boundary), not just in prose above it.

**Phase 4 — Commit.** One scoped `git add` of the single file + a descriptive message;
landed as `b6bd243f7` on `develop`.

## 4. Prompts that worked

- **Goal prompt** (`"Update plan-purpose skill to call scenario-design…"`) — weak as written
  (wrong skill name, asked for a call that already existed). It still worked *only because the
  AI verified first*. **Stronger version:** "Check whether `plan-proposal` already invokes
  `scenario-design`; if it does, make that invocation a mandatory, verifiable gate that blocks
  the commit boundary — don't just add a call."
- **High-leverage follow-up:** `"commit"` — a one-word unlock once the edits were confirmed
  good. Effective because the AI had already staged a clear, scoped change.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Take the skill name literally (`plan-purpose`) | Rely on the AI's grep to find the real skill (`plan-proposal`) | State "find the actual skill; the name may be a typo" up front |
| Risk adding a redundant "new" scenario-design call | The AI self-corrected via `ask_user`: "this already exists — what do you want?" | Ask the operator to specify *add vs. enforce* in the goal prompt |
| Describe rules procedurally (prose only) | Implicit quality bar: make it a **hard, verifiable** gate | Say "enforce at the boundary with a re-invoke/count check, not just prose" |

The key correction was structural, not textual: the human didn't retype the goal — the AI's
own `ask_user` reframed a "typo'd add request" into an "enforcement request," and the human
confirmed. Preserve that reflex: **verify existence before editing a skill.**

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this session *hardened an existing skill*
(`plan-proposal`). The reusable lesson worth capturing: **when asked to "make X call Y,"
first check if it already does; if so, convert the ask into an enforcement/gating task.** The
pattern for gating a skill step is reusable:

1. Rename the step "(MANDATORY — never skip)" and add a re-invoke check on its output
   artifact.
2. Insert a completeness gate (every input row → exactly one output task, count-verified)
   before the irreversible boundary step.
3. Add a precondition on the boundary step + Guardrail bullets that restate the block.

If this "harden a skill step into a verifiable gate" move recurs, it justifies a small
skill of its own.

## 7. Pitfalls & dead ends

- **Wrong skill name.** "plan-purpose" doesn't exist; it was `plan-proposal`. If a named
  skill isn't found, grep for the *behavior* (`grep -rl "scenario-design"`) instead of
  trusting the name.
- **Redundant work risk.** The requested feature already existed. If you hit "add a call to
  Y," first `grep` for Y in the target file — you may only need to *strengthen*, not add.
- **Prose-only rules aren't gates.** A rule stated above the boundary step is skippable. Put
  the enforcement (precondition + re-invoke/count check) at the choke point.
