# How we did it: Tracing "Subagent not found" to a v4/v7 id collision, then planning the fix — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
no implementation. The operator had hit the dashboard message *"Subagent not found in this
session"* when expanding a subagent card, and wanted to understand **why the log disappears**.
The real objective, once the first steering turn landed a concrete id, was: **trace one
specific subagent id (`019f71d4-c7f0-7cec-aea4-7fd771b9431a`) end-to-end through the stack,
find the root cause, and — after the trace held up — plan an OpenSpec change that fixes it.**

The trail led to a clean root cause: every foreground subagent is minted with **two unrelated
ids** — a v4 `randomUUID()` `agentId` (the only key the parent's `subagents` map ever sees)
and a v7 time-ordered runner *session* id. A v7 session id landing in the `:agentId` URL slot
always misses the v4-keyed map → "not found." The session ended by producing a fully
doubt-reviewed OpenSpec planning change (`resolve-subagent-inspector-by-session-id`).

## 2. TL;DR playbook

1. **Stay in explore mode for the trace.** Don't jump to a fix — the id's *nature* is the whole story.
2. **Demand a concrete id.** "Trace" is unactionable without one; the operator supplied `019f71d4…`.
3. **Follow the id through every store, in order:** repo grep for the error string → `~/.pi/dashboard/server.log` (50 MB, grep the id) → on-disk stores (`dashboard.db`, `preferences.json`) → **live server API** (`/api/sessions`) because live state lives in RAM, not on disk.
4. **Check the UUID version** (`python3 -c "import uuid; uuid.UUID(sid).version"`). v4 vs v7 was the decisive clue — different id spaces, minted by different generators.
5. **Read the producer source in `node_modules`**, not just the repo — the emit side (`@blackbelt-technology/pi-dashboard-subagents/extensions/agent.ts:932`) is out-of-repo; the repo only ships the *consumer* (inspector).
6. **Save the root cause** to durable memory (fell back to a memory when stores were full — see §7).
7. **Switch to `plan-proposal`** to author the OpenSpec change; run the built-in **doubt-driven cross-model review** and let it loop until artifacts stabilise.
8. **Fold scenario-design → tasks.md**, validate (`openspec validate`), commit to `develop`, and **stop at the worktree boundary** (planning ≠ implementation).

## 3. How the collaboration unfolded

**Phase 1 · Discovery (why the card is empty).** The AI grepped the repo for `"Subagent not
found"`, read the source, and explained the data-flow quirk: the Agent card is stitched from
**two stores** — `tool_execution_start/end` details feed the header (survives refresh), while
`subagent_*` frames feed `session.subagents` (a Map that a late-subscribe for a still-running
subagent misses). Effective because it separated *symptom* (empty body) from *mechanism* (two
sources, one survives) before touching a single id.

**Phase 2 · Trace the id (evidence, not guesses).** With `019f71d4…` in hand, the AI walked
every store **in order of authority**: repo → 50 MB `server.log` (grep + `sed` windows) → stale
on-disk `dashboard.db`/`preferences.json` → **live server API** (the reveal: state is in RAM).
Big finding: `019f71d4` is **not a nested subagent** — it's a standalone dashboard-spawned pi
session (`source=dashboard`, own `.jsonl`, `parentSession` pointer to a *different* lineage
`019f71ae`, first msg "Fix stale kb entries"). Reading the transcript head confirmed it was an
unrelated forked session, now ended.

**Phase 3 · Root cause (the id-version tell).** The AI read the producer's spawn loop in
`node_modules`, found `agentId = randomUUID()` at `agent.ts:932`, and — decisively — checked
UUID versions: `agentId` is **v4**, `019f71d4…` is **v7**. Different generators, different stores,
never cross-referenced. It then ruled out every in-app path that could feed a session id into the
`:agentId` slot (grep for URL builders + producers came back empty) → conclusion: only a
**hand-built / stale deep-link URL** reaches the not-found path.

**Phase 4 · Plan (with adversarial review).** The operator switched to `plan-proposal`. The AI
ran a pre-scaffold coherence check (not a duplicate), confirmed the **producer is a separate
GitHub repo** (so the change owns only the consume half + names the producer as a prerequisite),
scaffolded the OpenSpec change, then ran **`doubt-driven-review` cross-model on `@propose-review-1`
(glm-5.2)** — **3 cycles**, each surfacing real findings that were verified against source:
cycle 1 moved the new field onto `AgentDetails` (so the after-refresh backfill path works), cycle
2 caught alias-lifecycle edges, cycle 3 **simplified** the whole design — alias becomes *derived*
(an O(≤64) scan of the already-bounded `snapshots` map) instead of a tracked map + `finished` set,
dissolving several findings at once. Then folded 14 scenario rows into `tasks.md`, validated, and
committed to `develop`.

**Decision points the human owned:** (2) supplying the id; (3) `b` = "trace the spawn/forwarding
path"; (4) `yes` = save the root cause; (5) invoking `plan-proposal`; and mid-plan, choosing
**option D (full dual-key, both halves in one proposal, producer as documented prerequisite)**.

## 7. Pitfalls & dead ends

- **On-disk stores are stale.** `dashboard.db` was months old and `sqlite3 .schema` failed; the
  live map lives in **server RAM**. → Query the running server's `/api/sessions` (get the port
  from `config.json`), don't trust the DB.
- **Both memory stores were full.** The `add` to project memory and to the failure/insight store
  both hit capacity. → The AI fell back to a tighter entry, then noted a **skill** is the better
  home for a procedure anyway. If you hit capacity, prefer a skill for how-to knowledge.
- **The producer isn't in the repo.** The emit code (`agentId` mint, frames) is
  `@blackbelt-technology/pi-dashboard-subagents` in `node_modules` (separate GitHub repo); this
  monorepo only ships the inspector. → A true dual-key needs a producer version bump (`>= 0.2.3`);
  scope the in-repo change to the consume half and name the producer as a prerequisite.
- **Frame-only fields miss the after-refresh path.** Doubt-review cycle 1 caught that putting the
  new `agentSessionId` only on `subagents:*` frames leaves the `tool_execution_end` backfill (the
  actual refresh case) unaliased. → Put it on `AgentDetails` so it flows through **both** paths.
- **2 bash commands failed** (`sqlite3` on the stale DB; a port-resolution one-liner) — recovered
  by switching to `preferences.json` + a python port read.
