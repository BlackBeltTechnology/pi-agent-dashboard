# How we did it: Stabilizing the session-card PROCESS line — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a "think, don't
implement" stance. The real objective, surfaced over the first two turns: the
dashboard **session card's PROCESS subcard jumps around in height during a run**. It
mounts when the first `bash` tool starts, grows a row per concurrent tool, shrinks as
tools finish, and unmounts entirely at idle — so every tool start/stop reflows the
grid and neighbouring cards visibly jump. The user wanted this explored, designed,
and captured as an OpenSpec change proposal — **without writing implementation code**.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore`) — state up front: *think + design + write
   OpenSpec artifacts, but no implementation code*.
2. **Observe before theorizing**: open the live dashboard in the browser and watch the
   real jumping behaviour; don't reason about layout from source alone.
3. Read the actual owning component (`SessionCard.tsx` → `ProcessSubcard` →
   `SessionActivityBar` + `ProcessList`) to map the exact `return null` guards causing
   the mount/unmount.
4. Grab the real theme tokens (`index.css`) and build an **interactive mockup**
   (`serve_mockup`) that lets the user *play* BEFORE vs AFTER and measure pixel heights.
5. Verify the user's structural hypotheses against evidence (is it a plugin slot or
   core?) — correct the mental model with grep proof, not assertion.
6. Discover reuse: the "one line + expand + persist" pattern **already exists**
   (`ProcessList` drawer + `useDrawerExpansion`) — fold both surfaces into it.
7. Promote the on/off decision to a real setting (`DisplayPrefs.reserveProcessLineAtIdle`)
   with global default + per-session override, mirroring `contextUsageBar`.
8. Run the **pre-scaffold coherence check** (sweep `openspec/changes/archive/` for
   related/contradicting changes) before writing anything.
9. Scaffold proposal + design + tasks + spec deltas; `npx openspec validate <change>`.
10. Commit **only** the scaffold files surgically (`git add` the change dir), leaving
    unrelated working-tree changes untouched.

## 3. How the collaboration unfolded

**Phase 1 — Observe the real behaviour (browser first).** The AI's first instinct was
to grep source, but it immediately pivoted to *watching the live dashboard in the
browser* (30 browser calls across the session) before theorizing. This is the single
most repeatable move: it saw the PROCESS region jump during actual tool execution
rather than guessing from JSX.

**Phase 2 — Map ownership in code.** Read `SessionCard.tsx` and found the jump source:
`ProcessSubcard → return null` when no activity, and `SessionActivityBar → return null`
when `tools.length === 0`, with each in-flight `bash` mounting its own row. Every
mount/unmount reflows the grid.

**Phase 3 — Interactive mockup as the design surface.** Pulled real theme tokens and
built `mockups/index.html`, served via `serve_mockup`. The mockup measured concrete
numbers — **BEFORE 134px (neighbours pushed) vs AFTER 83px stable** — and let the user
toggle policies live. Decision points were *felt*, not argued.

**Phase 4 — Correct the mental model, then find reuse.** The user hypothesized "a
plugin renders it." The AI tested that with grep, **disproved it** (only
`session-card-badge/-desktop/-flows/-memory` slots exist; PROCESS is core), and in
doing so discovered the drawer's existing collapse/persist pattern
(`useDrawerExpansion` / `processDrawerCollapsed`) — so the fix became "unify both
surfaces under a pattern that's already built."

**Phase 5 — Promote the toggle to a real setting.** When the user said the reserve
line "should be a global settings parameter," the AI found the purpose-built
`DisplayPrefs` system (already does global default + per-session override for
`contextUsageBar`) and mapped the new `reserveProcessLineAtIdle` field onto it exactly.

**Phase 6 — Coherence check → scaffold → surgical commit.** Ran the mandatory
archive sweep first (confirmed clean delta on archived
`redesign-process-list-activity-bar`), wrote proposal/design/tasks + 4 spec deltas,
`openspec validate` → valid, then committed only the 8 scaffold files.

## 4. Prompts that worked

- **The goal prompt** (the `openspec-explore` skill invocation): effective because it
  established a firm *stance* — think and design and capture artifacts, but never
  implement — which kept a 2-hour session from drifting into premature coding.
- **"Currently processes presented at process, I think plugin renders it"** — a
  short, wrong-but-productive hypothesis. It's high-leverage because it forced the AI
  to *prove the ownership map with evidence*, which is exactly how the reusable drawer
  pattern got discovered. A wrong hypothesis stated plainly beats vague uncertainty.
- **"The reserve line in idle be a global settings parameter"** — one sentence that
  turned a hardcoded design pick into a proper `DisplayPrefs` setting with override.
  Effective because it named the *mechanism class* (global setting), letting the AI
  find the existing plumbing rather than invent new config.
- **"it seems OK" / "commit"** — terminal approvals that closed phases cleanly.

Rewrite of prompt #2 for next time: *"Confirm whether the PROCESS region is rendered
by a plugin slot or inline in SessionCard — show me the slot registrations as proof."*

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created. The session leaned on existing infrastructure,
and the reusable lessons are worth capturing:

- **`serve_mockup` + interactive HTML mockup as a design artifact** — captures a
  design decision as something the user can *play with and measure* (134px vs 83px),
  not a paragraph. The mockup then ships inside the OpenSpec change (`mockups/index.html`)
  as living documentation. Invoke it whenever a layout/UX change needs the human to
  *feel* the before/after.
- **Recommended memory to save**: *"For any dashboard on/off display behaviour, check
  `packages/shared/src/display-prefs.ts` first — `DisplayPrefs` already provides
  global default + per-session override (see `contextUsageBar`); add a field there
  rather than new config."* This would have shortcut Phase 5 directly.
- **Recommended memory**: *"PROCESS/activity region of the session card is CORE
  (`ProcessSubcard` in `packages/client`), not a plugin slot. Only
  `session-card-badge/-desktop/-flows/-memory` are plugin slots."* Prevents re-litigating
  the ownership question.

## 7. Pitfalls & dead ends

- **zsh glob on unquoted `*.tsx`** — a `find`/`grep` command tripped on the unquoted
  glob. If a bash tool errors on a glob, quote the pattern (`"*.tsx"`) or use `find -name`.
- **Apostrophe broke the commit heredoc** — `git commit -m "$(cat <<'EOF' … the card's … EOF)"`
  failed on the apostrophe. Fix: write the message to `/tmp/commit-msg.txt` and use
  `git commit -F /tmp/commit-msg.txt`.
- **`curl http://localhost:8000/api/health` failed once** — transient; retried with
  `-o /tmp/health.json` and it succeeded. Don't over-interpret a single failed health probe.
- **Design v1 was a dead end** — the first "first tool + `+N ⌄` chip" design was
  discarded once the real code revealed the drawer already solved half the problem.
  Reading the owning component early would have skipped v1 entirely.
