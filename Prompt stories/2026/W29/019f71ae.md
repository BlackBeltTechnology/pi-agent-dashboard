# How we did it: From "fix stale KB entries" to a fully-reviewed OpenSpec refactor proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff prompt was three words: **"Fix stale kb entries"**. On its face a
maintenance chore — `kb dox lint` was reporting 107 issues. But once the AI
cleared the stale rows, the *real* objective surfaced through four steering turns:
understand **why** the residual `over-threshold` flags couldn't be auto-cleared,
decide whether the DOX system was *designed* to split them, and — when the answer
was "no, by design" — turn that finding into a **fully-planned, cross-model-reviewed
OpenSpec proposal** (`fold-oversized-agents-directories`) for the directory-foldering
refactor, stopping cleanly at the git-worktree boundary. The session travelled the
whole distance from *janitorial fix* → *root-cause analysis* → *planned refactor*.

## 2. TL;DR playbook

1. **Triage the lint first, don't fix blindly.** Run `kb dox lint --json`, bucket
   issues by `kind` (`stale` / `missing` / `missing-companion` / `over-threshold`)
   with a small `node -e` script. Attack the cheap structural wins before the row-by-row work.
2. **Kill whole issue classes structurally.** The 25 `missing`/`missing-companion`
   issues were all from `Prompt stories/` (narrative, not source) — one exclusion in
   `packages/kb/src/dox.ts` + `npm run build` cleared them all.
3. **For stale rows, diff purpose-vs-source, don't rubber-stamp.** Build a side-by-side
   (row purpose vs current file exports). Of 72 stale rows only **4 had material drift**;
   the rest were sha-drift on accurate summaries → refresh hashes.
4. **When a flag *can't* be auto-fixed, ask the tool why before guessing.** Read the
   DOX source + CLI (`AGENTS_BYTE_CAP` vs `ROW_CAP`, `split-large-agents.mjs`) to learn
   the byte cap has an official auto-fix and the row cap does **not** — by design.
5. **Turn the finding into a proposal.** `openspec new change <name>`, then write
   `proposal.md` / `design.md` / `tasks.md` / `specs/*/spec.md` grounded in the
   two-category split (rollup dirs = doc-only fix; flat source dirs = real refactor).
6. **Run `plan-proposal` end-to-end.** doubt-driven-review (cross-model, auto on
   `@propose-review-1`) → verify every finding against real code → reconcile across all
   four artifacts → scenario-design manifest → category-routed fold into `tasks.md`.
7. **Commit at the boundary, keep unrelated work separate.** The tree mixed the
   *stale-fix* work with the *planning* artifacts — split into **two commits** so the
   planning commit stays clean. Stop before spawning the worktree.

## 3. How the collaboration unfolded

**Phase 1 — Triage & structural wins (Discovery).** The AI's first move was *not* to
edit rows but to understand the staleness mechanism and exclusion config. It bucketed
107 issues by kind and spotted that 25 came from `Prompt stories/` — narrative
session-playbooks, exactly the shape of the already-excluded `research`/`mockups` dirs.
One exclusion line + rebuild cleared them. **Why it worked:** killing a whole issue
*class* structurally beats fixing 25 rows individually (and avoided forcing 18 forbidden
rows onto the root `AGENTS.md`).

**Phase 2 — Stale-row diff, not rubber-stamp (Gather).** For the 72 stale rows the AI
built a purpose-vs-exports side-by-side and spot-checked the *version-specific* claims
most likely to drift (Dockerfile pi pin, i18n languages, FileLink editor branch). It
found exactly 4 real drifts, fixed those surgically, and refreshed the rest as sha-drift.
**Why it worked:** targeting the claims that *encode facts* (pins, enums, removed branches)
finds real drift fast without reading every file.

**Phase 3 — Root-cause the residual flags (steering #1).** The human asked the pivotal
question: *"can split over-thresholds? Is there official way — is the dox system designed
to handle that?"* Instead of guessing, the AI read the DOX source and CLI and produced the
key finding: **byte cap has an official auto-fix (`split-large-agents.mjs`); row cap does
not, intentionally** — the split script cuts bytes, leaving a pointer row, so counts don't drop.

**Phase 4 — Draft the proposal (steering #2 + #3).** "Create a proposal for that refactor"
+ "Add fix ROW_CAP". The AI grounded the proposal in an archived precedent
(`migrate-file-index-to-agents-tree`), discovered the over-thresholds split into **two
categories** (rollup dirs needing only scaffolded subdir `AGENTS.md`; genuinely flat source
dirs needing real moves + import churn), and — on the ROW_CAP steer — reframed the cap to
measure *inline detail volume* (exclude sidecar-pointer rows), not raw file count.

**Phase 5 — Full plan-proposal orchestration (steering #4).** The human pasted the
`plan-proposal` skill. The AI ran doubt-driven-review with an automatic **cross-model**
reviewer (`@propose-review-1` → zai/glm-5.2), got ~15 findings, **verified each against
real code**, and reconciled. Biggest catches: `components/preview/` *already existed*
(D4 rewritten to absorb into existing subfolders, no collisions); parents keep **no**
pointer rows (wrong model removed); `parseRowPaths` is cross-package (mandated a *sibling*
`countInlineRows`, never a signature change); string-literal path refs in `no-*.test.ts`
allowlists that `tsc` misses (codemod scope widened). Then scenario-design → manifest →
16 automated + 1 manual scenarios all folded into `tasks.md`.

**Phase 6 — Clean boundary commit (Verify).** The AI noticed the working tree mixed the
stale-fix work with the planning artifacts, flagged it, and on the human's "two commits"
split them: `1304f5382` stale-fix, `11d30891f` planning artifacts. Stopped at the worktree
boundary.

## 4. Prompts that worked

- **The goal prompt — "Fix stale kb entries."** Terse but effective *because the repo
  has a strong doctrine* (`kb dox lint`, AGENTS.md tree). A future kickoff is stronger
  as: *"Run `kb dox lint`, triage by kind, clear stale/missing structurally, and tell me
  which flags are structural vs auto-fixable."*
- **High-leverage follow-up — "Is there an official way? Is the dox system designed to
  handle that?"** This single question redirected the AI from *guessing at a fix* to
  *reading the tool's own design* — the highest-value turn in the session. It produced
  the byte-cap-vs-row-cap finding the whole proposal rests on.
- **"Create a proposal for that refactor."** Converted analysis into a durable artifact.
- **"Add fix ROW_CAP."** A three-word steer that flipped an explicit non-goal — the AI
  correctly *paused to pin the intended semantics* before editing (see §5).
- **Pasting the `plan-proposal` skill.** Handing the orchestration skill verbatim gave
  the AI the exact multi-step contract (doubt-review → scenario-design → fold → boundary).

## 6. Skills, tools & memory created — and why they're effective

No new skill was created, but the session was a textbook run of several existing ones:

- **`plan-proposal`** (main session only, never a subagent) — orchestrated the whole
  planning phase: artifacts → doubt-review → scenario-design → fold → stop at the
  worktree boundary. Invoke it whenever a proposal is drafted on `develop` and needs
  hardening before implementation.
- **`doubt-driven-review`** with an auto cross-model reviewer (`@propose-review-1`) —
  its value here was concrete: ~15 findings, and verifying them against real code caught
  a design error (`components/preview/` already existed) that would have been expensive
  to unwind after a ~430-file refactor started.
- **`scenario-design`** — produced the `test-plan.md` manifest and gated the fold; no
  spec gap meant no clarification STOP.

**Recommended skill to create:** a `fix-stale-kb-dox-rows` procedure capturing the triage
loop (bucket by kind → structural class-kills → purpose-vs-exports diff → refresh sha)
plus the **byte-cap-vs-row-cap** distinction, so the root-cause question doesn't have to be
re-derived. *(This project already ships one — invoke `fix-stale-kb-dox-rows`.)*

## 7. Pitfalls & dead ends

- **Don't rubber-stamp stale rows.** Most (68/72) were harmless sha-drift, but 4 encoded
  real drift (pi pin `@0.80.6`→`@0.80.10`, i18n gained `"hu"`, FileLink `openEditor` branch
  removed). Skipping the diff would have shipped false docs.
- **The byte split does NOT drop the row count.** `split-large-agents.mjs` promotes heavy
  rows to sidecars but leaves a pointer row — `components/AGENTS.md` still showed 172 rows
  after its byte flag cleared. This is *why* the ROW_CAP fix had to change *what's counted*.
- **`over-threshold` conflates two shapes.** Rollup dirs (`qa/` 54 rows, 51 in subdirs)
  need only scaffolded subdir `AGENTS.md`; flat source dirs (`components/` 175 files) need
  real `git mv` + import codemod. Don't treat them as one problem.
- **`parseRowPaths` is a cross-package export** (kb-extension consumes it) — never change
  its signature; add a *sibling* `countInlineRows` instead.
- **`tsc` misses string-literal path refs.** `no-*.test.ts` allowlists reference paths as
  strings — a type-only codemod won't catch them; add a `git grep` step + `npm test` gate.
- **One `mktemp`/edit error each** occurred (bash 1 fail, edit 1 fail — the atomic
  multi-edit that failed because reversibility text lived in `proposal.md`, not `design.md`).
  Re-apply edits per their actual file when an atomic multi-file edit fails.
