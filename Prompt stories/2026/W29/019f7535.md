# How we did it: Root-cause an empty `diff:` tab and capture it as an OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **OpenSpec explore mode** — a deliberately non-implementing stance:
"think, read, search, investigate; do NOT write code." The real objective, embedded in
the bug being explored, was: *clicking a file in the ChatView change-list opens a `diff:`
tab that renders **empty** for git-tracked files, while the same file's **File** view and
its inline chat change-card both render correctly.* The user wanted the AI to **find the
true root cause** (not guess) and then **capture the fix as an OpenSpec change proposal**
— artifacts, not an implementation. The only steering that followed was a single word,
`commit`, at the end.

## 2. TL;DR playbook

1. Enter explore mode explicitly (`openspec-explore` skill) so the AI reads/searches but never edits code.
2. Start from the **doc tree** (`kb_search` / `kb agents`) to locate `DiffPanel`, `DiffViewer`, `EditorPane`, not a blind `grep`.
3. Trace the render path from the click: `DiffViewer → DiffPanel(selection={changeIndex: null})`. Note which of Path A/B/C fires.
4. Reproduce the git behavior empirically in a throwaway repo (`/tmp/difftest`) — `git mv` + edit — to confirm the server produces valid diffs.
5. **Prove the root cause against the real library**: write a tiny `.mjs` that builds `new DiffFile(...)` with a bare hunk vs a header-bearing hunk. `bareHunk → 0 lines`, `fullHunk → 8 lines`.
6. Write the diagnosis: `extractHunks()` strips the `diff --git/---/+++` header that `@git-diff-view` v0.1.6 needs to reconstruct lines from empty content.
7. Scaffold the OpenSpec change (`proposal.md`, `design.md`, `tasks.md`, `specs/tool-renderers/spec.md` MODIFIED delta) following the existing `tool-renderers` spec conventions.
8. `openspec validate <change> --strict` until green.
9. On `commit`: stage **only** your change directory; leave unrelated working-tree edits untouched.

## 3. How the collaboration unfolded

**Discovery (doc-tree first).** The AI began not with `grep` but with the project's doc
tree to find `DiffPanel`, then traced the click path `DiffViewer → DiffPanel`. It
established the key asymmetry early: the `diff:` tab passes `changeIndex: null`, so
**Path A (RichDiff, the working inline path) is skipped** and Path B (git-aggregate) runs.
*Why it worked:* naming the exact code path up front turned a vague "renders empty" into a
testable hypothesis about one branch.

**Empirical git repro.** Rather than assume, the AI built a scratch repo in `/tmp/difftest`,
did a `git mv` + edit (mirroring the real "-6" numstat), and confirmed the **server side
produces valid diffs**. This eliminated the backend as the culprit and pointed at the
client renderer.

**Library-level proof (the decisive move).** The AI wrote standalone `.mjs` probes against
the actual installed `@git-diff-view/core`, feeding `new DiffFile(...)` a **bare** `@@…`
hunk vs a **header-bearing** one. Result: `bareHunk → 0`, `fullHunk → 8`. This is the phase
that converted a plausible theory into a proven root cause: `extractHunks()` strips the
header; empty `content` + headerless hunks = zero rendered lines.

**Capture as OpenSpec.** With the cause proven, the AI read the existing `tool-renderers`
spec to match delta conventions, then scaffolded a four-file change: proposal, design (3
paths, D1 header-preserving hunks, D2 Path C selection, rejected alternatives), a TDD
tasks.md (red test first), and a MODIFIED spec delta with two regression scenarios. It ran
`openspec validate --strict` to green.

**Commit (surgical).** On the human's `commit`, the AI noticed unrelated zrok/cors/tunnel
edits in the tree and staged **only** the proposal directory — commit `2193f3587`.

## 4. Prompts that worked

- **The goal prompt** — the `openspec-explore` skill invocation. Its strength: it set a
  hard *stance* ("think, don't implement; you MAY create OpenSpec artifacts") so the AI
  self-limited to investigation + proposal instead of jumping to a code fix. A future
  operator should keep the bug's three-way symptom ("empty in diff tab, fine in File view,
  fine in chat card") in the kickoff — that contrast is what made the root cause findable.
- **High-leverage follow-up** — `commit`. One word, because the artifact was already

  human only had to authorize the write.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The reusable pattern **is** the workflow,
and it's worth a skill:

- **Recommended skill: "prove-root-cause-against-real-dependency."** Captures the move of
  writing a throwaway `.mjs`/repro that exercises the *actual installed* library (not a
  mental model) to convert a theory into a proof — e.g. `bareHunk → 0` vs `fullHunk → 8`.
  Invoke it whenever a rendering/parsing bug points at a third-party lib and the fix depends
  on an exact input-format assumption. It removes the guess-and-patch loop and produces
  evidence you can paste straight into a proposal.

## 7. Pitfalls & dead ends

- **Don't `grep` blind for the render path.** The AI got there fast by starting from the
  doc tree (`kb`), then narrowing. If you hit a wall, that's the fallback — not the opener.
- **Bare hunks silently render nothing.** If a `@git-diff-view` panel is empty but you have
  a non-empty `gitDiff`, suspect header stripping: pass the whole header-bearing diff as
  `hunks: [file.gitDiff]`, don't feed it `extractHunks(...)`.
- **A dirty working tree at commit time.** There were unrelated zrok/cors/tunnel edits;
  committing them would have polluted the proposal commit. Always `git status` and stage
  only your change directory.
- **`changeIndex: null` skips Path A.** The `diff:` tab never runs the working RichDiff path
  — don't debug Path A when the tab uses Path B.
