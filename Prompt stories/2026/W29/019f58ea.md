# How we did it: forking a session-index proposal on its storage substrate — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`): *"Enter explore mode. Think
deeply. Visualize freely. Follow the conversation wherever it goes."* No implementation —
a thinking-partner stance to reason about how pi session knowledge should be indexed.

Once the steering turns landed, the real objective was concrete: the built
`packages/session-distiller` extracts **five** verified signal classes (fault, correction,
decision, procedure, documentation) but routes only **one** (`documentation`) into a
searchable kb. The operator wanted to decide **on what substrate** the missing signals
should become searchable — raw-in-code FTS5 upsert vs. `@fast`-synthesized markdown files —
capture the fork as an OpenSpec `design.md` addendum, and prove it works against a *real*
session rather than theory.

## 2. TL;DR playbook

1. Start in `openspec-explore`; forbid implementation, allow OpenSpec artifacts.
2. **Ground before theorizing** — map what already exists (`openspec list`, read the
   proposal/spec/plan, the distiller package, the kb chunker). The idea was a *fork in an
   existing proposal*, not greenfield.
3. Verify the one load-bearing claim: is `.pi` already a kb source root? (It is — read
   `.pi/dashboard/knowledge_base.json`.) That collapses one architecture to *zero* core changes.
4. Frame the decision as **Architecture A (in-code → FTS5, no model)** vs **Architecture B
   (distiller → `@fast` synthesis → structured markdown → kb's existing pipeline)**.
5. Capture it as `design.md` inside the existing change (OpenSpec artifacts are exempt from
   the caveman `docs/` subagent rule — write directly), then `openspec validate`.
6. **Prove with real data, not JSONL-in-context:** run the built distiller (dry-run,
   `--n 1`) over the project's 262 sessions, capture to tmp, parse in-sandbox, print only
   compact structure — no raw JSONL enters context.
7. Pull the strongest real cluster (`fault:edit:could-not-find-the-exact`, 45 sessions),
   fetch **real provenance + a real evidence string** from a source session, render into the
   proposed schema under `examples/` (real metadata + `@fast`-would-synthesize prose).
8. Run kb's actual chunker on the rendered file to empirically confirm heading anchors.
9. `commit` only your artifacts; leave unrelated working-tree changes (`groups.json`) untouched.

## 3. How the collaboration unfolded

**Discovery (ground the terrain).** The AI resisted theorizing and instead read the actual
artifacts: the `add-automatic-session-kb-index` proposal (0/30 done), the
`cross-session-distillation` spec, the distiller package, the hermes integration plan, and
how kb chunks markdown. *Why it worked:* it reframed the ask from "new idea" to "fork in an
existing proposal" — the single most valuable move of the session.

**Verify the load-bearing claim.** Before recommending anything, the AI checked whether
`.pi` was already a kb source root. Reading `.pi/dashboard/knowledge_base.json` surfaced
three grounded facts: `.pi` *is* a source root (→ Architecture B needs **zero** `packages/kb`
core change), ranking weights `headingPath:10 / heading:3 / body:1` (→ "structure that helps
agents pick chunks" *is* the heading schema, which only B controls), and
`respectGitignore: true` (→ "gitignored + searchable" is impossible — constrains the location
decision to three real options).

**Design (capture the fork).** On "Addendum to existing change", the AI wrote a 10.5 KB
`design.md` placing A and B side by side with five recommended decisions (build B /
file-per-cluster / external root + `docs/learned/` promotion tier / manual-then-auto /
model-formats-never-judges), then `openspec validate`d so the artifact set stayed coherent.

**Generate & verify (prove it real).** On "make some test from some existing session," the AI
ran the real distiller over 262 sessions (7,603 clusters, 6.2 MB plan), parsed it *in-sandbox*
to avoid pulling JSONL into context, and rendered the top real cluster into the schema with
**real** frontmatter/provenance and a **real** error string pulled from source session
`f522b9fe`. It then ran kb's actual chunker on the file — surfacing two honest nuances (only
4 chunks from 5 sections; `frontmatter.kb` read as undefined) that became open questions.

**Commit.** On "commit", the AI scoped the commit to only its 5 artifacts and explicitly left
the unrelated `groups.json` group-reassignment in the working tree.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore` stance).** Effective because it set a *no-implementation*
  guardrail while explicitly allowing OpenSpec artifacts — so the session produced a
  committed `design.md` without drifting into code.
- **"Addendum to existing change"** — high-leverage. Four words that told the AI the output
  is a `design.md` *inside* the existing change, not a fresh proposal, keeping the artifact
  set coherent.
- **"Can you make some test from some existing session to a markdown to test how it looks?"**
  — the most valuable follow-up: it forced the abstract fork to be validated against *real*
  distiller output, exposing that today's `body` is a bare one-liner (the exact gap
  Architecture B fixes). Stronger phrasing: *"render one real recurring cluster into the
  proposed schema using real provenance — no invented prose."*
- **"commit"** — trusted the AI to scope the commit correctly, which it did (excluding
  unrelated changes).

## 7. Pitfalls & dead ends

- **"gitignored + searchable" is a contradiction here.** `respectGitignore: true` means kb
  won't index anything git ignores → don't propose "personal gitignored files that are also
  searchable." Location choices collapse to: tracked under `.pi/kb/…`, tracked under
  `docs/learned/`, or an external per-machine source root.
- **Don't pull raw JSONL into context.** The distiller plan was 6.2 MB — copy to a project
  tmp area and parse *in-sandbox* (`ctx_execute` / `ctx_execute_file`), printing only compact
  structure. One `ctx_execute_file` failed on a relative import → fix with an **absolute**
  import path relative to the script dir.
- **Chunker nuances to expect:** a 5-section file yielded only 4 chunks (sub-120-char
  sections lose their anchor), and `frontmatter.kb` read as undefined (shallow `kb:`
  frontmatter parse). Both are real design open questions, not render bugs.
- **One bash command failed** (a multi-target `ls -R` on a non-existent path) — harmless;
  the grounding continued.
