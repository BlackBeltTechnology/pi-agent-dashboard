# How we did it: capturing an auto-session-naming feature as an OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance, explicitly *no implementation*. The real objective, which sharpened over five
turns, was: **design automatic topic-naming for pi sessions** (so a directory of work
stops reading as a wall of identical `cwd`-basename folders) and **capture that design
as a validated OpenSpec proposal** — proposal + design + delta specs + tasks — without
writing a line of feature code. The kickoff was the standard explore-mode preamble; the
substance emerged from grounding in the existing naming machinery and from one decisive
architecture question the human asked mid-flight.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore`) so the AI *thinks and designs* but never implements.
2. Let the AI **ground first**: grep the server + extension for the existing session-name
   machinery (`meta.name`, `rename_session`, `session_name_update`, `setSessionName`) before
   proposing anything.
3. Surface the **key finding** early — a full rename pipeline already ships; this feature is
   an *automatic producer* feeding it, not new naming infrastructure.
4. Answer the AI's design questions in **one keystroke** (`1`) to pick the decisive option
   (the real pi session name vs. dashboard-only name).
5. Ask the sharp architecture question yourself: **"Is it possible to call pi session without
   proxy?"** — forcing a spike that proves the bridge can call `@fast` in-process.
6. Say **`capture`** to lock the design into an OpenSpec change (proposal/design/specs/tasks).
7. Run a **duplicate/coherence check** against existing capabilities before scaffolding.
8. `openspec validate <change> --strict`, then say **`commit`** — stage ONLY the change dir,
   leave unrelated residue untracked.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding (grep the existing machinery).**
The AI ran a tight sequence of `grep`/`sed` probes across `packages/server/src` and
`packages/extension/src` looking for `meta.name`, `firstMessage`, `rename_session`,
`session_name_update`, `setSessionName`, and the model-proxy. *Why it worked:* it refused to
design on assumptions — it reconstructed the ground truth (a rename pipeline + a server-side
model-proxy already exist) and drew it as an ASCII data-flow before proposing anything.

**Phase 2 — First architecture fork (where does auto-naming live?).**
The AI framed the real decision: server-side (it has a model-proxy) vs. bridge-side (it owns
`setSessionName` + `@fast` role-resolution). The human unlocked the direction with a single
`1` — choosing the **real pi session name**, which pins the feature bridge-side.

**Phase 3 — The spike (can the bridge call a model with no server round-trip?).**
Prompted by the human's *"Is it possible to call pi session without proxy?"*, the AI traced
`streamer.ts` down to two primitives — `registry.getApiKeyAndHeaders(model)` and pi-ai's
`streamSimple(...)` — and proved the bridge already holds both (the live `ModelRegistry`, and
`pi-ai` is pi's own dep, resolvable in-process). Verdict: **pure-bridge direct call, no proxy.**

**Phase 4 — Capture (scaffold the OpenSpec change).**
On `capture`, the AI first did a coherence check (no duplicate auto-naming work; extend
`session-rename` + `global-preferences`), scaffolded `add-auto-session-naming/`, matched the
schema against existing proposals, then wrote proposal.md, design.md, three delta specs, and a
TDD-shaped tasks.md — encoding the provenance FSM (`nameSource: "auto" | "user"`, manual rename
= permanent lockout) and the rejected hybrid path.

**Phase 5 — Validate & commit.**
`openspec validate --strict` passed. On `commit`, the AI staged **only** the change directory,
deliberately leaving an unrelated `.pi/settings.json.bak-switch-*` file untracked. Commit
`fd813df49`, on `develop`, nothing built or applied.

## 4. Prompts that worked

- **Goal prompt — the explore-mode preamble.** Effective because the stance ("think, don't
  implement; you MAY create OpenSpec artifacts") is exactly right for *design capture*: it kept
  the AI from jumping to code and channelled it into grounding + a proposal.
- **`1`** — a one-character high-leverage unlock. When the AI lays out a clean fork with a
  numbered recommendation, answering with the number is the fastest possible steer.
- **`Is it possible to call pi session without proxy?`** — the single most valuable prompt.
  It converted a hand-wavy "two paths are feasible" into a *conclusive spike* and eliminated a
  whole architecture branch (the hybrid). Rewrite weak "which is better?" prompts into this
  shape: **name the specific simpler path and ask the AI to prove it feasible or not.**
- **`capture`** / **`commit`** — terse workflow verbs that work *because* the explore skill and
  project conventions define what they mean (scaffold an OpenSpec change; stage + commit).

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session — the work rode entirely on existing assets:

- **`openspec-explore`** — the stance skill that kept the AI in think/design mode and permitted
  OpenSpec-artifact creation. *Invoke it* whenever the goal is to capture a design, not build it.
- **`openspec new change` + `openspec validate --strict`** — the scaffold/validate loop that
  guarantees the proposal matches schema before commit.

*Recommended skill to create:* a **"design-spike-before-proposal"** micro-procedure — when a
feature has two feasible placements, trace the cheaper path to a proof (as the bridge/proxy spike
did) and record the rejected alternative in design.md. It removes the ambiguity that otherwise
survives into implementation.

## 7. Pitfalls & dead ends

- **`openspec change new` is not the command.** The first scaffold attempt (`openspec change new
  add-auto-session-naming`) failed; the working form is **`openspec new change <name>`**. If a
  scaffold command errors, run `openspec new --help` before guessing.
- **Unrelated working-tree residue at commit time.** A `.pi/settings.json.bak-switch-*` file was
  present but irrelevant — the fix was to `git add` only the change directory, never `git add -A`.
