# How we did it: Design a nightly Verdaccio release-dry-run — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **OpenSpec explore mode** — "Enter explore mode. Think deeply…
you must NEVER write code or implement features… You MAY create OpenSpec artifacts."
The real objective, once the four clarifying answers landed, was: **design a scheduled
nightly build that exercises the entire release pipeline** (31 npm packages + the
6-leg Electron installer matrix) **without polluting the public npm registry** — using
a throwaway **Verdaccio** virtual registry so the publish→install→bundle round-trip runs
at full fidelity, on cron, with **zero writes to public npm**. The exploration doubled as
a drift audit of what the Electron bundle actually ships.

## 2. TL;DR playbook

1. **Kick off in explore mode** with the real constraint stated: "design a nightly that
   round-trips the whole release pipeline against a local Verdaccio, zero public writes,
   on cron — do not implement, capture as an OpenSpec change."
2. **Ground the pipeline first** — have the AI map the real `publish.yml → electron →
   github-release` chain and, critically, *why* `electron` hard-depends on `publish`
   (`bundle-server.mjs` runs `npm install` that resolves `@blackbelt-technology/*` **from
   npm**). That coupling is the whole reason a nightly needs a registry.
3. **Audit the bundle composition** — ask "check it": enumerate `packages/*plugin*` vs what
   `BUNDLED_PLUGINS` actually ships. This surfaced live drift (missing `kb-plugin`, stale
   `honcho-plugin`) as a free side effect.
4. **Answer the design questions tersely** (`1., fidelity` / `2. virtual registry` / `3.
   zero` / `4. cron`) and let the AI fold them into `design.md` decisions.
5. **Write the OpenSpec artifacts directly** (proposal + design + tasks + a new
   `nightly-verification` capability spec) matching the repo's existing change structure;
   `openspec validate <change>` after each.
6. **Fix the drift you found, scoped** — add `kb-plugin` to `BUNDLED_PLUGINS`; remove stale
   gitignored honcho artifacts. Verify with a real `npm run build` + source-only bundle.
7. **Pin the invariant with a unit test** beside the existing `publish-allowlist-complete.test.ts`,
   asserting both directions (every runtime plugin listed; no stale entry).
8. **File findings as GitHub issues** (`gh issue create`), commit each concern separately
   with `Fixes #N` trailers, leave pre-existing dirty files untouched.

## 3. How the collaboration unfolded

**Phase 1 · Discovery / grounding.** The AI mapped the release pipeline and pinned the
load-bearing fact: `electron` needs `publish` because `bundle-server.mjs` resolves scoped
deps from the live registry. This is what made "nightly needs its own registry" concrete
rather than hand-wavy. *Why it worked:* it grounded the whole design in the actual coupling
before proposing a solution.

**Phase 2 · Bundle audit ("check it").** Enumerating on-disk plugins against `BUNDLED_PLUGINS`
turned up 10 plugin-ish dirs, 6 bundled — and revealed `kb-plugin` was silently missing and
`honcho-plugin` was a stale ghost. *Decision point:* the human split this into two follow-ups
— "add kb_plugin, remove honcho" — so the audit fed real fixes.

**Phase 3 · Capture as OpenSpec.** The AI wrote `add-nightly-verdaccio-build/` (proposal,
design with 6 decisions, ~30-task tasks.md, and a new `nightly-verification` spec delta),
validating after each. *Why it worked:* it chose a *new* capability rather than overloading
the existing `ci-cd-pipeline` one, and matched the repo's established structure instead of
guessing at `openspec new`.

**Phase 4 · Fix + verify the drift.** `kb-plugin` confirmed a real runtime plugin (id `kb`,
has client/server/claims, no `fixture`) → added. honcho confirmed source-less, gitignored
build output → removed. Proven with `npm run build` + `--source-only` bundle showing
"Bundled 7 first-party plugin(s)" (was 6).

**Phase 5 · Pin + track + land.** A completeness unit test went beside
`publish-allowlist-complete.test.ts`; findings filed as issues #368/#369; two scoped commits
(`fix(electron)…` with `Fixes #368 #369`, then the OpenSpec change), leaving another session's
dirty files alone.

## 4. Prompts that worked

- **The goal prompt (explore-mode kickoff).** Effective because it set a hard *stance* ("think,
  don't implement; you MAY create OpenSpec artifacts"), which kept the AI producing design
  artifacts instead of jumping to code.
- **`1., fidelity / 2. …virtual registry… / 3. zero / 4. cron`** — a single terse reply that
  answered four open design questions at once. High leverage: it unblocked the entire `design.md`
  decision set in one turn. A future operator should batch design answers this way.
- **"check it"** (inside prompt 2) — turned a design task into a live audit; the highest-value
  four words in the session, since they surfaced the kb-plugin/honcho drift.
- **"1. add kb_plugin  2. remove honcho"** — converted audit findings into scoped actions.
- **"file the findings as issues" / "commit"** — short unlock prompts that moved from analysis
  to durable tracking + landed work.

*Weak-prompt rewrite:* prompt 5 was literally `I want` (truncated/cut off) and the AI correctly
paused to ask. Next time, send the full instruction — e.g. "pin the kb-plugin invariant as a
unit test now" — instead of a fragment.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Offer three paths and wait ("pin a test / file issues / build the change") | Say "ok" — which is ambiguous across 3 options; AI re-asked | Name the path explicitly ("pin the test now") to skip a round-trip |
| Treat design questions one at a time | Answer all four in one numbered reply | Batch design answers up front |
| Risk committing unrelated dirty files | Rely on AI scoping to just the fix + guard | State "commit ONLY my changes; leave pre-existing dirty files" |
| Break heredoc commit messages on an apostrophe | AI fell back to a message file | Use `git commit -F <file>` for messages with apostrophes |
| Leave incomplete `--source-only` bundle behind | Full `npm test` caught a self-inflicted failure | Clean `resources/server/` after any partial bundle run |

## 6. Skills, tools & memory created — and why they're effective

No pi *skill* or *memory* was created this session. The durable, reusable asset produced was a
**completeness invariant unit test**: `packages/shared/src/__tests__/bundled-plugins-complete.test.ts`.

- **What it captures:** reads `BUNDLED_PLUGINS`/`BUNDLED_WORKSPACE_PKGS` from `bundle-server.mjs`
  by regex (no execution) and scans `packages/*` for the "must-bundle" set (`pi-dashboard-plugin`
  manifest AND not `fixture`).
- **Why it's effective:** asserts *both directions* — every runtime plugin is listed (catches the
  **kb-plugin class**: added to `packages/`, forgotten in the array) and no stale entry survives
  (catches the **honcho class**: deleted from `packages/`, left in the array). It runs in normal
  `npm test`, no build needed, mirroring the existing `publish-allowlist-complete.test.ts` convention.
- **When to invoke:** any time a plugin is added/removed, this guard fails the build on drift.

*Recommended follow-up asset:* the planned `assert-bundled-plugins-complete.mjs` build-time gate in
the nightly change complements this source-list test.

## 7. Pitfalls & dead ends

- **Malformed `ctx_batch_execute` calls** early on (4 errors) — the AI corrected to use the batch
  tool correctly. If a batch tool call fails, re-check the parameter shape before retrying.
- **`--source-only` bundle left an incomplete `resources/server/`** (no `npm install` → no
  materialized `pi-dashboard-web/dist`), which tripped `bundled-server-materialization.test.ts`.
  Fix: `rm -rf packages/electron/resources/server` (gitignored, regenerates on a real build), then
  re-run. Don't mistake this self-inflicted failure for a regression.
- **Running vitest directly needs `HOME=$(mktemp -d)`** due to the test-isolation guard; `npm test`
  sets it automatically. Direct `npx vitest run …` will otherwise fail.
- **Heredoc commit message broke on an apostrophe.** Use `git commit -F /tmp/msg.txt`.
- **Committed onto `develop` directly** (the branch the operator was on) — and a *concurrent session*
  in the same repo produced an interleaved commit. Verify `git log` / `git branch --contains <sha>`
  when history looks unfamiliar; confirm which dirty files are actually yours before staging.
