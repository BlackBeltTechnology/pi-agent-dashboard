# How we did it: Promote learned skills into the repo — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with (verbatim, typos and all):

> "The skill manage have a lot of learnt skill. Ceck tem some of them can be part of
> this prroject which are general enough, so there is no local environment details"

The real objective, once decoded: **audit the personal, project-scoped learned skills
that live in the private memory store (`~/.pi/agent/projects-memory/pi-agent-dashboard/skills/`)
and promote the ones that are portable — no machine-local paths, durable project
knowledge — into the repo's committed `.pi/skills/` so every contributor gets them.**
Skills that overlap an existing committed skill should be *folded in*, not duplicated.
The lone steering turn was `commit`.

## 2. TL;DR playbook

1. Locate the two skill stores: committed repo skills (`git ls-files .pi/skills/`) vs.
   personal learned skills (`~/.pi/agent/projects-memory/<project>/skills/`).
2. Prove portability mechanically: `grep -rn -E '/Users/|robson|/home/[a-z]' */SKILL.md`
   — any machine-local path disqualifies a skill from promotion.
3. **Triage into tiers**, don't binary-classify: Tier 1 = clean, standalone, promote
   as-is; Tier 2 = general but overlaps a committed skill → fold into it.
4. Copy Tier-1 skills verbatim into `.pi/skills/`; fix any internal cross-refs that
   still point at the old personal-store name.
5. For Tier-2, extract the *durable method* into the host skill's `references/*.md` and
   **strip transient version specifics** (pinned package versions age badly).
6. Wire pointers: add a symptom-table row + a "when to use" section in the host
   `SKILL.md`; register every new file as a caveman-style, path-alphabetical row in
   `.pi/skills/AGENTS.md`.
7. Verify: `git status --short`, confirm each new `SKILL.md` has `name` + `description`
   frontmatter, and that no repo skill references a now-nonexistent standalone skill.
8. Remove the promoted Tier-1 copies from the personal store (avoid double-loading);
   keep Tier-2 originals since they were folded, not copied 1:1.
9. Commit with a message naming the promote/fold split.

## 3. How the collaboration unfolded

**Discovery.** The AI first distinguished the two skill locations, discovering all six
candidate skills lived in the *personal* memory store, not the repo — then checked what
the repo already tracked to avoid re-committing existing skills.

**Triage.** Rather than a yes/no on "is it portable", the AI graded each skill on two
axes: (a) does it hardcode machine-local paths? (none did) and (b) how durable/general
is the knowledge? That produced a **Tier 1 (promote as-is) / Tier 2 (fold in)** split —
the key decision that kept the repo skill set clean instead of bloated with near-dupes.
The human's implicit approval ("all six selected") unlocked execution.

**Generate.** Tier 1 → 4 new standalone committed skills, copied verbatim, with a
cross-ref fix in `frontend-mockup-loop-dashboard`. Tier 2 → folded into the existing
`debug-dashboard` skill: a new `references/isolated-verification.md`, plus a
version-stripped "spawn_register_timeout" section in `references/known-issues.md`, plus
a symptom-table row in `SKILL.md`.

**Register + verify.** Added 5 caveman-style, path-alphabetical rows to
`.pi/skills/AGENTS.md`, verified frontmatter validity and cross-references, tidied one
dangling `description:` reference, then removed the superseded personal copies.

**Commit.** On the `commit` steering turn, staged `.pi/skills` and committed as
`3b5d05e5c` — deliberately not pushed.

## 4. Prompts that worked

- **The goal prompt** was terse and typo-laden but carried the one decisive constraint:
  *"general enough, so there is no local environment details."* That single criterion is
  what made the audit tractable — it gave the AI a mechanical test (grep for local paths)
  and a judgment axis (durability). A stronger phrasing a future operator should use:
  *"Audit my project-scoped learned skills in the personal memory store. Promote into the
  committed `.pi/skills/` any that have no machine-local paths and capture durable project
  knowledge; fold ones that overlap an existing committed skill instead of duplicating."*
- **High-leverage follow-up:** `commit` — a one-word unlock once the diff was staged and
  verified. Effective because the AI had already surfaced the full diff and told the
  operator what would land, so "commit" needed no further scoping.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat "promote skills" as a binary copy job | (Implicit) accept the AI's own tier split | State up front: "tier them — standalone vs. fold-into-existing" so overlaps don't become duplicates |
| Stop after preparing the diff | `commit` | Say "audit, promote/fold, then commit" in one prompt to avoid the extra round-trip |
| Risk carrying transient version pins (`pi-web-access@0.12.0`) into a durable doc | Self-corrected — stripped versions | Make "strip transient specifics when generalizing" an explicit instruction |

Note: this session needed *very little* steering — the AI's tier-based triage and
version-stripping were self-directed. The lesson is more about the effective self-imposed
quality bars than about human corrections.

## 6. Skills, tools & memory created — and why they're effective

No new skill was *authored* this session (`skill_manage` was used once, for inspection).
Instead the session **promoted 4 learned skills into the repo and folded 2 more** — that
promotion itself is the reusable asset:

- **`fix-worktree-opsx-skills-not-created`** — pure repo fact: `worktreeInit` must call
  `@fission-ai/openspec` (bare `openspec` is a squatted 0.0.0 stub). Every contributor
  with a worktree hits it. Invoke when worktree skills silently fail to appear.
- **`run-dashboard-e2e-local-changes`** — repo workflow: `docker/compose.yml build`
  before `npm run test:e2e`. Invoke before running E2E against local changes.
- **`pre-scaffold-openspec-coherence-check`** — repo OpenSpec discipline; pairs with the
  committed `spec-coherence-check`.
- **`frontend-mockup-loop-dashboard`** — thin adapter binding the packaged mockup loop to
  repo paths/theme tokens.
- **Folded into `debug-dashboard`**: `isolated-ui-verification` → `references/isolated-verification.md`
  (verify a change without touching the live server); `diagnose-spawn-register-timeout` →
  version-stripped section in `references/known-issues.md`.

**Why effective:** promotion moves knowledge from a single operator's private store into
the shared, git-tracked skill set, so it loads for every contributor and survives machine
changes. The *should-create* meta-lesson: a recurring "promote learned skills to repo"
workflow is itself skill-worthy — mechanical grep test + tier triage + fold rules.

## 7. Pitfalls & dead ends

- **Two skill stores look alike.** Learned skills live in `~/.pi/agent/projects-memory/<project>/skills/`,
  committed ones in `<repo>/.pi/skills/`. Confusing them wastes a promotion. Always diff
  `git ls-files .pi/skills/` against the personal store first.
- **Version pins age.** Folding `diagnose-spawn-register-timeout` verbatim would have
  baked `pi-web-access@0.12.0` into a durable doc. Keep the *method*, drop the pins.
- **Double-loading.** Leaving Tier-1 copies in the personal store after promoting them to
  the repo loads them twice. Delete the personal copies for promoted skills; keep folded
  originals.
- **Dangling cross-refs.** A promoted skill's `description:` referenced a standalone skill
  that no longer existed as a separate skill — had to be tidied so no repo skill points at
  a nonexistent name.
- **`AGENTS.md` growth.** Adding rows can trip `kb dox lint over-threshold`; the split
  script (`scripts/split-large-agents.mjs`) handles it if flagged.
