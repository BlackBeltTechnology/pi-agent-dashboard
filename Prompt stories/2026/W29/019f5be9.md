# How we did it: Chat Gateway (explore → proposal) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (the `openspec-explore` skill preamble was the
literal first prompt — "Enter explore mode. Think deeply… you must NEVER write code").
The *real* objective, which the four short steering turns clarified, was: **decide whether
pi-agent-dashboard should grow a general "chat gateway" (drive a pi coding session from
Discord/Slack/Telegram), whether an existing package or Hermes can be adopted, and — once
decided — turn that thinking into a strict-valid, implementation-ready OpenSpec change,
Discord-first.** It ended with a surgical commit of a proposal + a repo-root design record.

## 2. TL;DR playbook

1. **Start in explore mode** (`openspec-explore`) — commit to *thinking, not building*.
2. **Fan out research + recon in parallel:** spawn 3 `Explore` subagents on the ecosystem
   clusters while you personally read the substrate (pi RPC/SDK, the dashboard's own
   PromptBus / browser-protocol).
3. **Inventory before inventing:** pull the npm registry JSON for every chat platform,
   filter to pi packages → a 41-package map. Find the two that already generalize.
4. **Dissect the strongest candidate at the seam** (`@gamalan/pi-gateway`): read its
   adapter contract in full, *structurally* dissect its 63 KB `index.ts` hub without
   dumping it into context. Verdict: **adopt the adapter layer, discard the hub** — the
   dashboard already *is* the hub.
5. **Verify the load-bearing assumption against source**, not vibes: confirm the server
   fans `prompt_request` to all subscribers and accepts `prompt_response` from any
   (`handleSubscribe`, `event-wiring.ts`, `browser-gateway.ts`). This is what makes "zero
   protocol change" a fact.
6. **Capture the investigation as a repo-root narrative doc** (`chat-gateway-exploration.md`)
   — deliberately *not* under `docs/` (caveman-prose rule would gut the diagrams/rationale).
7. **Move to a proposal only on the user's word.** Run the pre-scaffold coherence check
   (`add-connector-layer` is orthogonal *outbound*, not a duplicate). Scaffold
   `add-chat-gateway`, validate `--strict`.
8. **Run `scenario-design` adversarially** → 33 scenarios + **8 spec gaps it refuses to
   guess**. Ask all 8 as decision-forcing questions, **fold** answers back as `SHALL` +
   scenarios, clear every marker, re-validate.
9. **Surgical commit** — stage only your 6 files, leave unrelated untracked dirs alone.

## 3. How the collaboration unfolded

**Phase 1 · Discovery & inventory.** Three parallel `Explore` subagents (multi-platform
bridge, RPC-bot pattern, Hermes gateway) ran while the model browsed pi.dev's package
registry and pulled clean npm JSON. Output: a 41-package, 5-family map. *Why it worked:*
parallel recon + a registry pull beats paginating a noisy browser, and it grounded every
later claim in a real inventory instead of speculation.

**Phase 2 · Seam dissection (the build-vs-adopt decision).** Rather than read 63 KB of
`index.ts`, the model dissected it structurally (grep for the functions/classes) and read
the *adapter contract* in full. This produced the pivotal verdict: gamalan is a **parallel
hub** that reimplements the dashboard — extract its MIT adapter transport, discard the rest.

**Phase 3 · Source verification.** The whole "headless dashboard client" design rests on
one assumption: prompts fan to all subscribers, responses accepted from any. The model
traced `PromptBus`, `handleSubscribe`, `sendToSubscribers`, `case "prompt_response"` and
built a requirement→evidence→status table. It even *corrected its own earlier framing*
(target PromptBus messages, not legacy `extension_ui_request`). *Decision point:* this is
what let "no bridge/server protocol change" become a written invariant.

**Phase 4 · Capture.** Investigation written to repo-root `chat-gateway-exploration.md`
(~16 KB) + two compact project memories as durable pointers. Project memory was at capacity
(4949/5000) — the model **declined to evict** without permission and relied on the doc.

**Phase 5 · Proposal (on "create proposal… discord first").** Pre-scaffold coherence check
caught the active `add-connector-layer` change and disambiguated it (inbound vs outbound).
Scaffolded a complete `add-chat-gateway` (proposal/spec/design/tasks), fixed two markdown
parser gotchas (`ctx.ui.*` glob, `SHALL` must lead the requirement line), validated strict.

**Phase 6 · Adversarial hardening ("run" → `scenario-design`).** 33 scenarios and **8 real
spec gaps** surfaced. The model asked all 8 as decision-forcing questions with security-first
defaults, then on "fold" wrote every answer back as a testable `SHALL` + scenario, cleared
all markers, and folded 33 scenario ids into `tasks.md`. On "commit" it made a surgical,
convention-following commit.

## 4. Prompts that worked

- **Goal prompt — `openspec-explore` preamble.** Effective because it *pinned the stance*:
  think, don't implement. That constraint is what produced a rigorous design record instead
  of a half-built feature.
- **"create proposal and I would like to support discord first"** — the single steering line
  that unlocked the whole scaffold. Effective because it named the **first platform**, which
  let the model design an extensible adapter interface with a concrete v1 target.
- **"run" / "fold" / "commit"** — three one-word high-leverage unlocks. They worked *only
  because* the skills (`scenario-design`, the fold routine) had already loaded a precise
  next-action; the human just authorized each gate.

*Rewrite for next time:* instead of a bare "run", say **"run scenario-design in soft-gate
mode and surface spec gaps as decision-forcing questions"** — makes the gate explicit.

- **Two project memories** (pointers to `chat-gateway-exploration.md` + the verdict:

  silent design defects into decision-forcing questions *before* implementation.
- **The repo-root design doc pattern**: capturing an exploration narrative at the repo root
  (not `docs/`) preserves diagrams + rationale that the caveman-prose docs rule would strip.
- *No skill was created, but the repeatable asset is the loop itself:* **explore → verify →
  decide → propose → scenario-design → resolve gaps → fold → commit.**

## 7. Pitfalls & dead ends

- **OpenSpec strict-validate markdown gotchas:** a `*` in `ctx.ui.*` breaks SHALL detection;
  a requirement that starts with "When…" pushes `SHALL` to line 2 and the parser misses it.
  *Fix:* lead the requirement line with `SHALL`, avoid glob `*` in requirement text.
- **Don't dump a 63 KB file into context** to judge it — dissect structurally (grep
  functions/exports, read only the seam/contract).
- **Project memory at capacity (4949/5000):** don't silently evict; the durable record is
  the doc. Save a compact pointer or ask before pruning.
- **Coherence check is not optional:** an active `add-connector-layer` looked like a dup but
  was orthogonal (outbound). Read active changes before scaffolding a similarly-named one.
- **Surgical commit:** other untracked change-dirs + a `groups.json` edit were present —
  stage only your files, never `git add -A`.
