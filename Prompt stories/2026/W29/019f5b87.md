# How we did it: turning a vague "list_models is empty" hunch into a grounded OpenSpec change

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation task. The operator's underlying objective: figure out *why* the
agent-facing `list_models` tool sometimes returns an empty `{ "models": [] }`, decide
whether it's a real bug, and — if so — capture it as an OpenSpec change **without writing
any implementation code**. What started as "is this broken?" ended as a fully-scaffolded,
validated 4-artifact planning change (`fix-list-models-empty-on-unhydrated-registry`),
committed to `develop`.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) so the AI investigates but never
   implements. State the symptom: "`list_models` sometimes returns empty."
2. **Run `list_models` live first** — the AI immediately proved the catalogue was
   *full* (100+ models), reframing the bug as **contextual**, not global.
3. **Steer to real evidence**: "check it with browser." The AI drove the dashboard UI +
   `/api/models` and confirmed the registry is populated everywhere reachable.
4. **Kill the wrong hypothesis**: ask "Is there anything NOT fixed by
   `fix-builtin-role-names-relay`?" — forces the AI to *read* that change instead of
   linking it by name. It retracted the guess: that change touches roles, not models.
5. **Demand code-grounding before scaffolding**: the AI found the smoking gun —
   `role-model-tools.ts:66` collapses *registry-absent* and *zero-credentials* into the
   identical `{ models: [] }`.
6. **`create proposal`** → then run `openspec-ff-change` to fast-forward
   design → specs → tasks in one pass.
7. **`cogence check`** (coherence audit): verify delta header ↔ main spec header, no
   conflicting active/archived changes, code claims still true.
8. **`commit`** atomically: `git reset && git add <change-dir> && git commit` in one
   command so no concurrent session's WIP leaks in.

## 3. How the collaboration unfolded

**Phase 1 — Reframe the symptom (Discovery).** The AI ran `list_models` at the top of the
turn and got a full 100+ model catalogue. Instead of chasing "the catalogue is gone," it
reframed: `list_models` is a *projection* of the current process's `ModelRegistry` —
only providers with resolved credentials show up. `{ models: [] }` means "this session
booted without auth," almost never "the catalogue vanished." *Why it worked:* running the
tool live before theorizing turned a vague bug report into a precise failure model.

**Phase 2 — Verify in the browser (Gather).** Steered by "check it with browser," the AI
drove the live dashboard: `/api/health`, `/api/models` (default + `annotated=1`), and the
UI model-selector dropdown — all returned the full set, matching the MCP `list_models`
1:1. Verdict: the registry is not empty anywhere reachable. *Decision point:* the human
insisted on empirical proof, not assertion.

**Phase 3 — Kill the name-based guess (Correction).** The AI had loosely linked the
symptom to `fix-builtin-role-names-relay` *by its name*. The human pushed back: "Is there
anything not fixed by it?" Forced to actually read the artifacts, the AI **retracted**:
that change relays `builtinRoleNames` (role labels), touches zero of the model-resolution
path. *Why it mattered:* this stopped a wrong root cause from being baked into a proposal.

**Phase 4 — Ground the root cause in code (Design).** One research pass located the real
defect: `role-model-tools.ts:66` returns `[]` when `registry` is absent **and** when
`registry.getAvailable()` yields zero credentials — two structurally different states,
one indistinguishable output. `cachedModelRegistry` is captured mid-bootstrap
(`bridge.ts:2244`), so a freshly-spawned/headless child hits `!registry → []` and the
agent can't tell "not ready yet, retry" from "you genuinely have no models."

**Phase 5 — Scaffold + fast-forward (Generate).** `create proposal` then
`openspec-ff-change` produced all four artifacts: proposal (additive `registryReady`
discriminator, explicit Non-Goal of *not* re-plumbing hydration timing), design (3-state
table, signal-and-retry over block-and-await), delta spec (MODIFIED requirement, full
prior content preserved + 4 new scenarios), and TDD-first tasks.

**Phase 6 — Coherence + commit (Verify).** "cogence check" ran a 5/5 audit: delta header
matched the main spec header exactly, no active change touched the capability, archived
ancestor `add-agent-role-model-tools` was the copy-base not a duplicate, all three code
line-references verified live. Then an atomic scoped commit landed `517d1f9f8`.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Kicking off in `openspec-explore` was the right
  move: it let the AI investigate deeply while a hard rule ("never implement") kept it
  from jumping to code before the root cause was proven. A future operator with an
  ambiguous bug should open the same way.
- **"check it with browser"** — a 4-word high-leverage follow-up. It converted a
  plausible theory into end-to-end empirical proof across server API + UI.
- **"Is there anything which is not fixed by fix-builtin-role-names-relay?"** — the
  session's best prompt. It refused to accept a name-based linkage and forced the AI to
  *read the artifact*, catching a wrong hypothesis before it hardened into a proposal.
- **"cogence check"** — short, but triggered a full pre-commit coherence audit
  (header binding, cross-change conflicts, live code-claim re-verification).

*Rewrite of the weak spot:* rather than letting the AI speculate a linkage, state it up
front — "Do NOT link changes by name; read each artifact's scope before claiming overlap."

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session — but the workflow is highly
repeatable and **should** become one. Recommended skill: *"explore-to-grounded-openspec"*
— the loop of (1) run the tool live to reframe the symptom, (2) verify in the browser,
(3) read-not-guess to kill wrong hypotheses, (4) find a file:line root cause, (5) scaffold
via `openspec-ff-change`, (6) coherence-audit, (7) atomic scoped commit. The existing
`openspec-explore` + `openspec-ff-change` skills already carry steps 1 and 5; the missing
glue is the "ground before you scaffold" discipline that the human had to enforce by hand.

Effective existing assets leaned on: `openspec-explore` (investigate-don't-implement
guardrail), `openspec-ff-change` (one-pass artifact generation), and `session_search`
(pulled the prior `list_models`-empty investigation for context).

## 7. Pitfalls & dead ends

- **Name-based change linking.** The AI initially tied the symptom to
  `fix-builtin-role-names-relay` purely from its name. *If you hit this:* open the change's
  artifacts and read the Non-Goals — that change relays role labels, not models. Never
  claim overlap without reading scope.
- **"Empty catalogue = broken" trap.** `{ models: [] }` is a *projection* of the current
  process's credential-resolved registry, not a static list. *If you see empty:* re-run
  with `annotated: true` (shows `excludedReason`), and suspect an unhydrated/headless
  registry before assuming the catalogue is gone.
- **Scaffolding on assumption.** Proposing before verifying the root cause in code risks a
  proposal built on a wrong premise. *Do:* land a file:line reference
  (`role-model-tools.ts:66`) into the proposal first.
