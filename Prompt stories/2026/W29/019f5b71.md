# How we did it: Tracing a dead custom-roles UI to a two-hop relay bug — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-only stance,
no implementation. The user's actual complaint surfaced two prompts later: *"currently
in settings I cannot define that dynamic provider names"* and then the decisive
clarification — *"I'm in web dashboard. Check with browser. My problem is the @fast etc
definitions."*

The real objective: **the `@fast`-style custom named-role UI is invisible on the web
dashboard**. Settings → General → ROLES renders a flat pill grid with no "＋ Add custom
role" button and no Built-in/Custom grouping — even though the feature (`add-custom-roles-ui`,
#282) was already merged. The goal became: **find why the shipped feature never appears,
prove the root cause, and land a fix through the full OpenSpec change → apply → ship
pipeline.**

## 2. TL;DR playbook

1. **Don't trust "it's shipped."** When a merged feature is invisible, verify it *in the
   running browser* first — `browser` tool: open `/settings/general`, read the actual
   rendered DOM, name what's missing (here: no group headers, no add-custom control).
2. **Map the data path end-to-end** before blaming staleness. Grep the *sender* (bridge),
   the *relay* (server), and the *reader* (client hook) for the payload field
   (`builtinRoleNames`). The bug lives where the field is present upstream but absent
   downstream.
3. **Distinguish stale-runtime from real-bug.** Rule out browser cache (hard reload),
   stale bundle (`stat` the served `dist`, grep it for the feature string), and stale
   bridge (`npm run reload`) — *one at a time*. When all are fresh and it's still broken,
   it's a code bug.
4. **Find the drop points.** The field was emitted by the bridge but silently dropped at
   **two relay hops**: `event-wiring.ts` (server re-broadcast) and `useMessageHandler.ts`
   (client handler). Both only forwarded `{roles, presets, activePreset}`.
5. **Check the spec.** The existing `dashboard-roles-ownership/spec.md` already *mandated*
   `builtinRoleNames` reach the client → this is a **spec-conformance bug**, which frames
   the change cleanly as a bug-fix.
6. **Scaffold the change** with `openspec new change <name>` (not `openspec change new`).
   Write proposal + design (4-hop trace, Mermaid) + delta spec + TDD tasks. Validate strict.
7. **TDD red→green:** write 2 regression tests (server hop + client hop) proving they fail
   against current source, then apply the 3 additive one-liners, then confirm green + full
   suite + `tsc --noEmit`.
8. **Verify in the real browser** (fast path) and author a **permanent E2E guard**
   (`tests/e2e/roles-custom.spec.ts`, system Chrome against the Docker harness).
9. **Ship** via `ship-change`: branch → verify gate → archive+sync → commit (exclude
   unrelated concurrent edits) → PR → watch CI → auto-apply CodeRabbit → squash-merge.

## 3. How the collaboration unfolded

**Phase 1 — Disambiguate the ask (Discovery).** The user said "dynamic provider names";
the AI first searched OpenSpec and (correctly) reported provider-management was already
shipped. The user pushed back — the AI then grounded itself in the *actual UI source*
(`SettingsPanel.tsx`) and asked a clarifying question. The unlock came when the user said
"@fast etc definitions": **roles, not providers** — a different subsystem
(`pi-dashboard-roles-plugin`, Settings → General). *Why it worked:* the AI stopped
guessing and re-anchored on the user's concrete words each time it was corrected.

**Phase 2 — Reproduce & isolate (Investigation).** Using the `browser` tool the AI opened
the live dashboard, confirmed the ROLES section renders **flat** (the back-compat branch),
and then eliminated false causes in order: browser cache (hard reload — still flat),
served bundle (`stat` + grep "Add custom role" — fresh, has the feature), bridge
(`npm run reload` — still flat). With every runtime layer fresh, it traced the payload and
found `builtinRoleNames` **dropped at two relay hops**. *Decision point:* the human's
"check with browser" instruction is what forced empirical proof instead of a code-reading
guess.

**Phase 3 — Frame as a spec bug (Design).** The AI checked `dashboard-roles-ownership/spec.md`
and found line 191 already *requires* the field to reach the client → the implementation
**violates an existing requirement**. That reframed the fix from "new feature" to
"spec-conformance bug-fix," which is a cleaner, lower-risk change.

**Phase 4 — Scaffold + TDD (Generate).** `openspec new change fix-builtin-role-names-relay`,
then proposal/design/delta-spec/tasks. TDD: 2 regression tests written red, 3 one-line
fixes applied, tests green, full suite 9925 passed / 0 failed, `tsc` clean.

**Phase 5 — Verify at every level (Verify).** Fast browser verification confirmed the fix
end-to-end. Then the user asked whether the unchecked manual tasks could be covered by
Playwright in a *system* browser — the AI authored `tests/e2e/roles-custom.spec.ts`, built
the per-worktree Docker image, fought through boot issues (see Pitfalls), and got it green
in system Chrome. *Decision point:* "make tests" → the human explicitly wanted a permanent
regression guard, not just a one-off check.

**Phase 6 — Ship.** `ship-change`: branch, verify gate, archive+sync specs, a clean commit
that **deliberately excluded** an unrelated `groups.json` concurrent edit, PR #304, CI
green, one CodeRabbit comment (ASCII→Mermaid) auto-applied, squash-merge, cleanup.

## 6. Skills, tools & memory created — and why they're effective

**Two memories saved** (both about the same failure mode):

- **failure · insight** + **project** memory — *"custom-roles UI can silently break because
  `builtinRoleNames` is dropped on the server→browser relay; it must be carried at BOTH
  relay hops (`event-wiring.ts` broadcast and `useMessageHandler.ts` handler)."*
  **Why effective:** encodes the non-obvious two-hop drop pattern so the next person who
  sees a flat ROLES render checks the relay first instead of re-tracing from scratch. The
  general lesson — *a feature wired at sender+reader but not the intermediate relay hops is
  permanently invisible* — applies to any bridge→server→client payload field.

**E2E skill patched** (not created): the manual `test-up.sh` **attach recipe** (pre-build
the per-worktree image, bring the container up seeded with `PI_E2E_SEED=1` +
`PI_TEST_PEERS=both`, attach Playwright in fast mode) was folded into the existing e2e skill
because it was undocumented and hard-won.

**Recommended skill that should exist:** a *"diagnose a merged-but-invisible dashboard
feature"* playbook — reproduce in browser → eliminate cache/bundle/bridge → grep the
payload field across sender/relay/reader hops → check the spec for a conformance
requirement. This session followed exactly that shape.

## 7. Pitfalls & dead ends

- **`openspec change new` is wrong** — it failed; the correct command is
  `openspec new change <name>`.
- **Stale-runtime red herrings** — hard reload, `stat`+grep the served bundle, and
  `npm run reload` all came back *fresh*; the real bug was in code. Don't stop at "must be
  stale."
- **Docker E2E boot fought back:** (1) `test-up.sh` runs `docker compose up` **without
  `--build`**, so you must pre-build the per-worktree image first (~4–6 min); (2) it can
  rebuild *inline* and blow the 180s health cap under load (4 other test containers + 8 pi
  sessions were running); (3) a manual `test-up.sh` **without `PI_E2E_SEED=1`** leaves the
  onboarding CTA disabled ("Set up credentials first"). Fix: bring the container up manually
  detached with `PI_E2E_SEED=1 PI_TEST_PEERS=both`, wait for health, attach Playwright in
  fast mode.
- **Shared-checkout concurrency:** other live sessions edited `groups.json` and a skill file
  mid-work, and git even switched the branch back to `develop` once. Stage only your own
  files; expect the working tree to move under you.
- **Memory stores at capacity** — the `memory add` calls hit full stores; the AI skipped a
  consolidation detour since the knowledge was captured in `design.md` anyway.
