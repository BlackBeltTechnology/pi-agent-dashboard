# How we did it: shipping an apply-ready OpenSpec change with cross-model doubt review — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
no implementation allowed. The real objective, once it crystallized: turn a rough idea —
*"the session list has no way to group sessions by kind of work"* — into a **complete,
validated, apply-ready OpenSpec change** (`add-session-tags`) with mockups, a design, a
spec, and tasks — and then **harden it against real implementation bugs before writing a
single line of code**. The finished artifact was committed surgically to `develop` as
docs-only, ready for a future `openspec-apply`.

## 2. TL;DR playbook

1. Start in `openspec-explore`. Let the AI **ground the idea in existing code** first
   (it found `SessionMeta.tags` sidecar + sidebar filter were the natural anchors).
2. Pick the smallest option deliberately: reply **`A`** to choose the "thin manual
   labeling layer" over heavier alternatives.
3. Ask for **mockups folded into the proposal** — `create mockup and be part of the proposal`.
   Iterate them visually (`start mockup server`, `colorize tags`, `keep auto hue`).
4. Fast-forward the rest of the artifacts: invoke `openspec-ff-change` to generate
   `design.md → specs/*/spec.md → tasks.md` in one pass, each grounded in real code paths.
5. **Run a cross-model doubt review** before implementing: `doubt review deepseek pro as
   secondary model`. Pick a *different architecture family* as the adversary.
6. Drive multiple cycles (`second cycle`, `third cycle`) — but **verify every reviewer
   claim against the real files** before folding fixes in. Stop when cycles stop
   converging OR the remaining risk is a scope decision, not a patch.
7. Resolve the last open scope question (`B` = single change, filter task = explicit audit).
8. Commit **only** the change directory (`commit`) — surgical, leave unrelated tree work alone.

## 3. How the collaboration unfolded

**Phase 1 — Ground before sketching (Discovery).** In explore mode the AI read
`session-meta.ts`, `DashboardSession`, and the sidebar filter before proposing anything.
*Why it worked:* it discovered the feature was 90% precedented — a `.meta.json` sidecar
and a filter row already existed — so the proposal could be tiny. **Decision point:** the
human picked **Option A** (thin manual `tags: string[]` layer) over restructuring the
typed classification fields.

**Phase 2 — Mockups as thinking (Design).** The AI scaffolded the change, then built three
cross-linked dark-theme mockup pages (`index`, `card-states`, `filter-in-action`) sharing a
`_tokens.css`, each visually resolving one of the proposal's Open Decisions. It verified
renders with the `browser` tool (Playwright headless wasn't installed — it fell back
gracefully). **Decision points:** `colorize tags` → deterministic per-tag hue; `keep auto
hue` → locked auto-hue as zero-storage (`hash(tag) % palette`), dropping the override map.
*Why it worked:* the load-bearing visual distinction (solid colored user chips vs
dashed/muted execution chips) made the whole "Option A discipline" legible at a glance.

**Phase 3 — Fast-forward the artifacts (Generate).** `openspec-ff-change` produced
`design.md` (D1–D6, each tied to a real code path), `specs/session-tags/spec.md`, and
`tasks.md` in one pass — then validated clean. *Why it worked:* the AI re-grounded in the
actual write→broadcast handlers and filter predicate before writing, so the design cited
real files, not guesses.

**Phase 4 — Cross-model doubt review (Verify — the payoff).** The human chose **DeepSeek
v4 Pro** as an adversarial reviewer from a *different architecture family*. The AI probed
reachability, then ran three cycles: each spawned DeepSeek with an **issues-only, no-claim**
prompt and repo read access, and the AI **verified every load-bearing finding against the
real code before classifying it**. It caught bugs the spec would otherwise have shipped:
tags **wiped on every save** (the `onChange` persistence is a full-overwrite enum with a
warning comment), a mis-described write path (D2 invented a `mergeSessionMeta` call that
doesn't exist), a filter integrated at *one* site when *7+* folder-tier gates needed it, an
"automation" phase chip guaranteed to return zero results, and an FNV hash that overflows in
JS. **Decision point:** `B` — keep the risky filter work in a single change but de-risk it
with an explicit *audit-every-gate* task plus tier-coverage tests.

**Phase 5 — Surgical commit.** With unrelated Gateway/roles work in the tree, the AI staged
**only** `openspec/changes/add-session-tags/` and committed docs-only to `develop`.

## 4. Prompts that worked

- **Goal prompt (the explore-mode skill invocation).** Strong because it set a *stance*
  (think, don't implement) — which forced grounding-before-proposing and kept the output as
  reusable artifacts rather than premature code.
- **`A` / `B`** — single-letter option picks. High leverage: the AI had already laid out
  the trade-offs, so one character committed the direction without re-litigating.
- **`create mockup and be part of the proposal`** — tied a visual artifact to the spec so
  the mockup became load-bearing, not decoration.
- **`doubt review deepseek pro as secondary model`** — the highest-leverage prompt in the
  session. It named both the *method* (doubt review) and a *cross-family adversary*, which
  is what surfaced the real bugs.
- **`second cycle` / `third cycle`** — cheap prompts that unlocked large verification work;
  each was justified because the artifact had *materially changed* since the prior pass.

**Rewrite for next time:** instead of the bare `colorize tags`, say *"add deterministic
per-tag color (hash→palette, zero storage) and keep execution chips uncolored so the
user-vs-derived distinction survives."* — that states the discipline the AI otherwise had
to infer over two turns.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were saved, but the session is a textbook application of three
existing ones worth invoking deliberately:

- **`openspec-explore` → `openspec-ff-change`** — the explore stance forces
  grounding-before-implementing; the fast-forward then generates all four artifacts in one
  validated pass. Invoke this pair whenever an idea is fuzzy but you want an apply-ready
  change, not just notes.
- **Cross-model doubt review (via `Explore` subagents on `deepseek/deepseek-v4-pro`)** — the
  reusable pattern: pick an adversary from a *different architecture family*, hand it an
  **issues-only prompt with no claim/reasoning** plus repo read access, then **verify each
  finding against real code before acting**. It caught five real bugs here. *This deserves a
  saved skill* (e.g. `cross-model-spec-review`) if you don't already have one — it removes
  the "my own spec looks fine to me" blind spot before implementation cost is sunk.
- **`serve_mockup` + `browser` tool** — mockups verified visually in a real browser (with a
  graceful fallback when Playwright headless was absent). Effective for making design
  decisions concrete before they're spec text.

## 7. Pitfalls & dead ends

- **Playwright headless shell not installed** → the AI fell back to the `browser` tool for
  visual verification. If mockup rendering fails, use `browser` directly rather than blocking.
- **A cycle-3 reviewer spawn returned empty** → surfaced (not swallowed), retried once,
  succeeded. If a cross-model subagent returns nothing, treat it as a transient provider
  hiccup and retry before concluding.
- **Self-inflicted contradictions after folding fixes** → cycle-1 edits fixed "Active-only"
  in Context/D4 but left it in the Goals bullet; cycle 2 caught it. Lesson: after a large
  spec correction, re-grep for the *old* term everywhere, or let the next doubt cycle find
  the residue.
- **Line-number-based integration claims are brittle** → "3 filter sites" became "7+ gates."
  Reframe integration tasks as a *behavioral requirement + audit-every-gate task*, not a
  fixed site list.
