# How we did it: Promoting reusable project skills into publishable workspace packages — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation one — with a broad question about how pi skill *activation* works and
whether a skill's presence could depend on OpenSpec being set up. Two steering turns
later the *real* objective crystallized: **"take the reusable skills we authored in
root `.pi/skills/` and promote them into publishable workspace packages in the
monorepo, so they ship as deliverables (`npm publish -ws`) instead of living only in
this repo."** The first concrete prompt that set the direction:

> *"spec-coherence-check, fix-worktree-opsx-skills-not-created,
> pre-scaffold-openspec-coherence-check, faq-mine have to be in package in the
> monorepo as deliverable skills. Maybe its multiple extensions, check and add them.
> Check other skills, some of them general skills which reusable in other project
> type."*

So the deliverable was: classify every project-authored skill, group the generic ones
into new thematic packages, `git mv` them (preserving history), scaffold each package
(`package.json` + `pi.skills`, `README.md`, `AGENTS.md` DOX), genericize any
project-coupled text, verify pi still discovers them, then commit and push.

## 2. TL;DR playbook

1. **Ground the mechanism first.** Confirm how packaged skills reach this repo: root
   `workspaces: ["packages/*"]` auto-symlinks each package into
   `node_modules/@blackbelt-technology/…` on `npm install`; pi scans each package's
   `pi.skills` array. → Moving a skill into a `packages/*` package keeps it available
   here. **No breakage.**
2. **Scan and classify** all skills with a full pi-accurate discovery (3 surfaces:
   project `.pi/skills` + `.agents/skills`, global `~/.pi`, and package `pi.skills`).
   Split *ours* vs *tool-generated* by the `generatedBy`/`author: openspec` marker.
3. **Coupling check** — grep each candidate for hardcoded project paths/names. Pure
   moves (0 refs) vs light-scrub (a few example paths) vs needs-genericizing.
4. **Create the package dirs and `git mv` the skills** (preserves history). Do this
   **idempotently** — a git `index.lock` from a concurrent session can leave a partial
   move; re-run with `mv_if` guards, don't assume a clean slate.
5. **Scaffold each package**: `package.json` (with `pi.skills` + `publishConfig.access:
   public`), `README.md`, `AGENTS.md` DOX table (caveman-style, one row per file). Copy
   an existing pure-skill package (`anti-slop`) as the template.
6. **Genericize** the coupled lines — swap `pi-agent-dashboard`/`src/client` examples
   for neutral placeholders in the 3 flagged skills.
7. **`npm install`** to create the workspace symlinks, then **verify**: symlinks live,
   every `pi.skills` entry resolves, no residual coupling, no broken path refs, scanner
   tests pass (with an ephemeral `HOME=$(mktemp -d)`).
8. **Re-stamp the DOX staleness map** for any skill whose content you edited (hash
   drifts → `kb dox lint` flags `stale`); prune dangling old-path keys.
9. **Commit precisely and push.** Stage only your files by path (a concurrent session
   may already own the index).

## 3. How the collaboration unfolded

**Phase 1 — Explore / reframe (the thinking stance).** The AI stayed in explore mode,
read pi docs, and produced the key insight: *pi has no runtime conditional skill
activation* — a skill's description is static text baked into the system prompt at
startup. "Activation depends on OpenSpec" can only mean **presence** (does the SKILL.md
exist in a scanned location, controlled by a hook/generator) or **visibility**
(`disable-model-invocation` frontmatter). This grounding is what made every later
decision correct. *Why it worked:* the AI refused to answer from imagination and
instead derived the mechanism from the actual docs + the existing `openspec-*` skills.

**Phase 2 — Grounded inventory.** A read-only full scan surfaced the payload finding:
*18 skills mention openspec but only 8 are generated → 10 custom skills silently depend
on openspec being active.* The scan also caught a real pitfall — a naive `SKILL.md`
find **under-reports** because package skills are registered via `pi.skills` in
`package.json`, discovered differently. *Decision point:* the human redirected from the
abstract "gated audit skill" idea toward the concrete packaging task.

**Phase 3 — Classify + plan the move.** Before touching files the AI ran a coupling
check on each candidate (pure move vs light scrub vs needs-genericizing) and confirmed
the loading mechanism so the move couldn't silently break skill availability. It
presented the grouping (3 new packages + 1 addition) and got the "handle it" go-ahead.

**Phase 4 — Execute the sweep.** `git mv` into `packages/openspec-workflow`,
`frontend-patterns`, `code-review-toolkit`; `faq-mine` into `authoring-toolkit`. A git
`index.lock` (concurrent session) caused a partial first run — the AI recovered
idempotently rather than force-blasting. Then it scaffolded manifests/READMEs/DOX,
genericized the 3 coupled skills, ran `npm install`, and verified everything green
(33/33 tests, 4/4 symlinks, 16 `pi.skills` resolve).

**Phase 5 — Follow-ups + polish.** The human said "handle" for three loose ends:
licensing/NOTICE (investigated git history → project-authored, none needed), stale
docs pointers (delegated to the **DocScribe** subagent per the repo's Rule-6
caveman-style docs rule), and residual coupling. Then two targeted steers: replace
`haiku` with the `@fast` role alias in faq-mine, and audit whether any skill hardcodes
a model name where a role belongs.

**Phase 6 — Commit + push.** A surprise: `git diff --cached` was empty though the index
showed the moves. Root cause: a **concurrent session's commit `757975f89`** had swept
the staged `git mv` renames in via the shared index (the earlier `index.lock`
contention). The AI diagnosed it, staged the remaining 19 files precisely, committed
`c4200afdc`, flagged the untidy history honestly, and pushed.

## 7. Pitfalls & dead ends

- **git `index.lock` from a concurrent session** halted the first `git mv` batch
  mid-run → partial move. **Fix:** don't force a clean re-run; use idempotent `mv_if`
  guards (`[ -d src ] && git mv …`) so already-moved skills are skipped.
- **A concurrent session committed your staged renames.** `git diff --cached` came back
  empty even though the index showed the moves — commit `757975f89`
  ("plan(slim-kb-search-output)") had swept the `git mv`s in via the shared index.
  **Fix:** verify with `git log --oneline -- <new-path>` to find which commit actually
  carried the move; stage only *your* remaining files by explicit path, don't `git add -A`.
- **Scanner tests need an ephemeral HOME.** The vitest scanner suites failed until
  re-run as `HOME=$(mktemp -d) npx vitest run …`.
- **DOX staleness after editing content.** Genericizing/`@fast`-swapping a skill drifts
  its content hash → `kb dox lint` reports `stale`. **Fix:** re-stamp the acknowledged
  hash in the staleness map and prune dangling old-path keys after moves.
- **Naive `find … SKILL.md` under-reports skills.** Package skills live behind
  `pi.skills` in `package.json`, not always a `SKILL.md` in a scanned dir — resolve
  them the way pi does or the audit is wrong.
- **Project memory at capacity** (4858/5000) — saving blindly would evict good entries.
  Skip + flag `consolidate-pi-memory-store` instead.
