# How we did it: Styling GFM tables in the chat view — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
no implementation allowed. The operator's real objective, which only became crisp after
the first steering turn: *chat-view Markdown tables look flat and unreadable — figure out
why, prove a better design that works across every theme, and capture it as a scaffolded
OpenSpec change (proposal + design + spec delta + tasks + a live mockup), without writing
any production code.* The AI's job was to ground the "two renderers look different" hunch
in the actual source, disprove or confirm it, and turn the finding into a build-ready
change.

## 2. TL;DR playbook

1. Kick off in **explore mode** so the AI investigates and mocks but never touches
   production code: `Enter explore mode …` (the `openspec-explore` skill prompt).
2. Ask it to **ground the hypothesis in source first** — find every Markdown/table
   renderer and every table CSS rule before theorizing.
3. Let it **build a live comparison mockup** (`serve_mockup`) showing *current vs
   proposed* side by side, and screenshot it with the `browser` tool to verify.
4. Steer with three crisp answers in one turn: **"apply to all themes, add a theme
   selector to the mock, style the whole markdown content."**
5. Have it **pull real theme tokens straight from `themes.ts`** (dump to JSON) instead
   of hand-transcribing — then regenerate the mock across all 9 themes × dark/light.
6. Spot-check the **riskiest palettes** (low-contrast Solarized, a light theme) in the
   browser, not just the happy-path base theme.
7. Say **"scaffold"** — it runs the coherence check (archive sweep for duplicate
   capabilities), picks ADDED vs MODIFIED deliberately, writes all artifacts, and
   validates with `openspec validate <name> --strict`.
8. Say **"commit"** — it stages **only** the change dir (`git reset` first) so unrelated
   pre-staged work is left untouched.

## 3. How the collaboration unfolded

**Phase 1 · Discovery (ground the hypothesis).** The AI grepped for Markdown renderers
and table CSS across `packages/`. It found both the chat view and the content view funnel
through the *same* `MarkdownContent` component styled by a *single* `.markdown-content
table` block in `index.css` (bordered header, **no zebra striping anywhere** in the repo).
*Why it worked:* it refused to accept the "two competing renderers" framing and proved the
real root cause — a **contrast problem** (header `--bg-tertiary #1e1e1e` sits only ~10 luma
from the chat bubble `--bg-secondary #141414`) plus absent row banding.

**Phase 2 · Design + first mockup.** It built a live `serve_mockup` page (current vs
proposed, light/dark toggle) and screenshotted it. Proposed: header = `--bg-surface`,
soft dividers, zebra even-rows, 8px rounded clip, row hover. *Decision point:* the human
answered the AI's open questions — **all themes, theme selector in the mock, whole markdown
content** (steering #1).

**Phase 3 · Generalize across the theme system.** The AI discovered the theme system is
**not** two CSS blocks but **9 named themes × dark/light = 18 palettes** applied inline
from `packages/client/src/lib/themes.ts`. It **dumped the real token maps to JSON** and
regenerated the mock with a full theme + mode selector plus live token swatches. *Why it
worked:* the design collapsed to **two theme-adaptive knobs** — header reuses each theme's
existing `--bg-surface` (no new token), stripe is one new semantic `--table-stripe` overlay
per mode. No hand-transcribed colors.

**Phase 4 · Verify the matrix.** It spot-checked Solarized/dark (teal header vanishing
into teal bubble) and GitHub/light in the browser, confirming both knobs adapt
automatically across all 18 palettes.

**Phase 5 · Scaffold + validate.** On "scaffold" it ran a coherence check: capability =
`markdown-rendering`; archive sweep found `ascii-table-monospace` / `markdown-chat-renderer`
(ASCII/monospace) and `theme-system` / `theme-gallery` (themes) — none did GFM zebra, so
**no duplicate**. It chose **ADDED** a focused "GFM table visual styling" requirement over
MODIFYING the giant existing GFM paragraph, wrote proposal/design/tasks/spec-delta/mockup,
and passed `openspec validate --strict`.

**Phase 6 · Surgical commit.** On "commit" it `git reset`, staged only the change dir, and
committed `b116e58e8`, deliberately leaving pre-existing unrelated staged changes untouched.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — the session leaned on existing assets:

- **`openspec-explore`** — kept the AI in think/mock mode so it produced a *build-ready
  change* instead of prematurely editing `themes.ts`/`index.css`. Invoke it whenever the
  problem is still fuzzy and you want a proposal, not a patch.
- **`serve_mockup` + `browser`** — the design was *verified visually across 18 palettes*
  before a single production line changed. Invoke this pairing for any theme-sensitive UI
  change.
- **`theme-system` skill knowledge** — pointed at `themes.ts` as the token source of truth.

*Recommendation:* this exact workflow (ground → multi-theme mock → coherence-check →
scaffold) is repeatable enough that a **"theme-aware UI change proposal"** skill would pay
off — it would encode "dump `themes.ts` to JSON, generate an N-theme mock, spot-check the
low-contrast palettes."

## 7. Pitfalls & dead ends

- **The "two competing renderers" hypothesis was wrong.** If a UI looks different in two
  places, don't assume two code paths — grep first. Here both views shared one component;
  the difference was **background contrast**, not styling.
- **The theme system is bigger than the CSS suggests.** `index.css` only shows `:root` +
  `[data-theme="light"]`, but the real 9 themes live inline in `themes.ts`. If you mock from
  `index.css` alone you miss 16 palettes — always check `themes.ts`.
- **One failed grep** (`nth-child\|zebra\|striped…` with a bad escape) — retried with the
  repo-wide variant; no real loss, just re-run the pattern across `packages`.
- **Pre-staged unrelated changes** were sitting in the index. `git reset` before `git add
  <change-dir>` kept the commit surgical — do this whenever the index isn't clean.
