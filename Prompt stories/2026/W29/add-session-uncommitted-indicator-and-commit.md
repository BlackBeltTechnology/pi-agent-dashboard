# How we did it: Session uncommitted-changes indicator + one-click commit — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff was a single skill invocation:

```
/skill:openspec-apply-change add-session-uncommitted-indicator-and-commit
```

The real objective, decoded from the attached OpenSpec proposal: a dashboard session
card shows git branch / PR / worktree but gives **no signal that the working tree is
dirty** — so a user watching an agent work can't tell the agent produced uncommitted
changes. This change adds (1) a **dirty-count pill** on the card and folder header,
(2) a **Commit dialog** with per-file selection, and (3) an **AI-drafted commit
message** generated by an isolated fork-subagent. A 34-task, security-sensitive,
TDD-mandated vertical slice spanning all four packages (shared → extension → server →
client), then landed end-to-end through CI + CodeRabbit.

The whole build ran on **Opus (high thinking)** across four operator prompts — one
goal, three short steers — over ~8 hours.

## 2. TL;DR playbook

1. **Kick off with the apply skill:** `/skill:openspec-apply-change <change>`. Let it
   read the proposal + all context/spec files before touching code.
2. **Do TDD per task, bottom-up:** shared types first, then bridge, server, client.
   Write the failing test, then the minimal implementation, then mark the task.
3. **Run vitest with an ephemeral HOME** (`HOME=$(mktemp -d) npx vitest run <file>`)
   so the pi registry/config doesn't leak into the test.
4. **Expect worktree tsc noise:** `npx tsc --noEmit` flags `pi-dashboard-shared` errors
   because the worktree resolves the shared package to the *main* checkout. Trust
   **vitest** (resolves worktree source) and **`npm run build`** (vite, resolves
   correctly) — not raw tsc — for shared-export changes.
5. **Delegate the `docs/architecture.md` prose to a subagent** with the caveman-style
   rule verbatim (project Rule 6). Main agent never edits `docs/` prose directly.
6. **Turn the QA/`V.*` tasks into Playwright E2E** driven by the **system Chrome**
   (`PW_CHANNEL=chrome`), setting up git state via the dashboard's own same-origin REST
   (cookie-auth inherited by `page.evaluate(fetch)`).
7. **Rebuild the Docker harness from local changes** before running E2E — a stale
   long-running container silently runs the *old* image. Recreate, wait for health,
   attach.
8. **Ship with the ship-change skill:** verify gate → archive+sync specs → merge
   develop (resolve conflicts) → push → PR → watch CI → drain CodeRabbit → squash-merge
   → remove worktree.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (read the whole change first).** The AI resolved the
`openspec-apply-change` skill from the main repo root (worktrees don't carry the skill),
pulled `openspec status`, and read *every* context + spec file before writing a line.
It explored the existing git plumbing (`vcs-info.ts`, `git-operations.ts`,
`git-routes.ts`, shared `platform/git.ts`) to reuse rather than reinvent. **Why it
worked:** a 34-task security-sensitive change rewards front-loading context — the AI
picked a single `parseGitStatusV2` parser reused by *both* bridge and server instead of
two drifting copies.

**Phase 2 — Vertical build, bottom-up TDD.** Shared types + protocol + REST types +
the porcelain-v2 parser (with unit tests) → bridge `gatherGitStatus` folded into the
*existing* 30 s VCS tick (deduped via `lastGitStatusJson`, no new loop) → server
`getGitStatus`/`getChangedFiles`/`commitFiles` + routes (with a path-injection test) →
client `GitDirtyPill`, `CommitDialog`, per-cwd `git-status-cache`, wired into
`SessionCard`/`GroupGitInfo`/`App`. The AI ran tests package-by-package with an
ephemeral HOME, marking each task as it went. **Decision point:** the AI created a
*pure, injectable* `commit-draft.ts` (fork-subagent → diff-only → stub ladder) separate
from the SDK-coupled `commit-draft-agent.ts` (in-process `SessionManager.inMemory`,
`tools:[]`) — keeping the fallback logic testable and the SDK glue isolated.

**Phase 3 — Steer #1: real E2E, real browser.** The human redirected the leftover QA
`V.*` tasks: *"Implement missing tasks as e2e playwright tests with system browser."*
This forced the AI to study the Docker harness, discover it could dirty the tree via
the markdown-only `POST /api/file/write`, and drive the pill/dialog through real
testids. It also surfaced a **genuine bug**: `GroupGitInfo` rendered the header pill for
*single*-session folders, double-counting a solo session — fixed + RTL-gated.

**Phase 4 — Steer #2: "go on" → harness reality.** The AI rebuilt the Docker image from
local changes, caught that a 5-hour-old container was running the *stale* image,
recreated it, learned the client uses cookie auth (so `page.evaluate` fetches inherit
it), fixed its own helper (`json.success`, not `json.ok`) and a shared-container
cleanliness assumption, and got **all 5 E2E specs green** against system Chrome.

**Phase 5 — Steer #3: "ship-change".** Verify gate (`npm run build` ✓; the 18 `npm
test` reds were all in *untouched* packages — `image-fit` Jimp v0/v1 env mismatch +
a `doctor` flake, later confirmed by green CI). Archive + sync 2 new specs, merge
develop (3 conflicts resolved by *union*), push, PR #316, watch CI. Two real CI fixes
(a `TS2493` empty-tuple mock error caught only by `npm run lint`/tsc, not `npm
test`/build; and one flake re-run), then drained CodeRabbit's 16 comments (7 applied,
rest deferred with documented reasons), and **squash-merged** to develop.

## 4. Prompts that worked

- **The goal prompt** — `/skill:openspec-apply-change <change>`. Effective because the
  change already had a proposal + tasks.md; the skill gives the AI a task ledger to work
  and mark, so it never loses the plot across 34 tasks and 8 hours.
- **`Implement missing tasks as e2e playwright tests with system browser`** — a
  high-leverage one-liner. It converted vague manual QA tasks into *runnable,
  regression-proof* coverage and (as a side effect) surfaced a real double-count bug.
  The "system browser" clause is load-bearing: it steered to `PW_CHANNEL=chrome` against
  the real harness, not a headless mock.
- **`go on`** — a trust-unlock that let the AI push through the multi-step harness
  rebuild + debug loop without hand-holding.
- **`ship-change`** — invoked the full land-it pipeline as one word.

Rewrite for next time: fold the E2E intent into the *first* prompt —
*"apply this change; implement every `V.*` QA task as a Playwright E2E spec against the
system browser (`PW_CHANNEL=chrome`) via the Docker harness."* That removes the round
trip in Phase 3.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Leave `V.*` QA tasks as manual/unverified | "Implement missing tasks as e2e playwright tests with system browser" | State up front that QA tasks become Playwright E2E on `PW_CHANNEL=chrome` |
| Pause to ask for prioritization mid-build (the one `ask_user` call) | "go on" / full send | Say "full send, don't check in" in the kickoff for a well-specified change |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session — the work rode existing project
skills (`openspec-apply-change`, `ship-change`) and the caveman-docs subagent
convention. What *should* be captured as reusable knowledge:

- **"Worktree shared-package tsc noise is expected"** — a memory/quirk worth saving:
  in a `.worktrees/*` checkout, `tsc --noEmit` resolves `pi-dashboard-shared` to the
  *main* checkout, so shared-export edits show phantom errors. **vitest** and **`npm run
  build`** (vite) resolve worktree source correctly; trust those. Saves re-diagnosing
  the same false alarm every worktree change that touches shared.
- **"Dirty the harness tree via markdown REST"** — the E2E pattern (`POST
  /api/file/write` on a `.md` fixture, cookie-auth inherited by `page.evaluate`) is a
  reusable recipe for any git-state E2E scenario.

The one subagent spawned — `general-purpose` to update `docs/architecture.md` in
caveman style — is the correct division of labor: it keeps the main agent out of
`docs/` prose (Rule 6) while the main agent orchestrates.

## 7. Pitfalls & dead ends

- **Stale Docker container** — a container "Up 5 hours" ran the pre-change image; the
  new endpoint 403'd. *If E2E behaves like the old code, recreate the container from a
  fresh `--build` and confirm health before attaching.*
- **Helper read the wrong response field** — the dashboard's `ApiResponse` uses
  `success`, not `ok`; the E2E helper misread every success as a failure. *Check the
  actual `ApiResponse` shape before asserting on it.*
- **Shared-container cleanliness** — a spec assumed a clean baseline that a prior buggy
  run had dirtied. *Establish your own baseline in the spec; never assume the shared
  harness is clean.*
- **tsc-only CI failure** — `npm test` + `npm run build` were green locally but CI's
  `npm run lint` failed on a `TS2493` empty-tuple mock arg. *Run `npm run lint` before
  pushing.*
- **CodeRabbit "move out of archive/" false positive** — `openspec archive` legitimately
  places completed changes under `openspec/changes/archive/YYYY-MM-DD-<name>/`; that
  guideline is about *creating* new artifacts. Deferred, documented.
- **Final `bash` lockout** — removing the worktree in the last ship step killed the
  session's own cwd; bash could no longer start. Expected — do worktree removal last.
