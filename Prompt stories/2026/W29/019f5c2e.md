# How we did it: Elevate two project skills into shippable packages — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation task. The literal first prompt was the skill's boilerplate: *"Enter explore
mode. Think deeply… You may create OpenSpec artifacts if the user asks."* The **real
objective**, which crystallized over the first two steering turns, was:

> Look at the ~30 project skills and decide which ones deserve to be **promoted out of
> this repo** — either folded into the published `eng-disciplines` package or spun into
> their own npm-released pi extension — and capture those decisions as OpenSpec proposals.

By the end it had narrowed to **two concrete moves**: elevate `scenario-design` into
`eng-disciplines`, and extract `distill-session-knowledge` (+ its `session-distiller`
engine) into a separately published package. Both were captured as full, validated
OpenSpec changes and committed.

## 2. TL;DR playbook

1. **Start in explore mode** (`openspec-explore`) so the AI investigates and reasons but
   is forbidden from implementing — perfect for a "which of these should we ship?" question.
2. **Ask for the elevation test first, not the answer.** Have the AI read the target
   package's charter (`eng-disciplines` README) and derive the *criteria* a skill must meet.
3. **Make it sort every candidate into buckets** against that test (A: repo machinery →
   never elevatable · B: elevatable · C: needs decoupling). One pass, no re-derivation later.
4. **Probe the packaging shape with a sharp yes/no question** ("is X a pi extension?"). This
   surfaces the skill-vs-engine trap: a public skill can't shell out to an unpublished
   internal CLI.
5. **Let the human pick the split** ("A into eng-disciplines, B as a separate npm package").
   Don't guess the boundary — it's a product decision.
6. **Run the coherence check before scaffolding** (archive + active collision sweep) and use
   the `openspec` CLI (`openspec new change <name>`), never hand-mkdir.
7. **Mirror a recent complete change** for artifact format, then write all four artifacts per
   change: `proposal → design → specs → tasks`. Reference any archived predecessor as a *delta*.
8. **Validate** (`openspec validate <change>`) until each reports `done` / `isComplete`.
9. **Save the reusable judgment as a project skill** so the next person doesn't re-derive the
   bucketing.
10. **Commit surgically** — only the new change dirs; leave unrelated working-tree churn
    (`groups.json`) out unless explicitly told to include it.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (charter grounding).** The AI resisted theorizing. It read the
`eng-disciplines` README to extract its explicit charter — *portable, cross-cutting
disciplines*, with an explicit exclusion list (`frontend-ui-engineering`,
`code-review-and-quality`, `ci-cd`, `git-workflow`, …). *Why it worked:* the charter became
the objective yardstick, so "should this be elevated?" stopped being taste and became a test.

**Phase 2 — Sort (the 4-part test + A/B/C buckets).** The AI defined a 4-part elevation test
(practice-not-pattern · portable · outside-excluded-categories · fills-a-gap) and ran all ~30
project skills through it, bucketing them. *Decision point:* the human didn't touch this — the
AI's grounded sort was accepted.

**Phase 3 — Packaging shape (the sharp question).** Human steered: *"is session-distiller a pi
extension?"* The AI investigated `package.json` and found `private: true` + no `pi` field →
it's a plain internal CLI/lib, **not** a discoverable extension. This exposed the core
constraint: a published `eng-disciplines` skill cannot depend on an unpublished internal
engine. Human then set the split explicitly: *"scenario-design → eng-disciplines, but
distill-session-knowledge → separate npm-released extension in the monorepo."*

**Phase 4 — Scaffold + generate.** The AI ran the coherence check (found an archived
`2026-06-23-distill-session-knowledge` → treated the new proposal as a *delta* on it, not a
dup), scaffolded both changes via the `openspec` CLI, mirrored a recent change's format, and
wrote all eight artifacts. *Why it worked:* format-by-example + CLI scaffold avoided schema
guesswork; the validate loop caught the "specs delta required next" ordering.

**Phase 5 — Capture + commit.** Human: *"save it as a project skill"* → the AI wrote
`elevate-skill-to-eng-disciplines` capturing the test + buckets + skill-vs-engine trap. Then
*"commit"* → surgical commit of only the two change dirs, deliberately excluding unrelated
`groups.json` churn until the human said *"commit groups.json"* separately.

## 4. Prompts that worked

- **Goal prompt (the explore stance).** Launching via `openspec-explore` was the right
  kickoff for an open-ended "which of these should ship?" question — it bought deep
  investigation while hard-blocking premature implementation. A stronger explicit version:
  *"In explore mode: audit our project skills against the eng-disciplines charter and tell me
  which qualify for elevation, with the criteria you used."*
- **`is session-distiller a pi extension?`** — a tiny, high-leverage probe. One yes/no
  question forced the AI to inspect the package manifest and surfaced the skill-vs-engine
  constraint that reshaped the whole plan.
- **`scenario-design be part of eng-disciplines, but distill… be a separate npm released pi
  extension`** — the human making the product-boundary call in one sentence. Unlocked both
  proposals cleanly.
- **`save it as a project skill`** — converted one-off judgment into reusable memory.

## 7. Pitfalls & dead ends

- **`openspec validate` "specs delta required" is not a failure.** After writing only the
  proposal, validate complained — that's the schema demanding the *next* artifact
  (`design + specs → tasks`), not a broken proposal. Keep going down the artifact chain.
- **Don't hand-mkdir change dirs.** Use `openspec new change <name>`; it scaffolds the README
  and correct structure. The AI checked `openspec new change --help` first.
- **Unpublished engine + published skill = broken dependency.** The whole `distill` move exists
  *because* `session-distiller` is `private:true` with no `pi` field — a public skill couldn't
  call it. Verify the dependency surface before proposing an elevation.
- **Unrelated working-tree churn (`groups.json`).** It was pre-existing group renames, not this
  session's work — kept out of the surgical commit until explicitly requested.
