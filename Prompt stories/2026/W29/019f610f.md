# How we did it: Fix the split-pane composer overflow — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened in **explore mode** ("Enter explore mode. Think deeply…") with a
visible UI bug: in the dashboard's side-by-side split view, the chat composer's toolbar
overflows the narrow chat pane and the red **stop** button gets clipped. The real
objective — clarified by the steering turns — was not "hide the stop button" but
**make the composer toolbar fold by its own width instead of the viewport's**, so every
control (thinking level, Steer|Queue, terminal, after-turn, stop) stays usable in a
narrow split pane on a wide screen. Then carry it through the full OpenSpec lifecycle:
diagnose → mockup → surgical fix → proposal + spec delta → tasks → E2E → archive.

## 2. TL;DR playbook

1. **Diagnose before touching code.** `kb_search` + grep to locate `CommandInput.tsx`
   and `SplitWorkspace.tsx`; confirm the fold uses viewport `md:`/`sm:` breakpoints.
2. **Name the root cause precisely:** narrow pane + wide viewport ⇒ `md:` stays
   "desktop" ⇒ all controls render inline ⇒ row overflows the `overflow-hidden` pane.
3. **Build a repro mockup** (`serve_mockup`) with broken/fixed panels side by side —
   don't fix blind. Screenshot to confirm.
4. **Measure the breakpoint from data, not a guess.** A `measure.html` page reported the
   toolbar's natural inline width = **689px (43.09rem)**. Pick the fold threshold *above*
   that.
5. **Apply the surgical fix:** mark the composer card `@container`; switch folds from
   viewport `md:`/`sm:` to container `@[44rem]:`/`@[30rem]:` (Tailwind v4 container
   queries, built-in). ~5 class edits, one file.
6. **Verify end-to-end:** `tsc --noEmit`, run the CommandInput suites (104 pass),
   `npm run build`, then grep the built CSS to confirm `@container (min-width:44rem)` was
   emitted.
7. **Deploy:** `curl -X POST http://localhost:8000/api/restart`; confirm `/api/health`
   returns `mode: production`.
8. **Then formalize:** `openspec-ff-change` → proposal.md + `chat-view` MODIFIED spec
   delta + tasks.md; `openspec-apply` the one open follow-up (Playwright E2E);
   `openspec-archive` to sync the delta into the main spec.
9. **Commit surgically** — stage only your files, leave unrelated working-tree changes
   untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI grepped `packages/client/src` for the
composer/split components, read `CommandInput.tsx`, and confirmed Tailwind v4 (container
queries available). It stated the root cause with an ASCII diagram before writing
anything. *Why it worked:* explore-mode discipline forced diagnosis-first; the model
never jumped to a patch.

**Phase 2 — Mockup + measure.** Rather than edit the component and eyeball it, the AI
built `composer-split-overflow.html` (broken vs fixed panels) and a throwaway
`measure.html` that reported the toolbar's natural inline width. **Decision point:** the
human flagged that Steer|Queue *also* overflowed, not just stop — proving the first
`@[36rem]` guess was too low. The measurement (689px) justified raising the fold to
`@[44rem]`. *Why it worked:* the breakpoint came from measured data, so the second guess
was correct.

**Phase 3 — Surgical fix + verify.** ~5 class-only edits in `CommandInput.tsx`. Because
tests are DOM-presence based, they were unaffected; the AI still ran `tsc`, 104 unit
tests, a production build, and grepped the emitted CSS to prove the container-query rules
shipped. **Decision point:** the human said "seems ok" then "go on" → deploy via
`/api/restart`, verified healthy.

**Phase 4 — Formalize (OpenSpec).** The human invoked `openspec-ff-change`,
`openspec-apply-change`, then `openspec-archive-change`. The AI wrote proposal.md, a
`chat-view` MODIFIED spec delta (generalizing the trigger from viewport-width to
container-width), tasks.md with already-done work checked and one genuine follow-up open
(the E2E), authored `tests/e2e/split-composer-overflow.spec.ts`, ran it against the
docker harness, then synced the delta into the main spec and archived.

**Phase 5 — Commit.** Two commits (`4c98f7182` fix, `47dd937a5` archive+sync), scoped
strictly to this change; unrelated tree changes deliberately left alone.

## 4. Prompts that worked

- **Goal prompt (explore mode):** effective because it forced diagnosis before code —
  the AI produced a root-cause diagram and a repro mockup instead of a speculative patch.
- **"The Steer / Queue button also wrong on tight. So not only the stop button…"** — a
  high-leverage correction that expanded scope from one symptom to the real class of bug,
  and triggered the *measure-the-threshold* move. Rewrite for next time:
  *"The whole secondary toolbar overflows in a narrow split pane, not just stop —
  measure the natural inline width and fold above it."*
- **"make proposal for the change" / skill invocations** — short unlocks that drove each
  OpenSpec phase. Effective because the implementation was already proven, so the
  paperwork could be generated confidently.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session, but the workflow leaned on existing
project skills that made it reproducible:

- **`serve_mockup` + a `measure.html` scratch page** — the reusable move here is
  *measure the natural width, then choose the breakpoint above it.* This converts a
  guess-and-check loop into one correct edit. Invoke whenever a responsive fold threshold
  matters.
- **OpenSpec chain (`ff-change` → `apply` → `archive`)** — turned a shipped one-file fix
  into a validated spec change with a MODIFIED `chat-view` delta and an E2E gate. Invoke
  after any UI fix that changes documented behavior.
- **Recommended memory to save:** *"Composer toolbar folds by container width
  (`@[44rem]`/`@[30rem]`), not viewport — natural inline width ≈ 689px."* Saving this
  avoids re-measuring if the toolbar changes.

## 7. Pitfalls & dead ends

- **First breakpoint too low.** `@[36rem]` (576px) sat *below* the 689px natural width, so
  the 576–689px band snapped controls inline but still overflowed. → Always fold *above*
  the measured inline width.
- **`/api/restart` with `-X POST` + `-d '{}'` failed once** (curl arg/response handling);
  the working form wrote the body to a file and checked the HTTP code separately.
- **Playwright bundled-Chromium download was network-blocked** (CDN timeouts, repeated).
  → Use the harness's `PW_CHANNEL=chrome` system-Chrome channel to bypass the download.
- **Managed E2E harness hit the 180s health cap** under host contention (4 stale test
  containers from other worktrees, 27–42h old). → Fall back to manual `test-up.sh -d`
  (reuses the built `:local` image) + attach mode on the derived port, then tear down.
- **Docker image must be rebuilt from local source** (`docker compose build`, ~6 min)
  before the harness reflects your `CommandInput.tsx` change — a cached image tests stale
  code.
