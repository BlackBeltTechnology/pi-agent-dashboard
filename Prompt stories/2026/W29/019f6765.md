# How we did it: Mime-type icons + auto-fold for the change-summary block — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation run. The concrete objective, once the steering turns landed, was: **improve
the per-turn `ChangeSummaryBlock` UI in two ways** — (1) lead each changed-file row with an
extension-keyed *mime icon* instead of the generic `+ / ●` status glyph, and (2) **auto-fold**
the block when a turn touches many files so streaming assistant messages don't get pushed out
of view. The deliverable was **not code** — it was a validated OpenSpec change proposal (with a
reviewed mockup) ready to hand to `ship-it`.

## 2. TL;DR playbook

1. Enter `openspec-explore` and let the AI **locate the real component first** — `rg` for the
   rendering site (`ChangeSummaryBlock.tsx`) before proposing any design.
2. Ask it to check for **existing machinery** to reuse — here `lib/file-icon.ts` already
   exported `fileIcon(path) → {iconPath, colorClass}`, so nothing new had to be built.
3. Prompt: **"make mockup and ux review"** → AI loads the dashboard mockup skill, pulls the
   *real* theme tokens + MDI SVG paths, and serves an A/B/C option comparison.
4. Have it **screenshot both themes** and score against a rubric (contrast, hierarchy, token
   fidelity, anti-slop) — pick the winner from real pixels, not a guess.
5. Add the second requirement (**auto-fold at ≥8 files, sticky manual override**); let the AI
   draw the state machine and pin the two boundary decisions before writing.
6. **Run the pre-scaffold coherence check** — read active/related OpenSpec changes and the spec
   that already owns the component, to avoid delta collisions.
7. `npx openspec new change <name>` → write proposal + design + spec delta + tasks; copy the
   mockup into `mockups/` inside the change folder; `openspec validate --strict`.
8. Commit all artifacts together on `develop` with a `docs(openspec): propose …` message.

## 3. How the collaboration unfolded

**Phase 1 · Discovery (find the real thing).** The AI resisted the urge to design blind. It
`rg`-ed the client for the rendering component, confirmed the dot in the screenshot was a
*status glyph* (`added → green +`, `modified → gray ●`), and discovered `lib/file-icon.ts`
already provided the exact icon API used by `EditorFileTree`. **Why it worked:** grounding in
the real code turned "build an icon system" into "reuse one that exists" — the scope collapsed.

**Phase 2 · Design options (real pixels).** On *"make mockup and ux review"* the AI loaded the
mockup skill, captured the **actual theme CSS tokens** and **real MDI path data**, built an
A/B/C mockup (Replace / Add-both / Hybrid) against the true dark+light themes, screenshot both
via the browser skill (Playwright headless shell was missing — it fell back cleanly), and scored
against a rubric. **Decision point:** option **A (replace status glyph with mime icon)** won —
it matches `EditorFileTree`, and the `+X −Y` counts already carry add/modify so the status glyph
was redundant.

**Phase 3 · Second requirement + boundary pinning.** The user added auto-fold. The AI drew a
two-state machine (`EXPANDED ⇄ COLLAPSED`, effective state = `userToggled ? userChoice :
fileCount <= THRESHOLD`) and used `ask_user` to lock the two decisions that actually change the
logic: **collapse at ≥8** and **sticky manual override**. **Why it worked:** it isolated the
genuinely ambiguous choices instead of guessing them into the spec.

**Phase 4 · Coherence check (the payoff).** Before scaffolding, the AI read the *active*
`collapse-diff-file-tree` change and the existing `change-summary-table` spec. It found two
collisions: the spec already had an **"Overflow collapse" (+M more)** scenario — a *different*
strategy than block-level fold — and the active change also modified the same spec but a
different component (`ChangesRailSection`). It scoped the delta to distinct requirements and
confirmed `TurnFileSummary.status` is only `added|modified` (no deleted → no strikethrough).

**Phase 5 · Scaffold, validate, commit.** `npx openspec new change`, four artifacts written,
mockup copied into `mockups/`, `openspec validate --strict` green, everything committed together
as `56bca2ad4` on `develop`.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore`)** — starting in explore mode kept the AI in "read + reason"
  mode and prevented premature code. Effective because it forced discovery of the existing
  `fileIcon()` helper before any design.
- **"make mockup and ux review"** — a 4-word high-leverage prompt. It unlocked the full
  mockup-skill pipeline (real tokens → real icons → screenshots → rubric), turning a vague
  "add icons" into a scored A/B/C decision.
- **The auto-fold prompt** described the *symptom* ("messages haven't shown because changed
  files take the place") not a solution — which let the AI design the right mechanism. A stronger
  version bakes in the threshold up front: *"auto-collapse the change block at ≥8 files, sticky
  once the user toggles it, so streaming messages stay visible."*
- **"move mockups to proposal and commit"** — a clean close-out; the mockup was already inside
  the change folder, so this became verify-location-then-commit.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Present a design decision (which glyph slot wins) without committing | *"make mockup and ux review"* | Ask for a mockup + rubric review whenever a UI trade-off has >1 viable option |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — the session **consumed** existing project skills, which is
itself the lesson:

- **`openspec-explore`** — kept the work in a thinking stance (no premature code) while still
  allowing OpenSpec artifacts. Invoke it whenever the ask is "should we / how might we" rather
  than "build it now."
- **Dashboard mockup skill** — pulls real theme tokens + MDI paths, serves a comparison, and
  scores against a rubric. Invoke it for any client-surface design so decisions rest on real
  pixels, not descriptions.
- **`browser` skill** — the fallback screenshot path when Playwright's headless shell is absent.

If this pattern recurs (UI change → mockup → OpenSpec proposal), the repeatable move worth a
skill is the **pre-scaffold coherence check**: enumerate active + archived changes touching the
same spec/component and scope the delta to distinct requirements before writing.

## 7. Pitfalls & dead ends

- **Playwright headless shell not installed** → screenshots failed. Fix: fall back to the
  `browser` skill's CLI (as the AI did) — don't block the UX review on the missing shell.
- **Spec-collision trap** — `change-summary-table` already owned a *different* overflow strategy
  ("+M more"), and an active change modified the same spec. If you skip the coherence check you
  write a conflicting delta. Read the owning spec and every related change first.
- **Mockup location confusion** — the mockup was authored in `/tmp` (scratch, outside git) then
  copied into `openspec/changes/<name>/mockups/`. Only the in-folder copy is the proposal
  artifact; the `/tmp` one is disposable.
