# How we did it: Scripting the dashboard over its WebSocket bus — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — a thinking stance, not an implementation
task. The literal kickoff was the `openspec-explore` skill prompt ("Enter explore
mode. Think deeply… you must NEVER write code"). But the *real* objective surfaced in
the first steering turn: **"Is it possible that all functions can be called via the
event Bus? Maybe the script can be executed to drive that."** The operator wanted to
know whether the dashboard could be driven by a *script over a single event bus*
instead of the LLM hand-writing `curl` against ~153 REST endpoints — and if so, to
capture that idea as a validated OpenSpec change ready for implementation.

## 2. TL;DR playbook

1. **Ground the idea in the real API surface first.** Before sketching, enumerate what
   already exists: `grep` the server routes (`packages/server/src/routes/`) and the
   shared protocol (`packages/shared/src/protocol.ts`, `browser-protocol.ts`).
2. **Find the true control plane.** Check whether the WebSocket bus is bidirectional —
   it is. The browser drives the app through **75 `BrowserToServerMessage` verbs**; REST
   (153 paths) is a *secondary facade*, and a partial one.
3. **Prove REST is a facade, not the control plane.** Grep the web client: it sends
   `spawn_session` / `send_prompt` / `abort` over WS, not REST. The REST command
   endpoints exist mainly to serve the curl-based skill.
4. **Check for the generalization seam.** `plugin_action` is the one generic verb every
   extension rides — but verify the server dispatch before trusting it (this is where
   the blocker hides).
5. **Capture as an OpenSpec change** with `npx openspec new change <name>`; write
   `proposal.md` + `design.md` + a spec delta; `npx openspec validate`.
6. **Run `plan-proposal`** (main session only). It chains **doubt-driven-review**
   (single-model + a mandatory cross-model second opinion) → **scenario-design** →
   fold into `tasks.md`.
7. **Reconcile the review honestly** — narrow scope to what's provable, spin the
   discovered blocker into a *second* follow-up change rather than overreaching.
8. **Commit only your artifacts** to `develop`; leave ambient churn (`groups.json`
   auto-reconcile, `package-lock.json`) untouched. Stop at the worktree boundary.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground before sketch).** The AI resisted designing on a blank
page: it grepped routes and the protocol union first. Effective because the whole
argument rests on a factual claim (REST vs. bus completeness) that only source can
settle. Decision point: the operator's "via the event Bus?" question redirected the
whole exploration away from "a scripting engine that wraps REST" toward "a headless
client that speaks the bus."

**Phase 2 — The reframe.** Enumerating `BrowserToServerMessage` (75 verbs) vs. REST
(153 paths) revealed the bus is *more* complete — terminals, workspaces, plugin
actions, roles are WS-only. And correlation is already built in (`spawnRequestId`
echoed on results), so `await` can be *exact*, not heuristic. This became the core
thesis.

**Phase 3 — Generalization probe.** The operator asked whether pi-flows and other
extensions could be driven the same way. The AI found the generic `plugin_action`
channel and initially concluded "every extension for free." (Phase 5 corrects this.)

**Phase 4 — Capture.** Once the operator said "capture and [item] 4 be part," the AI
scaffolded `add-dashboard-bus-client-scripting` (proposal + design + spec delta),
validated it, and surfaced it on the canvas — with Tier 2 (consolidating REST twins
onto the bus) *in scope*, not optional.

**Phase 5 — Doubt-driven review (the payoff).** `plan-proposal` triggered a
single-model adversarial review, then a **mandatory cross-model** pass on
`@propose-review-1` (glm-5.2, different architecture family). Both models agreed the
draft was overconfident. The cross-model pass found a *deeper* blocker the first
missed: `plugin_action` dispatch is **last-writer-wins** (`customHandlers.set(type,…)`),
so `goal` silently overwrites `flows`' handler — the "every extension for free" claim
was false as-built. Decision point: the operator chose **Option 3** — narrow this
change to goal-only + spin the seam fix into a *second* change
(`fix-plugin-action-fanout-and-handlers`).

**Phase 6 — Scenario-design → fold → commit.** scenario-design's hard gate passed (every
test triple was fillable from spec/source — no fake questions), producing 13 scenarios
folded into a 35-task `tasks.md`. Committed both changes to `develop` (`8e3eb61f8`),
stopping at the worktree boundary.

## 4. Prompts that worked

- **The goal prompt** (explore-mode skill): good because it *forbade implementation* —
  it kept the AI in thinking/capture mode, which is exactly right when the deliverable
  is a validated proposal, not code.
- **"Is it possible that all functions can be called via the event Bus?"** — the single
  highest-leverage prompt. It reframed the entire problem from "wrap REST" to "speak the
  bus." A future operator should lead with this hypothesis directly.
- **"In this mono repo what can be modified to use this way instead of rest? Check
  skills, utils etc"** — forced the AI to prove the claim across real consumers
  (skill, client, plugins), which is what turned an idea into a scoped migration map.
- **"capture and 4 be part"** — a 4-word unlock: promote item 4 from optional to in-scope
  and capture as OpenSpec. Terse steering works once shared context is established.

Rewrite of a weak prompt: instead of "capture and 4 be part", a future operator should
say **"Capture this as an OpenSpec change; make the Tier-2 REST-twin consolidation
in-scope, not optional."**

## 6. Skills, tools & memory created — and why they're effective

No new *skills* were authored this session — instead it **exercised the existing
planning chain**, and that composition is the reusable asset:

- **`plan-proposal`** — orchestrates the develop-side planning phase (artifacts →
  doubt-review → scenario-design → fold → commit) and *stops at the worktree boundary*.
  Effective because it enforces the review + test-design gates before a single line of
  implementation, catching overconfident scope early. Invoke it in the main interactive
  session after drafting a proposal.
- **`doubt-driven-review`** — the value engine here. Its **mandatory cross-model second
  opinion** (walk the `@propose-review-N` role series, prefer a *different architecture
  family*) surfaced the last-writer-wins blocker that the same-family reviewer missed.
  Invoke whenever an irreversible/high-stakes plan is about to stand.
- **`scenario-design`** — its hard gate (every input·trigger·observable triple must be
  fillable from spec/source) prevents "gate theater"; when all slots fill, it proceeds
  rather than inventing fake clarification questions.

Recommendation: if this pattern recurs, a `capture-explore-as-change` skill could
codify "explore → validate → plan-proposal → commit at boundary."

## 7. Pitfalls & dead ends

- **Grep mangled multi-line route registrations.** The first `grep` for
  `fastify.get|post…` missed multi-line and produced garbled output. Fix: scope to the
  `routes/` dir and grep specific verbs, or `awk`-slice the interface bodies.
- **Grep polluted by archives/worktrees.** A repo-wide REST-consumer scan pulled in
  `openspec/` archives and `.worktrees/`. Fix: exclude those and scope to `skills/`,
  `scripts/`, `client/src`, `utils`.
- **Trusting `plugin_action` as a universal bus.** It is *not* as-built: dispatch is
  last-writer-wins, `flows` is a stub, and real actions are `flow.run`/`flow.new` (not
  `start-flow`). Verify the handler registry before claiming cross-extension reach.
- **Fictional Tier-2 "WS twin" rows.** `plugin_config_write` is *deliberately*
  intercepted client-side to REST (a test asserts this); `canvas-types` /
  `openspec-task-toggle` have no Browser→Server twin. Check the protocol union exists
  before listing a migration.
- **Sweeping ambient churn into a commit.** `groups.json` (auto-reconciled group store)
  and `package-lock.json` showed as dirty but weren't from this work. Stage only your
  own paths.
