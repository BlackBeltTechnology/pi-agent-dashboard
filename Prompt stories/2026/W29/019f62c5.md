# How we did it: Plan `.eml` email preview for the dashboard — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking stance,
not an implementation task. The first prompt was the skill's boilerplate ("Enter explore
mode. Think deeply. Visualize freely… you must NEVER write code"). The *real* objective
surfaced one turn later when the user typed **"There is in documents"** — meaning: *there
are real `.eml` files on this machine, go look at them.* From that seed the objective
crystallized: **explore how the pi-dashboard should render saved `.eml` emails, then
capture that thinking as a fully-planned, security-reviewed OpenSpec change** ready for a
worktree to implement. It ended as a committed `add-eml-preview` change: proposal, design,
delta spec, 49 tasks, and a 33-scenario test plan.

## 2. TL;DR playbook

1. **Ground in reality before theorizing.** `find` the actual `.eml` files, `head` one to
   read its MIME structure, `du -sh` to learn the size profile (36 emails, 51 MB, some 15 MB).
2. **Recon the existing architecture second.** `rg` the client for the preview system —
   discover `packages/client/src/components/preview/` already dispatches by extension.
   Reframe the whole feature as *"add one renderer"*, not *"build an email client"*.
3. **Mock it up in HTML, verify in a real browser.** `serve_mockup` two static variants;
   drive them with the `browser` tool (Playwright headless shell wasn't installed) to prove
   header-expand + inline-PDF interactions.
4. **Load `plan-proposal` and run its mandatory pre-scaffold coherence check** — confirm no
   duplicate/colliding change in archive or active, verify current-code claims (`RENDERER_BY_EXT`,
   server route only accepts `.adoc`).
5. **Scaffold the artifacts** (proposal · design D1–D5 · delta spec against `file-and-url-preview`
   · tasks) and run `npx openspec validate` until green.
6. **Run `doubt-driven-review` with BOTH a single-model and a cross-model reviewer.** Feed
   the reviewer **ARTIFACT + CONTRACT only** — no claims, no reasoning. The cross-model pass
   (glm via `@propose-review-1`) caught two Critical security holes the first missed.
7. **Reconcile findings into the artifacts** — reverse the iframe posture, add the attachment
   XSS firewall, pin deps — re-validate.
8. **Run `scenario-design`** at design stage; where a Triple can't be filled (no latency
   budget existed), STOP and force a decision, fold answers into design D6.
9. **Commit to `develop` and stop at the worktree boundary.** Do NOT implement.
10. **Clean up:** kill the mockup server (`lsof` the port, stop it) when the session ends.

## 3. How the collaboration unfolded

**Phase 1 — Ground (Discovery).** Instead of designing from imagination, the AI first
located the real emails (`~/Documents/Kozmu/NAPELEM/emails/`), dissected one `.eml`
(multipart/mixed → alternative text/plain + text/html → two PDF attachments), and measured
the corpus. *Why it worked:* the 15 MB size fact drove the single most important
architectural decision (parse server-side, keep it off the client).

**Phase 2 — Recon existing infrastructure.** `rg` surfaced an already-shipped preview
dispatcher. The AI reframed the feature as **~80% existing infrastructure**: EML is a new
`EmlPreview.tsx` sibling to `HtmlPreview`/`PdfPreview`, one entry in `preview-dispatch.ts`,
one new server route. *Decision point:* this reframing is what kept scope sane.

**Phase 3 — Mockup + browser verify.** Two static HTML mockups (`/tmp/eml-mockup/`),
served and driven interactively. *Why it worked:* proving the collapsed-header expand and
inline-PDF-via-existing-`PdfPreview` interactions in a browser de-risked the design before
a single spec line was written. When Playwright's headless shell was missing, the AI
pivoted to the `browser` tool rather than stalling.

**Phase 4 — Plan-proposal scaffold.** Loaded `plan-proposal`, ran the coherence gate, named
the capability correctly (`file-and-url-preview`), scaffolded proposal/design/delta-spec/tasks,
validated green.

**Phase 5 — Doubt-driven review (the payoff).** Single-model review first (3 Critical), then
the *mandatory* cross-model second opinion via the `@propose-review-1` role (glm, a different
family). The cross-model reviewer found two Criticals the first missed — reshaping the design.
*Decision point:* accepting that untrusted sender HTML needs an **opaque-origin `sandbox=""`
iframe**, deliberately diverging from the shipped `allow-same-origin` invariant (which was
written for *trusted local* files).

**Phase 6 — Scenario-design + commit.** ~34 Triples derived; one genuine gap (no latency
budget) forced a decision, folded into design D6. 49 tasks, 33 scenarios. Committed to
`develop` (`fd2a76dc7`), stopped at the worktree boundary. Later, killed the mockup server.

## 4. Prompts that worked

- **The goal prompt** was the explore-mode boilerplate — fine as a *stance* setter, but the
  work only got direction from the follow-up. A stronger kickoff: *"Explore mode. I have real
  `.eml` files in ~/Documents/…/emails — figure out how the dashboard should preview them and
  capture it as a planned change."*
- **"There is in documents"** (steering #1) — terse but high-leverage: it pointed the AI at
  real source data, which anchored every downstream decision in fact instead of theory. The
  lesson: *tell the AI where the real inputs live, early.*
- **"kill mockup services which sessions are ended"** (steering #2) — a hygiene instruction
  that closed the loop. Worth baking into the workflow so it happens automatically.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Start from explore-mode boilerplate with no concrete target | "There is in documents" — point it at the real `.eml` files | Name the source-data location in the opening prompt |
| Leave the mockup HTTP server running after the design was done | "kill mockup services which sessions are ended" | Add an end-of-session cleanup step (`lsof` port → stop) to the mockup workflow |
| (Self-corrected) Trust the shipped `allow-same-origin` iframe posture for email HTML | The cross-model review forced the reversal | Treat *any externally-sourced HTML* as untrusted → opaque `sandbox=""` by default |

The biggest quality bar the human's process (not a single prompt) imposed: **always run the
cross-model doubt review** — it earned its keep by catching security holes a single reviewer,
same-family as the author, was blind to.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session, but it is a textbook run of an existing
chain worth codifying as a **combined "plan a file-preview renderer" playbook**:

- **`openspec-explore`** — ground-then-design stance; forbids implementing, keeps the session
  a thinking exercise that outputs artifacts.
- **`plan-proposal`** — the orchestrator; its *pre-scaffold coherence check* prevented a
  duplicate change and verified code claims before writing specs.
- **`doubt-driven-review` (cross-model)** — the highest-value tool here. Invoke it with
  **ARTIFACT + CONTRACT only** and always take the cross-model second opinion via a
  different-family reviewer role (`@propose-review-1` → glm).
- **`scenario-design`** — its HARD gate on unfillable Triples forced the missing latency
  budget into the open instead of letting it slip.
- **`serve_mockup` + `browser`** — cheap, high-confidence UI validation before spec-writing.

If anything should be saved: a memory that **`@propose-review-1` resolves to a non-Claude
family (glm)** and is the correct cross-model reviewer for this repo.

## 7. Pitfalls & dead ends

- **Playwright headless shell not installed** → don't stall; fall back to the `browser` tool
  to capture/drive the mockup.
- **A multi-target `edit` mis-format applied only the first edit** — the AI re-read the file
  and reapplied cleanly. When an edit silently drops changes, re-Read and split into separate,
  well-anchored edits.
- **`mktemp` template collisions** (seen while generating this very guideline) — use a unique
  suffix or `mktemp -t`. Not fatal; the tool still printed to stdout.
- **Trusting a shipped invariant blindly** — `HtmlPreview`'s `allow-same-origin` posture was
  written for *trusted local* files; reusing it for untrusted email HTML would have been a
  stored-XSS vector. Re-derive trust assumptions when the data source changes.
