# How we did it: From "fix stale kb entries" to a grounded OpenSpec refactor proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a one-line prompt: **"Fix stale kb entries."** In this repo that
means driving `kb dox lint` toward zero — the DOX system tracks per-file `AGENTS.md` rows
and flags them `stale` (sha drift), `missing`/`missing-companion`, and `over-threshold`
(byte cap or row cap exceeded). The *real* objective, once the steering turns landed, grew
past a cleanup: it became **(a) mechanically clear the actionable lint issues, then (b)
understand why one class of flags refuses to clear, and (c) turn that finding into a
grounded OpenSpec proposal** for a staged directory-foldering refactor — complete with a
lint-severity code fix and a re-definition of what the row cap actually measures.

## 2. TL;DR playbook

1. **Snapshot the lint state as data, not prose.** `kb dox lint --json` piped through a
   `node -e` grouper — count issues by `kind` so you know the shape before touching a file.
2. **Take the cheap structural win first.** The `Prompt stories/` dir generated 25
   `missing`/`missing-companion` issues; it's narrative playbook prose, not navigable
   source — so exclude it from the DOX walk in `packages/kb/src/dox.ts` (join the existing
   `research`/`mockups`/`doc-example` exclusions), rebuild `dist`, re-lint.
3. **Triage stale rows by drift, not count.** Build a side-by-side (row purpose vs current
   file exports) and only *edit* rows with **material** drift; the rest are sha-drift and
   just need a hash refresh. Here: 72 stale → only **4** real edits (Dockerfile pin,
   `FileLink.tsx` removed branch, `i18n.tsx` new `"hu"` language).
4. **Acknowledge the rest in bulk** by refreshing hashes to current sha256, then re-lint to
   confirm `stale`/`missing` hit zero.
5. **Don't guess why a flag persists — read the source.** When asked whether over-thresholds
   can be auto-split, grep `scripts/split-large-agents.mjs` + the CLI: discover the byte cap
   has an official auto-fix, the **row cap does not, by design**.
6. **Turn the finding into a proposal.** Run the pre-scaffold coherence sweep, read the
   *archived* change that established the DOX tree to ground against shipped intent, then
   `openspec new change <name>` and write proposal/design/tasks/spec-delta.
7. **When steered to flip a non-goal, pin the semantics first**, then fold the change across
   **all four** artifacts, and `openspec validate` after every edit.

## 3. How the collaboration unfolded

**Phase 1 — Measure (Discovery).** The AI's first move was the right one: it turned the lint
output into JSON and grouped by `kind` with an inline `node -e` script rather than eyeballing
prose. That produced the working budget: 71 stale, 18 missing, 7 missing-companion, 10
over-threshold. Decision point: attack the cheapest structural cluster first.

**Phase 2 — Cheap structural win.** All 25 `missing`/`missing-companion` issues traced to
`Prompt stories/` — session playbooks, not source. The AI excluded that directory from the
DOX walk in `dox.ts`, rebuilt `dist`, and cleared all 25 in one edit. Effective because it
recognized a *category* error (wrong directory being walked) instead of adding 18 rows to a
forbidden root `AGENTS.md`.

**Phase 3 — Stale triage.** Rather than blindly refresh 72 hashes, the AI built a drift view
and spot-checked the rows most likely to have drifted (version pins, feature flags). It found
exactly 4 material drifts and fixed those surgically, then bulk-refreshed the rest.
`stale`/`missing`/`missing-companion` → 0; only `over-threshold` (advisory) remained. It also
opportunistically cleared the one *byte* flag (`components/AGENTS.md`, 32 KB, auto-injected
every turn) with `split-large-agents.mjs`.

**Phase 4 — Investigate the residue (steering #1).** The human asked whether over-thresholds
could be split "the official way." Instead of guessing, the AI read the split script and CLI
and reported precisely: **byte cap has an auto-fix; row cap is intentionally structural** —
the split script cuts bytes only (a promoted row leaves a pointer row behind, so `rows.length`
doesn't drop), and there is no `kb dox split` command.

**Phase 5 — Propose (steering #2).** Told to "create a proposal for that refactor," the AI ran
the coherence sweep, read the *archived* `migrate-file-index-to-agents-tree` change to ground
against shipped design intent, and discovered the over-thresholds split into **two categories**:
*rollup dirs* (`qa/`, `docker/` — doc-only fix, zero source risk) and *genuinely flat source
dirs* (`components/`, `server/src/`, `lib/` — real refactor with import churn). It wrote all
four artifacts and `openspec validate`d them.

**Phase 6 — Flip a non-goal (steering #3).** "Add fix ROW_CAP" contradicted the proposal's
explicit non-goal ("40 stays; only severity classification changes"). The AI paused to pin the
*semantics* before editing: the fix redefines `ROW_CAP` to measure **inline detail volume, not
raw file count** — excluding sidecar-pointer rows (those carrying the `→ see \`<File>.AGENTS.md\``
marker). It then folded that change across all four artifacts with a precise detection regex and
re-validated.

**Phase 7 — Hand to plan-proposal (steering #4).** The human pasted the `plan-proposal` skill;
the AI kicked off the planning orchestration (doubt-review + cross-model adversarial review via
the configured `@propose-review-1` role) for the drafted change.

## 4. Prompts that worked

- **Goal prompt — "Fix stale kb entries."** Terse but effective *in this repo* because the KB
  doctrine and `kb dox lint` give the AI an unambiguous target and a measurable definition of
  done. A stronger, project-agnostic version: *"Drive `kb dox lint` to zero actionable issues;
  only edit rows with material drift, bulk-refresh the rest."*
- **High-leverage follow-up — "can split over-thresholds? Is there official way to do it — the
  dox system is designed to handle that?"** This unlocked the whole proposal by forcing the AI
  to *read the design intent* instead of hand-waving. The phrase "is there an official way"
  reliably steers the AI to inspect the tooling before answering.
- **"Okay. Create a proposal for that refactors."** A clean scope-expansion trigger — cheap to
  say, large in effect, because the prior turn had already surfaced the finding to propose.
- **"Add fix ROW_CAP."** Three words that flipped a non-goal. Effective *because* the AI treated
  it as a semantics question first rather than a mechanical edit.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stop at "mechanically cleared the lint" and treat the residual `over-threshold` as done-enough | "can split over-thresholds? Is there official way?" | Ask *why* a flag persists and *what the tool is designed to do* before declaring advisory-and-done |
| Treat the cleanup as the whole ask | "Create a proposal for that refactor" | State up front whether findings should become an OpenSpec change, not just a fix |
| Honor the proposal's own non-goal ("40 stays") | "Add fix ROW_CAP" | When a decision is deliberately deferred, say so — and be ready to reverse it as new intent arrives |
| Risk editing across artifacts inconsistently | (implicit quality bar) | Fold any semantics change across **all four** artifacts (proposal/design/tasks/spec) + `openspec validate` after each |

The dominant guardrail: **the AI's instinct is to stop at "advisory, not CI-gated."** The human
repeatedly pushed it to (a) read the design source, (b) escalate a finding into a proposal, and
(c) reverse a stated non-goal — each a *judgment* redirection, not a factual correction. State
"treat lint residue as a design question, not just a checkbox" up front to skip two of these.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created this session — but three existing assets carried it, and
one workflow is a clear skill candidate:

- **`kb dox lint --json` + inline `node -e` groupers.** The backbone move: convert lint output
  to structured data and reason over counts, not prose. Invoke this whenever a lint/audit tool
  emits many issues — it turns "107 issues" into an actionable histogram in one command.
- **`scripts/split-large-agents.mjs`.** The *official* byte-cap auto-fix (promotes heavy rows to
  pull-only `<File>.AGENTS.md` sidecars). Reach for it when a directory `AGENTS.md` trips the
  30 KB byte cap — it removes per-turn context bloat without touching source.
- **`plan-proposal` skill (invoked at the end).** The planning-phase orchestrator (doubt-review +
  cross-model adversarial review) that the drafted change was handed to.
- **Recommended skill to create:** *"triage-stale-dox-rows"* — the drift-vs-sha-drift triage
  loop (JSON snapshot → side-by-side purpose/exports view → edit only material drift → bulk
  hash-refresh → re-lint) is highly repeatable and was reconstructed from scratch here.

## 7. Pitfalls & dead ends

- **Row cap ≠ byte cap.** They look like one `over-threshold` kind but need opposite fixes. The
  byte cap has an auto-fix; the row cap is structural — splitting bytes leaves a pointer row, so
  `rows.length` doesn't drop. If you try to "split away" a row-count flag, you'll spin.
- **Pre-existing `node:sqlite` type error in the kb build.** The `kb` package `dist` rebuild
  emitted despite it — confirm it's *pre-existing* (grep the built output for your change) before
  assuming your edit broke the build.
- **One failed grep** (`grep -nE '^\| \`(FileLink|OpenFileButton)\.tsx\`'` with a `sed` pipe) —
  the shell mangled the alternation; the retry without the `sed` post-filter worked. If a
  backtick-heavy grep fails, simplify the pipeline before doubting the pattern.
- **`qa/` "(no row found)" false negatives.** A row-scan regex missed subdir-path rows — the rows
  existed and were fine. Don't refactor on a scan miss; confirm against the actual file.
- **Flipping a documented non-goal is expensive to do inconsistently.** "Add fix ROW_CAP"
  required edits to proposal, design (new D6 + Goals/Non-Goals), tasks, and spec — validate after
  each so the four artifacts never drift apart.
