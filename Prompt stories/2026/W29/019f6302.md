# How we did it: capturing a UI bug as a validated OpenSpec change — without writing a line of code

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a deliberate *thinking, not
implementing* stance. The operator's real objective was narrow and clear: a UI defect existed
(the `⚙ View` popover in `ChatViewMenu` clips off the left edge when the ChatView panel is slim),
and they wanted the AI to **root-cause it, visualize it, decide the fix approach, and capture it as
a validated OpenSpec change proposal** — explicitly *not* to build it. In ~11 minutes the session
went from "there's a rendering bug" to a strict-validated, committed change with proposal + delta
spec + tasks.

## 2. TL;DR playbook

1. **Enter explore mode** with the `openspec-explore` skill — this hard-blocks implementation and
   keeps the AI in root-cause + capture mode.
2. Let the AI **find the component and the hook** (`ChatViewMenu.tsx`, `usePopoverFlip.ts`) and
   confirm the root cause: the flip hook only measures the **vertical** axis, so the fixed-width
   right-anchored popover always spills left.
3. Make the AI **draw the bug** as an ASCII wide-vs-slim diagram before proposing anything — the
   picture is what makes the fix options obvious.
4. When offered fix options, **pick one with a single letter** (`B`) — the AI already framed the
   tradeoffs, so a one-token answer unlocks the whole scaffold.
5. Let it **check for existing/archived popover work first** (`openspec list`, grep archive) so the
   new change extends the existing `popover-viewport-positioning` spec instead of duplicating it.
6. AI scaffolds the change with `openspec new change <name>`, writes **proposal.md + delta spec +
   tasks.md**, and runs `openspec validate <name> --strict` until clean.
7. Say **`commit`** — the AI stages *only* the change artifacts (leaving unrelated working-tree
   edits untouched) and commits with a `plan(<name>):` message.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (root-cause).** The AI grepped for the `View` component, opened
`ChatViewMenu.tsx`, then read `usePopoverFlip.ts` and confirmed the hook has *no horizontal logic*
— it only flips up/down and clamps `maxHeight`. Effective because it traced from symptom → concrete
CSS (`absolute right-0 w-64`) → the missing axis in the shared hook, rather than guessing.

**Phase 2 — Visualize.** The AI rendered a side-by-side ASCII diagram (WIDE vs SLIM ChatView)
showing labels clipping off the left edge. This is the explore-mode payoff: the diagram makes the
two viable fixes self-evident, so the human's decision becomes a one-letter choice.

**Phase 3 — Decide.** The AI presented fix options; the human answered **`B`**. Decision point:
extend `usePopoverFlip` with a horizontal counterpart (`anchorRight` + `maxWidth`) so `ChatViewMenu`
swaps hard-coded `right-0` for a hook-driven `left-0 ⇄ right-0`.

**Phase 4 — Reuse-check + scaffold.** Before writing, the AI checked `openspec list` and grepped the
archive for prior popover work — finding the existing `popover-viewport-positioning` spec (and a
prior archived `fix-popover-viewport-flip`). It framed the change as a **clean additive extension**
to that spec, then scaffolded via `openspec new change` and wrote the three artifacts.

**Phase 5 — Validate + commit.** `openspec validate --strict` passed. On `commit`, the AI noticed
unrelated changes in the working tree and deliberately staged **only** the 4 change-artifact files,
keeping the commit surgical.

## 4. Prompts that worked

- **The goal prompt** — invoking the `openspec-explore` skill *is* the kickoff. It sets the stance
  (investigate + capture, never implement) so the AI won't jump to code. For a bug like this, that's
  exactly right: you want a validated plan, not a half-built fix.
- **`B`** — a single-letter answer to a well-framed options menu. High leverage: because the AI had
  already laid out the tradeoffs and default-preservation, one token unlocked the entire scaffold.
- **`commit`** — one word, and the AI did the safe thing (surgical staging). Effective *because* the
  prior work was already scoped to one change dir.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created. The leverage came from an **existing** skill:

- **`openspec-explore`** — captures the *think-don't-build* stance. It's effective because it
  removes the single most common failure mode for a bug report ("the AI starts patching before the
  root cause and the spec are agreed"). Invoke it whenever you want a **validated change proposal**
  out of an investigation, not a diff.

Repeatable pattern worth remembering (candidate for a memory, not a skill): **before scaffolding a
new OpenSpec change, grep `openspec/changes/archive/` and run `openspec list` for the topic** — it
routes the work into an existing spec (here `popover-viewport-positioning`) as an additive delta
instead of a duplicate.

## 7. Pitfalls & dead ends

- **`openspec change new <name>` failed** — the correct subcommand is **`openspec new change
  <name>`** (word order). If `change new` errors, check `openspec new --help`; the noun/verb order
  is `new change`, `new proposal`, etc.
- **Dirty working tree at commit time** — there were unrelated edits present. The safe move is
  `git add openspec/changes/<name>/` (the change dir only), never `git add -A`.
