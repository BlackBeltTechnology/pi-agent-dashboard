# How we did it: Diagnosing a QR pairing "race the clock" symptom — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **openspec-explore** mode (a thinking stance, not an implementation
one): *"Enter explore mode. Think deeply… you must NEVER write code or implement features…
You MAY create OpenSpec artifacts."* The concrete complaint behind that stance: cross-device
pairing (laptop dashboard ↔ phone PWA) felt like **racing a clock** — "1 in 3 times I have
enough time to type the code." The *real* objective, once steering clarified it, split in two:
(a) capture the **discoverability finding** (the zero-typing camera path exists but is never
signposted) as an OpenSpec change, and (b) separately confirm and deploy the fix for a
**distinct** "shows the verification code then flips to 'expired' after ~5s" bug the operator
was actually hitting.

## 2. TL;DR playbook

1. **Stay in explore mode.** Ground every claim in code *before* theorizing — `kb_search` +
   `grep` the pairing state machine (`packages/server/src/pairing.ts`, `PairLanding.tsx`,
   `GatewayPairQR.tsx`) rather than guessing.
2. **Map the full state machine** end-to-end (mint → paste/scan → redeem → approve → poll)
   and find the **binding constraint** — here `CODE_TTL_MS = 60_000` and *where* the clock
   restarts.
3. **Separate two look-alike symptoms** the moment the human hints at a second one. "Racing
   the clock while typing" (discoverability) ≠ "shows code then expires in 5s" (a redeem-TTL
   bug). Say *explicitly* they are different before acting.
4. **Scaffold the discoverability finding as an OpenSpec change** (`openspec new change`),
   writing proposal + design + delta spec + tasks — a pure-UX Direction A, no TTL change.
5. **For the real bug, check git history + the live server, not the source tree alone.**
   Prove the fix commit exists (`795344f40`) and that the *running* server started **after**
   it — timeline is decisive.
6. **Build + deploy to the local instance**: `npm run build`, then restart via
   `POST /api/restart` with a **non-empty JSON body** (`-d '{"dev":false}'`), verify pid
   changed + mode stayed `production`.
7. **Archive the unbuilt proposal WITHOUT syncing its delta spec** — a 0/9-tasks change is a
   *shelved idea*, not a delivered one; syncing would make the main spec lie.
8. **Commit only your own artifacts** — leave unrelated churn (`groups.json`, stray mockups)
   out per the surgical-changes rule.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground before theorizing).** The AI's first move was *not* an answer;
it was `grep`/`kb_search` across `pairing.ts`, `pair-protocol.ts`, `PairLanding.tsx`,
`GatewayPairQR.tsx` to read the actual two-code, two-clock state machine. It found
`CODE_TTL_MS = 60_000` and the subtle detail that **redeem restarts the clock** — so the
operator's 8-digit phase is *not* the bottleneck; the phone's thumb-typing-before-redeem
phase is. *Why it worked:* the "1 in 3" number was explained mechanically (a 22-char
case-sensitive base64url string thumb-typed against a 60s window minus a network round-trip),
not hand-waved.

**Phase 2 — Reframe as discoverability.** The AI realized the codebase already ships a
**zero-typing path** (native camera → `https://host/pair#payload` → `PairLanding` auto-runs on
mount). The bug is that `GatewayPairQR.tsx` never *says* "scan with your camera" and puts a
copy-string front-and-center — so users fall into the manual path that races the clock. *This
was the key insight:* not a code defect, a **signposting gap**.

**Phase 3 — Capture as OpenSpec (explore-mode-legal).** The AI ran a pre-scaffold coherence
check against the two archived camera-scan changes, then `openspec new change
signpost-camera-scan-pairing` and wrote four artifacts (proposal, design with a two-path
diagram + D1–D4 decisions, a MODIFIED delta spec, tasks), and validated clean. Direction A =
UI only, `CODE_TTL_MS` untouched.

**Phase 4 — The human's steering split the work (decision point).** Prompt 2 — *"Is this about
the error (expired) message after 5s in mobile?"* — forced a hard separation. The AI answered
**"no, that's a different, already-fixed bug"** and pivoted to prove it: `git log`/`git show`
found commit `795344f40 (restart code TTL on redeem + reject expired codes at approve)` whose
own message describes the exact symptom. It then checked the **live server**: v0.5.4,
production, started `14:26 UTC` — **22 min after** the fix landed at `14:04 UTC`. Decisive
timeline.

**Phase 5 — Build & deploy.** On *"build and deploy"*, the AI ran `npm run build` (exit 0) and
probed `/api/tunnel/endpoints` **in parallel** to confirm the phone reaches *this* server via
its zrok share. Restart first failed (empty body), then succeeded with `-d '{"dev":false}'`:
pid `44062 → 57588`, mode `production`, bridges reconnected.

**Phase 6 — Archive safely + commit.** On the archive request, the AI **refused to
silently do damage**: status showed 0/9 tasks, so it archived the proposal WITHOUT running
spec-sync (proved via a `grep` that returns exit 1 = 0 matches in the main spec), then
committed only the archive (`132c6f664`), leaving unrelated `groups.json` + mockup churn out.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Effective because the stance forbade implementation and
  *permitted* OpenSpec artifacts — it channeled a vague "this feels slow" gripe into grounded
  investigation + a captured proposal, without premature coding.
- **High-leverage follow-up: *"Is this about the (expired) message after 5s in mobile?"***
  One sentence that surfaced a **second, distinct** symptom. It's high-leverage because it
  stopped the AI from conflating a UX discoverability change with a timing bug — forcing an
  explicit "these are two different things" split.
- **"build and deploy"** — terse, but landed cleanly because Phase 4 had already established
  *which* server and *which* fix; the AI knew exactly what "deploy" meant (build client +
  restart the zrok-fronted local instance).
- **Weak prompt → stronger version.** *"it seems ok now."* → better:
  *"Confirmed working on the phone — full ~60s window after the code appears. Keep the
  signpost proposal shelved; don't implement it yet."* (states the verification result AND the
  disposition of the open proposal in one turn, saving a round-trip).

## 6. Skills, tools & memory created — and why they're effective

**Memory saved (tool-quirk):** *"POST /api/restart with `Content-Type: application/json` and
an EMPTY body → 400 `FST_ERR_CTP_EMPTY_JSON_BODY`; the server does NOT restart (pid/uptime
unchanged). Must send a body, e.g. `-d '{"dev":false}'`."*
- **What it captures:** a Fastify content-type gotcha that silently no-ops a deploy.
- **Why it's effective:** the AS hit this live (first restart failed, same pid), diagnosed it,
  and recorded it so the next "build and deploy" doesn't lose a cycle to a phantom restart.
- **When to invoke:** any time you script `POST /api/restart` — always pass `-d '{"dev":…}'`.
  *(Note: the store was full when the AI tried to persist a second note — see Pitfalls.)*

**No skill was created, but one is warranted.** The runtime-vs-source verification move
("prove the fix is in the *running* server, not just the branch") is a repeatable diagnostic.
A `verify-fix-is-deployed` skill — compare fix-commit time to server start time, confirm the
line is on disk, confirm the client reaches *this* server via its tunnel endpoint — would make
this reproducible.

## 7. Pitfalls & dead ends

- **Empty-body restart no-ops silently.** `POST /api/restart` with no body → 400, same pid.
  *Fix:* send `-d '{"dev":false}'` (keeps production mode).
- **`openspec change new` CLI failed; `openspec new change` is the correct form.** The first
  scaffold attempt errored — check `openspec new --help` and use `new change <name>`.
- **Archiving a 0/9-task change would corrupt the spec.** The archive workflow's spec-sync
  folds the delta into the live spec — so it would claim behavior that doesn't exist in
  `GatewayPairQR.tsx`. *Fix:* archive WITHOUT sync; verify with a `grep` on the main spec that
  returns 0 matches (exit 1 is the success signal here).
- **Memory store full.** A second tool-quirk note couldn't be saved. *If you hit this:* skip
  the note or run a memory-consolidation pass — don't detour mid-deploy.
- **`git branch --contains` is not proof of deployment.** A fix on the branch may not be in the
  *running* server. Compare commit time to server start time.
