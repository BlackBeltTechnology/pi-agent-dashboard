# How we did it: Triaging leftover uncommitted changes — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The working tree had accumulated a pile of uncommitted junk and the operator wanted
it cleaned. The first prompt was terse: *"There is a leftover redesign-prompt-input
proposal remove not committed."* The real objective, which the two follow-up prompts
clarified, was broader: **walk the dirty working tree change-by-change and decide, per
item, whether to remove it, commit it, or fix-then-commit it** — without touching the
unrelated work in flight. Not "revert everything," but "triage each dirty entry on its
merits."

## 2. TL;DR playbook

1. `git status --short` to enumerate every dirty entry (staged, unstaged, untracked).
2. For each item, ask **"why does this exist?"** before acting — `git log`, `git show
   --stat` the commit that introduced it, and read the related source.
3. For a **leftover proposal**: find the commit that added it (`git log --oneline --
   <path>`), delete *all* of its artifacts (proposal dir **and** the mockups from the
   same commit), and commit the removal scoped to just those paths.
4. For an **uncommitted doc edit**: check whether it matches current source. If source
   already has the feature but the doc row lagged, the edit is a valid **docs-sync** —
   commit it, don't discard it.
5. For **server-managed state files** (e.g. `groups.json`): identify what writes them,
   keep the legitimate changes, surgically strip only the dead reference (the entry
   pointing at what you just deleted), validate, commit.
6. After each commit, re-print `git status --short` and report what remains, so the
   operator can steer to the next item.
7. Leave genuinely unrelated in-flight work (other untracked change dirs, `.bak`
   files) untouched — name them and ask before cleaning.

## 3. How the collaboration unfolded

The session was a three-item triage, one item per prompt, each a distinct git-hygiene
decision.

- **Item 1 — the leftover proposal (Discovery → Remove).** The AI ran `git status`
  and saw `openspec/changes/redesign-prompt-input/` already deleted in the working tree
  but *not committed*. Rather than just `git add` the deletion, it traced the origin
  commit (`780eed583`) with `git show --stat` and discovered the same commit had also
  added `mockups/prompt-input-v2/`, which still existed on disk. **Why this worked:**
  removing a proposal means reverting the *whole* commit's footprint, not just the dir
  the operator named. It deleted the mockups too and committed the full removal (6
  files, 1215 deletions), scoped to only those paths — leaving the other dirty entries
  alone. Decision point: the human's one-word scope ("redesign-prompt-input") was
  honored literally; unrelated work was explicitly not swept up.

- **Item 2 — the leftover AGENTS.md (Investigate → Commit).** Prompt 2 was just "There
  is leftover AGENTS.md." The AI resisted the temptation to treat "leftover" as
  "delete." It diffed the uncommitted `video-transcription/src/AGENTS.md` edit (added
  `.mov` to the docs), then checked the actual source: `discover.ts` already supported
  `.mov` (committed in `4dbdc8d17`), but that commit had missed the AGENTS.md row.
  **Why this worked:** the edit was a *correct doc-sync filling a gap the feature commit
  left*, not junk. It committed it rather than reverting. Decision point: "leftover"
  ≠ "wrong" — the AI verified intent against source before choosing remove vs. commit.

- **Item 3 — groups.json (Understand ownership → Surgical fix).** Prompt 3 was one word:
  "groups.json." The diff re-added `redesign-prompt-input` — the very thing just deleted
  — and reshuffled many entries. The AI first asked *what manages this file*, grepped,
  and learned it's **dashboard UI state written by the server** (`openspec-group-store.ts`),
  tracking grouping/ordering. So most of the diff was legitimate (current dashboard
  groupings), but the `redesign-prompt-input` reference was now dangling. **Why this
  worked:** it didn't blindly revert or blindly commit a machine-written file — it kept
  the real groupings, dropped only the dead entry, validated JSON (`python3 -m json.tool`),
  confirmed zero remaining references, and committed.

## 4. Prompts that worked

- **The goal prompt** — *"There is a leftover redesign-prompt-input proposal remove not
  committed."* Terse but effective because it named a **specific artifact** and a
  **specific verb** (remove). The AI could locate it immediately. A stronger version
  would add the scope guard up front: *"Remove the leftover redesign-prompt-input
  proposal and everything from its commit, but leave my other uncommitted work
  untouched."*
- **High-leverage follow-ups** — the one-word prompts ("groups.json", "There is leftover
  AGENTS.md") worked because the AI had already established the pattern: *for each dirty
  item, investigate origin → decide remove/commit/fix → report remainder*. Naming the
  next file was enough to trigger the whole routine. This only works because the AI kept
  echoing the remaining dirty items after each commit, giving the operator a menu to
  point at.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat the named artifact narrowly (just the deleted dir) | Nothing — the AI caught the co-committed mockups itself | State "remove everything from that commit" so scope is explicit |
| Risk reading "leftover" as "delete" | Naming the file only ("leftover AGENTS.md"), trusting the AI to investigate | Say "check if it's a valid change before removing" up front |
| Want to blanket-commit or blanket-revert a big machine-written diff | Naming just "groups.json," letting the AI discover it's server-managed | State "this is server-written UI state — keep real groupings, drop dead refs" |
| Potentially sweep up unrelated in-flight work | Implicit scope — the AI proactively listed untouched items and asked | Keep the "leave unrelated work untouched + report remainder" habit |

The core steering pattern was **minimal**: the operator gave one artifact name per turn
and let the AI do origin-tracing and remove/commit/fix classification. The guardrail that
made this safe was the AI's own discipline of *reporting the remaining dirty items and
asking before touching them*.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session. But the workflow is clearly repeatable
and worth capturing:

- **Recommended skill: `triage-dirty-worktree`.** Captures the decision tree for each
  git-status entry: (1) trace origin via `git log`/`git show --stat`; (2) classify as
  *leftover-to-remove* (revert whole commit footprint), *valid-uncommitted-change*
  (docs-sync / real edit → commit), or *machine-written-state* (keep legit changes,
  strip dead refs, validate); (3) commit scoped to only that item; (4) re-print status
  and report remainder before the next item. **Why effective:** it prevents the two
  classic mistakes — blanket-reverting a valid edit, and blanket-committing a
  machine-written file with a dangling reference — and it keeps unrelated in-flight work
  safe by design.

## 7. Pitfalls & dead ends

- **One failed command:** the opening `git status --short && ls openspec/changes/ | grep
  -i redesign` exited non-zero because `grep` found no match (the dir was already
  deleted). Harmless — the `&&` chain just reported the empty result via exit code. If
  you hit this, it's a signal the artifact is already gone from disk (but maybe not from
  git's index or from co-committed siblings — keep tracing).
- **"Leftover" is ambiguous.** Don't equate it with "delete." One of the three leftovers
  (the AGENTS.md edit) was a *correct* change that needed committing. Always diff against
  current source before discarding.
- **Reverting only the named path misses siblings.** The `redesign-prompt-input` proposal
  and `mockups/prompt-input-v2/` came in the same commit; deleting only the proposal dir
  would have orphaned the mockups. Always `git show --stat` the origin commit.
- **A machine-written file's diff is not all-or-nothing.** `groups.json` mixed legitimate
  UI groupings with a dead reference. Strip the dead entry, keep the rest — don't revert
  the file wholesale.

## 8. Reproduce it faster — checklist

- [ ] `git status --short` — enumerate every dirty entry.
- [ ] Per entry, `git log --oneline -- <path>` and `git show --stat <commit>` to learn
      why it exists and what shipped alongside it.
- [ ] Classify: **remove** (revert whole commit footprint) · **commit** (valid edit /
      docs-sync — verify against source first) · **fix-then-commit** (machine state —
      strip dead refs, validate, e.g. `python3 -m json.tool`).
- [ ] Commit each item **scoped to its own paths only**; write a message that states the
      rationale (e.g. "revert 780eed583, leftover proposal").
- [ ] After each commit, re-print `git status --short` and report the remainder.
- [ ] Explicitly leave unrelated in-flight work (other change dirs, `.bak` files)
      untouched — name them and ask.
