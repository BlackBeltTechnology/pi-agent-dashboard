# How we did it: Scoping full-app i18n coverage as an OpenSpec change — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator entered **explore mode** (`openspec-explore`) with a deceptively small ask:
figure out how to make *every* user-facing string in the dashboard translatable, when
only part of the app already goes through the client-side `t()` system. The first prompt
was the explore-mode stance ("think deeply, don't implement, you may create OpenSpec
artifacts"). The *real* objective, once steering clarified it: **audit the entire codebase
for untranslated strings, classify them by architectural zone, lock four design decisions,
and scaffold a validated OpenSpec change** — proposal, design, tasks, spec delta, and the
full inventory — without writing a single line of implementation.

## 2. TL;DR playbook

1. Enter explore mode: `/skill:openspec-explore`. State up front you want a *scoped audit
   + OpenSpec change*, not implementation.
2. Have the AI find the existing i18n infra first (`rg -l "lib/i18n"`, read
   `packages/client/src/lib/i18n.tsx`) — understand keys/catalogs/languages before counting.
3. Measure scope, then **partition the file tree into ~4 balanced chunks** and dispatch
   `@fast` subagents to audit each — but give them a **ripgrep-based method**, not "read
   every file" (see Pitfalls).
4. Have subagents write findings to `/tmp/i18n-audit/*.md` (one table per chunk), then
   synthesize a single **coverage map** grouping strings into architectural zones.
5. Give the AI your design decisions tersely (one line per zone). It expands them into a
   full target-state design.
6. Run the pre-scaffold coherence check (`ls openspec/changes/` — no duplicate/conflicting
   change), then `npx openspec new change <name> --description "…"`.
7. Author the four artifacts against the schema templates
   (`node_modules/@fission-ai/openspec/schemas/spec-driven/templates`), then
   `npx openspec validate <name> --strict`.
8. **Persist the `/tmp` audit tables into the change dir** (`audit/*.md`) so the
   implementation phase keeps the inventory.
9. `git add` only the change directory and commit surgically.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (understand before counting).** The AI resisted the temptation to
grep-and-count immediately. It first located the real i18n system
(`packages/client/src/lib/i18n.tsx` — `t()` + `useI18n()`, empty `en` dict = keys *are*
the English source, plus a `zh-CN` catalog), read it, and only then measured file counts.
*Why it worked:* the empty-`en` convention and the client-only reach of `t()` are exactly
the facts that later split the work into three zones — miss them and the audit is wrong.

**Phase 2 — Gather (parallel audit).** The AI partitioned the file tree into balanced
chunks and fanned out **16 `@fast` subagents** total (two waves). *Decision point:* the
**first wave returned nothing** — the `@fast` agents burned their budget reading ~60 files
each. The operator steered ("max 4"), and the AI re-dispatched in **waves of 4** with a
**ripgrep-based scan method** so each agent grepped cheaply instead of reading whole files.
Result: **~711 untranslated strings across ~141 files.**

**Phase 3 — Design (synthesize + lock decisions).** The AI collapsed the raw findings into
a three-zone coverage map: **Zone 1** client (has `t()`, easy), **Zone 2** plugins (separate
packages, can't import the client lib — needs `t` plumbed through plugin runtime context),
**Zone 3** server/extension (emit raw English — need error-code mapping). The operator then
locked all four decisions in one terse prompt (Zone 2 = per-plugin catalogs; Zone 3 = adopt
code-mapping; structured namespaces; translate `zh-CN`; **bonus: add Hungarian**).

**Phase 4 — Generate + Verify.** Coherence check (no conflicting change), `openspec new
change`, author proposal/design/tasks/spec-delta against the schema templates, `validate
--strict` → valid, persist the audit tables into `audit/`, and a **surgical commit** of
only the change directory (`868de90db`, 14 files) leaving unrelated working-tree changes
untouched.

## 4. Prompts that worked

- **The goal prompt (explore-mode stance).** Effective because it framed the work as
  *thinking + artifact creation, not implementation* — the AI stayed in audit/design mode
  and produced a change proposal instead of half-editing code. Stronger version: add one
  sentence naming the deliverable — *"audit all untranslated strings, then scaffold a
  validated OpenSpec change; do not implement."*
- **High-leverage follow-up (the four-line decision block).** `Zone 2 - Per plugin / Zone 3
  - adopt code-mapping / structured namespace… / zh-CN: Translate / bonus: Hungarian`.
  Four terse lines unlocked the entire design phase — the AI had already surfaced the zones,
  so the operator only had to pick. This is the pattern: **let the AI enumerate the option
  space, then choose in one shot.**
- **"commit"** — one word, because the AI had already staged the right scope mentally and
  knew to stay surgical.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Dispatch many subagents that each *read* ~60 files and ran out of budget (wave 1 returned nothing) | "re-dispatch, **max 4**" | Cap concurrent `@fast` audit agents at ~4 **and** give them a ripgrep scan method, not "read every file" |
| Treat the whole app as one flat i18n surface | Splitting into **Zone 1/2/3** by where the string originates | State up front: client vs plugin vs server strings need *different* strategies |
| Leave the ~700-row audit in ephemeral `/tmp` | (AI self-corrected) persist into `audit/` | Always move gather-phase artifacts into the change dir before commit |
| Risk sweeping unrelated dirty working-tree files into the commit | `git add` **only** the change directory | Stage by explicit path, never `git add -A`, when the tree has unrelated changes |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The reusable *pattern* worth capturing:
**"parallel-audit-then-scaffold"** — partition a large codebase surface, fan out capped
`@fast` subagents with a cheap ripgrep method, synthesize into zones, then turn the zones
into an OpenSpec change. If this recurs (i18n, a11y sweep, dead-code hunt, license audit),
create a project skill encoding: (1) chunk the file tree balanced by count, (2) cap agents
at 4 per wave, (3) mandate grep-not-read, (4) write to `/tmp/<audit>/*.md`, (5) persist into
the change `audit/` dir before commit.

The session leaned on existing skills correctly: `openspec-explore` (stance that kept it
from implementing), `openspec new change` (scaffold), and `openspec validate --strict`
(the correctness gate).

## 7. Pitfalls & dead ends

- **Subagents that read whole files run out of budget.** Wave 1's `@fast` agents produced
  *no output* because each tried to read ~60 files. **Fix:** give audit subagents a
  ripgrep-based method and cap the wave at ~4.
- **First recon `rg` failed** (`--type tsx` isn't a valid ripgrep type). Use `--glob '*.tsx'`
  instead of `--type tsx`.
- **`/tmp` is ephemeral.** The ~700-row inventory would have been lost after the session —
  persist it into `openspec/changes/<name>/audit/` before you commit.
- **Dirty working tree.** The repo had many unrelated uncommitted changes; a naive
  `git add -A` would have polluted the commit. Stage the change directory by explicit path.
- **Cross-package reach is a real blocker, not a detail.** Zone 2 plugins live in separate
  packages and *cannot* import `packages/client/src/lib/i18n.tsx` — this forced the
  per-plugin catalog + runtime-merge design. Surface such boundaries during the audit.
