# How we did it: Driving `kb dox lint` to a clean floor — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with three words: **"Fix stale knoledge base entries"**. In this repo
that maps to a concrete, mechanical target: the `kb dox lint` health-check reports
drift across the directory `AGENTS.md` tree, and 39 rows were flagged **stale**. Once
the two later steering turns landed ("fix them" → also clear the *other* lint
categories; "1" → commit it all as one commit), the *real* objective became: **drive
every actionable `kb dox lint` category to zero** — stale, missing, missing-companion,
orphan — accepting only the structural `over-threshold` floor, then land it as a
single clean commit that touches **only** this task's files.

## 2. TL;DR playbook

1. **Understand "stale" before touching anything.** A DOX row is stale when its source
   file's sha256 drifts from the acknowledged hash in
   `.pi/dashboard/kb/dox-staleness.json`. Read `packages/kb/src/dox.ts` +
   `reindex.ts` to confirm the mechanism.
2. **Scope with the linter:** `node_modules/.bin/kb dox lint` and
   `kb dox lint --json` → bucket the issues by category and by owning `AGENTS.md`.
3. **Never blind-run `kb dox lint --fix`** — it appends empty-purpose rows, including
   to the forbidden root `AGENTS.md` and to gitignored build/vendored dirs.
4. **Split the categories by root cause:** *exclude* (build output, vendored bundles,
   scratch dirs) vs *author* (real source docs) vs *code fix* (the linter's own
   `DEFAULT_EXCLUDE` / `isMdFile`).
5. **Fan out the review/authoring** to parallel `docs-editor` subagents, one per
   `AGENTS.md`; route every `docs/` write through its own subagent (Rule 6).
6. **Fix the linter as a code change** in `packages/kb/src/dox.ts` (add exclusions,
   exclude `*.agent.md` companions from `isMdFile`), **add a regression test**, and
   **rebuild `dist`** — the bin runs `dist/cli.js`.
7. **Re-acknowledge** any still-accurate stale row (refresh its hash) via the same
   logic the extension's `acknowledgeRows` uses.
8. **Commit with an explicit allowlist** of `*AGENTS.md` (no dot) + `*.agent.md` + kb
   src — `touch` the files first to defeat git's stat-cache skip, verify
   `HEAD == working` blobs, exclude all foreign/pre-existing changes.

## 3. How the collaboration unfolded

**Phase 1 — Mechanism discovery.** The AI resisted the temptation to run `--fix` and
instead read `dox.ts`/`reindex.ts` to learn *what stale means*: a sha256 mismatch in
`.pi/dashboard/kb/dox-staleness.json`. *Why it worked:* the whole task hinges on this
one fact — that "fixing" a stale row means re-verifying its purpose against the changed
source, then re-acknowledging the hash, **not** editing prose blindly.

**Phase 2 — Scoped parallel review (stale).** 39 stale rows across 9 `AGENTS.md` files
were delegated to 6 parallel `docs-editor` subagents (one per file; `docs/AGENTS.md`
through its own per Rule 6). The subagents' file-edits auto-acknowledged 33 rows via the
kb edit hook; the AI's script refreshed the remaining 6 still-accurate rows. **Stale → 0.**

**Phase 3 — The "fix them" expansion.** The user's "fix them" meant the other
categories too (missing 100, missing-companion 37, orphan 1, over-threshold 12). Here
the AI did its most valuable work: it **refused the naive path** and categorized 100
"missing" into buckets needing *different* treatment — 47 gitignored build/vendored
paths that should be **excluded from the linter**, not documented.

**Phase 4 — Linter as code.** Two precise edits to `packages/kb/src/dox.ts`:
`DEFAULT_EXCLUDE` gained build/vendored + generic-scratch patterns; `isMdFile` learned
to skip `*.agent.md` companions (which were self-flagging in infinite regress). A focused
regression test was added, `dist` rebuilt. *Decision point:* keep the published regex
**generic-defensible** (`mockups`, `research`, `site`, `CHANGELOG.md`) rather than baking
repo-specific filenames into a shared package.

**Phase 5 — Authoring + splitting.** 5 parallel authoring subagents added ~24 real rows
+ 16 companion sidecars; `scripts/split-large-agents.mjs` cleared the 4 byte-flags
(~293 sidecars). The AI correctly reported that the **8 row-count over-threshold flags
are a structural floor** requiring directory restructuring — and did *not* pretend to
reach zero.

**Phase 6 — The commit saga.** The single hardest part. Staging repeatedly missed the
tracked `AGENTS.md` edits. Root cause (found after many probes): the glob `*.AGENTS.md`
and regex `\.AGENTS\.md$` both require a **literal dot** before `AGENTS`, so they matched
sidecars/companions but **never plain directory `AGENTS.md` files**. Fixed with
`*AGENTS.md` (no dot) + `touch` to bump mtime past git's stat-cache skip. Final commit:
**346 files, +2320 / −317**, foreign changes excluded.

## 4. Prompts that worked

- **The goal prompt** — *"Fix stale knoledge base entries."* Terse but sufficient
  because the repo has a deterministic linter (`kb dox lint`) that defines "stale"
  precisely. A stronger version for a colder start: *"Run `kb dox lint`, fix only the
  **stale** category by re-verifying each flagged row against its changed source and
  re-acknowledging the hash — don't touch other categories yet."*
- **High-leverage follow-up** — *"fix them"* unlocked the full expansion to all
  categories. It worked *because* the AI had already surfaced the category breakdown, so
  the two-word steer had a clear referent. Reproduce by making the AI enumerate scope
  **before** you say "fix them".
- **The unlock** — *"1"* (choose commit-as-single-commit). Effective only because the AI
  had presented a numbered `ask_user` choice. Keep decision points as explicit numbered
  options so a one-character reply is unambiguous.

## 6. Skills, tools & memory created — and why they're effective

The session updated a **project skill** capturing the DOX staleness workflow
(`skill_manage` ran twice). What it captures and why it matters:

- **The staleness mechanism** — sha256 tracked in `.pi/dashboard/kb/dox-staleness.json`;
  a row is stale on drift; "fix" = re-verify purpose + re-acknowledge hash. This is
  non-obvious and un-greppable; encoding it saves the next operator the Phase-1 dig.
- **The `--fix` danger + category routing** — exclude vs author vs code-fix. Removes the
  single biggest failure mode (blindly appending empty rows).
- **The commit gotcha** — `*AGENTS.md` (no dot) + `touch` to defeat git's stat-cache.
  This alone consumed ~15 minutes of the session; documenting it makes the commit a
  one-shot next time.

*When to invoke:* any "fix stale/missing KB entries" or "DOX drift" request — this is
now the `fix-stale-kb-dox-rows` procedure.

## 7. Pitfalls & dead ends

- **`execSync` throws on `kb dox lint`** — it exits non-zero when issues exist, but the
  JSON is on stdout. Capture stdout despite the exit code.
- **`git add -A` swept in foreign untracked packages** (`nano-banana`, `video-production`,
  root `vitest.config.ts`). Reset and use a precise allowlist.
- **`*.AGENTS.md` glob silently excludes plain `AGENTS.md`** — the literal dot means it
  only matched `Foo.tsx.AGENTS.md` sidecars. Use `*AGENTS.md`.
- **git stat-cache skip** — tracked `AGENTS.md` with old mtimes were treated as unchanged
  by `git add` after a `reset`. `touch` them to force a re-hash.
- **`.agent.md` companions self-flag as `missing`** — they're pull-only artifacts; exclude
  them from `isMdFile` (infinite regress otherwise).
- **Pre-existing corpus timeout** — the `doc-example` golden-query test times out at 5s;
  unrelated to the exclusion edits. Don't chase it.
- **over-threshold row-count flags are unfixable by splitting** — they need directory
  restructuring. Accept the floor; don't burn time.
