# How we did it: Root-causing the "no available models" subagent failure — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) to investigate a report that an
LLM was "unable to determine available models." The real objective, once the transcript was
read, turned out to be different from the symptom: **a subagent spawned via the `Agent` tool
on a custom-provider model (openai/google/deepseek from `providers.json`) returns empty
output** — the child never responds, no error surfaces, and the calling skill misreads the
silence as "no models available" and wrongly escalates to an external CLI. The task became:
prove the root cause empirically, confirm the fix already exists but is unpublished, and land
the safe, self-contained parts (a skill patch + a local release + reviewer-role config).

## 2. TL;DR playbook

1. **Read the failing session transcript first**, not the symptom. Parse the JSONL with
   `node -e` / bash to find what the agent actually *did* (enumerated models → spawned
   custom-provider children → got `(no output)` → misdiagnosed as "no models").
2. **Separate "catalog" from "spawn."** Check the live catalog with
   `list_models --annotated` — every model showed `excludedReason: null` (credentialed).
   The catalog was fine; the *spawn* was broken. This reframes the whole bug.
3. **Trace to the producer code.** The subagents producer lives in a **sibling repo**
   (`../pi-dashboard-subagents`), not this repo. Find the resolution + spawn path; look for a
   recent fix commit (`inherit parent model registry in subagent spawn`).
4. **Establish the version story.** `npm view` the published package (`0.2.2`, pre-fix) vs the
   fix commit date. The installed producer predates the fix → the bug is unpublished, not new.
5. **Isolate with a control-vs-test spawn in a real Agent-tool session.** Anthropic child
   (built-in auth) → text; openai child (custom provider) → `(no output)`. Same tool, same
   type, only the child provider differs → cross-provider registry-inheritance confirmed.
6. **Land only the safe, self-contained work.** Patch `doubt-driven-review` to select the
   reviewer via a `@propose-review-N` role series (role refs route through the supported
   resolver the raw `provider/model` path bypassed). Seed the roles via one **atomic**
   `providers.json` write. Prepare the producer release **locally** (bump + CHANGELOG + tag,
   no push) and hand the push to the human.
7. **Commit surgically** — stage only your file; leave unrelated dirty files untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (read the real transcript).** The AI located the failing session in a
worktree, parsed its JSONL, and discovered the model ID `claude-opus-4-8` plus a chain of
custom-provider subagent spawns all returning `(no output)`. Key move: it did **not** trust
the "no models available" framing — it reconstructed the actual tool sequence.

**Phase 2 — Reframe (catalog vs spawn).** `list_models --annotated` proved every attempted
model was credentialed *right now*. That single check flipped the diagnosis from "missing
credentials / no catalog" to "the spawned child loses the custom providers."

**Phase 3 — Trace to the producer.** The producer is a **sibling repo**. A `find /` hung
(too broad) and had to be scoped. The AI found the recent fix commit
`inherit parent model registry in subagent spawn` and read the resolution function: a failed
resolve returns a *descriptive error*, not empty — so `(no output)` meant the child resolved
but died at request time ("No API key found for openai") because it built a **fresh disk
registry lacking the custom providers**.

**Phase 4 — Version forensics.** Published `0.2.2` (2026-06-05) predates the fix
(2026-07-08). A stray `v0.5.5` tag that didn't contain the fix was correctly ignored. The
running production defect is simply the *unpublished* producer fix.

**Phase 5 — Empirical isolation.** Several harness walls appeared: `pi -p` headless sessions
and dashboard-API-spawned sessions **don't register the Agent tool at all**, so only *this*
interactive session could run a real spawn. The decisive test ran here: control
(`anthropic/claude-haiku-4-5`) → `OK`; test (`openai/gpt-5.2`) → `(no output)`. Root cause
isolated to cross-provider registry inheritance.

**Phase 6 — Land the safe parts.** Decision points were all human-gated: the AI patched the
skill to a `@propose-review-N` role series, seeded three reviewer roles (Opus **last**, as the
same-family fallback) via one atomic write, added a `list_models → ask_user → update_roles`
bootstrap path, prepared release `v0.2.3` locally (not pushed), and committed only the skill
file.

## 4. Prompts that worked

- **The goal prompt** (explore-mode kickoff): effective because it framed the task as
  *investigate*, not *implement* — the AI read code and transcripts instead of jumping to a
  fix. A stronger kickoff states the artifact up front: *"Explore why session X reported 'no
  available models'. Read its JSONL, separate catalog from spawn, and find the root cause

- **"1 and 2 — And I would like to use review-1..review-x model roles to select review
  model."** — a high-leverage unlock: it both approved a work slice *and* introduced the
  structural fix (route reviewer selection through `@role` refs, which use the supported
  resolver the raw `provider/model` path bypassed).
- **"No. Be propose-review and plant that model and opus be the last"** — short, decisive
  steering that fixed both the role naming and the ordering rule in one turn.
- **"Add to skill the ability to set models via list_models and role api. So machines where
  provider not set ask user for reviewer model selection"** — turned a one-off config step
  into a reusable self-bootstrapping capability.

## 6. Skills, tools & memory created — and why they're effective

No new skill was created, but the **`doubt-driven-review`** skill was substantially patched
and **two memories** were saved:

- **Memory (project): cross-provider spawn bug.** Captures that a subagent on a
  custom-provider model returns empty output because the child builds a fresh registry
  lacking the custom providers. Reusable because this exact failure looks like "no models"
  and will recur until the producer fix ships.
- **Memory (failure · tool-quirk): how to test an Agent spawn.** *You MUST use a
  dashboard-managed session (`POST /api/session/spawn`), NOT `pi -p` headless* — headless and
  API-spawned sessions don't register the Agent tool. This is the single most time-saving
  fact of the session; it invalidates a whole class of "verification" that silently produces
  the parent model narrating an empty result.
- **Skill patch (`doubt-driven-review`):** reviewer now walks `@propose-review-1..x` (role
  refs route through the supported `model:resolve` handler), skips the author's own family,
  puts Opus last as fallback, and self-bootstraps a reviewer role via
  `list_models → ask_user → update_roles` when none is configured. Invoke it whenever an
  irreversible/high-stakes change needs a cross-model second opinion.

## 7. Pitfalls & dead ends

- **`find /` hung the session.** Scope every search to a known directory.
- **Loading the producer from the sibling *tree* (absolute or relative path) lost the Agent
  tool** — peer skew: the sibling bundles pi-coding-agent `0.75.5`, the host runs `0.80.6`,
  so the extension silently fails to register. Fix: overlay the fixed `.ts` onto the
  *installed* package (which resolves the correct shared SDK), never point `packages[]` at the
  sibling tree.
- **`pi -p` headless and dashboard-API-spawned sessions don't register the Agent tool.**
  "Verification" runs there are invalid — the parent model just narrates an empty result. Use
  a real interactive dashboard-managed session.
- **`npm run reload` is a soft bridge reload** — it does not re-import a separately-cached npm
  extension module. A session that imported the pre-fix producer at startup keeps running it;
  only a fresh session loads an overlay.
- **A stray `v0.5.5` tag** did not contain the fix and wasn't on npm — ignore misleading tags;
  trust `npm view` + commit dates for the release lineage.
- **`package-lock.json` version skew** (`0.2.2` vs the bumped `0.2.3`) can fail release CI's
  `npm ci` — sync the lock before pushing.
