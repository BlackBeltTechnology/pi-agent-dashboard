# How we did it: Wiring the OpenSpec pipeline into two orchestrator skills — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner
stance, no implementation. The real objective surfaced quickly: the user was living a
**manual relay** every time they landed an OpenSpec change — draft artifacts, remember
to run `doubt-driven-review`, remember to run `scenario-design`, hand-fold its catalog
into `tasks.md`, `openspec-apply`, hand-run e2e, then ship. They wanted that chain
**wired together** so the steps trigger automatically instead of being remembered.

The AI's first reframe set the whole session: *"The pieces already exist. What you're
missing is the wiring."* The four requested steps mapped almost 1:1 onto skills the
repo already ships (`scenario-design`, `doubt-driven-review`, `openspec-apply-change`,
`ship-change`) — the gap was auto-triggering and the hand-offs, not new machinery.

The output was **not code** — it was a fully-scoped, doubt-hardened OpenSpec change
(`add-openspec-pipeline-orchestrators`) proposing **two named orchestrator skills**:
`plan-proposal` (develop side, interactive) and `ship-it` (worktree side,
headless-capable), split at the **git-worktree boundary**.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) and force a grounding pass first:
   `openspec list --json`, grep the archive, read the candidate skills. Let the AI say
   *"which links are already forged?"* before sketching anything.
2. **Reframe the ask as wiring, not building.** Draw the 4 requested steps against the
   existing skills; label each gap (`✗ no auto-trigger`, `✗ doesn't auto-fold`).
3. **Find the spine.** Here it was the **git-worktree boundary** = the interactive
   (develop) / headless (worktree) line. One structural fact organized every decision.
4. **Lock the shape with a one-word steer:** "two named skills" → `plan-proposal` +
   `ship-it`. Name the seam before writing prose.
5. **Capture the proposal** (`openspec new change` → write `proposal.md`), validate it
   as artifact 1/4, and *deliberately leave one fork open* (convention vs contract).
6. **Keep exploring** the open forks — each "keep going / go on" pulled a thread that
   *reversed* a prior decision (tag polarity, subagent-ability). Ground every claim in
   a real file count before asserting it.
7. **Write `design.md`**, then run the **doubt cycle**: spawn a fresh-context
   `Explore` reviewer with ARTIFACT + CONTRACT only (no CLAIM, no verdict).
8. **Offer a cross-model second opinion** — probe reachability of non-Anthropic models
   in parallel, pick one that actually returns (`deepseek-v4-pro`), rerun the same
   adversarial pass.
9. **Reconcile** both reviews into a precedence-ordered table; let the human hand you
   the wheel ("ok, what now?") on the last architectural fork → pick **MANIFEST**.
10. **Fast-forward** the remaining artifacts (`openspec-ff-change`: specs → tasks),
    validate, then **commit only the change dir** — surgically, nothing else swept in.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding (interactive).** Before sketching, the AI ran
`openspec list --json`, listed active changes, grepped the archive for
`ship|apply|orchestrat|pipeline`, and read the four candidate skills. *Why it worked:*
it discovered the four steps were already-shipped skills and that the parallel-worktree
port problem was **already solved** (`docker/test-up.sh` + `lib-ports.sh` hash-derive a
free port pair per worktree) — deleting scope before adding any.

**Phase 2 — Find the spine.** Steering #1 gave the AI the key fact: proposal +
doubt-review + scenario-design belong to the **planning phase on `develop`**;
`openspec-apply` starts the **implementation phase in a worktree**. The AI recognized
the **worktree boundary IS the spine** and also the interactive/headless line. Decision
point: the human answered "make the orchestrator idempotent" to the "apply-or-ship?"
question → *"both, and it doesn't matter."*

**Phase 3 — Name the seam.** Steering #3 = "two named skills." That single move locked
`plan-proposal` (develop) + `ship-it` (worktree) and let the AI write `proposal.md`,
validating as 1/4 — while **explicitly leaving one fork open** rather than deciding
silently.

**Phase 4 — Pull the open threads (the reversals).** A run of short "keep
exploring / go on" prompts drove the AI to ground each open fork in real data. Two
prior decisions **flipped**: tag polarity reversed to `[automated]` after finding **38
active changes with zero tags** (tagging manual would break all of them); and
`plan-proposal` was proven **main-session-only** because `doubt-driven-review` can't
nest inside a subagent. *Why it worked:* every claim was checked against a file count
before being asserted.

**Phase 5 — Design + doubt cycle.** "Go on" = write `design.md` (11 decisions). The AI
then ran the doubt cycle: a fresh-context `Explore` reviewer got **ARTIFACT +
CONTRACT only** — no CLAIM, no verdict — surfacing 3 majors. It then honored the
skill's cross-model requirement: probed 4 non-Anthropic models in parallel, discarded
the unreachable ones (`gpt-5.2`, `gemini` returned empty), and reran with
`deepseek-v4-pro`, which caught a genuine blocker the first reviewer missed (the
`[automated]` tag could break the `openspec status --json` parser).

**Phase 6 — Reconcile + generate + commit.** The human said "ok. What now?" and handed
over the wheel; the AI chose **MANIFEST** (automated-vs-manual lives in `test-plan.md`,
`tasks.md` stays vanilla → parser + 38 legacy changes untouched), rewrote `design.md`
whole (11→12 decisions), then `openspec-ff-change` wrote both specs + `tasks.md`, fixed
one validation error, and committed **only** the six change-artifact files as
`fa75cdc51`.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore`)** — starting in explore mode was the leverage:
  it *forced grounding before sketching* and blocked premature implementation. A future
  operator should still open with "enter explore mode, ground this in what exists first."
- **"two named skills"** (steering #3) — a 3-word prompt that locked the entire
  architecture's shape. Naming the seam early is the highest-leverage move here.
- **"It will be called after apply or when I call ship it will call apply?"**
  (steering #2) — a precise entry-point question that produced the **idempotent
  orchestrator** design ("both, and it doesn't matter").
- **"Keep exploring" / "go on"** — cheap continuation prompts that were only powerful
  *because* the AI had been told to ground each thread in data. They unlocked the two
  decision reversals.
- **"ok. What now?"** (steering #9) — deliberately handing the AI the wheel on the last
  fork after two review cycles. Works when the option space is already narrowed to two.

**Rewrite of the weak "1" / "3" numeric replies:** prefer naming the choice —
"idempotent orchestrator (option 1)" — so the transcript stays self-documenting.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| treat all tests as one e2e bucket | "there are other tests, CI, electron — fold them by category, always check for that specific type" | tell scenario-design to route by test level up front |
| default to docker port 18000 | "parallel worktrees exist — don't use 18000, check for separated ports" | reuse the existing hash-derived port harness (`test-up.sh`) — never hardcode |
| blur the planning/implementation split | "proposal+doubt+tests are the planning phase on develop; apply starts implementation in the worktree" | make the **worktree boundary** the organizing spine from message 1 |
| leave a fork implicit and pick silently | proposal deliberately noted the fork; human said "keep exploring" | state open forks explicitly, resolve with data, never decide silently |

## 6. Skills, tools & memory created — and why they're effective

No new skill file was written this session — the whole point was to **compose existing
skills**. But the session *designed* two orchestrator skills worth building:

- **`plan-proposal`** (develop-side orchestrator) — chains artifact creation →
  `doubt-driven-review` → `scenario-design` → category-routed fold into `tasks.md`,
  then **stops at the worktree boundary**. Effective because it removes the "remember to
  run X" tax and provably must run in the main interactive session (doubt-review can't
  nest). Invoke when starting to plan any OpenSpec change on `develop`.
- **`ship-it`** (worktree-side orchestrator) — idempotent (keys off *test file exists +
  passes*, never the checkbox), owns its own bounded red-test fix loop, runs the docker
  harness on an auto-derived port with always-teardown, then drives `ship-change`
  inline. Effective because it makes the implementation half **headless-runnable** and
  safe. Invoke inside a fresh worktree after `openspec-apply`.

*(Both were later shipped as real skills — see `.pi/skills/plan-proposal` and
`.pi/skills/ship-it`.)*

Reusable technique worth saving as a memory: **the doubt cycle's cross-model reviewer
must be probed for reachability first** — a model listed in `list_models` can still
return empty from the SDK (`gpt-5.2`, `gemini` here). Probe in parallel, use the first
that actually answers.

## 7. Pitfalls & dead ends

- **Tag polarity backwards.** The first design tagged *manual* tasks; grounding found
  **38 active changes with zero tags** → tagging manual breaks all of them. Reversed to
  `[automated]`. *If you add a task tag, count how many legacy changes it breaks first.*
- **Inline tag breaks the parser.** The cross-model reviewer caught that an
  `[automated]` token in `tasks.md` could break `openspec status --json`. Resolution:
  **MANIFEST** — keep `tasks.md` vanilla, put disposition in `test-plan.md`. *Never add
  syntax to a file a generated CLI parses.*
- **Fake idempotence.** `openspec status` reads checkboxes, not the filesystem — a task
  marked `[x]` with the test file missing would skip apply forever. Fix: key
  idempotence off *test file present + green*.
- **Fix loop spins.** `apply` marks a task `[x]` on cycle 1, so a retry is a no-op and a
  real bug never gets fixed. Fix: **ship-it owns the fix loop directly**, bounded by
  progress-making cycles with a mechanical diff-assert forbidding test-weakening.
- **Unreachable models.** `gpt-5.2` and `gemini-3.1-pro` were listed but returned empty.
  Don't silently proceed — probe and fall through families.
- **Two `mktemp`/tool errors** in the log were harmless (a `ctx_batch_execute` and a
  `ctx_cmd_placeholder` failure) — the openspec CLI path carried the work.
