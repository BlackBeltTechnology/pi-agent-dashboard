## 1. Goal (the ask)

The operator entered **explore mode** (`openspec-explore` skill) — "Enter explore mode.
Think deeply… you must NEVER write code or implement features… you MAY create OpenSpec
artifacts." The real objective, once the exploration converged, was narrow and concrete:
diagnose why the KB **"Index now"** button feels dead right after a click, decide the
minimal fix, and **capture it as a complete OpenSpec change proposal** (proposal + design +
delta spec + tasks) — without writing any implementation code. The session ended by
committing the scaffolded change on `develop`.

## 2. TL;DR playbook

1. Kick off with the `openspec-explore` skill so the AI stays in *think-and-capture* mode,
   not *implement* mode.
2. Let it trace the actual flow: `grep` the button ("Index now"/"NOT INDEXED"/"reindex")
   → read the client component (`FolderKbSection.tsx`, `useKbStats.ts`) → read the server
   route (`kb-routes.ts`) to confirm where the race really lives.
3. Make the AI **locate the dead-zone precisely** (client-side, in the 2-round-trip window
   between click and the first `indexing:true`) before proposing any fix.
4. Approve the decision with a terse `yes` / `yes` once it presents the optimistic-pending
   state machine and the two-file touch plan.
5. Have it run the **pre-scaffold coherence check** against the archived
   `2026-07-04-fix-kb-index-feedback` change — confirm it's a genuine delta, not a duplicate.
6. Scaffold the four artifacts directly (no `openspec change new` subcommand exists) by
   copying conventions from an existing active change.
7. `openspec validate <name> --strict` before committing.
8. Say `commit`; make the AI stage **only** its own change folder and leave unrelated
   `groups.json` / `package-lock.json` drift untouched.

## 3. How the collaboration unfolded

**Phase A — Discovery (grep → read client → read server).** The AI grepped `packages/web/src`
for the button, then read the KB plugin client (`FolderKbSection.tsx`, `useKbStats.ts`) and
its `AGENTS.md`, then the server `kb-routes.ts`. *Why it worked:* it refused to theorize
about the bug before reading both sides — it confirmed the server already flips the job to
`running` synchronously and returns `202`, so the race is **entirely client-side**.

**Phase B — Locate the dead-zone.** It drew the click → `POST /reindex` → refetch →
`GET /stats` sequence and pinpointed that the *only* state change on click is
`setReindexError(null)` (invisible), so nothing renders until round-trip #2 resolves. *This
diagnosis is the whole value of the session* — the fix is small once the window is named.

**Phase C — Decision (steering: `yes` / `yes`).** The AI proposed **optimistic pending**:
set `pending=true` on click, render identically to `indexing` (spinner + disabled button),
clear only when `stats.indexing===true` is observed or the POST rejects. The human unlocked
it with two bare `yes`es. The load-bearing invariant: **pending must not clear on the bare
`202`** (else the spinner flickers).

**Phase D — Coherence check + scaffold.** Per project convention the AI ran the pre-scaffold
check against the archived `fix-kb-index-feedback`, confirmed a clean delta on the same
`kb-folder-slot` capability, found `openspec change new` unsupported, copied layout from an
active change, and wrote proposal / design / delta-spec / tasks. `openspec validate --strict`
passed.

**Phase E — Commit (steering: `commit`).** It noticed `groups.json` drift, determined it was
unrelated (its change wasn't even in it), staged only its own folder, and committed on
`develop` — 4 files, +215 lines, not pushed.

## 4. Prompts that worked

- **Goal prompt — the `openspec-explore` skill invocation.** Effective because it pins the
  AI to *capture thinking, not implement*: it read/searched freely but produced OpenSpec
  artifacts instead of code. Use this whenever the outcome you want is a **proposal**, not a diff.
- **`1. yes / 2. yes`** — a high-leverage unlock. After the AI laid out the state machine and
  the two-file touch plan as an explicit yes/no decision, one word each approved both. Works
  *because the AI framed the decision as answerable* — the lesson is to make the AI present
  decisions as enumerated choices, then approve tersely.
- **`commit`** — trusted the AI to do the right git hygiene (stage only its folder).

Weak-prompt rewrite: none needed — the explore skill did the heavy lifting. If reproducing
without the skill, open with: *"Explore why the KB 'Index now' button feels unresponsive on
click. Do NOT write code — trace the client+server flow, propose the minimal fix, and if it
holds up, scaffold an OpenSpec change (proposal/design/spec/tasks) and validate it."*

## 7. Pitfalls & dead ends

- **`openspec change new <name>` does not exist** — the command failed. Don't rely on a
  scaffold subcommand; create the four files directly, copying layout/conventions from an
  existing active change (e.g. `collapse-diff-file-tree`, `render-pptx-preview`).
- **Reading `.openspec.yaml` on an archived change failed** (no such file) — don't assume a
  per-change YAML manifest exists; inspect a real active change to learn the actual layout.
- **`groups.json` / `package-lock.json` drift at commit time** — unrelated to your change.
  Verify (`git diff openspec/groups/groups.json`) it doesn't reference your change, then
  stage only your own folder. Do not sweep it into the commit.
- **The `202` trap** (design-level pitfall to encode in the implementation): clearing
  optimistic `pending` on the bare `202` response makes the spinner flicker — clear it only
  once `stats.indexing===true` is actually observed, or on POST rejection.
