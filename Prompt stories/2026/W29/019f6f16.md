## 2. TL;DR playbook

1. **Kick off in explore mode** (`openspec-explore` skill) — investigate only, no code.
2. **Trace both dispatch paths** with `rg`/`kb_search`: the overlay path (`shared/renderer-by-ext.ts` → `dispatchPreview`) and the split path (`shared/file-kind.ts` → `fileKind`). Find the divergence: `.eml` is registered in one table, not the other.
3. **Draw the root-cause diagram** (two independent classification systems) so the seam is visible before proposing anything.
4. **Scaffold the change**: `openspec new change fix-eml-preview-in-editor-pane`, then write `proposal.md`, `design.md`, `tasks.md`, and a spec delta against `internal-monaco-editor-pane`.
5. `openspec validate <change> --strict` until clean.
6. **Switch to `plan-proposal`** (main session only) → run `doubt-driven-review`: probe `@propose-review-1`, run single-model + cross-model adversarial reviews **in parallel**.
7. **When reviewers converge or disagree, verify their claims against source** — don't rubber-stamp. Trace the actual FileLink dispatch to settle the disagreement.
8. **Fold confirmed findings back** into proposal/design/spec/tasks; re-validate; run **cycle-2** review on the corrected artifacts until the stop condition (only trivial notes remain).
9. **Stop at the git-worktree boundary.** Report the 4 artifacts and the load-bearing decisions; commit nothing.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI used `rg` and `kb_search` to locate `EmlPreview`, `SplitView`, `EditorPane`, and the two viewer registries. It resisted the urge to fix, staying inside the explore stance. *Why it worked:* mapping both dispatch tables before proposing anything exposed the true seam — `.eml → "email"` exists in `RENDERER_BY_EXT` but has no entry in `fileKind`, so the split pane falls through to the default (Monaco) branch.

**Phase 2 — Root-cause diagram.** The AI rendered an ASCII/mermaid flow of "OPEN AN .eml FILE" splitting into the overlay path vs the split-pane path. *Decision point:* the human implicitly accepted that this was a **spec seam** (`file-and-url-preview` vs `internal-monaco-editor-pane`), which framed the whole change as a spec delta, not a code patch.

**Phase 3 — Scaffold + draft.** `openspec new change` created the skeleton; the AI wrote proposal/design/tasks and a 2-requirement MODIFIED spec delta, then passed `--strict`. *Why it worked:* the design captured 4 explicit decisions (D1: add an `.eml` branch to `fileKind` rather than unify the two tables) so reviewers had concrete claims to attack.

**Phase 4 — Adversarial review (the payoff).** Steering turn #2 switched to `plan-proposal`. The AI probed `@propose-review-1` (glm-5.2 — a different model family), then ran single-model (Claude) and cross-model reviews **automatically and in parallel**. Both reviewers independently converged on the same findings — *and disagreed* on whether `FilePreviewOverlay` breaks for `.eml`.

**Phase 5 — Verify-then-reconcile.** Instead of trusting either reviewer, the AI traced the FileLink dispatch in source and confirmed: reclassifying `.eml → "email"` makes the shared `/api/file` gate stop returning `content`, which blanks a **third** surface (`FilePreviewOverlay`). GLM was right, Claude wrong. It classified every finding as Actionable / Trade-off / Noise, folded the confirmed ones back into all four artifacts, re-validated, and ran a cycle-2 review that found the corrections sound. *Decision point:* the human's scope question — split the overlay fix into a separate change? — was surfaced explicitly and left for the human, with the trade-off spelled out.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore`)** — effective because it hard-constrains the AI to *think, not implement*, while explicitly permitting OpenSpec artifacts. This kept the whole session in "capture thinking" mode and prevented premature code.
- **Steering prompt (`plan-proposal`)** — a single skill invocation that triggered the entire review orchestration (doubt-review → cross-model → verify → fold → cycle-2). High leverage: one prompt bought two full review cycles.
- **Rewrite for next time:** if you already know the bug is a two-table divergence, open with: _"Explore mode: trace how `.eml` is classified in `shared/file-kind.ts` vs `shared/renderer-by-ext.ts`, diagram the seam, then scaffold an OpenSpec change with a spec delta — don't implement."_ That front-loads the seam and saves the discovery grep loop.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — the session *consumed* existing ones, which is itself the lesson:

- **`openspec-explore`** — the stance that kept diagnosis from sliding into implementation. Invoke whenever the goal is "understand + capture", not "build".
- **`plan-proposal`** (main session only) — the orchestration twin of `ship-it`. It composes `doubt-driven-review` + `scenario-design`; one invocation drives probe → parallel single/cross-model review → verify → fold → cycle-2. Invoke after artifacts are drafted and validated, before the worktree boundary.
- **`doubt-driven-review`** — the value engine here. It caught a 3× blast-radius error a single reviewer missed. Invoke on any change where "no server change / small scope" is claimed.

If anything should be saved as memory: **"reclassifying a file extension in the shared `fileKind` ripples to `/api/file` `content` gating → check `FilePreviewOverlay` + `file-icon.ts` before claiming editor-pane-only scope."**

## 7. Pitfalls & dead ends

- **`openspec change new …` is the wrong verb** — the correct command is `openspec new change <name>`. The session burned a few `--help` probes discovering this. If `openspec change new` fails, try `openspec new change`.
- **Converging reviewers ≠ correct reviewers.** Two models agreed on findings but *disagreed* on the overlay breakage; only a source trace of the FileLink dispatch settled it. If two reviewers disagree on a load-bearing claim, read the code — don't pick a side.
- **"Icon follows automatically" is a trap.** `ICON_BY_EXT` is keyed by extension, not by `fileKind`. A classification change never updates the icon on its own.
- **Blast radius hides in shared modules.** `fileKind` is imported by both server and client; a client-motivated change silently altered the server's `/api/file` response.
