# How we did it: Planning a continuous-scroll PDF viewer as an OpenSpec change — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator entered **explore mode** (`openspec-explore`) to think through a UX gap:
the dashboard's `PdfPreview` renders **one page at a time** onto a single `<canvas>`
with a Prev/Next toolbar, so reading a multi-page PDF means clicking page by page.
The first prompt was the skill's stock explore preamble — the *real* objective, once
steering clarified it, was: **decide how to give PdfPreview continuous scroll, then
capture that decision as a validated OpenSpec change proposal (no implementation),
complete with a self-contained visual mockup wired into the proposal.** The session
stayed strictly in planning: nothing under `src/` was touched.

## 2. TL;DR playbook

1. **Enter explore mode** with `openspec-explore` — think-only, no code writes.
2. **Ground the problem in the real component:** `grep` for the `PdfPreview` source,
   its callers, and the installed `pdfjs-dist` version before proposing anything.
3. **Present 2–3 concrete options** (A/B/C) with tradeoffs; let the human pick one letter.
4. **Ask the gating questions as a bundle** ("proper viewer? theme? test?") so a
   one-line answer (`1. proper viewer 2. prefer dark 3. test it`) unlocks the whole design.
5. **Scaffold the change** with `openspec new change <name>`, match a recent archived
   proposal's format, then write proposal + design + tasks + spec deltas.
6. **Validate `--strict`** and fix until clean — this is the quality gate for planning.
7. **Build a dependency-free HTML mockup** using the *real* theme tokens; serve it and
   verify in-browser (BEFORE vs AFTER, theme toggle, continuous scroll in DOM).
8. **Wire the mockup into the proposal/tasks** as the visual acceptance target.
9. **Commit surgically** — stage only the change directory, leaving unrelated
   working-tree noise (version bumps, CHANGELOG) untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground before proposing).** The AI found the `PdfPreview`
source, mapped the single-`<canvas>` + `pageNum` architecture, enumerated the four
callers (`PreviewCard`, `DocxPreview`, `PptxPreview`, `EmlPreview`) that reuse it via
`srcUrl`, and confirmed `pdfjs-dist` **4.10.38** already ships the full component
viewer (`PDFViewer`, `EventBus`, `PDFLinkService`, `pdf_viewer.css`). *Why it worked:*
grounding the options in the installed version and the existing contracts meant the
proposal was buildable, not aspirational.

**Phase 2 — Options → decision.** The AI laid out A/B/C with a key insight: **the
public API `PdfPreview({ target, srcUrl })` stays identical**, so no caller needs
touching and the docx/pptx/eml tests (which stub `PdfPreview`) stay green. The human
chose **C** with a single character.

**Phase 3 — Bundle the gating questions.** The AI surfaced three open decisions; the
human answered all three in one line. Those three answers each mapped to a concrete
spec landing (`textLayerMode: 2`, `--bg-canvas` gutter, a bundle-leak test scenario).

**Phase 4 — Capture as an OpenSpec change.** `openspec new change`, format-matched to a
recent archived change, then proposal/design/tasks + two spec deltas, validated
`--strict` clean.

**Phase 5 — Mockup as acceptance harness.** On steering, the AI built a self-contained
`mockup/index.html` (dual BEFORE/AFTER + theme toggle) against **real** dashboard
tokens, served it, and verified in-browser that all 8 stacked pages were in the DOM.
Building against real tokens **surfaced a latent bug**: `--bg-canvas` is referenced by
today's `PdfPreview` but never defined in `index.css`. That became a task.

**Phase 6 — Show & commit.** Opened the mockup on the canvas, then committed **only**
the change directory (7 files) as `docs(openspec):`, leaving pre-existing unrelated
changes alone.

## 4. Prompts that worked

- **The goal prompt (`openspec-explore` preamble).** Effective because it establishes a
  *think-only* stance up front — the AI investigated and produced artifacts but never
  wrote `src/` code. Reproduce by entering explore mode before any planning task.
- **`C`** — a one-character decision after the AI presented A/B/C. High-leverage: a
  well-structured options menu lets the human decide in one keystroke.
- **`1. proper viewer 2. prefer dark 3. test it`** — answered three gating questions in
  one line, unlocking the entire design. The reusable move: *ask the AI to bundle its
  open questions so you can answer them all at once.*
- **`make mockup for test and be part of the proposal`** — short, but it added a whole
  verification artifact and tied it to the proposal. Stronger phrasing to reuse:
  "build a dependency-free HTML mockup using the real theme tokens, verify it
  in-browser, and wire it into the proposal/tasks as the visual acceptance target."
- **`stop and commit`** — a clean stop signal; the AI knew to stage surgically.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Present options and pause | `C` | Structure decisions as an A/B/C menu so one letter moves it |
| Leave design questions implicit | `1. proper viewer 2. prefer dark 3. test it` | Have the AI surface gating questions as a numbered bundle |
| Treat the proposal as text-only | `make mockup for test and be part of the proposal` | State up front that a verifiable mockup is part of the deliverable |
| Risk committing the whole dirty tree | `stop and commit` | Instruct "stage only the change directory" for surgical commits |

The quality bar the operator imposed implicitly: **planning artifacts must validate
`--strict`, and a proposal isn't done until it has a verified visual mockup.**

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved, but the session leaned on and demonstrated a
repeatable pattern worth codifying:

- **`openspec-explore` + `openspec new change`** — the think→capture pipeline. Explore
  mode enforces no-implementation; `new change` scaffolds the artifact tree so the AI
  only has to fill proposal/design/tasks/specs and validate `--strict`.
- **`serve_mockup` + `browser` verification** — turning a design into a self-contained
  `mockup/index.html` and verifying it in-browser (DOM assertions: "all 8 pages
  present") makes the proposal's visual claim testable, and doubles as a manual harness.
- **Recommended skill to create:** *"OpenSpec change with a verified mockup"* — grounds
  a UI change in the real component + tokens, scaffolds the change, builds a
  token-accurate HTML mockup, verifies it in-browser, wires it into the proposal, and
  commits surgically. This session is the template.

## 7. Pitfalls & dead ends

- **Missing theme token.** `--bg-canvas` is referenced by `PdfPreview` but **undefined**
  in `index.css`. If you build a mockup with fake colors you'd never notice — using the
  *real* tokens surfaced it. Always mock against the actual token set.
- **serve_mockup vs browser.** The AI initially reached for screenshots, then switched
  to the `browser` tool to assert the DOM directly (headings e5–e12 present). If a
  screenshot is ambiguous, verify structure via the browser instead.
- **Dirty working tree.** The tree had unrelated pre-existing changes (version bumps,
  CHANGELOG). Committing everything would have been wrong — stage only the change dir.
- **Explore-mode discipline.** It's tempting to "just implement it." Don't — explore
  mode is planning; exit and run the apply flow when ready to build.
