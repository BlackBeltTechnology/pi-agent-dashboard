# How we did it: making bare `openspec` resolve in dashboard sessions — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) as a thinking partner, with
no concrete target beyond the operator's suspicion that the dashboard's OpenSpec **Apply**
button misbehaves when the `openspec` CLI isn't installed. The first steering turn pinned
it down: *"The apply defined the openspec itself. It calls a skill which may define to run
with cli."*

The **real objective**, once the steering clarified it: the generated `openspec-*` skills
call bare `openspec`, and on a machine with no global install / no local dep / no worktree,
that command doesn't resolve — so the agent silently invents a lossy "hand-edit the
artifacts directly" fallback. Fix it **properly**, without editing files that
`openspec init --force` regenerates, and ideally version openspec from **one** source
instead of the 4–5 that are in play. The deliverable was **two committed OpenSpec change
proposals** — planning only, no implementation.

## 2. TL;DR playbook

1. **Explore first, don't build.** Enter `openspec-explore` and *ground the claim on disk*
   before theorizing — run `which openspec`, `node_modules/.bin/openspec --version`, and
   check `package.json` for a declared dep. (Here: user-level 1.6.0 vs local 1.4.1 — the
   CLI *did* resolve in this session, proving the bug is environmental.)
2. **Trace the button to its command.** `rg` for the Apply wiring
   (`SessionOpenSpecActions.tsx` → `onSendPrompt('/skill:openspec-apply-change …')`) and
   read the skill frontmatter (`allowed-tools: Bash(openspec:*)`, `Requires openspec CLI`).
   Confirm the skill has **no sanctioned fallback** — the hand-edit path is hallucinated.
3. **Enumerate the edit surfaces and kill the dead ends explicitly.** Editing `SKILL.md` →
   regenerated by `openspec init --force`. Injecting PATH at spawn → Apply reuses a **live**
   session, nothing is spawned. Write these down so the design can't relapse into them.
4. **Find the one live lever.** Read the pi bash tool source: `getShellEnv()` reads
   **live** `process.env` per command (`shell.js:103`), so a `process.env.PATH` prepend at
   bridge init propagates to every later Bash child. That's the mechanism.
5. **Scaffold with the CLI, not by hand:** `openspec new change <name>`, then write
   `proposal.md` / `specs/**/spec.md` / `design.md` / `tasks.md`; `openspec validate <name>
   --strict` after every artifact edit.
6. **Run `plan-proposal`**: doubt-review (cross-model, auto when `@propose-review-1` is
   configured) → **verify every load-bearing reviewer claim against source** → scenario-design
   (hard gate) → fold the manifest into `tasks.md` → commit at the worktree boundary.
7. **Treat each doubt-cycle kill as the deliverable.** The plan changed twice under review;
   the value was in the two invalidated mechanisms, not the first draft.
8. **Commit only your change dir** (`git add openspec/changes/<name>/`); leave shared files
   (`groups.json`, doctor hashes) that belong to other sessions untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI resisted the urge to theorize and instead
probed the box: `which openspec` showed a user-level 1.6.0 bin and a local 1.4.1 dep, so
the CLI resolved *here* — proving the reported failure was **environmental**, from a leaner
machine. Decision point: the operator corrected the AI's first worktree theory
("There is no worktree, it is on a branch"), which reframed the fix from "PATH into a
worktree" to "the dashboard manages sessions in **arbitrary** repos where openspec is not a
local dep and no global install exists."

**Phase 2 — Root-cause trace.** `rg` walked Apply button → `/skill:openspec-apply-change`
→ bare `openspec` in every step. The AI drew the causal chain: skill requires CLI on PATH →
absent → agent improvises the off-spec hand-edit. The operator then closed two escape
hatches: *"openspec skills are generated, openspec will overwrite them"* (kills SKILL.md
edits) and the AI itself verified Apply does `onSendPrompt` into a **live** session (kills
spawn-time PATH injection).

**Phase 3 — Find the sanctioned lever.** With both obvious surfaces dead, the AI read the
pi bash tool internals directly (`bash.js`, `shell.js`) rather than guessing, and found
`getShellEnv()` reads **live** `process.env` per command — so a bridge-init PATH prepend is
the *sole* in-extension mechanism. It also confirmed `user_bash` fires only for interactive
`!` bash, **not** the LLM Bash tool, so that alternative doesn't cover the skill path.

**Phase 4 — Draft + adversarial review (two kills).** Exited explore; scaffolded
`gate-openspec-apply-on-cli-presence` and ran `plan-proposal`. **Doubt cycle 1** (cross-model
glm-5.2, a different architecture family) *killed the design*: the server already bundles
the CLI so a server-availability signal is always-true and never gates; and `npx -y` warm-up
doesn't make bare `openspec` resolvable. The AI **verified all three reviewer claims against
source** before accepting them — the discipline that made the kill trustworthy. Redesign B
(bridge PATH shim) survived **cycle 2** as *mechanism-sound* but got hardened: extensionless
shim (Git Bash ignores PATHEXT), absolute `process.execPath`, resolve via `package.json`,
atomic re-point, fail-soft.

**Phase 5 — Single-source amendment (cycle 3).** The operator asked the pivotal architectural
question: *"is it possible that openspec be versioned in one place which is used everywhere
else?"* The AI found 4–5 declared version sources and proposed an npm `overrides` — which the
cross-model review caught as **wrong** (the root package.json is *published* with
`--include-workspace-root`, so the override would leak onto downstream installers, and it's
redundant since npm already hoists compatible caret ranges to one copy). The folded design
became *simpler*: consistent `^1.6.0` ranges + one-time `init --tools pi --force` commit +
`verify-release-deps.mjs` floor-consistency guard wired into CI.

**Phase 6 — Commit at the boundary.** Validated strict, folded 10 automated scenarios 1:1
into `tasks.md`, committed **only** the change dir, and stopped at the worktree boundary —
correctly diagnosing that a residual `groups.json` diff was a shared file mixing several
other sessions' entries and must be left alone.

## 4. Prompts that worked

- **Goal prompt (explore mode).** Effective because it set a *thinking, not implementing*
  stance up front — the AI grounded on disk instead of jumping to a fix. The strongest
  version of this ask states the symptom AND the machine where it happens:
  *"On a box with no global openspec and no local dep, the Apply button falls back to
  hand-editing artifacts. Explore why and where the real fix must live — don't implement."*
- **High-leverage steering — "Fix it properly."** Four words that rejected the tempting
  shallow fix (edit the skill) and forced the AI to honor the regeneration constraint.
- **High-leverage architectural nudge — "is it possible that openspec be versioned in one
  place?"** This one question converted a 5th version pin into a single-source design and
  exposed the whole version-proliferation problem. Ask the *"can we drive this from one
  source"* question whenever you notice a value declared in ≥3 places.
- **Weak prompt to avoid:** the bare `"a"` (an accidental keystroke) and `"commit"` with no
  scope. Prefer `"commit only the change dir; leave shared files for their owning sessions."`

## 6. Skills, tools & memory created — and why they're effective

- **Project memory (insight): openspec CLI resolution asymmetry.** Captures the durable,
  non-obvious fact that the `openspec-*` skills are **generated** (regenerated by
  `npx @fission-ai/openspec init --force`) and call bare `openspec` — so editing them is
  futile, and any fix must be external and regen-proof. *Effective* because it stops a future
  agent from re-attempting the dead-end SKILL.md edit and re-deriving the whole trace.
  *Invoke it* whenever an openspec skill misbehaves or you're tempted to patch a generated
  file. (Note: the project memory store was at capacity, so the same insight is also carried
  in the committed `design.md` Context section as the durable home.)
- **`plan-proposal` orchestration (used, not created).** The value it added: doubt-review →
  scenario-design (hard gate) → manifest fold → commit-at-boundary, run in the main session.
  Reuse it verbatim for any planning-phase change on `develop`.
- **Cross-model doubt-review (`@propose-review-1` = glm-5.2).** A *different architecture
  family* reviewer produced two code-grounded kills a same-family reviewer would likely miss.
  Configure a cross-architecture `@propose-review-N` role so kills come cheap and early.
- **Recommended skill to create:** a small "resolve-bare-CLI-in-pi-session" playbook —
  the `getShellEnv()`-reads-live-`process.env` fact + the extensionless/`process.execPath`
  shim recipe are reusable for *any* bare-command-not-on-PATH problem in the bridge.

## 7. Pitfalls & dead ends

- **Editing `SKILL.md` is futile** — `openspec init --force` regenerates it. If you hit a
  bug in a generated skill, fix outside it.
- **Spawn-time PATH injection does nothing for Apply** — it does `onSendPrompt` into a
  **live** session; no child is spawned to inherit env.
- **`npx -y @fission-ai/openspec` warm-up ≠ resolvable bare `openspec`** — it populates the
  npx cache, not a PATH-resolvable name.
- **`user_bash` doesn't cover the tool path** — it fires only for interactive `!`/`!!` bash
  in the TUI, not the LLM Bash tool that runs the skill's `openspec`.
- **An npm `overrides` for the version leaks** — the root package.json is published with
  `--include-workspace-root`, so the override forces the pin onto downstream installers; and
  it's redundant since npm hoists compatible caret ranges to one copy. Use consistent `^`
  ranges + a floor-consistency guard instead.
- **Multi-edit `oldText2/newText2` keys are invalid schema** — only the first edit applied
  twice in this session. Use one edit per call or the proper multi-edit array.
- **Don't stage `groups.json`** — it's a shared file whose hunk mixes several sessions'
  change registrations; you can't cleanly stage only your line. Leave it to its owners.
