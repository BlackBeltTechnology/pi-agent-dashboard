# How we did it: Fixing the subagent timeline that freezes at 3 steps — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) with a symptom, not a fix:
an in-memory Agent-tool subagent's live timeline in the dashboard "freezes after ~3
steps," and its later output — including a large final result — never renders. The
operator's *real* objective, which the steering turns clarified, was: **find the true
root cause (not the obvious `.slice(-3)` guess), design a truncation strategy that keeps
the subagent's opening AND final steps visible, prove it with real measurements, and
capture the whole thing as a validated OpenSpec change** — all without writing
implementation code (explore mode forbids it). The session ended at the git-worktree
boundary with a committed, `--strict`-clean planning artifact set.

## 2. TL;DR playbook

1. Enter `openspec-explore` with the raw symptom. Tell the AI to **consult the doc tree
   first, then delegate the deep trace to an `Explore` subagent** rather than
   pattern-matching the first `.slice()` it finds.
2. When the AI proposes a root cause, make it **verify the claim directly** (grep/read the
   exact lines) before accepting it. The real cause here was a **20 KB per-event
   serialized-size guard** (`memory-event-store.ts` `createTruncator`) that nukes the
   *whole* payload to `{__truncated:true}`, not a hardcoded "3".
3. Steer with **short, sharp diagnostic questions** ("when it clipped, it clipped the
   response, isn't it?", "can the 20k be 10kb head + 10kb tail?"). These force the AI to
   distinguish *dashboard copy* vs *real parent handoff*, and *byte-split* vs
   *structure-aware split*.
4. Lock the design with a one-token unlock: **"A + B"** (cap big string fields head+tail
   AND reduce the `entries[]` array head+tail). Then **"tune the design"** to make it
   tail-weighted (you already see the head; the tail is the payoff).
5. Say **"measure"** — force real numbers from the SQLite DB (`~/.pi/dashboard/dashboard.db`)
   instead of estimates. The measurement revealed `args.prompt` + `details.description`
   live *outside* `entries[]` and starve the budget → design changed to cap them and
   derive the budget dynamically.
6. Capture as an OpenSpec change (proposal · design · spec delta · tasks), matching an
   existing recent change's format. Run `openspec validate <name> --strict` after every
   edit.
7. Run `plan-proposal` → `doubt-driven-review`: spawn **fresh-context + cross-model**
   reviewers in parallel. Reconcile every actionable finding; loop until a cycle finds no
   new *design* hole. Then `scenario-design` → fold the manifest into `tasks.md`.
8. Commit only your change artifacts to `develop` and **stop at the worktree boundary**.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (don't trust the obvious guess).** The AI first grepped for
`slice(-3)` and found `flow-reducer.ts:245` — a plausible but *wrong* lead. It caught
itself: the flow-card 3-line cap keeps full history in `detailHistory`, so it couldn't
explain a lost *final result*. It delegated an `Explore` subagent to independently trace
the in-memory subagent path. The subagent found the real cause: the 20 KB size guard.
*Why it worked:* the human's implicit bar ("the true root cause") plus subagent
delegation stopped a confident-but-wrong fix from shipping.

**Phase 2 — Diagnostic Q&A (the human's questions drove the design).** Three tight
steering questions in a row forced precision: (a) "it clips the *response*, isn't it?"
→ the AI proved only the *dashboard's copy* is clipped; the real parent handoff is
in-process and untouched. (b) "can it be 10kb head + 10kb tail?" → the AI distinguished a
*byte-split of serialized JSON* (produces invalid JSON, useless) from a *structure-aware
head+tail* (the useful version). (c) "A + B" → locked both fixes at once.

**Phase 3 — Tune (reframe: lost tail, not lost middle).** On "tune the design," the AI
reframed: you already SEE the head today; what you MISS is the end. So a symmetric split
wastes budget re-showing the head. It moved to **tail-weighted** (head=1, tail=4) with a
**final-entry guarantee** (~6 KB reserved, dropped last).

**Phase 4 — Measure (numbers overturned the constants).** On "measure," the AI queried the
real SQLite event store, found no persisted Agent runs, and reconstructed the envelope
from a real `tool_execution_update` row. Key finding: `args.prompt` (the task, echoed on
every update) and `details.description` live **outside** `entries[]`, so a big prompt
alone eats the whole ceiling (16 KB prompt → 81 B budget). Fix: cap those strings too and
**derive** the budget dynamically instead of fixed constants.

**Phase 5 — Doubt-review (adversarial cycles found real holes).** `plan-proposal` ran
`doubt-driven-review` with fresh-context + cross-model (glm-5.2) reviewers in parallel.
Cycle 1 found a char-vs-byte OOM under-count and a per-field-vs-per-entry FINAL bug.
Cycle 2 found the revision's own new blocker: the byte-gate's `JSON.stringify(reduced)`
would allocate a multi-MB base64 image — the exact OOM the guard exists to prevent. Cycle
3 found no new design hole → stop. Then `scenario-design` produced a 20-automated + 1-manual
manifest, folded 1:1 into `tasks.md`, `--strict` clean, committed to `develop`.

## 4. Prompts that worked

- **Goal kickoff (explore mode):** launching via `openspec-explore` with only the symptom
  was effective *because* explore mode blocks implementation — it forced root-cause work
  and artifact capture instead of a premature code edit.
- **"When it clipped, it clipped the response. Isn't it?"** — a leading yes/no that forced
  the AI to separate *dashboard copy* from *real handoff*. High leverage: one sentence,
  large clarification.
- **"Is it possible the 20k trimming be 10kb from begin and 10kb from end?"** — proposed a
  concrete mechanism; the AI had to test it and surface the invalid-JSON landmine.
- **"A + B"** — a two-token unlock that accepted both design branches at once.
- **"tune the design" / "measure"** — single-word steers that unlocked the tail-weighted
  reframe and the measurement pass. *Rewrite for next time:* be explicit —
  "measure the real per-event envelope overhead from the SQLite store before fixing the
  budget constants" — to save the AI a discovery hop.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session — it was pure planning. But it is a
textbook run of three existing skills chained:

- **`openspec-explore`** — the stance that prevented a premature code edit and kept the
  work in root-cause + artifact-capture mode. Invoke it whenever you have a symptom and
  don't yet trust the obvious fix.
- **`plan-proposal`** — orchestrated `doubt-driven-review` (fresh-context + cross-model)
  and `scenario-design` → manifest fold, then stopped at the worktree boundary. Invoke it
  to turn a drafted proposal/design into a validated, test-planned, committed change.
- **`Explore` subagent delegation** — used 7×. The single most valuable move was letting a
  fresh-context subagent trace the root cause independently; it beat the parent's first
  guess. *Recommended skill to create:* a short "verify-root-cause-before-fix" memory that
  captures the 20 KB `createTruncator` guard as the real cause of subagent-timeline
  freezes, so the next occurrence skips the flow-reducer red herring.

## 7. Pitfalls & dead ends

- **`.slice(-3)` red herring:** `flow-reducer.ts:245` looks like the cause but keeps full
  history in `detailHistory`. If you see a lost *final result*, it is NOT the flow-card
  3-line cap — look at `memory-event-store.ts` `createTruncator`.
- **`rg` output mangling:** the AI noted `rg` substrings were being replaced mid-session;
  it fell back to `grep`/Read. If ripgrep output looks corrupted, switch tools.
- **`openspec change new` is not a subcommand here** — follow the artifact conventions by
  hand, matching a recent change's format (`ls`/`cat` a sibling under `openspec/changes/`).
- **Literal byte-split of serialized JSON = invalid JSON** → the client reducer reads it as
  "no update" and you lose the timeline anyway. Always split *structure-aware*.
- **base64 images inside `entries[]`:** a byte-gate that calls `JSON.stringify(reduced)`
  will allocate the multi-MB image — re-introducing the OOM inside the guard. Cap
  image `.data` before any full re-serialization.
- **`args.prompt` / `details.description` live outside `entries[]`:** a big prompt alone
  starves the timeline budget. Cap them and derive the budget dynamically.
- **Stray `groups.json` diff:** it belonged to an unrelated change — the AI correctly left
  it out of the commit. Check `git status --short` before staging.
