## 1. Goal (the ask)

The session opened in **explore mode** (`/skill:openspec-explore`), a thinking-only
stance — no code, no implementation. The real objective, which crystallized over the
first two turns: *diagnose why opening a `.md` file in the dashboard preview shows a
broken-image glyph for embedded local images, then capture the fix as a fully-planned
OpenSpec change* — proposal, design, delta spec, tasks, and a test-plan manifest —
committed on `develop` and stopped cleanly at the git-worktree boundary (planning
only, no build).

First prompt (verbatim intent): *"Enter explore mode. Think deeply… investigate the
codebase… you may create OpenSpec artifacts."* The subsequent one-word prompts
(`propose`, then the `openspec-ff-change` and `plan-proposal` skills, then `commit`)
walked that exploration all the way to a committed, review-hardened plan.

## 2. TL;DR playbook

1. **Explore first, don't touch code.** `/skill:openspec-explore` → trace the broken
   surface end-to-end before proposing anything. Use `kb_search` + `kb_get` on the
   directory `AGENTS.md` tree, not raw `grep`.
2. **Find the fork.** Confirm there are *two* markdown-image pipelines (chat inliner
   vs. file-preview) and only one inlines local images. Name the exact broken file.
3. **Check the endpoint before designing.** Read `/api/file/raw` path-scoping
   (`artifact-roots.ts`, `isAllowed`) to prove the clean client-only fix is viable
   with **zero server change**.
4. **Say `propose`.** Scaffold via `openspec change new <kebab-name>`; write
   `proposal.md` (Why / What / Caps / Impact + `## Discipline Skills`).
5. **Fast-forward the artifacts.** `/skill:openspec-ff-change` → delta spec, design,
   tasks in one pass; `openspec validate` until clean.
6. **Run `/skill:plan-proposal` in the main session.** It gates author-created
   `proposal.md`/`design.md` through **doubt-driven-review** (cross-model, auto if a
   `@propose-review-1` role from a different family is configured).
7. **Reconcile every finding against source** — open the files, don't rubber-stamp.
   Fold valid HIGH/MEDIUM findings; run a bounded 2nd cycle only if findings were
   material; STOP when a 3rd cycle would return trivia.
8. **Generate the test-plan manifest** via scenario-design, then **fold** every row
   1:1 into `tasks.md` (vanilla checkboxes + Triple + `(test-plan #id)`).
9. **`commit`** to `develop`, stop at the worktree boundary. Hand off to `ship-it`
   only when told.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / root-cause (explore mode).** The AI traced the whole
render path with `kb_search`/`kb_get` and targeted `rg`, and produced an ASCII
two-pipeline diagram: *Surface 1* (chat) inlines local images via the bridge
`markdown-image-inliner.ts` (`pi-asset:<hash>` → `PiAssetImg` → base64); *Surface 2*
(`.md` file preview) fetches text and hands it to `MarkdownContent` **with no base
path**, so relative `src` 404s against the dashboard origin. *Why it worked:* it
located the *definitive* broken component (`MarkdownPreview.tsx`) and confirmed the
already-hardened `/api/file/raw` endpoint would serve sibling images — turning a
vague bug into a one-prop client fix.

**Phase 2 — Propose (`propose`).** Scaffolded the change, wrote `proposal.md`
capturing **Option A** (thread `imageBase={cwd,dir}` into `MarkdownContent`;
`PiAssetImg` rewrites relative + local-absolute srcs → `/api/file/raw`; chat stays on
the inliner; zero server change). It flagged three open forks (out-of-cwd behavior,
URL-encoding, SVG mime) and *stopped* rather than auto-advancing — honoring the
explore stance.

**Phase 3 — Fast-forward artifacts (`openspec-ff-change`).** Wrote the delta spec,
design, and tasks; added the `## Discipline Skills` line
(`security-hardening`, `review-code`); validated clean.

**Phase 4 — Doubt-driven-review (`plan-proposal`).** Because it authored
`proposal.md`+`design.md` this session, it ran cross-model review automatically on
`@propose-review-1` (`glm-5.2`, different family from the Claude author). **Cycle 1**
caught mis-named surfaces (the real modal is `FilePreviewOverlay.tsx:246`, editor pane
`MarkdownViewer.tsx:164`; `MarkdownPreviewView.tsx` has *no* cwd/path prop), a leaky
scheme *denylist*, the `node:path`-in-browser convention violation, and the
context-vs-closure delivery question — each **verified against source**, then folded.
**Cycle 2** caught the big one: an unconditional `onError→placeholder` would flip
chat 404s to the placeholder and drop the pinned lightbox tests — a **chat
regression**. Scoped the placeholder to the rewritten path only. STOP condition met.

**Phase 5 — Scenario-design + fold.** Generated a 16-scenario `test-plan.md`
manifest (15 automated L1 + 1 manual-only), then folded every row 1:1 into `tasks.md`
with a fold-completeness gate (15↔15, 1↔1).

**Phase 6 — Commit + boundary stop (`commit`).** Two commits on `develop`
(`3e06cc3ca` artifacts, `e8eec9ce9` `groups.json` sync), working tree clean, stopped
at the worktree boundary and offered the `ship-it` hand-off.

## 4. Prompts that worked

- **The goal prompt** — `/skill:openspec-explore` with *"Think deeply… investigate…
  you may create OpenSpec artifacts."* Effective because it set a **thinking-only
  stance** that forced full root-cause tracing before any design, while explicitly
  authorizing artifact capture so the exploration wasn't wasted.
- **`propose`** (high-leverage, one word) — cashed the completed diagnosis into a
  scaffolded proposal at exactly the right moment.
- **Loading `openspec-ff-change`** — unlocked all remaining artifacts in one pass
  instead of stepping through each.
- **Loading `plan-proposal`** — the highest-leverage move: it *auto-triggered* the
  cross-model doubt-review that caught the chat-regression, the mis-named surfaces,
  and the browser-path violation. Without it the plan would have shipped three latent
  defects.
- **`commit`** — clean close; the AI knew to stop at the worktree boundary.

*Stronger kickoff for next time:* name the suspected surface and the endpoint up
front — *"Explore why `.md` preview shows broken images; I think `MarkdownPreview`
never passes a base dir and `/api/file/raw` could serve the bytes — confirm and
propose an OpenSpec change, client-only if possible."* — to shortcut Phase 1.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stay in pure-explore and stop after diagnosis | `propose` | Say "explore then propose" up front so the transition is expected |
| Draft with plausible-but-wrong surface names (`MarkdownPreviewView` "passes imageBase") | Loading `plan-proposal` → cross-model doubt-review found `FilePreviewOverlay.tsx:246` / `MarkdownViewer.tsx:164` are the real render sites | Always run doubt-driven-review on self-authored proposal+design; verify surface names against source before writing scenarios |
| Reach for a scheme **denylist** and `node:path` in client code | Cross-model review flagged both | State repo conventions early: browser-safe POSIX string ops only (no `node:path`); guard by scheme-*absence* not a blocklist |
| Consider an unconditional `onError` placeholder | Cycle-2 review: it would regress chat 404s + drop pinned lightbox tests | Scope error/placeholder behavior to the **rewritten** path only; leave the shared verbatim fall-through untouched |

The controlling quality bar the human imposed: **don't rubber-stamp review
findings — open the files and reconcile each against the actual code**, and run a
bounded second cycle only when findings are material.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — the session was a clean composition of existing
ones: `openspec-explore` → `openspec-ff-change` → `plan-proposal` (which internally
chains `doubt-driven-review` + `scenario-design`). The reusable lesson worth pinning:

- **`plan-proposal` is the guardrail that pays for itself.** Its automatic
  cross-model doubt-review (via a `@propose-review-1` role in a *different model
  family*) caught a chat-regression and three wrong surface names that a same-model
  self-review would have missed. Configure that reviewer role once; every planning
  session inherits the safety net.

## 7. Pitfalls & dead ends

- **`openspec change new` vs `openspec new change`** — the session hedged both
  orderings. Use `openspec change new <kebab-name> --json`.
- **Validation "fails" right after the proposal** — expected: the delta spec + tasks
  aren't written yet. Not a real failure; write the next artifacts and re-validate.
- **`groups.json` shows unrelated churn** — the scaffold *also* folds in other
  already-active changes and reorders groups. Only your `+<change>` line under
  `__ungrouped__` is yours; commit the whole machine-generated file with a
  transparent message.
- **Self-review blind spots** — the AI confidently named the wrong render surfaces.
  Don't trust surface/prop claims in a proposal until a *cross-family* reviewer +
  source read confirm them.
