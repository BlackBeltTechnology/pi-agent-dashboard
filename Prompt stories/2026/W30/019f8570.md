# How we did it: Fix a flaky CI test-harness race in the goal-supervisor — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator pasted a single link and one line:

> "Check the reason of failure and fix it: https://github.com/BlackBeltTechnology/pi-agent-dashboard/actions/runs/29830414007"

The real objective, once the work played out: **diagnose a red CI run, decide whether
it is a genuine product bug or a flaky test, and land the smallest correct fix.** The
failure turned out to be an `AssertionError: expected 'resume' to be 'fresh'` at
`goal-supervisor.test.ts:233` — the *poison: K consecutive no-progress resume-deaths →
fresh spawn re-primed* test. The actual fault was a **test-harness timing race**, not a
product defect, so the fix had to make the test deterministic without changing behavior.

## 2. TL;DR playbook

1. Read the failing run: `gh run view <id> --repo <owner/repo>` then re-view with
   `--log-failed | grep -iE "FAIL|AssertionError|expected|<testname>|Tests "` to pin the
   exact assertion and line.
2. **Reproduce locally first.** Run just the failing file: `npx vitest run <path>`. If it
   passes locally, suspect a **flaky race**, not a product bug.
3. Amplify the flake: run under a clean `HOME=$(mktemp -d)` and loop it 5× to see if fs
   I/O timing makes it intermittently fail.
4. Read the supervisor + test harness to find the async dispatch. Here: `performSpawn`
   was fire-and-forget (`void withGoalLock(...)`) and the test waited a fixed `10ms` for
   real fs I/O to settle — the race.
5. Make the settle **deterministic**: have the timer callback *return* its promise
   (harmless for real `setTimeout`, which ignores return values) and have the test fake
   `await t.fn()` instead of sleeping a fixed time.
6. Verify: run the file repeatedly until green consistently, then run the whole related
   suite (all goal test files).
7. Confirm typecheck/lint findings are **pre-existing** (stash → biome → pop) so you only
   own the lines you touched.
8. Commit exactly the two changed files with a scoped message.

## 3. How the collaboration unfolded

**Phase 1 — Triage the red run.** The AI pulled the run with `gh run view`, then narrowed
with `--log-failed` piped through `grep` to extract just the assertion, file, and line. It
did *not* start editing — it first identified the exact failing test.

**Phase 2 — Reproduce and classify.** It ran the single test file locally; it **passed**.
That single fact reframed the whole task: "This looks like a flaky test in CI." It then
amplified the flake with `HOME=$(mktemp -d)` and a 5× loop to expose the fs-I/O timing
dependency. Deciding *flaky vs. real* early is the pivotal decision point.

**Phase 3 — Root-cause the race.** It grepped the supervisor for the poison/breaker
logic and the timer plumbing (`setTimer`, `withGoalLock`, `timers.set/get/delete`), and
found the mechanism: the backoff timer callback dispatched `performSpawn` as
fire-and-forget, and the test's `runTimers()` only waited a fixed `10ms` for that async
chain (real goal-store fs writes) to settle. On a loaded CI runner the third
`performSpawn` hadn't pushed its spawn within 10ms, so `spawns.at(-1)` still read the
prior `resume` spawn instead of the new `fresh` one.

**Phase 4 — Deterministic fix.** Two surgical edits: (1) the timer callback now *returns*
the `withGoalLock(...)` promise instead of `void`-ing it and the `setTimer` dep type
widened to `() => void | Promise<void>`; (2) the test's `runTimers()` now `await t.fn()`
to await the real `performSpawn` rather than racing a fixed sleep. Bonus: tests run
faster (no 10ms sleeps).

**Phase 5 — Verify & scope-check.** It ran the file repeatedly (13 pass consistently),
then all 7 goal test files (80 tests) green. It checked tsc/biome and — crucially — used a
stash/pop dance to prove the remaining biome findings (`vi` unused at line 23, import
ordering) were **pre-existing** and on lines it never touched, and that CI's Biome gate
had already passed on the failing run. Then a single scoped commit of just the two files.

**Phase 6 — Land it.** The operator's only steering was one word: "commit". The AI
committed the two files as `d61212864` on `develop`.

## 4. Prompts that worked

- **The goal prompt** ("Check the reason of failure and fix it: <run URL>") was effective

  AI could go straight to `gh run view` with no back-and-forth. A stronger version would

  its own verification.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session — it was a fast (5-minute), self-contained
bugfix. But the workflow is repeatable and worth codifying. **Recommended skill:
"diagnose-flaky-ci-test"** capturing the loop: `gh run view --log-failed` → reproduce the
single file locally → if green, amplify with `HOME=$(mktemp -d)` + a 5× loop → find the
async fire-and-forget dispatch → replace fixed-sleep settling with an awaited promise →
verify with repeat runs + full suite → stash/pop scope-check → scoped commit. That last
"deterministic settle over fixed sleep" pattern is the reusable insight most flaky-timer
fixes need.

## 7. Pitfalls & dead ends

- **Don't trust a single local run to clear a CI failure.** It passed locally here — that
  was the *clue*, not the resolution. If local passes but CI fails, amplify timing with a
  clean `HOME` and a loop before concluding.
- **Fixed-sleep settling in async tests is the flake.** `void asyncThing(); wait(10ms)`
  races real fs I/O on loaded runners. Return the promise and `await` it instead.
- **One command failed** — `git stash && npx biome check …` hit a stale `.git/index.lock`.
  Recovery: `rm -f .git/index.lock && git stash list`, then continue. Don't panic-abort a
  scope-check over a lock file.
- **Widening a callback's return type is safe for real `setTimeout`** — it ignores return
  values — so `() => void | Promise<void>` breaks nothing in production while letting the
  fake timer await it.
