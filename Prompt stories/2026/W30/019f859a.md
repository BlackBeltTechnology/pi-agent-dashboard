## 1. Goal (the ask)

The opening prompt was a triage request:

> *"Check the https://github.com/BlackBeltTechnology/pi-agent-dashboard/issues/383 and reply in detail for that issue. Check the new 0.6.1 release resolves that and reply in details."*

The literal ask was "answer issue #383 and say whether v0.6.1 fixed it." But the
*real* objective — which surfaced the moment the user typed `Enter explore mode` —
was much larger: **turn a vague bug report about 35 leaked embedded sessions into a
fully-planned, doubt-reviewed, scenario-folded OpenSpec change ready for the worktree
boundary.** The issue was the seed; the deliverable was an apply-ready planning bundle
(`proposal.md` + `design.md` + `spec.md` + `tasks.md` + `test-plan.md`) for
`add-embed-session-lifecycle`.

## 2. TL;DR playbook

1. **Triage against reality first.** `gh issue view 383` + `gh release view v0.6.1` +
   `CHANGELOG` — establish chronology (issue filed 15h *after* the release) and prove
   v0.6.1 is release-plumbing only. Post a grounded reply; don't speculate.
2. **Enter explore mode before designing.** Ground in the actual lifecycle machinery
   (`idle-timer.ts`, `headless-pid-registry.ts`, `lastActivityAt`, `killBySessionId`,
   `SessionStatus`, `SessionSource`) — confirm the primitives exist and only the *loop*
   is missing.
3. **Map the "busy" predicate to real state** in one multi-file gather pass. Split
   signals into SOFT (event-derived) vs HARD (in-server truth) trust classes — that
   split decides whether the reaper is safe.
4. **Verify inferences against the pinned pi source** (`0.80.10`), not grep noise. Read
   the `.js.map` original TS to confirm resume/replay is lossless for settled turns and
   loses only the ephemeral steering/followUp queue.
5. **Pin introduction-versions from pi's CHANGELOG** before deciding a version floor —
   this reversed an earlier wrong "needs a piVersion fallback" claim (`agent-settled.ts`
   already normalizes it).
6. **Draft the proposal** in the house format (Why / What Changes / Capabilities /
   Impact / Discipline Skills); lock scope decisions with `ask_user` *before* writing.
7. **Fast-forward the artifacts** (`openspec-ff-change`): design → spec delta → tasks,
   each `openspec validate`-green.
8. **Run `plan-proposal`:** two cross-model doubt-review cycles → `scenario-design`
   manifest (32 automated scenarios) → fold 1:1 into vanilla task checkboxes → commit to
   `develop` and **STOP at the worktree boundary**.
9. **Keep unrelated changes out of the commit.** Scope `git add` to explicit paths.

## 3. How the collaboration unfolded

**Phase 1 — Triage (grounded, not speculative).** The AI pulled the issue, the release,
and the CHANGELOG, then led with chronology: v0.6.1 published `2026-07-20 21:10 UTC`,
issue #383 filed `2026-07-21 11:49 UTC`. It confirmed `visitorId`/`useEmbedMode` don't
even exist in current source (the report was against a v0.5.4 fork) before posting.
*Why it worked:* every claim in the reply traced to a command output — no hand-waving.

**Phase 2 — Explore (find the loop that's missing).** On `Enter explore mode` the AI
resisted implementing and instead mapped the machinery: `idle-timer.ts` is a
*whole-server* auto-shutdown, not a per-session reaper; `add-chat-gateway` spawns but
never reaps; `lastActivityAt` + `killBySessionId` + `status` + `source` all exist. The
reframe — *"every primitive is in the tree, only the loop isn't"* — is the pivot the
whole design hangs on. The human's `The "busy" predicate` steer forced the highest-risk
sub-question: what makes a reap safe?

**Phase 3 — Verify against pinned source.** Rather than trust grep, the AI located the
installed pi `0.80.10`, read the `agent-session-runtime` `.js.map` original TS, and
confirmed resume rebuilds state **only from the JSONL transcript** — the
steering/followUp queue rides an ephemeral `queue_update` event and dies with the
process. The `Check with 0.80.10` and `increasing pi minimum version?` steers pushed it
to pin every mechanism's introduction version from pi's CHANGELOG, which *reversed* an
earlier wrong claim about needing a version fallback.

**Phase 4 — Draft + fast-forward.** With three scope decisions locked via `ask_user`
(**full issue · off by default · shared cross-front provenance**), the AI drafted the
proposal, then fast-forwarded design → spec delta → tasks, fixing a validator quirk
(a requirement's *first line* must lead with SHALL/MUST).

**Phase 5 — Plan-proposal (the quality gate).** Two cross-model doubt-review cycles
(`@propose-review-1` = `zai/glm-5.2`, non-Claude) produced 19 findings — all reconciled
and fixed (phantom-gear force-reaping an `ask_user`-blocked session; `agent_settled` not
captured server-side; coalesced-acquire fan-out). Then `scenario-design` produced a
32-scenario manifest, folded 1:1 into vanilla task checkboxes, committed to `develop`
(`854c16daf`), and stopped at the worktree boundary.

**Phase 6 — Unrelated `commit`.** The final `commit` steer referred to a *different*
uncommitted change (`compact-folder-header-actions`). The AI ran its tests first
(12/12 green), scoped `git add` to explicit paths so a third concurrent change
(`event-reducer`) wasn't swept in, and committed cleanly after a transient
`.git/index.lock` retry.

## 4. Prompts that worked

- **The goal prompt** (*"Check issue #383 … Check the new 0.6.1 release resolves that"*)
  was effective because it named a concrete artifact (a GitHub issue) and a concrete
  claim to test (does v0.6.1 fix it). A stronger version states the deliverable up front:
  *"Triage #383 against v0.6.1, then if unresolved, explore + draft an OpenSpec change to
  fix it."*
- **`Enter explore mode`** — the single highest-leverage move. It switched the AI from
  answer-mode to thinking-partner mode and unlocked the whole design.
- **`The "busy" predicate`** — a 3-word steer that redirected the AI onto the one
  sub-question (reap safety) that governs the entire design's conservatism.
- **`Check with 0.80.10`** and **`increasing pi minimum version?`** — forced
  verification against pinned source over inference, and caught a reversed conclusion.
- **`draft proposal` → `spec delta` → `openspec-ff-change` → `plan-proposal`** — a chain
  of tiny prompts that each advanced one artifact stage. `go on` twice let the AI keep
  its own momentum through multi-file research.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was *created* this session — it was a heavy *consumer* of the
project's planning stack, and that stack is the reusable asset:

- **`openspec-ff-change`** — fast-forwards proposal → design → spec → tasks in one pass,
  each `openspec validate`-green. Removes the manual "what artifact is next" bookkeeping.
- **`plan-proposal`** — orchestrates doubt-review + scenario-design + fold + commit and
  hard-stops at the worktree boundary. This is what turned a draft into an apply-ready
  bundle. Invoke it whenever a proposal + design exist and you need them hardened before
  building.
- **`doubt-driven-review`** (via plan-proposal) — cross-model adversarial review with a
  non-Claude reviewer. It *earned its keep*: 19 real safety findings, not theater.
- **`scenario-design`** — turns spec requirements into an input·trigger·observable
  manifest that becomes the single source of truth for tasks.md test rows.

*If anything should be saved:* a memory that **"resume/replay in pi is lossless for
settled transcript turns but drops the ephemeral steering/followUp queue"** — it's the
linchpin fact this whole design rests on.

## 7. Pitfalls & dead ends

- **OpenSpec validator reads only a requirement's first line as normative.** A
  requirement whose first line lacked `SHALL`/`MUST` failed validation even though the
  word appeared later. *Fix:* reorder so `SHALL` leads the first line.
- **`edit` oldText mismatches from line-wrapping / ellipses.** Several edits failed
  because the model's `oldText` had reflowed whitespace or literal `…`. *Fix:* `read` the
  exact file region first, copy verbatim, then edit.
- **Reasoning about pi internals from masked grep output** (identifiers mangled to `n`).
  *Fix:* read the pinned package's `.js.map` original TS instead.
- **Transient `.git/index.lock`** (no real git process — the dashboard's VCS poll).
  *Fix:* confirm no `git commit|add|merge` process via `pgrep`, then retry; don't blindly
  `rm` the lock.
- **Test runs need an ephemeral HOME** (project convention): `HOME=$(mktemp -d) npx
  vitest run …` — otherwise the suite touches the real home.
- **Blind `git add -A` would sweep concurrent unrelated changes** (`event-reducer`,
  `compact-folder-header-actions`) into the wrong commit. *Fix:* scope to explicit paths.
