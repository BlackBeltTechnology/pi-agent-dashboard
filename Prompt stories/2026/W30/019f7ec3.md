## 1. Goal (the ask)

The kickoff was terse: *"Check https://github.com/BlackBeltTechnology/pi-agent-dashboard/issues/370, maybe it fixed in 0.6.0. Check it."* The real objective, once the follow-ups clarified it, was a **code-grounded verdict, not a changelog guess**: read the open issue's acceptance criteria, prove against the *actual shipped source and tests* whether each was met by 0.6.0, post an evidence-mapped comment on the issue, and — rather than close it — track the one remaining gap (a consolidated regression test) under a freshly created `0.6.1` milestone.

## 2. TL;DR playbook

1. `gh issue view 370 --repo BlackBeltTechnology/pi-agent-dashboard` — read the issue and its acceptance criteria first.
2. Establish the current version: `cat package.json | grep version` + `sed -n '1,80p' CHANGELOG.md`.
3. Find the *landed* fixes, not the prose: `ls openspec/changes/archive/ | grep -iE 'hydrat|replay|backpress'`, then `rg` for the exact machinery (`maxPayload`, `MAX_WS_BUFFER`, `bufferedAmount`, `replay-truncate`).
4. Confirm each fix is **synced** (present in `specs/`) and **tested** (grep the `*.test.ts` names), not merely proposed.
5. Build a **criterion → change → file/test evidence** table; write it to a comment file and `gh issue comment --body-file`.
6. State caveats honestly (what is *not* covered — e.g. no single consolidated regression test).
7. Do NOT auto-close: leave the issue OPEN and offer next steps.
8. When told to track the gap: `gh api …/milestones` to check existing → create `0.6.1` if missing → `gh issue edit --milestone "0.6.1"` → comment stating the follow-up lands there.

## 3. How the collaboration unfolded

**Phase 1 — Read the issue (Discovery).** The AI opened #370 with `gh issue view`, noted it was filed against v0.5.4 and still OPEN, and pulled out the 5 explicit acceptance criteria (large-session hydration overwhelming clients: WebSocket back-pressure, dropped frames, `Max payload size exceeded`). *Why it worked:* it anchored the whole investigation to the issue's own criteria instead of a vague "is it fixed?".

**Phase 2 — Locate the shipped fixes (Gather).** Rather than trust `CHANGELOG.md`, the AI searched `openspec/changes/archive/` for `reduce-session-replay-traffic` and `fix-stuck-tool-card-on-dropped-event`, then `rg`'d the server for the concrete mechanisms: `replay-truncate.ts`, `MAX_WS_BUFFER = 4 MB` in `browser-gateway.ts`, `getDroppedFrameStats()`, and the covering `browser-gateway-load.test.ts` / `browser-gateway-dropped-frames.test.ts`. *Why it worked:* it treated "in `specs/` = synced" vs "still a proposal" as the real bar for "shipped", and demanded a test name per claim.

**Phase 3 — Verdict + comment (Generate/Verify).** The AI wrote a `criterion → fix → evidence` table into `/tmp/issue-370-comment.md` and posted it via `gh issue comment --body-file`. Verdict: effectively fixed in 0.6.0, but two honest caveats — no explicit `maxPayload` cap, and no single consolidated regression test. *Decision point:* it deliberately did **not** close the issue, surfacing that choice back to the human.

**Phase 4 — Route the gap to 0.6.1.** On the human's instruction, the AI checked existing milestones (none for 0.6.1), created milestone `0.6.1`, assigned #370 to it, and commented that the consolidated synthetic-large-session regression test (all four invariants in one E2E scenario) will land there.

## 4. Prompts that worked

- **The goal prompt** — *"Check issue #370, maybe it fixed in 0.6.0. Check it."* Effective because it named the exact artifact (a URL) and the hypothesis to test (fixed in 0.6.0). Stronger version: *"Verify against the shipped code + tests whether every acceptance criterion in issue #370 is met by 0.6.0; post an evidence-mapped comment but don't close it."*
- **High-leverage follow-up `1`** — a one-character unlock accepting the AI's proposed next action. Terse steering like this only works because the AI had already laid out a clear menu of options; the guardrail is to *make the AI enumerate options* so a single token can pick one.
- **The routing prompt** — *"Add a message that consolidated regression tests will be added to 0.6.1. Add 0.6.1 milestone and add it."* Effective because it bundled three concrete deliverables (comment + create milestone + assign) in one line.

## 7. Pitfalls & dead ends

- **One `rg` gap-detection search failed** (searching for `resync|gap|missedSeq|expectedSeq` in a path that didn't exist). If a targeted grep returns nothing, widen the path (`packages/server/src` → whole repo) or `find` the spec dir first rather than assuming the feature is absent.
- **Trusting the CHANGELOG would have been wrong** — the fix was real but the issue was still OPEN and nobody had closed it. Always grep the actual source + test files before declaring "fixed".
- **Don't conflate proposed with shipped** — a change under `openspec/changes/` may be a proposal; confirm it landed in `specs/` and has covering tests before crediting it.
