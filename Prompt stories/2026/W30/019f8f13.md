# How we did it: Mid-turn tool OAuth ("courier mode") — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (openspec-explore skill), a "thinking, not
implementing" stance. The real objective, which surfaced through the steering turns,
was concrete: **let a tool an agent invokes mid-turn (canonically `rclone` connecting
to Google Drive) complete its interactive OAuth consent *inside ChatView*** — surface
the consent URL as a card, open the browser, and let the tool catch its own token —
without the dashboard becoming a credential broker. The desired end-state was not code
but a **buildable OpenSpec change**: proposal + design + spec deltas + tasks, validated
strict, committed.

## 2. TL;DR playbook

1. Enter **explore mode** (`openspec-explore`) — declare "capture thinking, don't implement."
2. Ground before theorizing: `kb_search` + read the two OAuth patterns already in the tree
   (`oauth-callback-server.ts` for LLM providers, `auth.ts`/`auth-plugin.ts` for dashboard login).
3. Answer the three scope questions up front (persist local · general tool · tool-owns-its-mechanics)
   so the design axis (**credential ownership**) is fixed early.
4. Trace one concrete end-to-end flow ("connect Google Drive via rclone") **hop-by-hop**,
   marking each hop ✅ exists / 🔶 glue / 🔴 novel — this collapses the problem to the *one* novel surface.
5. Run a **side-effect-free spike** (`rclone --help`, `--non-interactive`, `gh`/`gcloud --help`)
   to confirm the mechanism (rclone's JSON `"State": "*oauth…"` discriminator) *before* writing specs.
6. Capture the exploration as a **draft OpenSpec change** folder (proposal.md + design.md) — not `docs/`.
7. Fast-forward (`openspec-ff-change`): fold refinements into design → write spec deltas → write tasks.md
   → `openspec validate --strict`.
8. Commit **only** the change folder (`git add openspec/changes/add-mid-turn-tool-oauth/`), leaving
   unrelated working-tree files untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / Grounding.** Rather than theorize, the AI immediately read the
existing OAuth machinery: it found `oauth-callback-server.ts` (a temporary loopback
listener already shipping for LLM providers) and the dashboard-login callback pattern,
plus two adjacent in-flight changes (`add-cloud-sync-connector`, `add-connector-layer`).
*Why it worked:* the whole problem turned out to be ~90% existing primitives; grounding
first prevented inventing a redundant "fourth thing."

**Phase 2 — Fix the scope axis.** The human's steering #1 ("1. persist key on local
machine / 2. general tool / 3. keep own — when external tool have the mechanics") gave
three answers that collapsed the hard part. The AI mapped them onto a **credential-
ownership axis** and named two modes: *courier* (tool owns its OAuth app + config; the
dashboard just orchestrates) vs *owner* (dashboard vault runs the flow). Decision point:
courier is a thin **wrapper, not a broker**.

**Phase 3 — Hop-by-hop trace.** The AI traced "connect Google Drive via rclone" as
numbered hops, marking each ✅/🔶/🔴. This isolated the **one novel surface — HOP 3**:
detecting a headless tool blocking on a consent URL and routing it through ChatView.

**Phase 4 — Verified spike.** Explicitly **safe** (no real remote, no live browser
popup): `rclone v1.74.3` + `--non-interactive` revealed the OAuth step is a structured
`"State": "*oauth-islocal…"` JSON discriminator (no fragile regex), and
`--auth-no-open-browser` is the knob that lets the dashboard own the browser hop. A
later spike on `gh`/`gcloud` revealed courier splits into **three challenge kinds**
(loopback `url` / device `code` / OOB `paste`) — which *partially reversed* the earlier
"auth is local-only" claim (device/OOB are remote-capable).

**Phase 5 — Capture & fast-forward.** The AI rejected `docs/plans/` (Documentation
Protocol routes `docs/` through DocScribe caveman-style, which would mangle nuanced
research prose) and instead captured to an **OpenSpec change folder**. Then
`openspec-ff-change`: folded the three-kind refinement into design.md, corrected
proposal.md, wrote the capability spec (6 requirements / 15 scenarios) and a TDD-ordered
tasks.md, and passed `openspec validate --strict`.

**Phase 6 — Surgical commit.** With unrelated modified/untracked files in the tree, the
AI staged **only** the change directory and committed on `develop` — 4 files, 437 insertions.

## 4. Prompts that worked

- **Goal prompt (explore-mode skill invocation).** Effective because it set a *stance*
  ("think, don't implement, but you MAY create OpenSpec artifacts"), giving the AI room
  to ground and capture without prematurely writing code.
- **Steering #1 — the three numbered answers.** The single highest-leverage prompt:
  three terse lines fixed the entire design axis. A future operator should front-load
  exactly this: *"persist locally · make it a general tool · let the external tool keep
  its own auth mechanics."*
- **"go on" (×2).** Short continuation prompts that let the AI carry a well-scoped thread
  to completion without re-litigating direction.
- **"Okay. But there can be other tool, like gh, gcloud etc."** Unlocked the three-kind
  taxonomy — a scope expansion that materially improved the design. Rewrite for reuse:
  *"generalize this beyond rclone to gh/gcloud/aws — confirm each tool's challenge kind
  with a --help spike."*
- **openspec-ff-change invocation + "commit".** Clean graduation from draft to
  apply-ready to committed.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session — the workflow rode existing skills
(`openspec-explore` → `openspec-ff-change`). The reusable pattern worth capturing is the
**"ground → scope-axis → hop-trace → verified-spike → capture-as-change"** exploration
loop:

- **What it captures:** how to turn a vague "can we do X?" into an apply-ready OpenSpec
  change without writing production code, by proving the mechanism with side-effect-free
  spikes and isolating the single novel surface.
- **Why it's effective:** it repeatedly avoids re-inventing shipped primitives (the
  problem was ~90% already in the tree) and defers artifacts until one verified fact
  ("`State` discriminator exists") makes the design buildable.
- **When to invoke:** any exploration where the feature likely overlaps existing
  machinery and the risk is over-building. Consider saving this as a project skill.

## 7. Pitfalls & dead ends

- **`find` for a non-existent plans file failed** (1 command error) — harmless; the AI
  pivoted to confirming the right capture location instead.
- **`docs/plans/` is a trap for research prose** — the project's Documentation Protocol
  routes `docs/` writes through the DocScribe subagent in caveman style, mangling
  nuanced narrative. Capture exploration in an OpenSpec change folder instead.
- **`openspec change` (1.6.0) has no `new` subcommand** — the change folder was
  hand-written following existing structure; OpenSpec still recognized it (`proposal` +
  `design` done, `applyRequires: ["tasks"]`).
- **"auth is local-only" was an over-claim** — true only for the *loopback* kind; device
  and OOB kinds are remote-capable. Don't lock a topology conclusion before spiking every
  tool's challenge kind.
