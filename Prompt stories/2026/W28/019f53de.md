# How we did it: Designing a tree-sitter code-symbol index for the KB — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
explicitly *no implementation*. The seed idea, hinted by the session name "LSP", was:
the KB can find prose but can't answer the agent's most common question — **"where is
method / type / function X defined?"** The real objective, sharpened by the steering
turns, became: **produce a complete, validated OpenSpec change** (`add-kb-code-symbol-index`)
that specifies deterministic, zero-LLM code-symbol indexing into the KB's existing but
empty Tier-1 `nodes`/`edges` graph — grounded in real research on tree-sitter, WASM vs
native bindings, all-language coverage, and supply-chain reproducibility.

## 2. TL;DR playbook

1. **Enter explore mode** with `openspec-explore`; state up front "capture thinking as
   OpenSpec artifacts, don't implement."
2. **Ground before theorizing** — read the real KB schema (`packages/kb/src/sqlite-store.ts`)
   and any active/adjacent changes before proposing anything.
3. **Reframe the idea** as "filling an empty room" (the KB already ships `nodes`/`edges`
   but nothing populates typed code symbols) — not a new subsystem.
4. **Scaffold the change by hand** (no `openspec change new` in this CLI): write
   `proposal.md`, `design.md`, `tasks.md`, and two `specs/*/spec.md`, copying format
   from a recent change and aligning vocabulary with the existing spec.
5. **`openspec validate <name>`** after every batch of edits; keep it green.
6. **Research each open fork with real fetches**, not guesses: pi ecosystem scan →
   tree-sitter WASM API → aider/Continue tag-extraction → language-pack coverage →
   integrity/offline behavior.
7. **Fold each finding back into the artifacts** (design.md sections + spec requirements
   + tasks) as decision-forcing threads; re-validate.
8. **On "commit"**: stage ONLY the change directory, commit with a scoped message, do
   not push, and report exactly what was left untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery & reframe (prompt 1).** The AI resisted the urge to theorize and
first read the KB's actual SQLite schema and two adjacent active changes
(`add-kb-semantic-annotation-plane`, `add-automatic-session-kb-index`). This produced
the session's pivotal insight: the Tier-1 graph already declares an `entity` node kind
but *nothing populates code symbols* — the idea "moves into a room that already exists"
and fits the KB's zero-LLM, pull-not-push doctrine. **Decision point:** the human's idea
was reframed from "add LSP" to "feed the empty graph," and the engine was left open.

**Phase 2 — Scaffold the proposal.** No CLI scaffolder existed, so the AI wrote the five
artifacts directly under `openspec/changes/add-kb-code-symbol-index/`, copying a recent
change's format and reusing spec vocabulary (`nodes`/`edges`, `child_of`, content-hash
incremental). `openspec validate` → valid.

**Phase 3 — Research forks (steering #1–#4).** Each short steering prompt opened a
grounded research thread instead of speculation:
- *"pi extensions with tree-sitter?"* → local scan proved **none exist** anywhere in the
  pi ecosystem; bundling grammars is unavoidable work. Also surfaced `pi.registerTool()`
  as the clean integration seam.
- *"how can tree-sitter be integrated?"* → fetched web-tree-sitter API + aider's extraction
  loop; concluded **WASM beats native** (one artifact, no per-platform prebuild matrix).
- *"all languages supported?"* → `tree-sitter-language-pack` ships 306 grammars with
  `tags` queries + on-demand download; "all" is a **curation decision, not engineering**,
  gated by the `tags.scm` subset and the asset wall.
- *"keep pulling"* → the highest-leverage prompt: the AI ran a doubt-driven pass and
  found lazy-fetching remote WASM **contradicts the KB's offline/reproducible DNA**, then
  chased name-collisions (`UNIQUE(type,name)`), SCIP phase shape, and a real perf budget.

**Phase 4 — Fold & validate.** After each thread the AI edited `design.md`, added spec
requirements, rewrote `tasks.md` sections, added `security-hardening` to Discipline
Skills, and re-ran `openspec validate` — landing 8 grounded threads, 741 lines, valid.

**Phase 5 — Commit (steering #5).** On "commit" the AI staged **only** the change dir,
committed `67b82dd7c` on `develop` with a scoped message, did **not** push, and listed
every unrelated modified/untracked file left untouched.

## 4. Prompts that worked

- **Goal prompt (explore mode):** effective because it set the *stance* (think, capture
  as OpenSpec, never implement) — freeing the AI to ground and reframe rather than rush
  to code.
- **"Research maybe there are pi extensions with tree-sitter functions"** — turned a
  guess into a proof (there are none), which *hardened* the design.
- **"is it possible to add all languages supported by tree-sitter?"** — forced the
  coverage/asset-wall analysis that produced the registry + lazy-fetch design.
- **"keep pulling"** — the standout high-leverage prompt: a two-word nudge that
  triggered an adversarial self-review exposing the offline/reproducibility contradiction.
  Reuse this verbatim when a design feels "done but under-stressed."
- **"commit"** — worked because the AI already knew the repo hygiene rule (stage only
  what you created). Strengthen by saying "commit only this change dir, don't push."

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created — this was a pure explore/plan session. The
reusable asset is the **change itself** (`add-kb-code-symbol-index`, validated,
implementation-ready). Recommended skill to create if this pattern recurs:

- **`ground-every-design-fork`** — a discipline that, for each open architectural fork,
  requires a real repo scan or doc fetch before a decision is recorded. It removes the
  "plausible but wrong" guess (e.g. "surely pi bundles tree-sitter") and makes each
  design decision traceable to evidence. Invoke during any explore/plan session with
  multiple binding forks.

## 7. Pitfalls & dead ends

- **`mktemp`-style scaffolding assumption:** there is **no `openspec change new`** in
  this CLI version — write artifacts directly under `openspec/changes/<name>/`.
- **"tree-sitter is bundled somewhere" mirage:** it is **not** in pi core, the repo, or
  any `~/.pi` extension. Don't plan to inherit it.
- **Shelling out to installed CLIs** (rust-analyzer, pyright, macOS BSD `ctags`) is a
  dev-box mirage — breaks reproducibility; keep it deferred/opt-in, never baseline.
- **Native `node-tree-sitter`** drags in the node-pty-class per-platform prebuild matrix
  → choose WASM.
- **Lazy remote-WASM fetch** silently violates offline/reproducible reindex → require
  opt-in + SHA-verified + content-addressed; rely on the WASM sandbox to cap RCE.
- **`nodes.UNIQUE(type,name)`** collides on same-named symbols across files → model the
  node as a *concept* with N `defined_in` edges.
- **3 of 6 `ctx_batch_execute` calls errored** — batch fetches are flaky; verify output
  and retry rather than trusting the first result.
