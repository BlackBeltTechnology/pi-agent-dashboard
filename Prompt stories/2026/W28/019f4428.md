# How we did it: Root-cause a "can't scroll to top" bug and turn it into a validated OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
not an implementation session — with a UX bug: *you cannot reliably scroll to the top of a
virtualized chat transcript on real, long sessions.* The first prompt was the explore-mode
skill preamble ("Enter explore mode. Think deeply… you must NEVER write code"). The *real*
objective, which the one-word steering turns unlocked, was: **investigate the actual scroll
machinery, pull a reproducing session as evidence, isolate the true root cause, and capture
it as a validated OpenSpec change proposal** — all without writing a line of implementation.

## 2. TL;DR playbook

1. **Enter explore mode** so the AI grounds in real code instead of jumping to a fix
   (`openspec-explore` skill). State the symptom concretely: "can't scroll to top of the
   virtualized transcript on long sessions."
2. **Let it map the scroll machine first** — the container, the TanStack virtualizer, the
   row-size estimator (`chat-virtual-rows.ts`), the event reducer's head-trim logic. Ask
   for a ranked list of *plausible causes*, not one guess.
3. **Say `pull`** — feed a real reproducing session JSONL as evidence. The AI profiles
   record sizes (median vs max, byte distribution, where the giants sit).
4. **Demand a verdict table**: each hypothesis → evidence from the session → CONFIRMED /
   CLEARED / not-the-cause. This is what separates a guess from a root cause.
5. **Say `draft`** — scaffold the OpenSpec change by hand (proposal + design + delta spec +
   tasks), mirroring an existing change, then `openspec validate --strict`.
6. **Say `keep exploring`** — before trusting the design, read the *installed library
   source* (`node_modules/@tanstack/virtual-core`) to confirm the fix mechanism. This is
   where the first-draft design got overturned.
7. **Say `update`** — rewrite the artifacts to match what the source proved, re-validate.
8. **Say `commit`** — stage ONLY the change dir, commit `docs(openspec): propose …`.

## 3. How the collaboration unfolded

**Phase A — Ground the scroll machine (Discovery).** The AI resisted guessing and instead
grepped for `scrollTo/scrollTop/useVirtualizer/overscan`, read `chat-virtual-rows.ts`, and
checked the event reducer for a head-trim cap. It produced an ASCII diagram of the scroll
container + virtual spacer + streaming tail, then ranked **three** plausible causes
(dynamic-height estimate drift · server-side head-trim · onChange bottom-pin). *Why it
worked:* enumerating non-exclusive hypotheses up front prevented anchoring on the first
idea.

**Phase B — Pull the evidence (`pull`).** Given a real session id
(`019f43e4-…`), the AI located the JSONL, profiled it with `python3` one-liners, and found:
156 records (nowhere near the 20 000 cap → head-trim **CLEARED**), but a heavy-tail size
distribution — median row 1.7 KB, **max 303 KB**, top-5 records = 48% of all bytes, and the
giants (a 294 KB pasted image at L5, a 24 k-char toolResult) **sit near the top**. That
confirmed hypothesis #1: content-blind static estimates (`user:96`, `toolResult:120`)
under-shoot real heights by 10–50×, so `getTotalSize()` jumps on mount and the top recedes.

**Phase C — Draft the change (`draft`).** No `openspec change new` subcommand existed, so
the AI scaffolded by hand, mirroring the sibling `virtualize-chat-transcript-tanstack`
change: proposal, design (3 decisions), a delta spec, and a TDD-first tasks.md.
`openspec validate --strict` passed.

**Phase D — Verify the fix against library source (`keep exploring`).** The decision point
that made this session valuable. Instead of trusting the design, the AI read
`@tanstack/virtual-core/index.js` and discovered its Decision 2 was **wrong**: TanStack
*already* anchor-corrects above-viewport rows by default (line 534). So a manual
`scrollTop += delta` would **double-correct**. The real defeater: the built-in correction
reads a **stale `this.scrollOffset`** (refreshed only on debounced scroll events), so during
a continuous upward flick it yanks the position back by an amount ∝ the estimate error.
Root fix = shrink the estimate error (Fix 1), and **do not** fight the built-in correction.

**Phase E — Correct & commit (`update` → `commit`).** The artifacts were rewritten to cite
`virtual-core index.js:534`, relabel Fix 1 as primary, flip Fix 2 from "add anchoring" to
"don't double-correct," and name the double-correction trap in the risks. Re-validated, then
committed with only the 4 artifacts staged (223 insertions) — nothing from the shared
working tree leaked in.

## 4. Prompts that worked

- **The goal prompt (explore-mode preamble).** Effective because the *stance* — "think, do
  not implement" — forced grounding and hypothesis-ranking instead of a premature patch.
  A future operator should add the concrete symptom + "rank the plausible causes and tell
  me what evidence would confirm each."
- **`pull`** — a one-word high-leverage unlock. It turned speculation into measurement by
  feeding a real reproducing session. Stronger version: "pull session `<id>` and profile
  record sizes — median, max, and where the biggest rows sit relative to the top."
- **`keep exploring`** — the highest-leverage follow-up. It bought a second grounding pass
  against library source that *overturned the first design*. Bake in: "before we trust the
  design, verify the fix mechanism against the installed library source."
- **`draft` / `update` / `commit`** — terse workflow verbs that worked *because* the earlier
  grounding made the content unambiguous. Cheap prompts ride on expensive evidence.

The pattern: the human's steering was almost entirely **"go get more evidence"** — first
from a session (`pull`), then from library source (`keep exploring`). Both times the extra
grounding changed the conclusion.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session — but the workflow is a strong candidate for
one. The reusable procedure is: **explore-mode → enumerate hypotheses → pull a real session
as evidence → verdict table → draft OpenSpec change → verify against library source →
correct → commit.** A skill like `root-cause-from-session-evidence` would capture: (1) the
`python3` record-size profiling one-liners for a session JSONL, (2) the "verdict table"
output contract (hypothesis → evidence → CONFIRMED/CLEARED), and (3) the discipline of
reading `node_modules/<lib>` source before finalizing a design decision. It removes the
temptation to ship a plausible-but-wrong fix.

Tools that carried the session: `kb_search`/`kb agents` for the doc tree, `rg` for the
scroll machinery, `python3` for byte-distribution profiling, and `openspec validate
--strict` as the artifact gate.

## 7. Pitfalls & dead ends

- **Assuming TanStack doesn't anchor-correct.** It does, by default (`virtual-core`
  line 534). A manual `scrollTop += delta` would **double-correct**. *If you hit "can't
  reach the top" in dynamic-height virtualization, read the library's resize handler before
  adding your own correction.*
- **`openspec change new` doesn't exist as a subcommand.** *If you need a new change, scaffold
  by hand mirroring an existing `openspec/changes/<sibling>/`, then `openspec validate
  --strict`.*
- **A stray/duplicate edit key.** One edit failed and had to be retried clean (3 edit errors
  total). *If an edit rejects, re-read the target and re-issue a minimal, unique match.*
- **Validation-pass ≠ correct design.** The first draft passed `--strict` yet had the wrong
  Decision 2. *Never treat schema validation as root-cause verification.*
- **Sequencing caveat.** This change edits `virtualize-chat-transcript-tanstack` code that is
  still in-progress — land it *after* that change or fold it in.
