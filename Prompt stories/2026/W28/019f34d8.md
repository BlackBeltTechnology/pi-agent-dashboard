# How we did it: Diagnose a red CI regression and capture the fix as an OpenSpec change — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** — a thinking-partner stance, explicitly *not*
an implementation stance ("you must NEVER write code or implement features… You MAY
create OpenSpec artifacts"). The real objective, once the exploration converged: the
`develop` branch CI was red, and the operator wanted the failure **root-caused and
captured as a reviewable OpenSpec change proposal** — without fixing the code yet.
The whole run is a diagnosis-to-proposal loop that deliberately stops short of the
implement step, ending on a single steering word: `commit`.

## 2. TL;DR playbook

1. Pull the failing run: `gh run list --branch develop --limit 10` → `gh run view <id> --log-failed`.
2. **Filter the log noise immediately** — grep for `FAIL|Test Files|Tests |AssertionError` and exclude the known non-fatal lines (`attach failed`, `reload failed`, `mDNS`, `providers.json`).
3. Reproduce locally with **HOME isolation**: `HOME=$(mktemp -d) npx vitest run <the 3 test files>`. Confirm it's a real regression, not flake.
4. Find the culprit commit: `git log --oneline -5 -- <changed file>`; read the exact block it introduced.
5. State the root cause as a **before/after guard diff** in plain terms (here: `!isLive` was a leaky proxy for "cold replay").
6. Run the coherence check: `openspec list --json` + scan `openspec/changes/archive/` for the originating change.
7. Scaffold the change **by hand** (no `openspec change new` subcommand exists) — copy the structure of an existing fix change: `proposal.md` + `tasks.md` + `specs/<cap>/spec.md`.
8. `openspec validate <change-name>` until green.
9. On `commit`: `git add` **only your change dir**, commit, and explicitly leave unrelated dirty files untouched.

## 3. How the collaboration unfolded

**Discovery (CI triage).** The AI fetched the failing `develop` run, saw 3 client
`event-reducer` tests failing — all asserting a single collapsed `thinking` row where
the reducer now emitted two. The effective move was refusing to read the raw log:
successive greps narrowed 60 lines of CI noise down to the three real assertions.

**Reproduce & isolate.** First local `vitest` run needed a retry — it hit the real
`$HOME`. Re-running under `HOME=$(mktemp -d)` isolated the environment and confirmed
the failure reproduces deterministically on `develop`. This is the decision point
that turned "maybe flaky" into "real regression, fix it."

**Root cause.** `git log` on `event-reducer.ts` fingered `f5ee00a32` (the
`reconstruct-reasoning-on-replay` work). The AI read the new `message_end` block and
articulated the mechanism precisely: the `!isLive` guard *assumed* it meant "cold
replay, nothing rendered yet," but a streamed turn whose `message_end` isn't flagged
`isLive` double-fires — two producers of `thinking` rows collide.

**Capture (OpenSpec).** Before scaffolding, a coherence check (`openspec list`,
archive scan) confirmed the origin change was archived and no active change covered
it. `openspec change new` **failed** (no such subcommand), so the AI created the
directory structure manually by mirroring an existing fix change. `openspec validate`
passed.

**Commit.** The lone steering turn — `commit` — triggered a scoped commit: only the
3-file change dir, deliberately leaving unrelated dirty files (`manage-flows/SKILL.md`,
`groups.json`, `b05_*.txt`) alone.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created. The workflow, however, is clearly repeatable and
deserves one. **Recommended skill:** *"triage-red-ci-to-openspec-proposal"* —

- **What it would capture:** the deterministic path from a red `develop` run to a
  validated OpenSpec change: fetch → noise-filter → HOME-isolated repro → culprit
  commit → before/after guard statement → coherence check → hand-scaffold → validate.
- **Why it's effective:** it removes the two repeated stumbles (log noise, `$HOME`
  leakage) and encodes the "no `openspec change new`" gotcha, so the next operator
  skips both retries.
- **When to invoke:** any time CI on `develop` goes red and you want the fix reviewed
  as a proposal before touching code.

## 7. Pitfalls & dead ends

- **`vitest` without HOME isolation** — the first run leaked to the real `$HOME` and
  had to be retried under `HOME=$(mktemp -d)`. Do the isolated form first.
- **`openspec change new <name>` does not exist** — it failed. Scaffold manually by
  copying the layout of an existing change under `openspec/changes/`.
- **Raw `--log-failed` output is 60+ lines of unrelated noise** (`attach failed`,
  `mDNS`, `providers.json`). Always grep + exclude before reading.
- **`git add -A` would have swept in unrelated dirt.** Stage only your change dir.
