# How we did it: Scoping a "copy file path" feature in explore mode — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill), whose stance is
*think, don't implement*. The first prompt was the skill's boilerplate — no concrete
feature named yet. The *real* objective, which emerged in the first exchange and the
three short steering turns that followed, was: **let a user copy a file's path out of
the editor pane's file-tree rail (`EditorFileTree.tsx`).** Today a row is just
`[chevron] [icon] name` with no path affordance. The goal was not to build it, but to
*scope it* — explore the interaction options, mock them against the real theme, pick
one, and capture the decision as a strict-clean OpenSpec change ready to implement
later.

## 2. TL;DR playbook

1. Enter explore mode with the `openspec-explore` skill — you get a thinking partner
   that reads/searches but refuses to implement.
2. Ask it to locate the surface: it `grep`'d `packages/client/src` and found
   `EditorFileTree.tsx`, then drew the component tree so the target row was unambiguous.
3. Have it build a **live HTML mockup** of the competing interaction options against the
   dashboard's real CSS theme tokens (`serve_mockup` on a throwaway `/tmp` dir).
4. Let it `score_mockup`/`browser`-capture each option so you *see* them rendered in
   the dark theme before choosing.
5. Read its A-vs-B comparison table, then steer with a **one-word/one-phrase pick**
   ("Option A with popup menu").
6. Have it rebuild the mockup to the single chosen design and re-capture the resting +
   menu-open states.
7. Say **"capture"** — it reads an existing archived change for format conventions,
   then writes `proposal.md` + spec delta + `tasks.md` under
   `openspec/changes/copy-file-path/` and runs `openspec validate --strict`.
8. Say **"stop and commit"** — it stops the mockup server and commits *only* the new
   change directory, deliberately leaving unrelated pre-existing working-tree changes
   untouched.

## 3. How the collaboration unfolded

**Discovery (locate the surface).** The AI `grep`'d the client source for
`FileTree|clipboard|full.*path`, found `EditorFileTree.tsx`, and rendered the
`EditorPane → EditorTabs → EditorFileTree → viewer` tree with an arrow on the exact row
that lacked a path affordance. *Why it worked:* it anchored the abstract ask to a
concrete file + row before proposing anything.

**Design (mock the options against real tokens).** It grepped the CSS for the theme
custom properties (`--bg-hover`, `--bg-selected`, `--text-secondary`, …), then built a
`/tmp/filetree-copypath-mockup/index.html` using those *real* tokens, served it with
`serve_mockup`, and used `browser` + `score_mockup` to capture how each option renders
in the dark theme. It presented a crisp **A (hover-reveal icon) vs B (right-click menu)**
table scored on discoverability, row noise, extensibility, touch, and repo precedent.
*Decision point:* the human picked **"Option A with popup menu"** — hover-reveal glyph
that opens a small copy menu (a hybrid of the two).

**Refine (rebuild to the single design).** It rebuilt the mockup to only the chosen
design and re-captured. One capture missed the popup because a browser `eval` was echoed
rather than executed in page context; it fixed that by adding a demo auto-open so the
menu was visible in the shot. The behavior got *locked by the mockup*: glyph fades in on
hover (files + folders), click `stopPropagation`s (never opens the file), popup flips
above on overflow, header shows the truncated absolute path, three actions (full /
relative / name).

**Generate (capture as OpenSpec).** On **"capture"** it read an archived change
(`collapse-files-panel-by-default`) to learn the proposal/spec/tasks format, then wrote
the three artifacts: a proposal, one **ADDED** requirement on the
`internal-monaco-editor-pane` capability with 6 scenarios, and a TDD-first `tasks.md`.
`openspec validate copy-file-path --strict` came back clean.

**Commit (surgical staging).** On **"stop and commit"** it stopped the server, ran
`git status`, noticed unrelated pre-existing changes (`groups.json`, vitest configs,
test files), verified via `git diff` that its `openspec new change` had *not* touched
`groups.json`, and staged **only** `openspec/changes/copy-file-path/` — committing as
`2ea21dfb8` and leaving everyone else's work alone.

## 4. Prompts that worked

- **The goal prompt (the explore-mode skill invocation).** Effective because it set a
  *stance* — read/search/mock, but do not implement — which kept the whole session in
  scoping territory and produced a spec instead of half-baked code. A future operator
  should open the same way: "Enter explore mode. I want to scope <feature> on <surface>,
  not build it."
- **"Option A with popup menu"** — a high-leverage 4-word pick. It resolved the entire
  design branch in one turn *because the AI had first laid out a scored A/B table and a
  live mockup*. The lesson: make the AI present a comparison + a rendered mockup, and
  your decision collapses to a phrase.
- **"capture"** — one word that converted the settled design into three validated
  OpenSpec artifacts. Works only because the design was already locked by the mockup.
- **"stop and commit"** — one phrase that closed the session cleanly (server down,
  surgical commit).

*Rewrite of a weak prompt:* instead of a bare "capture", a slightly stronger version is
"capture as an OpenSpec change; validate strict; do not implement" — it names the output
format and the guardrail explicitly, so nothing is left to inference.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Offer *two* interaction patterns (A and B) and wait | "Option A with popup menu" | State the interaction preference up front if you already have one, else expect a mock-both round |
| Leave the mockup server running "in case you want to re-look" | "stop and commit" | Say "when done, stop the server and commit only the change dir" in the kickoff |
| Face a dirty working tree with unrelated changes | (no correction needed — it self-guarded) | Ask for surgical commits explicitly: "stage only <path>, leave pre-existing changes" |

Note this session needed *very little* correction — the steering turns were **decisions**
("pick A", "now capture", "now commit"), not fixes. That is the signature of a
well-run explore→scope session: the AI does the divergent work (mock both, score both)
and the human only supplies convergent picks.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created. The reusable assets here are **existing skills used
well**:

- **`openspec-explore`** — the stance skill. It *refuses to implement*, which is exactly
  what you want when scoping: it forces the output to be a proposal/spec, not code.
  Invoke it whenever you want to think a feature through and land a change proposal
  without touching production code.
- **`serve_mockup` + `score_mockup` + `browser`** — the live-mockup loop. Building the
  mock with the app's *real* CSS theme tokens (not invented colors) and capturing it in
  the actual dark theme is what let a 4-word pick settle the design confidently.

*Skill that could be created:* a "scope-a-UI-affordance" playbook — grep for the target
component → mock competing interactions against real theme tokens → score/capture →
one-phrase pick → write OpenSpec change → surgical commit. This session is a textbook
instance of that loop; if you repeat it, capture it as a skill.

## 7. Pitfalls & dead ends

- **Wrong package path first.** The opening `ls packages/web/ … src/client` command
  failed — this repo's client lives at `packages/client/src`, not `packages/web` or
  `src/client`. If you `ls` and it 404s, grep for the component name instead of guessing
  the directory.
- **Browser `eval` echoed, not executed.** A capture missed the popup because the eval
  string was echoed rather than run in page context. Fix: add a demo auto-open (or drive
  the real interaction) so the transient UI is present in the screenshot.
- **Edit retries.** 2 of 3 `edit` calls errored before succeeding — normal churn when
  editing a mockup; not a blocker.
- **Dirty working tree at commit time.** Unrelated `groups.json` / vitest / test-file
  changes were already present. Don't `git add -A`. Verify with `git diff` that your
  tooling (e.g. `openspec new change`) didn't touch shared files, then stage only your
  change directory.
