## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
explicitly *no implementation*. The first prompt loaded the explore skill; the real
objective emerged one steering turn later:

> "1" — *pick Thread 1: design the TanStack Virtual "Step B" follow-up change.*

Restated: **turn a vague "adapt TanStack Virtual for ChatView" instinct into two coherent,
strict-valid OpenSpec changes** — an imported 4-phase performance umbrella and a downstream
`virtualize-chat-transcript-tanstack` Step B design — *de-risked by real tests and an
adversarial doubt review before a single line of feature code is written*. The session then
overflowed its explore boundary once (a live ping-pong scroll bug surfaced) and the operator
chose to fix + deploy + push that too.

## 2. TL;DR playbook

1. **Enter explore mode** with the `openspec-explore` skill and ground immediately in real
   artifacts (the zip proposal + the actual `ChatView.tsx` + the upstream TanStack **Chat
   guide**) before theorizing.
2. **Force the fork early.** When there are two plausible directions, present them and let a
   one-character reply (`1`) pick — don't silently choose.
3. **Audit before importing** external artifacts: map *every* factual claim in the umbrella
   to current repo reality; fix stale line refs and de-dangle nonexistent-change dependencies.
4. **Consume, don't delete.** When collapsing a diagnosis-only change into the solution,
   fold its unique evidence into the design Context and preserve any excluded finding as a
   *named deferred follow-up* so nothing silently vanishes.
5. **De-risk with a 3-layer test split:** unit-mockable logic → real characterization test;
   browser-layout claims → mapped Playwright `test.fixme` skeleton; trace-only claims → noted.
6. **Run the `doubt-driven-review` skill adversarially** on the design, then escalate to a
   **cross-model** reviewer (different architecture = different blind spots). Fold every
   actionable finding back into the artifacts.
7. **Commit surgically** — stage only your files; explicitly exclude auto-churned metadata
   (`groups.json`), generated files, and stray scratch files, stating each reason.
8. **When a live bug appears, diagnose the exact loop before touching code**, apply the
   minimal guard, verify with the existing unit suite, then build + `/api/restart` + push.

## 3. How the collaboration unfolded

**Phase 1 — Ground & fork (explore).** The AI refused to theorize in the abstract: it read
the umbrella zip, the real `ChatView.tsx` scroll/render machinery, and *fetched* the TanStack
Virtual Chat guide. It surfaced the tension — Step B was **explicitly deferred** by the
umbrella (task 4.5) — and offered forks instead of guessing. *Why it worked:* three
independent sources (proposal, upstream guide, actual code) gave the design real anchors, and
the fork made the human own the direction.

**Phase 2 — Scaffold the Step B change.** It discovered a pre-existing 0-task
`lag-dashboard-transcript-rendering` (diagnosis-only) and read the `chat-scroll-lock` spec so
its deltas would *preserve* the 50px threshold, the scroll-to-bottom button, and the
multi-batch replay race. Then it scaffolded `virtualize-chat-transcript-tanstack` and
validated it `--strict`.

**Phase 3 — Import & consume with an audit.** On "import, but check the usable parts," it
built a claim→repo-reality table: verified the un-memoized ChatView and missing rAF batching,
fixed two stale line refs, and caught a **dangling dependency** (Phase 4 pointed at a change
that didn't exist) — folding Phase 4 in as 4 concrete tasks naming the exact unstable props at
`App.tsx:1545`. On "consume proposal lag-…," it folded the diagnosis's unique evidence into
the umbrella and preserved the excluded full-res-screenshot finding as a named follow-up.

**Phase 4 — De-risk by testing the design premises.** "Is it possible to validate with mock
tests?" → it split claims into unit-mockable vs browser-only vs trace-only, proved the three
mockable ones with mock models (14 pass), then rewired the fold-invariance check against the
**real** `event-reducer` (3 pass under `npm test`) and wrote a 6-test Playwright skeleton
(`test.fixme`, each mapped to a spec requirement, with the one unblock — a `long-transcript`
fixture — drafted into the proposal).

**Phase 5 — Doubt review, cross-model.** "doubt review" loaded the `doubt-driven-review`
skill. A fresh-context adversarial reviewer found substantive gaps; the AI then escalated to
**GPT-5 (`openai-codex/gpt-5.4`)**, which corroborated *and* surfaced two deeper issues Claude
missed (`turnIndex` lives only on the last user message; `ChatImage` has no dimensions). The
load-bearing correction: the design's "delete the hand-rolled scroll machinery" instruction
was *wrong* — the streaming tail renders outside the virtualized list, so that machine must
stay. All 7 findings folded in (CR-1…CR-7), then committed as `abaa47699`.

**Phase 6 — Live bug + ship.** A real ping-pong scroll bug appeared in the *shipped*
virtualized code. The AI read the two bottom-pin sites, pinned the culprit
(`virtualizer.onChange` re-pinning on every scroll inside the 50px band), applied a
one-guard fix (re-pin only when `scrollHeight` grew), verified 55/55 ChatView tests, built +
restarted production, then recognized its ~10-line fix was tangled in a large uncommitted
virtualization implementation it *didn't* write — so it backed out staging, mapped the surface
into groups, and let the human commit. Finally pushed `develop`.

## 4. Prompts that worked

- **Goal prompt (explore skill):** the `openspec-explore` stance was the right kickoff — it
  forced grounding-before-implementing and made "capture as OpenSpec artifacts" the natural
  output. A stronger explicit version: *"Explore Step B (TanStack Virtual for ChatView);
  capture the design as an OpenSpec change; do not implement."*
- **`1` / `1. Import, but check the usable parts`** — tiny high-leverage replies that unlocked
  whole phases *because the AI had already laid out the forks*. The "check the usable parts"
  clause is what triggered the claim-by-claim audit instead of a blind copy.
- **`consume proposal lag-dashboard-transcript-rendering`** — one verb ("consume") that the AI
  correctly interpreted as *fold-in + preserve-nothing-lost*, not delete.
- **`is it possible to validate the solution with some mock tests?`** — turned a design doc
  into a de-risked design with passing real-code tests. Reusable phrasing:
  *"which of these claims can we prove in a unit test vs. need a browser/trace?"*
- **`doubt review`** — invoked the discipline skill by name; the proposal itself had listed it
  as a gate, so the loop closed cleanly.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Want to theorize / offer both forks | `1` (pick a thread) | State the chosen direction in the goal prompt |
| Blindly trust an external proposal | `Import, but check the usable parts` | Always ask for a claim→repo-reality audit on imported artifacts |
| Risk *deleting* a diagnosis change | `consume proposal lag-…` | Say "consume" (fold + preserve), never "remove" |
| Stop at a design doc | `is it possible to validate…?` | Ask for the 3-layer test split up front |
| Ship design on its own confidence | `doubt review` | Name `doubt-driven-review` in the proposal's Discipline Skills line |
| Bundle a small fix into a huge uncommitted diff | `I've committed first parts, recheck` | Map the uncommitted surface before staging; commit only your files |

The recurring quality bar: **capture/validation only, no feature code** — the operator held
the explore boundary until a genuine live bug justified crossing it, then scoped that fix
tightly.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were saved, but three existing skills carried the session:

- **`openspec-explore`** — the stance that kept the AI grounding-before-building and producing
  validatable artifacts. Invoke it whenever a change is fuzzy and you want thinking captured as
  specs, not code.
- **`doubt-driven-review`** — the adversarial gate. Its highest value here was the
  **cross-model escalation**: a second architecture (GPT-5) found premises Claude's own review
  missed. Invoke before any structural, hard-to-revert design lands; always take the
  cross-model offer for load-bearing claims.
- **`scenario-design` / test-split discipline** — the unit-vs-browser-vs-trace triage that
  turned a design into a de-risked one with a real characterization test.

*Recommend creating:* a small **"import-and-audit external OpenSpec change"** skill capturing
the claim→repo-reality table + de-dangle-dependencies + consume-not-delete moves — this
session reinvented that workflow ad hoc.

## 7. Pitfalls & dead ends

- **Vitest needs an ephemeral HOME** — the first run tripped the test-isolation guard; retry
  with `HOME=$(mktemp -d) npx vitest run …`.
- **Stale/dangling refs in external proposals** — the umbrella cited `useMessageHandler.ts:307`
  (real is `:296`), a wrong `truncateOutputForDisplay` location, and a Phase-4 dependency on a
  *nonexistent* change. Audit every factual claim before importing.
- **`groups.json` auto-churn** — the openspec tooling reshuffles *other authors'* changes into
  it; committing it bundles cross-author churn. Exclude it (it's regenerable board metadata).
- **A one-line fix can hide inside a huge uncommitted diff** — the ping-pong guard was embedded
  in an unshipped virtualization implementation. Map the full uncommitted surface (`git status
  --short`, grouped) before staging under a narrow commit message.
- **`test.fixme` for blocked e2e** — write the skeleton mapped to requirements but keep it
  skipping (not red) until the unblocking fixture lands; make the blocker explicit in tasks.
