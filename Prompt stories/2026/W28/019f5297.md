# How we did it: Clearing 17 stale KB DOX rows — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with a single terse line: *"There is 17 stale im kb index"* — a bare
observation, not an instruction. The **real objective**, once unpacked, was: *figure out
what "stale in the KB index" means, decide whether each of the 17 files needs a real
`AGENTS.md` documentation update or just a re-acknowledgement, apply the minimum correct
change, and drive the stale count back to 0.* The only later steering turn — `commit` —
confirmed the intent was to land a real fix, not just explain the signal.

## 2. TL;DR playbook

1. **Identify the signal source.** The stale count comes from
   `.pi/dashboard/kb/dox-staleness.json` — each source file keyed to the SHA it had when
   its owning `AGENTS.md` row was last acknowledged. Stale = current content ≠ acked SHA.
2. **List the offenders:** `npx kb dox lint --json` (fall back to `node packages/kb/dist/cli.js`).
3. **Group the 17 stale files by their owning `AGENTS.md`** so you review per-tree-file,
   not per-source-file.
4. **Triage each row with git history:** `git show <sha> -- <file>`. Ask "does the row's
   `See change:` trail already cover the latest commit?" If yes → **re-ack only**. If the
   role/exports actually changed → **edit the row**.
5. **Edit only the rows that drifted** (here: 6 substantive + 1 line-count fix). Match the
   existing row style and append the `See change:` trail entry.
6. **For a source file with NO owning row** (here `vitest.config.ts`), it's a genuine doc
   gap → add a new row. Under `docs/`, delegate the write to a subagent in caveman style
   (Rule 6).
7. **Re-acknowledge the rest** by writing current SHAs into `dox-staleness.json` (mirrors
   the extension's `acknowledgeRows`). Editing an `AGENTS.md` auto-clears its rows via the
   running kb-extension hook; only the untouched rows need the manual re-ack.
8. **Verify `stale count == 0`**, then `git add` only the `AGENTS.md` files and commit
   docs-only.

## 3. How the collaboration unfolded

**Phase 1 · Decode the signal (Discovery).** The AI did not guess. It ran `kb --help` and
`kb dox lint --json`, located `dox-staleness.json`, and grepped the kb-plugin/kb-extension
source for `staleCount`/`acknowledgeRows` to learn exactly how staleness is computed and
cleared. *Why it worked:* it reconstructed the mechanism from source before touching
anything, so every later edit was grounded in how the system actually re-acks.

**Phase 2 · Group & triage (Gather).** It bucketed the 17 files under 6 owning `AGENTS.md`
files, then walked git history (`git show <sha> -- <file>`) for each. This split the work
cleanly into *"row already documents this change → re-ack"* vs *"row is out of date → edit"*.
*Decision point:* the AI explicitly surfaced the two resolution paths (bulk re-ack vs
per-row review) and chose the correct, higher-effort one — verifying each row rather than
blindly re-stamping SHAs.

**Phase 3 · Apply minimum correct change (Design/Generate).** Only 6 rows had substantive
drift (browser-gateway, memory-event-store, meta-persistence, session-scanner, event-reducer,
rehydrate-session) plus one stale line-count (`server.ts ~1766→~2099`). The AI edited exactly
those. For `vitest.config.ts` — a root config file with no row — it delegated the new
`docs/AGENTS.md` row to a `general-purpose` subagent in caveman style.

**Phase 4 · Re-ack & verify.** Editing the `AGENTS.md` files triggered the live
kb-extension's `acknowledgeRows` hook, auto-clearing 13 of 17. A short Python script then
re-acked the remaining 4 whose rows correctly needed no change. Final verify: **0 stale**
across all 394 acked rows.

**Phase 5 · Commit.** On `commit`, the AI staged **only** its 3 `AGENTS.md` files and
explicitly left unrelated tree noise (`openspec/groups/groups.json`, untracked `b05_*.txt`)
out — a clean docs-only commit `072cd5263`.

## 4. Prompts that worked

- **Goal prompt — "There is 17 stale im kb index"** (weak but salvageable). It named the
  symptom and the exact count, which was enough for the AI to locate the signal. **Stronger
  rewrite:** *"`kb dox lint` reports 17 stale DOX rows. Triage each: update the `AGENTS.md`
  row only where the source's role/exports actually changed, re-ack the rest, drive the
  stale count to 0, then commit docs-only."*
- **High-leverage follow-up — "commit".** One word, but it unlocked the closing phase and
  implicitly demanded a clean, scoped commit. The AI honored scope discipline without being
  told which files to include.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Potentially bulk re-ack all 17 (fast but wrong — hides real drift) | (Implicit) the goal framed it as "stale", inviting real review | State up front: "verify each row against git; edit where role/exports changed, re-ack only where the trail already covers it" |
| Risk committing unrelated working-tree noise | "commit" (trusting scope judgment) | Say "commit docs-only, stage only the `AGENTS.md` files you changed" |
| Truncated command output hid the server rows | AI self-corrected with a targeted re-pull | Prefer `grep -nE '<row-names>'` over dumping whole files |

The key guardrail: **staleness is not automatically a doc bug.** A stale flag can mean "the
row already documents this, it just wasn't re-acked." Distinguish *re-ack* from *rewrite*
before editing.

No new skill or memory was created — this was a targeted maintenance pass. But the workflow

The reusable tool moves worth remembering:
- `npx kb dox lint --json` — the authoritative stale/missing/orphan report.
- Editing an owning `AGENTS.md` **auto-re-acks** its rows via the live kb-extension hook;
  only untouched-but-stale rows need a manual SHA write into `dox-staleness.json`.
- Under `docs/`, new rows are written by a subagent in caveman style (Rule 6), never by the
  main agent directly.

## 7. Pitfalls & dead ends

- **Bulk re-ack is the tempting trap.** Writing every current SHA into `dox-staleness.json`
  makes the count 0 without documenting the actual code drift — you lose the signal. Always
  triage first.
- **Command output truncation.** A `for f in … cat` dump was cut off before the server rows
  arrived. If a batch read truncates, re-pull the specific rows with `grep -nE`.
- **Don't over-stage.** `git status` showed unrelated files (`groups.json`, `b05_*.txt`);
  staging `git add -A` would have polluted a docs-only commit. Add only the files you changed.
- **A stale file with no owning row is a real gap, not a re-ack.** `vitest.config.ts` had no
  `docs/AGENTS.md` row — that needed a *new* row (delegated), not a SHA bump.
