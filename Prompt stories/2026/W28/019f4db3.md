# How we did it: diagnosing a permanently-stuck tool card and drafting the supersede-heal proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
no implementation allowed, but OpenSpec artifacts permitted. The real objective that
emerged: figure out *why a dashboard tool card can spin "executing" forever* (observed at
2m 5s with no recovery) even though the session keeps rendering later cards normally, then
**capture the diagnosis as a reviewable OpenSpec change proposal**. The first prompt set
the stance; the human's screenshots and one-line clarifications drove the diagnosis from a
wrong first theory to the correct root cause.

## 2. TL;DR playbook

1. Enter `openspec-explore` — thinking only, artifacts allowed, no code.
2. Ground the theory in **how the machinery actually runs** before hypothesizing (read pi's
   `bash.js` / `child-process.js` — don't guess at the exit-detection path).
3. When a screenshot **contradicts** the theory (a plain `Read` with no process also hangs),
   *drop the theory* and move up to the shared path both tools traverse.
4. Follow the shared lifecycle: tool-event forwarder → server store → browser reducer.
   `grep` for the reducer in the **right package** (`packages/client/src`, not `web/src`).
5. Let the codebase confirm you: the `useStaleToolReconcile.ts` header comment *already*
   documents the dropped-`tool_execution_end`-under-backpressure bug.
6. Find the **uncovered hole**: the shipped heal only covers HOP 2 (server→browser); a loss
   on HOP 1 (bridge→server) means the store never had the result → HTTP heal 404s forever.
7. Read the base change (`fix-stuck-tool-card-on-dropped-event`) to scope a clean complement,
   not an overlap — it *explicitly* leaves the store-eviction case "row running".
8. Draft the change dir; validate with `openspec validate <name> --strict` until clean.
9. On request, add an **## Open Caveats (pick up later)** section for deferred decisions.
10. Stage **only** your change dir (`git add openspec/changes/<name>/`), commit, push.

## 3. How the collaboration unfolded

**Phase 1 — Ground the first theory (bash exit detection).** The AI read pi's own
`core/tools/bash.js` + `utils/child-process.js` and diagrammed `waitForChildProcess`'s
three-signal completion detection ('exit' / stdout 'end' / stderr 'end' / 'close'). It
framed the bug as a classic "lost exit" from a detached descendant holding the pipe open.
*Why it worked:* grounding in real source before theorizing produced a precise, defensible
first hypothesis — and made the next step's contradiction meaningful.

**Phase 2 — The screenshot that killed the theory.** The human posted a screenshot showing
a plain `Read` of `CHANGELOG.md` stuck at "0 done / 2m 5s". A `Read` is `fsReadFile` — no
process, no pipe. The AI immediately **abandoned** the bash story: "my process-exit theory
can't explain this one," and reframed as *two different bugs wearing the same costume*.
*Decision point:* the human supplied counter-evidence; the AI let it override its own prior.

**Phase 3 — The decisive clue.** The human added: "it executed, because the session
continues, just the Edit/cat etc. tools stayed as executing." That ruled out "pi is wedged"
entirely: event loop alive + card never flips = a **lost/unapplied tool-completion event in
the dashboard**. The AI grep'd the client reducer (correcting `web/src` → `packages/client/src`)
and found `useStaleToolReconcile.ts` + `coalesce-live-events.ts`.

**Phase 4 — Codebase self-confirmation + the uncovered hole.** The reconcile hook's header
comment already described the dropped-`tool_execution_end`-under-backpressure bug and its 25s
heal. But the screenshot showed 2m 5s. The AI traced the **two WS hops**: HOP 1 bridge→server
(ring buffer evicts oldest while disconnected), HOP 2 server→browser (healed via HTTP). Only
HOP 2 is covered; a HOP-1 loss means the store 404s forever — the real gap.

**Phase 5 — Scope a clean complement + draft artifacts.** The AI read the still-active base
change, confirmed it *deliberately* "keeps the row running" on 404, and drafted
`fix-stuck-tool-card-superseded-heal` (proposal + design with a Mermaid state machine + spec
delta + TDD tasks). Validated `--strict`. Then, on "write caveats," added **## Open Caveats**
(C1 display-heal-not-recovery, C2 attribution-still-inferential). Committed only the change dir.

## 4. Prompts that worked

- **Goal / stance prompt** (`openspec-explore`): effective because it licensed *artifact
  creation while forbidding implementation* — the AI could capture the full diagnosis as a
  proposal without prematurely coding a fix.
- **"There is other stucked entries… [image]"** — the single highest-leverage turn. A
  screenshot of a *counter-example* (a `Read`, not a `bash`) forced the AI off a plausible-
  but-wrong theory. Lesson: when the AI is confidently wrong, one contradicting artifact
  beats a paragraph of argument.
- **"I think it executed, because the session continues, just the Edit, cat etc. tools stayed
  as executing"** — a precise behavioral observation that eliminated an entire branch
  ("pi is wedged") in one line.
- **"draft proposal" / "Write caveats to proposal to be able to pick in later" / "commit and
  push"** — terse, unambiguous transition prompts. Each moved a completed phase to the next
  with zero wasted tokens.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session. The reusable asset produced is the **OpenSpec
change** `fix-stuck-tool-card-superseded-heal` itself — a reviewable, `--strict`-valid
artifact that:

- Captures the two-hop loss model and the *uncovered* HOP-1 case in `design.md` (with a
  Mermaid state machine), so the fix decision survives outside the chat.
- Frames the fix as a **supersede-proof fallback**: proof = a *later turn* (not a sibling
  `tool_start`, for parallel-tool safety), fire only after recovery is exhausted (≥2×404),
  reuse `complete` + `healedBy:"superseded"` (no new enum), count + badge every heal.
- Records the two open caveats as *pickable* follow-ups (C1 real source fix: never-evict the
  latest `tool_execution_end` keepalive ring; C2 live-confirmation to distinguish
  store-eviction from transport drop).

**Recommended skill to create:** a "diagnose-stuck-tool-card" project skill — the trace path
(non-process counter-example → session-continues tell → `packages/client/src` reducer →
`useStaleToolReconcile.ts` → two-hop model) is a repeatable investigation worth codifying.

## 7. Pitfalls & dead ends

- **Grounding a theory in the wrong layer.** The bash-exit theory was well-researched but
  wrong for the reported symptom — because it only fit *one* tool type. If a bug reproduces
  across process and non-process tools, the cause is *above* the individual tool. Test your
  theory against the counter-example before drafting around it.
- **Wrong grep root.** `web/src` returned empty; the client is `packages/client/src`. Confirm
  the package before assuming the reducer is missing.
- **HTTP heal 404s forever** when the loss is on bridge→server (store never had the result) —
  the shipped 25s reconcile can't cover it; that's the hole the new change closes.
- **Committing stray files.** Unrelated `b05_*.txt` files sat in the tree; a blanket
  `git add -A` would have swept them in. Stage the change dir explicitly.
