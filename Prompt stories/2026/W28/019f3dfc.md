# How we did it: Bridging skills to subagents — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`/skill:openspec-explore`) — a thinking stance,
not an implementation task: "Enter explore mode. Think deeply… follow the conversation
wherever it goes." The *real* objective that emerged through steering: **decide which of
the repo's ~21 extension skills should be wrapped as isolated subagents, route each to the
best-suited model/provider by function, and capture that as a design doc** — then, later,
**verify the sibling `pi-dashboard-subagents` repo's actual state against the doc** and
correct a stale/false justification about SDK project-trust. It became a
planning + reconciliation session, not a feature build.

## 2. TL;DR playbook

1. Start in `openspec-explore` mode so the AI investigates and documents but never
   implements. Ask the framing question: *"can a skill BE a subagent, and which of mine
   should be?"*
2. Have the AI ground the mechanism in the real pi docs (skill = loaded into parent
   context; subagent = isolated context, own model + tool allow-list, returns a distilled
   summary) before it proposes anything.
3. Pull the **live role/provider map** (`@fast`, `@research`, `@coding`, `@vision`,
   `glm`/opus) so model recommendations map to models you actually have.
4. Have it **fitness-score every skill** into Tier A (wrap now) / B (wrap analysis only) /
   C (leave inline — user-loop skills like `interview-me`, `frontend-mockup-loop`).
5. Generate the deliverable: `docs/skills-as-subagents.md` (Mermaid bridge diagram +
   routing table) + a few Tier-A wrapper agents under `.pi/agents/`.
6. Before moving wrappers into per-package dirs, **read the resolver** — confirm whether
   a discovery tier even scans that path. (Here it did not: surface the blocker first.)
7. When told "check the sibling repo", verify shipped code against the proposal **by
   reading git log + the actual functions**, not the prose. Reconcile drift explicitly.
8. If you find a false claim in a doc/spec/comment, apply a **minimal prose-only
   correction** (no behavior change) across every *live* occurrence; leave archived
   history and stale worktree copies untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery & grounding.** The AI inventoried all `SKILL.md` under `packages/`,
read the pi skills/subagent docs, and searched past sessions. Key move: it grounded the
"can a skill be a subagent?" question in the docs *before* recommending — establishing that
they are two orthogonal mechanisms you *bridge* with a thin `.pi/agents/<Name>.md` shell.

**Phase 2 — Routing by function (steering #1).** The user added: *"check what model
provider is best suited to given subagent."* The AI pulled the real role map and produced a
function→role table (glue/lookup → `@fast`; synthesis → `@research`; code → `@coding`;
visual → `@vision`; map-reduce → chunks `@fast`, merge `@research`). This mapped advice to
models that actually exist.

**Phase 3 — Generate (steering #2 "agents on same extension as the skills").** The AI
wrote `docs/skills-as-subagents.md` + 4 Tier-A wrappers, then — critically — **read the
resolver before co-locating them** and surfaced a blocker: the `pi-dashboard-subagents`
`resolveAgentMdPath()` had a fixed 3-tier lookup (project / user / subagents-pkg-bundled)
with **no tier scanning per-package `.pi/agents/`**. So the user's instinct (atomic
per-package delivery) was right, but undeliverable today. It documented co-location as a
§8 follow-up instead of moving files into a never-scanned dir.

**Phase 4 — Verify the sibling repo (steering #3 "check it").** The AI inspected git state
and found the discovery tier was **already shipped, wired, merged (PR #1), and archived —
user-scope only** — not merely proposed. It validated every load-bearing SDK claim against
the real `.d.ts`, and caught the state shifting under it (the change got archived mid-session).

**Phase 5 — Correct the false premise (steering #4 "yes").** The archived spec + a code
comment justified "no project-scope" with *"`ExtensionContext` has no `isProjectTrusted()`"*
— but the AI verified that method **does** exist in the current SDK (likely added by an SDK
bump after the claim was written). Since archived history is immutable, it applied a
**minimal, prose-only** reframe ("deliberate conservative design choice, not an SDK
limitation") across all 4 *live* occurrences, preserving user-scope-only behavior.

## 4. Prompts that worked

- **The goal prompt** (`openspec-explore`): effective because the stance forbids
  implementation — it forced the AI to *think and document*, producing a grounded design
  instead of premature code. Reuse it for any "should we / how would we" architecture question.
- **"check what model provider is best suited… collect best suitable provider for
  function"** — a high-leverage add that turned generic advice into a concrete routing
  table tied to the real role map.
- **"The agents be on same extension as the skills. It helps to deliver consistently"** —
  a one-line design constraint that triggered the resolver check and surfaced the whole
  discovery-gap blocker.
- **"The changes made in pi-dashboard-subagent project, check it"** — short redirect that
  pivoted from designing to **verifying reality**, which is where the false-claim bug was found.
- **"yes"** — a single-word unlock approving the minimal-correction path.

Stronger rewrite of the terse ones: instead of *"check it"*, say
*"verify the sibling repo's shipped code against this doc — read git log and the actual
functions, flag any drift or false claims before editing."*

## 6. Skills, tools & memory created — and why they're effective

- **Memory saved (project):** the subagent **discovery gap** — skills are scanned
  per-package by pi core (`packages/*/.pi/skills/*`), but agents are resolved by
  `pi-dashboard-subagents`'s `resolveAgentMdPath()` with no per-package tier. *Why
  effective:* future sessions won't re-discover this the hard way before co-locating
  wrappers. *When to invoke:* any time someone proposes bundling agents inside a skill's
  package. (Project memory was at capacity; the fact was durably captured in
  `docs/skills-as-subagents.md` §8 + the `docs/AGENTS.md` row instead.)
- **Artifact — `docs/skills-as-subagents.md`:** the reusable playbook itself (skill↔subagent
  bridge, fitness tiers, function→role routing, §8 co-location follow-up).
- **No skill was created**, but the repeatable move here — *"grade my skills for
  subagent-wrapping and route them by model"* — is exactly the kind of thing worth turning
  into a reusable `skill-to-subagent` fitness pass.

## 7. Pitfalls & dead ends

- **Colon-space YAML trap:** an agent `description:` containing `Map-reduce:` (colon-space)
  can silently drop the agent. If an agent won't load, grep the *value* (not the key) for
  `: ` and quote/rephrase it.
- **grep flooding on `.d.ts.map`:** verifying SDK surface, a broad grep caught sourcemaps.
  Constrain to `-name '*.d.ts'` (exclude `.map`).
- **Malformed tool call at start:** the first `ctx_batch_execute` used the wrong schema
  (4 of 8 batch calls errored). Re-issue with the correct schema rather than improvising.
- **Editing the wrong tree:** an edit hit ENOENT because the change had been **archived**
  (`archive/2026-07-07-…`). If an expected path is gone, re-scan git state before editing.
- **Don't edit archived/immutable history** or stale worktree checkouts — fix only *live*
  occurrences.
