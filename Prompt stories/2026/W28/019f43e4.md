# How we did it: Diagnosing a stuck "Reading…" tool card into an evidence-backed OpenSpec change — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **`openspec-explore` mode** — a thinking-partner stance, no code
allowed. The concrete symptom that seeded it: a dashboard tool card was stuck showing
`Reading…` with a spinning icon at **1m 44s** for a `Read ChatView.tsx`, while *later*
tool cards in the same session had already completed. The real objective, once the
exploration clarified it: **find the true root cause of the stuck card, prove it with
evidence, and capture the fix as an OpenSpec change proposal** — without touching
application code (explore-mode discipline). The finished artifact was the change
`fix-stuck-tool-card-on-dropped-event` (proposal + design + spec delta + tasks),
validated strict, then committed.

## 2. TL;DR playbook

1. **Reframe the symptom before chasing it.** A `Read` "stuck at 1m 44s" is impossible —
   plain reads are milliseconds. The tell: *later* tool calls in the same turn already
   completed, and tool calls run **sequentially**. So the read returned; the **dashboard
   card** is stale, not the process. State this reframing first.
2. **Trace the event path end-to-end** across the three hops:
   `pi bridge ──ws──► server ──ws──► React client`. Use the docs-first protocol
   (`kb_search`, directory `AGENTS.md` tree) before grepping source.
3. **Locate every silent drop point.** Found two: (A) `connection.ts bufferMessage()`
   ring-buffer `buffer.shift()` evicts the *oldest* buffered frame; (B)
   `browser-gateway.ts` fanout `if (ws.bufferedAmount > MAX_WS_BUFFER) continue` skips a
   frame with no retry/log. Plus the client's **max-watermark** seq cursor with **no gap
   detection**.
4. **Get empirical evidence from the server log** — but honestly. Both drop sites are
   **100% silent** (zero log statements), so you can only find *correlating* conditions
   (event-loop stalls, disconnect churn) not the drop itself. Say so explicitly.
5. **Run a coherence check before writing the proposal.** The bug was already encoded in
   the existing `incremental-event-sync` spec → the change must **MODIFY** that
   requirement, not invent a new capability.
6. **Scaffold via the OpenSpec CLI**, write all four artifacts, `openspec validate
   --strict` until green.
7. **Run `doubt-driven-review` on your own proposal** — adversarially attack the
   load-bearing assumptions. Here two of three broke, forcing a descope.
8. **Descope to the minimal robust fix** (HTTP backstop + instrumentation), defer the
   fragile mechanism (gap-detection), re-validate, commit.

## 3. How the collaboration unfolded

**Phase 1 — Reframe (Discovery).** The AI's first move was the highest-leverage one:
it *refused the obvious framing*. Instead of debugging a "hung read", it noticed the
screenshot showed later tool calls already `✓ COMPLETED` — and since pi runs tool calls
sequentially, the ChatView read **must** have returned. Conclusion: the stuck thing is
the **dashboard card**, not the read. *Why it worked:* it reasoned from an invariant
(sequential tool execution) rather than the surface symptom.

**Phase 2 — Trace the three hops (Gather).** Using `kb_search` + the directory
`AGENTS.md` tree, then targeted greps, the AI walked bridge emit → server relay → client
reducer. It confirmed the client reducer pairs `tool_execution_start`/`_end` robustly by
`toolCallId` (`findLastIndex`), so a **key mismatch was ruled out** — the `end` event
simply never arrived. It then found **two silent drop points** and a **non-contiguous
(max-watermark) seq cursor with no gap detection**.

**Phase 3 — Empirical evidence, kept honest (Verify).** The user steered "get evidence
from the log". The AI processed a 28 MB / 333 k-line server log and — crucially —
*led with the caveat* that both drop sites log nothing, so the log can only show
*ambient conditions* (1,473 genuine 5–60 s event-loop stalls; 3,688 client
disconnects), not the specific drop. It even separated laptop-sleep artifacts (multi-hour
"stalls") from real CPU stalls to keep the numbers honest.

**Phase 4 — Coherence + scaffold (Design).** Before writing, a coherence check found the
bug lives *inside* the existing `incremental-event-sync` spec's "Client-side sequence
tracking" requirement (which explicitly mandates the max-watermark). So the change
**MODIFIES** that requirement + **ADDS** three. Scaffolded via the CLI, wrote four
artifacts, hit a parser quirk (requirement statement read only line 1 → reworded so
`SHALL` lands on line one), validated strict.

**Phase 5 — Doubt review breaks the design (Adversarial).** The user typed
`doubt review` (twice). The AI attacked the three load-bearing assumptions and **two
broke**: the seq-based heal is **structurally blind to drop A** (seq is assigned
*server-side on ingest* — `memory-event-store.ts` `buf.nextSeq++` — so a bridge→server
drop never gets a seq, leaving the client's stream contiguous → no gap), and the REST
backstop **404s** when the event was never recorded. This forced a descope.

**Phase 6 — Descope, cross-reference, commit.** v1 became **backstop + instrumentation
only** (backstop uses HTTP, structurally independent of the WS buffer that caused the
drop); gap-detection was deferred as an evidence-gated latency optimization. The user
asked whether this related to `virtualize-chat-transcript-tanstack` — the AI showed they
are orthogonal (delivery integrity vs render perf) with one real interaction
(virtualization unmounts off-screen rows → the backstop timer must be state-scoped, not
component-scoped). Then `commit`: the change turned out already committed
(`28e0c2b5e`) with a full implementation done by a concurrent session, matching the
*corrected* design exactly.

## 4. Prompts that worked

- **The goal prompt** — entering `openspec-explore` with a concrete symptom + screenshot.
  Effective because it set a *thinking-only* stance (no premature code) while handing the
  AI a falsifiable anomaly ("read stuck 1m 44s, later cards done").
- **`doubt review`** (×2) — the single highest-leverage follow-up. Two words invoked the
  `doubt-driven-review` discipline and broke two load-bearing assumptions *before* they
  became an implementation plan. Rewrite-stronger version: *"Run doubt-driven-review on
  this proposal — attack every load-bearing assumption empirically, don't re-assert it."*
- **`is this change related to virtualize-chat-transcript-tanstack?`** — a scope-boundary
  probe that produced an explicit orthogonality analysis + the one real interaction
  constraint (session-scoped timer). Ask this whenever two changes touch the same surface.
- The terse steering (`a`, `II`, `i`, `1`, `ok`) were menu/branch selections inside
  explore mode — fine here, but a future operator should prefer naming the direction.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created, but the session is a **canonical demonstration of two
existing disciplines** worth codifying as a reflex:

- **`doubt-driven-review` before a proposal becomes a plan.** It removed a real overclaim
  (seq-based heal can't cover the bridge→server drop) and shrank the change to the minimal
  robust fix. Invoke it on *every* non-trivial proposal, especially transport/consistency
  work where "it heals" claims are easy to assert and hard to verify.
- **Context-mode / in-sandbox log processing for large logs.** A 28 MB log was mined for
  signal without loading it into context. Invoke whenever a log exceeds a few thousand
  lines.

**Recommended skill to create:** *"diagnose a stuck/stale dashboard tool card"* — encode
the reframe (sequential tool calls prove completion → card is stale), the three-hop trace,
the two silent drop points, and the honest-evidence caveat. This exact class of bug will
recur.

## 7. Pitfalls & dead ends

- **`openspec change new` is not a subcommand.** The CLI surface differs; check
  `openspec --help` / `openspec new --help`, or create the change directory manually
  (the convention permits it).
- **`openspec validate --strict` "SHALL missing" is a parser quirk.** It reads the
  requirement *statement* as only the **first line**. If line 1 lacks `SHALL`, it fails
  even when `SHALL` appears below. **Fix:** reword so `SHALL` lands on line one. A stray
  `offset` field in the delta also trips it.
- **Both drop sites are 100% silent** — you *cannot* find the specific dropped event in
  the log. Don't claim you did; report *correlating conditions* only. The silence is
  itself a finding: the system can't tell you which hop lost the event (→ the
  instrumentation task).
- **Multi-hour "event-loop stalls" are laptop-sleep artifacts**, not CPU blocks. Filter
  them out (>10 min) before quoting stall counts.
- **`seq` is assigned server-side on ingest**, so any seq-based client heal is blind to a
  bridge→server drop. Don't design gap-detection as the primary heal for drop A.
- **A concurrent session may already be implementing your change.** Before committing,
  `git log`/`git show` the change dir — the implementation (`28e0c2b5e`) already existed.
  Commit only your files; leave unrelated working-tree changes (generated files, scratch)
  untouched.
