# How we did it: designing a churn-proof chat-selection fix — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The operator opened in **explore mode** (`openspec-explore`) with a UX bug: in the dashboard's
`ChatView`, highlighting text inside a transcript card to copy it keeps collapsing the moment
the transcript churns (a new card arrives, the streaming tail re-renders, or auto-scroll pins
to bottom). The literal first prompt was the explore-mode skill preamble — *"Enter explore mode.
Think deeply… you must NEVER write code."* The **real objective**, once steering clarified it,
was to turn that fuzzy annoyance into a rigorous, apply-ready **OpenSpec change** — proposal,
design, spec deltas, and tasks — whose design had already survived adversarial review *before a
single line of code existed*. The output is a planning artifact, not an implementation.

## 2. TL;DR playbook

1. **Start in `openspec-explore`, not in code.** Ground the theory in the real source first:
   find `ChatView.tsx`, confirm it's a TanStack-Virtual windowed list, inspect the virtual-row
   **key** stability and the streaming-tail render path.
2. **Nail the ambiguous case with `ask_user` before scaffolding.** The bug had two candidate
   surfaces (transcript cards vs. composer input); one clean disambiguating question changed the
   entire fix.
3. **Check adjacent OpenSpec changes** (`fix-table-copy-empty-clipboard`,
   `virtualize-chat-transcript-tanstack`) so the new proposal doesn't overlap or contradict prior art.
4. **Fast-forward the artifacts** with `openspec-ff-change`: proposal → design → spec deltas → tasks,
   validating after each (`openspec validate <change>`).
5. **Run a doubt-driven review on the design *before* implementation** — spawn a fresh-context
   `Explore` reviewer that reads the actual `@tanstack/react-virtual` source to attack load-bearing claims.
6. **Add a cross-model second opinion.** Enumerate *reachable* models with `list_models`, pick a
   different architecture family than the author (Claude → DeepSeek), and re-review. Surface empty
   model output as a failure; fall back to a reachable model.
7. **Reconcile as orchestrator, not rubber stamp:** classify every finding, fold the fixes into
   *all four* artifacts, and re-validate.
8. **Commit only your change directory** — stage the one change folder explicitly, leave unrelated
   untracked dirs alone, and record the doubt-corrected rationale in the commit body.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground before theory).** The AI resisted the urge to theorize. It grepped for
`ChatView`, `getSelection`/`userSelect`/`selectionchange`, and the virtual-row key helper, and found
the decisive clue: the transcript is a **TanStack-Virtual** window (`useVirtualizer`, `overscan: 6`),
so a browser `Range` anchored to live Text nodes dies the instant those nodes unmount. It also spotted
prior art (`fix-file-preview-survives-message-churn`) showing the team had fought "message churn" before.

**Phase 2 — Disambiguate the surface.** An early `ask_user` came back ambiguous (a double-barreled
question). Rather than guess, the AI asked one clean follow-up and locked the case: **Path A + B,
transcript cards, either scroll position.** That precision is what let the mechanism become exact —
Path A (finished `React.memo` cards die only on virtualizer *unmount*) vs. Path B (streaming tail
re-renders markdown every chunk → Text nodes replaced).

**Phase 3 — Generate the artifacts.** With `openspec-ff-change`, the AI scaffolded the change, read the
existing specs it had to MODIFY (to copy exact requirement blocks), and wrote design + 3 spec deltas +
tasks, validating after each. A parser quirk surfaced: the validator reads only the **first line** of a
requirement, so a `SHALL` wrapped to line 2 failed — fixed by putting SHALL on line 1.

**Phase 4 — Doubt-driven review (twice).** This is where the session earned its cost. Before any code,
the AI ran the `doubt-driven-review` cycle: CLAIM → EXTRACT (artifact + contract only, no reasoning
leaked) → DOUBT (fresh-context `Explore` reviewer) → cross-model second opinion → RECONCILE → STOP. The
reviewers **read the real `virtual-core` source** and disproved a load-bearing design claim (that
mounting extra rows wouldn't change `getTotalSize()` — it does, via `measureElement → resizeItem →
itemSizeCache`). The fix: use the virtualizer's own **`rangeExtractor`** to union selection indices into
the mounted range. A second doubt cycle on the later ceiling/copy-fidelity material went deeper still,
citing DOM **§live-range-pre-remove-steps** to prove "past-N collapses visibly" was actually **silent
truncation** — the exact bug they claimed to prevent — and that the reactive framing lost a synchronous
race, forcing a *proactive* anchor-capture design.

**Phase 5 — Fold & commit.** After each review the AI reconciled every finding into proposal, design,
specs, and tasks (catching that `proposal.md` lagged the other three more than once), re-validated to
green, then committed **only** the one change directory, leaving two unrelated untracked change dirs
untouched, with the corrected rationale in the commit body.

## 4. Prompts that worked

- **The goal prompt (`openspec-explore`):** effective because it set a *stance* — investigate, never
  implement — which kept the AI grounding in real source instead of jumping to a patch. Reuse it for any
  "I have a fuzzy bug, help me think" task.
- **`"doubt review"` / `"doubt review, the secondary model is deepseek pro"`** — the highest-leverage
  prompts in the session. Three words invoked a full adversarial cycle; specifying the cross-model
  reviewer inline (`deepseek pro`) pre-wired the second opinion so the AI didn't have to guess.
- **`"keep exploring"`** — unlocked the ceiling analysis (what N should be) that a stricter scope would
  have skipped; good for "there's more to think about here" moments.
- **`"add to this proposal"` / `"add to proposal"`** — terse folding commands. *Weakness:* the AI twice
  updated design/specs/tasks but lagged `proposal.md`. **Stronger version:** *"fold this into ALL four
  artifacts (proposal, design, specs, tasks) and re-validate."*
- **`"commit"`** — fine as a closer because the AI already knew to stage only the relevant directory.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session — but the workflow leaned hard on existing assets worth
naming:

- **`openspec-explore` + `openspec-ff-change`** — the explore→fast-forward pair turns a fuzzy bug into a
  validated 4-artifact change without ever entering implementation. Invoke when you have a symptom and
  need a rigorous, apply-ready spec.
- **`doubt-driven-review`** — the star. It runs CLAIM/EXTRACT/DOUBT/RECONCILE/STOP *before* code, so a
  wrong design assumption costs an edit, not a shipped regression. Invoke whenever a design asserts
  unverifiable properties about a third-party library's internals (here, TanStack Virtual + DOM Range
  semantics).
- **Cross-model adversarial review pattern** — spawn a reviewer from a *different architecture family*
  than the author (Claude author → DeepSeek/GPT reviewer) so blind spots aren't shared. **Recommend
  capturing this as a reusable skill:** "pick-a-non-author-model-for-review" (enumerate reachable models,
  exclude the author's family, surface empty output as failure).

## 7. Pitfalls & dead ends

- **`openspec change new <name>` is the wrong subcommand** — it failed; the correct form is
  `openspec new change <name>`. If scaffolding errors, check `openspec new --help`.
- **Validator reads only the first line of a requirement.** A `SHALL` that wraps to line 2 fails
  validation. Keep SHALL on the requirement's first line.
- **`openspec validate` post-proposal "errors" are expected** — it checks full-change readiness, and
  spec deltas are the *next* artifact. Don't chase them before the design/specs exist.
- **Empty output from a model is a failure, not a clean review.** `openai/gpt-5.2` and `google/gemini-3-pro`
  returned empty; treat that as a probe failure and fall back to a reachable model (`deepseek-v4-pro`).
- **A sandbox/shell var didn't bind** in one turn — the AI just re-read the file directly instead of
  relying on the unset variable. Don't trust cross-tool variable persistence.
- **`proposal.md` drift** — folding review fixes into design/specs/tasks but not the proposal left
  contradictory guidance for a future implementer. Always reconcile the proposal too.
