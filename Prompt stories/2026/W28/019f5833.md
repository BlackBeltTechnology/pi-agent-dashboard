# How we did it: make the pairing QR camera-scannable — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The user entered **explore mode** (`openspec-explore`) with a single problem: the
device-pairing QR code in the dashboard *cannot be handled by a phone's native
camera*. The kickoff prompt was the explore-mode stance itself — "think deeply,
investigate, never implement, you MAY create OpenSpec artifacts." The real objective,
which the investigation surfaced, was: **understand why the pairing QR is inert to a
phone camera, design a fix that keeps the existing security handshake intact, and
capture it as a validated OpenSpec change proposal — without writing implementation
code.** The session ended with a committed, `--strict`-valid change directory.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore` skill) — a *thinking* stance, no implementation.
2. Ground first: `rg` for every QR call site, then `read` the two QR components + the
   pairing spec + the server pair routes. Do not theorize before reading source.
3. Separate the two QR codes explicitly — one is a bare `https://` URL (camera works),
   the other is an opaque `pi:pair:v1.<b64>` payload (camera can't act). Name the crux.
4. Trace who *redeems* the payload today (the Electron `PairView.tsx`) so the fix is a
   **direct port**, not a redesign.
5. Land on the minimal fix: wrap the same payload as `https://<tls-ep>/pair#pi:pair:v1.<b64>`
   — same bytes, now behind a real https link in the URL fragment.
6. Before scaffolding, run a **coherence check** against any in-progress change touching
   the same file (`add-gateway-qr-network-selector`) to avoid conflict.
7. Scaffold the OpenSpec change by copying an existing change's structure (the CLI's
   `change new` was unavailable) — proposal/design/tasks/spec-delta/.openspec.yaml.
8. `openspec validate <name> --strict` → must be valid.
9. Commit **only** the new change directory, leaving unrelated working-tree changes alone.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (grounding, ~2 min).** The AI resisted theorizing and instead
`rg`-searched all QR call sites, then read `QrCodeDialog.tsx`, `GatewayPairQR.tsx`,
and the `qr-device-pairing` spec. *Why it worked:* it discovered there are **two**
QR codes with different behavior, which reframed the whole problem.

**Phase 2 — Root-cause the crux.** It read the server `pairing-routes.ts` and the
Electron `PairView.tsx` redeemer. *Why it worked:* it established that the payload is
consumed by a 4-step handshake (challenge → redeem → confirm → poll) in the desktop
shell — so a phone browser only needs to **replicate** that flow, not invent one. The
bug crystallized: `pi:pair:v1.…` isn't `https://`, so no app claims the scheme.

**Phase 3 — Design the minimal fix.** Decision point: encode `https://<tls-ep>/pair#pi:pair:v1.<b64>`
— the **identical payload in the URL fragment**. A new `/pair` browser view ports the
Electron handshake; desktop typed-approval and the copy-string stay untouched; one QR
serves both phone and Electron.

**Phase 4 — Coherence + scaffold.** The AI checked the in-progress
`add-gateway-qr-network-selector` change (edits the same file, but presentation-only)
and noted the two are complementary. It copied an existing change's directory shape,
wrote proposal/design/tasks/spec-delta, and validated `--strict`.

**Phase 5 — Commit surgically.** On the human's one-word `commit`, it staged **only**
its own change directory, leaving pre-existing unrelated working-tree edits alone.

## 4. Prompts that worked

- **The goal prompt (explore-mode stance).** Effective because it set a hard boundary
  — *investigate and capture, never implement* — which kept the whole session focused
  on producing a proposal rather than drifting into code. A future operator should open
  the same way: `openspec-explore` for a design problem where the fix isn't obvious yet.
- **`commit` (high-leverage one-word follow-up).** After the change was scaffolded and
  validated, a single word closed the loop. It worked because the AI had already earned
  trust by grounding every claim in read source — there was nothing left to steer.

Stronger kickoff to reuse: *"Explore why the pairing QR can't be scanned by a phone
camera. Read the QR components, the pairing spec, and the redeem route before
theorizing. Then capture the fix as an OpenSpec change — don't implement."*

No new skill or memory was created. The session was a clean application of existing
assets:

- **OpenSpec scaffold-by-copy** — because `openspec change new` was unavailable, the AI

*Recommendation:* if this "port an Electron flow into a browser view" pattern recurs,

## 7. Pitfalls & dead ends

- **`openspec change new` isn't in this CLI.** Don't rely on it — scaffold by copying an
  existing `openspec/changes/<name>/` directory (`.openspec.yaml` + proposal/design/tasks
  + `specs/<cap>/spec.md`) and match the delta header format exactly.
- **Two QR codes, not one.** Assuming a single QR wastes the design. Enumerate call sites
  first (`rg qrcode`) so you know which QR is the inert one.
- **Shared-file conflict.** `add-gateway-qr-network-selector` edits the same
  `GatewayPairQR.tsx`; scaffolding blind would have created a silent conflict. Always
  coherence-check in-progress changes on the same file.
- **Dirty working tree at commit.** Pre-existing unrelated edits were present. `commit`
  must stage only the change directory, never `git add -A`.
