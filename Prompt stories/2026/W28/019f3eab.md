# How we did it: Turning pi session logs into training data AND searchable knowledge — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — "a thinking partner,
never an implementer." The first *real* ask arrived one turn later:

> "I would like to train pi jsonl logs of sessions"

The plain-language objective: **build a high-quality LoRA fine-tuning dataset out of this
project's pi session JSONL logs (targeting a 1T-parameter model).** But the steering turns
reframed the goal twice. By the end it had become: *produce a grounded research reference
plus two OpenSpec proposals that split the problem into (a) an **automatic** distill→KB-index
(RAG) path and (b) an **on-demand** LoRA-dataset-export skill* — never writing a line of
implementation, because explore mode forbids it.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) so the AI captures thinking as artifacts and
   refuses to implement — the correct stance for a research + proposal session.
2. **State the grounding constraint early:** "these are *this project's* pi session JSONL
   logs" — that single fact turned a hand-wavy essay into a schema-accurate reference.
3. **Let the AI inspect the real corpus first** (`ls ~/.pi/agent/sessions/`, `node -e` over a
   real `.jsonl`) before it writes anything — every schema claim gets verified, not invented.
4. **Write the reference doc outside `docs/`** (`research/lora-dataset-from-pi-logs.md`) so it
   escapes the repo's caveman-style docs constraint and reads as normal prose.
5. **Pull each new idea into the same doc as a numbered Part** (RAG alternative → transparent
   auto-indexing → lifecycle done-detection → governing decision) so one coherent arc emerges.
6. **Force the AI to reuse, not rebuild:** point it at the existing `session-distiller`
   (`signals.ts::episodeVerifiedGood`, `trajectory.ts` `isError`, `segment.ts CORRECTION_RE`)
   before it proposes new machinery.
7. **Make the automatic-vs-on-demand split explicit** — index = automatic (cheap, headless),
   LoRA export = deliberate skill (expensive, human-gated).
8. **Convert the settled thinking into two OpenSpec changes** (`openspec change new`), each
   with proposal + tasks + spec + the project-required `## Discipline Skills` line, then
   `openspec validate --strict`.
9. **Commit only your files** — stage the research doc + the two change dirs explicitly, leave
   unrelated pre-existing dirty files untouched.

## 3. How the collaboration unfolded

**Phase 1 — Ground the schema (Discovery).** Instead of theorizing, the AI ran bash to list
`~/.pi/agent/sessions/`, then `node -e` over a real large JSONL to dump record types and block
shapes. It discovered pi session **version 3** format: linked `type/id/parentId/timestamp`
records; `message` records carry `{role, content[]}` with role ∈ `user|assistant|toolResult`
and blocks ∈ `text|thinking|toolCall|image`; **781 sessions / 473 MB** for this project alone,
**1840 / 842 MB** across all projects. *Why it worked:* the corpus scan converted every later
claim from speculation into a measured fact.

**Phase 2 — Write the grounded reference (Design).** Wrote `research/lora-dataset-from-pi-logs.md`
(Parts 1–6: constraints → principles → 8-stage pipeline → LoRA formatting → pitfalls → recipe).
Deliberately kept **out of `docs/`** to dodge the caveman-style constraint. *Decision point:* the
human picked "Thread 1 — the success-detector is the crux," which sent the AI back to the corpus.

**Phase 3 — Solve the success-detector by reuse.** The AI mined 120 sessions and found explicit
user approval covers only ~10% of sessions (too sparse), while the raw `toolResult` messages carry
a **native structured `isError` boolean** (247:7 clean:error in one real session) — the
high-precision workhorse. Then it discovered the repo *already* solved this: `signals.ts` has a
46-test `episodeVerifiedGood` terminal-state detector. Folded §4.6 into the doc pointing at the
existing code. *Why it worked:* "check what already exists" beat inventing a new regex scanner.

**Phase 4 — Reframe: RAG vs. fine-tune (steering #4).** The human asked whether distillation
could **index** sessions for search instead of training. The AI grounded it against the repo's
four existing search layers (`session-distiller`, `packages/kb` FTS5+BM25, chunker, indexer),
concluded RAG is the better default for "recall what I learned," and added Part 7 — with the
explicit warning *don't rebuild the machinery that exists.*

**Phase 5 — Transparent auto-indexing (steering #5).** "How to index transparently?" exposed a
real constraint: only the **pure-code KB sink** can run headless; the skill/memory/docs sinks need
a live agent for judgment. Added Part 8 (watermark + `--index-only`) and, after another steer,
§8.5 — key the indexer on the dashboard server's **lifecycle transitions** (`agent_end`, bridge
`alive→ended`) instead of a file-mtime idle timer.

**Phase 6 — The governing decision, then ship the proposals (Generate + Verify).** The human made
the decisive pivot: **LoRA export = on-demand skill; session-distill→index = automatic.** Part 9
records it. The AI then scaffolded two OpenSpec changes, matched the exact proposal/tasks/spec
format from an existing change, added the `## Discipline Skills` line, validated both `--strict`
clean, staged **only** the 7 intended files, and committed (`1f8a5aacc`) on `develop`, unpushed.

## 4. Prompts that worked

- **The goal prompt** — "I would like to train pi jsonl logs of sessions." Short, but its power
  came from the follow-up grounding ("*this project's* logs"). **Rewrite for next time:**
  *"Write a grounded research doc on building a LoRA dataset from this repo's pi session JSONL
  logs — inspect the real logs first, reuse the existing `session-distiller`, keep it in
  `research/` not `docs/`."* That front-loads the three things that had to be steered.
- **High-leverage follow-up — "The session distiller can be improved... make distillation of
  sessions to be able to indexing to knowledge base — so can be searched without training."**
  One sentence that reframed the whole arc from train-only to RAG-first. Effective because it
  named a concrete alternative rather than asking an open question.
- **"no no. For just Lora only. The session distill be automatic."** A terse correction that
  cut through an over-engineered split and produced the clean Part 9 governing decision.
- **"1" / "yes" / "2"** — menu-pick replies to the AI's numbered threads. These worked *because
  the AI kept surfacing 2–3 concrete next threads at the end of each turn*, so a single digit
  chose a direction. The pattern (offer numbered threads → user picks a digit) is the real
  reusable mechanic here.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was *saved* this session — but two **OpenSpec proposals** were produced,
which are the reusable assets:

- **`add-automatic-session-kb-index`** — the automatic RAG path: `--index-only` headless mode +
  a `kb` sink routing all five verified signal classes into `packages/kb` FTS5, mandatory in-code
  secret-scrub gate (fail-closed), decoupled recurrence gate, lifecycle-triggered, idempotent via
  watermark + content hash. *Effective because* it makes distilled session knowledge searchable
  continuously with zero human judgment in the loop.
- **`add-lora-dataset-export-skill`** — the on-demand path: a `build-lora-dataset` skill,
  explicitly *not* auto-triggered, reusing the distiller's extraction + shared `scrub.ts` +
  `episodeVerifiedGood`. *Effective because* it gates expensive GPU-bound dataset builds behind a
  deliberate human choice of scope/quality/mixture.

**Skill that *should* be created:** a `distill-to-lora-dataset` or `session-kb-index` skill once
these changes are applied — this session is the proof that the workflow (inspect corpus → reuse
distiller → split auto/on-demand) is repeatable.

## 7. Pitfalls & dead ends

- **Sandbox blocks direct file reads of `~/.pi/agent/sessions/`.** The `read`/`ctx_execute_file`
  path failed on a session outside the project. **Fix:** use `bash` (`node -e` / `ls`) to inspect
  session JSONL instead of the sandboxed file tools.
- **Picked a worktree session file by accident** (from the worktrees listing) — the first probe
  command failed. **Fix:** pick a real file from the *main* project dir (`ls -S "$D"/*.jsonl`).
- **"idle = done" is the wrong done-detector.** Exploring file-mtime idle timers led into
  crash-grace / threshold complexity. **Fix:** key on the dashboard server's authoritative
  lifecycle transitions (`agent_end`, bridge `alive→ended`) — the server already knows.
- **Over-engineering the invocation split.** The AI briefly made *both* pipelines dual-mode; the
  human's "for just LoRA only" collapsed it. **Fix:** decide invocation model per pipeline before
  designing triggers.
