# How we did it: Diagnosing "Gemini is unusable with subagents" — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) with a standing premise:
*"Gemini 2.5 Pro can't be accessed / isn't usable with subagents — a dashboard 'spawn
new session' on a Gemini model just goes silent."* The first prompt was the explore-mode
stance ("Think deeply… investigate rather than guess, never implement, you MAY create
OpenSpec artifacts"). The **real objective**, once steering clarified it, was: *ground
the failure in live evidence, refuse to trust the premise, and capture the true root
cause in an implementation-ready OpenSpec change* — not to fix code, but to write a
proposal/design/specs/tasks that a builder can trust.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore`). State up front: **"prove every claim with a live test; the premise may be wrong."**
2. Read the resolution path first — `pi-dashboard-subagents` → `provider-register.ts` `model:resolve` → registry `excludedReason`. Confirm the model is actually *reachable* (green) before theorizing.
3. Dump the real env (`GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION=global`, `GOOGLE_GENAI_USE_VERTEXAI`).
4. **Test-fire, don't assert.** `curl` Vertex `:generateContent` with the real SA creds (both `global` + `us-central1`), then two in-memory subagent probes (plain gen, forced tool call). All 200 → auth/access/tool-calling refuted.
5. Read the *bundled* pi-ai serializer (`google-shared.js` `convertTools`) before writing a schema theory — discover pi sends `parametersJsonSchema`, not legacy `parameters`. Re-test the way pi *actually* sends → schema theory **refuted**.
6. Reproduce the **exact** failing path via the dashboard API: spawn session → `POST /api/session/:id/model` = Gemini → fire the heavy `doubt-driven-review` prompt → read the child transcript JSONL directly.
7. Root cause = **thinking-only turn**: `content=[thinking]`, all output tokens `reasoning`, 0 visible text, no tool call, `stopReason=stop`, `error={}`. Dashboard idles a clean-but-empty stop → silent.
8. Scaffold the change (`openspec new change …`), write proposal → design → 2 spec deltas → tasks, **correcting each artifact** as evidence refutes earlier drafts. Commit **only** the change dir.

## 3. How the collaboration unfolded

**Phase 1 — Trace resolution (don't theorize).** The AI read the subagent harness and
`provider-register.ts` to find where an "unusable model" verdict could originate
(`oauth-incompatible` / `excludedReason`). Finding: both Gemini entries show
`excludedReason: null` — reachable *now*. *Why it worked:* it located the actual
mechanism before guessing, so every later claim had a code anchor.

**Phase 2 — Ground in live tests.** Dumped Vertex env, flagged `GOOGLE_CLOUD_LOCATION=global`
as suspicious, then **test-fired**: raw `curl` (`global` + `us-central1` = 200), a no-tools
subagent (`PONG`), and a forced-tool subagent (`hello-from-gemini`). Auth, access, endpoint,
and tool-calling all refuted as causes. *Decision point:* the `curl` 200 also revealed
`thoughtsTokenCount: 188` for a 1-token answer — the "mandatory-thinking model" tell that
later proved central.

**Phase 3 — The false smoking gun, then self-refutation.** A hand-built tool schema with
`anyOf`+`const` returned **400 INVALID_ARGUMENT** — looked decisive. Before writing it into
the design, the AI read pi-ai's `google-shared.js` and found pi uses `parametersJsonSchema`
(full JSON Schema, which Gemini *accepts*), **not** the legacy `parameters` field the curl
had used. Re-tested the real path → 200. Schema theory **refuted by its own author.**

**Phase 4 — Reproduce the real path.** In-memory probes couldn't hit the failure because
they carried tiny, clean toolsets. The AI used the dashboard REST API to spawn a *real* full
`pi` session, switch it to Gemini, fire the heavy `doubt-driven-review` prompt, and read the
child JSONL. Captured live: a **thinking-only** turn (27,475 input tokens, 1351 reasoning
tokens, 0 visible text, `stopReason=stop`, no error) that dead-ends into idle.

**Phase 5 — Write honest artifacts.** Scaffolded the OpenSpec change and wrote
proposal → design → specs → tasks, **rewriting `proposal.md` twice** as evidence moved
(schema-sanitizer dropped; error-surfacing kept; empty-actionable-turn guard added as the
primary). Committed only the change dir.

Decision points the human drove: `draft` (proceed to design), `add to this proposal`
(expand to specs+tasks), `commit`.

## 4. Prompts that worked

- **The goal prompt (explore-mode stance).** Effective because it explicitly *forbids
  implementing* and *permits OpenSpec artifacts* — it framed the whole session as
  evidence-gathering, not coding. A stronger kickoff for a future operator: add one line —
  *"Treat the stated premise as a hypothesis; refute or confirm each claim with a live test
  before writing any artifact."*
- **`draft`** — a one-word high-leverage follow-up that moved proposal → design. Worked
  because the AI had already earned the context to know what "draft" meant.
- **`add to this proposal`** — expanded scope from 2/4 to 4/4 artifacts. Slightly
  underspecified (the AI flagged this); a better version: *"add the specs and tasks
  artifacts to reach 4/4."*
- **`commit`** — worked because the AI self-scoped it to only the new change dir.

## 7. Pitfalls & dead ends

- **The `anyOf`+`const` 400 is a trap.** It's real against the *legacy* `parameters` field,
  but pi sends `parametersJsonSchema`, which Gemini accepts. If you hit a 400, re-test with
  the field pi *actually* serializes (`convertTools(..., useParameters=false)`) before
  believing it.
- **In-memory subagent probes can't reproduce this.** They pass with tiny clean toolsets. If
  a probe is green but the user still sees silence, reproduce the **full spawned session**.
- **`server.log` is silent by design.** The model call runs inside the child `pi` process;
  400s/empty turns never reach the dashboard log or card. Don't conclude "no error" from an
  empty gateway log — read the child session JSONL directly.
- **No `model-proxy.jsonl` = spawned sessions call Vertex directly.** Absence of the proxy
  log refutes any "proxy mishandles Vertex" theory.
- **`openspec change new` is wrong** — the CLI is `openspec new change <name>`.
- **Memory stores can be full** (project 4949/5000, failure 9987/10000) — writes may not
  land; consolidate first.
