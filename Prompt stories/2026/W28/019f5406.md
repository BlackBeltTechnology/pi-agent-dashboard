# How we did it: Auditing the OAuth-incompatible model filter after a pi upgrade — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` — a thinking stance, no
implementation) with a research question: *did the pi-core 0.80.6 upgrade regress the
`filter-oauth-incompatible-models` mechanism, and is there a "null problem" in the model
selector?* The real objective, once the steering turns clarified it, was narrower and
concrete: **prove whether the OAuth filter still holds against the live pi-ai 0.80.6
catalog, prune any genuinely-dead entries from the override table, and land the small
correction that the audit surfaced** — without touching the concurrent-session changes in
a shared working tree.

## 2. TL;DR playbook

1. Enter `openspec-explore` — investigate only, do not implement until the scope is proven.
2. Trace the data path first: the model selector list comes from pi core's
   `cachedModelRegistry.getAvailable().map(toModelInfo)` (bridge.ts:724/2226/2503,
   session-sync.ts, command-handler.ts). Confirm *which* of the two "model-selector filter"
   mechanisms the question is really about.
3. Enumerate the ways the upgrade *could* break the filter (auth-cred shape, pi-ai method
   names, override-table vs catalog, null handling) and check each — build a verdict table.
4. Read the real pi-ai source in `node_modules` via the sandbox when tool output scrubs
   identifiers; confirm `getAvailable()` is now **synchronous** and filters by
   `hasConfiguredAuth`.
5. Make the surgical override-table edit (prune dead `-latest` aliases), run the scoped
   unit suites (`HOME=$(mktemp -d) npx vitest run …oauth-compat.test.ts …internal-registry…`).
6. **Deploy and verify live** — `curl -X POST http://localhost:8000/api/restart` (jiti, no
   build), then hit `GET /api/model-proxy/diagnostics` to read `getAllAnnotated()` +
   `excludedReason` per model. This is the step that catches static-analysis mistakes.
7. Restore anything the live verify proves you wrong about, re-run tests, re-verify.
8. Update the main spec (`model-proxy-credential-routing/spec.md`) and commit **only the
   scoped files** with `git reset -q && git add <exact paths> && git commit` — the tree is
   shared with concurrent sessions.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (which filter?).** The AI git-logged, `rg`-searched, and read the
bridge/provider/selector files to map the model-list data flow. Key early move: it noticed
there are **two different "model-selector filter" mechanisms** and refused to keep digging
blind — it laid out the finding and asked the human to confirm which thread. *Why it
worked:* disambiguating scope before deep analysis avoided auditing the wrong subsystem.

**Phase 2 — Evidence gathering (does 0.80.6 break it?).** The AI enumerated four break
vectors and checked each against the pinned pi 0.80.6: auth.json cred shape, pi-ai method
names (`registerBuiltInApiProviders` etc.), `OAUTH_INCOMPATIBLE` table vs the live catalog,
and null paths. It read pi source directly in `node_modules` (via `node -e` / sandbox) when
tool output scrubbed identifiers (`null`→`n`, `getAvailable`→`ln`). Produced a verdict
table: **no regression**.

**Phase 3 — The surgical edit (steering "a and b").** The human unlocked two tasks: (a)
prune 4 dead `-latest` entries, (b) trace the human-selector null path. The AI first checked
no test pinned the entries, edited, and ran the scoped vitest suites (12/12 green).

**Phase 4 — Deploy-and-verify (the catch).** On "next", the AI restarted the server and
queried `/api/model-proxy/diagnostics`. This exposed a regression *it had just introduced*:
the **live** model-proxy resolves pi-ai through the tool-registry — a *different* copy than
the top-level `node_modules` enumeration — and that copy **does** ship
`claude-3-5-haiku-latest`. Pruning it leaked a legacy OAuth-incompatible model as routable.
It restored just that one id, kept the other 3 pruned, re-verified live, saved a project
memory.

**Phase 5 — Spec + scoped commit.** On "update spec and commit", the AI filled the spec's
`TBD` Purpose, added a scenario pinning live-catalog `-latest` denial + a maintenance note,
then committed exactly 2 files (`48cbbb4a9`) without leaking concurrent-session changes.

## 4. Prompts that worked

- **The goal prompt** (`openspec-explore` stance): effective because it forced a
  *research-first, implement-never-until-proven* discipline. The audit was complete before
  any edit landed. Reuse: start ambiguous "did X regress?" questions in explore mode.
- **"a and b"** — a high-leverage unlock. After the AI laid out two candidate follow-up
  tasks, one two-letter reply authorized both. Effective because the AI had *pre-structured*
  the choices; the human just selected.
- **"update spec and commit"** — terse but unambiguous scope-closer. Worked because the
  session state made "spec" and "commit which files" unambiguous.
- **Weak prompt to rewrite:** "next" was ambiguous (deploy vs commit vs open question) and
  the AI correctly *paused to confirm* rather than guess. A stronger version:
  *"deploy to the live instance and verify the filter via the diagnostics route."*

## 6. Skills, tools & memory created — and why they're effective

- **Memory saved (project · insight):** the model-proxy OAuth-compat table nuance — the
  **live** `InternalRegistry` resolves pi-ai via the tool-registry `resolveModule("pi-ai")`,
  a *different copy* than a top-level `node_modules` enumeration, so
  `claude-3-5-haiku-latest` is present live and must stay OAuth-denied. *Why effective:* it
  pins the exact trap that cost a regression this session — the next maintainer auditing the
  `OAUTH_INCOMPATIBLE` denylist won't re-prune a live-but-hidden alias. Invoke when editing
  `packages/server/src/model-proxy/oauth-compat.ts` or auditing the model filter.
- **Recommended skill (not created):** a *"verify model-proxy filter against live catalog"*
  procedure — restart via `/api/restart`, GET `/api/model-proxy/diagnostics`, group rows by
  provider, assert `excludedReason` per expected id. This deploy-verify loop caught the bug;
  it deserves to be reproducible.

## 7. Pitfalls & dead ends

- **Static `node_modules` enumeration ≠ live catalog.** The top-level pi-ai copy and the
  tool-registry-resolved copy can ship different model ids. If you prune an entry based on
  the former, the live proxy may still ship it. → Verify via the diagnostics route.
- **Tool output scrubs identifiers** (`null`→`n`, `getAvailable`→`ln`). → Read the pi source
  directly with `node -e`/sandbox when a grep result looks mangled.
- **Proxy `/v1/models` needs the proxy API key** (stored hashed, unrecoverable). → Use the
  dashboard-auth `/api/model-proxy/diagnostics` route instead for verification.
- **Shared working tree with concurrent sessions.** → `git reset` then `git add` exact paths
  so unrelated changes don't leak into your atomic commit.
- **Memory at capacity** aborted one save mid-session (skipped rather than detour into
  consolidation).
