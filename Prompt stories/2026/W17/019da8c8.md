# How we did it: Reconciling a phantom release in CHANGELOG.md — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with a deceptively simple question: **"How release notes are
handled?"** What looked like a documentation-lookup task turned into a real cleanup
job. Within a few turns the *actual* objective emerged: the `CHANGELOG.md` claimed a
`## [0.3.0]` release that **was never cut** (no `v0.3.0` git tag, `package.json` still
at `0.2.9`). The real goal became: **reconcile the changelog with git reality** — kill
the phantom version, fold its bullets back into `## [Unreleased]`, back-fill every
user-visible commit since `v0.2.9` that was missing, normalize line wrapping to the
file's existing style, consolidate duplicates, and commit + push.

## 2. TL;DR playbook

1. **Ask "how are release notes handled?"** — let the AI read `CHANGELOG.md`,
   `docs/release-process.md`, and `.github/workflows/publish.yml` to state the flow
   (Keep a Changelog 1.1.0, human-curated, `npm version --workspaces`, tag `v*`, CI
   derives the GitHub Release body).
2. **Cross-check the top version against git reality:**
   `git tag -l | sort -V | tail` + `node -p "require('./package.json').version"`.
   A `## [X.Y.Z]` header with no matching `vX.Y.Z` tag = phantom release.
3. **Decide the reconciliation direction** — either *cut it for real* or *demote it
   back into Unreleased*. Here the user chose **demote (option B)**.
4. **Fold the phantom section's bullets up into `## [Unreleased]`**, drop the
   release-announcement framing paragraph, delete the phantom header.
5. **Normalize wrapping to the file's own convention** (≤76 chars, 2-space
   continuation indent) — verify with `awk 'length > 80 { print NR": "length }'`.
6. **Audit `git log v0.2.9..HEAD`** for user-visible `feat:`/`fix:` commits not yet
   in the changelog; `git show --stat <sha>` each candidate; add the missing bullets.
7. **Consolidate**: merge duplicates, group thematically (all tunnel fixes, all auth
   items), tighten wording without dropping any user-visible outcome.
8. **Commit + push** with a `docs(changelog):` conventional-commit message describing
   the reconciliation.

## 3. How the collaboration unfolded

The 47-minute session ran on Opus (medium thinking) across four clear phases.

- **Discovery — "how does this work?"** The AI read the changelog head, listed tags,
  and printed `package.json` version in one batched `bash` call, then explained the
  full human-curated release flow. *Why it worked:* it grounded the answer in three
  source-of-truth files instead of guessing, so the follow-up correction landed on
  solid facts.

- **Diagnosis — the phantom.** The user steered: *"Check changelog. It contains 0.3.0
  which is not exists."* The AI confirmed via `git tag` + `package.json` + a `git log`
  blame that the `## [0.3.0]` section was introduced by a *docs* commit (`f2ec691`)
  describing a release that was never tagged. It then presented **two named options —
  A: cut 0.3.0 for real, B: demote back to Unreleased** — instead of silently picking.
  *Decision point:* the user replied **"B"**.

- **Repair — fold, rewrap, back-fill.** Three tight edit loops: (1) merge the phantom
  bullets into `## [Unreleased]` and delete the header + announcement paragraph;
  (2) rewrap Unreleased bullets to the 0.2.x block's ~76-char style after the user
  flagged *"different line lengths… fit with changelog spec"*; (3) diff
  `git log v0.2.9..HEAD` and add **four missing user-visible feature commits**
  (`ask_user` batch, path-picker, brand-mark/barber-pole UI, editor-PID registry)
  after the user asked *"Is there anything missing?"* → *"yes"*.

- **Consolidate + ship.** On *"Consolidate Unreleased part"* the AI merged duplicates
  (two `ask_user` batch entries → one), grouped scattered fixes (6 zrok bullets → one
  "Zrok tunnel reliability"), taking 43 bullets → 35, then on *"commit and push"*
  committed as `docs(changelog): consolidate Unreleased section` and pushed to
  `origin/develop` (net −25 lines despite adding 4 items).

## 4. Prompts that worked

- **The goal prompt — "How release notes are handled?"** A good *discovery* kickoff:
  open-ended, forces the AI to read the actual process docs. It surfaced the phantom
  bug as a side effect. A stronger version if you already suspect drift:
  *"Explain how release notes are handled, then cross-check CHANGELOG.md's top version
  against git tags and package.json."*

- **High-leverage follow-ups:**
  - *"Check changelog. It contains 0.3.0 which is not exists"* — a single factual
    correction that pivoted the whole task from lookup to repair.
  - **"B"** — one letter, chosen from the AI's two explicit options. This is why
    offering *labeled* alternatives pays off: the human can steer with a keystroke.
  - *"There are commits. Is there anything missing from changelog?"* → **"yes"** — a
    cheap audit trigger that caught four unshipped features.
  - *"Consolidate Unreleased part of release notes"* — trusts the AI to dedupe/group
    with judgment, no micromanagement.

## 7. Pitfalls & dead ends

- **Phantom release trap:** a `## [X.Y.Z]` header can be added by a *docs* commit that
  merely *describes* a release. Don't trust the header — the truth is `git tag` +
  `package.json`. If both say `0.2.9`, `0.3.0` was never cut.
- **Wrap width has no spec:** Keep a Changelog does *not* mandate a wrap width. "Fit
  the spec" means **match the file's own existing style**, not an external rule. The
  header paragraph's inline-URL lines (5/6/8 here) legitimately exceed 80 chars and
  can't wrap through a URL — leave them.
- **"Nothing's missing" is a guess until you diff:** the changelog looked complete but
  `git log v0.2.9..HEAD` revealed four unshipped `feat:` commits. Always diff.
- **Unrelated noise:** the push surfaced 16 Dependabot alerts — noted, not acted on.
  Don't let incidental findings expand the task scope.
