# How we did it: Teaching `ask_user` to accept the batch shape Opus keeps hallucinating — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The session opened in **explore mode** ("Enter explore mode. Think deeply… you must NEVER write code or implement features") — a thinking stance, not an implementation request. But the real objective surfaced fast: Opus 4.7 kept failing `ask_user` calls because it insisted on sending a **batch-of-questions** shape — one or more question objects wrapped inside a `questions` array, often JSON-stringified — while the tool's schema was a strict 4-arm discriminated union (`confirm | select | multiselect | input`) that only accepts one flat question per call. The goal that emerged: **stop fighting the model and make `ask_user` natively support a `batch` method**, with aggressive argument-rescue so the malformed shapes Opus emits get normalized instead of rejected. The session ran the full OpenSpec arc — explore → proposal → implement → verify → archive → commit — and then caught two live regressions after rollout.

## 2. TL;DR playbook

1. **Start in explore mode** and force the AI to ground in the real schema first: "read `packages/extension/src/ask-user-tool.ts`, show me the exact shapes Opus sent and why each was rejected." Don't let it propose fixes before it has quoted the failing payloads.
2. **Pick the design that adds the least surface.** When offered options, choose **sequential prompts** (reuse `ctx.ui.*` per sub-question) over a new compound-dialog UI primitive — it needs zero new adapter code.
3. **`create proposal`**, then `/opsx:ff` to fast-forward all artifacts (proposal, design, spec delta, tasks) in one shot.
4. **`/opsx:apply`** to implement: add a `BatchSchema` arm + a `SubQuestionSchema` that deliberately **omits `batch`** (no nesting), and put all the messy normalization in `prepareArguments`.
5. **Carry warnings out-of-band.** Attach a **non-enumerable `__normalizations`** array to the args so rescue warnings reach `execute` without breaking TypeBox schema validation.
6. **`/opsx:verify`**, fix the one spec/impl drift it finds, then **`npm run reload`** to push the new bridge to live sessions.
7. **Expect reload to lie.** Node's ESM module cache pins the old tool code — `/reload` re-fires `session_start` but `bridge.ts` already resolved the old import. Only a **fresh process** picks up the change. Trust the unit tests + filesystem, not the live session.
8. **Archive + sync specs + commit.** Then when a live screenshot shows a *new* failure shape, treat it as "model pivoted to the adjacent drift" — add the missing rescue pass (backfill outer `title`), one test, one commit.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (grounded, not speculative).** The AI read `ask-user-tool.ts` and quoted *both* rejected payloads verbatim: attempt 1 with a nested `input_type` + `{label,value}` pairs, attempt 2 flat but still wrapped in a stringified `questions` array. It correctly diagnosed the cause as bleed-over from another agent framework that supports multi-question forms, and noted `prepareArguments` already rescued three other LLM quirks. **Why it worked:** the human's explore-mode prompt banned implementation, which forced a schema-grounded diagnosis before any code.

**Phase 2 — Design (least-surface choice).** The human picked **Option B** (sequential prompts). The AI baked five decisions into `design.md`: sequential dispatch (no new UI primitive), mid-batch cancellation returns partial results + `cancelled: true`, `batch` cannot nest, `{label,value}[]` normalized to `label[]` with a warning. **Decision point:** choosing sequential over a compound dialog kept the whole change inside `prepareArguments` + `execute` — no other component touched.

**Phase 3 — Generate (OpenSpec fast-forward).** `create proposal` → `/opsx:ff` produced proposal, spec delta, design, and a 7-group/~30-task `tasks.md`, all validating clean.

**Phase 4 — Implement + Verify.** `/opsx:apply` rewrote the tool: named schema constants, a `SubQuestionSchema` union omitting `batch`, the `BatchSchema` arm, four rescue passes in `prepareArguments`, and a batch branch in `execute`. Tests went 19 → 32. `/opsx:verify` produced a 35/35 report and flagged one spec/impl drift (sub-questions reuse the single-method schemas, so they may carry their own `message`), which the human told it to `fix`.

**Phase 5 — Rollout reality check.** `test as_user in this session` exposed the hard lesson: `npm run reload` did **not** make batch work live. The AI traced it correctly — stale `dist/` build **and** Node's ESM cache pinning the old module through `/reload`; a competing pi-flows `ask_user` (using a `type` discriminator) confirmed why runtime registration matters. Conclusion: code is correct, only a fresh process proves it.

**Phase 6 — Archive, commit, and the live pivot.** `/opsx:archive` synced the delta into the main spec; `commit changes` landed `7a0e926` (scoped to only this change, leaving unrelated dirty files alone). Later a screenshot ("There is not processed questions") showed Opus now sending `method: "batch"` explicitly but with **no outer title** — the adjacent drift. The AI split title-backfill into its own pass (`36bd96d`), added a test for the exact screenshot shape, then `f037530` added the spec scenario + CHANGELOG entry.

## 6. Skills, tools & memory created — and why they're effective

No pi skill or memory was created in this session — the reusable asset is the **OpenSpec change `ask-user-batch-questions`** itself (archived at `openspec/changes/archive/2026-04-20-ask-user-batch-questions/`) and the hardened tool.

Two patterns are worth extracting as durable memory/skill:

- **"Reload ≠ reload code" pitfall.** `npm run reload` re-fires `session_start` but Node's ESM cache pins the already-resolved `registerAskUserTool` import in `bridge.ts`; a stale `dist/` compounds it. **Invoke when:** any extension/bridge change "isn't taking effect" in a live session. **Solution:** rebuild `dist/`, then verify in a **new** process, not via `/reload`.
- **"LLM-shape rescue in `prepareArguments`" pattern.** Put all normalization (unwrap stringified arrays, synthesize `method`, rename `question`/`header`→`title`, flatten `input_type`, `{label,value}[]`→`label[]`) in one pre-validation pass, and carry warnings on a **non-enumerable `__normalizations`** field so schema validation stays clean. **Invoke when:** a strict tool schema keeps rejecting a model's persistent malformed shape — normalize instead of rejecting.

## 7. Pitfalls & dead ends

- **`/reload` won't load new extension code.** ESM module cache + stale `dist/`. → Rebuild and test in a fresh pi session; don't smoke-test batch in the session that issued the reload.
- **Competing `ask_user` implementations.** pi-flows ships an `ask_user` using a `type` discriminator; this repo's uses `method`. Runtime registration order decides the winner — a `confirm` call succeeding only proves *which* tool is active, not that your schema loaded.
- **Fixing one drift invites the next.** First fix synthesized `title` only when `method` was absent; Opus then sent `method: "batch"` *with* no title. → Backfill `title` on **any** batch call missing it, from `title ?? question ?? header ?? "Questions"`.
- **TypeBox strictness trap.** Extra unknown fields (`defaultValue: true`) are fine (Object is non-strict), but a rescue warning attached as a normal property would break validation — use a non-enumerable field.
- **Commit hygiene.** The working tree had unrelated dirty files (CHANGELOG, SessionHeader, test files); scope `git add` to only the change's files.
