# How we did it: Empty chat pane in the dashboard — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with one line: *"The chat window is empty in dashboard. Use browser
to check."* The real objective: a selected session in the pi-agent-dashboard renders
a completely blank right pane — no chat header, no transcript, no input box — and it
needs to be diagnosed **from the rendered DOM** (not guessed from source) and fixed.
The one steering turn (*"build and deploy"*) confirmed the second half of the job:
land the fix into the live production instance, not just the working tree.

## 2. TL;DR playbook

1. Reproduce in the real browser first: `agent-browser screenshot` on the selected
   session URL — confirm the pane is visually blank.
2. Inspect the actual DOM, don't trust source: `agent-browser eval` a small tree
   walk of `#root` to prove the right-pane container has **0 children**.
3. Rule out a data/API problem: `curl /api/health` and `/api/events/<sid>/0` to
   confirm events exist and the server is healthy — isolates it to the client render.
4. Locate the render fallback chain in `packages/client/src/App.tsx`
   (`grep` for `ContentViewSlot`, `sessionDetail ??`, `LandingPage`).
5. Spot the `??` bug: a ternary that always returns a **non-null** `<ContentViewSlot>`
   JSX element short-circuits `?? sessionDetail ?? <LandingPage>` even though the slot
   renders `null` internally (empty plugin registry).
6. Fix by gating the JSX on the registry actually having claims:
   `_pluginRegistry.getClaims("content-view").length > 0`.
7. Build + deploy: `npm run build` → `POST /api/restart` → verify with
   `/api/health` and one more browser screenshot.

## 3. How the collaboration unfolded

**Discovery (browser-first).** The AI didn't open source first — it took a screenshot
and ran `agent-browser eval` DOM tree-walks against `#root`, proving the right pane
`<div class="flex-1 flex flex-col min-w-0 min-h-0">` had **0 children** after routing
to `/session/<id>`. *Why it worked:* it turned a vague "empty window" into a hard,
falsifiable fact (0 DOM children) before touching any code.

**Isolate (data vs render).** It probed `/api/health` and the events endpoint
(`/api/events/<sid>/0`) to confirm events existed and the server was fine — cleanly
ruling out a backend/data cause and pinning the bug to the client render path.

**Root cause (read the fallback chain).** `grep` in `App.tsx` surfaced the
`(selected ? <ContentViewSlot/> : null) ?? sessionDetail ?? <LandingPage/>` chain.
Key insight: `??` checks the **source expression** for null, not the rendered output.
The ternary yields a live JSX element whenever a session is selected, so the fallbacks
are never reached — and `<ContentViewSlot>` itself returns `null` because the plugin
registry is empty until real plugins register claims. Result: blank pane.

**Decision point.** The AI paused (an `ask_user` attempt) to confirm intent because
the offending code was uncommitted work-in-progress, then applied the minimal gate.

**Fix + deploy.** One `edit` to `App.tsx`, `npm run build`, `POST /api/restart`, then
a confirming screenshot + health check (144 sessions, production mode). Because it was
a client-only change, no `npm run reload` of pi sessions was needed.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session. But the workflow is a clean, repeatable
pattern worth capturing: **"diagnose a blank/blank-pane React render via the live DOM,
not the source."** A future skill would encode: screenshot → `agent-browser eval` tree
walk of `#root` → confirm 0 children → rule out API with `/api/health` → grep the

of reading React conditionals cold and makes the "prove it in the DOM first" discipline
reproducible.

## 7. Pitfalls & dead ends

- **`??` does not fall through on a rendered `null`.** `(cond ? <Comp/> : null) ?? alt`
  keeps the `<Comp/>` element because nullish-coalescing inspects the **source
  expression**, not what `<Comp/>` renders. If a slot component can render `null`,
  gate the JSX on a real condition (e.g. `registry.getClaims(...).length > 0`), not on
  `??`.
- **Don't trust source for a render bug.** The pane looked wired correctly in code;
  only the DOM tree-walk (0 children) revealed the truth. Reproduce in the browser first.
- **Client-only change → restart, not reload.** `npm run build` + `POST /api/restart`
  is enough; `npm run reload` (pi sessions) is only for bridge/extension changes.
