## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
not an implementation task. The literal kickoff was the skill's boilerplate:

> "Enter explore mode. Think deeply. Visualize freely. Follow the conversation wherever it goes."

The *real* objective, revealed by the attached screenshot and description, was a bug hunt:
**selecting a session card that clearly has context (159k tokens, filled progress bar, 1h 9m
runtime) renders the "No messages yet" placeholder while history is still loading — sometimes
after ~15s, sometimes flashing before partial history appears.** The user wanted the AI to
root-cause the false-empty flash and capture the fix as an OpenSpec proposal — *without writing
implementation code*. The three later prompts (`C`, `Add option B too`, `commit`) show the
arc: pick a fix option, expand scope, land the artifacts.

## 2. TL;DR playbook

1. **Frame the symptom as a race, not a state.** The card *has* context but shows empty →
   suspect a hydration/loading-flag race, not a truly-empty session. Say so, then verify.
2. **Ground before theorizing.** `kb_search` for the existing `chat-history-loading-indicator`
   spec + `rg` the loading-flag machinery (`useMessageHandler.ts`, `App.tsx`, the replay handler).
3. **Trace the exact exits.** Enumerate every code path that clears the loading flag. Here: an
   early empty `isLast:true`, or the **hardcoded 15s safety-net timer** (`App.tsx:651`).
4. **Match the symptom to the mechanism.** User's "sometimes ~15s" ⇒ the timer wins the race
   against slow cold-load disk hydration for large ended sessions.
5. **Draw the causal chain as ASCII** so the human can confirm the story before committing to a fix.
6. **Present fix options A/B/C, let the human pick.** User chose **C** (give the already-emitted
   priming `event_replay{events:[], isLast:false}` marker a job).
7. **Run the mandatory coherence check** — `openspec list` + read the archived priors — because
   this *modifies* a shipped capability rather than inventing one.
8. **Scaffold the change directly** at `openspec/changes/<name>/` (no `openspec change new` subcommand
   exists here), then `openspec validate --strict` until green.
9. **Absorb the scope expansion** (`Add option B too` — heartbeat) by editing all four artifacts, keeping
   C and B composed on the *same* signal shape (no new message type).
10. **Commit only the four artifacts**, explicitly leaving unrelated working-tree changes unstaged.

## 3. How the collaboration unfolded

**Discovery (00:03).** The AI immediately reframed: "The card clearly has context … but the message
pane renders the empty state. And it's timing-dependent … That smells like a history hydration race,
not a truly empty session." It resisted theorizing and went to ground truth first.

**Trace (00:03–00:04).** `kb_search` surfaced the shipped `chat-history-loading-indicator` spec — a
"smoking gun" proving the intended behavior is a *spinner*, not the placeholder. Then `rg` + `read`
walked the replay handler and `App.tsx`, isolating the two flag-clearing exits and confirming the
**hardcoded 15000 ms timer at `App.tsx:651`** as the culprit. The AI mapped the whole race to an ASCII
diagram (select card → arm 15s timer → server parses whole JSONL from disk → 15s elapses mid-parse →
flag drops → "No messages yet" flash → parse finishes too late).

**Decide (00:07, prompt `C`).** The AI had laid out fix options; the human picked **C**. Decision point:
C reuses the priming `{events:[], isLast:false}` marker the client already ignores — cancel the blunt
15s timer on receipt, arm a longer "still-parsing" ceiling. Client-only, no protocol change.

**Coherence + scaffold (00:08–00:10).** Before writing, the AI ran the project's mandatory overlap
check (`openspec list`, read archived `show-chat-history-loading-indicator` and
`instrument-session-hydration-timing`), confirmed a **modify** (not a new capability), discovered
`openspec change new` doesn't exist here, and created the four artifacts directly, validating `--strict`.

**Scope expansion (00:11–00:16, prompt `Add option B too`).** The human widened scope: also add B (a
server heartbeat). The AI layered B *without* a new message type by re-sending the same
`event_replay{events:[], isLast:false}` marker periodically — the ceiling's role shifts from "max total
parse time" to "max gap between heartbeats" (dead-worker detector). This forced a fiddly spec edit
(a base requirement said "No protocol or server change" which B now contradicts).

**Commit (01:09, prompt `commit`).** The AI scoped the commit to only the four proposal artifacts,
deliberately leaving unrelated working-tree files (`event-reducer.ts`, `memory-event-store.ts`,
`b05_*.txt`) unstaged, and reminded the user this is proposal-only — no implementation touched.

## 4. Prompts that worked

- **The goal prompt** (the `openspec-explore` boilerplate + screenshot): effective because it set a
  *thinking, not implementing* stance and supplied a concrete reproduction (159k tokens, "sometimes
  ~15s"). A stronger explicit version: *"Root-cause the 'No messages yet' flash on large ended
  sessions; it appears ~15s in. Capture the fix as an OpenSpec proposal — don't implement."*
- **`C`** — a one-character high-leverage pick. It worked because the AI had already presented A/B/C
  with tradeoffs, so a single letter selected a fully-specified direction.
- **`Add option B too`** — a scope expansion that unlocked a *composed* fix. Effective because the AI
  found a way to layer B onto C's existing signal, keeping the design coherent.
- **`commit`** — trusted the AI to scope the commit; it correctly staged only the new artifacts.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Present multiple fix options and wait | Reply `C` to pick one | State the decision criterion up front ("prefer the client-only fix") to skip a round-trip |
| Scope the fix to a single layer (C) | `Add option B too` | Ask early: "is a defense-in-depth / server-side layer also wanted?" |

| Risk committing a dirty tree | `commit` (AI self-scoped) | Say "commit only the change dir" to make scoping explicit |

Quality bars the AI imposed on itself and should be repeated: **ground in code before theorizing**,
**enumerate every flag-clearing exit**, **run the coherence check before scaffolding**, and
**validate `--strict` until green**.

## 7. Pitfalls & dead ends

- **`openspec change new <name>` fails** — no such subcommand in this repo. Create the artifacts
  directly under `openspec/changes/<name>/` (proposal.md, design.md, tasks.md, specs/…/spec.md).
- **Spec parser reads the requirement statement as the *first line*.** A requirement that opens with a
  subordinate clause (SHALL on line 2) fails `--strict`. Put `SHALL` in the opening line.
- **Editing a spec dropped the `## What Changes` header** — a careless edit removed a required section;
  `validate --strict` caught it. Re-run validation after every spec edit.
- **Layering B silently invalidated a base requirement** ("No protocol or server change"). When adding a
  server-side layer, hunt the base spec for invariants your change now breaks and MODIFY them.
- **Dirty working tree** — many unrelated changes were present; scope `git add` to only the change dir.
