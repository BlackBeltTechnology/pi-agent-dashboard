# How we did it: Distilling 431 archived changes into a code-grounded Playwright test suite — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator wanted to mine years of archived OpenSpec changes for every frontend
smoke/QA test case ever specified, collect them into a Markdown file, and turn that
into a corpus for authoring Playwright tests — using **parallel gemma workers** to do
the extraction cheaply. The first prompt:

> *"Collect with parallel google_vertex gemma4 model the archive specs which changes
> the frontend what smoke / qa tests was on tasks. Collect them to a markdown file to
> be able to collect all use cases / tests cases to be able to create playwright tests.
> Be carefull! It is historic, so by time most of them drifted."*

The real objective, once steering clarified it, was a **two-artifact deliverable**:
(1) a raw historic inventory of everything ever tested, and (2) a *distilled,
code-verified* suite where every drifted case has been eliminated by checking each
candidate against the **current** monorepo source — not the long-gone `src/client/`.

## 2. TL;DR playbook

1. **Pre-filter the corpus.** Scan `openspec/changes/archive/`; keep only changes that
   touch the frontend (references to `src/client/`, `packages/web/`, `.tsx`, React
   hooks, named client components). 574 → 431. Tighten the filter until the noise drops
   (first pass kept 527/574 — too loose).
2. **Pre-extract compact per-change blobs** (proposal WHY/WHAT + the tasks
   *verification/test/QA* sections) so each worker **transforms text**, never does
   fragile multi-file tool reads.
3. **Smoke-test one worker** on the real provider id (`google/gemma-4-31b-it`) before
   fanning out. Confirm auth and that a large prompt actually produces stdout.
4. **Fan out in bounded waves.** Inline the content into per-worker prompt files
   (no tools needed), batch ~20 changes each (stay well inside gemma's 262K window),
   run in waves of 6–8 with a poll-and-kill safety net, capture stdout → markdown.
5. **Reconcile.** Diff outputs against inputs; find dropped/duplicated changes and
   regenerate the gaps. Assemble the raw inventory with a header + drift stats.
6. **Ground against CURRENT code.** Build a searchable index of the live client, then a
   **per-component source digest** (real `data-testid`s, visible text, roles, handlers).
7. **Two-stage distill.** Stage 1: workers judge each candidate keep/drop against its
   surface digest (behavior present → KEEP + rewrite for current DOM; absent → DROP).
   Stage 2: per-cluster dedup + tag which cases existing e2e specs already cover.
8. **Assemble + commit only your files.** Write both docs under `docs/qa/`, add the
   `AGENTS.md` tree node, `git add docs/qa/` (never `git add -A`).

## 3. How the collaboration unfolded

**Phase 1 — Corpus discovery & filtering.** The AI listed the archive (574 changes),
inspected a change's directory structure, and built a frontend filter. The first filter
was too loose (527/574); it tightened to require real client-path/component signals and
landed on **431**. *Why it worked:* narrowing the corpus before spending any worker
calls is the cheapest lever — every dropped change is saved compute.

**Phase 2 — Prompt engineering for tool-free workers.** Rather than let gemma read
files, the AI pre-extracted a compact signal blob per change (intent + verify/QA task
sections; 301 of 431 had explicit verify blocks) and **inlined the content into the
prompt**. Workers only transform text → markdown on stdout. *Decision point:* choosing
text-transformation over tool-use is what made a weak/cheap model reliable at scale.

**Phase 3 — Fan-out, and the subshell bug.** First batch finished in a suspicious 44s
with **empty outputs**. Root cause: workers were launched via `$(run_one)`
command-substitution — a subshell that broke `$!`/job tracking, so nothing was actually
backgrounded/awaited. Rewriting to launch directly in the main shell fixed it; a real
run took ~27 min and produced 430/431 (one change, `adopt-pi-071-072-073-features`, was
dropped and regenerated). Result: **`docs/qa/archived-frontend-test-cases.md`** — 431
sections, **1,811** Playwright-candidate cases, each tagged with a Drift risk rating.

**Phase 4 — The steering pivot: verify against current code.** The operator's second
prompt demanded distilling to *current state* by checking each case against the code.
The AI discovered the client had **moved out of `src/client/`** into a monorepo
(`packages/client/src` + per-plugin `src/client`) — major structural drift. It built a
current-code index (1008 components, 787 testids, 1076 UI strings), ran a deterministic
anchor-grep (**692 SURVIVES / 916 BEHAVIORAL / 60 PARTIAL / 102 DRIFTED / 41 NO_UI**),
and eliminated the 102 drifted + 41 no-UI immediately.

**Phase 5 — Digest-grounded two-stage distill.** For the 916 behavioral cases with no
greppable anchor, the AI built **per-component source digests** (testids, visible text,
roles, handlers — exactly what Playwright targets) and ran a 2-stage worker pipeline:
Stage 1 grounded keep/drop against digests (1668 → **482**), Stage 2 deduped per cluster
and tagged existing-e2e coverage (**340** distinct: 320 [NEW] gaps + 20 [COVERED]).
Result: **`docs/qa/distilled-current-test-cases.md`**.

**Phase 6 — Documentation + surgical commit.** New `docs/qa/` dir got an `AGENTS.md`
tree node (delegated to a subagent in caveman style per the repo's Rule 6). The commit
added **only** the 3 `docs/qa/` files; unrelated pre-existing working-tree changes were
left untouched.

## 4. Prompts that worked

- **The goal prompt** was effective because it named the *method* (parallel gemma
  workers), the *output* (one markdown file of test cases → Playwright), **and** the
  key risk up front ("it is historic, so most of them drifted"). Naming the drift risk
  in prompt 1 is what made the AI attach a Drift rating to every entry.
- **High-leverage follow-up:** *"Process all candidates and distil test cases for
  current state. For that for every case check the code. I would like to eliminate
  drifted test cases."* — one sentence that unlocked the entire Phase 4–5 grounding
  pipeline. It converted a raw inventory into a trustworthy suite.
- **Rewrite of the goal prompt** a future operator should use instead:
  *"Using parallel `google/gemma-4-31b-it` workers, mine `openspec/changes/archive/`
  for every frontend smoke/QA test case. Pre-filter to frontend-touching changes only,
  inline each change's intent + verify sections into the worker prompt (no tool reads),
  batch ~20/worker in waves of 8. Output one markdown inventory with a Drift risk rating
  per case. Then verify every case against the CURRENT client source and drop drifted
  ones."* — this front-loads the drift-verification requirement so it isn't a second round-trip.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was saved this session, but the workflow is **highly repeatable** and
deserves one. Recommended skill: **`parallel-gemma-corpus-distill`** capturing:

- **What it captures:** the pattern of mining a large document corpus (archived specs,
  changelogs, issues) with cheap parallel `google/gemma-4-31b-it` workers by *inlining
  content into tool-free prompts*, batching within the context window, running bounded
  waves with poll-and-kill, then **grounding results against current source via
  per-component digests**.
- **Why it's effective:** it removes the two things that make cheap-model fan-out fail —
  (1) fragile multi-file tool reads (solved by text-transformation prompts) and (2)
  untracked background jobs (solved by launching directly in the main shell, never via
  `$(…)` command substitution).
- **When to invoke it:** any "mine N archived artifacts into a distilled, still-accurate
  deliverable" task where a strong model would be too expensive per-item.

The session also used the `general-purpose` subagent to scaffold the `docs/qa/AGENTS.md`
tree node — the repo's standard Rule-6 delegation for any write under `docs/`.

## 7. Pitfalls & dead ends

- **44s "success" = empty outputs.** If a fan-out finishes suspiciously fast, the
  workers likely produced nothing. Cause here: launching via `$(run_one)`
  command-substitution ran them in a subshell and broke `$!`/job tracking. **Fix:**
  launch workers directly in the main shell; verify one runs synchronously first.
- **Stale code assumption.** Historic test anchors referenced `src/client/`, but the
  client had migrated to `packages/client/src` + plugin dirs. **Fix:** never verify
  against the path a spec *mentions*; index where the code lives *now*.
- **Loose pre-filter.** The first frontend filter kept 527/574 — near-useless. **Fix:**
  require concrete client-path/component signals and sanity-check the keep-rate.
- **One dropped change in a batch.** A worker silently dropped 1 of its 20
  (`adopt-pi-071-072-073-features`). **Fix:** always reconcile outputs vs inputs and
  regenerate gaps before assembling.
- **Noisy working tree at commit.** Unrelated changes (`.pi/skills/`, `openspec/`, stray
  `b05_*.txt`) sat alongside the work. **Fix:** `git add docs/qa/` only.
