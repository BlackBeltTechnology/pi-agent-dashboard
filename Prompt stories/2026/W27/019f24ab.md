# How we did it: Root-causing the Opus "xhigh-only" thinking-level dropdown — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (a thinking-partner stance — read/search/investigate,
never implement), and the human's real objective emerged one clarifier at a time. The
observed symptom: *in the pi dashboard model selector, the thinking-level picker for Opus
offers only `xhigh`* even though the current session displays `high`. The actual objective
was not "make the dropdown show more options" but **find the true root cause of why the
dropdown under-reports supported thinking levels, then capture it as a strict-valid OpenSpec
change proposal** — no application code, just the diagnosis and the fix contract.

First prompt (verbatim kickoff): *"Enter explore mode. Think deeply…"* — the openspec-explore
skill. The steering that clarified the real target came immediately after:
*"1. In the pi dashboard model selector up to command prompt input / 2. No. Models selectable"*
— i.e. **the thinking-level picker, not the model picker.**

## 2. TL;DR playbook

1. **Frame the ambiguity before tracing.** When a symptom ("opus xhigh only") has two
   plausible meanings (role map vs thinking-level picker), draw both and ask the human to
   point — don't guess.
2. **Trace the data flow end-to-end** from source of truth to render: pi-ai catalog
   (`models.generated.js` `thinkingLevelMap`) → bridge `toModelInfo()` →
   `supportedThinkingLevels` → StatusBar → `ThinkingLevelSelector` filter.
3. **Reproduce live** against the running dashboard (`:8000`) with the browser skill —
   open the composer's thinking-level dropdown, screenshot the single `xhigh` option.
4. **Find the divergence, not just the symptom.** Compare pi core's
   `getSupportedThinkingLevels()` against the dashboard's `toModelInfo()` projection — the
   bug is a **semantic misread**: pi treats `thinkingLevelMap` as a *sparse override*, the
   dashboard treats it as an *allowlist*.
5. **Locate where the bug is codified in the spec** (`openspec/specs/model-selector/spec.md`
   line 450, originally from archived `adopt-pi-071-072-073-features`) so the delta MODIFIES
   the right requirement.
6. **Scaffold the change manually** (`openspec` CLI has no `new`) — `proposal.md`,
   `design.md`, `tasks.md`, `specs/model-selector/spec.md`.
7. **Validate `--strict`** after every edit.
8. **Add a bridge-only review-gate section** to `tasks.md` (reload path, not full rebuild).
9. **Commit only the proposal directory** — leave unrelated working-tree changes untouched.

## 3. How the collaboration unfolded

**Phase 1 — Disambiguate (Discovery).** The AI's first move was *not* to trace code but to
lay out the two things "opus xhigh only" could mean — (A) the role map in
`~/.pi/agent/providers.json`, (B) the per-model thinking-level picker — with an ASCII
decision diagram. The human's one-line reply ("the picker, models selectable") collapsed
the search space instantly. *Why it worked:* investing one turn in framing avoided tracing
the wrong subsystem.

**Phase 2 — Static trace (Gather).** `grep` + `node -e` reads of
`models.generated.js` resolved the whole chain to **one line in the catalog**:
`claude-opus-4-* : thinkingLevelMap { xhigh: … }`. The AI showed the full pipeline from
catalog → `toModelInfo()` → dropdown filter, concluding the dashboard was "faithfully
reflecting a one-entry map."

**Phase 3 — Live reproduction (Verify).** On the human's steer *"Check in current running
dashboard with browser"*, the AI drove the live `:8000` dashboard, opened the composer's
thinking-level selector, and screenshotted the single `xhigh` option. This surfaced a
**second clue**: the trigger read `high` but `high` wasn't even in the selectable list.

**Phase 4 — Root cause (the pivot).** The human asked the sharp question: *"What can be the
problem's root cause?"* The AI first hypothesized a stale-persist bug, then dug into pi core,
found `setModel → _getThinkingLevelForModelSwitch → clampThinkingLevel` (pi **does** re-clamp
on model switch), which *disproved* the stale-persist theory and pointed at a **projection
divergence**. Side-by-side, pi's `getSupportedThinkingLevels` (sparse override: absent key =
supported) vs the dashboard's `toModelInfo` (allowlist: only map keys) — that's the bug.

**Phase 5 — Capture as OpenSpec (Generate).** On *"draft"*, the AI scaffolded the 4-file
change, traced the bug's origin to spec line 450, wrote a MODIFIED requirement + 6 scenarios,
and validated `--strict`. On *"yes"* it added a bridge-only review-gate section. On *"commit"*
it committed only the proposal directory.

## 4. Prompts that worked

- **The goal prompt** — `openspec-explore` skill invocation. Effective because it set the
  right *stance* (investigate + capture artifacts, never implement), which kept the session
  from prematurely writing a fix and instead producing a clean diagnosis + proposal.
- **High-leverage disambiguator** — *"the picker, not the model selector; models are
  selectable"* — one line that halved the search space. A stronger up-front version:
  *"The thinking-level picker for Opus shows only xhigh; the model picker is fine. Find why."*
- **The root-cause forcing question** — *"What can be the problem's root cause?"* — pushed the
  AI past its first (wrong) stale-persist hypothesis into the pi-core comparison that found
  the real divergence.
- **One-word drivers** — *"draft"*, *"yes"*, *"commit"* — each unlocked a full artifact phase
  because the preceding turn had already laid out exactly what would happen next.

## 5. Steering & corrections (what to watch for)

The decisive correction was epistemic, not tactical: the human's *"what's the root cause?"*
forced the AI to keep digging past a plausible-but-wrong answer to the structural one.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — but the workflow is highly repeatable and **should be
captured**. Recommended skill: **`trace-thinking-level-projection`** (or a broader

(2) static trace catalog→bridge→UI, (3) live browser repro, (4) compare pi-core function
vs bridge projection to find the semantic misread, (5) MODIFY the codifying spec requirement.

Skills that *were* leveraged: `openspec-explore` (stance), the `browser` skill (live repro),
and manual OpenSpec scaffolding validated with `openspec validate --strict`.

## 7. Pitfalls & dead ends

- **`openspec` CLI has no `new` subcommand** → scaffold the change directory + 4 files by
  hand, per convention, then `openspec validate --strict`.
- **First health-check `curl` failed** (bare `head -c` pipeline) → re-run writing to a temp
  file (`curl -s -o /tmp/health.json … && python3 -m json.tool`).
- **Stray field in a `tasks.md` edit** broke the first attempt → re-edit cleanly, re-validate
  `--strict`.
- **Stale-persist red herring:** the "trigger shows `high`, dropdown shows only `xhigh`" gap
  *looks* like a persistence bug — it isn't. pi re-clamps on model switch. Don't stop there;
  the real bug is the allowlist-vs-sparse-override projection mismatch.
