## 2. TL;DR playbook

1. Enter **explore mode** (`openspec-explore` skill) so the AI investigates without writing code.
2. Ask it to **trace the Stop path end-to-end** — client button → server engine → host abort — before theorizing about the bug.
3. Let it build the **evidence chain from source** (`rg`/`read` across `automation-plugin`, `server.ts`, `process-manager.ts`, `pi-gateway.ts`), not from assumptions.
4. Have it produce a **primitive-comparison table** (soft `abortSession` vs hard `killBySessionId`) — this is the diagnostic payoff.
5. Say **"draft proposal"** — it runs the coherence check (scan existing/archived changes), scaffolds via `openspec new change <name>`, writes proposal/design/spec/tasks, and validates `--strict`.
6. Ask for **"some example diagram"** — it emits Mermaid (project convention) for the primitives, the spawn→register race, and the completion path.
7. When you spot a **second related defect**, feed it as a plain-language observation; it extends all four artifacts under the shared root cause and re-validates `--strict`.
8. Say **"commit"** — it stages *only* the change dir and commits `docs(openspec): …`, leaving unrelated working-tree files untouched.

## 3. How the collaboration unfolded

**Phase 1 · Discovery (trace, don't theorize).** The AI resisted guessing. It located the
`automation-plugin` package, read its `AGENTS.md`, then followed the Stop path across
`routes.ts` → `engine.stopRun` → host `abortSession` in `server.ts`. *Why it worked:*
it built a verifiable call graph before naming a cause, so the diagnosis was falsifiable.

**Phase 2 · Root-cause isolation.** It surfaced the key fragility: `engine.stopRun` only
aborts when `ctx.sessionId` is set, and the abort itself is a soft `{type:"abort"}` WS
message (graceful turn-halt), *not* a process kill — while a hard-kill primitive
(`headlessPidRegistry.killBySessionId`) already existed and went unused. It captured this
in a two-mechanism comparison table plus a spawn→register race timeline. *Decision point:*
the operator picked option `1` to proceed to a proposal.

**Phase 3 · Draft the proposal.** On "draft proposal" it ran the project's coherence
convention (checked `openspec list`, scanned archived automation changes for
contradictions), found the existing spec *mandates the weak path*, then scaffolded and
wrote proposal.md, design.md, the spec delta, and tasks.md — validating `--strict`.

**Phase 4 · Diagrams.** "can you show me some example diagram?" → Mermaid flowchart +
sequence diagrams (per the repo's diagram convention), which doubled as design.md content.

**Phase 5 · Scope expansion.** The operator reported the completion-path bug in plain
language. The AI re-investigated (`spawnHeadless` → `buildHeadlessPiArgs` = `--mode rpc`,
persistent), confirmed `onSessionEnded` only finalizes the record and never tells the pi
process to exit, and **reframed the whole proposal around one root cause** — "the lifecycle
never terminates the session it spawns" — extending all four artifacts.

**Phase 6 · Commit.** "commit" → staged only `openspec/changes/fix-automation-stop-zombie-runs/`,
committed on `develop` as `786e1b4c4`, explicitly leaving unrelated pre-existing changes alone.

## 4. Prompts that worked

- **The goal prompt** (the `openspec-explore` skill preamble) — effective because it set a
  hard *no-implementation* stance, keeping the AI in trace/diagnose mode where it's strongest.
- **"draft proposal"** — a 2-word high-leverage unlock: it triggered the full
  scaffold→write→validate pipeline because the coherence conventions were already known.
- **"can you show me some example diagram?"** — cheaply produced reusable design.md content.

## 7. Pitfalls & dead ends

- **`openspec change new` is wrong** — the correct scaffold command is `openspec new change
  <name>`. The AI burned one failed command discovering this via `openspec --help`. If a
  scaffold fails, check the subcommand order.
- **Batch-index minification mangled bridge source** — `ctx_batch_execute` returned text
  where `"abort"` had been minified to `"n"`, misleading the first pass. *Fix:* `read` the
  actual handler file directly to confirm kill mechanisms rather than trusting a batched/
  indexed excerpt.
- **`agent_end` ≠ process exit** — the core trap the whole proposal addresses: a `pi --mode
  rpc` session idles forever after a turn ends; don't assume turn-completion reaps the process.
