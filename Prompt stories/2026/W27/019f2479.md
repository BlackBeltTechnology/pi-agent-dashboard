# How we did it: Split chat + editor workspace (OpenSpec proposal) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — thinking, not
implementing. The real objective, sharpened by the steering turns: the internal
Monaco editor pane and `ChatView` are currently *mutually exclusive* routes
(`/session/:id` **or** `/session/:id/editor`). The user wanted them **side-by-side
and resizable** — chat and editor in one split workspace, with the editor pinned to
the session's CWD, the opened file saved to the session, and a *second* resizable
divider inside the editor (browse-rail ↔ viewer). Along the way the user surfaced a
real bug: `@`-file-mention search "not found all files," suspected as a caching
issue. The final ask: **fold everything into ONE OpenSpec proposal** with mockups,
spec deltas, and a validated change — no app code (explore mode).

## 2. TL;DR playbook

1. Enter `openspec-explore`. Ground in the codebase **before** designing: `openspec list`,
   locate `EditorPane`, `ChatView`, `App.tsx` router, and the existing `ResizableSidebar`.
2. Map "already ships vs. actually asked" as a diagram — the delta is smaller than it looks
   because most machinery (tabs, file-tree, viewer-registry, resize-drag) already exists.
3. When the user reports a bug, **read the real mechanism** (`searchFiles()` in
   `command-handler.ts`) before theorizing. Here: no cache at all — a hard `MAX_VISITS=4000`
   BFS budget + depth-6 cap + `.gitignore` ignored. Correct the user's "stale cache" mental model.
4. Run the **mandatory pre-scaffold coherence check** on the subsystem's recent archive entries
   (`2026-06-30-add-internal-monaco-editor-pane`, `2026-06-05-fix-file-mention-search-ranking`).
   The archive explicitly chose "NO index" — do not silently reverse it.
5. Scaffold the change; build **one interactive HTML mockup** using real theme tokens that
   demonstrates every state (split↔unsplit, dark↔light, desktop↔mobile, dual-mode search,
   changed-on-disk banner). `serve_mockup` + browser screenshots to verify fidelity.
6. Write `proposal.md`, `design.md`, four spec deltas (`ADDED`/`MODIFIED`), and a TDD `tasks.md`.
7. `openspec validate <change> --strict` → fix quirks → commit **only** this change's folder.

## 3. How the collaboration unfolded

**Discovery (ground first).** The AI resisted brainstorming and instead read the
actual surfaces: `openspec list`, `EditorPane` dir, `ChatView` mount point, `App.tsx`
routes, and the `ResizableSidebar` drag pattern. It produced an ASCII "what already
ships" map. *Why it worked:* it reframed a big-sounding feature as a small delta on
existing machinery.

**Bug triage (read, don't theorize).** On the `@`-search complaint the AI opened
`searchFiles()` and found the opposite of the user's guess — no cache, a hard 4000
BFS visit budget + depth-6 cap that truncates large monorepos and ignores
`.gitignore`. When the user proposed a min-3-char fix, the AI **pressure-tested and
rejected it as insufficient** (the walk horizon is query-independent), while still
accepting min-3 as a useful debounce. *Decision point:* the human said "put it one
proposal" → unify split-layout + search-fix + dual-mode search.

**Coherence check (respect prior decisions).** The pre-scaffold sweep found the
archived ranking fix deliberately said *"NOT INTRODUCED: server-side caching or an
index."* The AI flagged that its own "watched file-index" pitch would reverse that
decision, then **downgraded the design** to a leaner `.gitignore`-aware + softened-budget
BFS that respects the prior choice.

**Design → Generate → Verify.** Built the interactive mockup with real dashboard
theme CSS vars, served it, screenshotted every state, caught + fixed a mobile flex
conflict and later added the **second (inner rail) divider** the user pointed out.
Wrote proposal/design/specs/tasks, validated `--strict`, and committed only the
`split-editor-workspace/` folder.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore`)** — kicking off in explore mode enforced
  think-before-build and produced grounding + a mockup instead of premature code.
- **"Put it one proposal"** — a 4-word high-leverage turn that collapsed three
  threads (split layout, `@`-fix, dual-mode search) into a single coherent change.
- **"The file editor browser panel is not resizable"** — surfaced a gap that was
  actually in the *original* ask; a precise, concrete correction the AI could act on
  immediately.
- **Weak → stronger:** "Maybe 3 char required? Is it make sense?" → better as
  *"Would a min-3-char debounce fix the missing-files complaint, or only reduce
  keystroke load? Explain the actual walk mechanism first."* — forces the mechanism
  read before accepting the fix.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Theorize a bug's cause ("stale cache") | Report the *symptom* and let the AI read the real code | State: "read `searchFiles()` before proposing a fix" |

## 6. Skills, tools & memory created — and why they're effective

- **Memory attempt (OpenSpec validator quirk):** the AI discovered that a
  requirement whose description **begins with a double-quoted phrase** (e.g. `Every "open
  a file" entry point SHALL…`) trips a false `[ERROR]` in `openspec validate`. It
  tried to persist this as a project `tool-quirk` memory but **project memory was
  full** — it correctly declined to evict a useful entry. *Reusable value:* if the
  strict validator flags a requirement that clearly contains SHALL, reword the
  leading quotes. **Recommend:** save this quirk once memory has room, or add it to
  the OpenSpec authoring notes.
- **No skill created**, but the workflow is repeatable — a **"scaffold an OpenSpec
  editor/UI change with a themed interactive mockup + coherence check"** skill would
  capture: ground → gap-map → coherence sweep → single-HTML mockup with real tokens →
  spec deltas → strict validate. Worth creating if this pattern recurs.

## 7. Pitfalls & dead ends

- **`openspec validate --strict` false ERROR** on a valid SHALL requirement →
  caused by a leading double-quoted phrase in the description. **Fix:** reword so the
  sentence doesn't *start* with quotes.
- **Mobile stacked layout clipped** — chat's `flex:1` ate the editor's space.
  **Fix:** give both panes explicit flex-basis / a row-resize divider so neither
  collapses below the fold.
- **min-3-char is NOT a fix for missing files** — the BFS visit horizon is
  query-independent; more characters can't reach past entry #4000 or depth 6. Treat
  min-3 as debounce only; the real fix is `.gitignore`-awareness + a softened budget.
- **Committing unrelated files** — `git status` showed pre-existing dirty files
  (`.pi/settings.json`, `groups.json`, `.bak-switch-*`). **Fix:** `git add` only the
  change's own folder, never `git add -A`.
- **Leftover mockup server** — always `serve_mockup{stop:true, port:<p>}` and verify
  the port is free (`lsof -nP -iTCP:<p>`) before declaring done.
