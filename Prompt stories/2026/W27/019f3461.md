# How we did it: Turning a "wall of tool rows" screenshot into a validated OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user entered **explore mode** (`openspec-explore`) with a screenshot of the chat
timeline showing a long, flat list of individual tool executions — grep, Read, grep,
Read… — and wanted them collapsed into a grouped, progress-aware widget. The first
prompt was the explore-mode skill boilerplate ("Enter explore mode. Think deeply…"),
so the *real* objective only crystallized through the screenshot and steering: **design
a new "burst group" UI that folds one uninterrupted run of heterogeneous tool calls
into a single collapsible widget — collapsed while running with a live progress signal,
summarized when done — and capture it as a validated OpenSpec proposal.** Crucially,
this was a *thinking* session: no implementation, just a mockup plus proposal/design/
spec/tasks artifacts.

## 2. TL;DR playbook

1. **Start in explore stance.** Load `openspec-explore` — it forbids implementation and
   keeps the work at the design/artifact layer.
2. **Ground against reality first.** `kb_search` + `grep` the existing timeline renderer
   (`groupConsecutiveToolCalls`, `ChatView.tsx`) so the design *evolves* the shipped
   `×N` collapse instead of colliding with it.
3. **Pull theme tokens** (`--bg-*`, `--text-*`, `--accent`) so the throwaway mockup
   looks native to the dashboard's 4-theme system.
4. **Build an interactive HTML mockup** in `/tmp` and `serve_mockup` it — show *multiple
   states side by side* (running-collapsed, running-expanded, done, baseline) so the
   human can pick between real forks.
5. **Resolve forks with tiny steering prompts.** Let the user answer "B2", "all three",
   etc.; re-serve the mockup after each decision.
6. **Run the repo's mandatory pre-scaffold coherence check** — sweep active + archived
   changes to prove no collision, then `openspec new change <name>`.
7. **Write the four artifacts** (proposal, design, spec delta, tasks) and
   `openspec validate <name> --strict`.
8. **Run doubt-driven-review**: spawn a fresh-context adversarial reviewer *with source
   access*, withhold your CLAIM, reconcile every finding, fold blockers back into the
   artifacts, re-validate.
9. **Commit surgically** — stage only the change directory, never the unrelated dirty
   files from other sessions. Leave unpushed.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / Grounding.** The AI resisted the urge to design blind. It
`kb_search`ed and grepped the timeline code and discovered the key tension: the existing
`groupConsecutiveToolCalls` collapses only *identical* consecutive calls (polling loops →
`×24`) and has a hard rule that **running tools are never grouped**. The user's ask was
the inverse: a *heterogeneous* burst, collapsed *while running*. Naming this "semantic vs
temporal" grouping axis up front is what made the rest coherent. *Why it worked:* design
against the shipped contract, not around it.

**Phase 2 — Mockup & fork resolution.** The AI built an interactive HTML mockup in
`/tmp/tool-group-mockup/index.html`, served it, and presented four states plus the flat
baseline. Each open design fork (what the running header shows, inner elision vs scroll,
denominator honesty, auto-expand behavior, coexistence with `×N`) was posed as a concrete
side-by-side choice. The human steered with terse prompts ("B2", "update mockup", "all
three"), and the AI re-served after each. *Decision points:* B2 (scrollbox, one collapse
level) beat the nested elision band; `12 done` (honest, no fake `~18` denominator) with an
indeterminate spinner; auto-expand while running → auto-collapse on done; nested `×24`
sub-group lives *inside* a burst.

**Phase 3 — Coherence check & scaffold.** Before scaffolding, the AI ran the repo's
mandatory pre-scaffold coherence check plus loaded `doubt-driven-review`. It swept active
and archived changes (`collapse-duplicate-tool-cards`, `add-openspec-change-grouping`,
`configurable-chat-display`, etc.), proved the new temporal axis doesn't collide, then
`openspec new change group-tool-call-bursts` and wrote proposal/design/spec/tasks.
`openspec validate --strict` passed.

**Phase 4 — Doubt-driven adversarial review.** The AI stated a CLAIM ("design is correct
and non-breaking"), *withheld it from the reviewer*, and spawned a fresh-context reviewer
with read access. The single-model reviewer returned **10 findings, 4 blockers**, verified
against actual source — including that the "reuse the same transparent-roles set" claim was
false (`assistant` is unconditionally transparent, so prose would be swallowed into a `×N`
group). The AI attempted a cross-model second opinion; all three paths failed (see §7). The
user said "stop"; the AI acknowledged cross-model as skipped and folded the findings in. The
load-bearing fix: **invert composition** — the burst pass runs OUTER on raw messages with
its own boundary rules, and `groupConsecutiveToolCalls` runs *inside* each burst, so prose
stays a real boundary. Re-validated `--strict`.

**Phase 5 — Surgical commit.** With ~10 unrelated dirty files from other sessions in the
tree, the AI staged *only* `openspec/changes/group-tool-call-bursts/`, committed
(`41c1cbdb3`), and deliberately left it **unpushed** (proposals pushed straight to
`develop` get cleaned up upstream).

## 4. Prompts that worked

- **The goal prompt (implicit).** The explore-mode boilerplate + a screenshot. A stronger
  kickoff would state the objective explicitly: *"Explore mode. Here's a screenshot of a
  flat wall of tool rows. Design a burst-grouping widget that collapses one heterogeneous
  investigation run while it's running, with a live progress signal, and capture it as an
  OpenSpec proposal. Don't implement."*
- **"How can expand the 7 more…?" + image.** High leverage — it surfaced the hidden
  second-level-collapse problem (expanding a big burst rebuilds the scroll wall), forcing
  the elision-vs-scroll fork.
- **"B2"** — a one-token decision that locked the scrollbox model. Terse steering works
  *because* the AI had laid out labeled options side by side.
- **"capture proposal and doubt review"** — unlocked the whole scaffold → validate →
  adversarial-review → reconcile phase in one short instruction.
- **"stop"** — cut the runaway cross-model probing (three dead paths) and let the AI
  proceed with the substantive single-model findings.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Propose a fake progress denominator (`12 / ~18`) | picking honesty (`12 done`) via the fork | State "no fabricated totals/labels" as a design rule up front |
| Over-engineer expansion (nested elision band, pinned head+tail) | choosing "B2" (plain scrollbox, one collapse level) | Default to the simplest collapse model unless the burst size demands more |
| Hide the "expand rebuilds the wall" issue | asking "how can expand the 7 more…?" | Enumerate the *second-level* collapse state in the first mockup |
| Keep probing dead cross-model review paths | saying "stop" | Cap cross-model attempts; fall through to single-model findings fast |
| Want to commit broadly | (AI self-corrected) surgical stage of only the change dir | Always `git add <change-dir>/` explicitly when the tree is dirty |

The quality bar the user imposed implicitly: **thinking-only** (no implementation),
**honest UI** (no invented denominators/labels), and **coherence with shipped code**.

## 6. Skills, tools & memory created — and why they're effective

No new persistent skill was created, but the session leaned on and validated three existing
ones worth invoking again:

- **`openspec-explore`** — enforces the "capture thinking, never implement" stance. Invoke
  whenever a design needs to become artifacts (proposal/design/spec/tasks) without code.
- **Pre-scaffold coherence check** — the mandatory active+archive sweep before
  `openspec new change`. It's what caught that the new *temporal* axis composes on top of
  the existing *semantic* `×N` collapse rather than colliding. Always run before scaffolding.
- **`doubt-driven-review`** — the CLAIM-withheld adversarial pass with source access. It
  found 4 verified blockers and exposed the false "reuse the transparent set" assumption.
  Invoke before any irreversible design commit.

Reusable tooling pattern: **interactive `/tmp` HTML mockup + `serve_mockup`, showing
multiple states side by side**, pulling real theme tokens so it reads as native. This is
the fastest way to make design forks *concrete* enough for one-token steering.

## 7. Pitfalls & dead ends

- **`openspec change new` is wrong** — the CLI is `openspec new change <name>` (the first
  form failed). Check `openspec --help` when a subcommand errors.
- **Cross-model review is fragile.** All three paths died: `opencode-go/deepseek-v4-flash`
  is a *role alias, not SDK-invocable* (empty output); `gemini` was `dyld`-broken (missing
  `libsimdjson.29.dylib`); `codex` returned 401 (expired auth). *If you hit this:* probe the
  reviewer with a trivial prompt **first**, and don't burn the session chasing dead paths —
  the single-model findings were already substantive.
- **Adversarial subagent returned empty output** on the first spawn (`Explore` label).
  Surface it and retry with a `general-purpose` label rather than proceeding as if reviewed.
- **Validator trips on stray edit keys** — leftover `newText_dummy`/stray keys failed
  `openspec validate --strict` twice. Reissue the edit cleanly.
- **Dirty tree from parallel sessions** — never `git add -A`. Stage only your change dir.
