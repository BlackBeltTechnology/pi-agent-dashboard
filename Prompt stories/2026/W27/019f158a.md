# How we did it: Scaffolding a "Directory Settings + scoped Markdown editing" OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (the `openspec-explore` skill) — a thinking
stance, not an implementation one: *read, search, sketch, but never write code.* The
operator wanted to think through an idea: the dashboard's folder-level "Pi Resources"
surface should become a proper **Directory Settings** page (cog-iconed, left-nav, like
global settings), and the operator should be able to **edit `.pi/` and `.md` files
in-place** with a file picker. The real objective, once the two short steering turns
landed, was concrete: **turn that idea into a validated OpenSpec change proposal that
is coherent with the codebase and with any active changes already in flight** — then
commit it. No code, just captured thinking.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore` skill) — states the "think, don't implement" guardrail for you.
2. **Ground before sketching.** Grep the real client (`packages/client/src`) for the exact components named in the idea (settings panel, folder action bar, the icon, the resource viewer) — don't design against an imagined layout.
3. Map the idea onto what exists; **name the hidden work.** Here: there is *no write path* today (read-only file API, render-only markdown), so "edit a file" is three layers, not one.
4. **Check for collisions with active OpenSpec changes** *before* scaffolding — a project rule. Grep `openspec/changes/` for overlapping work.
5. Reconcile with the collision: read the overlapping change's design and **build on its primitives** (reuse its write endpoint + security model) instead of forking a parallel API.
6. Steer with two words when ready: **"draft proposal. It depends on monaco feature."**
7. Scaffold the change dir manually (this OpenSpec version has **no `change new` command**): `proposal.md · design.md · specs/<cap>/spec.md (≥1 scenario each) · tasks.md`.
8. `openspec validate <change> --strict` until clean.
9. Commit **only** the proposal artifacts — leave unrelated working-tree edits unstaged.

## 3. How the collaboration unfolded

**Phase 1 — Ground (grep the real client).** The AI resisted sketching and instead
ran a burst of `grep`/`find` across `packages/client/src` to locate the two settings
surfaces (`SettingsPanel.tsx` global vs. the folder-level "Pi Resources" view), the
`FolderActionBar` icon, and the resource viewer. *Why it worked:* every later design
decision (icon swap, route shape, tab layout) referenced a real file, so nothing was
invented.

**Phase 2 — Name the hidden rock.** The AI decomposed "edit a file" into three
independent layers and surfaced that **only the cosmetic layer is cheap** — there is
no write endpoint, no editable markdown surface, no file picker, and no path-containment
allowlist for the global `~/.pi` scope. This is the highest-value move in the session:
it converted a one-line ask into an honest scope.

**Phase 3 — Collision check (the pivotal find).** Before scaffolding, the AI grepped
`openspec/changes/` and found an **active `add-internal-monaco-editor-pane`** change — a
4-phase roadmap whose v3 (`POST /api/file/write`) and v4 (edit existing + mtime-409
conflict) are *exactly* the write path this idea needs. It read that change's design and
noted it explicitly rejected CodeMirror in favor of Monaco. *Decision point:* rather than
build a second textarea/CodeMirror editor, realize the feature as the Monaco roadmap's
`MarkdownViewer` flipped to `editable` — one write path, one security model.

**Phase 4 — Generate + verify.** On the "draft proposal" steer, the AI discovered
`openspec change new` doesn't exist in this version, scaffolded the directory by hand
(5 files, each spec requirement carrying ≥1 scenario), and ran `openspec validate
--strict` until green. The security boundary — `isWritableMdTarget(absPath, {cwd?})`
with cwd-containment vs. a hard `~/.pi/agent/**/*.md` allowlist, realpath-normalized,
with traversal/symlink/sibling rejection scenarios — was made the centerpiece.

**Phase 5 — Commit surgically.** `git status` showed an unrelated `groups.json` edit.
The AI committed **only** the 5 proposal artifacts and left the unrelated change unstaged.

## 4. Prompts that worked

- **The goal prompt** (the `openspec-explore` skill invocation) — effective because the
  stance itself is a guardrail: it forbids implementation and *permits* creating OpenSpec
  artifacts, which is exactly the lane this work needed.
- **"draft proposal. It depends on monaco feature"** — a 6-word high-leverage steer. It
  did two things at once: unlocked generation, and *pinned the dependency* so the proposal
  was built on the Monaco change instead of forking a parallel write API. Restated stronger
  for reuse: *"Draft the proposal as a change that depends on `add-internal-monaco-editor-pane`
  — reuse its write endpoint and security model, don't invent a second one."*
- **"commit"** — trivial, but the AI correctly narrowed it to *only the proposal artifacts*.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this was an application of the existing
`openspec-explore` skill. The reusable asset is the **workflow shape** itself:

- **Ground → name hidden work → collision-check → reconcile → scaffold → validate → commit.**
  Its value is the *collision check before scaffolding* (a project rule) — it caught the
  Monaco overlap and prevented a duplicate write API and a contradicted design decision.

*If this pattern recurs*, a `scope-openspec-proposal-against-active-changes` skill would be
worth creating: grep `openspec/changes/` for overlap, read the overlapping design, and
express the new change as a dependency rather than a fork.

## 7. Pitfalls & dead ends

- **`openspec change new <name>` does not exist** in this OpenSpec version (command
  failed). → Scaffold the change directory by hand: `proposal.md`, `design.md`,
  `specs/<capability>/spec.md`, `tasks.md`; confirm subcommands with `openspec change --help`.
- **A stray grep against `packages/web/src`** failed — the client actually lives in
  `packages/client/src`. → Confirm the real package path before mass-grepping.
- **`openspec validate --strict` requires ≥1 scenario per requirement** — write each spec
  delta with at least one scenario or strict validation rejects it.
- **Unrelated working-tree edits** (`groups.json`) were present at commit time. → Stage the
  proposal dir explicitly (`git add openspec/changes/<name>/`), never `git add -A`.
