# How we did it: Elevate title design — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`/opsx-explore`) — a thinking-only stance:
read, search, visualize, but *never* implement; capturing thinking as OpenSpec
artifacts is allowed. The seed idea was vague: make the dashboard's **session and
folder titles feel more "elevated" / stunning** instead of flat text on flat cards.

The *real* objective, once the steering clarified it: **decide — with pixel
evidence across all themes and both light/dark modes — how much visual depth the
titles and cards can gain before it tips into "AI slop,"** then capture the survivor
as a validated, ready-to-build OpenSpec change. The answer that emerged was not the
original instinct (text-shadow on titles) but a disciplined Tier-1 stack: **font
weight 400→600 + a neutral panel bevel**, with everything riskier explicitly
deferred so nobody re-litigates it.

## 2. TL;DR playbook

1. Enter explore mode with the vague design instinct ("elevate the titles").
2. **Ground first**: `kb_search` + `grep` the real theme tokens, `SessionCard.tsx`,
   folder/workspace header markup. Confirm what exists (`--shadow-card`, 9 themes ×
   light/dark) and what's missing (no text-shadow token).
3. Build a **throwaway HTML mockup** in `/tmp` and `serve_mockup` it — "react to
   real pixels, not my table."
4. Iterate the mockup as **intensity ladders** (flat → subtle → boundary → cheese),
   one risk axis per page: title-shadow, depth, accent rim, selection glow.
5. **Test every claim in BOTH modes and all 9 themes** — the light pane repeatedly
   kills effects the dark pane loves.
6. When the user invokes UX validation, **cite the rule** (Laws of UX, Nielsen,
   WCAG) and tier the recommendation by evidence × risk.
7. Build a clean **Tier-1 before/after** so the shippable scope is unambiguous.
8. Scaffold the OpenSpec change (`openspec new change <name>`), write proposal /
   design / tasks / spec-delta, **copy the mockups into the change dir**, `openspec
   validate`, commit. Explore-mode = only the OpenSpec artifact is committed, zero
   source touched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding.** Before any sketching, the AI read the real
theme CSS, tokens, and the actual title elements in `SessionCard.tsx` /
`WorkspaceHeader.tsx` / `SortableWorkspaceFolder`. Finding: cards already lift
(`--shadow-card`, per-mode alpha) but the *text* is flat, and there is **no
text-shadow token**. *Why it worked:* the whole concept "lives or dies on the
light/dark axis," so knowing the token system up front framed every later test.

**Phase 2 — First mockup + the light/dark reveal.** The AI built
`/tmp/title-shadow-mockup/index.html`, served it, and screenshotted. The pixels
*contradicted its own prior table*: title-shadow is a **dark-mode-only affordance** —
on light backgrounds any visible shadow becomes dirty ink around glyphs. Decision
point: the human asked to "open mockup for me to check," making the human the judge
of pixels.

**Phase 3 — Boundary-finding across all 9 themes.** `all-themes.html` put all 9
themes × light/dark in an A/B grid with alpha sliders, then pushed the sliders to the
**failure boundary** (light 0.28 / dark 0.85) to find the safe ceiling, not just a
lucky default. Verdict: no alpha window makes light "lift"; it jumps from no-op to
grimy. Canary = Tokyo Night light (colored glyphs bleed first).

**Phase 4 — Depth & 3D ladders.** `depth-ladder.html` (flat → engrave → raised →
**extruded cheese** → panel bevel) located the tipping point: extruded glyph text is
the 2008-game-logo wall; the real "more 3D" win is **panel bevel** (raise the
container, keep glyphs crisp) — works identically in both modes.
`accent-bevel.html` ran a rim-light P0→P4 ladder and found P1 (status-colored top
hairline) is the tasteful ceiling, but exposed a **20-card confetti scaling trap**.

**Phase 5 — Selection-hierarchy conflict (human-driven).** The human flagged the
real risk: a status rim could compete with the *selected* card. The AI pulled the
**real** selected-card styling (animated rotating rainbow conic glow, 13s) and built
`selection-conflict.html`, `selected-glow.html`, and `selected-glow-light.html` to
prove selection still dominates — and re-confirmed light-mode dominance comes from
**border + tint + lift + a colored drop shadow**, never glow.

**Phase 6 — UX validation + Tier-1 isolation.** Asked to "use your UX validation
skills," the AI separated **elevation (depth)** from **attention (color)** — opposite
rules — and tiered the recommendation, citing Nielsen/Gestalt/WCAG. `tier1.html`
isolated the shippable scope: session-name 400→600 + neutral bevel, no color.

**Phase 7 — Capture as OpenSpec + commit.** Coherence check against existing
`theme-system` / `sleek-card-design` capabilities, scaffold via `openspec new
change`, write the 4 artifacts (with a validation record + rejected-variants list),
copy all 8 mockups into `mockups/`, `openspec validate` → PASSED, commit
(`a4d852216`, 13 files, no source touched).

## 4. Prompts that worked

- **The goal prompt** — the `/opsx-explore` template. It worked because the *stance*
  (think, don't implement; capturing OpenSpec artifacts is OK) kept the session from
  jumping to code and instead produced a decision backed by evidence. A stronger
  future kickoff would name the constraint explicitly: *"Explore how to elevate the
  session/folder titles. Test every option in BOTH light and dark and all themes.
  Reject anything that reads as AI slop. Capture the survivor as an OpenSpec change."*
- **High-leverage follow-ups (short, unlocked a lot):**
  - `"P1 seems ok, but check with current selected card design."` — forced the AI to
    pull the *real* selection styling instead of guessing; caught the hierarchy
    conflict early.
  - `"what about light theme?"` — the recurring, highest-value redirect; it repeatedly
    invalidated dark-only effects.
  - `"Use your UX validation skills, what is the suggestion?"` — flipped from vibes to
    cited principles and a tiered recommendation.
  - `"stop and commit"` — a crisp closure signal that ended exploration cleanly.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Validate an effect on **dark only** and call it a win | "what about light theme?" | State up front: *every* effect must be shown in light AND dark before it counts |
| Show a title effect **in isolation** from real selection state | "check with current selected card design" | Always mock new depth/color against the *real* selected-card treatment, not a clean list |
| Reach for **more glow / more 3D** ("push into rim-light") | "maybe glow for selected?" then reining it back to tiers | Frame each axis as an intensity ladder with an explicit "slop wall" rung, decide against the wall |
| **Vibe** the recommendation | "Use your UX validation skills" | Cite the rule (Laws of UX / Nielsen / WCAG), don't assert taste |
| Risk **decoration for its own sake** (confetti of status rims) | asking to see Tier 1 in isolation | Separate *elevation* (depth, every card) from *attention* (color, rare) — opposite rules |
| Leave mockups in `/tmp` | "add the mockups to proposal" | Copy validation artifacts into the change dir so they travel with the spec |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session, but the workflow is highly
repeatable and leans on existing assets:

- **`serve_mockup` + `score_mockup` + throwaway `/tmp` HTML ladders** — the core
  engine. Reusable problem it solves: *design decisions made on real pixels across
  the full theme matrix, not on the model's prose table.* Invoke whenever a visual
  change is theme-sensitive.
- **The mockup-loop / UX-validation discipline** ("cite the rule, don't vibe it") —
  turns taste debates into evidence. Invoke the moment someone asks "is this good UX?"
- **Recommended skill to create:** a **"theme-matrix depth mockup"** project skill

  screenshot all-9-themes × light/dark → find the slop-wall rung → isolate Tier-1
  before/after → fold into an OpenSpec change with mockups committed. This session is

## 7. Pitfalls & dead ends

- **`serve_mockup` ports time out.** The server died mid-review and restarted on a
  *new* port (63815 → 49516). Don't hardcode the port in follow-up curls; re-read the
  port from the latest `serve_mockup` output. A stale `curl` to the dead port 404'd.
- **`ctx_execute_file` was sandbox-blocked** for reading a source file — `read` still
  worked. If a sandbox tool refuses a repo file, fall back to plain `read`.
- **`openspec change new <name>` is the wrong subcommand** — it errored. The correct
  form is **`openspec new change <name>`**. Check `openspec new --help` when unsure.
- **Text-shadow on light is a physics dead end.** Any shadow strong enough to see on
  white becomes dirty ink; there is no safe alpha window. Don't spend cycles tuning
  it — light-mode depth comes from weight + size + color + a colored drop shadow.
- **Extruded/stacked glyph shadow is the slop wall** in both modes — the #1
  dated/"game-logo" tell. Cap glyph-level 3D below it.
- **Status-rim confetti** — an effect that's elegant on 3 cards becomes a rainbow on
  20. Always sanity-check depth/color effects at realistic list length.
