# How we did it: Turning a "table false-positive" hunch into a data-loss bug proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — thinking, not implementing.
The user's real objective emerged through the questions: *understand how the tree
`AGENTS.md` documentation system stays current* — who fills the purpose column, when
subagents spawn to do it, and why a new `.ts` file he'd seen in a chat log got no
doc-update subagent. That curiosity hardened into a concrete suspicion — *"maybe
`kb dox lint` is producing table false-positives"* — and the goal became: **ground the
hunch in the real parsing code and, if warranted, capture it as an OpenSpec change.**

What made it premium: eight short steering prompts drove a 4-hour investigation that
uncovered a **critical data-loss bug** the user hadn't even suspected.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore`) — investigate only, no code writes.
2. Ask the AI to **map the mechanism first**: who authors the `AGENTS.md` purpose
   column (LLM) vs who fills paths/hashes/orphan-pruning (the `kb dox` CLI).
3. Trace the **subagent visibility model**: which tree-update paths spawn an Agent
   (docs/ Rule-6 delegation, migration fan-out) vs which the main agent edits inline
   (source-tree rows). This explains "no subagent, but also no gap."
4. **Run the actual lint** (`kb dox lint`) and read the raw category counts — don't
   trust the headline number. Filter to the case you care about (missing `.ts/.tsx`).
5. Inspect the **`agentsFile` field** on reported orphans to test the false-positive
   theory against data, not intuition.
6. Before scaffolding, **read the parsing code** (`packages/kb/src/dox.ts`) — the
   regex on line 259 and the path resolution on line 263 are the smoking guns.
7. Scaffold the change with `openspec change new`, capture **both** defects, run
   `npx openspec validate <name> --strict`, then `git commit` **only** the new
   `openspec/changes/<name>/` artifacts.

## 3. How the collaboration unfolded

**Phase 1 — Mechanism discovery (16:46–16:58).**
The AI used `kb_search` + `kb_get` + targeted `read`s to lay out the *two update paths*
of the tree `AGENTS.md` system: deterministic CLI (path/hash/orphan) vs LLM-authored
(purpose/prose/caveman fragments). *Why it worked:* it established a shared mental model
before touching the bug, so every later finding had a place to land. The user's
follow-ups ("When is purpose filled by LLM?", "Where are spawned agents shown?") each
pulled a new thread the AI traced with fresh searches — including the producer/consumer
split where the actual spawning lives in an installed extension outside the repo.

**Phase 2 — Grounding the hunch in data (16:58–17:00).**
The user surfaced the real trigger: *"in a chat log I see a new `.ts` created but the
doc update was not there as a subagent."* The AI ran `kb dox lint` (exit 1, 1226 issues)
and — critically — **refused to trust the headline**. It filtered: **0 missing `.ts/.tsx`
rows**, 1069 orphans that looked like noise. *Decision point:* rather than accept
"drift," it checked the `agentsFile` field on the orphans to see who owned them.

**Phase 3 — The bigger bug (19:14–19:16).**
Before scaffolding, the AI read `dox.ts` directly. The table-scope regex (line 259,
matches *any* backtick-first-cell row) was the minor bug the user predicted. But
verifying the orphan data exposed a **critical second bug**: line 263 resolves row
paths against `cwd` (repo root) instead of the owning `AGENTS.md`'s directory —
so **991 of 992 basename orphans are false**, and `kb dox lint --fix` would **delete
all 991 valid rows**. A cosmetic hunch became a data-loss finding.

**Phase 4 — Capture & commit (19:16–20:45).**
The AI scaffolded `fix-dox-lint-false-positives` (proposal / design / tasks / spec
delta), answered the user's "maybe it's a settings option" question inside `design.md`
(and recorded it as a *rejected* alternative), validated `--strict` clean, then
committed **only** the four new artifacts — explicitly leaving unrelated pre-existing
working-tree changes untouched.

## 4. Prompts that worked

- **The goal prompt** (the explore-mode skill invocation): effective because it set a
  hard *investigate-don't-implement* stance, which kept the session producing a
  grounded proposal instead of a half-baked fix.
- **"When is the purpose filled by LLM?"** — a precise mechanism question that forced
  the AI to separate deterministic vs LLM responsibilities. High leverage: it seeded
  the whole mental model.
- **"And what about source code's AGENTS.md? Because in a chat log I see a new ts
   created but doc update was not there as subagent"** — the single most valuable
  prompt. It injected a concrete real-world observation the AI could test against
  `kb dox lint` data. *Rewrite for reuse:* lead with the anomaly and the evidence
  location ("in chat log X, a new `.ts` landed with no doc-update subagent — is that a
  gap or by design?").
- **"sketch that proposal. Maybe the mentions parameter have to be on settings.
   (I'm not sure)"** — good because it *offered a hypothesis while flagging
  uncertainty*, letting the AI evaluate and record it as a rejected option rather than
  silently adopt it.
- **"commit"** — terse, but the AI correctly scoped it to only the new artifacts.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The repeatable pattern deserves one:

- **Recommended skill — `investigate-lint-false-positive`:** a procedure for
  *validating a linter/CLI "drift" report before trusting `--fix`* — run the tool,
  read raw category counts, inspect the per-item ownership field (here `agentsFile`),
  then read the parsing/resolution code to locate the exact defect line before
  scaffolding a change. It removes the manual "is this real drift or noise?" triage
  and encodes the data-loss guardrail (`--fix` can delete valid rows). Invoke it
  whenever a repo-wide lint reports a suspiciously large orphan/missing count.

The workhorse tools were `kb_search`/`kb_get` (mechanism mapping), `bash` + `rg`
(finding the producer package and exact code lines), `ctx_execute` (data filtering),
and `openspec validate --strict` (the coherence gate before commit).

## 7. Pitfalls & dead ends

- **Don't trust the lint headline.** `kb dox lint` reported 1226 issues / exit 1;
  the truly actionable subset was tiny (8 over-threshold, 30 missing-companion). If you
  see a huge orphan count, assume noise until the `agentsFile` field proves otherwise.
- **`kb dox lint --fix` is dangerous here.** With the line-263 `cwd`-resolution bug it
  would delete 991 valid source-tree rows — the whole DOX record. Do **not** run `--fix`
  on this repo until the proposal lands.
- **The spawner isn't in the repo.** Subagent spawning + `inheritContext` live in the
  installed `@blackbelt-technology/pi-dashboard-subagents` extension
  (`~/.pi/agent/extensions/`), not the tree. Searching only the repo for the spawn
  logic is a dead end — the repo holds just the consumer/reducer half.
- **Two `ctx_*` tool calls errored** during data filtering; the AI recovered by
  switching to direct `bash`/`rg`. If `ctx_execute_file`/`ctx_batch_execute` errors,
  fall back to plain shell.
