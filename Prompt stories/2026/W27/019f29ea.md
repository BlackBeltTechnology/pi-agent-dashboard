# How we did it: Attributing the dashboard's "sometimes stuck" event-loop stalls — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — the user invoked the `openspec-explore` skill,
whose stance is *think, don't implement*. The first "real" ask came as a vague symptom
report, not a spec:

> "Sometimes seems the server stucked. I cannot decide it is happens on client or in the server."

The real objective, once the steering turns clarified it: **turn an intermittent,
un-attributed "the dashboard freezes for a fraction of a second" complaint into a
measured, non-duplicative OpenSpec change proposal** — one that names the actual
culprit rather than re-proposing fixes that already shipped. The finished artifact was
a validated `attribute-openspec-poll-eventloop-stalls` change (proposal + design + tasks
+ two spec deltas), committed to `develop`.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore` skill) — commit to *investigate, don't
   implement*. This is what keeps the output a proposal, not a half-built patch.
2. **Ground in reality before theorizing.** `kb_search` + `grep` the codebase for
   existing metrics infrastructure (`perf_hooks`, `monitorEventLoopDelay`,
   `hydration-metrics.ts`) so you build on what's there.
3. **Find the signal that already exists but isn't exposed.** Here: the server
   self-measures event-loop delay but only serves it poll-only via `/api/health`
   (and resets the histogram on read).
4. **Take a live baseline** — `curl /api/health` once. The `p99 ≈ 21ms` vs
   `max = 731ms` gap is the smoking-gun pattern for "sometimes stuck."
5. **Run a sampling loop** — poll `/api/health` ~20× over ~40s while reproducing the
   symptom. This *caught the spike live* and flipped the hypothesis (it was NOT
   hydration).
6. **Mine the server log in-sandbox** (`~/.pi/dashboard/server.log`) for tick-duration
   distributions to correlate the spike with a periodic task.
7. **Run the coherence check BEFORE drafting** — list archived openspec changes to
   avoid re-proposing already-shipped work. This is the highest-leverage step.
8. **Scaffold with `openspec new change <name>`**, write proposal/design/tasks + spec
   deltas as *measure-first* (attribute, then fix), then `openspec validate --strict`.
9. **Commit only your change directory** — stage the proposal dir explicitly, leave
   unrelated `.bak` files and other change dirs untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground in the real architecture).**
Before saying anything, the AI ran `kb_search` and a fan of `grep`s to map the existing
metrics spine: `extension/process-metrics.ts` (perf_hooks, event-loop delay, CPU, RSS),
the server's `hydration-metrics.ts` ring buffer, and the client (which measures nothing).
*Why it worked:* it refused to theorize about a stall before knowing what was already
instrumented. It found the server *does* self-measure event-loop delay — the question
became "is it exposed?" not "does it exist?"

**Phase 2 — Disambiguate client vs server.**
The user's steering ("I cannot decide it is client or server") is the classic "which
side stalled?" problem. The AI produced a truth-table of existing vs missing signals:
server event-loop delay ✅, hydration timing ✅, but client main-thread stall ❌ and
WS round-trip latency ❌. **Decision point:** the user narrowed the symptom to
"chatlog loading seems slow," giving the AI one concrete path to trace end-to-end.

**Phase 3 — Live measurement (the turning point).**
On the "run loop" steering, the AI polled `/api/health` 20× over ~40s while the user
opened chatlogs. It **caught a 711ms main-thread block live** — but the hydration
sample never changed during the spike, which **exonerated hydration and the client**
and pointed at a *periodic server task*. This is the moment guessing stopped.

**Phase 4 — Correlate to a timer + mine the log.**
The AI found two poll loops in `directory-service.ts`, identified `scheduleOpenSpecTick`
(60s cadence), and mined the 20MB server log in-sandbox for `durationMs` buckets:
9,327 of 9,533 ticks landed in 4–6s, fanning across 11–19 pinned dirs.

**Phase 5 — Coherence check (saved the proposal from being dead work).**
Before drafting, the AI listed archived changes and discovered mtime-gating,
poll-burst optimization, jitter, and worker-offload **all already shipped** (3 archived
changes). It also realized the `durationMs=4.6s` was **mostly the intentional 5s jitter
stagger**, so the built-in `TICK_SLOW_WARN_MS=5000` alarm was largely a false alarm.
The genuinely-unaddressed issue: discrete ~700ms event-loop spikes that stay *below*
the 5s warn threshold and are therefore invisible today.

**Phase 6 — Draft, validate, commit.**
The AI scaffolded the change with `openspec new change`, wrote a *measure-first*
proposal (attribute the sub-5s stall, then fix), added two ADDED spec deltas, fixed a
validator error (the requirement's first line must contain SHALL), passed
`openspec validate --strict`, and on "commit" staged *only* its change directory.

## 4. Prompts that worked

- **The goal prompt (the explore-skill invocation).** Starting in `openspec-explore`
  mode was the single best move — it locked the AI into investigation and produced a
  proposal instead of a premature patch. *Reuse this whenever a symptom is vague.*
- **"I cannot decide it is client or server"** — naming the *ambiguity* (not a fix)
  invited the AI to build a signal truth-table, which is exactly what a diagnosis needs.
- **"run loop"** (2 words) — unlocked the entire live-capture phase. A tiny prompt that
  triggered the measurement that flipped the hypothesis. High leverage.
- **"2"** — chose "draft the proposal," which then triggered the coherence check that
  saved the work from duplicating shipped changes.

**Rewrite of the weak opener:** instead of "Sometimes seems the server stucked,"
a stronger kickoff: *"The dashboard intermittently freezes for a fraction of a second.
Diagnose whether it's client or server before proposing any fix — measure first, and
check archived openspec changes so we don't re-propose shipped work."*

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session, but the workflow is **clearly
repeatable** and deserves one. Recommended skill to create:

- **`diagnose-eventloop-stall`** (project scope) — capturing the exact loop:
  (1) `curl /api/health`, read the `p99` vs `max` gap; (2) sampling loop 20× / 40s
  while reproducing; (3) if the hydration sample doesn't move during a spike, it's a
  *periodic server task*, not hydration/client; (4) mine `~/.pi/dashboard/server.log`
  for `durationMs` buckets; (5) **coherence check archived changes before drafting.**
  *Why effective:* it front-loads the two moves that saved this session — live capture
  (which flipped the hypothesis) and the archived-changes check (which prevented dead
  work). The existing `debug-dashboard` skill covers "why isn't X working" but not this
  *attribution* loop.

## 7. Pitfalls & dead ends

- **`ctx_execute_file` sandbox maps a different root** (3 failed calls). The sandbox
  couldn't see `~/.pi/dashboard/server.log`. *Fix:* just `grep` the log directly — the
  output (counts + a few samples) is small enough for context.
- **`/api/health` resets its event-loop histogram on every read.** A single poll during
  a quiet window shows nothing. *Fix:* run a sampling loop while reproducing the symptom.
- **`openspec change new` is not the command** (1 failed call). The correct invocation
  is `openspec new change <name>`. Check `openspec new --help` when unsure.
- **The `slow tick` warning is largely noise.** `TICK_SLOW_WARN_MS=5000` trips almost
  by construction because `jitterSeconds=5` inflates `durationMs` to ~4.6s. Don't chase
  the alarm; chase the sub-threshold ~700ms spikes.
- **Almost proposed already-shipped work.** mtime-gate + poll-burst throttling + jitter
  + worker-offload were all done in 3 archived changes. The coherence check is not
  optional.
- **Multi-curl-with-jq one-liner failed** across ports (1 failed call) — fall back to
  writing each response to a temp file then `jq` it.

## 8. Reproduce it faster — checklist

**Inputs to have ready:**
- A running production dashboard server (`pi-dashboard`, mode `production`).
- Access to `~/.pi/dashboard/server.log`.
- The ability to reproduce the symptom (open a large chatlog while sampling).

**Checklist:**
1. `openspec-explore` mode — investigate, don't implement.
2. `grep`/`kb_search` for the existing metrics spine (`perf_hooks`, `hydration-metrics`).
3. `curl -s localhost:8000/api/health | jq` — read `eventLoopDelay.{p99,max}`. A large
   `max` with tiny `p99` = intermittent single-tick block.
4. Sampling loop: poll `/api/health` ~20× / 40s while reproducing. Watch whether the
   hydration sample changes during the spike (it didn't → periodic task).
5. `grep -oE "durationMs=[0-9]+" server.log` → bucket the distribution; correlate to
   the 60s `scheduleOpenSpecTick` cadence.
6. **Coherence check:** `openspec list` + `ls openspec/changes/archive*` — read shipped
   work before drafting.
7. `openspec new change <name>`; write measure-first proposal/design/tasks + spec deltas
   (ensure each requirement's first line contains SHALL).
8. `openspec validate <name> --strict`.
9. `git add openspec/changes/<name>/ && git commit` — stage only your dir.
