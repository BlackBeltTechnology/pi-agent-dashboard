# How we did it: Wiring durable Google Gemini/Gemma access into pi — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with:

> _"gemma4 32b is not working. Maybe it is a provider be set by hand. Research how can be used with pi agent"_

The literal ask was "make gemma4 work in pi." But the steering turns revealed the **real** objective: get a *durable, unattended* Google model path working for pi — one that survives token expiry and reaches dashboard-**spawned** (non-interactive) sessions, not just the current shell. The journey walked through three auth worlds (AI Studio API key → user ADC → service account) and ended on Vertex AI + Gemini 3.x/2.5 with a service account, because Gemma-4 turned out to be a dead end on every path the user's org allows.

## 2. TL;DR playbook

1. **Don't trust "it's broken" — reproduce it.** Test the raw API (`curl` with the key) *and* `pi --provider … --model … -p "reply PONG"` before touching config. Half the "failures" here were unrelated dashboard-extension stack-trace noise (exit 0, real answer returned).
2. **Identify the auth type by prefix.** `AIza…` (~39 chars) = permanent AI Studio API key. `AQ.Ab8R…` (~53 chars) = short-lived OAuth token that will expire. If the user's org blocks plain API keys, AI Studio is a dead end → go Vertex.
3. **Pick Vertex AI (`google-vertex`) for durability.** It authenticates with a service account / ADC (no expiry), offers Gemini 3.x + 2.5 serverless. It does **not** offer Gemma-4 as a managed API (Gemma is Model-Garden self-deploy only → 404 on `generateContent`).
4. **Persist env vars where spawned pi can see them.** With oh-my-zsh, `~/.zshrc` is interactive-only. Put `GOOGLE_*` exports in `~/.zshenv` (sourced by *every* zsh) — or in an oh-my-zsh custom script that `~/.zshenv` then `source`s.
5. **Wire the service account for unattended auth.** Move the SA JSON out of `~/Downloads` to `~/.config/gcloud/service-accounts/` (`chmod 600`, dir `700`), set `GOOGLE_APPLICATION_CREDENTIALS` (takes precedence over user ADC, doesn't expire).
6. **Match the model to pi's param support.** Gemini 3.x → `thinking_level`; Gemini 2.5 → `thinking_budget`. `gemini-3.5-flash` on Vertex *rejects* `thinking_level` that pi sends → 400. Safe default: `gemini-2.5-flash` (GA, mature pi support, higher quota).
7. **Expect quota 404s on a fresh project.** Vertex's `global` endpoint returns a confusing **404 (not 429)** when you exceed the tiny per-minute per-model quota (as low as 5 RPM). Space diagnostic calls; don't burn quota with bursts.
8. **Verify end-to-end in a fresh non-interactive shell** (`zsh -c '…'`) simulating a spawned pi session, with user ADC disabled so only the SA can authenticate.

## 3. How the collaboration unfolded

**Phase 1 — Reproduce before fixing (Discovery).** The AI read pi docs + the user's `models.json`/`providers.json`, then tested the raw Google API with `curl` and a headless `pi … -p "PONG"`. Finding: the model, key, reasoning, *and* tool-calling all worked. The "failure" was unrelated dashboard-extension noise, and the user's hand-written `my-google` provider was a redundant duplicate of pi's built-in `google/gemma-4-31b-it`. **Why it worked:** proving the base case first stopped the team from "fixing" a working config. **Decision point:** user said "yes" → remove the redundant block.

**Phase 2 — The API-key dead end.** The user wanted a *permanent* key. The AI opened AI Studio and Cloud Console in the browser. But every key the user produced was still the short-lived `AQ.` OAuth token — and then the org policy surfaced: *"only service account keys can be used"* (plain `AIza…` keys blocked). **Decision point:** this killed the AI-Studio `google` path entirely.

**Phase 3 — Pivot to Vertex + make it durable.** The AI confirmed `google-vertex` authenticates via existing ADC (HTTP 200, PONG), then hardened persistence: env vars moved to `~/.zshenv` (spawned-session reach), organized into an oh-my-zsh `custom/vertex-ai.zsh` sourced from `.zshenv`, the stale `AQ.` token removed from `auth.json`, and the SA JSON relocated from `~/Downloads` to a `600` home location with `GOOGLE_APPLICATION_CREDENTIALS` set. The `vision` role was repointed off the blocked AI-Studio provider onto Vertex.

**Phase 4 — Gemma-on-Vertex research.** User asked whether Gemma-4 is reachable via Vertex. The AI ran an empirical test (404 on every Gemma variant, `global` + `us-central1`) *and* fetched Google's docs in parallel. Verdict: Gemma-4 on Vertex = self-deploy to your own GPU endpoint only, no serverless API, no API-key path. **A clean "no."**

**Phase 5 — The 404 mystery (systematic debugging).** `gemini-3.1-pro-preview` and later *all* models started 404-ing. The AI resisted the "model missing" guess: an isolated call after a 20s cooldown returned 200, but bursts of 8 all 404'd. Root cause: the `global` endpoint returns **404 instead of 429** on per-minute-per-model quota exhaustion — and the AI's own diagnostic bursts were eating the tiny quota. Preview/pro models sit at 5–15 RPM.

**Phase 6 — gcloud forensics + quota bump.** Using the *user* account (the SA was too low-privilege to read IAM/billing), the AI found billing WAS enabled (hypothesis wrong), the SA was missing `roles/aiplatform.user` (had only `aiplatform.serviceAgent`) — granted it — and confirmed the default `base_model` quota is 5 RPM. It enabled `cloudquotas.googleapis.com` and submitted 4 quota-increase preferences via the Cloud Quotas REST API (the SDK lacked the `gcloud quotas` group). All came back `granted: 5, reconciling` — **not** self-service on a fresh project. The AI opened the Console Quotas page for the user to push a human-reviewed request.

## 4. Prompts that worked

- **Goal prompt** — _"gemma4 32b is not working… Research how can be used with pi agent"_. Effective because it paired a symptom with an explicit "research" mandate, licensing the AI to investigate rather than blindly patch. Stronger version: _"gemma-4 fails in pi. - **High-leverage follow-ups:** _"yes"_ (approve the redundant-block removal), _"both"_ (do both durable fixes), _"test it"_ / _"Research"_ — tiny prompts that unlocked whole phases because the AI had already laid out the options.
- **The pivot prompt** — _"The api key does not allow to create Gemni API key it tels only service account keys can be used"_ — the single most valuable steer: it revealed the org policy and redirected the entire effort to Vertex.
- **The forcing prompt** — _"check with gcloud. Maybe some not allowed with service account, or the key is not okay"_ — pushed the AI from "it's transient" hand-waving into hard forensic evidence (billing, roles, quota numbers).

## 7. Pitfalls & dead ends

- **"It's not working" was mostly noise.** The dashboard/bridge extension crashes in print mode and dumps a stack trace *after* a successful completion (exit 0). Don't read that as a model failure — check for the real answer + exit code.
- **AI-Studio API keys are a dead end under org policy.** If keys must be service accounts, stop trying to mint `AIza…` keys → go straight to Vertex.
- **Gemma-4 on Vertex = 404.** It has no serverless `generateContent`; it's Model-Garden self-deploy (your own GPU endpoint) only. No API-key path exists for the user's org at all.
- **`gemini-3.5-flash` + pi = 400.** pi sends `thinking_level`; that Vertex model rejects it. Use `gemini-2.5-flash` (or a 3.x model that accepts `thinking_level`).
- **Vertex `global` returns 404, not 429, on quota exhaustion**, then a cooldown blocks *all* models. Isolated calls after cooldown return 200. Preview/pro models default to ~5 RPM on a fresh project.
- **`gcloud quotas` command group may be absent** from the installed SDK. Fall back to enabling `cloudquotas.googleapis.com` and calling the Cloud Quotas REST API (still gcloud-authenticated).
- **Quota bumps aren't self-service** on a fresh project — API requests came back `granted: 5, reconciling`; a human-reviewed Console request (with billing enabled + usage history) is the real lever.
- **Low-priv SA can't read billing/IAM** (`getIamPolicy` denied). Introspect with the Owner user account instead.

## 8. Reproduce it faster — checklist

**Inputs to have ready:**
- Google Cloud project ID with **billing enabled** (e.g. `judo-ng`).
- A **service account JSON key** with `roles/aiplatform.user`.
- gcloud installed; user account with Owner/Editor for admin checks.

**Steps:**
1. Reproduce first: `curl` the raw API + `pi --provider google-vertex --model gemini-2.5-flash -p "reply PONG"`. Ignore post-answer extension stack traces.
2. If org blocks plain API keys → skip AI Studio, use `google-vertex`.
3. Move SA key → `~/.config/gcloud/service-accounts/<proj>.json` (`chmod 600`, dir `700`).
4. Put exports in `~/.oh-my-zsh/custom/vertex-ai.zsh`, then `source` it from `~/.zshenv`:
   `GOOGLE_GENAI_USE_VERTEXAI=true`, `GOOGLE_CLOUD_PROJECT=<proj>`, `GOOGLE_CLOUD_LOCATION=global`, `GOOGLE_APPLICATION_CREDENTIALS=<sa-path>`.
5. Remove any stale `AQ.` token from `~/.pi/agent/auth.json`; repoint any roles (e.g. `vision`) off the blocked `google` provider onto `google-vertex/gemini-2.5-flash`.
6. Verify: `zsh -c 'echo $GOOGLE_CLOUD_PROJECT'` (non-interactive reach) + an SA-token `generateContent` call returning 200.
7. If 404s appear, space calls; if persistent, raise per-`base_model` quota via Console (human review) — API auto-adjuster keeps a fresh project at 5 RPM.
