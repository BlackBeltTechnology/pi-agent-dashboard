# How we did it: designing the KB folder slot in explore mode — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance where the AI may read, search, and produce OpenSpec artifacts but must **never
implement**. The first real content prompt was a terse hint: *"bash-write blind spot."*
That seeded an investigation into how the dashboard's markdown knowledge base (KB) gets
reindexed and where it silently fails to update.

The real objective only crystallized through steering: **make the KB visible and
controllable in the dashboard sidebar** — a per-folder slot showing entry counts + a
reindex button, with mockups — and, crucially, fix the worktree trap (worktrees don't
inherit the parent's KB and sit silently empty). It grew to include per-project source
path management and a hard architectural decision: **build it as a new dashboard plugin
(`packages/kb-plugin`), not fold it into the session extension.** Nothing was
implemented; the deliverable is a fully-validated OpenSpec change ready to build.

## 2. TL;DR playbook

1. **Start in explore mode** (`openspec-explore`) so the AI grounds in source and writes
   artifacts, never code.
2. **Ground the mechanism first.** Have the AI grep `docs/` + read the actual trigger
   files (`kb-extension/src/extension.ts`, `reindex.ts`, `indexer.ts`) before reasoning
   about the fix — the "blind spot" reframes once you see the code.
3. **Confirm the cost model** so the fix is cheap-by-construction: a no-op reindex
   short-circuits on `mtimeMs` before any read/hash → re-walking everything is fine.
4. **Ask for mockups** of the UI change. AI serves static HTML via `serve_mockup` and
   opens it in the **system browser** (`open <url>`) — not just a screenshot tool.
5. **Locate the reuse pattern** before designing infra: the per-folder sidebar slot
   (`FolderGoalsSection`, `FolderAutomationSection`) already exists → the KB widget is a
   `FolderKbSection` claiming the same slot; only two thin `/api/kb` routes are missing.
6. **Scaffold the OpenSpec change** matching an archived reference's `.openspec.yaml`
   shape; write proposal / design / spec / tasks; `npx openspec validate <name> --strict`.
7. **Extend on each new steering turn** (settings/path management, plugin packaging),
   re-validating `--strict` after every fold.
8. **Stop and summarize** — server down, artifacts listed, "nothing implemented."

## 3. How the collaboration unfolded

**Phase 1 — Discovery & grounding (the blind spot).** From the one-line hint, the AI
grepped `docs/` and read the two files that implement reindex triggering. It surfaced the
key distinction the whole question hinged on: the **KB (SQLite/FTS5)** auto-updates on
md write/edit via a debounced `tool_result` hook, while `docs/file-index-*.md` is a
human-curated catalog that does **not**. It then found two real holes: the hook *bails on
all bash* (comment defends against parsing bash for a path — but `scheduleReindex` ignores
the path anyway and re-walks everything), and **only `kb_search` calls `reindexNow`** —
`kb_neighbors`/`kb_get` don't. Grounding in source before theorizing is what made the
reframe possible.

**Phase 2 — UI investigation & mockups.** On the "add a KB slot to the directory" prompt,
the AI investigated the client's slot architecture (`dashboard-shell-slots`,
`plugin-ui-primitives`) and found the exact reusable pattern: plugins already render
per-folder sections. It confirmed the backend (`store.counts()`, `indexSource`,
`reindexNow` all exist) and pinned **the one gap: no `/api/kb` route**. It built a static
HTML mockup showing five KB states (populated / empty-worktree / indexing / stale / error)
and served it on `:59300`.

**Phase 3 — Scaffold the OpenSpec change.** After a "yes", the AI matched an archived
change's `.openspec.yaml` shape and wrote proposal / design / spec / tasks + the mockup,
validating `--strict` (exit 0).

**Phase 4 — Iterative extension under steering.** Three follow-ups each grew the change:
manage KB source **paths per project** (folder-scoped behind the `→`, not global
settings), then the naming polish loop ("KB" vs "Knowledge Base"), then the decisive
**"Is this whole developed to plugin?"** — which produced a three-layer diagram (engine
`packages/kb` → session extension `packages/kb-extension` → **new** dashboard plugin
`packages/kb-plugin`) and locked the packaging decision across all artifacts. Every fold
re-ran `openspec validate --strict`.

**Phase 5 — Stop.** On "stop", the AI killed the mockup server and summarized: proposal,
design (locked packaging), spec (4 req / 25 scenarios), tasks (8 groups), two mockups,
validates `--strict`, nothing implemented.

## 4. Prompts that worked

- **Goal prompt — `openspec-explore` stance.** Entering explore mode framed the whole
  session as *think + capture artifacts, never implement*. This is what kept a 2-hour
  design session from drifting into a half-built feature.
- **`bash-write blind spot`** — a 3-word hint that worked *because the AI grounded it in
  source first*. Terse hints are fine when you trust the AI to read the code before
  theorizing.
- **High-leverage one-word unlocks:** `yes` (scaffold the change), `extend` (fold in the
  path-management scope), `update` (lock the plugin decision). Short approvals move a lot
  once the AI has laid out a concrete plan to approve.
- **`Is this whole developed to plugin?`** — a single architectural question that forced
  the most important decision (new `kb-plugin` vs fold into the extension). Ask the
  "where does this actually live?" question *before* the tasks harden around a wrong host.

**Rewrite for next time:** instead of `Is it popssible to add to direcory a slot...`, a
future operator should say: *"In explore mode, design a per-folder sidebar KB slot showing
chunk count + reindex button, with worktree support; produce clickable mockups and an
OpenSpec change — don't implement."*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Show mockups only via a screenshot tool (Playwright not installed) | "open mockup" / "mockup open in system browser" | State up front: *serve the mockup and `open <url>` in the system browser* |

The naming loop (spell-out → wrap → revert to "KB") is the classic waste: **settle
user-facing naming before mockup polish**, keeping technical tokens (`kb_search`,
`/api/kb/`, `FolderKbSection`) lowercase and untouched throughout.

## 7. Pitfalls & dead ends

- **`ctx_batch_execute` hiccup** — one batch call errored; the AI recovered by running the
  greps directly. If a batch tool fails atomically, just run the commands individually.
- **Two failed `edit` calls** — section renames in `tasks.md` collided because edits match
  against the *original* file, and a stray `newText_dummy` key slipped in once. When
  extending an artifact, **re-read the current file first** and match exact live content.
- **Playwright not installed** → `score_mockup`/screenshots unavailable. Fall back to
  serving static HTML and `open <url>`; the mockup renders fine.
- **Naming wrap trap** — spelling out "Knowledge Base" broke the tight sidebar layout.
  Verify long labels against the real container width before committing wording.
