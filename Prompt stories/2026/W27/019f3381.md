# How we did it: Wire the non-zrok pairing view — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a rough, misspelled question:

> "How can I share QR code for conenct WHICH is not zrok?"

On the surface it reads like a how-to. But once the steering turns landed, the *real*
objective emerged: **there is no non-zrok pairing path a normal operator can actually
use.** The keypair-pairing backend shipped weeks earlier (`/api/pair/payload`,
`/redeem`, `/approve`, `/poll`), the device-side shell was built — but **the dashboard
web UI never calls any of it**, and the only way to add a non-zrok endpoint is
hand-editing `~/.pi/dashboard/config.json`. The task therefore became a **planning
change**: verify the gap against source, then scaffold an OpenSpec proposal
(`wire-nonzrok-pairing-view`) that wires the operator-side pairing view (QR generation
+ typed-compare approval) into `packages/client`, plus a config-free way to register a
non-zrok TLS endpoint — and to do so *without inventing a duplicate route.*

## 2. TL;DR playbook

1. **Trace before answering.** Grep `packages/server/src/pairing.ts`, `pairing-routes.ts`,
   and the whole `packages/client` tree for callers of `/api/pair/payload` and
   `/api/pair/approve`. Discover: **zero client callers** → the feature is unusable end-to-end.
2. **Separate the two QR mechanisms.** Sidebar QR = zrok-only (`QrCodeDialog.tsx`);
   Device Pairing QR = `{v,id,code,urls[]}` where `urls[]` = tunnel + `pairing.publicBaseUrls`.
   Only the second is non-zrok.
3. **Find the hard floor.** `getReachableUrls()` (`server.ts:247`) advertises **`https`/`wss` only**
   (D4/D14). Client identity-verify uses `crypto.subtle` (Ed25519) → **secure-context-only**,
   so plain-http LAN in a browser **cannot pair**. This is a browser rule, not a project choice.
4. **Run the pre-scaffold coherence check** (repo convention) to confirm no archived/active
   change collides. Delta target spec: `qr-device-pairing`.
5. **Scaffold via `openspec new change wire-nonzrok-pairing-view`**, then author
   `proposal.md`, `design.md`, `tasks.md`, `specs/qr-device-pairing/spec.md`.
6. **Ask for a `doubt-driven-review`** of your *own* draft before it stands. It caught a
   DRY violation: the proposed `POST /api/pair/public-urls` duplicates existing `PUT /api/config`
   (`writeConfigPartial` already merges `pairing.publicBaseUrls`).
7. **Apply corrections everywhere** — drop the new route, reuse `PUT /api/config`, move
   security to read-time `reachableUrls()` filtering, flag the shallow-merge clobber risk,
   and record the "oversight vs deliberate deferral" open question as a task.
8. **`openspec validate` until clean**, then **commit only the 5 change files** — surgically,
   leaving unrelated working-tree changes untouched.

## 3. How the collaboration unfolded

**Phase A — Discovery (what actually ships today).** The AI resisted answering the config
recipe and instead grepped the real wiring. It found two distinct QR paths and, critically,
that `/api/pair/payload` has **no caller anywhere in the client**. Decision point: the human's
follow-up ("Is this pairing mode can work with desktop frontend?… process flow?") forced the
AI to widen from "how to configure" to "what's the actual reachability model."

**Phase B — Grounding the LAN reality.** Steering turns 3–4 ("QR pairing for LAN when no
trusted network set?", "any way to use letsencrypt?") pushed the AI to trace the crypto path,
not hand-wave. It surfaced the **secure-context wall** (`crypto.subtle` undefined on plain-http
non-localhost) and the **Let's Encrypt DNS-01** constraint (LE issues for domains not IPs;
HTTP-01/TLS-ALPN-01 fail on a no-public-inbound LAN box). These became design decisions D5/D6.

**Phase C — Scaffold & draft.** The AI ran the coherence check first (repo protocol), scaffolded
with `openspec new change`, and wrote all four artifacts. Turns 6–7 ("yes", "yes, but in proposal
be a task") steered docs work into a *task* (FAQ entry, Rule-6 subagent + caveman style) rather
than doing it inline.

**Phase D — Self-review (the highest-leverage move).** Turns 8–9 ("honest review", "doubt review")
made the AI stress-test its own draft against source. It **flipped its own decision**: the new
route was a DRY violation vs `PUT /api/config`. What held up: the feature is genuinely unusable,
main-client placement is correct, the secure-context floor is real.

**Phase E — Apply & commit.** "apply" folded corrections across proposal/design/tasks/spec;
`openspec validate` confirmed only the intentional D2 supersession note remained. "commit" staged
**only** the 5 change files (`414229c36` on `develop`), leaving unrelated tree changes alone.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted. The session **consumed** three repo disciplines that
already exist and are worth invoking by name next time:

- **Pre-scaffold coherence check** (OpenSpec convention) — prevents duplicating archived work;
  invoke *before* `openspec new change`.
- **`doubt-driven-review`** — the star of this session. It made the AI verify its own claims
  against source and flip a bad decision (duplicate route) while correction was still cheap.
  Invoke on any non-trivial self-authored plan before it stands.
- **Rule-6 / caveman-style docs subagent** — the FAQ entry was scheduled as a task so the
  `docs/` write routes through a subagent, per repo protocol.

**Recommendation:** a small project skill — *"verify a shipped feature is wired end-to-end
(grep for zero-caller endpoints) before proposing new work"* — would make Phase A reproducible.

## 7. Pitfalls & dead ends

- **`packages/shell/src` doesn't exist where you'd guess.** One `ls packages/shell/src` failed;
  the PairView lives at `packages/shell/src/components/PairView.tsx` — grep, don't assume paths.
- **Don't propose a new route without grepping for an existing writer.** `PUT /api/config` +
  `writeConfigPartial` already persists `pairing.publicBaseUrls` with a generic no-whitelist merge.
- **Shallow-merge clobber:** `writeConfigPartial` merges `pairing` shallowly — the client must
  send the **full** `pairing` object or it wipes sibling keys.
- **Plain-http LAN pairing is impossible in a browser** — `crypto.subtle` is `undefined` outside a
  secure context. Don't design a UI that implies it works; teach the secure-road options instead.
- **Let's Encrypt won't help a LAN IP** — no cert for `192.168.x.x`; HTTP-01/TLS-ALPN-01 need
  public inbound. Only **DNS-01** works for an internal box.
