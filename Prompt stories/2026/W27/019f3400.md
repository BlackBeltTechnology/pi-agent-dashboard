# How we did it: Pivoting the Resources tree into per-type card pages — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation task. The operator wanted to rethink how the dashboard's **Resources**
surface presents skills / extensions / prompts. Today it's a **nested collapsible tree**
where a row's *position* carries the meaning: nesting under `LOCAL`/`GLOBAL` encodes
scope, nesting under a `📦 package` encodes source. The real objective — clarified over
the steering turns — was to **flatten that tree and re-pivot on resource *type***: give
Skills / Agents / Extensions / Prompts / Themes their own left-nav pages with a **card
grid**, and move the facts the tree encoded by position (scope, source, path, toggle)
onto each card as **badges**. The output was not code — it was a captured, validated
**OpenSpec change proposal** (`resources-card-tabs`) plus two interactive mockups.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) so the AI thinks/sketches but never implements.
2. **Ground in real code first** — grep for the existing Resources view, tree component,
   the `PiResource` shared type union, and the settings-panel nav before proposing anything.
3. **Pull the real theme tokens** (`--bg-*`, `--accent-*`, light-theme block) so the mockup
   looks like the actual dashboard, not a generic sketch.
4. **Build an interactive HTML mockup** and serve it (`serve_mockup`); screenshot with the
   browser tool for review.
5. **Answer the AI's design questions tersely** (`1. yes … 2. delete … 3. keep`) and say
   **"iterate mockups for all"** to unlock building every type page in one pass.
6. **Ask for the sibling variant** ("sketch global settings variant") to prove the shared
   card component works under a *different* nav shape.
7. **Say "capture"** to convert the explored design into the four OpenSpec artifacts
   (proposal / design / tasks / spec deltas), mirroring a recent similar change's structure.
8. **Validate** with `openspec validate --strict`, **stop the mockup server**, then **commit
   only the change dir** — nothing else.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground before sketching).** The first thing the AI did on the goal
prompt was *not* draw — it ran a burst of `grep`/`find` to locate `ResourcesPage.tsx`,
`resource-tree.tsx`, the `PiResource` union in `packages/shared/src/rest-api.ts`, the
`DirectorySettings/` components, and the `SettingsPanel.tsx` nav. **Why it worked:** the
resulting mockup and proposal were anchored in real file paths and the real type union, so
the design named actual server work (scan `.pi/agents/*.md`, extend the `type:` union)
rather than hand-waving.

**Phase 2 — Design articulation (make the pivot legible).** The AI drew the BEFORE→AFTER of
both the tree and the nav as ASCII, and — crucially — a **mapping table** ("old tree
position → new card element"): `under LOCAL/GLOBAL → scope badge`, `loose vs under 📦 →
source badge`, `path → mono line`, `tree toggle → card toggle`. This table became the spine
of the whole change.

**Phase 3 — Generate + iterate mockups.** The AI pulled the real light-theme tokens, built
`index.html` (Directory Settings variant), served it via `serve_mockup`, and screenshotted
it. After the operator's terse three-answer steer plus **"iterate mockups for all"**, it
built all five type pages into one interactive mockup with **type-specific card
treatments** — Agents show `◆ model` + `🔧 tools` badges, Themes get a live **swatch strip**
instead of a description row.

**Phase 4 — Prove portability.** On **"sketch global settings variant"** the AI checked the
global `SettingsPanel` (grouped nav, global-scope only), then produced `settings.html` using
the **identical card component** under a *grouped* nav — deliberately slotting the five pages
into a **new `RESOURCES` group** to avoid a name clash with the existing `Extensions` group.
This proved the card design survives a second surface.

**Phase 5 — Capture + verify.** **"capture"** turned the explored design into
proposal / design / tasks / four spec deltas, structured by mirroring a recent similar
change. `openspec validate --strict` passed. Then **"stop mockup server"** and **"commit"**,
with the AI carefully staging **only** the `resources-card-tabs/` dir.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Launching via `openspec-explore` set the right
  contract up front: *think and sketch, never implement, but you MAY create OpenSpec
  artifacts.* This is why the session produced a validated proposal instead of half-built
  React. **Reuse it** for any "rethink this surface" task.
- **"Iterate mockups for all"** — a 4-word high-leverage unlock. It authorized the AI to
  stop asking per-page and build every type page (Skills/Agents/Extensions/Prompts/Themes)
  with appropriate per-type card treatments in one pass.
- **"sketch global settings variant"** — cheap prompt, big payoff: it forced the design
  through a *second* nav shape, exposing the `Extensions`-group name-clash and validating
  the shared card component.
- **"capture"** — the one-word command that converts explored thinking into durable OpenSpec
  artifacts. Effective because the AI had already grounded everything in real paths, so
  "capture" had concrete material to serialize.
- **Terse numbered answers** (`1. yes, have own / 2. delete / 3. Keep packages as it is`) —
  answering the AI's own decision questions inline kept momentum; no re-explaining needed.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Design one page and pause for confirmation | "iterate mockups for **all**" | State "build all N type pages in one interactive mockup" in the goal prompt |
| Treat the mockup as the deliverable | "capture" | Ask up front: "when the design settles, capture it as an OpenSpec change" |
| Keep the mockup server running | "stop mockup server" | End explore sessions with an explicit teardown step |
| Risk staging unrelated dirty files | "commit" (AI then staged **only** the change dir) | Tell it "commit only `openspec/changes/<name>/`, leave pre-existing changes untouched" |
| Sketch generic UI | (implicit, self-corrected early) | Always say "pull the real theme tokens first" so the mockup matches the app |

The through-line: this operator steers with **very short prompts** and trusts the AI's
grounded defaults. That only works because Phase 1 (grounding in real code + tokens)
happened first — the terse steers land because the AI already had the full picture.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were saved this session, but the workflow leaned on three existing
tools worth naming:

- **`openspec-explore` (the stance).** The reusable asset here is the *explore→capture*
  discipline: think and mock freely, never implement, then serialize into OpenSpec artifacts
  on "capture". Invoke it for any surface-redesign where the design isn't settled.
- **`serve_mockup` + browser screenshot.** Fast visual iteration loop — serve an HTML mockup,
  screenshot, review, revise. Effective because it's disposable (torn down at the end) yet
  concrete enough to make real layout decisions.
- **Recommended skill to create:** an *"explore-to-capture"* checklist skill that codifies
  this exact sequence (ground in code → pull tokens → interactive mockup → prove on a second
  surface → `openspec validate --strict` → commit only the change dir). This session ran it
  by hand across 6 prompts; it's clearly repeatable.

## 7. Pitfalls & dead ends

- **Name-clash trap:** folding the five resource pages into the existing `Extensions` nav
  group would have created a group named "Extensions" containing an item "Extensions". The AI
  caught this and made a dedicated `RESOURCES` group. **If you add per-type pages to a
  grouped nav, check for a group/item name collision first.**
- **Agents is not just a relayout:** the "Agents" type requires **real server work** —
  enumerate `.pi/agents/*.md`, parse `model` + `tools` frontmatter, and add `type: "agent"`
  to the `PiResource` union in `rest-api.ts`. Don't let a card-grid mockup hide the backend
  cost; the proposal called it out explicitly.
- **Mockup server left running:** `serve_mockup` binds a port (49329 here) and stays up until
  told to stop. End with an explicit "stop mockup server" or you leak the port.
- **Dirty worktree at commit time:** the repo had unrelated untracked/modified files
  (`manage-flows`, `groups.json`, `b05_*.txt`). The AI staged only its own change dir — do
  the same, never `git add -A` at the end of an explore session.
