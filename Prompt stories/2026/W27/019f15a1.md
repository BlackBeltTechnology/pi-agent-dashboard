# How we did it: Restoring instant "prompt sent" feedback — an AI collaboration guideline

## 1. Goal (the ask)

The user opened **explore mode** to think through a UX annoyance: when you send a
prompt to an *idle* dashboard session, the chat shows nothing for the full
server round-trip (several seconds) before the message bubble appears. The first
prompt was the standard `openspec-explore` skill preamble ("Enter explore mode.
Think deeply… NEVER write code"), and the real objective surfaced immediately:
*can we render the message client-side instantly with an "in-progress" visual
(optimistic UI), and — crucially — does that collide with the existing mid-turn
message-queue logic?* The session never wrote app code; the deliverable was a
**validated OpenSpec change proposal** (`optimistic-prompt-progress`) plus an
interactive mockup, committed on `develop`.

## 2. TL;DR playbook

1. Enter explore mode with the `openspec-explore` skill — this is thinking-only, no code.
2. **Ground before sketching.** Trace the real send path (`useSessionActions.ts` →
   `handleSendPromptToSession`) and the render path (`event-reducer.ts` → `ChatView.tsx`)
   with `grep`/`Explore` before proposing anything.
3. Discover the key fact: the feature *already existed* (`optimistic-prompt` capability)
   but v2 removed the write site — the bubble/type/timeout are dead-code, still present.
4. Build an **interactive HTML mockup** (`serve_mockup`) showing current-vs-proposed
   3-state design, using the real theme tokens and bubble geometry. Screenshot it (`score_mockup`).
5. When the user asks "will this affect the message-queue logic?" — **don't guess.**
   Read the queue code and the v2 removal commit (`git log -S`, `git show 0375da1b`) to
   learn *why* the optimistic write was killed (ghost-reappearance bug class).
6. Frame the design so the write is **scoped to idle sends only** — which dissolves the
   entire ghost-bug class by construction (queue bugs only fire when a queue exists).
7. Draft the OpenSpec change: `proposal.md`, `design.md`, `specs/…/spec.md` (MODIFIED/REMOVED
   deltas against the existing capability), `tasks.md`. Run `openspec validate --strict`.
8. Commit **only** the change dir; leave unrelated untracked dirs alone.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / Grounding.** Instead of jumping to a design, the AI traced
the actual send and render flow (spawned an `Explore` subagent, then `grep`ped the
send handler, reducer, and `ChatView`). This surfaced the session's pivotal insight:
the optimistic-prompt feature *used to exist and was removed in v2* — the type,
render block, and 30s timeout are all still in the tree as disconnected dead-code.
Grounding first is what turned a vague "add optimistic UI" into "reconnect a removed
feature, correctly this time."

**Phase 2 — Mockup & visual steering.** The AI built an interactive mockup with
real tokens showing a 3-state progression (SENDING → SENT → confirmed), served it,
and screenshotted it. The human steered on a visual bug ("the blue gradient appears
outside the card" + screenshot) — the AI diagnosed a mis-placed `overflow:hidden`
(clip on the pseudo-element instead of the bubble) and fixed it.

**Phase 3 — The queue-collision investigation (the important part).** The human
asked "Is [this] will effect the message queue logic?" The AI resisted guessing and
instead read the queue code, finding the comment that spelled out the v2 rationale,
then dug into commit `0375da1b` to reconstruct the **ghost-reappearance bug class**
that the unconditional v1 write caused. This is where the design's core constraint
was found: scope the write to *idle* sends.

**Phase 4 — Proposal drafting.** On "draft proposal," the AI checked OpenSpec
conventions and an existing change layout, noticed the **spec/code were out of sync**
(the `optimistic-prompt` spec still described a write the code had deleted), and
wrote the change to reconcile them. `openspec validate --strict` passed.

**Phase 5 — Commit.** On "commit," the AI staged only the change dir, left an
unrelated `card-gradient-state-animation/` untracked dir alone, and reported the
next step (confirm the bridge ack in `bridge.ts` decides 3-state vs 2-state).

## 4. Prompts that worked

- **The goal prompt** (the `openspec-explore` skill invocation): effective because it
  set a hard "thinking, not implementing" stance, which kept the AI grounding in real
  code and producing a *proposal* rather than a half-baked patch.
- **"Is [this] will effect the message queue logic?"** — the single highest-leverage
  prompt. It forced the AI to investigate the exact interaction that had sunk the v1
  implementation, and became the design's central constraint. A stronger phrasing:
  *"Before we design this, check whether it collides with the mid-turn queue and why the
  earlier version was removed."*
- **"draft proposal"** — short, unlocked the full artifact set because the grounding
  work was already done.
- **"commit"** — worked because the AI had already isolated its change to one dir.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Produce a visually plausible mockup with a CSS clip bug | "the blue gradient appears outside of card" + screenshot | Screenshot-review every mockup state; put `overflow:hidden` on the clipping container, not the pseudo-element |
| Risk designing optimistic UI in isolation | "Is [this] will effect the message queue logic?" | State up front: *any* send-path change must be checked against the mid-turn queue and the v2 removal history |
| Move toward proposal before understanding the removal | "yes" (dig into git history) | Always `git log -S`/`git show` the commit that removed a feature before re-adding it |

The through-line correction: **don't re-add a removed feature until you understand
why it was removed.** The human's queue question is what converted this from a
regression-reintroduction into a properly-scoped fix.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The workflow, however, is a strong
candidate for one:

- **Recommended skill: "reconcile spec-vs-code drift for a removed feature."**
  It captures the repeatable move set here — trace the live path, detect the
  dead-code/spec mismatch, `git show` the removal commit to recover the *reason*,
  then scope the re-introduction so the original failure class can't recur. Invoke it
  whenever a spec describes behavior the code no longer has, or when re-adding
  something a prior commit deliberately deleted.

The session leaned on existing tooling well: `openspec-explore` (stance),
`serve_mockup`/`score_mockup` (visual proof), and `openspec validate --strict` (gate).

## 7. Pitfalls & dead ends

- **CSS sweep bleed:** an `::after` sweep gradient slid past the bubble's rounded
  corner. If you see a gradient escaping a rounded card, move `overflow:hidden` onto
  the bubble element itself, not the animated pseudo-element.
- **The ghost-reappearance bug class:** the v1 optimistic write was *unconditional*
  (fired on every send, including mid-turn queue entries), which spawned a cascade of
  "ghost card pops back" bugs each needing its own band-aid (clear-all, per-chip
  remove). Don't set an optimistic bubble on mid-turn sends — scope it to idle only.
- **Spec/code drift:** the `optimistic-prompt` spec still described a write the v2
  commit had deleted. When a capability spec and the code disagree, treat reconciling
  them as part of the change, not an afterthought.
