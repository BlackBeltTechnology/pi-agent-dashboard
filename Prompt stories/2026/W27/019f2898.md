# How we did it: colorize default mermaid nodes from the theme palette — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation task. The operator's real objective emerged over the first few turns: the
dashboard renders Mermaid diagrams with Mermaid's stock `default`/`dark` themes, so every
node gets the same pale grey fill — while the app already ships a rich, theme-aware accent
palette (6 hues × light/dark × 4 themes) that never reaches the diagrams. The ask, once
clarified by steering: **auto-color each *default* node with a different accent hue, but
leave any node the author explicitly colored alone** — auto-rainbow with manual override
winning. The output was not code but a complete, `--strict`-validated OpenSpec change
proposal plus a live interactive mockup that pinned down the exact visual treatment.

## 2. TL;DR playbook

1. Enter `openspec-explore` mode — you want a proposal/design captured, not code written.
2. Ask the AI to **map the current render pipeline** (which component initializes mermaid,
   what theme vars are set). It found `MermaidBlock.tsx` only overrides fonts.
3. State the real mechanism precisely: *"auto-color default nodes; author-colored nodes
   win."* This is a different lever than "wash one brand color over everything."
4. Demand the detection heuristic be **grounded in real DOM, not guessed** — render actual
   mermaid 11.16 output in a browser and inspect the emitted SVG.
5. Adopt the one clean signal it found: shape's inline `style` contains `fill:` → author
   set it → **skip**; empty → **default** → colorize. Use `hash(nodeId) → accent` for
   edit-stable colors.
6. Ask for a **live mockup** using the *real* accent tokens from `themes.ts`, with a
   before/after toggle and a theme selector.
7. Tune the visual on screen: "too harsh" → soft tint (low-opacity fill + full-accent
   border + normal text); dial a strength slider; lock the value ("8%").
8. Have the AI back-propagate the chosen value (8%) into proposal/design/spec/tasks,
   re-validate `--strict`, then commit **only** the change's files.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (map the pipeline).** The AI grepped for mermaid usage, found the
React `MermaidBlock` component, and drew the current color pipeline: stock theme → pale
fills, with the rich `themes.ts` accent tokens sitting entirely unused. *Why it worked:* it
established that the diagrams live in a separate color world before proposing any fix, so
the proposal targeted the actual gap.

**Phase 2 — Reframe the mechanism.** After steering #1, the AI recognized the ask was
*per-element variety with author override*, not a single brand wash. Crucially it flagged
the constraint that shapes the whole design: mermaid `themeVariables` has one fill slot for
flowchart nodes — there is no palette-cycling knob — so variety must be applied
post-render in the SVG.

**Phase 3 — Ground the heuristic in real DOM.** Rather than guess how to tell "default"
from "author-colored," the AI rendered real diagrams and inspected output. It first tried
jsdom, hit its missing CSS APIs, and pivoted to a **real browser** (the dashboard's actual
environment). Result: one unified predicate — inline `style` contains `fill:` → skip — that
covers `style X`, `classDef`, and class-diagram styling across flowcharts and class
diagrams. *This is the session's key insight, and it was evidence-based, not assumed.*

**Phase 4 — Scaffold the OpenSpec change.** `openspec new change …` created the tree; the
AI wrote proposal/design/tasks/spec, encoding the grounded DOM evidence and the
`hash(id) → palette` scheme, and validated `--strict`.

**Phase 5 — Mockup + on-screen tuning.** Steering #3 asked for a live mockup using the real
tokens. The AI built an HTML page running the exact colorize pass, served it, and verified
it in a browser. The operator drove the aesthetic directly: "too harsh" → soft tint; then
"8% is cool" locked the default. The AI then updated all four artifacts to match and
re-validated.

**Phase 6 — Surgical commit.** It staged only the five files of the change and left
pre-existing unrelated modifications untouched.

## 4. Prompts that worked

- **The goal (explore mode).** Entering `openspec-explore` set the right stance: capture
  thinking as artifacts, never implement. Good kickoff because it kept the output a
  reviewable proposal, not premature code.
- **"not one color the classes when no direct color given for diagram element"** (steering
  #1) — short but decisive: it corrected the whole mechanism from "brand wash" to
  "per-element auto-color with author override." Reframed the design.
- **"create mockup with the current mermaid renderer with the extended color tokens"**
  (steering #3) — high-leverage: forced a *live, real-token* artifact instead of a
  description, which is what made the aesthetic decisions possible.
- **"Its too harsh" → "8% is cool"** — two tiny prompts that converged the visual by direct
  observation. Stronger than any verbal spec of "subtle."

*Rewrite for next time:* combine the mechanism up front — *"Auto-color only default mermaid
nodes from the theme accent palette; any node with an explicit fill keeps its color. Ground
the default-vs-authored detection in real rendered DOM, then build a live mockup with the
real theme tokens and a strength slider."*

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session — but two reusable patterns are worth
capturing:

- **"Ground detection heuristics in real rendered DOM."** Instead of guessing which SVG
  attribute distinguishes author-colored from default nodes, render the actual library
  version in a real browser and read the emitted markup. Removes fragile assumptions and
  produces a design backed by evidence. Invoke whenever a design hinges on a third-party
  renderer's output shape.
- **"Real-token live mockup for aesthetic decisions."** Build a served HTML page running the
  *exact* proposed algorithm against the *real* design tokens, with before/after toggle and
  a tuning slider, so the human decides the look by eye and the chosen value is copied back
  into the spec. Invoke for any visually-subjective change ("too harsh"/"too subtle").

## 7. Pitfalls & dead ends

- **jsdom can't render mermaid 11.** It lacks the CSS APIs mermaid 11 needs — if you try to
  inspect output under jsdom you get errors. Render in a real browser (also matches the
  dashboard's actual environment).
- **Wrong edit-parameter names split the update.** Two `edit` calls failed when back-propagating
  the 8% decision; the fix was to split into separate, precise edits. Keep artifact edits
  small and targeted when reworking proposal/design/spec/tasks together.
- **Commit scope creep.** The working tree had unrelated modified/untracked files. Stage
  *only* the change's files (`git add openspec/changes/<name>/`) — don't `git add -A`.
- **Mockup lives in `/tmp`, not committed.** The `/tmp/mermaid-mockup/` reference is scratch;
  it is intentionally not part of the change. Stop the served server when done.
