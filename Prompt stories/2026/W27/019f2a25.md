# How we did it: A discipline-skills trilogy from a Hermes review — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The session opened in **OpenSpec explore mode** — a "thinking, not implementing"
stance. The first prompt was the skill's own boilerplate: *"Enter explore mode.
Think deeply… follow the conversation wherever it goes."* There was no explicit
feature request in prose; the real objective **emerged through steering**: survey the
external **Hermes Agent** skill catalog, find what genuinely fills a gap in
pi-dashboard's `eng-disciplines` package, de-risk the riskiest claim with a runtime
spike, and capture the whole thing as **validated OpenSpec proposals** — then extend
the idea two more hops (wire the skills into the openspec loop, seed them into
`project-init`), and finally commit. The output is a **stacked trilogy of proposals**,
zero implementation code.

## 2. TL;DR playbook

1. **Start in explore mode** (`openspec-explore`) so the AI investigates without
   writing feature code — proposals are allowed, implementation is not.
2. **Ground the external claim first.** Fetch the source repo tree
   (`ctx_fetch_and_index` on the Hermes GitHub tree), separate *real in-repo source*
   (19 skills) from the *marketing catalog* (~250 hosted entries). Only 9
   `software-development/` skills were relevant.
3. **Diff against what already exists.** List `packages/eng-disciplines/.pi/skills/`
   to prove the precise gap: *no debugging discipline, no runtime/breakpoint skill*.
4. **De-risk the headline risk with a spike, not an opinion.** The candidate skill
   claimed breakpoints hit emitted JS under a TS loader. Run a real CDP spike against
   this repo's exact stack (Node 24.15 + jiti 2.7.0) and **record the evidence**.
5. **Write the proposal with the spike evidence baked into `design.md`** so the claim
   is reproducible, not asserted.
6. **Validate every change** with `openspec validate <name>` before moving on.
7. **Fold each new idea into its own standalone, independently-reviewable change** —
   don't bloat one proposal. Steering prompts ("integrate to openspec proposals
   without touching openspec", "part of project init?") each became a separate change.
8. **Stage surgically and commit** only your own files, leaving unrelated
   working-tree changes untouched.

## 3. How the collaboration unfolded

**Discovery / Grounding.** The AI pulled the Hermes repo tree and immediately
corrected a first-glance illusion: the repo *looks* like hundreds of skills, but only
19 have shippable source and only the 9 `software-development/` ones map onto a
TypeScript monorepo. *Why it worked:* it fetched-and-indexed the actual tree instead
of trusting the docs catalog, then read the full text of the top gap candidates.
**Decision point:** the human said **"dig deeper"** → the AI narrowed to a
*debugging pair* (`systematic-debugging` + `node-inspect-debugger`) as the real hole,
since every existing eng-discipline is pre-failure or quality.

**Spike / De-risking.** Before proposing, the AI ran a CDP breakpoint spike in
`/tmp/jiti-spike`: two probes proved jiti transpiles **line-preserving** and registers
compiled JS under the `.ts` URL (1:1 alignment), so `setBreakpointByUrl('widget.ts',6)`
binds exactly — **overturning the Hermes skill's documented #1 pitfall.** *Why it
worked:* the riskiest star-rating claim was settled with reproducible evidence, and
that evidence went straight into the proposal.

**Generate (×3, stacked).** The human drove three proposal hops with short prompts:
- **"propose"** → `add-debugging-skills` (port the 2 skills + a TS `cdp-inspect.ts`).
- **"integrate to openspec proposals without touching openspec itself"** →
  `wire-discipline-skills-into-openspec` (AGENTS.md-only: a checkpoint table + a
  `## Discipline Skills` proposal convention; the *proposal-as-carrier* mechanism
  seeds the implement loop with skill names).
- **"part of project init session?"** → `bundle-disciplines-in-project-init`
  (Option A: global `pi install` + detect-and-offer, graceful degrade to doctrine-only).

Each was scaffolded, then **`openspec validate`d clean** before the next.

**Verify / Commit.** On **"commit"**, the AI staged exactly its 15 files, explicitly
leaving unrelated changes (a `manage-flows` edit, settings `.bak` files, a pre-existing
change dir) untouched, and committed on `develop`.

## 4. Prompts that worked

- **The goal prompt** — here it was the explore-mode boilerplate. It worked *because
  the stance was right* (investigate + capture proposals, never implement), but a
  future operator should front-load intent: *"Explore Hermes Agent's skills; find what
  genuinely fills a gap in eng-disciplines; de-risk the riskiest claim with a spike;
  capture as validated OpenSpec proposals."*
- **"dig deeper"** — high leverage: pushed past the surface catalog into the precise
  two-skill gap and the spike.
- **"integrate to openspec proposals without touching openspec itself"** — a
  *constraint-shaped* prompt. Naming the boundary ("without touching openspec")
  produced the elegant AGENTS.md-only, proposal-as-carrier design.
- **"part of project init session?" / "can init ask to install it if it doesn't?"** —
  each unlocked a full standalone change. Short questions, big scope, because they
  named a concrete insertion point.
- **"commit"** — worked because the AI had kept every change validated and scoped, so
  the commit was a clean, surgical stage.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| stop at the first useful answer | "dig deeper" | stating the depth bar up front ("survey *and* de-risk the top candidate") |
| treat one big proposal as enough | "integrate…", "part of project init?" | asking "what are the orthogonal hops?" so each becomes its own reviewable change |
| risk asserting an external skill's claim | (implicitly) demand a spike | making "de-risk the headline claim with a runtime spike + record evidence" a default for ported skills |
| trust a repo's apparent skill count | AI self-corrected the catalog-vs-source illusion | separating *in-repo source* from *hosted catalog* before quoting numbers |
| potentially over-stage the commit | "commit" (AI scoped it correctly) | always list what's deliberately left unstaged |

## 6. Skills, tools & memory created — and why they're effective

No pi *skill* or *memory* was created in-session — the deliverables were **three
OpenSpec proposals** that, once implemented, *add* two eng-disciplines skills:

- **`add-debugging-skills`** — ports `systematic-debugging` (method) +
  `node-inspect-debugger` (tool, with a TS `cdp-inspect.ts` scope-walker). *Effective
  because* its `design.md` carries **reproducible spike evidence** and a corrected
  jiti-launch recipe, not an assertion. Invoke the eventual skills when a bug is in
  front of you and `console.log` isn't enough.
- **`wire-discipline-skills-into-openspec`** — an AGENTS.md checkpoint table + a
  `## Discipline Skills` proposal line. *Effective because* it makes dormant
  situational skills fire during the implement loop **without editing openspec**, via
  the artifacts the loop already reads.
- **`bundle-disciplines-in-project-init`** — detect-and-offer global install so every
  new coding project inherits the doctrine, degrading gracefully to doctrine-only.

**Recommended skill to create next time:** a *"port-an-external-skill"* procedure —
fetch-and-index the source repo, separate source from catalog, diff against existing
skills, spike the riskiest claim, and land it as a validated proposal with the evidence
in `design.md`. This session *is* that procedure.

## 7. Pitfalls & dead ends

- **`ctx_execute` indexed output instead of printing it** — the first repo-tree probe
  returned nothing visible. *Fix:* re-run capturing to a file (`curl -o /tmp/…json`)
  then parse, rather than piping through an indexing tool.
- **Two failed bash commands** (a `curl | python3` inline heredoc and a package.json
  probe) — inline multi-line Python over a pipe is brittle. *Fix:* write the JSON to
  `/tmp` first, then run the parser against the file.
- **`--inspect-brk` entry-halt confusion** — the first `Debugger.paused` was the entry
  halt at line 1, *not* the breakpoint. *Fix:* resume past the entry halt, then wait
  for the real hit before reading locals.
- **Catalog illusion** — the Hermes repo's ~250 skill entries are a hosted marketing
  catalog; only 19 have in-repo source. Don't quote the big number.
