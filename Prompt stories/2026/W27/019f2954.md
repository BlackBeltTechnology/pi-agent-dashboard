# How we did it: Redesigning the dashboard content editor in explore mode — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened by entering **openspec-explore mode** — a thinking-only stance where
the AI may read, search, mock up, and capture OpenSpec artifacts, but must **never**
implement application code. The real objective emerged over the first three prompts:
take the dashboard's internal Monaco editor pane (which shipped read-only, with a thin
viewer registry and seven known defects) and **redesign it** — fix the defects, add
media viewers (mermaid, image, video, sound), and figure out whether HTML files and
live dev-servers could be previewed *safely* inside the dashboard. The output had to be
a **validated OpenSpec change proposal plus an interactive, browser-verified mockup** —
not a single line of production code.

First prompt (verbatim intent): *"Enter explore mode. Think deeply. Visualize freely."*
Restated once steering landed: *"Redesign the editor pane — mockup the media viewers,
work out the security model for HTML/live-server previews, and capture it all as an
OpenSpec proposal I can build later."*

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) so the AI captures thinking, not code.
2. **Ground before designing** — have the AI map `packages/client/src/components/editor-pane/`
   and trace each known defect to a concrete root cause in source (browse filter,
   `useTheme` vs `useThemeContext`, `<object>` PDF, etc.). Don't accept fixes without a traced cause.
3. **Grab real theme tokens first**, then build ONE self-contained `editor.html` mockup
   with a live light/dark switch to prove theme-follow.
4. **Serve + screenshot every viewer state** (`serve_mockup` + browser) — mermaid, image,
   video, audio, PDF, markdown edit toggle. Verify on screen, not by assertion.
5. **Ask the security question explicitly**: "can we preview HTML / server links, and
   what breaks?" Force the AI to name the **origin decision** (opaque sandbox vs dashboard origin).
6. **Run the coherence check** against archived/shipped work before scaffolding — discover
   what's already built (`render-file-previews`, `preview/*`, `editor-view` proxy) so the
   proposal *reconciles* instead of reinventing.
7. **Scaffold the change** (`proposal.md`, `design.md`, `tasks.md`, three spec deltas),
   then `openspec validate` and fix validator nits (SHALL must lead the first description line).
8. **Add the two hard cases to the mockup** (sandboxed HTML file vs origin-isolated live server)
   to make the security contrast tangible.
9. **Wrap up** — stop the mockup server, close the browser, and **commit only your files**.

## 3. How the collaboration unfolded

**Phase 1 — Ground the defects (Discovery).**
The AI immediately resisted designing in the abstract: it found the editor-pane directory,
read the files behind all 7 issues, and traced each to a concrete root cause (e.g. `browse.ts`
strips `.`-prefixed dirs at line 92, so hidden dirs render as unopenable files; a local
`useTheme()` instead of the shared `useThemeContext()` for the theme-ignore bug). *Why it
worked:* every later fix pointed at a real line of code, so the proposal was defensible.

**Phase 2 — Build & verify the mockup (Design → Verify).**
On *"Create mockups… mermaid, image, video, sound"*, the AI captured real theme tokens, then
built one self-contained `editor.html` and drove a browser through every state (88 browser
calls). It hit — and fixed on screen — real bugs: indented mermaid source, a global
`svg{width:16px}` rule shrinking diagrams to icon size, a CDN that hung headless (swapped for
a static SVG: *"reliability beats authenticity"* for a mockup). *Decision point:* the human's
media list drove exactly which viewers got built and screenshotted.

**Phase 3 — The security question (Discovery).**
*"Is it possible to open HTML / server links? What problems can be there?"* reframed the whole
effort. The AI grounded it in how the server actually serves files, found **no CSP anywhere**,
and reduced the question to one axis: does the HTML run in an **opaque/null origin** (safe, no
JS) or the **dashboard origin** (full compromise — reads the JWT, calls `/api/restart`).

**Phase 4 — Coherence check + scaffold (Gather → Generate).**
*"fold all + live-server"* triggered the project's required coherence check. The key finding:
the editor-pane runs its own thin `viewer-registry` while a richer, already-shipped
`file-and-url-preview` renderer set sits unused next to it — so most of the "new viewers" ask
is **reconciliation, not new code**. The AI scaffolded the full change and validated it.

**Phase 5 — Resolve the isolation question (Design).**
A mis-click (`a` then *"I wrongly choice"*) forced a confirm. The decisive constraint: **zrok
tunnels a single port**, so separate-port / subdomain isolation silently breaks remote preview.
Only **same-origin path proxy + `sandbox="allow-scripts"` without `allow-same-origin`** works
both locally and over the tunnel. Captured in `design.md` D7.

**Phase 6 — Wrap & commit.**
Server stopped, browser closed, and the commit was **scoped to only the 8 files** under the new
change — three unrelated pre-staged files were deliberately left untouched.

## 4. Prompts that worked

- **The goal prompt** — `openspec-explore` set the *stance* (think, don't build) up front, which
  kept every artifact as a capture rather than premature code. A stronger kickoff would have
  named the concrete goal in the same breath: *"Explore mode: redesign the editor pane — fix its
  7 defects, mock the media viewers, and settle the HTML/live-server security model as an OpenSpec proposal."*
- **High-leverage follow-ups:**
  - *"Create mockups for that. …mermaid, image, video, sound"* — turned abstract exploration into
    a concrete, verifiable artifact list.
  - *"Is it possible to… open HTML / Server links. What problems can be there?"* — the single most
    valuable prompt: it forced the origin/security analysis that reshaped the whole design.
  - *"fold all + live-server"* — a three-word prompt that expanded scope to the full reconciliation
    and unlocked the coherence check.
  - *"commit"* — clean handoff, trusting the AI to scope the commit correctly.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Explore abstractly without a concrete deliverable | *"Create mockups for that"* + a media list | Name the artifact (mockup + proposal) in the goal prompt |
| Treat "new viewers" as new code | *"fold all"* (implying reuse of shipped previews) | Ask for a coherence check against archived changes *before* scaffolding |
| Pick the theoretically "stronger" isolation (separate port/subdomain) | reveal the zrok single-port constraint via the mis-click detour | State remote-access (zrok) as a first-class constraint up front |
| Risk sweeping unrelated staged files into the commit | implicit trust on *"commit"* — AI self-corrected to path-scope | Say "commit only the change files" to make scoping explicit |

Watch the **mis-click recovery** (`a` → *"I wrongly choice"`*): the AI correctly stopped and
re-confirmed instead of acting on the wrong option — good behaviour to preserve.

## 6. Skills, tools & memory created — and why they're effective

- **Project memory saved (1):** the embedded-content isolation rule — *zrok tunnels a SINGLE port
  (the model-proxy's second port stays loopback-only, not tunneled), so "separate origin by
  port/subdomain" schemes break remote access.* **Why effective:** it converts a hard-won,
  non-obvious infrastructure constraint into a durable guardrail that will pre-empt the same
  wrong isolation choice in any future preview/proxy design. Invoke it whenever an "isolate
  untrusted content by origin" question comes up. (Note: project memory was full, so the same
  decision was also durably captured in `design.md` D7 + the spec — belt and braces.)
- **No skill was created**, but this workflow is clearly repeatable. A **`mockup-then-propose`
  skill** should exist: ground defects → capture theme tokens → build one self-contained HTML
  mockup → browser-verify each state → coherence-check against archived changes → scaffold +
  validate the OpenSpec change. That is the exact spine this session followed by hand.

## 7. Pitfalls & dead ends

- **Mermaid in a headless browser hangs / CDN blocked** → don't fight it in a mockup; dedent the
  (whitespace-sensitive) source and drop in a static SVG fallback. Reliability > authenticity for mockups.
- **Global `svg{width:16px;height:16px}`** silently shrinks diagrams and media to icon size →
  scope icon-sizing rules to `.icon` selectors only.
- **`</script>` inside a JS string** terminates the outer `<script>` block early and breaks the page
  → escape as `<\/script>` in self-contained HTML mockups.
- **Stale browser cache** hid a working theme flip → hard-reload with a cache-bust query param.
- **`openspec validate` only scans the first line** of a requirement's description for SHALL/MUST →
  keep SHALL leading; don't let text-wrapping push it to line 2.
- **A stray `editable` field** kept sneaking into edits (twice) → redo the edit cleanly rather than patching over it.
- **Separate-port / subdomain isolation looks stronger but breaks zrok remote access** → dead end;
  use same-origin path proxy + opaque sandbox instead.
