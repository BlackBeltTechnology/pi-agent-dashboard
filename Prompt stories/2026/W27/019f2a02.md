# How we did it: Fix 3 skills silently dropped by a YAML frontmatter bug — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** ("Enter explore mode. Think deeply… you must NEVER
write code or implement features"), so there was no concrete goal in prompt 1 — just a
thinking stance. The real objective arrived in prompt 2, when the operator pasted the pi
startup warnings verbatim: a wall of `[Skill conflicts]` and, buried inside, three skills
failing to load with `Nested mappings are not allowed in compact mappings`.

The true objective, once clarified: **triage the startup noise into its distinct classes,
find and prove the root cause of the 3 skills that genuinely fail to load, and land a
durable fix** — not just quote three lines, but add a guard so the class of "silently
dropped skill" becomes a loud CI failure instead of a startup warning nobody reads.

## 2. TL;DR playbook

1. **Paste the raw startup warnings** into the session. Don't summarize them — the exact
   error string (`Nested mappings are not allowed in compact mappings`) is the search key.
2. **Ask the AI to triage into severity classes first.** It found three: (A) cosmetic
   project-shadows-package collisions, (B) a loader false-positive scanning `AGENTS.md` as
   a skill, (C) the real bug — 3 skills fail to parse.
3. **Prove the root cause with a control case.** A *working* skill (`frontend-mockup-loop-dashboard`)
   uses the identical `Triggers:` pattern but **quoted** → loads fine. That nails the cause
   to unquoted YAML scalars with an inner colon-space.
4. **Locate the loader** (`node_modules/@earendil-works/pi-coding-agent/dist/core/skills.js`)
   to decide the fix surface: loader is upstream (not ours), so fix the files + prevent recurrence.
5. **Scaffold an OpenSpec change** (`openspec new change`), write proposal + design + a new
   capability spec + TDD tasks. Design records loader-tolerance + AGENTS.md over-scan as
   **upstream follow-ups**, not silent drops.
6. **Write the guard test FIRST (TDD red):** a vitest that globs all `SKILL.md`, parses each
   with `yaml@2.9.0` (pi's own parser), asserts a non-empty description. Confirm it fails on
   exactly the 3 offenders.
7. **Fix the 3 descriptions** by double-quoting each value (`JSON.stringify` for correct
   escaping — wording byte-identical, only quotes added). Guard goes green (67/67).
8. **Verify → code review → archive → commit.** Full suite (unrelated flakes noted), CodeRabbit
   advisory clean, `openspec archive`, then stage **only your files** and commit.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore stance).** The AI listed 45 active OpenSpec changes (most at
0/N) and offered directions rather than picking one. The operator redirected it with the
real signal: the startup warnings. Effective because the AI didn't guess — it waited for the
concrete symptom.

**Phase 2 — Triage & root-cause proof.** The AI resisted theorizing and read the actual
files, then split the noise into three classes by severity. The decisive move was the
**control case**: it found a skill with the same `Triggers:` pattern that loads fine because
it's quoted, then confirmed with a real `yaml` parser that unquoted-scalar-with-inner-colon
is the culprit. Root cause *proven*, not guessed.

**Phase 3 — Locate the fix surface.** The AI grepped the loader in `node_modules` and found
`if (entry.name !== "SKILL.md") continue;` — the loader lives in pi core, upstream. This
resolved the "fix files vs fix loader" tension by *location*: files are the only surface this
repo owns. Loader tolerance became an upstream note.

**Phase 4 — Scaffold the change (still in explore).** The operator chose "1" (draft the
OpenSpec change). The AI scaffolded proposal/design/spec/tasks, hitting and fixing validator
requirements (delta headers `## ADDED Requirements`, SHALL on the first body line). The
durable value framed as the **guard**, not the 3 quotes.

**Phase 5 — Apply with TDD.** Prompt 4 invoked `openspec-apply-change`. The AI wrote the
guard test first, confirmed it fails on exactly the 3 offenders (64 others pass), then fixed
the descriptions with `JSON.stringify` escaping and re-parsed to green.

**Phase 6 — Verify, review, archive, commit.** Full `npm test` surfaced 2 failures; the AI
grepped the log to prove zero references to its touched files (pre-existing environmental
flakes: `node-electron-resolution`, `doctor-route` timing). Prompt 5 ("Archive and code
review") → CodeRabbit clean + `openspec archive`. Prompt 6 ("commit") → staged **only** its
own files, leaving a pre-existing `manage-flows` toggle and `.bak` artifacts untouched.

## 4. Prompts that worked

- **The goal prompt (prompt 2):** pasting the *raw* startup warnings verbatim. This was the
  real kickoff — the exact error text was the search key that unlocked the whole diagnosis.
  Lesson: paste the literal error, don't paraphrase.
- **"1" (prompt 3):** a one-character unlock choosing "draft the OpenSpec change" from the
  AI's offered menu. High-leverage because the AI had already laid out the options clearly,
  so a single token committed the direction.
- **"Archive and code review" (prompt 5)** and **"commit" (prompt 6):** terse workflow verbs
  that the AI mapped to the correct multi-step sequences (review-on-diff → archive; stage-mine
  → commit) because the OpenSpec + implement skills defined those flows.

Rewrite of a weak kickoff: instead of opening in bare explore mode, the stronger first prompt
would be: *"Here are the pi startup warnings [paste]. Triage them by severity, prove the root
cause of any real load failure with a control case, then propose an OpenSpec change that fixes
the files AND guards against recurrence."*

## 6. Skills, tools & memory created — and why they're effective

No pi *skill* or *memory* was created, but the session produced a durable in-repo asset that
plays the same role:

- **`scripts/__tests__/skill-frontmatter.test.mjs` (the guard).** Globs all 67 `SKILL.md`
  manifests, parses each with `yaml@2.9.0` (the exact parser pi's loader uses), and asserts a
  non-empty description. **Why effective:** it converts a silent-at-startup warning nobody
  reads into a loud-at-CI failure that blocks merge. **When to invoke:** it runs automatically
  in the `scripts` vitest project — no manual step. Any new skill with malformed frontmatter
  now fails CI.
- **`openspec/specs/skill-frontmatter-validity/spec.md` (new capability).** The durable
  contract behind the guard, promoted to main specs on archive. **Why effective:** future
  changes inherit the requirement rather than re-discovering it.
- **`skill-creator` SKILL.md rule.** Adds "quote colon-space descriptions" to the authoring
  guidance so the bug is prevented at write time, not just caught at CI.

Recommendation: this workflow (paste warnings → triage → prove via control case → guard-first
TDD → upstream-note the rest) is itself repeatable and would make a good `.pi/skills/` skill.

## 7. Pitfalls & dead ends

- **OpenSpec validator is strict about delta headers.** A new capability spec needs
  `## ADDED Requirements` and the `SHALL` statement on the **first body line** of each
  requirement — the AI had to restructure twice. If you hit validation errors, lead each
  requirement with SHALL.
- **`openspec change new` is the wrong subcommand** — it's `openspec new change <name>`. The
  first invocation failed; check `openspec new --help` when the CLI shape is uncertain.
- **Full-suite flakes will scare you.** `npm test` showed 2 failures (`node-electron-resolution`,
  `doctor-route` timing at 3403ms vs a 3000ms "slow CI" threshold). Both are environmental and
  unrelated. If you hit them, grep the test log for your touched filenames to prove non-involvement
  before chasing them.
- **A dirty working tree can tempt over-staging.** A pre-existing `manage-flows` toggle and
  `.bak-switch-*` artifacts were present but *not yours*. Stage explicitly by path — never
  `git add -A` when the tree has unrelated churn.
