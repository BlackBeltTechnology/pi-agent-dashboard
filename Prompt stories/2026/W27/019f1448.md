# How we did it: From a cryptic `Unexpected token '<'` to a scoped OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user hit a wall: *"There is no way to open worktree. What is the reason?"* — attached
to a screenshot showing the browser error `Unexpected token '<', "<html> <h"... is not valid
JSON`. The literal ask was a diagnosis. The **real** objective, which the two steering turns
clarified, was: *root-cause the failure, then turn the fix into a properly-scoped, validated,
committed OpenSpec proposal* — not just patch the one broken call, but establish a durable
client-side HTTP-hygiene capability.

## 2. TL;DR playbook

1. Feed the AI the **verbatim error string** + a screenshot. `Unexpected token '<'` is the
   canonical signature of `res.json()` swallowing an HTML error page.
2. Ask it to separate **symptom from root cause** — don't accept the first `.json()` site as
   the answer; trace *what upstream returned HTML*.
3. Let it walk the request path: client `git-api.ts` → server git routes → `networkGuard`
   preHandler → `auth-plugin.ts` HTML pages → not-found/proxy handlers.
4. Once diagnosed, prompt **"create a proposal for that"** — the AI runs the project's
   pre-scaffold coherence sweep (archive + active OpenSpec changes) *before* writing.
5. Have it **ground the scope with numbers** (`grep -c` the unguarded `.json()` calls across
   `lib/*.ts`) so the proposal cites real counts, not hand-waving.
6. Scaffold via `openspec new change <name>`, write the four artifacts, then
   `openspec validate <name>`.
7. Commit **only the proposal folder** with `git commit -F <msgfile>` (heredoc breaks on the
   `<html>` quotes) — leave unrelated working-tree changes untouched.

## 3. How the collaboration unfolded

**Phase 1 · Diagnosis (symptom → root cause).** The AI immediately decoded the error as an
HTML body reaching `res.json()`, but explicitly flagged it as *"a symptom, not the root
cause."* It read `WorktreeSpawnDialog.tsx`, `git-api.ts`, the server git routes, then the
`networkGuard` preHandler and `auth-plugin.ts`. The decisive move was *fingerprinting the
HTML*: the body began with a bare `<html>` and **no `<!DOCTYPE>`**, which ruled out the SPA
`index.html`, Fastify's JSON 404, and the auth pages (which emit `<!DOCTYPE html>`). Why it
worked: it treated the exact bytes of the error as evidence instead of guessing.

**Phase 2 · Coherence check (before writing anything).** On *"create a proposal for that"*
the AI did **not** jump to scaffolding. It swept `openspec/changes/archive/` and active
changes for overlap (`error-handling-improvements`, `unify-error-retry-lifecycle`) and
concluded those were *server/agent-side* error lifecycle — its concern was *client-side HTTP
transport hygiene*, so no duplication. Decision point: new capability, not an extension.

**Phase 3 · Grounding the scope.** Before writing prose it quantified the problem: **~58
`.json()` calls across 15 client lib files**, `res.ok` guarded inconsistently (git-api: 3/17),
content-type checked **nowhere**. Those numbers went straight into the proposal.

**Phase 4 · Generate + validate.** Scaffolded with `openspec new change guard-client-fetch-json`,
wrote `proposal.md` / `design.md` / `tasks.md` / `specs/.../spec.md` (1 capability, 2
requirements, 8 scenarios), then ran `openspec validate` → ✅.

**Phase 5 · Surgical commit.** On *"commit"* it checked `git status`, noticed a pre-existing
unrelated `openspec/groups/groups.json` change, and deliberately staged **only** the proposal
folder — leaving the unrelated diff unstaged.

## 4. Prompts that worked

- **Goal prompt — "There is no way to open worktree. What is the reason?" + screenshot.**
  Effective because it pasted the *exact* error text. The single most useful input for a
  transport-layer bug is the verbatim error string; `Unexpected token '<'` alone points a
  competent model at the `res.json()`-on-HTML class of bug.
- **"create a proposal for that"** — a 4-word high-leverage follow-up. It unlocked the entire
  OpenSpec pipeline *because the project conventions (pre-scaffold sweep, grounding, validate)
  were already known to the AI.* A future operator can be even sharper: *"create an OpenSpec
  proposal for a shared guarded `fetchJson` helper; sweep archive first; ground the scope with
  real `.json()` counts."*
- **"commit"** — trusted the AI to figure out *what* to commit. It correctly scoped to the
  proposal folder only.

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created this session. But the workflow is clearly repeatable and a
skill *should* exist:

- **Recommended skill: `diagnose-html-in-json-response`.** Captures the fingerprint table
  (bare `<html>` vs `<!DOCTYPE html>` vs JSON 404 vs SPA index) that maps an HTML body back to
  its emitter (auth page / proxy / gateway / not-found), plus the request-path walk
  (client lib → route → preHandler guard → auth plugin). Effective because it removes the
  repeated manual trace every time a `res.json()`-on-HTML error surfaces, and because it
  encodes the *symptom≠root-cause* discipline that made this diagnosis correct.
- The existing OpenSpec skills (`openspec-new-change`, validate) already carried the pipeline;
  this session is a good example of *why* the pre-scaffold coherence sweep is worth keeping.

## 7. Pitfalls & dead ends

- **Heredoc commit broke on the HTML/quotes** — the `<html>` and quotes in the commit message
  broke `git commit -m "$(cat <<'EOF' … )"`. Fix: write the message to `/tmp/pi-commit-msg.txt`
  and `git commit -F`. Reach for a message file whenever the body contains code, angle
  brackets, or quotes.
- **First `openspec change new` invocation failed** — the CLI subcommand shape was wrong; the
  AI recovered by running `openspec --help` / `openspec new --help`, then `openspec new change
  <name>`. If a CLI call fails, check `--help` before retrying blindly.
- **Two grep one-liners failed** (over-complex `for`-loop / escaping) — no harm; the AI
  simplified and re-ran. Don't over-engineer a shell one-liner when a plain `grep -c` per file
  works.
- **Don't stop at the first `.json()`** — the symptom site is never the root cause for this
  bug class; the HTML came from *before* the handler (a preHandler guard).
