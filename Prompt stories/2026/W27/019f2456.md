# How we did it: Add `.mov` support to the video-transcription skill — an AI collaboration guideline

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`), which is explicitly a
thinking stance: read, search, map — but *never* implement. The first prompt was the
verbatim explore-mode preamble ("Enter explore mode. Think deeply... you must NEVER
write code or implement features"). The *real* objective that emerged: **teach the
`video-transcription` skill to accept `.mov` (QuickTime) files** alongside the MKV/MP4
it already handled. Once the human started firing `commit`, the intent flipped from
"explore whether this is feasible" to "make the one-line change and land it."

## 2. TL;DR playbook

1. Read the skill and find the single gate: `cat .../video-transcription/SKILL.md`, then
   `grep -rniE '\.(mkv|mp4|m4a|mp3|mov)' src` to locate the real extension filter.
2. Confirm the architecture generalizes: everything downstream of `isVideo()`
   (`extractAudio` → ffmpeg → `.mp3` → Soniox) is format-agnostic. `.mov` is just a
   container ffmpeg reads natively → the change is **one entry in `VIDEO_EXTENSIONS`**.
3. Add `.mov` to `VIDEO_EXTENSIONS` in `src/discover.ts`.
4. Update the human-facing format list in `SKILL.md` ("MKV, MP4, **MOV**, M4A, and MP3").
5. Add a parity test in `src/__tests__/discover.test.ts` asserting `.mov` is discovered
   and classified as video (import `isVideo`, mirror the existing case).
6. Run the narrow test: `npx vitest run src/__tests__/discover.test.ts` → expect green.
7. **Commit ONLY the three video-transcription files** — explicitly `git add` each path;
   leave unrelated working-tree changes (`.pi/settings.json`, other skills, `groups.json`)
   untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI read `SKILL.md`, grep'd for extension
patterns, and produced an ASCII map showing exactly where `.mov` had to land: one Set in
`discover.ts`, one doc line, one test. It correctly identified that ffmpeg/Soniox needed
*no* change. *Why it worked:* it traced the data flow to the single gate instead of
guessing, so the blast radius was proven-small before any edit.

**Phase 2 — Implement + scope the commit.** On `commit`, the AI realized the `.mov`
change had only been *explored*, never *written* — and that the working tree already held
unrelated changes it must not sweep in. It made the real edit (`discover.ts`, `SKILL.md`,
`discover.test.ts`), ran the focused vitest (9/9 passing), and committed **only** the
three files by explicit path. Commit `81e4efc49` landed on `develop`. *Decision point:*
the human's terse `commit` was the trigger to leave the explore stance and land the work.

**Phase 3 — The `wrong` moment.** A second `commit` then a bare `wrong` signalled the
human was unhappy — but with no detail. The AI did *not* thrash: it used `ask_user` to
ask what "wrong" meant (undo? revert? something else?), and when no selection came back it
took **no destructive action**, leaving the repo in a known, described state.

## 4. Prompts that worked

- **The goal prompt (explore-mode preamble).** Effective as a *framing* device — it kept
  the AI from prematurely editing and forced a clean data-flow map first. But it never
  stated the actual task; a stronger kickoff would name it: *"In explore mode, map exactly
  where `.mov` support must land in the video-transcription skill — don't implement yet."*
- **`commit` (high-leverage, one word).** Unlocked the transition from exploration to
  landing. It worked because the AI had already done the mapping, so "commit" had an
  unambiguous target. Reusable pattern: explore first, then a single word ships it.

**Rewrite the weak parts:** `wrong` gave the AI nothing to act on and cost a full
clarification round-trip. Prefer *"wrong — the unrelated files should have been committed
too"* or *"wrong — undo commit 81e4efc49"*. One extra clause turns a stall into an action.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stay in explore mode and only *map* the change | `commit` (twice) to force it to land the code | State up front: "explore, then implement + commit the `.mov` change" |

guessing** and **took no irreversible action** — exactly right when a commit is already on
a shared branch.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this was a surgical edit to an *existing* skill
(`video-transcription`). The reusable lesson is a **pattern**, not an asset:

> **"Add a format to a format-agnostic pipeline" pattern** — when a media pipeline funnels
> everything through one classifier (`isVideo()` → extract-to-audio → cloud STT), adding a
> new container type is a single-Set edit + doc + parity test. Find the classifier first;
> never touch the downstream stages.

If this recurs (adding `.webm`, `.avi`, etc.), that three-touch recipe is the whole job.

## 7. Pitfalls & dead ends

- **Explore-mode inertia.** The AI produced a perfect map but hadn't *written* anything;
  the first `commit` had nothing to commit until it made the edit. → If you want code,
  say "implement" — a map is not a diff.
- **Bare `wrong` stalls the loop.** It triggered an `ask_user` round-trip with no reply
  and zero progress. → Always attach the object of the correction.
- **Working-tree contamination risk.** Unrelated changes (`.pi/settings.json`,
  `manage-flows/SKILL.md`, `groups.json`) sat in the tree. → Commit by explicit path, never
  `git add -A`, when the tree is dirty with out-of-scope work.
- **Known unaddressed gap:** audio-less `.mov` screen recordings will fail extraction —
  pre-existing, not fixed here. A follow-up would skip-or-warn on video with no audio track.
