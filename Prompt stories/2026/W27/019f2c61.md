# How we did it: Capture two doubt-reviewed node/Electron resolution proposals — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) against a failing
tool-registry test — a "boomerang" the operator suspected was an npm-version mismatch
under Electron. The literal kickoff was the explore-mode stance prompt: *"Enter explore
mode. Think deeply… NEVER write code or implement features… You MAY create OpenSpec
artifacts."*

Once the steering turns landed, the **real objective** was narrow and concrete:
diagnose the failing test `node-electron-resolution.test.ts` from *proof, not theory*,
then **capture two OpenSpec change proposals** — one for the immediate test-isolation
leak, one for an adjacent latent runtime bug it exposed — and only after each survived
a **doubt review** against source, commit them. No implementation, proposals only.

## 2. TL;DR playbook

1. Enter explore mode: run `.pi/skills/openspec-explore/SKILL.md` — thinking + artifacts, no code.
2. **Reproduce before theorizing:** run the exact failing vitest, capture the real assertion diff.
3. Trace the leak to its source line (`nodeScriptToArgv` → `resolveJsScript` → raw `realpathSync`/`process.execPath` escaping the test's injected `exists`/home seams).
4. Steer: *"capture proposal, but check it can't cause side effects on the Electron build."* Verify the fix is additive and never on the healthy-Electron runtime path before scaffolding.
5. `openspec new change <name>`, then write `proposal.md` + `design.md` + `tasks.md` + `specs/tool-registry/spec.md` matching an existing change's format; `openspec validate --strict`.
6. Steer: *"create other proposal for the adjacent latent runtime bug"* — scaffold the second change the same way.
7. Steer: *"doubt review the two proposals"* — spawn a **fresh-context `Explore` reviewer** with contracts only (no CLAIM); reconcile findings **against source** before applying; rewrite the overstated artifact.
8. Run a **second** doubt cycle on the rewrite; when it surfaces a blocker, re-verify against source, generalize the fix, re-validate `--strict`.
9. Steer: *"commit"* — stage only the two proposal dirs; record the doubt-review provenance in the commit message.

## 3. How the collaboration unfolded

**Phase A — Reproduce & diagnose (explore stance).** The AI resisted theorizing: it ran
the failing vitest under an isolated `HOME=$(mktemp -d)`, captured the real diff
(`received [.pi-dashboard/node/bin/node, <script>]` vs `expected [bundled-npm]`), and
walked the resolution chain in `definitions.ts` / `strategies.ts` to the exact leak —
`toArgv: nodeScriptToArgv` resolving a node binary through raw `realpathSync` that
*escapes the test's injected `exists` seam and reads the real disk/home.*
**Why it worked:** grounding the whole thing in a reproduced assertion killed the wrong
"npm version mismatch" hypothesis before it wasted a proposal.

**Phase B — Electron-safety check, then capture #1.** On the operator's steer, the AI
verified the additive fix (`ctx.execPath ?? process.execPath`) is never reached under a
*healthy* packaged Electron (bundled-node strategy short-circuits) and that the
`no-electron-execpath-spawn` lint only scans `packages/electron/src/lib/**`, so it won't
collide. Only then did it scaffold `fix-node-electron-resolution-test-isolation`.

**Phase C — Adjacent runtime bug, capture #2.** The isolation dig exposed a real runtime
defect: `buildSpawnEnv` **strips** `ELECTRON_RUN_AS_NODE`, so a `[Electron-binary, script]`
fallback argv re-launches the GUI (single-instance lock → exit, script never runs). The
AI sharpened this from "a missing flag" to a **desync between two spawn-env builders**
(argv-aware `runner.buildSpawnEnvForArgv` re-adds the flag; argv-blind
`process-manager.buildSpawnEnv` cannot) and captured `fix-nodescript-argv-electron-execpath-fallback`.

**Phase D — Two doubt cycles.** Cycle 1's fresh-context reviewer found Artifact 2
**materially overstated** — the fallback fires only on a *triply-degraded* install (all
five node strategies fail), not "bundled missing" alone; the `pi-core-updater` vector was
already neutralized. The AI reconciled *against source*, rewrote Artifact 2, trimmed
Artifact 1. Cycle 2 surfaced a **blocker**: `spawnTmux`/`spawnWslTmux` don't node-wrap
(shell token, PATH-resolved) — only `spawnWt` + `spawnHeadless` do, plus the RPC keeper
spawns its *own* `[execPath, keeper.cjs]`. The AI re-verified each finding against source,
generalized the requirement to "any node-wrapped `argv[0]===execPath` under a stripped
env," re-validated `--strict`.

**Phase E — Commit.** Staged only the two proposal directories; commit message records
the doubt-review provenance so a future implementer knows scoping was *verified*.

## 4. Prompts that worked

- **The goal prompt** (explore-mode stance): effective because it fenced the AI to
  *thinking + OpenSpec artifacts, never implementation* — exactly right for a
  capture-only session. Stronger kickoff would name the artifact: *"Explore this failing
  test and capture an OpenSpec proposal — no code."*
- **"capture proposal, but check that it can cause side effects on electron build"** —
  high-leverage: forced a runtime-safety proof *before* writing, which is what kept the
  fix scoped to a path healthy Electron never runs.
- **"create other proposal for adjecent latent runtime bug"** — unlocked the second,
  higher-value change by telling the AI the diagnosis had a runtime tail, not just a test bug.
- **"doubt review the two proposal"** — the single most valuable steer; it turned two
  plausible drafts into source-verified ones and caught the reachability overstatement.
- **"yes" / "commit"** — terse unlocks; worked only because the preceding context was
  unambiguous.

## 5. Steering & corrections (what to watch for)

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session; it *used* existing ones well:

- **`openspec-explore`** — kept the session in capture-only mode; the correct frame for
  "diagnose + propose, don't fix."
- **`Explore` subagent as adversarial doubt reviewer** (spawned twice) — the reusable
  move worth repeating: pass *contracts only, no CLAIM*, force fresh context, then
  **reconcile every finding against source** rather than rubber-stamping. This is what
  caught both the overstatement and the tmux/keeper blocker.

**Recommend saving a skill:** *"doubt-review an OpenSpec proposal"* — scaffold contracts →
spawn fresh-context reviewer → reconcile-against-source → rewrite → re-validate → repeat
until a cycle is clean. The session executed exactly this loop twice; it deserves to be
one invocation. (The `doubt-driven-review` eng-discipline skill covers the spirit; a
proposal-specific wrapper would encode the `openspec validate --strict` gate.)

## 7. Pitfalls & dead ends

- **Malformed `ctx_batch_execute` calls** (4/4 errored) — the AI abandoned them and used
  Bash directly. If batch-exec misfires, don't retry it; drop to plain Bash.
- **Wrong initial hypothesis** ("npm version mismatch with Electron") — dissolved only
  because the AI *reproduced the assertion first*. Never scaffold a proposal off an
  unreproduced theory.
- **`openspec new` vs `openspec change new`** — the first scaffold attempt guessed the
  subcommand; check `openspec new --help` before assuming the syntax.
- **Doubt theater risk** — a reviewer's finding is not automatically true. Both cycles
  *re-verified against source* (`process-manager.ts:216-225`, `keeper-manager.ts:172`)
  before applying; cycle 2's "blocker" was real, cycle 1 downgraded several to minor.
