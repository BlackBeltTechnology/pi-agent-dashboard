# How we did it: Drafting a "disable pi resources per folder" proposal — grounded, doubt-reviewed, and pivoted on evidence

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill: think, don't implement).
The real objective surfaced only after two steering turns:

> *"Mean in the pi is there any settings mechanism to disable extensions?"*
> *"Is it possible to wrap pi (as in install as I know) to be part of folder settings page?"*

Restated plainly: **can the dashboard let a user deactivate an installed pi resource
(extension / skill / prompt) per folder — without uninstalling it — and where does pi's
own `pi config` enable/disable machinery live?** The deliverable ended up being a fully
grounded, doubt-reviewed **OpenSpec proposal** (`folder-resource-activation-toggle`) plus
a vendor-neutral update to the `doubt-driven-review` skill — not a single line of feature
code (explore mode forbids it).

## 2. TL;DR playbook

1. **Start in explore mode** (`openspec-explore`) — investigate, never implement.
2. **Ground before theorizing:** search pi's shipped docs + dist for the actual gating
   mechanics (`pi config`, `settings.json` resource arrays, `--no-extensions`) before
   proposing anything.
3. **Find the existing surface first:** the dashboard *already* wraps pi's install
   dimension (`directory-settings-page`) — locate the precise gap (install ≠ activation).
4. **Check the archive for collisions:** read `add-plugin-activation-ui` before drafting;
   confirm it's a *different* concern (dashboard plugins ≠ pi resources).
5. **Draft the OpenSpec artifacts** (`proposal.md` / `tasks.md` / `spec.md`); run
   `openspec validate` until valid.
6. **Run the doubt cycle** (`doubt-driven-review`): CLAIM → EXTRACT → DOUBT with a
   *fresh-context adversarial reviewer*, then a **cross-model second opinion**.
7. **Follow the evidence, even when it refutes you:** when reviewers converge, pivot the
   design; then **read pi's own source** to settle the open questions definitively.
8. **Rewrite the artifacts around the verified design**, re-validate, and **commit only
   your files** (clean up probe junk, exclude unrelated churn).

## 3. How the collaboration unfolded

**Phase 1 — Discovery (grounding the mechanics).** The AI resisted theorizing and grepped
pi's `node_modules/@earendil-works/pi-coding-agent/docs` + dist for how extensions/skills
are gated. It found three real levers: **`pi config`** (persistent enable/disable, global
or project), the `settings.json` resource arrays (`!pattern` / `-path` exclusions), and
`--no-extensions` (per-run). *Why it worked:* every later claim rested on shipped behavior,
not guesses.

**Phase 2 — Map the existing surface.** Rather than invent a new page, the AI discovered
the dashboard *already* has a `directory-settings-page` that wraps pi's **install**
dimension — and drew the exact boundary: install (done) vs. activation toggle (the gap).
It then read the archived `add-plugin-activation-ui` to rule out a collision (that one is
dashboard *plugins*, not pi resources).

**Phase 3 — Draft (`draft proposal`).** Scaffolded `folder-resource-activation-toggle/`
with proposal + tasks + spec delta, validated clean. A follow-up `1. Make one click
reload / 2. fold in` folded a one-click reload affordance and global scope into the same
change.

**Phase 4 — Doubt cycle (`doubt review`).** The AI materialized a CLAIM, spawned a
**fresh-context adversarial reviewer** (Opus) that returned **9 issues, 5 blocking** —
including that the proposal *misread the codebase* (the scanner never reads user
`settings.json` arrays; `reloadSessions` is private + all-sessions, not folder-scoped).
The AI **self-verified each finding against source** rather than rubber-stamping.

**Phase 5 — Cross-model review (heavy steering).** The user pushed for a second-architecture
reviewer via a pi subagent on Gemini. This took **many probes** (see Pitfalls) before
`google-vertex/gemini-3.1-pro-preview` worked. Vertex Gemini independently reproduced every
blocker **and found a new one** (object-form partial-key mutation trap). Two cross-arch
models converging = **decisive pivot signal**.

**Phase 6 — Settle by reading pi's source & rewrite.** The pivot ("delegate to `pi config`")
raised the blocking question *is `pi config` scriptable?* The AI read pi's
`config-selector.js` and `config.js`: the **CLI is interactive-only**, but pi **exports the
primitives** — `PackageManager.resolve()` → `ResolvedResource.enabled` (read) and
`SettingsManager` setters writing `+<relPath>`/`-<relPath>` (write). This *vindicated* the
original `-path` direction and *refuted* two reviewer worries. Artifacts were rewritten
around the verified design, re-validated, and committed surgically.

## 4. Prompts that worked

  grounding work was already done.

  scope expansions into one change without a wall of text.
- **`doubt review`** — two words that invoked the whole adversarial discipline.
- **`don't mention vertex / gemini directly in skill`** — a precise quality bar that kept

## 6. Skills, tools & memory created — and why they're effective

- **Memory (project · insight):** *`pi config` is interactive-TUI-only, but pi exports the
  primitives* — `PackageManager.resolve()` → `ResolvedResource.enabled` for the read and
  `SettingsManager` setters (`+<relPath>`/`-<relPath>`) for the write. *Reusable problem it
  solves:* anyone building resource activation in the dashboard reimplements **zero** glob
  logic — reuse pi's resolver + writer. *Invoke when:* implementing this change or any
  settings-toggle feature.
- **Memory (memory · tool-quirk):** *Spawn a Gemini subagent as
  `google-vertex/gemini-3.1-pro-preview`* (Vertex prefix) when
  `GOOGLE_CLOUD_PROJECT`/`LOCATION` + `GOOGLE_GENAI_USE_VERTEXAI` are set; the `google/…`
  prefix returns empty. *Reusable problem:* saves the ~1h of probing this session spent
  finding the working address. *Invoke when:* running any cross-model pi subagent on Google.
- **Skill edit — `doubt-driven-review`:** documented the **subagent-addressing-a-cross-model**
  path as the preferred Pi-native second opinion (cleaner than a CLI: no shell-escaping,
  isolated context, can open repo files), with the empty-return gotcha ("probe with a
  trivial prompt first; empty = provider not SDK-configured"). Later genericized to
  `<provider/model-id>` placeholders. *When to invoke:* any high-stakes decision needing a
  cross-architecture doubt pass.

*Skill that should exist:* a small "cross-model reviewer address book" is overkill — the
tool-quirk memory covers it. But the pattern **ground → propose → doubt → cross-model →
read-the-source → pivot** is worth naming as a proposal-hardening discipline.

## 7. Pitfalls & dead ends

- **Gemini via subagent returned empty for a long time.** `google/gemini-3.1-pro-preview`,
  `@vision`, `google/gemini-2.5-pro`, inline label, and via `Explore` all returned empty.
  *Fix:* the working address is `google-vertex/gemini-3.1-pro-preview` (Vertex prefix) —
  try the alternate provider prefix before giving up.
- **`gemini` CLI is broken in this environment:** `dyld: Library not loaded:
  libsimdjson.29.dylib` — Homebrew node 25.6.1 links a stale simdjson. *Fix:* don't rely on
  the CLI; use a pi subagent, or run the JS entry under a working nvm node.
- **`openspec change new` scaffold was unavailable** (command failed). *Fix:* create the
  `openspec/changes/<name>/…` tree manually, then `openspec validate`.
- **`git commit -m` tripped on apostrophes** in the message. *Fix:* write the message to a
  file (`git commit -F /tmp/commitmsg.txt`).
- **`pi config` probe left junk** (`.pi/settings.json.bak-switch-*`). *Fix:* clean up your
  own probe artifacts before committing; exclude unrelated `groups.json` churn to keep the
  commit surgical.
- **Memory store at capacity (4949/5000):** the second batch of findings couldn't be
  force-saved. *Fix:* durable design findings live fine in `design.md`; run the
  memory-consolidation skill before relying on a global save.
