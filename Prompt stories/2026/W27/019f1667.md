# How we did it: Drafting a fix for parallel-worktree E2E Docker collisions — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened **explore mode** (`openspec-explore`) — a thinking stance, no
implementation — to investigate why parallel worktrees running `npm run test:e2e`
still collide despite an earlier `parallelize-test-harness` change. The first prompt
was the skill's boilerplate ("Enter explore mode. Think deeply..."), so the *real*
objective only crystallized through steering: **trace exactly where the managed
Playwright E2E path leaks past the existing parallelization layer, and capture the
fix as a validated OpenSpec proposal — without writing any harness code.** The
deliverable is a committed change draft (`proposal.md` + `design.md` + `tasks.md` +
2 spec deltas), not an implementation.

## 2. TL;DR playbook

1. Enter explore mode: invoke the `openspec-explore` skill. Stay in "capture thinking,
   never implement" mode for the whole session.
2. **Ground before theorizing.** `cat` the actual harness: `docker/test-up.sh`,
   `test-down.sh`, `playwright.config.*`, `tests/e2e/lifecycle.ts`, `global-setup.ts`,
   `docker/compose.test*.yml`, `lib-ports.sh`. Map real ports/names/tags, not guesses.
2. Diagram the collision with a race timeline (two worktrees, `probeFreePort()` →
   TOCTOU on the freed ephemeral port) so the *surface* is visible, not asserted.
3. Read the **archived** `parallelize-test-harness` change to reuse its conventions and
   pinpoint what it fixed (the manual path) vs. what it left open (the managed path).
4. Prompt `draft propose`: scaffold the change dir with `proposal.md`, `design.md`,
   `tasks.md`, and per-capability `specs/<cap>/spec.md` deltas.
5. `openspec validate <change> --strict` — iterate until clean **before** deep-diving.
6. Pressure-test one decision (`maybe the image has to be worktree-specific`): split it
   into cheap-tag-reuse vs. full-rebuild, prove the *baked-source-vs-overlay* distinction
   from the Dockerfile + entrypoints, promote it to **load-bearing**, re-validate.
7. Add the teardown-cleanup decision (`docker image rm` after `down -v`, scoped +
   non-fatal), re-validate `--strict`.
8. Commit **only** the change directory (`git add openspec/changes/<name>/`), leaving
   unrelated working-tree edits (e.g. `groups.json`) out.

## 3. How the collaboration unfolded

**Phase 1 — Ground the harness (Discovery).** The AI's first instinct was to theorize;
it corrected itself ("Let me ground this in the actual harness before theorizing") and
`cat`-ed every harness file. This is the phase that earned trust: it produced a concrete
race-timeline ASCII diagram showing `probeFreePort()` binding `:0`, releasing the port,
and the OS handing the same number to worktree B → bind failure → 180s flake. *Why it
worked:* the fix rests on a real TOCTOU, not a hunch.

**Phase 2 — Reuse prior art.** Rather than inventing conventions, the AI read the
**archived** `parallelize-test-harness` proposal and its spec deltas, then framed the
new change as "the earlier change fixed the *manual* `test-up.sh` path; the *managed*
e2e path bypasses it." Two named holes: (①) `lifecycle.ts` ephemeral-port probe with no
disjoint window, (②) a shared `pi-dashboard:local` image tag causing silent wrong-code
reuse. Contention (③) was scoped **out** as a non-goal.

**Phase 3 — Draft + validate (`draft propose`).** Scaffolded the full change tree and
ran `openspec validate --strict`, iterating to clean before moving on.

**Phase 4 — Pressure-test the load-bearing decision.** The human's `maybe the docker
image have to run can be worktree specific` was the pivotal steer. The AI split
"worktree-specific" into (a) per-tag with shared BuildKit layers (~seconds) vs. (b) full
isolated rebuilds (minutes, N× disk), then read the Dockerfile + `test-entrypoint.sh` to
prove the container has **two code surfaces**: the dashboard's *baked* source (`/app`,
`COPY packages`, `pi-dashboard` on PATH) vs. the `HOST_CWD` *overlay* (managed workspace
data only). Conclusion: per-worktree tag **and** `--build` are correctness requirements,
not optimizations. Decision 3 promoted to LOAD-BEARING; `--build` flagged "MANDATORY,
not an optimization to remove."

**Phase 5 — Cleanup + commit.** `use docker image rm after tests` became Decision 4: run
`docker image rm -f pi-dashboard:$project` *after* `down -v`, project re-derived from
`$PWD`, non-fatal `|| true`. Then a scoped commit of just the change directory, keeping
pre-existing `groups.json` edits out.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore` boilerplate).** Effective *because* it pinned the
  stance: capture thinking as OpenSpec artifacts, never implement. A stronger explicit
  kickoff: "Explore mode: trace where parallel-worktree E2E still collides past
  `parallelize-test-harness`, then draft a validated OpenSpec change for it."
- **`draft propose`** — a 2-word high-leverage unlock: it turned the traced analysis into
  a scaffolded, validatable change tree.
- **`maybe the docker image have to run can be worktree specific`** — the highest-leverage
  follow-up. A tentative "maybe" invited the AI to *prove* the granularity question rather
  than assert it, upgrading a clobber-avoidance note into a load-bearing correctness rule.
- **`use docker image rm after tests`** — converted an implied cleanup into a defined,
  scoped teardown step.
- **`yes`** — a one-word unlock confirming the promote-to-load-bearing direction.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this was a pure `openspec-explore` → draft session.
The reusable asset is the **committed OpenSpec change** itself
(`fix-parallel-e2e-docker-collisions`): it encodes the port-race + baked-image findings
as validated spec deltas so an implementer can execute without re-deriving them.

*Recommended skill to create:* a **`docker-harness-collision-audit`** procedure —
"enumerate every shared Docker resource (ports, container names, volumes, image tags)
across parallel worktrees; for each, classify as namespaced-safe vs. leaking; prove
baked-vs-overlay code surfaces from the Dockerfile + entrypoints." That would make this
grounding phase reproducible instead of re-traced by hand each time.

## 7. Pitfalls & dead ends

- **`ctx_batch_execute` malformed 4/4 times.** Don't use batch-exec for the initial
  multi-file grounding cat — the AI aborted it and used plain `bash` (`cat A && echo === && cat B`).
- **`openspec list` failed once** (piped/head interaction) — fall back to `find` /
  `ls openspec/changes/` and reading the archived proposal directly.
- **Ephemeral-port `:0` probe is a TOCTOU trap.** `probeFreePort()` releasing the port
  before Docker binds it is the whole bug — never "find a free port then bind later"
  across processes; derive in a disjoint per-worktree window and bind-retry instead.
- **`--build` looks like an optimization you can drop — it is not.** The container bakes
  the dashboard source; without a per-worktree tag + `--build`, worktree B's container
  runs worktree A's code. Flag it MANDATORY in the design so no one caches it away.
- **Don't `git add -A`.** Unrelated `groups.json` board-state edits were in the tree;
  commit only the change directory.
