# How we did it: Turning a GitHub issue into a validated OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking stance,
not an implementation workflow. The real objective, made concrete by the two short
steering turns, was: **take GitHub issue #98 ("dashboard hardcodes `~/.pi/agent/sessions`,
but pi itself lets you configure it"), verify whether its claims are true against the
actual code, and — if valid — capture the fix as an OpenSpec change proposal, commit it,
and reply on the issue with evidence.** No code was to be written; the deliverable was
*captured thinking* (proposal + design + spec + tasks), not an implementation.

## 2. TL;DR playbook

1. Enter explore mode with the `openspec-explore` skill so the AI investigates but never implements.
2. Give it the issue number and one instruction: **"verify the claims against the code before judging validity."**
3. Let it `gh issue view 98 --comments`, then `rg`/`grep` the repo AND the vendored `node_modules/@earendil-works/pi-coding-agent/dist` to confirm both the hardcoded paths and pi's real config precedence.
4. Read its grounded verdict (file:line evidence for each claim). Unlock the build with a single **"yes"**.
5. Let it scaffold via `openspec new change <name>`, write the 4 artifacts (proposal/design/spec/tasks), and `openspec validate --strict`.
6. Say **"commit and update issue"** — it commits only its own artifacts (excluding unrelated churn) and posts a verdict comment with the chosen design + file:line proof.

## 3. How the collaboration unfolded

**Phase 1 — Verify the issue (Discovery).** The AI resisted the temptation to judge the
issue on its wording. It pulled the issue + comments, then grep-traced *both* claims:
(a) the three hardcoded `os.homedir()` call sites in `session-scanner.ts`,
`session-discovery.ts`, `migrate-persistence.ts`, and (b) pi's actual resolution chain
(`--session-dir` → `$PI_CODING_AGENT_SESSION_DIR` → settings → default) by reading pi's
own compiled `dist/main.js` / `config.js`. *Why it worked:* grounding the verdict in
file:line evidence turned a plausible-sounding bug report into a confirmed, actionable fact.

**Phase 2 — Design the fix (Design).** Once the human said **"yes"**, the AI checked
OpenSpec conventions, scaffolded the change, and made the key design call: a single
`resolvePiSessionsDir()` resolver with precedence `config.json#piSessionsDir` → env →
pi-core's exported `getSessionsDir()`. *The decisive insight:* the server package already
depends on `@earendil-works/pi-coding-agent`, so **reusing pi's own `getSessionsDir()`**
keeps the default in lockstep with pi forever and deletes all three hardcoded copies.

**Phase 3 — Generate & validate (Generate).** It wrote proposal.md, design.md,
tasks.md (6 TDD-ordered task groups) and a MODIFIED+ADDED `session-persistence/spec.md`,
then ran `openspec validate --strict` before declaring done.

**Phase 4 — Commit & report (Verify).** On **"commit and update issue"**, it staged only
its artifacts, noticed unrelated `groups.json` churn and *deliberately excluded it*, then
committed and posted an evidence-backed verdict comment answering a reviewer's Windows/Electron concern.

## 4. Prompts that worked

- **The goal prompt (explore skill + "verify before judging").** Effective because it set
  a *stance* (investigate, don't build) and a *quality bar* (prove the claims) in one shot —
  so the AI produced a grounded verdict instead of an opinion.
- **"yes"** — a one-word unlock. Because the AI had already surfaced a clear verdict and
  proposed next step, "yes" authorized the whole scaffold-and-write phase with zero re-explaining.
- **"commit and update issue"** — five words that triggered a complete close-out
  (selective commit + evidence comment). High leverage because the AI already knew the artifacts and the issue number.

Stronger kickoff to reuse: *"Explore mode. Verify issue #98's claims against the code
(cite file:line for each), give a valid/invalid verdict, and if valid scaffold an OpenSpec
change capturing the fix."*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Pause after the verdict for approval | "yes" | State up front: "if the issue is valid, proceed to scaffold the proposal without waiting." |
| Stop after writing artifacts | "commit and update issue" | Include "then commit your artifacts and post an evidence comment on the issue" in the goal prompt. |
| (self-corrected) nearly stage unrelated `groups.json` churn | — (AI caught it) | Reinforce: "commit only the files you created; exclude pre-existing churn." |

The steering here was minimal and additive — the human never had to *correct* a wrong
direction, only *unlock the next phase*. That is the signature of a well-grounded explore session.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created. The reusable asset is the **workflow pattern itself**,
already embodied by the `openspec-explore` skill: *verify-then-capture*. If anything,
this session is a strong argument for a small **"issue-to-proposal"** recipe:

- **What it would capture:** the loop of `gh issue view --comments` → grep-trace claims in
  repo *and* vendored deps → verdict with file:line → `openspec new change` → validate → commit + comment.
- **Why effective:** it removes the ambiguity of "is this bug real?" and produces a
  committed, reviewer-answerable proposal in ~5 minutes.
- **When to invoke:** any time a GitHub issue proposes a change you want to triage and formalize without implementing.

## 7. Pitfalls & dead ends

- **Don't trust the vendored-dep behavior from memory** — the AI confirmed pi's precedence
  chain by reading the *compiled* `dist/main.js` and `config.js`, not by guessing. If you
  need to know how a dependency resolves a path, grep its `node_modules/**/dist`.
- **Watch the commit staging.** `git add <dir>` can sweep in unrelated pre-existing churn
  (here, `openspec/groups/groups.json`). If `git status --short` shows files you didn't
  touch, `git restore --staged` them before committing.
- **Zero failed commands** this run — the discipline of read-before-conclude paid off.
