# How we did it: Measuring the 51k startup context & proving context-mode's ROI — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with a curiosity question about token cost:

> *"When start a new session 51k token is used. Can you draw what and from filling the session?"*

The real objective, once the steering turns landed, was bigger than a diagram: **measure exactly what fills the ~51k startup context, then decide whether the `context-mode` MCP plugin (which dominates that budget) actually earns its ~24k-token tool-schema cost** — or whether the `kb` extension already covers its job. The end state the user wanted: a written ROI report (md + PDF), filed under `docs/`, committed, plus an unrelated cleanup of dead references in `groups.json`.

## 2. TL;DR playbook

1. **Measure the real bytes, not guesses.** `wc -c` every startup-context source (tool JSON schemas, base system prompt, `AGENTS.md`, hermes memory `*.md`, skill catalog) and divide by ~3.7 to approximate tokens. Render a `mermaid pie` of the split.
2. **Find the decisive usage data.** Locate the transcript store (`~/.pi/agent/sessions/<project>/*.jsonl`) and context-mode's self-reported `stats-pid-*.json` files. `grep` tool-call frequency across ALL project transcripts to get `ctx_*` vs `kb_*` counts.
3. **Frame the ROI split before analysis:** sandbox tools (`ctx_execute*`) = "kb can't run code"; retrieval tools (`ctx_search/index/fetch`) = "kb overlaps this". Note the counts.
4. **Dispatch a subagent for the heavy aggregation** — a GLM-5.2 subagent (`opencode-go/glm-5.2`) crunched all 1,863 stats files + the schema split and returned the verdict: **trim, don't drop** (sandbox = 97% of calls, KEEP; retrieval = 2%, redundant with kb, DROP).
5. **Write the report md**, then render to PDF via the `document-converter` facade (`pi-doc-engine:0.1.0` Docker image).
6. **Fallback for PDF:** the facade ships no bundled templates → generate a pandoc `reference.docx` as the `default` template, mount via `templatesDir`; if the facade's `renderPdf` post-check reports the file missing, run `soffice --headless --convert-to pdf` directly in the same image.
7. **File under `docs/`** with `git mv`, then **delegate the `docs/AGENTS.md` row additions to a subagent** (Documentation Update Protocol — main agent never edits `docs/` prose).
8. **Commit only the report work**; leave unrelated staged changes alone.
9. **Cleanup pass:** compute dangling `groups.json` assignments (referenced change IDs no longer in `openspec/changes/`), strip them, keep groups + `changeOrder`, validate JSON, commit.

## 3. How the collaboration unfolded

**Phase 1 — Measure the startup context (Discovery).**
The AI resisted hand-waving and instead `wc -c`'d every real source of startup bytes, then converted to approximate tokens. Result: tool schemas ~24k (context-mode MCP descriptions dominate), base prompt ~9k, `AGENTS.md` ~7k, hermes memory ~6.5k, skill catalog ~4k. Delivered as a table + `mermaid pie`. *Why it worked:* measuring bytes beats estimating; the pie immediately showed context-mode was the single biggest lever.

**Phase 2 — Prove the ROI (Gather + Analyze).**
The user's steering turn ("does context-mode help or does kb replace it? Maybe ROI isn't best") reframed the task. The AI located the 623-transcript / 443 MB store plus context-mode's own `stats-pid-*.json` savings files, `grep`'d tool-call frequency across all transcripts, and pre-computed the key split (sandbox ~4,427 calls vs retrieval ~108 calls, overlapping kb's ~98). Then it **dispatched a GLM-5.2 subagent** to aggregate all 1,863 stats files and produce the verdict. *Decision point:* the human explicitly asked for a *subagent* and named the model — the AI honored the model choice rather than doing it inline.

**Phase 3 — Report to PDF (Generate).**
"Create a report md from that and convert to PDF." The AI wrote the report, then hit the document-converter facade's rough edges: no bundled templates, module resolution failing from `/tmp`, and `renderPdf` reporting a missing output. It worked around each (pandoc reference docx as template, run inside the repo, LibreOffice fallback) and produced a 13-page PDF.

**Phase 4 — File + commit (Verify).**
"put them to docs" → `git mv` the two files, then **delegate** the `docs/AGENTS.md` rows to a `docs-writer` subagent per the caveman-style Documentation Update Protocol. "commit" → the AI staged only the report work, spotted a stray manifest artifact and an unrelated `groups.json` change, and left the latter alone.

**Phase 5 — Cleanup (bonus).**
"cleanup groups.json, remove references which is archived." The AI computed exactly which of the referenced change IDs were archived/deleted (87 dangling: 85 archived + 2 renamed/deleted), stripped only those, kept all 7 groups + `changeOrder`, validated the JSON, and committed.

## 4. Prompts that worked

- **Goal prompt** — *"When start a new session 51k token is used. Can you draw what and from filling the session?"* Concrete number + "draw" → forced a measured, visual answer. A stronger version states the real intent up front: *"Measure exactly what fills my 51k startup context (bytes → tokens per source) and show a pie; I want to know which component to trim."*
- **High-leverage follow-up** — *"Analyze with glm 5.2 subagent the session logs that the context-mode helps or the kb replaces the functions? Maybe the ROI is not best."* Names the model, names the hypothesis, names the data source (session logs). This single sentence set up the entire analysis.
- **Terse chain** — *"Create a report md from that and convert to PDF"* → *"put them to docs"* → *"commit"*. Each is one unambiguous next action against an already-shared context. Effective because the artifact was already agreed; the user only issued the transitions.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was persisted this session, but two workflows are clearly reusable and **should be captured**:

- **`context-mode-roi-audit`** — the measure-bytes → grep-tool-frequency → aggregate-stats-files → trim/drop verdict pipeline. Reusable whenever a heavy MCP plugin's token cost is questioned. Removes the manual recon of finding transcript + stats paths and re-deriving the sandbox-vs-retrieval split.
- **`md-to-pdf-via-doc-engine`** — the working MD→DOCX→PDF path with the two known workarounds (pandoc `reference.docx` as the `default` template + `soffice` LibreOffice fallback when `renderPdf`'s post-check fails). The AI even offered to save this; a future job would skip all the trial-and-error. **Create it.**

Subagents used effectively: `context-mode-roi-analyst` (GLM-5.2) for the stats aggregation, and `docs-writer` for the caveman-style `docs/AGENTS.md` rows (mandatory per Documentation Update Protocol — main agent must not edit `docs/` prose directly).

## 7. Pitfalls & dead ends

- **Module resolution fails from `/tmp`.** The document-converter workspace package won't resolve outside the repo → run the render script from the repo root.
- **The doc engine ships no bundled templates.** `default` template is absent in `pi-doc-engine:0.1.0` → generate one with `pandoc --print-default-data-file reference.docx` and mount it via `templatesDir`.
- **Facade `renderPdf` reports the output missing even when LibreOffice ran.** Its post-check doesn't find the file. Fallback: `soffice --headless --convert-to pdf --outdir <staging>` directly in the same image, then copy out. (The DOCX render through the facade itself worked cleanly.)
- **Stray `*_manifest.xml` render artifact** appears in the working tree after rendering → `rm` it before committing.
- **`groups.json` dead refs come in two flavors** — archived (date-prefixed in `openspec/changes/archive/`) and simply deleted/renamed. Both are dangling; strip both, but the second class is easy to miss.
