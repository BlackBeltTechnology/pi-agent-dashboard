# How we did it: Fork-from-any-message in the dashboard chat — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with `/skill:openspec-explore` and:

> "Currently we can fork from session card only. But in pi tree command is available
> where the message can be selected where fork from. I would like to adapt this
> feature, to be able to add fork function to the card."

The real objective, once steering clarified it: **let a dashboard user fork a session
from *any specific message* in the chat view — not just from the latest leaf** — by
placing a fork control on each user/assistant message, mirroring pi TUI's tree
selector. The finished feature: a "Fork from here" icon sitting in the message
toolbar next to the Copy buttons, wired through an `entryId` that flows from the
session file, through the protocol, to a server that prunes the JSONL before spawning
`pi --fork`.

## 2. TL;DR playbook

1. **Explore first, don't code.** `/skill:openspec-explore` + spawn `Explore` to map
   the *current* fork flow (`--fork` always forks the latest leaf) and pi's real
   primitives (`SessionManager.getTree/createBranchedSession/branch`).
2. **Trace the data path end-to-end** before designing: session file → `state-replay`
   → `event-reducer` (`ChatMessage`) → `browser-protocol` → `session-action-handler`
   → UI. The missing piece is a single `entryId` threaded down this path.
3. **Answer the design fork questions in one steering turn** (embed `entryId`; fork
   button per message; server-side `createBranchedSession`) — tell the AI to *verify
   its assumption and only re-ask if wrong*.
4. **`/opsx:ff`** to fast-forward proposal → design → specs → tasks (14 tasks / 4
   groups) in one shot.
5. **Ask "is there anything to clarify?"** *before* apply — this surfaced the
   live-vs-replayed `entryId` gap early instead of at QA.
6. **`/opsx:apply`** task-by-task. When `SessionManager` won't import (optional peer
   dep, absent from `node_modules`), pivot to **Approach C**: do the JSONL surgery
   yourself in `session-file-reader.ts` (`createBranchedSessionFile`).
7. **`npm run build` → `curl -X POST .../api/restart` → `npm run reload`**, then verify
   in a real browser with the `browser` skill (hover to reveal the button).
8. **Close the live-event gap**: enrich `message_start`/`message_end` in `bridge.ts`
   with `ctx.sessionManager.getLeafId()` so *live* messages also carry `entryId`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore, don't build).** The AI ran `/skill:openspec-explore`,
spawned the `Explore` subagent, and grep-walked pi's `dist/*.d.ts` to find the real
primitives. Key finding: pi's `SessionManager.createBranchedSession(leafId)` writes a
*new pruned session file* (root→leaf) — exactly "fork from this message". The current
dashboard `--fork` always forks the latest leaf. **Why it worked:** it separated "what
pi can already do" from "what the dashboard is missing" before any design.

**Phase 2 — Design (thread one field).** The AI mapped the whole propagation chain and
the human answered the open questions in a single turn (embed `entryId`, per-message
fork button, server-side branching via Approach A "if the fork is executed there —
check and don't re-ask"). **Decision point:** the user explicitly told the AI to
*verify then decide* rather than ping-pong questions.

**Phase 3 — Generate artifacts.** `/opsx:ff` produced proposal, design, spec (6
requirements), and tasks.md (14 tasks / 4 groups) in one pass.

**Phase 4 — Clarify before apply.** Prompted with "Is there anything to clarify?", the
AI proactively flagged that **live** pi events (`message_start`/`message_end`) don't
carry the session-entry `id` — only **replayed** events do. It judged this acceptable
for the ended-session case and proceeded. This became the exact bug hit later — but it
was already understood.

**Phase 5 — Apply + the peer-dep pivot.** Working task-by-task, the AI discovered
`@mariozechner/pi-coding-agent` is an *optional peer dep* not present in
`node_modules`, so the server **can't** import `SessionManager` (Approach A dead).
Pivot to **Approach C**: hand-write `createBranchedSessionFile()` in
`session-file-reader.ts` (the file is plain JSONL with `id`/`parentId`). 112 tests
pass.

**Phase 6 — Verify in the real UI + iterate.** Build/restart/reload, then the `browser`
skill. The user reported "I don't see any fork icon." Root cause = the earlier known
gap: the *active* session's messages arrived live (no `entryId`). Fix: enrich the
bridge events with `getLeafId()`. Final polish steered by the user — move the fork
icon **into** the message bubble toolbar next to the Copy buttons instead of a
separate hover button.

## 4. Prompts that worked

- **The goal prompt** (`/skill:openspec-explore` + the ask): good because it named the
  *reference implementation* ("pi tree command") — grounding the AI in an existing,
  inspectable feature instead of an abstract request. **Stronger version:** add the
  acceptance shape up front — "put the fork control in the message toolbar next to
  Copy" — which the user only reached at prompt 11.
- **High-leverage follow-up — the batched design answer** (prompt 3): answered four
  design questions at once *and* delegated a decision ("Option A — check it and if it
  doesn't, ask again"). This is the pattern to copy: decide what you can, and give the
  AI a verify-then-proceed rule for the rest.
- **"Is there anything to clarify?"** (prompt 6): a cheap pre-apply gate that surfaced
  the live-vs-replayed gap before it cost a QA cycle. Use it before every `/opsx:apply`.
- **"go on without full test" / "build and deploy"**: short unblock prompts that kept
  momentum once the plan was trusted.

## 7. Pitfalls & dead ends

- **`openspec change new` failed** — the scaffold command isn't that; the AI fell back
  to `mkdir -p openspec/changes/<name>/…` + `openspec status/instructions`. If
  `change new` errors, create the dir tree manually and drive via `openspec
  instructions <artifact>`.
- **Approach A (import `SessionManager` server-side) is a dead end** — it's an optional
  peer dep, not in `node_modules`; the require/import both fail. Do the JSONL surgery
  yourself (`createBranchedSessionFile`, root→target by `id`/`parentId`).
- **Fork icon invisible on the live session** — live pi events omit the entry `id`;
  only replayed events have it. If the button is missing on the *current* session,
  enrich `message_start`/`message_end` in `bridge.ts` with
  `ctx.sessionManager.getLeafId()`.
- **Screenshots won't show hover-only controls** — the button is `opacity-0` until
  `group-hover/msg`. Use the browser skill's `hover` + snapshot, not a bare screenshot,
  to confirm it's wired.
- **Pre-existing TS errors** in the extension (from optional peer deps) pollute
  `tsc --noEmit`; grep the output for only your changed files to judge your work.
