# How we did it: Error-handling states for the dashboard session lifecycle — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — "Enter explore mode. Think deeply… you must
NEVER write code or implement features." — a deliberately open-ended stance, not a
task. The *real* objective surfaced during exploration: **the dashboard treats the pi
agent as always-happy.** There is no concept of an error state in the session
lifecycle, so when an LLM provider returns quota-exceeded / rate-limited / overloaded /
auth / network errors, the user sees nothing — the spinner just hangs. The end goal
became a full OpenSpec change (`error-handling-improvements`) that makes those errors
**visible**: extract them, show a banner, mark the session card red, and stop the stuck
pending-prompt spinner — all **client-only, no protocol change**.

## 2. TL;DR playbook

1. `/opsx:explore` on the problem area first — let the AI map the error data flow end to
   end (pi-agent-core → bridge → reducer → UI) **before** proposing anything.
2. Push for the root-cause synthesis: "the error info already flows, it's just ignored
   at every stop." That one insight keeps the change small.
3. `create proposal` → `/opsx:ff` to fast-forward proposal → design → specs → tasks.
4. `/opsx:apply` — implement **group by group, TDD**: write failing tests, run them red,
   then minimal implementation to green.
5. Run tests **scoped to the client package** (jsdom config), not from repo root.
6. `/opsx:verify` — check tasks/requirements/scenarios coverage; expect a couple of
   WARNINGs, then `fix them`.
7. `/opsx:archive` — sync delta specs to main specs, archive the change.
8. `commit and push` — **stage only your files**; unrelated dirty files will be mixed in.

## 3. How the collaboration unfolded

**Phase 1 · Discovery (explore mode, ~4 min of dense grepping).** The AI walked the
monorepo, grepping `event-reducer.ts`, `types.ts`, `bridge.ts`, and even the installed
`pi-agent-core` dist for how `agent_end` / `stopReason` / `errorMessage` propagate. The
effective move: it traced the **full path** of a provider error and discovered the
error payload already reaches the client inside `agent_end.data.messages` — the reducer
just drops it. *Why it worked:* mapping the real data flow first meant the fix needed
**zero protocol changes**.

**Phase 2 · Artifacts (proposal → ff).** `create proposal` captured three gaps (extract
& show errors, fix stuck spinner, persistent spawn-failure state). `/opsx:ff` generated
design (6 decisions), 3 specs (18 scenarios), and an 18-task tasks.md ordered by
dependency.

**Phase 3 · Implementation (apply, TDD, 5 groups).** Each group followed the same loop:
write tests → run red → implement → run green. Groups: (1) `extractAgentEndError` +
`lastError` on `SessionState`; (2) `pendingPrompt` clearing on `agent_end` + a new
`usePendingPromptTimeout` 30s hook; (3) red dismissible banner in `ChatView`; (4) red
status dot on `SessionCard` via an `errorSessionIds` memo prop-drilled through
`SessionList`; (5) persistent spawn/resume error banners in `useMessageHandler`.

**Phase 4 · Verify & fix.** `/opsx:verify` produced a coverage table (20/20 tasks,
18/18 scenarios) plus two WARNINGs. `fix them`: moved the spawn banner inside the
collapse region, added 6 direct unit tests for `extractAgentEndError`.

**Phase 5 · Archive & ship.** `/opsx:archive` synced 3 new capability specs to main
specs. `commit and push` landed `104ebdf` on `develop` — but only after the AI noticed
unrelated dirty files and **staged selectively**.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Effective because it forbade implementation and
  forced a thinking-first pass. For a future operator: keep this — the discovery phase
  is what produced the "no protocol change needed" insight that shrank the whole change.
- **`create proposal`** — a two-word unlock once exploration was done. Worked because
  the AI already had the full landscape in context.
- **`/opsx:ff`** — fast-forwarded four artifacts in one shot; high leverage.
- **`fix them`** — two words that turned a verify report's WARNINGs into commits. Only
  works because `/opsx:verify` had just enumerated exactly what to fix.
- **`commit and push`** — fine, but see §5: pair it with an explicit "stage only the
  files from this change" so unrelated dirty files aren't swept in.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stay in open-ended explore mode | `create proposal` — an explicit exit-to-build signal | State up front "explore, then create the proposal when I say go" |
| Run tests from the repo root (wrong vitest config, jsdom missing) | Re-run scoped to the client package | Always run client hook/component tests from `packages/client` (jsdom config lives there) |
| `git add -A` would have swept in unrelated dirty files (`bridge.ts`, `event-wiring.ts`, `OpenSpecActivityBadge.tsx`) | Notice the mix and stage only the change's files | Tell it "stage only files from this change" before `commit and push` |
| Leave `pendingPrompt` uncleared on `agent_end` (old test asserted the old behavior) | Update the stale test to the new spec | Flag intentional behavior changes so the AI updates, not preserves, the guarding test |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this was a **pure OpenSpec-driven feature build**.
The reusable asset is the **workflow itself**: explore → proposal → ff → apply → verify
→ archive → ship, driven end-to-end by the `/opsx:*` command family. It is effective
because each step hands a machine-checkable artifact (tasks.md, specs, verify report) to
the next, so coverage is provable (20/20 tasks, 18/18 scenarios) rather than asserted.

*Recommendation:* if this explore→ship arc repeats, the existing project skills already
cover it (`openspec-explore`, `openspec-ff-change`, `openspec-apply-change`,
`openspec-verify-change`, `openspec-archive-change`, `ship-change`) — invoke them by
name rather than pasting the long command prompts.

## 7. Pitfalls & dead ends

- **`openspec change new <name>` fails** (2 attempts, ❌). The correct command is
  `openspec new change <name>`. If `change new` errors, flip the word order.
- **Tests fail from repo root** — the root vitest config lacks jsdom; client hook/
  component tests need the client package's own config. Run them from `packages/client`.
- **Pre-existing unrelated test failures** (localStorage/theme, TunnelButton,
  CommandInput teardown). Don't chase them — verify only *your* changed files pass.
- **Dirty working tree at commit time** — unrelated changes (`bridge.ts`,
  `event-wiring.ts`, `OpenSpecActivityBadge.tsx`, electron branding) were present. If you
  `git add -A` you ship someone else's half-work. Stage explicitly.
- **A stale test can encode the *old* behavior** — one test asserted `agent_end` must
  NOT clear `pendingPrompt`, the exact behavior being changed. Update it deliberately.
