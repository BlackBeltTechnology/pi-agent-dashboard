# How we did it: Chasing a phantom "Server offline" banner to a stale-hostname root cause — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with three words: **`build and deploy`**. On the surface a routine rebuild-and-restart of the pi-agent-dashboard. But the real objective only surfaced through eleven steering turns: the dashboard UI kept showing a red **"Server offline"** banner even though the server was demonstrably healthy via `curl`. The true goal became **"figure out why the browser can't reach a running server, and make it recoverable"** — which resolved into a root cause (a `.local` hostname resolving to a *second machine* on the LAN) and a small durable fix (make the `ServerSelector` show a localhost escape hatch when a stale non-localhost server is pinned in `localStorage`).

## 2. TL;DR playbook

1. **Rebuild + restart first, cleanly:** `npm install` (catches missing deps like `bonjour-service`) → `npm run build` → `pi-dashboard start` → `npm run reload`.
2. **Confirm the server is actually healthy** before touching client code: `curl -s http://localhost:8000/api/health | jq .mode` and `lsof -i :8000 -P | grep LISTEN`.
3. **When "server responds to curl but the browser says offline," it's a connectivity/identity mismatch, not a dead server.** Ask *which URL is in the address bar* immediately.
4. **Grab the browser console errors.** The WebSocket target URL (`ws://<host>:8000/ws`) in the error IS the diagnosis — note the hostname it's dialing.
5. **If that host is a `.local` mDNS name, resolve it:** `dscacheutil -q host -a name <host>.local`. Two IPs → two machines answering on :8000. That's your bug.
6. **Test the WS upgrade per-IP,** not just localhost: a raw `curl -i -N -H "Upgrade: websocket" …` against each resolved IP reveals which one returns 401 (the foreign server with auth).
7. **Fix the recoverability gap:** if `localStorage["pi-dashboard-last-server"]` pins a non-localhost host and the `ServerSelector` hides itself, always inject a localhost entry so the user can switch back.
8. **Rebuild + deploy the client fix:** `npm run build` → restart. Give the user the one-liner console escape hatch too: `localStorage.removeItem("pi-dashboard-last-server"); location.reload();`.

## 3. How the collaboration unfolded

**Phase 1 — Build & deploy (the easy part).** The AI ran `npm install` (surfacing a missing `bonjour-service`), `npm run build`, `pi-dashboard start`, `npm run reload`. Health check green, PID reported, zero connected sessions. Clean. *Why it worked:* it followed the project's rebuild matrix and verified with `/api/health` rather than assuming.

**Phase 2 — "Server is offline" contradiction.** The user reported the banner while `curl` said `ok`. The AI correctly reframed: the server is up, so this is a *browser-to-server* problem, and asked for the address bar URL. *Decision point:* the user pasted a **screenshot** and then the **raw browser console** — which contained the WebSocket target `ws://bb-robertcsakany-6.local:8000/ws`. That hostname was the whole case.

**Phase 3 — The long auth red herring.** The AI saw the hostname-based WS get **401**, and spent a dozen turns hypothesizing server-side auth: inspecting `config.json`, `authConfig` resolution, `auth-plugin.ts`, `validateWsUpgrade`, the zrok tunnel, `localhost-guard.ts`, even adding temporary debug logging. Every check said *auth is disabled*. The contradiction (`/auth/status` returns `{authenticated:false}` from the hostname but `{authenticated:true, authEnabled:false}` from localhost) was the tell — but it was read as "a mysterious hook" for too long.

**Phase 4 — The DNS reveal.** `dscacheutil` resolved `bb-robertcsakany-6.local` to **two** IPs: the local box (`192.168.196.194`) and a *different machine* (`192.168.16.237`) also running a dashboard (dev mode, auth on, 248 sessions, PID 18102). The debug log never fired for the hostname request because **the request never reached the local server** — the browser was talking to the neighbour. Root cause found. *Why it worked:* the AI finally tested the resolved IPs directly instead of trusting the hostname.

**Phase 5 — Make it recoverable (the durable fix).** Even knowing the cause, the user asked the sharper question: *when `pi-dashboard-last-server` is set, make the server selector active so I can switch back to localhost.* The AI edited `src/client/components/ServerSelector.tsx` to inject a synthetic localhost entry and always render when the current server isn't localhost, then rebuilt and deployed. Cleaned up its debug edits to `server.ts` and re-enabled the tunnel.

## 4. Prompts that worked

- **The goal prompt — `build and deploy`:** fine as a kickoff *because the project has a known rebuild matrix*, but it hid the real problem. A stronger opener: *"Rebuild and deploy, then confirm the browser UI actually connects — I'm seeing a Server offline banner."*
- **`use browser skill for that`** — high leverage: redirected the AI away from guessing what the browser saw and toward the project's actual `browser` skill for verification.
- **Pasting the raw console log** — the single most valuable input. The WebSocket URL in the error *was* the root cause; every earlier turn was blind without it.
- **`Is it possible when pi-dashboard-last-server is set the server selector be active to switch back to localhost?`** — the model follow-up: it converted a one-off diagnosis into a reusable product fix. Rewrite of the weak `?` / `still does not work :(` turns → paste the console/address-bar state *with* the complaint.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was persisted this session — a miss, because the workflow is textbook-reusable. **Recommended skill to create:** `diagnose-dashboard-browser-offline` (project scope) capturing: (1) curl-healthy + browser-offline ⇒ connectivity/identity mismatch; (2) read the WS URL from the console; (3) `dscacheutil -q host -a name <host>.local` to catch multi-IP `.local` collisions; (4) per-IP raw WS-upgrade probe; (5) the `pi-dashboard-last-server` localStorage escape hatch + the ServerSelector fix. A durable memory worth saving: *`.local` mDNS names on this LAN can resolve to a second dashboard host — always diagnose via resolved IPs, not the hostname.*

## 7. Pitfalls & dead ends

- **The 12-turn auth rabbit hole.** Every auth check was a dead end because auth *was* disabled. Lesson: when two identical routes return *different* JSON shapes by hostname, suspect **two servers**, not one server with a hidden hook.
- **Debug logging that never fires = request never arrives.** The missing log line for the hostname request was the proof the traffic went elsewhere — read *absence* of logs as signal.
- **`npm run reload` / `pi-dashboard start` failed early** (server mid-restart, missing `bonjour-service`); `npm install` fixed the dep, a retry fixed the timing.
- **The `browser` tool wasn't usable from this session** (an unrelated extension error blocked `pi tool`), so live browser verification fell back to curl. If the browser skill is blocked, say so and diagnose via resolved-IP curls.
- **`bb-robertcsakany-6.local` is a trap on a shared LAN** — it can answer from a neighbour's machine. Prefer `localhost:8000` or the explicit LAN IP.
