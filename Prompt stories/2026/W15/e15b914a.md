# How we did it: Fix OpenSpec auto-attach firing on change name alone — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user reported a UX bug in the pi-dashboard: **when an OpenSpec workflow ran (e.g. a
proposal was created), the session did not automatically attach the created spec.**
The opening prompt — _"When an openspec execution catched - for example proposal
creation - the session does not attach the created spec automatically"_ — was a symptom
report, not a root-cause diagnosis. The *real* objective, once traced, was: find why the
auto-attach gate never fired for real OpenSpec runs, remove the faulty condition, cover
it with tests, and update the docs. The session landed as a 25-minute surgical fix across
two source files plus two doc files.

## 2. TL;DR playbook

1. **Kick off with the symptom + the subsystem** so the AI knows where to look:
   _"openspec execution … session does not attach the created spec automatically."_
2. **Let the AI explore first.** It ran an `Explore` subagent + targeted `grep`/`find`
   over `.pi/skills/openspec-*` and `src/server/` to locate the detector and the
   auto-attach gate in `event-wiring.ts`.
3. **Confirm the root cause in one sentence before touching code:** auto-attach required
   BOTH `openspecPhase` AND `openspecChange`, but `phase` is only set when the agent
   *reads* a SKILL.md via the `read` tool — prompt-template / cached skills never emit
   that event, so phase stays unset and the gate never opens.
4. **Do TDD:** add failing tests to `src/server/__tests__/auto-attach.test.ts` first
   (the no-phase case + the auto-name-from-changeName case), run them, watch them fail.
5. **Apply the minimal fix** in `event-wiring.ts`: gate auto-attach on `openspecChange`
   alone; keep `phase` for the activity badge only.
6. **Restart the server** with `curl -X POST http://localhost:8000/api/restart` (server
   change → restart, no rebuild — jiti) and re-run the scoped vitest file.
7. **Update the specs:** `docs/architecture.md` (why phase isn't a gate) and the
   `openspec-activity-detector.ts` row in `AGENTS.md`.

## 3. How the collaboration unfolded

**Discovery.** The AI opened with an `Explore` subagent ("Explore OpenSpec auto-attach")
and a burst of `grep`/`find` across the OpenSpec skills and `src/server/` tests. This
narrowed the surface to the activity detector and the auto-attach branch in
`event-wiring.ts` fast — worth repeating: *explore before editing when the bug is a
"why didn't X fire" question.*

**Diagnosis.** The AI read `event-wiring.ts` and stated the bug crisply: the gate needed
`openspecPhase && openspecChange`, but phase depends on a `tool_execution_start` for a
SKILL.md `read` that never happens when skills arrive via prompt templates / context.
`changeName` *was* being detected from file ops — so the fix was to drop the phase
requirement.

**Implementation (TDD).** The AI wrote the tests first, ran vitest, confirmed red. The
human then steered: _"go on. do not run full test"_ — i.e. apply the fix and keep the
test run scoped, don't run the whole suite. The AI edited `event-wiring.ts`, restarted
the server via the `/api/restart` endpoint, and re-ran only the scoped test file.

**Docs.** After _"update specs"_, the AI edited `docs/architecture.md` to explain the
phase-isn't-a-gate rationale and updated the `openspec-activity-detector.ts` key-file row
in `AGENTS.md`.

## 4. Prompts that worked

- **The goal prompt** named both the *symptom* ("does not attach the created spec") and
  the *subsystem* ("openspec execution", "proposal creation"). That subsystem anchor is
  what let the AI jump straight to the detector + gate. A stronger version would add the
  observable: _"the session card should auto-attach the OpenSpec change but stays
  unattached after a proposal is created — find why the gate doesn't fire."_
- **High-leverage follow-up "go on. do not run full test"** — a 6-word steer that both
  approved the fix and set the test-scope guardrail (scoped vitest, not `npm test`),
  saving minutes on this repo's large suite.
- **"update specs"** — a two-word trigger that reliably fans out to the right docs
  because this repo's doctrine ties source changes to `docs/architecture.md` + the
  nearest `AGENTS.md` row.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Reach for the full test suite after writing tests | "do not run full test" | State the scope up front: "run only the scoped vitest file, never the full suite" |
| Treat the fix as done at code | "update specs" | Add "and update docs/architecture.md + the AGENTS.md row" to the goal prompt |
| Risk over-fixing (touching phase logic broadly) | (implicit) minimal-diff expectation | Say "minimal diff: drop the phase gate only, keep phase for the badge" |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this was a contained bug fix. But the workflow is
repeatable and worth a skill: **"diagnose a dashboard detector/gate that never fires."**
It would capture the pattern used here — *explore the detector + gate → find the event
that never emits → widen or drop the over-strict AND-gate → TDD → restart server →
update the architecture doc + AGENTS.md row.* Invoke it whenever a "feature X doesn't
auto-trigger" report lands on an event-driven subsystem.

## 7. Pitfalls & dead ends

- **The AND-gate trap.** The original code required two independent signals
  (`openspecPhase && openspecChange`) where one (`phase`) depended on a tool event that
  doesn't always fire. If a feature "sometimes works, sometimes doesn't," suspect a gate
  that ANDs a reliable signal with a fragile one — prefer the reliable signal alone.
- **One `read` error** occurred during exploration (1 of 5 reads) — a wrong path guess;
  harmless, recovered by re-globbing.
- **Don't run `npm test`** to verify a one-file change on this repo — scope vitest to the
  touched test file (`npx vitest run src/server/__tests__/auto-attach.test.ts`).
- **Server change = restart, not rebuild.** `curl -X POST .../api/restart` (jiti) is
  enough; no `npm run build` needed for `src/server/`.
