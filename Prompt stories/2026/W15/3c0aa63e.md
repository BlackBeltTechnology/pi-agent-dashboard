# How we did it: Split the dashboard into a monorepo of publishable packages — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened in explore mode with a product hunch:

> "Because the frontend supports to connect remote servers maybe make sense to separate web server and dashboard server as separated product. Maybe someone would like to use dashboard only, but the server and pi agents run separate servers."

The *real* objective, once the steering turns clarified it: **restructure the single `pi-agent-dashboard` npm package into an npm-workspaces monorepo of independently publishable packages** — `shared`, `server`, `extension`, `client` (web), plus a meta-package that depends on all of them — so the React web client can be hosted separately (CDN/Nginx) and talk to a remote dashboard server over CORS. This ran the full OpenSpec loop: explore → proposal → design → specs → tasks → apply → verify → fix → build/deploy → commit → archive.

## 2. TL;DR playbook

1. **Explore first, don't code.** `/skill:openspec-explore` with the product idea. Let the AI map the current coupling (it found only **one** cross-package import violation — client importing `ArchiveEntry` from server — a clean starting point).
2. **Pick the ambition level explicitly.** Answer "level 2" (separate npm packages, not just static hosting, not fully separate repos). Then add scope: "extension package needs to be separate too. Restructure to monorepo."
3. **Answer the design questionnaire tersely.** The AI asks 5–6 numbered questions; reply `1. longer 2. ok 3. yes 4. A ...` — one line settles the whole design.
4. **Generate all artifacts.** `create proposal`, then fast-forward the rest (design → 5 specs → tasks). Result: 4 packages + meta-package, dependency graph, `useApiBase()`/`getApiBase()` plan, CORS w/ localhost default, optional static serving, `ArchiveEntry` migration.
5. **Ask "is there anything to clarify?" before apply.** This surfaced the real decisions (per-file vs barrel exports, reload-script path, which skills move) so implementation didn't stall mid-flight.
6. **Apply task-by-task.** Scaffold `packages/{shared,server,extension,client}` → copy sources → rewrite `../shared/` imports to `@blackbelt-technology/pi-dashboard-shared/*` → vitest workspace → cross-origin client → server CORS → optional static serving.
7. **When the full test suite hangs, timebox it.** After 3 hang retries: "stuck again, so ignore it." Verify with per-package runs instead of the root suite.
8. **Verify against specs, fix the gaps, then build+deploy+commit+archive.** `/opsx:verify` caught auth routes + editor iframe not prefixed and the old `src/` left behind; fix, `npm run build`, restart, `npm run reload`, commit/push, `/opsx:archive` (syncs 5 delta specs to main).

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI read `server.ts`, `App.tsx`, `ServerSelector`, and the existing `docker-packaging` change, then drew a Mermaid graph of the "currently one process" topology and offered a Level 1/2/3 spectrum. *Why it worked:* it grounded the abstract idea in the real dependency graph before proposing anything, and it discovered the codebase was already ~90% decoupled (client already supports remote servers via `getInitialWsUrl()` + localStorage).

**Phase 2 — Design negotiation.** The human chose "level 2" and expanded scope to include the extension and a full monorepo. The AI mapped imports precisely (49 relative `/api` calls, 151 `../shared/` imports, 165 test files) and settled the `@blackbelt-technology/*` package names. *Decision points:* monorepo-with-workspaces over separate repos; per-file exports over a barrel (minimal import churn); localhost as the default CORS origin.

**Phase 3 — Artifact generation (OpenSpec).** `create proposal` → fast-forward → design (10 decisions) + 5 spec files + tasks (9 groups, 52 tasks). The pre-apply "anything to clarify?" turn locked per-file exports, kept `reload` script at root, and moved only the `pi-dashboard` skill.

**Phase 4 — Apply.** Scaffold packages, `cp -r` sources into `packages/*/src/`, move `ArchiveEntry` to `packages/shared/src/archive-types.ts`, rewrite imports, build a vitest workspace. A late pragmatic pivot: instead of threading `apiBase` through every function/component, the AI introduced a **module-level `setGlobalApiBase`/`getApiBase()` getter** set once in `App.tsx` — collapsing a sprawling mechanical change into a small one.

**Phase 5 — Verify & fix.** `/opsx:verify` flagged three gaps: auth routes + editor iframe `proxyPath` not prefixed, and the **old `src/` tree left alongside `packages/`**. All fixed; per-package tests green (shared 72/72, extension 265/265).

**Phase 6 — Build, deploy, ship.** Vite couldn't resolve the shared package's `.ts` exports → added a resolve alias; jiti appended `.ts` to already-`.js` paths → fixed the exports map to `"./*.js" → "./src/*.ts"`. Then build ✓, restart ✓, reload ✓, commit/push (477 files), `/opsx:verify` clean, `/opsx:archive` (synced 5 new capability specs to main).

## 4. Prompts that worked

- **Goal prompt** — `/skill:openspec-explore` + the product hunch. *Why:* explore mode makes the AI investigate coupling and draw the topology before committing to a structure. A stronger version states the ambition up front: *"Explore splitting the dashboard into an npm-workspaces monorepo with independently publishable server/client/extension/shared packages, so the web client can be hosted separately and talk to a remote server over CORS."*
- **"level 2"** — a 2-word high-leverage pick that collapsed a Level 1/2/3 spectrum into a concrete plan.
- **"extension package need to be separate too. Restructure to monorepo"** — one line that set the whole target architecture.
- **"1. longer / 2. ok / 3. yes / 4. A / 5. OK, but local be added by default / 6. extension"** — terse numbered answers to the design questionnaire; settled six decisions at once.
- **"is there anything to clarify?"** — forced the AI to surface hidden decisions *before* apply, preventing mid-implementation stalls.
- **"stuck again, so ignore it"** — a decisive timebox that unblocked progress when the root test suite hung repeatedly.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created in this session — it rode the existing OpenSpec skill chain (`openspec-explore` → `-ff` → `-apply` → `-verify` → `-archive`).

**Recommended skill to create:** *"npm-workspaces monorepo split"* — capturing the reproducible move set: map cross-package imports first, choose per-file exports to minimize churn, use a module-level `getApiBase()` getter instead of threading `apiBase`, add a Vite resolve alias + a `"./*.js" → "./src/*.ts"` exports map for source-only TS packages under jiti/tsx, and verify per-package (not root) when the workspace suite hangs. These are the non-obvious bits that cost the most time here.

## 7. Pitfalls & dead ends

- **Root test suite hangs.** `npm test` across the new vitest workspace hung repeatedly (jsdom/canvas + stale root `vite.config.ts`/`vitest.config.ts` being auto-loaded). *Fix:* remove the old root configs so `vitest.workspace.ts` takes effect; run per-package to verify; don't block on the root suite.
- **`workspace:*` is pnpm-only.** npm workspaces choked on it — use `*` or the actual version.
- **Vite can't resolve source-only `.ts` package exports.** Add a resolve alias in the client's `vite.config.ts` mapping the package name to the real `src`.
- **jiti/tsx double-suffix.** Imports say `…/config.js`; exports `"./*": "./src/*.ts"` produced `src/config.js.ts`. *Fix:* map `"./*.js" → "./src/*.ts"` so `.js` is stripped and `.ts` added.
- **Cross-package test dependency.** `state-replay.test.ts` in the extension imported client code — move the test to the package that owns the code under test.
- **Un-prefixed relative URLs slip through.** Auth `fetch`, the auth `<a href>`, and the editor iframe `proxyPath` all needed `getApiBase()`/`apiBase` in cross-origin mode; the first mechanical pass missed them.
- **Old `src/` left behind.** After copying into `packages/`, the original tree lingered and risked stale imports — remove it once packages verify.
