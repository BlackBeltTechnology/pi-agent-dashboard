# How we did it: Rescue a crashed dashboard server (TDZ crash → merge conflicts → redeploy) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with a one-line incident report: *"server became offline and never came
back"*. No stack trace, no file, no theory — just a dead dashboard. The real objective, once
the follow-up steering clarified it, was a full incident-to-green recovery: **find why the
Node server process died, fix the root cause in source, ship it (commit + push), then later
untangle the git merge conflicts that had accumulated on the working tree and rebuild +
redeploy the running instance**. It spanned two calendar days and three distinct failure
modes — a temporal-dead-zone crash, unresolved merge conflicts, and a missing runtime
dependency after restart.

## 2. TL;DR playbook

1. **Read the server log first, not the code.** `pi-dashboard status; tail -80 ~/.pi/dashboard/server.log` — the crash line names the file, the error class, and the line number.
2. **Confirm the port is actually free** (`lsof -i :8000 -i :9999`) so you know it's a process death, not a stuck bind.
3. **Open the crashing file at the reported line** and read the *whole enclosing scope* — a `ReferenceError: Cannot access 'X' before initialization` is a temporal dead zone (TDZ): a `const`/`let` used above its declaration, often a duplicate declaration in the same scope.
4. **Fix minimally:** hoist the declaration above first use; rename the duplicate rather than deleting logic.
5. **Type-check the scope, not the repo:** `npx tsc --noEmit | grep -E '<file>'` — ignore pre-existing unrelated errors.
6. **Restart via the single source of truth:** `curl -X POST http://localhost:8000/api/restart`, then verify `/api/health`.
7. **Commit + push** the fix with a message that names the root cause (`fix: temporal dead zone crash in …`).
8. **When conflicts surface later,** grep the markers (`grep -rn '<<<<<<' src/`), resolve by *keeping both* additions when they're independent features, then **explicitly `git add` the resolved files** — content resolution alone doesn't clear "unmerged" state.
9. **Rebuild + redeploy:** `npm run build`; if `/api/restart` doesn't bring the server back, `pi-dashboard start` fresh and read the log — a fresh start surfaces missing deps a hot restart hides.

## 3. How the collaboration unfolded

**Phase 1 — Triage (log-first diagnosis).** The AI did not guess. It ran `pi-dashboard status`
and tailed `~/.pi/dashboard/server.log`, which surfaced the exact crash:
`ReferenceError: Cannot access 'meta' before initialization` at `pi-gateway.ts:88`. It
cross-checked the port with `lsof`. *Why it worked:* the log gave file + line + error class in
one shot, collapsing the whole search space before any source was opened.

**Phase 2 — Root cause + surgical fix.** Reading the enclosing `setTimeout` callback in
`src/server/pi-gateway.ts` revealed the shape of the bug: `meta` was referenced on line 88
(`!meta?.sleepRetried`) but its `const meta = heartbeatMeta.get(sessionId)` declaration sat at
line 115 — *and a second `const meta` existed in the same scope*. The AI moved the declaration
above first use and renamed the duplicate to `meta2`. It type-checked only the touched file,
noted the remaining errors were pre-existing and unrelated, then restarted through
`/api/restart` and confirmed the server was back. *Decision point:* the human let the AI drive
the whole diagnose→fix→restart loop without intervening — the log evidence made the fix
unambiguous.

**Phase 3 — Ship it.** Two terse steering prompts (`commit changes`, `push`) closed the loop:
committed as `feaba4b` with a root-cause-naming message, pushed to `develop`.

**Phase 4 — Merge-conflict cleanup (next day).** The operator returned with
*"there are conflicts in code. Resolve them"*. The AI grepped conflict markers, found two
conflicts in `src/client/App.tsx` and `src/client/hooks/useMessageHandler.ts`, both merging two
*independent* additions: `setEditorStatuses` (upstream editor-status tracking) and `maxSeqMapRef`
(stashed replay-dedup sequence tracking). Resolution kept both; the AI verified the hook
signature accepted both and that it compiled.

**Phase 5 — Stage + rebuild + redeploy.** A second nudge (*"There are git conflicts"*) exposed
that git still marked the files unmerged despite resolved content — they just needed
`git add`. Then *"build and deploy"*: `npm run build` succeeded, but `/api/restart` didn't bring
the server back. A fresh `pi-dashboard start` + log read revealed a **missing `@fastify/reply-from`
dependency**; `npm install`ing it brought the server up (pid 93930, port 8000) with the client
build deployed. *Why it worked:* falling back from hot-restart to a cold start surfaced the
dependency error the restart path had swallowed.

## 4. Prompts that worked

- **The goal prompt — *"server became offline and never came back"*.** Effective despite being
  one line: it framed a *symptom* and gave the AI freedom to diagnose. For an incident, a bare
  symptom + "and never came back" (i.e. it's a hard crash, not a transient) is enough — the log
  is the real input. A stronger version pre-attaches evidence: *"dashboard server crashed and
  won't restart — check server.log and fix the root cause."*
- **High-leverage follow-ups:** `commit changes` / `push` — two words each, they moved a verified
  fix to shipped. `build and deploy` unlocked the entire rebuild-redeploy tail. Short works when
  the preceding context is unambiguous.
- **Weak-prompt rewrite:** *"there are conflicts in code. Resolve them"* → stronger:
  *"resolve the merge conflicts, keep both additions where they're independent features, then
  stage and confirm the tree is clean."* Naming the resolution policy up front avoids the
  "resolved content but not staged" round-trip.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Resolve conflict *content* but leave files unmerged in git | Re-prompting *"There are git conflicts"* | State "resolve **and** `git add`" — content edit alone doesn't clear unmerged state |
| Trust `/api/restart` to bring the server back | (self-corrected after health check failed) | After a rebuild, verify `/api/health`; if dead, cold-`start` and read the log rather than re-curling restart |
| Treat "conflicts" as a fresh task each day | Two separate prompts a day apart | For a multi-session incident, restate the end-goal ("green + deployed") so the AI drives to done |

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session — it was a live incident, resolved reactively.
But the workflow is textbook-repeatable and **should** be captured. The
project already ships the right ones; invoke them next time instead of improvising:

- **`debug-dashboard` skill** — exactly this triage: tail `server.log`, probe `/api/health` for

- **`implement` skill (rebuild matrix)** — encodes the correct redeploy path: server change →

  do I rebuild" guesswork in Phase 5.
- **Memory worth saving:** *"TDZ `ReferenceError: Cannot access 'X' before initialization` in
  pi-gateway.ts = a `const`/`let` used above its declaration or a duplicate `const` in the same
  scope — hoist + rename."* and *"a fresh `pi-dashboard start` surfaces missing-dependency errors
  that `/api/restart` swallows."*

## 7. Pitfalls & dead ends

- **`grep '<<<<<<' src/` returning exit-1 looks like an error but isn't** — it just means no
  markers found (grep exits 1 on no match). Don't chase it; widen scope or trust the clean result.
- **`/api/restart` can silently fail to bring the server back** when a runtime dependency is
  missing — the hot path swallows the module-resolution error. If health stays down, run
  `pi-dashboard start` and read `~/.pi/dashboard/server.log` for the real cause
  (here: `@fastify/reply-from` not installed).
- **Resolved conflict content ≠ resolved merge.** Git keeps files "unmerged" until you
  `git add` them — the build/commit will fight you until you stage.
- **Don't repo-wide `tsc`** to validate a one-file fix — pre-existing unrelated type errors bury
  the signal. Grep tsc output down to the file(s) you touched.
