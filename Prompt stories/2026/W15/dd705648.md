# How we did it: Fork-from-message in the dashboard chat — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator wanted to bring pi's TUI "fork from any message" capability into the web
dashboard. The first prompt:

> `/skill:openspec-explore` — "Currently we can fork from session card only. But in pi
> tree command is available where the message can be selected where fork from. I would
> like to adapt this feature, to be able to add fork function to the card."

The **real objective**, once the steering clarified it: add a per-message **Fork**
button in the dashboard's `ChatView` so a user can branch a new session from *any* prior
message — not just the latest leaf — matching pi's `getTree()`/`createBranchedSession()`
behaviour. The finished feature landed the fork icon inside the message bubble's toolbar,
next to the existing "Copy" buttons.

## 2. TL;DR playbook

1. **Kick off in explore mode:** `/skill:openspec-explore` with the feature ask. Let the
   AI + an `Explore` subagent map the *current* fork path (`resume_session {mode:"fork"}`
   → `pi --fork <sessionFile>`, always from the latest leaf) and pi's available primitives
   (`getTree()`, `createBranchedSession(leafId)`, `branch()`).
2. **Decide the entry-ID plumbing up front.** Answer the design questions in one shot:
   embed `entryId` on events, add a per-message Fork button, do the fork server-side.
3. **Scaffold the OpenSpec change:** `/opsx:ff fork-from-message` → proposal → design →
   specs → tasks (14 tasks / 4 groups).
4. **Verify the risky assumption before coding:** ask "is there anything to clarify?" —
   this surfaced that **live** pi events (`message_start`/`message_end`) do *not* carry the
   session entry `id`; only replayed events do.
5. **Apply the change TDD-first:** `/opsx:apply` — propagate `entryId` through
   `state-replay.ts` → `event-reducer.ts` → `browser-protocol.ts`, add tests at each layer.
6. **Hit the peer-dep wall, pivot to Approach C:** `SessionManager` is an *optional peer
   dep* not installed server-side → don't import it. Instead write the JSONL surgery
   yourself: `createBranchedSessionFile()` prunes root→target entry, then `pi --fork
   <prunedFile>`.
7. **Wire the UI:** Fork button in `ChatView.tsx`, callback through `App.tsx` →
   `useSessionActions.ts`.
8. **Build + deploy + verify in-browser:** `npm run build` → `POST /api/restart` →
   `npm run reload`, then drive the real UI with the `browser` skill to confirm the button.
9. **Fix the "no icon on live messages" gap:** enrich live bridge events with
   `ctx.sessionManager.getLeafId()` in `bridge.ts` so the fork button also appears on the
   current turn's messages.
10. **Polish placement:** move the fork icon *inside* `MessageBubble`, alongside the Copy
    buttons, instead of a floating hover button.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode + subagent).** The AI ran `/skill:openspec-explore`,
spawned an `Explore` subagent, and grepped both the repo and the installed
`@mariozechner/pi-coding-agent/dist` typings. It found pi's `SessionManager` exposes
exactly the needed primitives and that the current dashboard fork always branches from the
*latest* leaf. *Why it worked:* grounding the design in pi's real API (not guesses) meant
the plan mapped cleanly onto existing primitives.

**Phase 2 — Design decisions.** The human answered the open questions decisively (embed
`entryId`, per-message Fork button, server-side fork via "Approach A —
`createBranchedSession`, verify first"). The AI confirmed fork runs server-side in
`session-action-handler.ts` → `spawnPiSession()`, then produced the ordered change plan.

**Phase 3 — Artifact generation.** `/opsx:ff` fast-forwarded proposal → design → specs
(6 requirements) → tasks (14 tasks). *Decision point:* the human paused implementation to
ask "is there anything to clarify?" — a cheap check that caught the live-vs-replayed
`entryId` asymmetry before any code was written.

**Phase 4 — Implementation (TDD).** `/opsx:apply` walked all 14 tasks: `entryId` added to
replay events → `ChatMessage` → protocol, each with tests. The peer-dep discovery forced a
mid-flight pivot from Approach A (import `SessionManager`) to Approach C (hand-rolled JSONL
pruning in `session-file-reader.ts`). All 112 tests passed.

**Phase 5 — Verify + iterate in the real UI.** After build/restart/reload, the AI used the
`browser` skill to drive the live dashboard. Two rounds of steering followed: (a) the fork
icon was missing on live messages → enrich `bridge.ts` events with `getLeafId()`; (b) the
floating hover button was ugly → relocate it inside `MessageBubble` next to Copy.

## 4. Prompts that worked

- **Goal prompt** (`/skill:openspec-explore` + the feature ask): effective because it
  opened in *explore* mode — the AI mapped current state and pi's API before proposing,
  rather than jumping to code. Reuse this pattern for any "port a pi/TUI feature into the
  dashboard" task.
- **The batched design answer** ("1. yes, embed entryId. 2. make sense. 3. Fork button per
  message. createBranchedSession: Option A — because as I know the Fork is executed there.
  Check it and if doesn't ask this question again"): a single high-leverage turn that
  resolved every open design question *and* delegated verification ("check it… don't ask
  again"). This is the move that unlocked the whole implementation.
- **"Is there anything to clarify?"** — a short pre-implementation prompt that forced the AI
  to surface hidden assumptions (the live-event `entryId` gap) while course-correction was
  still cheap.
- **"Can it put where Copy as icons are placed in the bottom of message box?"** — precise
  UI-placement steering that turned a functional-but-clumsy hover button into polished UX.

*Weak-prompt rewrite:* "go on" and "go on without full test" worked here only because
context was rich. A stronger reusable form: **"proceed to `<next artifact/task group>`;
skip the full suite, run only the tests for the files I touched."**

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session, but two reusable assets were exercised:

- **`Explore` subagent** — used once to map fork functionality across repo + installed pi
  typings without polluting the main context. Invoke it whenever you need to locate "how
  does X currently work" across both the dashboard source *and* the pi peer package.
- **The `browser` skill** — drove the live dashboard to confirm the fork button rendered
  (including hover-only `opacity-0` states via Playwright hover). Invoke it to verify any
  client-side UI change end-to-end instead of trusting a build.

**Skill worth creating:** a `port-pi-feature-to-dashboard` playbook capturing the
recurring shape — explore pi's primitive → decide the event/protocol plumbing → remember
the server-can't-import-pi constraint → apply TDD → verify in-browser → enrich live bridge
events if the feature needs data pi doesn't emit.

## 7. Pitfalls & dead ends

- **`openspec change new fork-from-message` failed** — the subcommand didn't exist; fell
  back to `mkdir -p openspec/changes/fork-from-message` + `openspec status/instructions`.
  If `openspec change new` errors, scaffold the directory manually.
- **`require('@mariozechner/pi-coding-agent/dist/core/session-manager.js')` failed** — the
  package is an **optional peer dep, not in `node_modules`** on the server side. Don't try
  to import pi runtime classes server-side; do the JSONL work yourself.
- **Fork icon missing on live messages** — live `message_start`/`message_end` events don't
  carry the entry `id`; only replayed events (from `state-replay.ts`) do. Fix by attaching
  `ctx.sessionManager.getLeafId()` in the bridge's event enrichment.
- **Hover-only button invisible in screenshots** — the button uses
  `opacity-0 group-hover/msg:opacity-100`; a plain screenshot won't show it. Use Playwright
  `hover` (or snapshot the accessibility tree) to verify it exists.
