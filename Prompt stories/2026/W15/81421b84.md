# How we did it: Fork-from-message in the dashboard chat view — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user wanted to bring pi's TUI "fork from any message" capability into the
dashboard. The opening prompt:

> `/skill:openspec-explore` — "Currently we can fork from session card only. But in pi
> `tree` command is available where the message can be selected where fork from. I would
> like to adapt this feature, to be able to add fork function to the card."

The real objective, once the steering clarified it: **add a per-message "Fork from
here" control in the chat view** that spawns a new session pruned to `root→that
message`, mirroring what pi's `tree` selector does — instead of the dashboard's
existing "fork the whole session from the latest entry" behavior.

## 2. TL;DR playbook

1. Kick off in `/skill:openspec-explore` to map pi's fork primitives *before* writing any code.
2. Confirm the pi API: `SessionManager.getTree()`, `createBranchedSession(leafId)`, `branch()` — the fork-from-specific-entry primitive already exists in pi.
3. Trace the current fork path server-side: `session-action-handler.ts` → `spawnPiSession()` runs `pi --fork <sessionFile>` (always from the latest leaf).
4. Decide the design up front: **propagate `entryId` end-to-end** (replay events → `ChatMessage` → `resume_session` protocol → server), and **prune the session file server-side** before `pi --fork`.
5. Scaffold the OpenSpec change (`/opsx:ff`): proposal → design → specs → tasks (14 tasks, 4 groups).
6. Apply tasks (`/opsx:apply`) TDD-style: entryId propagation + tests, protocol field, server branched-fork + tests, UI fork button.
7. When `SessionManager` turns out to be an **optional peer dep not installed in the server's `node_modules`**, pivot to **Approach C**: do the JSONL surgery yourself (`createBranchedSessionFile()` writes a pruned `root→target` JSONL).
8. Build + `curl -X POST /api/restart` + `npm run reload`, then verify in the browser skill.
9. When the fork button is missing on live messages, enrich live bridge events with `ctx.sessionManager.getLeafId()` so `entryId` is present without a reload.
10. Final polish: move the fork icon **into** `MessageBubble` next to the Copy buttons, not a separate hover control.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI ran `/skill:openspec-explore`, spawned an
`Explore` subagent, and grepped both the repo and pi's installed `dist/*.d.ts` for
`getTree`, `createBranchedSession`, `branch`, `entryId`. *Why it worked:* it found that
pi already ships the exact primitive (`createBranchedSession(leafId)` writes a new
session file containing only `root→leafId`), so the design became "wire the plumbing"
rather than "invent forking." **Decision point:** the human answered a batch of design
questions in one turn — embed `entryId`, a fork button per message, and "Approach A
(server-side branch), verify it and don't re-ask."

**Phase 2 — Design & scaffold (OpenSpec).** `/opsx:ff` generated proposal → design →
specs (6 requirements) → tasks (14 tasks in 4 groups). *Why it worked:* the design
committed to a single data-flow spine — attach `entry.id` in `state-replay.ts`, carry it
on `ChatMessage`, add an optional `entryId` to `resume_session`, prune server-side.

**Phase 3 — Implement (TDD apply).** `/opsx:apply` walked the 14 tasks, writing tests
first for each layer (state-replay, event-reducer, session-file-reader). **The key pivot:**
the server *can't* import `SessionManager` — pi-coding-agent is an optional peer dep,
absent from server `node_modules` (only present at runtime inside a pi session). The AI
switched to **Approach C**: a hand-written `createBranchedSessionFile()` that parses the
JSONL `id`/`parentId` tree and writes the pruned file. All 112 tests passed.

**Phase 4 — Deploy & verify (browser).** `npm run build` → `/api/restart` → `npm run
reload`, then drove the browser skill. **Two corrective loops:** (a) fork buttons were
missing on the *live* session — live pi events don't carry the entry id — fixed by
enriching `message_start`/`message_end` in `bridge.ts` with `ctx.sessionManager.getLeafId()`;
(b) the human asked to move the icon next to the Copy buttons, so the button was
refactored into `MessageBubble`.

## 4. Prompts that worked

- **Goal prompt (`/skill:openspec-explore` + the ask).** Effective because it forced a
  discovery pass on pi's real API before any implementation — the whole design hinged on
  finding `createBranchedSession`.
- **Batched design answers** (steering #2): *"1. yes, embed entryId. 2. make sense.
  3. Fork button per message. createBranchedSession: Option A — because as I know the Fork
  is executed there. Check it and if doesn't ask this question again."* One turn resolved
  every open design decision **and** granted autonomy ("check it, don't re-ask").
- **`/opsx:ff` then `/opsx:apply`** — high-leverage: two skill invocations took the change
  from idea to 14 implemented+tested tasks.
- **"go on without full test"** and **"build and deploy"** — short unblock prompts that
  kept momentum without micro-managing.
- **Weak → strong rewrite:** *"I dont see any icon for fork in chatr window"* is a bug
  report, not a spec. Stronger: *"Fork buttons only render on replayed messages (they
  have `entryId`); live-session messages lack it — enrich live `message_start`/`message_end`
  events with the entry id so the button shows without a reload."*

## 7. Pitfalls & dead ends

- **`SessionManager` import fails on the server.** `node -e "require('@mariozechner/
  pi-coding-agent/...')"` and the import variants all failed — the package isn't in server
  `node_modules`. *If you hit this:* do the JSONL surgery yourself (`createBranchedSessionFile`),
  don't chase the import.
- **`openspec change new <name>` failed** — the subcommand shape was wrong; fell back to
  `mkdir -p openspec/changes/<name>` + the `openspec instructions/status` JSON flow.
- **Fork button invisible on the live session.** Live pi events don't carry the entry id;
  only replayed events (from `state-replay.ts`) do. *Fix:* enrich `message_start`/`message_end`
  in `bridge.ts` with `ctx.sessionManager.getLeafId()`.
- **Hover-only button not visible in screenshots.** The button is `opacity-0
  group-hover/msg:opacity-100`; verify with a Playwright hover (or the snapshot's `@ref`
  list), not a plain screenshot.
