# How we did it: Trusted networks — letting the dashboard reach past localhost

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in explore mode ("Enter explore mode. Think deeply… you must
NEVER write code or implement features"). The *real* objective, which only surfaced
once the exploration mapped the codebase: **the dashboard binds on `0.0.0.0:8000` but
every sensitive route is gated by a per-route `localhostGuard` that 403s any
non-loopback IP** — so remote access (LAN, another machine, mDNS-discovered peer)
is impossible even when you want it. The operator wanted a *deliberate* escape hatch:
mark specific LAN CIDRs as trusted (via a Settings button), and let authenticated
(OAuth JWT) remote users through too — without opening the server to the world.

## 2. TL;DR playbook

1. **Explore first, don't code.** `/opsx:explore` the security model: find where the
   server binds (`server.ts` `listen`), find every `localhostGuard` preHandler, and
   map the auth `onRequest` hook vs route `preHandler` execution order.
2. **Let the exploration surface the design**, then pick the shape: a top-level
   `trustedNetworks: string[]` config, merged with the existing `auth.bypassHosts`,
   consumed by a single `createNetworkGuard()` factory. Settings gets an "add local
   network" button that reads detected interfaces.
3. **Feed the model the real-world edge cases as steering** *before* generating
   artifacts: zrok tunnel (appears as loopback — works today), authenticated remote
   (JWT passes auth hook but `localhostGuard` still 403s), mDNS-discovered peer
   (health probe passes, all API calls 403).
4. **`/opsx:ff`** to generate proposal → design → specs → tasks in one pass, then
   **iterate the proposal** as each edge case lands (the guard becomes a three-way
   check: loopback → trusted network → `request.isAuthenticated` → else 403).
5. **`/opsx:apply`** and implement TDD-style: write the guard/config tests first,
   watch them fail, then implement `createNetworkGuard`, thread it through all 7
   route files via `route-deps.ts`, add the `decorateRequest('isAuthenticated')`.
6. **Test → build → deploy → commit → push** in tight loops after each functional
   chunk; skip the full suite when it hangs ("go on without full test").
7. **Verify with `/opsx:verify`**, fix the warnings (stale docs, duplicate re-export,
   dropdown UX), then **`/opsx:archive`** and sync delta specs to main specs.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI traced the binding (`0.0.0.0:8000`),
enumerated every `localhostGuard` usage across the route files, and diagrammed the
two independent security layers (auth `onRequest` hook + per-route `localhostGuard`
preHandler). *Why it worked:* explore mode forbade implementation, so the model spent
its budget building an accurate mental model and ASCII flow diagrams instead of
prematurely editing code.

**Phase 2 — Design shaping.** The human chose "Option C, but be a button" (add
networks from Settings) and "merge them" (unify `trustedNetworks` with
`bypassHosts`). The AI checked `os.networkInterfaces()` for interface detection and
settled on a `createNetworkGuard` factory + `RouteDeps` threading. *Decision point:*
Option A (auth hook tags request via `decorateRequest`) over Option B (guard does its
own JWT check) — single source of auth truth.

**Phase 3 — Artifact generation + iterative deepening.** `/opsx:ff` produced all four
artifacts. Then three steering turns each surfaced a new access scenario (zrok,
authenticated-remote, mDNS) and the AI updated proposal/design/specs/tasks in place.
The guard grew from two-way to three-way. *Why it worked:* the human front-loaded the
hard cases as explicit prompts, so the spec matured before a line of code was written.

**Phase 4 — Implementation (TDD).** `/opsx:apply` walked 35 tasks in dependency order:
extract IP helpers into `localhost-guard.ts`, add config parsing, the auth decorator,
the guard factory (tests first, red, then green — "All 18 tests pass"), thread the
guard through 7 route files, WS-upgrade check, network-interfaces endpoint, Settings
UI. *Decision point:* "tests stuck, go on without full test" — targeted vitest runs
per module instead of the hanging full suite.

**Phase 5 — Real-world debugging.** Two operator screenshots drove two fixes: the
Settings save button didn't detect `trustedNetworks` as dirty (diff builder missed
the field), and cross-machine connection failed because Node reports remote IPv4 as
`::ffff:192.168.x.x` when listening on `0.0.0.0` — the CIDR matcher only handled pure
IPv4. Strip the `::ffff:` prefix before matching. *Why it mattered:* the feature only
truly worked after the IPv6-mapped-address fix.

**Phase 6 — Verify, clean, archive.** `/opsx:verify` flagged stale docs, a duplicate
`isBypassedHost` re-export, and two untested scenarios. The human said "fix them"; the
AI updated `AGENTS.md`/`architecture.md`, removed the re-export, added click-outside
dropdown close. Then `/opsx:archive` synced delta specs to main and archived the
change (plus two sibling changes from earlier work).

## 4. Prompts that worked

- **Goal prompt (`/opsx:explore`)** — effective *because it banned implementation*.
  It forced a full-fidelity investigation of the two-layer security model before any
  code, which is exactly what a subtle access-control change needs.
- **"Option C, but be a button which can add local networks to trusted network in
  settings"** — high-leverage: one sentence fixed both the mechanism (config-driven
  trusted CIDRs) and the UX (Settings button), removing a whole round of design churn.
- **"Merge them / text enough"** — a two-word unlock that collapsed the
  `trustedNetworks` vs `bypassHosts` duplication decision.
- **The three edge-case steering prompts** (zrok/JWT redirect, mDNS-only-localhost,
  "Is there anything to clarify?") — each expanded scope *before* generation, so the
  spec absorbed the complexity instead of a post-hoc patch.
- **"tests stuck, go on without full test"** — pragmatic override that kept momentum;
  the AI switched to per-module vitest runs.

*Rewrite of the weak ones:* "fix them" and "fix ig" work only because `/opsx:verify`
had just produced a numbered warning list. Next time, prefer "fix warnings 1 and 3,
leave 2" to keep the AI from over-reaching.

## 7. Pitfalls & dead ends

- **`openspec change new <name>` failed** — the CLI subcommand differs; fall back to
  `mkdir -p openspec/changes/<name>` + `openspec status --change` to drive the flow.
- **Full test suite hangs** — don't wait on it; run per-module vitest (`npx vitest run
  src/server/__tests__/<file>.test.ts`) and move on.
- **IPv6-mapped IPv4 (`::ffff:192.168.x.x`)** — the single biggest trap. On a `0.0.0.0`
  bind, Node hands you mapped addresses; a naive IPv4 CIDR matcher silently 403s every
  remote client. Strip the prefix first.
- **Settings "No changes to save"** — a new top-level config field is invisible to the
  save button until you add it to the diff builder. Wire both ends.
- **Duplicate `isBypassedHost` re-export** — after extracting helpers to
  `localhost-guard.ts`, remove the old re-export from `auth-plugin.ts` and fix the test
  import, or `/opsx:verify` flags it.
