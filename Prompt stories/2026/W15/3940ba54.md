# How we did it: Fork-from-message in the dashboard chat — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The operator wanted to bring pi's TUI "fork from any message" capability into the
dashboard. The opening prompt:

> "Currently we can fork from session card only. But in pi tree command is available
> where the message can be selected where fork from. I would like to adapt this
> feature, to be able to add fork function to the card."

The **real objective**, once the steering clarified it: add a per-message **Fork**
button in the dashboard chat view so a user can branch a *new* session from any
chosen message (not just the latest leaf), matching what pi's tree selector does —
and do it through the full OpenSpec workflow (explore → proposal → design → specs →
tasks → apply → deploy → verify in a real browser).

## 2. TL;DR playbook

1. **Kick off in explore mode** — `/skill:openspec-explore` with the one-paragraph
   ask. Let the AI map pi's own primitives first (`SessionManager.getTree()`,
   `createBranchedSession(leafId)`, `getBranch()`).
2. **Lock the four design decisions early** (embed `entryId`, per-message Fork button,
   server-side `createBranchedSession`) so the proposal is unambiguous.
3. **Fast-forward the artifacts** — `/opsx:ff fork-from-message` to generate
   proposal + design + specs + tasks in one pass.
4. **Verify one risky assumption before coding** — ask "is there anything to clarify?"
   The AI surfaced that **live pi events don't carry the entry `id`** (only replayed
   events do). Decide the fork button is replay-only… then later enrich live events.
5. **Apply the tasks TDD-style** — `/opsx:apply`, 14 tasks, tests first per group.
6. **Handle the peer-dep reality**: `@mariozechner/pi-coding-agent` is an *optional
   peer dep not installed in the server's node_modules* → can't import `SessionManager`
   server-side → do the JSONL surgery yourself (`createBranchedSessionFile`).
7. **Build + deploy + verify in the browser** — `npm run build`, `POST /api/restart`,
   `npm run reload`, then drive the real UI with the browser tool to confirm the button.
8. **Iterate on placement** from real screenshots — move the Fork icon from a hover-only
   external button into the message bubble toolbar next to the Copy buttons.
9. **Chase the regression** the operator spotted — forked cards showed stale OpenSpec
   "Exploring" phase; root-cause it (replay re-triggers activity detection) and fix by
   skipping detection during replay.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI spawned two `Explore` subagents and
grepped both the dashboard source and pi's installed dist to find fork primitives. Key
find: `SessionManager.createBranchedSession(leafId)` writes a *new session file*
containing only root→leaf — exactly "fork from this message." *Why it worked:* it
grounded the design in pi's real API instead of inventing a fork mechanism.

**Phase 2 — Design decisions.** The operator answered the open questions crisply
(embed `entryId`; Fork button per message; use the server-side path "Approach A").
Notable steer: *"createBranchedSession: Option A — because as I know the Fork is
executed there. Check it and if doesnt ask this question again from user."* The AI
confirmed fork runs server-side in `session-action-handler.ts` and stopped asking.

**Phase 3 — Artifacts.** `/opsx:ff` produced proposal, design, specs (6 requirements),
and tasks (14 tasks, 4 groups). The AI drew mermaid diagrams of the entry-ID
propagation chain (`state-replay.ts → event-reducer.ts → ChatMessage`).

**Phase 4 — Pre-flight clarification.** Before implementing, the operator asked "Is
there anything to clarify?" The AI caught the load-bearing gap: **live** events
(`message_start`/`message_end`) don't include the session entry `id`; only **replayed**
events do. Decision: acceptable — fork button appears on prior-turn (replayed) messages.

**Phase 5 — Implementation (TDD).** `/opsx:apply` walked all 14 tasks, writing tests
first per group. Mid-way, the peer-dep wall appeared: the server can't `import`
`SessionManager` (optional peer dep, not in `node_modules`). The AI pivoted from
"Approach A" (call pi's method) to "Approach C" (write the pruned JSONL directly in
`session-file-reader.ts`), since the session file is just `id`/`parentId` JSONL.

**Phase 6 — Deploy + browser verify.** Build, restart, reload, then the browser tool
opened the live dashboard. First check: live session's messages had no `entryId` (as
predicted) so no button. The AI then **enriched live events** using
`ctx.sessionManager.getLeafId()` in the bridge so future live messages also carry the
entry ID. Re-verified via hover — "Fork from here" buttons present.

**Phase 7 — UX polish + regression fix.** Operator asked to move the fork icon next to
the Copy buttons in the bubble toolbar — done by pushing `entryId`/`onFork` into
`MessageBubble`. Then the operator reported forked cards inheriting a stale OpenSpec
"Exploring" phase and asked to **analyze only, not modify**. The AI root-caused it
(replayed parent events re-fire `detectOpenSpecActivity()`), then on "fix it" skipped
OpenSpec detection + phase-clearing during replay.

## 4. Prompts that worked

- **The goal prompt** (effective): named the *source of truth* ("pi tree command") and
  the *target surface* ("add fork function to the card"). A stronger version states the
  workflow up front: *"Via OpenSpec, add a per-message Fork button in the dashboard
  chat that branches a new session from any message, mirroring pi's tree fork."*
- **Decision batch** (`"1. yes embed entryId. 2. make sense. 3. Fork button per message.
  createBranchedSession: Option A — check it and if doesnt ask again"`): unblocked the
  whole design in one message and told the AI to *self-verify rather than re-ask*.
- **`"Is there anything to clarify?"`** — a high-leverage pre-flight prompt that forced
  the AI to surface the live-vs-replayed `entryId` gap *before* coding, not after.
- **`"Do not modify, just analyze the problem"`** then **`"okay, fix it"`** — separating
  diagnosis from action produced a clean root-cause before any edit.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session, but the workflow is a strong candidate
for one. Recommended skill: **"fork/branch a session from an arbitrary message"** —
capturing (a) pi's `createBranchedSession` semantics, (b) the **server-can't-import-pi
peer-dep rule** → do JSONL `id`/`parentId` pruning in `session-file-reader.ts`,
(c) the **`entryId` propagation chain** (`state-replay.ts` for replayed events +
bridge `getLeafId()` enrichment for live events), and (d) the **replay-suppression
rule**: any per-event side-effect (OpenSpec activity detection, phase clearing) must be
gated behind `replayingSessions.has(sessionId)` or forked cards inherit stale state.

The two `Explore` subagents were the effective tool here — they isolated the "where do
pi and the dashboard implement fork" search out of the main context.

## 7. Pitfalls & dead ends

- **`openspec change new` failed** — the CLI verb was wrong; fell back to
  `mkdir -p openspec/changes/<name>` + `openspec status/instructions`. If `change new`
  errors, scaffold the directory manually.
- **`require('@mariozechner/pi-coding-agent/.../session-manager.js')` failed** — the
  package isn't in the server's `node_modules` (optional peer dep, only present when the
  *extension* runs inside pi). Don't design server logic around importing pi; operate on
  the JSONL file directly.
- **Fork button invisible on the live session** — live pi events don't carry the entry
  `id`. If a per-message feature depends on `entryId`, enrich live events via
  `ctx.sessionManager.getLeafId()` in the bridge, don't rely on replay alone.
- **Forked card stuck in "Exploring"** — replaying the parent's JSONL re-fires
  `detectOpenSpecActivity()`. Gate all replay side-effects behind the replay flag.
- **Hover-only buttons don't show in screenshots** — `opacity-0 group-hover` means you
  must actually `hover` with the browser tool (or read the a11y snapshot) to confirm.
