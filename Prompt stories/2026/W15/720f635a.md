# How we did it: Fork-from-message in the dashboard chat view — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator wanted to bring pi's TUI "pick a message and fork from there" capability
into the dashboard. The kickoff prompt:

> `/skill:openspec-explore` — "Currently we can fork from session card only. But in pi
> tree command is available where the message can be selected where fork from. I would
> like to adapt this feature, to be able to add fork function to the card."

The real objective, once steering clarified it: **add a per-message "Fork from here"
button in the dashboard chat view** that forks a new session containing only the path
from the conversation root down to the chosen message — matching what pi's
`SessionManager.createBranchedSession()` does under the hood, but driven from the web UI.

## 2. TL;DR playbook

1. Kick off with `/skill:openspec-explore` and describe the feature + the pi primitive
   you're copying ("pi's `tree` lets you fork from any message").
2. Let the AI map both sides: pi's fork primitives (`getTree`, `getBranch`,
   `createBranchedSession`, `branch`) **and** the dashboard's current fork path
   (`resume_session {mode:"fork"}` → `pi --fork <sessionFile>`, which always forks the
   *latest* leaf). This gap is the whole feature.
3. Answer the design questions decisively in one turn: embed `entryId` in events, add a
   **per-message** fork button, do the fork **server-side** (Approach A).
4. `Create proposal`, then fast-forward the remaining artifacts (design → specs → tasks)
   with the `/opsx:ff` skill.
5. Before applying, ask **"Is there anything to clarify?"** — this surfaced the key
   limitation (live events lack `entryId`; only replayed messages have it).
6. `/opsx:apply` the change, working the 14 tasks in dependency order:
   entryId propagation → protocol → server fork logic → UI button.
7. When the peer-dep import fails (`SessionManager` not in `node_modules`), pivot from
   Approach A to **Approach C**: do the JSONL tree surgery yourself in
   `session-file-reader.ts` (`createBranchedSessionFile()` writes a pruned root→target file).
8. `build and deploy` (rebuild + `/api/restart` + `npm run reload`), then verify in the
   browser.
9. When the button doesn't appear on live messages, enrich live `message_start` /
   `message_end` events in the bridge with `ctx.sessionManager.getLeafId()` so both
   replayed and live messages carry `entryId`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** Spawned an `Explore` subagent and grepped both
the dashboard source and the installed `@mariozechner/pi-coding-agent` dist. Found pi's
`SessionManager` already exposes exactly the needed primitives, and that the dashboard's
`--fork` always forks the latest leaf. *Why it worked:* the AI reconciled two codebases
(pi internals + dashboard) before proposing anything, so the design was grounded in real
method signatures, not guesses. **Decision point:** the human chose Approach A
(server-side `createBranchedSession`) and a per-message button.

**Phase 2 — Artifacts (openspec).** Created proposal → design → specs → tasks via
`/opsx:ff`. Design captured a clean four-stage flow: entryId propagation → protocol →
server fork → UI. 14 tasks in 4 groups. *Why it worked:* the four-stage decomposition
mirrored the data path, so each task touched one seam.

**Phase 3 — Clarify before build.** The human asked "Is there anything to clarify?"
The AI checked `flow-event-wiring.ts` / `bridge.ts` and discovered **live pi events
don't carry the session entry `id`** — only replayed events (from `state-replay.ts`) can.
This was flagged as an accepted limitation up front rather than discovered as a bug later.

**Phase 4 — Implement (apply).** Worked the 14 tasks TDD-style (tests alongside each
change). **Decision point / pivot:** at task 7 the server-side import of `SessionManager`
failed — `pi-coding-agent` is an *optional peer dep*, absent from the server's
`node_modules`. Rather than force it, the AI switched to **Approach C**: hand-roll the
JSONL prune (`createBranchedSessionFile()` walks `id`/`parentId` root→target and writes a
new file). All 112 tests passed.

**Phase 5 — Deploy & verify.** `npm run build` → `curl /api/restart` → `npm run reload`,
then drove the browser to hover chat messages. The button was missing on the *live*
session (live messages had no `entryId`). Final fix: enrich live `message_start` /
`message_end` in `bridge.ts` with `ctx.sessionManager.getLeafId()`. After reload, both
replayed and future live messages carried `entryId` and the hover "Fork from here"
button appeared throughout.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session — the work rode existing skills
(`openspec-explore`, `/opsx:ff`, `/opsx:apply`) and one `Explore` subagent.

**Skill that *should* exist:** a "fork-a-session-file" note capturing the reusable trap —
the dashboard **server** can't import `SessionManager` (optional peer dep), so any
session-tree operation (prune, branch, fork-from-entry) must be reimplemented as **direct
JSONL surgery** over `id`/`parentId` in `session-file-reader.ts`. That single fact was the
session's biggest pivot and will recur for any future session-file feature. Worth a
project memory: *"src/server has no `@mariozechner/pi-coding-agent` at runtime — do tree
ops on the raw JSONL, don't import SessionManager server-side."*

## 7. Pitfalls & dead ends

- **`SessionManager` import fails server-side.** `pi-coding-agent` is an optional peer
  dep, not in the server's `node_modules`. If you hit `Cannot find module` / empty
  `node_modules/@mariozechner`, don't try to install it — do the JSONL prune yourself
  (`createBranchedSessionFile()`), walking `parentId` from the target entry to root.
- **Fork button invisible on the active session.** Live pi events don't include the
  session entry `id`; only replayed events (`state-replay.ts`) do. If the button only
  shows after a reload, enrich live `message_start` / `message_end` in `bridge.ts` with
  `ctx.sessionManager.getLeafId()`.
- **`openspec change new fork-from-message` failed.** The scaffolder subcommand wasn't the
  right shape; the change dir was created with `mkdir -p openspec/changes/<name>` +
  `openspec status --json` instead. Check `openspec --help` before assuming a subcommand.
- **Hover-only button looks "missing" in screenshots.** The button is
  `opacity-0 group-hover/msg:opacity-100`. It won't appear in a plain screenshot — hover
  the message (Playwright `hover`) or read the accessibility snapshot to confirm it's there.
