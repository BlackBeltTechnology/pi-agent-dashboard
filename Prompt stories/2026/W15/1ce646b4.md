# How we did it: Packaging the whole pi-dashboard architecture into Docker — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The user opened in explore mode and asked to package the entire pi-dashboard stack into a single Docker image:

> `/skill:openspec-explore` — "Search web and think ultrahard. I would like to package the whole architecture inside a docker image. I would like to be able to mount volumes which can be used as a directory - means to limit them. In the docker image I would like that all tools which can be used be add. code-server, zrok, tmux, bash tools jq, tmux, pi itself... In volume mount prefer OS version - for example fs type deriver can be set different from default to be able to handle lot of writes, fast read etc. It's ok to create a compose which able start stuff."

The **real objective**, once the steering clarified it: produce a *ready-to-implement* OpenSpec change (`docker-packaging`) for an all-in-one container — server + bridge + pi agent + code-server + zrok + tmux + CLI tools — with performance-tuned volume mounts, dual API-key provisioning, an optionally-exposed external gateway, and per-workspace bind mounts. A later steering turn expanded scope: let the **Electron desktop app connect to a Docker-hosted gateway** while remaining the local UI shell.

## 2. TL;DR playbook

1. Kick off with `/skill:openspec-explore` + "search web and think ultrahard" so the AI grounds the design in current best practices before writing anything.
2. Let it run **parallel web research** (node-pty/glibc, overlay2 vs ext4/xfs tuning, zrok-in-docker, tmpfs driver options) and **read the project's own runtime files** (`tunnel.ts`, `process-manager.ts`, `editor-detection.ts`, `fix-pty-permissions.cjs`) in the same phase.
3. Answer its clarifying question compactly — a numbered list mapping 1:1 to its questions ("1. both … 2. Yes … 3. Yes! 4. yes") is enough to lock the design.
4. When the CLI scaffold command fails (`openspec change new` is not a subcommand), fall back to `mkdir -p openspec/changes/<name>` and mirror an existing change's file layout.
5. Drive artifacts with `openspec status --change <name> --json` to get the dependency order, then `openspec instructions <artifact> --change <name> --json` before writing each one.
6. Fast-forward the rest with `/opsx:ff` to generate design → specs → tasks in sequence without stepping through each interactively.
7. To expand scope later, re-enter `/opsx:explore`, read the archived sibling change (`electron-desktop-bundle`) and the monorepo's `packages/electron/` + `packages/client/` files, then land the delta as a new decision/requirement/task group across **all four artifacts** at once.
8. Verify consistency with `openspec status --change <name>` after every batch of edits.

## 3. How the collaboration unfolded

**Phase 1 — Explore & research (parallel).** The AI read the explore skill, then fired two `web_search` calls and a batch `fetch_content` (overlay2 tuning blog, zrok docker guide, tmpfs driver docs) while simultaneously reading the project's runtime touchpoints. *Why it worked:* research and code-grounding happened together, so the design was anchored in both external best practice and the repo's actual node-pty/tunnel/editor behavior. **Decision point:** the human's first prompt front-loaded "search web and think ultrahard," which is what triggered the deep research posture.

**Phase 2 — Clarify & lock design.** The AI asked a small set of design questions (dual provisioning, external gateway, per-workspace mounts, volume profiles). The human answered with a terse numbered list. *Why it worked:* the answers mapped 1:1 to the questions, so no ambiguity survived into the proposal.

**Phase 3 — Scaffold the change.** `openspec change new docker-packaging` **failed** (not a valid subcommand). The AI recovered by inspecting `openspec --help`, listing an existing change's directory (`hide-debug-events`), and hand-creating `openspec/changes/docker-packaging/` to match. **Decision point:** rather than fight the CLI, mirror a known-good change's structure.

**Phase 4 — Generate artifacts (`/opsx:ff`).** Using `openspec status --json` for the build order and `openspec instructions … --json` per artifact, the AI produced proposal → design → specs → tasks: 7 key design decisions, 8 requirements / 17 scenarios, 20 tasks in 7 groups. It also noticed the *sibling* `hide-debug-events` change was **already fully implemented** in code and archived it with `openspec archive hide-debug-events --skip-specs -y`.

**Phase 5 — Scope expansion (Electron remote mode).** Days later the human returned: "make the electron apps selectable so a docker-based gateway is used but dashboard is the app." The AI re-explored, discovered the repo had been **restructured into a monorepo**, read `packages/electron/src/` (`main.ts`, `server-lifecycle.ts`, `wizard-state.ts`) and `packages/client/`, then folded the delta into all four artifacts: Decision 8 ("Remote" mode), 2 new requirements / 5 scenarios, and a new task group 7. Final tally: **27 tasks across 8 groups**, ~50 lines of Electron change.

## 4. Prompts that worked

- **Goal prompt** — pairing `/skill:openspec-explore` with "Search web and think ultrahard" was the high-leverage kickoff: it put the AI in explore mode *and* authorized deep research before any file was written. A future user should keep this pattern (skill + explicit "research first, think hard").
- **High-leverage follow-up "1. both … 2. Yes … 3. Yes! 4. yes"** — a compact numbered reply that resolved four open design questions in one turn. This is the ideal shape for answering a batch clarification.
- **"yes"** — a single word approving the proposal direction, enough to unblock artifact generation.
- **Scope-expansion prompt** — "check how to make the electron apps to be selectable that docker based gateway be used but dashboard be the app" clearly stated the desired end-state (Electron = UI, Docker = gateway), which let the AI find the exact three files to change.
- **Weak → stronger:** the goal prompt had typos and run-ons ("stufzz", "deriver"). A cleaner version: *"Explore + web-research a single all-in-one Docker image for the whole pi-dashboard stack (server, bridge, pi, code-server, zrok, tmux, jq). Support performance-tuned volume mounts (selectable fs/driver for write-heavy vs read-fast), a docker-compose to start it, and an optionally-exposed external gateway."*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Ask design questions one direction at a time | Answering with a 1:1 numbered list ("1. both … 2. Yes …") | Front-loading the answers in the goal prompt, or asking the AI to batch all questions once |
| Reach for a non-existent CLI subcommand (`openspec change new`) | Nothing — the AI self-recovered by mirroring an existing change dir | Prefer `mkdir -p openspec/changes/<name>` + copy a known change's layout when the CLI errors |
| Assume the repo's original single-package layout | Not needed; the AI detected the monorepo restructure on re-read | Note "repo is now a monorepo — read `packages/*`" up front on returning sessions |
| Treat a proposal-only sibling change as unbuilt | — | When a change looks done, grep the source first, then archive with `--skip-specs -y` instead of re-implementing |
| Scope creep risk on Electron | The human scoped it tightly: "gateway in Docker, dashboard stays the app" | State the target topology explicitly so the delta stays ~50 lines |

Key quality bar the human imposed: keep the Electron change **minimal and consistent across all four artifacts** — the AI updated proposal + design + specs + tasks together rather than just adding a task.

## 7. Pitfalls & dead ends

- **`openspec change new docker-packaging` → error.** Not a valid subcommand. *If you hit this:* run `openspec --help`, then `mkdir -p openspec/changes/<name>` and copy the file layout from an existing change (`ls openspec/changes/hide-debug-events/`).
- **Stale path assumptions after monorepo restructure.** `cat src/client/components/ServerSelector.tsx` and `ls openspec/changes/electron-desktop-bundle/` both failed because files had moved / been archived. *If you hit this:* `find . -name "<pattern>" | grep -v node_modules | grep -v archive` to relocate, and check `openspec/changes/archive/` for archived siblings.
- **Re-implementing an already-done change.** `hide-debug-events` looked pending but was fully coded (hook + ChatView filters + SettingsPanel toggle all present). *If you hit this:* grep the source to confirm before writing, then archive with `openspec archive <name> --skip-specs -y`.
- **4 of 47 bash commands failed** — all were the above discovery misses, cheaply recovered. None blocked progress.
