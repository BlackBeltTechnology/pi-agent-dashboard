# How we did it: Elevate the dashboard "add" buttons — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner
stance, explicitly *not* an implementation session. The real objective, which
crystallized over the steering turns: the dashboard's "add" affordances (pin a new
top-level folder, create a new workspace, add a folder to a workspace) were tiny,
scattered, and buried. A 10px `📌 Folder` text chip sat wedged between two search
inputs and the `Hidden` toggle in the sidebar header; a dashed `+ New workspace…`
button floated mid-list; a cramped `mdiPin` icon hid in each workspace header. The
goal was to **explore the design space and capture the decision as an OpenSpec
proposal** — unifying all three behind one prominent, full-width `+ Add Folder`
line-button treatment mirroring the existing `FolderSpawnButtons.tsx`. No application
code — proposal only.

## 2. TL;DR playbook

1. Enter explore mode with the `openspec-explore` skill — commit to *thinking*, not coding.
2. Ground the discussion in real sources: `grep` for the actual components
   (`FolderSpawnButtons.tsx`, `SessionList.tsx`, `WorkspaceHeader.tsx`) before drawing any design.
3. Have the AI render the **current** UI as an ASCII diagram, then the **target** — visualize before deciding.
4. Answer the AI's design questions tersely (`1. Replace / 2. yellow ok / 3. Yes`) to lock scope fast.
5. Steer naming and scope inline as they surface (`Rename Pin Folder to Add Folder`; "do it in the Workspace too").
6. When the design is stable, say `commit proposal` → AI scaffolds the OpenSpec change via `openspec new change`, writes proposal + specs + tasks, and runs `openspec validate`.
7. Align delta capability names to **real existing specs** (`sidebar-header`), not invented ones.
8. To land it: `commit to develop` — but expect the AI to detect **jj**, not plain git, and split cleanly.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground before design).** A one-shot `Explore` subagent
returned nothing, so the AI fell back to direct `grep`/`find` over `src/client`,
locating the three real affordances and the `FolderSpawnButtons.tsx` style to mirror.
*Why it worked:* every later design claim was anchored to a real file and handler
(`onOpenPinDialog`, `setNewWsOpen`, `onAddFolderViaPicker`), so nothing was invented.

**Phase 2 — Visualize the design space.** The AI drew the *current* sidebar as an
ASCII box diagram, then a *target* diagram, and surfaced multiple placements. The
human chose direction with a 3-line answer (`Replace / yellow / Yes`) and later locked
placement **B** (top of scroll list). *Decision points:* replace vs. keep the old
controls; button color; whether to proceed.

**Phase 3 — Scope expansion.** Two follow-ups widened the change: `Rename Pin Folder
to Add Folder` (label-only, action unchanged) and "in the Workspace also replace the
pin button." The AI folded the workspace-scoped `mdiPin` removal into the *same*
`dashboard-add-buttons` capability — one unified treatment across three affordances.

**Phase 4 — Generate the proposal.** On `commit proposal` the AI scaffolded the change
with `openspec new change`, wrote `proposal.md` + two delta specs + `tasks.md`,
verified capability names against real specs (`sidebar-header` documents the very
"Pin+ button" being removed), and ran `openspec validate` to green.

**Phase 5 — Land it through jj.** On `commit to develop` the AI discovered the repo is
managed by **Jujutsu (jj)**, and a *concurrent session* had wiped its untracked files
via a working-copy operation. It recreated all files, found them mixed into an
in-progress PR #85 fix commit, and used `jj split -o @-` to extract *only* the
openspec files into a clean commit, then fast-forwarded the `develop` bookmark — and
**stopped before pushing** because push affects everyone and the repo was in flux.

## 4. Prompts that worked

- **Goal prompt (the explore-mode kickoff):** invoking `openspec-explore` set the
  right stance — the AI read/searched/visualized but never wrote code, and captured
  the outcome as artifacts. A strong kickoff *names the mode* and *forbids
  implementation*, which this skill does automatically.
- **`1. Replace / 2. yellow ok / 3. Yes`** — high-leverage. Terse, numbered answers to
  the AI's own enumerated questions lock several decisions in one turn with zero ambiguity.
- **`Rename Pin Folder to Add Folder`** — a one-line correction that the AI correctly
  scoped to *label only* (action `onOpenPinDialog` unchanged), flagging the copy
  mismatch with the `PinDirectoryDialog` for later.
- **`In the Workspace also replace the pin button for very same Add folder`** — a
  scope expansion that unified a third affordance under the same treatment.
- **`commit to develop`** — trusted the AI to figure out the VCS; it detected jj and
  handled a race safely instead of blindly `git commit`.

*Rewrite of weak prompts:* `go on` / `Follow` are fine as continuations here, but a
future operator can compress the whole design phase by front-loading the constraints:
"Unify all dashboard-scope add affordances (header chip, mid-list dashed button,
workspace pin icon) into one full-width yellow `+ Add Folder` line button mirroring
`FolderSpawnButtons.tsx`; capture as an OpenSpec proposal, no code."

## 5. Steering & corrections (what to watch for)

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created — but two reusable patterns stand out:

- **`openspec-explore` as a design-capture front end.** It enforces think-don't-build
  and still lets you emit proposals/specs. Invoke it whenever a UI change needs a
  grounded proposal before any code. *It removes* the temptation to jump straight to
  edits and produces a validated, implementable `tasks.md` instead.
- **Ground-then-visualize discipline.** `grep` the real components, then draw
  before/after ASCII diagrams. Worth turning into a habit (or a small skill) for any
  sidebar/layout redesign — it keeps the proposal honest and the deltas accurate.

If this jj-under-a-shared-working-copy dance recurs, a **project skill** capturing
"detect jj → `jj split -o @-` to extract only your files → advance the bookmark →
don't auto-push a shared repo" would pay for itself.

## 7. Pitfalls & dead ends

- **The `Explore` subagent returned nothing** — don't block on it; fall back to direct
  `grep`/`find` over `src/client`.
- **Untracked files vanished mid-session.** The repo is **jj**-managed and a concurrent
  session ran a working-copy operation that wiped the untracked proposal files. *If you
  hit this:* recreate the files and commit *immediately* to shrink the window.
- **Recreated files landed mixed into another commit** (PR #85 CodeRabbit fixes + docs
  edits). *Fix:* `jj split -o @- -m "<msg>" <your-paths>` extracts only your files into
  a new commit on the parent, leaving unrelated work intact in `@`.
- **Invented capability names fail validation.** Check `openspec/specs/` first —
  `sidebar-header` was the real capability documenting the button being removed.
- **Don't auto-push a shared/in-flux working copy.** Advance the bookmark locally and
  ask before `jj git push`.
