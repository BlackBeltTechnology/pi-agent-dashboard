# How we did it: Generalizing worktree init into a gate + a project-init skill — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance,
not an implementation task. The first prompt was the skill's boilerplate ("Enter
explore mode. Think deeply… you must NEVER write code"), so the *real* objective
only crystallized through steering. It turned out to be two-fold:

1. **Generalize the narrow worktree-bootstrap** (`harden-worktree-spawn`) — which
   today only runs a package-manager install on new worktree creation — into a
   **project-defined init hook** driven by a bash **gate** (`exit 0 = needs init`),
   surfaced as an "Initialize" button that appears only when the gate says so.
2. **Add a second layer**: a pi-dashboard-delivered **project-init skill** that
   scaffolds greenfield directories (AGENTS.md, init hook, settings, prompts) using
   selectable **project profiles** (coding, docs, …). Elegantly, Layer 2's output
   *is* Layer 1's input — a configured project.

Output was **design artifacts only**: two OpenSpec change proposals, validated
`--strict`, committed. No application code.

## 2. TL;DR playbook

1. **Kick off in explore mode** with `openspec-explore` — keeps the AI in
   design/proposal territory, not implementation.
2. **Ground first**: have the AI read the existing mechanism (`harden-worktree-spawn`
   proposal, `bootstrap-install` + `git-operations-api` specs, the caller code) and
   diagram what exists today before proposing anything.
3. **Answer the AI's fork questions tersely** — numbered/lettered replies
   (`1. Manual button…`, `A needs init convention / B cache it / C show in a card`).
   Each answer collapses design ambiguity into a locked decision.
4. **Let the AI re-diagram after every batch of answers** — the ASCII/Mermaid
   redraw is the confirmation that your terse answers were understood.
5. **Expand scope deliberately** when the shape is clear ("also add a project-init
   skill with profiles…") — the AI will spot the Layer 2 → Layer 1 recursion.
6. **Say "both" / "settle B"** to authorize scaffolding once forks are resolved.
7. **Match existing OpenSpec format exactly**: scaffold dirs, then read a sibling
   change (`harden-worktree-spawn`) for proposal/design/tasks/spec-delta structure.
8. **Validate each change** `openspec validate <name> --strict` and **fix
   cross-change contradictions** (scope A to the hook-present case so B owns no-hook).
9. **Commit both proposals together** with a `docs(openspec):` message.

## 4. Prompts that worked

- **The goal prompt** — the `openspec-explore` skill invocation. *Effective because*
  it pinned the AI to a design/thinking stance, so it produced proposals not code.
  A stronger explicit kickoff for a repeat: *"Explore mode. I want to generalize the
  hardcoded worktree-bootstrap into a project-defined init hook (bash gate + script|agent
  run), plus a project-init skill that scaffolds greenfield dirs from profiles. Ground
  in `harden-worktree-spawn` first, then propose."*
- **High-leverage follow-ups** — terse decision tokens:
  - `A needs init convention / B yes. cace it / C yes, show in a card` — resolved
    three design forks in one line each.
  - `Settle B` / `both` — authorized generation without re-litigating.
  - `commit to git` — clean handoff to version control.
  *Why they worked:* the AI had already laid out lettered/numbered options, so a
  single letter carried a full decision. Terse answers + AI re-diagram = fast convergence.

## 6. Skills, tools & memory created — and why they're effective

No new skill/memory was created — the session's *output* was two OpenSpec change
proposals (the design artifacts themselves). But two reusable ideas were captured:

- **The gate-as-state pattern** (`gate: bash test, exit 0 = needs init`, cached,
  invalidated on run) — collapses detection + status-probe + idempotency into one
  project-defined primitive. Worth extracting into an architecture note.
- **The two-layer polymorphic Initialize button** (Layer 2 produces Layer 1's input)
  — a clean recursion pattern for "bootstrap the thing that bootstraps."

*Recommended skill to create:* a `scaffold-openspec-change-pair` procedure that
codifies "read a sibling change for exact format → write proposal/design/tasks/spec
deltas → validate `--strict` → reconcile cross-change contradictions → commit
together." It removes the format-matching and validation-snag rediscovery this
session paid for.

## 7. Pitfalls & dead ends

- **zsh glob failures** when hunting callers — the AI switched to `find`/explicit
  paths. If a glob fails, use `find … -type f` instead.
- **`openspec change new` scaffolds only `.openspec.yaml`** — no proposal/design
  templates. You must mirror a sibling change's structure by hand.
- **REMOVED spec-delta entries fail `--strict`** if the requirement isn't in the
  *baseline* spec. Here the bootstrap requirements lived only in the unarchived
  `harden-worktree-spawn` delta, so REMOVED had nothing to remove. Fix: drop REMOVED,
  keep ADDED + MODIFIED.
- **Cross-change contradiction**: two changes both touching `folder-action-bar` for
  the no-hook case. Resolve by scoping each change to a disjoint case (A: hook
  present; B: hook absent) so both validate independently.
