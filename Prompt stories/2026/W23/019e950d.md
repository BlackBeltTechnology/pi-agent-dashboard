# How we did it: Diagnose & spec the `@` file-mention dropdown ranking bug — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened **explore mode** (`openspec-explore`) with a bug report: typing `@`
in the chat composer's file-mention dropdown "does not show all matched files — only a
portion." The stated task was to *think*, not implement — trace the defect end-to-end and,
if warranted, capture the thinking as an OpenSpec change proposal. The real objective, once
the steering turns landed, was: **root-cause the truncation in the bridge's `searchFiles`,
prove it also breaks the bare-`@` and slashed-path (`@x/db`) cases, and produce a validated,
commit-ready proposal that redesigns the walk from "stop at first 20" to "walk-all → rank →
cap"** — all with zero source-code changes.

## 2. TL;DR playbook

1. **Enter explore mode explicitly** — `openspec-explore` skill. It hard-blocks
   implementation, so the AI stays in trace-and-propose mode and won't "fix" the code.
2. **Trace the data path, not the symptom.** Ask the AI to follow the `@` query from
   client → server → bridge. Here: `CommandInput.tsx` → `onListFiles` → server `list_files`
   → extension `searchFiles(cwd, query)`.
3. **Find the single cap.** The truncation was one constant: `MAX_RESULTS = 20` in
   `packages/extension/src/command-handler.ts:19`, with a DFS `walk()` that hard-stops the
   moment `results.length >= MAX_RESULTS`.
4. **Steer for the adjacent cases.** Prompt: *"Maybe the simple `@` also has this problem"*
   and *"When I type `@x/db` will it display the stuff under that path?"* — this forces the
   AI to test bare-`@` (worse: DFS drains all 20 slots into the first subtree) and slashed
   queries (path-substring match works, but ranking collapses).
5. **Scaffold by mirroring an existing change.** There is no `openspec change new`
   subcommand — the AI read a sibling change (`add-dashboard-slash-commands`) to copy the
   proposal/design/tasks/spec-delta layout exactly.
6. **Modify the existing capability spec.** A `file-autocomplete` spec already existed and
   *codified* the 20-cap — so the delta is `MODIFIED Requirements` (full text), not a new
   capability.
7. **Validate strict.** `openspec validate fix-file-mention-search-ranking --strict` → valid.
8. **Fold the slash-aware split into all four artifacts**, re-validate, then `commit`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / trace (client → server → bridge).**
The `Explore` subagent role failed to resolve, so the AI dropped to direct investigation:
grepped the client for the mention UI, found `CommandInput.tsx`, followed `onListFiles` to
the server `list_files` forward, and landed in the bridge's `searchFiles`. *Why it worked:*
it chased the *wire*, not the UI — the cap was "server-side-of-the-wire," invisible from the
client alone. The client renders the whole array it receives (no client-side slice), so the
defect had to be upstream.

**Phase 2 — Root cause.** One constant (`MAX_RESULTS = 20`) plus a depth-first `walk()`
that stops at the first 20 matches. Decision point: the human's *"maybe bare `@` too"* turn
exposed a **second** defect — with an empty query every entry matches, and DFS fills all 20
slots from the first subtree instead of top-level files.

**Phase 3 — Scaffold the proposal.** No generator subcommand exists, so the AI mirrored an
existing change's file structure and discovered a pre-existing `file-autocomplete` capability
spec that *codified the 20-cap*. Decision point: scope the change as a **modification** of
that capability (`MODIFIED Requirements`), not a greenfield spec.

**Phase 4 — Refine on the slash question.** The *"`@x/db`"* prompt exposed a subtlety: the
AI's basename-centric ranking never matches a slashed query (basenames have no `/`), so every
slashed result collapsed into flat path-substring order. The fix: **split the query at the
last `/`** — the prefix scopes the candidate set to that directory, the leaf ranks as a
basename inside it. This was folded across all four artifacts.

**Phase 5 — Validate & ship.** `--strict` validation passed twice (once before, once after
the slash fold). Final `commit` first silently failed (a hook reset the index); the AI
re-staged with `git add` and retried → `82a71b59` on `develop`, 4 files / +264, proposal-only.

## 4. Prompts that worked

- **Goal prompt (explore-mode kickoff).** Entering via `openspec-explore` was the highest-
  leverage move: it framed the whole session as *think-and-propose*, guaranteeing no code got
  touched. A future operator should do the same when the ask is "diagnose + spec," not "fix."
- **"yes. Maybe the simple `@` also have this problem"** — a 9-word follow-up that doubled the
  bug's scope and surfaced the *worse* bare-`@` DFS-starvation case. High leverage: it turned
  a single-symptom fix into a correct root-cause redesign.
- **"An when I type `@x/db` will display the stuff under path?"** — forced the AI to test its
  own ranking design against a real query shape and caught the basename-vs-path ranking gap
  *before* it was spec'd wrong.
- **"create propose"** / **"commit"** — terse unlock prompts; each cleanly advanced a phase.

Rewrite of the weak prompts a future user should prefer:
- Instead of *"Maybe the simple `@` also has this problem"* → **"Verify the empty-query
  (bare `@`) path uses the same cap and traversal order; show whether it's better or worse."**
- Instead of *"An when I type `@x/db`…"* → **"Trace how a slashed query (`@x/db`, `@x/db/co`)
  matches and ranks today, and whether the new ranking handles directory-scoped queries."**

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Fix only the reported symptom (dropdown truncation) | "Maybe the simple `@` also has this problem" | Prompt the AI to enumerate ALL query shapes (empty, plain, slashed) before designing the fix |
| Design basename-centric ranking that silently fails slashed queries | "When I type `@x/db` will it display stuff under path?" | State query-shape coverage as an acceptance criterion up front |
| Reach for a nonexistent `openspec change new` generator | (self-corrected) mirror an existing change | Note in the plan: no generator — copy a sibling change's layout |

The pattern: **the human's steering was almost entirely scope-widening** — "does defect X
also apply to case Y?" Each cheap question caught a real gap the AI would have spec'd wrong.

## 7. Pitfalls & dead ends

- **`Explore` subagent role didn't resolve.** Don't block on it — drop to direct
  investigation (grep the index / client, follow the wire).
- **No `openspec change new` subcommand.** If you reach for a generator, stop — mirror an
  existing change's directory layout instead.
- **A pre-existing capability spec can *codify the bug*.** The `file-autocomplete` spec
  literally said "display up to 20 entries." Always grep `openspec/specs/*/spec.md` for the
  behavior you're changing before writing a delta — scope it as `MODIFIED`, not new.
- **Basename-centric ranking silently ignores slashed queries.** If you rank on filename
  only, a `@x/db` query collapses to flat path order. Split at the **last** `/`: prefix =
  directory scope, leaf = basename rank.
- **The `git commit` silently no-op'd** (a hook reset the index). If a commit "didn't go
  through," re-run `git add`, re-check `git status --short`, then retry.
- **Stray `oldText2` in an edit.** When an edit misbehaves, re-apply cleanly rather than
  patching the patch.
