# How we did it: Turning "can we auto-build docs?" into a validated OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance, explicitly *not* an implementation session. The real question surfaced in the
second prompt:

> "Is it possible to make markdown-based documentation which is transformed with a
> deterministic build to web-browsed docs?"

The true objective, once the steering turns clarified it: **stand up end-user
documentation for pi-dashboard** — Markdown-authored, deterministically built to a
static site, skinned with the existing theme tokens, with **auto-generated,
reproducible light/dark screenshots** sourced from the ~280 OpenSpec capabilities —
and capture the whole plan as a validated OpenSpec change proposal (not code).

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore`) — state up front "capture thinking as an
   OpenSpec proposal, do not implement."
2. Have the AI **ground in reality first**: inspect the existing Astro site
   (`site/astro.config.mjs`, `package.json`, `src/content/features.ts`, existing
   `public/screenshots/`, and the `scripts/screenshots/capture.ts` pipeline).
3. Ask the deterministic-build question → let the AI map *what you already have* vs
   *what docs needs* (Astro static + MDX + Playwright were already present).
4. Feed the two constraint answers that pick the tool: **"search matters later"** +
   **"share only colors/fonts/CSS, not the look"** → lands on **Starlight skinned via
   CSS variables**.
5. Redirect scope to the real feature source: **"scan all features from openspec"** —
   forces the AI to confront that ~280 specs ≠ user-facing features and curate.
6. Add the two requirements that shape the screenshot axis: **new cutout screenshots**
   keyed on `data-testid`, and **light + dark** variants tied to the doc theme toggle.
7. Nail the definition of "reproducible" = *same declared capture targets every run*
   (a manifest), not byte-identical PNGs. This unlocks the single-registry insight.
8. `create proposal.` → AI writes `proposal.md` / `design.md` / `tasks.md` /
   `specs/.../spec.md`, then `openspec validate <change> --strict`.
9. Resolve the biggest open question inline ("Pagefind search now") — promote it from
   deferred to a first-class launch requirement across all four artifacts.
10. `commit changes to develop` — scope the commit to *only* the proposal files.

## 3. How the collaboration unfolded

**Phase 1 · Ground in reality (Discovery).** Before recommending anything, the AI ran
a burst of read-only `bash` scans: found Astro 5 `output: "static"`, `@astrojs/mdx`
installed, a Playwright `capture.ts` screenshot pipeline, 14 features in
`features.ts`, and committed screenshots. *Why it worked:* the recommendation was
anchored to "you're ~80% wired for this already," not a theoretical greenfield design.

**Phase 2 · Answer the real question + pick the tool (Design).** The deterministic
MD→HTML build question mapped cleanly onto Astro Content Collections. Two short human
answers — *search important later* + *only share colors/fonts/CSS* — were enough for
the AI to converge on **Starlight** (bundled Pagefind search, CSS-variable theming,
free sidebar/nav) and explain the `--pi-*` → `--sl-*` token skinning.

**Phase 3 · Reframe the content source (Gather).** "Scan all features for openspec"
blew the scope open: `openspec/specs/` held ~280 capabilities and 386 archived
changes. The key judgment call the AI surfaced: **specs are an engineering
decomposition, not a user's mental model** — so it split user-facing (terminal-emulator,
session-search, theme-gallery…) from internal (jiti-loader, ws-ping-pong…) and proposed
curating ~40.

**Phase 4 · Shape the screenshot pipeline.** Two additions — cutout crops and
light/dark — were checked against reality: the client already had **369 unique
`data-testid` values across 175 files** (cutouts feasible now), and `capture.ts`
already captured dark with an orphaned `desktop-light/` folder (light was half-built).

**Phase 5 · Converge on the core insight.** The human's precise definition of
"reproducible" (a declarative list of capture targets, extensible with sub-features)
unlocked the design's spine: **one hierarchical feature registry = single source of
truth for BOTH the docs structure AND the screenshot capture set.**

**Phase 6 · Generate + Verify.** `create proposal.` produced four artifacts;
`openspec validate add-end-user-docs --strict` → **valid**. A later turn promoted
Pagefind search to a launch requirement (edited all four files, re-validated). Final
turn committed only the proposal to `develop` (`c0003ef4`, 4 files, +275).

## 4. Prompts that worked

- **Goal prompt (explore mode).** Effective because it set a *stance* (think, don't
  build) and permitted capturing the result as an OpenSpec artifact — so the session
  ended with a validated proposal, not scattered code.
- **"Is it possible to make markdown docs with a deterministic build?"** — a crisp
  capability question. It let the AI answer with the existing stack rather than
  inventing one.
- **"Only colors, fonts, css" + "search important later"** — two-word constraints that
  *decided the tool*. High leverage: they collapsed a big design space to one choice.
- **"scan all features for openspec"** — redirected the content source from 14 landing
  cards to the real ~280-capability surface. This is the prompt that made the docs
  *complete* instead of a marketing rehash.
- **"I mean reproducible that when I execute script same screen areas… will be shot"** —
  clarified an ambiguous word and handed the AI the registry insight.

*Rewrite of a weak prompt:* instead of "Pagefind search now" (terse), a stronger
future prompt is *"Promote search from deferred to a launch requirement — update
proposal, design, tasks, and the spec delta, then re-validate strict."*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Scope docs to the 14 landing-page features | "scan all features for openspec" | State the real content source (openspec specs) in the goal prompt |
| Treat "reproducible screenshots" as byte-identical (a tar pit) | Redefining it as "same declared capture targets every run" | Define "reproducible = same manifest → same shots" up front |
| Recommend before grounding | (implicitly) — AI self-corrected by scanning first | Ask it to inspect the existing site/pipeline before recommending |
| Leave search as a deferred open question | "Pagefind search now" | Decide search-at-launch in the first design pass |
| Consider a single theme per run | Requiring light **and** dark tied to the doc toggle | List the full screenshot axis (theme × viewport × cutout) early |

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created — this was a pure explore→proposal session
under the existing `openspec-explore` skill. The reusable assets are the **OpenSpec
artifacts** themselves:

- `openspec/changes/add-end-user-docs/{proposal,design,tasks}.md` +
  `specs/end-user-documentation/spec.md` — 5 design decisions, a curated ~40-feature
  registry, 7 workstreams / ~25 tasks, 4 requirements / 9 scenarios, **validated
  strict**.

*What should be captured as a skill:* the **"docs-registry as single source of truth
for docs + screenshots"** pattern (one hierarchical registry drives Starlight sidebar
pages AND the Playwright capture set, walked over `[dark,light] × [desktop,mobile] ×
[full,cutouts]`). That is a repeatable design worth a project skill if a second
docs-plus-screenshots effort appears.

## 7. Pitfalls & dead ends

- **`Explore` subagent role failed to resolve** ("The Explore role can't resolve").
  The AI recovered by doing the curation inline (it already had the full spec list).
  → If a subagent role won't spawn, don't block — fold the work back inline when the
  data is already in context.
- **`ctx_batch_execute` reported 2 errors** during the gather phase — the AI fell back
  to plain `bash` scans. → Prefer direct `bash` reads for simple file inspection.
- **Staged noise at commit time.** The tree had unrelated staged `jj-workspace` skill
  renames. The AI scoped the commit explicitly (`git commit -o <the four proposal
  files>`) so only the proposal landed. → Always name the paths when the index is dirty.
- **Specs ≠ user features.** Blindly turning all ~280 openspec capabilities into doc
  pages would bury users in internal machinery. → Curate user-facing vs internal first.

## 8. Reproduce it faster — checklist

1. `openspec-explore` mode, stance stated: capture-as-proposal, no code.
2. AI scans existing site + screenshot pipeline before recommending.
3. Give the two tool-deciding constraints (search-later? theme-only skin?).
4. Point the content source at `openspec/specs/`; ask for a curated user-facing subset.
5. Define "reproducible" as *same declared capture targets each run* (a registry).
6. State the full screenshot axis: theme (dark+light) × viewport × full+cutouts, keyed
   on `data-testid`.
7. `create proposal.` → then `openspec validate <change> --strict`.
8. Resolve open questions inline (e.g. search-at-launch) and re-validate.
9. Commit ONLY the proposal files to `develop` (name the paths).
