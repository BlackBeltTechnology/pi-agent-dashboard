# How we did it: Relocate the ⚙ View menu into the StatusBar — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-only
stance where the AI investigates the codebase but never edits code. The real objective
emerged through steering: a small UI wart bugged the operator. The per-session display
popover (the `⚙ View` button) sat in its own **full-width toolbar row** at the top of
`ChatView`, wasting a whole horizontal band just to right-align a single button. The
operator wanted that button **moved down into the bottom StatusBar**, tucked between the
reload button and the model selector, and the wasted row deleted. The deliverable was
**not code** — it was a validated OpenSpec change proposal, committed to `develop`.

## 2. TL;DR playbook

1. Enter `openspec-explore` to trace the UI before proposing anything ("Enter explore mode. Think deeply.").
2. Let the AI locate the components: `ChatViewMenu.tsx` (the `⚙ View` popover) and its mount site (`ChatView.tsx:307`).
3. **Anchor the target concretely** — a screenshot region or exact bar name — because "between model and reload" is ambiguous (there are multiple reload buttons).
4. When the AI guesses the wrong toolbar, correct it hard and short ("No. The slot down!") until it finds the real `StatusBar` (bottom composer bar).
5. Say `create proposal` to have it scaffold an OpenSpec change under `openspec/changes/<name>/`.
6. Confirm it's an **ADDED requirement** (the spec didn't previously pin mount location) and let it write `proposal.md` + `specs/.../spec.md` + `tasks.md`.
7. Run `openspec validate <change> --strict` — the AI does this before declaring done.
8. Say `commit to git develop`; in this **jj-colocated repo** the AI uses jj (describe `@`, move `develop` bookmark, fresh working copy) — never mutating git.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore stance).** The AI stayed read-only. It first tried the
`Explore` subagent, hit a role-config issue, and fell back to grepping the file index and
`packages/client/src` directly. It located `ChatViewMenu.tsx` and the offending full-width
row at `ChatView.tsx:307`. *Why it worked:* the explore skill's hard "no edits" rule kept
the session focused on understanding the layout before touching anything.

**Phase 2 — Layout tracing (the hard part).** The AI produced ASCII diagrams mapping the
screenshot to real components: `SessionHeader` (Attach + `ElapsedBadge` "2m 21s" + refresh),
`TokenStatsBar` (the `1.0M` context bar), and the `ChatView` View row. It initially fixated
on `SessionHeader`'s reload button — the **wrong** toolbar. The operator's terse corrections
forced a re-search that surfaced `StatusBar.tsx`, which holds the `ModelSelector` and a
`leading` slot for the refresh button. *Decision point:* "The slot down!" told the AI the
destination was the **bottom** bar, not the top header.

**Phase 3 — Proposal generation.** On `create proposal` the AI inspected the OpenSpec setup,
found the existing `chat-display-preferences` capability owned the popover, and noted the spec
**did not** pin the mount location — so this became an **ADDED requirement**. It wrote three
artifacts and ran `openspec validate --strict`.

**Phase 4 — Commit.** On `commit to git develop` the AI detected `.jj`, chose jj over git,
described the working copy, moved the `develop` bookmark, and started a fresh empty working
copy. It flagged that `develop` was ahead of origin and **asked before pushing** rather than
pushing unprompted.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore` skill invocation).** Effective because it forces a
  read-only investigation stance — the AI can't jump to code and instead builds an accurate
  mental model first. A better explicit kickoff: *"Explore where the ⚙ View button mounts and
  where I could move it in the bottom StatusBar — don't edit code yet."*
- **`create proposal`** — a 2-word unlock that converted exploration into a concrete OpenSpec
  change. High leverage because the AI already had the full scope in context.
- **`commit to git develop`** — short, and the AI correctly self-detected the jj-colocated
  repo and adjusted its VCS commands.
- **Weak prompt to rewrite:** *"Only just that button be down down between the model selector
  and reload"* was ambiguous and mis-parsed. Stronger: *"Move `⚙ View` into the **bottom
  StatusBar's** leading slot, between the reload button and the model selector, and delete the
  full-width View row at the top of ChatView."*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Assume "reload" = `SessionHeader`'s refresh button (top toolbar) | "No. The slot down!" | Naming the exact bar (`StatusBar`, bottom composer) up front |
| Right-align the button "to the far right" of the header | "not to the far right… between the model and the reload button" | Pointing at a screenshot region, not relative words |
| Guess layout from grep output instead of confirming | Repeated terse corrections until it re-searched | Have it read the actual JSX/mount site before proposing placement |
| (Correctly) pause at VCS mutation | — | Keep this: it asked before `jj git push`, didn't push unprompted |

The recurring trap: **multiple "reload" buttons** exist (`SessionHeader` refresh, OpenSpec
refresh, `StatusBar` leading-slot refresh). Ambiguous positional language ("between X and Y")
is unreliable when the anchors are duplicated — always disambiguate by component/bar name.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created. The workflow leaned on existing assets:

- **`openspec-explore`** — the read-only thinking stance that kept the session from
  prematurely editing code; ideal when the operator is still deciding *what* to change.
- **`Explore` subagent** — attempted but hit a role-config issue; the AI degraded gracefully
  to direct grep. *Recommendation:* if `Explore` fails, don't retry blindly — fall back to
  `file-index-client.md` + scoped grep, as this session did.

**Skill worth creating:** a short **"anchor UI placement by component name, not position"**
guardrail — every UI-relocation session in this repo risks the duplicate-reload-button trap.

## 7. Pitfalls & dead ends

- **`Explore` subagent role-config error** → fall back to file-index grep; don't loop retrying.
- **Guessing the wrong toolbar** cost two steering rounds → read the JSX at the mount site
  and name the exact bar before proposing a destination.
- **2 failed bash commands** were grep pattern misfires (over-filtered `Attach`/paperclip
  search) → widen the pattern or grep the file directly rather than chaining `rg … | rg -v …`.
- **jj-colocated repo:** `git status` looks normal but `.jj` exists → use jj (`describe`,
  bookmark move, fresh working copy), never mutating git commands.
