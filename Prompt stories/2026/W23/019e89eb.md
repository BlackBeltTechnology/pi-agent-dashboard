# How we did it: Gate the context-usage bar independently — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The user opened with (two UI screenshots attached):

> "I would like that steh context bar drives the visibility the progress bar in
> content header, not the statistic enablement"

Decoded past the typos: the content-header **context-window progress bar** was
being shown/hidden by the wrong preference. It was gated on the **"Token stats
bar"** toggle, together with the butterfly chart + token counters. A separate
**"Context usage bar"** preference already existed in the data model (with toggles
in Settings *and* the per-session ChatView menu) but gated nothing. The real
objective: **split the gating** so the progress bar follows `contextUsageBar` and
the stats follow `tokenStatsBar`, each independently. The later steering turns
extended scope into: write an OpenSpec change, sync + archive it, then commit and
push cleanly.

## 2. TL;DR playbook

1. **Locate the component from the index first**, then read source: the progress
   bar lives *inside* `TokenStatsBar`, and `App.tsx` gates the whole component on
   one pref. Confirm `contextUsageBar` exists as a pref but wires to nothing.
2. **State the fix before editing:** add two independent gating props to
   `TokenStatsBar` (`showStats`, `showContextBar`), both defaulting to `true` for
   backward compatibility.
3. **TDD:** add the 3 new gating test cases first, then implement the split so
   they pass (hide stats / hide context bar / context bar only).
4. **Wire `App.tsx`** to derive each pref independently (`override ?? global ??
   true`) and mount `<TokenStatsBar>` when *either* is on.
5. **Verify client-only:** run the component tests + `npm run build`, then
   `POST /api/restart` if a dashboard is running.
6. **Formalize with OpenSpec** *after* the code lands: `openspec new change`,
   write proposal/tasks/spec-delta, `openspec validate --strict`.
7. **Sync the delta into the main spec, then archive** the change.
8. **Commit with jj (not git):** this is a jj-colocated repo — inspect state
   before acting, `jj split` your files into their own described commit, advance
   `develop`, `jj git push`.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created this session. The workflow, however, is a
clean repeatable pattern worth capturing:

- **A "split-a-pref-gate" recipe** — add independent boolean gating props
  (default `true` for back-compat), wire each to its own preference via
  `override ?? global ?? true`, mount the container when *any* region is enabled.
  Reusable anytime one toggle is overloaded to control two UI regions.

  by pasting the skill), plus the standard OpenSpec new/validate/sync flow. If this

## 7. Pitfalls & dead ends

- **jj-colocated repo, not git.** `git status` did *not* show the `App.tsx` change
  (already committed in a parent). If your edit "disappears," check `jj status` /
  `jj log` before concluding it's lost.
- **Shared/undescribed working copy `@`.** It contained unrelated in-progress work
  from other changes. Use `jj split <your-paths> -m "…"` to carve out exactly your
  files; the rest stays as the uncommitted child working copy.
- **Feature split across two commits.** The `App.tsx` wiring landed in an unrelated
  parent commit. Advancing `develop` to your commit carries the ancestor too —
  acceptable here because the feature *needs* that wiring to function.
- **Pre-existing `tsc` project-reference error** on the client — unrelated to the
  change; `npm run build` still succeeds. Don't chase it.
- **Pre-existing strict-spec warning** (`Missing ## Purpose` — the main spec's top
  header is `## ADDED Requirements`, present in HEAD). Leave it untouched to keep
  the sync surgical.
- **`Explore` subagent unavailable** (`@fast` role wouldn't resolve — roles plugin
  not loaded). Fall back to editing the docs-index row directly.
