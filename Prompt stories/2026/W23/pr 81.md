# How we did it: Rebasing a stale PR branch onto develop with conflicts — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator gave a two-word instruction: **`rebase develop`**. The `pr-81` worktree
branch was **3 commits ahead / 23 behind** `develop` and carried an *uncommitted*
local `.pi/settings.json` tweak (an absolute `source` path). The real objective, once
the work unfolded, was: **cleanly rebase `pr-81` onto the moved `develop` tip,
resolve every conflict by preserving intent (not just picking a side), and restore
the local uncommitted settings edit afterward without losing it or clobbering
develop's new `worktreeInit` block.** A late follow-up (`Is it possible that the
worktree base be os/add-ctx-tool-renderer`) asked whether the branch could be
re-pointed at a different base — a scope-probe, not a new task.

## 2. TL;DR playbook

1. **Survey first.** `git status && git branch --show-current && git log --oneline -5`,
   then compare against the remote: `git fetch origin && git rev-list --left-right --count pr-81...origin/develop`.
2. **Protect uncommitted work.** Stash the dirty file *by path* before rebasing:
   `git stash push -m "pre-rebase settings" .pi/settings.json`.
3. **Rebase and let it stop:** `git rebase develop` — read the conflict list, don't panic.
4. **Resolve by intent, not by side.** For each conflict, ask *what did this commit
   mean to do* — a rename/delete that develop already performed becomes a no-op (keep
   develop's version); a doc/code row that both sides extended should keep **both** additions.
5. **Continue non-interactively:** `git add <resolved> && GIT_EDITOR=true git rebase --continue`.
6. **Restore the stash and merge it by hand** if it conflicts — keep *your* local edit
   AND upstream's new block; don't let `--theirs` overwrite your merged file.
7. **Verify position:** `git rev-list --left-right --count pr-81...develop` should read
   `N ahead / 0 behind`, and `git status --short` should show only the intended
   uncommitted working-tree edit.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (survey the divergence).** The AI ran `git status`, `git branch`,
`git log`, then fetched origin and computed the exact ahead/behind counts. This is the
effective bit: *never rebase blind*. It found the 3/23 split and, critically, spotted
the uncommitted `.pi/settings.json` edit that a naive rebase would have refused or lost.

**Phase 2 — Protect and rebase.** It stashed only the dirty file (path-scoped stash,
not a blanket `git stash`), then launched `git rebase develop`, which immediately hit
conflicts. Path-scoped stashing keeps the rest of the tree pristine and makes the later
pop surgical.

**Phase 3 — Resolve three conflicts by intent.** The decision points that mattered:
  - **`wire-tool-renderer-slot` rename/delete** — the incoming commit `1af6df61` existed
    to *delete* the active openspec scaffold. Develop had already **archived** it
    (renamed to `archive/2026-06-05-…`). The AI recognized the intent was already
    satisfied, so it kept develop's archived files and let the commit collapse to a no-op.
  - **`docs/file-index-client.md`** — both sides added a row. Develop's `ToolCallStep.tsx`
    row was richer (it carried the plugin-slot logic); the incoming side added a new
    `CtxToolRenderer.tsx` row. Resolution: **keep both rows**, not one.
  - **`ToolCallStep.tsx`** (code) — auto-merged cleanly once the docs were sorted.

**Phase 4 — Restore local work.** `git stash pop` conflicted because develop had *also*
touched `settings.json` (added a `worktreeInit` block). The AI merged by hand to keep
**both** the local absolute-`source` tweak and the upstream `worktreeInit`. A misstep
here (`git checkout --theirs`) briefly overwrote the merged file with the stash version,
dropping `worktreeInit`; the AI caught it and rewrote the correct merged content.

**Phase 5 — Verify.** Final check: `pr-81` is **2 ahead / 0 behind** develop, with only
the intended uncommitted settings edit remaining. It reported the final 3-commit history
and flagged that `add-ctx-tool-renderer/tasks.md` had also been modified during the rebase.

## 4. Prompts that worked

- **The goal prompt — `rebase develop`.** Terse but sufficient *because the AI treated it
  as "rebase safely and preserve my uncommitted work"* rather than a mechanical
  `git rebase`. A stronger version for a future operator: *"Rebase `pr-81` onto
  `develop`; I have an uncommitted `.pi/settings.json` edit — stash it, resolve
  conflicts by preserving intent, then restore my edit merged with any upstream change."*
- **High-leverage follow-up — `Is it possible that the worktree base be os/add-ctx-tool-renderer`.**
  A scope-probe that let the operator confirm the branch topology without committing to a
  re-base onto a different parent. Effective as a *question* — it kept the completed
  rebase intact while exploring an alternative.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session. The workflow is, however, clearly
repeatable and worth capturing. **Recommended skill: `rebase-preserving-dirty-tree`** —
a procedure that (1) path-scoped-stashes uncommitted edits, (2) rebases, (3) resolves
conflicts by *intent* (rename/delete already-done → no-op; additive index rows → keep
both), (4) pops the stash and hand-merges when upstream also changed the file, and
(5) verifies with `git rev-list --left-right --count` + `git status --short`. It would
remove the repeated manual reasoning and the `--theirs` foot-gun shown here.

## 7. Pitfalls & dead ends

- **`git checkout --theirs` on a hand-merged file destroys your merge.** After you've
  manually reconciled a conflicted file (keeping both sides), do NOT run `--theirs`/`--ours`
  — it overwrites your work with one raw side. Edit the file directly and
  `git reset -q <file>` to clear the index conflict while keeping your working-tree version.
- **A blanket `git stash` is riskier than a path-scoped one.** Stash only the dirty file
  (`git stash push <path>`) so the pop is surgical and can't drag unrelated changes.
- **The failed final command** (`git worktree list … | grep -i 'ctx\|os/'`) was an
  exploratory probe for the follow-up question about re-basing — a dead end, not part of
  the rebase. It did no harm.
- **Rebasing can silently modify sibling files** — `add-ctx-tool-renderer/tasks.md` was
  changed as part of a replayed commit. Always diff the full commit range afterward, not
  just the files you resolved.
