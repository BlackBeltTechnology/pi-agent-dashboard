# How we did it: Placeholder card for Worktree session create — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance, explicitly *no implementing*. The real objective, once framing settled: figure
out **why spawning a normal session shows an instant placeholder skeleton card but
spawning a worktree session shows nothing**, then design a fix and capture it as an
OpenSpec change proposal (not code). The finished artifact was a validated,
committed `add-worktree-spawn-placeholder-card` proposal on `develop`.

## 2. TL;DR playbook

1. Enter explore mode with `openspec-explore` — commit to *think, don't implement*.
2. Ask the AI to **trace the placeholder mechanism end-to-end**: where the optimistic
   card is born on normal spawn vs. the worktree spawn path.
3. Let it delegate a read-only `Explore` subagent to locate the card + spawn flow, then
   grep `spawningCwds` / `setSpawningCwds` / `createWorktree` to pin the exact lines.
4. Have it explain the root cause in a diagram (normal cwd = existing folder group;
   worktree path = brand-new dir that no group renders under).
5. Answer the two design forks in one terse turn (`1. Dialog submit` / `2. yes`) to
   lock **Option A refined**: key the placeholder on the *parent* cwd, fire from dialog
   submit.
6. Say `create proposal` → AI reads the existing `placeholder-spawn-card` spec, scaffolds
   `openspec/changes/add-worktree-spawn-placeholder-card/` (proposal + tasks + 2 spec
   deltas), and `openspec validate --strict`.
7. Say `commit` → single `docs(openspec):` commit, implementation deferred.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (trace the mechanism).** The AI started from `docs/file-index*.md`,
then grepped the client/server source for `placeholder|optimistic|spawningCwds`. It
delegated one `Explore` subagent ("Find placeholder card and session creation flow") to
map the code, then read `App.tsx` / `SessionList.tsx` sections directly. *Why it worked:*
index-first, subagent for breadth, direct read only for the 3 files that mattered — cheap
and precise.

**Phase 2 — Root-cause the asymmetry.** It distilled the finding to one fact: the
placeholder is keyed entirely by **cwd** in a single `Set<string>` `spawningCwds`, and
only renders inside a folder group whose `group.cwd` is in the set
(`SessionList.tsx:712`). Normal spawn's cwd *is* an existing group → card shows. Worktree
spawn's path is a **brand-new dir** no group renders under → homeless placeholder, nothing
shows. Delivered as an ASCII flow diagram. *Decision point:* the human now had a clean
mental model to choose a fix.

**Phase 3 — Design fork.** The AI surfaced options; the human answered `1. Dialog submit`
+ `2. yes` in one line. The AI recognized both answers collapse to **Option A refined**:
key the placeholder on the resolved **parent cwd** (via the same
`pin > jjState.workspaceRoot > gitWorktree.mainPath > cwd` precedence the real card uses),
firing `onSpawnStart(parentCwd)` from dialog submit and `onSpawnAbort` on `createWorktree`
failure. Disabling the parent `+Session` button came *for free* from `spawningCwds.has(group.cwd)`.

**Phase 4 — Capture as a proposal.** `create proposal` → it read the pre-existing
`placeholder-spawn-card` spec (noting drift: spec describes a `requestId`-keyed
`pendingSpawns` model vs. the live `spawningCwds` Set), copied an example change's layout,
and scaffolded proposal.md, tasks.md (6 TDD-ordered groups), a MODIFIED
`placeholder-spawn-card` delta and an ADDED `worktree-spawn-dialog` delta. `openspec
validate --strict` passed.

**Phase 5 — Commit, stop at the boundary.** `commit` → one `docs(openspec)` commit
(`21232dad`). The AI explicitly held the line: nothing implemented, next step is
`openspec-apply-change`.

## 4. Prompts that worked

- **Goal prompt (explore mode):** launching via `openspec-explore` set the *think-don't-build*
  guardrail up front, so the AI traced and designed instead of editing code. Effective
  because the stance is baked into the skill — no need to repeat "don't implement."
- **`1. Dialog submit` / `2. yes`** — a two-token high-leverage follow-up that resolved
  the entire design (timing + button behavior). Effective because the AI had already framed
  the forks as numbered options; the human just picked.
- **`create proposal`** then **`commit`** — minimal control tokens that advanced through
  scaffold → validate → commit. Worked because the workflow (openspec change layout,
  validation, conventional commit) was already known to the AI.

*Stronger rewrite of the terse steering:* instead of bare `commit`, a future operator can
say `commit as docs(openspec) and stop before apply` to make the boundary explicit.

## 7. Pitfalls & dead ends

- **Spec drift:** the on-disk `placeholder-spawn-card` spec describes a `requestId`-keyed
  `pendingSpawns` model, but the live code uses a `spawningCwds` Set. If you hit this, write
  the delta against *live* behavior and note the drift — don't assume the spec is current.
- **One failed command** (`cat openspec/specs/placeholder-spawn-card/spec.md` combined with a
  project.md read) — the path/format assumption was off. If a combined `cat` fails, split it
  and read the example change layout separately (which is what unblocked the scaffold).
- **Premature `commit`:** committing while still exploring is a no-op (clean tree). Reach
  `create proposal` first so there are files to commit.
