# How we did it: Redesigning the ask_user question cards — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation task: *"Enter explore mode. Think deeply. Visualize freely. Follow the
conversation wherever it goes."* No concrete target was stated in prompt 1.

The **real objective** surfaced through the steering turns: the dashboard's `ask_user`
interactive cards have two live, observable usability problems — long option labels wrap
into an unscannable mess (`select`/`multiselect` render as horizontal flex-wrap buttons),
and answered cards collapse to only the picked value, discarding the context of *what the
choices were*. The goal became: **explore a redesign, mock every state faithfully against
real theme tokens, settle five design decisions, and land a single OpenSpec proposal** —
without writing any implementation code.

## 2. TL;DR playbook

1. Start in `openspec-explore` mode. Ground first: map the codebase, read the actual
   renderer components (`packages/client/src/components/interactive-renderers/`), and
   check the live dashboard `/api/health`.
2. Find a **live example of the bug** — open a real "Waiting for input" session (view-only)
   to see the exact broken `select` card you are redesigning against.
3. Pull the **real theme tokens** (`--bg-*`, `--border-*`, `--text-*`, accent) with `rg`
   so mockups are faithful, not invented.
4. Build **static HTML mockups** in `/tmp` (single-question cards + batch wizard),
   screenshot them through the browser tool.
5. When the human says the mockups miss the mark, **serve them** (`python3 -m http.server
   8899`) with an `index.html` so they can click through live on desktop/phone — then
   iterate one decision at a time.
6. Capture each settled decision inline as a quoted **Decision** block as you go.
7. On "stop and create one proposal", study the OpenSpec format (there is **no
   `openspec change new`** — scaffold manually), persist the mockups into the change
   folder, write proposal/design/tasks + spec deltas, and `openspec validate --strict`.
8. Commit only the proposal files.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / Ground (01:40–01:41).** The AI launched parallel investigations,
hit tool guards, and adapted. It located the interactive renderers under `packages/client`
(not `src/client`), read `ConfirmRenderer`/`SelectRenderer`/`InputRenderer`/
`MultiselectRenderer`/`EditorRenderer`/`NotifyRenderer` wired through `registry.ts`, and
discovered **the critical architectural fact**: there is *no `batch` renderer*. Batch is
decomposed on the bridge side (`ask-user-tool.ts`) into a sequential loop of blocking
`await ctx.ui.X()` calls — the client only ever sees one independent card at a time.

- **What worked:** grounding in the *real* component tree and the *live* bug before drawing
  anything. Opening a pending session (view-only) gave the exact defect to design against.

**Phase 2 — Design / Mock (01:42–01:46).** The AI grabbed the exact theme tokens, built
faithful dark-theme HTML mockups, and screenshotted them. When told the mockups missed the
vision, it did **not guess** — it served them on port 8899 with a LAN link so the human
could click through on a phone.

- **Decision point:** the human requested a live server rather than more screenshots.

**Phase 3 — Iterate one decision at a time (01:49–02:31).** This is where the value was.
Each short steering prompt settled exactly one thing; the AI updated the mockup, re-synced
the served copy, and reflected the decision back as a quoted block:
1. Confirm → **Yes / No** (not Allow/Deny) — matches the tool's generic-question semantics.
2. **Answered cards keep full context** — all options stay, dimmed, pick(s) highlighted.
3. Input answered → **read-only value field**, with a distinct `(left blank)` state.
4. **Many options shown in full** — no collapse, no `+N more` expander.
5. **Batch = wizard** (stepper, Back/Next, Review+Edit) and a multiselect step yields
   *multiple* answers rendered as pills throughout in-progress / review / answered states.

**Phase 4 — Generate proposal (02:31–02:35).** On "stop and create one proposal", the AI
stopped the server, learned the OpenSpec layout is manual (no `change new`), read the
`interactive-renderers` capability and the bridge batch dispatch to write precise deltas,
persisted the mockups into the change's `mockups/`, wrote proposal/design/tasks + 2 spec
deltas, and passed `openspec validate --strict`.

**Phase 5 — Commit (02:35).** Staged only the proposal files, committed `baf5082d` on
`develop`, clean tree.

## 4. Prompts that worked

- **Goal prompt (the explore-mode preamble):** effective because it set a *stance* — think,
  don't implement — which let the AI freely investigate and mock without prematurely
  writing code. A stronger version would name the surface up front:
  *"Explore a redesign of the ask_user interactive cards; the long-label wrap and the
  answered-card context-loss are the two bugs to fix."*
- **High-leverage follow-ups (each one settled a whole decision):**
  - *"Maybe better the Allow be Yes and Deny be No — what do you think?"* — turned a wording
    nit into a documented default.
  - *"Currently the answered cards only shows the selected answers and does not seen the
    whole options"* — surfaced the core context-loss bug in one line.
  - *"many options be shown as asked"* — closed the last open design question decisively.
  - *"stop and create one proposal"* — the clean hand-off from explore → capture.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Screenshot mockups the human couldn't feel | "serve it so I can click through" (implied) | Serve mockups on a LAN port by default when a human is reviewing UI |
| Default confirm to permission wording (Allow/Deny) | "Maybe better the Allow be Yes and Deny be No" | Treat `ask_user` confirm as a generic yes/no question; reserve Allow/Deny for real permission gates |
| Collapse answered cards to the picked value | "answered cards only shows the selected answers, not the whole options" | Rule: answered cards collapse in *emphasis*, not *information* — keep the full option set |
| Consider collapsing long option lists (>6/10) | "many options be shown as asked" | Always render the full list; no `+N more`, no folding |
| Show only single-answer wizard steps | "in batch ask_user multiple answers can be made" | A batch step can be multiselect → render multiple answers as pills everywhere |
| Keep exploring past the settled design | "stop and create one proposal" | Watch for the explore→capture hand-off signal and stop mocking |

## 7. Pitfalls & dead ends

- **Wrong path assumption:** the client lives under `packages/client`, **not** `src/client`.
  Early `rg` against `src/client/...` returned nothing; adapt to the monorepo layout.
- **Parallel helper guards:** the opening batched investigation (`ctx_batch_execute`) and a
  combined health/openspec command hit guards/failed — the AI fell back to smaller targeted
  `bash` calls. Don't over-batch the first probe.
- **No `openspec change new`:** OpenSpec changes are scaffolded *manually* (`mkdir -p` the
  `changes/<name>/specs/<capability>/` tree). Study an existing change (e.g.
  `elevate-folder-spawn-buttons`) for the proposal/tasks format first.
- **Atomic edit failure:** one mockup `edit` failed because the badge match wasn't unique/
  applied — redo with a smaller, unique match string.
- **Browser scroll got stuck** in empty space when capturing answered sections — reload the
  page fresh and re-screenshot rather than fighting the scroll position.
- **Keep the served copy in sync:** the source mockup lived in `/tmp/ask-user-mockup.html`
  while the served copy was `/tmp/ask-user-mockups/mockup.html`; every edit needed a `cp`
  re-sync. Serve directly from the edited file to avoid this.
