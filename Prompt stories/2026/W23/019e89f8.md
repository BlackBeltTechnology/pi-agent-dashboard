# How we did it: Design a `ctx_*` tool-result renderer — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill): *"Enter explore mode.
Think deeply… You may read files, search code, and investigate the codebase, but you must
NEVER write code or implement features… You MAY create OpenSpec artifacts."* The real
objective, once steering clarified it: the dashboard client renders `ctx_*` MCP tool calls
(`ctx_execute`, `ctx_search`, `ctx_batch_execute`, …) as a **raw JSON dump** because those
tool names have no entry in the client's renderer registry. The goal was to **investigate
why, design a proper card renderer, and capture it as a validated OpenSpec change
proposal** — thinking captured as artifacts, not code written.

## 2. TL;DR playbook

1. Kick off with `openspec-explore` so the AI investigates without prematurely writing code.
2. Point it at **real evidence**: have it harvest actual `ctx_*` request/response records from the on-disk session JSONL store (`~/.pi/agent/sessions/**/*.jsonl`), not guesses.
3. Let it map the wire shape (`toolCall` item → `toolResult` message) **and** the current render path (`getToolRenderer` → `registry.ts` Map → `GenericToolRenderer` JSON fallback).
4. Steer the design with 3 crisp answers: **one renderer** (not seven), **parse the structured text**, and **verify the `details` field** is really empty before committing to a text grammar.
5. Say `create proposal` — the AI matches existing OpenSpec conventions (`.openspec.yaml`, proposal/design/tasks + spec delta) and validates `--strict`.
6. Say `Resolve the 3 open questions` — force every open question into a **binding decision anchored to a spec scenario**, not loose prose.
7. Say `commit to git develop` — in this **jj-colocated** repo the AI must use `jj`, commit only its own paths, and leave unrelated uncommitted work untouched.

## 3. How the collaboration unfolded

**Phase A — Evidence gathering (the strong bit).** `session_search` returned nothing, so the
AI pivoted to reading the raw session store on disk. Using ~31 `ctx_execute` sandbox runs it
harvested representative `ctx_*` call+result pairs across **112 session files / ~2,150 calls**,
discovering the record shapes: an assistant `content[]` item `{type:"toolCall", name:"ctx_…",
arguments}` paired with a `{role:"toolResult", content:[{type:"text",text}], details, isError}`
record. It also captured the *distinct output grammars* per tool (summary lines, batch/search
accordions, `intent` auto-index output, validation/timeout/no-result errors).

**Phase B — Grounding in the render pipeline.** The `Explore` subagent role wasn't available, so
the AI located the renderer directly via the file-index: `ToolCallStep → getToolRenderer →
registry.ts` (has `read/edit/write/bash/Agent/ask_user`; `ctx_*` absent) → falls through to
`GenericToolRenderer` which `<pre>`-dumps `JSON.stringify(args)`. That is the entire bug surface.

**Phase C — Design lock-in.** Human steered `1. one renderer / 2. yes, scan structured / 3. check
it.` The AI verified point 3 empirically: `details === {}` on **2,155/2,155** results — no
machine-readable payload exists, so the card must parse the **text** with a regular grammar that
**fails soft** to `{kind:"raw"}`.

**Phase D — Proposal generation.** On `create proposal`, the AI read an existing change to match
conventions exactly, identified the target capability (`tool-renderers`), and wrote 5 artifacts
(additive spec delta: 1 MODIFIED + 2 ADDED requirements, 18 scenarios), validating `--strict`.

**Phase E — Resolve + commit.** `Resolve the 3 open questions` turned each into a binding decision
tied to a scenario. `commit to git develop` was executed via `jj`, committing only the 5 proposal
files and protecting a co-worker's unrelated uncommitted `relocate-view-menu-to-status-bar` files.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore`)** — effective because it puts the AI in *investigate-and-capture-artifacts* mode: it gathered real evidence and produced a proposal without prematurely coding.
- **`1. one renderer / 2. yes, scan structured / 3. check it.`** — a 3-token high-leverage reply that collapsed a whole design space (one vs. seven renderers; structured-field vs. text parse; and *verify your assumption*).
- **`create proposal`** — short unlock; the AI already had convention knowledge and evidence, so one word produced 5 validated artifacts.
- **`Resolve the 3 open questions`** — forces closure: converts "open questions" into binding, testable decisions.
- **`commit to git develop`** — scoped, deliberate; the AI stopped at commit (didn't push) because that's exactly what was asked.

*Rewrite for next time:* replace `3. check it.` with `3. verify details is actually empty across many results before assuming a text grammar` — same intent, states the assumption to test.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session, but the workflow is highly repeatable:

- **`openspec-explore`** (used) — the right kickoff for "investigate + capture as a proposal without coding." Invoke whenever you want thinking captured as OpenSpec artifacts.
- **Worth creating:** a skill *"map a tool's wire shape from the session JSONL store"* — the reusable move of harvesting real `toolCall`/`toolResult` records across `~/.pi/agent/sessions/**/*.jsonl` to ground a renderer/parser design in evidence instead of guesses. It removes the manual JSONL spelunking and makes the grammar derivation reproducible.

## 7. Pitfalls & dead ends

- **`session_search` returned nothing** → don't stop; the raw session JSONL store on disk is the real evidence source. Read files directly.
- **`Explore` subagent role unavailable** → fall back to the file-index to locate the renderer instead of relying on a subagent.
- **Assuming `toolResult.details` carries structure** → it's `{}` on every one of 2,155 results. Verify before designing; the card must parse the `text` string, with a **raw fallback** that never throws.
- **jj-colocated repo** → mutating `git` commands are wrong here; use `jj`, and the working copy `@` may mix your files with others' uncommitted work — commit only your explicit paths.
