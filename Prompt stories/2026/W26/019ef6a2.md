# How we did it: Unblocking dashboard "can't start a new session" — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened as routine ops: `full rebuild and deploy`. That first prompt was
not the real objective — it was the warm-up. The session drifted through a plugin
audit and a `develop` rebase, then landed on the actual problem five prompts later:
`Could not able to start a new session`. The **real goal** that emerged: figure out
why clicking **"+ New session"** in the dashboard yields a yellow
`spawn_register_timeout` banner and no session card — and fix it so fresh sessions
spawn again. The answer turned out to be a *broken upstream extension release*
(`pi-web-access@0.12.0`) crashing every fresh `pi --mode rpc` at startup, masked by a
genuinely overloaded box.

## 2. TL;DR playbook

1. **Reproduce server-side, not via the UI.** `curl -X POST /api/session/spawn` with a
   real cwd, then poll `/api/health` for `server.activeSessions`. If the count doesn't
   climb, the spawn is really failing — not just a slow-rendering card.
2. **Separate overload from a code bug.** Check `uptime` load average, count live pi
   processes (`pgrep -f 'pi-dashboard:openspec-poll' | wc -l`), and read server RSS. High
   load can *defeat the registration watchdog* independently of any bug.
3. **Clear the noise first.** Kill runaway keeper subtrees (keeper **+** child together —
   the RPC keeper respawns a lone-killed child), restart the server, bump
   `spawnRegisterTimeoutMs` to 90000 in `~/.pi/dashboard/config.json`.
4. **Re-test.** If spawn *still* fails with load now low, it is a real bug — not overload.
5. **Read the keeper log,** not the server log:
   `~/.pi/dashboard/sessions/keeper-<transport-id>.log`. It records `pi exited code=1
   elapsed=…ms` — the smoking gun the server log hides.
6. **Reproduce pi's crash by hand** with output capture on:
   `NODE=~/.pi-dashboard/node/bin/node; $NODE <cli.js> --mode rpc` in the failing cwd to
   capture the extension load error.
7. **Fix the extension version.** Pin the broken global extension to its last-good version
   in `~/.pi/agent/npm/package.json`, reinstall with `--legacy-peer-deps`, verify pi exits 0.
8. **Confirm end-to-end:** one more `/api/session/spawn` should register in ~4 s.

## 3. How the collaboration unfolded

**Phase A — Routine deploy (prompts 1, 4).** Twice the operator asked for
`full rebuild and deploy`; the AI ran build → `/api/restart` → `npm run reload` and
reported health. Reload raced the restart the first time and succeeded on retry — a
recurring, benign timing quirk worth expecting.

**Phase B — Side quests (prompts 2, 3).** A plugin-requirement audit (`/api/health`
plugin dump) and a "is kb active?" check. Useful hygiene, but not the main thread.

**Phase C — The risky rebase (prompt 4: "rebease to develop").** The operator was
already *on* `develop`, with uncommitted changes. The AI paused to inspect git state
before touching history — correctly. Mid-rebase, a **concurrent `_cq_probe` checkout
from another pi session sharing the same working tree** stomped the rebase into a
detached HEAD. The AI recovered via reflog (nothing lost), redid the rebase in one
tight shell sequence to minimize the concurrency window, and restored the working
changes. Decision point: *history ops in a shared working tree are dangerous.*

**Phase D — The real investigation (prompts 5–6).** After the second deploy, the
operator reported new sessions wouldn't start. The AI worked the funnel: server log →
spawn route → **reproduce via API**. The spawn returned success but `activeSessions`
stayed flat — proving the failure was real and *post-launch*. It first over-attributed
the cause to system overload (24 live pi procs, load ~14, server RSS 2.2 GB, an
automation re-arm hot loop, 4.6 s openspec-poll ticks) and remediated that. **Crucially,
after clearing the load the spawn still failed** — which reclassified it from "overload"
to "real bug."

**Phase E — Root cause (still prompt 6).** The AI read the **keeper log**
(`keeper-<id>.log`) and found `pi exited code=1 elapsed=4018ms`. Reproducing `pi --mode
rpc` by hand surfaced the crash: `pi-web-access@0.12.0` imports
`@earendil-works/pi-ai/compat`, a subpath the bundled `pi-ai@0.78` does not export.
Node resolved `dist/index.js` then appended `/compat` → module-not-found → extension
load failure → pi exit 1 → never registers → watchdog fires. The version was installed
*13 minutes before* the symptom — time-correlated. Fix: pin `pi-web-access` to 0.10.7,
reinstall `--legacy-peer-deps`, verify pi exits 0 and a dashboard spawn registers in 4 s.

**Phase F — Capture & handoff (prompt 7).** The operator hit a separate `pi update pi`
error; the AI explained the pnpm-global install path and clarified the global CLI (0.74.0)
is a *different* pi from the dashboard's bundled 0.78.0.

## 4. Prompts that worked

- **The goal prompt that actually mattered — `Could not able to start a new session`.**
  Short and vague, but it flipped the session onto the real problem. A stronger version
  a future operator should use: *"New session button gives a yellow
  spawn_register_timeout, no card — diagnose whether it's overload or a spawn bug and
  fix it."* — names the symptom + the fork the AI must resolve.
- **`rebease to develop`** (typo for rebase) — worked because the AI *refused to run
  blind*: it inspected git state and flagged the ambiguity ("you're already on develop")
  before acting. The lesson: on history-rewriting asks, the effective move is the AI's,
  not the prompt's — state up front *"inspect state and confirm before touching history."*
- **`full rebuild and deploy`** — a good repeatable kickoff *because the project workflow
  is codified*; the AI knew build → restart → reload without further instruction.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat "rebase to develop" literally while already on develop | (implicit) — AI self-caught and asked | State the *intent* ("sync my local develop onto origin") not the git verb |
| Attribute the spawn failure to system overload and stop there | Persisting — the symptom survived the load fix | Always re-test after remediation; "load is high" ≠ "load is the cause" |
| Look in the server log for the spawn crash | — | Go straight to `~/.pi/dashboard/sessions/keeper-<id>.log` for the pi exit code |

Scope also expanded mid-session: the "duplicate session pairs" the operator worried about
were a **red herring** — distinct UUIDv7 sessions spawned milliseconds apart share only
the timestamp prefix. Don't chase apparent duplicates without matching UUIDs to live PIDs.

## 7. Pitfalls & dead ends

- **Server log is the wrong place** for a fresh-spawn crash. The pi exit code lives in the
  per-transport `keeper-<id>.log`; the server log only shows the watchdog timing out.
- **`git stash` "Entry not uptodate"** during the rebase — a concurrent process was
  touching the same files. A **temporary WIP commit** is cleaner than stash for rebasing in
  a shared working tree; `git update-index -q --refresh` clears a stale stat cache.
- **History ops in a shared working tree are hazardous.** Another pi session's `_cq_probe`
  checkout stomped the rebase mid-flight. Recover via reflog; redo the rebase in one tight
  shell sequence to shrink the concurrency window.
- **`pi-web-access@0.12.0` is broken and still npm `latest`.** Don't blindly install/update
  it against `pi-ai@0.78` — it crashes every fresh spawn. Pin 0.10.7.
- **`0.10.7` needs relaxed peers** — install with `--legacy-peer-deps` (the original tree
  was built that way; a strict install hits an unrelated `pi-dashboard-subagents` peer).
- **`pi update pi` "cannot self-update"** just means the install is pnpm-global; update via
  `pnpm add -g @earendil-works/pi-coding-agent@latest`. And remember the global CLI is a
  *separate* pi from the dashboard's bundled copy.
