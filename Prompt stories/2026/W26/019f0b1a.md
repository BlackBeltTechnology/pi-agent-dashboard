# How we did it: Recovering from an orphan-branch jam in the worktree spawn dialog — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
explicitly *no implementing*. The operator was chasing a real bug: creating a worktree
session in the dashboard died with `branch_exists: branch os/default-node-24-keep-22-floor
already exists`, and **no session ever spawned**. The real objective, once the exploration
converged: figure out *why* that branch was stuck, and — after the explore turned into a
green light — ship the minimal client-only fix so the UI can recover from it with one click.

## 2. TL;DR playbook

1. **Start in explore mode** to trace the failure *before* touching code — map the two
   layers (worktree creation vs. session spawn) instead of guessing.
2. **Grep the symptom string** (`branch_exists`) across `packages/` + `src/`, then trace the
   client dialog → server route → `onSpawn`/`handleSpawnSession` chain.
3. **Ask the operator for the one data point that bisects the bug**: "does *checkout existing
   branch* work?" A yes collapses the whole hypothesis space.
4. **Confirm live disk state**: `git branch --list <b>`, `git worktree list`, `/api/health` —
   prove the branch is a true orphan (exists, no worktree, no dir).
5. **Mirror the existing recovery pattern.** The dialog already had orphan-*path* cleanup;
   add the equivalent for orphan-*branches*: a `branch_exists` → "Check out this branch
   instead" inline button.
6. **Refactor the submit path to take an override** (`handleCreateAndSpawn({ mode, base })`)
   so the one-click resubmit doesn't read stale React state.
7. **TDD the recovery**: run the 45 existing dialog tests green first, then add 2 tests (the
   reuse-resubmit flow + button-only-shows-for-`branch_exists`).
8. **Deploy per the client workflow**: `npm run build` → `POST /api/restart` → verify new pid
   + production mode via `/api/health`.
9. **Commit surgically**: stage only the change's 3 files; leave unrelated board-state churn
   (`openspec/groups/groups.json`) unstaged. Push to `develop`.

## 3. How the collaboration unfolded

**Phase A — Explore & trace (discovery).** The AI stayed in the explore stance, grepping the
`branch_exists` symptom and walking the flow: `WorktreeSpawnDialog.tsx` → server
`createWorktree` in `git-operations.ts` → the parent `onSpawn` → `handleSpawnSession`. It
built a two-layer mental model and — crucially — framed `branch_exists` as a *symptom of a
retry*, not the root failure. *Why it worked:* it refused to fix the first thing it saw and
instead separated cause from symptom.

**Phase B — Bisect with a live data point (decision).** The operator supplied the key steer:
*"But after for existing branch it works"* (checkout mode works). That single fact ruled out
the spawn machinery / overload / extension-crash entirely and collapsed the bug to one thing:
fork mode (`git worktree add -b`) is the only path that can *orphan* a branch and the only one
with no recovery. The AI confirmed on disk that the branch was a dangling orphan.

**Phase C — Minimal fix, TDD, deploy (generate + verify).** Green light to implement. The AI
refactored `handleCreateAndSpawn` to accept a `{ mode, base }` override, added a
`handleReuseAsCheckout` handler and the inline recovery button, ran the existing 45 tests
green, then added 2 targeted tests. It rebuilt the client and restarted the server
(`/api/restart`), verifying the new pid in production mode.

**Phase D — Surgical commit (land).** On *"commit and push"*, the AI inspected `git status`,
spotted unrelated `groups.json` board-state churn, and staged only the 3 files belonging to
the change before pushing to `develop` (`2e376f8e`, +95/−9).

## 4. Prompts that worked

- **The goal prompt (explore-mode skill):** kicking off in `openspec-explore` was the right
  frame for a *diagnosis-first* bug — it kept the AI tracing and hypothesizing instead of
  jumping to a patch. Good kickoff for any "why is X broken?" investigation.
- **High-leverage follow-up — the bisecting fact:** *"But after for existing branch it
  works"* is the whole playbook in seven words. A single behavioral data point that
  eliminates most of the hypothesis space is worth more than any amount of code reading.
  Stronger version to reuse: *"Checkout mode works, fork mode doesn't — what's different
  about the fork path?"*
- **"commit and push"** — short, but landed cleanly because the AI already knew to stage
  selectively. Pair such terse ship prompts with a standing "stage only my change's files"
  expectation.

## 7. Pitfalls & dead ends

- **`npx vitest` / `npm test` didn't resolve the runner cleanly** — the fix was to invoke
  vitest directly with an isolated HOME + localstorage file:
  `HOME=$(mktemp -d) NODE_OPTIONS="--localstorage-file=$(mktemp)" node node_modules/vitest/vitest.mjs run <test>`.
  If the standard test command flakes on env/state, use this isolated invocation.
- **`npx tsc --noEmit -p packages/client/tsconfig.json` surfaced a pre-existing
  project-reference config quirk** — not caused by the change. Don't chase it; confirm it's
  pre-existing and move on (the vitest run transpiles directly and is the real signal).
- **`/api/restart` takes several seconds** — the AI polled `/api/health` with backoff (sleep
  4→6→8→12) to confirm the new pid. Don't assume the server is up immediately after restart.
- **`openspec/groups/groups.json` shows up dirty** — it's dashboard board-state churn, not
  your change. Never blanket `git add`; stage your files explicitly.
