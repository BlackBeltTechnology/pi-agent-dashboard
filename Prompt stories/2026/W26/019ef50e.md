# How we did it: Distill pi session logs into reusable memory — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **openspec-explore mode** — a "think, don't implement" stance.
The first prompt was the explore-skill preamble ("Enter explore mode. Think deeply.
Visualize freely… you must NEVER write code… you MAY create OpenSpec artifacts").
No concrete topic was stated in the kickoff itself; the real objective emerged in the
first minute of grounding: **turn every pi session JSONL trace into distilled, reusable
memory** — skills, memory entries, and searchable docs — anchored on the one objective
success signal the logs already carry (`toolResult.isError`). The deliverable was a
fully-validated OpenSpec change proposal (`distill-session-knowledge`) capturing that
design, not an implementation.

## 2. TL;DR playbook

1. **Enter explore mode** with the openspec-explore skill — sets the "capture thinking,
   never implement" guardrail and permits creating OpenSpec artifacts.
2. **Ground in reality first.** In parallel: inspect how pi stores sessions
   (`~/.pi/agent/sessions/<project>/<ts>_<uuid>.jsonl`) and pull OpenSpec context.
3. **Map the JSONL schema without dumping raw content** — use `ctx_execute` to
   summarize event shapes (`session`, `model_change`, `message` roles, `toolResult.isError`)
   across many real sessions. This is the linchpin discovery.
4. **Check for prior art before scaffolding** — run the pre-scaffold coherence/dup scan.
   It surfaced an existing stale `pi-log-miner-skill` proposal (0/75 tasks). Diff the two
   approaches in a Mermaid flowchart + table instead of silently duplicating.
5. **Pull external best practices** with one `web_search` (Voyager, Trace2Skill, Memp,
   ReMe) → adopt the "distill, don't dump; anchor on verifiable signal; promote only
   recurring cross-session patterns" principle.
6. **Scaffold via CLI:** `openspec new change distill-session-knowledge` (not
   `openspec change new` — that form failed).
7. **Write the 3 artifacts** (proposal, design, tasks) + **3 delta capability specs**
   (validation requires them), and add a SUPERSEDED banner to the stale proposal.
8. **Resolve parked questions from the human's terse steering** (`N=3`,
   `ask_user→project`, `confidence-decay`, `patch`) and bake each into all artifacts.
9. **`openspec validate` until clean**, then **commit ONLY this exploration's files**
   (leave unrelated working-tree changes unstaged).

## 3. How the collaboration unfolded

**Phase A — Discovery & schema mapping (17:40–17:42).** The AI resisted the urge to
theorize and instead read the actual data: it located the session JSONL files and used
`ctx_execute` to map the event schema across ~40 real sessions *without* pasting raw
content into context. The payoff was concrete: `toolResult.isError` is a per-tool-call
objective success/failure boolean — the anchor the entire design would hang on.
*Why it worked:* grounding in the real file format before designing prevented a
fantasy spec.

**Phase B — Prior-art conflict catch (17:45–17:47).** Before scaffolding, the AI ran the
project's coherence/dup scan and found an *existing* active proposal, `pi-log-miner-skill`,
that mines the same logs — but with a heavyweight Honcho/Docker/pgvector summarization
stack. Instead of duplicating or ignoring it, the AI **stopped, diagrammed the divergence**
(existing = summarize per session into new infra; new idea = distill reusable artifacts
into existing sinks), and proposed the lean approach as a *superseding* change.
*Decision point:* the human implicitly endorsed the lean supersede path.

**Phase C — Research grounding (parallel in Phase B).** One `web_search` mapped the
agent-memory literature and produced the reframing that "index logs into the KB" is the
wrong primitive alone — distill and gate on recurrence instead.

**Phase D — Generate artifacts (17:48–17:50).** `openspec new change` scaffolded the tree;
the AI wrote proposal/design/tasks plus 3 delta specs (validation demanded them), added
the supersede banner, and ran `openspec validate` to green.

**Phase E — Resolve parked decisions (17:53–17:59).** The human fired terse steering
tokens. Each resolved one parked design question, and the AI propagated it across every
artifact and re-validated. See §5.

**Phase F — Surgical commit (18:31).** The tree held unrelated changes (mockups, other
skills, `redesign-goal-create-dialog`). On the single word `commit`, the AI staged **only**
the `distill-session-knowledge` files + the 6-line supersede banner and committed
(`c8e2e00d` on `develop`), leaving everything else untouched.

## 4. Prompts that worked

- **The goal prompt (explore-skill preamble):** effective because it set an explicit
  *stance and guardrail* ("never implement; you MAY create OpenSpec artifacts") rather
  than a task. A future kickoff should still name the concrete topic in one line, e.g.
  *"Explore: mine pi session JSONL into reusable memory anchored on `isError`."*
- **`What is recurrence threshold?`** — a high-leverage clarifying question from the
  human that forced the AI to define the key design knob (N) precisely before locking it.
- **`3` / `N=3`** — a two-character prompt that resolved the single most important
  parameter. Terse works *when the AI has already framed the choice*.
- **`ask_user -> project` / `confidence-decay` / `patch`** — one line resolving three
  parked questions at once; the AI had pre-listed them, so shorthand mapped cleanly.
- **`commit`** — trusted the AI to scope the commit correctly (it did, surgically).

Rewrite weak → strong: instead of relying on the AI to infer the topic from grounding,
lead with the one-line objective *and* the anchor signal to save the first two minutes.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Leave the recurrence threshold defaulted (N=2) as a parked question | `3` / `N=3` | State the promotion threshold up front: "promote a pattern only after it recurs in ≥3 distinct sessions" |
| Park routing/expiry/correction questions in design.md for later | `ask_user -> project` / `confidence-decay` / `patch` (one line, three answers) | Decide sinks up front: ask_user decisions → project memory (convention); expiry → confidence-decay (no hard TTL); corrections → patch AGENTS.md rule + write failure memory |
| Risk committing the whole dirty tree | `commit` (AI self-scoped to only its files) | Explicitly say "commit only this change's files; leave unrelated changes unstaged" |
| Define abstract knobs without a worked example | `What is recurrence threshold?` | Always accompany a design knob with a concrete before/after example (stale-port fault promoted at the 3rd sighting) |

Quality bars the human imposed implicitly: no duplicate proposals (catch the stale
`pi-log-miner-skill`), keep the change validated at every step, and keep the commit surgical.

## 6. Skills, tools & memory created — and why they're effective

No new skill/memory was created in-session (explore mode is capture-only). The **artifact
produced** — the `distill-session-knowledge` OpenSpec change — *is itself the design for a
future skill* that would:

- **Capture:** verified signals from session JSONL (isError flips = fault/correction,
  ask_user call+result = decision, user "no/actually/don't" = rule correction, >5 verified
  toolCalls = procedure, recurring summaries = documentation).
- **Route** distilled artifacts to the three sinks already installed: `skill_manage`
  (procedures), the `memory` tool (faults/decisions/corrections), `docs/` + `ctx_index`
  FTS5 (documentation).
- **Why effective:** it removes manual retrospective note-taking and only promotes
  patterns seen in ≥3 distinct sessions, so noise stays out of memory.
- **When to invoke next:** exit explore, run apply-change on `distill-session-knowledge`.

Recommended follow-up skill to actually create: an **offline session-log miner** matching
this proposal (this very `session-to-guideline` run is a manual precursor of it).

## 7. Pitfalls & dead ends

- **Wrong CLI form.** `openspec change new distill-session-knowledge` failed
  (`CLI-failed-exit`). The working form is **`openspec new change <name>`**. Check
  `openspec new --help` / `openspec change --help` when unsure.
- **Two early bash commands failed** during grounding (exploratory `find`/`ls` combos) —
  harmless; grounding tolerates misses. Don't over-invest in one perfect probe.
- **Validation rejects a change with no delta specs.** `openspec validate` demanded
  capability specs; copy the format from a recent change's `specs/*/spec.md` before writing.
- **Stray key left in an edit** required a clean re-run of one edit (2 edit errors). After
  propagating a decision across artifacts, re-validate immediately to catch it.
- **Dirty working tree at commit time.** Never `git add -A` here — mockups + other changes
  were present. Stage only the change's own files.
