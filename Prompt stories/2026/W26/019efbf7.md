# How we did it: Unblock develop CI, ship cross-platform installers, and add recommended skill-extensions — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff was a release-readiness request:

> "Monitor develop. When CI is okay, build installable electron for all platforms and make smoke tests in CI. I would like to test the packages which plan to deploy"

The *real* objective evolved across the session into three chained goals: **(1)** get `develop` CI green and produce downloadable Electron installers for every platform with install smoke-tests, then **(2)** "full build and deploy. And add skill extensions" — surface the monorepo's own pi-extensions (kb, mockup-loop, plugin-skill, document-converter) in the dashboard's `RECOMMENDED_EXTENSIONS` list, and **(3)** make those skill-shipping packages actually *carry and advertise* their skills (npm `pi.skills` packaging + a dashboard `skillsRegistered` field the UI renders), publish `document-converter@0.5.4`, and locally deploy.

## 2. TL;DR playbook

1. **Read the release docs first.** Grep `docs/faq.md README.md docs/` for `electron|installer|release|smoke` and identify the on-demand workflows (`ci-electron.yml`, `ci-smoke.yml`) before touching `gh`.
2. **Diagnose red CI from the fast-fail timing.** A 11–16s CI failure = install-layer, not test-layer. `gh run view <id> --log-failed` → here it was `EBADENGINE`: `packages/kb` engines bumped to `>=23.4.0` (needs `node:sqlite`) while CI pins Node 22 + `engine-strict=true`.
3. **Fix the narrowest cause.** Revert *only* `packages/kb` engines `>=23.4.0 → >=22.5.0` (matches the code's `--experimental-sqlite` design and its sibling packages). No version bump, commit one file, push, watch until green.
4. **Dispatch the matrices only once CI is green:** `gh workflow run ci-electron.yml -f legs=all` (6 legs) + `ci-smoke.yml` (Node 22/24/25). Poll conclusions; download artifacts.
5. **Triage platform failures as flake-vs-defect.** Re-dispatch the failing leg once. A leg that passes on retry = flake; a leg that fails both times with `pi-dashboard.exe not found after 150s` while branding + uninstall PASS = a too-tight timeout, not a packaging defect.
6. **Add monorepo extensions to `RECOMMENDED_EXTENSIONS`** (`packages/shared/src/recommended-extensions.ts`); update EVERY hardcoded count/id assertion the change breaks (the `"twelve entries"` test, status-filter lists, `recommended-routes.test.ts` `toHaveLength`).
7. **Make a private package publishable carefully:** dropping `private` triggers `publish-allowlist-complete.test.ts` — add the package to `publish.yml`'s `PACKAGES` allowlist in dependency order.
8. **Derive skills, don't hardcode them.** Add `pi.skills` → `skillsRegistered` derivation in `npm-search-proxy.ts` (`deriveSkillIds`, skip container dirs named `skills`/`skill`); render it in `RecommendedExtensions.tsx`. Prove packaging with `npm pack --dry-run | grep SKILL.md`.
9. **Local-deploy each layer:** `npm run build` → `curl -X POST /api/restart` → `npm run reload`; verify with `curl /api/packages/recommended | jq length`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery & root-cause (CI red).** The AI grounded itself in the release docs before running `gh`, then read the two failing `develop` runs. The winning move was reading the *timing*: 11–16s failures can't be lint/test, they're `npm ci`. `--log-failed` confirmed `EBADENGINE`. It then traced the regression to commit `977387a4` bumping `packages/kb` engines to `>=23.4.0`, and — crucially — verified the kb code only needs `--experimental-sqlite` (Node 22.5+), that siblings stayed at `>=22.5.0`, and that kb isn't in the Electron/server bundle. That evidence justified the *narrowest possible* fix.

**Phase 2 — Fix, verify, gate.** Reverted one file's engine floor, committed with a message explaining the tradeoff, pushed, and watched CI to green (8m33s) **before** dispatching anything downstream. Decision point the human implicitly set: don't build on red.

**Phase 3 — Matrices & flake triage.** Dispatched `ci-electron` (6 legs) + `ci-smoke` (7 legs). Result: smoke 7/7 green, electron 4/6 (both Windows install-smoke legs failed). The AI resisted blaming its own change (kb isn't bundled; build + branding passed) and did a **Windows-only re-dispatch** to separate flake from regression: win32-x64 passed on retry (flake); win32-arm64 failed twice but with `uninstall PASSED` in the same run → the app *did* install, just past the 150s poll (arm64 Setup.exe runs on an x64 runner, slower). Verdict: neither failure is a defect or caused by the fix.

**Phase 4 — Recommended extensions (data).** Cross-referenced monorepo pi-extensions against the 12 recommended entries; found kb-extension, frontend-mockup-loop, plugin-skill missing, and document-converter *blocked* (`private:true`, `v0.0.0`, no `pi` entry, needs Docker). The human confirmed scope ("skill" + "docconverter"). The AI made document-converter publishable (drop `private`, `0.0.0→0.5.4`, add `pi.skills`, copy the skill into the package keeping the root copy) and chased the cascade of hardcoded-count test failures + the `publish.yml` allowlist requirement.

**Phase 5 — Skills surface + packaging.** "it does not have the skills" exposed a missing schema field. First pass hardcoded `skillsRegistered`; then the human pushed toward pi's real mechanism ("the pi has a mechanism to pack the skills inside an npm package"), so the AI re-architected it to **derive** `skillsRegistered` from each package's own `pi.skills` (single source of truth), skipping bogus container dirs, and proved tarball inclusion with `npm pack --dry-run`.

**Phase 6 — Publish, deploy, complete the UI.** Published `document-converter@0.5.4` manually (the `v0.5.4` tag already exists so the CI pipeline can't re-dispatch), pushed, kept CI green. Local-deployed via build → restart → reload. Finally, "There are some missing files. What topic related for?" surfaced the last gap: the *data* flowed to the API but no client component rendered it — added the skills badge to `RecommendedExtensions.tsx` + tests + delegated file-index doc rows to a subagent.

## 4. Prompts that worked

- **The goal prompt** — "Monitor develop. When CI is okay, build installable electron..." Effective because it stated a *precondition* ("when CI is okay") that correctly forced the AI to gate the build on a green pipeline rather than charging ahead. A stronger version would name the workflows up front: *"...dispatch ci-electron.yml legs=all + ci-smoke.yml only after ci.yml is green."*
- **High-leverage follow-up:** "full build and deploy. And add skill extensions" — short, but it bundled two irreversible-adjacent asks; the AI correctly split "deploy" into local-vs-release and asked before publishing.
- **The re-architecture nudge:** "the pi has a mechanism to pack the skills inside an npm package" — one sentence that redirected a hardcoded field into a proper `pi.skills`-derived one. High leverage: it named the *right primitive*.
- **The gap-finder:** "There are some missing files. What topic related for?" — an open diagnostic question that made the AI discover the data-without-presentation gap itself.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat "deploy" as one thing | Distinguishing local deploy (build+restart+reload) from a release (npm publish + GitHub Release reaching electron-updater clients) | State up front which deploy you mean; the AI should always ask before anything irreversible |
| Solve "add skills" with a hardcoded `skillsRegistered` field | "the pi has a mechanism to pack the skills inside an npm package" | Point at `pi.skills` + `npm pack --dry-run` as the source of truth from the start |
| Add data without wiring the UI | "There are some missing files. What topic related for?" | Treat a feature as data **and** presentation **and** docs; check the client component renders the new field |
| Publish at an existing version | (facts caught it) `v0.5.4` tag already released → pipeline rejects re-dispatch | Verify tag/npm state first; a manual `npm publish` is the only path for an existing tag |
| Sweep in unrelated working-tree changes | "commit" with the AI staging only its own files | Always `git add` explicit paths; leave `goal-*`/others untouched |

## 7. Pitfalls & dead ends

- **`mktemp` template must end in `X`es** (macOS): `mktemp /tmp/facts-XXXXXX.md` silently yields empty → downstream `cat ""` fails. Use `mktemp /tmp/facts.XXXXXX`.
- **`engine-strict=true` checks EVERY workspace.** One package's `engines.node >=23.4.0` fails root `npm ci` on Node 22 even though the package isn't bundled anywhere. Don't raise the whole-repo Node floor to "fix" it — revert the outlier.
- **De-privatizing a package trips `publish-allowlist-complete.test.ts`** — you MUST add it to `publish.yml`'s `PACKAGES` in dependency order, or the test fails.
- **Hardcoded counts are everywhere.** Adding recommended entries broke: the `"twelve entries"` test, two status-filter lists, and `recommended-routes.test.ts` `toHaveLength(12)`. Grep for `toHaveLength|twelve|length.*12` before assuming one edit suffices.
- **`pi.skills: ["skills"]`** (the convention container dir) yields a meaningless basename `"skills"` — filter container dirs (`skills`/`skill`) when deriving ids, or the API misreports (`pi-web-access`/`context-mode` did).
- **Vitest test-isolation needs an ephemeral HOME:** run with `HOME=$(mktemp -d) npx vitest run ...`.
- **An existing `v0.5.4` tag blocks the release pipeline** (`resolve` errors "tag already exists on origin"); the only way to publish one lagging package at that version is a manual `npm publish` (no CI provenance).
