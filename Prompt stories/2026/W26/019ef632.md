# How we did it: Rendering C4 architecture diagrams inside Markdown — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened inside **explore mode** (`openspec-explore`) — a thinking-partner
stance, explicitly *no implementation*. The real question surfaced one turn later:

> "render example markdown with c4 diagram embedded"

The genuine objective: **prove that C4 architecture diagrams can live in a plain
Markdown file and render cleanly** — pick the lowest-friction toolchain, produce a
concrete example against *this repo's* real three-component architecture, and
verify it renders rather than just asserting it works.

## 2. TL;DR playbook

1. Ask the AI to lay out the C4-in-Markdown landscape (Mermaid C4 vs Structurizr DSL vs C4-PlantUML) with the trade-offs.
2. Choose **Mermaid C4** — it renders zero-config on GitHub / VS Code preview, no server or `!include` stdlib.
3. Have the AI write `docs/examples/c4-example.md` using the *real* architecture (bridge extension + Node server + React client), not a toy example.
4. Include all three C4 levels: Context, Container, Component — each in a ` ```mermaid ` fenced block.
5. Render to PNG to *see* it: `npx -y @mermaid-js/mermaid-cli -i docs/examples/c4-example.md -o /tmp/c4-out.png`.
6. Read the actual output images — don't trust "it should work". Inspect each diagram for layout defects.
7. Note the experimental-layout weakness (label collisions on the Context diagram) and the `UpdateLayoutConfig` levers to mitigate.

## 3. How the collaboration unfolded

**Phase 1 — Landscape (Discovery).** The AI answered the "can C4 live in Markdown?"
question by mapping three rendering paths with an ASCII decision tree: Mermaid C4
(native in many renderers, experimental layout), Structurizr DSL (best model
fidelity, needs tooling), C4-PlantUML (most expressive, heavier toolchain). *Why it
worked:* it framed the choice before writing anything, so the pick was justified.

**Phase 2 — Generate.** On the steering prompt, the AI wrote
`docs/examples/c4-example.md` grounding the diagram in the repo's actual
three-component architecture. *Why it worked:* a real-architecture example doubles
as living documentation, not throwaway demo content.

**Phase 3 — Verify.** The AI didn't stop at "this renders on GitHub." It shelled out
to `@mermaid-js/mermaid-cli` to produce real PNGs and then **read the images back**,
reporting per-diagram: Container ✓ clean, Component ✓ best layout, Context ⚠ label
overlap. *Why it worked:* the verify step caught a genuine defect the model had
flagged as a theoretical risk, turning a claim into evidence.

**Decision point:** the human chose "render it" over "trust it" — the single move
that upgraded the deliverable from an assertion to a proof.

## 4. Prompts that worked

- **Goal prompt (implicit):** entering explore mode set a *think-first, don't
  implement* stance. Good kickoff for "is X even possible / what are my options"
  questions.
- **High-leverage follow-up:** `"render example markdown with c4 diagram embedded"`
  — five words that pivoted from theory to a concrete, verifiable artifact. Its
  power was demanding an *example* (forces real content) plus *rendered* (forces
  verification).

Stronger reusable version: *"Pick the lowest-friction C4-in-Markdown option, write a
`docs/examples/` file using our real architecture, then render it to PNG and tell me
which diagrams have layout defects."* — bakes in the verify step from the start.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session. The workflow **is** repeatable, so the
recommended skill would be *"embed-and-verify-mermaid-diagram"*: given a diagram
request, write the fenced-block Markdown against real project structure, render via
`@mermaid-js/mermaid-cli`, read the PNGs, and report per-diagram layout quality. It
removes the manual "does this actually render?" loop and standardizes the
grounding-in-real-architecture rule.

## 7. Pitfalls & dead ends

- **Mermaid C4 is experimental** — cross-relationship label reflow is weak. The
  Context diagram collided "Views sessions" text with the system box. If you hit
  label overlap, reach for `UpdateLayoutConfig($c4ShapeInRow=…, $c4BoundaryInRow=…)`
  or prefer the more vertical Container/Component layouts which render clean.
- **Don't trust "renders on GitHub"** blindly — export to PNG and eyeball it; the
  defect only showed in the actual output.

## 8. Reproduce it faster — checklist

- [ ] Choose **Mermaid C4** for zero-config Markdown rendering.
- [ ] Write `docs/examples/c4-example.md` with Context + Container + Component blocks using the real architecture.
- [ ] Render: `cd <repo> && npx -y @mermaid-js/mermaid-cli -i docs/examples/c4-example.md -o /tmp/c4-out.png`
- [ ] Open the PNGs; flag any label collisions (expect them on the Context diagram).
- [ ] Apply `UpdateLayoutConfig` levers if the Context layout is cramped.

**Inputs needed:** Node + `npx` (pulls `@mermaid-js/mermaid-cli` on demand); the
