# How we did it: Turning an idle-CPU complaint into a validated OpenSpec proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation task. The framing prompt was the skill boilerplate: *"Enter explore mode.
Think deeply… You may read files, search code, and investigate the codebase, but you must
NEVER write code or implement features… You MAY create OpenSpec artifacts."*

The **real objective**, which crystallized over the next five steering turns, was:
take a hand-written performance observation — *"PI Dashboard burns ~one full CPU core
while idle; the Electron renderer sits at ~43% and the GPU process at ~41% in lock-step"* —
**verify it against the actual code**, diagnose the root cause, and capture the fix as a
**strict-validating OpenSpec change proposal** (not an implementation). The scope then grew,
turn by turn, from one animation (the neon selection ring) to a unified treatment of *every*
idle GPU cost surface in the card UI.

## 2. TL;DR playbook

1. **Start in explore mode** and refuse to theorize — grep the exact CSS/Electron lines the
   report cites (`--neon-angle`, `conic-gradient`, `filter: blur`, `prefers-reduced-motion`,
   `mainWindow.hide()`, `backgroundThrottling`) and confirm each claim ✓ against source first.
2. **Draw the causal chain** (a cost engine + why it never stops) before proposing anything —
   makes the diagnosis defensible and the fix obviously targeted.
3. On **"create proposal"**, mirror an *existing* change dir (`selectable-tool-output-links`)
   for format — there is no `openspec scaffold` subcommand, so copy conventions by hand.
4. Write the 4 artifacts: `proposal.md`, `design.md`, `tasks.md`,
   `specs/<capability>/spec.md`. Run `openspec validate <name> --strict` after **every** edit.
5. **Answer the human's cost questions with a paint-vs-composite table**, not prose — classify
   each animated CSS property by Chromium pipeline stage (paint = expensive repaint,
   composite/opacity/transform = ~free).
6. When the human says **"yes"**, fold the new fix into *all four* artifacts symmetrically
   (proposal bullet + design decision + spec requirement+scenario + tasks section), then
   re-validate `--strict`.
7. On **"commit changes"**, `git add` **only** the change dir — leave pre-existing unrelated
   modifications untouched and say so explicitly.

## 3. How the collaboration unfolded

**Phase 1 — Verify before theorizing (Discovery).**
The AI's first move was a `ctx_batch_execute` that hiccupped; it immediately fell back to
plain `grep`/`sed` over `packages/client/src/index.css` and `packages/electron/src/main.ts`.
It confirmed every claim in the report line-by-line: the dual `conic-gradient` +
`@property --neon-angle` ring re-rasters every frame at `index.css:339-389`, the
`prefers-reduced-motion` guard at `406-409`, and close→`hide()` (no quit) at `main.ts:284-289`.
*Why it worked:* grounding in real line numbers turned a vibes complaint into a defensible
diagnosis, and made the eventual proposal auditable.

**Phase 2 — Draw the causal chain (Design thinking).**
Before writing anything, the AI drew a "cost engine + gatekeepers" diagram: the always-on
per-frame raster (cost engine) and *why it never stops* (macOS Reduce Motion OFF → the
reduced-motion guard is inactive; window hidden not quit → renderer keeps painting).
*Decision point:* the human implicitly accepted this framing by moving to "create proposal".

**Phase 3 — Scaffold by mirroring (Generate).**
On **"create proposal"** the AI discovered there is *no* `openspec scaffold` subcommand, so it
`cat`-ed a recent change (`selectable-tool-output-links`) to copy the proposal/design/spec/tasks
format, then wrote all four artifacts and validated `--strict`. The first proposal was
deliberately narrow: 3 client-only fixes (pause-on-hidden, cheap ring, `cursorBlink:false`),
with re-enabling `backgroundThrottling` **deliberately deferred** (blank-window-on-restore risk).

**Phase 4 — Scope expansion driven by the human (Refine, ×2).**
The human probed: *"Is the stripe [lines] for running/finished costs GPU?"* The AI answered
with a precise paint-vs-composite table (`background-position` = per-frame repaint; `opacity` =
free), concluding the stripes cost *but cheaper than the ring*. On **"yes"** it folded a
transform-based stripe fix into all four artifacts as **Decision 3**. Then the human added the
`ask_user`/question state: *"When Ask for question use the stripes with the question color"* —
the AI unified all three active states (running=yellow, unread=cyan, ask_user=purple) onto one
shared compositor-only `transform` mechanism, again threading it through every artifact and
re-validating.

**Phase 5 — Surgical commit (Ship).**
On **"commit changes"** the AI staged **only** `openspec/changes/throttle-idle-ui-animations/`,
committed `9d9ce03e` (4 files, 257 insertions), and explicitly listed the pre-existing unrelated
files it left untouched (`bundle-server.mjs`, `directory-service.ts`, a deleted mockup).

## 4. Prompts that worked

- **The goal prompt** (the explore-mode skill boilerplate): effective because it set a hard
  *think-don't-implement* boundary while explicitly permitting OpenSpec artifacts — so the AI
  produced a proposal, not code. A future user could sharpen the kickoff by pasting the raw
  performance observation *with* the `ps` numbers right into the explore prompt.
- **"create proposal"** — a two-word high-leverage turn that converted confirmed diagnosis into
  the 4-artifact OpenSpec change. Works because the diagnosis phase already did the thinking.
- **"Is the stripe [lines] for running/finished costs GPU?"** — a targeted probe that expanded
  scope precisely; it forced a rigorous cost classification instead of a hand-wave.
- **"yes"** — a one-word approval that unlocked a full symmetric fold into all four artifacts.
- **"When Ask for question use the stripes with the question color"** — a concrete UI
  requirement that unified the whole card-animation family; strong because it named the exact
  state and the exact visual treatment.

The quality bar the human imposed implicitly: **cost claims must be classified by Chromium
pipeline stage** (paint vs composite), and **every fix must be threaded through all four
OpenSpec artifacts** — not just mentioned in the proposal.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session, but two patterns are clearly reusable and worth
saving:

- **A `openspec-perf-proposal` project skill** — capturing the loop *verify claims against
  source → draw the cost-engine causal chain → mirror an existing change dir for format →
  fold each fix symmetrically into proposal/design/spec/tasks → validate `--strict` after every
  edit*. It removes the manual re-discovery that there's no `openspec scaffold` and encodes the
  "validate after every edit" discipline.
- **A reusable "CSS animation cost classifier" note** — the paint-vs-composite table
  (`background-position`/`filter`/`conic-gradient` = paint = expensive; `opacity`/`transform` =
  composite = ~free). Invoke it whenever a UI perf proposal touches animated CSS.

## 7. Pitfalls & dead ends

- **`ctx_batch_execute` hiccupped** at the very start → *if the context tool errors, just
  fall back to direct `grep`/`sed`* and keep moving; don't retry it.
- **No `openspec scaffold`/`new` subcommand exists** → *if you reach for a scaffold command,
  stop and `cat` a recent `openspec/changes/<name>/` dir to copy the format by hand.*
- **Stray field/marker leaked into edits twice** (the `edit` tool logged 4 errors) → *after an
  artifact edit, re-open the section and re-validate `--strict`; redo the whole edit cleanly
  rather than patch the stray.*
- **Over-broad commit risk** → *always `git add` the change dir only; run `git status --short`
  first and explicitly list the unrelated files you're leaving out.*
