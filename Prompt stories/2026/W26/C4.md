## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-partner stance,
no implementation allowed. The operator's real objective, once the steering turns
sharpened it: *design a way to reverse-engineer this codebase into **C4 architecture
diagrams** that an LLM can read and incrementally update — and package that capability as
a **publishable npm skill**, not a one-off local file.* The deliverable was never code; it
was a validated OpenSpec change proposal (`add-codebase-c4-diagrams`) ready to hand to
`openspec-apply-change`.

## 3. How the collaboration unfolded

**Phase 1 — Ground (Discovery).** Before proposing anything, the AI ran `find`/`grep` to
count TS/TSX files and LoC and to enumerate the repo's *existing* navigation system. This
reframed the problem: the codebase already has a maintained backbone (`AGENTS.md` +
`file-index*` splits), so C4 had to *complement* it, not duplicate it. **Why it worked:**
grounding first turned a generic "add diagrams" ask into a repo-specific design constraint.

**Phase 2 — Gather (parallel research).** Three `@fast` `researcher` subagents ran
concurrently on distinct angles. The AI synthesized the convergent finding —
**diagrams-as-code (Mermaid / JSON edge-lists), not images** — and explicitly quarantined
untrustworthy citations. **Decision point:** the human chose parallel `@fast` research to
keep it cheap and fast.

**Phase 3 — Design (OpenSpec drafting).** On the "b" unlock, the AI checked for
duplicate/conflicting changes, mirrored a sibling change's file layout, and wrote
`proposal.md` / `design.md` / `tasks.md` / `spec.md`. Core design decisions: L1/L2
hand-authored, L3 generated from `dependency-cruiser` (ground-truth edges kill hallucinated
ones), L4 out of scope, two artifacts (Mermaid for humans + text edge-list for LLMs).

**Phase 4 — Repackage (the pivot).** *"It's a skill delivered as an npm package"* forced a
clean **PACKAGE (published, reusable on any TS repo) vs OUTPUT (`docs/c4/*`, this repo
only)** separation. `dependency-cruiser` moved from root devDep to a **runtime dep of the
package**; the generator became `src/bin/c4gen.ts` + a testable core. The AI noted the pivot
*sharpened* the design.

**Phase 5 — Name & validate.** "Use a better name" → `@blackbelt-technology/pi-dashboard-c4-skill`,
skill `c4-codebase-map`, bin `pi-dashboard-c4`, mirroring the sibling convention. `openspec
validate --strict` was re-run after every change until green.

**Phase 6 — Commit (scoped).** On "commit changes" the AI caught a **pre-staged unrelated
file** (`docs/examples/c4-example.md`), reset it out, and committed only its own five
artifacts as `4d3f089e`.

## 4. Prompts that worked

- **Goal prompt (`openspec-explore` stance):** effective because it *forbids implementation*
  and keeps the session in design mode — the AI produces artifacts, not code, exactly what a
  proposal needs.
- **"research web for best practices / existing skills … Use @fast model for exploration in
  parallel"** — high leverage: names the *research shape* (parallel), the *model* (cheap
  `@fast`), and the *angle* (existing skills + incremental update) in one line.
- **"it's a skill delivered as an npm package"** — a 7-word steer that reshaped the entire
  change. Lesson: **state the delivery/packaging target up front**; it changes dependency
  placement, file layout, and conventions.
- **"use a better name"** — short, but the AI already had the sibling convention to anchor on,
  so it resolved cleanly. Stronger version: *"name it to match the `pi-dashboard-plugin-skill`
  convention."*
- Weak prompt to rewrite: **"b"** worked only because the AI had just offered a lettered menu.
  A future operator should instead write *"draft the OpenSpec proposal now"* so the intent is
  self-contained.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was **saved** in this session — the output was an OpenSpec proposal,
not a reusable procedure. But the proposal *is* the reusable asset: `add-codebase-c4-diagrams`
specifies `@blackbelt-technology/pi-dashboard-c4-skill`, a publishable package that any TS repo
can install to generate C4 diagrams. Three `@fast` `researcher` subagents were the key tool:
parallel, cheap, angle-separated research whose convergent signal (diagrams-as-code) survived
even after the hallucinated citations were discarded.

**Recommended skill to create** on apply: once `c4gen.ts` exists, capture a project skill for
*"regenerate the L3 component diagrams from dependency-cruiser"* so the drift-check becomes a
one-command routine.

## 7. Pitfalls & dead ends

- **Hallucinated citations from `@fast` research** — future-dated arxiv IDs (`2603.*`,
  `2604.*`). *If you hit this:* keep only claims that converge across independent agents and are
  independently verifiable; discard the rest.
- **One failed bash + one failed edit + one failed `ctx_batch_execute`** — recovered by
  re-running. *If a validate/edit fails:* re-run `npx openspec validate <change> --strict` to
  see the exact schema complaint (here: the validator wanted a clearer `SHALL` lead sentence).
- **Pre-staged unrelated file** (`docs/examples/c4-example.md`) sitting in the index. *If you
  hit this before a commit:* `git reset -q HEAD <file>` and add only your own artifacts.
- **Wrong model name in the operator's head** ("C5"). *Guardrail:* the AI should flag naming
  mismatches instead of silently guessing.
