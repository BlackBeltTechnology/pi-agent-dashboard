# How we did it: An explore-mode transport-tech evaluation, captured as a research note

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user entered **explore mode** (`openspec-explore`) to think through a technology
question, not to build anything: *would adopting **iroh** (a P2P QUIC networking
library) improve pi-dashboard's communication transport?* Explore mode's contract is
explicit — "thinking, not implementing": read, search, investigate, visualize, but
never write code. The *real* objective, once the two short steering turns landed, was
to produce a **grounded, decision-ready research note** that a future maintainer can
read to understand why iroh is (or isn't) worth pursuing — and to commit it where
similar notes already live.

## 2. TL;DR playbook

1. Kick off in explore mode: *"Enter explore mode. Evaluate whether **iroh** would
   improve our transport. Ground it in (a) how bridge↔server↔client comms work today
   and (b) what iroh actually is."*
2. Let the AI **investigate in parallel** — one `web_search` for the unknown tech
   (what iroh is, JS bindings, NAT-traversal use cases) + a `grep` batch over the repo
   docs (`docs/file-index-server.md`, `docker/README.md`) for the current remote-access
   picture.
3. Have it lay out the **actual topology first** (the three comms legs), because that
   is what makes or breaks the new tech — evaluate against *your* constraints, not the
   library's marketing.
4. Ask for a **per-leg verdict** (which legs even have the problem iroh solves) and a
   named blocker (browser can't run native iroh) plus any narrow future niche.
5. Steer: *"Save the research result."* Let the AI find the existing convention
   (`docs/plans/*-research.md`) and match it rather than inventing a location.
6. Steer: *"commit."* One file, scoped stage, descriptive message.

## 3. How the collaboration unfolded

Three tight phases in under four minutes (3m 42s, ~$0.87).

- **Discovery / Gather (parallel).** The AI immediately split the question into
  *known* (our own architecture) and *unknown* (iroh). It ran a single `web_search`
  with three sub-queries and a `ctx_batch_execute` grep sweep over the server + docker
  docs — pulling the remote-access story (zrok reserved share + OAuth + tunnel
  watchdog) that is the only leg that actually crosses NAT. *Why it worked:* grounding
  the shiny new tech against the real topology before judging it.
- **Analysis.** It drew the three-leg diagram (bridge→server WS :9999, browser→server
  WS :8000, remote=zrok) and produced a per-leg verdict: Legs A and B are same-host
  Node↔Node / browser↔Node with reconnection already solved, so iroh buys nothing;
  only Leg C crosses the internet, and there the browser **cannot run native iroh** —
  the core blocker. It surfaced one narrow future niche (Electron-main-as-QUIC-proxy)
  and a clear recommendation.
- **Capture & commit.** On *"Save the research result"* the AI checked where similar
  notes live, found `docs/plans/honcho-integration-research.md`, and matched the
  `*-research.md` convention rather than guessing. It wrote
  `docs/plans/iroh-transport-research.md`, then on *"commit"* staged **only** that file
  and committed with a descriptive message (`2fd3e4cb` on `develop`, 70 insertions).

## 4. Prompts that worked

- **The goal prompt (explore-mode stance).** Effective because it framed the task as
  *evaluate a technology against our system*, not *adopt it*. Explore mode's guardrail
  ("no implementation") kept the output a decision note, not a half-built transport.
  A stronger kickoff bakes the grounding in explicitly: *"Evaluate iroh for our
  transport. First map the current comms legs, then judge iroh per leg, then give a
  recommendation + sources."*
- **"Save the research result"** — high-leverage. Three words that turned a chat answer
  into a durable artifact. Effective because the AI already knew the content; the only
  decision left was *where*, which it resolved by matching an existing convention.
- **"commit"** — one word, correctly scoped. Worked because the session had produced
  exactly one file, so "commit" was unambiguous.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stop at a chat-only answer (explore mode discourages writing) | "Save the research result" | Say up front: *"produce a committed `docs/plans/<topic>-research.md` note"* |
| Offer to also add a discoverability pointer / index row | (left standalone — user just said "commit") | State scope: *"just the note, no index changes"* |
| Nothing needed correcting on location or scope | — | The convention-matching (find a sibling `*-research.md`) was the right instinct — keep it |

This was a *low-steering* session: the two follow-ups were unlocks ("now persist it",
"now commit it"), not corrections. The AI's own instinct to match `docs/plans/`
convention and to stage only the one file was correct without prompting.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created — and none was warranted. This is a **one-off technology
evaluation**, not a repeatable procedure. The reusable *pattern*, however, is worth
naming for the next operator:

- **The explore→research-note pattern:** enter explore mode → ground the question in
  the real system topology → judge the new thing per-constraint → persist the verdict
  as a `docs/plans/<topic>-research.md` note matching existing siblings → commit that
  one file. If you find yourself doing this repeatedly for different candidate
  technologies, *that* would justify a skill; a single instance does not.

## 7. Pitfalls & dead ends

- **Zero failed commands** this session. The clean run came from grounding first
  (grep the repo docs + one focused web search) rather than reasoning about iroh in a
  vacuum.
- **Explore-mode trap:** the mode's "no implementation" stance can leave good analysis
  trapped in chat. If the thinking is worth keeping, *explicitly* ask to persist it —
  the AI won't write files unprompted in explore mode.
- **Convention drift risk (avoided here):** when saving a note, have the AI locate a
  sibling first (`ls docs/plans`) instead of inventing a path. It did; you should
  demand it.
