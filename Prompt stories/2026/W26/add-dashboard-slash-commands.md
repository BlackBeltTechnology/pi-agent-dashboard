# How we did it: shipping `add-dashboard-slash-commands` — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with a two-line prompt: *"Current proposal is: add-dashboard-slash-commands. Recheck with current state."* The real objective, once it unfolded, was much bigger than a recheck: **take an already-drafted OpenSpec proposal, re-validate its assumptions against the current `main`, then fully implement it** — a 69-task change that adds *executable-mode* slash commands (`/dashboard:server-health` runs a bash template locally against the dashboard REST API, skipping the LLM), wires the `source: "slash-exec"` flag end-to-end through bridge → shared types → client footer, ships ~33 command templates, **verifies it live in Docker**, and finally **ships it as a merged PR**. Each of those four escalations came as a separate one-word or one-line steering prompt.

## 2. TL;DR playbook

1. **Recheck before building.** Point the AI at the existing proposal and say "recheck with current state." It diffs proposal assumptions against live source, finds stale references (e.g. `protocol.ts` → actually `packages/shared/src/types.ts`), and patches `proposal.md` + `tasks.md` so the plan is accurate before a line of code is written.
2. **Approve the corrections** ("yes") — let it re-validate strict (`openspec validate --strict`).
3. **Kick off implementation** with `/skill:openspec-apply-change <change>`. It reads context files (specs + design), then works section-by-section (frontmatter parser → command-handler dispatch → shared type → client footer → templates → docs), running the ephemeral-`HOME` vitest convention after each.
4. **Delegate every `docs/` write** to a subagent in caveman style (AGENTS.md Rule 6); the main agent edits README + source-tree rows directly.
5. **Ask for live verification** ("Is it possible to make manual verification with docker and playwright?"). This is the highest-leverage prompt — it forced the AI to discover the feature shipped from the *wrong skill copy* and to build a real container test.
6. **When Playwright's browser download is blocked, pivot to a WebSocket REST driver** — spawn a real in-container session, subscribe to `/ws`, send the prompt, assert the `bash_output` event carries `source: "slash-exec"`.
7. **Fix what the live run catches** (wrong skill copy, cwd-dependent resolution, port-resolution env precedence) — add a unit test for each.
8. **Ship with the skill:** "Use ship-change skill." It runs the verify gate, archives + syncs specs, opens the PR, resolves develop conflicts, waits out CodeRabbit rate-limits, applies safe review fixes, and squash-merges.

## 3. How the collaboration unfolded

**Phase A — Recheck & de-stale the plan (Discovery).** The AI confirmed the dependency `fix-extension-slash-commands-in-dashboard` was *archived* (2026-05-09) so the precondition held, then verified every proposal assumption against source: `readTemplate` still returns a bare string, `expandPromptTemplateFromDisk(text, cwd, pi?)` unchanged, the `bridge.ts::sessionPrompt` insertion point (flow → `tryDispatchExtensionCommand` → `expandPromptTemplateFromDisk`) intact. It found two real corrections — the impacted file was `types.ts` not `protocol.ts`, and the dependency had *landed and extracted `slash-dispatch.ts`* — and patched the artifacts. **Why it worked:** grounding the plan in `grep`/`sed` of live source before coding prevented building against a stale map.

**Phase B — Section-by-section implementation (Generate).** After `/skill:openspec-apply-change`, the AI built in dependency order: (1) a hand-rolled frontmatter parser + `loadPromptTemplate()` discriminated union in `prompt-expander.ts`; (2) `tryExecSlashTemplate()` in `command-handler.ts` mirroring the existing `tryDispatchExtensionCommand`, with env injected via prepended `export` lines because `ExecOptions` has no `env` field; (3) the `source` field on `BashOutputData`; (4) client footer threading `source` through event-reducer → ChatView → BashOutputCard; (5) ~33 templates generated by script for consistency. **Decision point:** it chose a *shared helper* over a vestigial `ParsedPrompt` variant and annotated that refinement in `tasks.md`.

**Phase C — Live verification uncovers the real bugs (Verify).** Asked whether Docker+Playwright verification was possible, the AI investigated instead of guessing — and discovered the commands shipped **only in the repo-root skill copy**, while the *bundled, user-facing* skill is `packages/extension/.pi/skills/pi-dashboard/`. It also found local `scanDir` never descends into `commands/`, so resolution was cwd-dependent. Playwright's chromium download was network-blocked, so it pivoted to a WebSocket driver against a freshly-built container and proved `source: "slash-exec"` round-trips — which then exposed a third bug: `config.json` has no `port` in the container, so `buildDashboardExecEnv` must prefer `DASHBOARD_PORT`/`PI_DASHBOARD_URL` env vars.

**Phase D — Ship (Land).** "Use ship-change skill" drove the verify gate (8000+ tests), `openspec archive`, PR #184, two rounds of develop-merge conflict resolution (file-index rows, bridge.ts imports), a CodeRabbit rate-limit wait, 11 review comments triaged (apply the multi-line-passthrough + base-URL fixes, defer the design-by-spec ones with rationale), and a final squash-merge.

## 4. Prompts that worked

- **The goal prompt** — *"Current proposal is: X. Recheck with current state."* Effective because it scoped the AI to a known artifact and asked for *validation against reality first*, not blind implementation. A stronger version: *"Recheck proposal X against current main; patch any stale file refs in proposal.md/tasks.md, then stop for my approval before implementing."*
- **"yes"** — a high-leverage one-word approval that unblocked the artifact patches + strict re-validation.
- **`/skill:openspec-apply-change add-dashboard-slash-commands`** — invoking the apply skill by name gave the AI its whole section-by-section discipline for free.
- **"Is it possible to make manual verification with docker and playwright?"** — the single most valuable prompt. Framed as a question, it made the AI *investigate the real runtime* and surface three shipping-blocker bugs that unit tests and mock-server e2e had missed.
- **"Use ship-change skill"** — delegated the entire land pipeline to a battle-tested procedure.

## 6. Skills, tools & memory created — and why they're effective

No new skills were authored, but the session was a heavy *consumer* of existing ones, and the pattern is worth a dedicated skill:

- **`openspec-apply-change`** gave the section-by-section build discipline; **`ship-change`** owned the archive→PR→CI→CodeRabbit→squash-merge loop, including conflict resolution and rate-limit handling. Both proved that naming the skill in the prompt is far more reliable than describing the workflow.
- **Two `general-purpose` subagents** handled all `docs/` writes in caveman style (AGENTS.md Rule 6) — keeping the main agent out of `docs/` prose while it orchestrated.
- **Recommended new skill:** *"live-container-verify-extension-change"* — capturing the WebSocket-driver fallback (build image → spawn real session in a no-skill cwd → subscribe `/ws` → send prompt → assert the `bash_output` event shape) for when Playwright's browser binary is unavailable. This session reinvented it from scratch; it should be reusable.

## 7. Pitfalls & dead ends

- **`npx vitest` grabs a global build without jsdom** — client component tests fail. Use the project's local binary (`./node_modules/.bin/vitest`, pinned 1.61.1).
- **Tests need an ephemeral `HOME`** — prefix with `HOME=$(mktemp -d)` (project convention) or config-loading tests pollute the real home.
- **`search-files-ranking.test.ts` is a timing-sensitive flake** (builds a 4000+ entry FS tree, ~9s) — passes on rerun; not a regression signal.
- **Playwright chromium download blocked** (`cdn.playwright.dev` unreachable) — don't fight it; drive the container over the browser WebSocket instead.
- **Dashboard events aren't persisted to a readable file** — they live in an in-memory ring buffer broadcast over `/ws` on `subscribe`; you must have a WS client connected *when* the event fires.
- **`ExecOptions` has no `env` field** — inject environment via prepended `export` lines in the bash body; pass positional args via `bash -c <script> -- a b`.
- **A fresh worktree has empty `node_modules`** — run `npm install` before the verify gate, then `git checkout package-lock.json` to drop the incidental `dev: true` lockfile churn (surgical-changes rule).
- **`CONFLICTING`/`DIRTY` PR merge state silently blocks CI from starting** — if no CI run registers, check `gh pr view --json mergeStateStatus` and merge `develop` first.
- **CodeRabbit's green "pass/0" can be a rate-limit ACK, not a real review** — read its issue comment; wait for the reset window, then `@coderabbitai review`.
