# How we did it: Self-heal host Playwright browser — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) against a nagging pain: the
browser-E2E suite (`tests/e2e/`) couldn't be run because Playwright "cannot download."
The literal first prompt was the explore-mode stance boilerplate — *think, don't
implement* — so the real objective only crystallized through steering. What the operator
actually wanted: **make host E2E runs stop failing mysteriously**, understand *why* the
Chromium download breaks, and land a durable fix as a proper OpenSpec change (explore →
propose → apply → review → ship). The end state: a self-healing preflight that fails fast
with the exact remedy, a pinned Playwright version, and the whole thing committed to an
isolated branch without sweeping in unrelated churn.

## 2. TL;DR playbook

1. **Enter explore mode first, don't jump to a fix.** Reproduce the failure until you can
   name the *mechanism*, not just the symptom.
2. Ask the AI to **reproduce the download failure live** — it discovered the headline
   "cannot download" was two stacked failures: a missing `node_modules/.bin/playwright`
   symlink (the real culprit) plus a blocked CDN (a red herring).
3. Push it to **decompose the pain** ("make local host runs less painful") — it produced a
   4-friction-point map ranked by pain-removed ÷ effort.
4. Say **"draft proposal"** — it checked coherence against archived/active changes, mirrored
   the archived change's format, and scaffolded `proposal.md + design.md + tasks.md +
   specs/<cap>/spec.md`, then `openspec validate` → valid.
5. Apply with `openspec-apply-change`: preflight in `global-setup.ts` (runs **before** any
   Docker boot), `pretest:e2e` auto-install hooks, and a **surgical 1-line** version pin.
6. When the version pin triggered a **34k-line lock rewrite**, reject it — pin the root spec
   string only, `git checkout` the churn, verify `npm ls` resolves clean.
7. **"build and redeploy to test"** → do it, but state the honesty caveat: test-infra-only
   change doesn't ship in the running dashboard; the real proof is the 1s fail-fast.
8. **"review"** → run the CodeRabbit advisory gate; flag ambient `groups.json` churn as *not
   mine* and leave it unstaged.
9. **"use ship-change skill"** → verify preconditions **before** anything irreversible; when
   git state diverges from the skill's assumptions, STOP and confirm scope before push.

## 3. How the collaboration unfolded

**Phase 1 — Diagnose (reproduce, don't guess).** The AI ran the failing `npx playwright
install chromium` and dissected the failure into a diagram: `npx` looks for
`.bin/playwright` → missing → falls back to fetching the `playwright` pkg from npm → blocked.
Key finding: `@playwright/test@1.61.1` *is* installed and its `cli.js` runs, but the bin
symlink was never created (partial/`--no-bin-links` install rot). **Why it worked:** it
refused to accept the surface error message and instead proved the mechanism, which reframed
the whole fix.

**Phase 2 — Ground the topology.** On the steering "e2e can run on host, use docker-test
image to connect to — does it help?", the AI drew the host↔container wiring and answered
crisply: the container hosts only the *app under test*; Playwright drives Chromium **on the
host**, so Docker is **orthogonal** to the download bug. **Decision point:** the operator
learned Docker wasn't the lever, redirecting to host-side friction.

**Phase 3 — Decompose the pain.** "make local host runs less painful" → a 4-point map:
(1) hidden prereq (forget `playwright install` → boot slow Docker for ≤180s, THEN die at
browser launch — worst pain); (2) floating `^1.57.0` drifting to 1.61.1 → re-download;
(3) broken `.bin` link; (4) no browser preflight (fails late). Plus a fix menu ranked by
pain-removed ÷ effort.

**Phase 4 — Propose.** "draft proposal" → coherence check (nothing active overlaps;
`add-playwright-e2e` archived), format mirrored from the archived change, four files
scaffolded, `openspec validate` clean. The core design decision: **auto-install vs
fail-fast, split by path** — npm path (`pretest:e2e`) auto-installs; direct/`globalSetup`
path fails fast with the exact command.

**Phase 5 — Apply.** `openspec-apply-change`: `assertBrowserInstalled()` preflight called
**first** in `global-setup.ts`, pretest hooks, version pin. Verified the risky assumption
(`chromium.executablePath()` returns the path without throwing; `existsSync` gates it) before
editing. Live-tested fail-fast: **1s** fail, correct message, **zero** containers booted.

**Phase 6 — Redeploy + review.** `npm run build` + `POST /api/restart` (skipped
`npm run reload` — no bridge change). CodeRabbit advisory gate: no findings. Flagged ambient
`openspec/groups/groups.json` churn as unrelated dashboard reshuffle.

**Phase 7 — Ship (with a stop).** `ship-change` skill: the AI **paused before anything
irreversible** because git state diverged three ways from the skill's happy path (main
checkout not worktree; no feature branch; local `develop` 1 commit ahead with an unrelated
change; ambient `groups.json`). It confirmed scope, then did skill steps 1–4 only: isolated
branch from `origin/develop`, archive + sync specs, commit exactly the 10 owned files — no
push, no PR.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session — instead it was a **model application of
existing skills in sequence**: `openspec-explore` → `openspec-apply-change` → `ship-change`,
plus the repo's caveman-style docs-delegation rule (the file-index update went to a
`general-purpose` subagent). One subagent was spawned: *"Update file-index rows for e2e
change."*

**What should be captured as a skill:** the *diagnose-Playwright-host-download* procedure —
`npx playwright` fails → check `node_modules/.bin/playwright` symlink existence FIRST (the
common `.bin` rot), then CDN reachability, then the cached-revision vs wanted-revision gap.
This session also exposed that the same `.bin` rot hits `vitest` (run via
`node node_modules/vitest/vitest.mjs` to bypass). A short skill would turn a 1h diagnosis
into a 2-minute checklist.

## 7. Pitfalls & dead ends

- **34k-line lock churn from a version pin.** `npm install --package-lock-only` re-resolves
  the entire tree. If you hit this: `git checkout package-lock.json`, then edit only the root
  `@playwright/test` spec string (the installed entry was already `1.61.1`). Verify with
  `npm ls @playwright/test` → clean 1-line diff.
- **Broken `node_modules/.bin` symlinks** (`playwright` *and* `vitest`). Environment rot, not
  your change. Bypass by invoking the module CLI directly:
  `node node_modules/@playwright/test/cli.js` / `node node_modules/vitest/vitest.mjs`.
- **`npx playwright install` failure is a decoy.** The headline "cannot download" masks a
  missing bin symlink; the CDN block is secondary. Diagnose the symlink first.
- **`POST /api/restart` failed once** mid-session (transient) — retried successfully.
- **`openspec change new` had no scaffold command** — author the four files directly, matching
  the active-change layout.
- **Ambient `openspec/groups/groups.json` churn** appears unbidden (dashboard reshuffles
  groups). Never commit it as part of an unrelated change.
- **Redeploy ≠ verification for test-infra changes.** Build+restart proves nothing regressed,
  not that the new behaviour works. The real proof was the live 1s fail-fast run.
