# How we did it: Cleaning up pi memory and folding procedures into skills — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with: *"Analyze memory, maybe there are things worth to extract to
memory to be permanent and can remove safely."* The real objective, once the two
steering turns landed, was broader than a one-shot purge: **audit the pi-hermes
memory stores, delete only provably-redundant rows (never lose a durable lesson),
then re-home the step-by-step *procedures* that were hiding inside memory entries
into the skills that actually trigger them** — leaving memory holding only
quick-recall facts and pointers.

## 2. TL;DR playbook

1. Locate the stores: `~/.pi/agent/pi-hermes-memory/sessions.db` (SQLite `memories`
   table, 292 rows) plus the re-rendered `.md` subsets (`MEMORY.md`, `USER.md`,
   `failures.md`, per-project files).
2. **Read the `consolidate-pi-memory-store` skill first** — it carries the safe
   procedure and the SQLite-direct-edit caveat. Don't improvise.
3. Query SQLite for true duplicate groups; **diff every candidate pair** before
   deleting — near-identical ≠ identical (the `<!--created…-->` annotation baked
   into content inflates char counts).
4. `cp sessions.db sessions.db.bak.cleanup-<ts>` **before any DELETE.** FTS
   auto-syncs via triggers (292→282). Verify integrity + FTS row-count match.
5. Hand-sync the `.md` subsets: you edited SQLite directly, so strip the deleted
   entries from the live `.md` too (one entry per block, lone `§` separators).
6. Prune old `sessions.db.bak*` backups — keep the 2 most recent + the fresh
   rollback backup. (Freed ~117 MB here.)
7. **Second pass (skill placement):** map each *procedural* memory fragment to an
   existing skill. Don't create new skills — fold the steps into `ship-change`,
   `release-cut`, `debug-dashboard`, etc.
8. Trim the now-redundant source memory rows to short **stubs** (quick-recall facts
   + `see <skill> Pitfalls` pointer). Update SQLite content via parameterized SQL,
   then hand-edit `.md` to match, bumping the `last=` annotation.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (read the map before touching anything).**
The AI listed the hermes stores, read the core `.md` files, then immediately opened
the `consolidate-pi-memory-store` skill instead of winging the procedure. *Why it
worked:* the skill encodes the SQLite/`.md` dual-source model and the "edit SQLite,
FTS auto-syncs, then re-sync `.md`" rule — skipping it would have desynced the two.

**Phase 2 — Evidence-first triage.**
It queried the `memories` table for duplicate groups (8 found), then **diffed each
pair** rather than trusting char-length. This caught two traps: rows `858–863` were a
botched 2026-06-23 re-save that baked an HTML comment into stored content (real
dups), while `498/506` looked like dups but **diverged in body** (kept both). Decision
point: the human implicitly trusted the AI's keep/delete table via `ask_user`
approvals.

**Phase 3 — Safe execution.**
Backup → DELETE 10 rows → integrity check → `.md` re-sync → backup pruning (~117 MB
freed). Every destructive step was preceded by a backup and followed by a
verification query.

**Phase 4 — Steering turn: "anything better placed as a skill?"**
The AI drew the line explicitly: *memory = facts/quirks you recall; skill = a
triggerable multi-step procedure you execute.* It found 3 procedural fragments buried
in memory and — critically — recommended **folding into existing skills**, not
minting new ones (which would duplicate `ship-change`/`release-cut`).

**Phase 5 — Fold + stub.**
Applied 3 skill edits (caveman style per project protocol), then on the final "yes"
trimmed the two large source memory rows (`835`, `698`) to stubs. Hit — and
diagnosed — an FTS quirk where `-` in `ship-change` is a NOT operator; used quoted
phrase search to verify.

## 4. Prompts that worked

- **Goal prompt** — *"Analyze memory… extract to memory to be permanent and can
  remove safely."* Effective because it paired the action (analyze/remove) with the
  **safety constraint** ("safely") up front, which anchored the whole
  backup-before-delete discipline.
- **High-leverage follow-up #1** — *"Is there anything in memory which better placed
  as skill?"* One sentence that opened an entire second workstream (the memory-vs-skill
  taxonomy) and produced the durable value of the session.
- **High-leverage follow-up #2** — *"yes"* — a one-word approval that unlocked the
  stub-trimming pass. Works because the AI had already laid out the exact plan and
  offered it as an explicit optional follow-up.

Stronger goal-prompt to reuse next time: *"Audit the pi-hermes memory stores. Delete
only provably-redundant rows (diff every pair, back up first), then tell me which
procedural entries belong in a skill instead."* — bundles both passes and the safety
rule in one shot.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| treat the task as a one-shot memory purge | *"anything better placed as a skill?"* | state both goals up front: "clean up AND re-home procedures into skills" |

Quality bars the human implicitly imposed (and the AI honored): never delete without
a diff, always back up before a destructive DB op, keep both SQLite and `.md` in sync.

No *new* skill was created — the session's insight was the opposite: **most "memory"

## 7. Pitfalls & dead ends

- **Char-length ≠ duplicate.** The `<!--created=…, last=…-->` annotation baked into
  stored content inflates length; `498/506` looked identical but diverged. → Always
  diff bodies before deleting.
- **SQLite and `.md` are two sources.** Editing SQLite directly leaves the `.md`
  subsets stale — you must hand-strip/hand-sync them. FTS, however, auto-syncs via
  triggers.
- **FTS5 treats `-` as NOT.** A verify query for `ship-change` failed not because the
  data was missing but because `-` is an operator — use a **quoted phrase**
  (`"ship-change"`) to search.
- **The memory tool's `old_text` matching breaks on em-dashes / backticks / `→`.**
  For entries containing those, update SQLite content via parameterized SQL directly
  (per the consolidation skill) rather than the memory tool.
- **Always back up `sessions.db` before DELETE/UPDATE** — this session made
  `.bak.cleanup-*` and `.bak.trim-*` copies before each destructive step.
