# How we did it: A scheduled pi-dashboard automation that consolidates Hermes memory — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator wanted a recurring maintenance task: *"Create an automation which
consolidate hermes memory. Run on every 4 hours. It helps manage to keep intact."*
The literal ask is a schedule; the *real* objective is **hands-off memory hygiene** —
keep the Hermes memory stores from silently hitting capacity, without ever destroying
unique entries. The critical constraint hidden in "keep intact" is **non-destructive
by default**: only true duplicates/junk may go, semantic merges need LLM judgment. The
delivery vehicle was clarified one turn in: not an OS-level cron, but a **pi-dashboard
automation** — a scheduled headless pi session managed by the dashboard's automation
plugin.

## 2. TL;DR playbook

1. **Scope the mechanism first.** State up front: "use the pi-dashboard automation
   plugin, not launchd/cron." This is the single most important guardrail — the AI's
   default for "run every 4 hours on macOS" is a LaunchAgent.
2. **Reconnoiter the store.** Inspect `~/.pi/agent/pi-hermes-memory/` (the live `.md`
   stores + `sessions.db` SQLite superset) and the existing `consolidate-pi-memory-store`
   skill to learn what's *safe to automate* vs. *needs judgment*.
3. **Learn the automation contract before authoring.** Read the plugin's
   `parseAutomationYaml`, the schedule/cron format (`*/n` steps), the skill-vs-prompt
   action path, the model resolver (`@role` values), and `startRun` cwd behavior.
4. **Author two files** at `~/.pi/automation/<name>/`: `automation.yaml` (trigger + run
   config) and `prompt.md` (safety-first instructions that drive the existing skill).
5. **Pick config deliberately:** cron `0 */4 * * *`; `action: prompt`; a *strong* model
   (`@coding`/Opus — consolidation is delicate); `mode: local`; `sandbox: workspace-write`;
   `concurrency: skip`; decide `visibility` consciously.
6. **Validate deterministically** — parse the YAML with the plugin's own schema (or the
   `yaml` package), confirm the cron fires at the intended ticks.
7. **Confirm the running dashboard armed it** via `GET /api/plugins/automation/list` —
   the server auto-scans global scope + an fs-watcher arms on change.
8. **Verify a real run** by tracing the run record + `server.log` for the spawned headless
   session, not by trusting the UI.

## 3. How the collaboration unfolded

**Phase 1 — Discovery & the mechanism pivot.** The AI first inspected the Hermes store
and the consolidation skill, correctly distinguishing the **deterministic-safe** part
(dedupe/junk-prune/VACUUM the SQLite `sessions.db`) from the **judgment-required** part
(semantically merging the small `.md` stores). It then proposed a macOS **launchd**
LaunchAgent. The human immediately redirected: *"No. Not launchd. pi-dashboard
automation."* That one correction reset the entire implementation surface. **Why the
pivot mattered:** the two mechanisms share nothing — a LaunchAgent is a plist + shell
script; a dashboard automation is a YAML + prompt discovered and armed by a running
server.

**Phase 2 — Learn the plugin contract.** The AI read the `add-automation-plugin`
sources: cron format, how a `prompt` vs `skill` action becomes a spawned session,
the model resolver's valid roles (`fast`, `planning`, `coding`, `compact`), and what
cwd a **global** automation spawns in (`$HOME`). **Decision point:** global scope was
chosen because Hermes memory is global, independent of which repo is open.

**Phase 3 — Author + validate.** Two files written; YAML validated against the plugin's
schema; cron confirmed. A first validation attempt hit a jiti/`.js` resolution snag and
was rerouted to the `yaml` package directly — a small dead end, not a blocker.

**Phase 4 — Prove it actually runs.** "It seems no session is running" triggered a
forensic trace: run record present but `status: running` with no card. The AI found the
real cause — `visibility: hidden` filters automation sessions out of the list — and
confirmed via `server.log` that a headless Opus session (`019ef4ba…`) had genuinely
spawned and was streaming. **The lesson:** verify runs from the run store + log, not the
UI.

**Phase 5 — Explain the missing chat pane.** "The automation run view is not showing chat
window." An `Explore` subagent harvested the run-view components; the AI traced
`AutomationRunMonitor.tsx` and the `shell-overlay-route` wiring and concluded the monitor
**by design** renders only status + `result.md` and **replaces** the detail panel, so no
`ChatView` mounts there. The live transcript is reachable only via the direct
`/session/:id` URL. This is a dashboard architecture fact, not a misconfiguration — and it
was saved to memory.

## 4. Prompts that worked

- **The goal prompt** — *"Create an automation which consolidate hermes memory. Run on
  every 4 hours. It helps manage to keep intact."* Effective on intent (what + cadence +
  the non-destructive bar), but **under-specified on mechanism**, which cost a full
  wrong-path proposal. Stronger kickoff: *"Create a **pi-dashboard automation** (not
  launchd) that runs the `consolidate-pi-memory-store` skill every 4 hours, non-destructive
  by default."*
- **High-leverage correction** — *"No. Not launchd. pi-dashboard automation."* Four words
  that saved the build. When you already know the delivery vehicle, name it in turn one.
- **Verification nudges** — *"it seems no session is running"* and *"the automation run view
  is not showing chat window"* both converted vague unease into concrete forensic traces
  and surfaced two durable architecture facts.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Default "every 4 hours on macOS" to a **launchd LaunchAgent** | "No. Not launchd. pi-dashboard automation." | Name the mechanism in the goal prompt: "a pi-dashboard automation, not cron/launchd" |
| Trust that a run wasn't happening because no session card showed | "it seems no session is running" → forced a log/run-store trace | Know that `visibility: hidden` filters automation sessions out of the list; verify via `server.log` + run records, not the UI |
| Assume the run-monitor overlay shows a live chat | "the automation run view is not showing chat window" | Remember `/automation/run/:sid` shows only status + `result.md`; watch live via `/session/:id` directly |

Quality bar the human held throughout: **"keep intact"** — non-destructive by default.
The AI honored it by baking backups (and 5-newest-backup pruning) and an "only consolidate
a `.md` store at ≥~80% capacity or clear redundancy" rule into `prompt.md`, and by choosing
a strong model so semantic merges don't corrupt data.

## 6. Skills, tools & memory created — and why they're effective

No new skill was created (the existing `consolidate-pi-memory-store` skill was reused).
**Two project memories were saved**, both capturing the same non-obvious dashboard fact:

- **What they capture:** the `/automation/run/:sid` overlay (`AutomationRunMonitor.tsx`)
  renders **only** status + `result.md`, never a chat/transcript pane — because
  `shell-overlay-route` **replaces** the detail panel. Live chat is only at `/session/:id`.
- **Why effective:** this converts a repeat "why is the chat missing?" investigation
  (which here cost an `Explore` spawn + a multi-file trace) into an instant answer. It's a
  design invariant, so it stays true.
- **When to invoke:** any future "automation run has no transcript / blank chat" report.

**Recommended skill that *should* exist:** *"author a scheduled pi-dashboard automation"* —
the sequence (scope-check → learn `parseAutomationYaml`/cron/model-resolver → write
`automation.yaml` + `prompt.md` → validate schema+cron → confirm via `/api/plugins/automation/list`
→ trace the real spawn in `server.log`) is clearly repeatable and would front-load every
guardrail in this playbook.

## 7. Pitfalls & dead ends

- **Wrong mechanism default.** The AI proposed launchd for "every 4 hours." *If you want a
  dashboard automation, say so in turn one* — otherwise you pay for a discarded plan.
- **jiti/`.js` resolution failure when validating YAML via the plugin's parser.** *If the
  plugin's own import chain won't resolve standalone, validate with the `yaml` package
  directly plus a standalone cron check.*
- **"No session running" is misleading for `visibility: hidden` automations.** The card is
  suppressed by design. *If a run seems absent, check `~/.pi/automation/runs/` and
  `grep` `server.log` for `started run … model=…` before concluding it failed.*
- **The run-monitor overlay never shows a live chat.** *Don't debug the monitor for a
  missing transcript — it's by design; open `/session/<sessionId>` directly.*
- **Double-arming under both `global:` and `folder:` scope** (a session had cwd `$HOME`).
  Harmless because `concurrency: skip` drops the overlap — runs exactly once. No action
  needed.
- **Project memory hit capacity (4912/5000) at the end** — fittingly the exact pressure the
  automation addresses. The AI declined to evict an existing entry to force a save.
