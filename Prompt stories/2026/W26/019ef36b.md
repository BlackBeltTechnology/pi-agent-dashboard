# How we did it: an FTS5 markdown knowledge base, from web research to a working package — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with a research question, not a build order:

> "Make a research, search web what is the best way to index hundreds of markdown file to be FTS5 indexed be able to index markdown changes and for LLM be a tool where can search information. If possible be directory based. What is the best practicies. I prefer be not a docker service, sqlite can viable options. If possible it can be driven as a SKILL (pi agent is used)."

The **real objective**, once the 27 steering turns clarified it, was much larger: *design and validate a local, directory-based markdown knowledge base for LLM retrieval — FTS5/SQLite only, no Docker, no vectors in v1 — then encode it as a fully-referenced OpenSpec proposal AND land a working, tested `packages/kb/` vertical slice.* The session moved research → empirical benchmark → OpenSpec proposal → real TypeScript implementation, all in one continuous ~4.5h arc.

## 2. TL;DR playbook

1. **Kick off with a constrained research prompt** — name the hard constraints up front (FTS5, SQLite-viable, no Docker, directory-based, driven as a pi SKILL). Constraints make the research converge instead of sprawl.
2. **Drill, don't accept the first answer.** After each research reply, push one layer deeper ("dig deeper", "add all features X has", "what are the pros/cons vs alternatives", "need proof").
3. **Get a real corpus early.** Unzip a heading-rich, deeply-nested markdown set into `doc-example/` (691 `.md`) and make every design claim testable against it.
4. **Benchmark before building.** Write a throwaway prototype (`/tmp/kb-proto`) + a golden query set; measure baseline BM25 vs BM25F vs +dedup; prove/disprove each feature with P@1/Recall@10/MRR/nDCG numbers.
5. **Only then scaffold the OpenSpec change** — `research.md` (every external link traced) + `proposal.md` + `design.md` (schema, chunking algo, graph CTEs) + `tasks.md` + delta spec; run `openspec validate` after every edit.
6. **Fold each new research thread back into all artifacts** (Turso/Limbo eval, pluggable sources, retrieval-quality features, dox) — keep proposal/design/spec/tasks in sync, revalidate.
7. **Build the vertical slice for real** in `packages/kb/`: types/`KbStore` → chunker → `node:sqlite` FTS5 store → indexer → config → CLI → `kb eval` harness → packaged SKILL. TDD with vitest scoped to the package.
8. **Verify against the real corpus** — the package must reproduce the prototype's golden numbers (P@1 0.80, Recall 0.95) or the design is wrong.

## 3. How the collaboration unfolded

**Phase A — Research & grounding (prompts 1–6).** Eight `web_search` + `fetch_content` calls established FTS5-BM25-over-SQLite as the lexical baseline, structural heading chunking as the standard, and a Tier-1 heading-graph (`nodes`/`edges` + recursive CTEs) for the "knowledge graph" ask. The AI kept trying to hand the answer to pi's built-in **context-mode**; the operator forced deeper investigation of pi's actual hook/event surface (`tool_result`, `tool_call`, `input`, `registerTool`) rather than settling for the existing tool. *Why it worked:* every claim got grounded in the real `extensions.md` / bridge source before it was written down.

**Phase B — Empirical validation (prompts 7–9, 20–21).** The operator supplied a real corpus (`compsych-letter-demo2.zip` → `doc-example/`, 691 md). The AI indexed it (context-mode: 691 → 8,600 sections) and then built a **standalone prototype** to benchmark the *actual design* against a 20-query golden set. Headline finding: **BM25F lifts P@1 0.55 → 0.80**; **dedup collapses 23% cross-tree duplicates** (P@5 → 0.95); **pure lexical fails on paraphrase (Recall 0.11)** but **synonym/query expansion recovers it to 1.00** with no model. This turned every design decision from assertion into data.

**Phase C — OpenSpec authoring (prompts 10–11).** Ran the pre-scaffold coherence check, then scaffolded `openspec/changes/add-markdown-knowledge-base/` with research dossier (every external link traced), proposal, design (Mermaid + full SQL schema + chunking algorithm + graph CTEs), tasks, and an 8-requirement delta spec. `openspec validate` after each edit.

**Phase D — Iterative deepening (prompts 12–27).** Each steering prompt opened a research thread that was investigated, decided, and **folded back into all five artifacts**: TypeScript-vs-Python (→ TS, `better-sqlite3`/remark); Limbo/Turso (proof-hunted `v1cc0/aimem`, verdict: no FTS5 → deferred behind a `KbStore` seam); pluggable sources (filesystem/git/npm/https via a `SourceResolver`, reusing pi's package-source model + TOFU trust); retrieval-quality features (BM25F, proximity, MMR, parent/child, `kb eval`); dox evaluation (don't replace the file-index; borrow the in-prompt-map idea); directory-level AGENTS.md + indexing AGENTS.md/source `.md`. Spec grew to 18 requirements.

**Phase E — Real implementation (prompts 27–28).** "Keep going" → the Phase-1 vertical slice. A decisive environment probe found **Node 24's built-in `node:sqlite` ships full FTS5** — so the package needs **zero new dependencies** (superseding the `better-sqlite3` decision). Built `packages/kb/`: `KbStore` interface → chunker → `SqliteFtsStore` → indexer (mtime→sha256 incremental) → config layering → CLI → `kb eval` → packaged SKILL. Verified live (cold index 691 files/6,541 chunks in ~4.6s; no-op reindex 29ms; golden P@1 0.80). 13 vitest tests pass.

## 4. Prompts that worked

- **The goal prompt (Prompt 1)** was effective because it front-loaded *constraints* (FTS5, no Docker, SQLite-viable, directory-based, SKILL-driven). A weaker version — "how do I search my markdown files?" — would have produced a vendor listicle. **Reuse this shape:** state the non-negotiables in the first sentence.
- **"No. Dig deeper. Add all features context-mode is adding…" (Prompt 6)** — a high-leverage redirect that stopped the AI from off-loading the problem to an existing tool and forced a feature-parity investigation.
- **"Reference all external links so when needed it can be traced. The whole research can be a separated markdown file inside the proposal" (Prompt 11)** — set the durability bar. This is why `research.md` is a traceable dossier, not a summary.
- **"I would like to make some tests before… Tests the indexing and the retrieval performance, reliability, precision" (Prompt 20)** — the single most valuable steer: it demanded *evidence before spec*, which is what made the proposal defensible.
- **"need proof" (Prompt 14)** — three words that turned a plausible claim (a KB uses Turso's new engine) into a verified code-citation trail (`v1cc0/aimem`, `turso = {features=["fts"]}`).
- **Short unlocks — "yes", "record", "keep going"** — worked *only because* the AI had already laid out concrete options; the operator was approving a specific plan, not issuing a vague go-ahead.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Off-load the problem to pi's existing context-mode | "No. Dig deeper. Add all features context-mode is adding" | State up front: "design a NEW system with feature-parity, don't recommend an existing tool" |
| Assert design choices without evidence | "make tests… performance, reliability, precision" before repeatedly | Demand a prototype + golden-set benchmark BEFORE writing the spec |
| Accept a plausible external claim | "need proof" | Require a traceable citation (repo + line) for every "system X does Y" claim |
| Default to Python for a data/indexing task | "Is it possible to integrate to typescript instead of python?" | State repo-native language (TS) as a constraint in the goal prompt |
| Leave a latent design bug (per-root DB) unflagged | (AI self-caught it, but only when the operator kept probing DB location) | Cross-check every default against the invariants it interacts with (here: dedup is cross-root → DB must span roots) |
| Emit a stray `newText_alt`/`newText` field on edits (8 edit errors) | re-run the edit cleanly | Watch for repeated malformed edit calls; redo, don't stack |
| Cite an idea (`kb manifest`) as if already specced | "fix one dangling cross-reference" | Mark not-yet-specced ideas as *proposed*, never as existing |

## 6. Skills, tools & memory created — and why they're effective

**Memory saved (1, project scope):** the KB config contract — *config lives at project-level `.pi/dashboard/knowledge_base.json`; a global settings file provides defaults when no project config exists.* This is effective because the config-location decision recurs across every later artifact (proposal, design, CLI, tests); persisting it kept the layering consistent instead of re-derived each time.

**No skill was created, but one clearly should be.** This session is a repeatable meta-workflow: *research-thread → empirical benchmark → fold into OpenSpec artifacts → validate → repeat*. A `research-to-openspec-proposal` skill capturing that loop (coherence check → dossier with traced links → prototype benchmark → 5-artifact scaffold → `openspec validate` after each edit) would remove the improvisation. Invoke it whenever a research question is destined to become a buildable proposal.

**Reusable assets the session produced (adopt these patterns):**
- The **`KbStore` / `SourceResolver` seams** — isolating storage and source-resolution from indexing let Turso be evaluated and deferred without touching the indexer. Reuse the "resolution decoupled from indexing" pattern whenever a backend is uncertain.
- The **`kb eval` golden-set harness** — makes retrieval quality a number (P@1/Recall/MRR/nDCG), so every tuning change is measured and regressions are gated.

## 7. Pitfalls & dead ends

- **Local embeddings/reranker can't run here.** This is an **x64 macOS** box; `onnxruntime-node` ships no `darwin/x64` binary and transformers.js hard-requires it. Bun+ONNX crashes, WASM fallback fought the loader. *If you hit this, don't burn time on native ML locally — it's itself evidence for the lexical-first decision.*
- **Incremental reindex silently broken at first.** The indexer didn't persist file state after indexing a changed file, so `files` count stayed 0 and every reindex reported 691 changed. *If reindex never becomes a no-op, check you persist mtime+sha256 per file after upsert.* (Fixed → 29ms no-op reindex.)
- **Unit fixtures too tiny.** Two tests failed because fixtures were shorter than the 100-char tiny-chunk-merge threshold (sections merged away; empty-body heading → no graph node). *Make chunker fixtures realistic (>100 chars, non-empty bodies).*
- **CLI used `require` in an ESM package** — breaks at runtime. *Use top-level `import`.*
- **`openspec validate` wants `SHALL` on a requirement's first line** — reword requirements to lead with SHALL.
- **Repeated stray-field edit errors** (8 total) — an edit call kept emitting a `newText_alt` field; re-running the call cleanly fixed it each time.
- **`maxFiles` default = 200** bit the 691-file corpus in context-mode; the new package defaults to *no cap*.
