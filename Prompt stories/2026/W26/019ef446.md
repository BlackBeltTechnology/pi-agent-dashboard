# How we did it: Converting a monolithic doc-index into an in-place AGENTS.md tree — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-only
stance, no implementation. The kickoff was the skill's stance prompt, but the *real*
objective surfaced immediately: **should this repo adopt `agent0ai/dox`'s in-place
`AGENTS.md`-per-directory model instead of its current centralized `docs/file-index.md`
splits — 719 file rows / ~365 KB across 8 files, with a 118 KB client split that had
become as unwieldy as the root-`AGENTS.md` balloon it was meant to cure?**

Over five steering turns the objective sharpened into three linked deliverables:
1. An OpenSpec **proposal** to migrate to a per-sub-area `AGENTS.md` tree (pure DOX, delete the splits).
2. Fold the **auto-update enforcement** half of the idea into the *already-active* `add-markdown-knowledge-base` change (one `tool_result` hook, two jobs) instead of spawning a competing plugin.
3. Answer the **cold-start** question (treeless project) and spec `kb dox init` + a nudge, then **commit + push** as a stacked `jj` branch.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore`) — think, don't build. State the architectural question in one sentence.
2. **Ground before sketching**: fetch the upstream tool (`agent0ai/dox`) and read *your harness's* actual behavior. Here the linchpin was pi's context-file loading rule.
3. **Surface the one pivotal fact** that reshapes the decision (pi loads `AGENTS.md` from root + ancestors + cwd, **never descending**) and show what it implies for both options.
4. **Get the human's three granularity/format decisions** in one cheap round (`ask_user`), then lock them into artifacts.
5. **Run the mandatory pre-scaffold coherence check** + match an existing change's exact proposal/design/tasks/spec format before writing.
6. **Scaffold the OpenSpec change**, then `openspec validate` — fix schema errors (SHALL must be on the *first line* of a requirement body).
7. **Save the durable fact** (context-file loading rule) as a `tool-quirk` memory.
8. When a follow-up idea ("make it a plugin") arrives, **decompose it** (content / protocol / enforcement) and fold only the runtime half into the existing active change — don't create a second competing extension.
9. **Answer cold-start** by verifying default indexing on a fresh project first, then spec `kb dox init` + nudge.
10. **Commit surgically** with `jj`: commit only the new change's files into a *stacked* bookmark, leave unrelated working-copy edits untouched, push, and confirm remote refs.

## 3. How the collaboration unfolded

**Phase A — Discovery & the pivotal fact.** The AI fetched `agent0ai/dox`, then read
pi's README to pin down *exactly* how `AGENTS.md` is loaded. It found the crux: pi
concatenates global + ancestor + cwd `AGENTS.md` at startup but **never descends into
children**. That single fact reframed the whole choice — in a DOX layout, child
`AGENTS.md` become read-on-demand files *exactly like the current splits*, so neither
model bloats root context; DOX just wins on **locality + drift-resistance**. *Why it
worked:* the AI refused to sketch until the one decision-determining fact was resolved.

**Phase B — Decisions & scaffold.** The human answered three open questions in a
three-line steering turn (`1. file.agent.md - only just larger LOC; 2. ok; 3. ok`).
The AI ran the repo's pre-scaffold coherence check, matched a recent change's format,
quantified the blast radius of deleting `docs/file-index*.md` (~5 files + 2 protocols),
then created the change and validated it — hitting and fixing an OpenSpec parser quirk.
It saved the context-file rule as a memory.

**Phase C — The plugin decomposition.** Human asked whether this could be a
pi-dashboard plugin injecting DOX instructions + auto-update. The AI **decomposed the
ask into three layers** — CONTENT (the tree, no runtime), PROTOCOL (DOX rules, a context
file, no runtime), ENFORCEMENT (stale-row nudge, the *only* code) — and folded the
enforcement job into the KB change's **existing** Phase-2 `tool_result` hook (one hook,
two jobs) rather than a competing extension.

**Phase D — Cold-start.** Human asked what happens opening a project with no
`AGENTS.md`. The AI **verified default indexing on a fresh project before answering**,
then split the answer cleanly: *indexing works with zero AGENTS.md; hierarchy is
bootstrapped on demand* via global protocol + `kb dox init` + a nudge — all specced
into both changes.

**Phase E — Commit & push.** The repo uses **jj**. The AI inspected real jj state,
discovered its KB fold-ins were *already* absorbed into the bookmark commit, and that
the working copy held the new change mixed with two unrelated files (`.gitignore`,
`groups.json`). It committed **only** the convert-docs files into a stacked bookmark,
pushed, and confirmed both remote refs against GitHub.

## 4. Prompts that worked

- **The goal prompt** (the `openspec-explore` stance) was effective *because* it forbade
  implementation and licensed deep grounding — the AI spent its first phase reading, not
  writing. A stronger explicit kickoff: *"Explore mode: should we convert docs/file-index
  to an in-place AGENTS.md tree like agent0ai/dox? Ground in pi's context-loading rules first."*
- **High-leverage follow-up `1. file.agent.md - only just larger LOC that make sense / 2. ok / 3. ok`** — a three-line answer that unlocked the whole artifact write. Terse but decisive.
- **`Can be it a pi-dashboard plugin which injecting the default DOX agent instructions...`** — a good *what-if* that forced the decomposition; the AI's value was splitting it, not answering yes/no.
- **`When I open a project which does not have AGENTS.md will be able to handle the hierarchy and index?`** — a cold-start probe that exposed a real seam; effective because it targeted the edge case.
- **`commit changes to branch` → `push`** — minimal, trusting the AI to handle the jj mechanics and exclusions.

## 6. Skills, tools & memory created — and why they're effective

- **Memory (tool-quirk):** *pi loads `AGENTS.md`/`CLAUDE.md` from `~/.pi/agent/AGENTS.md`
  (global) + ancestor dirs walking up + cwd — it does **not** descend into children.* This
  is the fact the entire architectural decision hinged on; saving it means the next agent
  reasoning about DOX/context-file layout won't re-derive it. Invoke whenever a task
  concerns where per-file docs live or whether nested `AGENTS.md` auto-load.
- **No skill was created**, but the repeatable move here — *"decompose a feature ask into
  content / protocol / enforcement layers and fold the runtime half into the existing
  active change"* — is a strong candidate for a planning skill. Recommend creating
  `decompose-feature-into-layers` if this pattern recurs.

## 7. Pitfalls & dead ends

- **OpenSpec validator rejects `SHALL` on line 2.** The parser reads only the *first line*
  of a requirement body as the requirement text. Fix: lead the requirement's first line
  with `SHALL`/`MUST`. (Cost 3 retries here.)
- **Multi-edit shape error.** A batched `edit` with replacements not each as their own
  object fails. Each replacement must be a separate object.
- **Dangling sentence after a large edit.** One fold-in left a broken sentence and a
  duplicate `6.4` label — always re-view the anchor region after a big edit; anchors shift.
- **jj working-copy surprise.** Edits made earlier were already *absorbed into the bookmark
  commit*, not sitting in `@`. Always `jj st` + `jj log -r '::@'` before committing to see
  where changes actually live, and to spot unrelated files to exclude.
