# How we did it: Diagnosing a "missing" extension and shipping a source-switch skill — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** ("Enter explore mode. Think deeply…") with a
practical worry underneath it: *"my extension isn't showing up in this pi session —
is my install broken?"* The real objective, once the steering turns clarified it, was
threefold: (1) **explain** why a freshly-installed local monorepo extension wasn't
loaded in the running session, (2) **reconcile** the tangle of extensions that were
being loaded from *two* sources at once (local monorepo path **and** published npm),
and (3) **capture the fix as a reusable project skill** so the dev-vs-distribution
toggle never has to be reasoned out by hand again.

The punchline: **nothing was broken.** The extension install landed in `settings.json`
7 minutes *after* the session booted, and pi snapshots `packages[]` once at init.

## 2. TL;DR playbook

1. **Don't assume a broken install — check timing first.** Compare `settings.json`
   mtime against the session process start time (`ps -eo pid,lstart,command`). A write
   that postdates session boot = "installed, just not loaded here."
2. **Map every extension to its source(s).** For each monorepo package, list where it
   is referenced: global `~/.pi/agent/settings.json` `packages[]` (npm: vs dir-path)
   **and** project `.pi/settings.json` overlay (`+packages/…`). Find the double-sourced ones.
3. **Decide one source per package.** Dev machine → local path (edits take effect).
   Consumers → npm (frozen build). These are *by design*, not a bug.
4. **Back up, edit, re-validate JSON.** `cp *.bak-reconcile-$(date +%s)`, edit both
   layers, then `python3 -c "import json; json.load(open(...))"` before trusting it.
5. **Reload — but know its limit.** `npm run reload` re-loads bridge/extension *code*,
   but **added/removed `packages[]` entries** are read at session **init**; a running
   session may need a fresh spawn to pick them up.
6. **Turn the fix into a skill.** Follow repo skill conventions (TS under `scripts/`,
   `npx tsx`, JSDoc header, SKILL.md frontmatter). Build a `status | local | npm` toggle
   that guarantees exactly one source per package across both layers.
7. **Round-trip test the script** (npm ↔ local) before writing SKILL.md; clean up test backups.
8. **Commit surgically.** In a dirty tree, stage only your files + your index hunk
   (`git add -p`); leave machine-specific config and other people's in-progress work alone.

## 3. How the collaboration unfolded

**Phase 1 — Diagnosis (timing, not breakage).** The AI's first instinct was correct
and fast: `~/.pi/agent/extensions/` was empty (a red herring), so it pivoted to *when*
things happened. It cross-referenced `settings.json` mtime (22:44) against the session
PID's start time (22:37) and drew a timeline showing the install landed 7 minutes too
late for this process. **Why it worked:** it treated "not loaded" as a lifecycle
question, not a corruption question — the cheapest hypothesis first.

**Phase 2 — The two-layer reveal.** Digging further, the AI found kb-extension
referenced *twice* from *different* sources: the project overlay pointed at the live
monorepo tree, while the global settings pointed at a **separate frozen npm snapshot**.
Decision point: the human clarified (steering #1) that this duplication is intentional
— *local for my dev box, npm for other users*. That single sentence collapsed a scary
"conflict" into a clean dev-vs-distribution model.

**Phase 3 — Reconciliation.** With "yes" (steering #2) the AI built a full source map
of every monorepo extension, found exactly **two** real double-source problems
(kb-extension, and the bridge wired twice), read each package's `pi` field to get the
right entry points, backed up both settings files, edited them to **one source per
package**, and re-validated JSON. It ended each monorepo package with a single resolvable source.

**Phase 4 — Reload with an honest caveat.** On "reload" (steering #3) the AI ran
`npm run reload` but flagged the limit truthfully: package-list changes are init-time,
so a fresh session is the guaranteed path. **Why it worked:** it didn't oversell the reload.

**Phase 5 — Skillify.** On steering #4 ("create a project pi skill…") the AI inspected
existing skill conventions, wrote `switch-source.ts` + `SKILL.md`, round-trip tested the
toggle on one package, cleaned up test backups, and delegated the file-index row to a
`general-purpose` subagent per the repo's Documentation Update Protocol.

**Phase 6 — Surgical commit.** On "commit" (steering #5), facing a tree with ~150
unrelated modified files (honcho/jj plugin removals from other sessions), the AI staged
**only** its 2 skill files + its additive index hunk via `git add -p`, explicitly leaving
out the settings reconciliation (machine-specific) and everyone else's work. Commit `c921546c`.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Entering explore mode set the right stance —
  *investigate and explain, don't implement*. This kept the AI from jumping to a
  premature "reinstall" fix and let it uncover the timing root cause. A stronger
  kickoff would name the symptom directly: *"My local extension isn't loading in this
  session — investigate why before changing anything."*
- **Steering #1 — the domain correction** ("everything in development mode… but other
  users will use as npm package"). Highest-leverage prompt of the session: it reframed
  a flagged "conflict" as intended dev-vs-distribution design and defined the target
  end-state (one source per package, chosen per environment).
- **"yes" / "reload" / "commit"** — terse high-leverage confirmations that each unlocked
  a full phase (build the map → apply reload → land the change) because the AI had
  already laid out an explicit plan for the human to approve.
- **Steering #4 — "Create a project pi skill which able to switch between NPM and local
  extension packages."** Turned a one-off manual reconciliation into a durable,
  reproducible tool. The reusable-artifact ask is what makes this session worth distilling.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Flag two-source loading as a "conflict/bug" | "dev mode on my machine, npm for other users" | State up front that local-vs-npm duplication is *intentional* dev-vs-distribution |
| Explore broadly before converging | "yes" to approve the reconciliation plan | Give a crisp end-state ("exactly one source per package") so it converges faster |
| Present a fix and pause | terse confirmations ("reload", "commit") | Keep the explicit-plan-then-approve rhythm; it makes 1-word steering safe |
| Risk over-committing in a dirty tree | "commit" (implicitly: just my work) | Say "commit ONLY my new skill files" so surgical scoping is the default |

Quality bars the human imposed implicitly and the AI honored: **truthful caveats**
(reload vs init-time package list), **backups before edits**, **JSON re-validation**,
and **surgical commits** in a shared working tree.

## 6. Skills, tools & memory created — and why they're effective

**`switch-extension-source` project skill** (`.pi/skills/switch-extension-source/`,
`SKILL.md` + `scripts/switch-source.ts`):

- **What it captures:** a `status | local <pkg> | npm <pkg> [--overlay]` toggle that
  moves a monorepo extension/skill package between its published npm source and its
  local working-tree source, across *both* config layers (global `packages[]` +
  project overlay).
- **Why it's effective:** it **guarantees exactly one source per package** — every
  switch purges all other representations, so no shadowing / double-load. It backs up
  every edited file and re-validates JSON before writing, and it leaves
  dashboard-managed bridges (flows/goal/automation) alone.
- **When to invoke it next time:** "my edits don't take effect", "load local
  extension", "test the published npm build", or any dev-vs-distribution reconciliation.

**Subagent used:** `general-purpose` to add the file-index rows per the repo's
Documentation Update Protocol (caveman-style docs delegation) — keeps the main agent
out of `docs/` prose editing.

## 7. Pitfalls & dead ends

- **Empty `~/.pi/agent/extensions/` is a red herring** — this monorepo registers
  extensions via `settings.json` `packages[]`, not that directory. Don't chase it.
- **`for` loops choke under the ctx-mode shell** — the one failed command. Use plain
  `bash`/`python3` heredocs for multi-path checks instead of shell `for` loops.
- **`npm run reload` ≠ full re-init.** It reliably re-loads bridge/extension *code* but
  **not** newly added/removed `packages[]` entries (read at session init). If a change
  won't show, **spawn a fresh session** — that's the guaranteed path.
- **Committing in a dirty shared tree.** ~150 unrelated files (jj/honcho removals from
  other sessions) were interleaved, even inside the same index file. Use `git add -p`
  to stage only your hunk; never `git add .`.
