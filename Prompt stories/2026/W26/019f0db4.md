# How we did it: bootstrap-publishing 3 orphaned monorepo packages & wiring them into the recommended list — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened innocuously — `"what skills do you have?"` — but the *real*
objective emerged over the steering turns: **find the monorepo packages that are set
up to publish but never actually hit npm, bootstrap-publish them so npm Trusted
Publisher (CI OIDC auth) can be configured, then surface them everywhere they should
appear** (the curated recommended-extensions list) and commit the result. The trigger
prompt for the real work was `"Is there any missing plugin / extension in this
monorepo which is not released?"` followed by `"release 0.5.4 to be able to set the CI
trusted auth"`.

## 2. TL;DR playbook

1. **Inventory publish state.** Walk every `package.json`; classify each as
   *published*, *public-but-absent-from-registry*, or *intentionally `private: true`*.
   Cross-check the local version against what the registry actually serves.
2. **Name the 3 orphans.** Here: `anti-slop-frontend` (version-skewed at 0.1.0),
   `pi-dashboard-eng-disciplines`, `pi-dashboard-authoring-toolkit` — all `private:
   false`, `publishConfig.access: public`, `files` whitelist set, never on npm.
3. **Understand the chicken-and-egg** before touching npm: Trusted Publisher OIDC
   config requires the package name to *already exist* on the registry. So a one-time
   **local authenticated bootstrap publish** (no provenance) is mandatory first.
4. **Dry-run each publish** (`npm publish --dry-run`), then publish for real. Bump the
   version-skewed package to lockstep (0.1.0 → 0.5.4) first.
5. **Don't trust a 404 from the registry read** right after publish — CDN replication
   lags. Confirm success by re-publishing unmasked and reading the `E403 cannot
   publish over previously published version` — that error *proves* the write landed.
6. **Wire them into discovery.** Add each as a `status: "optional"` entry in
   `packages/shared/src/recommended-extensions.ts` (the curated manifest behind
   `GET /api/packages/recommended`, the wizard, and the Packages-tab banner).
7. **Fix the hardcoded test.** Update the two id-list assertions and the count-in-title
   in `recommended-extensions.test.ts` (15 → 18). Run via `npm test` wrapper.
8. **Commit surgically** — group only the intended files; leave unrelated pre-existing
   working-tree changes untouched unless the user explicitly asks to include them.

## 3. How the collaboration unfolded

**Phase A — Discovery (skills audit).** The first three prompts were a warm-up: list
skills, then a correction about mis-categorizing `veo-showreel-production-kit`, then a
regroup by on-disk location. Low-stakes, but it established the human's expectation of
*precise, honestly-labeled* answers.

**Phase B — Publish-state inventory.** On "any missing plugin not released?", the AI
walked every workspace `package.json` and produced a 3-bucket table (published /
public-but-unreleased / intentionally-private). The effective move: distinguishing
`private: true` (by design, not a problem) from `private: false` + absent-from-registry
(the real orphans).

**Phase C — Bootstrap publish.** The AI **read the trusted-publisher docs and paused
to confirm before executing** — the right instinct for an irreversible npm write. It
surfaced the chicken-and-egg (OIDC needs the name to pre-exist), dry-ran all three,
bumped anti-slop to lockstep, then published. It correctly diagnosed the post-publish
404 as CDN lag rather than failure, and *proved* success via the E403-on-republish.

**Phase D — Discovery wiring.** On "Is it added to recommended extensions?", the AI
located the authoritative curated manifest (`recommended-extensions.ts`), confirmed the
3 were absent, proposed `optional` entries matching the existing skill-only shape, got
a one-char `"1"` go-ahead, added them, fixed the hardcoded test, ran tsc + 18 tests.

**Phase E — Proposal triage + commit.** Two tangents: ranking 26 Electron proposals by
gain-per-effort, and a factual correction (portable `.exe` was *already dropped* —
proposal text was stale). Finally, `"commit changes, groups.json too"` bundled the
three files into one commit.

## 4. Prompts that worked

- **Goal prompt** — `"Is there any missing plugin / extension in this monorepo which
  is not released?"` Effective because it's a *state question* the AI can answer
  exhaustively by scanning files, forcing a complete inventory before any action.
- **High-leverage follow-up** — `"release 0.5.4 to be able to set the CI trusted
  auth"`. This one line encodes the *why* (CI OIDC), which let the AI reason about the
  chicken-and-egg constraint instead of blindly publishing.
- **`"1"` / `"commit changes, groups.json too"`** — terse unlocks that worked because
  the AI had already laid out an explicit numbered plan; the human just selected it.
- **Rewrite of a weak prompt:** instead of `"Is it added to recommended extensions?"`,
  a future operator should say `"add the 3 newly-published packages to
  recommended-extensions.ts as optional entries and update the test"` — same outcome,
  one turn instead of two.

## 7. Pitfalls & dead ends

- **`| tail -N` masks npm's exit code** — the pipe's exit status comes from `tail`, so a
  failed publish can look like success. Re-run unmasked when in doubt.
- **Registry read 404 right after publish is normal** (CDN replication lag, up to a
  minute for brand-new scoped names). Don't treat it as failure; the write side already
  knows — an `E403 cannot publish over previously published version` on retry is the
  real proof.
- **`vitest` `.bin` symlink was missing** — invoke the project's `npm test` wrapper
  (which sets `HOME`/`NODE_OPTIONS`) or call `node node_modules/vitest/vitest.mjs`
  directly rather than relying on PATH.
- **`sync-versions.js` erroring is benign** for standalone skill packages — it trips on
  pre-existing off-lockstep private packages (`session-distiller@0.0.0`), not the ones
  being published.
- **Hardcoded test assertions** — adding recommended entries silently breaks the
  count-in-title + id-list tests; update both when the manifest grows.
- **Stale proposal prose** — the `fix-windows-portable-exe` proposal claimed a target
  "still wired" that had already been dropped. Verify against live source before acting.
