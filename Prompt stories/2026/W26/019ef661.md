# How we did it: Consolidate a research-doc home + ship a research-doc skill-plugin — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** — a "think, don't implement" stance — with an
open-ended question about where research/planning docs should live so a *new* pi
session can find them if needed. The real objective only crystallized after the first
steering turn: **establish a process rule** — "when you create an OpenSpec proposal,
save the research" — and give that research a single, indexed home. It grew into three
concrete deliverables: (1) consolidate four scattered doc buckets (`plan/`, `plans/`,
`research/`, `architecture-notes/`) into one indexed `docs/research/` home; (2) add a
one-line convention to `AGENTS.md`; (3) package a reusable `research-doc-synthesis`
skill as a monorepo skill-plugin — then land it via a clean OpenSpec proposal, commit,
PR, and local-branch reconcile.

## 2. TL;DR playbook

1. **Start in explore mode**, but force the AI to *ground before theorizing*: "check
   what's actually in the repo first." It surfaced four redundant doc dirs, none
   indexed anywhere — reframing the ask from "add a pointer" to "consolidate + index."
2. **Name the process rule, not the artifact:** "add instructions to AGENTS.md when an
   OpenSpec proposal is created — save the research." This flipped the analysis from
   per-doc plumbing to a convention.
3. **Let the repo settle design tradeoffs.** The AI discovered `.pi/skills/openspec-*`
   is *gitignored/vendored* (a rule placed there evaporates) and that OpenSpec already
   designates `design.md` as the rationale home — so the convention became the
   *non-redundant half* only, placed in the git-tracked `AGENTS.md`.
4. **Consolidate with `git mv`** (preserve history), fix the few live inbound refs with
   `sed`, add an in-dir `README.md` **+** one `docs/file-index.md` row (two-layer
   discoverability).
5. **Gate the skill decision** ("is it worth a skill?") and scope it to the durable
   core — a doc-production procedure + stable template, not "do web search."
6. **Package as a skill-plugin** by copying the repo's proven precedent
   (`packages/dashboard-plugin-skill/`): `pi.skills` + `files` in `package.json`,
   version matching the **lockstep** line.
7. **Scaffold the OpenSpec change via the CLI** (`openspec new change …`), write the
   four artifacts, `openspec validate --strict`, mark tasks `[x]` (work already landed).
8. **Commit surgically**, branch from *fresh* `origin/develop`, cherry-pick, push, open
   the PR, then reconcile local `develop` back to origin.

## 3. How the collaboration unfolded

**Phase A — Ground the problem (Discovery).** In explore mode the AI resisted
theorizing and ran `ls`/`grep` first. It found four doc buckets for one kind of content,
*zero* index references, and — the deciding fact — that the OpenSpec skills are
gitignored. That single discovery eliminated the "natural" home (the skill) and pushed
the convention into `AGENTS.md`. *Why it worked:* grounding turned a vague "where should
this go" into a bounded, evidence-backed decision.

**Phase B — Consolidate (Execute).** All 9 docs were `git mv`'d into a flat
`docs/research/`, empty dirs removed, 5 stale refs `sed`-fixed, and a prose `README.md`
index written (the human explicitly vetoed caveman style for this new home). Two-layer
discoverability: in-dir README + one `file-index.md` row.

**Phase C — Decide + build the skill (Design → Generate).** The human asked "is it
worth a skill?" The AI treated it as a *should-we* question, mapped existing coverage
(librarian, web_search, the new convention) against the gap, and concluded yes — scoped
to the doc-production procedure. It then copied the `dashboard-plugin-skill` precedent
exactly, matching the `0.5.4` lockstep version, and baked in a grounded caveat (in-agent
`web_search({queries})` is *sequential* — real parallelism only comes from `@fast`
subagent fan-out).

**Phase D — Formalize + land (Verify → Ship).** Scaffolded the OpenSpec change with the
CLI, wrote proposal/design/tasks/spec, validated strict. Then the git dance: a surgical
commit excluding an unrelated C4 file, a feature branch off fresh `origin/develop`, a
cherry-pick (additive merges auto-resolved), PR #160, and a careful `develop`
reconcile that verified both local-only commits were preserved elsewhere before any
hard reset.

## 4. Prompts that worked

- **Goal (explore mode):** effective because it imposed a *stance* — the AI grounded in
  the repo before proposing, avoiding a speculative design.
- **"add instructions to AGENTS.md when openspec proposal created, save the research"** —
  a high-leverage reframe: it named the *process rule*, redirecting from per-doc
  plumbing to a durable convention. Stronger phrasing: "Add a convention to AGENTS.md:
  when an OpenSpec proposal is created, persist its research to an indexed home."
- **"yes, consolidate, but do not make caveman style"** — a short unlock + an explicit
  quality bar (prose, not the repo's caveman docs style) in one line.
- **"Is it worth to create a skill for that?"** — invited a should-we analysis instead
  of blind building, and seeded the `@fast` parallel-websearch idea.
- **"yes. And be a skill-plugin in mono repo"** — a two-word unlock that set the exact
  packaging target.

## 6. Skills, tools & memory created — and why they're effective

- **`research-doc-synthesis` skill-plugin** (`packages/research-doc-skill/`). Captures
  the *how* of producing a `docs/research/` doc: fan-out via `@fast` subagents for real
  parallelism, a stable skeleton (TL;DR · Question · Context · Findings · …), synthesized
  content, and a save-to-indexed-home step. *Why effective:* it slots precisely between
  the convention (WHERE/format) and the techniques (librarian/web_search) — turning
  scattered searching into a consistent, indexed artifact. *Invoke when:* a proposal's
  research outlives its `design.md` and needs a durable home.
- **The `AGENTS.md` convention line** (non-redundant half only): research → `design.md`;
  if it outlives the change → `docs/research/`, referenced from `proposal.md`. *Why
  effective:* it lives in the git-tracked, always-loaded file, and deliberately does NOT
  restate what OpenSpec already says.

## 7. Pitfalls & dead ends

- **`for` loop ran under `sh`, not bash** in `ctx_batch_execute` — the loop syntax broke.
  *Fix:* run shell loops through the Bash tool, not the batch tool.
- **`&&` chained off `tail` masked a real exit code** (a `sync-versions` drift). *Fix:*
  inspect full output; don't let a pipe's success hide the upstream command's failure.
- **Pre-existing lockstep version drift** (`mockup-loop`, `kb`, `kb-extension` at seed
  versions). *Fix:* recognize it as out-of-scope; keep your package at the released
  lockstep (`0.5.4`), don't "fix" unrelated seed packages.
- **Vendored skill home is a dead end** — `.pi/skills/openspec-*` is gitignored, so a
  rule placed there evaporates on sync. *Fix:* put durable rules in git-tracked files.
- **`git mv` renames split by the harness's intent-to-add** — old-path deletions went
  unstaged, so a naive commit would keep both copies. *Fix:* `git add -A` the moved-from
  dirs (surgically) so renames are detected.
- **Can't PR `develop`→`develop`; local had diverged** (ahead 2 / behind 2, one commit
  unrelated). *Fix:* branch from *fresh* `origin/develop`, cherry-pick only your commit.
- **`gh pr create` heredoc choked on shell quoting.** *Fix:* write the body to a file,
  use `--body-file`.
- **`git reset --hard` deletes intent-to-add (`-N`) files** — it removed a C4 session's
  uncommitted `c4-example.md`. *Fix:* verify local-only work is preserved elsewhere
  (jj-keep refs) before a hard reset, then restore the untracked file from the snapshot.
