# How we did it: Fix the internal file viewer — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a deliberately
non-implementing stance for thinking through a problem before writing code. The concrete
trigger: the dashboard's internal file viewer was throwing **"path outside working
directory"** when opening a file (e.g. `node_modules/vitest/package.json`) from a worktree
session, and separately **"Failed to load image"** on agent screenshots.

The real objective, once the steering clarified it: **don't just patch the symptom — diagnose
the containment security model, decide how far to widen it, and capture the whole fix tree as
validated OpenSpec proposals** (no implementation). The session ended with **three complementary
proposals** committed, cleanly partitioned by root cause.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore` skill) — stance is "think, don't implement; you
   MAY write OpenSpec artifacts."
2. **Ground the error string in real code first.** `grep -rn "path outside working directory"`
   → find the exact guard in `packages/server/src/routes/file-routes.ts`. Never theorize before
   reading the guard.
3. **Draw the failure geometry.** Show `cwd`, `resolved`, and the `startsWith(cwd + sep)` check
   as a concrete ASCII/tree diagram so the human sees *why* it trips.
4. **Offer labelled options** (A/B/C…) for the fix and let the human pick a letter.
5. **Design before scaffolding:** for the chosen option, map every touch point (all guard
   sites, git-root computation verified live with `git rev-parse --git-common-dir`).
6. **Scaffold OpenSpec artifacts** mirroring an existing change's structure
   (`proposal.md` / `design.md` / `tasks.md` / `specs/<cap>/spec.md`); `openspec validate <name>`
   after each write.
7. **Pressure-test the design** ("pressure-test", "poke holes") — ground each claim, surface
   HIGH findings (Windows sep bug, whole-repo scope, remote-auth blast radius).
8. **Fold the unambiguous findings; hold the judgment calls** for the human ("fold G2/G3/G4/A3",
   "Resolve G1 and A1").
9. **Partition by root cause** into separate proposals; commit only your own files
   (exclude volatile `groups.json` board state).

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding (16:12–16:18).** The AI resisted theorizing. It grepped for the
literal error string, opened `file-routes.ts:119-127`, and reproduced the two-gate containment
rule verbatim in the reply. It then drew the worktree geometry showing the opened file lived at
the *parent* repo root while the session cwd was the worktree — so the `startsWith(cwd + sep)`
gate returned FALSE. *Why it worked:* every claim was anchored to a file:line, so the human could
trust the diagnosis instead of a plausible guess.

**Phase 2 — Option choice & design (16:17–16:23).** The human picked **"C"** (re-anchor to the git
common root). The AI surfaced *new evidence* mid-design — the worktree had its *own* `node_modules`,
so option C "worked" only by legalizing a link that pointed at the wrong tree (a second, distinct
bug). It designed a **layered allow**: cheap `startsWith(cwd)` first, git-root fallback only on
miss — proving "ordering is perf, not security" because `cwd ⊂ gitRoot`. Then it scaffolded the
`git-root-file-containment` proposal and iterated on `openspec validate` (the parser wanted `SHALL`
on the requirement's first physical line).

**Phase 3 — Clarify & pressure-test (16:26–16:56).** On "Is there anything to clarify?" the AI
grounded its own soft spots and found the security justification was **false**: `networkGuard` is
*not* localhost-only — an authenticated remote user (Docker/zrok mode) passes it, so widening to the
git root means whole-repo read over a tunnel. The human logged decisions (Q1: no loopback gate, the
repo *is* the trust boundary; Q2: preserve per-site anchors + error strings). A screenshot ("Maybe
related") surfaced a **third anchor class** — files outside *any* repo (`~/.agent-browser/tmp`) — which
git-root would not fix. On "pressure-test", the AI attacked both designs and produced graded findings
(G1/G2/G3/G4, A1/A3).

**Phase 4 — Fold & partition (16:57–17:05).** The human triaged: "fold G2/G3/G4/A3" (unambiguous),
"Resolve G1 and A1" (judgment). The AI folded fixes across all four artifacts per change, kept the
proposals valid, and "consumed" the last open thread into a **third** proposal
(`inline-agent-screenshot-artifacts`, "Fix B") after grounding how the bridge already inlines images.

**Phase 5 — Commit (17:17).** The AI checked `git status`, noticed `groups.json` carried *unrelated*
board reassignments, and deliberately committed **only** the three proposal directories — leaving
someone else's live-dashboard board state unstaged.

## 4. Prompts that worked

- **"C"** — a single letter picked from labelled options. High-leverage because the AI had already
  laid out A/B/C with tradeoffs, so one character chose the whole design direction.
- **"Is there anything to clarify?"** — invited the AI to ground its own soft spots; this is what

- **"pressure-test"** — one word that triggered a genuine adversarial pass with graded findings.
- **"fold G2/G3/G4/A3"** and **"Resolve G1 and A1"** — terse, ID-based triage that separated the
  mechanical folds from the decisions needing human judgment.
- **"consume to this proposal"** — turned the last open thread into a third scoped proposal.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created this session. The reusable **workflow**, however, is
strongly repeatable and worth codifying:

- **"Ground-the-error-string → diagram the geometry → labelled options → design → validate → pressure-test → fold/partition"** is a complete explore→propose loop. It consistently turned a vague UI symptom into three scoped, validated OpenSpec proposals.
- Recommend saving a **project skill** (e.g. `explore-to-partitioned-proposals`) capturing: (1) grep the literal error string first, (2) reproduce the guard verbatim, (3) draw the failure geometry, (4) offer A/B/C options, (5) `openspec validate` after every artifact write, (6) run a pressure-test pass and fold by severity, (7) partition by root-cause class, (8) commit only your own files.
- Existing skills that fit the checkpoints: `doubt-driven-review` / `review-code` for the pressure-test phase; `security-hardening` was the right lens for the networkGuard finding.

## 7. Pitfalls & dead ends

- **`openspec change new` is not a subcommand here** — proposals are authored as files. Mirror an
  existing change's directory structure instead of expecting a generator.
- **OpenSpec validator quirk:** the requirement parser captures only the **first physical line** as
  the requirement text and wants `SHALL` there. Restructure the opening sentence, don't fight it.
- **Stray edit keys** (`saveText`, `newText2`) caused several failed edits (4 edit errors) — redo the
  edit cleanly rather than patching the malformed one.
- **False security assumption:** `networkGuard` (`createNetworkGuard`) is *not* localhost-only — it
  admits loopback **and** trusted CIDRs **and** authenticated remote users. Never justify a widened
  read surface on "localhost-only" without checking the guard.
- **Windows separator bug (G2):** `git --path-format=absolute` emits forward slashes while
  `path.resolve` emits native — `startsWith` fails on Windows. Normalize to native sep + drive case
  before comparing.
- **Don't commit `openspec/groups/groups.json`** — it's live-dashboard board state that accumulates
  unrelated reassignments; staging it bundles someone else's edits.
