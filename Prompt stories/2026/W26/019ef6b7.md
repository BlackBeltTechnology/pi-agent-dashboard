# How we did it: Scoping `document-converter` — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The session opened in **OpenSpec explore mode** — a thinking-partner stance, no
implementation. The literal first prompt was the explore-mode skill banner ("Enter
explore mode. Think deeply… you must NEVER write code"). The *real* objective, which
emerged over the next few turns, was: **decide how to bring the user's mature
Python document-processing skills (`document-conversion`, `docling`, templating,
diagram rendering) into this TypeScript monorepo without losing any features, so
they can feed the `kb` knowledge base and produce branded deliverables** — and
capture that decision as a complete OpenSpec change (proposal → design → specs →
tasks), then commit it. It started as an open "should we rewrite in TypeScript?"
question and converged, under steering, on a **"keep Python, wrap in TS" facade over
a Dockerized engine** architecture.

## 2. TL;DR playbook

1. **Enter explore mode** (`openspec-explore` skill) — force a think-first, no-code stance.
2. **Ground before opining:** have the AI enumerate the actual skills (global `~/Documents/.gemini`, `.agents`, project-local) and classify each by engine (Python vs TS-native). Don't let it theorize about code it hasn't opened.
3. **Find the real integration seam:** confirm `kb` is markdown-in by hard contract (`indexer.ts` walks only `.md`), so the new skill sits **upstream** and `kb` stays untouched.
4. **Set the decisive rule early:** steer with *"if it loses features from Python, keep Python but wrap in TypeScript."* This one sentence collapses the whole build-vs-adapt fork.
5. **Grow scope deliberately, one probe per turn:** add templating (rename skill), fold in nano-banana styled diagrams + md5 cache + mmdc fallback, sweep for *other* coupled skills (frontmatter-filler, markdown-table-profiler), confirm OCR is selectable (mode/lang/engine).
6. **Preserve the hard detail by linking, not copying:** add a *Source Skills — Implementation Reference* appendix pointing at the **richest** copy of each origin skill; flag the vendoring trap (`~/Documents` paths are build-time only; the image must build from a committed in-repo copy).
7. **Exit explore → scaffold:** run the coherence check, `openspec change new document-converter`, write `proposal.md`.
8. **Fast-forward the rest** (`openspec-ff-change`): `design.md` + `specs/…/spec.md` → `tasks.md`; fix the SHALL-first validator nit; `openspec validate` → valid.
9. **Commit surgically:** stage only the change's files; deliberately exclude unrelated pre-existing edits (`groups.json`, `c4-example.md`).

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding.** The AI resisted answering the TS-vs-Python
question abstractly. It first listed every candidate skill and read inside them to
judge tech stack, producing a table: which have clean TS equivalents (`xlsx`,
`pptx`, `document-organizer`) and which genuinely don't (`docling` — ML OCR/layout).
*Why it worked:* the decision splits per-skill, so the map had to exist before any
verdict. **Decision point:** the human revealed the target is the `kb` package —
which reframed everything.

**Phase 2 — Find the seam.** The AI inspected `kb` and found it only ingests
markdown by design (`sources.ts`: "KB only reads markdown; it never executes source
code"). Conclusion: don't adapt skills *into* kb; sit upstream as a conversion stage
emitting `.md` into a staging dir. *Why it worked:* an already-built, already-tested
boundary became the integration contract — zero kb changes.

**Phase 3 — The decisive rule (steering #1).** Human: *"If it loses features from
Python, keep Python, but wrap in TypeScript."* The AI re-scored every format lane
under this rule and it **collapsed the fork** — almost every lane keeps Python.
Crystallized architecture: **TS = contract surface + orchestrator, Python =
conversion engine, meeting at a CLI/JSON boundary**, one `pi-doc-engine` Docker image.

**Phase 4 — Deliberate scope growth.** Successive single-probe steering turns each
added a capability *without dropping features*: templating (→ rename to
`document-converter`, it's the *produce* direction), nano-banana styled diagrams
(opt-in frontmatter flag, **md5-of-source cache**, **mmdc fallback on any failure**),
a sweep that surfaced the **frontmatter bus** (frontmatter-filler +
markdown-table-profiler as writers), and selectable OCR (mode `auto/force/off`,
`lang[]`, engine EasyOCR/Tesseract/RapidOcr — with the per-engine language-code
translation caught as a design subtlety).

**Phase 5 — Preserve detail (steering #6).** Human: *"The proposal can lose details.
Maybe linking the original skills can help while implementing."* The AI added a
*Source Skills — Implementation Reference* appendix linking each origin at its
richest copy, and flagged the **vendoring trap**. *Why it worked:* the proposal
carries the *why/shape*; implementers read source-of-truth for the *exact how*.

**Phase 6 — Capture & commit.** Exit explore, coherence check (no name collision),
scaffold proposal, then `openspec-ff-change` generated design + specs + tasks (4/4
artifacts, 11 requirements, 30 task checkboxes). Fixed one validator nit (lead the
requirement with a clean `SHALL`). Committed **only** the change's 5 files, leaving
two unrelated pre-existing changes out.

## 4. Prompts that worked

- **Goal prompt (explore-mode banner).** Effective because it *pins the stance*: no
  code, think first, artifacts-allowed. For scoping a fuzzy architecture question,
  entering explore mode up front prevented premature implementation.
- **High-leverage: *"if it loses features from Python, keep Python, but wrap in
  TypeScript."*** One sentence that collapsed a multi-branch decision into a single
  clear architecture. This is the model prompt — a crisp, testable rule beats a
  long discussion.
- **High-leverage: *"Is there any other skills / utils which related document
  conversion / fixing / frontmatter editing?"*** A scope-completeness probe that
  surfaced the frontmatter bus the AI hadn't seen. Reusable move: after the obvious
  pieces are in, explicitly ask "what else is coupled to this?"
- **High-leverage: *"The proposal can lose details. Maybe linking the original
  skills can help while implementing."*** Turned a lossy-summary risk into a concrete
  appendix strategy.
- **Weak → stronger.** *"draft proposal"* worked only because context was already
  rich. A stronger standalone kickoff: *"Exit explore and scaffold the OpenSpec
  change `document-converter` with the architecture we settled on; run the coherence
  check first."*

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was saved this session — it was an application of existing
skills (`openspec-explore`, `openspec-ff-change`). The reusable asset produced is the
**OpenSpec change itself** (`openspec/changes/document-converter/`, 4 artifacts).

**Recommended skill to create:** a *"wrap-don't-lose-features adaptation"* playbook —
codifying the exact loop that worked here: (1) enumerate origin skills + classify
engine, (2) find the existing markdown/CLI/JSON integration seam, (3) apply the
keep-engine-wrap-contract rule, (4) sweep for coupled skills, (5) append a
Source-Skills reference with the vendoring trap called out. It removes the manual
re-discovery of "which lanes keep Python" and makes the vendoring/feature-loss
guardrails automatic. Invoke it whenever adapting an external (Python/shell) tool
into this TS monorepo.

## 7. Pitfalls & dead ends

- **`openspec change new` CLI discovery:** the first `openspec change new …` invocation
  failed; the AI had to probe `openspec --help` / `openspec new --help` to find the
  right subcommand. If the CLI verb is unknown, run `--help` before guessing.
- **Sandbox loop choke:** a `ctx_batch_execute` shell loop iterating skill dirs failed
  in the sandbox; the AI fell back to plain `Bash`/`find` + direct file reads. If a
  batched loop chokes, drop to a single explicit `find` + `sed -n`.
- **Empty greps:** greps for OCR config came up empty because the detail lived in files
  not matching the pattern — reading the skill files directly recovered it. Don't trust
  an empty grep as "feature absent"; open the source.
- **Validator SHALL-first nit:** OpenSpec's validator reads the first line of a
  requirement description; a `When…`-led line fails. Lead every requirement with `SHALL`.
- **Expected "validation error" mid-flow:** after writing only the proposal, `validate`
  flags the missing specs delta — that's the *next* artifact, not a real error.
