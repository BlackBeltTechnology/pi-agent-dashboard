# How we did it: Adding an unlisted model (GLM-5.2) to pi's `opencode-go` provider — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with a diagnosis-flavored question, quoting the first prompt:
> "Why GLM 5.2 is not listen in opencode go? Because the provider itself supports"

The literal ask is *why* a model the endpoint clearly supports (GLM-5.2) fails to
appear in the model selector. Once steering clarified the environment ("I'm in
pi"), the real objective sharpened into two parts: (1) explain the true root cause
*in pi specifically*, and (2) make GLM-5.2 usable now without waiting for a pi
upgrade — i.e. add it to the static model catalog via user config.

## 2. TL;DR playbook

1. Ask the diagnosis question, but **name the harness up front** — pi, not opencode.
2. Have the AI grep the *installed* package, not the internet, for the catalog:
   `@earendil-works/pi-ai/dist/models.generated.js`.
3. Confirm the catalog is a **static, release-shipped list** and that it caps at
   `glm-5.1` (no `glm-5.2` entry) — this is the whole root cause.
4. Read `~/.pi/agent/models.json` first to see what providers already exist.
5. **Upsert** a `glm-5.2` model under the built-in `opencode-go` provider name —
   pi keeps all built-ins and merges your custom entry by id.
6. Copy the spec from a sibling GLM entry: `openai-completions` API,
   `https://opencode.ai/zen/go/v1` baseUrl, context window, max output, cost,
   reasoning on, text-only input.
7. Validate the JSON (`python3 -m json.tool`) before trusting it.
8. Verify live: open `/model` (no restart — file reloads) or
   `pi --list-models | grep -i glm-5.2`.

## 3. How the collaboration unfolded

**Phase 1 — Wrong-tool discovery (misfire).** The AI ran a web search and
initially answered for the *opencode Go app*, blaming a "blanket `glm` exclusion
in `ProviderTransform.variants()`". Plausible-sounding, but it was about a
different tool than the user's actual environment. Lesson: an ungrounded web
search on an ambiguous term invites a confident wrong answer.

**Phase 2 — Reframe on steering.** The user's one-liner "I'm in pi" collapsed the
whole first answer. The AI correctly discarded it ("disregard that earlier answer,
it was about a different tool") and pivoted to reading pi's own docs and package.

**Phase 3 — Grounded root cause.** The AI grepped the installed monorepo
(`node_modules/@earendil-works`) for `glm`, found the static catalog
`pi-ai/dist/models.generated.js`, and confirmed `opencode-go` ships only `glm-5`
and `glm-5.1`. Root cause: **static per-release catalog, GLM-5.2 not yet added
upstream** — not a capability rejection, not a variant-exclusion rule.

**Phase 4 — Fix by user config.** The AI read `~/.pi/agent/models.json` (found an
existing `my-google` provider), then made a single `edit` merging an `opencode-go`
entry with a `glm-5.2` model alongside the existing provider. It validated the JSON
and explained pi's upsert-by-id merge behavior. Decision point: the user unlocked
the write with a terse "yes."

## 4. Prompts that worked

- **The goal prompt** ("Why GLM 5.2 is not listen in opencode go?") stated the
  symptom but not the environment. A stronger kickoff bakes in the harness:
  *"In pi, GLM-5.2 doesn't show in the `opencode-go` model list even though the
  endpoint supports it — why, and how do I add it?"* That one line would have
  skipped the entire wrong-tool detour.
- **High-leverage follow-up: "I'm in pi"** — three words that invalidated a whole
  answer and redirected to grounded evidence. Environment disambiguation is the
  cheapest, highest-leverage correction you can give.
- **"yes."** — the write-unlock. Fine once the plan was concrete and the target
  file already read.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session. But the workflow is clearly
repeatable and worth capturing. **Recommended skill: "add an unlisted model to a
built-in pi provider"** — procedure: locate `pi-ai/dist/models.generated.js` to
confirm the static catalog gap, then upsert the missing model id under the
existing provider name in `~/.pi/agent/models.json` (pi keeps built-ins and merges
by id), copy the spec from a sibling entry, validate JSON, verify via `/model` or
`pi --list-models`. It removes the repeated grep-hunt and the "will editing config
wipe the built-ins?" uncertainty.

## 7. Pitfalls & dead ends

- **If you get a confident answer about "opencode", check it's not the opencode Go
  app vs. pi's `opencode-go` provider** — same name, different tool. The AI
  conflated them and had to retract its first answer.
- **Don't trust web search for "which models does X ship"** — the ground truth is
  the installed catalog file, `@earendil-works/pi-ai/dist/models.generated.js`.
- **Editing `~/.pi/agent/models.json` does NOT remove built-ins** — pi upserts your
  custom model by id and preserves the shipped ones. Merge alongside existing
  providers (here `my-google`); don't replace the file.
- **Always `python3 -m json.tool` the file after editing** — a broken JSON silently
  drops your custom models.
