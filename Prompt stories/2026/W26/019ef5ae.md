## 1. Goal (the ask)

The operator opened **explore mode** (`openspec-explore`) with a thinking-partner stance —
"Enter explore mode. Think deeply… you must NEVER write code or implement features." The
underlying objective, which the four short steering turns clarified, was concrete: **design
a `code-quality` skill for pi-dashboard that plugs into the `goal-plugin` "Ralph loop"** —
a static-analysis analyze→fix→test loop a judge model can drive to "done." The session was
never about writing the tool; it was about producing the OpenSpec change (proposal + design +
tasks + spec + skill draft) that captures *how* such a skill should work, grounded in the
repo's actual tooling reality.

## 2. TL;DR playbook

1. Enter `openspec-explore` and state the target: "design a code-quality skill drivable by the goal-plugin loop."
2. Let the AI **ground first** — have it discover current tooling (`npm run lint = tsc --noEmit`, no ESLint/Biome/Prettier), the `goal-plugin`/judge mechanism, and the skill format before any option-sketching.
3. Make it surface the **scale + trap** early: `1712` TS/TSX files, space-indented, zero formatter → Biome's tab default would produce a 100k-line reformatting diff.
4. Decide the three axes in one steering line: **ratchet strategy · Biome · soft-warn CI**.
5. Have the AI **verify engine specifics via web search** (Biome `--changed`/`--staged`, severity exit codes) so rule names and glue aren't hand-waved.
6. Say **"draft proposal"** — it runs the pre-scaffold coherence check (no conflicting active/archived change), matches repo OpenSpec artifact formats, and scaffolds all 5 files.
7. Validate with `npx openspec validate <change> --strict`.
8. Say **"draft the skill"** — it writes `skill-draft.md` *inside the change dir*, not the live `.pi/skills/` path (explore-mode discipline: the skill references config/scripts that don't exist yet).
9. Say **"commit"** — it stages only the change dir and commits on `develop`.

## 3. How the collaboration unfolded

**Phase 1 · Discovery / grounding (20:20).** The AI refused to sketch options first. It
investigated the repo's real static-analysis story (`tsc --noEmit` only — no linter at all),
learned what a "goal" concretely is (`goal-plugin` wrapping `@ricoyudog/pi-goal-hermes`, a
judge model deciding done/continue each turn), and read the skill format. *Why it worked:* every
later design claim was anchored to a verified fact, not a guess.

**Phase 2 · Naming the trap (20:26–20:27).** It measured scale — `1712` source files, `200/200`
sampled space-indented — and pinned the single biggest risk: Biome's formatter defaults to
tabs, so a whole-repo `--write` would reformat everything and bury real fixes. This shaped the
whole design: **linter-only Phase 1, formatter off, formatter (if ever) only in changed-files
mode**.

**Phase 3 · Three decisions (20:30).** The human answered with three tokens — *ratchet strategy,
Biome, soft-warn CI*. The AI locked them and, before sketching the tier ladder, ran a web search
to verify Biome specifics rather than reinvent glue Biome already ships.

**Phase 4 · The core insight (20:31).** From verified exit-code semantics it derived the key idea:
**severity *is* the ratchet** (`off → warn → error`), and **one `biome.json` serves all three
scopes** by varying the *flag*, not the config (CI = plain `biome lint .` soft-warn; goal loop =
`--changed --error-on-warnings` hard on touched files). `quality:changed`'s exit code becomes the
judge's done/continue oracle.

**Phase 5 · Draft + validate (20:34–20:36).** On "draft proposal," it ran a coherence check (no
biome/lint/quality change in active or archive), matched exact artifact formats, scaffolded the
5-file change, and passed `openspec validate --strict`.

**Phase 6 · Skill draft + commit (20:38–20:40).** On "draft the skill" it wrote `skill-draft.md`
into the change dir (not live skills path). On "commit" it staged only the 6 files and committed
cleanly on `develop`: `4637819b docs(openspec): add-code-quality-skill proposal`.

## 4. Prompts that worked

- **The goal prompt** (`openspec-explore` stance) — effective because it set a *thinking, not
  implementing* boundary, which kept the AI grounding reality instead of prematurely writing a
  skill. A stronger explicit kickoff: *"In explore mode, design a code-quality skill the
  goal-plugin loop can drive; ground in current repo tooling and scale before sketching."*
- **High-leverage follow-up: `1. Ratchet strategy / 2. Biome / 3. Soft warn in CI`** — three
  words settled the three open axes at once and unblocked the entire design. This is the model
  answer format: enumerate the decisions, answer them tersely.
- **`draft proposal` / `draft the skill` / `commit`** — one-word state transitions that worked
  because the AI had already done the grounding; each just released the next deterministic step.

## 7. Pitfalls & dead ends

- **The 100k-line reformat cliff.** Biome's formatter defaults to **tabs**; this repo is spaces
  across 1712 files. A whole-repo `biome check --write` reformats everything and buries real
  fixes → never let the loop do that. Mitigations: `biome.json "indentStyle": "space"`, Phase 1
  linter-only (`formatter.enabled = false`), formatter (if ever) only in changed-files mode.
- **Reinventing glue.** Before designing a custom `--changed` script, the AI verified Biome ships
  native `--changed`/`--staged` — killing the need for it. Always check the tool's own docs first.
- **Explore-mode discipline.** Don't write the skill to the live `.pi/skills/` path from explore
  mode — it references `biome.json` and `quality:*` scripts that don't exist yet. Park it in the
  change dir.
- Zero failed commands this session (7 bash, 0 errors) — the grounding-first approach paid off.
