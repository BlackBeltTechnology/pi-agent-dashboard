# How we did it: Streamline the Electron bootstrap & recovery flow — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a deceptively small question — *"Is the electron rewrite the
`.pi-dashboard` directory contents? The embedded packages?"* — a request to
**understand how the Electron desktop app relates to the managed runtime install** at
`~/.pi-dashboard/`. Through 12 rapid clarifying prompts it grew into the real
objective: **redesign the whole first-run / recovery bootstrap** so that a user who
never opens Doctor can still self-heal a broken managed install. The end state:
per-launch inventory preflight, a slimmed 4-step wizard with a unified package
selector, loading-page reinstall/force-reinstall recovery, a surgical (non-nuclear)
force-wipe that preserves user packages, and a one-command offline `build:local`.
This was captured as the OpenSpec change `streamline-electron-bootstrap-and-recovery`,
then implemented, built into a macOS DMG, smoke-tested, and bug-fixed.

## 2. TL;DR playbook

1. **Start by asking the AI to map the system** — "how does X relate to Y, and where
   does each thing live?" Force it to answer with a *table of thing → what-it-is →
   where*, grounded in real source paths (not speculation).
2. **Probe each layer with a follow-up** ("what about node/npm versions? the plugins?
   the cache?"). Each answer surfaces a gap; each gap becomes a spec requirement.
3. **Demand verification before design** — "check that assumption is true." Make the AI
   grep the actual source and report what the code *really* does before proposing.
4. **State the safety constraint early** — "keep user settings and packages that don't
   belong to Electron." This turns a nuclear wipe into a surgical one.
5. **Say `create proposal`** once the gaps are enumerated. The AI writes
   `proposal.md` + `design.md` + `tasks.md` + per-capability spec files and runs
   `openspec change validate`.
6. **Implement in task groups**, marking `tasks.md` boxes as each group's tests pass
   (`HOME=$(mktemp -d) npx vitest run …` for env-isolated tests).
7. **Build the artifact locally** — `build:local` for a full offline DMG; caches warm
   → ~60s, cold → 10-20 min (run in background, tail the log).
8. **Smoke-test the real install**, feed Doctor screenshots back to the AI, and let it
   locate + fix each bug with a co-located test.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (system mapping).** The AI answered the opening question with a
clear separation: Electron rewrite = `packages/electron/` source; `~/.pi-dashboard/` =
the *runtime* install created at first launch; embedded packages = bundled Node +
server source + offline npm cacache in `resources/`. It backed every claim with grep
over `docs/architecture.md` and the actual source. *Why it worked:* the human kept
asking "and what about this layer?" so the map got exhaustive before any design.

**Phase 2 — Gap analysis (verify, don't assume).** Prompts 6–8 pushed the AI to
*verify* assumptions against code ("check that is assumption is true"). It found the
real behavior: bundled Node repairs on missing marker, but bundled packages have **no
version file** — only a presence check that runs *once* on first-run, then is skipped
forever by `decideStartupAction`. That's the core gap the whole change closes.

**Phase 3 — Design decisions (human-driven).** The human made the key calls: keep the
force-wipe surgical (preserve user-owned `node_modules`), add loading-page recovery so
users who never run Doctor can self-heal, question whether the wizard still has a
purpose (→ slim it to 4 steps, drop mode/API-key/bridge steps), and surface the *full*
bundled cache in the selector instead of a limited set.

**Phase 4 — Generate the proposal.** On `create proposal` the AI produced the full
OpenSpec artifact set — proposal, design (with before/after state-machine diagrams,
whitelist contract, force-reinstall safety model), a 14-group `tasks.md`, and 7 spec
files — and validated it.

**Phase 5 — Implement & verify.** Across a long tail (after a freeze/resume), the AI
worked task groups, ran env-isolated vitest, co-located a cross-version-banner test
inside the preflight test, delegated docs (Group 11) to a subagent per the caveman
Documentation Protocol, and marked boxes only after tests passed on disk.

**Phase 6 — Build, smoke-test, fix.** Ran `build:local` → 220 MB DMG with all four
offline cache tiers. Smoke test + Doctor screenshots surfaced 4 bugs (bundled-git
source ignored by reconciler → npm 404; duplicate git/npm registrations; server
`version: "unknown"`; Doctor server-log false-positive). The AI fixed 3 with tests
(121/121 passing) and correctly diagnosed the 4th as a pre-existing
`bundle-extract.ts` symlink-loop, plus caught that a stale 35-min server was masking
the version fix.

## 4. Prompts that worked

- **Goal prompt** — *"Is the electron rewrite the `.pi-dashboard` directory contents?"*
  A grounding question. It's effective because it forces the AI to establish the
  *mental model* (source vs runtime vs bundle) before anything is designed. Stronger
  version: *"Map how packages/electron/, ~/.pi-dashboard/, and resources/ relate —
  table of thing → what-it-is → where, cite source paths."*
- **High-leverage follow-up** — *"Check that this assumption is true"* (prompt 7).
  Short, but it flips the AI from confident speculation to grep-the-source verification
  and exposed the real "no version file, presence-check-once" gap.
- **Scope-cutting prompt** — *"With this mechanism, does the wizard have any sensible
  purpose?"* A single question that triggered a full redundancy audit and led to the
  4-step wizard redesign.
- **Safety prompt** — *"Keep the user settings, the installed packages… keep packages
  which don't belong to Electron."* One sentence that defined the force-reinstall
  whitelist boundary.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Answer confidently from its model of the code | "check that this assumption is true" | State up front: "verify every claim against source before proposing" |
| Treat force-reinstall as a full wipe | "keep user settings + non-Electron packages" | Name the whitelist boundary in the goal prompt |
| Assume Doctor is the recovery path | "user not always runs doctor… there was a page that couldn't connect" | Ask "what's the recovery path for a user who never opens Doctor?" |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session. One subagent was spawned:

- **`general-purpose` subagent for Group 11 (docs).** Used because AGENTS.md's
  Documentation Update Protocol mandates that every `docs/` write go through a subagent
  in *caveman style*. *Why effective:* keeps the docs-writing rules + the large doc
  context out of the main thread and enforces the house style automatically. Invoke it
  whenever a change lands docs updates.

**Skill worth creating:** a `verify-before-design` discipline — "when asked to design a
change to existing behavior, first grep the source and report what the code *actually*
does (with file:line), then design against the verified reality." This session's
biggest wins all came from that move; codifying it would remove the need to type
"check that assumption is true" every time.

## 7. Pitfalls & dead ends

- **`mktemp` with a `.md`-suffixed template can fail** (`mkstemp failed … File
  exists`) on some setups — use `mktemp` without a custom suffix, or a
  `$$_$RANDOM`-based path, for a unique facts-sheet output.
- **DMG packaging crashes on `macos-alias` native-module version mismatch** (built
  against Node 22, running Node 24). Rebuild the native module against the current Node
  before `electron-forge make`.
- **A stale, still-running server masks your fix.** A 35-min-old server (PID from
  before the rebuild) held port 8000; the new app attached to it and reported the old
  `version: "unknown"`. Always `pkill` the old server + confirm the PID before trusting
  a "fix didn't work" signal.
- **`fs.cp` self-copy on symlink loops.** `bundle-extract.ts` tripped when
  `~/.pi-dashboard/.../pino` was a symlink pointing back into the app bundle ("cannot
  copy to a subdirectory of self"). Wipe `~/.pi-dashboard/` cleanly and let the wizard
  re-run rather than re-extracting over symlinks.
- **App name mismatch: `/Applications/PI-Dashboard.app`** (hyphen) not `PI
  Dashboard.app` (space). `open "PI Dashboard.app"` silently fails — check the exact
  bundle name.
- **`bundled-git` packages 404 on npm.** The reconciler built an `npm:` spec for
  every package, ignoring `pkg.source === "bundled-git"`, so
  `@blackbelt-technology/*` packages (unpublished) failed. Honor the source field when
  building the install spec.
