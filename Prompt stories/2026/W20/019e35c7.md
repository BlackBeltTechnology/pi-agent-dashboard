# How we did it: Finish the Electron bootstrap/recovery change, ship a DMG, and turn the build footgun it exposed into its own OpenSpec change — a collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The kickoff was a `/opsx-apply` invocation on the change
`streamline-electron-bootstrap-and-recovery` — *"Implement tasks from an OpenSpec
change."* The literal ask was: finish the remaining tasks of an existing spec-driven
change (it opened at **65/97 tasks**, 32 remaining).

Once the work unfolded, the *real* objective grew into three linked goals:

1. **Land the 27 substantive code tasks** in Group 16 — six distinct Electron
   bootstrap/recovery failure modes (bundle re-materialization, static-client
   resolution, wrong `server.log` path, server-identity retry, watchdog respawn,
   clean-install smoke + docs), each with its own test suite.
2. **Produce a real macOS DMG** and actually exercise the fixes against it.
3. **Convert the build-system footgun the DMG run exposed** — a stale server bundle
   silently shipped in the installer — into a fresh OpenSpec change,
   `fix-build-installer-stale-server-bundle`, with all four artifacts ready to
   implement.

## 2. TL;DR playbook

1. `/opsx-apply <change>` → read `openspec status --json`; **triage remaining tasks
   into "autonomous code" vs "manual hardware QA"** before writing any code.
2. Implement the code sub-groups in **dependency order** (foundational paths first:
   16.C → 16.B → 16.A → 16.D → 16.E → 16.F), each as *edit + colocated vitest +
   run + mark task done* before moving on.
3. Run new tests **isolated with `HOME=$(mktemp -d)`** so machine state / stale
   `~/.pi-dashboard` never pollutes results.
4. Route each doc write (caveman-style AGENTS/FAQ, QA cheat sheet) to a
   `general-purpose` subagent per the repo docs protocol.
5. Stop at the manual/hardware boundary — **mark tasks that need real installers as
   remaining, don't fake them**; hand back a single-page QA cheat sheet.
6. To build the DMG: `cd packages/electron && npm run build:local`. If native
   modules fail, **check Node is in the `>=22.12.0 <25` range** and rebuild the
   offending native dep (`macos-alias`) under Node 22.
7. When the fresh DMG shows an "already-fixed" bug at runtime, suspect a **stale
   cached bundle**, not a bad fix — verify the *binary* contains your source edits.
8. Force a clean re-bundle with `npm run clean:resources`, rebuild, and grep the DMG
   for your new symbols to confirm the fix is actually shipped.
9. File the root-cause footgun as its own change: `/opsx-ff` →
   proposal → design + specs (in parallel) → tasks, all four artifacts in one pass.

## 3. How the collaboration unfolded

**Phase A — Triage before coding.** The AI opened the change, read
`openspec status --json`, and *immediately split* the 32 remaining tasks into Group
14 (manual cross-platform smokes — not autonomously doable) and Group 16 (27 code
tasks across six failure modes). It surfaced that Group 16 was a "major chunk" and
checked in before diving. *Why it worked:* naming the autonomous/manual boundary up
front prevented wasted effort on hardware-bound tasks and set honest expectations.

**Phase B — Implement in dependency order.** The AI sequenced the six sub-groups so
foundational path helpers landed first (16.C dashboard-paths, 16.B managed-dir-root
resolution), then the features that consume them (16.A materialization, 16.D retry,
16.E watchdog, 16.F smoke+docs). Each sub-group followed a tight loop: extract a
*pure, testable helper* (e.g. `resolveClientDir`, `resolveManagedDirRoot`), wire it
into the real call site, write a colocated vitest, run it isolated, mark the task
done. *Why it worked:* small verify-as-you-go increments meant collateral breakage
was caught within one sub-group, not at the end.

**Phase C — Docs via subagents.** Change-recovery docs and the manual-QA cheat sheet
were delegated to `general-purpose` subagents in caveman style, per the repo's docs
protocol (main agent never edits `docs/` prose directly).

**Phase D — Build the DMG (steering: "build dmg").** `npm run build:local` first hit
a native-module ABI mismatch (`macos-alias` built against the wrong Node), then a
Node-version-out-of-range error (host on 25.8.1, project needs `>=22.12.0 <25`). The
AI switched PATH to Node 22.22.2, rebuilt the native dep cleanly, and produced a
208 MB DMG.

**Phase E — The stale-bundle hunt (steering: "404 Not Found").** Installing the fresh
DMG reproduced Failure 1 + Failure 2 *even though the fixes were in source*. The AI
resisted the obvious "my fix is wrong" conclusion and instead asked **"is the running
server the one with my fixes?"** — then grepped the DMG's bundled server for the new
symbols. Root cause: `build-installer.sh:295` short-circuits the bundler whenever
`resources/server/node_modules/` merely *exists*, so it shipped a **May-16 cached
bundle** predating the Group 16 edits. `npm run clean:resources` + rebuild fixed it;
grepping the DMG confirmed the new symbols were present.

**Phase F — Turn the footgun into a change (steering: "make proposal" → `/opsx-ff`).**
The AI scaffolded `fix-build-installer-stale-server-bundle` and fast-forwarded all
four artifacts: proposal (the "18-hour-stale-DMG incident"), design (6 decisions,
chose an mtime **build-stamp sentinel** over dir-existence), specs (new
source-edit-triggers-rebuild / cache-hit-under-100ms scenarios), and a 22-task
tasks.md.

## 4. Prompts that worked

- **The goal prompt** (`/opsx-apply streamline-electron-bootstrap-and-recovery`): a
  structured slash-command that named the change and carried the full apply
  procedure. Effective because it gave the AI an unambiguous target and a schema to
  read status from — no guessing which change to work on.
- **"dereferenceWorkspaceSymlinks? Is it working on windows? Symlink is dangerous"**
  — a *single sharp question* that forced the AI to prove cross-platform safety. It
  surfaced dead code (`dereferenceWorkspaceSymlinks` was unused) and pinned a
  Windows-safety invariant in the docstring. High leverage: one skeptical question
  removed a real risk.
- **"build dmg"** — two words that moved from code to a real artifact, exposing the
  ABI/Node-version snags that only a real build reveals.
- **"404 Not Found"** — a *symptom paste*, not a diagnosis. Effective precisely
  because it let the AI own the root-cause hunt (it found the stale-bundle
  short-circuit) rather than being led to a wrong conclusion.
- **"make proposal" → `/opsx-ff`** — captured the just-discovered footgun as a
  durable change while the context was hot, and fast-forwarded all artifacts in one
  pass instead of stepping through each.

*Stronger rewrite for next time:* replace the bare "404 Not Found" with **"Fresh DMG
still shows Failure 2 at runtime — before assuming the fix is wrong, verify the
bundled server in the DMG actually contains the new symbols."** Same outcome, fewer
minutes lost.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Keep a misleadingly-named helper + unused sibling (`materialize`/`dereferenceWorkspaceSymlinks`) | "Is it working on windows? Symlink is dangerous" | Auditing new cross-platform helpers for dead code + a Windows-safety docstring invariant at creation time |
| Treat "remaining manual tasks" as a stopping point without a build | "build dmg" | Producing the real artifact as part of the apply loop when the change is installer-facing |
| Risk concluding "the fix didn't work" from a runtime symptom | "404 Not Found" (bare symptom) | Always verifying the *binary* contains the source edits before re-diagnosing the fix |
| Leave a discovered footgun as a loose "worth filing" note | "make proposal" then `/opsx-ff` | Scaffolding the follow-up change immediately while root-cause context is fresh |

Quality bars the human imposed implicitly: cross-platform correctness must be
*proven*, not asserted; a fix isn't done until it's in the shipped binary; discovered
problems become tracked changes, not TODO comments.

## 7. Pitfalls & dead ends

- **Stale cached server bundle (the big one).** `build-installer.sh:295` re-bundles
  only when `resources/server/node_modules/` is *absent*. Back-to-back local builds
  after editing `packages/server/src` or `packages/shared/src` silently ship stale
  code. *If you hit an "already-fixed" bug in a fresh DMG:* run
  `npm run clean:resources`, rebuild, and `grep` the DMG for your new symbols to
  confirm.
- **Node version out of range.** Project requires `>=22.12.0 <25`; a host on Node 25
  fails `build:local`. *Fix:* point PATH at a Node 22 (`~/.nvm/versions/node/v22.*`).
- **Stale native module (`macos-alias`).** The DMG maker's native `.node` was built
  against the wrong `NODE_MODULE_VERSION`; a partial rebuild under Node 25 wiped it.
  *Fix:* `cd node_modules/macos-alias && rm -rf build && npx node-gyp rebuild` under
  Node 22.
- **Machine-state-dependent tests.** Run new vitest with `HOME=$(mktemp -d)` so a
  populated `~/.pi-dashboard` doesn't flip smoke results.
- **Pre-existing lint/smoke failures.** Some failures were *not* from this session's
  changes; the AI verified by running only the touched packages rather than chasing
  unrelated red.
