# How we did it: Fix Electron dashboard server won't spawn after reboot — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with a runtime symptom, not a diagnosis:

> "I restarted my machine and pi-dashboard cannot start connect to dashboard, it exited with a spawn error. When I started cli pi, after connected (electron app)"

The *real* objective, once the session clarified it: **the Electron desktop app silently
fails to start the bundled dashboard server on a cold boot.** Root cause turned out to be
that Electron's server launcher called `launchDashboardServer(...)` without an explicit
`nodeBin`, so the shared launcher fell back to `process.execPath` — which inside an Electron
main process is the Electron *GUI* binary, not Node. The GUI binary re-launched the app,
hit the single-instance lock, and exited with no post-banner output. The task became: turn
that diagnosis into a proper OpenSpec change, ship a real fix with tests, and (a second bug
surfaced mid-session) fix a stuck "Resuming…" flag along the way.

## 2. TL;DR playbook

1. **Reproduce the signature from logs, not guesses.** `tail -100 ~/.pi/dashboard/server.log`
   — look for a launch banner with **zero further output** (child never reached `serve()`).
2. **Confirm the mechanism in the shipped bundle**, not just source:
   `strings /Applications/PI-Dashboard.app/Contents/Resources/app.asar | grep ELECTRON_RUN_AS_NODE`
   → zero refs proves the fallback-to-`process.execPath` theory.
3. **Turn the diagnosis into a change**: `create proposal` → run `/opsx-ff` to fast-forward all
   four artifacts (proposal, design, specs, tasks) with `openspec validate --strict`.
4. **Implement the pure helper first**: a `pickNodeForServer()` (bundled Node → system Node →
   `process.execPath` + `ELECTRON_RUN_AS_NODE=1` fallback) with unit tests before wiring.
5. **Wire both launchers** (`spawnFromSource` V2 + legacy `launchServer` V1) to pass explicit
   `nodeBin`, and fix the same bug in `doctor.ts`.
6. **Add a repo-lint** (`no-electron-execpath-spawn.test.ts`) that forbids the execPath-as-binary
   pattern so it can't regress — but scope it to flag only binary assignment, not legitimate uses.
7. **Prove you introduced zero new failures**: `git stash` the change, run the suite, compare the
   failure set with vs. without your diff.
8. **Restart the RIGHT server**: from the dev monorepo use `curl -X POST http://localhost:8000/api/restart`
   — NOT `pi-dashboard restart` (that starts the installed Electron bundle with no client build).
9. **Commit in logical units**; when done, `mark QA tasks deferred and archive` + sync deltas to main specs.

## 3. How the collaboration unfolded

**Phase 1 — Diagnosis (evidence first).** The AI did not accept the "spawn error" framing at
face value. It tailed `server.log`, listed ports (`lsof`), enumerated live PIDs, and inspected
the *shipped* `app.asar` with `strings`/`grep` to confirm `e.nodeBin ?? process.execPath` and the
absence of `ELECTRON_RUN_AS_NODE`. **Why it worked:** it separated the two co-resident processes
(Electron app launcher vs. bridge-spawned server) and proved the mechanism against the binary the
user was actually running (v0.5.3), not just the working tree.

**Phase 2 — Formalize as an OpenSpec change.** The human said `create proposal`, then pasted the
`/opsx-ff` fast-forward workflow. The AI produced proposal → design (D1 pure helper, D2 wiring, D3
conditional env stamp, D4 repo-lint) → two delta specs → a 10-group tasks.md, all passing
`openspec validate --strict`. **Decision point:** the human chose to formalize a small runtime fix
as a full spec change rather than a drive-by patch — buying tests, a lint guard, and an archive trail.

**Phase 3 — Implement + test.** `/opsx-apply` drove implementation: pure `pick-node.ts` + 8 unit
tests first, then both launcher wirings, the `doctor.ts` fix, and a `buildSpawnEnv` env-strip.
**Why it worked:** the pure helper was fully unit-testable in isolation before any Electron wiring.

**Phase 4 — Second bug surfaces (resume).** The human steered: "The resume also not working."
The AI initially explained resume was *indirectly* fixed (no server = nowhere for the WS message
to land), then when told sessions were still stuck at "Resuming…", it traced a **real** bug in
`event-wiring.ts`: the pending-resume consumer cleared `resuming:false` on the *new* session id
instead of `pendingResume.oldSessionId`, and `consume()` cancelled the 30s timeout so the cleanup
never ran. Two-line fix + regression test.

**Phase 5 — Land it (much later).** Weeks later the human returned to validate, defer the manual-QA
tasks (DMG build required), archive the change, and sync the delta specs into the main specs —
noticing mid-archive that the branch had switched from `develop` to `feat/enable-standalone-npm-install`.

## 6. Skills, tools & memory created — and why they're effective

No reusable skill or memory was persisted this session, but two reusable *assets* landed in-repo:

- **`pickNodeForServer()` pure helper (`pick-node.ts`)** — captures the "which Node binary should
  Electron spawn the server with" decision as a pure, unit-testable function (bundled → system →
  execpath+`ELECTRON_RUN_AS_NODE` fallback). Effective because it makes the previously-implicit
  fallback explicit and testable across POSIX/Windows path shapes. Invoke this pattern whenever an
  Electron main process needs to spawn a *Node* child.
- **`no-electron-execpath-spawn.test.ts` repo-lint** — a test that fails if any Electron call site
  passes `process.execPath` as a spawn binary. Effective as a *regression fence*: the exact bug can
  never silently return. Scope such lints narrowly (flag binary assignment, not legit `execPath` uses
  in `doctor.ts`/`dependency-detector.ts`) or they become noise.

**Recommended memory to save:** *"Dev-monorepo server restart = `curl -X POST localhost:8000/api/restart`;
`pi-dashboard restart` starts the installed Electron bundle (no client build)."* — this exact
confusion cost a steering round.

## 7. Pitfalls & dead ends

- **`pi-dashboard restart` in dev → blank page / "No client build found".** The CLI restarts the
  *installed* package, not your monorepo. Use the `/api/restart` curl instead.
- **Windows path unit test failed** because `path.join` uses the host separator (macOS `/`). Fix:
  use `path.win32.join` in both implementation and test for Windows path shapes.
- **A broad `process.execPath` ban is too noisy** — legitimate uses exist. Tighten the lint to the
  binary-assignment pattern only.
- **Don't trust "fixed" from the source tree** — the user runs a shipped `app.asar` (v0.5.3); a
  source fix isn't live until a fresh DMG is built and installed. Six QA tasks were correctly
  deferred for exactly this reason.
- **Branch drift between sessions.** Work resumed weeks later on a *different* branch; the archive
  commit landed on `feat/enable-standalone-npm-install` while the code fixes live on `develop`.
  `git status` before committing/pushing.
