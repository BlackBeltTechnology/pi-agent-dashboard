# How we did it: Streamline Electron bootstrap & recovery — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened not with a task but with a question:

> "Is the electron rewrite the .pi-dashboard directory contents? The embedded packages?"

The *real* objective only emerged over 13 clarifying turns: **make the Electron desktop
app self-heal.** Today's bootstrap is binary — first-run installs pi/openspec/tsx from
the offline cacache, every later launch assumes the managed install (`~/.pi-dashboard/`)
is intact. When it isn't (missing `.version` marker, half-installed deps, a server that
won't start), the user hits a dead "Cannot connect" wall. The goal became: **detect what
is actually present in `~/.pi-dashboard/`, offer targeted reinstall/force-reinstall from
three surfaces (loading page, Doctor, slimmed wizard), preserve user-owned packages, and
make it all work with the server down.** That understanding was then frozen into an
OpenSpec change (`streamline-electron-bootstrap-and-recovery`) and partially implemented.

## 2. TL;DR playbook

1. **Ask the architecture question first, don't assume.** "Is X the same as Y?" forces the
   AI to draw the boundary (repo source vs. `~/.pi-dashboard/` runtime vs. bundled
   `resources/`) before any code is proposed.
2. **Interrogate the current state layer by layer** — bundled Node, offline cacache,
   plugins, pi-core update path — one prompt per layer, demanding *verified* facts from
   source, not speculation.
3. **Probe the failure gap explicitly:** "does update work with the server down?" surfaces
   which paths are server-routed vs. Electron-main-process independent.
4. **State the safety constraint before designing the fix:** "keep user-installed packages,
   only wipe Electron-owned ones" → yields the whitelist contract.
5. **`create proposal`** — turn the verified findings into `proposal.md` + `design.md` +
   `tasks.md` + per-capability specs. Run `openspec change validate`.
6. **Apply in waves, not one shot.** Group 1 (whitelist + parity test) → Group 2 (installable
   v2 schema + migration) → checkpoint. Each group is independently testable.
7. **Run vitest with `HOME=$(mktemp -d)`** so tests don't touch the real `~/.pi-dashboard/`.
8. **`git stash` to prove a failing test is pre-existing**, not your regression, before
   marking a group complete.

## 3. How the collaboration unfolded

**Phase 1 — Boundary discovery (prompts 1–4).** The AI grepped `docs/architecture.md`,
`packages/electron/src/main.ts`, and `bootstrap-install.ts` to answer "what is what." It
produced clean distinction tables: Electron rewrite = `packages/electron/` source;
`~/.pi-dashboard/` = runtime managed install; embedded packages = `resources/` (bundled
Node, offline cacache). It then mapped the existing `pi-core` update system
(`GET /api/pi-core/versions`, `POST /api/pi-core/update`) and, critically, which update
paths **require the server** vs. run in the Electron main process (Doctor, wizard).

**Phase 2 — Gap analysis (prompts 5–9).** The human pushed on the failure mode: server
won't start → generic error, no recovery. The AI verified the exact code: `installManagedNode`
*does* handle a missing `.version` marker (re-copies), but the pi/openspec/tsx packages have
**no version file at all** — only a presence check (`isManagedDirPopulated`) that runs
**only on first run**. That's the confirmed gap. The human then set the safety boundary
(preserve user packages) and asked for a local build that bakes in the offline cache.

**Phase 3 — Scope negotiation (prompts 10–13).** The human questioned whether the wizard
still has a purpose once the loading page can reinstall. The AI produced a
responsibility-vs-covered table, concluding the wizard slims to a first-run welcome +
unified package selector (drop mode distinction, drop API-key step, drop bridge registration
as an error path).

**Phase 4 — Proposal (prompt 14, `create proposal`).** The AI scaffolded the OpenSpec change:
`proposal.md`, `design.md` (state-machine before/after, whitelist contract, force-reinstall
safety model), `tasks.md` (14 groups / 66 tasks), and 7 capability specs. Validated with
`openspec change validate`.

**Phase 5 — Waved implementation (prompts 15–19).** Ran `/opsx-apply`. The AI first proposed
Option B (checkpoint per group) but was told "A" (all at once), started, then **self-corrected
back to B after Group 2** when it realized 66 tasks in one patch is unreviewable. It shipped
Groups 1, 2, then (across sessions) 3, 4, 5 — whitelist, installable v2 schema, preflight
reconcile, force-reinstall, and the recovery IPC surface — each with tests.

## 4. Prompts that worked

- **The goal prompt** ("Is the electron rewrite the .pi-dashboard directory contents?") — a
  deceptively small question that forced the AI to establish the architecture boundary before
  anything else. Effective because a wrong mental model here poisons every later decision.
- **"And the cache, node, npm etc versions? The plugins and included packages?"** — enumerates
  every layer, so the AI answers exhaustively instead of picking one.
- **"Is it able to update without the dashboard server running?"** — the single highest-leverage
  prompt: it split the whole design into server-routed vs. Electron-independent paths.
- **"Keep the user settings, the installed packages... Keep packages which not belong to Electron"**
  — one sentence that produced the entire whitelist contract (`ELECTRON_OWNED_PACKAGES`).
- **"create proposal"** — a clean handoff once the facts were verified; the AI already had all
  the source-grounded material.
- Rewrite of the weak "A" / "2" / "continue with group 5" replies: instead of a bare letter,
  say **"Option A but checkpoint after each task group and run its tests before the next"** —
  it gets you the safety of B without the AI having to re-propose it mid-stream.

## 6. Skills, tools & memory created — and why they're effective

No pi skill or memory was persisted this session. But the workflow produced two **reusable
code contracts** worth treating as durable assets:

- **`ELECTRON_OWNED_PACKAGES` whitelist + parity test** (`packages/shared/src/managed-package-whitelist.ts`
  + `managed-package-whitelist-parity.test.ts`). Captures the single source of truth for
  "what force-reinstall may wipe." Effective because it turns a fuzzy safety rule ("don't
  delete user packages") into a machine-checked invariant: the parity test fails if the
  whitelist drifts from `offline-packages.json`. Invoke this pattern whenever a destructive
  operation needs a provable ownership boundary.
- **Installable catalog v2 migration** (`installable-list.ts` + `installable-list-v2-migration.test.ts`).
  A non-eager `schemaVersion: 2` envelope with a pure `migrateToV2` helper — backward-compatible
  by construction, 13 tests. Invoke when evolving a persisted JSON schema without a hard cutover.

**Recommended skill to create:** a `verify-managed-install-claims` note — the recurring move
of grepping `bootstrap-install.ts` / `power-user-install.ts` to confirm whether a marker file
or presence check actually gates an install path. It saved the session from designing around a
wrong assumption twice.

## 7. Pitfalls & dead ends

- **Pre-existing lint failure looks like yours.** Three Electron files
  (`dependency-detector.ts`, `launch-source.ts`, `server-lifecycle.ts`) import
  `node:child_process` directly and fail the `no-direct-child-process` test *before* this
  session's changes. → `git stash -u` then re-run the suite to confirm it fails without your
  diff, so you don't chase a ghost.
- **Tests touching the real home dir.** vitest for the Electron/shared packages hits
  `~/.pi-dashboard/`. → Always run with `HOME=$(mktemp -d) npx vitest run` to isolate.
- **No tsconfig in `packages/electron`.** `npx tsc --noEmit -p .` finds nothing; Electron
  type-checks via Vite/vitest. → Don't hunt for a tsconfig; run the vitest suite instead.
- **The `kind` field collision.** The proposal planned `kind: "core" | "extension"`, but the
  schema already uses `kind: "npm" | "pi-extension"` for install-path routing. → Dropped the
  new field; derived the tier from the existing `required` flag + a new informational `source`.
  Simpler than spec'd — let implementation reveal the collision and revise the spec in-flight.
- **Option A on a 66-task change.** Attempting everything in one patch produces an unreviewable
  5000+ LOC diff. → Wave it by task group; each `tasks.md` group is independently coherent.
