# How we did it: Fix the Electron wizard's `npm root -g` ENOENT crash — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The session opened with a screenshot (no words) of an Electron startup failure: the
PI-Dashboard.app server child process exited with `code=1` before becoming healthy.
The *real* objective, once the steering clarified it, was two-layered:

1. **Immediately** — get the user's broken local Electron install booting again (a
   corrupted `~/.pi-dashboard/` managed dir).
2. **Durably** — root-cause and fix the underlying bug: the wizard crashes with
   `Failed to run npm root -g: spawnSync npm ENOENT` because macOS GUI apps don't
   inherit the shell `PATH`, so bare `npm` isn't resolvable at first launch. Ship
   this as a proper OpenSpec change (`fix-electron-wizard-npm-root-enoent`) with a
   registry strategy, tests, and docs.

## 2. TL;DR playbook

1. **Read the real logs, not the UI error.** `~/.pi/dashboard/server.log` holds the
   child stdout/stderr — grep it for `MODULE_NOT_FOUND` / `spawnSync npm ENOENT`.
2. **Recover the corrupt managed dir surgically:** remove only `node_modules/`,
   `package.json`, `package-lock.json`, `.version`; **preserve** `honcho/`, `node/`,
   `node_modules.d/`, `packages/`, `recommended.json`, `server.log`. Relaunch → app
   re-extracts.
3. **Trace the ENOENT to source:** it's thrown at
   `packages/server/src/package-manager-wrapper.ts` when pi's `DefaultPackageManager`
   probes `npm root -g` and the `ToolRegistry` returns bare `"npm"`.
4. **Scaffold the OpenSpec change** (`openspec new change …`) and drive proposal →
   design → specs → tasks with `openspec instructions <artifact>` before each.
5. **Fix in the registry, not a bootstrap hook:** add
   `electronBundledRuntimeStrategy` to the `npm` **and** `node` chains, ordered
   `override → managed → electron-bundled → (win32 npmCliBesideNode) → where`. Map
   `classify("electron-bundled") → managed`.
6. **Also fix `nodeScriptToArgv`** to prepend `node` on *all* platforms for `.js`
   paths (bundled `npm-cli.js` has no usable shebang when node isn't on PATH).
7. **Test at the registry level:** 8 strategy-isolation tests + 9 chain-ordering /
   acceptance tests; regenerate the 1080-cell bootstrap-harness snapshots.
8. **Verify the fix by absence:** `grep -c 'Failed to run npm root -g'
   ~/.pi/dashboard/server.log` → `0` after a clean Electron boot.

## 3. How the collaboration unfolded

**Phase 1 — Emergency recovery (Discovery).** The AI ignored the on-screen Electron
error and went straight to `~/.pi/dashboard/server.log`, finding `Cannot find module
… pi-dashboard-server/src/cli.ts`. It diagnosed a partially-nuked managed install
(an earlier `rm -rf node_modules && npm install` restored only what `package.json`
listed, dropping the dashboard-server package). *Decision point:* the user said
**"preserve"** — so the AI deleted only the broken bits and kept memory/node/backups.

**Phase 2 — Root-cause the real bug (Investigation).** After the re-extract, a
*different* symptom surfaced (`Failed to run npm root -g: spawnSync npm ENOENT`). The
AI grepped the packages tree extensively to pin the throw site, then explained the
timing: pi's `DefaultPackageManager` probes `npm root -g` in the early window before
the registry is pointed at bundled/managed npm, and GUI-process PATH lacks
`/opt/homebrew/bin`.

**Phase 3 — Spec-driven design (Design).** The AI scaffolded
`fix-electron-wizard-npm-root-enoent` and wrote all four artifacts, calling
`openspec instructions <artifact>` before each. Design captured 7 decisions — most
importantly D1 (fix in the registry so every consumer benefits) and D6 (mirror the
exact bundled layout `getBundledNpmPath()` already knows).

**Phase 4 — Implement + test (Generate/Verify).** Wired the strategy into both `npm`
and `node` chains, discovered mid-implementation that `nodeScriptToArgv` needed a
cross-platform `.js` fix, then updated the design/spec to match. 37 tests pass;
1057 total pass with 2 pre-existing unrelated failures.

**Phase 5 — The rebuild rabbit hole (Dead ends).** "rebuild all" led into a long
fight: the DMG built but didn't contain the fix (`bundle-server.mjs` wasn't
triggered by `electron-forge make`); then the running server was a *stale* process
spawned before re-extraction; then `GET /` 404'd because bootstrap's `npm install`
wiped the workspace materialization under `node_modules/@blackbelt-technology/`. The
AT tried symlinks and `cp -R` hacks. *Decision point:* the user said **"I think
symlink is not a good idea"** — the AI reverted all managed-dir hackery and made an
honest call: the fix is proven by unit tests; the end-to-end Electron verification is
blocked by *two separate pre-existing bugs* that belong in
`streamline-electron-bootstrap-and-recovery`.

**Phase 6 — Hand off to a future session (Documentation).** The user asked to write a
detailed report into the parallel `streamline-electron-bootstrap-and-recovery` change
"because it will be performed with other session which does not have any detail." The
AI added +390 lines across proposal/design/tasks with timestamped repro sequences and
`file:line` references. Finally, a bulk-archive skill was invoked to archive
`fix-publish-tsx-missing` and sync its `ci-cd-pipeline` delta spec.

## 7. Pitfalls & dead ends

- **The UI error lies; the log tells the truth.** The Electron loading page showed
  "Port 8000 in use" *and* "Server not responding" while `/api/health` returned 200.
  Always confirm with `curl -s localhost:8000/api/health` + `lsof -i :8000`.
- **`electron-forge make` does not run `bundle-server.mjs`.** A DMG can build from a
  *stale* `resources/server/` tree. Run the bundle step manually, then verify your
  symbol appears (`grep -c electronBundledRuntimeStrategy …/resources/server/...`).
- **A healthy port ≠ your code running.** A server process spawned *before*
  re-extraction keeps serving old code even after `.version` matches. Kill the stale
  pid and let Electron respawn.
- **Bootstrap's `npm install` wipes workspace materialization** under
  `node_modules/@blackbelt-technology/` → `GET /` 404 (API-only mode) and "Cannot
  find module 'fastify'". Symlink/`cp -R` patches are a trap — revert and force a
  clean re-extract instead. (Filed for `streamline-electron-bootstrap-and-recovery`.)
- **Don't relaunch the app from a ctx-mode/sandboxed shell** — it inherits a
  sandboxed `TMPDIR` that jiti can't write to, crashing the server mid-bootstrap.
  Launch PI-Dashboard.app from Dock/Spotlight.
