# How we did it: Streamlining Electron bootstrap & recovery — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a small factual question — *"Is the electron rewrite the
.pi-dashboard directory contents? The embedded packages?"* — not a task. The operator
was **probing the mental model** of how the Electron desktop app relates to the managed
runtime install (`~/.pi-dashboard/`) and its bundled resources. Over fifteen prompts that
probe crystallized into the real objective: **design a complete OpenSpec proposal that
makes Electron bootstrap self-healing** — detect a broken/partial `~/.pi-dashboard/`
without the server running, offer targeted reinstall from the loading page, slim the
first-run wizard down to a unified package selector, add a Doctor force-reinstall, and
guarantee the reinstall never destroys user-owned packages/settings. The deliverable was
a validated `streamline-electron-bootstrap-and-recovery` change (proposal + design + tasks
+ 7 specs), and — a day later, in the same session — the Group 11 documentation rewrites.

## 2. TL;DR playbook

1. **Start with a grounding question, not a task.** Ask the AI to explain the current
   architecture (*"is X the same as Y? where does Z live?"*). Let it build the ownership
   table before you propose changes.
2. **Force verification against source.** After each answer, ask *"check that this
   assumption is true"* — the AI greps the real files (`bootstrap-install.ts`,
   `power-user-install.ts`, `main.ts`) instead of speculating.
3. **Probe each recovery axis one prompt at a time**: no-server updates → restart running
   clients → install-when-no-server → missing version file → preserve user packages →
   local build with cache → loading-page recovery → is the wizard still needed.
4. **Let contradictions surface the design.** When the AI says "the logic is binary,
   here's the gap," that gap becomes a spec.
5. **Name the safety boundary explicitly**: *"Keep the user settings, installed packages…
   keep packages which don't belong to Electron."* This turns into the whitelist contract.
6. **Say `create proposal`** only after the shape is clear — the AI scaffolds
   `openspec change new`, writes proposal/design/tasks + 7 specs, and runs
   `openspec change validate`.
7. **For docs, dispatch subagents in parallel** (caveman-style rule passed verbatim), one
   per file, and edit root `AGENTS.md` directly (it's not under `docs/`).
8. **Verify state before documenting.** Confirm the implementation files actually exist
   before writing docs that describe them.

## 3. How the collaboration unfolded

**Phase 1 — Grounding (prompts 1–4).** The AI never jumped to code. It answered the
"what is what" question with an ownership table (Electron app vs `~/.pi-dashboard/` vs
bundled `resources/`), traced the existing `pi-core` update system, and mapped which
update paths need the server versus which run in the Electron main process. *Why it
worked:* establishing shared vocabulary up front meant every later proposal referenced
real components, not invented ones.

**Phase 2 — Verified gap-finding (prompts 5–8).** Each steering prompt pushed a new
recovery axis. The AI's discipline here was the win: on prompt 7 it explicitly said *"Now
I can answer all three points concretely with verified facts"* and cited line numbers
(`installManagedNode` at `bootstrap-install.ts:299-320`, the presence-only check at
`power-user-install.ts:80`). It flagged where the operator's assumption was **right**
(no version file for pi/openspec/tsx) and **wrong** (missing Node marker *does* re-copy).
The safety prompt ("keep user packages") produced a per-path ownership table separating
wipe-and-reinstall from preserve.

**Phase 3 — Scope reduction (prompts 10–13).** The operator questioned whether the wizard
still had a purpose. The AI didn't defend it reflexively — it produced a
responsibility-by-responsibility table showing what the loading-page mechanism absorbs,
then narrowed the wizard to a four-step onboarding with a unified package selector and no
mode/auth/bridge questions.

**Phase 4 — Generate (prompt 14, `create proposal`).** The AI studied a recently archived
change for format, scaffolded the directory, wrote proposal/design/tasks + 7 spec files,
and validated. Design.md carried before/after state diagrams and the force-reinstall
safety model.

**Phase 5 — Document (prompt 15, a day later).** The operator picked "Group 11"
(docs). Before touching anything the AI **paused to check state** — it worried it might be
documenting code that didn't exist, verified the Group 1–10 files were real, then
dispatched four `general-purpose` subagents in parallel (one per doc) and edited
`AGENTS.md` directly.

## 4. Prompts that worked

- **Goal prompt (grounding, not tasking):** *"Is the electron rewrite the .pi-dashboard
  directory contents?"* — Effective because it made the AI teach the architecture first.
  A future operator should open the same way: **ask for the ownership model before asking
  for a change.**
- **"Check that this assumption is true" (prompt 7):** the single highest-leverage move —
  it converts confident-sounding answers into grepped, line-cited facts. Bake this into
  every planning session.
- **"Keep the user settings… keep packages which don't belong to Electron" (prompt 8):**
  a one-line safety constraint that became the whitelist spec. Naming the invariant early
  prevented a destructive design.
- **"With this mechanism, the wizard have any sensible purpose?" (prompt 11):** a
  scope-cutting question that forced a responsibility audit rather than feature accretion.
- **"create proposal" (prompt 14):** short unlock, issued only once the shape was agreed.
  Rewrite of a weaker version: instead of "write it up," this reader already had the AI's
  verified gap list in context, so the two-word command produced a grounded proposal.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Answer from plausible reasoning | "Check that this assumption is true" | Ask for line-cited verification on every factual claim before it enters a spec |
| Treat reinstall as nuclear (wipe `~/.pi-dashboard/`) | "Keep user settings, installed packages… keep non-Electron packages" | State the preserve/wipe boundary as an explicit whitelist up front |
| Keep the wizard's full step set | "Does the wizard have any sensible purpose?" / "advanced vs full doesn't distinguish" | Question every retained component's job; cut to minimum viable onboarding |

| Nearly document not-yet-existing code | (self-caught) "If I write docs now I'd mislead every agent" | Verify implementation files exist before writing docs that describe them |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session — but the workflow is strongly
repeatable and **should** be captured as a skill: *"verified-gap OpenSpec proposal from an

## 7. Pitfalls & dead ends

- **`awk … | grep -E "^(471|472…)"` failed** — the piped line-number filter returned no
  match; the AI switched to `awk 'NR==472 { print length($0) }'` to inspect specific
  lines directly. If you need one line's length, address it by `NR==`, don't post-filter.
- **`openspec change new` / `--help` exploration** — the AI ran `openspec --help` and
  `openspec change --help` to learn the CLI before scaffolding. Expect one or two
  orientation calls; don't assume the subcommand shape.
- **Documenting ahead of code** — the near-miss in Phase 5. Always reconcile "what the
  session header claims is done" against "what files actually exist" before writing docs.
- **Version-file assumptions** — the operator assumed a missing `.version` blocks install;
  it's true for pi/openspec/tsx (presence-only check) but false for bundled Node (marker
  re-copy). Verify per-artifact; the install logic isn't uniform.
