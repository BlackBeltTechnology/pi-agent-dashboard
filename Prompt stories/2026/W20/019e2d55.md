# How we did it: Streamline Electron bootstrap & recovery — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened as an *investigation*, not a build order. The first prompt was a
plain question:

> "Is the electron rewrite the .pi-dashboard directory contents? The embedded packages?"

What the operator actually wanted became clear only after ~13 clarifying turns: a
**hardened, self-healing Electron bootstrap** for pi-dashboard. Concretely — when the
managed runtime in `~/.pi-dashboard/` drifts, goes stale, or is partially wiped, the
Electron app should *detect what's actually installed*, *reconcile it selectively*
(preserving user-owned packages), and offer recovery *without* requiring the dashboard
server to be running. The end product was an OpenSpec change
(`streamline-electron-bootstrap-and-recovery`) plus the first three implementation
groups landed with tests. The real objective: turn a fragile binary "first-run install
/ else assume intact" flow into a **per-launch inventory + selective repair** system
across three surfaces (wizard, loading page, Doctor).

## 2. TL;DR playbook

1. **Map the terrain first, don't code.** Ask the AI to distinguish source (`packages/electron/`) from the runtime install (`~/.pi-dashboard/`) from the build-time embed (`resources/`). Make it produce a table.
2. **Interrogate the existing mechanism before proposing new work.** Prompt: "is it possible to check versions and update automatically?" — force the AI to inventory what *already exists* (`/api/pi-core/*`, `installManagedNode`, `/reload` broadcast, recovery dialog).
3. **Probe the gaps as concrete failure scenarios.** "Can it update without the server running?", "what if the `.version` file is missing?" — each question narrows to a specific code path the AI must *verify by reading source*, not guess.
4. **Demand verification, not assumption.** When the AI asserts behavior, ask it to check: it found the missing-marker path *does* recopy Node, but managed packages have *no* version file (pure presence check) — a real gap.
5. **Impose the safety constraint early.** "Keep user settings, installed packages — keep packages which don't belong to Electron." This forced a **whitelist / ownership boundary** into the design before any wipe logic was written.
6. **Ask the AI to challenge scope.** "With this mechanism, does the wizard have any sensible purpose?" — collapsed the wizard to a 4-step minimum and removed API-key/mode/bridge questions.
7. **`create proposal`** — turn the converged understanding into an OpenSpec change (proposal + design + 7 specs + tasks).
8. **Apply in waves, checkpoint each group.** Run `/opsx-apply`, implement group → run tests (`HOME=$(mktemp -d) npx vitest run`) → mark tasks → pause for review. Don't one-shot 66 tasks.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (grep-driven fact-finding).** The AI answered each question by
reading actual source (`bootstrap-install.ts`, `main.ts`, `power-user-install.ts`,
`build-installer.sh`) via targeted `grep -rn`. It resisted speculation and built
tables of *current state vs. gap*. **Why it worked:** every architectural claim was
anchored to a file:line, so the eventual proposal cited verified gaps, not
imagined ones.

**Phase 2 — Gap analysis (scenario interrogation).** The operator fired failure
scenarios one at a time (missing `.version`, server-down update, partial deps). Each
forced the AI to confirm or falsify an assumption against source. The decisive finding:
bundled Node self-heals on a missing marker, but managed pi/openspec/tsx packages have
**no version file at all** — only a presence check that short-circuits after first run.
That single fact justified the whole change.

**Phase 3 — Design convergence (constraint + scope pruning).** Two operator moves
shaped the architecture: (a) the *ownership constraint* ("preserve non-Electron
packages") → a managed-package whitelist as the safety boundary for any wipe; (b) the
*scope challenge* ("does the wizard still have a purpose?") → collapse the wizard,
surface recovery on the existing `loading.html`, keep Doctor for force-reinstall.

**Phase 4 — Proposal generation.** `create proposal` → the AI produced
`proposal.md`, `design.md`, `tasks.md` (14 task groups) and **7 capability specs**,
then validated with `openspec change validate`.

**Phase 5 — Waved implementation.** `/opsx-apply` drove the change. The AI initially
proposed Option A (all 66 tasks at once), the operator picked "A", but the AI itself
*course-corrected mid-flight* to Option B (checkpoint per group) after a reality check
on review burden. Groups 1–3 landed: whitelist + parity test, installable-list v2
schema + migration, and preflight-reconcile module — each with passing vitest.

## 4. Prompts that worked

- **The goal prompt (as an investigation):** "Is the electron rewrite the .pi-dashboard directory contents?" — *effective because* it made the AI establish shared vocabulary before any change was discussed. A stronger opener for a future run: *"Explain the three layers — Electron source, `~/.pi-dashboard/` runtime, and `resources/` embed — as a table, then tell me where the bootstrap can drift."*
- **High-leverage follow-up:** "Keep the user settings, the installed packages... Keep packages which don't belong to Electron." — one sentence that became the whitelist contract and the entire force-reinstall safety model.
- **The scope-cutting question:** "With this mechanism, does the wizard have any sensible purpose?" — unlocked a large simplification (removed a whole binary standalone/power-user distinction).
- **`create proposal`** — a single token that converted ~13 turns of converged understanding into structured OpenSpec artifacts.
- **Rewrite of a weak prompt:** several steering turns were terse/typo-laden ("Ony on mismatch", "wiard"). They worked only because context was rich. A future operator should instead state the rule crisply: *"Reconcile only on version/inventory mismatch; when the server is down or older than the Electron-delivered version, notify the user; add a Doctor force-replace of the cached `.pi-dashboard`."*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat first-run install as sufficient (binary "installed / not") | "sometimes the version file is missing... when something is missing from .dashboard, add to it. Check versions too" | State up front: reconcile is *per-launch inventory*, not once-ever |
| Risk a nuclear wipe on force-reinstall | "Keep packages which don't belong to Electron" | Define the ownership whitelist as the first artifact |
| Keep the wizard as a full installer | "does the wizard have any sensible purpose?" / "key settings not required" | Declare the wizard's minimal scope (welcome + package pick) before designing |
| Offer only a limited package selection | "the package installers appear... what will be installed effectively can be selected" | Spec the selector to surface the *full bundled cache*, defaults pre-checked |
| Propose implementing all 66 tasks at once (Option A) | AI self-corrected to Option B after a reality check | Ask for a group-checkpoint plan up front for any >20-task change |

The pattern: the human never wrote code, they wrote **constraints and failure
scenarios**. Every steering turn narrowed an assumption or added a safety boundary.

## 6. Skills, tools & memory created — and why they're effective

No pi *skill* or *memory* was created in this session — the reusable assets are the
**OpenSpec artifacts** and two **codified contracts**:

- **`managed-package-whitelist.ts` (`ELECTRON_OWNED_PACKAGES` + `isElectronOwnedPackage`)** — the single source of truth for "what Electron may wipe/reinstall vs. what the user owns." A parity test asserts it stays in sync with `offline-packages.json`. *Effective because* it turns a fuzzy safety intent ("don't nuke user packages") into a testable boundary reused by preflight, force-reinstall, and Doctor.
- **Installable-list v2 schema + `migrateToV2`** — adds `source` ("offline-cache" / "bundled-git" / "npm-registry") + `schemaVersion` with a non-eager migration and a 13-test suite. *Effective because* it routes install pathways without breaking existing `kind: "npm" | "pi-extension"` consumers.
- **`preflight-reconcile.ts`** — 7 pure helpers (inventory check, selective reinstall, cross-version verdict), 30 tests. *Effective because* the pure/I/O split makes the reconcile logic unit-testable independent of Electron's runtime.

*If this workflow recurs*, the skill worth creating is **"investigate-then-spec": a
grep-anchored discovery loop that produces a gaps table before any OpenSpec proposal.**

## 7. Pitfalls & dead ends

- **Pre-existing repo failures masquerade as your regressions.** 14 vitest failures and a `no-direct-child-process` lint (3 Electron files importing `node:child_process`) were **already red** before the session. *If you hit red tests mid-change, first confirm they fail on `HEAD` untouched* — don't chase someone else's debt.
- **`git stash` inside a test pipeline failed** (the one ❌ command). Don't stash to A/B a test run mid-implementation; run the suite on a clean checkout separately.
- **Vitest needs an isolated HOME.** All test runs used `HOME=$(mktemp -d) npx vitest run` — without it, tests touching `~/.pi-dashboard/` pollute the real managed dir.
- **Design collision on a new field.** The proposed `kind: "core" | "extension"` collided with the existing `kind: "npm" | "pi-extension"`. Fix: drop the new field, derive the tier from `required`, add only `source`. *Lesson:* check existing discriminated-union field names before adding one.
- **One-shotting a 66-task change is a review trap.** The AI nearly produced a 5000-LOC patch. Checkpoint per task group instead.
