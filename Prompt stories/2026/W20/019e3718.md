# How we did it: Peeling four stacked Electron runtime bugs behind one 404 — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff was a routine `/opsx-apply` prompt: **"Implement tasks from an OpenSpec
change … fix-build-installer-stale-server-bundle."** The literal ask was small — land
a bundle-staleness gate so DMG builds stop silently shipping pre-edit source.

But the *real* objective only surfaced once the first DMG was built and tested. The
build-staleness fix was a **keystone**: once DMGs reliably shipped live source, three
independent runtime bugs that had been masked for ~18 hours behind stale source
became visible one after another. The true goal became: **make a locally-installed
PI-Dashboard.app actually boot and serve its UI**, by peeling each newly-exposed bug
(404 → 500 → broken Settings) down to root cause and fixing it with a proper OpenSpec
change each time. Four changes shipped in one 6h 41m session.

## 2. TL;DR playbook

1. **Apply the keystone change first.** `/opsx-apply fix-build-installer-stale-server-bundle`
   — implement the content-stamp gate, write vitest for all four staleness reasons
   (`stamp-missing`, `source-newer`, `bundler-newer`, cache-hit), verify green.
2. **Build a real DMG and treat it as the test rig.** `npm run build:local` in
   `packages/electron` with the **correct Node** on PATH (engines pin `>=22.12.0 <25`;
   use `nvm use 24.15.0` or export `$HOME/.nvm/versions/node/v24.15.0/bin` — background
   builds do NOT inherit an nvm shell).
3. **Install + relaunch + probe live.** After each DMG, `curl http://localhost:8000/`
   and `/api/health`, and `lsof -i :8000` to confirm which PID/cwd is serving.
4. **When a probe fails, diagnose live before coding.** Compare curl-vs-browser,
   check `~/.pi/dashboard/server.log`, and inspect the managed dir
   `~/.pi-dashboard/` filesystem state at the exact moment of failure.
5. **Peel one bug per OpenSpec change.** Each root cause → `openspec change new`,
   proposal + design + tasks + delta spec, minimal fix, regression-pin test, rebuild,
   re-probe. Don't fold independent bugs into one change.
6. **Pin every fix with a test that reproduces the live failure mode** (durable-vs-volatile
   path resolution, no-fetch-handler SW, restrictive-`exports` package detection).
7. **Bust the version-marker trap on every iteration.** The extractor skips
   re-extraction when `~/.pi-dashboard/.version` matches the DMG version — `rm` it to
   force fresh files to land when iterating on a fixed version number.
8. **Distinguish server bug from client cache.** A browser 500/blank while `curl`
   returns 200 is almost always a stale service worker or old-hash cached assets —
   unregister the SW / use incognito before chasing a phantom server bug.

## 3. How the collaboration unfolded

**Phase 1 — Land the keystone (build-staleness gate).**
The AI implemented `fix-build-installer-stale-server-bundle`: a Node helper
(`_bundle-stamp.mjs`) writes a JSON stamp (`builtAt`/`srcMtime`/`bundlerMtime`) outside
the bundle dir, and `build-installer.sh` gates re-bundling on a stale-reason switch.
Node-based mtime walking sidestepped BSD-vs-GNU `stat` portability. 8 vitest tests
green in minutes. *Why it worked:* choosing a testable Node helper over inline bash made
the gate trivially unit-testable and cross-platform.

**Phase 2 — DMG as a live test rig.**
Building the DMG immediately surfaced a pre-existing `macos-alias` native-module
mismatch (compiled for Node 22, shell was Node 25 — outside the `<25` engines pin).
The AI switched to Node 24 via nvm, `npm rebuild macos-alias`, and discovered
background builds don't inherit the nvm shell — so it ran foreground with an explicit
PATH export. It then verified all four gate reasons end-to-end on **real DMG builds**,
including catching a genuine defect: the Vite `dashboardPlugins` plugin regenerates
`plugin-registry.tsx` every build, defeating the cache — fixed by excluding
`generated/` dirs from the walk (same class as `dist`/`node_modules`).

**Phase 3 — The 404 (resolveClientDir strategy order).**
User: **"404 Not Found."** The now-fresh bundle proved this was a *real* runtime bug,
not stale source. Live diagnosis: `GET /` → 404, `/api/health` → 200, but
`~/.pi-dashboard/node_modules/@blackbelt-technology/` was **empty**. Root cause traced
to a startup-order race: `resolveClientDir` strategy 1 (`createRequire` → scope-dir
path) wins at boot, `fastifyStatic.root` is locked to it, then bootstrap's `npm install`
**wipes that volatile scope dir** seconds later → 404 forever. Fix
(`fix-resolve-client-dir-prefers-durable-managed-path`): when the managed-install layout
is detected, promote the **durable managed-root candidate to position 1** ahead of the
volatile scope paths. Result: `GET /` → 200.

**Phase 4 — The 500s (pruned transitive deps).**
Settings showed "Failed to load settings"; `/api/config` returned **500 to the browser
but 200 to curl**. Driving a real browser via the agent-browser MCP surfaced the true
error: `Cannot find module … readable-stream/…duplex.js`. Bootstrap's `npm install <pkg>`
for the 3 installable packages (pi/openspec/tsx) **pruned the entire tree outside that
closure** — including `readable-stream`, `fastify`, `pino` the server needs at runtime.

**Phase 5 — The root of the reconciliation (restrictive exports map).**
Why did `npm install` run *every* launch instead of fast-pathing? The AI reproduced
`isNpmPackageInstalled` inside a jiti-loaded context and found the smoking gun:
`@earendil-works/pi-coding-agent`'s `exports` map omits `./package.json`, so Node 24
throws `ERR_PACKAGE_PATH_NOT_EXPORTED` on `require.resolve("X/package.json")` — the
check returns **false even when the package is fully installed**, so npm install fires
and re-prunes on every boot. Fix (`fix-is-npm-package-installed-exports-map`): a shared
`isPackageInstalledOnDisk` helper using `fs.existsSync` on the on-disk
`node_modules/<name>/package.json`, wired into both the server bootstrap and the wizard's
`isManagedDirPopulated`. Result: all 5 packages `status=satisfied`, npm install never
runs when versions match, transitive deps stay intact, `/api/config` → 200.

**Cross-cutting — the service-worker rewrite.**
Between phases the AI also shipped `fix-sw-strands-stale-assets`: the old `sw.js` had a
fetch handler that synthesised 5xx on transient failures for a real-time dashboard —
harmful. Rewrote it to install+activate only (cache cleanup + `clients.claim()`, **no
fetch handler**), pinned by a lint test.

## 4. Prompts that worked

- **The goal prompt** (`/opsx-apply fix-build-installer-stale-server-bundle`): effective
  because it named the exact change and let the skill drive the schema-aware apply loop.
  A stronger version would have added the intent behind it — "this unblocks live testing
  of the streamline bootstrap bugs" — so the AI frames the DMG as a test rig from step one.
- **"build the DMG to test"** — the single highest-leverage follow-up. It converted an
  abstract "tasks done" state into a real artifact that immediately exposed three hidden
  bugs. *Building the real thing is the test.*
- **Terse failure reports as steering** — "404 Not Found", "Both 404", "error 500",
  "settings does not work". Minimal, but each was a precise symptom that anchored the
  next live-diagnosis loop. They worked because the AI had already established a probe
  ritual (curl + health + lsof + server.log + managed-dir state).
- **"fix it"** — a valid unlock *only because* the diagnosis was already nailed down;
  the AI had root cause and a plan, so one word authorized the change.
- **Screenshot paths pasted as prompts** (`…pi-clipboard-*.png`) — gave the AI the exact
  browser error UI to reason about instead of a paraphrase.

Rewrite weak prompts: instead of "assd" / "a" / "1" (accidental/terse), a future operator
should reply with the observed outcome — "still 404 after clean relaunch, lsof shows PID
X" — which is exactly the data the AI's next step needs.

No new pi *skill* was created, but the session is a textbook case for one. The
repeatable procedure — **"iterate a native desktop bundle against live runtime bugs"** —
deserves a project skill:

- **What it should capture:** the DMG-as-test-rig loop (correct-Node build → install →
  `rm .version` → relaunch → curl/lsof/server.log probe → managed-dir filesystem
  inspection), plus the durable-vs-volatile managed-path rule and the curl-vs-browser
  cache-triage heuristic.
- **Why it's effective:** it removes the two biggest time sinks in this session — the
  Node-version/PATH build failures and chasing browser-cache phantoms as server bugs.
- **When to invoke:** any time an Electron/managed-install runtime bug is suspected after
  a local install (404/500/blank UI, "works in curl not browser", wizard re-fires).

Reusable tooling that *did* prove its worth: the **agent-browser MCP** to reproduce the
exact browser error (revealing the 500-only-in-browser divergence), and three
`general-purpose` subagents delegated to caveman-style docs updates per AGENTS.md.

## 7. Pitfalls & dead ends

- **Background build lost the nvm shell** — `npm run build:local` backgrounded didn't
  inherit `nvm use`; the process used the wrong Node. Fix: export
  `$HOME/.nvm/versions/node/v24.15.0/bin` into PATH or run foreground.
- **`macos-alias` / native-module Node mismatch** — DMG maker failed because the native
  binding was compiled for Node 22 while the shell was Node 25 (outside `<25` engines).
  Fix: `nvm use 24.15.0 && npm rebuild macos-alias`.
- **Bundle cache-hit hid a real edit** — the gate only tracked `packages/*/src`, not
  `public/`, so editing `public/sw.js` returned a false cache-hit. Worked around by
  `rm .bundle-stamp` + stale root `dist/`; the real fix is to track all inputs
  `bundle-server.mjs` reads (logged as a follow-up on the staleness change).
- **Stale root `dist/client/` beat fresh `packages/client/dist/`** — `bundle-server.mjs`
  preferred an old root `dist/` when present. Clean both before rebuilding.
- **The version-marker trap** — new DMG files never landed because
  `~/.pi-dashboard/.version` already matched `0.5.3`; the extractor skipped. Delete the
  marker to force re-extraction when iterating on a fixed version.
- **Chasing a "server 500" that was client-side** — `/api/config` was 500 in the browser
  but 200 in curl; the culprit was a stale service worker synthesising the error and,
  separately, old-hash cached asset URLs. Unregister the SW / clear cache / incognito.
- **`grep -c` exit code 1 read as failure** — zero matches returns exit 1; here that was
  the *expected* pass (no `fetch` listener in `sw.js`). Don't treat it as an error.

- Server log: `~/.pi/dashboard/server.log`. Probes: `curl localhost:8000/`, `/api/health`,

**Loop:**
1. Apply the build-staleness change first; verify all four gate reasons with vitest.
2. `npm run build:local` (correct Node, foreground); confirm gate reason in the log.
3. Install DMG, `rm ~/.pi-dashboard/.version`, fully quit + relaunch from /Applications.
4. Probe `/` + `/api/health` + `lsof`; if a probe fails, diagnose live (curl-vs-browser,
   server.log, managed-dir filesystem state) **before** writing code.
5. One root cause → one `openspec change new` → minimal fix + regression-pin test → rebuild → re-probe.
6. Before blaming the server on a browser 500/blank: unregister the SW / use incognito.
