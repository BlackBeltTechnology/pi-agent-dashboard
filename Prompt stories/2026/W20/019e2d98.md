# How we did it: Streamline Electron bootstrap & recovery — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened not with a task but with a **question**: *"Is the electron rewrite the
.pi-dashboard directory contents? The embedded packages?"* The operator was probing to
understand how the Electron app relates to the managed runtime install at `~/.pi-dashboard/`.

Over 18 prompts the real objective crystallized: **make Electron bootstrap and recovery
self-healing.** When the dashboard server won't start because managed packages (pi, openspec,
tsx) are missing/stale in `~/.pi-dashboard/`, the app should detect the drift, offer a
targeted reinstall (preserving user-installed packages), and expose force-reinstall recovery
on the loading page and in Doctor — without needing the server running. The session turned
that understanding into a full OpenSpec proposal (`streamline-electron-bootstrap-and-recovery`)
with 7 spec capabilities, then began implementing it group-by-group.

## 2. TL;DR playbook

1. **Ask the map question first.** Start with "how do X and Y relate?" to force the AI to
   build a verified architecture table before proposing changes. Don't ask for code yet.
2. **Probe each layer separately** — bundled Node, offline cacache, plugins, versions —
   one prompt each. Each answer is grounded in a `grep`/`cat` of actual source, not memory.
3. **Push the "no server running" constraint hard.** The interesting recovery paths only
   matter when the server is *down*; keep steering the AI back to that scenario.
4. **State the preservation rule early**: "keep user settings and packages that don't
   belong to Electron." This becomes the whitelist/safe-wipe boundary.
5. **Let the AI question its own scope.** When it asked "does the wizard still have a
   purpose?", that pruning produced a simpler design (drop mode.json, drop API-key step).
6. **`create proposal`** — once the design is verified, one prompt spins up proposal.md +
   design.md + tasks.md + 7 specs. Validate with `openspec change validate`.
7. **Apply in waves, not one shot.** Run `/opsx-apply`, but pick **Option B (checkpoint
   per task group)** — implement group → run tests (`HOME=$(mktemp -d) npx vitest run`) →
   mark tasks done → pause for review.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / architecture mapping (prompts 1–5).** The AI answered each probing
question with a verified table (`grep -rn` across `docs/architecture.md`, `packages/electron/`,
`packages/shared/bootstrap-install.ts`). It distinguished the Electron app source from the
`~/.pi-dashboard/` runtime, mapped the pi-core update REST endpoints, and established which
update paths work with the server down (Doctor, first-run wizard, manual npm) vs. which need
it (pi-core check, extension updates). *Why it worked:* every claim was source-grounded, so
later design decisions rested on facts, not speculation.

**Phase 2 — Gap analysis (prompts 6–8).** The operator's assumption ("missing version file →
won't install cached packages") was tested against source. The AI found it **partially wrong**:
bundled Node re-copies on a missing marker, but managed packages have *no* version file at all
— only a presence check that short-circuits after first run. This exposed the real gap: no
"server didn't start AND we think we're installed → inspect `~/.pi-dashboard/` and offer
targeted reinstall" path. The preservation constraint (prompt 8) fixed the safe-wipe boundary.

**Phase 3 — Scope pruning (prompts 10–13).** The operator surfaced the loading page
(`resources/loading.html`) as the recovery surface, then asked the sharp question: *"does the
wizard still have a purpose?"* The AI honestly reported that most wizard logic becomes
redundant, leaving only first-run onboarding. Prompts 12–13 stripped the wizard further:
unified package selector showing the full bundled cache, no mode distinction, no API-key step.

**Phase 4 — Proposal generation (prompt 14).** `create proposal` produced the full OpenSpec
change: proposal.md, design.md (state-machine before/after, whitelist contract, safe-wipe
model, alternatives), tasks.md (14 groups / 66 tasks), and 7 capability specs. Validated clean.

**Phase 5 — Implementation in waves (prompts 15–18).** `/opsx-apply` ran. The AI proposed
three strategies and the operator picked **A** first, then the AI *itself* pivoted to **B**
(checkpoint per group) after realizing a 66-task one-shot would be unreviewable. Groups 1–2
(whitelist + installable v2 schema), then 3–4 (preflight + force-reinstall) landed with tests
green. Ended at 16/66, paused for review.

## 4. Prompts that worked

- **The goal prompt** (*"Is the electron rewrite the .pi-dashboard directory contents?"*) —
  effective *because it was a question, not a command*. It forced a verified mental model
  before any code, so the eventual proposal was grounded. A stronger kickoff for a future
  operator: *"Map how the Electron app, `~/.pi-dashboard/` runtime, and bundled packages
  relate — with a source-cited table — before we touch anything."*
- **High-leverage follow-up** (*"Is it able update without the dashboard server running?"*) —
  one line that reframed the entire problem around the server-down scenario, which is where
  all the valuable recovery work lives.
- **The self-questioning unlock** (*"With this mechanism, the wizard have any sensible
  purpose?"*) — invited the AI to prune scope, producing a simpler design than originally
  planned.
- **`create proposal`** — a single word once the design was settled; the prior phases had
  loaded enough verified context that the AI could generate the whole change coherently.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Answer from the happy path (server running) | "Is it able to update **without the dashboard server running**?" | State the *degraded-mode* scenario up front — recovery work only matters when the server is down |
| Assume the operator's premise was correct | "Check that assumption is true" | Ask the AI to *verify each premise against source* before designing on it |
| Design a nuclear wipe of `~/.pi-dashboard/` | "Keep user settings, installed packages that don't belong to Electron" | Define the ownership whitelist (`ELECTRON_OWNED_PACKAGES`) as the safe-wipe boundary first |

| Show only a limited installable set | "what will be installed effectively can be selected … full bundled inventory" | Surface the whole bundled cache as selectable, sensible defaults on |
| Reach for a 66-task one-shot implementation | The AI self-corrected to Option B (checkpoint per group) | Always implement large OpenSpec changes in reviewable waves, tests green per group |

## 6. Skills, tools & memory created — and why they're effective

No pi skill or memory was created this session. The reusable asset is the **OpenSpec change

**Skill that *should* be created:** a `verify-before-design` guardrail — "when the operator

discipline, and it's fully repeatable.

## 7. Pitfalls & dead ends

- **Vitest touches real `$HOME`.** Bare `npx vitest run` can pollute/read the user's home.
  Every test run used `HOME=$(mktemp -d) npx vitest run` — do the same to keep tests hermetic.
- **Pre-existing repo-lint failure** (3 Electron files import `node:child_process` directly)
  surfaced mid-implementation. It was *not* introduced this session — don't chase it as your
  bug; note it and route around it, since it will block edits to those files later.
- **Schema field collision.** The proposed `kind: "core" | "extension"` collided with the
  existing `kind: "npm" | "pi-extension"` used for install-pathway routing. Fix: drop the new
  field, derive the tier from the existing `required` flag, add only `source` + `schemaVersion`.
  Lesson: read the existing type before adding an overlapping discriminant.
- **One-shot implementation is a trap for large changes.** A 66-task change in a single patch
  is unreviewable. Checkpoint per task group with tests green.
- **Some tasks were already done in a prior session.** Group 3 (preflight) existed already —
  verify filesystem/test state (`vitest run <suite>`) before re-implementing a checked task.
