# How we did it: Streamline Electron bootstrap & recovery — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened as a *question*, not a task:

> "Is the electron rewrite the .pi-dashboard directory contents? The embedded packages?"

The real objective only emerged through 15 follow-up prompts: **redesign the whole
Electron bootstrap + self-recovery story** so the desktop app can detect a broken /
missing / stale managed install in `~/.pi-dashboard/`, repair it selectively (without
nuking user-installed packages), do it *without the dashboard server running*, expose
recovery on the loading page + Doctor window, slim the now-redundant first-run wizard
down to a single unified package selector, and add a one-shot local Electron build that
bundles the offline cache. The output was a full OpenSpec change
(`streamline-electron-bootstrap-and-recovery`) plus a chunk of its implementation
(14 task groups → 41/67 tasks, +14 landed this session).

## 2. TL;DR playbook

1. **Start with orientation questions, not code.** Ask the AI to explain the current
   architecture ("Is X the same as Y? Where does Z live?"). It answered with source-cited
   tables distinguishing Electron app / `~/.pi-dashboard/` runtime / bundled `resources/`.
2. **Probe each layer's update path separately** — bundled Node, offline cacache, plugins,
   pi-core packages. This surfaces which mechanisms already exist vs. the real gap.
3. **Force verification, not assumption:** "Check that this assumption is true." The AI
   read `bootstrap-install.ts` / `power-user-install.ts` and corrected the mental model
   (missing `.version` → re-copies Node; but managed packages have *no* version file, just
   a presence check that never re-runs after first launch).
4. **Constrain the destructive path early:** "Keep the user settings, installed packages,
   keep packages which don't belong to Electron." → produced an explicit
   owner/wipe/preserve table = the whitelist contract.
5. **Say "create proposal"** once the design is agreed. The AI scaffolded the OpenSpec
   change: `proposal.md`, `design.md`, `tasks.md`, 7 capability specs, validated it.
6. **Resume implementation with a status check** ("go on, Group 3 4 5 6 implemented").
   The AI reconciled tasks.md state before writing, then batched low-risk groups
   (Doctor section → catalog assembly → build-local → backcompat) and *deferred the
   destructive wizard-slim group* to its own session.
7. **Gate every group with tsc + scoped vitest** run under a throwaway `HOME` so tests
   can't touch the real `~/.pi-dashboard/`.

## 3. How the collaboration unfolded

**Phase A — Discovery (prompts 1–5).** The AI ran ~15 `grep`/`cat` probes across
`docs/architecture.md`, `packages/electron/src/main.ts`, `packages/shared/src/bootstrap-install.ts`
and answered each question with a *distinction table* (Electron app vs runtime dir vs
bundled resources; per-layer update paths; what needs the server vs what doesn't). Why it
worked: the human asked one crisp architectural question at a time, so each answer was
verifiable and built the shared model incrementally.

**Phase B — Verify assumptions (prompts 6–7).** The turning point. The human wrote a
multi-point assumption ("version file sometimes missing → won't install; only on
mismatch; add missing deps; doctor force-update") and demanded the AI *check if it's
true*. The AI read the actual install code and returned a ✅/⚠️ verdict per claim,
correcting the model. This is where speculation was replaced with source-grounded facts.

**Phase C — Constrain the blast radius (prompt 8).** "Keep user settings / non-Electron
packages." The AI produced a per-path ownership table (`node/` wipe+recopy; the three
pinned packages wipe+reinstall; everything else PRESERVE). That table became the
`managed-package-whitelist` spec — the safety core of force-reinstall.

**Phase D — Design the surfaces (prompts 9–13).** Rapid design iteration: bundle the
offline cache into a local build; add reinstall/force-reinstall to `loading.html`; realize
the wizard is now mostly redundant → slim it to a unified package selector fed by the
bundled cache; drop mode-based branching and API-key/bridge steps. Each answer was a
scoped proposal with before/after tables the human accepted or trimmed.

**Phase E — Generate the change (prompt 14: "create proposal").** The AI looked at an
archived change for format, scaffolded `openspec/changes/streamline-electron-bootstrap-and-recovery/`
with proposal + design + 14-group tasks.md + 7 specs, and `openspec change validate`d it.

**Phase F — Implement in batches (prompts 15–16).** "go on, Group 3 4 5 6 implemented" →
the AI reconciled tasks.md (27/67 already done), recommended a batch order, and landed
Groups 7/9/10/13 with tests, explicitly **deferring the high-risk wizard-slim Group 8**
to a separate focused session.

## 4. Prompts that worked

- **Goal prompt (orientation form):** "Is the electron rewrite the .pi-dashboard directory
  contents?" — Effective because it forced a shared vocabulary *before* any design. A
  stronger kickoff for a repeat: *"Map the Electron bootstrap: what ships in `resources/`,
  what lands in `~/.pi-dashboard/`, and every update path per layer — cite the source."*
- **"Check that this assumption is true."** — The single highest-leverage prompt. It
  converted a plausible-but-wrong mental model into verified facts by making the AI read
  code. Bake this in: never let the AI design on an unverified premise.
- **"Keep the user settings, the installed packages... keep packages which don't belong to
  Electron."** — One sentence that produced the entire ownership/whitelist contract.
- **"With this mechanism, does the wizard have any sensible purpose?"** — A "should this
  still exist?" prompt that triggered a scope-reduction the AI wouldn't have proposed
  unprompted.
- **"create proposal" / "go on, Group X implemented"** — Short unlock prompts; effective
  because all the design context was already agreed, so they just released the next phase.

## 5. Steering & corrections (what to watch for)

## 7. Pitfalls & dead ends

- **Tests can clobber the real runtime dir.** Every vitest run used
  `HOME=$(mktemp -d -t pi-elec-test-XXXXXX)` so managed-install tests never touch the
  operator's real `~/.pi-dashboard/`. Do this — a naked `vitest run` risks real-home writes.
- **Pre-existing test noise.** The broader electron suite had 14 failures in files this
  change never touched (e.g. `preflight-reconcile.test.ts` from an earlier group). The AI
  `git stash`ed and re-ran to prove they were pre-existing — don't chase failures until you
  confirm your diff caused them.
- **Presence-check ≠ version-check.** `isManagedDirPopulated()` only checks a
  `package.json` exists; it never re-runs install after first launch. Any "why didn't it
  update?" bug likely lives here, not in a version comparison.
- **`.version` marker only guards Node, not packages.** Bundled Node self-heals on missing
  marker; the three pinned packages have no marker at all. Don't assume symmetry.
- **Defer the destructive group.** Wizard-slim (deletes steps + `mode.json` machinery) was
  intentionally *not* done in a batch with additive work — it deserves its own review.
