# How we did it: Exploring diagram renderers & inline charts for the dashboard — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened an exploration session to plan new rendering capabilities for the
dashboard's markdown surface. First prompt:

> `/skill:openspec-explore`
> "I would like to add more diagram renders like plantuml. Search web for the possible
> formats. And another, I would like to add inline chart support. Maybe some tables can
> be used to render charts."

The **real objective**, once the two steering turns landed, was: produce a written
exploration doc — a landscape survey of client-side diagram renderers (beyond the
existing Mermaid) and options for turning markdown tables into inline charts — grounded
in the current codebase, and save the whole discussion to `docs/plans/charts.md`. Not
to implement anything: to think, compare, and record.

## 2. TL;DR playbook

1. Kick off with `/skill:openspec-explore` — this is an ideas/research session, not a build.
2. **Ground first.** `grep -r` the client for the current renderer path:
   `MarkdownContent.tsx` (fenced-block interception) → `MermaidBlock.tsx` (renderer).
3. Confirm dependencies: `grep -E "mermaid|chart|d3|recharts|plotly|viz|graphviz" package.json`.
   Establish that **Mermaid is the only diagram renderer today**.
4. **Skip web search.** There is no dedicated web-search tool — only `browser`, which
   flails on DuckDuckGo/GitHub. Work from the model's own ecosystem knowledge instead.
5. Emit a comparison table of **client-side** diagram renderers (Mermaid, PlantUML via
   encoder+public server, PlantUML-wasm offline, Graphviz/viz.js, etc.) with columns:
   library · how it works · bundle size · LLM support.
6. Emit a second section for **inline charts from tables** (recharts/Chart.js/D3 +
   a fenced-block or table-annotation convention).
7. Note the clean extension pattern: new diagram languages = new `if (match[1] === "xxx")`
   branch in `MarkdownContent.tsx` + a sibling renderer component.
8. Save the full conversation: `mkdir -p docs/plans && write docs/plans/charts.md`.

## 3. How the collaboration unfolded

**Phase 1 — Ground in the codebase (worked).** The AI immediately `grep`-ed the client
for `mermaid|diagram|chart|plantuml`, read `MarkdownContent.tsx`, and checked
`package.json`. This established the true starting point: Mermaid is the sole renderer,
intercepted by language-tag on fenced code blocks and routed to `MermaidBlock.tsx`
(serialized render queue, SVG cache, zoom/pan, theme-aware). This grounding is what made
the later survey concrete rather than generic.

**Phase 2 — Web-search flailing (dead end, 34 browser calls).** Taking "Search web" at
face value, the AI tried to browse DuckDuckGo, then GitHub, then random GitHub profiles,
looping ("let me stop going in circles", "let me search properly") without ever using a
real search API — because there isn't one. Roughly 3 minutes of wheel-spinning.

**Phase 3 — Human redirect → knowledge-first survey (worked).** The user cut it off:
"do not use browser, websearch tool you have." The AI acknowledged it has no dedicated
web-search tool, dropped the browser, and produced the actual deliverable from its own
ecosystem knowledge + the codebase grounding: comparison tables for diagram renderers and
inline-chart approaches, an architecture note on the `match[1]` extension pattern, and
open design questions.

**Phase 4 — Persist (worked).** "Save this whole conversation to docs/plans/charts.md."
`mkdir -p docs/plans` then a single `write` produced the artifact.

## 4. Prompts that worked

- **Goal prompt** (`/skill:openspec-explore` + the ask). Good: it named the concrete
  target (PlantUML-like renderers, inline charts) and framed it as exploration. Weak part:
  "Search web for the possible formats" — this sent the AI into a tool it doesn't have.
  **Stronger version:** *"Explore, from your own knowledge and our codebase, the
  client-side diagram renderers we could add beyond Mermaid, plus inline-chart-from-table
  options. Don't web-search — survey from what you know and what's in `src/client`."*
- **High-leverage follow-up #1:** "do not use browser, websearch tool you have." One line
  that reclaimed ~3 wasted minutes and unlocked the real deliverable.
- **High-leverage follow-up #2:** "Save this whole conversation to docs/plans/charts.md."
  Turns an ephemeral chat into a durable plan doc in one move.

## 5. Steering & corrections (what to watch for)

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session. But two reusable facts are worth persisting:

- **Memory (tool-quirk):** *"pi has no dedicated web-search tool — only `browser`, which
  flails on DuckDuckGo/GitHub. For 'survey the landscape' asks, work from model knowledge
  + codebase grep, not the browser."* Saving this would have prevented the entire Phase 2
  dead end.
- **Convention worth a note:** the dashboard's markdown renderer extension pattern —
  fenced-block language tag intercepted in `MarkdownContent.tsx`, routed to a sibling
  renderer component. Any new diagram/chart format follows the same `match[1]` branch shape.

## 7. Pitfalls & dead ends

- **The browser is not a search engine.** If you catch yourself opening DuckDuckGo or
  guessing GitHub URLs, stop — there is no web-search tool. Answer from ecosystem
  knowledge and `grep` the repo instead.
- **Retrying a failing tool ≠ progress.** Three "let me search properly" attempts in a
  row means switch strategies, not repeat.
- **Explore output evaporates unless written.** An `openspec-explore` session that isn't
  saved leaves nothing behind — end with an explicit write to `docs/plans/`.
