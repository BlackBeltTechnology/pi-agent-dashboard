# How we did it: A dashboard package manager for pi extensions — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with:

> "/skill:openspec-explore — I would like to add the possibility to install extension to pi (equivalent pi install method). Maybe add possibility to make same as pi.dev Browse extension function."

The *real* objective, once the early steering turns clarified it: give the dashboard a
**full package manager UI** on top of the existing read-only `PiResourcesView` — browse
and search the npm registry the way `pi.dev/packages` does, install/update/remove packages
in **two scopes** (global → Settings, local → a new Resources tab), proxy every operation
through the dashboard server (using pi's own `PackageManager` API), and **auto-reload every
active pi session** whenever a package changes. It was scoped, designed, and implemented
end-to-end through the full OpenSpec lifecycle (explore → proposal → design → specs → tasks
→ apply → verify → archive).

## 2. TL;DR playbook

1. **Kick off in explore mode** with the goal *and* the reference product: "add a pi-install
   UI, like pi.dev's Browse function." Let the AI map what exists (`PiResourcesView`, read-only)
   vs. what pi's CLI already does (`pi install/remove/update/list`).
2. **Answer the scope questions in one numbered block**: globals in Settings, locals in a new
   Resources tab, use pi's package-manager API, proxy over the server, reload all sessions on change.
3. **Drive the OpenSpec artifacts**: `/opsx:ff` to fast-forward proposal → design → specs → tasks;
   answer the design-clarification batch (side panel vs dialog, README as overlay, install confirm,
   URL input, explicit "Check for updates" button) in one numbered reply.
4. **`/opsx:apply`** and let the AI implement task-by-task: shared types → server wrapper +
   npm proxy + REST routes (each with tests) → client hooks + components → wiring + docs.
5. **Build, restart, reload, then verify in the real browser**: `npm run build && curl -X POST
   .../api/restart && npm run reload`, then drive the UI with the browser tool to confirm buttons
   and filters actually render.
6. **Feed back screenshots for every visual defect** — README not rendering, install button
   invisible, empty Global section, flat hierarchy — one concrete symptom at a time.
7. **Fold all post-apply refinements back into the specs** ("Update specs with changes") *before*
   `/opsx:verify` and `/opsx:archive`, so the spec matches the shipped code.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI probed both sides of the gap: `pi --help`,
`pi install --help`, the global `pi-coding-agent` install for `DefaultPackageManager` /
`SettingsManager` exports, and `curl`'d `pi.dev/packages` to learn it's a client-side page
that searches npm for `keywords:pi-package`. It rendered the current-vs-target picture as
Mermaid graphs. *Why it worked:* grounding the design in the **actual pi API surface** and
the **reference product's real data source** (the npm search endpoint) meant no invented
abstractions — the proposal reused what already shipped.

**Phase 2 — Proposal & design (`/opsx:ff`).** Proposal → design → 8 capability specs → a
28-task plan. The AI paused with a **5-question design batch** (UI pattern, README surface,
install confirmation, git-URL support, update badges) rather than guessing. The operator's
one-block answer converted directly into design decisions and task edits (inline side panel,
README dialog overlay, confirm dialog, manual URL input, explicit "Check for Updates" button).

**Phase 3 — Implementation (`/opsx:apply`).** Task-by-task, TDD on the server: a
`PackageManagerWrapper` (mutex-serialized, progress-forwarding, session-reloading) over pi's
`DefaultPackageManager`; an `npm-search-proxy` with a 5-min cache; 7 REST endpoints; then
client hooks and components. Server pieces landed with tests (31 passing). Client pieces were
verified visually.

**Phase 4 — Iterative visual QA (the bulk of the session).** Fifteen-plus steering turns, each
a single concrete UI defect fed back with a screenshot: README rendering, ESC-to-close, collapsible
categories, progressive indentation, cross-scope "installed" badges, an empty Global section,
and an install button that was *present in the DOM but visually invisible*. The AI repeatedly used
the **browser tool** to confirm the real rendered state before and after each fix.

**Phase 5 — Reconcile & close.** "Update specs with changes" folded every post-apply refinement
into design.md (decisions 13-19), the specs, and a new task group (section 12) — then `/opsx:verify`
(39/39 tasks, 21/21 requirements, 31/31 tests) and `/opsx:archive` synced 6 new + 2 modified
capabilities to the main specs.

## 4. Prompts that worked

- **The goal prompt** — pairing the ask with a *concrete reference* ("same as pi.dev Browse
  function") was high-leverage: it gave the AI a real data source and UX target to reverse-engineer,
  not a blank canvas. A stronger version states scope up front: *"Add a package-manager UI to the
  dashboard: browse/search npm like pi.dev, install/update/remove in global (Settings) and local
  (Resources) scopes, proxy through the server via pi's PackageManager API, and reload all active
  sessions on any change."*
- **The scope block (steering #1)** — five numbered decisions in one message resolved every
  architectural fork at once (where globals live, where locals live, which API, proxy topology,
  reload behavior). Numbered answers to numbered questions is the fastest way to unblock the AI.
- **The design-clarification answers (steering #5)** — again one numbered block answering the AI's
  5-question batch. This is the pattern: when the AI asks a batch, answer as a matching numbered list.
- **"Update specs with changes"** — a short, high-leverage prompt that forced spec/code reconciliation
  before verify. Without it the archive would have shipped a spec that lied about the code.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Trust the DOM ("every card *has* an Install button") over the rendered pixels | Re-reporting "Where is the install button?" with a screenshot | Verifying **visual** state (screenshot), not just DOM presence, before declaring a UI fix done |
| Over-analyze an ambiguous complaint (looping on "no install button" across 5 turns) | Sending a screenshot pinning the exact symptom | Attaching a screenshot with the *first* report of any visual defect |
| Render README with a naive escape-then-HTML parser | "README preview doesn't detect html/markdown" | Reusing the existing `MarkdownContent` (react-markdown + remark-gfm + rehype-raw) from the start |
| Show flat, same-padding nesting | "Deeper levels need more padding" + screenshot | Designing a `depth`-driven `paddingLeft` for any nested tree UI up front |
| Import pi statically at module load (crashes — it's an optional peer dep) | Server-won't-start build output pasted back | Dynamic-importing optional peers, resolving from `npm root -g` via `pathToFileURL` |
| Leave Settings' global packages empty (same static-import failure) | "Why is global empty?" + screenshot | Same optional-peer lesson: resolve the global install path, cache after first load |
| Only filter the current npm search results for the "installed" pill | "Installed button shows nothing" | Synthesizing installed packages into the display list even when absent from search results |

Scope expansions the operator layered in mid-flight: collapsible categories (default collapsed),
collapsible sub-groups (Skills/Extensions/Prompts), ESC-to-close on dialogs, cross-scope install
badges, per-card "Check update", and merging loose-file scopes with package scopes into unified
Local/Global sections.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The reusable value is in the **workflow discipline**,
which is worth capturing:

- **OpenSpec end-to-end for a multi-surface feature** — explore → `/opsx:ff` → `/opsx:apply` →
  "update specs with changes" → `/opsx:verify` → `/opsx:archive`. The "update specs" reconciliation
  step between apply and verify is the non-obvious, high-value move: iterative UI QA always drifts
  the code past the spec, and folding it back keeps the archive honest.
- **Browser-tool-as-QA loop** — driving the actual rendered UI to confirm buttons/filters, catching
  the "DOM says yes, pixels say no" class of bug. Recommend a small project skill:
  *"verify-dashboard-ui-change"* — build → restart → reload → browser-snapshot → screenshot-diff.
- **Optional-peer-dependency loading pattern** — dynamic `import()` of `@mariozechner/pi-coding-agent`
  resolved from `npm root -g` via `pathToFileURL`, with fork fallback (`@oh-my-pi/...`) and a load
  cache. This recurred twice (installed list + global packages) and is a clear memory candidate.

## 7. Pitfalls & dead ends

- **`openspec change new package-manager-ui` failed** — the CLI subcommand wasn't available; the
  artifacts were scaffolded by `mkdir -p openspec/changes/package-manager-ui` + the `/opsx` skills
  instead. If `openspec change new` errors, create the change directory manually and drive artifacts
  via the instructions/status commands.
- **Static import of pi crashed the server at module load** — pi is an *optional peer dependency*,
  absent from the project's `node_modules`. Fix: never top-level-import it; dynamic-import lazily,
  resolve from the global npm root with `pathToFileURL`, cache the module.
- **`createRequire` on an ESM-only global module didn't work** — use `import(pathToFileURL(abs).href)`,
  not `require`, for ESM packages resolved by absolute path.
- **ESM vi.mock quirks** — `vi.clearAllMocks()` wiped the constructor mock's implementation; a
  dynamic import added an extra async tick before the mocked fn was called. Fixes: clear only the
  inner fns (not the constructor), and `await` a tick before asserting.
- **`useRef` needs an initial value** under newer React types — build failed until initializers were added.
- **Chasing an ambiguous "no install button" complaint for 5 turns** — the button was in the DOM the
  whole time; it was visually invisible (`text-[10px]`, `ml-auto`, pushed off the card). Lesson: for a
  "missing" UI element, screenshot first, then make it prominent (full-width, `text-xs`) rather than
  re-verifying the DOM.
