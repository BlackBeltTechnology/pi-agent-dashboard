# How we did it: inline image tool results in the dashboard — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened as an unrelated task: paste in the `nano-banana` image-generation
skill and produce an image ("a luminous human brain floating in deep dark space, with
kraken-like tentacles…"). The AI generated `output/kraken-brain.png`. The **real goal**
surfaced in the very next prompt:

> "Is it possible the generated picture be presented as an image in this dashboard
> session? So when an image generated be shown in the chat window."

Restated: **make the pi-agent-dashboard render images that come back from tool results**
(e.g. the `Read` tool reading a `.png`) inline in the chat view, instead of showing the
dead text string `"Read image file [image/png]"`. This became a full OpenSpec change,
`inline-image-tool-results`, carried from proposal through archive.

## 2. TL;DR playbook

1. **Ask the feasibility question first**, not the implementation: "can the dashboard
   show tool-result images inline?" Let the AI trace the pipeline before proposing code.
2. **Trace the data path end-to-end** — bridge → event store → state-replay → event-reducer
   → `ToolCallStep` → `ReadToolRenderer`. Grep for `tool_execution_end`, `content_block`,
   `image`, `base64`, `mimeType` at each layer.
3. **Verify the upstream assumption against pi's actual source** — read the installed
   `@mariozechner/pi-coding-agent` dist to confirm what `tool_execution_end.result` really
   contains (an object with a `content[]` array, not a flat string).
4. **Open an OpenSpec change**: `openspec new change inline-image-tool-results`, then
   `/opsx:ff` to fast-forward proposal → design → specs → tasks.
5. **Pause before coding** to re-check the riskiest assumption ("does the event actually
   carry image blocks?"). It did — and the check *shrank* the plan (bridge needed no change).
6. **Apply with TDD**: write failing tests per layer (`state-replay`, `event-reducer`,
   `ToolCallStep`), then the minimal implementation, layer by layer.
7. **Skip the full suite when it kills the session** — run only the targeted vitest files.
8. **Verify → sync specs → archive** with `/opsx:verify`, then `/opsx:archive`.

## 3. How the collaboration unfolded

**Phase 1 · Discovery (feasibility).** The human asked whether tool-result images could
render inline. The AI grepped `ChatView.tsx`, `event-reducer.ts`, `ToolCallStep.tsx`, and
the `tool-renderers/` dir, then gave a precise "not currently" answer: the dashboard renders
images on *user* messages but discards image blocks from *tool results*. Effective because
it separated "what works today" from "what it would take", naming the exact layers.

**Phase 2 · Design (OpenSpec proposal).** On "yes, create a proposal", the AI ran
`openspec new change`, walked the spec-driven artifact chain (proposal → design → specs →
tasks), and read pi's installed dist to ground the design. The `go on` prompts advanced each
artifact. It proposed 5 touched components including a bridge change and a 5 MB base64 cap.

**Phase 3 · The clarifying re-check (the pivotal moment).** Asked "is there anything to
clarify?", the AI flagged its own riskiest assumption — *does `tool_execution_end` actually
carry image content blocks?* — and verified it against pi source. Result: the image data
**already flows** through `extractSerializable` → event store (preserved by the `mimeType`
sibling check) → client, and is only discarded at the reducer's `extractContentBlockText`
(text-only). This **simplified** the plan: **no bridge/server changes needed**. The human
added one requirement here: "images be expanded by default."

**Phase 4 · Apply (TDD, layer by layer).** `/opsx:apply` drove implementation. Per layer:
write failing vitest, confirm red, implement minimal green — `state-replay.ts` (extract
`type:"image"` blocks into an `images` field), `event-reducer.ts` (`extractToolResultImages()`
covering both live `result.content` and replayed `data.images`), `types.ts` (`images?` on
`ToolRendererProps`), `ToolCallStep.tsx` (thread `images`, auto-expand when present),
`ChatView.tsx` (pass `msg.images`), `ReadToolRenderer.tsx` (render `<img>` max 512px, code
fallback). 9 new tests; 84 passing.

**Phase 5 · Verify → archive.** `/opsx:verify` produced a completeness/correctness/coherence
report (8/8 tasks, 5/5 requirements, 9/9 scenarios). `/opsx:archive` synced the two delta
specs to main (`inline-image-tool-results` new + `tool-renderers` modified) and moved the
change to `archive/2026-04-04-inline-image-tool-results/`.

## 4. Prompts that worked

- **The pivot prompt** — *"Is it possible the generated picture be presented as an image in
  this dashboard session?"* A feasibility question, not a directive. It let the AI investigate
  before committing to an approach, which is what produced the accurate layer map.
- **"Yes, create a proposal for that"** — high-leverage: converted a finding into a tracked
  OpenSpec change in one line.
- **"Is there anything to clarify?"** — the single most valuable follow-up. It invited the AI
  to surface and verify its riskiest assumption *before* coding, which shrank the plan.
- **"go on without test, because it kills the session"** — a pragmatic constraint that kept
  momentum (run targeted tests only).
- **Slash commands** (`/opsx:ff`, `/opsx:apply`, `/opsx:verify`, `/opsx:archive`) — drove the
  workflow deterministically instead of re-explaining each phase.

Rewrite of the weak `go on` prompts: instead of a bare "go on", say **"continue to the next
artifact; keep the 5 MB cap decision"** so intent survives across turns.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session. But the workflow is a clean, repeatable
pattern worth capturing:

**Recommended skill — "trace-tool-result-through-dashboard-pipeline."** The reusable problem:
any new tool-result payload (images, then audio/PDF/attachments) must be traced through the
fixed layer chain — bridge `extractSerializable` → event store truncation (`mimeType` sibling
preservation) → `state-replay.ts` → `event-reducer.ts` → `ToolCallStep` → the specific
`*ToolRenderer`. It removes the rediscovery grep-hunt each time and encodes the key insight
that **base64 data already survives to the client**; the fix is usually only in the reducer +
renderer, not the bridge. Invoke it whenever "render X from a tool result in the dashboard".

## 7. Pitfalls & dead ends

- **Assuming the bridge must forward image data.** The proposal initially added a bridge task
  and a 5 MB cap there. Reality: the event store already preserves base64 via the `key==="data"`
  + sibling `mimeType` check. *If you're about to touch the bridge for a payload, first confirm
  the data isn't already flowing — grep the event-store truncation logic.*
- **`data.result as string` is a lie for live events.** On live `tool_execution_end`, `result`
  is the full object `{content:[...], details:{}}`, not a string; the cast yields `"[object
  Object]"` unless `toDisplayString`/`extractContentBlockText` unwraps it. Extract images from
  `data.result.content` for live and `data.images` for replayed events — handle both sources.
- **Full test suite killed the session.** Run targeted `npx vitest run <file>` during apply;
  save the full suite for the very end (or CI).
- **One failed grep** (`grep -rn "image\|output_image" src/shared/state-replay.ts` returned
  nothing) — the term wasn't there yet; that absence *was* the signal that image blocks were
  being dropped at extraction.
