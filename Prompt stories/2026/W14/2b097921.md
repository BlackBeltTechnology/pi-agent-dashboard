# How we did it: Designing the pi-log-miner rolling-summarization skill — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The operator opened in **explore mode** and asked, ultrahard, for a *proper skill that
reads a pi session and produces a comprehensive, cost-efficient summarization*. The
first prompt:

> "I would like to create a proper skill which is able to read and make comprehensive
> session summarization. I would like to process response and reasoning one by one with
> a spawned haiku agent... Make a haiku session which reads the knowledge for the
> project. That session be used for next agent — it will help reduce the LLM costs. For
> that fork be added the rolling summarization... Check with the actual knowledge when
> the new information causes surprise or contradicts current knowledge or founds a gap
> and append that new knowledge to rolling summarization. In the next round reuse the
> rolling summarization and go on."

The **real objective**, once the steering turns clarified it, was a full OpenSpec
**change proposal** (not code): a knowledge-seed → topic-aware-chunking →
fork-per-chunk rolling-analysis pipeline built on cheap Haiku sessions, wired into the
dashboard with a Summarize button, a live-tracking toggle, and a real memory backend.
Over 11 prompts the memory backend evolved from an aspirational "Shodh" to **Honcho
running in Docker, routed through pi-model-proxy** so it needs no API keys of its own.

## 2. TL;DR playbook

1. **Enter explore mode first** (`/skill:openspec-explore`, "think ultrahard"). Do not
   let the AI jump to spec files — make it ground in the codebase first.
2. Let the AI read the **SDK session/fork docs, the JSONL format, and the dashboard
   spawn/resume APIs** before proposing an architecture. Confirm it traced
   `SessionManager.forkFrom` and `examples/sdk/11-sessions.ts`.
3. Answer its clarifying questions in **tight numbered lists** ("1. Yes, show the
   button / 2. Direct JSON but use pi api / 3. seed per project...").
4. When a dependency looks aspirational, **make the AI verify it exists** — this is how
   "Shodh" (zero code in the repo) got replaced by Honcho (real SDK, real community
   extension).
5. Point at concrete infra to reuse: *"Honcho connects to pi-model-proxy which
   delegates all models on localhost"* — one sentence collapsed the whole
   key-management problem.
6. **Fast-forward the artifacts** once the proposal is solid: `/opsx:ff
   pi-log-miner-skill` generates design → 10 specs → tasks in one pass.
7. Interrogate the finished plan: *"What are the integration points?"* and *"Is it
   possible to track automatically for session?"* — this surfaced the live-tracking
   feature (one line in `event-wiring.ts`).
8. Fold late decisions (toggle location, ON-by-default) back across **all four
   artifacts** in one update pass.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding.** Before writing anything, the AI read
`session-api.ts`, `process-manager.ts`, `state-replay.ts`, `rest-api.ts`, the
session-file-reader, and the SDK's `examples/sdk/11-sessions.ts` + `sdk.md` fork docs.
*Why it worked:* the architecture that followed used the real fork mechanic and real
JSONL shape instead of an invented one. The operator's "explore, think ultrahard"
opener bought this grounding.

**Phase 2 — First design + Mermaid.** The AI laid out a three-phase pipeline
(knowledge seed → chunk processor forks → rolling summary) as a Mermaid graph and
asked to sharpen it. The operator steered with a 5-point list (show button, direct
JSON via pi API, seed per project but recreatable, detect topic change → new category,
integrate with pi-log-miner + memory).

**Phase 3 — The Shodh→Honcho pivot (the key decision point).** The operator pointed at
`docs/plans/honcho-integration-research.md`. The AI *verified* the codebase and found
Shodh had **zero references beyond the proposal** — aspirational. It checked npm
(`@honcho-ai/sdk` v2.1.0, `@agney/pi-honcho-memory` community extension) and concluded
Honcho was real and had a proven integration pattern. Decision: replace Shodh.

**Phase 4 — Infra reuse.** Two one-line operator prompts collapsed hard problems:
"server creates/manages database over docker" (→ dashboard owns the Honcho Docker
lifecycle) and "Honcho connects to pi-model-proxy" (→ zero key duplication, OAuth
passthrough, graceful CRUD-only degradation).

**Phase 5 — Fast-forward generation.** `/opsx:ff` produced design.md (8 decisions),
10 spec files (one per capability), and tasks.md (59 tasks / 11 groups) in one pass.

**Phase 6 — Interrogate + extend.** The operator asked for integration points and
whether tracking could be automatic. The AI traced `event-wiring.ts` and found every
`agent_end` already flows through the server — automatic tracking needed **one line**.
This became a new `live-automatic-tracking` spec, a header toggle, a Settings switch,
and a bump to 75 tasks / 12 groups, ON by default.

## 4. Prompts that worked

- **The goal prompt** — effective because it (a) opened in explore mode, (b) said
  "think ultrahard", and (c) described the *mechanism* (Haiku forks + rolling summary +
  surprise/contradiction/gap detection) rather than just the outcome. It gave the AI a
  concrete pipeline to ground and critique.
- **"There is a docs/plans/honcho-integration-research.md. Maybe honcho can replace
  shodh. Research and think ultrahard about it."** — high leverage: it handed the AI a
  source file *and* a hypothesis to test, which triggered the verify-it-exists check
  that killed the aspirational dependency.
- **"Honcho connects to pi-model-proxy — which delegates all models from pi on
  localhost."** — one sentence that eliminated an entire key-management design branch.
- **"/opsx:ff pi-log-miner-skill"** — unlocked all downstream artifacts at once, after
  the proposal was solid.
- **"Is it possible to track automatically for session?"** — a probing question that
  surfaced a whole feature the plan was missing.

Weak prompts to rewrite: the terse "1. Ok / 2. No / 3. Ok / 4. delete by default" reply
works only because the AI had just posed a numbered question — restate the option text
when answering out of context so the plan stays self-documenting.

## 5. Steering & corrections (what to watch for)

## 7. Pitfalls & dead ends

- **Aspirational dependencies waste design effort.** The original proposal designed
  around "Shodh", which had zero code. If a dependency has no references beyond the
  proposal, `grep` for it before building on it — if empty, treat it as unverified.
- **Model-id hunting.** Several bash commands greped `pi-ai/dist` for `claude-*` ids
  across shifting node_modules paths; the working one was
  `.../pi-coding-agent/node_modules/@mariozechner/pi-ai/dist/models.generated.js`. Go
  straight to `models.generated.js` for canonical model ids.
- **3 failed commands** were all speculative greps for nonexistent code (`shodh`,
  `model-proxy` under docs) — negative results that correctly steered the design, not
  errors to fix.
- **Late scope additions ripple across artifacts.** The live-tracking feature arrived
  after specs+tasks existed, forcing edits to proposal, design, a new spec, config
  spec, ui spec, and tasks. Interrogate for event-driven/automatic angles *before*
  `/opsx:ff`, not after.
