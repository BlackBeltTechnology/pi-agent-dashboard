# How we did it: Keeping dashboard-monitored pi sessions alive through `vitest` — a debugging marathon

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened on a small visual bug — *"Duplicated cards. I've started one TUI and became 2 sessions"* (with a screenshot). But that first prompt was a door, not the room. Over 61 prompts across ~43 hours the real objective emerged: **make the pi-agent-dashboard robust when a monitored session does long-running in-process work** — running the full `vitest` suite, spawning background subagents — without the dashboard killing the session out from under it. Along the way the same session also fixed ghost/duplicate cards, missing font glyphs, truncated chat messages, unrendered `ask_user` history, broken Mermaid diagrams, fragile server restarts, stale skill caches, and lost subagent-completion state. The through-line: **"why does my pi session die when I run the tests, and how do I stop that."**

## 2. TL;DR playbook

1. **Confirm the symptom with data, not the screenshot.** Pull `/api/sessions`, find the dead session by id, and compare `endedAt` against the last heartbeat — the *gap* names the killer (exactly `180.0s` = heartbeat timeout; `120s` = 2-miss WS ping).
2. **Prove the event loop isn't the culprit first.** pi's bash tool already runs `spawn` (async) — so `process.exit()` in a `vitest` grandchild cannot kill the pi agent. Rule this out before touching timeouts.
3. **Add server-side liveness logging** (`connection closed`, `heartbeat timeout, WS state=<n>`) so the *next* death tells you whether the TCP socket was OPEN (state 1) or CLOSED (state 3) when the timer fired.
4. **Read the state code, not your assumptions.** `WS state=3` on death → the TCP connection *actually dropped*; it wasn't a busy event loop. Re-diagnose.
5. **Find the FD-inheritance root cause.** `vitest` uses `pool: "forks"`; forked workers inherit the parent's WebSocket FD, and when a worker exits it closes that inherited socket → the bridge's TCP connection dies, and the busy event loop can't fire `onclose`/reconnect until `vitest` finishes.
6. **Fix on the server, not the framework.** You can't stop Node's built-in WebSocket FD inheritance, so make the server *tolerant*: heartbeat/WS-ping check the real socket state before killing, and grant an extra grace window (→ 360 s) so the bridge reconnects once the loop frees.
7. **Ship the incidental fixes as you find them** — dev-mode→prod fallback, graceful `/api/restart`, `lsof`-based stop, `refresh=true` resource rescan, subagent event wiring — each is a self-contained commit.
8. **Restart via the API, never `stop && start`.** `curl -X POST /api/restart` preserves mode and health-checks the handoff.

## 3. How the collaboration unfolded

**Phase A — Ghost cards (discovery).** The AI pulled live `/api/sessions`, inspected extension registration, and found the bridge extension was loaded **twice** (local `package.json` + globally npm-linked package), each opening its own WebSocket and one spawning a ghost UUID session. Fix: move bridge state from `globalThis` to `process` (always shared in Node), add a generation counter so stale listeners bail, and add server-side dedup on `session_register`. *Why it worked:* the AI reproduced from the running system's own API instead of trusting the screenshot.

**Phase B — UI papercuts.** Missing font glyphs, truncated messages, unrendered `ask_user` history, and — the sticky one — Mermaid diagrams not rendering. The Mermaid hunt wandered (sanitizer? proxy? HTML entities? MIME type?) before landing on the real cause: **Vite fell back to port 5173 while the dashboard proxy/HMR config referenced port 3000**, so the dynamic `mermaid.js` import 404'd. Later, clipped node text was fixed by dropping the custom `fontFamily` (Mermaid sizes nodes for its own font) and adding `useMaxWidth: true`.

**Phase C — Restart resilience.** The human asked for fault-tolerant restarts so dev/prod sessions don't collide. The AI delivered three self-contained fixes: dev mode falls back to `dist/client/` when Vite is unreachable (no more 502s), `/api/restart` waits for the port to free and health-checks the new server, and `cmdStop` uses `lsof` to reap stale port holders. `/api/health` now reports `.mode` so clients restart in-place.

**Phase D — The session-death marathon (the core).** This is where most of the 61 prompts went. The pattern: run `vitest` → session dies → the AI proposes a theory → deploys → the human runs tests again → it dies again → repeat. The theories, in order the human forced them to be discarded: (1) `process.exit()` from vitest — *disproved, bash is async*; (2) OOM kill — *disproved, no node/pi in the kill log*; (3) heartbeat 90 s racing WS ping 120 s — *raised heartbeat to 180 s, still died at 180 s*; (4) busy event loop starving pongs — *added TCP-socket check before killing, still died*; (5) **`WS state=3` at death** proved the socket genuinely closed → the FD-inheritance root cause. Final fix: tolerate the drop with a 360 s grace window so the bridge reconnects after vitest releases the loop.

**Phase E — Subagent state loss.** Background `Agent` spawns completed but the dashboard never showed completion — because the bridge only forwarded `flow:*` events, not pi-subagents' `subagents:created/started/completed/failed`. The AI wired those events end-to-end (bridge → server → event-reducer `subagents` Map) so completion survives replay.

**Phase F — Incidental skill work.** The human asked to adapt a Claude-Code nano-banana image-gen skill into pi's format (`references/` not `examples/`, pi frontmatter, drop `.skillfish.json`), and to move public OAuth client IDs out of source to dodge GitHub's secret scanner.

## 4. Prompts that worked

- **The goal prompt** — *"Duplicated cards. I've started one TUI and became 2 sessions"* + screenshot. Effective because it paired the symptom with a visual, but a stronger kickoff would have been: *"Two session cards appear for one TUI I started — pull /api/sessions and find whether a ghost session with a random UUID exists."* Naming the diagnostic move shortcuts the discovery phase.
- **"Just analyze, do not modify. Is it possible to handle the execution in an async way to not block the websocket?"** — a high-leverage *analysis-only* prompt. It forced the AI to reason before editing and produced the correct early conclusion (bash is already async) that saved a whole wrong branch.
- **"Something fundamentally off. No heartbeat or ws exchange happens when something is executing. Think hard, analyze the reasons."** — the "think hard / this is fundamental" framing pushed the AI off band-aid timeout bumps toward the real socket-state investigation.
- **"THE TESTS KILLED THE SESSION. There is a Resume button. The task was not finished, vitest killed it!"** — blunt, high-signal steering that re-anchored the AI when it drifted toward "this is a normal session end."
- **"Check what the problem is with the socket state=3"** (paraphrased from the log-reading turn) — asking the AI to interpret its own instrumentation is what finally cracked the root cause.

## 7. Pitfalls & dead ends

- **Bumping timeouts is not a fix.** 90→180→360 s each looked plausible and each failed the same way. If a session dies at *exactly* the timeout value, the timeout isn't the disease — instrument the cause.
- **Don't trust the "normal exit" reading.** A session with `status: ended`, `currentTool: bash`, and a Resume button is a *killed* session, not a finished one.
- **OOM was a red herring.** `log show --predicate 'eventMessage contains "Killed"'` showed only a Metal compiler service — no node/pi. Check the kill log before blaming memory.
- **`process.exit()` from vitest cannot kill pi.** Because pi's bash runs `spawn`, vitest is a grandchild; its exit only kills its own tree. Don't chase this.
- **`serve: false` in dev mode broke static assets.** Disabling static serving for dev made the Vite fallback return `index.html` (HTML MIME) for JS requests → white screen. Always serve static; only route SPA paths through the not-found handler.
- **Mermaid "not rendering" was a port mismatch,** not a sanitizer/entity bug. Vite on 5173 vs config expecting 3000 → dynamic import 404. Check the actual Vite port before rewriting the renderer.
- **`/reload` does not refresh cached Pi Resources or pi's skill list.** Resources need `refresh=true` (server rescan); newly-added skills need a fresh/forked pi session — `/reload` only reloads the bridge extension.
- **Never `pi-dashboard stop && start`.** The 1–3 s gap disconnects every bridge and stale PIDs survive. Use `curl -X POST /api/restart`.

## 8. Reproduce it faster — checklist

**Inputs to have ready:** a running dashboard (`/api/health` reachable), the dead session's id, `~/.pi/dashboard/server.log`, and the ability to re-trigger `vitest` on a monitored session.

- [ ] `curl -s localhost:8000/api/sessions | jq` — find the dead session; compute `endedAt − last heartbeat`.
- [ ] If the gap == the timeout value, **stop bumping timeouts** — add `connection closed` + `heartbeat timeout, WS state=<n>` logging.
- [ ] Re-run tests; read `WS state`: `1` = OPEN (event loop starved) · `3` = CLOSED (socket actually dropped).
- [ ] For `state=3`: confirm `pool: "forks"` in `vitest.config` → FD inheritance is closing the WebSocket.
- [ ] Fix server-side: check real socket state before killing; grant a reconnect grace window (360 s).
- [ ] Wire every event namespace the bridge must forward (`flow:*` **and** `subagents:*`).
- [ ] Restart with `curl -X POST http://localhost:8000/api/restart`; verify `.mode` and new PID via `/api/health`.
