# How we did it: giving dashboard agents eyes (browser-visual-debug) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** — a deliberate "think, don't implement" stance:

> _"Enter explore mode. Think deeply. Visualize freely. Follow the conversation wherever it goes. … You must NEVER write code or implement features … You MAY create OpenSpec artifacts."_

The real objective that crystallized through the steering turns: **agents editing the
dashboard's React/Tailwind UI are blind — they can't see what they render.** The goal was
to design (and then, via OpenSpec, actually ship) a way for a pi agent to open the running
dashboard in a real browser, screenshot it, and feed that image back into the model's vision
so it can *see* the rendered result. The chosen solution: adopt the `pi-agent-browser`
extension for inline vision screenshots, plus a companion `browser-visual-debug` skill that
teaches agents *when and how* to use it (dashboard recipes, responsive presets, a detect
script). The session ran the full OpenSpec arc end to end: **explore → proposal → design →
specs → tasks → apply → verify → test → archive.**

## 2. TL;DR playbook

1. **Start in explore mode** to think without implementing: `/opsx:explore <idea>`.
2. **Ground before designing** — read the existing extension/tool surface (`src/extension/`,
   pi's `docs/extensions.md`) to learn how tools return content. Key discovery: tools can
   return `{ type: "image", data: base64, mimeType }`, and a vision model *sees* it.
3. **Evaluate candidates head-to-head, don't build from scratch** — clone the two proposed
   extensions (`pi-playwright`, `pi-agent-browser`), compare on a matrix, pick
   `pi-agent-browser` (inline vision, mature, Vercel-backed).
4. **Capture the thinking as a proposal**: `create proposal` → `proposal.md`.
5. **Fast-forward the rest of the artifacts**: `/opsx:ff browser-visual-debug` builds
   `design.md` → `specs/…/spec.md` → `tasks.md` in order.
6. **Ask "anything to clarify?"** before implementing — resolve the one open ambiguity
   (append-to-existing vs new) up front.
7. **Implement**: `/opsx:apply browser-visual-debug` (16 tasks: settings.json package entry,
   SKILL.md, detect-dashboard.sh, 3 reference files, AGENTS.md).
8. **Verify then actually test live**: `/opsx:verify` maps requirements → evidence; then
   `Test it` drives the real `browser` tool against the running dashboard (screenshot,
   snapshot, viewport, dark mode).
9. **Archive & sync specs**: `/opsx:archive browser-visual-debug`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding (18:37–18:47).** The AI resisted jumping to a design.
It read `src/extension/ask-user-tool.ts`, pi's `docs/extensions.md`, and the shipped
`antigravity-image-gen.ts` example. The payoff was one concrete fact: **a tool's result
`content` array can carry an `image` part in base64, which the LLM's vision reads directly.**
That single discovery defined the whole architecture (a screenshot → vision feedback loop).
_Why it worked:_ the design rested on a verified capability, not a hoped-for one.

**Phase 2 — Candidate evaluation (18:58–19:01).** Instead of designing an extension from
zero, the AI `git clone`d the two GitHub projects the human named, inspected their files,
and ran `npm info` on the underlying CLIs. It produced a head-to-head matrix
(`pi-playwright` = skill wrapping `@playwright/cli`, saves to file; `pi-agent-browser` =
extension registering a `browser()` tool, returns inline base64). **Decision point:** the
human picked **Option 2** (`pi-agent-browser`) for the inline vision loop.

**Phase 3 — Skill design (19:01–19:21).** The AI grounded recipes in the *actual* dashboard
(`src/server/server.ts`, `src/shared/config.ts` port 8000, the client component list) and
discovered `agent-browser` supports runtime `set viewport` / `set media dark` — enabling a
full responsive + theme audit in one session without restarts. **Decision point:**
`create proposal`.

**Phase 4 — Artifact fast-forward (19:22–19:24).** `/opsx:ff` generated `design.md`
(5 decisions), `specs/…/spec.md` (7 requirements / 14 scenarios), `tasks.md` (16 tasks / 5
groups) in dependency order via `openspec instructions <artifact> --json`.

**Phase 5 — Implement (21:33–21:36).** `/opsx:apply` worked the 16 tasks: added
`npm:pi-agent-browser` to `.pi/settings.json`, wrote `SKILL.md` + `detect-dashboard.sh` +
3 reference files, and updated `AGENTS.md`. The AI correctly recognized that `available_skills`

**Phase 6 — Verify → Fix → Test → Archive (22:15–22:40).** `/opsx:verify` produced a

## 4. Prompts that worked

- **The goal / kickoff prompt** — the explore-mode preamble. Its strength is the explicit
  *stance*: "think, don't implement; you MAY create OpenSpec artifacts." It kept the AI in
  grounding-and-design mode instead of prematurely writing code, which is exactly what you
  want before a proposal exists.
- **High-leverage follow-ups:**
  - `go on` (×2) — cheap continuation tokens that let the AI finish its grounding sweep
    without micromanagement. Effective *because* the AI had a clear stance to continue within.
  - The numbered answer block (`1. General browser 2. Extension - check these two repos … 4.
    Full 5. secondary`) — answered a batch of the AI's clarifying questions in one shot **and**
    handed it two concrete repos to evaluate. This is the single most productive human turn:
    it converted open design space into a bounded comparison.
  - `Option 2` — a one-word decision that unlocked the entire skill-design phase.
  - `Is there anything to clarify?` — invited the AI to surface ambiguity *before* apply,
    catching the append-vs-new question while it was still cheap.
  - `Test it` — forced a real end-to-end run instead of trusting the verify table. This is
    what caught the ANSI-in-path screenshot quirk.
- **Rewrite of a weak prompt:** `fix` and `ok` are terse; they worked only because the AI
  had just presented a precise diff/plan. A stronger, self-documenting form:
  `"apply the SUGGESTION — add 'browser close' to every recipe"` so the intent survives in
  the transcript.

## 6. Skills, tools & memory created — and why they're effective

**`.pi/skills/browser-visual-debug/` (skill + scripts + references)** — the primary asset.

- **What it captures:** *when and how* a dashboard agent should use the `browser` tool to
  see rendered UI — deliberately **not** registering the tool (that's `pi-agent-browser`'s
  job). It layers workflow knowledge on top of a capability.
- **Why it's effective:** it removes the blind-editing problem. `detect-dashboard.sh`
  auto-finds the dashboard URL/mode/Vite status so recipes are copy-paste ready;
  `dashboard-recipes.md` ties 7 recipes to concrete component file paths;
  `responsive-testing.md` gives viewport presets + dark/light workflow using runtime
  `set viewport` / `set media` (no browser restart). It makes a full responsive + theme
  audit reproducible in one session.
- **When to invoke it:** any time an agent edits `src/client/` React/Tailwind and needs to
  confirm the rendered result — before claiming a UI change "looks right."

**Config change:** `npm:pi-agent-browser` added to `.pi/settings.json` — the runtime hook
that makes the `browser` tool available on session load.

## 7. Pitfalls & dead ends

- **`openspec change new <name>` failed** — that subcommand doesn't exist in this repo's
  openspec. Fallback that worked: `mkdir -p openspec/changes/<name>/…` and drive artifact
  creation with `openspec instructions <artifact> --change <name> --json`.
- **ANSI escape codes in the screenshot path** — reading the screenshot file via the manual
  CLI failed because the returned path embedded ANSI color codes. Workaround for manual
  testing: read the file directly. Note: this is an **upstream `pi-agent-browser` quirk**;
  when used as the *registered extension tool* it reads the file itself and handles this
  correctly — the bug only bites raw CLI use.
- **`npm list playwright` returned nonzero** (package not present) — harmless during
  investigation; don't treat "not installed"探 probes as failures.
- **Don't hand-edit `available_skills`** — it's auto-generated by pi from the skills
  directories. Placing `SKILL.md` in the right path *is* the registration.
