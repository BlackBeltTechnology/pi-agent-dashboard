# How we did it: Turning a "the OpenSpec section pops in late" hunch into a validated proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a "think, don't
implement" stance. The kickoff prompt was the skill's boilerplate, so the *real*
objective only emerged through steering: **a folder's OpenSpec section appears several
seconds late with no loading indicator when a new worktree / cwd shows up.** The
operator wanted to understand *why* the existing pending-spinner machinery doesn't fire
on the worktree path, decide the cleanest fix, and capture it as a validated OpenSpec
change proposal — without writing a line of implementation code. The finished artifact:
a `--strict`-valid `emit-openspec-pending-from-poll` change, committed on `develop`.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore`) so the AI investigates but never implements.
2. First move: **"ground this in the actual code before we theorize."** Have the AI map
   the detection → emission → render path with `rg`/`read` (and one `Explore` subagent
   for the initial UI+detection sweep).
3. Ask the AI to produce a **state diagram** of the existing model (here: the
   `OpenSpecData` three-state `{initialized, pending}` machine) so the gap is visible.
4. Steer with the **hard case**: "but what happens when initialization *delays* the
   detection?" — force it to trace the timing race, not just the happy path.
5. Once the two scenarios are distinct (committed `openspec/` vs delayed init-hook),
   say **"create proposal"** — it scaffolds proposal.md / design.md / tasks.md + a
   delta spec.
6. Pick the design option explicitly (**"P2"**) so the AI locks the decision into
   design.md + tasks.md instead of leaving it open.
7. Have it run `openspec validate <change> --strict` and fix until clean.
8. **"commit changes"** — it stages the change dir + the auto-managed `groups.json`
   with a root-cause commit message. Stay on `develop`, no impl code.

## 3. How the collaboration unfolded

**Phase 1 · Ground before theorizing (Discovery).** The AI's first instinct was the
right one: *"Let me ground this in the actual code before we theorize."* It spawned one
`Explore` subagent to locate the OpenSpec status UI + detection code, then read the real
`OpenSpecData` type, the poller, and the cold-boot emission in the browser gateway. ~12
reads / 24 `rg`+`find` commands, zero speculation about unopened code.

**Phase 2 · Make the model visible (Design).** It drew the three-state machine
(`{initialized:false,pending:false}` → render nothing; `pending:true` → spinner;
`initialized:true` → "OpenSpec (N)") and located the exact render guard
(`FolderOpenSpecSection.tsx` `folder-openspec-pending-spinner`). Key finding: the spinner
UI *already exists*; only one code path (`buildOpenSpecConnectSnapshot`, browser
cold-boot) ever emits `pending:true`. The two subsystems (`openspec_update` broadcast vs
`worktree_init_*` event-bus) are genuinely separate pipes — so folding loading into the
init stream would *manufacture* a false dependency.

**Phase 3 · The steering that mattered — the timing race.** The operator asked: *"but
what happens when the initialization delays the detection?"* This split the problem into
**Scenario 1** (parent repo already has committed `openspec/` → dir present at probe time
→ pending fires, works) and **Scenario 2** (a delayed `openspec init` hook creates the
dir *after* the probe → the later discovery poll jumps straight to `initialized:true`,
skipping the transitional pending). That question is what made a naive
"emit-on-registration" fix insufficient.

**Phase 4 · Scaffold + decide + validate (Generate).** On "create proposal" it wrote the
5 change files, framed a **P1 vs P2** design decision, and on "P2" locked it:
*keep `pollOne` pure; add a shared `emitPendingIfDiscovered(cwd)` helper called by the
three broadcast wrappers just before each awaits the poll* — making `pending` a property
of **the poll**, not of registration, which covers all paths including late-appearing
dirs. Then `openspec validate --strict` → clean.

**Phase 5 · Commit (Verify).** It committed the change dir together with the
dashboard-auto-managed `openspec/groups/groups.json` (which carried the change's `ui`
group assignment), with a message capturing the root cause + the P2 decision. Stayed on
`develop`; no implementation code touched — faithful to explore-mode.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — the reusable asset here is the **workflow**, and the
existing `openspec-explore` skill already encodes it. What made it effective:

- **`openspec-explore` (used, not created).** Its "think, never implement; may create
  OpenSpec artifacts" stance is the perfect container for symptom → proposal work: it
  keeps the AI honest (no premature code) while still letting it produce the deliverable.
  Invoke it whenever you have a *symptom* and want a *validated change proposal*, not a
  patch.
- **One `Explore` subagent** for the initial "where is the OpenSpec status UI + detection
  code" sweep — isolates the noisy grep/read fan-out from the main reasoning context.
  Use it for the first locate-everything pass, then read specifics inline.

If you repeat this often, the reusable pattern worth a skill is: *"symptom → ground in
code → diagram current state model → force the edge/timing case → labeled design decision
→ scaffold + `--strict` validate → commit with auto-managed group file."*

## 7. Pitfalls & dead ends

- **The naive fix is a trap.** "Emit `pending:true` at directory registration" fixes
  Scenario 1 but silently misses Scenario 2 (delayed `openspec init` — dir absent at
  probe time, later poll jumps to `initialized:true`). If you hit a "sometimes it works,
  sometimes no spinner" symptom, suspect a **timing race**, not a missing emit call.
- **Don't fold loading into the worktree-init stream.** `openspec_update` (broadcast to
  all browsers, keyed by cwd) and `worktree_init_*` (scoped to one browser via requestId,
  an event-bus) are separate pipes. Coupling them manufactures a false dependency.
- **`openspec/groups/groups.json` churn.** It's dashboard-auto-managed; a `git status`
  will show unrelated churn plus your change's group assignment. Inspect the diff, then
  stage it *with* the change rather than reverting it.
- **`0 failed` commands, but 1 read error.** Nothing blocked progress — the code-first
  discipline (map, then read specifics) kept the exploration cheap.
