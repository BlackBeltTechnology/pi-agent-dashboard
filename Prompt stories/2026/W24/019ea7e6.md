# How we did it: Porting Hermes `/goal` into the dashboard — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (the `openspec-explore` skill): *"Enter explore
mode. Think deeply… you must NEVER write code or implement features… You MAY create
OpenSpec artifacts."* The real objective that surfaced through steering: **decide
whether Hermes's `/goal` cross-turn continuation loop can be ported into *this*
dashboard, prove it against the actual code, and — if viable — capture it as an
OpenSpec proposal** rather than build it. `/goal` = a standing objective that
survives across turns; after every turn a lightweight judge decides "done or
continue" and, if not done, feeds the agent its own continuation prompt.

## 2. TL;DR playbook

1. Kick off in **explore mode** (`openspec-explore`) — a thinking stance, artifacts allowed, no implementation.
2. `web_search` + `fetch_content` the prior art (`ricoyudog/pi-goal-hermes`) — confirm someone already solved the *"is it possible"* half.
3. Steer with one word: **"dig"** — force the model off the reference README and into *this* repo's real routing (`slash-dispatch.ts`, `bridge.ts`).
4. Steer **"trace"** (repeatedly) — make it follow one load-bearing mechanism end-to-end per trace (the follow-up queue lifecycle, the status-surfacing legs).
5. Ask the make-or-break question: **"Is it possible to make as plugin?"** — flips the architecture from a core edit to a three-part plugin (bridge/server/client), using `flows-plugin` as the proven analog.
6. Steer **"capture" / "capture proposal"** — scaffold `openspec/changes/add-goal-continuation-plugin/` matching the closest analog (`add-context-mode-plugin`), then `openspec validate --strict`.
7. **"commit changes"** — commit ONLY the proposal files, leave unrelated working-tree changes untouched.
8. Later: **"is this implemented?"** — reconcile against `git log`; discover PR #103 shipped it in parallel, proposal now redundant.
9. **"Archive it"** — archive the change; skip delta-spec sync because the shipped design diverged from the proposal.

## 3. How the collaboration unfolded

**Phase A — Discovery (prior art).** The AI `web_search`ed the Hermes `/goal`
feature and `fetch_content`ed `ricoyudog/pi-goal-hermes`, reading `goal-manager.ts`
and `index.ts`. Finding: a published Pi extension already replicates the Ralph-loop.
*Why it worked:* it split the problem into "is it possible" (settled by prior art)
vs "where should it live in *this* dashboard" (the actual open question).

**Phase B — Dig (ground in real code).** On the one-word steer **"dig"**, the AI
stopped trusting the reference README and grepped this repo's `slash-dispatch.ts`,
`bridge.ts`, and web reducer. Finding: `pi.dispatchCommand` is **dead code** as of
pi 0.74.1; `/goal` only routes on dashboard-*spawned* headless RPC sessions (Path C),
error-toasts elsewhere. *Decision point:* the human refused to accept the first
optimistic pass and forced verification against source.

**Phase C — Trace (one mechanism at a time).** Three **"trace"** steers each drove a
full end-to-end walk: (1) the `bridgeFollowUp` queue feed/drain lifecycle around
`agent_end` — revealing the collision a naive piggyback would cause; (2) the
status-surfacing path across three legs (bridge `event_forward` → shared protocol →
web reducer `default:` → `RawEventCard`). *Why it worked:* one mechanism per trace,
concrete line numbers, no hand-waving.

**Phase D — Plugin pivot.** The human asked **"Is it possible to make as plugin?"**
The AI checked `dashboard-plugin-runtime` + `ServerPluginContext` and found
`flows-plugin` ships a three-part **bridge/ + server/ + client/** structure with every
capability the goal loop needs. This flipped the design from "edit the core" to
"plugin-native, one core primitive touch."

**Phase E — Capture.** On **"capture proposal"** the AI scaffolded the OpenSpec
change matching `add-context-mode-plugin`, wrote proposal/design/tasks + two delta
specs, and passed `openspec validate --strict`. Committed as `92b9a52b`, isolating
the proposal from an unrelated `vitest.config.ts` change.

**Phase F — Reconcile & archive.** Days later **"is this implemented?"** exposed that
PR #103 had shipped the feature in parallel (installing `@ricoyudog/pi-goal-hermes`
as an extension, *not* vendoring it as the proposal assumed). The proposal commit had
dropped out of history. On **"Archive it"** the AI archived the change and
**deliberately skipped delta-spec sync** because syncing would have written an
inaccurate (vendored) architecture into canonical specs.

## 4. Prompts that worked

- **The goal prompt** — the `openspec-explore` skill invocation. Effective because it
  set a *stance* (think, don't build; artifacts OK) that kept the whole session from
  drifting into premature implementation.
- **"dig"** — one word, huge leverage. It rejected the reference-README answer and
  demanded proof against this repo's code.
- **"trace"** (×3) — each forced a single end-to-end mechanism walk instead of a
  survey. This is where the real design constraints (the follow-up drain collision)
  were found.
- **"Is it possible to make as plugin?"** — the highest-leverage question of the
  session; it reframed the architecture.
- **"is this implemented?"** — the honesty check that caught a redundant proposal
  before more effort was spent.

Weak-prompt rewrite: instead of bare **"trace"**, a future operator can front-load
*"trace the follow-up queue lifecycle around agent_end and tell me where a second
continuation would collide"* to reach the same finding in one turn.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. But the **explore → dig → trace →
plugin-check → capture** loop is clearly repeatable and worth a skill. Recommended
skill to create: **"explore-to-openspec-proposal"** — codifies (a) split prior-art
"is it possible" from "where does it live here", (b) verify against source with
`dig`/`trace` moves, (c) check the plugin runtime before assuming a core edit,
(d) scaffold matching the closest existing change and `validate --strict`,
(e) reconcile against `git log` before claiming implementation state.
The existing `openspec-explore` skill covers the stance; the value-add is the
verification discipline and the reconcile-before-claim guardrail.

## 7. Pitfalls & dead ends

- **`pi.dispatchCommand` is dead code (pi 0.74.1).** If you plan `/goal` routing from
  the dashboard chat, don't rely on `dispatchCommand` — only Path C (spawned headless
  RPC) works; tmux/terminal sessions error-toast.
- **Naive follow-up piggyback collides.** The bridge's own `agent_end` drain
  (`drainFollowupQueue`) pops ONE entry per turn; a goal continuation must go through
  a dedicated `enqueueSystemFollowup` primitive, not `sendUserMessage`.
- **Heredoc commit message silently dropped.** The first multi-line heredoc `git
  commit` didn't land (a pre-commit hook re-staged/aborted); the retry with a
  single-line message succeeded. If HEAD didn't move, re-check with `git log` and use
  a concise message.
- **Proposal became redundant.** The feature shipped via PR #103 while exploration was
  paused; the standalone proposal commit fell out of history. Always reconcile state
  before continuing multi-day work.
- **Don't sync divergent delta specs.** The proposal said "vendor the judge from
  `@ricoyudog/pi-goal-hermes`"; the shipped code installs it as a pi extension.
  Syncing would have written the wrong architecture into canonical specs — archive
  without sync when they diverge.
