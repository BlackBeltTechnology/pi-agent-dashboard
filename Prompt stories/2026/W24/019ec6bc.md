# How we did it: Compact stepper done-node letters — an AI collaboration guideline

## 1. Goal (the ask)

The user opened **explore mode** — the `openspec-explore` skill — with a screenshot of the OpenSpec lifecycle board. The first prompt was the standard explore-mode kickoff:

> *"Enter explore mode. Think deeply. Visualize freely. Follow the conversation wherever it goes… you must NEVER write code or implement features… you MAY create OpenSpec artifacts."*

The **real objective**, which surfaced through the thinking, was a UI-semantics problem: in the board's **compact** stepper variant (no text labels), every completed artifact node — Proposal, Design, Specs, Tasks — collapses to the *same* green checkmark, so you lose which artifact each node represents. The session's job was to diagnose *why* that happens, decide the right fix, and capture the decision as an OpenSpec change proposal — **without touching code**.

## 2. TL;DR playbook

1. **Kick off in explore mode** with the screenshot: `openspec-explore` skill → describe the visual bug ("all done nodes look identical in compact mode").
2. **Ground before riffing.** Spawn the `Explore` subagent to locate the stepper component, then read the `renderContent` state→icon logic. Find the exact rule that swaps letters for checks.
3. **Trace the cited spec.** The code comment claimed *"per design.md §6"* — read §6 in the archived `redesign-session-card-and-composer` change and confirm it says the **opposite** (letters are semantic identifiers, keep them).
4. **Present options, let the human pick.** Offer a small set of resolutions; user chose **Option B** (resolve by variant: letter in compact, check in sidebar).
5. **Find the governing spec.** `grep` reveals the stepper rule lives in `openspec-attach-combo` (line 111 already hedges "mdi-check **or** the artifact letter") and the board uses `variant="compact"`.
6. **On "draft proposal"** — scaffold `openspec/changes/stepper-compact-done-letters/` with `proposal.md`, `tasks.md`, and two MODIFIED spec deltas (`openspec-attach-combo`, `openspec-board`).
7. **Validate** with `openspec validate <change> --strict`.
8. **On "commit"** — stage **only** your four files (`git reset` first), leave pre-existing unrelated staged changes untouched, commit with a `docs(openspec):` message.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (ground the visual bug in code).**
The AI's first move was *"Let me ground this in the actual code before riffing."* It spawned the `Explore` subagent to find the board stepper, then read the component's `renderContent` to extract the exact rule: `state === "done" AND node has a letter → render ✓; otherwise → render the letter`. *Why it worked:* it converted a fuzzy screenshot complaint into a precise, quotable code rule before proposing anything.

**Phase 2 — Spec archaeology (the key insight).**
The code comment justified the check with *"per design.md §6."* Instead of trusting it, the AI pulled up §6 in the archived `redesign-session-card-and-composer` change and found the citation was **false** — §6 is about migrating glyphs→MDI icons and explicitly argues letters `P/D/S/T` are *semantic identifiers to keep*. This reframed the whole task: the fix isn't fighting the spec, it's correcting an **undocumented implementation choice that mis-cited the spec.** *Decision point:* the user said **"Option B"**, choosing the resolve-by-variant approach.

**Phase 3 — Locate the governing requirement.**
`grep` across the specs showed the actual normative line lives in `openspec-attach-combo` line 111, which already permits *"mdi-check **or** the artifact letter"* via an unresolved "or". The board was confirmed to use `variant="compact"`. So Option B simply **resolves the existing "or" by variant** rather than inventing new behavior.

**Phase 4 — Generate the proposal.**
On **"draft proposal"**, the AI checked an archived proposal's format first, then wrote four files: `proposal.md` (Why/What/Capabilities/Impact), `tasks.md` (1 code edit · 3 tests · verify), and two MODIFIED spec deltas restating the full requirements with the resolved rule + a new scenario.

**Phase 5 — Validate & commit.**
`openspec validate --strict` passed. On **"commit"**, the AI noticed unrelated staged changes (`groups.json`, `windows-authenticode-signing/tasks.md`), verified they were pre-existing and unrelated, did `git reset` to clear the index, and committed **only** its four files under `docs(openspec):`.

## 4. Prompts that worked

- **The goal prompt (explore-mode kickoff).** Effective because it set a hard *stance* — think and capture artifacts, never implement. This kept the session focused on diagnosis + proposal rather than jumping to a code edit. A stronger version attaches the screenshot and names the exact symptom up front: *"In the compact stepper, all done artifact nodes show the same green check — I can't tell Proposal from Tasks. Explore why and propose a fix."*
- **"Option B"** — a two-word high-leverage follow-up. It worked only because the AI had already laid out labeled options with tradeoffs; the human just picked one. Lesson: make the AI enumerate options *before* asking for a decision.
- **"draft proposal"** — unlocked the full artifact scaffold in one shot because the diagnosis groundwork was already done.
- **"commit"** — trusted the AI to isolate its own changes; it correctly excluded unrelated staged files.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Explore broadly and present multiple directions | "Option B" — decisively picking one resolution | Ask the AI to rank options with a recommended default, so one word ends the branch |
| Wait for a green-light before writing artifacts | "draft proposal" | State up front: "diagnose, then draft the proposal when you're confident" |
| Leave the commit scope ambiguous with unrelated staged files present | "commit" (trusting scope isolation) | Confirm the AI will `git reset` + stage only its own files — it did this correctly here |

The strongest steer wasn't a correction at all — the AI **self-corrected** the mis-cited spec (§6) without being told. Watch for and reward that: when a code comment cites a spec, always open the spec and verify.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this was a single-pass planning session driven by two existing pieces:

- **`openspec-explore` skill** — enforced the think-don't-implement stance and permitted OpenSpec artifact creation. *Reuse it* whenever a UI/design question needs a captured decision but no code yet.
- **`Explore` subagent** — isolated the "find the stepper component" search into its own context so the main thread stayed clean for reasoning. *Invoke it* first whenever you need to locate a component/symbol before reasoning about it.

*Recommended skill to create:* a **"trace-the-cited-spec"** micro-procedure — when a code comment says *"per <doc> §N"*, always open §N and confirm it actually sanctions the behavior. This session's entire pivot hinged on that check; it's a repeatable, high-value habit worth codifying.

## 7. Pitfalls & dead ends

- **Trusting the code comment.** The comment *"done nodes show the check (per design.md §6)"* was wrong. If you'd taken it at face value you'd have "fixed" nothing or fought a phantom spec. **If a comment cites a spec, open the spec.**
- **Committing everything.** Unrelated files (`groups.json`, `windows-authenticode-signing/tasks.md`) were already staged. **If `git status` shows changes you didn't make, `git reset` and stage only your own paths** before committing.
- **Ambiguous "or" in the spec.** `openspec-attach-combo` line 111 said "check **or** letter" — the code silently always picked check. **When a spec hedges with "or", the code has quietly resolved it; find out which way and whether that's intended.**
