# How we did it: Turn a clipped popover into a spec-drift proposal — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a "think, don't implement"
stance. The concrete problem: the `⚙ View` dropdown (`ChatViewMenu`) opens *off the bottom
of the screen*; its lower rows ("Use global settings", the tool-call toggles) render past
the viewport edge and are unreachable. The real objective, once steering clarified it, was
not "nudge one menu" but **produce a grounded OpenSpec change proposal** that (a) explains
*why* the menu clips, (b) audits *every* popover in the client for the same class of bug,
and (c) captures the fix as spec artifacts — without writing a line of implementation code.

## 2. TL;DR playbook

1. Enter `openspec-explore` mode — this hard-stops you from implementing and keeps the
   session as a thinking/artifact-capture partner.
2. Ask the AI to **locate the offending component and its mount point** (`ChatViewMenu` →
   `StatusBar` `leading` slot, pinned near the viewport bottom).
3. Have it answer the deciding architectural question first: *is a clipping ancestor to
   blame, or the viewport itself?* (No `overflow-hidden` ancestor → viewport bottom → a
   simple **flip-up** solves it, no portal / collision library needed).
4. Steer to the **whole surface**: "check all Popovers that avoid the out-of-screen
   experience." Get a classified audit (✅ already-correct / 🔴 the bug / 🟡 latent).
5. Say **"draft proposal."** Before writing, have the AI check OpenSpec conventions and grep
   archived/active changes for prior related work.
6. Let it find the **smoking gun**: `git log` on `ChatViewMenu.tsx` proving the specced
   auto-flip was marked `[x]` done in an archived change but the code never landed → reframe
   as **spec/code drift**, not a new feature.
7. Have it scaffold `openspec/changes/fix-popover-viewport-flip/` (proposal, design, tasks,
   2 spec deltas) and `openspec validate` it clean.
8. Say **"commit changes."** Insist the commit stays surgical — only the 5 proposal files,
   leaving unrelated pre-staged files untouched.

## 3. How the collaboration unfolded

**Phase 1 · Diagnosis (locate + classify the failure).** The AI grepped for `ChatViewMenu`,
found it mounted in `StatusBar`'s `leading` slot, and read the anchoring CSS: `absolute
right-0 mt-1` — hard-coded to grow *downward*. It then asked the one question that decides
the whole solution shape: is an ancestor `overflow-hidden` clipping the menu, or the window?
No clipping ancestor existed, so the clip is the **viewport bottom**. *Why it worked:*
settling "in-flow flip vs. needs-a-portal" up front prevented over-engineering — there is a
whole `flex-1` ChatView of empty space *above* the button, so a self-contained flip-up is
enough.

**Phase 2 · Surface sweep (audit every popover).** On the steering prompt, the AI swept the
client for dropdown/popover patterns and, rather than guessing, **extracted each one's
actual anchoring strategy** to classify vulnerable vs. safe. Result: a tiered table —
`ModelSelector` / `ThinkingLevelSelector` / `CommandInput` already do the correct
`bottom-full mb-1 + max-h + overflow-y-auto` pattern; `ChatViewMenu` is the bug; several
others are latent.

**Phase 3 · Grounding (coherence check before drafting).** Told to "draft proposal," the AI
first grepped archived/active OpenSpec changes and found `2026-06-03-relocate-view-menu-to-status-bar`
(the change that *moved* the menu into the bottom bar) and `2026-06-11-fix-settings-panel-and-reset`
(which added a spec requirement: "Per-session override popover SHALL auto-flip direction").
`git log` on the file proved auto-flip was **marked done but never committed** → the shipped
UI violates its own accepted spec. *Decision point:* this reframed the work from "add a
feature" to "**fix spec/code drift + refactor the duplicated hand-rolled flips onto a shared
hook**."

**Phase 4 · Generate + commit.** Scaffolded the 5 artifacts, `openspec validate` passed
clean, committed only those files (`6e4f88b2`), deliberately leaving an unrelated pre-staged
`windows-authenticode-signing/tasks.md` alone.

## 4. Prompts that worked

- **The goal prompt (explore-mode skill invocation).** Effective because the stance itself
  ("think, not implement; you MAY create OpenSpec artifacts") kept the session from jumping
  to a code fix and steered it toward a *grounded proposal* — exactly the deliverable.
- **"check all PopOver that avoid the out of screen experience"** — a high-leverage
  scope-expander. One short line turned a single-component fix into a full audit that
  surfaced the correct existing pattern (and thus the refactor target). Stronger phrasing:
  *"audit every popover in the client for viewport-edge clipping; classify each as
  correct / buggy / latent and name the anchoring CSS each uses."*
- **"draft proposal"** — worked because the AI treated it as *ground-then-write*: it checked
  conventions and prior archives before drafting, which is what surfaced the spec-drift.
- **"commit changes"** — worked with the AI's own guardrail of keeping the commit surgical.

## 5. Steering & corrections (what to watch for)

explore-mode stance doing the "don't implement" guardrail automatically.

## 7. Pitfalls & dead ends

- **`openspec change new <name>` may not scaffold** — the CLI `new` invocation failed here;
  the AI fell back to `mkdir -p` + writing artifacts manually, then `openspec validate`.
  If the scaffolder errors, create the `openspec/changes/<name>/specs/...` dirs by hand.
- **A `[x]`-checked task does not mean the code shipped.** The archived `2026-06-11` change
  marked auto-flip done, but `git log` on `ChatViewMenu.tsx` proved it was never committed.
  Always verify with file history, not the checkbox — this *is* the whole reframe of the bug.
- **Two commands failed** (a `git log` probe and the `openspec change new` attempt) — both
  recovered by falling back to manual steps. Don't trust the first tool path; confirm.
