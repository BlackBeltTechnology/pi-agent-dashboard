# How we did it: Diagnose & scope OpenSpec board drag visual feedback — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance, explicitly *not* implementation. The user had a working-but-unpolished OpenSpec
kanban board: drag-and-drop *logic* was fine (cards reassign groups, reorder; columns
reorder; everything persists) but it **felt dead** — no grab cursor, no drag ghost, no
drop highlight. The real objective, clarified by two terse follow-ups (`draft proposal`,
`commit`), was: **diagnose exactly why the board has no drag visual feedback, then land a
scoped OpenSpec change proposal** capturing the fix — without writing any implementation
code. From ambiguous "the drag feels off" to a validated, committed proposal in ~8 minutes.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore`) so the AI investigates without implementing.
2. Delegate the code hunt to an **`Explore` subagent**: "find the openspec content view drag-drop code."
3. Have the AI localize the exact component (`OpenSpecBoardView.tsx`) and read the card/column render + `@dnd-kit` wiring.
4. Ask it to **separate symptoms from root causes** — one table row per independent gap, with file + line.
5. Say **`draft proposal`** — it mirrors an existing sibling change (`fix-openspec-board-mobile-scroll`) for conventions, then scaffolds `proposal.md` + `specs/` + `tasks.md`.
6. Run `openspec validate <change>` before trusting it.
7. Say **`commit`** — but first check `git status`; stage **only** your change dir so unrelated staged files don't ride along.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (delegate the hunt).** The AI spawned an `Explore` subagent to
locate the drag-drop code, then grepped for `@dnd-kit` primitives (`DndContext`,
`DragOverlay`, `useDroppable`, `isOver`, `cursor: grab`). This kept the noisy repo-wide
search out of the main context and returned the one file that mattered:
`packages/client/src/components/OpenSpecBoardView.tsx`.

**Phase 2 — Root-cause split (the effective bit).** Instead of "the drag feels off," the AI
produced a **symptom → root cause → location** table with three *independent* gaps:
(1) no grab cursor — only column headers set `cursor:grab`, cards don't; (2) no drag
preview — `DragOverlay` is never rendered (grep: 0 hits), so the card just dims in place;
(3) no drop highlight — `useDroppable`'s `isOver` is destructured away and never used.
Three symptoms, three distinct one-line fixes, each pinned to a line. This is what made the
proposal writable in one pass.

**Phase 3 — Mirror-then-scaffold.** Before writing, the AI read a *similar small change*
(`fix-openspec-board-mobile-scroll`) to copy its proposal/spec/tasks conventions, then
scaffolded the new change: `proposal.md` (why + 3-part fix + a ghost-vs-chip design
decision), `specs/openspec-board/spec.md` (2 MODIFIED requirements), `tasks.md` (4 task
groups with TDD verify steps). It baked in a decision — **lightweight chip** over a faithful
card render in the `DragOverlay` (cheaper at 60fps, reads better as "what am I holding") —
and scoped the change to the board only, flagging `OpenSpecGroupManager.tsx` /
`SortablePinnedGroup.tsx` as deferred follow-ups sharing the same pattern.

**Phase 4 — Validate & commit clean.** Ran `openspec validate` (passed), then noticed
**unrelated staged changes** (`windows-authenticode-signing/tasks.md`, `groups.json`). It
did `git reset -q` then `git add` only its own change dir, committing `166924ac` with just
the three proposal files and leaving the user's other work untouched.

## 4. Prompts that worked

- **Goal prompt (the explore-mode skill):** the strongest kickoff move here was *not
  describing the fix* but entering explore mode and letting the AI diagnose. A future
  operator should say: *"Explore mode. The OpenSpec board drag works but has no visual
  feedback — find the code, split the symptoms into root causes with file+line, don't
  implement."*
- **`draft proposal`** — a two-word high-leverage unlock. It worked *because the diagnosis
  table already existed*: the AI had structured material to turn straight into an OpenSpec
  change. Weak version to avoid: "write it up" (no artifact target). Stronger: "draft an
  OpenSpec change proposal for this, mirror an existing small change's structure."
- **`commit`** — worked, but only because the AI self-checked `git status` first. Bake the
  safety in: *"commit only my change files."*

constraint-carrying skill. The lesson is in the *shape* of the first prompt, not the fixes.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created. The leverage came from **reusing** two existing
assets:

- **`openspec-explore` skill** — enforces a diagnose-don't-implement stance, so the AI
  produces a *proposal* rather than jumping to edits. Invoke it whenever the ask is "why is
  X like this / how should we fix it" and you want a reviewable change before code.
- **`Explore` subagent** — isolates the repo-wide code hunt so grep noise never enters the
  main context; it returns just the culprit file. Invoke it first for any "where is the code
  that does X" question.

**Recommended skill (if this recurs):** a small "diagnose-then-scaffold-openspec-change"
recipe — spawn `Explore`, build a symptom→root-cause→location table, mirror a sibling
change's structure, `openspec validate`, then stage-only-my-dir commit.

## 7. Pitfalls & dead ends

- **Unrelated staged files ride along on commit.** The working tree had pre-staged changes
  (`windows-authenticode-signing/tasks.md`, `groups.json`). If you hit this, `git reset -q`
  then `git add <your-change-dir>` explicitly — never a bare `git add -A`.
- **`DragOverlay` grep returns 0 hits — that IS the finding.** An empty grep here isn't a
  dead end; it's the confirmation that no drag preview is rendered anywhere.
- **One failed grep command** (a compound `echo/grep` probe) — harmless; the AI reran a
  narrower query. Don't over-invest in a single mega-grep; iterate.
