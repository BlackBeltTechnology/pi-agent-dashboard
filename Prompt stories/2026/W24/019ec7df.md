## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking stance,
not an implementation task. The operator wanted to explore whether pi ships a
scriptable dummy/mock model that could drive the dashboard's core round-trip
(**prompt → model → bridge event → server fan-out → client renderer**) end-to-end in
tests, instead of only checking that "the server starts." Once the four steering
answers landed (prompt 2), the *real* objective crystallized: **draft an OpenSpec
proposal for `add-faux-model-integration-tests`** — a Vitest-first integration suite
that uses pi's built-in **faux provider** to exercise every ChatView renderer
(text, thinking, tool calls, `ask_user` kinds) across the full matrix, grounded in
the *actual* pinned pi version.

## 2. TL;DR playbook

1. Enter explore mode: load the `openspec-explore` skill — think, don't implement.
2. **Ground research in installed source, not the web.** `grep -rli "faux\|dummy\|mock.*provider"` inside `node_modules/@earendil-works/pi-ai/` → find `providers/faux.ts` and `registerFauxProvider`.
3. Read the real artifact + doc: `cat node_modules/@earendil-works/pi-ai/dist/providers/faux.d.ts` and `pi-coding-agent/docs/custom-provider.md`.
4. Map the integration surface: how the server spawns pi (`packages/server/src/process-manager.ts`), and how the client keys **tool name → renderer** (`packages/client/src/components/tool-renderers/registry`).
5. **Verify the version** the runtime actually uses: `find … -path "*@earendil-works/pi-ai/package.json"` — confirm faux ships in pi's *bundled* copy, not just the root pin.
6. Run the pre-scaffold **coherence check** — sweep active + archived `openspec/changes/` for `faux|dummy|qa|renderer|integration|smoke` to prove the proposal is distinct.
7. Prompt `draft proposal`: scaffold `proposal.md` + `specs/<cap>/spec.md` + `tasks.md`, matching an existing change's delta format; `openspec validate <name>`.
8. Prompt `commit`: **stage only your own files** — `git reset` unrelated churn, commit the three artifacts.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (grounding).** The AI's first instinct was a `web_search` for
pi's mock provider, which returned partly hallucinated package names. It caught this
itself and pivoted to grepping the **installed source tree**, finding
`registerFauxProvider` exported from `@earendil-works/pi-ai`. *Why it worked:* the
answer was on disk the whole time; local `grep` beat the web for a private/internal API.

**Phase 2 — Gather (map the surface).** Parallel greps traced the three integration
points: how pi selects a model at spawn, how the bridge/server connects a session, and
— the goldmine — the client's **tool-name → renderer registry** (1:1 mapping). This is
what makes faux valuable: a faux script emitting `fauxToolCall("read", …)` deterministically
exercises the `read` renderer end-to-end.

**Phase 3 — Version check (the decision point the human forced).** Steering prompt 2
item 1 ("use same as pi version — check it") pushed a precise audit: root pins
`pi-ai ^0.75.5`, but the **runtime** pi (`pi-coding-agent@0.78.0`) bundles its own
`pi-ai 0.78.0`, and *both* export faux. Conclusion baked into the proposal: **the
fixture must NOT hard-pin pi-ai** — let it resolve to pi's bundled copy so it always
matches whatever pi ships.

**Phase 4 — Coherence check + Generate.** Per project convention, the AI swept active
and archived changes before scaffolding. The three nearest neighbors
(`server-launch-smoke-suite`, `expand-electron-qa-coverage`, `cross-platform-qa-vms`)
all stop at "server is up" — none drive prompt→model→event→renderer — so no collision.
It then wrote the three artifacts (touching **no production code**) and ran
`openspec validate`.

**Phase 5 — Surgical commit.** On `commit`, the AI noticed `openspec/groups/groups.json`
carried unrelated churn (a stray `"sdasdasd"` group it didn't create), `git reset` it,
and committed only its three proposal files as `edb2e4a1`.

## 4. Prompts that worked

- **The goal prompt** (explore-mode skill): effective because it set a *thinking-only*
  stance — the AI researched and proposed rather than jumping to code. Good kickoff for
  "is this even possible / where would it plug in?" questions.
- **The four-answer steering burst** (prompt 2): four terse directives at once —
  `1. use same as pi version - check it / 2. vitest first / 3. Drive the prompt, and
  check it can help to tests the ChatView renderers / 4. full matrix + different renderers,
  askuser etc.` This is high-leverage: it simultaneously pinned the version discipline,
  the test framework, the *purpose* (exercise renderers), and the *scope* (full matrix).
- **`draft proposal`** and **`commit`** — one-word unlocks that worked *because* the
  prior exploration had already established all the context.

*Rewrite for next time:* fold the version-discipline directive into the goal prompt —
"explore a faux-model test suite; confirm faux ships in the **runtime** pi version
(not just the root pin) before proposing anything."

## 7. Pitfalls & dead ends

- **`web_search` for internal pi APIs → hallucinated package names.** If you hit this,
  stop and `grep -rli` the installed `node_modules/@earendil-works/` tree instead.
- **Trusting the root `package.json` pin.** The runtime pi bundles its *own* pi-ai; the
  root pin (`^0.75.5`) is not what QA spawns (`0.78.0`). Resolve the actual bundled copy.
- **`openspec change new <name>` failed** — the CLI didn't scaffold as expected; the AI
  fell back to copying an existing change's structure by hand (`proposal.md` +
  `specs/<cap>/spec.md` + `tasks.md`) and `openspec validate`.
- **`openspec/groups/groups.json` had foreign churn** (a stray `"sdasdasd"` group). Don't
