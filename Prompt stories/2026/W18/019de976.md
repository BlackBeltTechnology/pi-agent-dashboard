# How we did it: Seed two monorepo plugins for npm publishing — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with:

> "There is plugins which have to be artifact in this mono repo. No npmjs package
> released yet, I would like to create seed versions to be able to release"

Two workspace packages (`flows-plugin`, `jj-plugin`) were marked `"private": true` and
had never been published to npm. The real objective — clarified over the next five
steering turns — was: **make both plugins publishable, wire them into the release
workflow, document the repeatable procedure for future plugins, and produce the exact
commands to bootstrap the first-ever publish given an OIDC-only (no NPM_TOKEN)
workflow.** The deliverable ended up being code edits *plus* a durable how-to doc, not
an actual live publish (that step needs the operator's npm credentials).

## 2. TL;DR playbook

1. **Survey the terrain first.** `ls packages/` + `cat` each plugin's `package.json`;
   grep the publish workflow to see which packages are already listed and how.
2. **Find the invariant before editing versions.** Read `scripts/sync-versions.js` — it
   enforces a strict lockstep: every workspace `package.json` MUST share one version
   string or the release `exit(1)`s. This constraint dictates everything.
3. **Make the packages publishable:** drop `"private": true`, add
   `"publishConfig": { "access": "public" }`, add `"license"`. Keep the version at the
   monorepo lockstep value (`0.4.5`), not `0.0.1`.
4. **Fix declared-vs-imported deps.** Grep each plugin's `src/` for
   `@blackbelt-technology/*` imports and reconcile against `dependencies` — `jj-plugin`
   imported `dashboard-plugin-runtime/context` at runtime without declaring it.
5. **Register in the release workflow.** Add both names to `PACKAGES=(...)` in
   `.github/workflows/publish.yml`, positioned **after** `dashboard-plugin-runtime` and
   **before** the root metapackage (sub-packages publish before the root that depends
   on them).
6. **Dry-run both tarballs** (`npm publish --workspace=<pkg> --access public --dry-run`)
   to confirm the file lists before any real publish.
7. **Write `docs/publishing-plugins.md`** capturing the full 7-step procedure + the
   OIDC chicken-and-egg (first publish must be local; Trusted Publisher requires the
   package to already exist).
8. **Commit only the task-relevant files** — the tree had unrelated openspec/diagram
   changes; stage the 4 files explicitly.

## 3. How the collaboration unfolded

**Phase 1 — Discovery.** The AI listed `packages/`, read all four plugin manifests, and
grepped `publish.yml`. It correctly classified the state: `dashboard-plugin-runtime`
already public, `flows-plugin`/`jj-plugin` private, `demo-plugin` an intentional
`fixture` that stays private. *Why it worked:* it built a truth table before proposing
any edit, so the plan was grounded in the actual repo, not assumptions.

**Phase 2 — Constraint discovery (the pivotal moment).** Before committing to a version
number, the AI read `scripts/sync-versions.js` and surfaced the **lockstep invariant**:
setting the plugins to `0.0.1` while the repo sits at `0.4.5` would break the next
release. It paused and presented three options (A: match `0.4.5`; B: one-shot `0.0.1`
seed then revert; C: exempt from sync — not recommended). *This is the highest-value
move in the session* — catching a release-breaking constraint before writing code.

**Phase 3 — Edit + reconcile.** Removed `private`, added `publishConfig`/`license`, and
found a real latent bug: `jj-plugin` imported a runtime package it never declared
(worked only via workspace hoisting). Added `dashboard-plugin-runtime: ^0.4.5`.

**Phase 4 — Wire the workflow + dry-run.** Inserted both packages into `PACKAGES=(...)`
in dependency order; ran `--dry-run` for both to confirm clean tarballs.

**Phase 5 — Document the OIDC chicken-and-egg.** Steering prompt 3 ("I can add only
when a release pushed to npmjs") exposed the crux: the workflow uses OIDC/Trusted
Publisher only, which **requires the package to already exist** — so a brand-new
package can never be bootstrapped by CI. The AI made this explicit in the doc: the
**first** publish of any new plugin MUST be a local `npm login` + `npm publish`; CI
takes over only afterwards.

**Phase 6 — Commit + final answer.** Committed exactly 4 files as `f917c4c` (leaving
unrelated tree changes untouched), then answered the final question: yes, the two
plugins can publish at the current `0.4.5` — simpler than the `0.0.1` seed because it
skips the bump-and-revert dance.

## 4. Prompts that worked

- **Goal prompt** — "create seed versions to be able to release." Clear intent, but
  underspecified on the version-number strategy. A stronger kickoff:
  *"Make flows-plugin and jj-plugin publishable to npm. Respect the sync-versions
  lockstep, wire them into publish.yml, and document the first-publish bootstrap."*
- **"give exact commands I have to execute"** (steering #3) — high-leverage. It flipped
  the output from prose to a copy-pasteable phased command block (auth → bump → dry-run
  → publish → verify → revert). Ask for exact commands early when the end goal is an
  operator runbook.
- **"Is it possible to release the 2 new package with current (0.4.5) version?"**
  (steering #5) — a good closing check that surfaced the simplest path (publish straight
  from lockstep, no bump/revert).

## 7. Pitfalls & dead ends

- **Lockstep trap.** Setting a new package to `0.0.1` while the repo is at `0.4.5`
  breaks the next release (`sync-versions.js exit(1)`). *If you must seed at `0.0.1`:*
  publish it locally right then, then revert the manifest to the lockstep version
  before committing.
- **OIDC can't bootstrap.** The `publish.yml` uses Trusted Publisher/OIDC only. A path
  of "cut a release, then configure TP after" does **not** work — TP requires the
  package to already exist. *Do:* the first publish locally (`npm login` + classic
  token), then configure TP, then CI handles every subsequent release.
- **Undeclared runtime dep.** `jj-plugin` imported `dashboard-plugin-runtime/context`
  without declaring it — works via workspace hoist locally, would break for a real npm
  consumer. *If publishing a workspace package:* grep `src/` for every
  `@scope/*` import and confirm it's in `dependencies`.
- **Dirty tree.** Unrelated openspec/diagram changes were present. *Do:* `git add` the
  specific task files, never `git add -A`.
