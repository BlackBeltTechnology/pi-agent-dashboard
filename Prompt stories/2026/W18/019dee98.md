# How we did it: Mine a 69-entry FAQ from README + docs with parallel haiku subagents — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened as a single how-to question — `How do build electron windows only zip out?` —
which the AI answered directly from an existing (1-entry) `docs/faq.md`. But the *real* objective
emerged one steering turn later: **turn the project's scattered README + docs knowledge into a
comprehensive, deduplicated `docs/faq.md`, then codify the whole procedure as a reusable skill.**
By the end the FAQ grew from **1 → 69 entries** across two extraction passes, plus a new
`.pi/skills/faq-mine/SKILL.md` capturing the workflow, all committed on `develop`.

## 2. TL;DR playbook

1. **Answer the literal question first** — grep the existing FAQ/README, give the direct answer,
   then notice the bigger doc-mining opportunity.
2. **Inventory with one read-only Explore agent**: "list every FAQ-worthy question in `README.md`
   + `docs/architecture.md`, dedup against existing headings." Get a clean question list back.
3. **Fan out extraction, one subagent per chunk/doc**, each writing to its *own*
   `docs/.faq-draft-<name>.md` — never the same file — to avoid write conflicts.
4. **Pass the caveman-style doc rule verbatim** into every subagent prompt so entries land in
   house style with no post-editing.
5. **Merge deterministically**: `cat docs/.faq-draft-*.md >> docs/faq.md && rm docs/.faq-draft-*.md`,
   then `grep -c '^## '` to confirm the new count.
6. **Second pass on the remaining evergreen docs** with **haiku** subagents (cheap, parallel),
   each also reading the current `faq.md` for dedup; skip historical docs (session-knowledge,
   spec-gap, file-index).
7. **Codify it as a skill** — write `.pi/skills/faq-mine/SKILL.md` with the phases, the
   per-doc-subagent rule, and explicit anti-patterns.
8. **Commit** with a source-by-source breakdown in the message.

## 3. How the collaboration unfolded

**Phase A — Direct answer (Discovery).** The AI grepped `docs/faq.md`, `README.md`, and
`packages/electron/scripts/`, then answered the Windows-zip question straight from the existing
FAQ. Good instinct: it consulted the doc index before speculating.

**Phase B — First mining pass (README + architecture).** On "Create FAQ from readme and
architecture," the AI ran an `Explore` agent to inventory 30 deduped questions, then dispatched
**4 parallel general-purpose subagents** (install/startup, config, dev/build, architecture), each
writing its own `docs/.faq-draft-N.md`. Concatenated → FAQ went 1 → 31. *Why it worked:* isolated
draft files mean zero write contention, and the Explore-first step deduped before any writing.

**Phase C — Second mining pass (the other docs).** The human pushed scope: "Search other docs
referenced in indexes and process them too… one by one. Use subagents with haiku." The AI filtered
to **5 evergreen docs** (electron-session, installation-windows, publishing-plugins, release-process,
service-bootstrap), skipped historical ones, and ran **5 parallel haiku subagents**, each reading
its source doc + the live `faq.md` for dedup. FAQ went 31 → 69. One duplicate ("Doctor utility")
was caught and dropped.

**Phase D — Codify (Design).** "Add a skill that does the same." The AI wrote
`.pi/skills/faq-mine/SKILL.md` — a 5-phase procedure (pre-flight → confirm scope → parallel
extraction → cross-draft dedupe → merge/cleanup) that bakes in the per-doc-subagent rule and the
AGENTS.md docs protocol.

**Phase E — Commit (Verify).** `git status`/`diff` review surfaced two files (`spec-gap-analysis.md`,
a proposal-queue-schema ref) that looked like new files but were an index inconsistency; the AI
`git checkout HEAD --`'d them back and committed only the 4 real files as `9839f93`.

## 4. Prompts that worked

- **Goal prompt** (`How do build electron windows only zip out?`) — a narrow how-to. It worked as a
  kickoff only because the FAQ already had the answer; the *stronger* opener for the real goal would
  be: *"Mine README + docs/architecture into docs/faq.md as deduplicated Q&A entries; use one
  subagent per source doc writing to isolated draft files."*
- **High-leverage follow-up:** `Use subagents with haiku.` — one clause that unlocked cheap parallel
  extraction across many docs. Naming the model tier explicitly is what made the batch affordable.
- **High-leverage follow-up:** `Add skill … which do the same what happens in this chat.` — turns a
  one-off into a reusable asset in a single sentence, right after the workflow proved out.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Answer only the literal question and stop | "Create FAQ from readme and architecture" | State the mining goal up front, not the single lookup |
| Mine only the two docs named | "Search other docs referenced in indexes and process them too" | Say "process ALL evergreen docs under docs/" in the goal prompt |
| Default to general-purpose subagents | "Use subagents with haiku" | Name the model tier (`haiku`) for cheap parallel batches |
| Leave the workflow as a one-off | "Add skill … which does the same" | Ask for the skill in the same turn as the successful run |
| Treat index-inconsistent files as new | (caught at commit review) | Always `git status` + `git diff --stat` and inspect surprising "new" files before committing |

## 6. Skills, tools & memory created — and why they're effective

- **`.pi/skills/faq-mine/SKILL.md`** — captures the exact two-pass mining workflow: pre-flight
  (read existing headings, enumerate README + docs, exclude index/session-knowledge/spec-gap/draft
  files), `ask_user` scope confirmation, **one haiku general-purpose subagent per doc** each writing
  an isolated `docs/.faq-draft-<basename>.md`, cross-draft dedupe, then `cat`→append→`rm` merge.
  *Why effective:* it removes the manual orchestration (which docs, which model, how to avoid write
  conflicts, how to dedup) and makes FAQ regeneration a single command. *Invoke when:* "build /
  regenerate / extend the FAQ", "mine docs into FAQ", "create FAQ from README + docs".
- **Explore agent (inventory pattern)** — a read-only pass that produces a deduped question list
  *before* any writing. *Effective* because dedup is cheap up front and expensive after 5 subagents
  have written overlapping entries.
- **Parallel isolated-draft pattern** — N subagents, N draft files, deterministic `cat` merge.
  Reusable any time you fan out writes to one target file.

## 7. Pitfalls & dead ends

- **Same-file parallel writes** — the whole design hinges on each subagent owning a unique
  `docs/.faq-draft-<name>.md`. If two agents share a target you lose entries. One draft per source.
- **Mining index/historical docs** — `file-index*.md`, `session-knowledge-*`, and
  `spec-gap-analysis.md` are not evergreen FAQ material; the AI correctly excluded them. Filter these
  out or the FAQ fills with stale, one-off content.
- **Phantom "new" files at commit** — `git status` showed `spec-gap-analysis.md` and a
  proposal-queue-schema ref as new, but they were identical to HEAD (an index inconsistency). Fix:
  `git checkout HEAD -- <files>` to restore the index; don't blindly `git add .`.
- **Duplicate questions across passes** — pass-2 subagents must read the live `faq.md`, or you get
  repeats (one "Doctor utility" dup slipped in and had to be dropped).
