# How we did it: strip per-token background pills from code blocks — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator entered **explore mode** — a thinking-only stance where the AI investigates
the codebase and may capture thinking as OpenSpec artifacts, but must never implement.
The first prompt was the boilerplate explore-mode charter ("Enter explore mode. Think
deeply… You must NEVER write code"). The *real* objective only surfaced through the next
two steering turns: **inside a code block, the per-character/per-token background pills
must disappear** — the code-panel box may stay visually distinct (its own `--bg-code`
surface), but individual syntax tokens (`.token.string`, `.token.deleted`,
`.token.inserted`, `.token.selector`, …) must not paint their own little background
rectangles. The deliverable was a complete OpenSpec change proposal
(`strip-token-backgrounds-in-code-blocks`) — proposal, design, delta spec, tasks — plus a
mid-flight discovery that the diff viewer's theme was hardcoded, which got folded into the
same change.

## 2. TL;DR playbook

1. **Open in explore mode** to force thinking-before-coding; the AI will diagram the
   render pipeline instead of editing.
2. Ask the AI to **map the code-block color pipeline** (theme switches → prism style →
   `customStyle` override). It produced an ASCII diagram of the two loosely-paired
   systems (app-theme background vs prism token palette).
3. **Narrow the ask in one sentence**: *keep the panel box distinct, remove only the
   per-token background pills.* This collapsed a big "make code transparent" idea into a
   surgical `stripTokenBackgrounds()` helper on `getSyntaxTheme()`.
4. Have the AI **enumerate every consumer** of the syntax theme (MarkdownContent,
   ReadToolRenderer, WriteToolRenderer, DiffPanel File view, DiffPanel Diff view) so the
   blast radius is explicit — 3 free, 1 one-line swap, 1 out-of-scope.
5. `create proposal` → `openspec new change <name>`, then fill proposal.md / design.md /
   specs/theme-system/spec.md / tasks.md. Run `openspec validate <name>` until clean.
6. Ask for a **paste-ready visual test** (a markdown message with `ts` + `diff` fenced
   blocks) so you can eyeball every touched surface before/after.
7. When you notice a related bug mid-explore (**diff view doesn't follow light/dark**),
   have the AI trace it (`diffViewTheme="dark"` hardcoded in DiffPanel.tsx) and **append
   it as new tasks** rather than mutating already-shipped `[x]` tasks.
8. `commit` only the artifact files you touched; leave sibling-change working-tree noise
   alone.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore stance).** The AI ran `rg` sweeps for
`highlight|prism|syntax|theme` across `packages/client/src`, read `themes.ts`,
`syntax-theme.ts`, `MarkdownContent.tsx`, and drew the color pipeline as ASCII: the theme
picks two prism styles (`oneDark`/`oneLight`), then render forces
`customStyle={{ background: 'var(--bg-code)' }}`. *Why it worked:* explore mode kept the
AI diagramming the mental model instead of jumping to an edit, so the operator could
correct the target before any code existed.

**Phase 2 — Narrowing the target (the pivotal steer).** The operator's first two
follow-ups were rough English but decisive: *keep the box, kill the character
backgrounds.* The AI redrew BEFORE/AFTER diagrams and reduced the change to a single
helper that clones the prism style and deletes `background`/`backgroundColor` from any
`.token.*` selector. *Decision point:* one sentence of scope narrowing turned a
surface-level rewrite into a ~15-line pure function.

**Phase 3 — Blast-radius map.** The AI tabulated all five consumers and classified them:
three call `getSyntaxTheme()` (auto-fixed), DiffPanel's File view needs a one-line
`oneDark → getSyntaxTheme()` swap, and DiffPanel's Diff view is highlighted by
`@git-diff-view/lowlight` + bundled CSS (flagged, out of scope). *Why effective:* the map
made "what does this change actually touch" auditable before writing the spec.

**Phase 4 — Author the proposal.** `openspec new change` (after two wrong CLI guesses),
then wrote proposal/design/spec/tasks and looped `openspec validate` to green.

**Phase 5 — Visual test + mid-flight bug.** The operator asked for a paste-ready test
message and a `cat`-style `.diff` sample to exercise every rendering path. Eyeballing the
diff surface exposed a *new* bug: switching light/dark didn't re-theme the diff view. The
AI traced it to a hardcoded `diffViewTheme="dark"` in `DiffPanel.tsx:209` and confirmed the
library's effect deps include the prop (so binding it makes it reactive).

**Phase 6 — Fold-in & commit.** Because tasks 1–5 had already shipped, the AI **appended**
tasks 6–9 (bind `diffViewTheme`, render test, visual smoke, AGENTS.md note) and narrowed
the proposal's out-of-scope note (diffViewTheme IS in scope; lowlight token CSS is NOT),
re-validated, and committed only the three artifact files as
`e4a19e0 docs(openspec): extend strip-token-backgrounds-in-code-blocks with diffViewTheme
binding`, deliberately leaving unrelated sibling-change work unstaged.

## 4. Prompts that worked

- **Goal prompt (explore-mode charter).** Effective *as a stance* — it forced the AI to
  investigate and diagram rather than edit, which is exactly right when the target is still
  fuzzy. A stronger kickoff would have front-loaded the actual objective:
  *"Explore mode. Investigate how code-block token backgrounds are themed; I want to remove
  the per-token background pills while keeping the code-panel box distinct. Map every
  consumer, then draft an OpenSpec proposal."*
- **"The box color be distinct… inside the code block the characters background do not be
  distinct"** — despite rough phrasing, this was the highest-leverage turn: it isolated
  *token pill* from *panel background* and shrank the whole change.
- **"1. yes / 2. diff tools too. / 3. ok"** — a compact multi-answer that unlocked scope
  (include the diff renderers) in three tokens.
- **"create proposal"** — clean handoff from thinking to artifact capture (still legal in
  explore mode).
- **"show a diff file to be able to test visually"** / **"Show a cat output of a diff
  file"** — demanding a concrete, paste-ready artifact instead of prose is what surfaced the
  diff-theme bug.
- **"When I switch theme mode… the diff view does not switch theme"** — a precise bug report
  that the AI could trace to a single hardcoded prop.

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created this session. The reusable asset is the **OpenSpec
change artifact set** itself (`strip-token-backgrounds-in-code-blocks/`), which captures
the token-stripping design, the diff-theme binding decision, and the delta spec so the

If this pattern recurs, the skill worth creating is **"map syntax-theme consumers before
touching `getSyntaxTheme()`"** — a checklist that enumerates the five render paths and
their fix classes (auto via helper / one-line swap / out-of-scope lowlight CSS), so the
blast radius is known before any edit.

## 7. Pitfalls & dead ends

- **`openspec change new` is wrong** — the CLI is `openspec new change <name>`. Two failed
  invocations before self-correction. Check `openspec new change --help` first.
- **`/api/restart` over `localhost:8000` failed repeatedly** (curl to the local dashboard
  returned nothing usable). The working path was the skill helper
  `.pi/skills/pi-dashboard/scripts/dashboard-api.sh` and/or `pi-dashboard restart`; a bare
  `curl` to the restart endpoint is unreliable here.
- **Don't mutate shipped `[x]` tasks.** When the diff-theme bug appeared after tasks 1–5
  had landed, appending tasks 6–9 kept the change history honest.
- **Dirty working tree with sibling changes** — stage only the files your change touched
  (`git add <the 3 artifact files>`), don't `git add -A`.
- **The lowlight diff CSS is out of scope** — DiffPanel's Diff view tokens come from
  `@git-diff-view/lowlight` + `diff-view.css`, not react-syntax-highlighter; the
  `stripTokenBackgrounds()` helper does not reach them. Only the `diffViewTheme` prop
  binding is in scope.
