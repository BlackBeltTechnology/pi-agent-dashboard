# How we did it: Ship a build, audit a refactor's regression risk, and keep AGENTS.md in sync — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened with a two-word instruction — `"build and redeploy"` — but the *real*
objective only surfaced across the follow-ups: after redeploying, the operator wanted a
**risk audit of the last 7 commits** (specifically whether the `ask_user` schema refactor
could regress), then wanted the **spec (`AGENTS.md`) updated to reflect those 7 commits**,
and finally **committed and pushed**. So the true goal was: *land a deploy, then close the
loop between recent code changes and the project's living documentation — with a regression
check in the middle.*

## 2. TL;DR playbook

1. **Deploy:** `npm run build && curl -s -X POST http://localhost:8000/api/restart && npm run reload`.
2. **Enumerate the change surface:** `git log -7 --oneline`, then `git show <sha> --stat` per commit.
3. **Zoom into the risky one:** `git show <sha> -- <changed-file>` to read the actual diff, not the summary.
4. **Prove the baseline is green** before judging risk: run the targeted test file *and* the full suite (`npm test 2>&1 | tee /tmp/pi-test.log`).
5. **Write the regression analysis** as concrete, severity-tagged risks (what the old schema enforced that the new one moved to runtime).
6. **Diff docs vs. reality:** `grep -n '<symbol>' AGENTS.md` to find the rows the commits should touch.
7. **Edit `AGENTS.md`** per-commit — update the affected rows in place, skip no-op version bumps.
8. **Commit with a per-commit changelog body**, then `git push`.

## 3. How the collaboration unfolded

**Phase 1 — Deploy (1 turn).** The AI chained build → `/api/restart` → `npm run reload` in one
command, confirmed `{"ok":true}`, and noted no pi sessions were connected to reload. *Why it
worked:* it used the project's canonical restart source of truth (`/api/restart`) rather than
manually killing/restarting the server.

**Phase 2 — Regression audit (the heavy phase).** Given "check the last 7 commits… any regression
of ask_user refactor?", the AI walked `git log -7`, ran `git show --stat` per commit to isolate the
`a53933f` `ask_user` refactor, then read the *actual diff* of `ask-user-tool.ts`. Crucially it
**established a green baseline first** — ran the targeted `ask-user-tool.test.ts` and the full 3638-test
suite — before making a risk claim. It then articulated the real regression surface: the schema moved
from a discriminated `Type.Union` of 5 per-method arms to a **flat `Type.Object`** (root `type:"object"`
for OpenAI function-calling compat), so schema-level guarantees (`select.options minItems:2`,
`multiselect minItems:1`, `batch.questions minItems:1`, required `title`) are now enforced *only at
runtime*. *Why it worked:* it separated "tests pass" from "the invariant weakened" — a passing suite
doesn't prove the constraint surface is unchanged.

**Phase 3 — Doc sync.** For "update spec with last 7 commits", the AI re-walked the log with
`--stat --format`, grep'd `AGENTS.md` for the symbols each commit touched
(`ask-user-tool`, `BUNDLED_EXTENSION_IDS`, `publish.yml`, `MarkdownContent`), and edited only the rows
that changed — explicitly skipping the version-bump commits as no-ops. *Decision point:* it judged each
commit as "spec change vs. no spec change" instead of blindly appending 7 entries.

**Phase 4 — Ship.** `git status`/`diff --stat`, then a single `git add AGENTS.md && git commit` with a
structured per-commit body, then push `b9c6a76` to `develop`.

## 4. Prompts that worked

- **The goal prompt — `"build and redeploy"`** — terse but unambiguous because the project has one
  canonical deploy path. *Stronger version for a cold start:* "build the client, restart via
  `/api/restart`, and reload connected sessions."
- **High-leverage follow-up — `"Check the last 7 commits… Is there any possible regression of ask_user
  refactor? What risks and what things can diverge?"`** — this unlocked a real audit because it named
  *the artifact* (last 7 commits), *the suspect* (ask_user refactor), and *the deliverable shape* (risks
  + divergence). Naming all three is what turned it from a vague "is it ok?" into a severity-tagged report.
- **`"Update spec with last 7 commits"`** — effective because in this repo "spec" maps to `AGENTS.md`
  rows; the AI knew to diff docs against commits rather than free-write.

## 5. Steering & corrections (what to watch for)

| Stop at "build and redeploy" as if it were the whole task | Following up with the real intent (audit, then doc-sync, then push) | Stating the full chain up front: "deploy, then audit the last N commits for regressions, then sync AGENTS.md, then push" |

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session. The workflow is nonetheless repeatable and worth
capturing. **Recommended skill to create:** a `commit-range-to-agents-sync` procedure that, given a
commit range, walks `git log --stat`, classifies each commit as spec-change vs no-op, greps `AGENTS.md`
for the touched symbols, and updates the matching rows — encoding the "skip version bumps, edit rows in
place" judgment this session applied manually. It would remove the repeated `git show`/`grep AGENTS.md`
dance every time recent commits need reflecting in the living spec.

## 7. Pitfalls & dead ends

No commands failed (16 run, 0 errors). Two process notes worth keeping:

- **Don't equate a green suite with "no regression."** The full 3638-test run passed, yet the real
  finding was a *weakened invariant* (schema-level `minItems`/required constraints demoted to runtime).
  Read the diff and reason about what the schema stopped enforcing, separately from the test result.
- **Use an isolated `HOME` for extension tests when needed** — `HOME=$(mktemp -d) npm test -w
  packages/extension` was used to run the ask-user tests without polluting the real home; handy when a
  test touches `~/.pi`.
