# How we did it: Hardening the Windows Electron installer bootstrap — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user was running the unzipped `PI-Dashboard-win32-x64` build on a real Windows
box and the setup wizard died immediately:

> *"Windows has problem `C:\test\PI-Dashboard-win32-x64>` Error occurred in handler
> for `'wizard:install-standalone'`: Error: **spawn npm ENOENT** … The system cannot
> find the path specified."*

The stated ask was "fix this one crash." The **real** objective — which only emerged
after ~20 rounds of screenshots and doctor dumps — was much bigger: **make the
Windows ZIP/portable bootstrap survive first-run on a machine with no dev tooling on
PATH.** Every layer of the cold-start (bundled Node → npm → tsx → managed pi/openspec
install → recommended-extension `git clone`) had a Windows-specific failure hiding
behind the next one. The session became a *diagnose-fix-rebuild-retest* loop that
peeled ~12 distinct bugs, ending with a comprehensive troubleshooting doc so the next
person can analyze further without re-deriving the whole chain.

## 2. TL;DR playbook

1. **Reproduce with the doctor, not guesses.** Every Windows round-trip is 10-15 min,
   so treat the `PI Dashboard Doctor` dump + the exact IPC-handler stack trace as the
   ground truth. Ask the user to paste the doctor block after each rebuild.
2. **Find the spawn leak.** `grep -rn` the codebase for raw `spawn("npm"` / `cpSpawn`
   callsites that bypass the existing `buildSafeArgv()` helper (`packages/shared/src/platform/exec.ts`).
   On Windows a bare `npm` is `ENOENT` — it must route through `cmd.exe /d /s /c`.
3. **Fix the Node version floor.** Bundle **≥ v22.18.0** (or v24.3.0) — v22.0–22.17 and
   v24.1–24.2 hit the Fastify crash [nodejs/node#58515]. Add a runtime picker that
   prefers system Node only when it is version-safe, else the bundled one.
4. **Dereference workspace symlinks before zipping.** Windows unzip does not preserve
   the relative symlinks that `npm` creates for `@blackbelt-technology/*` workspaces;
   patch `bundle-server.mjs` to copy real content.
5. **Inject a sane PATH into every spawned child.** Write `ensureWindowsSystemPath()`
   that prepends `System32`, `%APPDATA%\npm`, `Program Files\Git\cmd`, and pins
   `ComSpec` — call it at startup **and** inside `buildInstallEnv()` (belt + braces).
6. **Kill the git-clone hang.** Set `GIT_TERMINAL_PROMPT=0`, `GCM_INTERACTIVE=Never`,
   `GIT_ASKPASS=echo` so Git Credential Manager fails fast instead of waiting on an
   invisible prompt.
7. **Build ZIP-only + local.** `ZIP_ONLY=1 bash packages/electron/scripts/build-installer.sh
   --windows --arch x64` in Docker; skip the portable.exe to save ~5 min per iteration.
8. **Verify, then document.** Run the targeted vitest for each fix, then write the
   `docs/troubleshooting-windows-installer.md` that maps every symptom → cause → fix →
   residual risk.

## 3. How the collaboration unfolded

**Phase A — Discovery (the first spawn ENOENT).** The AI grepped for `install-standalone`
callsites, compared `v0.4.6` vs HEAD of `dependency-installer.ts`, and located the leak:
two `npm install` callsites (`dependency-installer.ts`, `bootstrap-install.ts`) called
`spawn()` directly instead of through `buildSafeArgv()`. It wrapped them, wrote a
regression test asserting `cmd === "cmd.exe"` on win32, ran the full suite (4154 pass),
bumped `0.4.6 → 0.4.7`, and **stopped before pushing** — offering a numbered
commit/push/discard menu. *Decision point:* the human chose local-only, no push.

**Phase B — The Node version wall.** User: *"Maybe node version not ok?"* The AI traced
`assertNodeVersionSupported()` and identified the bundled v22.12.0 as inside the broken
#58515 range. It bumped the bundle to v22.18.0, then added `pick-node.ts` (system Node
if safe, else bundled) with a 34-case test matrix, and bumped every pin to v24.3.0.

**Phase C — The bundling bugs.** Each Windows retest surfaced a new packaging gap:
`@blackbelt-technology/pi-dashboard-shared` missing from the bundled `node_modules`
(relative symlink not preserved by Windows unzip → dereference in `bundle-server.mjs`);
`dashboard-plugin-runtime` absent from the synthetic `resources/server/package.json`.

**Phase D — The PATH cascade (the long tail).** Repeated `spawn cmd.exe ENOENT` and
`'git' is not recognized`. The AI diagnosed that Electron's spawned children inherit a
PATH stripped of system dirs. It wrote `ensureWindowsSystemPath()` and — crucially,
after the user proved via `app.asar` byte-size that an *older build was still running* —
moved the call from just `main.ts` startup into `buildInstallEnv()` itself so no spawn
path could bypass it.

**Phase E — The invisible git hang.** User pasted `Get-Process git` showing two git
PIDs at 0% CPU with no clone dir. The AI correctly named it: **Git Credential Manager**
popping an interactive prompt with no window. Fix: `GIT_TERMINAL_PROMPT=0` +
`GCM_INTERACTIVE=Never` + `GIT_ASKPASS=echo`, all guarded with `?? "…"` to preserve
explicit user overrides.

**Phase F — UX + housekeeping + doc.** Fixed the offline-install progress events (step
names `offline-cache` didn't match the UI's `pi-coding-agent` listeners), added a busy
spinner to the "Install selected" button, pruned Docker (43 GB reclaimed when the build
image space ran low), and finally wrote the 531-line troubleshooting guide.

## 4. Prompts that worked

- **The goal prompt** pasted the *exact* IPC handler name + stack trace + console line.
  That single verbatim block let the AI grep straight to the leaking callsite. **Always
  paste the full error, not a paraphrase.**
- **"build win32 x86_64 locally. Only zip"** — a high-leverage constraint that cut the
  iteration loop in half by skipping the portable.exe. Give build constraints early.
- **"What is the version recommended for pi-dashboard?"** forced the AI to state the
  supported Node matrix explicitly (engines floor + the #58515 exclusions) rather than
  bury it in code.
- **"Is it possible to test node version … and if not the required one use the internal
  node"** — a design nudge that spawned the whole `pick-node.ts` helper. A good "can we
  make this self-healing?" prompt.
- **Pasting `Get-Process` / `app.asar` byte sizes** was the highest-signal steering of
  the session: it *proved* the running build was stale and *proved* git was hung with
  no CPU — ending two guessing spirals instantly. **When a fix "doesn't work," measure
  the running artifact before theorizing.**

Rewrite of a weak prompt: instead of *"Another problem: [image]"*, a future operator
should paste *"After rebuild N, the doctor still shows X and the handler Y throws Z —
here's the block"* so the AI doesn't have to ask which build is running.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Want to cut/push the release immediately after the fix | Choosing "local-only, no push" from the menu | Always stop at commit and present a push/discard menu for release-affecting changes |
| Build the full installer (ZIP + portable.exe) | "Only zip" / "Do not make installers" (×2) | Default local Windows builds to `ZIP_ONLY=1`; only build portable on explicit request |
| Assume the latest fix was running | User pasted `app.asar` byte size proving it was stale | Print the built `app.asar` size in the build summary so the user can diff it |
| Trust the doctor's server-launch smoke test failure as a real bug | Recognize it was the doctor's own `-e` string-escape bug (`\t`,`\P`) | Never eval Windows paths inside `tsx -e`; invoke tsx with argv file paths |
| Fix PATH only at `main.ts` startup | Prove spawned children still had a stripped PATH | Inject `ensureWindowsSystemPath` inside the env builder, not just at boot |

Scope expansions the user imposed: bump the Node pin *everywhere* (scripts + CI, not
just the local build); make the git fix permanent in-code, not just a manual PowerShell
workaround; and finally, **document every symptom** ("Don't miss any symptom … what
potentially risks there").

## 6. Skills, tools & memory created — and why they're effective

No pi *skill* or *memory* was saved this session, but three reusable code assets were
created that function as durable guardrails:

- **`pick-node.ts`** — a pure system-vs-bundled Node selector with a locked 34-case test
  matrix. Removes the manual "which Node runs the server" guesswork and encodes the
  #58515 broken ranges so a future Node bump can't silently reintroduce the Fastify
  crash. Invoke/extend it whenever the supported Node range changes.
- **`ensure-windows-path.ts`** — idempotent PATH + ComSpec hardening for every spawned
  child. Solves the entire class of `spawn X ENOENT` on Windows once. Call it in any new
  env-builder that spawns a child process.
- **`docs/troubleshooting-windows-installer.md`** — the 531-line symptom→cause→fix→risk
  map plus the full bootstrap tool-resolution chains. This is the artifact that makes
  the *next* Windows regression a lookup instead of a 9-hour re-derivation.

**Recommended skill to create:** a `windows-installer-bootstrap` project skill capturing
the diagnose→fix→ZIP_ONLY-rebuild→doctor-verify loop and the "measure the running
artifact before theorizing" rule — this session's shape is clearly repeatable.

## 7. Pitfalls & dead ends

- **`curl`/`python urlretrieve` of the GitHub release ZIP failed** (5 attempts) — don't
  try to fetch the prior release binary to diff; build locally instead.
- **A stale unzip kept masking fixes.** If a fix "doesn't work," get the running
  `app.asar` byte size and compare to the freshly built one *before* changing code.
- **Windows unzip silently drops workspace symlinks** → dereference in `bundle-server.mjs`.
- **`ENOTEMPTY: rmdir '.offline-cache/_logs'`** — Windows AV/log-handle race on cleanup;
  retry the wipe up to 5× with ~150 ms backoff, then fall through tolerantly.
- **Git Credential Manager hangs on public HTTPS clones** with 0% CPU and no clone dir —
  it's the invisible auth prompt, not a slow network. Set `GIT_TERMINAL_PROMPT=0` +
  `GCM_INTERACTIVE=Never`.
- **`tsx -e "import 'C:\test\...'"`** — the `\t`/`\P` become JS escapes → MODULE_NOT_FOUND.
  Never eval Windows paths; pass them as argv.
- **The root vitest config excludes `packages/electron`** — its "orphan failures" are
  pre-existing; run the electron test file standalone to confirm your change.
- **Docker ran out of space mid-build** — `docker system prune -a --volumes` reclaimed
  43 GB, but it also nukes *named* project volumes; warn the user before pruning volumes.
