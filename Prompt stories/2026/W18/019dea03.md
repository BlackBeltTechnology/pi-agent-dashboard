# How we did it: Fix the darwin DMG arch collision — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was

## 1. Goal (the ask)

The user opened with a screenshot of a GitHub release and a plain question:

> "In the release one dashboard dmg is presented. Is it contain both x86 and arm64?"

The *real* objective — which emerged as the AI diagnosed and the user steered — was:
**the release ships only one un-suffixed `PI Dashboard.dmg`, one macOS arch is silently
lost, and we need a properly-scoped OpenSpec change that fixes the root cause, protects
it with a regression test, and lands cleanly without an accidental version bump.** This
started as a diagnostic question and became a full planning → apply → verify → archive →
commit cycle for the `fix-darwin-dmg-arch-collision` change.

## 2. TL;DR playbook

1. **Ask the diagnostic question with evidence** — paste the release screenshot and ask
   "does this DMG contain both arches?". Let the AI read `forge.config.ts` +
   `publish.yml` and name the root cause before proposing anything.
2. **Confirm the two-bug root cause**: static DMG `name` (no arch token) + `softprops/
   action-gh-release@v2` overwriting by basename → last matrix leg wins.
3. **`create proposal`** — scope the fix to `forge.config.ts` + a regression test; keep
   `publish.yml` untouched.
4. **Ask "does the site/README need updating?"** — the AI audits docs and finds they were
   *already* prepared for dual-DMG; only a version-claim needs reconciling.
5. **Fast-forward the artifacts** (`/opsx:ff`) — proposal → design → specs → tasks, all
   strictly valid. Park the version-bump decision in `design.md`.
6. **Steer versioning OUT of the change** — revert the test-tag bump back to `0.4.5`
   across all workspaces + lockfile; reword the README migration note to be
   *version-agnostic*. Versioning is the release-cut skill's job.
7. **`/opsx:apply`** TDD: write `forge-config-dmg-naming.test.ts` → confirm RED → make
   `name` = `` `PI-Dashboard-darwin-${process.arch}-${pkgVersion}` `` → confirm GREEN.
8. **`/opsx:verify`** — catch the one mis-marked checkbox (5.2 archive), fix it.
9. **`/opsx:archive`** then **commit as two logical commits** (version revert, then the fix).
10. **Run the full test suite** — root suite green, electron suite +6 (your tests), 0 new failures.

## 3. How the collaboration unfolded

**Phase 1 — Diagnosis (evidence-first).** The AI read `packages/electron/forge.config.ts`
and `.github/workflows/publish.yml` and found *two compounding bugs*: the DMG maker `name`
was the static string `"PI Dashboard"` (no `arm64`/`x64` token), and the release upload
globs `electron-*/**/*` into `softprops/action-gh-release@v2`, which names each asset by
its **basename** — so both matrix legs produced `PI Dashboard.dmg` and the last one
uploaded overwrote the first. *Why it worked:* the AI refused to speculate and quoted exact
file:line ranges, so the fix scope was unambiguous before any artifact existed.

**Phase 2 — Proposal + doc audit.** `create proposal` produced a scoped proposal. The
user's "Maybe the site and readme have to be updated" triggered a docs sweep that
discovered the README, `site/src/lib/github-release.ts`, `DownloadSection.astro`, and
`InstallTabs.tsx` were **already** built for the dual-DMG world — only the "v0.5.x release
line" claim in README needed reconciling. *Decision point:* the version question was
deliberately **parked in design.md** rather than answered inline.

**Phase 3 — Fast-forward artifacts.** `/opsx:ff` generated design + specs + tasks. Design
captured D1–D4 (compose the name in JS since the DMG maker has no version placeholder;
scope the spec delta to `Requirement: DMG configuration` to avoid colliding with the
pending `add-darwin-x64-build` delta; keep the legacy `"DMG (universal)"` classifier as a
safety net).

**Phase 4 — Version un-bump (the key steer).** The user said the repo should NOT ship in
this form and asked to revert `0.4.6` → then "back to 0.4.5". The AI `git checkout --`'d
all 10 workspace `package.json`s + lockfile back to `0.4.5`, regenerated the lockfile, and
rewrote the README migration note to be version-agnostic. It also rewrote design.md D3 from
"ship as 0.4.7" to "no version bump in this change".

**Phase 5 — Apply (TDD).** `/opsx:apply` ran red→green: 6-test regression file, confirmed
4/6 failed against the static name, implemented the arch-tagged name, confirmed 10/10
(new + sibling) green. Docs tasks (README/AGENTS/CHANGELOG) done; the local-build smoke
tasks deferred with a documented rationale.

**Phase 6 — Verify → archive → commit → full test.** `/opsx:verify` caught a mis-marked
`- [x] 5.2` archive checkbox and corrected it to `- [ ]`. Archive synced the spec delta
into the main spec. The work landed as **two logical commits** (version revert, then the
fix). Full test run: root suite 4153 passed / 0 failed; electron suite +6 new tests green,
11 pre-existing unrelated failures unchanged.

## 4. Prompts that worked

- **Goal prompt** — *"In the release one dashboard dmg is presented. Is it contain both x86
  and arm64?"* + screenshot. Effective because it attached **evidence** and asked a
  falsifiable yes/no; the AI had to inspect the actual build config, not guess.
- **"create proposal"** — a two-word high-leverage unlock once the root cause was agreed;
  it moved straight into the OpenSpec workflow.
- **"Maybe the site and readme have to be updated"** — a scope-widening nudge that produced
  a docs audit and prevented a half-fix. Stronger phrasing: *"Audit README + site for any
  DMG/arch claims and tell me which already match the fix and which need reconciling."*
- **"I would like to revert 0.4.6 … it will not release this form"** then **"back to
  0.4.5"** — the decisive steer that kept versioning out of the change. Stronger up-front
  version: *"This change must NOT bump any package.json version — versioning is release-cut's
  job. Keep the working tree at the last published version (0.4.5) and word docs
  version-agnostically."*

## 6. Skills, tools & memory created — and why they're effective

No new pi *skill* or memory was created this session — the work rode the existing OpenSpec
workflow skills (`openspec-new-change` → `-ff` → `-apply` → `-verify` → `-archive`). The
**reusable asset produced is a regression test**: `packages/electron/src/__tests__/
forge-config-dmg-naming.test.ts` (6 tests). *Why it's effective:* it locks the arch-tagged
DMG basename contract so any future refactor that flips back to a static `"PI Dashboard"`
name fails CI **before** a release tag ships a broken single-arch DMG — turning a
silent-at-release-time bug into a caught-at-PR-time one.

If this pattern recurs (release-asset basename collisions from a build matrix), it would be
worth a short skill: *"scope a build-config fix as an OpenSpec change with a naming-contract
regression test, keep versioning out."*

## 7. Pitfalls & dead ends

- **Inline commit message interpolation** — the first `git commit -m "…${…}…\`…\`"` was
  partially expanded by bash (parameter expansion inside double quotes + backticks),
  producing an empty message and aborting mid-commit, leaving the index in an odd state.
  *Fix:* write the message to a file and `git commit -F /tmp/commit-msg.txt`.
- **Deleted a sibling test mid-implementation** — a stash/rm step removed
  `forge-config-naming.test.ts`; it had to be restored. *Fix:* prefer `git stash` over `rm`
  when temporarily isolating files, and restore explicitly.
- **`npm install --package-lock-only` exit code 1** — looked like a failure but was an
  `npm audit` advisory; the lockfile regenerated correctly. *Fix:* verify the actual
  artifact (grep the lockfile for the old version) rather than trusting the exit code.
- **Electron tests excluded from the root suite** — `packages/electron/` is excluded by
  design, so `npm test` at root never runs the new DMG tests. *Fix:* run the electron
  suite separately (`cd packages/electron && npm test`) and compare pass counts before/
  after against the prior HEAD to prove 0 new failures.
- **HOME pollution in electron tests** — several vitest runs needed
  `HOME=$(mktemp -d)` to avoid picking up the real `~/.pi` state.
