# How we did it: Unblock, extend, and land a stalled fork PR — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator wanted a stuck pull request merged:

> "Fix https://github.com/BlackBeltTechnology/pi-agent-dashboard/pull/16 to be able to
> merge. If required checkout on temp directory, fix there and push back"

PR #16 was a contribution from an external fork (`ChicK00o/pi-agent-dashboard`) adding a
configurable `askUserPromptTimeoutSeconds`. It could not merge: the branch had drifted
behind `develop`, CI was red, and the feature was incomplete. The *real* objective — once
the steering turns landed — was: **get CI green, close the gaps the review would raise
(surface the setting in the UI, document it in specs), and push everything back to the
contributor's fork so a maintainer can merge.** Because it's a fork PR, all fixes had to be
made in a throwaway checkout and pushed to the contributor's branch, not committed locally.

## 2. TL;DR playbook

1. **Read the PR state first, not the code.** `gh pr view 16 --json mergeable,mergeStateStatus,statusCheckRollup,headRepository,headRepositoryOwner,maintainerCanModify` — learn *why* it's blocked and whether you can even push.
2. **Pull the failing CI log** for the exact error: `gh run view <id> --log-failed | head -200`.
3. **Clone to a temp dir and check out the PR branch:** `cd /tmp && gh repo clone … pr16-fix && cd pr16-fix && gh pr checkout 16`.
4. **Merge `origin/develop` into the branch** to kill drift; discard any auto-regenerated `package-lock.json` and re-run `npm install` cleanly.
5. **Reproduce CI locally** with `npm run lint` + `npm test` until both are green; fix the root causes (here: a stale workspace version pin).
6. **Add the review-obvious gaps yourself** — surface the config field in `SettingsPanel.tsx` and update the openspec `spec.md` files. Ask the operator before expanding scope.
7. **Regenerate `package-lock.json` cross-platform** with `npm install --package-lock-only` (NOT a plain `npm install` on macOS — that drops the Linux native bindings).
8. **Push to the contributor's fork** (`git remote add fork git@…:ChicK00o/…` → `git push fork HEAD:<branch>`), then poll `gh pr view` until `MERGEABLE`.
9. **If the PR merges out from under you**, the fork push is rejected (`maintainerCanModify` → false). Open a small follow-up PR against `develop` for the leftover changes instead.

## 3. How the collaboration unfolded

**Phase A — Diagnose (why is it red?).** The AI started with `gh pr view` and `gh run view --log-failed` rather than reading source. It found three independent root causes: (1) the branch was behind `develop` and missing new fields across `types.ts`, `session-meta.ts`, `server.ts`, `browser-gateway.ts`, `event-wiring.ts`; (2) a recent test file (`system-routes-restart.test.ts`) had type errors already fixed in develop's `ec794d4`; (3) `packages/jj-plugin/package.json` was pinned to `0.4.4` while the root required `^0.4.5` — which was *also* breaking develop's own CI. *Why it worked:* reading PR/CI metadata before code turned a vague "won't merge" into a precise, three-item fix list.

**Phase B — Rebase & repair in a temp clone.** Cloned to `/tmp/pr16-fix`, merged `origin/develop` cleanly (no conflicts), bumped `jj-plugin` to `0.4.5`, regenerated the lockfile, and verified with `npm run lint` (clean) and `npm test` (4140 passed, 9 skipped). Committed and pushed to the fork. *Decision point:* the AI kept all work in the disposable temp dir per the operator's instruction, never touching the local working copy.

**Phase C — Close the feature gap (operator-steered).** The operator asked "Is it presented on settings page?" The AI checked and reported honestly: the field was wired through config/bridge/prompt-bus but **not** surfaced in `SettingsPanel.tsx` or whitelisted in `config-api.ts` — users could only hand-edit `~/.pi/dashboard/config.json`. On the operator's "yes", it added a `NumberField` under Settings → General → Sessions (with a `-1`/`0` = infinite hint), confirmed no server change was needed (the partial-write path deep-merges unknown scalars), and re-ran the settings/config test files green.

**Phase D — The lockfile cross-platform trap.** The operator pasted a fresh CI failure: `Cannot find native binding … @tailwindcss/oxide`. Root cause: regenerating `package-lock.json` on macOS had recorded only the `oxide-darwin-*` binding and dropped the `oxide-linux-*` entries CI needs. Fix: `npm install --package-lock-only` (resolves the full dep tree without platform filtering), restoring 15 linux + 6 darwin oxide variants plus the rollup/esbuild/swc fan-out. Verified with a real `npm run build`.

**Phase E — Specs, and a race with the maintainer.** On "update specs" the AI edited three openspec `spec.md` files (`shared-config`, `ask-user-tool`, `settings-panel`), confirming the pre-existing `## Purpose` validation failures were repo-wide (168/211 specs) and not introduced by its edits. While it worked, a maintainer **merged PR #16**, flipping `maintainerCanModify` to false and rejecting the spec push. The AI recognized this immediately and opened **PR #17** against `develop` carrying just the spec updates.

## 4. Prompts that worked

- **The goal prompt** (effective): it named the exact PR URL *and* pre-authorized the mechanism — "checkout on temp directory, fix there and push back." That single clause removed a round-trip of "how should I do this?" and set the fork-safe workflow up front. A future operator should always state the push target explicitly for fork PRs.
- **"Is it presented on settings page?"** — a high-leverage audit question. It forced the AI to distinguish "config plumbing exists" from "user-facing feature complete," surfacing a real gap a reviewer would have bounced.
- **"yes"** — a one-word unlock that authorized the scope expansion (add the UI field) after the AI had already scoped and proposed it. The AI proposing the concrete two-file change *before* asking is what made "yes" sufficient.
- **Pasting the raw CI error block** — the fastest way to hand the AI a fresh failure; it went straight to the known npm optional-deps signature without a guessing loop.
- **"update specs"** — terse but adequate because the feature and its touch-points were already established in-context.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session. The workflow is clearly repeatable, so the
asset that **should** exist is a project skill — call it `unblock-fork-pr`:

- **What it would capture:** the diagnose-in-temp-clone → merge-develop → reproduce-CI-locally →
  fill-review-gaps → cross-platform-lockfile-regen → push-to-fork → fallback-follow-up-PR loop.
- **Why it's effective:** it removes the two expensive lessons this session paid for — (1) the
  macOS lockfile trap that costs a full CI round-trip, and (2) the "config plumbed ≠ feature
  done" completeness gap — and encodes the fork-push mechanics + the "merged out from under
  you" escape hatch.
- **When to invoke:** any external fork PR that's red or incomplete and needs landing.

Two facts worth a project memory: **regenerate lockfiles with `npm install --package-lock-only`
(never a bare macOS `npm install`)**, and **`jj-plugin` version pins must track the root
`^` requirement or they break CI on both the PR and develop.**

## 7. Pitfalls & dead ends

- **macOS lockfile loses Linux native bindings.** A plain `npm install` regen records only
  the host's `@tailwindcss/oxide-<host>` binding; CI on `ubuntu-latest` then can't find the
  Linux one (npm/cli#4828). → Use `npm install --package-lock-only`, then verify with an actual
  `npm run build`.
- **A merge auto-regenerates `package-lock.json`.** After `git merge origin/develop`, discard
  the churned lockfile (`git checkout -- package-lock.json`) and re-install deliberately.
- **`action_required` on CI is not a code failure.** For first-time fork contributors GitHub
  gates the run behind maintainer approval; don't chase it as a bug.
- **`maintainerCanModify` flips to false once a PR merges/closes.** A late push to the fork is
  then rejected — pivot to a fresh follow-up PR against the base branch.
- **Pre-existing spec validation noise.** `openspec validate` failed on `shared-config` /
  `settings-panel` for a missing `## Purpose` header — a repo-wide condition (168/211 specs),
  not your edit. Confirm the failure predates you before "fixing" it.
