# How we did it: Spec'ing external dashboard plugins — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** ("Enter explore mode. Think deeply. Visualize
freely… you must NEVER write code or implement features… You MAY create OpenSpec
artifacts") — a thinking-partner stance, not an implementation task. The concrete
question surfaced one prompt later: *"Is it possible to make a pi-dashboard plugin
which makes a settings screen for that?"* — where "that" was the companion extension
`pi-memory-honcho`. The **real objective**, once the steering clarified it, was to
prove that a *third-party* (non-monorepo) plugin could ship a Settings screen through
the dashboard's plugin runtime, trace the full discovery→install→render handshake,
and then capture the finding as a complete OpenSpec change (`external-dashboard-plugins`)
ready for implementation.

## 2. TL;DR playbook

1. **Start in explore mode** with the "thinking, not implementing" stance — permission
   to read/search/diagram but a hard no on writing code until a proposal exists.
2. **Anchor to a concrete external artifact.** Point the AI at the real target
   (`github.com/acsezen/pi-memory-honcho`) so it grounds the abstraction in a shipping
   extension, not a hypothetical.
3. **Ask "is X possible?"** and let the AI trace the existing runtime seams
   (`settings-section` slot, `packages/demo-plugin/` fixture, `discoverPlugins()`,
   `registerPluginBridge()`, `pi-resource-scanner.ts`).
4. **Feed decisions in terse batches** ("1. Yes / 2. global / 3. do it") to answer the
   AI's branching questions without derailing the thread.
5. **Force the constraint check**: "Check how pi and dashboard do it (dashboard also be
   able to install plugins)" — makes the AI reconcile pi's per-cwd scope vs the
   dashboard's single-process/many-cwd model.
6. **Say "create proposal"** to convert the explored design into `proposal.md`.
7. **Run `/opsx:ff`** (fast-forward) to generate every remaining artifact —
   `design.md`, two delta `specs/*/spec.md`, `tasks.md` — in one shot.
8. **End on `openspec validate <change> --strict`** to confirm the change is
   apply-ready before stopping.

## 3. How the collaboration unfolded

**Phase 1 — Feasibility trace (Discovery).** The AI fetched and grepped
`pi-memory-honcho`, established it is a *vanilla* pi extension (only `registerTool`,
`registerCommand`, `ctx.ui.notify`, `ctx.ui.input` + standard lifecycle hooks), and
concluded the dashboard bridge already proxies every one of those primitives. *Why it
worked:* proving "plug-and-play" from the extension's actual API surface, not from
assumptions, made every later design decision defensible.

**Phase 2 — Find the exact seam.** The AI located the `settings-section` slot and the
`packages/demo-plugin/` blueprint, showing the entire registration is one
`pi-dashboard-plugin` manifest block in `package.json`. *Decision point:* the human
confirmed global scope ("dashboard and honcho run on host machine as directory"),
which collapsed a config-path ambiguity — honcho writes a single global
`~/.honcho/config.json`, so the plugin server entry can read/write it directly.

**Phase 3 — Trace the handshake.** The AI mapped the two-sided wiring with sequence
diagrams: `discoverPlugins()` → `loadServerEntries()` → `registerPluginBridge()` writes
a `dashboardPluginBridges[...]` key into pi's `settings.json`, which pi loads on
session start. *Why it worked:* surfacing that the flow is **dashboard-server-driven,
not extension-driven** is the crux that makes external plugins possible.

**Phase 4 — Reconcile the scope conflict.** Prompted to "check how pi and dashboard do
it," the AI exposed the real tension: pi is clean per-cwd; the dashboard is one process
serving N sessions across N cwds. It classified every slot into global-mounted
(`settings-section`, `management-modal`, `toast`) vs per-session (`tool-renderer`,
`footer-segment`) — the classification that drives the manifest schema.

**Phase 5 — Generate + validate (Artifacts).** "create proposal" then `/opsx:ff`
produced `proposal.md`, `design.md` (7 decisions), two delta specs
(`dashboard-plugin-loader` +7 requirements, `package-install` +2), and `tasks.md`
(10 groups / 50+ checkboxes). The session closed on
`openspec validate external-dashboard-plugins --strict` passing.

## 4. Prompts that worked

- **Goal prompt (explore-mode preamble):** effective because it set an explicit
  *stance* — read/diagram freely, never implement, but OpenSpec artifacts are allowed.
  This kept the AI in design mode for hours without prematurely writing code.
- **"Is it possible to make a pi-dashboard plugin which makes a settings screen for
  that?"** — a sharp yes/no feasibility question aimed at a *named* target. It forced a
  grounded trace instead of a generic essay.
- **"Check how pi and dashboard do it (dashboard also be able to install plugins)"** —
  high-leverage: one line that expanded scope to the install path and surfaced the
  per-cwd-vs-single-process conflict that the whole design hinges on.
- **"create proposal" / the `/opsx:ff` fast-forward** — short unlocks that converted
  ~3h of exploration into the full artifact set in one pass.

*Weak-prompt rewrite:* the terse batches like "1. yes 2. ok 3. accepted" moved fast but
are unreadable later. Stronger: name the decision — e.g. *"Global scope confirmed;
accept the workspace-shadows-global tie-break; proceed to specs."*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Explore the plugin abstraction generically | Naming the concrete target (`pi-memory-honcho`) | State the real external artifact + its repo URL in prompt 1 |

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created this session — it was pure exploration + artifact
generation. The reusable asset is the **OpenSpec change itself**
(`external-dashboard-plugins`): proposal + design (7 decisions) + two delta specs +
`tasks.md`, all `--strict`-validated.

*Skill worth creating:* a **"trace-plugin-handshake"** playbook that, given a candidate
external extension, mechanically walks `discoverPlugins()` → `loadServerEntries()` →
`registerPluginBridge()` → pi `settings.json#dashboardPluginBridges` and classifies each
slot as global vs per-session. This session redid that trace by hand; capturing it would
make the next external-plugin feasibility study minutes instead of hours.

## 7. Pitfalls & dead ends

- **45 commands, 0 failures** — this was a clean run, but it took many narrow greps to
  locate seams (`slot-types.ts`, `plugin-bridge-register*`, `package-manager-wrapper.ts`,
  `pi-resource-scanner.ts`). *If you hit the same:* start from
  `packages/dashboard-plugin-runtime/` and the `packages/demo-plugin/` fixture — they are
  the canonical map of the runtime.
- **Scope is the trap.** The dashboard deliberately violates pi's per-cwd model (one
  process, many cwds). *If you design a global slot* (`settings-section`), it has no
  natural cwd — resolve scope before touching the manifest schema, not after.
- **explore mode ≠ implement mode.** The stance forbids writing code; the exit is an
  explicit "create proposal". Don't try to implement inside explore mode — emit the
  OpenSpec change and switch out.
