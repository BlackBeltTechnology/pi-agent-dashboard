# How we did it: reattach-move-to-front — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a two-word prompt — `build and deploy` — that looks trivial
but was the trigger for a full feature cycle. The *real* objective only surfaced two
turns later: **"Is it possible that the last 2 sessions are not displayed on cards? I
haven't found [them]."** The user had restarted the dashboard and two live pi sessions
had "vanished" from the top of their folder lists. The actual goal became: diagnose
why reattached sessions get buried on server reboot, then design and ship an OpenSpec
change (`reattach-move-to-front`) that lets reattached sessions optionally float back
to the front — configurably, without regressing the deliberate drag-order feature that
was *already* protecting those slots.

## 2. TL;DR playbook

1. **Build + deploy first, then observe.** `npm run build`, `POST /api/restart`, then
   `curl /api/health` and `/api/sessions | jq` to see live state.
2. **Reproduce the "missing sessions" as a data question, not a UI hunt.** Query
   `~/.pi/dashboard/preferences.json` `sessionOrder[<cwd>]` with `jq` to prove the
   sessions exist but sit at a deep index — they render, just buried.
3. **Trace the actual code path before theorizing.** `rg` the `session_register` /
   `onSessionRegistered` / `pendingResumeIntents` chain to confirm which branch
   (front / keep / null-intent reattach) the sessions hit.
4. **Present design options, let the human pick.** Offer 2–3 options (new intent vs.
   startedAt fallback); the recommended one wins with a short "2".
5. **Run the OpenSpec artifact chain** (`openspec new change` → proposal → design →
   specs → tasks), validate `--strict` to 4/4 before writing any code.
6. **Apply TDD task-by-task** (`/opsx:apply`): tests in each task's `.4`/`.5`
   sub-step, minimal implementation to green, announce each `✓ Task N`.
7. **Verify against the spec, then audit the code independently** — the second,
   suspicious pass is where the critical bug was caught.
8. **Sync delta specs, archive, commit, push.**

## 3. How the collaboration unfolded

**Phase A — Deploy & observe (prompts 1–2).** The AI built, restarted the server to
production mode, then treated the "missing sessions" report as a data-forensics task:
it pulled `/api/sessions` and cross-referenced `sessionOrder` in
`preferences.json`. It proved both sessions were healthy (`hidden:false`,
`dataUnavailable:false`, valid PIDs) but sat at index 10 and index 2 of their folder
lists. Key move: it did **not** assume a rendering bug — it located them in the
persisted order map first.

**Phase B — Root-cause & design (prompt 2 → 3).** The AI explained this was the
*documented* behavior of the earlier `preserve-session-order-on-reboot` change: when
`consume` returns `false` (no user intent), the reattach branch returns early without
touching `sessionOrder`, protecting drag-order. It then laid out design options in a
table and recommended a new `"reattach"` register-reason plus a `reattachPlacement`
config policy. The human's decision point was a single character: **"2"** (pick option
/ "move them to front" path). The AI verified the real flow (bridge already calls
`sendStateSync` on both connect and reconnect) before committing to the plan.

**Phase C — Spec authoring (prompt 3 = the /opsx:apply skill text).** `openspec new
change reattach-move-to-front`, then proposal + design (6 decisions D1–D6) + 3 delta
specs + tasks (6 groups, ~20 checkboxes, TDD-first). `openspec validate --strict` →
4/4 clean before any implementation.

**Phase D — Implementation (TDD).** Task-by-task through protocol → config → bridge →
server → settings UI → docs → verification. Each task announced (`✓ Task 1.4 (48
passed)`). Full suite hit **3818 passing** after §6.

**Phase E — Verify + independent audit (prompts 5–6).** The `/opsx:verify` skill ran
twice. The first pass produced a clean report. The second, deliberately *suspicious*
pass ("I'm suspicious of D6…") found a **CRITICAL** bug: `register()` hardcodes
`status:"active"`, so the `"streaming-only"` policy was silently identical to
`"preserve"`. The AI plumbed `priorStatus` through `OnChangeContext`, added a
regression test, and corrected design D6. Suite rose to 3822.

**Phase F — Archive & ship (prompts 7–8).** A `general-purpose` subagent synced delta
specs to main; the change was archived to
`openspec/changes/archive/2026-05-01-reattach-move-to-front/`; two commits (`cbf951e`
impl, `0e0667b` archive) pushed to `develop`.

## 4. Prompts that worked

- **The goal prompt — `build and deploy`.** Weak as a spec, but it correctly kicked
  off the deploy that *surfaced* the real problem. Stronger version:
  *"Build and deploy, then check whether all my active sessions still show on cards
  after the restart."*
- **`Is it possible that the last 2 sessions are not displayed on cards?`** — the
  high-value prompt. It framed a symptom, not a solution, which let the AI do proper
  root-cause forensics instead of patching the UI.
- **`2`** — a one-character decision that unlocked the whole build. Effective *because*
  the AI had presented numbered options with a clear recommendation first.
- **The `/opsx:apply`, `/opsx:verify`, `/opsx:archive` skill invocations** — pasting
  the skill contract verbatim kept the OpenSpec lifecycle rigorous and repeatable.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat "build and deploy" as the whole task | Following up with "the last 2 sessions aren't on cards" | Front-load the acceptance check: "…then verify all active sessions still render" |
| Offer to just one-shot edit `preferences.json` to move sessions up | Choosing "2" — the proper design path, not the hack | State up front: "I want a durable fix via OpenSpec, not a manual data edit" |
| Trust its own implementation summary during verify | Re-invoking `/opsx:verify` a second time, forcing an independent audit | Always run verify twice — once against spec, once as an adversarial code audit |
| Assume design D6 ("read status after register") was correct | (AI self-corrected on the suspicious re-read) | Note the `register()` `status:"active"` coercion as a known trap in AGENTS.md |

The load-bearing correction was structural, not verbal: **running verify a second
time** is what caught the `streaming-only == preserve` regression that all tests had
been green through.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session, but the workflow is a textbook case
for one. The reusable pattern worth capturing:

- **"Verify twice — spec pass, then adversarial code pass."** The single most valuable
  move here. The first verify trusted the implementation summary; the second re-read
  what `register()` *actually* does to `status` and found a silent policy no-op. A
  `doubt-driven-review` / second-audit habit should be invoked on any change where a
  config policy branches on runtime state.
- **A memory-worthy trap:** *`memory-session-manager.ts::register()` hardcodes
  `status:"active"`, so any policy that reads `session.status` after register sees
  `"active"` — plumb `priorStatus` through `OnChangeContext` instead.*

Recommend saving that trap as a project memory so the next status-dependent change
doesn't repeat the D6 mistake.

## 7. Pitfalls & dead ends

- **Blank `jq` on `preferences.json`** — the first `cat … | jq '.sessionOrderByCwd …'`
  failed (key was `sessionOrder`, not `sessionOrderByCwd`). If a `jq` filter returns
  empty, `ls`/`head -c 500` the raw file to confirm the actual key names first.
- **Tests pass but the policy is dead.** `"streaming-only"` was silently equal to
  `"preserve"` while the whole suite (3818 green) stayed happy — because no test pinned
  the `register()` status-coercion interaction. If a policy branch depends on prior
  runtime state, write a regression test that pins *that* interaction, not just the
  branch in isolation.
- **`HOME=$(mktemp -d) npx vitest`** — several config/bridge tests read real
  `~/.pi/dashboard` state; run them under a throwaway `HOME` to avoid host-config
  contamination.
