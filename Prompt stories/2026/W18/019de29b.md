# How we did it: ship a Jujutsu-workspace dashboard plugin — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — a thinking stance, not an implementation one:

> "Enter explore mode. Think deeply. Visualize freely… You may read files, search
> code, and investigate the codebase, but you must NEVER write code or implement
> features… You MAY create OpenSpec artifacts."

The *real* objective, which emerged over the first few steering turns, was: **let
multiple parallel pi sessions work the same project safely** by giving each its own
Jujutsu (`jj`) workspace, surfaced as a first-class dashboard plugin — a `jj:<name>`
badge, a `+ Workspace` button, fold-back/forget actions, and a diff view that shows
*all* of an agent's workspace commits instead of only the last. The full arc ran
explore → OpenSpec proposal → a 66-task, multi-session implementation → build/deploy
→ live debugging of four end-to-end bugs, ending with the plugin **verified live**.

## 2. TL;DR playbook

1. **Open in explore mode** and forbid implementation. Let the model draw the problem
   (state matrices, decision trees) before committing to a shape.
2. **Interrogate the load-bearing risk first.** Here: "why is a dirty git index
   dangerous in a colocated jj repo?" That one question hardened three artifacts.
3. **Turn the exploration into an OpenSpec change** (`proposal.md`, `design.md`,
   `tasks.md`, `specs/…/spec.md`), validate with `openspec validate <name>`, and
   **commit ONLY the change artifacts** (`git add openspec/changes/<name>/`) — never
   the unrelated WIP in a dirty tree.
4. **Pin the fuzzy threads before applying.** Ask "is there anything to clarify?" and
   answer the open questions terse-and-numbered (`1. Refuse 2. Yes 3. Auto 4. B 5. Per plugin`).
5. **Apply phase-by-phase** with `/opsx:apply`. Mirror an existing plugin
   (`flows-plugin`) as the canonical reference; register the new package under
   `packages/*` (auto-picked-up workspace); write tests per phase.
6. **Run tests with a clean HOME:** `HOME=$(mktemp -d) npx vitest run <files>` to
   dodge machine-state contamination.
7. **Build + deploy the right layer:** `npm run build` (client) → `POST /api/restart`
   (server, runs TS directly, no build) → `npm run reload` (bridges). Verify the
   plugin loaded via `curl /api/health` + server log.
8. **Debug live with throwaway `.cjs` probes** in `/tmp` that hit the running server's
   REST endpoints; confirm each fix end-to-end before moving on.

## 3. How the collaboration unfolded

**Phase 1 — Explore & de-risk (prompts 1–5).** The AI investigated in parallel,
then drew the problem as ASCII state matrices: parent-repo type (jj-colocated vs
plain git) × operation, and a "is this git command safe in a jj repo?" decision tree.
The human's follow-ups drove the depth — *why* a dirty git index corrupts, whether
plain `git reset` is a safe escape hatch (yes; `git stash` is forbidden), what happens
when session B spins a workspace while session A has uncommitted edits (always safe;
the wrinkle is `baseRev` selection), and whether the diff view should be jj-aware
(yes — `git diff HEAD` is silently *wrong* once an agent makes more than one `jj new`).
Each answer was folded back into the design doc as a numbered decision.

**Phase 2 — Proposal + pin threads (prompts 6–8).** The AI drafted four OpenSpec
artifacts (~50-item task list, 8 phases), validated clean, and committed **only** the
change dir (`b73a72f`) — deliberately leaving ~50 unrelated WIP files untouched. When
asked "anything to clarify?", it surfaced five load-bearing open threads (forget
semantics, init-button visibility, conflict handling, bookmark naming, per-repo
config); the human resolved them in one terse numbered reply, and they landed as
Decisions 10–14 (`8ba6422`).

**Phase 3 — Implement across sessions (prompts 9–11).** `/opsx:apply` ran the
spec-driven schema. The model paused honestly at clean handoff points (19/55 → 54/65 →
62/66), phase by phase: tool-registry `jj` entry + `platform/jj.ts` recipes → bridge
VCS probe (`git-info.ts` → `vcs-info.ts` via `git mv` to preserve history) → plugin
scaffold mirroring `flows-plugin` → client components → regime-aware session-diff →
REST routes → skills. Tests were written each phase.

**Phase 4 — Build, deploy & live-debug (prompts 12–20).** Build → restart → reload,
then the human hit real gaps: no visible init button, no `+ Workspace` row, and the
button "not working". The AI traced each to a concrete cause and fixed four bugs live
(see §7), confirming the plugin end-to-end: badge + button render, `/api/jj/workspace/add`
and `/forget` return 200, `jjState` populates on every live session.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Effective because it *withheld* implementation:
  it bought a full design phase where the expensive decisions (fold-back semantics,
  diff correctness, opt-in visibility) got settled before a line of code existed.
- **"Why is a dirty git index problematic?" (steering #1).** A single *why* on the
  riskiest assumption. It forced the model to prove the corruption mechanism, which
  upgraded a vague spec line into a non-negotiable refusal with three enumerated
  alternatives. **Reuse pattern:** point the model at the one load-bearing risk and
  ask it to justify the guardrail.
- **"Is it possible to add the DiffView… use jj to diff?" (steering #4).** A scoping
  question that exposed a latent correctness bug (`git diff HEAD` misses multi-commit
  workspaces) — reframed from "feature" to "correctness fix."
- **"1. Refuse 2. Yes 3. Auto 4. B 5. Per plugin" (steering #7).** A high-leverage
  terse unlock: five open design threads resolved in one line, immediately foldable
  into decisions.
- **"commit and go on" / "build server client and deploy" (steering #10, #13).** Short
  imperatives that kept momentum once the shape was locked.

**Rewrite weak prompts:** the terminal debugging prompts ("I dont see", "no row",
"+Workspace is not working") were minimal. Stronger: *"The + Workspace button doesn't
appear on the session card — here's the Network tab bundle hash and any console errors
mentioning jj/Plugin."* Supplying the bundle hash + console output up front would have
skipped two stale-cache round-trips.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat "add a diff view" as a simple feature | "use jj to diff" → exposed multi-commit correctness gap | State up front: in a jj workspace, diff against the workspace base, not `HEAD` |
| Leave design threads implicitly-defaulted | "Is there anything to clarify?" then answered 5 threads | Ask the model to enumerate open threads before `openspec apply` |
| Ship the init affordance opt-in (hidden by default) | "I dont see any button" → temporarily drop the opt-in gate | Decide default-visible vs opt-in explicitly in the spec, and wire the config plumbing before the UI lands |
| Put workspace name + command on separate rows | "workspace name and command can be in one line… before openspec" | Specify card layout (row grouping, ordering) in the design doc |
| Assume the browser had the fresh bundle | Repeated "no row / not working" | Verify the served bundle hash AND force a hard refresh (`Cmd+Shift+R`) before deep-debugging |
| Read the first N sessions (historical/ENDED) when checking live state | — (self-caught) | When verifying live state, filter to `alive` sessions, not the first rows |

Scope expansions the human introduced: the jj-aware diff (steering #4) and the
one-line badge+button layout (steering #16) both widened the change mid-flight.

## 6. Skills, tools & memory created — and why they're effective

Two skills were authored (Phase 6):

- **`.pi/skills/jj-workspace/SKILL.md`** — captures the safe-operations model for
  jj-colocated repos (the three git-private surfaces safe to mutate: index, reflog,
  git config; everything else is shared-store and dangerous). Effective because it
  encodes the exact corruption mechanism the human's "why?" surfaced, so the next
  agent doesn't re-derive it. **Invoke when:** adding or automating any `jj`/git
  interop in this repo.
- **`.pi/skills/jj-workspace-fold-back/SKILL.md`** — captures fold-back semantics
  (Flavor 1 default: preserve commits, rebase, push bookmark; squash/PR as gated
  variants; refuse on conflicts or dirty index). Effective because fold-back is the
  load-bearing, easy-to-get-wrong operation. **Invoke when:** merging a workspace's
  work back to trunk.

**Recommended addition:** a `build-deploy-verify` note capturing the layer matrix
(client→build, server→restart, bridge→reload) plus the "confirm plugin loaded via
`/api/health` + server log, then hard-refresh the browser" ritual — it recurred and
cost several round-trips.

## 7. Pitfalls & dead ends

- **`jj workspace add` fails if the parent dir is missing.** The route didn't `mkdir -p`
  the `.shadow/` parent. → **Fix:** create the parent before shelling out.
- **`fork_point(a, b)` is wrong for jj 0.40** — `fork_point()` takes one argument. It
  bit both the route revset and `selectJjDiffBase`, plus a spec test that pinned the old
  syntax. → **Use the single-arg form** and update the pinned test.
- **`sendJjStateIfChanged` short-circuits after a server restart.** `lastJjStateJson` is
  preserved across bridge reconnect, so the bridge "thinks it already sent" while the
  server has cleared state → empty `jjState`. → **Fix:** reset the change-detection cache
  on reconnect, then trigger a tick.
- **Slot machinery is scaffolded but not populated** — the runtime slot registry is
  created empty; `flows-plugin` works only because `SessionCard.tsx` hardcodes its
  imports. → **Bridge:** wire jj components directly into `SessionCard.tsx` the same way
  until the slot consumers land.
- **Stale browser bundle** masqueraded as "button not working" for two turns. → Check
  the served hash (`index-*.js`) matches, then `Cmd+Shift+R` (or DevTools → Disable cache).
- **Reading the wrong sessions when verifying live state** — the first rows were ENDED
  historical sessions with no `jjState`; live sessions were correct. → Filter to alive.
- **`tsc --noEmit` cross-package errors pre-existed** the change (config issues) — don't
  chase them; verify with a scoped `vitest run` instead. Likewise a themes-count test
  (5→9) was an unrelated pre-existing regression (`git status` proved `themes.ts` untouched).
