# How we did it: Fixing the pi-dashboard.dev marketing site — 404s, bento gaps, and a wrong package name

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** ("Enter explore mode. Think deeply… you must
NEVER write code or implement features") pointed at the public marketing site under
`site/`. The real, quickly-clarified objective: **the live site at
`https://pi-dashboard.dev/` was serving broken assets** — every `_astro/*.css`,
`_astro/*.js`, `screenshots/*`, and `app-icon.png` was 404-ing. The job grew across
steering into three landed fixes: (1) kill the 404s, (2) remove ugly whitespace in the
feature bento cards, (3) correct a wrong npm package name shown on the site. All three
shipped live to `pi-dashboard.dev` in one ~57-minute session.

## 2. TL;DR playbook

1. **Diagnose in explore mode first.** Ask the AI to find *why* assets 404 before
   touching code. Root cause here: `site/astro.config.mjs` still had
   `base: "/pi-agent-dashboard"` + `site: "https://blackbelttechnology.github.io"` —
   correct for a GitHub Pages **subpath**, wrong for the **apex custom domain** the
   `public/CNAME` now points at.
2. **Map the blast radius before editing.** Have the AI list every file that bakes the
   stale prefix (`astro.config.mjs`, `features.ts`, `HeroAnimation.tsx`, `404.astro`)
   and — critically — every file that *legitimately* contains `pi-agent-dashboard` (the
   real GitHub **repo** URLs in `Footer`, `Nav`, `InstallTabs`). Don't touch those.
3. **Drop `base`, set `site` to the apex domain**, strip the `/pi-agent-dashboard`
   prefix from screenshot/asset constants, fix the `404.astro` home link.
4. **Rebuild and grep the `dist/` output** for both the old prefix *and* protocol-relative
   `//x.png` double-slashes (an empty base turns `${BASE_URL}/x.png` into `//x.png`).
   Fix by using `${BASE_URL}x.png` (BASE_URL already ends in `/`).
5. **Commit ONLY `site/**`.** The tree had 7 unrelated unpushed commits + untracked
   openspec proposals — stage the site files explicitly, confirm with the human.
6. **Push to `develop`** (that auto-triggers `deploy-site.yml`); don't just
   `gh workflow run` it — the workflow builds `origin/develop`, not your uncommitted local
   edits.
7. **Verify live** with `gh run watch` + `curl -so /dev/null -w "%{http_code}"` probes
   against the real URLs.
8. **Fix bento whitespace with CSS/template only**: `row-span-2` banner cards → horizontal
   split (text vertically-centered left, image fills right); image-less cards → inline SVG
   `visual` prop instead of stretching to a neighbour's height.
9. **Fix the package name** by grepping for the exact wrong string
   (`@blackbelt-technology/pi-dashboard`, missing `-agent-`) and confirming the real name
   against root `package.json` before editing.

## 3. How the collaboration unfolded

**Phase 1 — Diagnose (explore mode).** The AI read `astro.config.mjs`, `public/CNAME`,
and the workflow, and produced ASCII diagrams pinning the 404 to a config mismatch: the
CNAME made GitHub Pages serve at the apex, but the build still emitted every URL with the
`/pi-agent-dashboard/` subpath prefix. *Why it worked:* it named the single root cause and
distinguished the stale-prefix files from the legitimate-repo-URL files **before** any
edit — so the fix was surgical, not a find-and-replace that would have broken the GitHub
links.

**Phase 2 — Fix + verify build.** After "exit explore mode and implement", the AI made 4
config/constant edits, rebuilt, and grepped `dist/` — catching a **latent bug the fix
surfaced**: `${BASE_URL}/app-icon.png` now produced `//app-icon.png` (protocol-relative,
broken) because the empty base left a leading double slash previously masked by URL
normalization. It fixed all 4 occurrences (`Footer`, `Nav`, `Base.astro` favicon+ogImage)
and re-verified zero prefixes and zero `//` URLs.

**Phase 3 — Ship correctly.** On "Execute Deploy Site github flow", the AI dispatched the
workflow but immediately flagged that the run built `origin/develop`, **not the
uncommitted local fix** — so it would redeploy the broken state. It staged only the 7
`site/**` files (ignoring unrelated commits/proposals), pushed, watched the run, and
verified live with curl probes.

**Phase 4 — Bento whitespace.** On the vague "too much white space… cards with gaps", the
AI opened the live layout in the browser and found *two distinct* causes: banner cards
spanning 2 rows with image glued to the bottom (`mt-auto`) leaving a middle void, and
image-less cards stretching to a neighbour's height. It offered five fixes; the human
picked **C + D**. C = `FeatureCard` detects `md:row-span-2` and switches to a horizontal
split; D = a `visual` prop rendering inline SVGs (`PromptBusVisual`, `DiscoveryVisual`) so
image-less cards get real content instead of empty space — **no new screenshots, no
capture-pipeline change, no JS**.

**Phase 5 — Package name.** The human spotted the site showing
`@blackbelt-technology/pi-dashboard`; the correct published name is
`@blackbelt-technology/pi-agent-dashboard`. The AI confirmed the real name against
`package.json`, grepped for the exact wrong string, fixed 3 spots (`Footer`,
`InstallTabs`), verified the site's own `-site` package and workspace packages were
untouched, and shipped.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Starting in explore mode forced *diagnosis before
  code* — the AI mapped the root cause and blast radius first. A stronger, direct version
  for a repeat: *"The live site at pi-dashboard.dev 404s all `_astro/*` and image assets.
  Diagnose the Astro base/site config vs the CNAME before editing; list which files carry
  the stale subpath prefix and which legitimately reference the GitHub repo name."*
- **"exit explore mode and implement"** — a clean one-line unlock once the plan was
  agreed. Effective because the plan was already concrete (4 files, 5 lines).
- **"Execute Deploy Site github flow"** — triggered the ship phase, where the AI caught the
  "workflow builds origin, not your local edits" trap.
- **"C + D"** — a two-character high-leverage pick from an enumerated menu of five fixes.
  Enumerating options *with aesthetic/effort tradeoffs* let the human choose fast.
- **"Wrong name in site: … Correct: …"** — a precise correction with both the wrong and
  right string. Effective because it gave the AI an exact grep target.

## 6. Skills, tools & memory created — and why they're effective

**None created this session.** But the workflow is clearly repeatable and would benefit
from a project skill. Recommended: a **`deploy-site` skill** capturing the Astro
apex-domain contract for `site/`:

- **What it would capture:** the `astro.config.mjs` (`site` = apex, no `base`) + CNAME
  relationship; the `${BASE_URL}x.png` (no leading slash) rule; the "which files carry the
  subpath prefix vs the legitimate GitHub repo URL" map; and the ship contract (push
  `site/**` to `develop`, don't just `gh workflow run`).
- **Why it's effective:** it removes the re-diagnosis of the base/CNAME mismatch and the
  protocol-relative double-slash trap — both non-obvious and both re-encountered whenever
  the domain or base changes.
- **When to invoke:** any `site/` asset-404, domain move, or deploy-workflow confusion.

## 7. Pitfalls & dead ends

- **Empty `base` → `//asset.png`.** Dropping `base` makes `${BASE_URL}` a bare `/`, so
  `${BASE_URL}/x.png` becomes protocol-relative `//x.png` (browser tries `https://x.png/`).
  Fix: `${BASE_URL}x.png`. Previously masked by URL normalization under the subpath.
- **`gh workflow run` ≠ your local fix.** The deploy workflow builds `origin/develop`.
  Dispatching it before pushing redeploys the *old* broken state. Commit + push first.
- **`astro preview` backgrounding.** One `npx astro preview &` + immediate `curl` raced
  (server not up yet) — the retry read the log/added sleep. `pkill -f 'astro preview'` when
  done.
- **Don't blanket-replace `pi-agent-dashboard`.** It's the real GitHub repo name in
  `Footer`/`Nav`/`InstallTabs` GitHub URLs — only the **npm package** string was wrong
  (`pi-dashboard` → `pi-agent-dashboard`). Grep the exact token.
- **Binary fetch "errors" are false alarms.** The fetch tool refusing to render a PNG means
  it *did* fetch a real image (HTTP 200 + `image/png`) — not a failure.
