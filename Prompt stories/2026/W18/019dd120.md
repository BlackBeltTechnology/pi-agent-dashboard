# How we did it: Tracing the dashboard slash-command pipeline in explore mode — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The user opened the session in **explore mode** — a strict thinking-partner stance with
one hard rule: *read, search, investigate, but never write code or implement features.*
The opening prompt was the standard explore-mode preamble (`Enter explore mode. Think
deeply. Visualize freely…`), so the *real* objective only crystallized through the two
steering turns that followed: **understand how slash commands in the dashboard's command
palette actually work today** — specifically which commands are real vs. aspirational,
and whether an *extension-registered* command (like `flows:new`) is genuinely supported
end-to-end or needs new wiring. The session closed with a request to visualize the whole
architecture as a Mermaid diagram.

## 2. TL;DR playbook

1. Open **explore mode** and state the constraint out loud: *investigate only, no code.*
2. Paste the concrete artifact you're confused about (here: a command-palette screenshot /
   command list) and ask the AI to map **each item to where it comes from today**.
3. Let the AI grep the three components in order: **client** (`CommandInput.tsx`), then
   **extension** (`session-sync.ts`), then **server** (`event-wiring.ts`).
4. Ask the sharp follow-up: *"Can you make extension-registered commands supported?"* —
   forcing the AI to trace the **end-to-end path** rather than propose new code.
5. Have the AI produce an ASCII pipeline diagram: `registerCommand → getCommands →
   commands_list → setSessionCommands → CommandInput merge`.
6. Confirm the verdict (**already supported end-to-end**) and pinpoint where a specific
   command "falls off" (filtering / extension-not-installed), not where code is missing.
7. Finish by asking for a **Mermaid** architecture diagram (repo convention — not ASCII)
   to lock the mental model in a shareable form.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (client-side).** The AI grepped `CommandInput.tsx` for `tab`,
`autocomplete`, `slash`, and `commands`, and located `BUILTIN_COMMANDS`. It immediately
made the key distinction: the pasted command list was from `docs/plans/plano-pi-integration.md`
(a forward-looking plan), **not** the live palette. It produced a "WHAT YOU SEE TYPED →
WHERE IT COMES FROM (today)" table separating built-ins (`/compact /reload /new`),
App.tsx interceptors (`/flows`), extension-provided commands (`/flows:edit`, `/roles`),
and pure-plan items (`Ctrl+A Toggle auto-routing` — implemented nowhere). *Why it worked:*
grounding every visible token in a real source file killed the aspirational/real ambiguity
in one move.

**Phase 2 — End-to-end trace (steering turn #1).** The user asked whether an
extension-registered command could "be supported." Instead of writing code, the AI traced
the existing path across all three components and answered **"it already is supported."**
It grepped the extension (`session-sync.ts:51` — `getCommands()` → `filterHiddenCommands`
→ `commands_list`), the server (`event-wiring.ts:429` — relay verbatim), and the client
(`useMessageHandler.ts:144` — `setSessionCommands`), showing the merge point at
`CommandInput.tsx:105`. *Decision point:* the human's framing ("can you make it work")
tempted an implementation answer; the explore-mode stance redirected it into a diagnosis —
where a given command *falls off* (stripped by `DASHBOARD_NATIVE_COMMANDS`, or the
extension simply isn't installed) rather than what to build.

**Phase 3 — Architecture visualization (steering turn #2).** Two days later the user
returned and asked for a Mermaid architecture diagram. The AI rendered the three
components (pi session + bridge, dashboard server with dual WS gateways + store +
persistence + REST, React/Vite client) with the slash-command path highlighted, honoring
the repo's Mermaid-over-ASCII convention. *Why it worked:* the diagram consolidated the
scattered grep findings into one shareable artifact.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Effective because it set a *stance* — no
  implementation — that kept every later answer diagnostic. For a future operator, pair it
  immediately with the concrete artifact you're confused about so the AI has a target.
- **High-leverage follow-up: "Can you [make] extension registered command be supported?"**
  Short, and it unlocked the entire end-to-end trace. Stronger rewrite: *"Trace the
  end-to-end path an extension-registered command takes from `registerCommand` to the
  palette, and tell me where mine falls off — don't propose new code."* — this states the
  no-code constraint and asks for the failure point explicitly.
- **"Draw a mermaid diagram of architecture."** Terse but effective because the repo
  convention (Mermaid, not ASCII) is already known. Bake the convention into the request
  when the convention isn't guaranteed.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat a pasted command list as the live feature set | Implicitly, by asking "where does each come from" | Say up front: *distinguish implemented vs. planned/aspirational* |

The dominant guardrail here is the **explore-mode stance itself**: it converts every
"make it work" instinct into a "trace why it doesn't" diagnosis, which is exactly what you
want before writing a change proposal.

## 7. Pitfalls & dead ends

- **One failed grep:** `grep -rn "Toggle auto-routing\|Manage flows" packages/ --include=…`
  returned nothing — because those strings live in a *plan doc*, not source. **If a grep
  for a command comes back empty, suspect it's aspirational (docs/plans/), not missing
  code.** The AI recovered by re-scoping to `--include="*.md"` and confirming the plan
  origin.
- **Don't answer "can you make X work" with code in explore mode.** The trace-not-build
  reflex is the whole point; a code answer would have violated the stance and skipped the
  diagnosis.
