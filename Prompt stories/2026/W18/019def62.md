# How we did it: Focus-driven folder compaction — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened an **explore-mode** session — a thinking-partner stance, no code,
just investigate and (optionally) capture thinking as OpenSpec artifacts. The kickoff
was the standard explore-mode preamble ("Enter explore mode. Think deeply. Visualize
freely… NEVER write code"). The *real* objective only crystallized after the first
steering turn: the session sidebar's directory groups are too heavy. Even "collapsed"
groups render a full header — folder name, git info, action bar, plugin slots, an
OpenSpec section — eating 4–10 vertical lines each, so 6+ pinned directories consume
the whole viewport before a single session card is visible. The goal: **density** —
compact inactive folders down to just the sessions that demand attention, without
touching the active folder's existing collapse/expand behavior. The session ended
with a complete, validated OpenSpec change (`focus-driven-folder-compaction`): proposal,
design, 3 spec files, and a 35-task `tasks.md`.

## 2. TL;DR playbook

1. **Open explore mode** with the standard preamble to keep the AI in thinking-only
   mode (reads/searches OK, no implementation).
2. **Describe the pain, not the solution.** State the density problem and let the AI
   draw the current-state render (ASCII) so you both agree on what's heavy *today*.
3. **Correct the AI's over-engineering fast.** It will invent multi-cell state
   machines; steer it to the *one simple rule* you actually want ("in inactive folders,
   ignore the collapse toggle; show only attention cards").
4. **Ground the predicate in real fields.** Ask the AI to verify every proposed
   condition (`unread`, `ask_user`, `streaming`) against the actual `Session` type
   before locking the design — no wishful fields.
5. **Say `create proposal`** once the shape is agreed; the AI runs `openspec new change`
   and writes `proposal.md`.
6. **Fast-forward the rest** with the `/opsx:ff` skill — it generates `design.md`,
   `specs/*`, and `tasks.md` in dependency order and validates each.
7. **Confirm `openspec validate <change>` passes** before handing off to `/opsx:apply`.

## 3. How the collaboration unfolded

**Phase 1 — Disambiguate the ask (Discovery).** The operator's opening steering turn
was dense and hard to parse ("Only just show cards which asking question or unread or
processing… when clicking the directory, selects it…"). The AI's first move was the
right one: it *reflected the ask back* in its own words and asked for correction rather
than guessing. This turned a fuzzy request into a shared model of "density pain."

**Phase 2 — Draw the current state (Gather).** Before proposing anything, the AI
grepped the client (`SessionList.tsx`, `SortablePinnedGroup.tsx`) and rendered an ASCII
diagram of what each directory group emits *today* — header + `GroupGitInfo` +
`FolderActionBar` + plugin slot + `FolderOpenSpecSection` — proving that even a collapsed
group costs 4–10 lines. Grounding the design in the *actual* rendered structure (not an
imagined one) is what made the later spec accurate.

**Phase 3 — Argue the shape (Design).** The AI initially over-modeled the problem: a
four-cell state machine with "active group resolution," sticky per-group overrides, and
accordion semantics. The operator cut it down to **one rule scoped to inactive folders**.
The AI re-stated that simpler contract, then grounded the attention predicate against the
`Session` type: `currentTool === "ask_user"` (awaiting), `status ∈ {streaming, active}`
(processing), `unread === true` (already server-managed). No new persistence, no protocol
change — pure client-side derivation. That verification step is what kept the design
buildable.

**Phase 4 — Generate the artifacts (Generate).** On `create proposal`, the AI ran
`openspec new change focus-driven-folder-compaction`, checked `openspec status --json`
for the build order, and wrote `proposal.md`. Then the `/opsx:ff` fast-forward drove
`design.md` (8 decisions), three spec files (new `folder-focus`, modified
`session-filtering` + `collapsible-groups`), and a 35-task `tasks.md` — each artifact
created only after its dependencies, with `openspec validate` between steps.

**Phase 5 — Verify (Verify).** Final `openspec validate focus-driven-folder-compaction`
returned valid; the AI summarized the artifact set and pointed to `/opsx:apply` as the
next move. No implementation was attempted — the explore-mode guardrail held.

## 4. Prompts that worked

- **The goal prompt (explore-mode preamble).** Effective because it fixes the *stance*:
  the AI reads and diagrams but never implements, and it's explicitly allowed to capture
  thinking as OpenSpec artifacts. Reuse it verbatim when you want a thinking partner, not
  a coder.
- **High-leverage follow-up — the "make it simpler" steer.** The operator's second prompt
  ("as now, only just hide the rest… only show cards which asking question or unread or
  processing") collapsed a four-cell state machine into one rule. Short, concrete, and it
  reset the whole design.
  - *Rewrite for reuse:* "Don't build a state machine. In inactive folders only: keep the
    header, show only cards that are asking / unread / processing, hide the rest. The
    active folder's existing toggle stays exactly as-is."
- **`create proposal`** — a two-word unlock once the shape was agreed. It works because
  the AI already had the full contract in context; nothing more needed saying.
- **`/opsx:ff` fast-forward** — one prompt that generated every remaining artifact in
  order. Effective because the OpenSpec skill enforces dependency sequencing and validation
  automatically.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Over-engineer: a four-cell state machine with sticky per-group overrides + accordion semantics | "as now, only just hide the rest… only show attention cards" — one rule, scoped to inactive folders | State the **simplest rule + its scope** up front; explicitly forbid new state ("no per-group sticky state") |
| Risk inventing convenient fields for the attention predicate | (self-corrected) — grounded `unread`/`ask_user`/`streaming` against the real `Session` type before locking | Tell it "verify every field against the actual type before you design around it" |
| Rush from fuzzy ask to a shape | The dense steering prompt forced a re-statement; the AI reflected it back first | Ask the AI to **reflect the ask back and diagram the current state** before proposing |

There were no brand/naming or scope-creep corrections — the main steering axis was
**simplicity**: the operator repeatedly pulled the design back toward the minimal rule.

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created this session. The workflow leaned on existing
OpenSpec skills:

- **`/opsx:ff` (fast-forward artifact creation)** — generates proposal→design→specs→tasks
  in dependency order, validating between each. It removes the manual "which artifact
  next, is it unblocked yet" bookkeeping and guarantees a validated change ready for
  `/opsx:apply`. Invoke it once the proposal shape is agreed and you want the full change
  scaffolded in one go.
- **Explore mode** — the stance that kept this a *planning* session (5 spec/proposal files,
  zero code). Invoke it whenever you want to think through a UI change and capture it as a
  proposal without drifting into implementation.

*Recommendation:* nothing here is novel enough to warrant a new skill — the OpenSpec skill
chain already captures the repeatable path.

## 7. Pitfalls & dead ends

- **One failed command:** `ls src/client/components/ | grep -iE "group|pinned|sidebar|director"`
  — the client lives under `packages/client/src/components/`, not `src/client/`. If a grep
  in `src/client/` returns nothing, the code is under `packages/client/src/`. Use the doc
  tree (`kb agents`) or `find packages/client/src -name "*.tsx"` instead of guessing the
  layout.
- **Design over-modeling (the real dead end).** The AI's first design was a four-cell state
  machine. It cost a round-trip. Avoid it by stating the minimal rule and its scope before
  the AI proposes.
