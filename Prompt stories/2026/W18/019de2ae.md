# How we did it: designing the `/dashboard:*` slash-command namespace — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened in **explore mode** — a thinking stance, explicitly *not* an
implementation one ("You may read files, search code… but you must NEVER write code or
implement features… You MAY create OpenSpec artifacts"). The real objective that emerged:
turn the dashboard's ~50 REST endpoints (already wrapped by the `pi-dashboard` skill's
curl helper) into a first-class, **modular slash-command namespace** the operator can fire
from any pi session — `/dashboard:session-list`, `/dashboard:abort-all`, and friends — and
capture that design as a validated OpenSpec proposal. The session never wrote product code;
it produced a spec.

## 2. TL;DR playbook

1. **Open in explore mode** with the "thinking, not implementing — but OpenSpec artifacts are allowed" stance so the AI investigates freely and stays out of the code.
2. **Ground the AI in the real pipeline first:** have it read `packages/extension/src/command-handler.ts` + `prompt-expander.ts` and the existing `.pi/skills/pi-dashboard/` skill before proposing anything. The design must fit how slash commands *actually* route.
3. **Settle the architectural question up front:** *can the LLM invoke slash commands?* (No — they're expanded before the LLM sees them.) This decision shapes the whole namespace.
4. **Steer the naming grammar early:** ask for modular names — `/dashboard:<resource>-<verb>` (singular resource, hyphen to verb) — before the AI generates the command list.
5. **Name the missing capability:** a command that renders output *without* calling the LLM. This became a second, orthogonal spec (`prompt-template-executable-mode`, `executable: bash` frontmatter).
6. **Scaffold with `openspec new change <name>`**, then write proposal.md / design.md / tasks.md / specs, and `openspec validate <name> --strict` until clean.
7. **Commit only the proposal directory** (`git add openspec/changes/<name>/`) — leave the rest of the dirty working tree untouched.
8. **Cross-check against sibling changes:** ask "is there crossover with `fix-extension-slash-commands-in-dashboard`?" then pin the routing precedence and a `Depends On` link so the two proposals can't collide.

## 3. How the collaboration unfolded

**Phase A — Discovery (read the real routing).** The AI began by reading the
`api-reference.md` (594 lines), the `pi-dashboard` SKILL + helper script, and the two
routing files (`command-handler.ts`, `prompt-expander.ts`). *Why it worked:* the whole
design is downstream of how pi expands `/cmd` — it aliases the first `:` to `-` and scans
`.pi/prompts/*.md`, `.pi/skills/*/SKILL.md`, and `pi.getCommands()`. Reading that first
meant the naming grammar was chosen to match the existing file-resolution, not fought
against it.

**Phase B — The architectural pivot.** The AI surfaced two foundational questions and
answered them before enumerating commands: (1) the LLM cannot directly "use" slash commands
— they're expanded into a user message *before* the model responds; (2) there is currently
**no clean way for a slash command to render output without invoking the LLM**. That second
gap became a whole separate capability.

**Phase C — Naming grammar (steered).** The operator interrupted with "commands be
modularized… session commands be `dashboard:session-<>`". The AI turned that into a formal
grammar: `/dashboard:<resource>-<verb>`, singular resource, one colon then hyphens to keep
the namespace shallow.

**Phase D — Generate + validate.** The AI scaffolded the change with
`openspec new change add-dashboard-slash-commands`, then wrote 5 artifacts (proposal,
design with a 5-pipeline diagram, tasks with 60+ items, and two spec files) and ran
`openspec validate --strict` until green.

**Phase E — Commit surgically, then reconcile with siblings.** On "commit" it staged
*only* the new proposal dir (`dc3d684`). Two days later the operator asked about crossover
with `fix-extension-slash-commands-in-dashboard`; the AI found both proposals touch the
exact same routing lines, and added a `Depends On` section, a routing-precedence
requirement (extension-dispatch > exec-mode > LLM fallback) with two scenarios, and a
task precondition — committed as `ebbf140`.

## 4. Prompts that worked

- **The goal / kickoff (explore-mode stance).** Strong because it hands the AI a *stance*,
  not a task list, and pre-authorizes exactly one output type: OpenSpec artifacts. This
  keeps a "planning" session from drifting into code. Reuse it verbatim for any
  design-before-build session.
- **"The commands be modularized… `dashboard:session-<>`"** — a tiny, high-leverage steer.
  Two days of naming bikeshedding avoided by pinning the grammar in one sentence *before*
  the AI generated the list.
- **"Be a session-info which displays session info without call llm"** — unlocked the entire
  second capability. A future operator should phrase it as: *"add a command that renders
  output directly, without an LLM round-trip — treat that as its own capability."*
- **"IUs there any crossover between this proposal and `fix-extension-slash-commands-in-dashboard`?"**
  — the reconciliation prompt. Cheap to ask, and it caught two proposals silently editing the
  same call sites. Bake this in: *always ask the AI to diff a new proposal against sibling
  open changes.*

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Reach for flat, ad-hoc command names | "commands be modularized… `dashboard:session-<>`" | State the `<resource>-<verb>` grammar in the goal prompt before any list is generated |
| Treat "render info" as just another LLM-backed command | "session-info… without call llm" | Call out non-LLM rendering as a *separate capability* up front (`executable: bash`) |
| Design a proposal in isolation | "any crossover between this and `fix-…`?" | Ask the AI to reconcile against every open sibling change and pin routing precedence |

## 6. Skills, tools & memory created — and why they're effective

No new pi skill or memory was created this session — the reusable assets are the **two
OpenSpec capabilities** the design carved out:

- **`dashboard-slash-commands`** — the namespace, the 30+ command set, the discoverability
  footer, and the skill-bundling rule. Reusable because it standardizes how every future
  dashboard endpoint gets a command.
- **`prompt-template-executable-mode`** — the orthogonal infra piece: `executable: bash`
  frontmatter, a `slash-exec` ParsedPrompt variant, env injection, positional args, and a
  `bash_output.source` field. Effective because *any* skill can reuse it to render output
  without an LLM round-trip.

*Recommended skill to create:* a `reconcile-sibling-proposals` habit — when a new OpenSpec
change touches shared code, diff it against open changes and emit a `Depends On` + routing
precedence. This session did it by hand; it's clearly repeatable.

## 7. Pitfalls & dead ends

- **`openspec change new` vs `openspec new change`.** The first form (`openspec change new
  add-dashboard-slash-commands`) and an early `ls` on the not-yet-created dir failed; the
  working invocation was **`openspec new change <name>`**. If a scaffold command errors,
  check `openspec new --help` for the correct subcommand order before retrying.
- **Two proposals, same routing lines.** `add-dashboard-slash-commands` and
  `fix-extension-slash-commands-in-dashboard` both edit `bridge.ts::sessionPrompt` +
  `command-handler.ts`'s `parsed.type==="slash"` branch. Left unreconciled they'd have
  clobbered each other. Fix: an explicit `Depends On` and a spec'd precedence order
  (extension dispatch > exec-mode > LLM fallback) with scenarios so the order can't be
  misread.
- **Long wall-clock, tiny active work.** The session spans ~65h but is really a handful of
  bursts — don't read the elapsed time as effort.
