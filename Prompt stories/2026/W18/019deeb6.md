# How we did it: From a red "npm update exited with code 1" to two OpenSpec proposals — an AI collaboration guideline

## 1. Goal (the ask)

The session opened as a **support question**, not a planning request. The first prompt was:

> "Plugins installed correctly, but pi cannot be updated. What can be the reason?" *(with a screenshot of the failing Update badge)*

The real objective only emerged through steering: the user was on **Windows**, running the **Electron/managed install** (`~/.pi-dashboard/`), and `npm update` failed because **system npm was not on PATH** and the bundle shipped `node.exe` without the `npm.cmd`/`npx.cmd` shims. Once the root cause was pinned, the goal escalated from "explain the error" to "**design a permanent fix**": embed a managed Node runtime inside `~/.pi-dashboard/` and make it updatable. That became **two OpenSpec change proposals**, fully scaffolded to apply-ready.

## 2. TL;DR playbook

1. **Reproduce the exact failing command manually.** The badge only shows `npm update exited with code 1` and strips stderr — so run the same command with `--loglevel=verbose` in the real environment (`cd %USERPROFILE%\.pi-dashboard` → `where npm` / `where node` → `npm update @mariozechner/pi-coding-agent --loglevel=verbose`).
2. **Map the npm error code to a cause** with a small table (ENOTFOUND=network, EBUSY=locked files, EINTEGRITY=stale lockfile, **ENOENT/empty `where npm`=npm not on PATH**).
3. **Trace the code path** that produces the error: `grep` `pi-core-updater.ts`, `bootstrap-install.ts`, `docker-make.sh`, `dependency-installer.ts` to confirm `installSource: "managed"` maps to the `~/.pi-dashboard/` npm-update branch and that the Windows bundle **skips the npm shims**.
4. **Offer the durable architecture** once the immediate fix is clear: embed Node into the managed dir so server + bridge + every pi session share one runtime via PATH.
5. **Turn the design into OpenSpec changes** — `openspec new change <name>` for each, ordered so the user-visible fix ships first.
6. **Drive each change to apply-ready** with the `/opsx:ff` fast-forward loop: `openspec status --change <name> --json` → create `proposal.md` → `design.md` → `specs/` → `tasks.md`, validating after each.
7. **Verify** with `openspec validate <name>` until clean (all 4 artifacts `[x]`).

## 3. How the collaboration unfolded

**Phase 1 · Triage from a screenshot (Discovery).** The AI read the badge ("local" → `installSource: "managed"`), grepped `pi-core-checker.ts`, `pi-core-updater.ts`, and the client components to explain *why* the update runs `npm update` inside `~/.pi-dashboard/` and why the UI hides the real stderr. It listed three plausible code-1 causes without yet knowing the OS. **Effective bit:** it grounded every claim in a real source file rather than guessing.

**Phase 2 · Narrow to the real environment (Steering-driven).** The user steered hard here — "Give me proper Windows based execution", then pasted `where npm` → `Could not find files`. That single paste was the **diagnostic key**: empty `where npm` = npm not on PATH = the Electron bundle ships `node.exe` but no `npm.cmd`. The AI confirmed by reading `packages/electron/scripts/docker-make.sh:115` and pinpointed the missing shim copy.

**Phase 3 · From workaround to architecture (Design).** The user asked a series of escalating "is it possible…" questions — install Node inside `.pi-dashboard`? embed it in Electron resources and copy on bootstrap? make the runtime updatable afterward? Each got a concrete, source-anchored design: `bootstrapInstall` already owns first-run setup, `ToolRegistry` is already the single resolution point, offline-cacache is the copy-from-resources precedent. The AI proposed a **source-aware model** (`managed` / `system` / `bundled-electron`) mirroring how pi itself is already classified.

**Phase 4 · Generate two proposals (Generate + Verify).** "create proposals" kicked off `openspec new change` for both `embed-managed-node-runtime` and `manage-node-runtime-updates`. Two `/opsx:ff` prompts then fast-forwarded each through proposal → design → specs → tasks, calling `openspec status --json` and `openspec validate` after each artifact. Result: **14 files, both changes apply-ready and validation-clean**, ordered so the fix change ships before the updater change.

## 7. Pitfalls & dead ends

- **Zero failed commands** this session (30 bash, 0 errors) — because every command was a read-only `grep`/`ls`/`openspec status`, not a mutation. Lesson: **diagnose with reads before writing anything.**
- **Don't trust the badge text.** `npm update exited with code 1` is a *stripped* message; the real error lives in the `pi_core_update_progress` event stream. If you only have the badge, reproduce manually with verbose logging.
- **The Windows bundle bug is silent.** `node.exe` present but `where npm` empty looks like a PATH problem; it's actually a *missing shim* in the bundle (`docker-make.sh` copies `node.exe` + `node_modules` but not `npm.cmd`/`npx.cmd`). Grep the make script before blaming the user's PATH.
- **`<app>\resources\node\` is wiped on every Electron upgrade** — which is exactly why the fix embeds Node into the *persistent* `~/.pi-dashboard/node/` instead.
