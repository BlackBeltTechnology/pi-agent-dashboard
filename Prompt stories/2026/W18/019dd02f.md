# How we did it: From a red rebase to a shipped OpenSpec change — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff was small and operational:

> "There are conflicts in git repo, I pulled develop. Check carefully and rebase"

The *real* objective grew out of that one line. Resolving the rebase surfaced two
failing tests in `browse-endpoint.test.ts`. Instead of patching the tests, the
session used those failures as evidence of a genuine product defect — `GET /api/browse`
doing two jobs at once (enumeration + `isGit`/`isPi` classification), firing up to
400 `fs.access` syscalls per request and silently dropping the project past a
`MAX_ENTRIES = 200` cap. The end goal became: **turn a flaky-test symptom into a
properly-scoped OpenSpec change (`split-browse-flags`), implement it TDD-style, and
land it committed** — enumeration and flag-classification cleanly separated.

## 2. TL;DR playbook

1. **Resolve the rebase surgically.** `git status` → find the single conflicted file
   (`App.tsx`) → merge *both* sides intentionally → `git add` → `git rebase --continue`.
2. **Run the full suite** (`npm test 2>&1 | tee /tmp/pi-test.log | tail -60`) and
   *classify* each failure as regression vs. pre-existing before touching anything.
3. **Prove the failures are pre-existing** by checking them out on the base commit —
   don't assume, verify (`git checkout <base> -- <testfile> && npx vitest run …`).
4. **Push the clean rebase** with `git push --force-with-lease` (never plain `--force`).
5. **Enter explore mode** to diagnose the *product* bug behind the test failures —
   read code first, theorize second. Produce a blast-radius map of every consumer.
6. **Pick a direction, then stress-test it:** "Direction C, but analyze possible API
   break and side effects." Trace every consumer of `isGit`/`isPi` before choosing a shape.
7. **`openspec new change` → fast-forward the artifacts** (proposal → design → specs →
   tasks), validating after each (`openspec validate <change>`).
8. **Apply TDD:** write hermetic tmpdir tests to replace the host-coupled ones, then
   implement enumeration/classification split behind `detect=1` + new `/api/browse/flags`.
9. **Sweep docs** (`architecture.md`, skill api-reference, `AGENTS.md`) for the changed surface.
10. **Archive + commit.** If `openspec archive` hits a parser quirk, fall back to
    `--skip-specs --yes` and apply the spec delta by hand, then a single conventional commit.

## 3. How the collaboration unfolded

**Phase 1 — Rebase & triage (Discovery).**
The AI ran `git status`, found the conflict isolated to `packages/client/src/App.tsx`,
and merged both branches' intent (kept the incoming extension-UI slash-command match
*and* HEAD's `clearImagesForSession` cleanup, extending cleanup to the early-return
path). It continued the rebase, ran the full suite (3271 passed / 2 failed), and
**refused to hand-wave the 2 failures** — it checked them out on the base commit to
prove they were pre-existing, host-coupled failures (project sits 438th alphabetically
in a 576-entry `~/Project`, sliced out by the 200-cap). *Why it worked:* the AI
separated "my change broke this" from "this was already broken," which prevented a
scope-creep fix on a red rebase.

**Phase 2 — Explore the real bug (Design thinking).**
The human invoked explore mode. The AI grounded in code before theorizing, then drew
a three-layer diagnosis: (1) test design couples to host FS, (2) the 200-cap silently
drops entries, (3) `/api/browse` conflates enumeration with expensive classification.
The decision point: the human chose **"Direction C, but analyze possible API break and
side effects"** — forcing a blast-radius trace of every `isGit`/`isPi` consumer
(type def, producer, single client consumer `PathPicker.tsx`, and *documented public
surface* in the skill api-reference + architecture.md).

**Phase 3 — Capture as OpenSpec (Generate artifacts).**
"C3 and create proposal" locked the shape: opt-in `detect=1` param + new bulk
`GET /api/browse/flags`, `BrowseEntry.isGit/isPi` become TS-optional (no skill-recipe
break), truncation/cap-bump/mtime-caching explicitly *out of scope*. The AI stopped
after `proposal.md` per the OpenSpec gate, then fast-forwarded design (6 numbered
decisions with rejected alternatives) → specs (MODIFIED + ADDED requirements with
scenarios) → tasks, validating clean at each step.

**Phase 4 — Implement TDD (Build & Verify).**
28 tasks across shared types → server split (`probeFlags`/`classifyPaths`/
`parseFlagsQuery`, `MAX_FLAG_PATHS = 100`, reused `createSemaphore(32)`) → routes →
client two-phase fetch → hermetic tests → docs. Result: **3336 passing / 0 failing**
(up from 3271, +65 tests), with the 2 host-coupled tests replaced by tmpdir fixtures.

**Phase 5 — Archive & land.**
`openspec archive` hit a parser quirk on the spec header lookup; the AI fell back to
`--skip-specs --yes` and applied the spec delta manually with `Edit`, then committed
as `35454e5`.

## 4. Prompts that worked

- **Goal prompt** — *"Check carefully and rebase."* The "**carefully**" set the quality
  bar that made the AI verify (not assume) the failing tests. A stronger kickoff would
  add: *"classify each test failure as regression vs. pre-existing before fixing anything."*
- **"Run all tests"** — cheap, high-leverage: forces a ground-truth baseline before any
  claim of "done."
- **"Enter explore mode. Think deeply."** — the pivot from firefighting to root-cause
  design; kept the AI from silently implementing a band-aid.
- **"Direction C, but analyze possible API break and side effects. Maybe some other
  part of code uses that info"** — the single most valuable steer: it converted a
  design pick into a *blast-radius investigation* and caught the documented public API.
- **"C3 and create proposal"** — a 3-token prompt that locked scope and kicked off the
  OpenSpec workflow. High leverage because the prior turn had already enumerated options.
- **"go on, last command stuck"** — unblocked a hung archive step and licensed the
  manual `--skip-specs` fallback.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat failing tests as something to just fix | "Check **carefully**" + "Run all tests" | State up front: classify each failure as regression vs pre-existing, prove it on the base commit |
| Jump toward implementing the fix | "Enter explore mode… NEVER write code" | Use explore mode explicitly for root-cause before any change |
| Pick an API shape without checking consumers | "analyze possible API break and side effects. Maybe some other part of code uses that info" | Require a blast-radius map (type → producer → consumers → docs) before choosing a shape |
| Risk breaking documented skill recipes | (implicit in the side-effects steer) | Make new fields TS-optional; grep skill api-reference + architecture.md for the surface |
| Stall on an `openspec archive` parser quirk | "go on, last command stuck" | Know the fallback: `archive --skip-specs --yes` + manual spec-delta `Edit` |

Quality bars the human imposed: verify-don't-assume on tests, scope-guard the change
(truncation/cap-bump deferred to follow-ups), and keep the public API non-breaking.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session, but the workflow is textbook-repeatable
and the repo already encodes it:

- **`openspec-explore` → `openspec-new-change` → `openspec-ff` → `openspec-apply` →

  test failure smells like a product bug, not a test bug.
- **Recommended memory to save:** *"`openspec archive` can hit a spec-header parser

  `archive --skip-specs --yes` then apply the delta via `Edit`."* This removes the
  10-minute stall that happened at 00:46.
- **Recommended memory:** *"`browse-endpoint` tests must use hermetic tmpdir fixtures —
  scanning real `~/Project` couples to host FS and the 200-entry cap."*

## 7. Pitfalls & dead ends

- **Host-coupled tests look like a rebase regression but aren't.** If `isGit`/`isPi`
  tests fail, check whether the project sits past the `MAX_ENTRIES = 200` alphabetical
  cap of its parent dir — fix with a tmpdir fixture, don't chase the rebase.
- **`vitest` needs sandbox flags in this repo.** Runs used
  `HOME=$(mktemp -d) NODE_OPTIONS="--localstorage-file=$(mktemp)"` to avoid state bleed.
- **`openspec archive` parser quirk.** On a spec with a new ADDED requirement beside a
  MODIFIED one, the header lookup can mismatch despite byte-identical headers → use
  `--skip-specs --yes` and hand-apply the delta.
- **Never plain `git push --force`.** The session used `--force-with-lease` throughout.
- **Don't mark manual verification tasks done.** Tasks 8.2/8.3 were left for the human
  to run — mark only what the AI actually verified.
