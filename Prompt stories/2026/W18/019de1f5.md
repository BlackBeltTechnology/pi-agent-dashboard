# How we did it: Fixing the dashboard-restart bridge auto-start race — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with a terse bug report:

> _"Server restart does not work from pi-dashboard. I started terminal and it started dashboard"_

The real objective, once the diagnosis landed: **make `pi-dashboard restart` (and the
Electron / `POST /api/restart` path) reliable** by killing a race where every connected
pi bridge auto-restarts the server the instant its WebSocket dies — beating the intended
restart path to the port and orphaning a half-started daemon. The fix had to run the full
OpenSpec change lifecycle (proposal → design → tasks → implement → verify → archive →
ship) end-to-end, land as one clean commit, and prove itself by restarting the *live*
server through the new code path.

## 2. TL;DR playbook

1. **Reproduce from the log, not the code.** `tail -n 80 ~/.pi/dashboard/server.log` — the
   missing `pi-dashboard start (parent pid …)` header after a `cmdStop` wave is the smoking gun.
2. **State the root cause as a numbered race** before proposing anything (stop → WS dies →
   bridges auto-start → a bridge wins the port → `cmdStart` sees "already running" → exits
   early → the bridge-started daemon dies with the bash tool).
3. **Ask whether a second symptom shares the cause** (here: Electron restart) — confirm by
   reading `server-lifecycle.ts` + `restart-helper.ts` before claiming it.
4. **Scaffold the OpenSpec change**: `openspec change new fix-restart-bridge-auto-start-race`,
   then fast-forward all four artifacts (proposal, spec, design, tasks). Validate with
   `openspec validate <name> --strict`.
5. **Implement bottom-up by dependency**: protocol message → server broadcast → bridge
   quiesce → CLI delegation → orchestrator hardening → spec parity → docs. Write the test
   first for each task group, run it scoped with `HOME=$(mktemp -d) npx vitest run <file>`.
6. **Run the full suite as a final guard** — fix the lint/esbuild fallout from embedded-JS
   strings and the fake-timer teardown, don't paper over it.
7. **Build + deploy, then restart the live server through the new path** — the deploy IS
   the integration test. Grep `server.log` for the previously-missing start header AND the
   *absence* of a `bridge auto-start` header.
8. **Verify → archive → sync specs → commit ONE clean scope** — stash unrelated working-tree
   churn, rebase, fast-forward push.

## 3. How the collaboration unfolded

**Phase 1 — Diagnose from evidence (Prompt 1).** The AI resisted guessing at the code. It
read `~/.pi/dashboard/server.log`, spotted that `cmdStop()` ran (a wave of
`session unregistered (explicit)` lines) but `cmdStart()` never wrote its header, and
reconstructed the race as a 6-step sequence. It also surfaced that a robust path already
existed (`POST /api/restart` → `restart-helper.ts`) and recommended it as the interim
workaround. **Why it worked:** the log diff *was* the proof; the AI led with observable
evidence, not speculation, and initially declined to change code until asked.

**Phase 2 — Confirm the second surface (Prompt 2).** Asked whether Electron restart shared
the cause, the AI read `server-lifecycle.ts` and confirmed: yes, plus an Electron-specific
twist (the orchestrator's `detached: true` server escapes Electron's Job Object, breaking
supervision). **Decision point:** one root cause, two surfaces → one change.

**Phase 3 — Scaffold the OpenSpec artifacts (Prompt 3, `/opsx:ff`).** Four artifacts
created and validated: proposal (log evidence + 3-part fix + file-by-file impact + Electron
parallel), a NEW `server-restart` capability spec (4 requirements / 7 scenarios), a design
doc (4 decisions D1–D4 with rejected alternatives, 5 risks, rollback), and a 28-task tasks.md
ordered by dependency.

**Phase 4 — Implement task-by-task (Prompt 4, `/opsx:apply`).** The AI walked the tasks in
dependency order, writing focused unit tests before each implementation slice and marking
checkboxes with `sed`. Notably it made a documented judgment call: Task 7 (a heavyweight
multi-bridge WS integration test) was marked "covered-by-composition-of-unit-tests" with an
explicit note, rather than silently skipped.

**Phase 5 — Build, deploy, self-test (Prompt 5, "build and deploy").** `npm run build`,
then `pi-dashboard restart` — which *exercised the new `cmdRestart` path on itself*. The
log now showed the missing `pi-dashboard start (parent pid …)` header and, critically, **no
`bridge auto-start` race**. All 4 live bridges reconnected via discovery during the quiesce
window.

**Phase 6 — Verify, archive, ship (Prompts 6–9).** `/opsx:verify` produced a
requirement→implementation→test map (29/29 tasks, 5/5 requirements, 7/7 scenarios). Prompt 7
("fix") got a clarifying push-back because verification found nothing to fix. `/opsx:archive`
synced the new capability spec into `openspec/specs/`. Final commit isolated *just this
change's* 21 files, leaving 128 unrelated working-tree changes for their owners.

## 4. Prompts that worked

- **Goal prompt** — _"Server restart does not work from pi-dashboard. I started terminal and
  it started dashboard."_ Short, but it embedded the key clue ("I started terminal and it
  started dashboard" = a *bridge* auto-started it). A stronger version states the reproduction
  and points at the log: _"`pi-dashboard restart` leaves the server down until I open a fresh
  terminal. Diagnose from `~/.pi/dashboard/server.log` before changing code."_
- **High-leverage follow-up** — _"Create proposal. And is it possible thats the same reason
  cause electron app restart does not work?"_ One sentence expanded scope to a second surface
  *and* forced a cross-check instead of an assumption — high leverage.
- **The `/opsx:*` slash-command chain** (ff → apply → verify → archive) drove the whole
  change lifecycle with almost no prose. Each carried its own embedded procedure.
- **`build and deploy`** — three words that turned "tests pass" into "proven on the live
  server," because the deploy re-ran the exact failing scenario.

## 7. Pitfalls & dead ends

- **Lint banned `process.kill(...)`** inside the orchestrator's embedded JS string. Fix: add
  the `// ban:process-kill-ok` opt-out marker — but note it must be placed so **esbuild
  doesn't parse a backtick in the comment as a template-literal opener** (that broke the
  build a second time). Keep backticks out of embedded-script comments.
- **Lint passed alone but failed when two files were specified** — different workspace configs
  interfere. When a scoped lint disagrees with the suite, trust the full `npm test` run.
- **A deferred `process.exit(0)` `setTimeout` fired after `afterEach` mock-restore**, breaking
  the test with a real exit. Fix: use fake timers in the restart-route test so the deferred
  exit never actually runs.
- **Don't write a heavyweight multi-bridge WS integration test just to satisfy a task
  checkbox** if focused unit tests already pin every contract — but *document* the decision
  explicitly (the apply skill flags this).
- **Committing everything** would have mixed 128 unrelated changes (flows-plugin, theme strip,
  viewed-session-tracker, stray `.d.ts`/`.js.map`) under one message. Stash/scope first.
