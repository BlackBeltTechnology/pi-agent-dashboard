## 1. Goal (the ask)

The operator opened in **explore mode** — an explicit "think, don't implement" stance:
*"Enter explore mode. Think deeply. Visualize freely. Follow the conversation wherever
it goes... you must NEVER write code or implement features... You MAY create OpenSpec
artifacts."* The seed problem: the dashboard had accumulated **three generations of
dialog/confirm code** that were never retired, producing visual and behavioural drift
(three overlay tints, inconsistent scroll-lock / Esc / focus-trap / ARIA, and copy-paste
`ConfirmDialog` descendants).

Once the steering clarified it, the **real objective** was not to write any React — it
was to *capture the thinking as a complete, apply-ready OpenSpec change*: proposal +
design + two capability specs + a 47-task plan for a `Dialog` primitive and a `Confirm`
preset, then commit **only** those artifacts.

## 2. TL;DR playbook

1. **Open in explore mode** with the think-not-implement stance; state that OpenSpec
   artifacts *are* allowed (capturing thinking ≠ implementing).
2. **Map the terrain first.** `rg` for `confirm|dialog|modal` across `src/client` and
   `packages/*/src`; grep `fixed inset-0` to find every overlay. Name the pattern you
   see — here, *three eras* of dialog construction, drawn as ASCII.
3. **Pick a direction** with a one-token reply (the operator typed `2`) once the AI
   surfaced numbered options.
4. **Fast-forward the artifacts:** `/opsx:ff` → `openspec new change "unify-dialog-system"`,
   then follow `openspec status --json` build order (proposal → design + specs → tasks).
5. **Fill each artifact from `openspec instructions <artifact> --json`**, validating after
   each: `openspec validate unify-dialog-system --strict`.
6. **Commit surgically.** Stage *only* your change dir: `git add openspec/changes/unify-dialog-system`.
   Verify the diff is yours before committing.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / naming the pattern (10:12–10:16).** The AI ran read-only recon:
five `rg` passes over `src/client`, `packages/client/src`, and the plugin packages,
plus a `grep` of overlay selectors. Its key move was *not* to enumerate "3 confirm
dialogs" but to reframe them as **three eras** of construction (shared `ConfirmDialog`
→ later hand-rolled overlays → newest portal-based dialogs), drawn as an ASCII diagram.
*Why it worked:* naming the real axis of the mess (era, not shape) is what made a clean
"introduce one primitive, migrate era-by-era, delete the copies" plan possible.

**Decision point:** the operator replied `2` — choosing one of the AI's surfaced
directions without re-litigating.

**Phase 2 — Scaffold + proposal (10:25–10:17… ff run).** `/opsx:ff` kicked off the
fast-forward: `openspec new change`, then `openspec status --json` to read

eras + copy-paste drift; what: a `Dialog` shell owning portal/overlay/scroll-lock/Esc/
click-outside/focus-trap/ARIA/z-index/sizes/intent, plus a `Confirm` preset; two new
specs `dialog-system` + `confirm-dialog`; existing `dialog-portal` spec left untouched

**Phase 3 — Design + specs + tasks (→10:29).** Driven by `openspec instructions

## 4. Prompts that worked

- **The goal prompt (explore-mode preamble).** Effective because it set an explicit
  *stance*: read/search/investigate freely, never implement, but OpenSpec artifacts are
  in-scope. That single constraint kept the whole session in "capture thinking" mode and
  produced a plan instead of premature code.
- **`2` — the one-token direction pick.** High leverage: once the AI presented numbered
  options, a single character committed to a path and unlocked the entire ff run. Don't
  over-explain when the AI has already framed the choice.
- **`/opsx:ff`.** The fast-forward command generated *every* artifact needed to reach
  apply-ready in one motion, following the tool's own dependency order.
- **`commit`.** Terse, but note it needed the guardrail below — see §5.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat the problem as "3 confirm dialogs" | (implicit) exploring until it reframed as *three eras* | Ask "what's the real axis of the mess?" before planning a fix |
| `commit` naively over a dirty tree — swept in unrelated pre-staged files | Reset and re-stage only the change dir | State up front: *"commit ONLY the files this task created; scope the `git add` to the change dir"* |
| Nothing else — the explore-mode preamble pre-empted the biggest risk (writing code) | — | Keep the "never implement in explore mode" preamble as a reusable stance block |

The decisive correction was **commit scoping**: a bare `commit` on a repo with a stale
staged tree is dangerous. The AI recovered well (`reset --soft` + `reset HEAD -- .`), but
the loss is avoidable by naming the exact paths to commit.

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created this session. The workflow leaned entirely on
**existing OpenSpec tooling**, used well:

- **`openspec new change` + `openspec status --json`** — scaffolds the change dir and
  yields the machine-readable `applyRequires` build order, so artifacts are written in
  dependency order (proposal → design/specs → tasks) instead of guessed.
- **`openspec instructions <artifact> --json`** — gives per-artifact authoring guidance;
  driving each write from it keeps artifacts spec-conformant.
- **`openspec validate <change> --strict`** — the correctness gate run after every
  artifact; only stopping when it's clean prevents an invalid change reaching apply.

*Recommendation:* the recovery from the dirty-tree commit is repeatable enough to warrant
a tiny **"scoped-commit" habit** — always `git add <change-dir>` (never `git add .`) when
landing OpenSpec artifacts, and diff-check before committing.

## 7. Pitfalls & dead ends

- **Dirty pre-staged tree → over-broad commit.** The repo had unrelated staged files; the
  first `git add openspec/changes/... && git commit` still swept them in. **If you hit
  this:** `git reset --soft HEAD~1 && git reset HEAD -- .`, then stage *only* your change
  dir and re-commit. Always `git status --short | wc -l` after resetting to confirm a
  clean base.
- **Don't touch `dialog-portal`.** The instinct to "unify everything" would delete the
  existing portal spec; the plan deliberately *reuses* it (the new shell consumes it).
  Retiring working infrastructure you actually depend on is a false economy.
