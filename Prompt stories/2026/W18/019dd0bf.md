# How we did it: Fix the chat scroll race during multi-batch replay — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — a thinking-partner stance, explicitly *no
code, no implementation*:

> "Enter explore mode. Think deeply. Visualize freely. Follow the conversation
> wherever it goes… You may read files, search code, and investigate the codebase,
> but you must NEVER write code or implement features… You MAY create OpenSpec
> artifacts."

The real objective, which only crystallized after the first steering turn, was a
concrete bug: **switching to a large, server-uncached session lands the user
mid-conversation instead of at the latest message, with a floating scroll-to-bottom
button appearing.** The end-to-end goal became: diagnose the root cause, capture it
as an OpenSpec change, implement the fix TDD-style, deploy, verify, archive, and
commit — all in one sitting.

## 2. TL;DR playbook

1. **Open in explore mode** to reason about the bug *before* proposing a fix. Trace
   the session-switch → `event_replay` → scroll code path (`ChatView.tsx`,
   `useMessageHandler.ts`) with `rg`/`find` under `packages/`, not `src/`.
2. **Reproduce the mechanism on paper first** — draw the timeline as ASCII (state ·
   browser · network columns). The race only becomes obvious once `scrollTo()`, its
   lagging `onScroll`, and the next replay batch are on the same diagram.
3. **Answer the AI's diagnostic questions tersely** (where it lands, is the button
   there, cached-vs-uncached timing). One key observation — *the floating button
   appears* — pins the bug: something actively flips `isNearBottom` to `false`.
4. **Capture, don't code** while in explore mode: `openspec new change <name>`, then
   write proposal.md / design.md / specs delta / tasks.md; `openspec validate
   <name> --strict`.
5. **Exit to apply** with `/opsx:apply` — implement TDD: failing test first
   (`ChatView.scroll-race.test.tsx`), confirm it fails, then the minimal fix (a
   ~150 ms `programmaticScroll` suppression window around every self-initiated
   `scrollTo`; `handleScroll` early-returns while set).
6. **Run the full sweep** `npm test 2>&1 | tee /tmp/pi-test.log` and *quarantine
   pre-existing failures* — here the 2 `browse-endpoint.test.ts` failures belonged
   to the in-flight `split-browse-flags` change, not this fix.
7. **Build + deploy + reload**: `npm run build`, `POST /api/restart`, `npm run
   reload`. Get the human to smoke-test the real uncached-session scenario.
8. **Archive + sync + commit**: `/opsx:archive`, sync the delta into
   `openspec/specs/chat-scroll-lock/spec.md`, commit only *this* change's files —
   leave the other in-flight change's files staged-untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI read `ChatView.tsx` /
`useMessageHandler.ts`, greping for `scroll|bottom|stick|atBottom|autoScroll` and
`replay|batch|history|backfill`. It corrected an early path assumption (files live
under `packages/client/src/`, not `src/client/`). *Why it worked:* it produced a
falsifiable timeline diagram of the suspected race and asked the human to confirm
"we're looking at the same thing" instead of jumping to a fix.

**Phase 2 — Root-cause lock-in (steering).** The human's terse answers — especially
"floating button there, after pushing scrolling to end" — let the AI conclude that
`handleScroll` (the only thing that can flip `isNearBottom` to false) fires from a
lagging `onScroll` after each `scrollTo`, measures the *old* `scrollTop` against the
*new* `scrollHeight` grown by the next batch, and wrongly decides the user scrolled
up. Decision point: the human picked **Option 2** (suppress measurement during
programmatic scroll) and sub-option **a**.

**Phase 3 — Capture as OpenSpec (still explore mode).** `openspec new change`
scaffolded the folder; the AI wrote all four artifacts (proposal, design with the
race diagram + the 150 ms rationale + alternatives + test strategy, a 3-scenario
delta on the existing `chat-scroll-lock` capability, and a TDD-ordered tasks.md),
then `openspec validate --strict` passed.

**Phase 4 — Apply TDD.** `/opsx:apply` → wrote the failing test, confirmed Test 1
fails (button visible pre-fix) while Test 2 (real scroll-up) already passes, then
implemented the `markProgrammatic()` helper, the `handleScroll` early-return, and
dropped the now-redundant `&& !programmaticScroll.current` gate on the auto-scroll
effect. All 26 ChatView tests green.

**Phase 5 — Deploy & verify.** `npm run build`, restart via `POST /api/restart`
(PID changed, uptime reset), `npm run reload`. Human smoke-tested ("okay, tested").

**Phase 6 — Archive, sync, commit.** `/opsx:archive` moved the folder to
`archive/2026-04-28-…`; a `general-purpose` subagent synced the delta into the main
`chat-scroll-lock` spec (pure addition, no conflict). Final commit landed only the
archive + spec sync; the actual code fix was already `d3d68b5`.

## 4. Prompts that worked

- **Goal prompt (explore mode preamble).** Effective because it *forbids
  implementation* — forcing diagnosis and a written proposal before any edit. Reuse
  it verbatim whenever the bug isn't fully understood yet.
- **"Option 2 first" / "a".** High-leverage one-word decisions. They worked because
  the AI had already laid out numbered options with tradeoffs, so a single token
  chose the whole implementation strategy.
- **The terse diagnostic answers** ("floating button there, after pushing scrolling
  to end"). A precise *observation* about UI state was worth more than a guess about
  the cause — it eliminated every hypothesis except the `handleScroll` flip.
- **"build and deploy" → "okay, tested" → "commit changes".** Minimal phase gates.
  Effective because each hands control back to the human at exactly the
  irreversible/verify boundaries.

Rewrite of a weak prompt: instead of "I dont know" for the timing question, a
stronger operator answer is *"uncached sessions load slower and arrive in batches —
assume multi-batch replay."* That states the mechanism the AI needs.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The workflow, however, is a clean
repeatable pattern that *should* be captured:

- **Recommended skill: "explore-then-apply bugfix loop."** Captures the
  explore-mode-diagnose → OpenSpec-capture → `/opsx:apply` TDD → build/restart/reload
  → archive/sync/commit arc. It removes the manual bookkeeping of which command
  belongs to which phase and enforces the *diagnose-before-code* discipline.
- **Subagent used:** a `general-purpose` agent for the delta-spec sync during
  archive — good isolation for the mechanical spec-fold step.

The reusable insight worth a memory: *a lagging `onScroll` after a programmatic
`scrollTo` will misfire during any async content growth; guard every self-initiated
scroll with a short suppression window rather than trying to debounce the event.*

## 7. Pitfalls & dead ends

- **Wrong path root.** `ls src/client/components/ChatView.tsx` fails — the code is
  `packages/client/src/components/ChatView.tsx`. Start with `find packages -name …`.
- **`openspec change new` vs `openspec new change`.** The first form errored; the
  working invocation is `openspec new change <name> --description "…"`. Check
  `openspec new --help` when unsure.
- **jsdom test env needs an isolated HOME.** Vitest run needed
  `HOME=$(mktemp -d) npx vitest run …` to avoid a config/state collision.
- **Pre-existing red tests.** 2 failures in `browse-endpoint.test.ts` were *not*
  caused by this change (in-flight `split-browse-flags`). Don't chase them — confirm
  with `git stash` + rerun, then move on.
- **Two overlapping changes in the tree.** `rest-api.ts` and `split-browse-flags/`
  belong to another change; the archive commit must exclude them.
