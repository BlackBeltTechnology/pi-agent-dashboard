# How we did it: Ship a "scaffold a dashboard plugin" skill — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — an explicit *think, don't implement* stance:
"Enter explore mode. Think deeply… You may read files, search code, and investigate,
but you must NEVER write code." The bare topic was: *we have a dashboard-plugin
architecture (archived change `dashboard-plugin-architecture`, a `dashboard-plugin-runtime`
loader, a `demo-plugin`) — now give authors an on-ramp.*

Once the exploration sharpened it, the **real objective** was a publishable pi
skill, `dashboard-plugin-scaffold`, that does two distinct jobs:

- **`new` mode** — scaffold a brand-new plugin package inside the monorepo from an
  up-front `ask_user` batch (id, slots, server?, bridge?).
- **`augment` mode** — run *inside an existing pi-extension project*, grep its TUI
  surface (`ctx.ui.*`, `pi.registerTool`, custom components), and map those calls to
  dashboard slot claims + React/server scaffolding.

The finished artifact: `packages/dashboard-plugin-skill/`, published as
`@blackbelt-technology/pi-dashboard-plugin-skill`, driven end-to-end through the full
OpenSpec loop (proposal → apply → verify → archive).

## 2. TL;DR playbook

1. **Open in explore mode** and force the ambiguity to the surface *before* any code.
   Here the key distinction was **pi extension** vs **dashboard plugin** — two
   overlapping concepts the prompt straddled. Draw the ASCII contrast table, then ask.
2. **Resolve the two modes explicitly** (`new` vs `augment`) and lock the `augment`
   contract: grep-and-map an existing project's TUI surface, don't just template.
3. **Capture the thinking as an OpenSpec change** while still in explore mode:
   `openspec change new add-dashboard-plugin-skill`, then write proposal / design /
   tasks / delta-spec. Validate with `openspec change validate`.
4. **Exit explore mode, commit ONLY the proposal** (`git add openspec/changes/<name>/`)
   — the working tree had unrelated in-progress work; never `git add -A`.
5. **Apply the change** (`/opsx:apply`): walk `tasks.md` group by group — package
   scaffold → SKILL.md + references → templates → scripts → `render.ts` + bin → tests.
6. **Make the skill programmatically testable**: the SKILL.md is prose, but add a
   tiny `render.ts` template renderer + a `bin/scaffold.ts` so vitest has something to
   exercise. 41 tests (render-new, render-augment, grep-prelude).
7. **Run the FULL suite**, not just the package (`npm test`) — confirm 4271 tests
   still green before touching docs.
8. **Update docs by the AGENTS.md routing rules**: AGENTS.md Key-Files row (≤200
   chars), README section + TOC, and dispatch a **subagent** for the `docs/` prose edit.
9. **Verify** (`/opsx:verify`): trace every requirement to test evidence, then
   **archive + sync specs** (`/opsx:archive`) and commit the docs/archive delta.

## 3. How the collaboration unfolded

**Discovery (explore mode).** The AI refused to implement and instead produced an
ASCII contrast table separating *pi extension* (lives in `~/.pi`, loaded every
session, third-party) from *dashboard plugin* (lives in `packages/<name>-plugin/`,
first-party, slot claims + REST + WS). *Why it worked:* the original ask was
genuinely ambiguous; naming the two concepts side-by-side let the human pick a
direction instead of the AI guessing. **Decision point:** the human clarified that
`augment` runs *inside an existing extension project* and must **analyze** the TUI
surface — turning a vague "make a scaffold" into a concrete grep-and-map contract.

**Capture.** Still in explore mode (allowed: "capturing thinking, not
implementing"), the AI scaffolded the OpenSpec change — 4 artifacts, 8 task groups,
30+ items, 10 requirements — and validated it. **Decision point:** `exit explore
mode`, then `commit changes` — but the AI committed *only* the proposal because the
tree held unrelated WIP.

**Generate (apply).** Days later, `/opsx:apply` walked `tasks.md` top to bottom. The
AI added `render.ts` + a bin script so the markdown skill had a programmatic core the
tests could drive. Templates, 6 reference docs, 2 shell scripts, then 41 tests.

**Verify & archive.** `/opsx:verify` built a requirement→evidence trace (11/11
covered, 41/41 tests). `/opsx:archive` synced the delta into a new main spec
(`openspec/specs/dashboard-plugin-skill/spec.md`) and the final `commit` staged only
docs + archive move, again leaving unrelated in-flight work untouched.

## 4. Prompts that worked

- **The goal prompt (explore mode preamble).** Strong *because* it forbade
  implementation and demanded thinking first — which is exactly why the extension/plugin
  ambiguity got caught before any code was written. For a topic this fuzzy, an
  explore-mode kickoff is the right call, not a "just build it" prompt.
- **High-leverage follow-ups** were tiny: `exit explore mode`, `commit changes`,
  `commit`. Each was a one-word gear-shift that moved the work to the next phase. They
  worked because the *preceding* phase had already been captured in OpenSpec artifacts,
  so "commit" had an unambiguous target.
- **The `/opsx:apply`, `/opsx:verify`, `/opsx:archive` slash-prompts** carried the
  whole workflow — the human didn't re-explain the task, just invoked the next stage.

Rewrite tip: a weak version of the goal would be *"add a skill to scaffold dashboard
plugins."* The stronger version states the two modes and the augment contract up front:
*"…a skill with `new` (batch-driven monorepo scaffold) and `augment` (grep an existing
extension's TUI surface and map it to slot claims) modes."*

## 6. Skills, tools & memory created — and why they're effective

- **`dashboard-plugin-scaffold` skill** (`packages/dashboard-plugin-skill/.pi/skills/`).
  *Captures:* the entire on-ramp for authoring a dashboard plugin — a single
  `ask_user` batch, two modes, 6 reference docs (slot taxonomy, manifest schema,
  plugin/server context APIs, TUI→dashboard mapping, build integration), and 9
  templates. *Why effective:* it removes the "read three packages and the archived
  spec by hand" tax; an author gets a validated package skeleton in one flow. *Invoke
  when:* someone says "create a dashboard plugin" or "add dashboard support to my
  extension."
- **`render.ts` + `bin/scaffold.ts`.** *Captures:* the template rendering as callable
  code. *Why effective:* makes the skill deterministically testable (41 tests) instead
  of trusting prose.
- **`grep-tui-surface.sh` (python-backed).** *Captures:* deterministic JSON of a
  project's `ctx.ui.*` / `pi.registerTool` / custom-component surface. *Why effective:*
  the whole `augment` mode depends on a reliable inventory; a python core sidesteps the
  `set -e` + ripgrep-exit-1-on-no-match fragility (see §7).

## 7. Pitfalls & dead ends

- **Bash grep script died under `set -e`.** ripgrep returns exit 1 on *no match*,
  which `set -e` treats as fatal. *Fix:* rewrote `grep-tui-surface.sh` in python so a
  zero-match is a normal empty result, not a crash.
- **AGENTS.md Key-Files row overran the limit** (263 > 200 chars). *Fix:* trim to
  exactly 200. If you hit an over-threshold row, shorten the purpose text, don't split.
- **Tempted to exclude `src/__tests__/` from the npm `files` allowlist.** *Don't* —
  sibling packages ship their tests too; it's a repo convention. Match it.
- **`git add -A` would have swept unrelated WIP** (flows-anthropic-bridge-plugin,
  spawn-failure tests, App.tsx). *Fix:* stage by explicit path every time.
- **`8.3` first-publish gate is a manual policy item** — you can't run an end-to-end
  install from the session; mark it "documented as gating policy."
