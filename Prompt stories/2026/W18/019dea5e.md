# How we did it: From a broken site screenshot to a shipped release-notes footer — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with almost no words: `"Site have a problem"` plus a screenshot of
`pi-dashboard.dev` rendering as broken CSS/JS and `astro-island` hydration errors. The
*real* objective — which only emerged across ten steering turns — was much larger than a
one-line CSS fix: **(1)** diagnose and fix the apex-domain asset-path breakage, **(2)**
un-draft and correct the v0.4.6 GitHub release, **(3)** turn a Windows SmartScreen block
into permanent user-facing documentation *and* a build-side signing plan, **(4)** wire
that documentation into an auto-appended release-notes footer so every future release
carries it, and **(5)** commit + push cleanly in a Jujutsu-colocated repo. What started
as "fix a screenshot" became a full diagnose → document → automate → ship arc.

## 2. TL;DR playbook

1. **Diagnose from the symptom, not the stack trace.** A cascade of `astro-island`
   hydration errors was downstream of one root cause: `base: "/pi-agent-dashboard"` in
   `site/astro.config.mjs` while the site serves from the apex `pi-dashboard.dev` (per
   `site/public/CNAME`). Assets 404'd at `/pi-agent-dashboard/_astro/...`.
2. **Confirm the fix scope with a grep sweep**, not a guess:
   `rg -n "/pi-agent-dashboard" --glob '!dist' --glob '!node_modules'` → drop `base`,
   point `site` at `https://pi-dashboard.dev`, fix hardcoded screenshot/404 paths.
3. **Verify with a real build**: `cd site && npm run build` then grep `dist/` for
   leftover `/pi-agent-dashboard/` strings (release URLs are the only legit ones).
4. **Fix the release with `gh`**: `gh release edit v0.4.6 --draft=false`, then slice the
   body and re-append platform warnings deterministically (see §3 Phase 2).
5. **Answer "unsigned binary" correctly**: SmartScreen/Gatekeeper is *not a defect* — give
   the user-side workaround (More info → Run anyway / right-click → Open) AND scaffold an
   OpenSpec change for the permanent fix (Authenticode signing).
6. **Make the docs self-perpetuating**: create `.github/release-notes-footer.md` as the
   single source of truth and append it inside `publish.yml`'s "Extract release notes"
   step so every future release inherits it automatically.
7. **Ship in a jj repo the jj way**: `jj describe` → `jj bookmark move develop --to @` →
   `jj git push --bookmark develop`. Never `git commit`/`git rebase`/`git stash`.

## 3. How the collaboration unfolded

**Phase 1 · Diagnose the broken site (Discovery).** From a screenshot alone, the AI
located `site/public/CNAME` (apex domain) vs the stale `base:` in `astro.config.mjs`,
explained the hydration errors as *downstream* of asset 404s, swept the tree with `rg`
for hardcoded `/pi-agent-dashboard/` paths, fixed four files, and proved it with a clean
`npm run build`. **Why it worked:** it treated the loud symptom (hydration) as a
consequence and chased the quiet root cause (base path), then verified against build
output instead of asserting.

**Phase 2 · Rescue the v0.4.6 release (Repair).** The user pivoted to "Fix the release,
release notes of 0.4.6." The AI un-drafted it with `gh release edit`, then used an
idempotent `sed`/`awk` pipeline to strip any prior appended warning block and re-append
the current one — so re-runs never double-stack the footer. **Decision point:** the human
kept the loop on the *actual published body*, forcing every edit to round-trip through
`gh release view --json body`.

**Phase 3 · SmartScreen: workaround + permanent fix (Design).** "Windows does not allow"
+ a screenshot. The AI correctly framed it as an unsigned-binary reputation problem, laid
out user-side vs build-side options in a cost table, and — on the terse steering reply
`"3"` — scaffolded the `windows-authenticode-signing` OpenSpec change (Azure Trusted
Signing, sign post-`electron:make`, fork-PR dry-run escape). It then honored `"DMG apps
also have to be xattr-s"` by extending the docs to macOS Gatekeeper + the Properties →
Unblock path, and named `macos-notarization` as an explicit out-of-scope follow-up.

**Phase 4 · Automate the footer (Generate).** "Add to release note builder" became
`.github/release-notes-footer.md` (single source of truth) wired into the existing
"Extract release notes from CHANGELOG" step in `publish.yml`, appended after the CHANGELOG
slice *and* after the generated-fallback body. Verified: YAML still parses, the
no-bash-on-windows lint still passes, and an `awk` dry-run against the live CHANGELOG
confirmed the exact next-release body.

**Phase 5 · Commit + push in a jj colocated repo (Ship).** The user pasted the "NEVER use
mutating git" jj policy. The AI recognized it was in the `default` workspace (not a shadow
one), so `jj-workspace-fold-back` didn't apply; it used `jj describe` → `jj bookmark move
develop --to @` → `jj git push --bookmark develop`. It flagged that the earlier
apex-domain fixes had been reverted in the working tree (so they weren't in the commit) and
surfaced 17 unrelated Dependabot alerts.

## 4. Prompts that worked

- **Goal prompt — `"Site have a problem" + screenshot`.** Minimal but effective *because a
  screenshot carries the error text*. A future operator can strengthen it: "The site at
  pi-dashboard.dev serves broken CSS/JS with astro-island errors — find the root cause."
- **`"okay. I deploy will use the latest relese version of artifacts?"`** — a good
  verification prompt: it forced the AI to trace the whole build-time release-resolution
  chain (`github-release.ts` → live API → static cache → fallback) rather than assume.
- **`"3"`** — a high-leverage unlock: after the AI presented numbered options, a single
  digit selected the permanent-fix path and triggered the full OpenSpec scaffold. Terse
  replies work *when the AI has already enumerated the choices*.
- **`"DMG apps also have to be xattr-s. Document that too. And ... unblock"`** — a scope
  expansion that generalized a Windows-only doc into a cross-platform one. Strengthen by
  stating both platforms up front: "document the unsigned-binary unblock for Windows *and*
  macOS."

## 7. Pitfalls & dead ends

- **Hydration errors are a red herring.** `astro-island` failures were *downstream* of
  asset 404s. If you see them, check the `base:` vs custom-domain (`CNAME`) mismatch first.
- **Appending to a release body is not idempotent by default.** Re-running a naive append
  double-stacks the warning. Strip the prior block with `sed '/^### <heading>$/,$d'` before
  re-appending.
- **`jj-workspace-fold-back` only applies to shadow workspaces.** In the `default`
  workspace, advance the bookmark (`jj bookmark move develop --to @`) and `jj git push`.
- **NEVER run mutating `git` in a colocated `.jj`+`.git` repo** (`git commit/rebase/
  cherry-pick/merge/reset --hard/checkout/stash`) — it silently corrupts jj history.
- **Working-tree reverts can silently drop your fix.** The apex-domain asset fixes were
  reverted before commit; always confirm what's staged vs pending before pushing.
- **`shell: bash` on `runs-on: ubuntu-latest` is fine** for the no-bash-on-windows lint —
  the lint only flags bash on Windows runners.
