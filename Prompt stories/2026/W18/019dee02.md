# How we did it: Build a Windows Electron zip — and fix the Windows PATH bugs it exposed — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The opening prompt was terse: *"full build and build windows zip electron bundle (no
others)"*. The real objective, once the session unfolded, was **two-layered**: (a)
produce the Windows Electron zip via the existing build scripts, and (b) — because the
build kept surfacing runtime failures on the target Windows machine (screenshots of
"node not found", `spawn EFTYPE`, `spawn cmd.exe ENOENT`, duplicate installer rows) —
**root-cause and fix the underlying Windows PATH / tool-resolution bugs** so the bundle
actually works when installed. The build was the trigger; the durable value was three
surgical code fixes in `packages/shared` and `packages/server`.

## 2. TL;DR playbook

1. **Discover the build path before touching config.** Ask "is there already a script
   for this?" → `ls packages/electron/scripts/` and `grep -nE "ZIP_ONLY|zip"` the build
   scripts. `docker-make.sh` already supports `ZIP_ONLY=1` — no forge/maker-zip changes
   needed.
2. **Run the correct one-liner:** `ZIP_ONLY=1 bash packages/electron/scripts/build-installer.sh --windows --skip-client`
   (`--skip-client` because `npm run build` already produced `dist/`). Output lands in
   `packages/electron/out/make/zip/x64/`.
3. **If Docker can't pull images**, diagnose macOS keychain, not the build. `security
   list-keychains` failing (error -50 from `docker-credential-osxkeychain`) is a
   system-level TCC/keychain problem the agent **cannot fix from its own security
   session** — hand the exact `ZIP_ONLY=1 …` command to the human to run in their shell.
4. **Treat each screenshot of a Windows failure as a bug report.** Read the failing
   code path (`grep` the tool registry + dependency installer), state a root-cause
   diagnosis, then propose the smallest-scope fix and ask before applying.
5. **Fix 1 — duplicate installer rows:** in `dependency-installer.ts`, give each row its
   own package-name label instead of broadcasting the combined `"Installing pi-coding-agent, tsx"`;
   stop fanning raw npm stdout to every row.
6. **Fix 2 — server has a stripped PATH:** move `ensureWindowsSystemPath()` from
   `packages/electron/` to `packages/shared/src/platform/`, leave a re-export shim in
   electron, and call it from `packages/server/src/cli.ts` at startup (defense-in-depth:
   works whether the server is Electron-spawned or standalone).
7. **Fix 3 — `node` not found → `spawn EFTYPE`:** add a `process.execPath` strategy to
   the `node` tool registration in `tool-registry/definitions.ts` so the strategy chain
   becomes `[override → managed → where → execPath]`. This makes the npm/pi executors
   build `[node.exe, cli.js]` again instead of `[cli.js]`, killing the `EFTYPE` cascade.
8. **After each fix: `npm run build` + targeted `npx vitest run <pkg>`; confirm green,
   note pre-existing unrelated failures, and remind the human to rebuild the zip to test
   on the affected machine.**

## 3. How the collaboration unfolded

**Phase A — Discovery & a wrong first move (reverted).** The AI initially added
`@electron-forge/maker-zip` to `package.json` + `forge.config.ts`. The human pushed back:
*"There is a script for building for electron apps. Why don't you get that info?"* The AI
re-inspected the scripts, found `ZIP_ONLY=1` already does exactly this, and **reverted its
forge changes** (`git checkout -- …`). *Why it worked:* checking existing scripts before
inventing config avoids reinventing a supported path.

**Phase B — The Docker/keychain wall.** The build runs the Windows artifact inside a Linux
Docker container (wine+nsis), but `docker pull` failed with keychain error -50. The AI
correctly localized this to macOS (`security list-keychains` fails *before* Docker is
involved), tried several bypasses (empty `DOCKER_CONFIG`, `credsStore:""`,
`DOCKER_BUILDKIT=0`), and eventually diagnosed a stale `login_renamed_1.keychain-db` from
a corruption-recovery rename. Decisive realization: **the keychain works in the human's
shell but not the agent's security session — a TCC boundary the agent cannot cross.** It
handed the exact build command to the human to run themselves.

**Phase C — Duplicate installer rows.** Human sent a screenshot of duplicate "Installing…"
messages. The AI identified intentional fan-out in `dependency-installer.ts` broadcasting a
combined label to every row, proposed a per-row-label fix, asked "want me to apply?", got
*"yes"*, and applied it.

**Phase D — The Windows runtime bugs (the real payload).** Human sent screenshots of
`node not found`, `spawn cmd.exe ENOENT`, `spawn EFTYPE`, `npm update exited with code 1`.
The AI read `server-lifecycle.ts`, `dependency-installer.ts`, and the tool registry, then
diagnosed **two distinct root causes** across two rounds: (1) the server never called
`ensureWindowsSystemPath()` and the helper lived in electron so the server couldn't import
it → moved it to `shared`, shimmed electron, called it in `cli.ts`; (2) the `node` tool
only resolved via `where`, so the bundled `node.exe` wasn't found and the npm executor fell
back to `[npm-cli.js]` which libuv can't exec → `EFTYPE`. Added a `process.execPath`
strategy. A final follow-up screenshot ("another error") was **the same root cause** (the
headless pi spawn used the same `nodeScriptToArgv` helper) — already fixed, no new code.

## 4. Prompts that worked

- **Goal prompt (weak → stronger):** *"full build and build windows zip electron bundle
  (no others)"* was terse but the `(no others)` scoping was useful. Stronger version for a
  reader: *"Build ONLY the Windows Electron zip using the existing build scripts — check
  `packages/electron/scripts/` for a ZIP-only path before adding any forge config."*
- **The highest-leverage steer:** *"There is a script for building for electron apps. Why
  don't you get that info?"* — one sentence that reverted a wrong abstraction and pointed
  the AI at the supported path. Bake this in as a standing rule (see §5).
- **Screenshot-as-bug-report follow-ups:** *"Interesting Duplicate messages [image]"*,
  *"There is problems with executions [image ×4]"*, *"Better, but still have problems"* —
  each short prompt + screenshot unlocked a full diagnose-and-fix cycle. Effective because
  the AI treated the image as ground truth and read the code before proposing a fix.
- **"yes"** — the one-word unlock after a scoped "want me to apply that fix?" proposal.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session. But the workflow is clearly repeatable and a
skill **should** be created:

- **A `build-windows-electron-zip` project skill** capturing: the `ZIP_ONLY=1 bash
  packages/electron/scripts/build-installer.sh --windows --skip-client` one-liner, the
  output path, the keychain-error-50 → hand-to-human rule, and the "check the script
  before touching forge config" guardrail. It removes the two dead-ends this session hit
  (wrong forge config, keychain bypass looping) and makes the build a one-command action.
- **A memory** that on macOS, `docker-credential-osxkeychain` error -50 is a keychain/TCC
  problem the agent process cannot resolve — the human must run the Docker-dependent
  command in their own shell.

## 7. Pitfalls & dead ends

- **Don't add `@electron-forge/maker-zip`** — `docker-make.sh` already zips the packaged
  `win32-x64/` dir when `ZIP_ONLY=1`. Reverting cost a round-trip.
- **Don't loop on keychain bypasses.** Empty `DOCKER_CONFIG`, `credsStore:""`,
  `DOCKER_BUILDKIT=0`, custom `--config` — none cross the security-session boundary. Once
  `security list-keychains` fails with -50, hand the build command to the human.
- **A `.js`-only executor argv → `spawn EFTYPE`.** If npm/pi spawns fail with `EFTYPE` on
  Windows, check that the `node` tool resolves — the executor must be `[node.exe, cli.js]`,
  not `[cli.js]`. Fix at the registry (`process.execPath` strategy), not per-caller.
- **One helper can feed many call sites.** `nodeScriptToArgv` builds both the npm and pi
  executors; fixing `node` resolution once fixed both. A "still broken" follow-up was the
  same root cause, not a new bug.
- **16 pre-existing test failures** (resolver/git-source/jiti) are unrelated — don't chase
  them; note them and move on.

## 8. Reproduce it faster — checklist

**Inputs to have ready:** working Docker + a *healthy* macOS keychain (`security
list-keychains` returns a list; `echo "https://index.docker.io/v1/" |
docker-credential-osxkeychain get` prints `{}` / "not found", not error -50). `npm run
build` already run so `dist/` exists.

1. [ ] `ls packages/electron/scripts/` and `grep -nE "ZIP_ONLY|zip"` — confirm the
       ZIP-only path exists; do NOT add forge/maker-zip config.
2. [ ] `npm run build` (full build of client/server).
3. [ ] `ZIP_ONLY=1 bash packages/electron/scripts/build-installer.sh --windows --skip-client`
       (hand to the human if Docker keychain is broken).
4. [ ] Zip lands in `packages/electron/out/make/zip/x64/`.
5. [ ] For Windows runtime failures: fix installer labels
       (`dependency-installer.ts`), server PATH
       (`ensureWindowsSystemPath` → `packages/shared/src/platform/`, called in
       `packages/server/src/cli.ts`), and `node` resolution
       (`process.execPath` strategy in `tool-registry/definitions.ts`).
6. [ ] After each fix: `npm run build` + `npx vitest run <pkg>`; rebuild the zip to test
       on the affected machine.
