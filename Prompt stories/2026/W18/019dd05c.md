# How we did it: Chasing "repeating messages" in the dashboard chat — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with a screenshot and one line: **"After page refresh I see the
following:"** — the dashboard chat panel showed ~40 duplicate tool-call rows
(`$ sleep 3 && curl … /api/health`) that appeared out of nowhere on reload. The *real*
objective, which only crystallized after several steering turns, was: **find and fix the
actual cause(s) of chat messages appearing duplicated after a page refresh / server
restart in `packages/client`.** What looked like one bug turned out to be *two distinct*
bugs — a replay-dedup bug for pending `ask_user` prompts, and a grouping bug for
polling-loop tool calls — plus one red herring (a suspected client state-bleed that never
materialized).

## 2. TL;DR playbook

1. **Get the data before theorizing.** Dump the exact WebSocket event stream the server
   is replaying for the suspect session (`toolCallId`, `seq`, `command`) and compare it to
   what the JSONL actually contains. This immediately tells you whether the duplicates are
   *in the data* (server-side) or *invented by the client*.
2. **Split "duplicate messages" into its real sub-bugs** — don't assume one root cause.
   Here: (a) pending `ask_user` cards double after restart, (b) identical bash calls in a
   polling loop don't collapse. They live in different files.
3. **For the replay-dedup bug:** in `collapse-retried-errors.ts`, the pairing helper only
   hid a tool-call card when `toolStatus === "running"`; after replay it's `complete`.
   Drop the `running` precondition so *any* `toolResult` followed by a `pending`
   `interactiveUi` is hidden.
4. **For the polling-loop bug:** in `group-tool-calls.ts`, the grouper broke on the first
   non-`toolResult` row, but the reducer inserts `turnSeparator`/`message_end` rows between
   consecutive tool-only turns. Add a `TRANSPARENT_ROLES` skip-set so grouping walks across
   them.
5. **TDD each fix:** update/replace tests first, run to confirm red, then implement to
   green. Verify with the full suite (stash to prove pre-existing failures aren't yours).
6. **Build + restart + verify the fresh bundle** (`npm run build`, restart, confirm the new
   `index-*.js` hash is served) after each client change.
7. **Update the spec** (`openspec/specs/chat-view/spec.md`) to encode both new invariants,
   then `openspec validate`.
8. **Commit only your files** — this repo runs parallel sessions; `git status` first and
   stage exactly the files you touched, leaving other in-flight work untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / false trail (the hardest hour).** The AI first read the JSONL and
the client reducer, and confidently reported the duplicates were *not in the session data*.
It escalated to a live WebSocket dump of the server's replay for `019dd05c` and confirmed
zero `sleep 3 && curl … /api/health` polling events in that session's stream. Conclusion at
the time: "the screenshot is from a *different* session" or a client state-bleed race. This
was a genuine dead end — the AI could not reproduce or trace a leak from a static read, and
said so honestly rather than inventing a fix. *Why it worked partially:* dumping the actual
event stream is the right instinct; *why it stalled:* the operator was looking at a real bug
the AI hadn't yet isolated, and hard-refresh made the triggering page disappear.

**Phase 2 — Reframe via steering.** Prompt 3 ("In other session after reload the questions
also repeated") redirected the AI onto a *different, cleaner* bug: duplicated interactive
`ask_user` confirm prompts after reload. This one was traceable. The AI found
`state-replay.ts` synthesizes a `tool_execution_end` for orphan tool calls — correct for
crashed `bash`, wrong for a legitimately-pending `ask_user`. The dedup helper only hid the
card while `running`, so post-replay `complete` cards slipped through.

**Phase 3 — Fix #1 (TDD).** Updated tests to assert the corrected behavior, ran red, removed
the `running` precondition in `collapse-retried-errors.ts`, ran green (17 tests), built and
restarted.

**Phase 4 — Fix #2 (the original symptom, now understood).** Prompt 5 ("After reload still
growing message arrives") brought back the polling-loop symptom — but now the AI had the
data lens to read it correctly: the same `curl … | grep -oE` bash call rendered as ~40
cards. The event store had 108 `tool_execution_start` events for ~34 real calls. Root cause:
`groupConsecutiveToolCalls` broke on the `turnSeparator` the reducer inserts between
tool-only turns. Fix: a `TRANSPARENT_ROLES` skip-set + `lastToolEnd` index tracking. TDD
again (5 new tests, 14/14 green), build + restart, confirmed fresh bundle.

**Phase 5 — Spec + commit.** Prompt 6 ("update spec") → rewrote two requirements in
`chat-view/spec.md` and validated. Prompt 7 ("commit changes") → `git status` to separate
own files from parallel-session churn, committed only `group-tool-calls.*` + the spec edit
as `1ce5659` on `develop`, left `AGENTS.md`/`CHANGELOG.md`/`ChatView.tsx` and other
sessions' `openspec/changes/*` untouched. Did not push (in-flight work elsewhere).

## 4. Prompts that worked

- **The goal prompt** (screenshot + "After page refresh I see the following:") was weak on
  its own — a screenshot with no session id, no reproduction steps. It *would* have been
  stronger as: *"In session 019dd05c, after a soft page-refresh, ~40 duplicate
  `sleep 3 && curl` tool cards appear that I only ran once. Dump the server's replay for
  this session and compare to the JSONL before theorizing."*
- **High-leverage follow-up "1 + 2"** (Prompt 4) — a terse unlock that told the AI to pursue
  *both* candidate fixes it had proposed, not pick one. Short prompts like this work when the
  AI has already laid out an enumerated menu.
- **"In other session after reload the questions also repeated"** (Prompt 3) — the single
  most valuable steer: it broadened scope from one session to a *class* of bug and handed the
  AI a cleaner, traceable instance to crack first.
- **"update spec" / "commit changes"** — minimal terminal prompts that worked because the
  repo's conventions (openspec spec location, commit-only-your-files discipline) were already
  known to the AI.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session — but two are clearly warranted:

- **"WebSocket replay dump" diagnostic** — a small script that connects to
  `ws://127.0.0.1:8000/ws`, subscribes to a session id, and prints every replayed event
  (`seq`, `toolCallId`, `command`). *Why effective:* it settles "is this duplicate in the
  data or invented by the client?" in seconds and prevents the exact hour-long dead end this
  session hit. (Note the auth quirk: use `127.0.0.1`, not `localhost`, and the path is `/ws`,
  not `/ws/browser`.) Worth saving as a project skill.
- **"Duplicate chat rows after reload → two known causes" memory** — capture the two root
  causes (orphan `ask_user` replay in `state-replay.ts`; `turnSeparator` breaking
  `groupConsecutiveToolCalls`) so the next report of "repeating messages" starts from the
  answer instead of the dead end.

## 7. Pitfalls & dead ends

- **Don't conclude "different session / unreproducible" from a clean data dump alone.** The
  data *was* clean for the polling-loop events at the point checked, yet the bug was real —
  the duplication was in how the client *grouped* rows, not in the event payloads. If data
  looks clean but the user sees duplicates, suspect *rendering/grouping*, not just the wire.
- **Hard-refresh (Cmd+Shift+R) can hide the very bug you're chasing** by clearing the state
  that triggered it — capture the diagnostic *before* asking the user to hard-refresh.
- **`bash_output` events are memory-only, never in JSONL**, and `state-replay.ts` doesn't
  synthesize them — so grepping the JSONL for them is a false negative. Know which events are
  persisted vs replay-only before drawing conclusions.
- **The WS auth/path quirk:** `localhost` failed; `127.0.0.1` (loopback bypass) worked, and
  the endpoint is `/ws` not `/ws/browser`. Several failed `ws-dump.cjs` attempts came from
  guessing this wrong.
- **Parallel sessions dirty the tree.** `AGENTS.md`, `CHANGELOG.md`, `ChatView.tsx`, and
  several `openspec/changes/*` belonged to other in-flight sessions — committing them would
  have tangled unrelated work. Always scope the commit.

## 8. Reproduce it faster — checklist

`node_modules/ws` available; a soft-refresh repro (don't hard-refresh yet).

1. Dump the server's WS replay for the session (`127.0.0.1:8000/ws`, subscribe, print
   `seq`/`toolCallId`/`command`); compare counts to the JSONL.
2. If duplicates aren't in the payloads → suspect **grouping/rendering**, not the wire.
3. Pending `ask_user` doubles after restart → fix `collapse-retried-errors.ts`: drop the
   `toolStatus === "running"` precondition in `findActiveInteractiveToolResultIds`.
4. Identical bash calls in a loop don't collapse → fix `group-tool-calls.ts`: add
   `TRANSPARENT_ROLES` (`assistant`, `thinking`, `turnSeparator`, `rawEvent`,
   `commandFeedback`) skip-set + `lastToolEnd` tracking.
5. TDD each: tests red → implement → green; run full suite (stash to prove pre-existing
   failures aren't yours).
6. `npm run build` + restart; confirm the served `index-*.js` hash is fresh.
7. Update `openspec/specs/chat-view/spec.md` (both invariants) → `openspec validate`.
8. `git status`; stage only your files; commit; don't push if others are in-flight.
