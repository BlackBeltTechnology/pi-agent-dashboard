# How we did it: fix streaming-text vs interactive-UI render order — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** ("Enter explore mode. Think deeply. Visualize
freely… you must NEVER write code"). The real objective surfaced from a UI bug: in the
dashboard chat, when an assistant turn ships `[thinking?, text, toolCall]` in one
message, the **tool card / prompt dialog renders *above* the assistant's describing
prose** — and the gap between "tool starts" and "message_end commits the text" scales
with tool runtime (a 4-minute `npm test` leaves the card mis-ordered for 4 minutes).
The goal became: confirm an existing OpenSpec change (`fix-streaming-text-vs-interactive-ui-order`)
actually covered the full root cause, widen it where it under-billed scope, then
implement, verify, and archive the fix.

## 2. TL;DR playbook

1. **Start in explore mode** to investigate the ordering bug without touching code —
   read `event-reducer.ts`, `ChatView.tsx`, `bridge.ts`; map the event timeline.
2. **Ask whether an existing change already covers it**: *"Maybe `<change>` is
   addressing the same problem. Check it is handling everything."* — forces a
   coverage audit instead of a fresh proposal.
3. **Have the AI widen the proposal** where it under-bills scope — here: long-running
   bash (not just `ask_user`), `[thinking, text, toolCall]` shape, `setTimeout(0)`
   send-defer mechanics. Update `proposal.md` + `tasks.md` + `design.md` together.
4. **Demand a risk register**: *"What risks presented?"* → R1–R7 with likelihood ×
   impact, each mitigation citing a task ID; fold audits/decisions into a new §11.
5. **Apply the change** (`/opsx:apply`): pure helper + reducer wiring + entryId
   stamping at `message_end`, then the reducer + DOM (ChatView) test files.
6. **Run the FULL suite the project way** — `npm test`, not a hand-rolled
   `HOME=$(mktemp -d) vitest` (that misses localstorage setup and fake-fails).
7. **Verify** (`/opsx:verify`): map every spec scenario → code + test; catch the
   spec-sync gap where a *extended* requirement scenario was missed.
8. **Archive** (`/opsx:archive`) + sync delta spec into main spec, then **commit
   selectively**, disclosing any foreign in-flight lines you had to keep.

## 3. How the collaboration unfolded

**Phase 1 — Explore & root-cause (2h).** The AI stayed read-only, grepped the reducer
for `reorderToolCardsForAssistantMessage` / `message_end` / `tool_execution_*`, and
built ASCII timeline diagrams proving the mis-order is *structural* (the `message_end`
that commits streaming text is gated behind tool runtime), not a reorder-helper bug.
*Why it worked:* refusing to theorize until the architecture was mapped produced a
diagram the human could validate against the screenshot.

**Phase 2 — Coverage audit & scope widening.** Prompted to check the existing change,
the AI confirmed the mechanism was right but the *narrative under-billed scope* and the
test plan had a blind spot. It widened `proposal.md`/`tasks.md`/`design.md` to cover
long-running bash and the `[thinking, text, toolCall]` shape, then re-ran
`openspec validate`. *Decision point:* human said "add the missing parts" → AI edited
all three artifacts coherently rather than just the proposal.

**Phase 3 — Risk register.** "What risks presented?" produced R1–R7 (e.g. R1: flushed
row lacks `entryId` for the whole tool window → fork button silently disabled). Each
risk got a mitigation site as a task ID; a new §11 captured pre-merge audits/decisions,
mirrored into `design.md` as open questions.

**Phase 4 — Implement.** `/opsx:apply`: pure helper + reducer arms + entryId stamping
at both `message_start` and `message_end`, then a 31-test reducer file and 3 DOM-level
ChatView tests. *All 4014 tests pass, zero regressions.*

**Phase 5 — Verify, archive, commit.** `/opsx:verify` mapped 12 scenarios → code/tests
and caught a spec-sync gap (an *extended* requirement scenario missed by task 7.1),
fixed inline. `/opsx:archive` moved the change and synced the delta spec. Final commit
`070ddef` staged selectively and **disclosed** 2 import lines belonging to another
in-flight change (`extract-flows-as-plugin`) that couldn't be reverted without breaking
the build.

## 4. Prompts that worked

- **Goal prompt (explore mode):** effective because it *forbade implementation* — the
  AI mapped the whole event pipeline and drew timelines before proposing anything.
- **"Check it is handling everything"** — high leverage: turned a vague suspicion into a
  structured coverage audit of an existing change.
- **"Add the missing parts"** — unlocked coherent multi-file edits (proposal + tasks +
  design in one pass) instead of a partial patch.
- **"What risks presented?"** — forced a grounded R1–R7 register tied to task IDs, not
  generic worry. Reusable pattern: *always ask for a risk table before applying.*
- **"yes" / "mark all tasks"** — short unlocks that advanced multi-step work once the
  plan was trusted.

Weak-prompt rewrite: instead of *"Add to that given proposal the missing parts"*, say
*"Widen proposal.md, tasks.md and design.md together to cover long-running bash and the
`[thinking,text,toolCall]` shape; re-run `openspec validate`."*

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were created this session — the work rode the existing
**OpenSpec `/opsx:apply` → `/opsx:verify` → `/opsx:archive`** command chain. That chain
is the reusable asset: it enforces task tracking, requirement-to-test mapping, spec
sync, and archival in a repeatable loop. *When to invoke:* any change with a tasks.md.

Recommendation for a future skill: a **"coverage-audit an existing OpenSpec change"**
procedure — grep the delta specs, diff scope against the live repro, and emit the
under-billed dimensions before deciding to apply. This session did it by hand; it
repeats often enough to codify.

## 7. Pitfalls & dead ends

- **`HOME=$(mktemp -d) npx vitest`** produced spurious `draft-storage.test.ts` failures
  (missing `window.localStorage.clear`). *Fix:* run `npm test` — the project's runner
  sets up the localstorage file; the "failures" vanish.
- **`openspec instructions apply … | python3 -c "…"`** failed once on JSON shape. *Fix:*
  read `d['progress']` (`complete`/`total`) rather than iterating a task list that may
  differ by schema.
- **Spec-sync gap:** task 7.1 appended the new requirement but missed an *extension*
  scenario on an existing requirement. *Fix:* `/opsx:verify` catches it — always run it
  before archive; diff `#### Scenario:` lines between delta and main spec.
- **Foreign in-flight lines:** 2 imports in `event-reducer.ts` belonged to
  `extract-flows-as-plugin` and couldn't be reverted (their source files were gone
  locally). *Fix:* stage selectively and **disclose** them in the commit body.
