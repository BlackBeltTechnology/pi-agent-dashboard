# How we did it: Removing the App.tsx flow-command interceptors — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened in **explore mode** — a deliberate "think, don't implement" stance:

> *"Enter explore mode. Think deeply. Visualize freely… You may read files, search code,
> and investigate the codebase, but you must NEVER write code or implement features…
> You MAY create OpenSpec artifacts."*

The concrete objective only sharpened after the first steering turn: **delete the
`/flows` and `/flows:new` slash-command interceptors that live in the dashboard's
`App.tsx`, and rely entirely on the extension-provided commands (pi-flows) as the single
source of truth** — so autocomplete and runtime behavior can never drift apart. The
accepted cost: pi-flows becomes a *mandatory* dependency for flow features. The real
deliverable was never code — it was a **validated OpenSpec change proposal** capturing
that deletion, ready to apply once explore mode is exited.

## 2. TL;DR playbook

1. **Open in explore mode** and state the constraint out loud: *thinking + OpenSpec
   artifacts only, no implementation.*
2. **Map the surface first.** `grep`/`rg` for the command strings (`/flows`, `/flows:new`,
   `flowPickerOpen`, `setFlowNewOpen`, `BUILTIN_SLASH_COMMANDS`) across `packages/client/`
   to find every interceptor, state hook, and JSX dialog gated on them.
3. **Verify the "other side" before proposing.** Read the pi-flows extension source
   (`~/.pi/agent/git/.../pi-flows`) to confirm which commands it actually registers and
   that its handlers stand alone (`ctx.ui.*` → PromptBus → DashboardDefaultAdapter).
4. **Ask the scoping questions** (full removal vs. partial? keep the collision guard?
   what to do with the stale Plano plan doc?) via `ask_user` — don't guess.
5. **Scaffold the OpenSpec change** with `openspec change new`, write `proposal.md` +
   `specs/…/spec.md` (+ `tasks.md`), and **`openspec validate <name> --strict`** until clean.
6. **Let the answers simplify the scope.** When "pi-flows is fully self-contained" is
   confirmed, drop `design.md` — pure deletion needs no design rationale.
7. **Stage surgically** (`git add openspec/changes/<name>/` only — the tree had unrelated
   WIP) and commit with an `openspec(propose):` message.
8. **Hand off** the apply path (`openspec show <name>` → apply skill) for after explore mode.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / de-confusing the screen.** The operator pasted a command-palette
screenshot. The AI's first win was recognizing it was *not* the live palette — it came
from `docs/plans/plano-pi-integration.md`, a forward-looking (partly aspirational) plan.
It drew an ASCII table mapping *what you type → where it comes from today* (`App.tsx`
interceptor vs. extension cmd vs. `BUILTIN_COMMANDS` vs. unimplemented Plano idea). That
single diagram dissolved the confusion before any change was scoped.

**Phase 2 — Locate every interceptor.** `grep`/`rg` across `packages/client/src/` surfaced
that "remove the interceptors" actually touches **three** categories, not one:
`wrappedHandleSend` string matches, the `BUILTIN_SLASH_COMMANDS` collision guard, and
~7 state hooks + their JSX dialogs (`flowPickerOpen`, `flowNewOpen`, `flowEditPickerOpen`,
`flowDeletePickerOpen`, …). Enumerating the real blast radius up front is what kept the
proposal honest.

**Phase 3 — Verify the extension can stand alone.** Rather than assume, the AI opened the
pi-flows repo and confirmed it registers all five commands (`flows`, `flows:new`,
`flows:edit`, `flows:delete`, `roles`) and that every handler routes through `ctx.ui.*` →
PromptBus → `DashboardDefaultAdapter` for dashboard sessions. It also noticed a nuance
worth surfacing: the interceptors weren't pure duplication — they swapped in *richer*
dashboard dialogs. That nuance became an explicit decision point instead of a silent
regression.

**Phase 4 — Scope via questions, then simplify.** The AI drafted a first, heavier proposal
(`decouple-flow-commands-from-app-shell`: new command-modal slot, 9 phases, ~30 tasks,
plus a `design.md`). The operator's terse answers — **Q1=A (full removal), Q3=keep the
collision guard, Q4=just delete the file** — collapsed the scope. The AI **deleted the v1
change** (`rm -rf`) and re-drafted the leaner `remove-flow-dialog-interceptors`
(7 phases, no new slot, no design.md). Confirming `SessionFlowActions` already owns a rich
picker via the `session-card-action-bar` slot proved users lose nothing.

**Phase 5 — Validate, commit, hand off.** `openspec validate … --strict` gated every draft.
The final commit `0ba2ed4` staged **only** the new proposal directory, deliberately
leaving unrelated in-tree WIP untouched, and closed with the apply instructions.

## 4. Prompts that worked

- **The goal prompt (explore-mode preamble).** Effective because it set an unambiguous
  *stance*: read/search/investigate freely, create OpenSpec artifacts, but never
  implement. That single guardrail kept the whole 3-day session producing a *proposal*
  instead of half-finished code.
- **High-leverage follow-up: `Q1: A / Q2: a / Q3: keep / Q4: just delete`.** Four
  characters per answer collapsed an over-engineered v1 proposal into a pure-deletion v2.
  Terse, decisive answers to well-formed questions are the fastest way to steer scope.
- **`commit`** — a one-word unlock that trusted the AI to stage surgically and write the
  message; it worked because the AI had already announced it would stage *only* the
  proposal dir.
- **Rewrite of the weak first steering prompt.** The original —
  *"remove the App.tsx interceptors and rely entirely on extension-provided commands …
  and re,pve plano"* (typo-laden) — would be stronger as: *"Draft an OpenSpec proposal to
  delete the `/flows` and `/flows:new` interceptors in App.tsx so pi-flows is the single
  source of truth for flow commands. Verify pi-flows registers those commands standalone
  first. Also remove the stale Plano integration plan doc. Keep `BUILTIN_SLASH_COMMANDS`."*

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. But the workflow is textbook-repeatable
and the repo *already ships* the right skills for it:

- **`openspec-new-change` / `openspec-explore`** — the explore-mode-then-propose loop used
  here. Invoke when a request is "delete/refactor X" but you're forbidden (or unwilling)
  to implement yet; it captures the thinking as a validatable artifact.
- **`plan-proposal`** — the scaffold → doubt-review → scenario-fold orchestrator; worth
  running for a proposal like this to force the scoping questions earlier.

If anything deserved a memory, it's the **project fact** that pi-flows commands
(`flows`, `flows:new`, `flows:edit`, `flows:delete`, `roles`) route through
`ctx.ui.*` → PromptBus → `DashboardDefaultAdapter` and are self-contained — the exact
finding that made this a pure-deletion change. Save it so the next flow-command decision
skips the re-verification.

## 7. Pitfalls & dead ends

- **Don't skip verifying the extension side.** Deleting the interceptors *without* first
  confirming pi-flows registers the same commands standalone would ship a change that
  breaks flows for everyone until pi-flows updates. Always read the extension source.
- **The v1 proposal was a dead end.** The AI drafted `decouple-flow-commands-from-app-shell`
  (new slot type, design.md, ~30 tasks), then `rm -rf`'d it once the answers landed. Lesson:
  ask the scoping questions *before* the heavy draft, not after.
- **Grep the narrow file, not the whole repo, for command strings.** One `grep` failed
  (`Toggle auto-routing|Manage flows` across `packages/`) because those strings only exist
  in a plan doc — re-scoping with `--include` and the right paths fixed it.
- **Watch the dirty tree.** The working tree had unrelated WIP (extract-flows-as-plugin
  diffs, deleted components). Stage explicitly (`git add openspec/changes/<name>/`) so the
  commit contains only the proposal.
- **`openspec validate --strict` is the gate.** Every draft was re-validated until clean;
  treat a non-strict pass as incomplete.
