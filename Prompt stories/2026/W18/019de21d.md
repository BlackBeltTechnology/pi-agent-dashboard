# How we did it: Adding four dark/light dashboard themes — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with: *"Is it possible to search web for more palettes and adapt them? Palettes have to support dark/light themes"*. The real objective, once the one-letter approval turn ("a") confirmed it, was concrete rather than exploratory: **extend the dashboard theme gallery with well-known editor palettes, each shipping a proper dark AND light variant plus a paired code-syntax style, without touching any UI wiring.** The session shipped four new themes — Tokyo Night, Rosé Pine, Solarized, Gruvbox — bumping the gallery from 5 to 9, then updated the spec and committed only the theme-related files.

## 2. TL;DR playbook

1. Ask the AI to explain how the current theme system works and where a new palette plugs in (`packages/client/src/lib/themes.ts`, `syntax-theme.ts`).
2. Have it survey **source palettes that already publish official light + dark variants** (Solarized, Gruvbox, Tokyo Night, Rosé Pine) — those are drop-in; dark-only palettes need hand-tuned light counterparts.
3. Confirm the shortlist ("a" / "go") and let it append entries to `THEMES[]` — one map of the 25 `CSS_VAR_KEYS` for dark, one for light, plus a Prism style pointer.
4. Point new palettes at the closest existing `react-syntax-highlighter` prism style (list `node_modules/react-syntax-highlighter/dist/esm/styles/prism/` to pick).
5. Extend the syntax-theme test's hard-coded theme list so the token-background-strip invariant covers the new palettes.
6. Run the suite with the project wrapper (`HOME=$(mktemp -d) npx vitest run …` or `npm test`) — the isolated HOME dodges a pre-existing test-infra issue.
7. Say "update specs" → have it edit `openspec/specs/theme-gallery/spec.md` (bump the count, list the new themes, pin the syntax mappings).
8. Say "commit changes" → stage **only** the theme files, commit with a `feat(client):` message, leave unrelated working-tree changes untouched.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (how do themes work here).** The AL grepped for existing palette names (`dracula|nord|catppuccin`), read `themes.ts` and `syntax-theme.ts`, and reported the architecture back: each theme is just two flat maps of 25 CSS variables plus a Prism-style pointer, and `ThemePicker` auto-iterates `THEMES[]` so no UI change is ever needed. *Why it worked:* establishing "adding a palette = appending one array entry" up front set a tight, low-risk scope.

**Phase 2 — Source survey & decision.** The AI proposed a tiered list: Tier 1 palettes with official light+dark variants (drop-in), Tier 2 dark-only palettes needing a hand-tuned light counterpart. The human's one-character "a" approved proceeding with the four Tier-1 picks. *Decision point:* choosing official-variant palettes minimized the guesswork of inventing a light scheme.

**Phase 3 — Generate.** It appended ~220 lines (4 dark/light pairs + 4 registry entries) to `themes.ts`, imported 5 new prism styles in `syntax-theme.ts`, and extended the syntax-theme test list. It darkened light-mode accents from their dark counterparts to stay readable on light backgrounds — the known contrast trap.

**Phase 4 — Verify.** First test run hit a pre-existing infra issue; the AI re-ran with the project's wrapper (`HOME=$(mktemp -d)`), and all 3961 tests passed.

**Phase 5 — Spec + commit.** On "update specs" it edited the theme-gallery spec (count 5→9, listed new themes, pinned the dual-mode syntax mappings). On "commit changes" it staged exactly the 4 theme files and committed `23f69de` on `develop` (+346/−3), deliberately leaving unrelated uncommitted work alone.

## 4. Prompts that worked

- **The goal prompt** — *"Is it possible to search web for more palettes and adapt them? Palettes have to support dark/light themes"*. Effective because it named the hard constraint (dark **and** light) up front, which steered the AI straight to official-variant palettes instead of dark-only ones. A stronger version: *"Add 3–4 well-known editor palettes with official light+dark variants to the theme gallery; each needs a paired Prism syntax style and must pass the existing tests."*
- **"a"** — a one-character approval that unblocked the whole build. High leverage precisely because the AI had already laid out a concrete shortlist to approve.
- **"update specs"** — short, and enough because the spec location (`openspec/specs/theme-gallery/spec.md`) was unambiguous from context.
- **"commit changes"** — trusted the AI to scope the commit; it correctly staged only theme files.

## 7. Pitfalls & dead ends

- **Test-infra failure on the first run.** A bare `npx vitest run` tripped a pre-existing HOME-related infra issue. *If you hit it, do:* re-run with `HOME=$(mktemp -d) npx vitest run …` (or `npm test`, the project wrapper).
- **Spec validation "error" that isn't yours.** `openspec validate theme-gallery` reports a `## Purpose` / `## Requirements` header issue because the file is delta-style (`## ADDED Requirements`). It predates the edit — confirm with `git stash && openspec validate … && git stash pop` before chasing it.
- **Light-mode contrast trap.** Reusing a palette's dark-mode accents on a light background is unreadable. Darken accents for the light variant (as was already done for Dracula).

6. Stage ONLY the theme files; commit `feat(client): …`.
7. `npm run build && curl -X POST http://localhost:8000/api/restart` to see them in the palette dropdown.
