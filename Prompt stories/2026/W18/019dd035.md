# How we did it: turning an empty mDNS scan into a self-diagnosing, manual-add UI — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator opened with a bug report, not a feature request:

> "I'm running dashboard server on a macbook in the same network in 192.168.16.202, but scan is not show"

The literal ask was "my Network Discovery scan finds nothing." The *real* objective —
which emerged as the session unfolded — was two-layered: **first diagnose why mDNS
scans come back empty on a normal home LAN, then turn that dead-end into a recoverable
UX.** The finished result was not a bug fix at all but a product change: a diagnostic
empty-state that explains the common mDNS failure modes, plus an inline manual-add form
so a user can bypass discovery entirely by pasting `host:port`. It shipped end-to-end —
code + tests + build + deploy + an OpenSpec change created, validated, and archived.

## 2. TL;DR playbook

1. **State the symptom with the concrete address** ("scan is empty, server is at 192.168.16.202"). The AI immediately framed mDNS-across-machines as environmental, not a code bug.
2. **Let the AI enumerate root causes first** (AP/client isolation, mesh routers, VLANs, VPN, macOS firewall) and hand you `curl /api/health` + `dns-sd -B _pi-dashboard._tcp .` probes to confirm "network, not app."
3. **Approve the pivot from "debug my network" to "make the empty state recoverable"** — a one-word "yes" unlocked the whole build.
4. **Build test-first**: a pure `parseHostInput()` helper (URL / `host:port` / bare host / bracketed IPv6) with a 12-case unit test, then wire the component to it.
5. **Enhance `NetworkDiscoverySection`**: surface scan errors instead of swallowing them, show the diagnostic block on 0 results, add the inline manual-add form with dedupe warning.
6. **"build and deploy"** → `npm run build` → `POST /api/restart` → `npm run reload` (client + server + bridge, the 3-component matrix).
7. **"Update specs and commit"** → create the OpenSpec change (`proposal` + `tasks` + delta spec on `known-servers`), update AGENTS.md, commit as one feature.
8. **Fast-forward + archive the change** → `openspec change new` / `validate` / archive folds the delta into the main `known-servers` spec.

## 3. How the collaboration unfolded

**Phase 1 · Diagnosis (no code).** From the very first prompt the AI resisted the
temptation to grep the mDNS source for a bug. It correctly classified an empty
cross-machine scan as an *environmental* multicast problem and produced a triage
sheet: five common failure modes and two shell probes (`curl /api/health` to prove the
server is reachable, `dns-sd -B _pi-dashboard._tcp .` to prove mDNS is or isn't
resolving). **Why it worked:** separating "is the server up?" from "is multicast
crossing the network?" is the fastest way to stop chasing a non-bug.

**Phase 2 · The pivot (`yes`).** The AI proposed converting the dead-end into a
product improvement rather than "fix your router." A single "yes" from the operator
authorized a three-part plan: a pure `parseHostInput()` helper, a diagnostic +
manual-add enhancement to `NetworkDiscoverySection`, and a `quickProbe()` reachability
check. **Decision point:** the human chose recoverable UX over a network-config
support thread.

**Phase 3 · Test-first build.** The AI wrote the `parse-host-input.test.ts` suite
(12 cases: URLs, `host:port`, bare hostname, bracketed IPv6, and the rejects — bare
IPv6, invalid ports, empty strings) *before* the implementation, ran it green, then
built the component. It kept the parser **pure** (returns `null` on bad input) so all
the edge logic lived in a unit-tested function, not in React. Type-check + broader
client suite + `npm run build` all clean.

**Phase 4 · Deploy (`build and deploy`).** Executed the full 3-component restart
matrix: `npm run build` (client), `POST /api/restart` (server, verified new PID +
`mode: production` via `/api/health`), `npm run reload` (bridge across live pi
sessions).

**Phase 5 · Spec + commit (`Update specs and commit`).** Created the OpenSpec change
`diagnose-empty-mdns-scan` (proposal, tasks, delta spec on `known-servers`), validated
it clean, updated the AGENTS.md key-files table for the two new client files, and
committed all seven files as one coherent `feat(network-discovery)` commit (`bca5b66`).

**Phase 6 · Fast-forward + archive.** Later prompts (pasted `/opsx:ff` and
`/opsx:archive` command bodies) drove the AI to confirm the change was already
apply-ready (all tasks `[x]`, `applyRequires: ["tasks"]` satisfied), then archive it —
folding +2 ADDED requirements and +3 scenarios into the main `known-servers` spec
(`7e5da4f`). A final "commit changes" swept in an unrelated ChatView scroll-race fix
(`d3d68b5`).

## 4. Prompts that worked

- **The goal prompt** — *"scan is not show … server at 192.168.16.202"*. Effective
  because it carried the **concrete reproduction address**. That let the AI hand back
  runnable `curl`/`dns-sd` probes instead of generic advice. A stronger version states
  the environment too: *"Both Macs on the same Wi-Fi; scan finds nothing; is this the
  app or my network?"* — which pre-empts the diagnosis.
- **`yes`** — the single highest-leverage token in the session. It approved the
  scope pivot (bug → product change) and the full three-part build plan in one shot.
  This only works because the AI had *already laid out an explicit, numbered plan* to
  say yes to. Lesson: make the AI propose a concrete plan, then unlock it with one word.
- **`build and deploy`** — trusted the AI to run the whole 3-component matrix without
  re-listing the steps. Works when the deploy procedure is already project-documented.
- **`Update specs and commit`** — folded documentation + version-control into one
  instruction; the AI knew to create the OpenSpec artifacts *and* the AGENTS.md row *and*
  a single semantic commit.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Treat the empty scan as a possible app bug worth grepping | Give the concrete server IP so the AI classified it as environmental | Open with "same LAN, server at X:port, is this app or network?" |
| Wait for approval before building the recoverable-UX pivot | Answer "yes" to the numbered plan | Say up front "if it's environmental, add a diagnostic empty-state + manual-add" |
| Stop after code | "build and deploy" | Name the deploy expectation ("ship it via the 3-component matrix") in the same breath as the build ask |
| Leave the change undocumented | "Update specs and commit" | Ask for the OpenSpec change + AGENTS.md row as part of the feature, not a follow-up |
| `git add -A openspec/` swept 3 unrelated draft change folders into the archive commit | The AI flagged it after the fact and offered to amend | Stage explicit paths, never `-A`, when the working tree has unrelated untracked openspec drafts |

The recurring theme: the operator steered with **very short prompts** ("yes", "build
and deploy", "commit changes") that only landed because the AI had already produced an
explicit plan or knew the project's ritual. The guardrail is to make the AI *state the
plan first*, then approve tersely.

## 6. Skills, tools & memory created — and why they're effective

No pi skill or memory was created in this session, but the workflow is **clearly
repeatable** and two reusable assets were produced in-code:

- **`parseHostInput()` (pure helper + 12-case test).** Captures all the host-string
  parsing edge logic (URL, `host:port`, bare host, bracketed IPv6, and the rejects) in
  one tested function. Effective because it removes the temptation to scatter regex/URL
  logic through the React component; the manual-add form just calls it and trusts
  `null` = invalid. Invoke this pattern any time UI accepts a free-form address.
- **The OpenSpec change `diagnose-empty-mdns-scan`.** Turns a one-off UX fix into a
  spec'd, archived requirement on `known-servers` (+2 requirements, +3 scenarios). This
  is the reproducible artifact — future work on Network Discovery inherits the
  documented behavior.

**Recommended skill to create:** a `diagnose-empty-network-scan` playbook capturing the
"empty cross-machine scan = classify environmental first (AP isolation / mesh / VLAN /
VPN / firewall), probe with `curl /api/health` + `dns-sd -B _pi-dashboard._tcp .`, then
offer manual-add as the recoverable path" sequence — it would collapse Phase 1 to a
single reference.

## 7. Pitfalls & dead ends

- **`git add -A openspec/` is dangerous with untracked drafts.** The archive step
  swept three unrelated draft change folders (`fix-chat-scroll-race-during-replay`,
  `fix-openspec-flag-rename-bug`, `split-browse-flags`) into the commit. → Stage
  explicit paths when other openspec work-in-progress sits untracked in the tree.
- **A `grep -c` validation command failed** (exit 1) mid-session — a brittle inline
  check against spec files. → Prefer `openspec validate` / `openspec spec validate` over
  hand-rolled greps for spec conformance.
- **The spec validator flagged a pre-existing project-wide formatting issue**
  (177/208 specs fail the same check). → Don't chase it; confirm *your* delta merged
  cleanly and proceed. Note it, don't fix it.
- **Vitest needed a clean HOME** in one rerun (`HOME=$(mktemp -d) npx vitest run …`) to
  avoid a config-pollution failure. → If a client test fails oddly, retry with an
  isolated HOME before assuming a real regression.
- **The optional `design.md` artifact was never created** — non-blocking (not in
  `applyRequires`), so archive proceeded with a warning. → Fine to skip; only add it
  when you want design-decision history.
