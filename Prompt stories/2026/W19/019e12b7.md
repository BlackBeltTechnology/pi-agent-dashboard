# How we did it: Fixing vitest 4 + fastify 5 type errors in CI — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user pasted a wall of CI TypeScript errors and said, in effect: *"Run tests as
in CI to catch problems"* — then dropped the raw `tsc` output. The failures were
concentrated in test files (`server-launcher-launch.test.ts`, the shared
`server-launcher.test.ts`, and a honcho-plugin e2e fixture) and were all
type-level: `TS2493` (empty tuple has no element at index 0), `TS2339` (property
does not exist on `never`), `TS2345` (string not assignable to number), and a
`TS2322` fastify `inject` overload mismatch.

The *real* objective, once the steering clarified it: make CI-level typechecking
pass **without changing any runtime behaviour** — these were a vitest 4 + fastify 5
upgrade fallout where mock typings and overload resolution tightened, and the fix
had to stay purely type-level.

## 2. TL;DR playbook

1. **Reproduce CI locally, not just `npm test`.** Read `.github/workflows/ci.yml`
   to learn what CI actually runs (`npm run lint` / typecheck), then run that exact
   command — the runtime tests were already green; the failures were typecheck-only.
2. **Group errors by root cause, not by file.** All of them traced to two library
   upgrades: vitest 4 tightened `vi.fn()` mock typing (`mock.calls[N]` lost its
   tuple), and fastify 5 added an overload to `inject` that unioned into the awaited
   result.
3. **Type the mocks explicitly.** Replace bare `vi.fn(impl)` with
   `vi.fn<typeof realFn>(impl)` (or wrap in `spawnSpy`/`probeSpy` helpers typed via
   `typeof spawnNodeScript`) so `mock.calls[0]` keeps its parameter tuple.
4. **Disambiguate the fastify overload with a cast.** Cast the awaited result to
   `LightMyRequestResponse` and the payload to `InjectPayload` so TS stops unioning
   the no-arg `Chain` overload into the result.
5. **Fix the `EarlyExitError` construction** — replace the bogus string-arg
   construction with a typed cast that preserves the explicit `err.code = 17`
   assignment (the mocked class has a field initializer that would overwrite a
   constructor arg).
6. **Run lint + the specific test file** until both are clean. Use
   `HOME=$(mktemp -d)` when a test touches `~/.pi` state.
7. **Audit that every diff hunk is type-only** before committing — new
   `import type`, generic annotations, and `as` casts all erase to identical JS.
8. **Commit** with a message that names the two library upgrades as the cause.

## 3. How the collaboration unfolded

**Discovery → reproduce CI.** The AI first grepped the source (`server-launcher.ts`,
`node-spawn.ts`) to understand the real signatures behind the mocks, checked the
vitest and fastify versions in the `package.json` files, then read
`.github/workflows/ci.yml` to learn the *exact* CI command. This was the key move:
`npm test` alone passed, so the failure only surfaced under the typecheck/lint step
CI runs. Grounding in CI's real command avoided chasing a non-reproducing bug.

**Fix → type the mocks.** With the versions known (vitest 4, fastify 5), the AI
recognized the errors as upgrade fallout and applied targeted type-level fixes:
explicit generics on `vi.fn`, `spawnSpy`/`probeSpy` helper wrappers, and overload
disambiguation casts. Five edits across three files, re-running `npm run lint` after
each cluster.

**Verify → prove runtime-safety.** After the human's steering (*"Check this can be
effect the current runtime code not only tests"*), the AI produced a hunk-by-hunk
audit showing every change was type-only — `import type`, erased generics, erased
casts — including the one behaviour-adjacent case (`EarlyExitError` constructor
arg) which it proved equivalent because `code` is set explicitly on the next line.

**Commit.** On the human's *"commit changes"*, committed as `89f1ca25` on
`develop` with a message naming vitest 4 + fastify 5 as the root cause.

## 7. Pitfalls & dead ends

- **`npm test` green ≠ CI green.** Runtime tests passed the whole time; the failure
  lived in the typecheck/lint step. If tests pass but CI is red, read the workflow
  and run *its* command.
- **A test needing `~/.pi` state fails under a stale HOME.** The AI re-ran the
  extension test with `HOME=$(mktemp -d)` to get a clean run — do this when a launcher
  test probes real home-dir state.
- **`vi.fn(impl)` silently loses its call-args tuple under vitest 4.** `mock.calls[0]`
  becomes `never`/empty-tuple. Always annotate `vi.fn<typeof realFn>`.
- **fastify 5's `inject` no-arg `Chain` overload unions into the awaited result.**
  Cast the result to `LightMyRequestResponse` and payload to `InjectPayload`.
- **A field initializer on a mocked error class overwrites constructor args.** Don't
  pass the arg; set the field (`err.code = 17`) explicitly on the next line.
