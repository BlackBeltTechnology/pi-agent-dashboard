# How we did it: Lifecycle icons on linked-session pills — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The user opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation one — to reason about a small UI gap in the dashboard sidebar. In the
`FolderOpenSpecSection`, each OpenSpec proposal lists its attached sessions as compact
blue pills. Those pills were "jump only": clicking navigated to the session, but there
was **no way to hide/unhide, resume, or fork a linked session without first jumping
into it** and acting on its `SessionCard`.

The real objective, once the exploration converged: **surface the SessionCard
lifecycle actions (hide/unhide, resume, fork) as trailing icons directly on each
linked-session pill**, keeping the name region's click = jump behavior. Then run it
through the full OpenSpec loop — proposal → apply → build/deploy → verify → archive →
commit — end to end in one sitting.

## 2. TL;DR playbook

1. **Explore first, don't code.** Launch `openspec-explore`; ask the AI to map the
   *current* pill shape and lay out the design space as a small variant table (A/B).
2. **Answer the design questions tersely.** The AI surfaced 3 decisions; the user
   replied `1. A / 2. yes / 3. yes` — Variant A (name=jump, icons to the right).
3. **`create proposal`** — capture the decision as an OpenSpec change
   (`proposal.md` + `tasks.md` + a MODIFIED spec delta with new scenarios). Validate.
4. **Apply the change** (`openspec-apply-change`): thread 3 optional props into
   `FolderOpenSpecSection`, forward the 3 handlers already in scope at `SessionList`,
   add `e.stopPropagation()` on each icon, extend the test file.
5. **Run the scoped test file** with `HOME=$(mktemp -d) npx vitest run …` — isolate
   from the real `$HOME` so no user config bleeds in.
6. **`build and deploy`**: `npm run build`, then `pi-dashboard restart` (NOT raw curl —
   the hook blocks direct HTTP to `/api/restart`).
7. **Verify** (`openspec-verify-change`): map every spec scenario → code + test evidence.
8. **Archive + sync** the MODIFIED requirement into the main spec, then **commit only
   this change's files**, leaving unrelated pre-staged WIP untouched.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Starting in `openspec-explore` was the highest-
  leverage move: it forced a design-space pass *before* any code, yielding the A/B
  variant table and the "handlers already exist" discovery. Reusable kickoff:
  *"Enter explore mode. Look at how linked-session pills render in FolderOpenSpecSection.
  I want lifecycle actions (hide/resume/fork) on the pill itself — lay out the options
  before we commit."*
- **`1. A / 2. yes / 3. yes`** — a terse batch answer to the AI's 3 design questions.
  High leverage because the AI had already framed the choices as a table; the human
  just picked a row.
- **`create proposal`** — one verb that converted the settled exploration into a
  validated OpenSpec artifact set.
- **`build and deploy`** — trusted the AI to pick the right deploy path (it correctly
  avoided raw HTTP and used `pi-dashboard restart`).
- The `/opsx:apply`, `/opsx:verify`, `/opsx:archive` skill invocations chained the
  standard OpenSpec loop without re-explaining intent each time.

The dominant quality bar the user imposed: **run the full OpenSpec loop, not just the
edit** — proposal, apply, verify, archive, and a clean scoped commit.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The workflow leaned on existing
skills, which is itself the lesson: **the `openspec-explore → new-change → apply →
verify → archive` chain is the reusable asset.** For a small, purely-UI surfacing
change like this (no server/protocol/persistence), that chain is the fast path.

Worth capturing as a project skill if not already: *"surface existing SessionCard
lifecycle actions onto a new UI surface"* — the pattern of (1) confirm handlers exist
at the call site, (2) thread optional props, (3) mirror the conditional-visibility
logic, (4) add `stopPropagation`, (5) extend the co-located test file.

## 7. Pitfalls & dead ends

- **Raw HTTP to the dashboard is blocked.** `curl`/`wget` to `http://localhost:8000/api/health`
  and `/api/restart` all failed (4 failed attempts). Use `pi-dashboard restart` /
  `pi-dashboard status` instead.
- **`tsc` on the whole client shows a pre-existing error (line 413).** Don't panic —
  `git stash` your edits, re-run, confirm the error persists, then `stash pop`. It's
  unrelated to a linked-session-pill change.
- **vitest picks up real `$HOME` config.** Run with `HOME=$(mktemp -d) npx vitest run
  <file>` to isolate.
- **Unrelated pre-staged WIP in the index.** Before committing, inspect `git status
  --short` and `git restore --staged` anything not part of your change (here:
  `fix-fork-empty-session-silent-timeout` archive + `session-resume/spec.md`).
