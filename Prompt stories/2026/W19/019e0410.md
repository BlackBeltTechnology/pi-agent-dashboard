# How we did it: Designing OpenSpec change-grouping through explore mode — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** — a thinking-partner stance, explicitly *not*
implementation. The first prompt was the `openspec-explore` skill boilerplate:

> "Enter explore mode. Think deeply. Visualize freely. Follow the conversation
> wherever it goes… You may read files, search code, and investigate, but you must
> NEVER write code or implement features."

The *real* objective emerged one turn later: **"Is it possible to organize proposals
into groups? I would like to categorize the changes."** By the end, the user had a
strictly-validated, spec-driven OpenSpec change (`add-openspec-change-grouping`) that
adds per-repo grouping to the dashboard's OpenSpec surfaces — a proposal, a design
with 18 decisions, four spec files, and a tasks file, all passing
`openspec validate --strict`.

## 2. TL;DR playbook

1. **Enter explore mode** with the `openspec-explore` skill. Ask the AI to *sketch the
   current shape before proposing anything* — it maps the existing UI/data model so
   your design is grounded, not invented.
2. **State the goal as a capability question**, not a solution: "Can I organize
   proposals into groups?" Let the AI enumerate the design space (where groups live,
   single vs. multi, per-repo vs. global) and present orthogonal choices.
3. **Pin storage location early.** The single highest-leverage correction was moving
   group config from a user-local sidecar to **in-repo** `<cwd>/openspec/groups/`.
   Decide this before the proposal solidifies.
4. **Probe for scaling risks** ("be sure you're not flooding the group read"). This
   forces the AI to add an mtime-gated cache + debounced broadcast to the design.
5. **Supersede, don't patch, when scope broadens.** The first narrow change
   (`add-folder-openspec-name-filter`, proposal-only) was deleted and re-scaffolded as
   the broader `add-openspec-change-grouping` once grouping subsumed the filter.
6. **Fast-forward artifact creation** with `/opsx:ff` — one prompt generates
   design → specs → tasks in sequence until apply-ready.
7. **Gate on `openspec validate <change> --strict`** as the definition of done.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding.** Before any design, the AI grep'd the client for
existing filter controls (`SessionList.tsx`, `FolderOpenSpecSection.tsx`,
`ArchiveBrowserView.tsx`) and drew an ASCII map of the three sidebar controls
(folder filter, session filter, hidden toggle) and where OpenSpec surfaces live.
*Why it worked:* the design was anchored to the real component tree, so every later
decision named a concrete file.

**Phase 2 — Design-space enumeration.** When the user asked about grouping, the AI
didn't jump to a schema. It laid out orthogonal questions — where the group lives,
single-group vs. tags, per-repo vs. cross-repo — and showed that OpenSpec's CLI has
*zero* group concept, so anything is layered on top. The human picked: per-repo,
single group, sections + filter pills + name-substring input.

**Phase 3 — Storage correction (the pivot).** The human steered storage from the
sidecar `~/.pi/dashboard/openspec-groups.json` to in-repo
`<cwd>/openspec/groups/groups.json`. The AI enumerated what drops out for free
(no `byCwd` map, version-controlled, team-shared, no migration) and what it costs
(out-of-band edits become a real path the server must tolerate).

**Phase 4 — Performance hardening.** The human flagged flooding risk. The AI traced
the hot path (server joining `groupId` into every `OpenSpecData` WS broadcast, N cwds
× M broadcasts) and baked in an **mtime-gated in-memory cache** (stat-only on hit,
no parse), in-flight promise sharing per cwd, and a 50–100 ms trailing debounce.

**Phase 5 — Generate & verify.** A `/opsx:ff` fast-forward produced design.md (18
decisions D1–D18), four spec files (one new capability + three deltas), and tasks.md.
Final `openspec validate add-openspec-change-grouping --strict` passed.

## 4. Prompts that worked

- **Goal prompt (capability question):** *"Is it possible to organize proposals into
  groups? I would like to categorize the changes."* — Effective because it names the
  desired capability, not an implementation, letting the AI own the design space.
- **High-leverage steer (storage):** *"be sure the groups config is in
  cwd/openspec/groups"* — one short line that flipped the whole persistence model to
  version-controlled/team-shared. Rewrite for reuse: *"Store the group config in-repo
  at `<cwd>/openspec/groups/`, not a user-local sidecar — it must be git-tracked and
  team-shared."*
- **High-leverage steer (perf):** *"but be sure you're not flooding the group read"* —
  forced a caching + debounce layer into the design before it was written. Rewrite:
  *"The server joins group data into every WS broadcast — add an mtime-gated cache so
  we don't disk-read per broadcast."*
- **Fast-forward:** the `/opsx:ff` skill prompt — one command drove all remaining
  artifacts to apply-ready.

## 5. Steering & corrections (what to watch for)

## 6. Skills, tools & memory created — and why they're effective

No new skills or memories were saved this session, but two existing skills carried the
work and are worth invoking deliberately:

- **`openspec-explore`** — enforces a *think-before-build* stance. Effective here
  because it made the AI map the existing UI and enumerate the design space instead of
  writing a schema immediately. Invoke when the requirement is a genuinely open
  question ("can we organize X?") rather than a known change.
- **`openspec-ff` (`/opsx:ff`)** — fast-forwards design → specs → tasks in one shot
  once decisions are locked. Invoke once the proposal is settled and validation is the
  only remaining gate.

*Recommended skill to create:* a **"server-side WS join cost check"** guardrail — any
time the server enriches broadcast payloads by reading a file, require an mtime-gated
cache + debounce. This correction recurred and is generalizable.

## 7. Pitfalls & dead ends

- **Narrow-first proposal wasted a scaffold.** `add-folder-openspec-name-filter` was
  created (proposal only) then deleted when grouping subsumed it. *If the ask is still
  fuzzy, hold off on `openspec new change` until the scope stabilizes* — or accept a
  cheap supersede (`rm -rf openspec/changes/<old>` + re-scaffold).
- **In-repo storage invites out-of-band edits.** Moving config into the repo means
  hand-edits and other tools can write it. The design had to add mtime-recheck +
  1-shot retry → 409 to tolerate this. *If you make config git-tracked, plan for
  concurrent writers.*
- **"Re-read on every request" is a silent stampede.** Naively joining group data into
  every WS broadcast disk-reads per cwd per poll cycle. *Always cost the hot path
  before shipping a server-side join.*
