# How we did it: Race-safe "replace attached proposal" dialog — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator entered **explore mode** — "Think deeply. Visualize freely. Follow the
conversation wherever it goes… Explore mode is for thinking, not implementing." — and
opened a concrete design question one prompt later: *"But what happens while dialog is
open and newer is coming?"*

The real objective, once the steering clarified it: **design (not implement) a
race-safe UI flow** for the case where a pi session has a proposal manually attached,
the LLM emits a *newer* active OpenSpec change while a "Replace X with Y?" dialog is
open, and the user's click must land on exactly what they saw. The deliverable is an
OpenSpec **change proposal** capturing the design — proposal.md + design.md + tasks.md
+ a delta spec — validated and committed, with zero production code written.

## 2. TL;DR playbook

1. Kick off in **explore mode** with the standard "thinking, not implementing" stance
   prompt. State the concrete race question in prompt 2, don't bury it.
2. Let the AI **map the race as a timeline diagram** (dialog open → t3 newer events
   arrive → t4 click) and enumerate the behavioral options (ignore / swap / coalesce /
   queue). Pick one — here, **coalesce**.
3. Say **"ground this in the actual code"** — force the AI to open `event-wiring.ts`
   and find the exact no-op branch (line 248: manual-attach + different-name → nothing)
   before it designs anything.
4. Approve the **three-layer model** (detector filter → server coalesce → client
   commit/suggestion split) and the invariant: *button label = commit target; server
   may freely update the suggestion*.
5. Prompt **"create proposal"** → AI runs `openspec change new <name>`, writes
   proposal/design/tasks/spec, and `openspec validate`s to green.
6. Come back later and ask **"is this related to <other change>? Maybe merging makes
   sense?"** to force a relationship map against sibling changes.
7. Say **"recheck current codebase, because lots of features already implemented"** —
   the highest-leverage steer. The AI audits archived changes and prunes assumptions
   that already shipped.
8. **"commit changes"** → `git add` the touched proposal files + commit.

## 3. How the collaboration unfolded

**Phase 1 — Frame the race (explore).** The AI refused to jump to a fix. It drew the
CURRENT FLOW and a t0→t4 TIMELINE diagram, split the problem into **DISPLAY STATE** vs
**COMMIT STATE**, and listed four behaviors (ignore / swap / coalesce / queue). It also
pinned down *what "change event" even means* (bridge detector vs poller vs tool call) —
because the mitigation differs per source. The human's terse "yes"/"es" replies
approved directions without over-specifying.

**Phase 2 — Ground in code.** Triggered by the human's approval, the AI stopped
theorizing and used `find`/`rg`/`grep` to locate the real branch:
`event-wiring.ts:248`, where a manually-attached session that sees a new active
`changeName` does **nothing today**. This is the effective move — the whole race lives
in that one server spot, and finding it turned abstract options into a concrete state
machine (`pendingReplaceProposal`, `pendingReplaceSeenAt`).

**Phase 3 — Design + generate.** The AI crystallized the **three-layer model** and the
button-label invariant, then on "create proposal" ran `openspec change new` and wrote
the four artifacts: proposal.md, design.md (three-layer model + decision log D1–D6 +
deferred multi-proposal case), tasks.md (8 groups / ~45 items), and a
`proposal-attachment` delta spec (7 ADDED, 1 MODIFIED). It closed with
`openspec validate` → clean.

**Phase 4 — Relate + audit (weeks later).** Two follow-ups reopened the change. First,
"is this related to unify-dialog-system?" produced a relationship map across sibling
changes. Then the killer steer — **"recheck current codebase, lots already
implemented"** — drove a codebase audit that found `unify-dialog-system`,
`openspec-read-only-no-attach` (the `isActive` filter), and the witness rule had
**already shipped** in archived changes. The proposal was pruned to net-new work
(`event-wiring.ts:248` is still a no-op; no `pendingReplaceProposal` state exists yet)
and a "Codebase Anchors (verified)" section was added.

**Phase 5 — Commit.** `git add` the touched proposal files, commit `ccd6d196` on
`develop`. The AI flagged an unrelated `groups.json` line that rode along — honest, not
hidden.

## 4. Prompts that worked

- **Goal / kickoff** — the explore-mode stance prompt ("thinking, not implementing…
  you MAY create OpenSpec artifacts"). Effective because it *licenses design output*
  while forbidding code, which is exactly the boundary this task needed.
- **"But what happens while dialog is open and newer is coming?"** — one sentence that
  named the entire race. High leverage: it forced the timeline analysis.
- **"yes" / "es"** — terse unlocks that approved a direction without micro-managing;
  fine *because* the AI had laid out explicit options to pick from.
- **"create proposal"** — the mode-switch trigger from exploring to artifact
  generation.
- **"Recheck current codebase, because lots of features already implemented"** — the
  single most valuable steer. Rewrite for reuse: *"Before finalizing, audit archived
  OpenSpec changes and shipped code; strip any assumption that already exists and add a
  verified-anchors section."*

## 5. Steering & corrections (what to watch for)

proposals *rot* against a moving codebase — the audit steer exists precisely to counter
that.

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created this session. The repeatable pattern that **should**
be captured:

- **"OpenSpec proposal codebase-audit" step** — before archiving or committing a
  proposal that has aged, diff its assumptions against `openspec/changes/archive/` and
  live source, then add a "Codebase Anchors (verified)" section. Reusable because
  long-lived proposals routinely assume dependencies that shipped in the interim; the
  audit prevents building the same thing twice. Invoke it whenever a proposal is
  reopened after other changes have merged. (This overlaps the existing
  `openspec-verify-change` skill — consider folding a "verify against shipped code"
  clause there.)

## 7. Pitfalls & dead ends

- **`rg` type flags for `.tsx`** — `rg -t tsx` failed (unknown type); the working form
  was `rg --type-add 'tsx:*.tsx' -t ts -t tsx …` or plain path globs. If an `rg` type
  filter errors, register the type or fall back to `-g '**/*.tsx'`.
- **Assuming `openspec/archive/`** — the archive lives at
  `openspec/changes/archive/`, not `openspec/archive/`. Check the real path before
  grepping for shipped changes.
- **Stale proposal drift** — the biggest trap. Half the original proposal's "new" work
  had already shipped. Never trust a weeks-old proposal's novelty claims; audit first.
- **`extract-openspec-as-plugin` was already invalid** (proposal-only, no specs), so
  editing it didn't "break" anything — verify a sibling's validation state before
  worrying about your edit.
