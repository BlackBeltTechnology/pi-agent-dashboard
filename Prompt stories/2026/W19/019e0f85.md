# How we did it: Finishing the last 13 tasks of a plugin OpenSpec change — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — "Enter explore mode.
Think deeply… you must NEVER write code." The real objective, which surfaced once the
operator toggled out of exploring, was concrete: **drive the `honcho-dashboard-plugin`
OpenSpec change from 97/110 tasks to a fully-archived 110/110.** The 13 remaining tasks
weren't a uniform backlog — they split into four categories (stale external-repo tasks,
unbuilt E2E fixture tasks, Docker-integration tasks, and manual QA), each needing its own
decision before any code was written. The finish line was: green test suite, a clean
`/opsx-archive`, synced main specs, and a committed diff that excludes unrelated residue.

## 2. TL;DR playbook

1. **Start in explore mode to triage, not to build.** Ask the AI to read the tasks file
   and *categorize* the remaining work before touching code (here: A stale / B E2E / C
   Docker / D manual).
2. **Capture the design decision in `design.md` first.** For the E2E work, the AI appended
   an "E2E Test Fixture Approach" section (vitest+jsdom + in-process Fastify, **no
   Playwright**) justified against the actual asserts — then validated.
3. **Run `/opsx-apply` and let it pause for category routing.** It stopped and asked which
   category to tackle; answer with a single letter (`B`) to unlock one track at a time.
4. **Build the fixture bottom-up**: `tmpHome` → `server-fixture.ts` (reuse
   `launchDashboardServer`) → `client-mount.tsx` (fetch shim → `fastify.inject`) → simplest
   test first to prove the fixture, then the rest.
5. **Let a real test expose a real bug.** The map-popover round-trip surfaced a silent
   `DELETE /sessions` merge bug; fix it in source (`replaceConfigFile`), add a unit test,
   re-run.
6. **Defer, don't delete, out-of-scope tasks.** Docker-integration tasks (9.6/9.7) got a
   *new* change `add-honcho-docker-integration-tests` and inline `*(deferred to …)*`
   annotations, keeping the parent archivable.
7. **Mark stale tasks superseded with an inline note** matching existing precedent, run the
   **full** suite (`5349 passed`), then have the human eyeball the one manual-QA task.
8. **Archive → sync specs → commit selectively**, staging only your files and calling out
   the uncommitted residue from other threads.

## 3. How the collaboration unfolded

**Phase 1 — Explore & triage (prompts 1–2).** The AI grounded in the change state (97/110),
read the tasks file, and drew the "what you have vs what you need" picture (vitest+jsdom vs
`qa/tests/*.sh`, neither sufficient for React-UI-plus-server asserts). *Why it worked:*
mapping the gap before proposing a tool prevented an over-engineered Playwright pull.

**Phase 2 — Capture the approach in design.md (prompt 2 = "b").** Rather than implement, the
AI appended a decision section (four fixture layers, per-task mapping, one deferred open
question) and validated clean. *Decision point:* the human kept it in explore mode so the
thinking landed in an artifact, not in code.

**Phase 3 — Category-routed apply (prompts 3–4).** `/opsx-apply` paused with a four-category
breakdown and asked for direction. The human answered `B` — build the E2E fixture + 5 tests.

**Phase 4 — Build & verify (the bulk).** In-process Fastify fixture, client mount with a
`globalThis.fetch` shim delegating to `fastify.inject`, one test at a time. A failing test
revealed the DELETE-merge bug → `replaceConfigFile` helper + route fix + unit test. All 5
e2e tests (14 cases) green; full suite `527 files / 5349 tests` green.

**Phase 5 — Route the leftovers (prompts 5–9).** The human asked clarifying questions
("What means docker integration?", "Wh honcho is empty?", "What is in honcho database?").
The AI answered with the plugin's two-mode model, then **deferred** Docker tasks into a new
change and **superseded** the stale external-repo tasks with annotations, and diagnosed the
"empty" honcho (stack alive but never written; lazy data model) — seeding
peer/workspace/aiPeer via the config API.

**Phase 6 — Land it (prompts 12–14).** `/opsx-archive` synced two new main specs, then a
**selective** commit staged only this thread's files, explicitly listing the residue from
unrelated threads left uncommitted.

## 4. Prompts that worked

- **Goal prompt (explore mode).** Effective because it forced a *triage-first* stance — the
  AI categorized 13 tasks instead of blindly implementing. Reusable framing: *"Don't write
  code yet. Read the tasks file and group the remaining work into categories, each with the
  decision it needs."*
- **`B` / `A` / `a` single-letter unlocks.** High-leverage: after the AI presents a labeled
  menu (category A/B/C/D, option a/b), a one-character reply advances a whole track. Cheap
  for the human, unambiguous for the AI.
- **"run full test".** Short, decisive quality bar — forced a whole-repo vitest run
  (not just the touched package) before claiming done.
- **"git commit".** Triggered the selective-staging discipline; the AI self-audited "mine vs
  pre-existing" before staging.
- Weak prompts to rewrite: *"Wh honcho is empty?"* → **"The honcho panel shows empty —
  check whether the stack is running, whether peer/workspace/aiPeer are configured, and
  whether any data was ever written."** Same answer, less round-trip.

## 6. Skills, tools & memory created — and why they're effective

No pi *skill* or *memory* was created in this session, but three **reusable assets** landed
in the repo and one clear skill-shaped pattern emerged:

- **E2E fixture harness** (`server-fixture.ts` + `client-mount.tsx` + `README.md`). Captures
  "test real React UI against a real plugin server without Playwright or a full pi-agent":
  in-process Fastify mounts the plugin routes, a `fetch` shim routes to `fastify.inject`,
  each test gets a `mkdtemp` HOME. *Invoke when* a plugin task needs UI + server-config-write
  fidelity but not browser-only behavior.
- **`replaceConfigFile` helper** (`config-store.ts`). Fixes a class of bug: merge-only config
  writers can't express deletion. *Invoke when* a route must remove a key, not just upsert.
- **Deferred-change pattern** (`add-honcho-docker-integration-tests`). A full proposal/design/
  tasks/spec stub that lets the parent change archive while tracking the skipped work with
  explicit trigger conditions. *Invoke when* tasks are real but out of the current scope.
- **Should-exist skill:** *"finish-openspec-change"* — triage remaining tasks into
  supersede / defer / build / manual-QA, then archive+sync+selective-commit. This session is
  a textbook run of it.

## 7. Pitfalls & dead ends

- **`node /tmp/debug-delete.mjs` failed** (❌) — running an ad-hoc ESM debug script from
  `/tmp` didn't resolve project modules. *Fix:* move it into the repo root
  (`mv /tmp/debug-delete.mjs ./debug-delete.mjs && node …`) so imports resolve, then delete.
- **RTL auto-cleanup silently off** — the first fixture run leaked a "flash of install gate"
  between tests because vitest globals weren't enabled, so React Testing Library's cleanup
  never fired. *Fix:* enable vitest `globals` for the e2e project.
- **Silent DELETE via merge** — `mergeConfig` has no delete semantic, so the map-popover
  "clear" never removed the key and the round-trip test failed. *Fix:* add `replaceConfigFile`
  and point the DELETE route at it. Lesson: a real round-trip test catches what a merge-only
  unit test hides.
- **Dirty worktree at commit time** — unrelated honcho threads (auto-mint-proxy-key,
  fullscreen-dialogs, remint-proxy-key) sat in the tree. *Fix:* stage selectively, never
  `git add -A`, and enumerate the residue in the commit note.
