# How we did it: De-flake a bin-wrapper test & un-gitignore shared team state — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user pasted a failing vitest run — a single red test out of 5365 — and nothing
else:

> `FAIL @blackbelt-technology/pi-dashboard-server … bin/pi-dashboard.mjs wrapper >
> resolves jiti from process.argv[1] anchor and re-execs cli.ts … expected 1 to be +0`

The literal ask was "make this test green." The *real* objective, once the root cause
was understood: make the test assert what it actually means to verify (the wrapper
resolved jiti and re-execed `cli.ts`) **without** depending on flaky external state (a
live dashboard server discovered over mDNS). A second, unrelated thread emerged mid-
session: why `openspec/groups/groups.json` never shows as a changed file, and how to
share it with the team.

## 2. TL;DR playbook

1. **Reproduce the assertion, not the vibe.** Run the one failing test file in
   isolation: `npx vitest run <path> 2>&1 | tail -50`.
2. **Prove it's environment-coupled**, not logic-broken, by re-running under a clean
   HOME: `HOME=$(mktemp -d) npx vitest run <path>`. If the result flips, the test
   depends on external state.
3. **Read the code under test** to confirm the exit code is *legitimately* variable
   (`grep -n "status\|not running" packages/server/src/cli.ts`) — exit 1 = "not
   running", which is correct behavior, not a bug.
4. **Narrow the assertion to intent.** Drop `expect(result.status).toBe(0)`; keep the
   assertions that actually prove the wrapper worked (no jiti-miss on stderr, cli.ts
   emitted its own output).
5. **Re-run to green**, then `commit and push` only the intended file — leave
   unrelated dirty files alone.
6. **For the gitignore thread:** locate the ignore with `grep -n groups.json .gitignore`
   and trace *why* via `git log --oneline --all -- <path> .gitignore`.
7. **To share per-user state with a team:** remove the `.gitignore` line **and** `git
   add` the file in the same commit, with a message explaining the policy flip.

## 3. How the collaboration unfolded

**Phase 1 — Diagnose (bash ×5, read ×1).** The AI ran the failing test standalone,
then re-ran it under `HOME=$(mktemp -d)` to isolate it from the operator's live
environment. It grepped `cli.ts` for the `status` path and correctly concluded the
test was **flaky, not wrong**: the wrapper's job is to resolve jiti and re-exec
`cli.ts`; whether `cli.ts status` then exits 0 or 1 depends on whether a dashboard
server is up (mDNS discovery), which is external state the unit test shouldn't bind to.

**Phase 2 — Fix & ship (edit ×1, bash ×3).** The AI dropped the `result.status === 0`
assertion and kept the two that prove wrapper behavior. It re-ran the file to green,
then on the "commit and push" turn committed **only** the test file (`29bccedc` →
`develop`), deliberately leaving the unrelated openspec changes uncommitted.

**Phase 3 — The gitignore detour (bash ×2, read ×1, edit ×1).** The operator asked
why `groups.json` never appears as changed. The AI found `.gitignore:9` ignored it and
traced the reason to commit `3df3e414` ("gitignore … per-user state"). When the
operator said "I wanna share between team," the AI removed the ignore line and
committed the current `groups.json` in one commit (`659b3432`) so lanes/colors/
assignments are now versioned.

## 4. Prompts that worked

- **The goal prompt** = the raw failing test output, pasted verbatim. This is a good
  kickoff: it gives the exact file, line, and assertion. It would have been *stronger*
  with the intent stated — e.g. "This test is flaky in CI; make it assert wrapper
  behavior without depending on a running server." That framing points straight at the
  fix instead of tempting a naive "force status to 0."
- **"commit and push"** — a high-leverage two-word unlock, effective *because* the
  preceding turn had already produced a clean, scoped diff. Works only when the working
  tree is already in the intended state.
- **"Why I never see groups.json as changed file?"** — a good diagnostic prompt: it
  asks for a *cause*, which pushed the AI to `git log` the history rather than guess.
- **"I wanna share between team."** — a one-line intent that cleanly triggered the
  policy flip. Stronger version: "Un-ignore `groups.json` and commit it so the team
  shares it" — same result, no inference needed.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session — it was a short, surgical fix (3m 9s, 4
prompts). Two repeatable patterns are worth capturing if they recur:

- **"Flaky-test → assert intent, not environment."** When a test binds to external
  state (a running server, network discovery, real HOME), re-run under
  `HOME=$(mktemp -d)` to prove the coupling, then narrow the assertion to the behavior
  the test *names*. A small project skill could encode the `mktemp -d` isolation probe.
- **"Un-ignore per-user state for a team."** The two-step move (delete `.gitignore`
  line + `git add` the file in one commit) is a clean, reusable recipe worth a note.

## 7. Pitfalls & dead ends

- **Don't "fix" a flaky test by forcing the flaky value.** Asserting `status === 0`
  would pass only when a server happens to be up. The correct fix removes the coupling.
- **A gitignored file is invisible to `git status` by design.** If a file "never shows
  as changed," check `.gitignore` (`grep -n <name> .gitignore`) before assuming git is
  broken — then `git log --all -- <path>` to learn *why* it was ignored.
- **Scope your commits.** With unrelated dirty files present (the openspec changes
  here), commit only the intended path so unrelated work isn't dragged in.
