# How we did it: Unblocking the Windows v0.5.0 release build — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking-only stance,
no implementation — staring at a red release pipeline. The literal kickoff was the
explore-mode skill prompt, but the *real* objective surfaced one steering turn later:

> "Every platform have own builder. Both windows builder failed." *(with a screenshot)*

The goal was to **diagnose and fix why the `publish.yml` release workflow's two Windows
legs (win32-x64 and win32-arm64) were failing while every other platform stayed green**,
and to ship a clean **v0.5.0** release with correctly arch-tagged Windows artifacts. What
looked like one bug turned out to be **two independent regressions** from the same prior
change ("Simplify electron bootstrap derived state", which removed the NSIS maker).

## 2. TL;DR playbook

1. **Don't guess at a silent CI failure — instrument it first.** The offline-bundle
   script printed `✗ npm install failed:` with *empty* stderr/stdout. Add a diagnostic
   patch to the failure branch that dumps `cmd`, `status`, `signal`, and
   `error.code/errno/syscall/message` — the fields `spawnSync` populates when the spawn
   itself (not the child) fails.
2. **Retag to re-fire, don't "Re-run failed jobs."** The old run was on a commit without
   the diagnostics. Move the tag to HEAD: `git tag -d v0.5.0 && git push origin
   :refs/tags/v0.5.0 && git tag v0.5.0 <newsha> && git push origin v0.5.0`. `publish.yml`
   triggers on tag push; `npm publish` is idempotent so already-published packages are safe.
3. **Read the timestamps in the CI log.** "3 ms between spawn and failure" = the child
   never ran = spawn-level error, not a network/registry/long-path problem. This kills
   whole hypothesis branches instantly.
4. **Let the diagnostic run tell you the two distinct failures:**
   - win32-arm64 → `error code=UNKNOWN errno=-4094 syscall=spawnSync` = libuv's mapping of
     `ERROR_BAD_EXE_FORMAT (193)` = **wrong-arch node.exe** (arm64 binary on x64 runner).
   - win32-x64 → `Could not find any make targets configured for the "win32" platform` =
     **no Windows maker** in `forge.config.ts` (NSIS was removed).
5. **Fix both root causes surgically:**
   - `bundle-offline-packages.mjs`: gate on CPU too — `TARGET_OS === process.platform &&
     TARGET_CPU === process.arch` — so the arm64 cross-build falls back to system npm.
   - `publish.yml`: run `electron-forge make` for `matrix.platform != 'win32'`, and rename
     the Windows packaging step to cover **all** win32, not just arm64.
6. **Retag once more, then poll to green:** a `while :; do gh run view … --json
   status,conclusion; done` loop until the run finishes.
7. **Verify the artifact list**, confirming every Windows asset is distinctly arch-tagged
   (`PI-Dashboard-win32-x64.zip`, `-win32-arm64.zip`, `-x64-portable.exe`, `-arm64-portable.exe`).

## 3. How the collaboration unfolded

**Phase 1 — Discovery (in explore mode, no edits).** The AI opened the failing
`bundle-offline-packages.mjs`, traced the `spawnSync` call, and immediately spotted that
the failure branch logs `stderr + stdout` but **never inspects `.error` or `.signal`** —
so a spawn-level failure prints nothing. It laid out a hypothesis table (spawn ENOENT,
wrong arch, Defender block, long paths) rather than committing to one. **Why it worked:**
refusing to fix blind and instead identifying *what evidence was missing* set up the whole
fix.

**Phase 2 — Reframe on human correction.** The human's "both windows builders failed"
(with screenshot) killed the arch-mismatch theory: both runners are arch-native, so it's
**Windows-specific, not arch-specific** at that point. The AI redrew the platform matrix
and narrowed to "running npm via bundled node.exe on Windows."

**Phase 3 — Instrument & re-fire.** With browser log access blocked ("Sign in to view
logs"), the AI switched to `gh` CLI (authenticated), pulled the log, and read the
**3-millisecond** gap between spawn and failure as proof of a spawn-level error. It wrote
the diagnostic patch, node-`--check`ed it, committed, and **retagged v0.5.0 to the new
SHA** to re-fire CI — explicitly explaining why "Re-run failed jobs" on the old commit
would just reproduce the blind failure.

**Phase 4 — Two smoking guns.** The diagnostic run returned two *different* errors, one
per arch. The AI connected both to the same prior change (#18 removed NSIS): the arm64
leg was a cross-build the CPU gate ignored, and the x64 leg had no forge maker at all.

**Phase 5 — Fix, retag, poll, verify.** Two surgical edits, a YAML+JS syntax check, a
commit, a final retag, a poll loop to completion, and an asset-list verification: 9/9 jobs
green, draft release created with correctly named Windows artifacts.

- **Why it's effective:** it removes the guesswork loop on empty-output CI failures and

- **When to invoke:** any red release/`publish.yml` run with empty or misleading logs,

## 7. Pitfalls & dead ends

- **Empty CI output ≠ no error.** `spawnSync` puts spawn-level failures in `.error`, not
  stderr/stdout. If a script logs only `stderr+stdout` and prints nothing, patch the
  failure branch to dump `.error.code/errno/syscall` and `.status/.signal`.
- **In-agent browser is anonymous** for private GitHub Actions logs ("Sign in to view
  logs"). Use `gh run view <id> --log-failed` with an authenticated CLI instead.
- **"Re-run failed jobs" reuses the old commit** — useless when your fix is a new commit.
  Move the tag: `git tag -d v… && git push origin :refs/tags/v… && git tag v… <sha> &&
  git push origin v…`.
- **`errno=-4094` / `code=UNKNOWN` on Windows spawn** = libuv's catch-all for
  `ERROR_BAD_EXE_FORMAT (193)` = wrong-arch executable. On x64 runners, an arm64 cross-build
  must fall back to system tooling — gate on **CPU as well as OS**.
- **"Could not find any make targets configured for win32"** = `forge.config.ts` has no
  Windows maker. Don't run `electron-forge make` for win32 if the maker was removed; scope
  the make step to `platform != 'win32'` and package Windows separately.
- **A single config removal can regress multiple legs differently** (arm64 vs x64 here) —
  don't assume one fix covers both.

## 8. Reproduce it faster — checklist

**Inputs to have ready:** authenticated `gh` CLI (repo write for tag push), the failing
`publish.yml` run id, push access to `develop`.

1. `gh run view <id> --repo <org/repo> --log-failed` → find the failing step + read
   timestamps (a sub-second spawn→fail gap = spawn-level error).
2. If output is empty, patch the failing script's failure branch to log
   `cmd/status/signal/error.{code,errno,syscall,message}`; `node --check` it.
3. Commit to `develop`; retag the release to HEAD and force-push to re-fire CI.
4. Read the *new* per-leg errors:
   - `UNKNOWN errno=-4094` → wrong-arch binary → gate offline-bundle on `TARGET_CPU ===
     process.arch` too; fall back to system npm on cross-builds.
   - `no make targets for win32` → add/restore a Windows maker OR scope
     `electron-forge make` to `platform != 'win32'` and package Windows in its own step.
5. Syntax-check (`node --check` + `python3 -c "import yaml; yaml.safe_load(...)"`), commit,
   retag, force-push.
6. Poll: `while :; do gh run view <id> --json status,conclusion …; done` until complete.
7. Verify assets are arch-distinct: `gh release view v<x> --json assets` — expect
   `win32-x64.zip`, `win32-arm64.zip`, `x64-portable.exe`, `arm64-portable.exe`.

**Artifacts produced:** edits to `packages/electron/scripts/bundle-offline-packages.mjs`
and `.github/workflows/publish.yml`; a green v0.5.0 draft release with 9/9 jobs passing and
fully arch-tagged Windows artifacts.
