# How we did it: Bump the bundled Electron Node from v22 → v24 (with a single source of truth) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened **inside explore mode** (`openspec-explore` skill loaded) — a
thinking stance, not an implementation one. The real objective, once the model
mapped the terrain: **bump the Node version the Electron app bundles from `v22.18.0`
to the latest v24 LTS**, and do it *without* leaving the version hardcoded in six
different places. The AI's first move was to enumerate every pin site rather than
start editing — turning a vague "bundle Node 24" into a concrete list of build
scripts, Docker images, QA scripts, and a runtime guard that each carried their own
copy of the version string.

## 2. TL;DR playbook

1. **Stay in explore mode first.** Ask the AI to *map* every place the old version is
   pinned before touching anything: `grep -rn` across `packages/electron/scripts`,
   `forge.config.ts`, `package.json`, `.github/`.
2. **Confirm the exact target version.** One `web_search` ("latest Node.js v24 LTS
   release") → pin `v24.15.0` (LTS, 2026-04-15). Don't trust a fuzzy "24.x".
3. **Create a single source of truth.** New `packages/electron/scripts/_node-version.sh`
   exporting `BUNDLED_NODE_VERSION="v24.15.0"` and `BUNDLED_NODE_MAJOR="24"`.
4. **Make every build script source it.** `download-node.sh`, `build-installer.sh`,
   `build-windows-zip.sh`, `docker-make.sh` — replace literals with the shared var.
5. **Parameterize the Dockerfile.** `ARG NODE_BUILD_IMAGE=node:24-bookworm-slim` +
   `FROM ${NODE_BUILD_IMAGE}`, passed via `--build-arg` from the builders.
6. **Update static heredocs with a back-reference comment.** QA scripts that can't
   `source` the file get the literal + a `# see _node-version.sh` pointer.
7. **Rebuild the offline cache.** `bash scripts/download-node.sh` to fetch Node 24,
   then `node bundle-offline-packages.mjs` so the npm cache is built with bundled
   npm 11.
8. **Verify.** `bash -n` syntax-check every script, `npm test`, and confirm no
   `v22.18.0` leaks in source build paths (`grep`, excluding `out/`/`node_modules`).

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI refused to edit and instead produced a
table of every pin site: 6+ literal copies of `v22.18.0` plus `node:22-bookworm-slim`
Docker tags. It flagged that the host-Node check (`"22.12+"` error string) was a
*separate concern* from the bundled version — important, because bumping one shouldn't
touch the other. *Why it worked:* mapping first exposed the duplication problem, which
reframed the task from "change a number" to "centralize a number."

**Phase 2 — Pin the target.** A single `web_search` fixed the exact LTS (`v24.15.0`).
The AI announced "Exiting explore" before writing anything — a clean stance handoff.

**Phase 3 — Centralize + edit.** It created `_node-version.sh` as the source of truth,
then rewired each build script to source it. Where sourcing wasn't possible (Docker
`ARG`, static QA heredocs) it used a build-arg or a literal + back-reference comment.
Ten edits, one new file.

**Phase 4 — Rebuild the cache.** Downloaded the 128M Node 24 toolchain into
`resources/node/` and re-ran the offline-package bundler so the 49M `npm-cache.tar.gz`
was regenerated under npm 11 / Node 24.

**Phase 5 — Verify.** `bash -n` on all scripts, `npm test`, and a leak grep. The
decision point: the human's single steering turn ("1. no, latest ok / 2. both / 3.
yes / 4. yes") unlocked the whole execution at once.

## 4. Prompts that worked

- **The goal (explore-mode kickoff).** Loading `openspec-explore` first was the
  high-leverage move: it forced a *map-before-edit* discovery pass instead of a
  premature edit. For a version bump touching many files, mapping first is the whole
  game.
- **The batched unlock — `1. no, latest ok / 2. both / 3. yes / 4. yes`.** Four
  terse answers to the AI's clarifying questions authorized (a) using latest LTS,
  (b) both mac/linux and windows/docker paths, (c) centralization, (d) cache rebuild
  — in one turn. *Why effective:* the AI had already enumerated the decisions; the
  human just had to greenlight them. Rewrite of a weaker "just update it": **"Map
  every pin site first, propose a single source of truth, then bump to latest v24 LTS
  everywhere including the offline cache."**

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was persisted this session. But the workflow is textbook-repeatable
and there is already a project skill for it: **`bump-pi-version`** covers "bump a
pinned version across the monorepo's source-of-truth sites." The pattern worth
capturing from *this* session specifically: **"introduce a `_node-version.sh` single
source of truth so the next Node bump is a one-line change."** If a Node bump recurs,
the reusable asset is the shared file itself — future bumps edit `BUNDLED_NODE_VERSION`
in one place instead of chasing six literals.

## 7. Pitfalls & dead ends

- **`curl … | python3 -c json.load` one-liners failed 3×** while probing
  `nodejs.org/dist/index.json` (piping truncated JSON into a strict parser). *If you
  hit this:* download the index to a file first (`curl -o /tmp/nodejs-index.json`)
  then parse — or just use the `web_search` result, which is what actually settled the
  version here.
- **A `git stash && npm test … && git stash pop` probe failed.** Stashing mid-edit to
  test the old tree is fragile. *If you hit this:* run the targeted tests against the
  working tree directly; don't stash a half-finished change.
- **Version literals hide in heredocs and Dockerfiles** where you can't `source` a
  shell var. *Do:* leave the literal but add a `# see _node-version.sh` comment so the
  next bumper finds it.
