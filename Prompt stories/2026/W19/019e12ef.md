## 1. Goal (the ask)

The user pasted a raw vitest failure — a single red test in a 5,365-test suite:

```
Error: Test timed out in 5000ms.
 ❯ src/__tests__/pi-dashboard-bin-wrapper.test.ts:61:3
   it("resolves jiti from process.argv[1] anchor and re-execs cli.ts", …
```

No instruction beyond the paste. The **real objective**: make that one
`pi-dashboard-bin-wrapper` test stop timing out and go green, without weakening what
it verifies — then land the fix. The failure is not a logic bug; the test spawns the
wrapper (which cold-starts jiti to load `cli.ts`) under the vitest default 5 s budget,
and a cold jiti transform of `cli.ts` blows past 5 s on a loaded machine.

## 2. TL;DR playbook

1. Locate the file: `find . -name 'pi-dashboard-bin-wrapper.test.ts' -not -path '*/node_modules/*'`.
2. Read the failing `it()` around line 61 — confirm it does a real `spawnSync` with its **own** 30 s timeout, so the bottleneck is the *outer* vitest 5 s limit, not the spawn.
3. Fix minimally: append a per-test timeout to that single `it()` → `it("…", async () => { … }, 60_000)`. Do **not** touch `testTimeout` globally.
4. Verify the file alone: `npx vitest run packages/server/src/__tests__/pi-dashboard-bin-wrapper.test.ts 2>&1 | tail -30`.
5. Verify hermetic: re-run with `HOME=$(mktemp -d)` prefixed, to prove it passes with a clean home (no cached jiti/warm state masking the fix).
6. Commit only that file: `git add <the test> && git commit -m "test: bump pi-dashboard wrapper test timeout to 60s"`; leave unrelated unstaged work (openspec artifacts) alone.
7. `git push` to `develop`.

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session — appropriately, since it was a
one-line, well-scoped fix. The *pattern* is reusable, though:

- **When a spawned/cold-start subprocess test times out at vitest's 5 s default**, the
  fix is a per-test timeout arg (`it(name, fn, ms)`), sized above the inner
  `spawnSync`/subprocess timeout — **not** a global `testTimeout` bump (which hides
  slow tests everywhere) and **not** a `spawnSync` timeout change (that's not the
  ceiling).

If this recurs across several wrapper/PTY/jiti tests, consider a tiny project skill:
"jiti-coldstart-test-timeout" capturing the diagnosis (inner timeout vs. outer vitest
budget) and the `HOME=$(mktemp -d)` hermetic re-verify step.

## 7. Pitfalls & dead ends

- **First edit was overcomplicated → reverted.** If your first instinct is to
  restructure the test or touch config, stop: the correct change here is a single
  `, 60_000)` argument. Do the simple thing first.
- **Relative path in vitest output is misleading.** The failure printed
  `src/__tests__/…` but the file lives under `packages/server/src/__tests__/…`. Run a
  scoped `find` to resolve the real path before reading/editing.
- **A single normal pass can be a false positive.** Cold-start timing depends on cache
  warmth. Re-run with `HOME=$(mktemp -d)` to prove the fix holds from a clean state.
