# How we did it: Unify `/opsx:` and `/opsx-` slash-command aliases — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`/opsx:explore`) — a thinking-only stance, no
implementation. The operator started from a concrete curiosity ("what is this rendered
skill card in my chat?") and let it lead somewhere. The *real* objective surfaced two
prompts later:

> "the possibility to handle **same** the `/opsx:` and `/opsx-` commands"

i.e. the dashboard's bridge prompt-expander resolves `/foo:bar` and `/foo-bar`
asymmetrically — colon→hyphen aliasing exists in only one direction and only against the
local `.pi/prompts/` + `.pi/skills/` scan, never against `pi.getCommands()`. And anything
matched via the alias gets force-classified as a *prompt template*, suppressing the
collapsible skill card. The goal became: **write an OpenSpec change proposal that makes
the two punctuation forms fully interchangeable**, without touching any code (explore →
propose, never implement).

## 2. TL;DR playbook

1. **Enter explore mode** (`/opsx:explore`) to investigate before committing to a change.
   Ask the AI to trace the actual code path (`prompt-expander.ts`) and draw the current
   resolution flow.
2. **Name the asymmetry precisely**: "handle `/opsx:` and `/opsx-` the same." Let the AI
   build a truth-table of which typed form hits which store today.
3. **`create proposal`** — one short prompt. The AI runs `openspec new change`, picks the
   affected capability (`skill-invocation-rendering`), and drafts `proposal.md`.
4. **Fast-forward the artifacts** (`/opsx:ff`) — generate design + spec delta + tasks in
   sequence, each validated (`openspec validate <change>`).
5. **Stress-test the tricky invariant**: "when the original form of a command exists,
   prefer *that* form, not the remapped one." This forces the AI to promote a buried
   parenthetical into a first-class must-hold rule with worked adversarial examples.
6. **Commit only this change's files**: "commit changes" — but verify the AI stages *only*
   the 5 proposal files, not the pile of unrelated unstaged work in the tree.

## 3. How the collaboration unfolded

**Discovery (explore mode).** The AI traced `git log` for the skill-card commit
(`2fa37306 feat(chat): render skill invocations as collapsible cards`), then read
`packages/extension/src/prompt-expander.ts` and rendered the current resolution flow as an
ASCII diagram: local-scan → colon→hyphen alias → `pi.getCommands()` (still colon). It
built a truth-table showing the dead cells where a typed form never resolves. *Why it
worked:* the AI grounded the abstract "handle them the same" ask in the exact 3-step
resolver and the specific store each step queries — so the proposal had a precise target.

**Propose.** On "create proposal" the AI ran `openspec new change
unify-opsx-colon-hyphen-aliases`, identified that it *modifies* an existing capability
(`skill-invocation-rendering`) rather than adding one, and wrote `proposal.md`: replace the
single alias step with a **candidate-name list** (`name`, `:↔-` toggle, `skill:`-prefixed
forms) probed in order across both stores, and rewrite `isSkillResolution` to depend on the
hit's *source*, not the typed punctuation.

**Fast-forward artifacts.** `/opsx:ff` drove design + spec + tasks to 4/4, each validated.
Design captured 5 decisions (candidate-list resolver, tagged result, no scan-time aliasing,
original-form precedence, no envelope changes); the spec delta added a symmetric resolver
requirement with 7 scenarios plus a broadened (punctuation-blind) wrap condition; tasks laid
out 16 items across 4 groups.

**Harden the invariant (the key human intervention).** The operator flagged: original form
must win over the remapped form. The AI re-read its own proposal, found the rule was buried
as a parenthetical, and promoted it to a top-level **must-hold rule** enforced at three
layers — proposal bullet, Design Decision 4 (with the outer-loop-iterates-names /
inner-block-probes-all-stores structure spelled out and the "all local then all registry"
restructuring explicitly forbidden), and **two new adversarial spec scenarios** (both
variants registered as distinct `pi.getCommands()` entries; original-form-in-registry beats
remapped-form-in-local-scan).

**Commit.** On "commit changes" the AI staged *only* the 5 files of this proposal, leaving
the large pile of unrelated unstaged work (honcho-plugin, openspec-change-grouping,
tsx→jiti edits) untouched → `9f50270d`.

## 4. Prompts that worked

- **Goal kickoff** — starting in explore mode let the AI investigate freely before any
  proposal existed. A stronger opener states the target up front:
  *"Explore mode. The bridge prompt-expander resolves `/opsx:` and `/opsx-` asymmetrically —
  trace `prompt-expander.ts`, show the truth-table of which form hits which store, then we'll
  decide on a change."*
- **"the possibility to handle same the /opsx: and /opsx- commands"** — a one-liner that
  named the exact symmetry to fix. High-leverage: it converted an open exploration into a
  bounded scope.
- **"create proposal"** — two words that unlocked the whole OpenSpec artifact chain.
- **"Check proposal: when original form of command exists prefer that form, not the replaced
  and remapped one"** — the single most valuable steer. It caught a correctness invariant
  the AI had under-specified and forced explicit adversarial coverage.
- **"commit changes"** — worked *because* the AI self-limited the stage set; a safer phrasing
  bakes that in: *"commit ONLY this change's files, leave unrelated unstaged work alone."*

**Recommended reusable asset:** the "original-form-first precedence" invariant is exactly the

> When aliasing/normalizing identifiers (`:` ↔ `-`, case folding, prefix forms), the **typed

> both-variants-registered test.

## 7. Pitfalls & dead ends

- **`ls openspec/specs/ | grep -iE 'prompt-tem|slash|command-router|expand'` returned
  nothing** (1 failed command). The capability wasn't named after the code file — it lived
  under `skill-invocation-rendering`. *If a capability grep misses, list the specs dir plain
  and match on behavior, not on the source filename.*
- **Precedence rule invisible in one place.** The invariant was technically present but only
  enforced by a single spec scenario — easy to miss in review. *If a rule matters, enforce it
  at proposal + design + ≥2 spec scenarios including the adversarial case.*
- **Dirty worktree at commit time.** A large pile of unrelated unstaged changes coexisted with
  the proposal. *Always `git add` the change dir explicitly and confirm the staged set before
  committing.*
