# How we did it: Add session-status icons to folder OpenSpec rows — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a *scoping* question, not the real feature:

> "Which other proposal add-rpc-stdin-dispatch-with-keeper-sidecar depends on?"

That was reconnaissance. The **real objective** surfaced two prompts later: the
linked-session rows under each change in the folder OpenSpec section
(`FolderOpenSpecSection.tsx`) were dead — just blue text + trailing lifecycle icons,
with **no live status signal**. You couldn't tell from the folder view whether an
attached agent was thinking, waiting on you, idle, or dead. The goal became: **reuse
the `SessionCard` status vocabulary** (source-icon-as-status-dot: green/yellow/red +
`animate-pulse`) inside the folder row, plus a **blue selection border** matching the
dashboard's existing selected-card idiom — captured as a full OpenSpec change,
implemented TDD, archived, and committed.

## 2. TL;DR playbook

1. **Recon first**: ask the dependency question (`grep depend|requires|blocked` across
   the candidate proposals) to learn which change ships before yours.
2. **Enter `openspec-explore`** — think, don't implement. Have the AI render ASCII
   sketches of *current* vs *proposed* row so you can approve the visual before any spec.
3. **Pin the visual vocabulary**: point the AI at `SessionCard.tsx`'s existing
   status-dot logic (`statusColors`, `deriveDotColor`, pulse rules) and say "mirror it".
4. **Answer the design questions tersely** (`1. A  2. as today  3. status-only …`) —
   each answer becomes a spec scenario.
5. **Scaffold the change**: `openspec change new <name>`, let the AI write
   proposal + tasks (TDD order) + delta spec; `openspec validate <name> --strict`.
6. **`/opsx-apply`**: extract shared helper *first* (`session-status-visuals.ts`),
   unit-test it, refactor `SessionCard` to consume it (regression guard), then wire the
   folder row.
7. **Full gate**: `npm test | tee /tmp/pi-test.log`, `npm run build`,
   `openspec validate --strict`. Triage pre-existing failures out.
8. **`/opsx-archive`** → sync delta specs to main specs → `commit`.

## 3. How the collaboration unfolded

**Phase 1 — Recon (Discovery).** The AI grepped the candidate proposals for
dependency keywords and read the "Depends On" section, answering: this work sits on
top of `fix-extension-slash-commands-in-dashboard`. Cheap, deterministic, and it
framed the surrounding change graph before touching UI.

**Phase 2 — Explore (the design conversation).** Under `openspec-explore` the AI
located the exact render site (`linkedSessions.map(...)` around line 245) and the
`SessionCard` status logic, then drew **ASCII before/after sketches** of the row and a
decision table (status reading, tooltip, hidden-session handling). This was the highest-
leverage phase: the human approved the *look* on paper, so the spec wrote itself.

**Phase 3 — Propose.** `openspec change new` + three files (proposal, tasks, delta
spec). Tasks were ordered TDD: **extract helper → test → refactor consumer → wire new
site → test → docs**. `openspec validate --strict` passed on first scaffold.

**Phase 4 — Apply (TDD implementation).** The AI extracted
`session-status-visuals.ts`, wrote its unit tests, refactored `SessionCard` to import
it (re-exporting `statusColors`/`sourceBadgeColors` for back-compat), threaded a new
`selectedId?` prop through `SessionList → FolderOpenSpecSection`, and wired the
status-icon + selection border into `renderChangeRow`. Two **real latent bugs** in the
original `SessionCard` logic surfaced through the new tests (see §7).

**Phase 5 — Verify & land.** `npm test`, `npm run build`, strict validate. Two failing
tests were triaged as **pre-existing** (a deleted `effective-status.sh`, unrelated
`pi-dashboard-bin-wrapper` jiti machinery) — none in touched files. `/opsx-archive`
synced 2 requirements + 12 scenarios into the main spec; committed `26cc9ee7`
(11 files, +763/−52).

## 4. Prompts that worked

- **Goal / recon prompt** — *"Which other proposal X depends on?"* Good kickoff: it's a
  cheap, answerable question that maps the change graph before any code. Reproduce it as
  the first move whenever you're extending an existing proposal.
- **"Enter explore mode. Think deeply. Visualize freely."** (the `openspec-explore`
  skill) — this unlocked the ASCII sketches and the decision table. High leverage: it
  forced design-before-spec and kept the AI from prematurely implementing.
- **Terse numbered answers** — *"1. A  2. as in today  3. status-only  4. on the icon
  only  5. yes"*. Each line resolved one open design question and became a scenario.
  Effective because the AI had already enumerated the questions; you just index into them.
- **"When session is selected … have a border to indicate the selected card."** A single
  sentence that added a whole second requirement (5 scenarios). Strong because it named
  the exact idiom (border = selection) the codebase already used.
- **`/opsx-apply`, `/opsx-archive`, `commit`** — the skill-driven pipeline; near-zero
  prose, maximum throughput.

**Rewrite of the goal prompt** for a future operator who already knows the feature:
> "In explore mode: the linked-session rows in `FolderOpenSpecSection` show no live
> status. Mirror `SessionCard`'s source-icon-as-status-dot (color + pulse) on each row,
> and add the blue selection border for the selected one. Sketch before/after, then
> scaffold an OpenSpec change with TDD tasks."

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Answer only the literal recon question | Following up with `openspec-explore` to open the real feature | State the feature goal up front; use recon as context, not the task |
| Design status visuals from scratch | "mirror `SessionCard` exactly" (Reading A) | Point at the existing component and say "reuse its vocabulary" in prompt 1 |
| Leave selection unaddressed | "have a border to indicate the selected card" | List *all* interaction states (status **and** selection) in the explore turn |
| Consider bigger pill restyles | "border-only on these tiny pills … one" | Set the scope bar ("smallest change, one border") before implementation |
| Treat pre-existing test failures as blockers | Implicit trust in the AI's triage (it isolated failures to untouched files) | Run `git status` + grep failures against changed files to prove innocence |

## 6. Skills, tools & memory created — and why they're effective

No new pi *skill* or *memory* was created — the session rode the existing OpenSpec
pipeline (`openspec-explore` → `openspec change new` → `/opsx-apply` → `/opsx-archive`)
plus two throwaway `general-purpose` subagents (update `docs/file-index-client.md`;
sync delta specs). What's reusable is the **code asset** it produced:

- **`packages/client/src/lib/session-status-visuals.ts`** — extracts `SessionCard`'s
  inline status-color / icon / pulse tables into a shared, unit-tested helper.
  *Effective because* it turns a copy-pasted visual vocabulary into one source of truth,
  lets the folder row and the card stay in sync, and its tests caught two latent bugs the
  inline version silently carried. **Invoke the same extract-then-reuse pattern** whenever
  a second UI surface needs an existing component's status semantics.

If you repeat this shape often, the skill worth creating is *"mirror a component's status
visuals onto a new surface via a shared helper + regression tests."*

## 7. Pitfalls & dead ends

- **Regex substring false-positive.** A helper test asserted an edge case where the
  color regex substring-matched `bg-` inside `--bg-tertiary`. The original short-circuits
  on ended-state first, so it never fires in practice — the fix was to **drop the
  edge-case test** (verbatim-move semantics), not to "harden" the helper.
- **`ended` + `resuming` inconsistency (real bug).** `deriveDotColor` returned
  yellow+pulse while `deriveIconStatusColor`'s `status === "ended"` short-circuit forced
  muted. Fix: **only mute when the dot color was actually the ended palette**, not when
  resuming/error overrode it. The inline `SessionCard` had carried this latent for ages.
- **Vitest needs a clean HOME.** Runs used `HOME=$(mktemp -d) npx vitest run …` to avoid
  polluting/reading the real `~/.pi`. Do this for component tests.
- **Two pre-existing red tests** (`effective-status.sh` deleted from working tree;
  `pi-dashboard-bin-wrapper` jiti machinery). *If you hit them*: confirm they're
  unrelated with `git status --short` and grep the failure list against your changed
  files before treating them as yours.
- **Spec header drift.** `openspec/specs/openspec-folder-section/spec.md` uses
  `## ADDED Requirements` instead of `## Purpose` + `## Requirements`, so strict validate
  flags it. Pre-existing, unrelated — leave it, note it for a separate cleanup pass.
