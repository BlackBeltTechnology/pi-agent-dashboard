# How we did it: Cutting release v0.5.1 with a dirty tree and broken CI — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a two-word prompt — `build and deploy` — but the *real*
objective only became clear across the next eight steering turns: **cut and ship
release `v0.5.1` of pi-agent-dashboard end-to-end**, which meant (a) unblocking CI,
which was red from a lockfile drift and orphaned typecheck errors, (b) landing the
fixes on `develop`, (c) tagging/publishing the release, and (d) propagating the new
version to the public Astro download site. The twist: the working tree was carrying
~200 files of unfinished feature work (`model-proxy`, `openspec-groups`,
`honcho-plugin`) that both *caused* the CI breakage and *blocked* the clean-tree
release gate.

## 2. TL;DR playbook

1. **Refresh the lockfile with the right Node.** Local Node was v25 (violates
   `"node": ">=22.12.0 <25"`). Run installs under nvm: `export PATH=~/.nvm/versions/node/v22.22.2/bin:$PATH; npm install`, then commit `package-lock.json`.
2. **Fix CI typecheck errors in an isolated worktree**, not the dirty main tree.
   Delegate the mechanical fix to a subagent so the main context stays clean.
3. **Separate "my task" failures from pre-existing failures.** Diff test results
   against the develop tip; call out unrelated red tests instead of fixing them silently.
4. **Land each fix as its own surgical commit + push** (`develop`), verifying
   `tsc -b` clean and the full `npm test` green (4803 passed) before moving on.
5. **At the release gate, STOP on the dirty tree.** Do not auto-clean. Surface the
   ~200 dirty files and get a human decision.
6. **Stash the WIP non-destructively** (`git stash push -u -m "WIP: ..."`), run the
   release-cut pre-flight, then restore the stash after tagging.
7. **Cut the release:** promote `## [Unreleased]` → `[0.5.1]` in CHANGELOG, bump all
   workspace versions (`npm version 0.5.1 --workspaces --include-workspace-root
   --no-git-tag-version` + `node scripts/sync-versions.js`), regen lockfile, commit
   `chore(release): v0.5.1`, tag `v0.5.1`, push branch + tag.
8. **Propagate to the site.** The Release → Sync Release Version → Deploy Site chain
   can race; if the site deployed *before* the version sync, manually re-trigger
   `sync-release-version.yml` then `deploy-site.yml` and verify the live JSON.

## 3. How the collaboration unfolded

**Phase 1 — Build & local deploy.** `build and deploy` triggered `npm run build`,
`pi-dashboard restart` (server up on :8000), `npm run reload` (no bridges). Several
`curl`-to-`/api/restart` attempts failed; the AI fell back to the `pi-dashboard
restart` CLI. *Why it worked:* the CLI is the reliable restart path when raw curl
against the local port is flaky.

**Phase 2 — Lockfile drift.** CI's `npm ci` failed (missing
`@earendil-works/pi-tui`, `chalk`, `marked` from the lock file). The AI discovered
local Node v25 violated the engine range, switched to nvm v22.22.2, ran `npm
install` to refresh the lock, and committed it. *Decision point:* human said
`commit and push` → pushed `b04e0283`.

**Phase 3 — CI typecheck in a worktree.** Human pasted a wall of TS errors and said
*"Create a working tree and fix this… caused by other changes which are not
finished."* The AI spawned a `general-purpose` subagent that made 4 surgical edits
in worktree branch `pi-agent-60f3f737-2278-4a8`: stripped ~134 lines of orphaned
`model-proxy`/`openspec-group` imports from `server.ts`, added a missing
`pendingSpawnsRef` test dep, cast past a TS `never` narrowing, and exported
`JITI_PACKAGES`. It reported `tsc -b` clean **and flagged 4 pre-existing failures as
out of scope**. Merged + pushed `e01353df`.

**Phase 4 — "Fix other issues".** The AI then fixed the 4 pre-existing failures
tied to the `@oh-my-pi` → `@earendil-works` fork migration: updated the expected
package name and the `JITI_PACKAGES` contract to `["jiti", "@mariozechner/jiti"]`,
asserted upstream-wins, deleted an obsolete fork test. Full suite: **4803 passed, 0
failed**, `tsc -b` clean → `d69ed3cb`.

**Phase 5 — Release gate.** On `Relase 0.5.1 and publish site`, the AI ran
release-cut pre-flight, hit the **massively dirty tree** (~200 files), and *stopped
to ask* rather than clean it. On approval it `git stash push -u`, ran pre-flight
clean, promoted the CHANGELOG, bumped every workspace to 0.5.1, committed
`chore(release): v0.5.1`, tagged and pushed `v0.5.1`, then restored the stash.

**Phase 6 — Site propagation.** The GH Release auto-published (not draft). But
`Sync Release Version` failed on a push race against the release event. The AI
manually re-ran `sync-release-version.yml` (committed `d11f3ad2`), noticed Deploy
Site had used pre-sync data, re-ran `deploy-site.yml`, then fetched the live
`latest-release.json` to confirm the site reads **v0.5.1**.

## 4. Prompts that worked

- **Goal prompt — `build and deploy`.** Too terse to be a good kickoff; it only
  worked because the operator stayed in the loop. A stronger version:
  *"Cut release v0.5.1: fix CI (lockfile + typecheck), land on develop, tag it, and
  propagate to the site."*
- **`Create a working tree and fix this. This caused because other changes which is
  not finished effect this file: <pasted errors>`** — high-leverage: it named the
  *isolation strategy* (worktree) AND the *root cause* (unfinished parallel work),
  so the AI could scope the fix to orphaned code without touching live features.
- **`fix other issues`** — short unlock that authorized cleaning up the pre-existing
  failures the AI had deliberately flagged-but-skipped in Phase 3.
- **`release astro site with 0.5.1`** — the follow-up that caught the sync/deploy
  race the automatic pipeline missed.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Retry `curl` against `/api/restart` repeatedly when it failed | (implicit) let it fall back to `pi-dashboard restart` | Prefer the CLI restart path first; don't loop on raw curl |

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were persisted this session, but two repeatable patterns
deserve to be captured:

- **Isolated-worktree typecheck fix (via subagent).** Spawning a `general-purpose`
  agent to fix CI typecheck errors in a throwaway worktree branch kept ~200 files of
  unfinished WIP out of the fix, kept the main context clean, and produced a
  4-file surgical diff that merged cleanly. *Invoke when:* CI is red from orphaned
  code and the main tree is too dirty to work in directly.
- **Stash-gated release cut.** `git stash push -u -m "WIP: ..."` → run release-cut →
  `git stash pop` is the safe way to satisfy the clean-tree gate without losing
  in-progress feature work. *Invoke when:* you must cut a release but the tree
  carries unlanded work. The existing `release-cut` skill should note this stash
  escape hatch explicitly.

## 7. Pitfalls & dead ends

- **`npm ci`/`npm install` under Node v25 silently drifts the lock.** The repo pins
  `>=22.12.0 <25`; use nvm v22.22.2 or the lock will keep mismatching CI.
- **`curl -X POST /api/restart` was flaky** (5 failed variants). Use `pi-dashboard
  restart` instead of grinding on curl/node fetch one-liners.
- **Fixing pasted errors ≠ fixing CI.** Phase 3 left 4 pre-existing failures; only
  the explicit `fix other issues` turn made the suite fully green. Always diff
  against the develop tip and surface unrelated red.
- **Release pipeline race.** `Sync Release Version` can fail on a push race against
  the `release: published` event, and `Deploy Site` may run *before* the version is
  synced — the live site then shows the OLD version. Re-trigger
  `sync-release-version.yml` then `deploy-site.yml`, and confirm the deployed JSON.
- **Restoring the stash reintroduces the CI-breaking files.** After
  `git stash pop`, the `model-proxy`/`openspec-groups`/`honcho-plugin` WIP is back —
  land it properly before the next release cut.
