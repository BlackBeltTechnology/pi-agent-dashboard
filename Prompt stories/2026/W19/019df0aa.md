# How we did it: Fix the UUID-becomes-session-name bug — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened with an observation dressed as a question:

> "When new session started, the UUID became the name. What was recent changes and related to what proposal?"

The *real* objective, once the discovery turns clarified it: **root-cause a regression
where a freshly-spawned dashboard session gets auto-named with a raw UUID instead of a
human slug, tie it to the proposal that introduced the class of bug, then fix it
properly through the full OpenSpec loop** — propose → design → spec → tasks → apply →
verify → archive → commit. Not just a patch: a durable, spec-backed fix with
defense-in-depth so the same class of bug can't recur a third time.

## 2. TL;DR playbook

1. **Ask the diagnostic question first, not "fix it".** Prompt: *"X happened. What recent changes caused it and which proposal is it related to?"* — this forces a git-archaeology + data-flow trace before any code moves.
2. Let the AI trace the cascade end-to-end and draw a **Mermaid data-flow diagram** (tool event → `detectOpenSpecActivity` → `event-wiring.ts` auto-attach → `attachRenameTarget` → `rename_session`). Confirm the direct cause line.
3. Say **`create proposal`** — the AI scaffolds `openspec new change fix-uuid-rename-bug` and writes `proposal.md`.
4. Say **`/opsx:ff`** (fast-forward) to generate `design.md`, `specs/proposal-attachment/spec.md`, and `tasks.md` in one shot; require `openspec validate <name> --strict` to pass.
5. Say **`commit`** to land the proposal artifacts alone (keep unrelated unstaged work untouched).
6. Before implementing after a gap, prompt **"Check with current implementation, is it actual?"** — re-verify the proposal against HEAD so you don't implement against stale assumptions.
7. Say **`/opsx:apply`** — TDD loop: failing tests first (slug-shape rejection), then the `isValidOpenSpecChangeSlug` helper gating all 3 detector branches (Read/Write/Bash), then the defense-in-depth guard at the rename site in `event-wiring.ts`.
8. Say **`build and reload`** — restart server, `npm run reload` the bridges; observe already-corrupted UUID sessions as live proof of the bug.
9. Run the manual smoke tests (negative UUID path + positive slug path), then **`/opsx:verify`** and **`/opsx:archive`** to sync the delta spec into main specs.
10. **`commit`** the implementation — but **check `git branch --show-current` first** (see Pitfalls: the branch drifted mid-session).

## 3. How the collaboration unfolded

**Phase 1 — Discovery / git archaeology (prompts 1–2).**
The AI ran ~30 `git log`/`grep` sweeps across all branches and the archive to find the
naming-on-spawn origin. It surfaced the most-related archived proposal
(`fix-mobile-attach-proposal-display`, the `attachRenameTarget`/`detachShouldClearName`
witness rule) and, crucially, the *sibling* bug `fix-openspec-flag-rename-bug` — the
same class, previously "fixed" with only a `-`-prefix guard. *Why it worked:* asking
"what proposal is this related to?" turned a vague symptom into a documented lineage,
which made this the **second regression of the same class** and justified a stronger
fix than the last one.

**Phase 2 — Root-cause trace (prompt 2, "yes").**
The AI produced a Mermaid diagram pinning the direct cause: the detector's
`[^\s"']+` token capture accepts *anything*, including a UUID, then the auto-attach +
auto-rename cascade renames the still-unnamed session. Decision point: the human's
"yes" authorized turning the trace into a proposal.

**Phase 3 — Artifact generation (prompts 3–5).**
`create proposal` → `/opsx:ff` generated all four artifacts. Design made 5 explicit
decisions — the key one being to **reverse the prior "no duplication / single source"
rule** and add defense-in-depth at the rename site, precisely because the detector-only
fix had already failed once. `commit` landed only the 5 artifacts (commit `1698678` on
`develop`), leaving the user's other unstaged work alone.

**Phase 4 — Re-verification after a ~42h gap (prompt 6).**
"Check with current implementation, is it actual?" — the AI re-checked every proposal
claim against HEAD line-by-line and even found a *refinement* (the `-` guard was
bash-branch only; Read/Write had no guard at all), confirming the proposal without
needing edits. *Why it worked:* cheap insurance against implementing on stale ground.

**Phase 5 — TDD implementation (prompts 7–8).**
`/opsx:apply`: 7 failing tests first, then `isValidOpenSpecChangeSlug`
(`^[a-z][a-z0-9-]{0,63}$`) gating all 3 branches; then an *isolated* new test file
(`auto-attach-slug-defense.test.ts`) that **mocks the detector to return a UUID** to
test the rename-site guard independently. Full suite: the change contributed 0 new
failures (the one red test was pre-existing untracked `doctor-core.ts` work).
`build and reload` restarted the server and reloaded 13 bridges.

**Phase 6 — Smoke, verify, archive, commit (prompts 9–14).**
Manual negative/positive smoke tests (user ran them, reported "tests ok"), then
`/opsx:verify` (17/17 tasks, requirement→code→test map), `/opsx:archive` (delta synced
to `openspec/specs/proposal-attachment/spec.md`), and a final `commit`. Decision point
surfaced at the very end: the working branch had silently switched to
`simplify-electron-bootstrap-derived-state`, orphaning the proposal commit on `develop`.

## 4. Prompts that worked

- **The goal prompt** — *"When new session started, the UUID became the name. What was recent changes and related to what proposal?"* Effective because it pairs the **observable symptom** with two research demands (recent changes + related proposal). It front-loads diagnosis and prevents a premature patch. A future-you upgrade: add *"draw the data-flow from event to rename"* to get the Mermaid trace on turn one.
- **High-leverage one-worders:** `yes` (authorize proposal), `commit`, `build and reload`, `1`, `tests ok`. Each is tiny because the AI had already laid out numbered options — the human just picked. *Lesson:* when the AI ends a turn with an explicit menu, a single token steers it.
- **`Check with current implementation, is it actual?`** — the single most valuable steering prompt. After a multi-day gap it forced a full re-validation against HEAD before any code was written. Bake this in as a habit whenever apply follows propose by more than a few hours.
- **Slash-command prompts** (`/opsx:ff`, `/opsx:apply`, `/opsx:verify`, `/opsx:archive`) drove the OpenSpec lifecycle deterministically. These map to the repo's `openspec-*` skills — invoking them by name is the reproducible path.

## 5. Steering & corrections (what to watch for)

**Skill worth creating:** a `diagnose-auto-rename-regression` project skill capturing the

## 7. Pitfalls & dead ends

- **Vitest needs an isolated HOME.** The detector test only passed under `HOME=$(mktemp -d) npx vitest run ...` — the first bare run failed. Use a throwaway HOME for these suites.
- **The pre-existing red test is not yours.** The full-suite failure was `doctor-core.ts:565` (`no-direct-platform-branch`) in *untracked* work already in the tree. Don't chase a failure your diff didn't introduce — confirm the file is outside your change set.
- **Strict spec validation fails repo-wide.** `openspec validate --strict` on main specs fails because they use `## ADDED Requirements` instead of `## Requirements` — pre-existing on every main spec, not something your sync introduced. Change-level strict validation is the one that must pass.
- **Branch drift over a multi-day session.** The proposal commit `1698678` landed on `develop`, but by the final commit the branch was `simplify-electron-bootstrap-derived-state` (`eb978fb`) — splitting the change across two branches. Check the current branch before every commit; reconcile via cherry-pick or merge-back, not a blind re-apply.
- **Already-corrupted sessions don't self-heal.** The design deliberately ships **no migration/backfill** — sessions already named with a UUID keep that name; clear them via the rename UI or by detaching the UUID-shaped `attachedProposal`.
