# How we did it: hardening silent worktree-spawn failures — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) with a vague symptom: the
dashboard's **+Worktree dialog** "was not working" — clicking `Spawn →` on a row seemed
to do nothing. The real objective, once the steering turns clarified it, was: **find out
why spawning a pi session into a sibling worktree silently fails, prove it end-to-end with
a live browser, decide whether the bug leaks into unrelated projects, then turn the
finding into a shipped OpenSpec change** (`harden-worktree-spawn`) that (a) auto-installs
`node_modules` for bridge-dependent worktrees and (b) surfaces a global toast when a
`spawn_error` arrives for an off-screen cwd. It grew from "explore a symptom" into a full
proposal → design → specs → tasks → TDD implementation → worktree-hand-off.

## 2. TL;DR playbook

1. **Start in explore mode, not implement mode.** Investigate the symptom before proposing
   a fix. State the candidate failure modes explicitly ("here are 4 plausible causes").
2. **Reproduce with the browser + a live log tail, not by reading code.** Background a
   `tail -F ~/.pi/dashboard/server.log`, click the actual button, correlate the log.
3. **Separate "spawn worked" from "UI rendered".** The first hypothesis (UI keyed by cwd)
   was wrong; the log proved the session registered but the card looked absent.
4. **Chase the real signal:** `~/.pi/dashboard/sessions/spawn-failures.log` →
   `REGISTER_TIMEOUT` → bridge never attaches → **worktree has no `node_modules`** and its
   `.pi/settings.json` `source: ".."` resolves to the wrong parent.
5. **Ask the blast-radius question up front:** "does this hit unrelated projects?" Answer
   in the proposal (Bug A = pi-dashboard-only; Bug B = generic silent-failure plug).
6. **Fast-forward the OpenSpec artifacts** (`openspec-ff-change`): proposal → design →
   specs → tasks in one pass, validating clean.
7. **Apply strict TDD, group by group** (`openspec-apply-change`): tests first, one
   `npm test` at the very end per your pacing — 9 groups, 48 tasks.
8. **Hand off cleanly into a git worktree:** move ONLY this session's files onto a fresh
   branch from `develop`; re-apply any file that a foreign WIP import polluted; verify with
   a full green suite in the worktree before declaring done.

## 3. How the collaboration unfolded

**Phase 1 — Explore & first (wrong) hypothesis.** The AI traced the wiring
(`WorktreeSpawnDialog → onSpawn → handleSpawnSession → spawn_session`) and theorized the
error display was keyed by cwd, so off-screen cwds swallowed the banner. Plausible, but
unproven. *Why it mattered:* the operator immediately pushed back ("Not resolved. Use
browser to test") — reading code alone had produced a theory, not a fact.

**Phase 2 — Live reproduction (the turning point).** The AI backgrounded a server-log tail,
asked the human to click the button, and correlated events. This flipped the diagnosis
twice: first it showed the session **did** register (so "spawn works, UI broken"), then a
plugin-refresh banner was masking the new cards, then the **non-main row** produced *no*
`session registered` line at all. *Why it worked:* every claim was tied to a log line or a
screenshot, not a guess.

**Phase 3 — Root cause.** Following `spawn-failures.log` → `REGISTER_TIMEOUT` → the AI found
the sibling worktree had **no `node_modules`** and a `.pi/settings.json` whose
`source: ".."` pointed at `/Users/robson/Project/` (worktree parent) instead of the repo.
Bridge import fails → `register_session` never called → 30s watchdog → silent drop.

**Phase 4 — Blast-radius decision.** The human asked "is this a special case to pi-dashboard
or does it break unrelated projects?" The AI answered structurally: **Bug A** (bridge crash)
needs three conditions true only when developing pi-dashboard from source; **Bug B** (silent
`spawn_error`) is generic. That framing scoped the whole proposal.

**Phase 5 — Artifacts + TDD implementation.** `openspec-ff-change` produced all 4 artifacts;
`openspec-apply-change` drove 9 groups / 48 tasks with tests-first, deferring the single
`npm test` to the end per the operator's pacing. Result: 16 new files, 6659 tests green.

**Phase 6 — Worktree hand-off & merge confirmation.** The human said "don't use jj — create a
git worktree from develop and move all this session's changes there." The AI moved **only**
its 36 files, caught a foreign `dashboard-config-api.js` WIP import in `App.tsx` and
re-applied that file surgically, then later confirmed the work had actually merged as
`4264ac2a` (PR #52) and cleaned up the now-redundant worktrees.

## 4. Prompts that worked

- **The goal prompt (explore-mode skill).** Entering as a *thinking partner* rather than an
  implementer kept the session from coding a fix before the root cause was proven. Good
  kickoff — but pair it with "reproduce it live before theorizing."
- **"Not resolved. Use browser to test."** The single highest-leverage steering turn. It
  converted a code-reading theory into an evidence-driven reproduction and exposed that the
  first hypothesis was wrong.
- **"Is it cause problems in other projects which unrelated?"** Forced a blast-radius
  analysis that scoped Bug A vs Bug B and shaped the proposal's gating heuristic.
- **"dont use jj. Create a git worktree named harden-worktree-spawn based on develop and
  move all this session changes there."** Precise, unambiguous hand-off instruction —
  branch base, name, and "only this session's changes" all specified.
- **"Is this changes already merged to develop?"** A verification prompt that caught the AI's
  own stale claim (it had said "not merged"; re-checking `git log` showed PR #52 was in).

**Rewrite of a weak prompt:** the opening "not working" was too vague. Stronger:
*"The +Worktree dialog's `Spawn →` appears to do nothing on non-main rows. Reproduce it live
with the browser + server-log tail before proposing a cause."*

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was persisted this session, but the workflow is highly repeatable and
three assets already carried the weight:

- **`openspec-explore` → `openspec-ff-change` → `openspec-apply-change` chain.** Explore keeps
  investigation honest (no coding until root cause proven); ff-change scaffolds all four
  artifacts in one pass; apply-change drives grouped TDD. *Invoke when* a symptom needs
  diagnosis before it becomes a shipped change.
- **Live-repro pattern (log tail + browser).** `tail -F ~/.pi/dashboard/server.log` in the
  background + the `browser` skill to click the real button. *Invoke when* a UI action
  "does nothing" — it distinguishes server-side success from client-render failure.

**Recommended skill to create:** a `diagnose-spawn-register-timeout` project skill capturing
the exact signal chain (`spawn-failures.log` → `REGISTER_TIMEOUT` → missing `node_modules` /
`source: ".."` misresolution). *(One already exists in this project's memory store — reuse
it before re-deriving.)*

## 7. Pitfalls & dead ends

- **Reading code first produced a wrong theory (cwd-keyed banner).** If a UI action "does
  nothing," reproduce live before theorizing.
- **A plugin-refresh banner masked the new cards.** The cards *were* rendering; a stale
  server-vs-client hash banner made it look broken. Check for refresh/version banners.
- **`.pi/settings.json` `source: ".."` in a worktree resolves to the worktree's parent**, not
  the repo root — silently loads a bridge path that doesn't exist.
- **A sibling worktree with no `node_modules` crashes the bridge on import** → 30s
  `REGISTER_TIMEOUT`, swallowed silently. If a spawn times out, check the worktree has deps.
- **Copying "all my files" carried a foreign `dashboard-config-api.js` WIP import.** When
  moving changes into a new branch, re-apply polluted files from `develop`, don't copy blind.
- **Answering "is it merged?" from memory was wrong.** `develop` had advanced; the work was
  already in as PR #52. Always re-check `git log --all`.
