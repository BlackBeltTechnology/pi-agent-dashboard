# How we did it: Add a "+Worktree Session" dialog to the dashboard — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened tiny — `create a worktree in tmp from develop and make as CWD` —
and immediately turned into a design question: *"Is there any API in pi to respawn
this session and set cwd?"* That reframed the whole thing. The **real objective** that
emerged across 28 steering turns: give the dashboard a first-class **git-worktree
workflow** — a `+Worktree` button on each folder group that opens a unified dialog
(list existing worktrees + create a new one from a base branch), spawns a pi session
in the worktree, groups that session's card *under its parent repo* (not orphaned),
and shows a `worktree` pill on the card. It became a full OpenSpec change,
`add-worktree-spawn-dialog`, implemented across 5 packages in 11 sections (~57 tasks).

## 2. TL;DR playbook

1. **Don't build from the one-line ask.** Enter explore mode
   (`/opsx-explore`) and map what already exists before sketching anything.
2. Ask the AI to **ground the idea in the codebase first** — it found `BranchPicker`,
   `PathPicker`, `git-routes`, `FolderOpenSpecSection`, `spawn(cwd=…)`: nearly every
   piece already existed to reuse, not rebuild.
3. **Find the isomorphism.** The jj `.shadow/` workspace collapse
   (`jjState.workspaceRoot` grouping precedence) is the exact pattern git worktrees
   need — mirror it instead of inventing grouping logic.
4. **Search for prior art before drafting.** Two stale, unimplemented proposals
   (`worktree-awareness`, `workspace-actions`) already overlapped — consolidate and
   supersede them rather than adding a third.
5. Fast-forward the artifacts (`/opsx-ff-change add-worktree-spawn-dialog`): proposal,
   design (8 decisions), tasks, 5 spec deltas. `openspec validate --strict`.
6. Implement on a **feature branch, section-by-section with a pause after each**
   (`§1 shared+bridge → reload`, `§2 server → restart`, … `§11 verify`). Commit +
   test-summary per section.
7. After the client sections, **rebuild + restart** (`npm run build` +
   `POST /api/restart`) — a stale prod-fallback bundle hides new UI.
8. **Verify in the real browser** (browser tool snapshot/screenshot), not by reasoning
   about `canSubmit`.

## 3. How the collaboration unfolded

**Phase 1 — Explore & ground (prompts 2–3).** Instead of `git worktree add`, the AI was
steered into explore mode. It read `BranchPicker`, `PathPicker`, `git-operations.ts`,
`git-routes.ts`, `session-action-handler`, and drew the existing-infra box diagram.
*Why it worked:* the conclusion "this is very buildable — reuse, don't rebuild" came
from evidence, not optimism.

**Phase 2 — Design crystallization (prompts 4–10).** Rapid single-token steering
(`a`, `A`, `2`, `yes`) converged the dialog shape, the base-branch fallback chain
(`current → develop → main → master`), the `.worktrees/<slug>` path layout, and the
`.git/info/exclude` (not `.gitignore`) decision. The human caught a real problem early:
*"sessions grouped by pinned directory … it will not be rendered under pinned
directory."* The AI traced `resolveSessionGroupPath` and found the fix mirrors
`jjState.workspaceRoot` exactly.

**Phase 3 — Prior-art reconciliation (prompt 11 area).** Before writing artifacts the AI
discovered `worktree-awareness` and `workspace-actions` — both drafted, zero
implementation. It built an overlap matrix and consolidated into one change that
supersedes both.

**Phase 4 — Artifact generation + commit dance (prompts 11–12).** `/opsx-ff-change`
produced 10 artifacts, validated strict. Because this is a **jj-colocated** repo (main
checkout on a jj working copy, not directly on `develop`), the AI moved the staged
proposal into a `develop` worktree and committed there (`eaa1e438`).

**Phase 5 — Section-by-section implementation (prompts 13–23).** Feature branch
`feature/add-worktree-spawn-dialog`, 11 sections, each: read → edit → test → lint →
commit with a summary block. Cumulative test count climbed to 88+ across the touched
suites. Discipline held: pause + confirm scope before each section.

**Phase 6 — Verify & debug the UI (prompts 24–28).** The disabled-button and
orphaned-card reports triggered a chain of real root-causes (below). The AI stopped
guessing and used the browser tool to snapshot the live DOM.

## 4. Prompts that worked

- **Goal + immediate reframe** (`create a worktree…` → *"Is there any API in pi to
  respawn this session and set cwd?"*). The follow-up question is what turned a
  throwaway command into a feature. **Reuse:** *"Before you run that, is there a
  dashboard-native way to do this repeatedly?"*
- **`Enter explore mode. Think deeply … NEVER write code.`** The single most
  leverage-heavy prompt — it forced grounding before building.
- **`Check the current render. Currently sessions grouped by pinned directory … it
  will not be rendered under pinned directory.`** A domain-knowledge nudge that
  surfaced the grouping bug the AI would otherwise have shipped.
- **`Why isLocalhost?`** Three words that exposed a wrong security assumption (below).
  **Reuse:** always challenge a client-side visibility gate with "why is this gated?"
- **`okay, fix to use parent's bridge`** — a one-line unlock that authorized the
  `rewriteWorktreePiSettings` fix for the dogfooding edge case.

## 6. Skills, tools & memory created — and why they're effective

**No skills or memories were saved this session** — a miss, given how many durable
lessons surfaced. If repeating this, capture:

- A **project memory / skill: "worktree dogfooding loads stale bridge code."** When a
  worktree of *this* repo runs a pi session, `.pi/settings.json`'s `source: ".."`
  resolves to the worktree's own (branch-era) `packages/extension/`, not the main
  checkout — so new bridge code is invisible until the branch lands. The fix
  (`rewriteWorktreePiSettings`) rewrites relative `packages[].source` to absolute paths
  against the main repo. This is non-obvious and cost ~5 debugging prompts.
- A **memory: "the network boundary is the server, not the browser."** Never gate a
  destructive/API button on `isLocalhost()`; `networkGuard` already authorizes remote
  authenticated users. Only hide a button when the action is *impossible* remotely
  (e.g. a native-editor window on the server's display).
- A **skill: "jj-colocated repo → commit OpenSpec artifacts via a `develop`
  worktree,"** since the main checkout isn't directly on `develop`.

## 7. Pitfalls & dead ends

- **`/tmp` worktree vanished between sessions** (macOS tmp cleanup). The commit
  `eaa1e438` survived in the git object store on `develop` anyway — verify with
  `git merge-base --is-ancestor <sha> develop` before panicking. Use a persistent path
  (`~/Project/wt-…`), never `/tmp`, for worktrees you'll return to.
- **Disabled "Create + Spawn" button** had two causes, neither the obvious one: (a) a
  thrown `createWorktree` left `submitting` stuck `true` (no try/catch → wrapped it);
  (b) the *real* cause — a **stale prod-fallback client bundle** that never contained
  the `+Worktree` button. Fix: `npm run build` + `POST /api/restart`.
- **Orphaned worktree card** in `/test`: the session reported `gitWorktree: undefined`
  because pi at `/test` loaded **develop-era bridge code** via `source: ".."`. Not a
  grouping bug — a code-loading path bug (the dogfooding trap above).
- **`/reload` doesn't re-read `.pi/settings.json`** — that's loaded once at pi startup.
  A settings-path change needs a kill + respawn of the session, not a reload.
- **Spec envelope mismatch:** the draft spec said `{ error: <code>, message }` but the
  repo convention is `{ error: <human>, code: <classifier> }`. Match existing
  conventions during implementation, and update the spec/tasks to reflect the truth.
