# How we did it: On-demand Electron CI build workflow — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`), a thinking-only stance:
*"Enter explore mode. Think deeply. Visualize freely… you must NEVER write code."* The
real objective surfaced within a few steering turns: the repo could only build Electron
installers through the **release pipeline** (`publish.yml`), which demands a SemVer tag,
an npm publish, and a GitHub Release — all irreversible side effects. The user wanted a
**manual, side-effect-free CI workflow** that builds Electron artifacts on demand
(`workflow_dispatch` only), uploads them as run artifacts you can download from the
GitHub web UI, and **never** publishes to npm or cuts a Release. The design then had to
be captured as an OpenSpec change and implemented.

## 2. TL;DR playbook

1. **Explore first, code never.** Enter `openspec-explore`; have the AI read
   `publish.yml`, `build-installer.sh`, `bundle-server.mjs`, and `app-updater.ts` and
   *diagram* the current 4-job pipeline (prepare→publish→electron×6→github-release).
2. **Force the safety decisions early** via `ask_user`: version-slug shape, no-publish /
   no-release, reusable `workflow_call` boundary, `upload-artifact` only, dispatch-only
   trigger. Lock them in a decision table before any YAML.
3. **Scaffold the OpenSpec change**: `openspec change new add-ci-electron-on-demand-build`
   → `proposal.md`, `design.md`, `tasks.md`, two spec deltas. `openspec validate` until clean.
4. **Spike the one risky assumption**: does `bundle-server.mjs --source-only` produce a
   bundle that boots without an npm-registry round-trip? Write
   `spike-source-only-bundle.sh`, reuse the existing `test-server-launch.sh` Docker harness.
5. **Isolate failures during the spike**: when the Docker boot fails, re-run the harness
   against the *full* bundle to prove the failure is pre-existing, not caused by `--source-only`.
6. **Close the E2E gap**: swap the harness loader from `tsx` to the production `jiti`
   loader → server boots → `GET /api/health` returns 200 in-container. Design proven.
7. **Exit explore, apply the change** (`openspec-apply-change`): extract the electron job
   into reusable `_electron-build.yml`, shrink `publish.yml`'s job 366→15 lines, add
   `ci-electron.yml`, add a safety-lint test that scans both workflows for forbidden
   `npm publish` / release / tag strings.
8. **Commit in clean, described slices** with `jj split`, keeping unrelated local files
   (qa VM config) out of the pushed branch. Push, let CI run.

## 3. How the collaboration unfolded

**Phase 1 — Discovery & diagramming.** The AI read the release workflow and support
scripts, then rendered the existing pipeline and the *proposed* pipeline as ASCII
diagrams. This made the side-effect surface (npm publish = irreversible registry write)
visually obvious and framed every subsequent decision. *Why it worked:* visualizing the
"what you have vs. what you want" delta turned a vague ask into six concrete decisions.

**Phase 2 — Decision locking.** A run of `ask_user` prompts settled: version slug
`<base>-ci.<UTC-stamp>.<branch-slug>.<sha7>` (prerelease segment, branch capped at 20
chars); **no npm publish, no Release** (safe by construction); a new
`_electron-build.yml` reusable `workflow_call` consumed by *both* `publish.yml` and
`ci-electron.yml`; `upload-artifact` only, 14-day retention; `workflow_dispatch` only.
The decision table became the spec.

**Phase 3 — OpenSpec scaffold.** Proposal + design (6 decisions + open-questions list) +
tasks + two spec deltas (new `ci-electron-on-demand-build` capability, modified
`ci-cd-pipeline`). `openspec validate` gated each write.

**Phase 4 — The spike (the heart of the session).** The one unproven assumption —
"`bundle-server.mjs --source-only` yields a runnable bundle" — got an executable answer.
The AI wrote a non-destructive probe (`spike-source-only-bundle.sh`: back up → bundle →
structural assertions → hand off to the Docker harness → verdict). Three failures
surfaced *in sequence*, each isolated and fixed:
- Harness `COPY resources/server/dist` — orphan path present in *neither* bundle → deleted.
- `docker run -it` needs a TTY the `tee`-piped spike lacks → dropped `-it`.
- A `Bonjour` ESM/CJS error — the AI **re-ran against the full bundle**, got the *identical*
  error, and concluded it was pre-existing rot, not a `--source-only` defect.

**Phase 5 — Closing the E2E gap.** The user asked "can we add tests?" The gap: the harness
booted under `tsx` but production uses `jiti`. Swapping to the shipped
`node_modules/jiti/lib/jiti-register.mjs` loader made the server boot to ready and serve
`/api/health` → 200 in 12s inside a clean `node:24-bookworm-slim` container. Every design
assumption now backed by a passing test.

**Phase 6 — Implementation.** Out of explore mode: `_electron-build.yml` written (6 inputs,
per-leg `if:` filter, YAML-validated); `publish.yml`'s electron job replaced with a 15-line
`uses:` consumer; contract test updated (9 pass); `ci-electron.yml` added; a safety-lint
vitest that strips YAML comments then scans for `npm publish` / `gh-release` / `git tag/push v`.
Docs delegated to a caveman-style subagent per AGENTS.md.

**Phase 7 — Clean commits.** `jj split` separated spike, implementation, and unrelated
local work. Only the two described commits were pushed; the qa VM config (machine-specific
ISO path) and already-on-develop openspec files were kept out.

## 4. Prompts that worked

- **The goal prompt (explore-mode kickoff).** Effective because it set a *stance*
  ("think, don't implement") that kept the session in design space long enough to surface
  the safety decisions before any YAML was written. For a faster start next time, pair it
  with the concrete objective: *"Explore a manual, side-effect-free CI workflow that builds
  Electron artifacts on demand and uploads them as run artifacts — no npm publish, no Release."*
- **High-leverage micro-answers.** `"#4 - use A"`, `"2"`, `"yes"`, `"1"`, `"ok"` — terse
  replies to the AI's numbered decision menus. They worked *because the AI had structured
  the choices as a table first*; the lesson is to make the AI present enumerated options,
  then answer by number.
- **"Is it possible to test bundle-server.mjs in a docker that the design works or doesn't?"**
  The single most valuable steer — it converted a design assumption into an executable spike.
- **"Is it possible to add tests?"** Pushed past a deferred E2E gap and produced the
  jiti-loader boot proof. Both "is it possible…" prompts unlocked the empirical backbone.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stay abstract in explore mode | "Is it possible to test … in docker that the design works or doesn't?" | Ask for an executable spike of the riskiest assumption *before* committing to the design |

## 6. Skills, tools & memory created — and why they're effective

- **`spike-source-only-bundle.sh`** (kept in `packages/electron/scripts/`). Captures the
  empirical design record: bundle → structural assertions → Docker boot → verdict.
  *Effective* because it turns "we think the source-only bundle is runnable" into a
  repeatable PASS/FAIL, and doubles as a future regression harness. Invoke it whenever the
  bundle format or loader changes.
- **`test-server-launch.sh` fixes** (orphan `COPY dist` removed, `-it` dropped, jiti loader).
  Made a rotted harness actually boot the server to `/api/health`. Reuse for any
  "does the bundled server start in a clean container" question.
- **`ci-electron-no-side-effects.test.ts`** — a safety-lint that fails CI if either workflow
  gains an `npm publish` / release / tag-push string. *Effective* because it makes the
  no-side-effects guarantee enforceable, not just documented.
- **Subagent (`general`)** for the `docs/` writes in caveman style per AGENTS.md. Reuse the
  DocScribe pattern for any `docs/` prose so the main agent never edits docs directly.

  *Recommended skill to create:* a `spike-a-design-assumption` procedure — "write a
  non-destructive probe script, reuse the nearest Docker harness, isolate failures by
  A/B-ing against the baseline path" — since this loop recurred and is clearly reusable.

## 7. Pitfalls & dead ends

- **Orphan `COPY resources/server/dist`** in the harness → the `dist/` path exists in
  *neither* the source-only nor the full bundle (tsx/jiti compile TS on the fly). If a
  COPY fails, confirm the path exists in the current bundle before assuming your change broke it.
- **`docker run -it` under `tee`** → "the input device is not a TTY". Drop `-it` for
  piped/non-interactive runs.
- **`Bonjour` ESM/CJS interop error** at boot looked like a `--source-only` regression but
  was pre-existing — the full bundle hit the *identical* error. Always A/B a failure against
  the baseline path.
- **`tsx` vs `jiti` loader mismatch** — the harness booted under `tsx` while production uses
  `jiti`; the real E2E proof only came after swapping to the shipped jiti register URL.
- **Safety-lint false positives** — the lint matched `"no npm publish"` inside a doc comment
  and an `echo` summary. Strip YAML comments and reword human-readable strings that contain
  trigger tokens.
- **Stray files in commits** — `jj` snapshotted unrelated local work (qa VM config, openspec
  files already on `develop`) into `@`. Verify each file against `origin/develop` before
  including; keep machine-specific config (hardcoded ISO paths) permanently local.
