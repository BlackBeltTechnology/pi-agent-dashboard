# How we did it: Rewriting the `jj-workspace` skill so an LLM operates jj correctly — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` — think, don't implement).
The operator's live pain was a "neurotic" feeling about jujutsu (`jj`): every session
seemed to sit in a *detached HEAD* state and the existing `jj-workspace` skill kept
nudging the agent to "fix" it. The real objective — which only crystallised across the
steering turns — was: **rewrite the `jj-workspace` SKILL.md so that an LLM reading it
internalises that detached HEAD is the correct steady state, stops treating reattachment
as routine hygiene, and gets pointed at the right sibling skill when the task is actually
"push work back to the git remote."**

## 2. TL;DR playbook

1. Enter explore mode and ask the AI to *explain the mechanism first* ("why does jj always
   look like detached HEAD?") — get a diagram of jj's `@`-is-a-real-commit model before touching the file.
2. Confirm the mental model is right, then say **`improve skill`** to authorise the rewrite.
3. Have the AI restructure `.pi/skills/jj-workspace/SKILL.md`: lead with the one thing that
   matters (`@` is a commit, HEAD detachment is normal, read `jj st` not `git status`).
4. **Demote** the reattachment procedure to a footnote — keep the script contract verbatim,
   but frame it "for handing off to non-jj tooling, NOT routine hygiene."
5. Promote the safety rules (forbidden git commands, jj quick-reference) near the top.
6. Ask the scoping question explicitly — *does this skill also cover getting data back to
   the remote?* — and let the AI map skill boundaries before adding cross-links.
7. Say **`yes`** to authorise linkage: add a "Related skills" block under the title and
   redirect rows in the jj-vs-git table (`push to remote` → `jj-workspace-fold-back`,
   `uncommit` → `jj-uncommit-to-working-copy`).
8. Verify with `wc -l` that the file stayed tight (~205 lines) and no script semantics changed.

## 3. How the collaboration unfolded

**Phase 1 — Diagnose the mechanism (explore).** Instead of jumping to edits, the AI
"thought out loud" and drew the jj/git divergence: jj snapshots the working copy `@` as a
real commit on every keystroke; git's HEAD must point at a *finalized* commit, so the git
backend exports `HEAD@git = @-` and leaves git detached there. Framing the problem as
*structural, not a bug* is what made the rest of the work coherent — the fix was
documentation weighting, not a script change.

**Phase 2 — Rewrite by re-weighting (`improve skill`).** With `ls`/`wc -l` recon of the
skill folder, the AI rewrote SKILL.md v1→v2: new lead section ("the one thing you have to
internalise"), reattachment demoted from ~40% of the body to a bottom footnote (script
contract preserved verbatim), safety rules promoted, risks tightened from 5 paragraphs to
5 one-liners, redundant "shipping back" prose cut.

**Phase 3 — Fix the boundary (`IS the skill about … back to git repo?` → `yes`).** The
operator's scoping question exposed that "push back to the remote" belongs to a *sibling*
skill (`jj-workspace-fold-back`), not this one. The AI mapped the two skills'
responsibilities, then added a "Related skills" pointer under the title plus two redirect
rows in the quick-reference table — so an agent reaching for `git reset HEAD~1` or
`git push` hits a row that sends it to the right skill instead of guessing.

## 4. Prompts that worked

- **The goal prompt (explore-mode kickoff).** Effective because it forced *mechanism before
  edit*: the AI explained *why* jj looks detached before proposing any change, so the rewrite
  targeted the real cause (doc weighting) not a symptom. A stronger explicit version:
  *"In explore mode, explain why jj sessions always look like detached HEAD, then propose how
  the jj-workspace skill should be reweighted so an LLM stops trying to 'fix' it."*
- **`improve skill`** — a two-word high-leverage unlock. It worked only because Phase 1 had
  already established the shared model; the AI knew exactly what "improve" meant. Reproduce
  the *setup*, not just the terse prompt.
- **`IS the skill about how committed data will back to git repo?`** — a scoping question
  that did more than any instruction: it made the AI enumerate skill boundaries and discover
  the missing cross-link. Stronger phrasing: *"Which skill owns pushing jj work back to the
  git remote — this one or a sibling? Map the boundary."*
- **`yes`** — a one-word authorisation to act on the boundary analysis.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created; the work *improved an existing skill* —
`.pi/skills/jj-workspace/SKILL.md`. Why the improvement is effective:

- **Reweighting for LLM attention.** Leading with the mental model and promoting forbidden-
  command rules puts the load-bearing content where the model reads first, so future agents
  stop the reattachment reflex without extra prompting.
- **Footnote-not-delete.** The reattachment script contract (exit codes, preconditions,
  forbidden alternatives) is preserved verbatim, so existing callers don't break — only its
  *framing* moved. This is the reusable pattern: demote by relocation + explicit "not
  routine" warning, never by deletion.
- **In-table cross-links.** Redirect rows (`push to remote` → `jj-workspace-fold-back`,
  `uncommit` → `jj-uncommit-to-working-copy`) route an agent from the git command it was
  about to run to the skill that actually handles it.

If this pattern recurs, a `skill-reweight-for-llm-attention` skill would be worth creating:
lead with the mental model, promote safety rules, demote procedures to footnotes with a
"not routine" warning, and add in-table cross-links to sibling skills.

## 7. Pitfalls & dead ends

- **No failed commands** this session (4 bash calls, 0 errors) — the recon-first approach
  (`ls`, `wc -l` before editing) kept it clean.
- **The trap avoided:** editing the skill to make reattachment *smoother* would have doubled
  down on the wrong behavior. The fix was to make reattachment *rarer and clearly optional*.
  If you feel pulled to "improve the reattach flow," stop — the real bug is that the doc
  encourages reattaching at all.
- **Scope creep the other way:** don't fold "push to remote" content into `jj-workspace` —
  keep it in the `jj-workspace-fold-back` sibling and cross-link instead.
