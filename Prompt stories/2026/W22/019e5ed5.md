# How we did it: Multiline + image-paste for `ask_user{method:"input"}` — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **OpenSpec explore mode** — a "think, don't implement" stance:

> _"Enter explore mode. Think deeply. Visualize freely. Follow the conversation wherever it goes… You must NEVER write code or implement features… You MAY create OpenSpec artifacts."_

Once the steering turns landed, the *real* objective emerged: the dashboard's main
prompt composer already supports **multiline text + clipboard image paste**, but the
`ask_user{method:"input"}` dialog is still a bare single-line `<input type="text">`.
The goal was to **close that asymmetry** — give `ask_user` inputs the same multiline
textarea and image-paste affordance — and capture the whole design as a committed
OpenSpec proposal (proposal + design + spec delta + tasks), pushed to `develop`,
*without writing any implementation code*.

## 2. TL;DR playbook

1. **Kick off in explore mode** with the `openspec-explore` skill — force a think-first stance so the AI maps architecture before proposing anything.
2. **Let the AI diagram the current dataflow** (`ask-user-tool.ts → ctx.ui.input → PromptBus → InputRenderer`) so both sides share the same mental model.
3. **Correct the AI's false-novelty assumption early** — point out the main composer *already* solves image paste (`CommandInput` + `useImagePaste` + `ImagePreviewStrip`). This reframes the work as "port an existing pattern," not "invent one."
4. **Force a design decision with a single letter** — when the AI lays out options A/B/C, reply `C` to lock the disk-backed side-channel approach.
5. **Add the one hard requirement the AI missed**: "the images also **read**" — i.e. bytes must hit disk so the LLM's `Read` tool can see them (not just browser thumbnails).
6. **Batch the scope-closing decisions in one steering turn**: defer a prune tool, confirm batch sub-questions get the same treatment, confirm the renderer is reused across `polyfillMultiselect`, no discoverability hint.
7. **Switch to `openspec-ff-change`** to fast-forward all four artifacts (proposal → design → spec delta → tasks) in one pass; `openspec validate` until clean.
8. **Commit the change dir alone** with `jj split` (isolate the change files from unrelated working-copy edits), then `jj bookmark set develop` + `jj git push --bookmark develop`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / mental-model build (13:12–13:24).**
The AI opened by ASCII-diagramming the full `ask_user` input path down to
`PromptResponseBrowserMessage{answer:string}` ("string only"). It initially framed
multiline+paste as novel. **Decision point:** the human's steering #1 ("in our prompt
image is replaced the filename… there is already a method") corrected this — the AI
re-scanned and found `CommandInput`, `useImagePaste`, and the
`(text, ImageContent[]) → [{type:"text"},{type:"image"}]` pipeline already in place.
This reframed the whole effort as *porting a proven pattern into a second renderer*.

**Phase 2 — Design convergence (13:32–14:33).**
The AI surfaced options A (multi-block tool_result), B (synthetic user-turn
injection), C (disk-backed side channel). **Decision point:** the human answered `C`.
The AI then flagged the real subtlety: the existing `pi-asset:<hash>` scheme is
*display-only* (bytes ride out-of-band via `asset_register`, hash is not a filesystem
path) — the LLM can't `Read` it. **Decision point:** steering #3 ("the images also
read") pinned the dual-path requirement: `asset_register` for human-visible
thumbnails **and** a real disk write under `~/.pi/dashboard/attachments/<sid>/` so the
LLM's `Read` gets a genuine path. Steering #4 batched the remaining scope calls
(defer prune tool, batch parity, renderer reuse, silent affordance). The AI then
*verified its own risk claims* against source — confirming `InputRenderer` is the
single global handler for `type:"input"` and that batch sub-questions loop through the
same `ctx.ui.input` → `PromptBus` → `InputRenderer` path.

**Phase 3 — Generate artifacts (14:33–14:42).**
Switching to `openspec-ff-change`, the AI ran `openspec new change`, then filled
`proposal.md` (60 lines), `design.md` (131 lines, 8 numbered decisions with A/B
explicitly rejected), `specs/ask-user-tool/spec.md` (167 lines, 7 ADDED requirements,
28 scenarios), and `tasks.md` (125 lines, 8 groups, 36 checkboxes) — validating clean.

**Phase 4 — Commit & push (14:43–14:45).**
The repo is jj-colocated with unrelated working-copy edits present. **Decision
point:** steering #6 ("commit this proposal to develop"). The AI used
`jj split '<change-dir>/'` to isolate *only* the change files, described the commit,
moved the `develop` bookmark, and `jj git push --bookmark develop` — fast-forwarding
develop while leaving 8 unrelated pre-existing edits untouched in the working copy.

## 4. Prompts that worked

- **The goal prompt (explore-mode skill invocation).** Effective because it forced a
  think-first stance: the AI mapped the entire dataflow and rejected two design
  alternatives *before* writing a single artifact. For a fresh run, seed it with the
  actual target: _"Explore how to give `ask_user{method:'input'}` the same
  multiline+image-paste UX the main `CommandInput` already has."_
- **"there is already a method" (steering #1).** High-leverage: one sentence
  collapsed a whole "invent it" branch into "port the existing `useImagePaste`
  pattern." **Watch for the AI overstating novelty; name the existing implementation.**
- **"C" (steering #2).** A single letter locked the architecture. Works only because
  the AI had first laid out labelled options — always ask for enumerated A/B/C so you
  can decide in one keystroke.
- **"1. The images also read" (steering #3).** The single most important correction:
  it turned a display-only thumbnail scheme into a disk-backed, LLM-readable side
  channel. State this requirement up front next time: _"pasted images must land on
  disk so the agent's Read tool can see them, not just render as thumbnails."_
- **"commit this proposal to develop" (steering #6).** Short, decisive close-out.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Overstate novelty — treat multiline+paste as new work | "there is already a method" (the main composer solves it) | Name the existing implementation (`CommandInput` + `useImagePaste`) in the goal prompt |
| Design for browser thumbnails only (`pi-asset:<hash>`, display-only) | "the images also **read**" — bytes must hit disk for LLM `Read` | State the dual-path requirement (disk write + `asset_register`) as a hard constraint up front |
| Leave scope edges open (prune tool, batch parity, renderer reuse) | One batched turn: defer prune, confirm batch parity, confirm renderer reuse, no hint | List the explicit non-goals + parity requirements in the kickoff |
| Assert risk claims without checking ("renderer is reused… I asserted it, didn't verify") | Let the AI self-verify against source before writing | Ask the AI to grep-confirm every "I believe X is reused" claim before it becomes a design decision |

Scope discipline that worked: the human explicitly *deferred* a `prune-attachments`
tool ("we can add it later if it ever matters") — keeping the proposal tight rather
than gold-plating.

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created in this session. The workflow used three existing
skills as a chain — worth naming because the sequence is the reusable asset:

- **`openspec-explore`** — enforces think-before-build; produced the architecture
  diagrams and the A/B/C option set. Invoke first whenever a change's *shape* is
  unclear.
- **`openspec-ff-change`** — one-shot generation of all four artifacts once the design
  is locked. Invoke only *after* the design decisions are settled, or it will
  fast-forward past unresolved questions.
- **jj-split commit discipline** — isolating a change directory from unrelated
  working-copy edits with `jj split '<dir>/'`. **Recommendation:** this is a clean
  candidate for a small project skill, e.g. `commit-openspec-change-jj`, capturing
  the `split → describe → bookmark set develop → git push --bookmark` sequence.

## 7. Pitfalls & dead ends

- **`openspec change new` vs `openspec new change`.** The first invocation form failed;
  the correct CLI is `openspec new change <name>`. If `change new` errors, flip the
  word order (check `openspec new --help`).
- **`jj split` with no fileset opened an editor / did nothing useful.** The AI first
  tried bare `jj split` and `jj split --insert-before`; what worked was passing the
  path fileset explicitly and, when the editor blocked, `JJ_EDITOR=true jj split
  '<change-dir>/'`. If `jj split` hangs on an editor, set `JJ_EDITOR=true`.
- **`pi-asset:<hash>` is not a filesystem path.** Don't assume the existing image
  scheme gives the LLM a readable file — its bytes flow in-memory via `asset_register`
  for browser display only. A separate disk write is required for `Read` to work.
- **One failed grep** (`ask-user-tool.ts` path guess) — the tool lives at
  `packages/extension/src/ask-user-tool.ts`; renderer at
  `packages/client/src/components/interactive-renderers/InputRenderer.tsx`.
