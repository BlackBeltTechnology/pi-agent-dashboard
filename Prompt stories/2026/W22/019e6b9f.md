# How we did it: A configurable chat-display OpenSpec proposal, explored then surgically shipped — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill), not with a concrete
feature request. The kickoff prompt was the skill preamble itself — *"Enter explore mode.
Think deeply. Visualize freely… you must NEVER write code or implement features… You MAY
create OpenSpec artifacts."* The real objective, which the steering turns clarified, was:
**the dashboard chat/stream view shows too much surface** (token bars, context bars,
reasoning blocks, tool-call cards, huge tool results, turn metadata) — great for power
users, overwhelming for non-technical ones — so **design a configurable display-preferences
system** and capture it as a validated OpenSpec change (proposal + design + tasks + spec),
then commit only those artifacts to `develop`.

## 2. TL;DR playbook

1. Start in explore mode: `openspec-explore`. State the constraint up front — *think and
   draft OpenSpec artifacts, do NOT write implementation code*.
2. **Ground before designing.** Grep the real components (`ChatView.tsx`, `SessionCard.tsx`,
   `tool-renderers/`, `preferences-store.ts`) to catalog every surface the chat view renders
   and where each toggle would attach.
3. Surface the **open design questions as a compact numbered/lettered menu** (granularity,
   defaults, storage side, per-session vs global) so the human answers with one terse line.
4. Lock decisions, then scaffold with `openspec change new configurable-chat-display` and
   write the four artifacts (`proposal.md`, `design.md`, `tasks.md`,
   `specs/chat-display-preferences/spec.md`).
5. `openspec validate <change>` until clean.
6. To ship: detect repo state first (`git status`, `jj status`) — this is a **jj-colocated**
   repo with a detached HEAD and lots of unrelated working-copy edits.
7. **Surgically isolate the 4 files** onto a fresh commit on top of `develop`
   (backup → `jj new develop` → restore files → `jj bookmark set develop -r @` →
   `jj git push --bookmark develop`), then return the working copy to the user's original
   state so unrelated edits stay intact.
8. Answer the audit question honestly: diff `develop` vs working copy to list which
   proposals are committed and which are still local-only.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding (explore stance).** The AI resisted jumping to a schema.
It first grepped the client for the actual surfaces (`TokenStatsBar`, `ContextUsageBar`,
`ThinkingBlock`, `ToolCallStep`, `CollapsedToolGroup`) and read
`packages/server/src/preferences-store.ts`. **Why it worked:** it discovered two facts that
shaped the whole design — server-side prefs *already* split clean (`preferences.json` =
global, `<session>.meta.json` = per-session), and the tool taxonomy was *already* enumerated
by the `tool-renderers/` registry. The design mapped 1:1 onto existing structure instead of
inventing one.

**Phase 2 — Design questions as a menu.** Instead of a prose Q&A, the AI presented the open
choices as a numbered/lettered list. The human answered in two terse turns
(`1. Global / 2. By type / … server side` and `Q1: A Q2: C / 1: askUser always visible…`).
**Decision points locked:** per-element toggles (no presets in Settings); first-launch modal
with 3 presets (dismiss = Standard); `ask_user` hard-coded non-hidable; tool errors hide
with results; tool-call granularity by type (read/bash/edit-incl-Write/agent/generic);
storage global in `preferences.json` + sparse override in `.meta.json`.

**Phase 3 — Generate + validate.** The AI wrote the four artifacts (11 task groups,
5 requirements, 14 scenarios) and ran `openspec validate` to green. It explicitly honored
the explore-mode discipline: **no implementation code written.**

**Phase 4 — Surgical commit ("commit and push").** The AI stopped before acting and flagged
two blockers: detached HEAD, and a working copy full of unrelated changes. It then executed
a jj-colocated extraction: back up the 4 files, `jj new` on top of `develop` (3ab2), restore
files, move the `develop` bookmark, `jj git push --bookmark develop`, and restore the user's
original working-copy commit. Result: commit `d5ed2cb8`, exactly 4 files, unrelated edits
untouched.

**Phase 5 — Honest audit.** The final prompt asked which proposals were *not* committed to
`develop`. The AI diffed `develop` vs the working copy and enumerated the local-only
proposals (`bump-pi-compat-to-0-76`, `restore-pi-version-skew-surface`, the `0.75`→`0-75`
rename), even noting `develop` had advanced past its own push during the session.

## 4. Prompts that worked

- **The goal prompt (explore-mode preamble).** Effective because it set a hard *stance* —
  think + draft artifacts, never implement — which kept the AI grounding and designing
  instead of writing code prematurely. Reuse it verbatim for any "explore this idea" task.
- **`1. Global / 2. By type / 3. ok / … server side`** — a high-leverage one-liner. Because
  the AI had framed the decisions as a numbered menu, the human unlocked the entire schema
  direction in a single terse reply. The lesson: **make the AI present choices as a menu, then
  answer by index.**
- **`commit and push`** — short, but powerful *because the AI had already grounded the repo
  state*. Do not fear terse action prompts once context is established; the AI filled in the
  jj-vs-git nuance.
- **`Is there any proposal is not committed to git develop?`** — a good audit prompt that
  forces a real diff, not a memory-based answer. Rewrite weak "did we commit everything?"
  into this explicit form.

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session — the reusable asset is the **workflow
itself**, driven by the existing `openspec-explore` skill. Two patterns are worth
promoting into durable form:

- **"Ground-before-design in explore mode."** Grep the real components and existing
  persistence layer *before* proposing a schema, so the design maps onto reality. This is
  already the explore-mode discipline; keep invoking `openspec-explore` for it.
- **"Surgical jj-colocated single-purpose commit."** Backup files → `jj new <base>` →
  restore → move bookmark → push → restore working copy. This is a strong candidate for a
  saved **project skill** ("commit-N-files-cleanly-in-jj-colocated-repo"), because the repo
  routinely carries a dirty working copy with a detached HEAD and this dance is easy to get
  wrong.

## 7. Pitfalls & dead ends

- **Detached HEAD + dirty tree.** A plain `git push` would have failed and/or dragged in
  unrelated edits. *If you hit this,* isolate your files onto a fresh commit on top of the
  target bookmark rather than committing the whole working copy.
- **jj vs git confusion.** The repo is jj-colocated; use `jj status`/`jj log`/`jj bookmark`
  and `jj git push --bookmark develop`, not raw `git push`. One `git ls-tree … | diff …`
  command failed during the audit — prefer `jj diff --from develop --to @` for the compare.
- **`develop` moved under you.** A newer commit (`34688753`) landed on `develop` during the
  session. *Always re-check `origin/develop` before concluding your push is the tip.*
- **Directory-rename churn.** `bump-pi-compat-to-0.75` → `bump-pi-compat-to-0-75` (dot→hyphen)
  left both an old committed dir and a new local dir; renames read as add+delete in the diff.
