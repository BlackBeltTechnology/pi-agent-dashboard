# How we did it: Mode-aware server-ready deadlines (15s prod / 60s dev) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened with a vague symptom: **"why server does not start?"** What it
turned out to *really* be was a latent product bug. The dashboard server *was*
starting — but slowly. In dev mode, jiti has to cold-compile ~400 server-side TS
files (measured 25–60 s on this Mac), while two independent readiness deadlines were
hard-coded far shorter: the `/api/restart` health poll at **10 s** and the Electron
`SERVER_READY_DEADLINE_MS` at **15 s**. Every dev-mode cold boot tripped both, logging
`restart failed: new server did not respond to /api/health within 10s` (12+ times
since May 7) and flipping Electron into `loading-page-error`. The real objective,
uncovered by steering: **make both deadlines mode-aware — 15 s prod / 60 s dev — so a
slow-but-healthy dev boot is no longer misreported as a failure**, then ship it as a
scoped commit with tests and docs.

## 2. TL;DR playbook

1. Don't accept the vague symptom. Probe `/api/health` for `mode`, `pid`, `uptime`,
   and **`launchSource`** first — it disambiguates who owns the port.
2. Read the runtime evidence, not the code: `~/.pi/dashboard/restart.log` and
   `server.log`. The repeated `within 10s` line is the smoking gun.
3. Correlate the two symptoms ("restart stuck" + "electron cannot connect") to **one**
   root cause: readiness deadlines shorter than jiti cold-boot time.
4. Locate the two hard-coded constants: `restart-helper.ts` (`20 × 500ms`) and
   `server-lifecycle.ts` (`SERVER_READY_DEADLINE_MS = 15_000`).
5. Confirm the plan before editing (`ask_user`): mode-aware, 15 s prod / 60 s dev.
6. Put the new constants + `getServerReadyDeadlineMs(kind)` helper at the **real call
   site** (`launch-source.ts`); have `server-lifecycle.ts` re-export for back-compat.
7. Thread `dev` through `system-routes.ts` → `spawnRestart` → embedded orchestrator
   script; interpolate the actual deadline into the failure-log message.
8. Add targeted tests (dev=60s, helper routing, no stale `"within 10s"` literal). Run
   with `HOME=$(mktemp -d)` to isolate.
9. Delegate the `docs/file-index-*` update to a subagent (caveman style).
10. Commit scoped to **only** the touched files via `jj split` — leave other WIP alone.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (grep the FAQ, not the code).** The AI's first move on the
vague prompt was to grep `docs/faq.md` / `README.md` for documented start-failure
causes and to `ask_user` for the context (Electron vs CLI vs which symptom). This
was correct instinct: three distinct documented causes exist, so guessing would waste
a cycle. The human's second prompt ("execute server in dev mode") let the AI probe
`/api/health` — which reported the server was *already up* in dev mode. First loop
closed with "nothing to do".

**Phase 2 — False lead (the black page).** A pasted screenshot of a React shell
`ErrorBoundary` sent the AI hunting `PluginContextProvider`/`ShellSessionsProvider`.
It opened the browser, found the page rendering fine, and correctly declared the error
**transient / not reproducible** rather than inventing a fix. Good discipline: it
asked for the actual JS error or a repro instead of guessing.

**Phase 3 — The real diagnosis.** The "restart stuck / electron cannot connect"
prompt triggered a single `ctx_batch_execute` gathering health + logs + processes +
electron config at once. That surfaced **two competing owners on port 8000**: an
Electron app from 3 h ago and a fresh standalone `--dev` server. `launchSource:
"standalone"` proved Electron didn't own it. Then `restart.log` revealed the same
`within 10s` failure 12+ times — collapsing both symptoms into **one** root cause:
deadlines shorter than jiti cold-boot.

**Phase 4 — Fix, test, ship.** After `ask_user`-confirming the mode-aware plan, the
AI edited 4 source files, added 7 tests, ran them isolated with `HOME=$(mktemp -d)`,
correctly attributed 5 pre-existing failures to an earlier refactor (not its change),
delegated the doc update to a subagent, and committed exactly 8 files via `jj split`.

## 4. Prompts that worked

- **Goal prompt — "why server does not start?"** Weak as written (too vague; the AI
  had to `ask_user` before it could act). Stronger version: *"Dashboard restart hangs
  and Electron shows 'cannot connect'. `/api/health` says mode=dev, launchSource=
  standalone. Check restart.log for the real failure."* — gives the disambiguating
  facts up front.
- **"execute server in dev mode"** — a short redirect that let the AI verify actual
  runtime state instead of theorizing.
- **"dashboard restart stuck - or electron client cannot connect"** — the
  high-leverage turn. Naming *both* symptoms together is what let the AI unify them
  into one root cause.
- **"update specs docs and commit"** — a clean close-out prompt that triggered the
  scoped `jj split` + subagent doc delegation.

tests for the new behavior, docs updated, and a **surgically scoped commit** that
left other sessions' WIP untouched.

No new skill or memory was persisted this session, but the workflow is textbook

## 7. Pitfalls & dead ends

- **Vague symptom → premature answer.** "why won't it start" has ≥3 documented causes.
  If you can't disambiguate, `ask_user` or probe `/api/health` — don't dump all causes.
- **The screenshot rabbit hole.** A React `ErrorBoundary` black page was transient and
  non-reproducible. If the page renders fine now, ask for the JS error or a repro; do
  not invent a fix.
- **Two owners on one port.** If `launchSource !== "electron"`, the Electron app does
  **not** own the server — a standalone `--dev` process bound the port. Quitting +
  relaunching Electron re-attaches cleanly (no data loss); no code change needed to
  unblock.
- **Pre-existing test failures.** 5 `server-lifecycle-spawn-options` failures were
  stale invariants from the earlier `eliminate-electron-runtime-install` refactor —
  **not** caused by this change. Verify attribution before "fixing" unrelated red.
- **`vitest` + real `$HOME`.** Run with `HOME=$(mktemp -d)` to isolate from the live
  `~/.pi/dashboard` state.
- **Wrong VCS reflex.** This repo is `jj`, not plain git. Use `jj split -m …` to scope
  a commit to specific files; never `git commit` here.
