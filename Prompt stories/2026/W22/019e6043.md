# How we did it: Making Windows Electron bundles actually runnable — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) staring at a Windows crash: a
downloaded `electron-win32-x64-<sha7>.zip`, unzipped and double-clicked, threw
`BundledServerMissingError` — it couldn't find `resources/server/node_modules/@blackbelt-technology/pi-dashboard-server/src/cli.ts`.

The *literal* ask was "why does the Windows bundle not run?" The **real objective**, once
the steering turns clarified it, was much larger: **make CI-dispatched Electron artifacts
runnable exactly like production** (bundle source-repo packages *and* their transitive
external deps), prove it end-to-end on a real Windows machine, and — as the investigation
peeled back layers — **draft an OpenSpec change for every distinct bug the journey
surfaced** (splash occlusion, Doctor false-positives, a missing `System32` PATH, wmic
stderr leak) without implementing the ones that needed more review.

## 2. TL;DR playbook

1. **Start in explore mode** with the actual error string + the install path. Let the AI
   trace `launch-source.ts` → `bundle-server.mjs` → the CI workflow that produced the ZIP.
2. **Disambiguate the artifact source early**: a dev `ci-electron.yml` build ≠ a release
   `publish.yml` build. They bundle differently. Confirm *which* ZIP you're holding.
3. **State the runnability contract in one line**: "make them runnable, same as production —
   source-repo packages contribute from source, external deps serialized."
4. **Write the OpenSpec proposal + a CI assertion gate** (`assert-runnable-bundle.mjs`)
   that fails the build if `cli.ts` is missing post-bundle. The gate is the durable win.
5. **Spike before you trust**: flip `source_only_bundle: true → false`, push, dispatch a
   single-leg CI run (`win32-x64`), and *poll/report* rather than block.
6. **Validate on real hardware**: download the 313 MB artifact, unzip on a clean Windows VM,
   run the bundled server via a copy-paste PowerShell recipe (no system Node needed).
7. **Read the runtime evidence** the user pastes back (Doctor reports, server logs, Process
   Explorer, the Tools panel) and treat each anomaly as a *separate* candidate change.
8. **Split commits by authorship** in the jj-colocated repo — push only your files with
   `jj git push --bookmark`, never raw `git push`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI traced the crash from
`BundledServerMissingError` back through the bundle pipeline and pinned the cause: the ZIP
came from `ci-electron.yml` (a `--source-only` dev build) that skipped `npm install`, so
transitive deps never materialized. *Why it worked:* starting from the exact throw site and
walking the data flow (not guessing) produced a provable root cause in one pass.

**Phase 2 — Contract & proposals.** The human set the runnability rule ("same as
production; source packages from source, external deps serialized") and chose to reconcile
overlap with sibling changes (`add-ci-electron-on-demand-build`, `eliminate-electron-runtime-install`)
by *annotating*, not superseding. The AI drafted `fix-ci-electron-runnable-bundles` +
`add-bundle-mode-marker`, each validating `--strict`.

**Phase 3 — Implement + spike.** On `openspec-apply`, the AI flagged that spike tasks
(1.x) and post-merge tasks (6.x) are human-gated (need workflow dispatch + clean VMs), then
implemented only tasks 2–5: flipped the flag, added the runnable-bundle assertion step,
extended the lint contract (`publish-workflow-contract.test.ts`, 9 → 11 tests), delegated
docs to a subagent. It dispatched a single `win32-x64` spike and *polled* it to green
(run 26416255173, ~6 min, 313 MiB artifact — confirming `node_modules/` shipped).

**Phase 4 — Real-hardware verification → cascade of findings.** The user ran the portable
`.exe` and pasted back: a hung splash, a Doctor report, a server log, a Process Explorer
snapshot, and finally the **Settings → Tools panel**. Each artifact surfaced a *distinct*
bug. Decision point after decision point, the human said "draft" / "add" and the AI wrote a
scoped OpenSpec change for each rather than one mega-fix.

**Phase 5 — Root cause of the Windows symptoms.** The Tools panel was the smoking gun:
`pi/openspec/node-pty` resolved via `bare-import` (bundle is good) but
`powershell/tasklist/taskkill/wmic/node` were all "not found" — meaning `C:\Windows\System32`
was missing from the dashboard process PATH. AGENTS.md referenced an `ensure-windows-path.ts`
that **didn't exist in the tree**. That single missing file explained the wmic stderr leak,
the broken process scanner, and the Doctor false-positives at once.

## 4. Prompts that worked

- **The goal prompt** (explore-mode invocation + the raw error + the install path). Effective
  because it gave the AI a concrete throw site to trace, not a vague "it's broken." A stronger
  version states the artifact source too: *"This ZIP is from a `ci-electron.yml` dispatch —
  trace why `cli.ts` is missing after unzip."*
- **"B: make them runnable, same as in production. For packages which have the source this
  repo use the source to contribute, the external dependencies be serialized."** — the whole
  contract in two sentences. This one prompt fixed the design.
- **"spike"** — unlocked the entire CI-verification path with one word.
- **"poll/report"** — told the AI to *not block* on the 6-min run and instead report status,
  a high-leverage async pattern.
- **"draft" / "add" / "go on"** — terse approvals that kept the proposal-per-bug cadence moving.
- **Pasting runtime evidence** (Doctor tables, server logs, Process Explorer, Tools panel) —
  each paste was itself a high-leverage "prompt" that advanced the diagnosis further than any
  question could.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Assume the ZIP was a release build | "no node_modules in zip. packages present but no transient deps" | Ask which workflow produced the artifact *first* |
| Consider superseding sibling changes | "Maybe there is overlap with add-ci-electron-on-demand-build and eliminate-electron-runtime-install" | Check sibling changes before drafting; annotate, don't replace |
| Want to block on the CI run | "poll/report" | Default to poll-and-report for any >2-min CI dispatch |
| Reach for raw `git push` in a jj repo | "the git hedless again" / "my local git is detached" | Use `jj git push --bookmark`; git HEAD trails jj's `@` by design |
| Fold many bugs into one change | "draft" (repeated per finding) | One OpenSpec change per distinct root cause |
| Trust Doctor's "pi Not found" | Pasted the Tools panel showing pi resolves via bare-import | Cross-check Doctor against the live ToolRegistry (Tools panel) |
| Test against `npm run dev` | "In local spawn seems working - but local dev server used" | Reproduce against the *real bundle*, not the dev server |

The quality bar the human imposed throughout: **prove it with runtime evidence, don't
theorize.** Every claim ("fix landed", "pi is installed", "wmic leaks") was backed by a CI
log, a health probe, or a controlled `execSync`/`spawnSync` test.

## 6. Skills, tools & memory created — and why they're effective

No new skill was saved this session, but two durable artifacts emerged:

- **`assert-runnable-bundle.mjs`** — a CI gate that fails the Electron build if `cli.ts`
  (and, later, the launch-helper scripts) is missing after bundling. It converts a
  "broken-on-arrival" class of bug into a hard CI failure. Invoke it in every electron-build
  leg.
- **`start-server.{cmd,ps1,sh}` + README** — copy-paste launch helpers shipped *inside* the
  bundle so a user with no system Node can run the server directly (the exact production argv
  shape). Reusable whenever hands-on bundle validation is needed.

**Skill that *should* be created:** a `verify-electron-bundle-on-windows` playbook capturing
the "dispatch single-leg CI → download artifact → unzip on clean VM → run bundled server via
PowerShell recipe → read Doctor + Tools panel" loop. This session executed it manually four
times.

## 7. Pitfalls & dead ends

- **jj-colocated repo, detached git HEAD.** `git status` shows detached HEAD because jj's `@`
  sits above the bookmark. Don't "fix" it with `jj edit <bookmark>` — that snapshots
  uncommitted working-copy changes into an already-pushed commit. Push with
  `jj git push --bookmark <name>`; raw `git push` pushes nothing useful.
- **Concurrent-agent noise.** Multiple agents were writing to the same repo (`svxkuott`,
  `add-worktree-spawn-dialog/`, `tighten-process-list-ux/`, a stale generated
  `plugin-registry.tsx`). Split *only your files* into a described commit; leave the rest.
- **YAML `node -e "..."` escaping.** An unquoted YAML scalar with an embedded `: ` (e.g.
  `"See change: ..."` inside a JS string) breaks the parser. Use a block-literal `run: |`.
- **Doctor lies on Windows bundles.** It reads `~/.pi-dashboard/node_modules` + PATH, not the
  bundled `resources/server/node_modules`, and reads the old `health.starter` field (renamed
  to `launchSource`). Three false-positives — don't chase them as real.
- **macOS can't reproduce wmic.** The wmic code paths are `process.platform === "win32"`
  gated. Reproduce the *pattern* with a controlled `execSync(default-stdio)` test instead.
- **"Preparing first launch…" forever-hang.** An `alwaysOnTop` splash occludes the wizard
  window (which never `.focus()`es) on Windows, so the user never sees `[Launch dashboard]`.
  Close splash before opening the wizard; `show: false` + `ready-to-show` focus on the wizard.
