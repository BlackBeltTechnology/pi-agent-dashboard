# How we did it: Deploy a production build, then archive completed OpenSpec proposals — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The kickoff prompt was three words: **"build an deploy in production mode"**. The real
objective — clarified by the steering turns that followed — was a two-part housekeeping
pass on the dashboard: (1) produce and serve a fresh **production** client build, then
(2) sweep the OpenSpec backlog — figure out which proposals are actually done, **archive
all of them** (fixing any spec-sync breakage that blocks the archive), and land the result
on `develop` with CI skipped. The second half turned out to be the substantive work: five
changes archived and three corrupt/mislabelled spec files repaired along the way.

## 2. TL;DR playbook

1. **Deploy prod:** `npm run build` → if it fails on a missing dep, `npm install` and rebuild → restart via `POST /api/restart {"dev": false}`.
2. **Confirm the mode:** `curl -s localhost:8000/api/health | jq '{mode, uptime}'` should read `production` with a low uptime.
3. **Survey the backlog:** list recent commits (`git log --oneline -15`) and cross-reference each against OpenSpec proposal completion to find real archive candidates.
4. **Pre-flight the archive:** check delta specs for capability conflicts (each capability touched by exactly one change) before running anything.
5. **Archive:** let the openspec CLI do archive **+** spec-sync in one move.
6. **Repair spec-sync failures in place:** fix corrupt main-spec headers and mislabelled `## MODIFIED` deltas that should be `## ADDED`, then re-run archive on just the failed ones.
7. **Verify final state,** then commit + push to `develop` with `[ci skip]` in the message.

## 3. How the collaboration unfolded

**Phase A — Production deploy (prompt 1).** The AI ran the build, which failed because
`pdfjs-dist` was declared in `packages/client/package.json` but not installed. It
diagnosed the unresolved import in `PdfPreview.tsx`, ran `npm install`, rebuilt (9.58 MB →
2.78 MB gzip), restarted the server in production mode, and confirmed via the health
endpoint. *Why it worked:* it treated the build failure as a dependency-state problem, not
a code problem, and verified the deploy through `/api/health` instead of assuming success.

**Phase B — Backlog triage (prompt 2).** Given "list recent commits and collect what
proposals can be archived," the AI cross-referenced `git log` against proposal task
completion and merge status, then presented a table of archive-ready changes. *Decision
point:* the human reviewed the candidate list before authorizing action.

**Phase C — Bulk archive + spec repair (prompt 3, "archive all").** The AI first checked
for capability conflicts (none — each capability owned by one change), then let the
openspec CLI handle archive + sync. Two archived cleanly; three failed on spec-sync
mismatches. Rather than skip them, the AI root-caused each: `open-in-editor`'s main spec
had a delta-style header (`## ADDED Requirements`) making its requirements invisible to the
parser; two other deltas used `## MODIFIED` against requirements that didn't exist in any
main spec. It fixed all three (header repair + `MODIFIED`→`ADDED` conversions) and
re-archived, ending with all five archived.

**Phase D — Land it (prompt 4).** Committed the 34 archive-move + spec-sync changes and
pushed `0e440b8e..c94cb06b develop -> develop` with `[ci skip]`.

## 4. Prompts that worked

- **Goal prompt — "build an deploy in production mode".** Terse and typo-laden, but it
  worked because the AI knew the repo's deploy contract (build → restart → verify health).
  A stronger version: *"Build the client for production and redeploy; confirm `/api/health`
  reports `mode: production`."*
- **"List recent commits and collect what proposals can be archived"** — high-leverage: it
  scoped a fuzzy "clean up the backlog" task into a concrete cross-reference (commits ↔
  proposal status) and produced a reviewable list before any destructive action.
- **"archive all"** — a two-word unlock once the candidate list was trusted. Effective
  *because* the prior turn had already surfaced and vetted the list.
- **"commit and push with [ci skip]"** — explicit about the CI-skip tag, avoiding a wasted
  pipeline run on pure archive-move commits.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Stop after the prod deploy (the literal prompt 1) | Adding "list recent commits and collect what proposals can be archived" | State the full intent up front: "deploy prod **and then** archive completed proposals" |
| Present analysis and wait | Saying "archive all" to authorize the sweep | Pre-authorize: "archive every proposal that's fully complete and merged" |
| Leave CI to run on trivial commits | Specifying `[ci skip]` explicitly | Make "[ci skip] for archive-only commits" a standing rule |

The notable *self-correction* (no human nudge needed): when three archives failed on
spec-sync, the AI didn't retry blindly — it diagnosed each mismatch and repaired the spec
files. That's the behaviour to reinforce, not steer away from.

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created this session. But the spec-repair pattern is clearly
reusable and **should** be captured as a skill:

- **Recommended skill — "archive-openspec-changes-with-spec-repair".** Captures: run the
  openspec archive CLI; when spec-sync fails, the two recurring causes are (a) a main spec
  with a **delta-style header** (`## ADDED/MODIFIED Requirements`) instead of the canonical
  `# Spec / ## Purpose / ## Requirements`, and (b) a delta using `## MODIFIED Requirements`
  for a requirement that has **no** entry in any main spec (should be `## ADDED`). Fix in
  place, re-archive the failed ones only. *Why effective:* it turns a mid-archive stall into
  a mechanical two-rule repair. *When to invoke:* any bulk `openspec archive` that reports
  spec-sync mismatches.

## 7. Pitfalls & dead ends

- **Build fails on `pdfjs-dist` (or any declared-but-uninstalled dep).** The error is an
  unresolved import in the consuming component (`PdfPreview.tsx`), not a code bug. Fix: run
  `npm install` and rebuild — the dep was in `package.json` but not on disk.
- **`curl … /api/health` can return "server not running".** The lone failed command in the
  session; harmless when the server is mid-restart. Re-probe after the restart settles.
- **`openspec archive` fails on spec-sync.** Don't retry blindly. Two causes: corrupt main
  spec header, or `## MODIFIED` used where the requirement is actually new (`## ADDED`). Fix
  the file, then re-archive only the failures.
