# How we did it: Unify tool-renderer code font size — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The user opened an **explore-mode** session (the openspec-explore skill: think, investigate,
never implement) with a fuzzy complaint — the code/diff text in chat tool-call cards looked
inconsistently sized between "read" and "edit" surfaces. There was no exact file, no exact
number, just an eye-level "these don't match." The *real* objective, once the investigation
and three steering turns clarified it: **prove the mismatch with measured evidence, decide a
single canonical code font size (settled at 12px), and capture the fix as an OpenSpec proposal
— without writing a line of implementation.** The session ended by landing those 4 proposal
files on `origin/develop` from a *separate jj workspace* so a second session already editing
the branch was never disturbed.

## 2. TL;DR playbook

1. Enter explore mode (`openspec-explore` skill) — commit to *thinking only, no code*.
2. Don't trust the described symptom. **Grep the renderer tree** (`packages/client/src/components/tool-renderers/`) for `fontSize|text-(xs|sm|base)`.
3. **Measure live, don't eyeball**: open the running dashboard in the browser, inject a `getComputedStyle` probe (`/tmp/measure.js`) to print `fontSize / lineHeight / fontFamily` for each surface.
4. Build a **font-size map** of every renderer (Read, Write, Edit desktop+mobile, Bash, Generic, DiffPanel) so the proposal isn't half-blind. This surfaces the true outlier: `EditToolRenderer` desktop → `RichDiff` has no font-size → inherits ~14px.
5. Present findings as an ASCII diagram + a numbered **DECISIONS** block; let the user answer with a terse list (`1. 12px  2. keep  3. ok`).
6. Scaffold the change under `openspec/changes/<name>/` following the existing flat convention (`.openspec.yaml` + `proposal.md` + `tasks.md`), then `openspec validate`.
7. Validator complains about a missing specs delta → add `specs/tool-renderers/spec.md` with the parity scenarios, re-validate.
8. To land on a shared branch safely: **`jj workspace add .shadow/font-fix -r develop`**, copy the 4 files in, describe + move the `develop` bookmark, restore the files out of the main workspace, `jj git push`.

## 3. How the collaboration unfolded

**Phase A — Discovery (don't trust the symptom).** The user's words were "content window / read vs
edit." The AI's first move was skepticism: *"'Content window' isn't a term I see verbatim in the
codebase."* It grepped `src/client/components/` (wrong tree — this repo's client lives under
`packages/client/`), corrected course, and re-grepped the right path. **Why it worked:** treating
the described symptom as a hypothesis, not a fact, avoided fixing the wrong surface.

**Phase B — Gather / measure (evidence over assumption).** Rather than reason about CSS, the AI
opened the live dashboard in the browser and injected a `getComputedStyle` probe. First reading was
a red herring — baseline chat and input matched perfectly at 14px. That *ruled out* the chat-vs-input
theory and pointed at sub-elements. The AI then realized "read and edit" literally meant the **Read
tool** and **Edit tool** renderers, measured a session that actually had those cards, and found the
real gap. **Why it worked:** the negative measurement (they *do* match) was as valuable as the positive.

**Phase C — Design (map everything, decide out loud).** The AI swept *all* renderers into one
font-size map, isolated the desktop-Edit/`RichDiff` inheritance bug as the headline, and presented a
sketched normalization plus a numbered DECISIONS block. **Decision points (human):** target size
11–12px → then locked to **12px, no fractionals**; make it a **shared token** (`.text-code` utility
via `@layer utilities` in `index.css`); **DiffPanel out of scope**; mobile may differ from desktop but
must be consistent within a surface.

**Phase D — Generate (capture, don't implement).** Scaffolded the 4 proposal files, hit the
validator's specs-delta requirement, added the spec with 4 parity scenarios, re-validated green. Net
planned change: ~7 line edits across 6 files + 1 utility class — explicitly *not executed*.

**Phase E — Land safely on a shared branch.** The final steering turn: "commit to develop, but another
session is on this branch — maybe a separate checkout." The AI recognized a **jj-colocated repo**, read
the workspace skill first, then used `jj workspace add` to build the commit in an isolated tree and
fast-forward `develop` without touching the other session's WIP.

## 4. Prompts that worked

- **The goal prompt** — invoking the `openspec-explore` skill was the high-leverage kickoff: it set the
  *stance* (investigate + measure + capture a proposal, never implement), which is exactly what a
  fuzzy "these fonts look off" complaint needs. A stronger cold-start version for next time: *"Explore
  mode. The code text in Read vs Edit tool-call cards looks different sizes — measure the computed
  font-size of every tool renderer in the browser, map them, and draft an OpenSpec proposal for one
  canonical size. Don't implement."*
- **High-leverage follow-ups** — the terse decision lists (`1. 12px  2. keep  3. ok`) worked because
  the AI had already framed numbered questions with an ASCII DECISIONS block. Answering by index is
  faster than prose and leaves an audit trail of what was chosen.
- **The safety redirect** — *"Other session working on this branch, so maybe do it over a separate
  checkout"* — one sentence that prevented clobbering a colleague's uncommitted work.

## 5. Steering & corrections (what to watch for)

The quality bar the user imposed: **decisions must be integers, scope must be surgical, nothing gets
implemented in explore mode, and a shared branch must be touched without collateral damage.**

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session, but two existing ones carried the weight:

- **`openspec-explore`** — enforced the think-don't-implement stance that kept a fuzzy complaint from
  turning into premature CSS edits. Invoke it whenever the ask is "something looks/feels wrong" and the
  fix isn't yet pinned to a file.
- **The jj-workspace skill** (read before acting) — the reusable pattern for landing work on a branch
  another session is editing. **Worth promoting to a memory/skill:** *"To commit onto a shared branch
  without disturbing an in-flight workspace: `jj workspace add .shadow/<name> -r <branch>`, copy files
  in, describe + move the bookmark, `jj restore` the files out of the main workspace, push."*

If a skill *should* be created from this session, it's a **"measure-then-propose UI sizing"** playbook:
inject a `getComputedStyle` probe into the live dashboard, build a per-surface font-size map, and turn
the outlier into an OpenSpec proposal.

## 7. Pitfalls & dead ends

- **Wrong component tree.** `src/client/components/` doesn't exist here; the client is `packages/client/src/`. If a grep returns nothing, check the path before concluding "no matches."
- **First measurement was a red herring.** Baseline chat vs input both read 14px — the mismatch was *inside* tool renderers, not chat-vs-input. Don't stop at the first surface; map them all.
- **Validator fails without a specs delta.** `openspec validate` rejects a change that has no `specs/<capability>/spec.md`. Add the delta *with* the proposal, not after.
- **`RichDiff` (`@git-diff-view`) sets no font-size** — it silently inherits the parent (~14px). That inheritance is the actual visible bug; a library with no explicit size is a prime suspect for drift.
- **Don't `git commit`/`git checkout` in a jj-colocated repo** — use pure jj (`workspace add`, `describe`, `bookmark set`, `restore`, `git push`) to avoid corrupting the colocated state or a peer's workspace.
