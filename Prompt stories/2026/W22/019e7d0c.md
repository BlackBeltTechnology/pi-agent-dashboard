# How we did it: fix cold-start worktree session grouping — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation request. The real objective emerged in the first few turns: **after a
machine reboot, every pi session shows `ended` and no bridge has reattached — and in that
state, worktree (git `.worktrees/*`) and jj `.shadow/*` sessions vanish from the dashboard
sidebar entirely.** The operator wanted to understand *why*, capture it as an OpenSpec
change, implement the fix end-to-end, backfill the already-broken data on disk, and land it
on `develop`. The through-line: **prove the root cause with hard evidence before touching a
line of code**, then make a surgical fix.

## 2. TL;DR playbook

1. **Start in explore mode** to diagnose, not implement — `openspec-explore` keeps the AI
   from jumping to code. Ask it to trace the grouping path and draw the data flow.
2. **Demand empirical proof, not a plausible theory** — "to prove, check the actual sessions
   on disk and collect the numbers." The AI read all 34 `.meta.json` sidecars and tallied
   which parentage fields were persisted (answer: `gitWorktree.mainPath` = 0/34).
3. **Fast-forward the OpenSpec artifacts** with `openspec-ff-change` once the framing is
   settled (proposal → design → specs → tasks, TDD-ordered).
4. **Apply with `openspec-apply-change`** — write failing tests first, confirm the RED state
   (with `HOME=$(mktemp -d)` for test isolation), then the minimal 3-file implementation.
5. **Rebuild + deploy** via the post-apply protocol: `npm run build` → `POST /api/restart`
   → health-check `mode: production`.
6. **Backfill the legacy data** — a one-shot `node` script (run via Bash, *not* ctx_execute,
   so FS writes actually land) that additively stamps parentage onto the 34 old sidecars.
7. **Commit + push on jj** (colocated repo): describe `@`, advance the `develop` bookmark,
   push. Archive the change + sync specs as a second `[ci skip]` commit.
8. **When CI goes red, prove ownership before reacting** — diagnose whether the failure is
   *yours* or a latent pre-existing break surfaced by your first non-`[ci skip]` push.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore mode).** The AI grepped the server + client grouping code
(`session-scanner.ts`, `SessionList.tsx`, `resolveSessionGroupPath`, `FolderOpenSpecSection`)
and produced Mermaid diagrams of the cold-start data flow. It found the real mechanism: the
collapse-under-parent behaviour depends on `session.gitWorktree.mainPath`, **which is only
set by a live `git_info_update` event from the bridge** — never persisted. Post-reboot the
field is undefined, so every worktree session falls to its own unpinned group, and the
"hide folders with only ended sessions" rule then suppresses it. *Why it worked:* the AI was
told to think, not code, so it kept digging until it had the exact line
(`SessionList.tsx` unpinned-group `.filter`) rather than a guess.

**Phase 2 — Second surface, same root.** The operator pointed out the OpenSpec section had
"the same problem." The AI traced `FolderOpenSpecSection.tsx:230` `linkedSessions` and
confirmed it was the *identical* root cause on a second surface — folded it into the same
proposal instead of spinning a new change.

**Phase 3 — Empirical proof.** The decisive steer: *"To prove check the sessions and
collect."* The AI read every `.meta.json` on disk and produced a hard table: `gitWorktree`
0/34, `mainPath` 0/34, `jjState` 0/34, `attachedProposal` 23/34, all 34 `ended`. This
converted a theory into a proven diagnosis and validated the fix shape before any code.

**Phase 4 — Artifacts + TDD implementation.** `openspec-ff-change` generated proposal /
design / specs / tasks; `openspec-apply-change` drove a strict red→green loop. Three surgical
edits — all on the path `gitWorktreeBase` already travelled: `session-meta.ts` (two optional
nested fields), `server.ts` (`onChange` save writes them), `session-scanner.ts`
(`sessionFromMeta` reconstructs them). 7 new tests, zero regressions across ~6857.

**Phase 5 — Deploy + backfill.** Rebuild/restart per protocol. Then a one-shot backfill
script additively stamped parentage onto all 34 legacy sidecars (29 git + 5 jj), restart to
rescan, verified via `/api/sessions` that 0 worktree sessions were left uncollapsed.

**Phase 6 — Land + CI triage.** jj commit + push to `develop`, archive + spec-sync as a
`[ci skip]` follow-up. CI then went red — and the AI proved the failure was **100% the
in-progress `pi-image-fit-extension` change**, not this one: the earlier image-fit scaffold
commits used `[ci skip]`, so this push was the *first real `tsc --noEmit`* over the whole
workspace and surfaced latent breakage (an import of an unreleased pi symbol +
a genuine type bug). Recorded as a project memory so it isn't re-investigated.

## 4. Prompts that worked

- **Goal (explore mode):** entering `openspec-explore` framed the whole session as
  *diagnose-first*. Effective because it blocked premature code and forced a proven root
  cause. A future kickoff should say explicitly: *"Explore mode. Root-cause why X, prove it
  with on-disk evidence, then propose a change — don't implement yet."*
- **"To prove check the sessions and collect."** The single highest-leverage steer — it
  converted a believable theory into 34/34 hard numbers and de-risked the entire fix.
- **"Under openspec same problem. The worktree attached session doesn't appear."** Surfaced a
  second symptom that shared the root cause, letting the AI fold it into one proposal.
- **Skill-invocation prompts** (`openspec-ff-change`, `openspec-apply-change`,
  `openspec-archive-change`) moved cleanly from artifacts → implementation → archive.
- **"CI failed"** — deliberately terse; the AI's job was to *prove* whose failure it was, and
  it did (ownership analysis, not a reflexive fix).

## 6. Skills, tools & memory created — and why they're effective

- **Memory saved (project · failure):** *"CI on develop fails at `npm run lint` (tsc
  --noEmit) due to `packages/image-fit-extension` (in-progress pi-image-fit-extension
  change), NOT unrelated commits."* **Why effective:** the next person who sees red CI on
  `develop` won't re-run the same 40-minute investigation — the memory names the exact
  package, the two errors (unreleased `isToolCallEventType` import + `ImageFitConfig` cast),
  and the reason (first non-`[ci skip]` push surfaced latent breakage). **Invoke when:** CI
  lint/typecheck is red and the diff looks unrelated.
- **Subagent used:** `openspec-sync-specs` to fold the two delta specs into the main specs
  before archiving — keeps the sync mechanical and out of the main context.
- **No new skill was created, but one is warranted:** a *"prove-CI-ownership"* mini-procedure
  (first-non-`[ci skip]`-push detection + `npm pack` registry check to distinguish local dev
  builds from published versions) would make the Phase-6 analysis reproducible.

## 7. Pitfalls & dead ends

- **`ctx_execute` discards filesystem writes.** The backfill had to run via **Bash + a
  `node` script** so writes landed in the real `~/.pi`. If a data-repair script "runs" but
  nothing changes on disk, you used the wrong tool.
- **Vitest needs an ephemeral HOME.** A test-isolation guard fails without
  `HOME=$(mktemp -d)`; the RED-state run only worked once HOME was ephemeral.
- **`npm ci` vs local `node_modules` skew.** A symbol (`isToolCallEventType`) existed in the
  local dev pi build but *not* in the published `0.78.0` the CI installs — same version
  string, different contents (integrity mismatch). Verify with `npm pack` against the
  registry, not the local tree.
- **jj colocation noise.** `Failed to update Git HEAD ref` is benign — the push still
  succeeded (confirm via `git ls-remote`).
- **Don't commit the one-shot repair script.** `/tmp/backfill-worktree-parentage.mjs` was
  intentionally kept out of the codebase — it's local data repair, not a feature.
