# How we did it: Scoping the `tighten-process-list-ux` OpenSpec change — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **OpenSpec explore mode** — a "think, don't implement" stance.
The real objective, once steering clarified it: the SessionCard **process list** was
showing three kinds of noise, and the operator wanted a single, well-scoped OpenSpec
change proposal to tighten it. The noise: (a) the bridge's own spawned pids (the pi
session's own `pi --mode rpc` child + sidekick keeper) leaking into the list, (b) a
scan cadence / min-elapsed floor that felt sluggish, and (c) unbounded list length.
The deliverable was **not code** — it was a validated 4-artifact OpenSpec change
(`proposal.md`, `design.md`, `spec.md`, `tasks.md`) committed straight to `develop`.

## 2. TL;DR playbook

1. Enter explore mode (`/skill:openspec-explore`) and hand the AI the three symptoms
   as a bullet list — let it ground itself in the code first.
2. Let it read `bridge.ts` / `process-scanner.ts` and draw the current pipeline +
   "three knobs" table (scan tick, min-elapsed, list cap). Confirm the grounding.
3. Steer the scope in one terse message: **one change**, name the exact fix
   (detect + filter the session's own spawned pid/sidekick), pick options by letter.
4. Have it scaffold with `openspec new change tighten-process-list-ux`, then fill
   `proposal.md` first (unlocks `design` + `specs`).
5. Answer the one deferred design question (list ordering) — pick **longest-running
   first** so stuck processes keep their slot.
6. Let it write `design.md` (decisions D1–D5), the spec delta, then `tasks.md`;
   `openspec validate` after each until green.
7. To land it: `git worktree add /tmp/<name> -B <branch> origin/develop`, copy the
   change dir in, commit, `git push origin <branch>:develop` (fast-forward).
8. Clean up: `git worktree remove …`, `git branch -D …`, and `git rm -rf --cached`
   the change dir from the main cwd since it now lives on `develop`.

## 3. How the collaboration unfolded

**Phase A — Ground before exploring.** The AI resisted the temptation to
brainstorm cold. It ran the docs-first protocol (grep the file index), then read
`bridge.ts` and `process-scanner.ts` and rendered a pipeline diagram plus a
three-knob table (`PROCESS_SCAN_INTERVAL` 10 s, `DEFAULT_MIN_ELAPSED_MS` 30 s,
list cap). *Why it worked:* every later decision referenced real symbols and line
numbers, so scope debates were concrete, not hand-wavy.

**Phase B — Lock scope, sketch the shape.** On the first steering turn the operator
compressed four decisions into four lines. The AI sketched the "self-spawned
registry" design (a `Set<number>` on `BridgeContext`, populated at the
`server-launcher` and RPC-keeper spawn sites, filtered at capture time) *before*
writing any artifact. *Decision point:* exclude at capture, not at filter — cheaper
and keeps dead PGIDs from lingering in `trackedPgids`.

**Phase C — Fill artifacts in dependency order.** `openspec new change` scaffolded
the skeleton; `proposal.md` went in first (it gates `design` + `specs`). The AI
flagged one open question it had deliberately deferred — how to order >5 processes —
and asked the human to choose rather than guessing.

**Phase D — Design → spec → tasks, validate each.** `design.md` captured five
decisions (D1–D5); the spec delta modified 4 requirements with ~20 scenarios;
`tasks.md` broke into 7 groups / 26 tasks. `openspec validate` ran after each
artifact until the status showed 4/4 complete.

**Phase E — Land on develop via a throwaway worktree.** The repo is jj-colocated but
the operator asked for git. The AI added a `/tmp` worktree tracking `origin/develop`,
copied in the change dir, committed `docs(openspec): …`, and pushed
`<branch>:develop` as a fast-forward — then tore down every worktree/branch it
created and un-staged the change from the main cwd (it now lives on `develop`).

## 4. Prompts that worked

- **The goal prompt** (explore-mode skill + three symptoms). Effective because it set
  a *stance* ("think, don't implement") and gave concrete noise categories, so the AI
  grounded itself instead of proposing code.
- **High-leverage steering #1** — `"1. One change / 2. Detect the session's spawned
  pi pid and sidekick and filter them out / 3. yes / 4. B"`. Four lines that locked
  the entire scope: single change, the exact mechanism, and menu picks by letter. This
  is the pattern to copy — answer the AI's enumerated questions positionally.
- **`"+3 more / keep 30s / invisible"`** — terse tuning of the three knobs in one line.
- **`"create a worktree from develop in /tmp and commit proposal on there and push
  back to develop"`** — a complete landing instruction in one sentence; the AI executed
  it end-to-end and self-proposed cleanup.

Weak prompt to rewrite: `"ok"` / `"yes"` carried real decisions (e.g. confirming
longest-running ordering). Stronger: state the choice explicitly —
*"confirm longest-running-first ordering"* — so the transcript is self-documenting.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Leave scope open-ended in explore mode | "One change" + name the exact fix | State "single OpenSpec change, scope = X" in the goal prompt |
| Defer sub-decisions (list ordering) to the human | Picking "longest-running first" | Give the ordering rule up front, or accept the AI's default |
| Offer to clean up but wait | "remove them" | Say "create the worktree, push, then remove all worktrees/branches you made" |
| Leave the change staged in the main cwd after pushing | "the proposal committed to develop, no need to be in this branch" | Add "un-stage/remove the local copy once it's on develop" to the landing instruction |

## 7. Pitfalls & dead ends

- **`wc -l src/extension/process-scanner.ts …` failed** — the paths were guesses. The
  AI recovered with `find … | grep -v node_modules` and discovered the real files live
  under `packages/extension/src/` and `packages/client/src/`. *If you hit a missing
  path, `find`/grep the monorepo `packages/*` layout, don't assume `src/`.*
- **jj-colocated repo** — `git worktree` works, but confirm the VCS before scripting
  git commands; the AI called this out explicitly before pushing.
- **Change left staged in main cwd** — pushing to `develop` via a worktree does *not*
  remove the copy in your working tree. Finish with
  `git rm -rf --cached openspec/changes/<name> && rm -rf openspec/changes/<name>`.
- **Pre-existing worktrees** (`/tmp/pi-agent-dashboard-develop`, `…-fix-ci`) — the AI
  correctly left ones it didn't create untouched until the operator OK'd removal.
