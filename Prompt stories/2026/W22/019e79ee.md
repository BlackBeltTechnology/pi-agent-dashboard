# How we did it: Attach archived changes + auto-fill worktree branch — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) — a thinking-partner
stance, explicitly *not* implementation. The first substantive ask:

> _"I would like to show the timeline, tasks for archived attached. And be an Attach
> Archived button on cards, and in Worktree dialog."_

The **real objective**, once the steering turns landed, was narrower and cleaner than
the opening ask. What the user actually wanted was two separable improvements to the
OpenSpec ↔ worktree UX:

1. Let a session attach an **archived** proposal (not just active ones), surfacing its
   timeline/tasks — collapsed into "one picker that also shows archived entries."
2. In the generic **+Worktree** dialog, auto-derive the worktree name and branch from
   the selected proposal name.

By the end, only #2 was captured as a validated OpenSpec change proposal; #1 stayed as
explored-but-unwritten thinking. The tangible artifact: a strict-validated proposal for
`auto-fill-branch-from-proposal-in-worktree-dialog`, committed with `[ci skip]`.

## 2. TL;DR playbook

1. **Enter explore mode** with the `openspec-explore` skill — think, sketch, do NOT
   implement. This is the right stance when the ask is still fuzzy.
2. **Map the existing flow first.** Spawn an `Explore`/`general-purpose` subagent to
   trace the attach + worktree-create path (`FolderOpenSpecSection` →
   `WorktreeSpawnDialog`) instead of reading files serially yourself.
3. **Reflect the shape back as ASCII diagrams** and surface decision points *before*
   drafting — let the user pick the direction.
4. **Let steering collapse scope.** When the user reframes ("just show archived in the
   same picker"), fold multiple asks into the smallest change.
5. **Split unrelated ideas into separate changes** — the auto-fill-branch idea was
   explicitly carved off as "some other change."
6. **Verify the code reality before writing the spec.** Discover that path already
   derives from branch (`derivedPath` chain), which shrinks the change to *one effect*.
7. **Scaffold with `openspec new change <name>`** (not `openspec change new`), then
   write `proposal.md`, `tasks.md`, `specs/<capability>/spec.md`.
8. **Validate strict:** `openspec validate <name> --strict`.
9. **Commit with `jj`** (this repo has jj) and `[ci skip]` in the body; push to
   `develop`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (explore stance).** The AI entered explore mode and immediately
mapped the two entry points into `WorktreeSpawnDialog`: the per-change `⑂+` button
(carries `attachProposal` / `initialBranch="os/<change>"`) and the folder-header
`+Worktree` button (no proposal). *Why it worked:* it named the actual seam — a
session↔proposal binding, not a worktree↔proposal binding — before proposing anything.

**Phase 2 — Shape & steer.** The user pushed twice on the attach idea: first "add an
Attach Archived button," then the sharper reframe "better idea — in Attach show hidden
buttons and select archived too." The AI redrew the picker as a single unified list
(ACTIVE + collapsed *Archived (47)*), collapsing two buttons into one control. **Decision
point:** the human chose the unified-picker direction over separate buttons.

**Phase 3 — Scope split.** The user then said "some other change: in worktree creation
when a proposal is selected inherit the worktree name and branch from proposal name."
The AI correctly treated this as a *separate* change rather than bolting it onto the
attach work.

**Phase 4 — Verify-then-shrink.** Hours later ("1" = pick change #1), the AI verified the
dialog's real behavior and found the path already auto-follows the branch via
`derivedPath`. That collapsed the change from "auto-fill name + branch" to a single
reactive effect: `setNewBranch("os/<name>")` respecting a dirty flag. *Why it worked:*
reading the code reality before writing the spec removed ~half the proposed surface area.

**Phase 5 — Generate & validate.** On "draft proposal," the AI scaffolded the change
(`.openspec.yaml`, `proposal.md`, `tasks.md`, `specs/worktree-spawn-dialog/spec.md` with
6 scenarios) and passed `openspec validate --strict`.

**Phase 6 — Ship the doc.** On "commit and push with [ci skip]," the AI detected this is
a **jj** repo (`jj st`), described the commit with `[ci skip]` in the body, and pushed to
`develop` as `c49ceeaa`.

## 4. Prompts that worked

- **The goal prompt (explore skill):** launching in `openspec-explore` set the right
  guardrail — think, don't implement — which kept the session from prematurely writing
  code before the shape was clear. A stronger kickoff would have named the two features
  up front: *"Explore two changes: (a) attach archived proposals in one picker, (b)
  auto-fill worktree branch from proposal name."*
- **High-leverage follow-ups:**
  - _"Maybe better idea — in Attach show hidden buttons and select archived too"_ —
    collapsed two UI controls into one picker in a single sentence.
  - _"Some other change."_ — the four-word scope-split that kept the two features clean.
  - _"1"_ / _"draft proposal"_ / _"commit and push with [ci skip]"_ — terse
    state-machine nudges that each advanced one concrete step once the thinking was done.

**Recommendation:** the *verify-then-shrink* move (read the component's real data flow to

you may only need one effect."**

## 7. Pitfalls & dead ends

- **Wrong OpenSpec verb.** `openspec change new <name>` is not the command — it's
  `openspec new change <name>`. The AI discovered this via `openspec --help` /
  `openspec new --help`. If scaffolding fails, check the subcommand order.
- **Assuming git.** This repo carries a `.jj` dir; `git status` alone is misleading.
  Probe with `test -d .jj` / `jj st` before committing, and use `jj describe` +
  `jj bookmark`/push rather than `git commit`.
- **Over-sizing before verifying.** The first mental model of the branch change was
  twice as large as needed. Reading the `derivedPath` chain shrank it to a single
  reactive effect — always verify code reality before writing tasks.
- **Feature #1 left unwritten.** The archived-attach picker was explored thoroughly but
  never captured as a change. If both matter, draft *both* proposals before shipping.
