# How we did it: Show full tool-call args (collapsed + expanded) — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a thinking stance, not an
implementation run. The kickoff prompt loaded the skill and set the rule: *"Enter explore
mode. Think deeply… You must NEVER write code or implement features… You MAY create
OpenSpec artifacts."*

The real objective emerged from a screenshot the user was staring at: **long tool-call
argument strings are hard-sliced in the dashboard chat view.** A `bash.command` (and
`Agent.description`, `ask_user.title`, `read.path`, …) is cut at `slice(0,60)` with no
ellipsis in the collapsed `ToolCallStep` row, and even expanding the row doesn't fully
reveal it. The goal: **surface the full argument** in both the collapsed and expanded
views, then capture the fix as an OpenSpec change proposal — no code.

## 2. TL;DR playbook

1. Kick off with the `openspec-explore` skill so the AI investigates but does not implement.
2. Point it at the symptom (a screenshot / one concrete offender like a long `bash.command`).
3. Let it locate the two truncation layers: `ToolCallStep.tsx` (the `slice(0,60)` summary)
   and `tool-renderers/BashToolRenderer.tsx` (the expanded view).
4. Answer the design fork with a terse triple — e.g. `1. yes  2. desktop  3. same fix`.
5. Have it draft the change: `openspec/changes/show-full-tool-call-args/{proposal.md, tasks.md, specs/chat-view/spec.md}`.
6. Validate: `openspec validate show-full-tool-call-args --strict`.
7. Ask for an isolated branch: **"create a git worktree named X, move the changed files there."**
   State **"don't use jj"** up front if you want plain git.
8. Verify the split: `git worktree list` + `git -C .worktrees/<name> log --oneline`.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (the truncation autopsy).** The AI grepped the client for
`truncate|text-ellipsis|overflow-hidden`, found the `.tsx` tree under `packages/client/`,
and pinned the exact cut: `bash: (args) => \`$ ${String(args?.command).slice(0,60)}\`` in
`ToolCallStep.tsx:29`, plus a `className="truncate"` span, then a second layer in
`BashToolRenderer.tsx`. It drew an ASCII map of *where the bytes get eaten*. **Why it worked:**
it treated "truncation" as two independent layers instead of one, so nothing was missed.

**Phase 2 — Design fork.** The AI surfaced choices (add ellipsis? hover-reveal? apply the
fix everywhere?). The human collapsed the fork with a three-line answer
(`1. yes  2. desktop  3. same fix`). **Decision point:** desktop hover-title as the reveal
mechanism, same fix applied across all long-arg tools.

**Phase 3 — Generate the proposal.** It wrote `proposal.md`, a `tasks.md` (5 sections,
~12 tasks), and `specs/chat-view/spec.md` (2 requirements, 6 scenarios), then ran
`openspec validate … --strict` — clean.

**Phase 4 — Isolate the change (the messy part).** Asked to "create a worktree and move the
changed files," the AI reached for **jj** first (the repo is jj-colocated): `jj workspace add`
into `.shadow/show-full-tool-call-args/`, bookmark, describe. The human immediately steered:
**"dont use jj. Please move to git worktree."** The AI then reversed cleanly: stashed the 3
files to `/tmp/sftca-stash`, deleted the jj bookmark + workspace, added `.worktrees/` to
`.gitignore`, ran `git worktree add -b show-full-tool-call-args .worktrees/… develop`,
copied the files back in, and committed on the branch. `develop` stayed clean.

**Phase 5 — Reconciliation.** Two `?` prompts flagged confusion. The AI's answer was the
useful move: it enumerated the three plausible sources of surprise (dirty `.gitignore` in
main, the commit only living on the branch, jj still colocated at the root) and asked which.

## 4. Prompts that worked

- **The goal prompt (skill-loaded explore mode).** Effective because it fixed a *stance*:
  investigate + produce OpenSpec artifacts, never implement. That kept the session on drafting
  a proposal instead of hacking the `.tsx` directly.
- **`1. yes / 2. desktop / 3. same fix`** — a high-leverage follow-up. Three numbered choices
  answered in six tokens; unblocked the whole design without a paragraph.
- **"create a worktree named show-full-tool-call-args and a branch and move changed files there"**
  — clear artifact + name + action. Would have been *stronger* with the VCS named up front
  (see §5).
- **Weak → strong rewrite:** the two bare `?` prompts cost a full round-trip of guessing.
  Better: *"The new commit isn't on develop — is that expected?"* — name the specific surprise
  so the AI answers instead of enumerating.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Reach for **jj** on a jj-colocated repo when asked for a "worktree" | "dont use jj. Please move to git worktree" | Say the VCS in the ask: *"using **plain git worktree** (not jj)"* — or save a memory that this branch's workflow is git-only |
| Leave `.gitignore` dirty in the **main** working copy after the worktree move | (surfaced via `?`) | Decide up front whether the ignore rule lands on `develop` or in `$GIT_DIR/info/exclude` |
| Present a design fork as open-ended prose | Answered with a numbered triple | Offer numbered options *with defaults* so a one-line reply resolves it |
| Answer a vague `?` by guessing | Enumerated the 3 likely sources of confusion, then asked | Ask the specific question instead of `?` |

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created this session. Two are clearly warranted:

- **A `git-worktree-for-change` skill (project scope).** Captures the exact reversible
  sequence the AI had to improvise: stash change files to `/tmp`, add `.worktrees/` to
  `.gitignore`, `git worktree add -b <name> .worktrees/<name> develop`, copy files back,
  commit on the branch, verify with `git worktree list`. Removes the jj-vs-git guessing on a
  colocated repo and the manual file shuffle. Invoke whenever "put this change on its own
  branch/worktree" comes up.
- **A memory:** *"When asked for a worktree in this repo, default to plain `git worktree`
  (not jj) unless jj is named explicitly."* One line kills the most expensive steering turn
  of the session.

## 7. Pitfalls & dead ends

- **jj-first on a colocated repo.** The AI built a whole `jj workspace` +
  `.shadow/show-full-tool-call-args/` + bookmark before being told to use git. *If you want
  git, say so in the first sentence* — otherwise you pay for the jj build **and** its teardown.
- **One failed grep:** `grep -n "…\\${" …CollapsedToolGroup.tsx ToolCallStep.tsx` errored on
  the escaped `${`; the retry with `grep -n -E` worked. *If a grep with shell-special chars in
  the pattern fails, switch to `-E` and drop the backslash gymnastics.*
- **Bare `?` steering.** Twice the human sent only `?`, forcing the AI to enumerate guesses.
  Cheap to avoid: name the surprising thing.
- **Dangling `.gitignore` edit.** The `.worktrees/` ignore rule was left uncommitted in the
  main working copy — decide its home before moving on.

- [ ] Load `openspec-explore`; state "produce a proposal, don't implement."
- [ ] Give one concrete offender (a long `bash.command` screenshot) — not "truncation in general."
- [ ] Let the AI find **both** layers: `ToolCallStep.tsx` (`slice(0,60)`) + `BashToolRenderer.tsx`.
- [ ] Resolve the design fork with numbered answers (reveal mechanism + scope).
- [ ] Draft `openspec/changes/show-full-tool-call-args/{proposal,tasks,specs/chat-view/spec}.md`.
- [ ] `openspec validate show-full-tool-call-args --strict`.
- [ ] **Name the VCS in the branch ask:** "plain git worktree, not jj."
- [ ] `git worktree add -b <name> .worktrees/<name> develop`; move files; commit; `git worktree list`.
- [ ] Decide where the `.worktrees/` ignore rule lands (commit on develop vs `info/exclude`).
