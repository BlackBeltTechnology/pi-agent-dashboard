# How we did it: Untangle a working copy after `develop` moved — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

## 1. Goal (the ask)

The operator opened with:

> _"Check the unstaged files in fetched develop. If something already added remove from changed files."_

Plain reading: after `git fetch`, a large local working copy (51 changed files) had drifted
against a moving `develop`. Some of those local edits had **already landed upstream** and were
now noise. The real objective — which only crystallised across the 12 steering turns — was a
full **branch-hygiene sweep for the `openspec-worktree-spawn-button` feature**:

1. Separate the genuinely-local edits from the ones `develop` already carries.
2. Figure out *which change / branch / PR* the survivors belong to.
3. Rebase the stale PR (#46) onto current `develop` and push it clean.
4. Stash the now-redundant local re-implementation.
5. Open PRs for the other orphaned no-PR branches.
6. Build + deploy the dashboard.

## 2. TL;DR playbook

1. `git fetch origin develop` then **classify** every working-copy file: byte-identical to
   `develop` (drop) vs genuinely different (keep). Ask the AI to produce the two lists before
   touching anything.
2. Let the rebase engine drop the already-landed files for you — `jj rebase -r @ -d develop`
   (jj-colocated repo) collapses 51 → 18 automatically and surfaces only the real conflicts.
3. Resolve conflicts **smallest-first**; for each, state the rule ("take develop's version
   unless local adds a distinct feature") so decisions are auditable.
4. Run the full test suite after resolution; expect one or two **mechanical** failures
   (duplicate exports from over-eager conflict-keeping; a lint marker like `// platform-branch-ok`).
5. Map the survivors to **one OpenSpec change** and to the matching **branch + open PR** — use
   per-file byte comparison against each PR HEAD, not a noisy full `git diff`.
6. Rebase the stale PR branch in an **isolated `/tmp` git worktree** (never in the live working
   copy), resolve, re-test, force-push, confirm `mergeable: MERGEABLE`.
7. Once the PR is canonical, **stash** the local re-implementation with a descriptive message so
   it is recoverable but out of the way.
8. Sweep remaining branches: list `no-PR` branches sorted by commits-ahead, open PRs for the
   live ones using each branch's commit body as the description.
9. `npm run build` → `POST /api/restart` → `npm run reload` to deploy.

## 3. How the collaboration unfolded

**Phase 1 — Classify (prompts 1–3).** The AI diffed the 51-file working copy against
`FETCH_HEAD` and split it into *already-in-develop* (32 files) vs *genuinely local* (18 + 1 new).
This up-front triage is the move worth repeating: never resolve conflicts on files that are
already upstream noise.

**Phase 2 — Collapse via rebase (prompts 2–3).** Recognising a **jj-colocated** repo, the AI
switched from `git merge` to `jj rebase -r @ -d develop`, which dropped the 32 already-landed
files automatically and left 5 real conflicts. Resolved smallest-first (SessionList → App →
git-worktree → worktree-bootstrap → git-operations), each with an explicit rule. Full suite:
**6725 passed** after fixing two mechanical issues (duplicate `isSameWorktreePath`/
`isOrphanWorktreePath` from keeping a redundant conflict block; a missing `// platform-branch-ok`
lint marker).

**Phase 3 — Attribute (prompts 4–6).** "What session / which branch / which PR do these belong
to?" The AI mapped all 16 survivors to the single change `openspec-worktree-spawn-button`, then
compared them byte-for-byte against every open PR HEAD — concluding **zero exact matches**: the
local copy was a *fresh re-implementation* of the same feature that PR #46 already owned, just
authored differently and rebased newer.

**Phase 4 — Rebase the real PR in isolation (prompts 7–8).** Instead of pushing the local
re-impl, the operator chose to **rebase PR #46 itself**. The AI did this in a throwaget worktree
`git worktree add /tmp/pr46-rebase`, keeping the live checkout untouched. 14 conflict blocks
across commit 1, 1 in commit 2, take-ours in commit 4 → 4 clean commits, **6730 passed**,
force-push, `mergeable: MERGEABLE`.

**Phase 5 — Stash the redundant copy (prompt 9).** With PR #46 canonical, the 16-file local
re-impl was `git stash`ed with a descriptive message — recoverable, not deleted.

**Phase 6 — Branch sweep + deploy (prompts 10–12).** Listed no-PR branches sorted by
commits-ahead, opened PRs #54/#55/#56 for the three live ones (using commit bodies as
descriptions, flagging #54's dependency on #47), then `build` → `restart` → `reload`.

## 4. Prompts that worked

- **Goal prompt** — _"Check the unstaged files in fetched develop. If something already added
  remove from changed files."_ Effective because it names the exact discriminator (*already
  added upstream*) — the AI could turn that straight into a byte-comparison classification.
  Stronger version: _"After fetching develop, split my working copy into files already identical
  to develop (to drop) vs genuinely local (to keep) — list both before changing anything."_
- **"What session / which branch / can I check against related branches?"** (prompts 4–5) —
  high-leverage attribution questions that forced the AI to tie loose edits to a concrete change
  and PR instead of resolving in a vacuum.
- **"Don't use jj. Check files unstaged when it is on PR, not in develop."** (prompt 6) — a sharp
  correction that redirected the comparison baseline from `develop` to *open PR HEADs*.
- **"Maybe the changes have to roll to #46. Rebase #46 branch to develop."** (prompt 7) — the
  pivotal decision: promote the existing PR rather than push a parallel re-implementation.
- **"stash the processed files in working copy"** (prompt 9) — short, decisive: preserve-not-delete.

## 7. Pitfalls & dead ends

- **Duplicate exports after conflict resolution.** Keeping a conflict block whose functions the
  auto-merge already inserted produced two copies of `isSameWorktreePath`/`isOrphanWorktreePath`
  → build error cascading into many "failures". *Fix:* grep for duplicated `export function`
  after any take-both resolution, before trusting the test run.
- **Lint marker required.** A `process.platform` line failed the `no-direct-platform-branch`
  rule → add `// platform-branch-ok`. *Fix:* expect this repo-specific marker whenever you touch
  platform branching.
- **Noisy `git diff` against a long-diverged branch.** Comparing the whole tree against a branch
  that forked ~20 commits back is unreadable. *Fix:* compare **only the changed files**, and use
  per-file **byte-identity** vs each PR HEAD to answer "is this already delivered?".
- **jj vs git mismatch.** In a jj-colocated repo, `git merge --ff-only` on a detached HEAD is the
  wrong tool for the working copy; jj rebase is correct there — but the isolated PR rebase used
  plain `git` in a fresh worktree. *Fix:* pick the tool per surface, not globally.
- **Never rebase a foreign PR in the live checkout.** The AI used `/tmp/pr46-rebase`; the main
  16-file working copy stayed untouched the whole time. Leaving a stale local worktree at
  `.worktrees/openspec-worktree-spawn-button` (old SHA) is fine — sync it manually later.
