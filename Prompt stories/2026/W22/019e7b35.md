# How we did it: A `/view` media-file renderer for the dashboard — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened by entering **explore mode** (`openspec-explore`) — a deliberate
*think-don't-implement* stance. The operator wanted to design a way for the dashboard
to preview non-markdown artifacts (PDFs, videos, AsciiDoc, HTML, YouTube URLs) inline
in chat, since markdown was the only first-class preview surface. The real objective,
once the steering turns landed, was concrete: **produce a complete OpenSpec change
proposal** (`render-file-previews`) for a dashboard-local `/view` slash command that
dispatches per-MIME renderers into an inline preview card with an expand-to-overlay
affordance — and commit it with `[ci skip]`. No code was written; the deliverable was
the design, not the feature.

## 2. TL;DR playbook

1. Kick off in **explore mode** (`/skill:openspec-explore`) — this forbids
   implementation and keeps the AI as a thinking partner that captures decisions.
2. Let the AI **ground first**: it spawned an `Explore` subagent + grepped
   `CommandInput.tsx`, `MarkdownContent.tsx`, `MarkdownPreviewView.tsx`, `/api/file`
   to map what rendering/`@`-mention/slash-command plumbing already exists.
3. Answer its **numbered threads compactly** (`T1: …`, `T2: …`) — one line per open
   design decision. This is the highest-leverage move; see §4.
4. Add scope in the same turn (`Add HTML renderer too`) rather than a new round-trip.
5. When it presents a second batch of sharp questions (T8–T11), answer them just as
   tersely (`b`, `i`, `current session only`, `ok`).
6. Let it run `openspec change new render-file-previews`, draft
   `proposal.md / design.md / tasks.md` + two capability specs, then
   `openspec validate`.
7. Ask it to **`commit and push with [ci skip]`**; expect it to handle a
   `git pull --rebase` race and to *leave unrelated untracked changes alone*.

## 3. How the collaboration unfolded

**Phase 1 — Discovery / grounding (01:29–01:38).** Before proposing anything the AI
mapped the terrain: an `Explore` subagent ("Find rendering + slash command + @ mention
code") plus ~9 targeted greps established that `CommandInput.tsx` *already* did both
`/command` and `@file` autocomplete, that `MarkdownContent` + `MarkdownPreviewView`
were the existing render surfaces, and that `/api/file` was UTF-8-only (binary-hostile
to PDF/video). *Why it worked:* it reused existing plumbing instead of inventing a new
composer — the whole design became "extend what's there," which is why the spec stayed
small.

**Phase 2 — Design threads (01:38–02:05).** The AI drew the proposed shape as ASCII
boxes and surfaced open decisions as **numbered threads** (T1…T11). The human resolved
them in two compact batches. Decision points captured: inline card + `⤢ expand`
overlay (T1), dashboard-local so `/view` never reaches the agent (T2), `@` extended
with current-session URLs (T3), a new `/api/file/raw` endpoint (T4), server-side
AsciiDoc via `asciidoctor` (T5), `pdfjs-dist` lazy-loaded (T6), YouTube `<iframe>`
(T7), preview persisted as a `ChatMessage` variant (T8), current-session-only URL
scope (T10).

**Phase 3 — Generate (02:05–02:09).** With "all threads pinned," it wrote the five
artifacts under `openspec/changes/render-file-previews/` — proposal, design (D1–D10 +
risks), tasks (~12 groups / ~60 sub-tasks), and two capability specs
(`file-and-url-preview`, `view-slash-command`).

**Phase 4 — Verify + ship (02:09–02:13).** `openspec validate render-file-previews`
passed, then `commit and push with [ci skip]`. A push race forced a
`git pull --rebase` (and a `git stash -u`/pop cycle); it also had to `git reset HEAD`
an unrelated `linkify-tool-output/` directory to keep it out of the commit. Landed as
`d078ec25` on `develop`, 5 files / 627 insertions.

## 4. Prompts that worked

- **The goal prompt (explore mode).** Starting in `openspec-explore` was the right
  kickoff: it framed the whole session as *capture thinking → OpenSpec artifacts*, not
  code, so the AI grounded and questioned instead of scaffolding a half-baked feature.
- **The compact thread reply — the highest-leverage prompt.**
  `T1: Render inline, but icon to make as overlay / T2: Dashboard local / T3: recent
  url from chat too / … / Add HTML renderer too`. One terse line per open decision
  resolved eight design questions in a single turn *and* expanded scope inline. This is
  the pattern to reuse: **make the AI enumerate decisions as numbered threads, then
  answer them positionally.**
- **`b` / `i` / `current session only` / `ok`.** A four-token turn that pinned the last
  four decisions — proof the numbered-thread protocol scales.
- **`commit and push with [ci skip]`.** Short, unambiguous, and it correctly implied
  "handle the rebase and don't touch unrelated files."

*Weak-prompt rewrite:* instead of a bare `T3: recent url from chat too`, a future
operator could pre-empt the follow-up round with
`T3: extract recent URLs from the current session's ChatMessage[] only` — folding the
T10 scope answer into the first pass.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Offer inline *or* overlay as an either/or | `T1: Render inline, but icon to make as overlay` — asked for *both* (card + expand) | State "inline card with an expand-to-overlay affordance" as the default preview pattern up front |
| Leave URL-source scope open | `T3: recent url from chat too` then `T10: current session only` | Say "URLs come from the current session's chat only" in the first thread reply |
| Ask design questions in two rounds | Answered batch 1 (T1–T7) then batch 2 (T8–T11) | Ask the AI to surface *all* open threads in one list before answering |
| Risk sweeping unrelated untracked files into the commit | Implicit "only this change" — AI `git reset HEAD`'d `linkify-tool-output/` | Tell it "commit only `openspec/changes/render-file-previews/`" when other untracked dirs exist |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created — this was a scoped planning session using existing
assets. The reusable machinery that carried it:

- **`openspec-explore` (skill).** The explore stance is what kept the session on
  design instead of code. Invoke it whenever the ask is "should we build X / how would
  X work" — it captures decisions into OpenSpec artifacts without prematurely coding.
- **`Explore` subagent.** Used once to locate rendering + slash-command + `@`-mention
  code, keeping the grep noise out of the main context. Invoke it for "where does X
  live" grounding before a design.
- **The numbered-thread protocol (implicit).** The AI's habit of enumerating open
  decisions as `T1…Tn` and the human answering positionally is a *repeatable
  collaboration pattern* worth naming — it compresses a multi-round design negotiation
  into two terse turns. Consider a small skill/memory that instructs the AI to always
  present design decisions as a numbered thread list.

## 7. Pitfalls & dead ends

- **1 failed command (grep on a non-existent path).** An early
  `grep … src/client/components/CommandInput.tsx` missed because the file lives under
  `packages/client/src/components/`. *If a grep returns nothing, `find` for the file
  first* — the code had already moved into the `packages/*` monorepo layout.
- **Push race on `develop`.** The first `git push` was rejected; recovery took a
  `git pull --rebase`, then a `git stash -u` / rebase / `stash pop` cycle. *If push is
  rejected with untracked changes present, stash-untracked → rebase → pop → push.*
- **Unrelated untracked directory.** `openspec/changes/linkify-tool-output/` was
  sitting in the tree; it had to be `git reset HEAD`'d out so the commit stayed scoped.
  *Check `git status --short` before committing and explicitly stage only your change's
  directory.*
