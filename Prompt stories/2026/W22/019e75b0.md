# How we did it: "build and deploy" the pi-dashboard — a AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The operator gave a two-word instruction: **`build and deploy`**. In this repo that is
a well-known ritual, not an open question — it means: rebuild the web client, restart
the running dashboard server so it picks up code changes, and reload the connected
bridges. The *real* objective that emerged during the session was more specific:
**get a healthy dashboard back on `http://localhost:8000` in dev mode after a code
change** — which turned into a small debugging exercise when a stray duplicate code
block silently crashed the freshly spawned server.

## 2. TL;DR playbook

1. `npm run build` — build the web client (Vite) into `dist/client/`.
2. `curl -X POST http://localhost:8000/api/restart` — the canonical restart path.
3. Poll health: `curl -s http://localhost:8000/api/health | jq .mode` — expect `dev`.
4. **If the restart returns `{ok:true}` but port 8000 never binds** → the spawned
   server crashed on parse. Don't trust the ok; verify the port is actually listening.
5. Read the failure at the source: `tail -40 ~/.pi/dashboard/server.log`.
6. Fix the code error (here: a duplicated function block), then restart.
7. Fallback restart when `/api/restart` won't rebind: `kill <pid>` then
   `./node_modules/.bin/pi-dashboard start --dev`.
8. `npm run reload` — reload connected bridges (they also auto-reconnect via mDNS).

## 3. How the collaboration unfolded

**Phase 1 — First build/deploy (looked fine).** The AI ran `npm run build`, then hit
`/api/restart`. The endpoint returned ok, but the spawned server never bound port 8000
(stuck ~2 min at startup). The AI fell back to `kill` + `pi-dashboard start --dev`,
which came up clean in ~6s, and reported a healthy dashboard. *Why it worked:* it
didn't take the ok response at face value — it polled `/api/health` and the listening
port, caught the silent hang, and switched to a hard restart.

**Phase 2 — Second build/deploy exposes a real crash.** The next `build and deploy`
(hours later) failed differently: the server refused to start due to a *code error*.
This time the ok/hang symptom had a root cause. *Decision point:* stop retrying the
restart, start investigating.

**Phase 3 — Root-cause the crash.** The AI tailed `~/.pi/dashboard/server.log`,
grepped `packages/server/src/git-worktree.ts` for the offending symbols, and found
**duplicate declarations** of `isSameWorktreePath` + `isOrphanWorktreePath` (lines
197+ were an identical copy of 107+). It removed the duplicate block, restarted, and
verified only one declaration each remained. *Why it worked:* it treated "restart
returned ok but nothing is listening" as evidence of a *parse/startup crash*, then read
the log instead of re-poking the endpoint.

**Phase 4 — Clean deploy + honesty note.** Rebuilt client (`dist/client/`), restarted
to a healthy PID, confirmed `mode=dev`. The AI flagged that the fix left an uncommitted
working-tree change and that the duplicate looked like a stray paste rather than WIP —
surfacing a judgment call rather than silently committing.

## 4. Prompts that worked

- **The goal prompt — `build and deploy`.** Effective *only because this repo has a
  documented rebuild ritual* (AGENTS.md "Build & Restart Workflow"). The AI knew the
  three-component matrix (extension→reload, server→restart, client→build+restart). A
  future operator can keep it this terse — but see the guardrail below for when to be
  explicit.
- **Repeating the same prompt to re-trigger deploy** worked as a "do it again" signal
  after a code change landed.

Stronger version to use when a change is non-trivial:
> "build and deploy — this touched `packages/server/`, so verify port 8000 actually
> binds after restart, and if it doesn't, tail `~/.pi/dashboard/server.log` and fix
> the startup crash before reporting success."

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Trust `/api/restart` returning `{ok:true}` | (self-corrected) verify port 8000 actually binds | Always poll `/api/health` + `lsof -iTCP:8000` after restart, never trust the ok alone |

## 6. Skills, tools & memory created — and why they're effective

No skill or memory was created in this session. But the workflow is clearly repeatable
and already codified — the operator should lean on the existing **`implement` skill**
(the "Build & Restart Workflow" in AGENTS.md), which encodes exactly this matrix:
extension→`npm run reload`, server/shared→`/api/restart` (jiti, no build), client→
`npm run build` + restart. The reusable lesson worth a memory:

> **`/api/restart` returning `{ok:true}` does NOT mean the server started.** The
> orchestrator dispatch succeeds even when the spawned server crashes on parse and
> never binds port 8000. Always verify the listening port + `/api/health`, and on
> failure read `~/.pi/dashboard/server.log`.

Invoke this whenever a restart "succeeds" but the dashboard is unreachable.

## 7. Pitfalls & dead ends

- **`/api/restart` ok but port 8000 empty** → the spawned server crashed at startup.
  Don't retry the endpoint; `tail -40 ~/.pi/dashboard/server.log` and fix the code.
- **Spawned server stuck ~2 min at startup** (first phase) → fall back to a hard
  restart: `kill <pid>` then `./node_modules/.bin/pi-dashboard start --dev`.
- **Duplicate function declarations** in `packages/server/src/git-worktree.ts`
  (a stray paste: lines 197+ copied 107+) crash the jiti parse silently. Grep the
  symbols to confirm exactly one declaration each after editing.
- **5 of 26 commands failed** here were mostly health-poll curls against a
  not-yet-listening port — expected noise while waiting for the server; wrap health
  checks in a bounded retry loop rather than a single curl.
