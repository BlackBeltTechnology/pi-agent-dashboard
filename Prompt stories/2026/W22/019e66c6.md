# How we did it: Capturing a jj-parallel-work design exploration — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore`) — a *thinking-partner* stance,
explicitly "for thinking, not implementing." The seed idea: make **jujutsu (jj) the audit
trail for LLM sessions** — every file edit a pi session makes lands as a jj commit tagged
with the session id (and proposal id when attached), so the local repo *itself* records
"who did what, on behalf of which conversation, against which spec," and GitHub PRs become
a downstream projection.

Once the steering turns landed, the *real* objective became clear: **capture two separable
design threads into one durable planning doc** — (A) commit-tagging for session/proposal
audit, and (B) a workspace-creation UX that mirrors the existing worktree-spawn dialog.
The deliverable was a thinking record (`plans/jj-parallel-work.md`), never code.

## 2. TL;DR playbook

1. **Enter explore mode** with `openspec-explore` — locks the AI into thinking/investigation, forbids implementation. Perfect for design captures.
2. **State the seed idea richly** and let the AI reframe it (here: "jj = audit trail for sessions") before touching code.
3. **Ground in reality first**: ask the AI to survey what already exists (npm extensions `pi-jj-auto`, `pi-jj`, `pi-jujutsu`; the in-repo `packages/jj-plugin/`) and produce a gap analysis.
4. **Probe the leaky edges** with a sharp question ("what happens when the LLM runs a script that modifies a file?") — forces the design to confront the hard cases.
5. **Snapshot the discussion to disk** ("Save this whole discussion to `plans/...`") the moment a thread stabilizes — don't wait for the whole thing to finish.
6. **Split conflated features** when the AI treats two ideas as one: "Maybe it's 2 separate features" reframes the doc into Feature A + Feature B.
7. **Anchor new UX on an existing template**: point the AI at `WorktreeSpawnDialog.tsx` as the literal mirror, so the design is a 1:1 mapping, not an invention.
8. **Resolve open questions inline** by quoting your directive verbatim into the doc and marking each Q as RESOLVED / STILL OPEN.

## 3. How the collaboration unfolded

**Phase 1 — Framing (prompt 1).** The AI took the seed idea and reframed it as "jj becomes
the audit trail for LLM sessions," drawing the SESSION = JJ COMMIT STREAM diagram and naming
the four hard parts (shared working copy, where the session-id lives, PR branch math,
proposal grouping). *Why it worked:* letting the AI restate the idea in its own words surfaced
the load-bearing questions before any code was read.

**Phase 2 — Grounding in prior art (prompts 2–3).** Steered to "check the jj pi extension /
maybe it does tagging," the AI surveyed three npm extensions and concluded **none tag with
the pi session or proposal id** — a clean gap analysis. The follow-up "what happens when the
LLM calls a script that modifies the file?" exposed the guard-bypass path (Bash tool edits
aren't guarded the way Edit/Write tool edits are). *Decision point:* the human kept pushing on
the leaky edges rather than accepting the happy-path design.

**Phase 3 — Persist the thread (prompt 4).** "Save this whole discussion to
`plans/jj-parallel-work.md`" produced a ~29 KB thinking record with the full flow, the
extension survey, the shape-A-vs-shape-B tradeoff, and the critical pending question
(single- vs multi-session-per-cwd). ASCII diagrams were kept verbatim because the ask was to
*save the existing discussion* (the AI flagged that a *new* artifact would use Mermaid per repo
convention).

**Phase 4 — Second feature, grounded in code (prompts 5–7).** "Is it worth using git worktree
+ jj?" got an honest "rarely worth it" with the path-divergence reasoning. Then the workspace-
creation-UX idea arrived. The AI **read `packages/jj-plugin/` first** (found it already ships as
`@blackbelt-technology/pi-dashboard-jj-plugin@0.5.4`), then discovered `WorktreeSpawnDialog.tsx`
and `NewWorkspaceDialog.tsx` and used the worktree dialog as the exact template. Feature B
(B.1–B.10) was appended, and a two-features preamble was added to the top of the doc.

**Phase 5 — Resolve & crystallize (prompts 8–9).** Short directives ("1", then the Q1/Q2
answers) resolved the open questions. The AI applied three edits: reframed B.7 (Q1 → RESOLVED,
Q2 → STILL OPEN), updated B.10, and added **B.11 — "Session card — cwd-driven isolation block"**
with both directives quoted verbatim, a detection-rules table, a three-case mockup, and
slot/component mapping that re-uses existing components.

## 4. Prompts that worked

- **The goal prompt (explore-mode preamble).** Kicking off inside `openspec-explore` set the
  right stance: think, investigate, visualize — never implement. For a design capture this is
  the correct kickoff; it prevents the AI from jumping to code.
- **"Currently there is a pi extension for jujutsu. Check maybe it makes some tagging."** —
  High-leverage: redirected the AI from designing in a vacuum to grounding in existing prior
  art, which produced the gap analysis the whole design hinges on.
- **"What happens when LLM calls a script which modifies the file?"** — A single sharp
  edge-case question that exposed the guard-bypass failure mode.
- **"Save this whole discussion to plans/jj-parallel-work.md"** — Persist-early: turned an
  ephemeral chat into a durable artifact mid-session.
- **"Maybe it's 2 separate features."** — Short reframe that untangled two conflated ideas into
  a clean A/B document structure.

*Rewrite of a weak prompt:* the terse "1" (prompt 8) worked only because the AI had just listed
numbered options. A stronger, self-contained version: **"Answer Q1 with option (a) — the card
adapts based on cwd — and record the reasoning in the doc."**

## 6. Skills, tools & memory created — and why they're effective

No skills or memories were created this session. The reusable *asset* is the planning doc itself
(`plans/jj-parallel-work.md`) — a two-feature design record that survives the conversation.

**Recommended skill to create** if this pattern repeats: a **"design-capture-to-plans-doc"**
procedure — enter explore mode, survey prior art, probe edge cases, persist to `plans/<name>.md`
early, split conflated features into labelled sections, and tag every open question
RESOLVED/OPEN with the resolving directive quoted verbatim. That is exactly the sequence that
made this session productive.

## 7. Pitfalls & dead ends

- **Narrow greps miss the target.** The AI first grepped too narrowly for the worktree dialog
  and missed `WorktreeSpawnDialog.tsx` / `NewWorkspaceDialog.tsx`; a second, wider search found
  them. *If a component "doesn't exist," widen the grep before concluding it's absent.*
- **`ctx_batch_execute` and `ctx_fetch_and_index` each errored once.** The bash/read fallbacks
  succeeded. *If a context tool errors on a survey step, fall back to plain `rg` + `read`.*
- **ASCII vs Mermaid.** Diagrams were kept as ASCII because the ask was to *save an existing
  discussion*; the repo convention is Mermaid for *new* artifacts. *If you want Mermaid, say so
  when you ask for the save — otherwise the AI preserves what it already drew.*
