# How we did it: Scaffolding OpenSpec proposals without shipping duplicates — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** — a thinking-partner stance, not an implementation
run:

> *"Enter explore mode. Think deeply… You may read files, search code, and investigate
> the codebase, but you must NEVER write code or implement features… You MAY create
> OpenSpec artifacts."*

The *real* objective emerged over the first few steering turns: **understand why
context-mode's `ctx_*` MCP tools render as an ugly generic JSON dump in the dashboard,
and capture the fix as OpenSpec proposals** — a plugin that auto-activates when the
context-mode pi extension is present. Two paired changes got scaffolded
(`wire-tool-renderer-slot` + `add-context-mode-plugin`) and pushed to `develop`.

The sting in the tail (and the actual lesson of this session): **weeks later, a gap-check
revealed both proposals were duplicates of work already shipped and archived 8 days
before the session even started.** The session's lasting value is not the proposals — it's
the *coherence-check discipline* born from cleaning up the mistake.

## 2. TL;DR playbook

1. **Enter explore mode** to investigate a rendering/architecture question — no code, just
   trace the dispatch chain (`ToolCallStep.tsx` → `getToolRenderer` → `GenericToolRenderer`
   fallback).
2. **Find the precedent before proposing.** Ask *"is there existing mechanics like this?"* —
   here `honcho-plugin` + `subagents-plugin` already gate on `piExtensions` presence.
3. **⛔ BEFORE scaffolding, run a coherence check** (this is the step that was skipped):
   `ls openspec/changes/archive/ | grep -iE '<topic>'` **and** grep the live source for the
   functionality (not just the old component name).
4. Lock the design decisions explicitly (number them; make the human confirm each).
5. Scaffold the artifacts to match house style — read a reference change first.
6. **Commit only this session's files** to `develop` (jj-colocated repo → use
   `jj squash --from @ --into <new-commit> <paths>` to isolate, never `git checkout`).
7. When a duplicate is later found, **revert via a backout commit** (preserves audit trail,
   no force-push), then **encode the lesson as a skill/memory**.
8. Run a **full coherence sweep** mechanically in the sandbox (file-existence,
   archive-name collision, capability-already-shipped, cross-proposal overlap) so only the
   summary enters context — then deep-read only flagged proposals.

## 3. How the collaboration unfolded

**Phase 1 — Discovery (why does `ctx_*` render ugly?).** The AI traced the renderer
dispatch and correctly identified that there is no literal "unknown renderer" — it's
`GenericToolRenderer`, the explicit fallback dumping raw JSON args + plaintext output. It
found the tool comes from the `context-mode` **pi extension** registering MCP tools with
TUI-only renderers. *Effective because:* it followed the chain to ground truth
(`settings.json` → `package.json#pi.extensions` → `mcp-bridge.js`) instead of guessing.

**Phase 2 — Find the precedent.** Prompted with *"is there any mechanics currently similar
like this?"*, the AI surfaced `honcho-plugin` and `subagents-plugin` — both auto-activate
on `requires.piExtensions`. This shaped the whole design: lift honcho's sync
`/api/health`-fed cache pattern verbatim.

**Phase 3 — Lock the design.** The human answered a numbered decision batch (two changes,
loose optional-prop contract with fall-through, monorepo package). The AI crystallized four
decisions and only then offered to scaffold.

**Phase 4 — Scaffold + commit.** 8 artifacts written; both changes validated with
`openspec validate`. The commit step was careful: a jj-colocated repo with pre-existing
unstaged changes (other people's WIP skills + a plugin-registry mod). The AI used
`jj squash` to land **only** its 8 OpenSpec files on `develop`, leaving the WIP untouched —
and paused to confirm before touching anything.

**Phase 5 — The gap-check (weeks later).** *"there was lot of commits that can effect this
proposal. Check it, analyze gaps, contradictions."* This is where it unravelled: the AI
discovered `2026-06-05-wire-tool-renderer-slot` and `2026-06-05-add-ctx-tool-renderer`
**already archived** — its commit was pure churn with a hard name collision. Crucially it
diagnosed **its own root cause**: it asked *"is the `<ToolRendererSlot>` consumer component
mounted?"* (grep → no hits) when it should have asked *"is the claims registry consulted for
`tool-renderer` claims?"* (yes — via `useSlotRegistryOrNull` + `forToolName`).

**Phase 6 — Revert + encode the lesson.** Backout commit (rebased through several remote
races), then a `pre-scaffold-openspec-coherence-check` skill and failure memories.

**Phase 7 — Full coherence sweep.** Ran mechanical detection over 70 active / 423 archives /
292 specs in the sandbox, surfaced 4 high-signal flags, verified each with evidence
(overturning **two** of its own premises mid-sweep), retired 4 changes (2 removed, 2
archived), flagged 3 for human review. 70 → 66 active. Committed + pushed.

## 4. Prompts that worked

- **Goal / explore-mode kickoff** — the explicit *"thinking, not implementing; you MAY
  create OpenSpec artifacts"* stance kept the AI from jumping to code and framed the whole
  session as capture-the-thinking.
- **"Is there any mechanics currently similar like this?"** — high-leverage. One question
  routed the entire design toward an existing, proven pattern (honcho presence-probe)
  instead of inventing a new one.
- **Numbered decision answers** (`1. Two changes / 2. Doesn't have to match… render, else
  fallback / 3. yes / 4. monorepo`) — terse, unambiguous, unblocked scaffolding instantly.
- **"there was lot of commits that can effect this proposal. Check it, analyze gaps,
  contradictions"** — the single most valuable prompt: it caught a shipped-duplicate before
  it caused more damage. **Bake this in:** run it *before* scaffolding, not after.
- **"Only the proposal related to this session be committed to develop"** — a precise scope
  fence that prevented committing other people's WIP.

**Rewrite of the weak kickoff:** instead of exploring then scaffolding, lead with
*"Before proposing anything for `<topic>`, grep `openspec/changes/archive/` and the live
source for prior art; only scaffold if nothing covers it."*

## 6. Skills, tools & memory created — and why they're effective

- **Skill `pre-scaffold-openspec-coherence-check` [project]** — captures the exact miss:
  run archive-name-collision + capability-already-shipped + live-source-functionality checks
  **before** scaffolding any OpenSpec proposal touching tool-renderers/plugin-slots/MCP
  rendering. *Effective because* it converts a costly duplicate (a churned commit + revert +
  sweep) into a 10-second pre-flight grep. **Invoke it** at the top of every new-change flow.
- **3 failure memories** — encode the specific trap: "ToolRendererSlot unused" was misread
  as "tool-renderer slot unwired"; the fix is to grep the *functionality*, not the symbol.
  *Effective because* they're pointer-style and survive even when the skill is forgotten.
- **`Explore` subagent** ("Find tool renderer system in dashboard") — isolated the
  read-heavy dispatch trace out of the main context.
- **Sandbox mechanical detection** (`ctx_execute` / `ctx_batch_execute`) — ran the 70-proposal
  sweep in-sandbox so only the flagged summary entered context. *Effective because* it made a
  423-archive coherence pass affordable without deep-reading everything.

## 7. Pitfalls & dead ends

- **Duplicate proposals from a skipped archive check** — the headline pitfall. Both changes
  were archived 8 days *before* the session. → Always `ls openspec/changes/archive/ | grep`
  first.
- **Grepping a refactored symbol name** — `ToolRendererSlot` returned no hits because the
  wiring was inlined via `useSlotRegistryOrNull` + `forToolName`. A no-hits grep is **not**
  proof the feature is absent.
- **"Byte-identical duplicate" from one-file diff** — `diff proposal.md` matched, but the
  full recursive diff showed `design.md`/`tasks.md`/`specs` differ. → Recursive-diff the dir
  before deleting. (The AI nearly deleted a *non*-duplicate on this basis.)
- **jj-colocated repo + `git checkout`** — unsafe with `.jj` present. → Use jj:
  `jj new -d develop --no-edit`, `jj squash --from @ --into <c> <paths>`,
  `jj bookmark set develop -r <c>`, `jj git push --bookmark develop`.
- **Remote races on push** — `develop` moved several times mid-revert. → fetch, rebase,
  retry; a backout commit (not force-push) keeps the audit trail.
- **Memory store at hard capacity** (9828/10000) — the failure memory wouldn't fit. → Put the
  procedural lesson in a *skill* and keep a minimal pointer memory.
