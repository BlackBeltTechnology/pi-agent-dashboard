# How we did it: Fixing a CI-only `pi-ai` bare-import test failure — an AI collaboration guideline

> A reusable playbook reconstructed from a real pi session. It explains **what was
> asked, how it was built with the AI, what had to be steered, and how to reproduce
> the result faster next time.** Write for a future operator who has the same goal.

---

## 1. Goal (the ask)

The session opened in **explore mode** (`openspec-explore` skill) as a thinking
partner, not an implementer. The real objective surfaced immediately: a single
assertion out of 6571 tests was failing in CI —
`packages/shared/src/tool-registry/__tests__/bare-import-exports-map.test.ts` could
not resolve `@earendil-works/pi-ai` against the repo's `node_modules`. The operator
wanted the AI to **root-cause why CI ≠ local, sketch the fix inside explore mode,
then (on the word) switch modes, apply it, commit, and push** — and later reattach
a detached git HEAD and redeploy. The genuine ask: *make the test green in CI
without breaking the published package surface or the runtime peer-dependency
contract.*

## 2. TL;DR playbook

1. Reproduce the failure and confirm scope: `npm test -- bare-import-exports-map`
   (1 of 6571 failing — isolate it before touching anything).
2. Diff CI vs local `node_modules`: `grep -n "@earendil-works/pi-ai" package-lock.json`
   and `ls node_modules/@earendil-works/pi-coding-agent/node_modules/@earendil-works/`.
   The package was **nested-only** in the lockfile; local passed only because a stale
   ad-hoc install had hoisted it to top level.
3. In explore mode, sketch the change but **do not edit** — get the operator's "switch".
4. On switch, place `@earendil-works/pi-ai: ^0.75.5` in root **`devDependencies`**
   (NOT `dependencies`, NOT `peerDependencies`) — pinned to match what
   `pi-coding-agent` requires.
5. `npm install` to regenerate `package-lock.json`; verify the new top-level
   `node_modules/@earendil-works/pi-ai` entry appears.
6. `npm test -- bare-import-exports-map` → 5 passed.
7. Rebase the fix directly onto the live `develop` tip (remote advanced mid-work),
   then push.
8. Later: reattach detached HEAD with `jj rebase -r @ -d develop` + `git checkout develop`,
   then `npm run build` and `npm run reload`.

## 3. How the collaboration unfolded

**Discovery (explore mode).** The AI ran the failing test, then dir-walked the
resolver logic in `packages/shared/src/tool-registry/strategies.ts` and compared the
lockfile's nesting against the local tree. It nailed the CI≠local root cause: `pi-ai`
was declared only as an **optional `peerDependency`** of the root, so `npm ci` honoured
the lockfile strictly and left it nested under
`pi-coding-agent/node_modules/`; the `bareImportStrategy` dir-walk never found it.
*Why it worked:* the AI refused to guess and instead produced side-by-side lockfile
vs. local trees, making the fix self-evident.

**Design (still explore mode).** The AI drafted a diff moving `pi-ai` into root
`dependencies`, then **self-corrected before touching files**: root `package.json` is
itself published (`@blackbelt-technology/pi-agent-dashboard`), so `dependencies` would
force every consumer to install `pi-ai` and defeat the optional pattern. Correct slot:
`devDependencies` — present for CI/workspace tests, absent from the published surface.
Decision point: operator said "ok, switch" to leave explore mode.

**Apply + verify.** One-line `edit` to `package.json`, `npm install` to regenerate the
lockfile, re-run the isolated test → green. The AI also drafted the full conventional
commit message (with the CI run ID that produced the failure).

**Land.** The fix had stacked on an unrelated in-flight commit; the AI rebased directly
onto `develop`, noticed the remote had advanced, fetched + rebased again, and pushed
`f37171a4` cleanly on top of the intervening `docs(openspec)` commit.

**Reattach + redeploy (later, prompts 7–8).** Git was left detached. `jj rebase -r @ -d develop`
moved the working-copy commit (an auto-regenerated `plugin-registry.tsx`) onto the new
tip; it became **empty** because PR #50 had already absorbed the same generator output.
`git checkout develop` reattached; then the standard `npm run build` + `npm run reload`
full-rebuild flow.

## 4. Prompts that worked

- **Goal prompt (explore mode skill invocation).** Entering explore mode first was the
  high-value move: it forced root-cause + design *before* any edit, and the AI produced
  a reviewable diff sketch the operator could approve. A stronger explicit kickoff:
  *"Explore mode: root-cause why bare-import-exports-map passes locally but fails in CI,
  then sketch the minimal package.json fix — don't edit yet."*
- **High-leverage one-word follow-ups.** `2` / `a` / `ok, switch` / `yes` / `commit and push`
  each unlocked a full phase because the AI had already staged the next concrete step and
  was waiting for a go/no-go. This works *only* because the AI ended each turn with an
  explicit "say the word and I'll execute" recap.
- **`currently git is unattached, attach back to develop, resolve conflicts`** — precise
  state description + desired end state let the AI act without a discovery round-trip.

## 5. Steering & corrections (what to watch for)

| The AI tended to… | The human had to steer by… | Bake this in next time by… |
|-------------------|----------------------------|----------------------------|
| Draft `pi-ai` into root `dependencies` first | (self-caught, but the pattern is the risk) | State up front: "root package.json is published — CI-only deps go in `devDependencies`, never `dependencies`/`peerDependencies`" |
| Wait for explicit mode switch before editing | "ok, switch" | This is correct explore-mode discipline — keep it; the guardrail is *stating* when to switch |
| Assume the local pass meant the fix was unneeded | operator drove the CI-first framing | Always diff `npm ci` (lockfile-strict) vs local `npm install` before trusting a green local run |
| Leave HEAD detached after a jj rebase | "attach back to develop, resolve conflicts" | End any jj-rebase flow with an explicit `git checkout <branch>` reattach step |

## 6. Skills, tools & memory created — and why they're effective

No new skill or memory was created this session. The workflow is repeatable enough to
warrant one:

- **Recommended skill: `diagnose-ci-only-dep-resolution`** — captures the CI≠local
  lockfile-nesting failure mode. *Solves:* the recurring "passes locally, fails in
  `npm ci`" class where a package is hoisted locally but nested per the lockfile.
  *Removes:* the manual lockfile-vs-tree diffing and the dependencies-vs-devDependencies-vs-peer
  slot decision for a **published** root package. *Invoke when:* a resolver/bare-import
  test is green locally and red in CI.

The session leaned on existing skills correctly: `openspec-explore` (think-then-apply
discipline) and the project's standard `npm run build` + `npm run reload` rebuild flow.

## 7. Pitfalls & dead ends

- **`grep -l "@earendil-works/pi-ai" packages/*/package.json` failed** (no matches → non-zero
  exit). Use `grep -rn ... 2>/dev/null | head` when a glob may match nothing.
- **`curl http://localhost:8000/api/health` failed** — the dashboard wasn't up yet in the
  redeploy phase. Bring the server up (or check mode) before probing `/api/health`.
- **Local green is a false signal.** The test passed locally only because a stale May-20
  ad-hoc `npm install` had hoisted `pi-ai` to top level. Trust `npm ci`, not the working tree.
- **Detached HEAD after `jj rebase`.** The working-copy commit went empty (PR #50 already
  landed the same generated file); always finish with `git checkout develop` to reattach.
