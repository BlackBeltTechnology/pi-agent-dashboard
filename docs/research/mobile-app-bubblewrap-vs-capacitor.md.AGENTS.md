Research artifact. Explore-mode, no change / no impl. Ship pi-dashboard as mobile app: Google **Bubblewrap** (PWA→Android TWA APK) vs **Capacitor** (embedded webview, iOS+Android). Disambiguates Google Bubblewrap from Linux `bwrap` sandbox. Substrate ~90% present (public/manifest.json + sw.js + icons = valid TWA input; packages/shell = zero-dep static PWA at https://pi-dashboard.dev = mobile-companion model); NO repo extension addresses mobile (0 hits). DECISIVE CONSTRAINT: TWA origin-locked via Digital Asset Links (.well-known/assetlinks.json matching signing SHA-256) → only viable origin = project-controlled pi-dashboard.dev (shell), NOT per-user dynamic tunnels (zrok/ngrok/tailscale). TWA fork: A wrap-shell-as-is (low effort, connect-nav may pop URL bar) vs B shell-hosts-client (bundle packages/client, all in-origin). VERDICT: Capacitor better fit — sidesteps origin lock (bundles shell, connects out via existing pairing, no URL bar) + iOS + native push/biometric/secure-store keyring. Sequencing: Bubblewrap Option A as MVP proof, Capacitor as durable answer. Bubblewrap mechanics: init --manifest→build (APK/AAB)→install; Play App Signing re-sign caveat; CI via deploy-site.yml. Sources: github.com/GoogleChromeLabs/bubblewrap, developer.chrome.com TWA quick-start/overview.
