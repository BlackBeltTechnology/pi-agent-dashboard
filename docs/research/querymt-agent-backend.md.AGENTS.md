Research dossier. Can query.mt replace pi under dashboard? Explore-mode, no change / no impl. querymt = Rust agent runtime, `qmtcode --config agent.toml`, one TOML = provider/model/tools/scheduling/memory/mesh, 17+ WASM/native providers, modes `--stdio` (ACP) + `--dashboard` (own WS API), crate `querymt-agent` v0.3 early. No in-process JS/TS extension API like pi `ExtensionAPI`; only config hooks (out-of-process command, `mcp_tool`) + compiled Rust middleware. Coupling measured: protocol `packages/shared/src/protocol.ts` (~94 msgs) loose; bridge `packages/extension/src/` (78 files) tight (`pi.events` ×84, `sendUserMessage` ×28, `on` ×14, `registerTool` ×8…) + ~29 plugin source files. Verdict: OPTION B second backend — spawn `qmtcode --stdio`, new `SessionDriver` seam (`PiDriver` + `AcpDriver`), translate ACP → protocol. Full swap (A) huge; provider-only (C) low value. Works chat/tool cards/abort/permissions/model pick; loses flows/subagents/commands/UI/kb/roles/session-tree/context-budget. Hooks = control points not telemetry; hybrid = dashboard-owned long-lived MCP server (`mcp_tool` execution hooks + tools) + tiny CLI for session/stop/delegation command hooks. pi→qmt gaps: no streaming/message_end/model_select equivalents; `additional_context` only on stop/post_compaction/delegation_*; max one `stop` continuation per turn. Open: session resume via ACP, rpc-keeper assumed pi, v0.3 ACP coverage, overlap with qmt own dashboard, MCP injection via generated per-session TOML. Next: ACP+hook traffic spike, read qmt WS API.
