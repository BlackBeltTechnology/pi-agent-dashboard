# research/dsh-harness-support-feasibility.md — index

Research artifact. Feasibility of supporting DeepSeek Harness (`dsh`) as the agent harness instead of pi. Explore-mode output, no OpenSpec change. Source: github.com/deepseek-ai/deepseek-harness (docs read 2026-08-18). Core finding: not a harness swap — a bridge-layer + event/session-model rewrite. Deepest mismatch = TOPOLOGY: pi sessions are OS processes on disk (fan-in) vs dsh sessions are in-memory objects in one process (fan-out via `ctx.sessions`/`ctx.agents`/`session/event` firehose/`sessionProjections`+cache; browser = HTTP POST up + `events.mux`/`events.host` WS downlinks). Coupling scan (measured): `extension/` 15k LoC = full rewrite as dsh Cordis plugin; `shared/` ~40%, `server/` ~30% rewrite; `client/` 81k mostly survives if wire protocol stable. Event map pi→dsh (turn=N steps, waterfall tools, no `ctx.ui`). Two concepts pro/con: A Fan-in/Bridge (keep our stack, cross-machine native) vs B Fan-out/Native (build on dsh web, less code, single-process, no cross-machine). Recommends `Harness` seam in shared/ first. dsh is dev-preview (breaking changes) = standing risk.
