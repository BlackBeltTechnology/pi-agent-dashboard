## Decisions

### D1 — #1116: own-Other option under an opted-in prompt (confirmed — owner, 2026-11-20)
Options:
- A. No change; document the split as intended.
- B. **Chosen (recommended):** keep opt-in. For an opted-in prompt, the inline row replaces the caller's own "Other…" option; typed text is the answer.
- C. Default-on for all selects. Rejected: pi-flows branch routing needs an exact option (archived D1).

Why B: `allowOther: true` already declares "free text is acceptable", so B only removes the duplicate row + second `input` prompt (the observed inconsistency) for the dominant emitter, `ask_user`. Non-opted-in prompts stay byte-identical. One predicate stays shared by UI and REST (`isOtherAllowed`), so the row shows iff the REST road accepts custom text. The literal "Other (describe)" string is still a valid option for REST clients. Heuristic stays English-only: the `hasOwnOtherOption` regex becomes per-option `isOwnOtherOption(o)` (non-strings never match); `hasOwnOtherOption` is removed (its tests move to `isOwnOtherOption`). Each renderer computes `listedOptions = options.filter(o => !(otherAllowed && isOwnOtherOption(o)))` once and uses it for rows, "Select all", counts (`N of M`) and answer-value filtering, so the hidden option can never be selected or submitted by the UI. Edge: `options: ["Other"]` alone with `allowOther` shows only the inline row (listed options empty).
Residual: the model may still ask a follow-up `input` after getting custom text; the existing custom-answer note line already tells it the user typed free text.

### D2 — #1117: store shape
- Live source of truth: a module-level in-memory `Map` (`lib/state/prompt-draft-storage.ts`), written synchronously on every change and read on mount, so a surface mounted right after another (card → dialog, session switch) never sees stale storage. `sessionStorage` (NOT `localStorage`; confirmed — owner, 2026-11-20) `ask-draft:<sessionId>:<promptId>` → `{v:1, savedAt, state}` is a mirror for reload survival within the tab (cleared by the browser when the tab closes, so free-text that may hold credentials/PII never outlives the tab; selections use the same store for simplicity). Card ↔ dialog draft sharing is same-tab only (the in-memory Map is per-tab, and `sessionStorage` is not shared across tabs/windows); a second tab or window starts with no drafts. A duplicated tab copies `sessionStorage` once at duplication, then diverges; `state` is renderer-specific JSON (select/multiselect: `{otherActive, otherText, checked[]}`; input: `{value}`; batch: `{answers, step, otherDraft}`).
- Mirror writes debounced at 300 ms (the literal used by the chat-draft effect, `App.tsx:1750`; no shared constant exists, so the store declares its own `PROMPT_DRAFT_DEBOUNCE_MS = 300`), and flushed synchronously on renderer unmount and on `pagehide`, so typing then switching session or reloading inside the window loses nothing. Per-entry cap 16 KiB, measured as `JSON.stringify(entry).length <= 16384` (UTF-16 code units, inclusive; no `TextEncoder`) (over cap → skip the mirror write, keep the memory entry); parse failures → ignore entry. `sessionStorage` access or `setItem` throwing (quota, private mode, `SecurityError`) → swallow silently and stay memory-only for that entry (same rule as over cap; no UI notice, same-tab restore still works). `usePromptDraft` with no `sessionId` → ephemeral state, nothing persisted or restored (same rule as a missing `promptId`; no `ask-draft:undefined:*`/`ask-draft::*` key).
- `usePromptDraft(sessionId, promptId)` re-initialises when the key changes (`QuestionDialog` reuses one renderer element across questions; add `key={promptId}` or equivalent). Simultaneously mounted surfaces (card + dialog) each initialise from the store on mount and write on their own edits; a surface never writes unless its user edited, so no cross-surface subscription is needed.
- Images (input renderer, batch input answers): module-level in-memory `Map` keyed by the FULL draft key `ask-draft:<sessionId>:<promptId>` plus step index for batch (never `promptId` alone — no cross-session leak); survives session switch, not reload — matches `chat-input-state` "Per-session pending image attachments". `images` are stripped from `answers` before serialising to `sessionStorage` (a base64 image would blow the 16 KiB cap) and re-joined from the Map on restore. The Map feeds `useImagePaste` controlled mode (`images`/`onImagesChange`).
- Images are NOT restored in `QuestionDialog`: its answer road is text-only (`lib/questions/dialog-answer.ts` strips images), so restoring one there would show an image that is silently dropped on submit. Renderers take an optional `restoreImages` prop (default true); the dialog passes false and neither reads nor writes the image Map.
- Cleared when the request leaves `pending`, driven from STATE not from a mounted view: an App-level effect over `sessionStates[*].interactiveRequests` calls `deletePromptDraft(sessionId, requestId)` for every non-`pending` request that still has a draft (idempotent `removeItem` + memory entry + in-memory image entries for that key and all its steps + pending-timer drop). The sweep skips requests with no draft (presence check against the in-memory store / known keys, not a `sessionStorage` write), because it re-runs on every `sessionStates` change (each streamed event) and must not `removeItem` resolved requests repeatedly. This covers prompts answered in the terminal or dismissed while their renderer is unmounted. Clearing at status transition (not at the click) keeps the draft if delivery fails and the prompt stays pending (the dialog's `answerError` path). After deletion, the unmount flush MUST NOT re-write the entry (flush writes only when the memory entry still exists). A shortened TTL sweep (24 h from `savedAt`) at store hydrate is the fallback for requests that never reach this client's state again (session removed, dialog-only rows) in a long-lived tab; the 7-day TTL is dropped because `sessionStorage` is already bounded by the tab's lifetime, and entries never outlive it. No dedicated session-removal hook: `session_removed` keeps the session row as `ended` (`useMessageHandler.ts` `session_removed` case) and its pending requests become non-pending, so the sweep above covers it.
- A prompt without an id (an old-server `QuestionRow`/detail from a rollback or mixed-version pair arrives without the optional `promptId`) is NOT persisted or restored: `usePromptDraft` falls back to ephemeral component state, so id-less prompts never share a `ask-draft:<sessionId>:undefined` bucket. Chat-card prompts always have `requestId`; only the dialog can lack it.
- Storage medium: `sessionStorage` for all drafts (free-text `input` and selections) — confirmed (owner, 2026-11-20). Rejected: `localStorage` (credentials/PII in `input` prompts would persist across browser restarts and be readable from other tabs). Trade-offs accepted: drafts do not survive closing the tab/browser and are not shared across tabs/windows; not persisting sensitive prompts at all stays a possible follow-up. Compat/rollback: previously written `localStorage` `ask-draft:*` keys do not exist (feature is new), so there is no migration; a rollback leaves only per-tab `sessionStorage` keys that vanish with the tab.

### D3 — #1117: cross-surface key
Key by (`sessionId`, `promptId`). Chat card/panel already hold `request.requestId` = promptId and the session id; the dialog only has the store id. Chosen: add optional `promptId` to `QuestionRow` (store already has `rec.promptId`, `question-store.ts:74`). Rejected: key by store id only (surfaces would not share); lookup endpoint (extra round-trip for one string).
Verified: chat `requestId` is the PromptBus `promptId` (`useSessionState.ts:160-167` `addPromptBusRequest` → `addInteractiveRequest(state, msg.promptId, …)`) and the store keys on `msg.promptId` (`question-store.ts` `keyOf(sessionId, promptId)`). Task 3.1 pins this with a test written first.

### D4 — #1136: directory-home composer
`CommandInput` gains `allowImageOnlySend` (default true); `DirectoryHomeView` passes false since spawn takes text only. Simpler than teaching spawn about images (non-goal).

## Risks
- Draft unmount/`pagehide` flush after a clear could resurrect an entry → flush writes only while the memory entry exists.
- Restoring a batch draft whose `questions` changed (same promptId, different shape) → validate lengths/step bounds on load, else discard.
- Restored Other row on a prompt that is no longer opted in → renderer ignores `otherActive` unless `isOtherAllowed`.
