A. Choosing the editor for a file

The mode switcher is unchanged: Preview first, then one craft mode per extension (each extension has exactly one craft claim, D2), so the choice stays at two buttons (Hick's Law). The gap is files with no built-in viewer (.psd .designcraft .scraftz .dng .dwg): Preview shows only "binary", and the way out is a small button in a different row. Proposal A4: the binary notice names the available mode as a button (Nielsen #6 recognition rather than recall, #10 help users recover). Core change in BinaryWarn, reading the same matching claims the switcher already has.

B. Frame toolbar per app type

Today's toolbar is app name + Save target (Overwrite / Copy). Two new types make that toggle mislead: in a foreign-format tab Ctrl+S never touches the file (it creates a .psd next to it), and a view-only tab cannot save at all. Design D4 already removes the toggle for preview claims. Proposal B2/B3: a short status chip states where saves go before the user saves (Nielsen #1 visibility of system status, #5 error prevention). Found while measuring: the shipped selected Save-target button (--accent-text on --accent-soft, 12 px) is 4.49:1 in dark and Nord, just under WCAG AA 4.5:1. All states here use --text-primary on --accent-soft (the pairing the token is documented for); proposed as a one-class fix in CraftFrame.tsx.

C. First overwrite when the app cannot confirm the file opened

Five apps (PdfCraft, CADCraft, DesignCraft, SoundCraft, DeckCraft) never report which document they opened, so every instance of them is "unconfirmed" (D4 fallback). As designed, the first overwrite then shows two modal dialogs back to back with the same three choices: the plugin's check, then core's fidelity notice. Repeated near-identical confirmations train users to click through (NN/g, "Confirmation dialogs can prevent user errors, if they are not overused"; Nielsen #8 minimalist design). Proposal C3: because "unconfirmed" is fixed per app, not per open, put the check sentence into those claims' static firstOverwriteNotice and drop the plugin dialog. One dialog, core-owned, once per instance, same protection. This also removes the documented double-prompt trade-off and test rows E28/F4.

D. Saving from an app that writes its own format

PhotoCraft opened photo.jpg and Ctrl+S produced a .psd. The dialog (D6) names the real target file, not the name typed in the app, and offers the next step that keeps work in one place ("Create and open"). Button order follows the plugin's existing in-frame dialog: primary first. Proposed copy changes only: say why in one line, and name the file on the buttons so each choice is self-describing (Nielsen #2 match with the real world).

E. Apps that name the save after their content (SoundCraft)

SoundCraft suggests the session name, so opening mix.scraftz and saving asks about "Midnight Groove.scraftz". The existing Save As question is reused (D10); without an explanation the user cannot tell why the name changed. Proposal E2: one sentence for saveName: "inner-title" profiles, and the Overwrite button names the tab file. Answer remembered only for the same suggested name (as designed).

G. Settings: ten more apps

Settings grows from 1 to 11 app groups. As designed, each new app shows a disabled version selector with a reason. A disabled control the user can never enable is noise, and its reason is easy to miss (NN/g, "Disabled buttons" guidance: explain or remove). Proposal G2: (1) a fixed channel renders as a read-only fact, "Verified 0.8.0", with the reason as hint text, no select; (2) groups are chunked under three headings by what the app does to your files (Miller / chunking, Gestalt common region), so the user knows which apps write to the workspace. Spec text "selector disabled with the reason" changes accordingly.
