## Why

The suite is green but its numbers mislead. Measured on the extension project (2025-09-18, provider temporarily installed): files that tests load report 93% line coverage, yet `packages/extension/src/bridge.ts` — the runtime entry point, now 4,227 of the package's 24,977 source lines (17%) — is imported by no test, sits at 0%, and is absent from the report because no coverage provider is configured. The same "green only because isolated" pattern hides elsewhere. Re-measured 2025-10-11 on the client project (639 files, 8,228 tests): 57s wall isolated; with `--no-isolate`, 173 tests in 49 files fail from leaked globals and mocks (missing `ThemeProvider` / `SplitWorkspaceProvider`, `getBoundingClientRect` stubs, call-count leaks), and wall time *rises* to 221s because leaked state stalls files (`AddFoldersDialog` 210s, `MergeConfirmDialog` 100s). So `isolate: false` is not a speed win until hygiene lands — the gate below decides on measured numbers. Separately, at least 45 test files (`readFileSync` of a literal `.ts`/`.tsx` path; ~89 counting path-built reads) assert on source text rather than behaviour. Reproduce: `HOME=$(mktemp -d) npx vitest run --project @blackbelt-technology/pi-dashboard-web --reporter=json` for timings, add `--no-isolate` for the failure count, and `--coverage.enabled --coverage.provider=v8 --coverage.reportOnFailure` (provider temporarily installed) for the 93%. Trust and speed share one root: tests were never gated on what they actually load or leave behind.

## What Changes

- **Honest coverage report.** Add `@vitest/coverage-v8` (root devDependency) and a `test:coverage` script that carries the same `HOME=$(mktemp…)` + `--localstorage-file` wrapper as `test`, reports *unloaded* source files at 0% (explicit `coverage.include` — vitest 4 reports only loaded files otherwise), and still writes the report when a test fails (`coverage.reportOnFailure: true`). Scope: `packages/*/src/**` minus `__tests__`/`test-support`; electron and `scripts/` are out of the coverage scope (stated, not silent). Untested large files (`bridge.ts`, `server/src/session/session-api.ts`, `shared/src/tool-registry/definitions.ts`) become visible.
- **Bridge handler extraction (continues `bridge-decomposition`).** `bridge.ts`'s `export default function (pi)` currently holds: 5 named `pi.on` handlers with bodies (`session_start`, `turn_end`, `session_shutdown`, `session_info_changed`, `project_trust`), 5 thin `pi.on` delegators into already-extracted modules (`tool_call` ×2 → `fanoutAdmission` / `pathGate`, `before_agent_start` → `pathGate`, `tool_execution_end` → `fanoutAdmission`, `cache_warming_decision` → `makeCacheWarmingDecisionHandler`), 2 loops registering `enrichedEventTypes` / `passThroughEventTypes` forwarders, 4 `pi.registerCommand`s, and a 23-branch inbound WebSocket dispatch — all sharing closure state (`sessionReady`, `cachedCtx`, `isActive()`, …). Move the handler bodies, forwarder bodies and dispatch into importable modules that receive an explicit per-incarnation instance object (which references the existing process-global `BridgeState` that survives reload); `bridge.ts` keeps that global state and its cross-reload adoption, the generation counter, `EVENT_BUS_MAP` + the EventBus emit intercept, the 5 thin delegators (their registration order is load-bearing: the path gate registers after fan-out admission), and the registration wiring; the instance carries its captured generation and derives `isActive()` from it. The moved code touches more closure state than the three named (`subagentTickThrottle`, agent-streaming state that survives reconnect, `sessionId`, `connection`, nonce/offline queue, …): design inventories every closure variable the moved code reads or writes before anything moves, and the instance object covers all of them — no module-level state in the new files. Each extracted module gets a test-plan'd suite. Every test that reads `bridge.ts` source text (13 on 2025-10-11 under `packages/extension/src/__tests__/`: `bridge-agent-settled-contract`, `bridge-coalesced-chat-order`, `bridge-polling`, `command-handler`, `command-path-mapping`, `multiselect-dashboard-routing`, `no-session-replacement-calls` (directory scan — picks up new modules by itself), `no-tui-multiselect-arm-regression`, `pi-version-tracker`, `plugin-event-forwarding`, `session-register-carries-pid`, `terminal-reload`, `usage-drain`; found by listing tests that mention `bridge.ts` and checking each calls `readFile`/`readFileSync` on it. `bridge-liveness-heal`, `bridge-queue-update-forward`, `ui-stale-guard` mention `bridge.ts` only in comments — comment refresh only. Re-run at slice start; the set grows) is retargeted to wherever its scanned code now lives, never left passing vacuously. No runtime behaviour change.
- **Source-grep test triage.** Classify each test that reads a source file (≥45 today; slice B's first task fixes the exact set with both detection patterns) and assert on its text: (a) deliberate structural pin with an inline rationale (e.g. `ChatView.notify-gate`, `i18n-orphans`, `engine-purity`, `no-bash-on-windows`, `no-tui-multiselect-arm-regression`) → keep, retarget if its target moved; (b) behaviour that a runtime test can assert → replace; (c) neither → delete with a one-line reason in the commit. No pin is deleted without a replacement or a reason.
- **Global-leak hygiene → cheaper isolation (gated).** Make client tests restore what they mutate (`localStorage` replacement, `getBoundingClientRect` stubs, module-level `vi.mock` state, missing `ThemeProvider`). Move pure client util/reducer tests (no DOM) to the `node` environment via a second project in root `vitest.config.ts` (vitest 4 has no `environmentMatchGlobs`); the jsdom project's include is narrowed so no file runs in both, and the new project imports the shared worker-target module. Then attempt `isolate: false` on the jsdom client project; **adopt only if** three consecutive full runs are green, a run with `--sequence.shuffle` (random file order within forks) is also green, AND the per-file HOME and per-fork localStorage invariants of `parallel-test-execution` still hold, AND the median wall time is ≤ the isolated baseline (on 2025-10-11 the un-hygiened `--no-isolate` run was 4× slower) — otherwise keep `isolate: true` and land the hygiene + node-env wins alone. Split the three subprocess-heavy `shared` files (`ensure-cli`, `git-checkout-roots`, `openspec-poller-parity`) so they don't serialize a worker.

Out of scope: rewriting `bridge.ts` logic, the e2e/Playwright layer, coverage thresholds as a CI gate (report first, threshold later), and the pinned pi version (`pnpm-lock.yaml` resolves `1.0.0`).

Trade-off acknowledged: four orthogonal slices in one change (user decision). Mitigation: design orders them as independently-landable slices — coverage → grep triage → bridge extraction → hygiene/isolation — each green before the next starts.

Ordering against other active changes that edit `bridge.ts` (127 commits touched it between 2025-09-17 and 2025-10-11): `security-boundary-audit` (in progress; inbound dispatch), `add-supervised-tool-approval` (`tool_call` wiring, which stays in `bridge.ts`), `skip-rpc-probes-in-event-forwarder` (forwarder path). Slice C starts only after none of these is mid-apply; if one lands during slice C, re-run the closure inventory and the reader search before the next move commit. Slices A, B, D are independent of them.

## Capabilities

### New Capabilities
- `test-coverage-reporting`: `npm run test:coverage` produces a v8 report covering every file under `packages/*/src` (loaded or not), survives test failures, runs under the isolated-HOME wrapper, and states its exclusions.

### Modified Capabilities
- `bridge-decomposition`: `pi.on` lifecycle handlers, event forwarders and inbound message dispatch live in importable modules that never import the entry point; `bridge.ts` delegates through a per-incarnation instance object and keeps the global state, adoption and generation counter.
- Every spec whose requirement text pins moved code to `bridge.ts` gets a location-only delta (behaviour unchanged; each MODIFIED block is the current main text with only the file pin reworded). 13 specs mention `bridge.ts`; 10 carry deltas: `bridge-extension` (session-replacement caches, session-scoped cache, multiselect lint target, multiselect patch, slash-dispatch call site), `bridge-decomposition` (session-sync, model-tracker delegation), `command-routing` (`flow_management` handler), `mid-turn-prompt-queue` (`sessionPrompt` fallback, `edit_followup_entry`), `multiselect-dialog`, `agent-session-context-injection`, `pi-api-feature-detection`, `ask-user-tool`, `model-selector`. No delta: `flow-event-bridge` (`EVENT_BUS_MAP` + intercept stay in `bridge.ts`), `jiti-cjs-transpile-safety` (import graph `bridge.ts → command-handler.ts` unchanged), `markdown-knowledge-base`, `electron-launch-source` (entry-point path only). Deltas are regenerated from main if main changes before archive.
- `parallel-test-execution`: pure client tests run under `node`; the jsdom client project may run `isolate: false` only under the gate above.
