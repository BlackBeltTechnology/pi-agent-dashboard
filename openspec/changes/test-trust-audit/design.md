## Context

Measured this session (reproduction commands in `proposal.md`): the extension project reports 93% line coverage over the 77 files tests load, while `packages/extension/src/bridge.ts` (3,630 lines, the entry point) is loaded by none and absent from the report; `bridge.ts` is one `export default function (pi)` closure holding 5 named `pi.on` handlers, 2 forwarder-registration loops (`enrichedEventTypes` ~L2081, `passThroughEventTypes` ~L2510), 4 `pi.registerCommand`s and a 21-branch `msg.type` dispatch, all sharing closure variables. The client project takes 109s wall for 496 files with a 66ms median test body; `--no-isolate` cuts nothing because 417 tests then fail on leaked state. 14 test files assert on source text; 10 of them read `bridge.ts`.

Existing constraints: `bridge-decomposition` already extracted `session-sync`, `model-tracker`, `flow-event-wiring`; `parallel-test-execution` mandates per-file `HOME` via `setupFiles`, per-fork localStorage, a single `vitest.workers.ts` worker target; root `vitest.config.ts` lists 33 project directories under `test.projects` (vitest 4 — no workspace file, no `environmentMatchGlobs`).

## Goals / Non-Goals

Goals: (1) a coverage report that cannot hide an unloaded file; (2) `bridge.ts` handlers/dispatch importable and tested; (3) every source-text test either justified, retargeted, replaced or deleted with a reason; (4) client suite faster via node-env split and, if the gate passes, `isolate: false`.

Non-goals: changing bridge behaviour; coverage thresholds in CI; touching Playwright/e2e; the pi version pin; refactoring tests beyond what hygiene requires.

## Decisions

**D1 — Coverage via root config, explicit include.** `@vitest/coverage-v8` as a root devDependency (pnpm), pinned to the exact installed `vitest` version (the provider peer-pins exactly; a caret range can install a refused mismatch). Root `vitest.config.ts` gains `test.coverage = { provider: "v8", include: ["packages/*/src/**/*.{ts,tsx}"], exclude: [".../__tests__/**", ".../test-support/**", "**/*.d.ts", "packages/electron/**"], reportOnFailure: true, reporter: ["text-summary", "json-summary"] }` with a comment naming the out-of-scope dirs (electron, `scripts/`, `tests/`, `.pi/`); enabled only by the `test:coverage` script (`… vitest run --coverage`), which copies the `HOME=$(mktemp …)` + `--localstorage-file` wrapper from `test`. Explicit `include` is what makes vitest 4 report unloaded files. Alternative rejected: per-package coverage blocks (33 copies).

**D2 — Bridge extraction shape: keep the two-tier state that exists, add an explicit per-incarnation object, move bodies.**
- State today is two-tier and must stay so: (i) `BridgeState` on `process[BRIDGE_KEY]` (`bridge.ts` L118–167) is **process-global and survives reload** — `initBridge` (L196–236) adopts `prev.sessionId/attachedChange/namerState/dashboardSpawned/shouldStopAfterTurn`, disconnects `prev.connections`, clears `prev.timers`, bumps `prev.generation`; `isActive()` compares a *captured* generation against that shared object, which is how the old incarnation's handlers learn they are stale. (ii) Per-incarnation closure variables (`sessionReady`, `lastSessionFile`, `cachedCtx`, `subagentTickThrottle`, the offline queue, …) live inside `initBridge`.
- Change: tier (i) is untouched — `getBridgeState`, the `prev` adoption, the subagent re-entry guard (`prev.pi !== pi`) and the generation bump all stay in `initBridge`. Tier (ii) becomes an explicit `BridgeInstance` object (`bridge-handlers/instance.ts`: type + `createInstance(pi, generation, shared)`), created once per `initBridge` call after the bump, carrying its captured `generation` and an `isActive()` that reads `shared.generation === this.generation`. Handler modules receive `(inst, pi)`; they read cross-reload values through `inst.shared` (the tier-i object). Reload takeover therefore works exactly as before: the old `inst` sees the shared generation move on and goes inert.
- **Boundary rule.** `bridge-handlers/*` never import `bridge.ts` (a one-line guard test enforces it). Helpers that only moved code calls move with it — `handleSessionChange` (~L3463, sole caller inside `session_start`) and `startGitPollTimer` (~L3512, callers inside `session_start` and `handleSessionChange`) therefore go into `lifecycle.ts`. Only the `sendStateSync`/`replaySessionEntries` wrappers (~L1951, called from retained reconnect wiring ~L1444/1455 *and* from moved handlers) are dual-consumer; they go to `bridge-handlers/session-helpers.ts`, imported by both sides — no cycle. The closure inventory confirms this classification before the move. The whole `session_start` handler (L2642–~3460, ~820 lines: promptBus construction, default adapter, `ui-prompt-patch` call, asset persistence, image paste, timers) moves to `lifecycle.ts`; it is the largest single move and lands as its own commit.
- **Closure inventory first.** Before moving anything, a script lists every identifier declared inside `initBridge` and referenced from the code being moved (`rg`/ts-morph over the moved ranges); that list *is* the `BridgeInstance` field set. It is checked against the existing `BridgeState` fields so nothing that belongs to tier (i) is duplicated into tier (ii). Nothing module-level in the new files.
- New dir `packages/extension/src/bridge-handlers/`: `instance.ts`, `lifecycle.ts` (the 5 named handlers as `(inst, pi) => handler`), `forwarders.ts` (the two loop bodies as `registerEnrichedForwarders(inst, pi)` / `registerPassThroughForwarders(inst, pi)`), `dispatch.ts` (`handleInboundMessage(inst, msg)`, 21 branches), and `ui-prompt-patch.ts` (the sub-block at ~L2771–2920 — starting at the `originalNotify` / `const originals = {…}` capture, not at the adapter registration — that captures `originals`, registers the already-extracted `createTuiPromptAdapter`, and patches `ctx.ui.select/input/confirm/editor/multiselect` onto `bus.request`). It is *not* `tui-prompt-adapter.ts` — that module already exists and stays. The `no-tui-multiselect-arm-regression` guard (bans `originals.custom` co-occurring with `prompt.type === "multiselect"`) is already vacuous: it scans `bridge.ts`, but the arm it bans (`else if (prompt.type === "multiselect" … originals.custom …)`) can only be re-added in `tui-prompt-adapter.ts`, where both substrings would sit together. Under D4 it is classified **keep + retarget**: same substrings, scan `tui-prompt-adapter.ts` — one line. Its negative check re-adds that arm there.
- `bridge.ts` keeps: constants, `BridgeState`/`getBridgeState`/`initBridge` adoption logic, `EVENT_BUS_MAP` + emit intercept, `pi.registerCommand` wiring (commands are thin; they stay), connection setup, and calls into the five modules.
- Order: ui-prompt-patch → dispatch → lifecycle → forwarders, one commit each, extension suite green + `npm run reload` smoke between commits. `doubt-driven-review` runs on the `BridgeInstance` shape after the inventory and before the first move.
- Alternative rejected: rewriting `bridge.ts` as a class — larger diff, same testability.

**D3 — Guard-test retargeting is part of each extraction commit.** The 10 files that read `bridge.ts` are listed in the proposal. Each commit that moves code updates the readers whose pattern moved, and each retargeted guard gets a negative check (re-introduce the anti-pattern in the new module → guard fails) so vacuous passes are impossible.

**D4 — Source-grep triage produces a table, then acts.** `docs/` gets no new prose; the triage table lives in this change's `tasks.md` outcome and the commit messages. Categories: keep (a JSDoc `@structural-pin <reason>` tag on the `describe` block is required; a guard test asserts every test that `readFileSync`s a `.ts`/`.tsx` source path carries it), replace (behavioural test in the same `__tests__` dir), delete (reason in commit). `readFileSync` of a *docs/config* file (i18n orphans, AGENTS rows) is not "source-grep" and is out of scope.

**D5 — Node-env split as a second config file, not an inline `extends`.** Vitest 4 merges an `extends` project through vite `mergeConfig`, which *concatenates* arrays (`include`, `exclude`, `setupFiles`) and resolves relative paths against the root project — so an inline node project would inherit the jsdom `setupFiles` and its own globs would be excluded. Instead: new `packages/client/vitest.node.config.ts` that imports the base config object and `PARALLEL_MAX_WORKERS` from `vitest.workers`, spreads `base.resolve` (aliases), and sets `test: { name: "@blackbelt-technology/pi-dashboard-web-node", environment: "node", pool: "forks", maxWorkers: PARALLEL_MAX_WORKERS, include: [<pure globs>], globalSetup: base.test.globalSetup, testTimeout: base.test.testTimeout }` with no `setupFiles`. Root `vitest.config.ts` lists the file path (precedent: `packages/electron/vitest.build-contract.config.ts`), and `packages/client/vitest.config.ts` adds the same globs to `exclude`. Candidate files are found by a script: a test file and its direct in-repo imports contain none of `react`, `@testing-library`, `document.`, `window.`, `localStorage`, `navigator`; the resulting include list is then *verified by running* the node project — any file that fails there for a DOM reason is moved back to jsdom before the slice is committed. Alternative rejected: per-file `@vitest-environment node` docblocks — ~150 edits and silently lost on copy-paste.

**D6 — Hygiene sweep is driven by the `--no-isolate` failure list, not by reading all 496 files.** Run `--no-isolate` once, group failures by message, fix the shared setup (`src/test-support/`) where a pattern repeats (a `restoreLocalStorage` helper, a default `ThemeProvider` wrapper in a shared `render` helper), then the residual files. Re-run until zero, then run the four-condition gate from the spec. If the gate fails, record why here under Risks and keep `isolate: true`.

**D7 — Subprocess-heavy shared files.** Split by scenario group so no single file exceeds ~10s; no change to what is asserted.

**D8 — Performance is measure-only (user decision).** No pass/fail threshold. Before/after wall time, `environment` and `import` totals for the client, client-node and shared projects are recorded in a `## Measurements` table appended to this file when the hygiene slice lands; the `isolate` gate (D6) is the only perf-related pass/fail.

## Risks / Trade-offs

- **Closure inventory misses a variable** → handler reads `undefined` at runtime while unit tests (stub instance) pass. Mitigation: TypeScript `noImplicitAny` on the moved code, plus the `npm run reload` smoke after each extraction commit and the existing 145 extension test files (~1,850 cases).
- **Reload takeover (`isActive()`)** — the behaviour unit tests are least likely to see. Mitigation: dedicated scenario in the spec; a test builds one shared `BridgeState`, two `BridgeInstance`s with generations 1 and 2, sets `shared.generation = 2`, and asserts handlers wired to instance 1 do nothing while instance 2's run. Cross-reload adoption (`sessionId`, `attachedChange`, `shouldStopAfterTurn`, …) stays in `initBridge` and is covered by the existing `agent-session-context-injection` / stop-after-turn tests.
- **`isolate: false` gate fails** → perf win limited to node-env split (estimated ~150 files × ~1s jsdom setup). Accepted; the hygiene is still worth landing.
- **Spec churn**: 9 requirement blocks re-stated to remove `bridge.ts` file pins. Accepted once; specs should not name files, so this prevents the same churn on the next extraction.
- **One change, four slices** (user decision). Mitigation: strict slice order coverage → triage → extraction → hygiene; each slice green before the next; `SHIP_IT_BLOCKED.md` on any red slice rather than pushing through.
