## Goals / Non-Goals

**Goals**
- "Isolated spawn" mode: the spawned session's pi resources, prompt, credentials and env carry nothing from the operator's agent dir, the server process env, or the cwd's ancestors — enforced by the host, not left to plugin discipline.
- The dashboard bridge still loads, registers and is abortable (control-channel invariant).
- A plugin can verify isolation actually happened, and can detect a missing host policy.

**Non-Goals**
- Provisioning the agent dir's contents/credentials (plugin's job; `add-web-chat-plugin`).
- A `--no-extensions` toggle (still forbidden).
- OS-level sandboxing (filesystem/network). The isolated session is contained by its tool allowlist; `HOME` stays the operator's.
- Making session roads policy-controllable.

## Decisions

### D1 — `scope.agentDir` turns a spawn into an isolated spawn
Setting `scope.agentDir` (absolute, plugin-owned) selects isolated mode. Env `PI_CODING_AGENT_DIR=<agentDir>` (pi has no CLI flag). A test pins that the installed pi's agent-dir env name is `PI_CODING_AGENT_DIR` (pi derives it from its branding, `config.js:476`) so a rebrand fails CI instead of silently escaping. Alternative (`scope.systemPrompt` + `-ne -e <bridge>`) rejected in planning: isolates the prompt only.

### D2 — Host forces the containment flags
Isolated mode always emits `--no-builtin-tools`, `--exclude-tools read,bash,edit,write,grep,find,ls` (∪ plugin `excludeTools`), `--no-context-files`, `--no-approve`, `--no-skills`. `--no-builtin-tools` alone is insufficient: pi activates `options.tools` names regardless of it (`dist/main.js:426-434`, `sdk.js:148-160`), and `_isAllowedTool` honours only `excludeTools` (`agent-session.js:1117-1121`), so `scope.tools:["read"]` would re-enable `read`. `agentDir` alone does not stop cwd-ancestor `AGENTS.md` or trust-gated project resources, and `HOME` stays the operator's, so any built-in file/shell tool could read the operator agent dir directly. The model can use only tools registered by the plugin's own extensions and skills listed in `scope.skills` (`--skill` bypasses `--no-skills`).

### D3 — cwd policy merged, minus `skills`
A cwd policy is tighten-only (`cwd-policy.ts`: allowlists intersect, denylists union, `no*` sticky) except `skills`, whose `--skill` paths load even under the forced `--no-skills`. Isolated spawns merge the policy with `skills` discarded, so operator tightenings still apply and nothing is added (MODIFIED `host-cwd-policy`).

### D4 — Bridge loaded by its extension entry file
Per spawn the server resolves the bridge dir from the same source non-isolated spawns load it from — the dashboard bridge package entry in the operator's pi `settings.json#packages` (written by `registerBridgeExtension`, `bridge-register.ts:135`, updated on overlay switch) — and appends `-e <dir>/<pi.extensions[0]>` — a file path, so pi loads only that file (`package-manager.js:1073-1077`) and not the package's skills. `existsSync` is checked at spawn (pi silently skips a missing `-e` path, `package-manager.js:1068-1072`, which would give a false `isolated: true`). Appended on the headless plugin path after `sessionFlagsToArgv`; deduped against `scope.extensions` (pi also dedupes by canonical path, `resource-loader.js:782-794`).

### D5 — Validation in the hook, on raw options, before any state is filed
`validateAgentDir` and the combination checks run right after mapping and before `pendingPluginRefRegistry` / initial-prompt / `automationRun` filing. Combination checks read the raw options (the mapper drops malformed `resume`/`mode`). Raw keys whose value is `undefined` count as absent (same convention as `validatePluginAcpSpawn`, `acp-spawn.ts:125-131`). Refused combos: `resume` incl. `null` (operator session file), non-`local` `mode`, `initialPrompt`; `agent` + `scope` is already refused earlier by the ACP road (`acp-spawn.ts:125-131`) with its existing message, (cwd-keyed FIFO, `server.ts:3446-3457`, consumed by whichever session registers next in that cwd, `event-wiring.ts:1852`). `pluginRef` (token-keyed, `server.ts:3430`; carries `automationRun`) stays allowed. Independently, an isolated registration never consumes the cwd FIFO, so an operator prompt queued for the same cwd cannot land in it. The plugin sends its first prompt after registration. Operator tree = operator agent dir computed exactly as pi does (`PI_CODING_AGENT_DIR` via `normalizePath`, which expands `~` — `config.js:478-480`, `utils/paths.js:59-75` — else `os.homedir()/.pi/agent`) plus `~/.pi` (local token, pins, grants live in `~/.pi/dashboard`), minus the spawning plugin's own data dir (`~/.pi/dashboard/plugins/<pid>`, `server.ts:3847` — the sanctioned provisioning root); realpath when existing, lexical otherwise; repo case-insensitive-filesystem helper. `agentDir`, `cwd` and plugin-supplied paths must all be outside it (a `cwd` of `$HOME` is refused: it is an ancestor of `~/.pi`). Any `mode` other than `"local"` is refused (plugin spawns are headless; `worktree` cwd is unknown until created). TOCTOU accepted (plugin-owned, short window).

### D6 — Mapper flags, never drops, an isolation request
`MappedSpawnOptions` gains `agentDir?: string` and `agentDirInvalid?: true`. A present-but-malformed `agentDir`, or a present non-`null` `scope` that is not a plain object (string, array, number), sets `agentDirInvalid` and the hook refuses. `scope: null` stays "absent" (it cannot carry an isolation request; spreads/JSON produce it). This changes non-isolated spawns with a string/array/number `scope` from "proceed, scope ignored" to "refused" — BREAKING for such callers only.

### D7 — Isolated env: allowlist, then existing shaping
Order: reduce the server env to the platform allowlist (spec lists it; case-insensitive on Windows, where env names are stored as-is, e.g. `Path`; includes CA and proxy vars so provider calls work on corporate TLS networks) → run the existing shaping unchanged (resolved-runtime `PATH` prepend, Electron `argv0` `ELECTRON_RUN_AS_NODE`, bridge control vars `PI_DASHBOARD_BRIDGE`/`_URL`/`_REQUIRE_SERVER_PROOF`/`_SOCKET`/`_SPAWN_TOKEN` under their existing conditions, `process-manager.ts:340-431`) → add `PI_EXT_*`, `PI_CODING_AGENT_DIR`, `PI_DASHBOARD_ISOLATED=1`. Spawn-env contributors are not applied (they configure the operator environment and may carry secrets; MODIFIED `plugin-spawn-env-contributor`). Non-isolated spawns delete an inherited `PI_DASHBOARD_ISOLATED`.

### D8 — Bridge control-channel-only mode
Entered only with `PI_DASHBOARD_ISOLATED=1` AND `PI_DASHBOARD_SPAWN_TOKEN` at first load (a shell-exported marker alone cannot neuter a terminal session); captured once on the bridge's process-global state like `dashboardSpawned` (`bridge.ts:352-357`), because the spawn token is consumed and deleted after first registration (`session-sync.ts:70-72,145-151`) and a reload would otherwise flip isolation off. The bridge only registers (env-pinned endpoint, spawn credential), forwards events, reports its own model list and handles inbound commands. No prompt fragment, no tool/provider/slash-command registration, no `/` prompt/skill expansion (`prompt-expander.ts:32-33` reads cwd `.pi/prompts`/`.pi/skills`), no auto-namer (`auto-session-namer.ts:320`), no dashboard MCP server (`mcp-token-delivery.ts:110-117` registers it with a bearer token), no credential-vault delivery (`vault-delivery.ts`, wired `bridge.ts:1173`, writes granted keys into `process.env`), no server auto-start (`server-auto-start.ts`), no OpenSpec shim provisioning (`openspec-cli-shim.ts:143`), no attachments cleanup (`ask-user-attachments.ts:43`), no provider-catalogue load (`provider-register.ts` reads at activation), no read/write under operator `~/.pi/` (incl. `path-gate/index.ts:33-45` config, `command-handler.ts:1349`, `local-token-header.ts:144`); the path gate denies path-bearing calls outside cwd instead of consulting operator grants. Event forwarding (turn content to the dashboard) is intentionally not isolated. Guard test (1) also enumerates every `homedir()` / `.pi` path construction in `packages/extension/src` and requires each module to be gated or explicitly allowlisted, so a new reader cannot bypass the rule. The bridge reports `isolated: true` in its registration; the server kills an isolated-spawn registration that does not, so `isolated: true` in the result is attested, not only host-asserted. One `isIsolated()` check gates the registration sites; two guard tests: (1) every `pi.registerTool`/`registerProvider` call site in `packages/extension/src` is reached only through the gate; (2) a load-and-turn run with `fs` spied asserts no path under the operator `~/.pi/` is opened. MODIFIED `agent-session-context-injection` and `agent-role-model-tools`.

### D9a — Spawn-scoped bridge credential (user decision)
Over loopback TCP the bridge today proves possession of the operator local token (`local-token-header.ts`, `local-credential-proof.ts`; required whenever `PI_DASHBOARD_REQUIRE_SERVER_PROOF` marks the endpoint), which an isolated bridge must not read. The server mints a ≥256-bit random credential per isolated spawn, binds it to the spawn token, and passes it as `PI_DASHBOARD_SPAWN_CREDENTIAL`. The bridge keys its proof and counter-proof verification with it (same grammar/binding/freshness/replay rules). Server-side, only on the bridge gateway upgrade: a proof that fails against the local-token key is tried against the live spawn-credential set (live isolated spawns capped at 256 — further spawns refused `agent_dir_capacity` — so the fallback costs ≤256 HMACs, p95 < 5 ms; user decision); the shared verifier used by the request-auth hook, network guard, pairing guards and browser WS never consults spawn credentials. Admission is scoped to that spawn's bridge registration; the counter-proof is keyed by the credential class that verified the proof. Revoked on session end, spawn failure or register-watchdog expiry; not persisted (a server restart strands live isolated sessions — plugin respawns). The bridge reads the credential once, keeps it in memory for reconnects and deletes it from `process.env`. Over the owner-only unix socket (POSIX default) no credential is needed. ADDED + four MODIFIED requirements in `pi-gateway-auth`. Alternative (let the bridge read the local token) rejected by the user.

### D9 — Result reports isolation
`PluginSpawnResult` gains `code?` (`agent_dir_invalid` | `isolated_path_invalid` | `agent_dir_unsupported_combo` | `agent_dir_capacity` | `agent_dir_bridge_unresolved`) and `isolated?: boolean`, propagated through the hook's return (`server.ts:~3470`). A customer-facing plugin asserts `isolated === true`. Isolated sessions follow `session-ownership-scoping` unchanged (ownerless unless a trusted owned-spawn road stamps an owner).

### D10 — Session file placement
Isolated sessions write to `<agentDir>/sessions` unless `scope.sessionDir` (validated outside the operator dir) overrides. Listed live via bridge registration; invisible to the operator session-file scanner (intended).

### D11 — `hasHostPolicy()` on the seam
`PluginIdentity`/`PluginIdentitySeam` gain optional `hasHostPolicy()` = `isEnforced() && policyRegistry.hasPolicy()` — the same `PolicyRegistry` instance the identity road gate reads (`server.ts:628`, passed to `createIdentityRoadGate` and `createPluginIdentity`), per call (arming latches after plugin load, `server.ts:610-611`). Equivalent to "named plugin registered" because `PolicyRegistry` accepts only the named plugin (`policy-registry.ts:86-100`). Documented caveat: covers non-session roads and plugin actions only; session roads stay owner-gated; the local operator bypasses policy.

### D12 — Plugin public namespace (user decision: core, in this change)
Need: a customer site's widget calls the plugin cross-origin from anywhere, streams responses, and authenticates with an identity-plane bearer or a plugin-defined credential. Today plugin WS routes require a genuinely-local peer (`plugin-ws-route`), plugin HTTP routes sit inside the guarded `/api` jurisdiction (`localhost-guard.ts:466,706+`), behind dashboard auth and the identity floor (`identity/identity-floor.ts:19-43`, enforced `server.ts:2032-2037`), the device-bearer tier gate (`route-tiers.ts:443-449` exact map, default `operate`), global CORS (`server.ts:1924-1940`, path-blind callback) and the mutation origin gate (`cors-origin.ts:196-228`, path-blind).

Decision — `ctx.registerPublicRoute` mounts `GET`/`POST` under `/api/plugins/<id>/public/`:
- **Authority comes from the operator, not the plugin**: served only when `plugins.<id>.publicRoutes.enabled` AND the plugin is enabled and loaded (runtime disable ⇒ `404` live — unlike plugin REST routes, which stay until restart, `routes/plugin-activation-routes.ts:136-138,272`); manifest priority grants nothing (`principal-resolution`: self-declared priority SHALL NOT grant registration).
- **One predicate, one early hook**: `isEnabledPublicNamespace(raw, resolved)` — BOTH views under the same namespace (guard exception semantics, `localhost-guard.ts:552-567,767`; `public/../config` gets nothing; unparseable `//` fails) over a config snapshot refreshed on change (≤2 s; no per-request `loadConfig()`, `shared/src/config.ts:2123-2128`). The namespace hook runs right after the host gate (`server.ts:1905`; host gate still applies — operator must allow the customer-facing Host) and before CORS (`server.ts:1928-1947`), the mutation gate (`:1951`), the cookie parser (`:1967`) and every auth hook. Disabled namespace ⇒ `404` there (no guard events/prompts/CORS).
- **Strip before parse**: whole `Cookie` header, `X-Pi-Local-Token`, `X-Pi-Local-Proof`; reset the local-credential verdict stamped at `server.ts:1717-1719` (`auth/local-credential.ts:95-98`); set `request.publicNamespace` so the OAuth gate (`auth-plugin.ts:466`), device branch (`bearer-auth.ts:83-91`) and break-glass branch (`identity/resolver-hook.ts:68-82`, `pi_op_`) skip it. Query keys that look like credentials ⇒ `400`; namespace logs record pathname only (`mutation-origin-gate.ts:50` logs `req.url`).
- **Principal resolution unchanged**: resolver accept ⇒ principal; resolver claim+reject ⇒ `401` (existing `kind === "reject"`, `resolver-hook.ts:103-107`); unclaimed ⇒ `null` to the handler; inert ⇒ ignored. Plugin credentials in a non-`Authorization` header.
- **Exemptions via the predicate**: network guard (new in-namespace exception, dual view), identity floor (`identity-floor.ts`), tier gate (skip before the exact `routeTier` lookup — no new tier), OAuth gate.
- **CORS answered by the namespace hook**, ahead of the path-blind global `@fastify/cors` callback: exact canonicalized `allowedOrigins` (https, or http for loopback names), no `Access-Control-Allow-Credentials`, `Vary: Origin`, preflight with route method/`allowHeaders`/`Max-Age: 600`; mutation gate uses `isPluginPublicOriginAdmitted` (exact, NO empty-list fallback — unlike `isPluginWsOriginAdmitted`, `cors-origin.ts:290-298`). `server-cors` MODIFIED twice (origin decision + credentials).
- **No ambient authority**: no cookies, no local credential, no device/break-glass ⇒ CSRF has nothing to ride; origin pinning is browser hygiene, the handler authenticates.
- **Host access policy**: classified `plugin:<id>:public`; with a principal the policy decides; anonymous traffic is the plugin's alone.
- **Bounds**: `maxConcurrent` (512) non-stream, 30 s non-stream duration (`408` + abort signal), `maxStreams` (256) and `maxStreamsPerPeer` (8); disable aborts in-flight requests and closes streams.
- **Streaming**: `openEventStream(request, reply)` helper → counted, heartbeats ≤4 s, `connectionTimeout` (`server.ts:1702-1703`) cleared, `onClose` exactly once on disconnect/close/disable; consumed via `fetch` (headers), not `EventSource`. GET-only: the widget posts a message (`POST`) and keeps one long-lived per-conversation stream (`GET`).
- **Path safety**: raw registration string validated (`%` rejected); plugin id `[a-z0-9-]`; `HEAD` ⇒ `405`.
- Alternatives rejected by the user: global `auth.bypassUrls` + global allowed origin (widens operator routes); separate change (c).

## Risks / Trade-offs

- **pi drift** (agent-dir semantics, `--no-skills`/`-e` resource rules) → L2 live test spawns real pi isolated in a cwd containing canary `AGENTS.md`, `.agents/skills`, `.pi/` package, with operator canaries in a fake operator agent dir and a canary `*_API_KEY`, and asserts none reach prompt, tools or env.
- **Bridge reader audit misses one** → enumerating test + D7 gate at registration sites.
- **Env allowlist too tight** for some platform (e.g. proxies `HTTPS_PROXY` for provider calls) → allowlist is a single constant; proxy vars added if the L2/Electron run shows the need. Recorded trade-off.
- **Subagents** spawned from an isolated session would inherit env but not the `-e` bridge; unreachable because built-in tools are off and the bridge registers no tools — only a plugin extension tool could spawn one. Documented in the plugin guide.
- **Plugins are mutually trusted**: a trusted plugin could point `agentDir` at another plugin's dir; out of the operator-vs-external threat model, documented.
- **MCP**: not forced off; MCP servers come from the plugin-owned agent dir's settings. Provisioning guidance: never copy operator `settings.json`/`mcp.json` into it.
- **`host-cwd-policy` "No shipping path injects extensions"** governs host *policy*; the bridge `-e` is host-owned plumbing, not a policy field — no conflict.
- **HOME-file credential chains** (`~/.aws`, gcloud, keychain) remain readable by plugin extension code; the model cannot reach them without a tool. Documented non-guarantee.
- **Electron overlay update**: the bridge dir is re-resolved per spawn from the settings registration, so isolated spawns follow an overlay switch; one L2 line checks registration after a switch.
- **Public namespace is an unauthenticated surface**: every handler must authenticate itself. Mitigations: operator opt-in per plugin, cookie + local-token stripping, device branch skipped, body limit, stream cap, exact origin pinning; rate limiting and side-effect-free `GET` handlers are the plugin's duty (plugin guide). A handler bug is a plugin vulnerability but runs in the dashboard process.
- **Deployment constraints (documented)**: per-peer stream cap keys on the socket peer, so behind zrok/docker set `maxStreamsPerPeer: 0` and rely on the plugin's per-customer limits; widgets in `Origin: null` contexts (sandboxed iframes, `file://`, some WebViews) cannot `POST`; the operator's own dashboard origin is not admitted on a namespace unless listed.
- **Explicit bypass category**: `auth-bypass-url-list` and `bearer-device-auth` "Bearer auth branch for REST" MODIFIED so the namespace's auth skip is reviewable, not implicit.
- **LAN customer sites must use https** (plain `http` origins allowed only for loopback names). Documented deployment constraint.
- **Enumeration oracle**: `404` (disabled) vs `401/403/2xx` (enabled) reveals whether a plugin's namespace is on. Accepted: the widget script URL is public by design.
- **Team-agent sessions** (`team-agent-sessions`) still load operator packages/env; they are not isolated spawns and are out of scope.

## Migration Plan

Additive. No persisted state; spawns without `agentDir` are byte-identical except that an inherited `PI_DASHBOARD_ISOLATED` is now removed and a malformed `scope` container is now refused (D6). Rollback = revert; plugins feature-detect `hasHostPolicy` and `isolated`.
