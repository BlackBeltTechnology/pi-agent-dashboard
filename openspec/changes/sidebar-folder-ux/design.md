## Decisions (confirmed or changed by the owner, 2026-11-20 — see /tmp/issue-batch/sidebar-folder-ux-DECISIONS.md)

### D1 — How "remove" hides the folder (confirmed (owner, 2026-11-20))
- A: client sends `remove_folder_from_workspace` (if in workspace) then `unpin_directory` (if pinned); #1086 hides ended-only folders. **Chosen.** Reuses the existing messages and their mirror-revoke paths. The `ShutdownBrowserMessage` verb (D2) is likewise already registered, so no new protocol/tier/scope/denylist entries are needed.
- B: new atomic `remove_folder_from_sidebar` server verb (`revokeMany`). Rejected: 4 registries (`ws-message-tiers`, `ws-road-classification`, `ws-message-scope`, MCP denylist) + bus verbs for a ~1 frame flicker saving.
- C: per-cwd "dismissed" preference cleared on new session. Rejected: new persisted state; #1086 made it unnecessary.

Known consequences of A (accepted, no mitigation added):
- **Not atomic.** Two independent messages: `handleRemoveFolderFromWorkspace` can fail (mirror-revoke error → `reportMirrorError`, nothing removed, `directory-handler.ts:380-391`) while `unpin_directory` (sent last) still succeeds, leaving the folder in the workspace but unpinned; it stays visible and the user can retry. The client has no ack to detect this, so no client test covers it.
- **Trust revocation.** Removing both sources revokes the dashboard-granted pi trust entry for the folder (`pi-trust-mirror-service.ts` `revoke`/`revokeMany`), so the next session started there may prompt for trust again. Existing behaviour of those messages; not surfaced in the confirm copy.

### D2 — Live sessions: confirm, end them, then remove (CHANGED by owner, 2026-11-20)
Supersedes the earlier "disabled with a reason" draft. **Remove from sidebar** is always enabled for a pinned / workspace folder. When the folder has live sessions (status ≠ `ended`) it opens a confirm dialog listing them; on confirm the client ends each via the existing **`shutdown`** browser message, then sends the D1 removal messages.

- **Which end path (verified).** `shutdown` is the single "end session" verb: client `handleShutdownSession` (`packages/client/src/hooks/useSessionActions.ts:272-284`, optimistically sets `closing`, sends `{ type: "shutdown", sessionId }`), surfaced to `SessionList` as the existing `onShutdown` prop (`SessionList.tsx:175,2155`; wired at `App.tsx:2269`). Server: `handleShutdown` → `shutdownSession` (`packages/server/src/browser-handlers/session-action-handler.ts:1029-1049`): polite `shutdown` to pi, then the shared terminator ladder (`SHUTDOWN_GRACE_MS` 1.5 s → SIGTERM → SIGKILL), `closedReason: "manual"`. Message type: `ShutdownBrowserMessage` (`packages/shared/src/browser-protocol.ts:1621-1624`). `force_kill` (`useSessionActions.ts:110`) is the abort-escalation path and is NOT used. `CloseWorktreeDialog` already does the same "end sessions, then act" composition (`CloseWorktreeDialog.tsx:84-96`) — precedent for the pattern.
- **Live set.** `group.sessions` is post-`filterSessions` (`SessionList.tsx:973`, hidden headless/automation sessions excluded), so using it would leave hidden live sessions running invisibly after the folder is removed. The confirm dialog therefore lists, and the confirm handler shuts down, every session **in that folder's group** (same grouping key as the card — NOT a raw `cwd` compare: a card's membership is `pathKey(resolveSessionGroupPath(s, pinnedKeys, plat))` = pin > `gitWorktree.mainPath` > `cwd`, `packages/shared/src/session-group-path.ts:58-68`, `session-grouping.ts:97-135`, so unpinned `.worktrees/<slug>` sessions render in the parent repo's card with a different `cwd`, and path drift is collapsed by `pathKey`) with status ≠ `ended` taken from the **unfiltered** `sessions` prop, **evaluated at confirm time** (a session that went live while the dialog was open is included). The "needs confirmation" decision uses the same unfiltered set. Implementation reuses the grouping key derivation (`inferPlatform` + `pinnedKeys` from `pinnedDirectories` + `resolveSessionGroupPath` + `pathKey`) via a small helper exported next to `groupSessionsByDirectory` rather than re-implementing it, and compares against `pathKey(group.cwd)`.
- **Dialog host and focus return.** Dialog state is held in `SessionList` (like `manageWorktreesCwd`, `SessionList.tsx:517,3383`), keyed by cwd, so it survives the menu closing (`FolderActionsMenu.tsx:319-322` calls `onOpenChange(false)` before `onSelect`, unmounting the focused item) and the folder leaving the list. Because `useFocusTrap` restores focus only to a still-mounted element (`useFocusTrap.ts:131-133`) and the opener is gone, the dialog's `onClose` explicitly focuses the folder's menu trigger (`[data-testid="folder-actions-menu-<cwd>"]`) when it is still in the document.
- **Order.** In one handler: `onShutdown(id)` for every live session, then `remove_folder_from_workspace` / `unpin_directory`. Shutdown is asynchronous; the folder leaves the sidebar once the sessions are `ended`/removed, by the existing #1086 rule (`SessionList.tsx:1474`: visible while any session ≠ `ended`). No client-side wait or polling — the intervening frames show the cards in their existing `closing` state. Edge: a currently *selected* session keeps its folder visible (`SessionList.tsx:1474` selected-session clause) until deselected — existing behaviour, left as is.
- **Dialog.** Built on the existing `Confirm` preset (`packages/client-utils/src/Confirm.tsx`, `intent="danger"`, `body` = list of live sessions with names, capped + scrollable like `CloseWorktreeDialog`'s `max-h-32` list). Inherits `role="dialog"`, `aria-modal`, `aria-labelledby`, focus trap, Esc dismissal, restore-focus (`Dialog.tsx`, `useFocusTrap.ts`). **Default focus must be Cancel** (destructive): today the trap focuses the first focusable element (`useFocusTrap.ts:65-67`), which is the built-in ✕, not Cancel. Add a small additive hook: `Dialog.Cancel` accepts `autoFocus` → renders `data-autofocus`, and `useFocusTrap` focuses the first `[data-autofocus]` focusable descendant before falling back to the first focusable; `Confirm` gets `defaultFocus?: "cancel"`. Default behaviour of every existing dialog is unchanged. Two small ADDED requirements record this (`dialog-primitive`, `confirm-dialog`).
- **Folders with no live sessions** skip the dialog (nothing destructive) and remove immediately as in D1.
- **Rollback.** Client-only; revert the commit. Ended sessions are untouched (stay in history/archive). Ending a session is irreversible only in the sense of a running process stopping — the reopen/resume path still works for the ended session.

### D3 — Compact-card chips hidden in Focus mode (CHANGED by owner, 2026-11-20)
Supersedes the earlier "exclude `init-needed` only" draft. **While Focus mode is on, the compact folder-banner chip is hidden for every rung** (`init-needed`, `setup`, `retrust`, `failed`, `running`) so a Focus folder card is just the slim header. **Outside Focus mode nothing changes** (compact chips still render for all rungs, including `init-needed`).
- Focus state: `useFocusState().enabled` (`packages/client/src/lib/state/CardSectionsContext.tsx:143-157`, `prefs.focus?.enabled === true`).
- Gate where the chip renders: `FolderActionBanner` `compact` branch (`FolderActionBanner.tsx:143-157`) — the chip is suppressed (return `null`) when `compact && focusMode`, at both call sites (`SessionList.tsx:2398` accordion compact; `SessionList.tsx:2440-2451` `compact={!showFolderBanner}`). Cleanest: `SessionList` passes a boolean prop (e.g. `suppressChip={focusEnabled}`) read from `useFocusState`, keeping `FolderActionBanner` pure/prop-driven. The expanded (`compact={false}`) banner is unaffected.
- Safety trade-off (owner decision, accepted): in Focus a blocked folder (re-trust / failed) no longer shows a cue on the card. Mitigation: the full banner with `folder-banner` visible (Focus off, or the profile toggled on) still exposes every rung; the same applies to init progress/failure feedback (`worktree-init-feedback`, recorded as an exception delta); Focus is an explicit opt-in to a minimal sidebar. The archived "Safety cues survive" wording for the chip is therefore narrowed to *outside Focus* via MODIFIED deltas on `focus-mode` (scenario replaced; the PROCESS chip still survives), `session-card-section-visibility` and `worktree-init-feedback`; the existing chip tests (`SessionList.card-blocks.test.tsx:178`, `SessionList.accordion.test.tsx:238`) run with Focus off and stay valid; task 2.1 retitles the former to say "outside Focus" and adds the Focus-on cases.

Grouping stays reachable from the folder actions menu.
