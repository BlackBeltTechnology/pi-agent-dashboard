## Why

Operators who run the chat gateway in several Discord servers (change A, `chat-gateway-multi-guild`) still have to leave the dashboard to moderate those servers. They create, rename or delete a channel, hand out or take back a role, or kick, ban or time out a member in the Discord client. A pi agent cannot do any of this either, even when the operator would approve each step. This change adds a narrow, opt-in moderation surface. Per-server gateway admins reach it with a chat command, and pi agents reach it with a tool. Every action is confirmed by a human and recorded.

Stack: A `chat-gateway-multi-guild` → B `chat-gateway-query-mode` → C `chat-gateway-agent-tools` → **D (this change)**. D consumes A's per-server record, `isGuildAdmin`, `team.authorizeServerRequest` (plus a non-logging `evaluateServerRequest` sibling D adds) and per-server disarm. It reuses B's chat-command parser (`src/server/query/commands.ts`) and C's `discord_*` tool registration, request lane, `ctx.ui.confirm` plumbing, shared confirm marker and L3 guard deny rule. D does not redefine any of them.

## What Changes

- **Per-server `guilds.<id>.moderation`** (the key A reserves): `enabled` (default `false`), `actions` (allowlist, default `[]`), `assignableRoles` (role ids the bot may hand out, default none), `allowAgents` (default `false`), `allowInQuery` (default `false`), `confirmTtlSeconds` (default 120), `maxPending` (default 10, chat confirmations), `maxAgentPending` (default 5, live agent previews), `rateLimit.perHour` (default 20, chat), `rateLimit.agentPerHour` (default 10), `rateLimit.agentPreviewPerHour` (default 30) and `rateLimit.perActorPerHour` (default 10). Every limit follows A's rule: **`0` = unlimited**. A preserves this reserved key verbatim, so a rollback to A keeps servers loadable. Moderation is configured only from the dashboard.
- **Ten actions**: `channel_create`, `channel_rename`, `channel_delete`, `role_create`, `role_assign`, `role_remove`, `member_kick`, `member_ban`, `member_unban`, `member_timeout` (set or clear). Channel actions touch plain text channels only. A required reason string goes to Discord's audit log.
- **Chat**: whole-message `!mod <noun> <verb> …  -- <reason>` is an admin command added to B's parser. It needs per-server gateway admin AND an explicit user-id mapping at the server-scoped tier `operate` (a role mapping can never grant it, because roles cap at `control`), and an armed server. It works in `interactive` servers, and in a `query` server only when that server also sets `moderation.allowInQuery`; otherwise it gets `Refused: query_mode.`, so query stays strictly request-only by default (decision 5) and the exception is explicit and visible.
- **Agent**: one bridge tool, `discord_moderate`, registered through C's bridge entry. Its flow is two-phase over C's lane: `discord/moderate-preview` → `ctx.ui.confirm` showing names the server resolved → `discord/moderate`. With no UI the tool is blocked before anything reaches Discord.
- **Every action is confirmed.** In chat, the native Yes/No buttons come from the existing confirm renderer. A click re-runs the whole gate (mode gate included) and must come from the invoker, a `!mod` without a team controller is refused `team_controls_required`, the confirmation is consumed before anything runs, and it expires after a configurable time. For agents, `ctx.ui.confirm` asks, the server re-validates everything on commit, and the session-bound `previewId` (in C's pending-confirmation registry) is one-shot. The tool result carries no Discord names and collapses every target refusal to `target_not_permitted`, so the tool is not a read oracle. Previews are metered (`agentPreviewPerHour`) before any Discord lookup, and the hourly limits are charged only when a Yes is accepted. An agent's moderation confirm is **never** rendered into a chat channel: it carries C's shared marker `AGENT_TOOL_CONFIRM_META` (D defines no marker of its own), and a title prefix is a second signal if the marker is lost. A session bound to a server can moderate only that server.
- **Protected targets.** Moderation never acts on the server owner, the bot itself, or a member or role at or above the bot's highest role. Chat requests are also refused for targets at or above the requester's highest role. Role assignment is limited to an operator allowlist (`assignableRoles`). Roles mapped to a gateway tier, roles that grant moderation permissions, managed roles and gateway-managed channels are refused too. Each case gets a specific reason.
- **Discord permissions are checked per action before confirming**, which gives a graceful refusal (`missing_permission`). A refusal from Discord itself is reported as `platform_refused`, with the platform code.
- **Gateway-spawned sessions cannot moderate.** The tool is denied by the L3 guard regardless of `toolPolicy.allow` (C's rule), and the server refuses `discord/moderate-preview` and `discord/moderate` from them as defence in depth.
- **Audit.** A refusal, a cancel, an expiry (chat or agent preview) and an authorization each write one command-log entry (with the required `channelId`; agent-preview refusals share one entry per server and reason per hour; the gate uses a non-logging `team.evaluateServerRequest`, and the durable append is transactional); the `permitted` entry is written durably after the human's Yes and before Discord is called, and the action is refused (`audit_unavailable`) when it cannot be written. Entries gain the optional fields `phase` and `detail`. Retention is C's `teamControls.auditRetention` (`0` = unlimited); D adds no retention key and no `limits.*` key.
- **Settings UI.** Each enabled server row gets a Moderation section with a toggle, an action checklist, assignable roles, the agent toggle, TTL, max pending and rate limits (hint "0 = unlimited"), and per-action missing-permission problems.

## Capabilities

### New Capabilities
- `chat-gateway-moderation`: per-server moderation settings, the action set, the `!mod` chat command, the agent tool, confirmation, protected targets and hierarchy, permission checks, rate limits, spawned-session denial, and moderation audit.

### Modified Capabilities
- `chat-gateway`: "Interactive prompts rendered natively via PromptBus" and "Hard in-session tool policy for spawned sessions" (C's current text verbatim, stack order A → B → C → D; D adds the title-prefix backstop, two scenarios, and `discord_moderate` in the hard-deny sentence), "Reach dashboard sessions from chat" (B's text plus `!mod`) and "Configuration surface" (C's text plus the moderation section). `add-supervised-tool-approval` also modifies the PromptBus requirement; that is reconciled at archive time.
- `chat-gateway-guilds`: "Query-mode servers refuse interactive actions" (B's text; `!mod` is answered only in a `query` server that sets `moderation.allowInQuery`, else refused with `query_mode`; the confirmation click of a pending moderation request is the one prompt answer a `query` server accepts). `chat-gateway-query-mode` is not modified: B's generic wording covers `!mod`.
- `chat-gateway-audit`: "Append-only command log" (C's text, which carries A's; plus the per-outcome moderation entries).
- `chat-gateway-tier-authorization`: "Tier resolution from chat identity", "Verb tiers come from the dashboard's shared effective-tier table" and "Configuration is editable only from the dashboard". All three blocks copy B's text verbatim and add the ten `mod_*` verbs (server-scoped, at `operate`) and "moderation settings" to the dashboard-only list.

## Discipline Skills

- `security-hardening`: privileged, irreversible actions are driven from untrusted chat text and model output. They need authorization, invoker-only confirmation, hierarchy checks, refusal of roles that would escalate privileges, and mentions disabled.
- `doubt-driven-review`: bans, kicks and channel deletes cannot be undone from the gateway. The confirm, re-validate and commit sequence has to be reviewed before it lands.
- `observability-instrumentation`: new request-lane endpoints (`discord/moderate-preview`, `discord/moderate`, `discord/moderate-cancel`), per-server outcome counters and audit phases.

## Impact

- **Code** (`packages/chat-gateway/`): `src/configSchema.json` (record `moderation`); new `src/server/moderation/` (parser, policy, pending store, rate limiter, request-lane handlers); `src/server/team/tier.ts` (`mod_*` verbs at `operate`); `src/server/team/audit.ts` (optional `phase` and `detail`; calls C's `appendDurable`, adds none); `src/adapters/base.ts` and `discord.ts` (optional `moderationFacts`/`moderate`, mentions-none confirm, `gatewayEdits`); `src/adapters/discord-payload.ts` (pure `moderationRefusal`); `src/server/gateway.ts` (`!mod` in B's pre-prompt match, pending-mod lookup ahead of `prompts`; the agent-confirm skip is C's, plus the title-prefix second signal); C's bridge entry (`discord_moderate`); C's `GATEWAY_HARD_DENY`; `src/shared/types.ts` (lane type constants); `src/client/ChatGatewaySettings.tsx`.
- **Discord**: the bot role needs Manage Channels, Manage Roles, Kick Members, Ban Members and Moderate Members, but only for the actions an operator allows. No new gateway intent is needed.
- **Docs**: `docs/chat-gateway.md` (via DocScribe), plus `packages/chat-gateway` `AGENTS.md` rows.
- **Compatibility**: everything is off by default. An older plugin ignores `moderation` and old command-log readers ignore `phase` and `detail`.
