## Goals / Non-Goals

**Goals.** Moderation is opt-in for each server and each action. Every action is human-confirmed, re-validated at commit and durably audited before it runs. Moderation fails closed on permissions, hierarchy, channel type and role assignment. It never acts on the owner, the bot or anyone who outranks it. Gateway-spawned sessions cannot use it, and a gateway-bound session can moderate only its own server. No limit is hardcoded: every limit is a setting and `0` = unlimited (A's single rule).

**Non-goals.** Bulk actions (one target per request). Message deletion or purges (ban never deletes messages; `deleteMessageSeconds` is not exposed). Editing role permissions, and setting permission overwrites on created channels. Slash commands. Moderation over DMs. Multiple bot tokens. Adopting `add-plugin-connector-kit` (possible later, not a dependency).

**Moderation is an explicit exception to "query = request-only" (decision 5 vs 12).** A `query` server never spawns, prompts, mirrors or provisions. It also never writes to Discord *by default*, and moderation is off by default in every server. An operator who turns `moderation.enabled` on for a `query` server opts that server in to the write actions in the allowlist `actions`. The exception is per server, per action and **explicitly opted in** (settled, T1): a `query` server refuses `!mod` and agent moderation with `Refused: query_mode.` unless the separate setting `moderation.allowInQuery` is `true` (default `false`) in addition to `moderation.enabled` and the action allowlist. Query stays strictly read-only by default (decision 5); the exception is explicit and visible in the settings, and it needs the dashboard.

## Decisions

### D1. Config shape (`guilds.<id>.moderation`)

This is A's reserved key (verified: A design.md:74/:92/:222, spec `chat-gateway-guilds` "Reserved record keys are preserved"). It is optional and fails closed: an absent key means off. The key shape is A's: a plain object at `guilds.<id>.moderation`. D's fragment below replaces A's placeholder `{"type":"object"}` in `configSchema.json` (D adds `additionalProperties:false` inside it). A's validator stays a plain-object check and never reads the inside, so a rollback to A keeps the object verbatim and the server loadable. A also clones the value with `structuredClone`, rejects `__proto__`/`constructor`/`prototype` keys at any depth, and bounds its size by `limits.maxReservedBytes` (262144, `0` = unlimited); D's fragment is validated on top of that cloned value and never weakens those checks. D's own validator runs from A's write lane and is D's task 1.3. D adds **no** `limits.*` key and never writes `limits`: A's `patchLimits` is the only `limits` writer, and every D number lives inside `moderation`. `moderation.allowAgents` is a per-server boolean (named apart from C's top-level `agentTools` object on purpose: a request needs both).

```json
"moderation": {
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "enabled":           { "type": "boolean", "default": false },
    "actions": {
      "type": "array", "uniqueItems": true, "default": [],
      "items": { "enum": ["channel_create","channel_rename","channel_delete",
                          "role_create","role_assign","role_remove",
                          "member_kick","member_ban","member_unban","member_timeout"] }
    },
    "assignableRoles":   { "type": "array", "items": { "type": "string", "pattern": "^[0-9]+$" }, "default": [],
                           "description": "Role ids role_assign/role_remove may touch. Absent or empty = none. Counts toward limits.maxMappings." },
    "allowAgents":       { "type": "boolean", "default": false,
                           "description": "Allow pi agents (discord_moderate) in this server. Also needs C's top-level agentTools.enabled." },
    "allowInQuery":      { "type": "boolean", "default": false,
                           "description": "Allow moderation (chat and agent) in a server whose mode is query. Default false: query stays read-only." },
    "confirmTtlSeconds": { "type": "integer", "minimum": 0, "default": 120,
                           "description": "Chat confirm expiry and agent token TTL. 0 = unlimited (no expiry)." },
    "maxPending":        { "type": "integer", "minimum": 0, "default": 10,
                           "description": "Unanswered chat confirmations per server. 0 = unlimited." },
    "maxAgentPending":   { "type": "integer", "minimum": 0, "default": 5,
                           "description": "Live agent previews per server (a preview holds its slot until commit, cancel, expiry or session end). Separate from maxPending so an agent cannot starve human admins. 0 = unlimited." },
    "rateLimit": {
      "type": "object", "additionalProperties": false,
      "properties": {
        "perHour":         { "type": "integer", "minimum": 0, "default": 20, "description": "Chat requests per server per rolling hour. 0 = unlimited" },
        "agentPerHour":    { "type": "integer", "minimum": 0, "default": 10, "description": "Agent commits per server per rolling hour. 0 = unlimited" },
        "agentPreviewPerHour": { "type": "integer", "minimum": 0, "default": 30, "description": "Agent previews per server per rolling hour that reach Discord lookups. 0 = unlimited" },
        "perActorPerHour": { "type": "integer", "minimum": 0, "default": 10, "description": "Per principal (user id or agent session). 0 = unlimited" }
      }
    }
  }
}
```

- **Unlimited.** A's single rule applies to every number here (`confirmTtlSeconds`, `maxPending`, `maxAgentPending`, `rateLimit.*`): `0` = unlimited. An absent value takes the documented default. A negative or non-integer value is rejected on the write lane (`invalid_moderation_setting`) and replaced by the default on the boot read. No limit is a constant in code. There is no per-session limit on live previews: they count toward `maxAgentPending` and are never silently replaced.
- **Boot read (total, never throws, in-memory only).** The raw object is normalized field by field and never rewritten to disk. `enabled`/`allowAgents`/`allowInQuery` that are not booleans become `false`. `actions` that is not an array becomes `[]`, and an entry that is not one of the ten names is dropped. `assignableRoles` that is not an array becomes `[]`; a non-snowflake entry is dropped. A limit that is negative, non-integer or not a number takes its default. A non-object `rateLimit` takes all four defaults. An unknown inner key is ignored. Every repair adds a `moderation_setting_repaired:<key>` entry to `GuildView.problems[]`, so the effective behaviour is visible next to the stored value. The write lane is stricter: any of these is rejected (below), and a successful write stores the validated shape.
- **Platform facts that are not settings**: the 2000-character message limit, the 512-character audit-log reason limit and the 28-day maximum timeout. Inputs beyond them are refused (`reason_too_long`, `timeout_too_long`). They are never silently truncated. Their units are fixed: the 512 limit counts UTF-16 code units (JS `.length`, the conservative choice: nothing over 512 units is ever sent), and Discord's 100-character name limit is counted the same way.
- **Timer clamp (A's shared rule).** `confirmTtlSeconds` above 2147483 s (Node's timer maximum, 2147483647 ms) is clamped to 2147483647 ms when the timer is armed; the stored value is kept and the dashboard hint says so. `0` arms no timer.
- **Validation** runs on A's live write lane (`chat_gateway_guilds_config`): `invalid_moderation_action` (unknown or duplicate action), `invalid_moderation_setting` (wrong type, negative or non-integer limit, unknown inner key, non-snowflake role id; `detail` names the key). The write carries A's required `expectedRevision` (`revision_required` when absent, `revision_changed` when stale), and A's merge replaces a top-level key as a whole, so the dashboard sends the complete `moderation` object each time. A's transient `clear` applies only to A's optional keys (`allowlist`, `ceiling`, `label`); the reserved `moderation` key is never cleared by it (`invalid_clear`), so "off" is an object (`enabled: false`), never a removal. `enabled: true` with an empty `actions` list is accepted; every request is then refused with `moderation_action_not_allowed`.
- **Dashboard only.** No chat verb writes `moderation`. B's `!config show` may display it, but the projection is B's.

### D2. Actions, Discord permissions, failure modes

| action | chat form | Discord call (discord.js) | bot needs | hierarchy / guard |
|---|---|---|---|---|
| `channel_create` | `!mod channel create <name> [in <categoryId>]` | `guild.channels.create({name,type:GuildText,parent,reason})` | Manage Channels | name via `channelNameFor`; no overwrites (inherits the category) |
| `channel_rename` | `!mod channel rename <#ch> <name>` | `channel.edit({name,reason})` | Manage Channels (in that channel) | `GuildText` only (D7); not gateway-managed |
| `channel_delete` | `!mod channel delete <#ch>` | `channel.delete(reason)` | Manage Channels (in that channel) | `GuildText` only; not rules/updates/system/AFK; not gateway-managed |
| `role_create` | `!mod role create <name>` | `guild.roles.create({name,permissions:0n,mentionable:false,hoist:false,reason})` | Manage Roles | `permissions` explicitly `0` |
| `role_assign` / `role_remove` | `!mod role add\|remove <@user> <@&role>` | `member.roles.add/remove(role, reason)` | Manage Roles | role in `assignableRoles`; role below the bot (and the requester in chat); not managed or `@everyone`; not tier-mapped; grants no moderation permission; **target checks (D7) apply to the member** |
| `member_kick` | `!mod kick <@user>` | `member.kick(reason)` | Kick Members | target protections (D7) |
| `member_ban` | `!mod ban <@user\|id>` | `guild.bans.create(id,{reason})` | Ban Members | target protections by id; a non-member is resolved with `client.users.fetch(id)` (REST) so owner/bot/gateway-admin ids are still refused |
| `member_unban` | `!mod unban <id>` | `guild.bans.remove(id, reason)` | Ban Members | `not_banned` if the id is absent from the ban list |
| `member_timeout` | `!mod timeout <@user> <N>(s\|m\|h\|d)` or `… off` | `member.timeout(ms\|null, reason)` | Moderate Members | target protections; also `target_is_administrator` |

- **Reason is required** on every action (`moderation_reason_required`). It is sent to Discord as `[pi-gateway chat:<userId>] <reason>` for chat and `[pi-gateway agent] <reason>` for agents. The agent's internal principal (`session:<id>`) stays in the command log and is never sent to Discord, where anyone with View Audit Log would read it. The reason is trimmed first: an empty result (including whitespace-only input) is `moderation_reason_required`, and the trimmed text is what is stored and sent. When the prefix plus the trimmed reason is longer than 512 UTF-16 code units (JS `.length`), the request is refused with `reason_too_long`.
- **Names (platform facts).** A `channel_create` or `role_create` name that is empty after normalisation (`channelNameFor` for a channel, trimming for a role) or longer than 100 characters (UTF-16 units) is refused `moderation_bad_syntax` (no extra reason; for a channel, `!!!` or emoji-only normalises to empty).
- **`channel_create … in <parentId>`.** The parent must be a category of THIS server: a parent of another type is `unsupported_channel_type`, an unknown id or one of another server is `target_not_found`, and a gateway-provisioned category is allowed.
- **Duration.** `N` is a positive integer with a unit `s|m|h|d`. The result must be at least one second, otherwise `invalid_duration` (this covers `0s`, an empty value and an unparsable one). `off` clears the timeout. More than 28 days is `timeout_too_long`. On the agent tool, `member_timeout` needs exactly one of `clear: true` or `durationSeconds ≥ 1`; both or neither is `bad_request`.
- **Permission pre-check.** At preview and again at commit, `moderationFacts` force-fetches the bot member (`guild.members.fetchMe({force:true})`) so a stale cache cannot pass (whether self-update events arrive without the GuildMembers intent is `unverified`). Guild-level actions read `me.permissions`; channel actions use `channel.permissionsFor(me)`, which includes channel overwrites. It also reads the getters (`kickable`, `bannable`, `moderatable`, `manageable`). A missing permission gets `missing_permission`, with `detail` naming it. The permission token is the discord.js `PermissionFlagsBits` key (for example `BanMembers`), and the chat reply is `Refused: missing_permission (BanMembers).`; the same string is the audit `detail` and the dashboard advisory's name.
- **Platform refusal.** If Discord rejects the call (for example `50013 Missing Permissions` after a role change between confirm and commit), the request gets `platform_refused` with `detail = <numeric API code>`, and the chat reply is `Refused: platform_refused (50013).`. Any other failure (an HTTP 5xx, a `RateLimitError`, `ECONNRESET`, `ETIMEDOUT`, a client that is not ready) is `discord_unavailable` with `detail` = the HTTP status when the error carries one, else the error's class name. A configured, enabled server that is absent from the Discord client (the bot was removed, or the cache is not built) is `discord_unavailable` too (chat Yes, agent preview and `moderationFacts`). Nothing is retried automatically. discord.js's own 429 queueing is left as is. **No deadline** is set for chat lookups or `adapter.moderate`: a stalled lookup holds its `maxPending` slot until it settles, and other servers are not blocked.
- **Member resolution** fetches a single member (`guild.members.fetch(userId)`). This is a REST read, so no `GuildMembers` intent is needed. *Unverified against a live server*; the existing bulk fetch at `discord.ts:442` is a different call. For chat, the requester's member is fetched the same way, to obtain the requester's highest role position.
- **Authority is the gateway's, not Discord's.** A requester needs per-server gateway admin + an explicit `operate` mapping (D3). They do **not** need to hold the Discord permission themselves (for example Ban Members). Only the bot's own permissions and role position, and the chat requester's role position (D7), bound what can happen. Settled (T3, consistent with decision 23): this is deliberate, and spec scenario "Requester's own Discord permissions are not required" states it. An optional `moderation.requireDiscordPermission` (default `false`) is deferred and not part of this change.
- **Per-server write gate (A).** A gates every adapter write path by guild with `guild_not_enabled` (`sendableChannel`, `startThread`, `archiveThread`, the `channelOps` create/overwrite/role operations; verified `adapters/discord.ts:319-404`, `:484`, `:709`). D's `moderate(op, reason)` and its `DiscordModerationOps` calls (channel create/rename/delete, role create/assign/remove, kick, ban, unban, timeout) route through that **same** per-guild gate, and D's `moderation.enabled` is required on top of it, never instead of it. An op for a guild that is not enabled is refused `guild_not_enabled` before any Discord call, even if a caller skipped the earlier gate steps.

### D3. Chat command (`!mod`) and authorization

- **Syntax.** Whole message: `!mod <form> -- <reason>`. Targets may be `<@id>`, `<@!id>`, `<#id>`, `<@&id>` or a bare snowflake. Anything else gets `moderation_bad_syntax` and a one-line usage reply: the fixed text `Usage: !mod <kick|ban|unban|timeout|role|channel> … -- <reason>` (the forms of the D2 table follow in `docs/chat-gateway.md`). The parser is pure (`src/server/moderation/parse.ts`).
- **No server, no command.** A `!mod` message or a click that carries no `guildId` (a DM) is dropped silently and counted as `guild_not_enabled`. It writes no audit entry, consistent with A's drop rule. The same drop applies in the un-adopted legacy single-server configuration (no `guilds` record, legacy keys present): moderation needs an adopted per-server record, so a legacy admin's `!mod` gets no reply and no entry (fail closed; legacy admins never had a moderation grant, and no reply means no probe surface). Pending records and rate windows are keyed by guild.
- **Dispatch.** `!mod` is added to **B's chat-command parser** `src/server/query/commands.ts` (B task 4.2) as one more admin command, next to `!mode`, `!bind`, `!config show` and `!report`. D adds only the entry and a handler in `src/server/moderation/`; B's `src/server/query/admin.ts` is not edited. B's whole-message match in `gateway.ts` (task 4.3) runs **before** prompt routing in both modes, so a `!mod` never reaches a bound session as a prompt; D adds `!mod` to that matched set. A's drop rule runs first: messages from non-enabled servers and channels that have not opted in never reach D. Because B answers admin commands in both modes, `!mod` is matched in `interactive` and `query` servers. In a `query` server it is answered only when `moderation.allowInQuery` is `true` (settled, T1); otherwise A's mode gate answers `Refused: query_mode.` with one audit entry, exactly as for any other `!` command a query server does not answer. D therefore MODIFIES B's "Query-mode servers refuse interactive actions" (the opt-in sentence and scenarios) and B's "Reach dashboard sessions from chat" (see §Shared MODIFIED blocks). `!mod` is registered with B's layer as a command a later capability handles through it, so B's per-(guild, user) command rate limit (`command_rate_limited`, B's generic wording since its cycle 2; one aggregated entry per burst) counts it and applies before D's gate; D therefore needs no MODIFIED block on `chat-gateway-query-mode`. The refusal reply for non-admins is B's `not_admin`. Refusal replies pass through A's `limits.refusalRepliesPerMinute` throttle (default 6 per channel, `0` = unthrottled). Following A's rule for `query_mode` (owner decision, cycle 2), a chat refusal at the request phase is audited **only when its reply is posted**; a reply the throttle suppresses is counted in `refusal_throttled` and writes no entry, so a flood of refused `!mod` messages cannot evict evidence from the ring. This does not apply to the confirm-phase entries (`not_invoker`, cancel, expiry, failed re-validation, `permitted`, `result`), which are bounded by `maxPending` and one entry per request and clicker, nor to agent-path refusals, which have no reply and use the preview dedupe (D9).
- **Server-scoped tier inside a bound channel.** The ten `mod_*` verbs join `SERVER_SCOPED_VERBS` in `tier.ts` (A: `disarm`; B: `search_messages`, `ask_messages`, `server_config_show`, `server_report`, `server_mode`, `server_bind`). They always resolve through the server-scoped chokepoint (for moderation its non-logging `team.evaluateServerRequest`, step 2 below) against the server's own `principals`/`roles`, even when sent in a bound channel. A's text says server mappings never grant a tier *inside a binding* for binding verbs; the rule that makes both true is the server-scoped-verbs sentence of "Tier resolution from chat identity". D MODIFIES that requirement (B's current text plus the `mod_*` verbs, one scenario). B's session verbs (`!status`, `!show`, `!sessions`) stay binding-scoped and are not touched by D.
- **Gate order** (first failure wins; every refusal replies `Refused: <reason>.` and, when that reply is posted, writes one audit entry, phase `request`; a throttled reply is counted `refusal_throttled` instead):
  0. **Mode gate (A's, before D).** The server is `query` and `moderation.allowInQuery` is not `true` → `query_mode` (audited when the reply is posted, as A's rule says; a throttled reply is counted `refusal_throttled`). In an `interactive` server, or a `query` server that opted in, the gate continues.
  1. `isGuildAdmin(guildId, author)`, otherwise `not_admin` (A).
  2. **No team controller → `team_controls_required`.** The gateway's `team` is optional and the shipped pattern fails open when it is absent (`gateway.ts:63-66`, `:1024`). D's handler tests `team === undefined` explicitly and refuses before anything else is parsed; it never calls `team?.…`. Otherwise `team.evaluateServerRequest({author, guildId, channelId, verb: "mod_<action>"})` covers non-human authors, the per-server disarm (`disarmed`), the allowlist and `insufficient_tier`. **`evaluateServerRequest` is a non-logging sibling of A's `authorizeServerRequest`**: both call the same pure `authorize()` with the same server-scoped inputs (so the chokepoint stays single), but the wrapper's `log.append` (`controller.ts:197-200`) is skipped. It is required because the logging variant would write a `permitted mod_<action>` row for a request that is merely posted, or left unanswered, and again on every Yes re-run, and would double-log refusals that D writes itself (D9). D writes every moderation entry itself. The ten `mod_*` verbs are added to `CHAT_COMMAND_ALLOWLIST` and to `CHAT_LOCAL_VERB_TIERS` at **`operate`** (`tier.ts:46`, `:78`), next to B's `server_*` verbs. Like them they also require gateway-admin status (step 1). Roles cap at `control` (A: `guilds.<id>.roles` never holds `operate`, refused with `role_cannot_map_to_operate_requires_explicit_identifier`), so only an explicit user-id mapping `guilds.<id>.principals.<userId> = "operate"`, under an effective ceiling of at least `operate`, can moderate.
  3. `moderation.enabled`, otherwise `moderation_disabled`, checked BEFORE parsing (fail closed: a disabled server never gets usage text).
  4. Parse (D3 syntax, D2 duration and names): `moderation_bad_syntax`, `invalid_duration`, `timeout_too_long`, `moderation_reason_required`, `reason_too_long`. Then the action must be in `actions`, otherwise `moderation_action_not_allowed`.
  An unexpected exception anywhere in the gate or in a facts lookup (not a Discord error) is `moderation_internal_error`: the request is consumed, one `refused` entry is written, nothing is executed and no pending record leaks (an adapter or network error is `discord_unavailable`, D2).
  5. `maxPending` cap (`moderation_too_many_pending`, not charged).
  6. Rate-limit **check** (D8, non-charging), otherwise `moderation_rate_limited`.
  7. Facts and protections (D7), then the permission pre-check (D2).
  8. Post the confirmation (D4). **Nothing is charged here** (D8): the limits are charged only when the invoker's Yes is accepted.
- **Ceiling coupling (settled, T2: keep A's contract, decision 6).** The effective ceiling of a server is `min(guild ceiling, global teamControls.ceiling)` and defaults to `observe` (`authorize.ts:122-124`; A: a server record can only lower the global ceiling). Chat moderation therefore needs the **global** ceiling at `operate`. A binding with no ceiling of its own inherits the global one (`team-config.ts:180-185`: `minTier(b.ceiling ?? ceiling, ceiling)`), so raising it also lets principals mapped to `operate` inside workspace bindings in every server resolve to `operate`. The dashboard warns of this (D10) and the docs advise lowering each binding's ceiling per binding, which keeps workspace tiers low while the global ceiling is `operate`. A moderation-specific ceiling cannot avoid the coupling without changing A's chokepoint (the global ceiling caps all), and a chokepoint change would contradict decision 6; neither is done. Who actually gets moderation stays limited by the explicit user-id mapping (decision 23).
- **Settled (owner decision 23): chat moderation needs BOTH** per-server gateway admin AND an explicit user-id mapping at `operate` in that server. Neither alone is enough: an admin who only holds a role-derived tier fails step 2 (`insufficient_tier`); a user with `operate` who is not in `admins` fails step 1 (`not_admin`). Roles never grant moderation.
- Being a Discord owner or administrator grants nothing (A). Admin status or a mapping in one server confers nothing in another.

### D4. Chat confirmation

- The confirmation is rendered with the **existing** confirm path: `adapter.sendInteractive(channelId, {requestId, method:"confirm", title, message}, {allowedMentions:"none", gatewayEdits:true})` → `toDiscordControl` → Yes/No buttons (`discord-payload.ts:265-287`). The message shows the action, the resolved target as a code span plus its id (`` `name` (id) ``), the server name, the reason and the expiry.
- **Escaping.** Every Discord-sourced string (member tag, nickname, role or channel name, server name) and the requester's reason is rendered inside a single-backtick code span after replacing backticks and control characters (including newlines) with spaces, so it cannot close the span, start a fake `Reason:` line or open a code fence. Ids are always shown beside names. Discord's own length limits (100 characters for names, 512 for the reason) are platform facts, so no further clipping is applied. The agent path uses the same rule for the dashboard dialog and labels the reason `Agent-supplied reason:`.
- **Mentions.** `sendInteractive` gains an optional third argument `{ allowedMentions?: "none", gatewayEdits?: boolean }`; `"none"` maps to `allowedMentions: { parse: [] }`. It is used for the confirmation and for every result post (`Done:`, `Refused:`), because display names can contain `@everyone`. C's `sendAgentMessage` (`allowedMentions: {parse: []}`) is a separate, non-chunking send for agent text and cannot carry buttons, so D adds the option to `sendInteractive` and reuses C's mentions value.
- **Who edits the message.** The adapter acks every click with `deferUpdate` and today ALWAYS edits the message to `…_→ yes_` afterwards (`discord.ts:630-652`), even when the gateway then refuses the click. With `gatewayEdits: true` the adapter acks only; the gateway edits (`cleanupInteractive`) after an accepted click, so a bystander cannot make a pending confirmation read `→ yes`.
- `requestId` is a fresh random id (128-bit). A `PendingModeration {requestId, guildId, channelId, invoker, op, expiresAt, auditedClickers}` is kept in an in-memory map, at most `moderation.maxPending` per server (`0` = unlimited). Live agent previews are **not** counted here: they have their own cap `moderation.maxAgentPending` (D5), so an agent cannot fill the human path. A request over the cap is refused with `moderation_too_many_pending` before any confirmation is posted, and is not charged. That map is consulted in `onInteractiveResponse` **before** `prompts` (`gateway.ts:1407`).
- **The click** is processed in this order. The record is consumed **synchronously, before any `await`**, so concurrent clicks cannot both run (the existing code deletes `prompts` before its work for the same reason, `gateway.ts:1459-1475`):
  1. The click has no `guildId` or a different one → ignored (`guild_not_enabled`).
  2. Clicker ≠ invoker → `not_invoker`. The prompt is **not** consumed (following `gateway.ts:1461-1464`) and the adapter edits nothing. One audit entry is written per (request, clicker); repeat clicks by the same user only increment the `not_invoker` counter, so a bystander cannot evict real evidence from the ring.
  3. No → consume, audit `moderation_cancelled`, post `Refused: moderation_cancelled.`.
  4. Yes → **consume the record now** (a second Yes finds none and is ignored), then re-run D3 steps **0**–4, 6 (check) and 7 for the clicker (step 2 through the non-logging `evaluateServerRequest`, so the re-run writes nothing), so a mode gate or `moderation.allowInQuery` that changed since the post refuses with `query_mode`, and a removed action or role edit is refused too. A failure is audited, replied, and the request is over (the invoker must re-issue it).
  5. **Charge, then write, with no `await` between**: `tryCharge` the chat limits (`perHour`, `perActorPerHour`; over a limit → `moderation_rate_limited`, nothing executes), then write the `permitted` entry durably (D9). If the append fails: refund the charge, `audit_unavailable`, nothing is executed. Both calls are synchronous, so two concurrent Yes clicks cannot both pass the same budget.
  6. `adapter.moderate`. Then post `Done: <summary>.` or `Refused: <reason>.` (mentions none) and call `cleanupInteractive`. A failure of the result post or of `cleanupInteractive` (for example the channel was the one just deleted) is swallowed and never changes the audit outcome (`discord.ts:586-596`).
- **Expiry.** After `confirmTtlSeconds` (`0` = never; above the timer maximum it is clamped to 2147483647 ms, D1), the buttons are removed, `moderation_confirm_expired` is audited and the record dropped. An agent preview expires the same way (a timer; `moderation_confirm_expired`, or `moderation_cancelled` when its session ends first), so silent expiry cannot leave an unaudited preview. A restart loses pending records (they are in-memory). A later click on an orphaned button finds no record and is ignored, which fails closed. The buttons stay visible but inert; `cleanupInteractive` runs on graceful stop.
- **Purge.** Pending chat records of a server are dropped (buttons stripped, one `moderation_cancelled` audit entry per record) when that server is disabled, removed, switched mode, disarmed (per-server or global), when `moderation.enabled` goes false, or when `moderation.allowInQuery` goes false in a `query` server. A removed action or edited `assignableRoles` needs no purge: the Yes re-runs the gate (step 4). Agent previews of that server are dropped the same way (one `moderation_cancelled` entry per preview). The gateway does not own an agent's confirm dialog (a dashboard prompt, C design D6), so it cannot cancel it, and **D does not remove C's pending-registry entry**: C keeps the entry while the dialog may still be open (so the dialog cannot render in chat later) and removes it on that `previewId`'s commit or cancel, the session's end or its own lifetime (D registered it with `confirmTtlSeconds`, `0` = until the session ends). The fail-closed equivalent: a later answer finds no D record and `discord/moderate` fails `moderation_preview_invalid` (and clears the registry entry), with nothing executed and the failure audited.

### D5. Agent tool (`discord_moderate`)

- **Registration.** One tool, `discord_moderate`, registered by **C's bridge entry** (`src/bridge/tools.ts`, `activate` in `src/bridge/index.ts`) with C's `discord_` prefix and `namespace: {name: "discord"}`, under C's `agentTools.exposure`. C's `discord/status` reply gains one optional field, `moderation: boolean` (true when an enabled server has `moderation.enabled` and `moderation.allowAgents`). The bridge registers `discord_moderate` only when `enabled && moderation`, and re-registers it `hidden` otherwise (the field is optional and left unclaimed by C in the `discord/status` field set); a C-only bridge ignores the extra field. It is declared `selfConfirming` to the untrusted-content guard registry, following the gmail pattern (`gmail-plugin/src/bridge/index.ts:12-26`). C's "Agent tools are off by default…" and "Read results are untrusted…" requirements now cover "any tool a later chat-gateway change adds" and "any later chat-gateway tool that confirms itself", so D does not modify them; if C narrows that wording again, D re-adds a MODIFIED block. Parameters: `{guildId, action, userId?, channelId?, roleId?, name?, parentId?, durationSeconds?, clear?, reason}`; the reason is trimmed (empty → `moderation_reason_required`).
- **What the model sees (no read oracle).** The tool returns `{outcome, reason?, detail?}` and **nothing else**. `detail` is limited to the missing Discord permission name (`missing_permission`), the platform code (`platform_refused`), the HTTP status or error class name (`discord_unavailable`) or the literal `timeout` (`unknown`). No member tag, nickname, role name, channel name or server name, and no `summary`, ever reaches the model: the names the server resolved go only into the human `ctx.ui.confirm` dialog, which the bridge builds from the preview's `summary` and never returns. Every refusal about a target, role or channel (`target_is_owner`, `target_is_self`, `target_outranks_bot`, `target_is_gateway_admin`, `target_is_administrator`, `role_*`, `channel_managed_by_gateway`, `unsupported_channel_type`, `target_not_found`, `not_banned`, `requester_not_found`) reaches the model as the single opaque reason `target_not_permitted`, so an unbound session cannot use the tool to learn who owns, administers or is mapped in a server, or any name (C's read allowlist, visibility and `not_readable` rules stay the only read path for names). **Residual, accepted, documented and tested (D-T7, settled):** a refused target and a passed target still differ, because only a passing target reaches a human dialog. An id that exists and is unprotected gets a preview, a nonexistent one gets `target_not_permitted` at once, so an unbound session in a server that allows agents can learn whether an id it already holds exists there. It learns no name, a positive costs a dialog the human sees, and a snowflake cannot be enumerated by guessing. C's visibility checks are not applied before the lookup (that would couple moderation to the read allowlist and block legitimate moderation of unlisted targets). The audit entry keeps the specific reason. Gate reasons about configuration (`moderation_disabled`, `moderation_action_not_allowed`, `moderation_rate_limited`, …) are returned as they are. This is the one place the audit reason and the returned reason differ (D12).
- **Flow** (two-phase over C's request lane; `sessionId` comes from the socket, `plugin-request-lane.ts:54-58`):
  1. Bridge: no `ctx.hasUI` → `blocked`. Nothing is sent to the server (`gmail tools.ts:160-165`).
  2. `discord/moderate-preview` (C's `discord/send-preview` pattern; registered `hubLocalOnly` like C's handlers). The gate runs in C's check order: C's `agentTools.enabled` (`agent_tools_disabled`); the session is known (`unknown_session`, C); adapter connected (`discord_unavailable`); input shape (`bad_request`); the guild is enabled (A, `guild_not_enabled`); the server mode (`query_mode` when the server is `query` and `moderation.allowInQuery` is not `true`, settled T1); **scope** (`cross_guild_denied` for a gateway-bound session naming a server other than its own, or one with no resolvable own server, by C's definition (all bindings, a DM binding beside a server binding leaves none; D6 of C); `spawned_session_denied` for a spawned one, D6); `moderation.enabled` (`moderation_disabled`), `moderation.allowAgents` (`moderation_agent_disabled`) and the action allowlisted (`moderation_action_not_allowed`); the guild is not disarmed (`disarmed`, from `team.isGuildDisarmed(guildId)` while the team controller runs, else A's `disarmStateFor(guildId)`, refusing on `"disarmed"` and on `"unknown"`, as C does; a global latch counts; a bound session's own server is the named server, so its latch is the one tested); reason, duration, `maxAgentPending` (`moderation_too_many_pending`; chat confirmations never count here, so agents cannot starve the human path), then the **preview budget**: `rateLimit.agentPreviewPerHour` per server, charged here, **before any Discord lookup** (`moderation_rate_limited`; a flooding or injected session is stopped before it costs REST calls); then D7 protections and the permission pre-check. On success it registers a pending entry in **C's pending agent-tool confirmation registry** (entry `{sessionId, previewId, expiresAt?}`, keyed by the server-issued, unguessable `previewId`; C design D3/D6; D adds no second registry and no per-session flag), with the lifetime D chooses as the registrant: `confirmTtlSeconds` (`0` = until the session ends), so C's `limits.agentToolConfirmPendingS` never ends D's entry before D's preview. It returns `{previewId, summary}` to the bridge only. D keeps its own record of the previewed op under that `previewId` (the op, the guild, the expiry); the `previewId` is one-shot, bound to `sessionId` (another session's id fails), has the `confirmTtlSeconds` TTL (`0` = until the session ends), is **not** replaced by a later preview (several may be live, bounded by `maxAgentPending`) and is dropped when the session ends. C's registry entry leaves through `discord/moderate`, `discord/moderate-cancel`, the session's end or its own lifetime (`confirmTtlSeconds`); D never removes it any other way.
  **Two records, one rule.** D's record and `confirmTtlSeconds` alone decide whether a preview is live, and `discord/moderate` trusts D's record, never C's registry (which stores no operation data). The registry entry takes its lifetime from D as the registrant, so `agentToolConfirmPendingS` (C's own lifetime for `discord_send`) is not involved: a `confirmTtlSeconds` above `agentToolConfirmPendingS` leaves the preview valid and committable until `confirmTtlSeconds`, and the confirm is never posted in Discord (marker, title prefix and C's suppressed-promptId set). A lapse of C's entry could only end the session-wide suppression window, never commit or invalidate a preview, and is not an error. D clears C's entry on commit or cancel when it exists and ignores it when it does not. D shows no advisory for this and keeps no "must be at least the PromptBus timeout" hint for `confirmTtlSeconds`; C's own hint covers its setting.
  3. Bridge: `ctx.ui.confirm("Discord moderation: <action>", summary lines, { pluginMeta: {...AGENT_TOOL_CONFIRM_META, tool: "discord_moderate"}, timeout })`, where `timeout` is `confirmTtlSeconds × 1000` when that is non-zero (so a headless-but-bridged session does not wait past the preview). False, a throw or a timeout calls `discord/moderate-cancel {previewId}` and the tool returns `denied`. The cancel must come from the preview's session and audits `moderation_cancelled`. If `ctx.ui.confirm` resolves after the lane's own timeout, the tool returns `{outcome:"unknown", detail:"timeout"}` (C's "may already have run" wording).
  4. `discord/moderate {previewId}`. D's record is **consumed synchronously before any `await`**: an unknown, already-used or other-session `previewId` is `moderation_preview_invalid` (a foreign session's attempt does NOT consume the owner's record: it is looked up by `sessionId` first, so the owner can still commit it) (a preview survives a bridge socket drop and reconnect with the same `sessionId`: it ends only by TTL, commit, cancel or the host's session-ended event; C reports the same case as `bad_request: unknown_preview`; D keeps its own reason so the audit says which lane), an expired one `moderation_confirm_expired`, so two concurrent commits execute at most once. The server then **re-runs the whole preview gate** (TOCTOU: settings, mode, disarm, hierarchy and permissions may have changed), then, as for chat (D4 step 5), `tryCharge`s `agentPerHour` and `perActorPerHour`, writes the `permitted` entry durably (D9, else `audit_unavailable` and the charge is refunded), executes and records a failure as in D4. The agent commit lane has no deadline of its own; when the 15 s request lane times out after the action may already have run, the bridge returns `{outcome:"unknown", detail:"timeout"}`, the `permitted` entry stays the authority and the preview is already consumed (a retry is `moderation_preview_invalid`).
- **Counting unit.** Each chain is counted once per limit: once at the preview against `agentPreviewPerHour`, once at the commit against `agentPerHour`/`perActorPerHour`. `discord/moderate` and `discord/moderate-cancel` do not re-count against `agentPreviewPerHour`, so a confirmed op is never refused for the preview budget after the human said yes, and a cancel is never refused. This keeps C's one-count-per-send-chain unit (C design D3 step 4) for each of D's budgets. The commit budget is charged at the commit, not at the preview, because "declined and expired requests are not charged" is D's own contract (D8).
- **Why two-phase.** The human confirms names the **server** resolved (member tag, role name, server name), not model-supplied ids. Commit-time re-validation closes the gap between confirm and execute. C's `discord_send` previews the target and re-checks at `discord/send` by `previewId`; D follows the same shape and adds only the three `discord/moderate*` handlers on C's lane (type constants in `src/shared/types.ts` beside C's).
- **Bound sessions moderate only their own server.** A session bound to the gateway (spawned or attached; C's definition, C D4 rule (d): all its bindings; a DM binding beside a server binding leaves no own server; private threads are not inherited) that names another server is refused `cross_guild_denied`; an unresolvable own server fails closed with the same reason. An unbound dashboard session may moderate any enabled server that allows agents. `discord_send` keeps C's allowlist model (C: confirm-gated, allowlisted targets); that residual is C's to state.

### D7. Protected targets and hierarchy (pure `moderationRefusal(facts)`)

This is a pure function next to `assignersForRole` (`discord-payload.ts:473-481`, the only hierarchy rule that exists today). It works over a `ModerationFacts` snapshot: guild owner id, bot id, the bot's highest role position, the requester's highest position (chat only, from the requester member fetch), the target member's highest position and Administrator flag (absent for a non-member ban target), the role's position, `managed` flag, `@everyone` flag and permission bits, the target channel's type and flags, and the gateway's own sets (admins, operate principals, tier-mapped role ids, protected channel ids). **The target checks apply to every member-targeting action** (kick, ban, timeout, role assign and remove), not only the first three. It returns the first refusal:

| check | reason |
|---|---|
| target = guild owner | `target_is_owner` |
| target = bot | `target_is_self` |
| target highest role ≥ bot highest | `target_outranks_bot` |
| (chat, requester ≠ owner) target highest ≥ requester highest | `target_outranks_requester` |
| requester member cannot be resolved (chat) | `requester_not_found` |
| target id is in `guilds.<g>.admins` or holds an `operate` mapping in `principals` (settled, T4: fail closed; the owner can act in Discord directly) | `target_is_gateway_admin` |
| timeout on a member with Administrator | `target_is_administrator` |
| role ≥ bot highest | `role_outranks_bot` |
| (chat, requester ≠ owner) role ≥ requester highest | `role_outranks_requester` |
| role `managed` or `@everyone` | `role_managed` |
| role id not in `moderation.assignableRoles` (`role_assign`/`role_remove` only) | `role_not_assignable` |
| role id appears in any tier mapping (`guilds.<g>.roles`, any binding's `roles`) | `role_mapped_to_tier` |
| role grants Administrator, Manage Guild, Manage Roles, Manage Channels, Kick, Ban or Moderate Members | `role_grants_moderation` |
| channel listed in `guilds.<g>.channels`, `guilds.<g>.index.channels` (B), a provisioned binding (`src/server/team/provisioning-store.ts:22-40`), a persisted binding in `bindings.json` or a fixed `teamControls.bindings.<ws>.channelId` | `channel_managed_by_gateway` |
| channel target is not a `GuildText` channel (thread, DM, category, voice, stage, forum, announcement) or is the guild's rules, public-updates, system or AFK channel; for `channel_create … in <parentId>`, a parent that is not a category | `unsupported_channel_type` |
| a member-dependent target (kick, timeout, role target) or a ban id that neither `members.fetch` nor `users.fetch` resolves; a channel or role id that is not in the guild; a `channel_create` parent that is unknown or of another server | `target_not_found` |

- **Why the escalation rules.** `role_not_assignable` makes role assignment an allowlist: an operator names the roles the bot may hand out, so a role that carries Manage Webhooks, Mention Everyone, Manage Messages, View Audit Log or access to a private channel's overwrites is never granted by accident. `role_mapped_to_tier` stops moderation from minting gateway tiers: assigning a mapped role would grant `control` to its holder. `role_grants_moderation` stays as a second layer, in case an operator lists a dangerous role. Agents have no Discord identity, so only the bot's hierarchy applies to them. A human confirms each agent action.
- **Gateway-managed channels** include `guilds.<g>.index.channels`, because deleting such a channel purges its local message index (B "Edits and deletes follow Discord"). Channel ids in C's `agentTools.read/send` lists are not protected: deleting such a channel only makes the id inert, which is accepted.
- `ModerationFacts` comes from the optional `adapter.moderationFacts(op)`. Execution goes through the optional `adapter.moderate(op, reason)`, both added to `base.ts`. Discord implements them through a `DiscordModerationOps` seam that follows the `DiscordChannelOps` pattern (`discord.ts:88`, `:489-530`). An adapter without them gets `moderation_unsupported`.

### D8. Rate limits

There are four rolling one-hour windows (sliding, half-open: a charge counts while `now − t < 3 600 000` ms, so it is free again exactly at 3 600 000 ms; the clock is monotonic, so a wall-clock jump neither locks nor frees a limit): `perHour` for **chat** requests per server across all admins, `agentPerHour` for **agent** commits per server, `perActorPerHour` per principal (Discord user id for chat, C's agent principal `session:<sessionId>` for agents; the per-server windows are what bound a swarm of new sessions), and `agentPreviewPerHour` for **agent previews** per server. The chat and agent budgets are separate, and so are the pending caps (`maxPending` for chat, `maxAgentPending` for agents, D4/D5), so a looping or injected agent cannot starve human admins.

- **Check at the request, charge at the Yes.** A chat request and an agent preview only *check* the commit budgets (non-charging, D3 step 6) when they are raised. The chat budgets (`perHour`, `perActorPerHour`) and the agent commit budgets (`agentPerHour`, `perActorPerHour`) are *charged* only when a Yes (chat) or a `discord/moderate` (agent) has passed the full gate and just before the durable `permitted` entry (`tryCharge`, synchronous; refunded when the append fails). So a refused request, a declined or expired confirmation and a bystander click never cost budget, which is what the spec requires, and one admin posting and declining requests cannot burn `perHour` for everyone. What bounds an admin who posts confirmations and leaves them unanswered is `maxPending` (D4; agent previews are bounded by `maxAgentPending`) and B's per-user command limit (`command_rate_limited`), not the hourly budgets.
- **Previews are metered separately.** `agentPreviewPerHour` (default 30, per server) is charged at each preview that passes the cheap config gate and **before** the first Discord lookup, so an injected or looping session cannot cause unbounded REST calls (`members.fetch`, `fetchMe({force:true})`, `users.fetch`) through previews. Over it: `moderation_rate_limited`, no lookup. `discord/moderate` and `-cancel` are not counted against it (D5 counting unit). A refusal in the cheap config gate costs no Discord call, so it needs no budget; its audit is bounded by the per-(server, reason) dedupe (D9).
- `0` = unlimited for every window. The counters are in-memory and reset on restart; this is accepted and documented.
- **A failed Discord call keeps its charge.** The chat charge is made at the Yes and refunded ONLY on `audit_unavailable`; a later `platform_refused` or `discord_unavailable` keeps it, so a loop of failing confirmed calls cannot hammer Discord.

### D9. Audit

Audit is evidence, so an entry never claims an authorization that did not happen (`audit.ts:58-71`: an entry with no usable outcome is dropped, and every non-`refused` entry is read as permitted). The entries are:

| when | outcome | phase | reason |
|---|---|---|---|
| a gate step refuses a `!mod` request, when its reply is posted (a throttled reply is counted `refusal_throttled`, D3), or a `discord/moderate-preview` (repeated preview refusals share one entry per server and reason, below) | `refused` | `request` | the reason (the specific one, never the model-facing `target_not_permitted`) |
| `not_invoker` (once per request and clicker) | `refused` | `confirm` | `not_invoker` |
| No, a cancel, an expiry of a chat confirmation **or of an agent preview**, a session end with a live preview, a purge | `refused` | `confirm` | `moderation_cancelled` / `moderation_confirm_expired` |
| a failed re-validation after Yes or at commit | `refused` | `confirm` | the reason |
| Yes (or a valid commit) after the final gate, **before** Discord is called | `permitted` | `confirm` | — |
| Discord rejects or is unreachable after that entry | `refused` | `result` | `platform_refused` (`detail` = code) / `discord_unavailable` (`detail` = HTTP status or error class) |
| an unexpected exception in the gate (not a Discord error) | `refused` | `request` or `confirm` | `moderation_internal_error` |

- An accepted request that is posted or previewed writes **no** entry by itself, so a confirmation that is never answered leaves no `permitted` row. The `permitted` entry is the authorization to execute, written only after a human said Yes.
- **Durable before execute, transactional.** D REUSES `CommandLog.appendDurable(entry): boolean`, which C adds in `audit.ts` (C's D9, owner decision P6; D defines no second one). It **stages** the entry: it builds the candidate ring (current entries plus the new one, trimmed to the retention), writes that candidate, and commits it to the in-memory ring only when the write succeeded. On failure the ring is unchanged and it returns false, so a failed `permitted` can never be persisted later by an unrelated append (the existing `append` pushes first, `audit.ts:100-120`). If it returns false, the request is refused `audit_unavailable` and nothing is executed. Refusal entries use the ordinary `append`.
- **The gate writes nothing by itself.** The chokepoint evaluation is the non-logging `evaluateServerRequest` (D3 step 2), so before the Yes the log holds only the refusal entries D writes itself, and a refusal is logged once, not once by the chokepoint and once by D.
- Entry fields: `verb: "mod_<action>"`, `principal` (the Discord user id for chat, C's `session:<sessionId>` for agents), `channelId` (**required** by `isEntry`, `audit.ts:58-71`: the invoking channel for chat; the empty string for an agent call, C's convention in `chat-gateway-audit` "Agent request is logged without a channel"; without it every entry built per this spec would be dropped on load), `guildId` (A), `target` (the target user, channel or role id; for `channel_create` and `role_create`, the guild id, with the parent id in `detail`), `outcome`, `reason`. C's `agent_send` and `agent_read` verbs are not reused.
- New optional fields are `phase: "request" | "confirm" | "result"` and `detail` (missing permission, platform code, the parent id of a created channel, or the reason text). `detail` is not clipped: the reason is already bounded by the 512-character platform fact (`reason_too_long`), so there is no code limit to configure. `outcome` stays within `{permitted, refused}`, so older `isEntry` (`audit.ts:58-71`) still loads the entries.
- **Retention.** The command log is a ring (`audit.ts:100-120`) bounded by the existing setting `teamControls.auditRetention` (default 10,000), which C converts in place so that `0` = unlimited (C's MODIFIED "Log survives restarts and does not grow without bound"). D adds no retention key and no `limits.auditRetention`; with `0` the file is rewritten whole per append and grows without bound (C documents the cost). Together with once-per-clicker `not_invoker` entries, a bystander can no longer evict genuine entries by spamming a button.
- **Preview-refusal dedupe.** The ring-eviction problem D solved for `not_invoker` clicks would re-open through the agent path (every refused preview is an entry, default ring 10,000, `0` = unlimited rewrites the whole file per append, `audit.ts:100-120`). The first version keyed the dedupe by principal and target, both of which an agent chooses, and refusals in the cheap config gate are not metered, so a looping session varying an id or a session identity would have written unlimited distinct entries. So a refused **preview** writes one entry per (server, reason) per rolling hour: the server is part of the key only when it is a configured server, otherwise the key carries an empty server (an agent-chosen guild id never creates a key). The key space is therefore bounded by configured servers × the closed reason set (D12). The window is the hour of the `rateLimit.*PerHour` settings, not a separate constant. The entry carries the first principal and target seen; repeats only increment the per-reason `refused` counter on the health surface. Entries for **confirm-phase** events are unaffected. Together with `agentPreviewPerHour` (stops the lookups) this bounds REST cost, log churn and the whole-file rewrite per append (`audit.ts:122-127`) from a looping agent.
- **Distinct bystanders (accepted residual).** `not_invoker` is audited once per (request, clicker), and the number of distinct clickers is bounded only by who can see the channel, so enough distinct clickers can still evict older entries from the ring. This is accepted and documented; the tests pin one entry per clicker and the counters.
- **Counters** per server are added to the health surface: `executed` (Discord call succeeded), `refused` (any `refused` outcome except `result`, deduplicated repeats included), `failed` (`result`-phase refusals: `platform_refused`, `discord_unavailable`) and `not_invoker` (all clicks, audited or not). This covers observability.

## Security notes

- **Untrusted input.** Chat text is parsed by a strict, pure parser into ids. Model output arrives only as typed tool params. Discord names are untrusted: they are rendered in escaped code spans beside their ids, sent with mentions disabled, and returned to the model as data. The agent-supplied reason is labelled as such in the dialog.
- **Prompt injection.** Content the bot reads (B's index, `!ask`) cannot trigger moderation, because `!ask` runs with no tools (B). An agent that is persuaded by content still needs a human confirm on names the server resolved, plus per-server opt-in, `allowAgents`, the own-server rule for bound sessions, and rate limits. **The tool is not a name oracle:** the model gets `{outcome, reason?, detail?}` with no names, and target refusals collapse to `target_not_permitted` (D5), so it cannot probe who owns or administers a server, which would bypass C's read allowlist. A residual remains and is stated, not hidden: it can learn that an id it already holds exists in a server that allows agents, because only a passing target reaches a human dialog (D5, D-T7, settled).
- **Least privilege.** The checks are: action allowlist per server; per-server admin AND `operate` through an explicit user-id mapping only (a role never grants it); invoker-only clicks; one-shot previews bound to the session, consumed before execution; re-validation at commit; role assignment limited to an operator allowlist; no permission bits on created roles or channels; refusal of escalation roles; text-channel-only channel actions; durable audit before every execution.
- **Fail-closed confirm path.** An agent confirm that loses its marker is still not rendered in chat (title second signal, D5). A confirmation whose audit write fails is not executed.
- **Spam and DoS.** Rate limits apply per server (separate chat, agent-commit and agent-preview budgets) and per actor; pending caps are separate for chat (`maxPending`) and agents (`maxAgentPending`); previews are metered before any Discord lookup and preview refusals share one audit entry per server and reason per hour, whatever the principal or target (D8, D9). Bystander clicks write at most one audit entry per request and clicker. `!mod` floods are cut by B's per-user command limit before D's gate. Refusals reply only to admins in opted-in channels, which is B's exposure.
- **Residual: the request lane (accepted by the owner, D-T5).** The confirmation is enforced in the bridge tool; `discord/moderate {previewId}` carries no proof that a human answered, and the lane is "Not authenticated — handler must authorize payload" (PLUG-C7). **Verified:** the bridge unix socket admits any same-user process with no credential (`decideBridgeUpgrade`, `bridge-upgrade-auth.ts:120`), so a child process of the same user (for example a bash tool of an injected agent) can register a fresh session id and call the lane directly. Such an id is unbound, so it may name any server that allows agents, and no UI is involved. The bot token is persisted in the plugin config of the same user's dashboard config file (`~/.pi/dashboard/config.json`, `docs/chat-gateway.md` "Dashboard Configuration"; its file mode is `unverified`), so server-held-token isolation is probably not a boundary against such a process either; C's `discord_send` has the same trust level. The own-server rule, per-server opt-in, `allowAgents`, rate limits and the Discord hierarchy still bound such a caller; the human confirm would not. Owner decision (D-T5): accept and document this residual, with the same trust model as C's `discord_send`; revisit when bridge authentication lands. The alternative considered was for the server to observe the human's answer (a gateway-seen `prompt_response` for the previewed prompt) before it executes.
- **Privacy.** No message content is persisted by D. Audit stores ids, the reason text (a reason can hold personal data, so the file is 0600) and outcomes. B's index must not capture `!mod` command messages (cross-fix to B).

## Migration, compatibility, rollback

- **Upgrade.** Nothing to do: `moderation` is absent, so moderation is off. No legacy keys are touched. The key `allowAgents` and the other fields are new and unreleased.
- **Older plugin with the new config (rollback).** A version without D ignores `guilds.<id>.moderation`. That relies on A's validator **preserving** reserved keys: verified in A's design (`design.md:92`, `:209`) and spec "Reserved record keys are preserved" (scenario "Rollback keeps servers loadable"), where `moderation` is a plain-object key stored and returned verbatim and kept when a write omits it. If an A-only version still dropped the key, moderation stays off, which fails closed. A non-object `moderation` is dropped alone on the boot read. Old audit readers keep entries and ignore `phase` and `detail`. Pending confirmations die with the process, and their orphaned buttons do nothing. D adds no `limits.*` key. `moderation.allowInQuery` is a new field inside `moderation`, preserved verbatim by A. An older plugin ignores it, so moderation stays off (the whole object is ignored). Retention keeps using C's `teamControls.auditRetention`; its rollback caveat for `0` is C's.
- **Rollback of the tool.** If C's bridge entry stops registering `discord_moderate`, nothing remains: the server handlers stay unregistered. A C-only bridge ignores the extra `moderation` field of `discord/status` (C then never registers the tool).
- **Discord side.** Actions already executed are not reverted. Discord's audit log holds the `[pi-gateway …]` reason.

## Risks / Trade-offs

- **In-memory pending state and rate-limit windows** keep this simple but reset on restart. Restart counts as fail-closed for pendings and as a reset for limits.
- **The chat skip depends on the dashboard bridge's `pluginMeta` copy, with the title prefix as backstop.** Without that bridge (TUI-only pi), there is no `prompt_request` and nothing to render. With an older bridge that drops `pluginMeta`, the title prefix still keeps the confirm out of chat. The tool returns `blocked` when `ctx.hasUI` is false, but it cannot detect an old bridge.
- **Requiring `operate` plus admin** may feel strict. It keeps role-based delegation from ever reaching moderation (owner decision 23). The price is the ceiling coupling (settled, T2: documented, with a dashboard warning and per-binding ceilings).
- **Out-of-scope: live-guild facts.** Whether `members.fetch` works without the GuildMembers intent, `fetchMe({force:true})` and `permissionsFor` with real overwrites are `unverified` against a live Discord server and are covered by manual verification only.
- **A consumed record cannot be retried.** After a Yes, a failed re-validation or a failed audit write ends the request; the invoker re-issues it. This is deliberate: it is what makes double execution impossible.
