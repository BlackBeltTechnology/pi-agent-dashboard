### #1097 — EditorSearchPanel ArrowDown flake

- The active-row class is `i === activeIndex ? "bg-[var(--bg-hover)]" : "hover:…"` (`packages/client/src/components/editor-pane/EditorSearchPanel.tsx:218`). `onKeyDown` ArrowDown does `setActiveIndex(i => Math.min(i+1, items.length-1))` (`:124-126`).
- Results only render once `debounced` is set (200 ms `setTimeout` `:80-83`, `DEBOUNCE_MS` `:49`): `canSearch` (`:86`) gates `items` (`:111-117`).
- **The same commit's passive effect resets the selection**: the search effect (`:89-106`) runs `setActiveIndex(0)` (`:94`) whenever `debounced/mode/regex/canSearch/onFilenameSearch/onContentSearch` change — i.e. in the very commit that first makes `src/editor.ts` visible.
- Test: `findByText("src/editor.ts")` then immediate `fireEvent.keyDown(ArrowDown)` (`__tests__/EditorSearchPanel.test.tsx:82-83`), then polls row 1 active (`:88-91`).
- Root cause (inferred from React semantics; task 1.1 attempts a deterministic confirmation): the debounce `setState` fires from a bare `setTimeout`, outside `act`, so the commit and its passive effects are separate scheduler tasks. `findByText` resolves on the DOM mutation (MutationObserver microtask), *before* the passive-effect task. `ArrowDown` then enqueues `i+1`; the pending effect flushes at the next render and enqueues `setActiveIndex(0)` **after** it → final index 0, row 1 never active, and polling cannot recover (the clobber already happened). It passes locally because RTL's post-`waitFor` macrotask tick usually lets the effect flush first; under CI load the ordering varies. Raising the 1 s `waitFor` timeout would not help (issue's cause #1 is a red herring; cause #2 is right).
- Not a production bug: the reset runs at search-fire time; results (`fileResults` / `setContentResults`) arrive afterwards and do not reset. A human cannot press ArrowDown inside the commit→effect window. The effect also re-fires — and resets selection to row 0 — when `mode`/`regex` toggle or when `onFilenameSearch` (`handleListFiles`, `hooks/useSessionActions.ts:586`, deps `[selectedId, send]`) / `onContentSearch` (`useCallback([cwd])`, `EditorPane.tsx:227-230`) change identity (WS reconnect, session/cwd change). In each case a new search fires, so a reset to row 0 is intended behaviour (reasoned from code, not covered by a test). Recorded on #1097 when closing (task 1.8).

### #1071 — real-serve orphan

- Stub spawns `node -e "process.stdin.resume(); … setInterval(…)"` with `{ stdio: "inherit" }`, not detached, no pid recorded (`fixtures/stub-exec.mjs:9-11`). Confirmed.
- `BridgeManager.terminate` = `stdin.end()`, then after grace `b.child.kill()` on the **stub only** (`packages/obs-studio-plugin/src/server/bridge.ts:168-181`, kill `:175`). The test's `spawn` is non-detached (`real-serve.test.ts:30`), so the grandchild is orphaned on dispose; `afterEach` only closes fake OBS (`:19-22`). Confirmed — every run of the 2nd test leaks one process.
- The stub models the real exec faithfully: `execVerb` spawns the child with `stdio: "inherit"`, no `detached`, installs no signal handlers, and only awaits `exit` (`packages/server/src/services/cli-service.ts:351-394`). A real `service exec` killed with SIGTERM/SIGKILL therefore also orphans its child and skips `release` (lease expires via heartbeat TTL). Spec only requires "hold a lease … forward exit code" (`openspec/specs/managed-services/spec.md:356-357`) — no signal contract.
- Production exposure is narrow: real `pi-obs serve` exits on stdin EOF (`packages/obs-studio-plugin/src/core/serve.ts:121`, `finish` `:81-87`), so the normal path never reaches the kill; a leak needs a serve whose `conn.close()` never settles (`:86`) or the 5 s request-timeout path (`bridge.ts:168`) against a wedged serve. Real but low-frequency → deferred (Decision 4).

## Goals / Non-Goals

Goals: deterministic #1097 test; verified closure of #1070; no process leaked by `real-serve.test.ts` on a normal run (pass, fail, or Ctrl-C that runs `afterEach`), enforced by an in-test liveness assertion. A vitest worker SIGKILLed mid-test can still leak one process (accepted, see Risks).
Non-Goals: changing `EditorSearchPanel`, `BridgeManager`, `cli-service.ts`; raising timeouts; backfilling a process-group kill into the platform layer.

## Decisions

1. **#1097: fake timers + `act` in the test, synchronous assertions.** `vi.useFakeTimers()`; `fireEvent.change`; `await act(async () => { await vi.advanceTimersByTimeAsync(DEBOUNCE_MS + 50) })` so the debounce commit and passive effects flush together; then `getByText("src/editor.ts")`, `fireEvent.keyDown(ArrowDown)` (RTL wraps in `act`), assert row 1 active **synchronously**, `Enter` → `onOpen`, `Escape`; `vi.useRealTimers()` in `afterEach`. The old `findByText` / `waitFor` poll is dropped: RTL's async utils can hang under `vi.useFakeTimers()` in vitest (no jest-style timer detection), and after the `act` flush the state is already committed so polling is unnecessary. Alternatives: (a) `await act(async () => {})` after `findByText` — rejected, effect scheduled outside act's queue so not guaranteed to flush; (b) re-fire ArrowDown inside `waitFor` — rejected, non-deterministic count, can overshoot; (c) derive the reset in the component (store index keyed by search key, no effect) — correct but production change for a non-production bug; optional follow-up; (d) bump `waitFor` timeout — does not address the clobber.
2. **#1070: no code change.** Stress-verify and close. Alternative (re-edit the test) rejected: already mutation-verified.
3. **#1071 test fix: pid file + in-test reap and liveness assertion.** Stub honours `STUB_CHILD_PID_FILE` (only in the `STUB_IGNORE_EOF` branch): `writeFileSync(file, String(child.pid))` synchronously after spawn. The EOF-ignoring test creates a tmp pid file and passes it via the `manager()` env arg; its `afterEach` reads the file (absent → skip; present but empty/non-numeric → fail the hook with a message naming the file path and its contents, since the stub's `writeFileSync` is synchronous and a malformed file is a real defect, not a skippable state; the first test's real serve exits on EOF and is asserted exit 0), reaps the pid with the shared `killProcess` (`@blackbelt-technology/pi-dashboard-shared/platform/process.js`, cross-platform: SIGTERM→SIGKILL on POSIX, `taskkill /F /T` on win32, `{timeoutMs}` kept short), then asserts `isProcessAlive(pid)` is false via a bounded poll (≤2 s; `killProcess` returns right after SIGKILL, before the OS necessarily finished termination, so a one-shot read can false-fail) and removes the tmp dir. The leak assertion is verified on Linux/macOS only (no Windows unit-test CI job exists; Windows behaviour is reasoned from the shared `killProcess` helper's own tests, no new infra). No `pgrep` (unavailable on Windows, regex-quoting hazards). No self-expiry timer in the grandchild: it would change argv, mask a regressed reap for a minute and diverge from the issue's documented cleanup command, for the sole benefit of the rare SIGKILLed-worker case. Alternatives: spawn stub `detached` + `process.kill(-pid)` — rejected, POSIX-only; stub forwards SIGTERM to child — rejected, stub would stop modelling real exec (no forwarding), hiding the product question.
4. **#1071 product hardening: deferred. Decided 2026-11-03 by owner (option A).**
   - Question: should production stop leaking a child when `BridgeManager.dispose` kills `service exec`?
   - Evidence: `cli-service.ts:351-394` `execVerb` spawns the child `stdio:"inherit"`, not detached, no signal handlers, releases the lease only after child `exit`; `bridge.ts:168-181` `terminate` = stdin EOF, then `child.kill()` (SIGTERM, exec only) after 5 s; real `pi-obs serve` exits on EOF (`core/serve.ts:121`) so a leak needs a hung `conn.close()` or the request-timeout path against a wedged serve; spec `managed-services/spec.md:356` has no signal contract.
   - Options: **A** test-only now, no product change (CHOSEN; lowest risk, leak remains in the rare wedge path). **B** `BridgeManager` spawns exec as group leader (`detached:true`) + `killProcessGroup` (reaches grandchildren; Windows detached/console semantics; fixes only this caller). **C** `service exec` forwards SIGTERM/SIGINT/SIGHUP to its child, awaits exit, releases lease, returns 128+n (fixes all callers + the lease-release gap; SIGKILL still unforwardable; needs a `managed-services` spec delta + cli-service tests; stub should then forward too).
   - Rationale: rare wedge path, test hygiene fixed now; C is a product/spec decision that deserves its own change (B optional as defence in depth). Because `Fixes #1071` auto-closes the issue, the question is tracked in follow-up issue #1103 (already filed; referenced via `Refs #1103` in the commit trailer and PR description).

## Risks

- #1097 root cause is inferred from React semantics. Mitigation: task 1.1 timeboxes a deterministic reproduction (control the commit→effect ordering, not statistical reruns of a ~1-in-16k flake). If none can be built, the cause stays recorded as inferred, the fix proceeds (it is harmless and strictly stronger synchronisation), and task 1.6 runs a mutation check (drop the `act` flush → the test must go red/warn).
- A vitest worker SIGKILLed mid-test never runs `afterEach`, so one `real-serve` grandchild can leak (it blocks on stdin forever). Accepted trade-off: rare, manual `kill` of the pid; a self-expiry timer was rejected (Decision 3). Failing runs/Ctrl-C that run `afterEach` are covered.
- One-off verification runs (mutation checks, negative controls, CPU-load stress: F1, F2, P1–P3, X3, X4 in `test-plan.md`) are recorded in task notes, never committed: committing them would pin the buggy ordering or a deliberately broken `afterEach` (owner decision 2026-11-03).
- pid reuse between exit and `afterEach` kill: negligible; `killProcess` targets only a pid the stub wrote moments earlier and checks liveness first.
- Issue #1071's documented `pkill -f "...setInterval"` cleanup still matches (grandchild argv unchanged).
