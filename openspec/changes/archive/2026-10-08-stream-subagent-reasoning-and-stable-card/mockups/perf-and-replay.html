Subagent: performance options + truncated replay

Part 1 shows the three performance fixes against today. Part 2 shows the "N steps hidden" replay problem and three ways to fix it. The numbers are measured on the real store unless marked "est."

Part 1

Performance fixes for the live tail

A: Drop the early timeline request on block end

Each mark is a full-timeline reply from the bridge, and each one is also stored. Over 60 s with the inspector open, the subagent produces 14 blocks and its timeline keeps growing.

Current build (backoff + request on every block end)≈ 30+14 full replies
backoff (2 s, timeline growing) extra on block end
With A (backoff only, last tail held)≈ 30 full replies (−30%)
Nothing changes on screen: the held tail covers the gap until the next backoff request (≤ 2 s).

B: Collapse subagent_* progress ticks in the store (keep the newest per agent)

Today the store keeps every subagents:started progress tick. tool_execution_update is already collapsed to 2. Measured: 100 s at 4 ticks/s.

Effect on replay: a reloaded tab replays 1 progress tick per subagent instead of 400. The client's end state is the same (same raw-vs-compacted replay check as the update collapse). Cost: a server change plus that test.

C: Shorten the tail from 280 to 160 chars

280 chars (current)~477 B/tick
Card: ticker (option C)
Opened view: live block
160 chars~357 B/tick (est. −25%)
Card: ticker (option C)
Opened view: live block

The card ticker looks the same (it only needs the current sentence). The opened view shows about half as much live text, but each finished block still shows in full once its entry arrives.

Combined (A + B + C), per 10-minute subagent, est.
Stored progress bytes: ~1 MB → ~0.5 KB (B dominates) · Full-timeline replies: −30% (A) · Bytes per tick on the wire: −25% (C)
Part 2

Replay hides the subagent's steps behind "⋯ N steps hidden ⋯"

When a timeline goes over the 256 KiB per-event limit, reduceSubagentEvent keeps the first and last few steps and swaps the middle for a text entry. After a reload, that's all you get: the steps are gone for good, though while the pi session is still running, the bridge still has the full timeline in memory.

On the terminal frame, the server writes the full timeline to ~/.pi/dashboard/subagents/<agentId>.json before truncating, and serves it over REST in pages. Works after the session has ended and after a server restart, and the in-memory store stays bounded. It's the biggest change: a new file store, retention and cleanup, and a new endpoint.

Suggested: R2 now (small, works everywhere) plus R1's load button while the session is alive. R3 later as its own change if you need full history after the session ends.
