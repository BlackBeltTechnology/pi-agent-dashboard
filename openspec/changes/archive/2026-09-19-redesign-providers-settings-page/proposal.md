## Why

Settings → Providers renders the entire provider catalogue as a flat list of full-height cards. On a live instance that is **42 rows, of which 35 are an "Add Key" button and nothing else** (plus one unconfigured Sign In row); only 6 hold a credential. The page shows what *could* be configured far more loudly than what *is*, so answering "what am I authenticated to?" means scrolling past three dozen inert cards. *(Row counts are instance-specific: the api-key rows come from the bridge-pushed catalogue, so the total varies with the connected session's model registry and pi-ai version. The ratio, not the absolute, is the problem.)*

The same page then carries a second, unrelated provider concept below it — **LLM Providers**, the custom OpenAI-compatible endpoint editor — with a different mental model (*register an unknown endpoint* vs *authenticate a known provider*) and a different persistence model (page-level Save/Discard bar vs instant write). Two answers to "how do I get a model working", stacked, neither obviously the right one.

Two defects surfaced while scoping this change and are folded in because the redesign makes them reachable rather than obscure:

- **`ProviderAuthStatus.authenticated` is not "is this provider configured".** For api-key rows it is `hasStoredKey || ambient` (`provider-auth-storage.ts:323`), where `ambient` means only the Vertex-ADC/Bedrock-IAM sentinel (`provider-register.ts:689-690`). The bridge catalogue separately carries `configured` + `source`, but `_buildAuthStatus` drops them, so a provider credentialed by a plain env var (`OPENAI_API_KEY=sk-…`) reads `authenticated: false`. Filtering the list on `authenticated` would hide exactly the state the redesign exists to surface.
- **The `-api` twin can destroy an OAuth credential.** When an OAuth handler exists for an id, `_buildAuthStatus` emits a second row `<id>-api` ("Anthropic (API Key)") from the *same* catalogue entry, and `resolveAuthJsonKey` (`provider-auth-storage.ts:362`) maps it back to the *same* auth.json key, which `writeCredential` (`:251`) blind-overwrites with no OAuth guard. Today that twin reads unconfigured, so a searchable Add picker would turn "silently revoke your own subscription login" into a two-click path.
- **The bridge spec is stale against pi-ai.** `provider-auth-bridge/spec.md:339` requires an env-var provider to carry `configured: false`; pi-ai's `getProviderAuthStatus` returns `{configured: true, source: "environment"}` (`model-runtime.js:419-420`). This change depends on the field's meaning, so the drift is reconciled here rather than left to the next reader.

## What Changes

- **The list shows state, not the catalogue.** The list renders only providers that hold a credential, unifying four kinds into one list distinguished by badge: **Subscription** (OAuth, expiry + Sign out), **API key** (masked key, Edit/Remove), **Environment** (`ambient`, or a non-`stored` `source` — badge + the `envVar` name, no Remove), and **Custom endpoint** (health pill, Test/Edit/Remove). Empty state when nothing is configured.
- **`ProviderAuthStatus` gains `configured` and `source`**, and the list filters on `configured` rather than `authenticated`. The derivation is **kind-aware and is the single most load-bearing detail of this change** (design.md carries the full table): an OAuth row derives it from its own credential; a plain api-key row from `hasStoredKey || ambient || source === "environment"`; and an **`-api` twin excludes exactly one piece of evidence: the catalogue entry's `source: "stored"`**, which describes the *sibling's OAuth credential* rather than a key. It MUST still honour `environment` / `runtime` / `models_json_*` evidence — `anthropic` and `github-copilot` both have env-var keys (`env-api-keys.js:88-93`) and the twin is their ONLY api-key row, so a blanket "own stored key only" rule would re-hide exactly the env-var credential this change exists to surface. Both failure directions are real: inherit too much and a keyless twin enters the connected list where Remove deletes the OAuth credential; inherit too little and a working key goes invisible. `source` is the pi-ai six-member union (`"stored" | "runtime" | "environment" | "fallback" | "models_json_key" | "models_json_command"`, `provider-composer.d.ts:44`); `packages/shared/src/types.ts:806` currently declares only four and must be widened. `authenticated` keeps its current meaning for existing consumers; `useProvidersReady` deliberately stays on `authenticated` (its under-count of env-var providers is pre-existing and out of scope).
- **One `+ Add provider` entry point** replaces the 35 inert rows and the separate "add custom provider" affordance. It opens a dialog: a searchable picker over the **unconfigured** providers plus a pinned "Custom endpoint…" entry, then a pane branching on `flowType` — `auth_code` (browser OAuth), `device_code` (user code + GitHub Enterprise domain prompt + the spec'd explicit "Open Registration Page" action), `api_key` (key field + env-var hint), or custom endpoint (name / baseUrl / api / key + Test). Already-configured providers are absent from the picker; they are managed from their row.
- **The `-api` clobber is closed at the API, not only in the UI.** UI rules alone are not an invariant: `PUT /api/provider-auth/api-key` with `provider: "anthropic-api"` still resolves to `anthropic` and blind-overwrites (`provider-auth-routes.ts:231-233` → `provider-auth-storage.ts:251`), and the **inverse** direction is equally live — completing an OAuth sign-in over a stored api_key destroys the key. The write path therefore refuses (or explicitly confirms) a write that would replace a credential of a *different type* under the same auth.json key. **Removal carries the same hole and the same fix**: `DELETE /api/provider-auth/anthropic-api` resolves to `anthropic` (`provider-auth-routes.ts:250` → `resolveAuthJsonKey`) and removes whatever is stored there, so deleting the api-key row silently revokes the subscription login — the removal is refused on the same kind-mismatch rule. Every refusal carries a stable machine `code`, per `ui-i18n-coverage`'s "Server and extension emit translation codes, not display English". The UI rules — picker suppression while the sibling is connected, and list membership only on the row's own evidence — sit on top of that guard, not instead of it.
- **New `PATCH /api/providers/:name` and `DELETE /api/providers/:name`.** `PUT /api/providers` has **replace** semantics — `merged` is built only from the request body (`provider-routes.ts:148`) and assigned wholesale (`:169`) — so a per-row write carrying one provider would delete the rest of `providers.json`. Single-provider endpoints give the dialog and the row correct semantics without a client-side read-modify-write that two concurrent writers would lose-update. `PUT` is retained unchanged for any remaining full-set caller. The new endpoints inherit **every** existing `PUT` invariant: masked-sentinel guard, blank-name guard (server-side, retained — dialog validation is additive, not a replacement), the `RECURSIVE_PROXY` self-pointing guard (`:116-131`), atomic tmp+rename, `credentials_updated` broadcast, and `refreshModelRegistry()` (`:188`). Health-cache handling is **not** inherited verbatim: `retainProviderHealth(names)` prunes every key outside the set (`provider-health-cache.ts:36-41`), so PATCH must pass the full key list and DELETE must drop only its own entry. **`PATCH` must upsert** (create-if-absent) or the Add dialog cannot add a custom endpoint at all. The blank-name guard cannot be inherited as-is: `PUT`'s guard iterates body keys, while `PATCH`/`DELETE` take the name from the URL, so `/api/providers/%20` needs its own rejection, alongside an explicit encoding rule (`providers.json` keys may contain `/`). Route registration: `ROUTE_TIERS` entries alone are insufficient — `mcp-manifest-completeness.test.ts` requires every `/api/*` path to be manifest-bound or denylisted, and `tools.manifest.ts` binds `/api/providers` exactly, so `/api/providers/:name` needs a manifest row or a denylist entry. (The runtime gate does **not** reject an unlisted route — `routeTier()` falls back to `operate`; the test is the enforcement.)
- **Custom LLM providers leave the Settings Save-bar draft model.** The dialog and the row commit on their own action via the new endpoints. What this does **not** change: the `providers` page keeps its dirty chip and the panel-level `beforeunload` guard, because `CONFIG_FIELD_PAGE.modelProxy = "providers"` (`SettingsPanel.tsx:298`) also files the API-Proxy section on that page. What must be **preserved, not inherited**: the `PROVIDER_AUTH_EVENT` dispatch, `refetchCatalogue()`, and the post-write health refetch currently living in the removed save task (`SettingsPanel.tsx:963-995`) move onto the new write paths. Blank-name rejection moves from save-time to dialog-time validation; the per-source Save-bar Retry affordance is replaced by per-write inline errors.
- **Badges carry the provider kind as a WORD, not a hue.** An audit run while designing this change found the `--accent-*` ramp fails the 4.5:1 text floor on its own surfaces in **80 of 108 palette×hue combinations (17 of 18 palettes)** — including `baseDark`, the default. Colour-coding the badges would be correct on 2 palettes and wrong on 16, so kind is carried by the label and WCAG 1.4.1 is satisfied by construction. The ramp remediation is its own change: **`remediate-accent-text-contrast`**. This change does not depend on it; adopting colour here is a later, additive follow-up.
- **One scoped token is still added:** `--accent-primary-strong: #2563eb` in `packages/client/src/index.css`. White on `--accent-primary` (`#3b82f6`) is 3.68:1, under the text floor, and the shipped component already sidesteps it with the Tailwind class `bg-blue-600` (`#2563eb`, 5.17:1) — the token names what the code does. Verified scoped: **no palette in `themes.ts` overrides `--accent-primary`**, so this is a 2-value addition (root + light), not an 18-palette one.
- **Behaviour explicitly removed, not overlooked:**
  - `provider-auth-ui` "OAuth providers without server handler render disabled" — deleted; already dead in practice, since OAuth rows are built from `getAllHandlers()`, the same source as `GET /api/provider-auth/handlers`. `provider-auth-server` carries the matching cross-spec mandate (*"The UI SHALL render disabled-with-tooltip rows for those gaps"*), which must be deleted with it or the two specs contradict. Whether `GET /api/provider-auth/handlers` and the client's `fetchHandlerIds`/`supported` gating survive at all is decided in design.md, not left implicit.
  - `provider-auth-ui` "Render unauthenticated OAuth provider" scenario, and the base requirement's **per-row key text input** — both replaced by the dialog.
  - `anthropic-peer-hint` "Signed-out anthropic row" — the *only* scenario of its "Hint gated on the authenticated state" requirement; the requirement needs a replacement scenario, not just a deletion.
  - `provider-connection-test` health-pill fallback "…or discards the edit" — loses its Discard half. Separately, its "**Each** provider row … SHALL render a health pill" quantifier narrows: after unification most rows are OAuth/api-key/environment rows that have no cached health and would read "not tested" forever, so the requirement must be re-scoped to custom-endpoint rows.
  - `settings-panel`'s page-section enumeration ("Provider Authentication, LLM Providers, API Proxy") — the LLM Providers section ceases to exist under that name.

## Capabilities

### New Capabilities
- `provider-add-flow`: the Add-provider dialog — picker over unconfigured providers, per-`flowType` panes, `-api` twin suppression, validation before write, and the abandoned-dialog contract (a flow completing after the dialog closes must still refresh the list, never write silently).
- `custom-provider-crud`: single-provider `PATCH`/`DELETE` semantics for `providers.json` — partial update, masked-sentinel preserve, blank-name rejection, health-cache retention for untouched providers, and the `credentials_updated` broadcast.

### Modified Capabilities
- `provider-auth-ui`: the section lists only providers holding a credential instead of the whole catalogue; four credential kinds render as one badged list; login and key-entry move out of the rows into the Add dialog; the handler-less-OAuth disabled-row requirement is removed.
- `provider-auth-server`: `GET /api/provider-auth/status` rows gain `configured` and `source`; the handler-ids requirement's UI mandate (disabled-with-tooltip rows) is removed, and its false claim that a handler-less catalogue id emits an OAuth row is corrected to the api-key row the code actually emits (`_buildAuthStatus` builds OAuth rows from the handler registry only); **both** `credentials_updated` trigger lists — "Bridge notification on credential change" and "Credentials updated triggers per-session model refresh" — gain the new `PATCH`/`DELETE`; a new `GET /api/provider-auth/catalogue-ready` carries the catalogue-availability signal; the credential-removal path gains the same cross-type refusal as the write path.
- `model-refresh`: its requirement is anchored to `PUT /api/providers` via "Settings → LLM Providers" and must cover the per-write endpoints.
- `provider-connection-test` also carries "Provider health is probed on save and cached", whose requirement text and scenario name `PUT /api/providers` explicitly — both must cover `PATCH`.

*(Deliberately NOT listed: `custom-provider-model-registry` — its discovery trigger is event-based ("when a provider is added/edited/removed"), not endpoint-anchored, so its requirements are unchanged.)*
- `settings-panel`: LLM providers are no longer a Save-bar draft source; blank-name rejection moves to the dialog. The page's dirty chip and the panel-level navigation guard are unaffected (the `modelProxy` config source still files there).
- `provider-connection-test`: the Test affordance moves to the custom-endpoint pane and the row's Edit state; the pill's "discards the edit" fallback is removed with the draft model.
- `landing-page-onboarding`: the `provider-auth-event` requirement names "the custom-LLM-provider save (which has replace semantics…)" and anchors scenarios to a dirty list plus a submitted save; those become per-write `PATCH`/`DELETE` dispatches.
- `provider-auth-bridge`: the "Provider with env var set but no auth.json entry" scenario asserts `configured: false`, contradicting pi-ai's actual `configured: true, source: "environment"` — this change depends on the field's meaning, so the drift is reconciled here. The `custom`-flag prose naming the "**LLM Providers** settings section" is a **rewording**, not a removal: the `_buildAuthStatus` `custom` skip is still required, since custom-endpoint rows come from `/api/providers`.
- `anthropic-peer-hint`: the hint's gating requirement keeps its meaning, but its signed-out scenario is no longer reachable through the UI.

## Impact

- **Server:** `provider-auth-storage.ts::_buildAuthStatus` (kind-aware `configured`/`source`) and `writeCredential` (cross-type overwrite guard), `packages/shared/src/rest-api.ts` (`ProviderAuthStatus`) and `packages/shared/src/types.ts` (widen `ProviderInfo.source` to six members), `provider-routes.ts` (new `PATCH`/`DELETE` reusing the sentinel guard, recursion guard, atomic tmp+rename, `refreshModelRegistry`, broadcast; `retainProviderHealth` called with the FULL key list on PATCH and a targeted drop on DELETE), plus `route-tiers.ts` and the MCP manifest/denylist. Response shapes are additive, so an older client keeps working against the new server.
- **Latency:** `PUT` currently **awaits** a live upstream probe per provider (8 s timeout each) before responding (`provider-routes.ts:194`). Under per-edit writes that cost lands on every single edit, so the new endpoints probe **only the touched provider**, and the row renders an optimistic pending state rather than blocking on the probe.
- **Client:** `ProviderAuthSection.tsx` (622 lines) restructured into connected-list + dialog. Invariants that MUST survive relocation: the `handleChanged` single-funnel for `PROVIDER_AUTH_EVENT` (never dispatched from `refresh`), the 3-consecutive-failure auth-code poll abort, the `AnthropicPeerHint` post-install latch, and the inline status-error-with-Retry that must never reach an ErrorBoundary. `SettingsPanel.tsx`: the providers tab body, `LlmProviderCard`, and the LLM-providers draft source and its baseline wiring.
- **Failure modes to spec, not discover:**
  - The unified list merges two fetches (`/api/provider-auth/status` and `/api/providers`). A failure of the former must NOT hide custom-endpoint rows — `provider-auth-ui` already requires the section stay interactive "so the operator can still reach the controls that repair credentials".
  - **Empty catalogue is not an empty state.** API-key rows exist only inside the catalogue loop, and `getLatestCatalogue()` returns `[]` with no connected pi session. A user with keys in `auth.json` would then be told "nothing configured" — a regression the old catalogue-shaped list could not produce. The section MUST distinguish *no catalogue* from *no credentials*; note the distinction is **not** derivable client-side from the current response, because `GET /api/provider-auth/status` returns a bare array whose shape `provider-auth-ui` pins (a non-array is an error). Carrying the signal therefore touches that contract — design.md decides how.
  - **Dialog lifecycle.** The auth-code/device-code poll MUST remain owned by the section, not the dialog: closing the dialog must not kill an in-flight flow, and a flow completing after close must still refresh the list. Note `landing-page-onboarding` currently *excludes* "writes that complete server-side after the initiating component unmounts" from its dispatch contract — that bound has to widen, or the abandoned-dialog case is spec-silent.
  - **Dispatch sites.** There are **two** `PROVIDER_AUTH_EVENT` dispatch sites today (`ProviderAuthSection.tsx:136` and the LLM-save task at `SettingsPanel.tsx:966`); `handleChanged` is the single funnel only for the auth section. The target invariant is that the redesign does not *increase* that count: the custom-endpoint write paths route through one funnel, not one per control.
  - **Duplicate row identity.** `_buildAuthStatus` skips api-key rows for `custom` ids but still emits OAuth rows for them, so a `providers.json` key equal to a handler id (`anthropic`) yields two rows with the same `id` in the unified list. Precedence must be defined, not discovered.
  - **Custom endpoint with an empty `apiKey`** is accepted by the server today; "configured" must be defined for it rather than left to the filter's accident.
  - **Server-side lost update.** `providers.json` has no lockfile (unlike `auth.json`). PATCH/DELETE must complete read→write with no `await` between them, probing only after the write.
- **Tests to rewrite, not adjust:** `ProviderAuthSection.test.tsx`, `ProviderAuthSection.peer-hint.test.tsx`, `ProviderAuthSection.corrupt-status.test.tsx`, `ProviderAuthSection.poll-budget.test.tsx`, `LlmProviderCard*.test.tsx`, `useProvidersReady.test.ts`, `SettingsPanel.test.tsx`, `settings-persistence.test.tsx`.
- **Conventions the new dialog must satisfy:** the repo's dialog-portal / modal-escape-dismiss / overlay-layering specs, and full i18n key coverage for every new string.
- **Mockups** under `openspec/changes/redesign-providers-settings-page/mockups/` — `index.html` (4 list states), `add-dialog.html` (5 panes), `ui-plan.md` (cited UX rules + the contrast matrix). Accessibility floor: **21/21 pass in both themes**, computed from the tokens, not eyeballed.
- **Theme layer:** `packages/client/src/index.css` gains `--accent-primary-strong` (root + light). `themes.ts`↔`index.css` parity and the `theme-system` skill doc are the closeout surface.
- **Rollback is not a pure client revert.** The client is revertible, but writes the new UI already made persist in `auth.json` / `providers.json`, and the added server endpoints plus the two new `ProviderAuthStatus` fields are additive and safe to leave in place. Reverting the client alone is therefore correct but not state-restoring.
