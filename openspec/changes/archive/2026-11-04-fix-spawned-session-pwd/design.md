## Goals / Non-Goals

Goals: dashboard-spawned pi (and descendants) see `PWD` naming the spawn cwd on every strategy; one choke point for sessions (`buildSpawnEnv`); the worktree agent hook covered; keeper respawns covered.

Non-Goals: changing context-mode (issue's optional upstream hardening); setting context-mode-specific vars; healing keepers already running; PTY/ACP-local paths; worktree gate/script hooks (`bash -c`, already correct); guaranteeing `wt.exe` env propagation (pre-existing exposure); a caller-supplied hook `opts.env` (used as given, per heap-limits).

## Decisions

**D1 — Set `PWD` in `buildSpawnEnv` via a new optional `cwd` option, as part of the host's own shaping.**
It is the single function every pi-session spawn mechanism already routes through (same rationale as the spawn-token injection, spec "injected via buildSpawnEnv … applies to every spawn mechanism"). The assignment sits with the host's fixed shaping (:359-433, next to the spawn-token injection), i.e. step 1 of the `plugin-spawn-env-contributor` build order, before contributors (:435). Absent `cwd` ⇒ env byte-identical (matches the file's convention for `argv0`, `mechanism`). The keeper inherits it as its own env and forwards it to pi, including on respawn.
All five call sites pass `cwd`, including tmux/wsl-tmux where the pane gets `PWD` from tmux anyway: the rule "every env this function builds carries `PWD`" stays uniform and testable at the env sink (the `execFileSync`/`spawnDetached` mocks), and costs nothing (verified: tmux's global `PWD` is the client's real cwd, not the env value).
Alternatives: (a) `env.PWD = process.cwd()` in `keeper-env.cjs` (the issue's proposal) — covers only the keeper path, leaves `wt` and any future mechanism; (b) set in `spawnKeeperFor` — same keeper-only coverage; (c) set in `spawnDetached` — wider blast radius (server/CLI launches). Chosen D1 because the invariant "child env describes the child's cwd" belongs where the env is built, not where it is consumed.

**D1b — `PWD` is a host-owned name: add it to the contributor deny list.** `DENY_EXACT` (`spawn-env-contributors.ts:35`) gains `"PWD"`. `isContributableName` (:84-86) gates both `collect` (:116, rejected with a warning at :130) and `removeSuperseded` (:105-110, a supersede marker cannot delete it), so no trusted plugin can add, replace or strip `PWD`, and it never enters `applied`/`contributedOut` → tmux never gets `-e PWD=` (`buildTmuxCommand` :657-658). Same treatment as `PATH`/`HOME`/`SHELL` (host-shaped, process-identity names). Alternative (rejected): set `PWD` as the last step and prune `opts.contributedOut.PWD` — works, but silently discards an "applied" contribution and extends the contributor build order with an unspecified step 5. Spec: MODIFIED `plugin-spawn-env-contributor` reject list.

**D2 — `PWD` only; do not set `PI_PROJECT_DIR`/`PI_WORKSPACE_DIR`/`CONTEXT_MODE_PROJECT_DIR`.**
Those are context-mode-private names (nothing in this repo reads them outside the context-mode-settings plugin descriptors); setting them would couple the host to one extension's resolution order and would silently override a user's own value (they outrank `PWD` in the cascade). `PWD` is the POSIX-defined variable, fixes every PWD-reading tool, and restores an invariant no shell would break. context-mode's `PWD` step then resolves correctly with no knowledge of it.

**D2b — Worktree agent hook: `runAgent` spawns with `opts.env ?? { ...defaultHookEnv(), PWD: <D4 value of cwd> }`.** Only the agent flavor execs pi without a shell. The gate and script hooks are left byte-identical: setting `PWD` there would be an unspecified behaviour change (bash keeps an inherited `PWD` that names the same directory, so their `$PWD`/`pwd` spelling could change). An explicit caller `opts.env` stays untouched (heap-limits). Alternative: `defaultHookEnv(cwd)` for all three children — rejected for that gate/script side effect.

**D3 — Leave tmux / pty / ACP-local paths alone.** Each is tmux/shell-mediated (tmux sets `PWD` from `-c` itself and runs the pane command through a shell, verified above; PTY is the user's shell) or allowlisted (ACP). No `-e PWD=` is added to `buildTmuxCommand` — redundant with tmux's own behaviour. Consequence for tests: the tmux pane observation passes at HEAD and serves only as a regression guard; the fails-at-HEAD proof for tmux/wsl-tmux is the env handed to `execFileSync`. The wsl-tmux pane's `PWD` depends on tmux inside WSL (same `-c` behaviour, not verified there); covered at the env sink only.

**D4 — Value is `normalizeCwdKey(path.resolve(cwd))`: the canonical physical path, falling back to the absolute lexical form.** Reuse `normalizeCwdKey` (`spawn-process/spawn-register-watchdog.ts:42-56`: `realpathSync`, raw string on ANY error, never throws). Repo precedent for exactly this alias class: the register watchdog missed `/tmp/x` vs `/private/tmp/x` until it normalised (`openspec/specs/spawn-register-watchdog/spec.md:120`). With it, `PWD` equals what the child's `getcwd()`/`process.cwd()` reports and what the bridge reports as the session cwd (`extension/src/session-sync.ts:156-162`) — one key per directory for context-mode, whatever spelling (`/tmp/x`, trailing slash, relative, symlink) the caller sent. `path.resolve` first makes a relative cwd (possible via the POST body) absolute against the server cwd — the same base the child's relative `cwd` uses — so the fallback is still absolute. Cost: one `realpathSync` per spawn (spawns are rare, user-initiated). Caveats, accepted: tmux panes keep tmux's own `-c`-derived spelling (a symlinked `-c` gives a logical pane `PWD`); for `wsl-tmux` on a Windows host the value lives only in the Windows-side env handed to `wsl.exe` and does not cross into Linux without `WSLENV` (inert). An empty `cwd` (`""`) is treated as absent (`if (opts.cwd)` semantics): `path.resolve("")` would re-stamp the server's cwd, the very stale value this fix removes; the spawn funnel rejects `""` upstream anyway (`existsSync`). Alternative: plain `path.resolve` (lexical) — rejected: a symlinked/aliased spelling would file one project under two context-mode keys, the issue's own failure class.

## Risks / Trade-offs

- Already-running keepers keep stale `PWD` (env fixed at exec). Mitigation: none needed; next spawn/restart of the session fixes it. Noted in release notes only.
- A user who deliberately exports a custom `PWD` to the server loses it for spawned sessions. Acceptable: a non-shell-consistent `PWD` is the defect; `PWD` is not a configuration knob.
- A trusted plugin that contributed `PWD` (none known) now gets a rejection warning instead of a value. Acceptable: host-owned name, same as `PATH`.
- `wt`: the env carries `PWD`, but pi sees it only if `wt.exe` propagates the spawn env (pre-existing exposure, same as the bridge stamp and spawn token). Covered at the env sink only; not testable off Windows; accepted. Practical reach is small: `PWD` exists on Windows only when the server was started from Git Bash (assumption: Windows shells other than MSYS/Cygwin do not export `PWD`; not verified on a Windows host).
- Physical `PWD` (D4): a user who reaches a project through a symlink sees the physical path in spawned sessions, not the logical one their shell would show. Accepted: it matches the dashboard's own session cwd.
- An operator who exports `PI_WORKSPACE_DIR` or `PI_PROJECT_DIR` to the server outranks `PWD` in the context-mode cascade, so every spawned session still resolves to that value. That is the operator's explicit override (D2: the host never sets or clears those names). Accepted.
- Caller-supplied hook `opts.env` keeps its own `PWD` (D2b, heap-limits "Explicit caller environment is respected"). Production never passes it (sole caller `routes/git-routes.ts:673`), so the scenario pins a test-only seam; kept deliberately so the `opts.env` contract stays uniform rather than special-casing one variable. Accepted.
- `PWD` on Windows / `wsl-tmux` (D4): where the server has no `PWD` (anything but Git Bash) the rewrite creates a new variable, and for `wsl-tmux` on a Windows host its value is a Windows-form path in the env handed to `wsl.exe` (inert without `WSLENV`). Kept for uniformity ("every env this function builds carries `PWD`", D1) over a per-strategy carve-out; harmless but not meaningful there. Accepted.
- Normative scope: the spec binds only the env the dashboard hands to the spawn mechanism. What tmux sets in the pane and what `wt.exe` propagates are third-party behaviours, recorded here (D3, `wt` above), not required by the specs.
- Windows key casing: the env is a plain-object copy, so a base env carrying a differently-cased `Pwd` would sit next to the new `PWD`. Git Bash exports `PWD`; no other source is known. Accepted, not handled.
