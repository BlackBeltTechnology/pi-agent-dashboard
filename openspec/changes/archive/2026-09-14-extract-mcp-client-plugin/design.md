## Context

See proposal.md — Why. Facts that shape the approach:

- `packages/apple-tools/src/mcp-config.ts` is a self-contained writer (`ConfigIO` injection, `ensureMcpEntry`, `readImcpEntry`, `setServerDisabled`, `setDirectTools`) with its own discovery walk. It is only Apple-specific by the literal `"iMCP"` name and by living in that package.
- `pi-mcp-adapter` (workspace 2.30.0; user install 2.31.0 — both export the same `./config` surface) exports `loadMcpConfig(overridePath?, cwd = process.cwd())`, `getConfigDiscoveryPaths(overridePath?, cwd = process.cwd())`, `getServerProvenance(overridePath?, cwd)` → `Map<name, {path, kind: "user"|"project"|"import", importKind?}>`, `writeProjectServerDisabledOverride`, `writeDirectToolsConfig`, path helpers `getPiGlobalConfigPath` / `getProjectPiConfigPath`. Types live under `./types`. No JSON Schema is shipped. Adapter facts the plugin must match: files are parsed as JSONC (`strip-json-comments`, trailing commas); `mcpServers` has an alias `mcp-servers` which `writeProjectServerDisabledOverride` **preserves** (writes back to whichever key exists); global settings nest under a top-level `settings` object; `loadMcpConfig` additionally merges `imports`, then agent-plugin configs, then `package.json#mcp` (precedence: files > agent plugins > package) — sources `getServerProvenance` does not list; **`getServerProvenance.path` is the adapter's *write* target, not the defining file** — every shared/global layer and every import reports `path === getPiGlobalConfigPath()` with `kind: "import"`, and `<cwd>/.mcp.json` (shared) and `<cwd>/.pi/mcp.json` (Pi) both report `kind: "project"` — so neither `kind` nor `path` alone distinguishes layers; `kind` plus equality with the two Pi-owned paths does; `overridePath` *replaces* the Pi-global file in discovery; on **enable** the adapter deletes `disabled` and writes an explicit `disabled: false` only when the merge of every lower-precedence source (including imports and host discovery) disables the server; `writeDirectToolsConfig` materialises full merged entries — credentials included — into the Pi layer.
- No cwd argument means "the dashboard server's cwd", so a naive global read would merge the server process's own project files.
- `apple-tools` already lists `pi-mcp-adapter: ^2.19.0` as a runtime dependency, so importing `pi-mcp-adapter/config` from a dashboard plugin has precedent; the dashboard resolves the workspace copy, not the user's `~/.pi/agent/npm` install. Version verdicts must probe the *user's* install (what pi sessions actually run), which `mcp-server-plugin/provisioning.ts` `probeAdapterVersion` already does against an injected version string; its one caller is `mcp-server-plugin/src/server/index.ts` L187, a registration-time `logger.warn` when below floor.
- `apple-tools/install.ts` also uses two `mcp-config.ts` exports that are not `mcp.json` writes: `ensureAdapterPackage` (adds `npm:pi-mcp-adapter` to `~/.pi/agent/settings.json#packages`) and `validateConfigShape` (check-mode parse status of `mcp.json` and `settings.json`).
- `dependsOn` + `missingDeps` + cascade toggle exist in the loader (`dashboard-plugin-loader` spec L900-964) with no first-party consumer. `ctx.provide`/`ctx.consume` exist with ordering guaranteed by `dependsOn`.
- cwd admission for folder-scoped writes already has a canonical implementation: `kb-plugin/src/server/kb-routes.ts` `isAllowedCwd(cwd, known)` + `canonPath`, specified by `kb-plugin-cwd-guard` — but it is module-local (kb-plugin exports only `registerPlugin`), and the only other copy in the tree (`apple-tools/src/server/index.ts` L68) is a bare `includes` with no canonicalisation. This change extracts the whole admission module — `isAllowedCwd`, `canonPath`, `mainCheckoutPath` and its git checkout-root probes (`checkoutRoots`/`isBoundCheckout`) — into `@blackbelt-technology/pi-dashboard-shared` (`cwd-guard.ts`) and points kb-plugin at it; mcp-client imports the same function, so worktree cwds whose main checkout is known are admitted for both. No behaviour change for kb.
- Bundling: Vite discovers plugins from the workspace; only `packages/electron/scripts/bundle-server.mjs` `BUNDLED_PLUGINS` is a hand-maintained list (test-enforced).
- Mockups + UX review live in `mockups/`; findings D1–D5 are already folded into the specs.

## Goals / Non-Goals

**Goals:**
- One owner for adapter configuration and the adapter floor; `apple-tools` and `mcp-server-plugin` become consumers.
- Zero re-implementation of layer discovery/precedence: read path calls the adapter.
- Prove the `dependsOn` + provide/consume contracts with a first-party pair and tests.
- Ship the S1–S5 surfaces from `mockups/ui-plan.md` with the accepted slot decision (S4 = `worktree-card-section` `SlotPill` twin of kb).

**Non-Goals:**
- Editing shared/host layers, OAuth flows, search/bulk operations on large server lists (N1), a generated schema pipeline, a host-titled WORKSPACE subcard wrapper.

## Decisions

### D1. Read via `pi-mcp-adapter/config`, write via our own merge-only writer that matches the adapter's parser

**Reads.** Folder view: `loadMcpConfig(undefined, cwd)` + `getServerProvenance(undefined, cwd)`. Global view: the same calls with `cwd` = a dedicated, always-empty scratch directory created once per process with `fs.mkdtempSync(path.join(os.tmpdir(), "pi-mcp-client-"))` — under the OS temp root, so the adapter's ancestor walk (`findProjectRoot` looks for `.git` / `package.json` / project config upward) finds nothing, and nothing under the dashboard server's own cwd is read. Layer parse errors are detected by re-parsing each `getConfigDiscoveryPaths` entry with the same JSONC parser the writer uses, so "unparseable" means the same thing to the adapter, the reader, and the writer. **Secret redaction happens server-side**: in the effective payload, any `x-secret` (or credential-named) field whose value is *not* defined in the requested scope's writable Pi-owned layer is replaced by a marker — `{ redacted: true }` for scalars, `{ redacted: true, keys: [{ name, secret }] }` for record fields (key names only, never values; `secret` per key from the credential-name pattern, applied server-side) — so the client never receives an inherited credential yet can state "N inherited keys incl. K secrets" on override. Masking is therefore not merely presentational.

**Writes.** A plugin-owned `ConfigIO`-injected merge-only patch writer lifted from `mcp-config.ts` and generalised over server name and scope, corrected to the adapter's file conventions: parse with `strip-json-comments` (trailing commas on); read `mcpServers ?? "mcp-servers"` and write back to **whichever key already exists** (default `mcpServers` for a new file), exactly as `writeProjectServerDisabledOverride` does — never both; a non-object existing entry is refused, not coerced (current `mcp-config.ts` rule, kept); settings live under the top-level `settings` object. **All writes, both scopes, go through the plugin's own writer** — the adapter's `writeProjectServerDisabledOverride` is *not* delegated to, because it commits with a predictable `<file>.<pid>.tmp`, default umask and no `fsync` (`config.js` `writeRawConfigObject`), which would regress the `wx` + `0o600` + `fsync` hardening `apple-tools/env.ts` applies today; that hardened `ConfigIO` moves into `mcp-client` unchanged. The writer builds entries as null-prototype objects and iterates with `Object.hasOwn`, so parsed keys can never hit the prototype setter.

The adapter's **enable rule** is satisfied by letting the adapter decide, not by reproducing its lower-merge: on enable, (1) delete `disabled` from the target layer entry and write; (2) re-run the adapter's full effective merge for the scope (`loadMcpConfig(undefined, cwd)` for project, `loadMcpConfig(undefined, scratchCwd)` for global); (3) if the server is still disabled there, write `disabled: false` into the target layer entry. Because step 2 is the same merge a pi session performs — every file layer, `imports` declared in any file including the target itself, host discovery, agent plugins, `package.json#mcp` — the outcome is "the server is enabled in pi's view" for every case, with no lower-merge re-implementation and no scratch override file. (The adapter's own writer consults file sources + the target's `imports` only, so it can leave a server disabled by an agent-plugin or package source; ours writes `false` there — a strict superset of the adapter's behaviour, and what the spec mandates.) Cost: at most two atomic writes; the intermediate state (key removed, server still disabled by a lower source) is what pi would observe for microseconds and is identical to what the adapter's own writer transiently produces. If step 1 leaves the layer entry with zero fields, the entry is deleted (as the adapter does) so no empty override chip appears. Disable is a single write of `disabled: true`.

**Record fields are layer-atomic.** The adapter merges entries with a shallow spread (`{...base, ...definition}`), so `env`, `headers`, `searchKeywords` and similar records defined in a Pi-owned layer *replace* the inherited record wholesale — there is no per-key merge across layers and the plugin cannot invent one. Consequently a patch may `set` a whole record only; and because inherited secret values are redacted (never sent to the client), they cannot be carried into the override. The editor therefore treats "override an inherited record" as an explicit action with a consequence note ("replaces N inherited keys at this layer, including K secrets, which will no longer apply") and starts the override record empty rather than pre-filled. This applies to **every object-valued field** the adapter spreads atomically — `env`, `headers`, `searchKeywords`, `oauth`, `requestHeadersCommand` — not just the two obvious ones; the schema marks them `x-atomic` so the editor derives the list rather than hard-coding it. `setDirectTools` is written by this writer as a plain field patch; it MUST NOT delegate to the adapter's `writeDirectToolsConfig`, which copies full merged entries including credentials into the Pi layer. Comments in a JSONC file do not survive a write (same as the adapter's own writer) — accepted.

Why: the adapter's writers are unhardened (project `disabled`) or credential-copying (direct-tools); we need global scope, arbitrary fields, settings, removal, hardened atomic IO, and the `ConfigIO` seam the existing tests exercise. Reusing the adapter for every *read* (including the lower merge that drives the enable rule) removes drift; keeping our writer keeps atomicity, permissions and unparseable-refusal under test control.

Alternative rejected: re-implementing discovery (status quo) — drift is the bug being fixed. Alternative rejected: patching the adapter to add a general writer — cross-repo, blocks the change.

### D2. Provenance comes from `getServerProvenance`, classified by `kind` + Pi-path equality

For each server in the effective view: look it up in `getServerProvenance`. `kind: "user"` → **Pi global**; `kind: "project"` **and** `path === getProjectPiConfigPath(cwd)` → **Pi folder**; `kind: "project"` with any other path (i.e. `<cwd>/.mcp.json`) → **Shared**, labelled by its path; `kind: "import"` → **Shared**, labelled by `importKind` (e.g. "global MCP config", ".agents MCP config", "cursor") — for imports `path` is the adapter's write target (`~/.pi/agent/mcp.json`), not the defining file, so it is never used as a label. Only Pi global and Pi folder are writable. A server present in `loadMcpConfig` but absent from the provenance map came from `package.json#mcp` or an agent plugin → **Other** (read-only, no file to edit; the row names the source kind). Lower defining layers are listed by re-parsing the discovered paths (needed anyway for parse-error reporting). Field-level "inherited" hints on the folder page need no merge replication: a field is inherited iff the folder-layer entry does not define it, and its shown value is the adapter's effective value (redacted if secret, per D1).

### D3. Adapter verdict probes the user's install, not the workspace

`probeAdapterVersion` + `ADAPTER_VERSION_FLOOR` + `readInstalledAdapterVersion` (which checks both `~/.pi/agent/npm/node_modules/` and `~/.pi/agent/node_modules/`) move from `mcp-server-plugin` to `mcp-client`, and the result type is replaced by `AdapterVerdict = { kind: "ok" | "absent" | "below-floor" | "unparseable" | "unknown"; installed?: string; floor: string; message?: string }` so every surface can show installed + floor; `unknown` is produced only by consumers when the service is absent. `mcp-server-plugin`'s existing `probe.ok` checks become `verdict.kind === "ok"`. Known gap, unchanged from today: the plugins-index `requirements` check uses the package-manager wrapper's `listInstalled` (global ∪ local) while the probe reads the two well-known paths; a local-scope-only install can show "requirement met" on the index and `absent` here. Not widened in this change. The verdict is cached with a 30s TTL (re-probe on expiry; no hook wiring in v1). `mcp-server-plugin` deletes its copy and calls `ctx.consume("mcp-client.config")?.adapterVerdict() ?? { kind: "unknown" }` lazily. Its registration-time below-floor `logger.warn` cannot stay at registration (no `dependsOn` → no ordering guarantee), so it fires once on the first local-pi provisioning call instead. It does not declare `dependsOn`, so the MCP endpoint survives `mcp-client` being disabled. There is no other provisioning call site in `mcp-server-plugin` (`provisionDashboardEntry` runs only at registration), so "first local-pi call" concretely means the first request handled by the plugin's `/mcp` route — the path where a below-floor local adapter actually matters; the warning fires once there.

**`mcp-server-plugin` writes its dashboard entry through the same core.** Today `provisionDashboardEntry` has its own `JSON.parse` reader, a hard-coded `~/.pi/agent/mcp.json` path and an `mcpServers`-only writer — three ways to disagree with pi (comments, custom agent dir, alias key). Instead of patching each, it takes `@blackbelt-technology/pi-dashboard-mcp-client-plugin` as a *package* dependency (not a plugin `dependsOn`, so the endpoint still works with the plugin disabled) and calls `createMcpClientConfigService({ configIO }).ensureServerEntry("pi-dashboard", entry, { kind: "global" })` after a `readServerEntry` (file-only, Pi-global layer) check that the existing key, if any, is a dashboard HTTP entry (its current refuse-to-overwrite rule, same layer it reads today). Merge-only changes one thing on refresh: operator-added fields on the `pi-dashboard` entry (`disabled`, `headers`) now survive instead of being clobbered — the delta spec's refresh scenario is updated accordingly. Write-only path: no adapter loading functions, so no new boot-time reads.

### D4. Service contract `mcp-client.config`

```ts
interface McpClientConfigService {
  adapterVerdict(): AdapterVerdict;                           // kind ok | absent | below-floor | unparseable (+ installed, floor)
  readServerEntry(name: string, scope: Scope): ServerEntry | undefined; // raw entry from that scope's Pi-owned file only — no adapter loading
  ensureServerEntry(name: string, fields: Partial<ServerEntry>, scope: Scope): ConfigWriteResult; // merge-only
  setServerDisabled(name: string, disabled: boolean, scope: Scope): ConfigWriteResult;
  setDirectTools(name: string, tools: string[] | undefined, scope: Scope): ConfigWriteResult;
  ensureAdapterPackage(): ConfigWriteResult;                  // `npm:pi-mcp-adapter` in ~/.pi/agent/settings.json#packages
  checkConfigFiles(opts?: { serverName: string; fields: Partial<ServerEntry> }): { mcpJson: ParseStatus; settingsJson: ParseStatus; ensure?: ConfigRefusal | "ok" }; // global files only; write-suppressed; generic (parse, mcpServers object, packages array) + a dry run of ensureServerEntry(serverName, fields) over the post-patch entry, so a dependent's check mode predicts its write verdict exactly
}
type Scope = { kind: "global" } | { kind: "project"; cwd: string };
```

`ensureAdapterPackage` and `checkConfigFiles` are the two non-`mcp.json` exports `apple-tools/install.ts` still needs (`ensureAdapterPackage`, `validateConfigShape`); they are adapter-installation concerns, so they move here rather than staying in `apple-tools`. `validateConfigShape` today hard-codes `mcpServers.iMCP`; the generic version takes the server name as an argument so `apple-tools` passes `"iMCP"` and check mode refuses exactly what `ensureServerEntry("iMCP", …)` would refuse. To make that literally true, the check takes the same `fields` the write would set and runs the writer's own validation over the same post-patch entry (non-object existing entry, prototype name, >1 transport after the patch), and the writer's refusal reasons are a closed union `ConfigRefusal = "unparseable" | "entry-not-object" | "invalid-name" | "transport-conflict" | { kind: "write-failed"; code: string }` (the last from `ConfigIO.writeFileAtomic` throwing EACCES/ENOSPC/ENOENT, as today's `writeOrError`) that `apple-tools` maps onto its existing terminal states: `write-failed` → `CONFIG_WRITE_FAILED`, everything else → `CONFIG_UNPARSEABLE` with a specific message — the 9-member `TerminalState` enum is unchanged. `ensureAdapterPackage` keeps using `sourcesMatch` from `pi-dashboard-shared`. `project` scope runs the shared `isAllowedCwd` (from `pi-dashboard-shared/cwd-guard`) before any IO. All writers are synchronous (`ConfigIO.writeFileAtomic`).

**Construction.** The service is built by an exported factory, `createMcpClientConfigService({ configIO, knownCwds, adapter? })`, from the package's `./core` entry (no host or React imports). `adapter` is a port `{ loadMcpConfig, getServerProvenance, getConfigDiscoveryPaths, getPiGlobalConfigPath, getProjectPiConfigPath }` whose **loading functions are async** (`Promise<…>`) and take a `{ timeoutMs }` option; the default port runs the real `pi-mcp-adapter/config` loaders inside a worker thread (D10), test stubs are plain async functions. **All target paths come from the port's pure path helpers** — `getPiGlobalConfigPath()` for the global layer, `getProjectPiConfigPath(cwd)` for the folder layer, `dirname(getPiGlobalConfigPath())/settings.json` for the adapter-package write, and `dirname(getPiGlobalConfigPath())/{npm/,}node_modules/pi-mcp-adapter/package.json` for the version probe (D3) — so reads and writes resolve the same file under `PI_CODING_AGENT_DIR` / a custom config dir (the adapter honours both; a hard-coded `~/.pi/agent` would not, and today's `apple-tools/env.ts` `join(home, ".pi", "agent")` is replaced by this). There is no separate `piAgentHome` input. The port exists as an injection seam because the adapter's shared-global paths are module-level `homedir()` constants; unit tests inject a fake port (path helpers pointed at a temp dir), and one integration test runs the real module under `HOME=<tmp>` via dynamic import. **Write-only operations use only the port's pure path helpers and `ConfigIO`** — `ensureServerEntry`, `setDirectTools`, `ensureAdapterPackage`, `checkConfigFiles` and disable never call `loadMcpConfig` / `getServerProvenance`, so the hostless CLI installer still touches exactly the two files it does today. `readServerEntry` is likewise a file-only read of the scope's Pi-owned layer. Only the effective view and enable's post-write check go through the loading functions. `registerPlugin` calls it with the real `ConfigIO` and `host.knownFolderCwds`, then `ctx.provide`s the result before any route is registered. The hostless CLI `pi-apple-tools-install` (`apple-tools/src/bin/install.ts`) calls the same factory from `createInstallerEnv` with its existing `configIO` seam, the default adapter port (or a test port), and an empty `knownCwds` (global scope only). This keeps "no writer in `apple-tools`" true for the CLI path and preserves the injection seam `install.test.ts` / `env-atomic-write.test.ts` use today (those tests exercise write-only operations, which never reach the adapter port). `apple-tools` therefore declares `@blackbelt-technology/pi-dashboard-mcp-client-plugin` as a package dependency (for `./core`) in addition to the manifest `dependsOn`.

### D5. `apple-tools` consumes at registration and fails closed

`apple-tools` `registerPlugin` calls `ctx.consume<McpClientConfigService>("mcp-client.config")`; `undefined` is impossible under the loader's ordering guarantee, but if it happens the plugin throws a descriptive error at registration (fail closed) rather than constructing its own service via the factory — in the dashboard the provided instance is the single writer. The installer's `runInstaller` receives the service through `InstallerEnv` (dashboard: the consumed instance; CLI: the factory-built one), same pattern as the existing injectable probes.

### D6. Schema is hand-authored JSON Schema with `x-secret`

`packages/mcp-client-plugin/schema/mcp-config.schema.json` describes `ServerEntry` (all fields optional, three transports `command` / `url` / `socket`, grouped by transport via an `x-transport` annotation — **no `oneOf`**, because a layer entry is legitimately partial: a folder override may contain only `disabled: true`) and `McpSettings`, transcribed from `pi-mcp-adapter/dist/types.d.ts`. Secret fields carry `"x-secret": true` — enumerated from the adapter types, not guessed: `bearerToken`, `oauth.clientSecret`, `headers` (values), `env` (values), `requestHeadersCommand.env` (values); the credential-name regex on `headers`/`env` keys is an additional client-side heuristic, never the only guard. Transport exclusivity is validated on the **layer entry the write would leave in the target file** (current entry + patch): at most one of `command` / `url` / `socket` in that entry — checked in the writer, so every path including the service enforces it — and at least one when no lower-precedence source defines the server (i.e. the write would create it), which needs the adapter's merge — for the scope's cwd, or the scratch directory for global scope, never `process.cwd()` — and is therefore checked in the HTTP route layer only; service callers always pass a transport (`apple-tools` passes `command`). The adapter's own merge resolves cross-transport fields between layers, so the plugin never replicates `mergeServerMaps`. A compile-time test asserts key-set **equality** in both directions: every schema property exists in the workspace adapter's `ServerEntry`/`McpSettings` types *and* every key of those types appears in the schema (`satisfies Record<keyof ServerEntry, unknown>` over the schema's property map plus the reverse union check), so both a typo and an omission fail CI — following the fail-closed spelling from the `verify-compile-time-assertions-fail-closed` skill, not the vacuous `const _x: T[] = []` form. Trade-off: the check runs against the *workspace* adapter version; a user whose installed adapter is newer gets no editor coverage for fields added since — reads and writes still preserve them (unknown-field rule). Served at `GET /schema`; the client renders from it via a small field-renderer (string / number / boolean / string[] / record / enum / `boolean | string[]` union as toggle-with-list / nested object as a group), with a validated JSON-editor fallback for any shape it has no widget for (`outputGuard: boolean | object`, `trace`), reusing host form primitives. The key-set check covers names only; a type-coverage test asserts every `ServerEntry`/`McpSettings` field resolves to a concrete widget or the fallback.

Alternative rejected: ts-json-schema-generator at build time — new dev dependency and build step for a type that changes rarely; revisit if the adapter starts shipping a schema.

### D7. HTTP surface shape

Plugin routes under the plugin prefix: `GET /effective?cwd=`, `GET /schema`, `GET /adapter`, `PUT /servers/:name` (body: `{scope, set: Partial<ServerEntry>, unset?: string[]}` — a **patch**, never a whole entry, so an override can only ever write the fields the operator changed and the client has no full-entry copy path), `DELETE /servers/:name?scope`, `PUT /servers/:name/disabled`, `PUT /settings` (patch of the `settings` object; `unset` deletes keys). For project scope, `cwd` travels in the body of `PUT` routes and as `?cwd=` on `DELETE`. `DELETE /servers/:name` returns the removed raw layer entry in its response body (own-layer content, the same visibility `GET /effective` already grants at that scope); the client's undo toast re-submits it verbatim as `set` — exact restoration with no server-side snapshot state. `:name` is `encodeURIComponent`-encoded by the client and decoded server-side; names are additionally validated before use: 1–128 characters, no `/`, `\`, control characters, and not `.`/`..` (whitespace is allowed — it is a legal JSON key). Ajv is declared as a direct dependency of the plugin. Bodies validated against the schema server-side with the plugin's **own** Ajv instance — `new Ajv({ strict: true, useDefaults: false, allErrors: true })` with `x-secret`, `x-transport` and `x-atomic` registered via `addKeyword` — not the runtime's `config-validator.ts` instance, whose `useDefaults: true` would inject schema `default`s into a patch (violating merge-only) and whose default strict mode rejects the `x-` keywords. The published schema keeps `default` values purely as display metadata for the settings form. Names `__proto__`, `constructor`, `prototype` are rejected. **Every route, GET included, is registered with `{ preHandler: ctx.networkGuard }`** (the pattern `goal-plugin/src/server/routes.ts` uses on its GET list too): mutating bodies become executable config for pi (`command`/`args`/`env`), and `GET /effective` intentionally returns own-layer secrets, so a tunnelled caller must be stopped at the guard on both. Plugin routes are not shielded by the core per-route guard on their own. Errors: `400` schema/name failure with field list, `403` unknown cwd or network-guard refusal, `409` unparseable target file, `504 { error: "adapter-timeout", timeoutMs }` when an adapter load exceeds `adapterLoadTimeoutMs` (D10).

### D8. Client structure mirrors kb-plugin

`src/client/`: `McpSettingsClaim` (settings-section), `FolderMcpSection` (both folder slots; renders `SlotPill`), `FolderMcpPage` (shell-overlay-route, `depth: 2`, `parentPath: "/folder/:encodedCwd"`), `useEffectiveConfig(cwd?)` store keyed by cwd with a single in-flight request per key. The client has no view of `host.knownFolderCwds` (the slot contract passes `{cwd, label}` only, exactly as kb-plugin receives), so cwd admission is server-side only: the pill and page issue the request once and render the "not tracked" state on `403`; the 403 is cached per cwd in the store and invalidated when the client's session list or pinned-folder list changes (both already flow to the client), so a folder that becomes known is retried. Adapter status is one derived object from `GET /adapter` feeding pill, banner, and a `readOnly` context that the switches/editor read (UX D1). The global settings form is a host draft source (`useSettingsDraftSource({ id: "plugin:mcp-client", isDirty, commit, reset })`, as `automation-plugin`/`blackhole-plugin` do) so the host Save Bar, dirty indicators and route guard apply — no section-local Save/footer; the same draft source also carries the plugin's own dashboard-side settings (a separate "Dashboard plugin settings" group holding `adapterLoadTimeoutMs`, D10) read via `usePluginConfig` and committed via `plugin_config_write` (the host `plugin-config-persistence` path, namespace `plugins.mcp-client`, validated by the manifest `configSchema`) — `commit` awaits both the adapter-settings `PUT /settings` patch and the plugin-config write, and stays dirty if either rejects; the server editor modal commits its patch directly on its own Save and is not a draft source. Row toggles commit immediately. Secret masking is a presentational wrapper keyed on `x-secret` or the credential-name regex (UX D5); a secret that is *inherited* (not defined in the layer being edited) renders masked with **no** reveal toggle, so an override session cannot surface or copy a lower layer's credential. The `apple-tools` panel learns its dependency state from its own `PluginStatus.missingDeps` in the plugins index (already in `packages/shared/src/dashboard-plugin/plugin-status.ts`).

### D9. Removal of `apple-tools` plugin actions is a hard break

`set-disabled` and `set-direct-tools` are deleted, not shimmed. No caller exists outside the panel; a shim would keep a second write path alive, which the proposal exists to remove.

### D10. Adapter loads run in a worker thread under an operator-settable timeout

`loadMcpConfig` and `getServerProvenance` are **synchronous** (`pi-mcp-adapter/dist/config.d.ts`): a stalled read (config file on a hung network mount, a slow `imports` resolution) would block the dashboard event loop, and no in-thread timeout can interrupt it. The default adapter port therefore executes the loading functions in a single lazily-spawned `worker_threads` Worker (`src/core/adapter-worker.ts`), one per service instance, requests serialised through it; the write-only operations and the path helpers never touch the worker, so the hostless CLI factory (`apple-tools` installer) spawns nothing. Each load carries a deadline `adapterLoadTimeoutMs`; on expiry the port calls `worker.terminate()`, rejects with `AdapterTimeoutError { timeoutMs }`, and the next load respawns the worker. The HTTP layer maps that error to `504 { error: "adapter-timeout", timeoutMs }`; for the enable flow (which removes `disabled`, then re-evaluates the merge) the removal write has already landed when the merge times out — the route returns `504` and the client refetches the effective view rather than reverting, because the removal alone is a valid enabled state whenever no lower layer disables. The value comes from the plugin's own host config namespace `plugins.mcp-client` (manifest `configSchema: ./configSchema.json` — **distinct** from `schema/mcp-config.schema.json`, which describes the *adapter's* config and is served by `GET /schema`): `adapterLoadTimeoutMs` integer, default `10000`, minimum `1000`, maximum `120000`, read per request via `ctx.getPluginConfig()` (as `grammar-plugin` does) so a Save Bar commit takes effect on the next request without restart. The settings section exposes it in a "Dashboard plugin settings" group inside the existing `plugin:mcp-client` draft source (D8). Worker spawn cost is paid once per plugin lifetime (or once per timeout), not per request.

## Risks / Trade-offs

- [First real `dependsOn` consumer surfaces loader bugs] → Test matrix in `dashboard-plugin-loader` tests: both enabled, dependency disabled, dependency absent from disk, cascade toggle; plus an `apple-tools` registration test with a stubbed service.
- [Workspace `pi-mcp-adapter` version ≠ user's installed version] → Reads use workspace code (discovery paths are stable across 2.x); verdict uses the user's install. Documented in AGENTS.md row. `pi-mcp-adapter` is a regular `dependencies` entry (`^2.20.0`), not a peer, so the hostless CLI path through `./core` resolves it without relying on peer auto-install.
- [User-supplied `command`/`args`/`env` become executable config for pi — a tunnel caller with auth off could plant a stdio server pi then spawns] → Mutating routes sit behind `ctx.networkGuard` in addition to auth; schema validation before IO; writes only into Pi-owned files; cwd admission via `isAllowedCwd`; inherited secrets redacted server-side; own-layer secrets never logged. `security-hardening` pass on the route layer.
- [Two in-process writers on `~/.pi/agent/mcp.json` (mcp-server-plugin provisioner at registration + mcp-client on user action)] → Every writer is a synchronous read→merge→`writeFileAtomic` sequence on the single Node thread, so two dashboard writers cannot interleave; no lost update is possible between them. A concurrent *external* editor (user's text editor, a pi session) remains last-write-wins at the file level — same as today. `provisionDashboardEntry` today reads and writes only `mcpServers` with plain `JSON.parse` at a hard-coded path; it is rewritten in this change to go through the shared core writer (D3), removing all three divergences.
- [Hand-authored schema drifts from adapter types] → Key-union compile check (D6) catches removals/renames against the workspace version; additions, and a newer user-installed adapter, need a manual follow-up when bumping the adapter.
- [JSONC comments lost on write] → Same behaviour as the adapter's own `writeProjectServerDisabledOverride`; documented in the settings UI footer ("comments in this file are not preserved").
- [Provenance parse of six files on every `GET /effective`] → Files are tiny; cache by mtime per path. No latency budget.
