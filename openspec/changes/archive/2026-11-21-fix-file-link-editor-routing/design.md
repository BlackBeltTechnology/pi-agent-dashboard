## Context

Editor pane already supports absolute out-of-cwd tab paths (`normalize-path.ts:27-38` keeps them verbatim; `isUnderSessionCwd`, `DocumentBar` `outsideCwd`). Reads go through `/api/file` with `path.resolve(cwd, abs)` + containment/grants. Writes (`isWritableMdTarget`, `writable-md-target.ts` `allowedRoot` = realpath of cwd) and file watching (`file-watch-manager.ts:246`, `if (!withinCwd(abs, cwd)) continue`) are cwd-only today. So #1137/#1157 are a routing + resolve-result problem plus one write-gate extension (D2), not a pane rewrite.

## D1 — Resolve result for paths failing containment (confirmed (owner, 2026-11-20))

| Option | Effect |
|---|---|
| A. Keep `null` | `~/Downloads/x.md` stays "not found"; grant prompt unreachable from links. Rejects #1157. |
| B. Stat outside paths and return resolved | Existence oracle for any path; contradicts D2/D12 of the original resolver. Rejected. |
| **C. Return `{resolved, kind, outside:true}` without stat** | No existence leak; link opens the pane; the read gate decides (grant prompt on operator click, 403, or 404 notice). |

Chosen: **C** (confirmed (owner, 2026-11-20)). Disclosure delta: the response echoes the normalized candidate (incl. expanded home dir) to an already network-guarded, cwd-admitted caller. The `outside` flag is true iff containment failed; never depends on existence.

## D2 — Out-of-cwd tabs are editable; writes need a write-mode path grant (confirmed (owner, 2026-11-20); CHANGED from read-only, then from "same gate as reads")

Today `POST /api/file/write` → `prepareMdWrite` (`file-routes.ts:236-248`) → `isWritableMdTarget(resolved, {cwd})` (`writable-md-target.ts:96-115`): realpath-normalized, extension allowlist, dashboardState refusal, then `within(real, root)` with `root` = realpath of cwd → an outside path is a flat `403`. The only grant/prompt machinery is on reads (`gateReadPath`, `file-routes.ts:423-461` → `evaluateContainment` with `hold`). Cycle-2 review showed that simply reusing the read gate is wrong for a write: `isAllowedReal` widens every anchor to its bound checkout roots (`path-containment.ts:187-195`, `checkoutAnchors`), and the grant layer admits ANY persisted/session subject (`containment-gate.ts:253` → `grantedSubjects()`, `access-grants.ts:270`) with no session filter and no notion of read vs write (`AccessGrant`, `access-grants.ts:88-108`, has only `subject/scope/grantedAt/origin/widenedFrom/via`). So an existing read grant, or merely being in a worktree/repo subdirectory, would have silently authorised text-doc writes.

| Option | Effect |
|---|---|
| A. Read-only outside tabs, hide Edit | Rejected by owner. |
| B. New preference gate | Rejected by owner ("no new preference"). |
| C-as-drafted. Reuse the read gate unchanged | Any grant and the bound-checkout roots admit writes with no prompt. Owner chose a stricter mechanism after the cycle-2 trade-offs (T3). |
| **T3=B. Grants carry a write mode; a write needs a write-mode grant or a fresh write prompt** | Read grants and checkout-root widening never admit an out-of-cwd write. Write prompt: allow once / allow-always (write grant for the chosen subtree) / deny. |

Chosen: **T3=B** (confirmed (owner, 2026-11-20)); directory scope only — global scope (no `cwd`) stays `~/.pi/agent`-only with no grant.

### Grant schema, persistence, compatibility (verified against code)

- `AccessGrant` gains `mode?: "read" | "write"`; absent = `read`. Named `mode` on the grant only — `GrantSettlementMode` (`"held" | "deferred"`, `browser-protocol.ts:2802`) and `DenialInput.mode`/`PendingGrant.mode` (`pending-grant-registry.ts:72,91`) already use `mode` for the prompt plane, so the denial-side field is called `action: "read" | "write"` and only `AccessGrant.mode` is the persisted one.
- Store stays `StoreFile {version: 1}` (`access-grants.ts:115`). `loadFromDisk` keeps unknown fields through its `{...g, origin}` map (`:206`) and refuses any other `version` outright (`:184`, which empties the whole grant set), so a version bump would make a rolled-back build drop **every** grant. Additive optional field instead (precedent: `via`, "older builds spread it through", `:100-108`). Load normalises: `mode` other than the exact string `"write"` → treated as read (fail closed on a hostile/hand-edited file).
- One entry per `(subject, mode)`. `recordGrant` is idempotent today per `subject` (`:400,413`); it becomes idempotent per `(subject, scope, mode)`, so a write grant is a second entry beside any read grant for the same directory and the two are revocable independently. Cap (`GRANT_CAP_PER_SCOPE`=200) counts entries.
- `grantedSubjects()` (`:270`, the READ predicate input) is unchanged and includes write entries (write ⊃ read). New `grantedWriteSubjects()` returns only `mode:"write"` subjects. Every other consumer (grep `grep-routes.ts:90`, browse roots `server.ts:1490`, pi-trust mirror `server.ts:1746`, provisioning) is untouched: they see a write grant as the read grant it also is.
- Pre-change build reading a post-change store: spreads `mode` through, treats the entry as a read grant (bounded read widening; see proposal Rollback). Provisioned / agent-prompt grants never carry `mode`.

### Write-mode check

`prepareMdWrite` runs `resolveScopedMdPath` + `isWritableMdTarget` as today. Pass → write (unchanged, no prompt). On a fail where the realpath passes the extension allowlist and `dashboardStateRefuses` is false (split the extension/state half out of `isWritableMdTarget` into an exported helper; `.mmd/.mermaid` remain directory-only so they never reach the gate) but is outside the cwd, call `evaluateContainment(realpath, [admitted.cwd], {site:"file-routes:write", subjectKind:"file", session: admitted.cwd, hold:{request, reply}, disclosure, action:"write"})`. With `action:"write"`:

1. Layer ② is skipped: `isAllowedReal` gets an option (default keeps today's widening) that disables the `checkoutAnchors` pass, so a worktree's parent checkout or a repo sibling of a subdirectory cwd is NOT admitted. (Layer ① already refused above.) Dashboard-state refusal still runs first.
2. The grant layer uses `grantedWriteSubjects()` only; a read grant never admits.
3. A miss records the denial with `action:"write"` (`PathDenial`, `access-denials.ts:24-36`) and holds via `holdDenial({plane:"filesystem", …, action:"write"})` (`DenialFacts`, `denial-hold.ts:34`).
4. `reEvaluate` (`containment-gate.ts:373`) re-runs with the same mode: `allow-always` → the persisted write grant is in `grantedWriteSubjects()`; `allow-once` → the answered subject is applied as a transient real-path grant for THIS request, checked against the write predicate, never persisted.
5. Re-bind: `performAtomicMdWrite` already re-`realpath`s the target; assert it equals the gated realpath, else refuse (`409`/`403`, no write) so a symlink swapped during the hold cannot redirect the write. (Reads close the same window with `access/verified-read.ts`; the write keeps its realpath + `wx` tmp + rename shape.)

Denied / expired / prompt-ineligible (bare loopback without proof, `currentCallerUnproven()`) → `403 {error:"path outside working directory — write not granted", ...remedy}` via `sendGateFailure`; nothing is written. `prepareMdWrite` therefore takes the live `request`/`reply`.

### Where the action/mode flows (never from the client)

The mode of a created grant is derived from the server-held denial/prompt, not from any browser or request field: (a) prompt path — `DenialFacts.action` → `DenialInput.action` → `PendingGrant` → on `allow-always`, `plane.grant` (`planes.ts:68-93`, `PlaneGrantRequest` `access-plane.ts:25-34`) → `grantNamedPathSubject` (`named-grant.ts:37`) → `recordGrant({…, mode})`; the browser `grant_response` carries only the verdict + chosen rung, so a read prompt can never be answered into a write grant. (b) denial-id path — `POST /api/access/grants` (`access-routes.ts:405-455`) reads `denial.action` from the recorded `PathDenial` and ignores any client `mode`. (c) the pending registry key becomes `plane \0 action \0 subject` (`keyOf`, `pending-grant-registry.ts:188`; also the backoff key `:373`), so a read denial and a write denial for the same directory are separate entries and one verdict cannot release the other; even a mis-joined allow could not widen, because re-evaluation is mode-specific.

### Access settings, prompt copy, ladder

- `GET /api/access/grants` rows (`access-routes.ts:164-175`) add `mode: "write"` (omitted for read). Client `AccessGrantRow`/`AccessEntry` (`access-grants-types.ts:44-59,129-138`) gain `mode?`; `AccessSection.tsx` renders a "Write" badge; `revokeAccessEntry` (`access-grants-api.ts:78-81`) sends `{subject, scope, mode}` and `DELETE /api/access/grants` passes an optional `mode` to `revokeGrant(subject, scope, mode)` (omitted = remove every entry for the subject — today's behaviour; `"write"` / `"read"` remove only that mode's entry; any other value → `400`, nothing removed). The pi-trust mirror snapshot (`mirror.revoke("accessGrants", subject, …)`) fires only when the last entry for that subject is removed, so revoking just the write grant never un-mirrors a still-present read grant.
- The write prompt keeps the held verdicts (allow once / allow-always / deny) and the same ancestor ladder (forbidden-subject and boundary rules unchanged); copy for `action:"write"`: "A write was blocked because this path is outside the session's working directory. Allowing it also allows reading and saving text documents under the chosen folder." (`GrantPromptDialog.tsx:64` is hard-coded read copy and the `grantPrompt.reason.filesystem` i18n key). `GrantRequestMessage` (`browser-protocol.ts:2860`) gains optional `action`; absent = read.

Client: no Edit-hiding. `MarkdownViewer.tsx:100-109` / `EditablePreviewTab.tsx:90-101` already `setError(body.error)` on a non-200/409 and leave `buffer` untouched, so a denied save keeps the dirty buffer; the guard dialog's Save treats a `403` like a failed save (stays open, buffer kept). The request pends while the operator is prompted (same as a held read), so the Save button shows its saving state.

No live watch: `file-watch-manager.ts:246` never watches outside the cwd, so an out-of-cwd tab gets no push `file_changed`; the save-time `mtime` 409 (`performAtomicMdWrite`) still detects a concurrent change. Accepted and documented; extending the watcher is a non-goal.

**Prompt before existence (accepted)**: the gate runs before `performAtomicMdWrite`'s stat, so a write to a nonexistent out-of-cwd text doc raises the prompt and then answers `404` (writes never create files). Stat-first would be an existence oracle for arbitrary outside paths — the posture D1 refuses — so the extra prompt is accepted. The `bodyLimit` (600 MiB, `file-routes.ts:1026`) is the route's existing limit; the body is held for the prompt's lifetime exactly as the route already holds it while writing; no new cap in this change.

**YOLO (confirmed (owner, 2026-11-20))**: a filesystem-plane denial is auto-answered allow-once under YOLO (`access-grant-yolo` "YOLO applies to the filesystem… planes"; `grant-coordinator.ts` consults `yolo.decide` at the prompt point and returns `allow-once`, still re-evaluated by the caller). The write hold is a filesystem-plane denial, so under YOLO an out-of-cwd text-doc save is auto-allowed once, exactly like a read. It is still bounded by the YOLO session's directory roots ("A YOLO session is bounded by a set of directory roots": the default root is the session cwd, so a default-scoped session does NOT auto-allow an outside write — it prompts), never resurrects a prior explicit refusal, never creates a persisted grant, and an ineligible caller is not auto-answered. The auto-allow checks the write predicate (transient subject, write mode only).

**Risk (flag for `doubt-driven-review`)**: a write grant is still a SUBTREE grant: allow-always on a broad rung admits every allowlisted text doc (`.md/.mdx/.adoc/.asciidoc/.csv`) under it for any admitted caller (grants are not per-session; `AccessGrant.origin` is provenance only, `access-grants.ts:94`). Mitigations: separate explicit write mode (a read grant, provisioning, agent-prompt grants and checkout roots never admit a write), write-honest prompt copy naming the folder, the forbidden-subject filter on every rung, extension allowlist, dashboard-state refusal, `mtime` optimistic check, atomic write, realpath re-bind, revocable per mode from the Access page. Residual: a pre-change build downgrades the grant to read (see proposal Rollback). `containment-gate.ts` doc ("a grant is a READ remedy", ~L206-211) is updated: a grant has a mode and only a write grant admits an allowlisted text-doc write at `file-routes:write`; `allowGrant:false` sites (`open-in-system`, `reveal-in-file-manager`) are unchanged.

## D3 — Unsaved guard shape (confirmed (owner, 2026-11-20))

| Option | Effect |
|---|---|
| **A. Dirty registry + confirm at owned leave points** | Small; mirrors handler `guardDiscard`/`close-risk`. |
| B. Keep-alive buffers (lift state to a store, like handler instances) | No loss and no prompts on tab switch / pane close; larger, memory + eviction rules. |

Chosen: **A** (confirmed (owner, 2026-11-20)). **Registry is an app-level module store, not React context.** `handleSelect` lives in `useSessionActions`, called by `App` itself (`App.tsx:1937`) *above* both `<FolderSplitProvider>` (`App.tsx:3021`) and `<SplitWorkspaceProvider>` (`App.tsx:3242`), and the sidebar renders outside them, so a context-scoped registry is unreachable from `handleSelect` and misses folder-pane buffers. Follow the `fileHandlerStore` precedent (`editor-pane/file-handler/file-handler-store.ts`, "page singleton"): a new `editor-pane/unsaved-store.ts` module singleton with `registerUnsaved(key, {dirty, save})` (returns an unregister fn), `hasUnsaved(keys?)`, `subscribe`, and `confirmLeave(keys?) → Promise<boolean>`. `key` = `${sessionId ?? folderKey}\u0000${tabPath}`, so one store serves session panes and folder panes and `confirmLeave` can be scoped to one tab, one pane/session or all. Lifecycle: a viewer registers on mount and re-publishes on `dirty` change; its effect cleanup unregisters, so stale entries cannot outlive an unmounted viewer (Discard/Save-then-leave unmounts and clears). The Save/Discard/Cancel dialog is rendered by one page-level `UnsavedChangesHost` mounted in `App` next to `FileHandlerLayer` (not inside a provider); `confirmLeave` opens it and resolves with the choice. Call sites: `closeTabAt`, `runBulkClose` (extend `CloseRiskLookups` with built-in dirty → listed once), pane close button, `LayoutModeSwitch` chat segment, `handleSelect` (calls `confirmLeave()` for the current session's keys before `navigate`). `beforeunload` is armed by the store while any entry is dirty; it is a separate listener from `FileHandlerLayer`'s (`FileHandlerLayer.tsx:251-259`), which already covers handler tabs, so the two cover disjoint tab sets and do not compete. Tab *switch* also unmounts the buffer today; left out (non-goal), flagged in DECISIONS.

## D4 — Link target in the pane (worktree sessions) (confirmed (owner, 2026-11-20); T2 = re-root when the worktree copy exists)

`FileLink` opens a **server-resolved path** in the pane, exactly as it opens it in the overlay today ("File links resolve lazily on open"). For a worktree session (`cwd` = `<parentRoot>/.worktrees/<slug>`) an absolute link rooted in the parent checkout is handled in two steps:

1. `resolveLinkOrigin(cwd, path, absolute)` (`lib/util/link-origin.ts:71`, pure string fn, unchanged; already computes the `<parentRoot>`→worktree re-root at render time, `FileLink.tsx:53`) yields the worktree candidate. When it differs from `path`, `FileLink` first calls `resolveFileMention(cwd, candidate)`. A non-null result (contained under the cwd and the file exists — the resolver stat-checks contained paths) is the open target: the pane opens the cwd-relative worktree copy.
2. A `null` result (the worktree has no such file, e.g. untracked or not installed `node_modules`) falls through to resolving the ORIGINAL `path` as before: the pane opens the parent-checkout path (contained by the git-common-root anchor, so no `outside`), as an absolute-path tab. A resolve *request failure* (network/5xx) still takes the offline fallback; it is never read as "copy absent".

Server side is unchanged (`resolve-file-mention.ts` has no worktree logic, so the existence signal is its normal contained-missing `null`; refresh the stale `FileLink.tsx` header comment "the server owns re-rooting" in 2.3). Cost: one extra resolve round-trip only for parent-rooted absolute links in worktree sessions. A parent-checkout tab that is opened (copy absent) is outside the cwd, so a save there goes through the **write prompt** (D2: bound-checkout roots no longer admit writes). Non-worktree and already-worktree-rooted/foreign links are unchanged.

## Scenario-design decisions (confirmed (owner, 2026-11-20), from `test-plan.md` gaps G1–G7)

- **G1 — routing with no live split.** A localhost browser with a detected editor keeps `openEditor` / `POST /api/open-editor` even when a `sessionId` exists; `buildEditorUrl` deep-link applies only when no editor is detected or the page is not on localhost; overlay only with no `sessionId`. Pane-first (live split) still wins over everything.
- **G2 — several dirty buffers / overlapping leave.** `confirmLeave(keys?)` shows ONE dialog listing every dirty tab in scope. Save saves them in order and resolves `true` only if all succeed (first failure stops, keeps that buffer + error, earlier saves are not rolled back); Discard drops all; Cancel changes nothing. A second `confirmLeave` while the dialog is open joins the open dialog's promise (same verdict), never stacking a modal.
- **G3 — `DELETE /api/access/grants` `mode`.** omitted → all entries for the subject; `"write"` / `"read"` → only that mode's entry; anything else → `400`, nothing removed.
- **G4 — coalesced concurrent writes.** Verified against `grant-coordinator.ts` `finish()`: today allow-once releases only the request that raised the prompt and coalesced joiners are denied (`allow-once-not-shared`). The write plane inherits this unchanged (no per-action special case): allow-once → first admitted, joiner `403`, nothing persisted; allow-always → every held request is released and re-evaluated against the persisted write grant. (The accepted answer "verdict releases every held request, as reads do today" rested on a premise that the code contradicts for allow-once; the "same as reads" intent is what is specified.)
- **G5 — unsaved dialog focus.** Initial focus on Cancel; Escape and backdrop click = Cancel; no default-Enter on Discard (mirrors `bulk-close-confirm`).
- **G6 — Windows drive letter.** `normalizeUnderCwd` compares only the drive letter case-insensitively (`c:` ≡ `C:`); the rest of the path stays case-sensitive.
- **G7 — write-containment latency.** Inherits the read ladder budget: p95 < 5 ms over 1000 iterations (`ladder-perf.test.ts`).
