# Proposal: stabilize-blocking-test-lanes

## Why

Blocking test lanes fail on host speed, not on code. Over the last 21 days `nightly-tests.yml` was red in 24 of 30 runs and `ci.yml` in 21 of 40. Almost every failure was a wall-clock or memory budget assertion on a shared runner: `kb-search-perf`, `browser-gateway-broadcast-serialize-once` P2, `ladder-perf` #P4, `graph-layout` #P1, `knip-scan` #P1 (8 of 16 red `ci.yml` runs), blender `real-binary.test.ts` P1–P3, `provisioning` #P1 and `dependency-declarations` P1/P2. A different one failed each night. (`SessionList.actions-menu` P1 also failed, but it asserts a render count under fake timers, so it is not a budget test; see Non-Goals.) The always-red nightly hid real deterministic failures for days. In 11 of 43 local sessions, `npm run codeql` (ship-it step 4.4b) stopped a headless ship with `codeql resolve extensions ... ETIMEDOUT`, which exits 2 after 60 s.

This is the core of a split (owner decision A8). Migrating the other ~300 upper-bound time and memory assertions, and making the guard blocking, is the follow-up change `migrate-budget-assertions`.

## What Changes

- **Budget lane.** A test whose pass or fail depends on a measured wall-clock duration or process-memory amount (a "budget test") can be placed in a file named `<name>.budget.test.<ext>`. Every vitest config whose project collects such a file excludes it unless `RUN_BUDGET_TESTS=1` (a shared `BUDGET_TEST_EXCLUDE` from `vitest.workers.ts`; six configs in this change), so `npm test`, PR CI and the tag gate do not even collect it. `RUN_BUDGET_TESTS` is set only by the `test:budget` script; the selector lists budget files by filename and nothing that `npm test`, PR CI or the tag gate runs sets it. A new blocking check, `scripts/check-budget-lane.mjs`, fails the `ci.yml` `ci` job and `npm test` when either `npm test` command would collect a budget file, or when a tracked budget file would run nowhere (judged from the resolved vitest configs, without setting the variable); it is separate from the warn-only guard below. The selector keeps budget files out of every unit shard, the real-process job and the packaging-scenarios job. Only a new nightly job, `budget`, runs them, on `ubuntu-latest` only (A7), so blender P1–P3 are no longer measured on macOS or Windows: an accepted loss. Assertion type decides what is a budget test, not filename. Only upper bounds count (A5): lower-bound waits, byte and bundle sizes, counts, fake-timer arithmetic and the skill-frontmatter size budget are not budget tests.
- **Move the budget cases observed failing (A9), and only those.** Each was verified by reading its assertion (design.md D6); every one asserts an upper bound on a wall-clock duration or process memory, so none drops out as a separate flake. Files: `kb-search-perf.test.ts` (P1 block and the S61 tail bound), `browser-gateway-broadcast-serialize-once.test.ts` (P2), `ladder-perf.test.ts` (#P4 RSS bound), `graph-layout.test.ts` (#P1), `knip-scan.test.mjs` (#P1), blender `real-binary.test.ts` (P1–P3; E10–E51 stay), `provisioning.test.ts` (#P1) and `dependency-declarations.test.mjs` (P1/P2). Functional cases stay blocking. A moved case whose other assertions check an outcome no blocking case asserts keeps a blocking copy without the bound (`ladder-perf` #P4 keeps `reg.size` 0). Thresholds are unchanged.
- **Warn-only guard (A10).** A new script, `scripts/check-budget-assertions.mjs`, finds upper-bound time and memory assertions in blocking lanes, including relative bounds, assertions split across lines, and durations returned by same-file functions. It runs as one step in the `ci.yml` `ci` job with `--warn`: each finding becomes a warning annotation, and the count and full list go to the job summary. It always exits 0 there, and it is not added to ship-it. **Until `migrate-budget-assertions` makes it blocking, a NEW budget assertion can still land in a blocking lane**, and the ~300 existing ones keep running there. Its `--list` output is the starting input for that change's inventory, not a complete one: the guard cannot see the forms design.md D5 lists, including the predicate form `expect(withinBudget(elapsed, n), …).toBe(true)` of `dependency-declarations` P1/P2, which this change moves although the guard never flagged it. The liveness allow-list for real-process deadlines (A6) and its admission rule (a real-process liveness deadline with a written reason) are designed and seeded now, but only reported on, not enforced. design.md D5 states what the guard cannot detect.
- **Blocking jobs stay blocking.** `blender-real` and `ci-scenarios` remain in `ci-result`. No job gets `continue-on-error`. (The new `nightly-attempt-1` download step uses step-level `continue-on-error`, like the existing report download at `nightly-tests.yml:191`; a failed download makes the run red.) PR `ci.yml` gets no budget job and no retry.
- **Nightly reruns failed jobs once, fail-closed.** A new workflow, `nightly-tests-rerun.yml`, has one job that holds only `actions: write`; it reads the first attempt's record and reruns the failed jobs only when that scheduled first attempt deferred. A first attempt that did not defer has already opened the issue and is not rerun. The report job opens or updates the `nightly-tests` issue only when a job also fails on the rerun. Tests that failed and then passed on the rerun, and jobs that failed without a failed assertion (timeout, cancellation, no report) and then passed, are listed in their own "Passed on rerun" section and open no issue on their own. The report job keeps its current permissions. Fail-closed: the first attempt defers only while both the rerun workflow and a separate watchdog workflow are active, and only when its report runs by 04:05 UTC on the UTC date the run was created (a report after midnight does not defer), so an automatic rerun ends by 05:35 UTC at the latest, two hours before the watchdog; a rerun of a night that may have deferred and cannot read the first attempt's record is red, while a manual re-run of a night that did not defer is judged on its own result; `nightly-tests.yml` loses its `concurrency` group so no other run can displace a scheduled one; and `nightly-tests-watchdog.yml` (cron 07:47 UTC, two hours after the worst-case end computed from the workflow timeouts, with the report job's permissions) opens the issue when the latest scheduled run did not end green and no open issue names it. The two safety nets live in separate files, so one bad edit cannot stop both. An early spike (task 1.1) checks nine platform behaviours, including the cross-attempt artifact reads, before any of this is built. If a blocking one fails, the rerun and watchdog (task group 6) are not built, the nightly keeps today's issue-on-first-failure, and ship-it stops and asks the owner instead of shipping spec text the tree does not meet; design.md D7 "If the spike fails" names that text.
- **CodeQL model-pack timeout.** The `codeql resolve extensions` step in `verifyModelPack` gets its own timeout. The default rises from 60 s to 300 s, and `PI_CODEQL_RESOLVE_TIMEOUT_MS` overrides it. The variable is read only after a CodeQL binary is found, so a machine without CodeQL still skips. A timeout stays `CODEQL ERROR` with exit 2 and never becomes a skip. The pack-download timeout and its skip on timeout are unchanged. One task measures and records why a cached, offline `resolve extensions` takes longer than 60 s, under a fixed list of six conditions; a condition the machine cannot produce is recorded as not run, with the reason. It ends with a named root cause backed by a timed run over 60 s, or with "not reproduced" plus every timing and the strongest lead (the owner accepted that second outcome as the A2 record, trade-off T-A8).

## Non-Goals

- No migration of any budget assertion beyond the A9 list, no blocking guard, no baseline, no `// budget-exempt:` marker and no opt-in-variable exception. All of that is `migrate-budget-assertions`.
- No trend store and no budget history. `timings.json` stays a shard-balancing input only.
- No retry of any kind in PR `ci.yml`. No vitest `retry:` outside the real-process config.
- No job-level `continue-on-error`. No removal of `blender-real` or `ci-scenarios` from `ci-result`.
- No change to the pack-download timeout or its skip on timeout. No lock shared across worktrees.
- No fixes for the deterministic failures the red nightly hid (`skill-frontmatter` "no budget warning" and the six "classified once, evidence consumed" tests). This change only makes them visible again.
- No re-tuning of budget thresholds. Budget cases move unchanged, apart from the shared helpers extracted so a split file and its budget sibling can both import them. (`provisioning` #P1 is the exception: its budget file gets a verbatim copy of the setup, because the original's harness is mutable module state; design.md D6.)
- No fix for `SessionList.actions-menu.test.tsx` P1 (`:169-196`). It asserts a React commit count under `vi.useFakeTimers()`, so it stays blocking; its CI failure is a separate flake to triage.
- No detection of a nightly that never starts. The watchdog checks only the latest scheduled run that did start.
- `KB_MEASURE` measurement harnesses stay opt-in and outside every CI lane, as today.
- No change to `publish.yml`. Its `pnpm test` (`publish.yml:120`) leaves out the budget lane by default. `schedule-release-rehearsal` owns the tag gate.

## Capabilities

### New Capabilities

None. Every requirement fits an existing capability.

### Modified Capabilities

- `parallel-test-execution`: ADDED "Budget test files run only in the nightly budget lane" (the lane, the config exclusion, and `RUN_BUDGET_TESTS` set only by `test:budget`), "A blocking lane check refuses a budget file outside the budget lane", "The budget cases observed failing in CI are in budget files" (the A9 moves), "A budget-assertion guard reports budget assertions in blocking lanes", "The budget guard runs warn-only in PR CI" and "The guard's liveness allow-list holds real-process liveness deadlines with a written reason". MODIFIED "Real-process tests run in a dedicated low-concurrency phase": server budget files are in neither phase by design, so its repo-lint and single-command coverage leave them out. MODIFIED "CI-only single retry for the real-process phase is reported, never silent", which allows a job-level nightly rerun once.
- `nightly-verification`: MODIFIED "A scheduled nightly SHALL run the full unit suite", which adds the budget job and removes the concurrency group. MODIFIED "A red test nightly SHALL name the failing tests and the commit range", which adds rerun once, an issue only when a job fails twice, a separate "passed on rerun" list, and the fail-closed rules (deferral only while the rerun and watchdog workflows are active, unreadable record is red, watchdog in its own file).
- `affected-test-selection`: MODIFIED "Selection is computed from a base ref and yields a mode, a reason, and shard assignments", which adds the budget-lane file set, found by filename, and forbids the selector to set `RUN_BUDGET_TESTS`. MODIFIED "Every shard proves it ran what it was assigned", which adds the budget job and fails it on any skipped budget case.
- `ci-cd-pipeline`: MODIFIED "CI uploads the vitest JSON report on every run", which adds the budget job's report and overwrites artifacts on a rerun attempt.
- `codeql-local-ratchet`: MODIFIED "Model pack is verified before analysis", which adds a configurable timeout that stays an error and keeps the missing-binary skip.
- `blender-mcp-server`: MODIFIED "Performance budget", measured on the `ubuntu-latest` budget lane only (A7).
- `dead-code-detection`: MODIFIED "Whole-graph Knip scan", whose 30-second scenario is asserted in the budget lane.
- `publish-correctness-verification`: MODIFIED "The check completes within a CI time budget", whose enforcing test runs in the budget lane.

The rerun text (the `nightly-verification` and `parallel-test-execution` retry requirements above, and the rerun paragraph and scenario of `ci-cd-pipeline`) depends on the spike. If the spike fails, it is withdrawn only with the owner's approval (design.md D7).
