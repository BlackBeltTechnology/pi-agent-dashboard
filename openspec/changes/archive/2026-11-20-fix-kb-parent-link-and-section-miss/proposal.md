## Why

Two kb defects, reproduced against the judo-blueprint catalog (`judo-blueprint/reports/kb-issues/KB.md` items 1 and 2), send agents down wrong paths:

- The markdown chunker stores a parent reference as a parse-time heading ordinal but names chunks by their final array index. A dropped preamble, an empty container heading, a tiny-merge or an oversize split shifts the two apart. `kb_search` then reports a sibling as `parent`, agents build a heading path that does not exist, and `kb_get` fails on it; a section that names itself writes a `child_of` self-loop into the graph. In `extension-points.md` every `##` section names `## Extra Routes` as its parent; `Extra Routes` names itself. The AsciiDoc chunker already maps ordinals to final indices; the markdown chunker never got the same fix.
- `kb_get` with a valid path and an unknown section prints `(not found: <path>)`, the same marker as an unindexed file. Agents conclude the file is missing and fall back to reading from disk.

## What Changes

- The markdown chunker resolves each parent reference to the first chunk of the section's direct enclosing section, and to null when that section was dropped (empty) or merged away (tiny), matching the AsciiDoc chunker. It is never a sibling, a descendant, a grand-ancestor or the section itself. The `child_of` graph edges derived from it are corrected the same way (a null parent links to the file node).
- The index schema version is bumped so existing indexes re-chunk and lose the stored wrong parents.
- A section fetch whose path resolves but whose section does not returns a distinct section-not-found marker naming the section and the path, followed by up to 50 of the file's body-section heading paths in document order, so the caller can retry. An unindexed path keeps `(not found: <path>)`.
- **Public type:** `FetchResult` (exported by `@blackbelt-technology/pi-dashboard-kb`) gains a `section-missing` variant; `FetchStore` gains a required `getChunks`.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `kb-markdown-chunking`: the parent reference names the direct enclosing section's first chunk, or null when it emitted none; never a sibling or the section itself.
- `markdown-knowledge-base`: a search hit's parent is always its direct enclosing heading or absent; an unknown section in a resolved file returns a section-not-found marker plus the file's heading paths instead of the path not-found marker.

## Impact

- Code: `packages/kb/src/chunker.ts` (parent resolution), `packages/kb/src/sqlite-store.ts` (`SCHEMA_VERSION`), `packages/kb/src/fetch-resolve.ts` (new result kind + render), `packages/kb/engine-fingerprint.json` (regenerated by the kb build), `packages/kb-extension/src/extension.ts` (`kb_get` description). The `kb_get` tool and `kb get` CLI share `renderFetch`, so both surfaces change together.
- Data: every kb index re-chunks once on the first pass after upgrade.
- Tests: `packages/kb/src/__tests__/fetch-resolve.test.ts` (unknown-section assertions change kind), `index-integrity-install.test.ts` (schema literal), new chunker cases.
- Docs: `docs/architecture.md` (`kb_get` resolution), `packages/kb/src/AGENTS.md`, `packages/kb/README.md`, `packages/kb/src/sqlite-store.ts.AGENTS.md`, `CHANGELOG.md`.
- Out of scope (design questions, not bugs): empty container headings becoming fetchable, the frontmatter meta chunk as file representative, listing sections on a path-only fetch, the read-discipline guard's pipe rule, the agents lane quota.

## Discipline Skills

- `doubt-driven-review`: the change adds a variant to an exported union type and forces a one-time re-chunk of every index (a data migration). Both were reviewed before planning stood. The re-chunk is reversible: an older engine re-chunks back on its own gate.
