## Context

See proposal.md for the defects. Current code:

- `packages/kb/src/chunker.ts:109-123` assigns `ordinal` per heading at parse time (and per synthetic preamble), stores the parent as `String(parentOrdinal)`, and increments `ordinal` even for sections that `flush()` later drops (`chunker.ts:87-89`, empty body — e.g. a preamble of blank lines left after frontmatter is stripped). Tiny-merge (`chunker.ts:132-137`, `MIN_CHUNK_CHARS = 100` at `:10`) and oversize-split (`chunker.ts:140-156`, `MAX_CHUNK_CHARS = 4000` at `:11`) then change the array, and `chunker.ts:158-167` names chunks `${sha}:${i}` by final index while keeping `parentChunkId: ${sha}:${parentOrdinal}`. The two numbering schemes diverge once a section is dropped, merged or split. Reproduced on judo-blueprint `catalog/agent-docs/frontend/extension-points.md`: `:1` (`Extra Routes`) has parent `:1`, `:5` (`Dashboard Page`) has parent `:1`.
- `packages/kb/src/adoc-chunker.ts:261-292` maps `ordinal → first final index` and sets the parent null when the parent ordinal is absent or self.
- `packages/kb/src/indexer.ts:245-246` builds `child_of` edges from `c.parentChunkId`, falling back to the file node when null; it needs no change once the id is right.
- `packages/kb/src/sqlite-store.ts:764-776` attaches `h.parent` from `parentChunkId` at search time, skips a null parent (`if (!pc) continue;`) and a self parent (`parent.chunkId !== h.chunkId`), so a self-reference shows only as a `child_of` self-loop; no change needed.
- `kb_search` condensed output prints the hit's leaf heading plus a `⤷ <parent headingPath>` line; agents rebuild a section path from the two.
- Re-chunk gates: `packages/kb/src/index-gate.ts:40-44` forces a source when `user_version < SCHEMA_VERSION`, the `gate:<root>` value (`<SCHEMA_VERSION>:<hash>`) differs, or the `engine:<root>` record differs from the running engine fingerprint (`packages/kb/engine-fingerprint.json`, regenerated by the kb `build` script, `packages/kb/package.json:25`; CI fails on a stale one, `scripts/check-kb-dist-fresh.mjs`). The legacy global gate for callers without a per-source gate checks `user_version` and `facetConfigHash`, not the engine (`packages/kb/src/index-run.ts:300-304`). `SCHEMA_VERSION = 3` at `sqlite-store.ts:12`.
- `packages/kb/src/fetch-resolve.ts:56-63` `resolveSection` returns `{ kind: "missing" }` for an unknown section, the same value `resolveFetch` returns for an unknown path (`fetch-resolve.ts:67`); `renderFetch` (`fetch-resolve.ts:86`) prints `(not found: ${arg})` for both. The CLI (`packages/kb/src/cli.ts:353-354`) and the `kb_get` worker (`packages/kb-extension/src/query-worker-entry.ts:45`) both call `resolveFetch` + `renderFetch`.
- `FetchStore` (`fetch-resolve.ts:19-22`) exposes `getChunk` and optional `getChunkBySection`; `SqliteFtsStore.getChunks(root, path)` exists (`sqlite-store.ts:857-859`) but is on neither `FetchStore` nor `KbStore` (`types.ts:231-236`). The frontmatter `:meta` chunk is inserted after the file's body chunks (`indexer.ts:238` vs `:274`) and may have an empty body. `FetchResult`/`FetchStore` are re-exported publicly (`packages/kb/src/index.ts:19`).

## Goals / Non-Goals

**Goals:** markdown parent ids always name the direct enclosing section's chunk or null; existing indexes are rebuilt on every gate path; an unknown section is reported as such, with a bounded retry list.

**Non-Goals:** making empty container headings (`## Practice`) fetchable; changing which chunk represents a file in search; listing sections on a path-only fetch; the guard pipe rule; the lane quota. The AsciiDoc chunker is not touched (it already follows D1).

## Decisions

**D1 — Direct parent or null, the AsciiDoc rule.** Each raw section keeps its parse-time `ordinal` and `parentOrdinal` through flush, tiny-merge and oversize-split (merged sections disappear; split pieces keep their ordinal). After normalization, build `ordinal → first final index` and resolve `parentOrdinal` through it; absent → null. This is the `adoc-chunker.ts:261-292` rule, which keeps the `kb-asciidoc-chunking` parity requirement ("same metadata contract as markdown chunks") and the Tier-1 rule that `child_of` points at the "parent section or file node". Self cannot occur (a parent ordinal is always smaller than the section's own); no self check is needed. Alternative considered: walk up to the nearest ancestor that emitted a chunk. Rejected: condensed `kb_search` output shows leaf + `⤷ parent`, so for `# Title > ## P (chunkless) > ### C` an agent would rebuild `Title > C`, a path that does not exist — the very failure this change fixes — whereas with no parent it passes the bare leaf `C`, which the last-heading fallback resolves. It would also break AsciiDoc parity and the Tier-1 edge rule. Cost: such hits carry no parent context; the markdown-knowledge-base delta states that explicitly.

**D2 — Bump `SCHEMA_VERSION` 3 → 4.** In normal installs the regenerated engine fingerprint already forces a re-chunk (`index-gate.ts:43-44`). The bump additionally covers the legacy global gate (`index-run.ts:300-304`), which checks only `user_version`, and runs where the fingerprint cannot be read (`runningEngine()` null → no engine check). Cost: one test pins the literal (`packages/kb/src/__tests__/index-integrity-install.test.ts:229`). Alternative: rely on the fingerprint alone. Rejected for the two uncovered paths.

**D3 — `section-missing` result with a capped heading list.** `resolveSection` returns `{ kind: "section-missing", sections }` when the path resolved; `{ kind: "missing" }` stays for unresolved paths. `getChunks(root, path)` becomes a required member of `FetchStore` only — the fetch layer's own structural interface, which `SqliteFtsStore` already satisfies; `KbStore` is not widened, since no other backend exists in-repo. Sections are the distinct `headingPath` values of body chunks in rowid order. Render: `(section not found: <section> in <arg> — sections:)` with `<arg>` as the caller passed it, then at most 50 paths, then `(+K more section[s])` when K > 0 (pluralised like the existing suppressed-sections line); `found: false`. The list can be empty: a file with frontmatter and no body sections resolves via its `:meta` chunk alone (`sqlite-store.ts:828-831`), which D4 filters out; the marker then reads `(section not found: <section> in <arg> — no sections)`. Cap rationale: `docs/architecture.md` has 464 headings (~47 KB of breadcrumbs); an uncapped list would flood the context on one typo. Cost: one indexed `SELECT` over one file's chunks per miss, only on the error path. Alternative: rank by similarity to the requested section. Rejected as speculative for a retry hint.

**D4 — Exclude the frontmatter `:meta` chunk from the list.** It is a synthetic chunk, not a heading; it sorts after the body (so "document order" would be false) and its body can be empty (so a round-trip could return nothing). Filter by the `:meta` chunk-id suffix. Agents reach the title text through search, not through this retry list.

## Risks / Trade-offs

- [One-time full re-chunk on upgrade] → same mechanism as earlier schema bumps; incremental afterwards.
- [Children of a chunkless heading carry no parent context] → their own `headingPath` is complete; the condensed leaf resolves via the last-heading fallback.
- [Adding a `FetchResult` variant and a required `FetchStore.getChunks` breaks exhaustive switches / custom stores of external embedders] → no in-repo consumer switches on the kind beyond `renderFetch`; noted in CHANGELOG.
- [A file with more than 50 sections may not list the wanted path] → `(+K more sections)` tells the agent; the last-heading fallback still matches a bare heading name.

## Migration Plan

Ship; the first index pass after upgrade re-chunks each source (D2). Rollback: an older engine sees `user_version` 4 ≥ 3 and does not force on that check, but its `gate:<root>` value (`3:<hash>` ≠ `4:<hash>`) and engine fingerprint differ, so it re-chunks back with its own code.
