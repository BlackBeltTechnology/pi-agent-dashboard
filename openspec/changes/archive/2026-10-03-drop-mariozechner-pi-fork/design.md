## Context

See proposal.md — Why. The fork is recognised through three mechanisms:

- **Alias lists.** Arrays that try `@earendil-works/*` first and `@mariozechner/*` second: `MANAGED_PI_PACKAGES` (`shared/platform/binary-lookup.ts`, consumed by `spawn-runtime.ts`), `PI_PKG_ALIASES` (`shared/pi-installs/candidates.ts`, re-exported from `pi-installs/index.ts`), `piPkgAliases` plus the `pi-coding-agent` / `pi-ai` module aliases (`shared/tool-registry/definitions.ts`), `PI_PKG_NAMES` (`extension/model-tracker.ts`), the alias loop in `server/pi/pi-version-skew.ts`, and `PACKAGES_TO_CHECK` (`electron/lib/update-checker.ts`).
- **Core-package identity.** `CORE_PACKAGE_NAMES`, `DISPLAY_NAMES`, `PI_DEV_PACKAGE` and `dynamicPiAliases` in `server/pi/pi-core-checker.ts`. On the client, `PI_CORE_PKG_LEGACY` / `isPiCorePkg` in `UnifiedPackagesSection.tsx`.
- **Manifests and types.** Optional peers and `peerDependenciesMeta` entries in the root `package.json` (`package.json:147-169`), `packages/extension/package.json:61-76`, and the `kb-extension`, `image-fit-extension` and `untrusted-content-guard` manifests. Also the `paths` entries in `tsconfig.base.json:19-32`, and the ambient `declare module` blocks for `@mariozechner/pi-coding-agent` / `@mariozechner/pi-ai` in `packages/extension/src/pi-env.d.ts:39,48`.
- **Resolution order.** `which("pi")` is the last step of the `pi` executor chain (`packages/shared/src/tool-registry/definitions.ts:644-665` → `whereStrategy`) and of `resolvePi()` (`packages/shared/src/platform/binary-lookup.ts`). It performs no package-identity check.

Some leftovers belong to the already-removed legacy-cleanup feature (commit `9d3edad66`): `legacyPiInstalls?` on the bootstrap status in `shared/browser-protocol.ts`, and the `packages/server/src/legacy-pi-cleanup.ts` allowlist entry in `shared/__tests__/no-direct-child-process.test.ts`. Nothing reads or writes either one.

Constraint: the dependency `update-pi-core-1-0-adopt-apis` must land first. It sets the 1.0.0 floor, removes the command-routing old-pi gate (and its fork case), and introduces the requirement "piCompatibility block and earendil pi ranges track pi-coding-agent in lockstep", which this change modifies.

## Goals / Non-Goals

**Goals:**
- One pi identity: every alias list holds only the `@earendil-works` name, or collapses to a single constant where only one name remains.
- No `@mariozechner/pi-*` peers, devDeps or ambient declarations in any manifest or `.d.ts`.
- The core version check takes `latestVersion` from the npm registry only.

**Non-Goals:**
- `@mariozechner/jiti` stays in `JITI_PACKAGES` (`packages/shared/src/platform/binary-lookup.ts:35`, `packages/server/bin/pi-dashboard.mjs:64`). It is a different package; the `jiti-loader` spec mandates it.
- No fork detection, identity check, migration banner or auto-uninstall (owner decision). A fork `pi` binary on PATH can still be found by `which("pi")` and spawned. It is no longer a recognised pi package, and only the dependency change's advisory below-floor flag applies (the fork never reached 1.0). Module resolution (`loadPiPackageManager`, the `pi-coding-agent` / `pi-ai` registry modules) does fail for a fork-only machine with the generic "not installed" error.
- No cleanup of stale specs whose code is already deleted (see Risks).
- `packages/electron/out/**` is build output and is not edited.
- Historical comments that only cite where a past baseline lived are allowed to stay: the `node-spawn.ts` jiti history, and `changelog-parser.ts`'s "formerly" note, which becomes a plain earendil reference. Executable code and messages may not name the fork.

## Decisions

1. **Remove the pi.dev latest-version path.** The alternative was to repoint it at earendil. Today `PI_DEV_PACKAGE` is the fork name, so earendil users already get npm-registry versions; removing the path keeps their effective behaviour unchanged. Repointing would turn on a new source that can report a version ahead of what `npm install <pkg>@latest` can install, and that divergence would then need its own spec. Delete `server/pi/pi-dev-version-check.ts` and its test (its only consumer is `pi-core-checker.ts`), along with `fetchPiDevRelease` in `PiCoreCheckerOptions`, `dynamicPiAliases` / `_resetDynamicPiAliases`, and the alias-intake branch. `changelog-remote.ts` mentions it only in a comment; reword that comment.
2. **The fork is rejected by omission.** `POST /api/pi-core/update` (`packages/server/src/routes/pi-core-routes.ts:78-92`) already answers `400 Unknown package(s)` for any name missing from `getStatus()`. Removing the fork from `CORE_PACKAGE_NAMES` is enough, so no new guard is added.
3. **Version reads are scope-agnostic; package lookups are earendil-only.** A single predicate `isPiCodingAgentName(name)` (`/^(@[^/]+\/)?pi-coding-agent$/`, exported from `packages/shared/src/pi-installs/candidates.ts`) replaces scope lists wherever a manifest name is tested rather than resolved. That covers `readRunningPiVersion` (`packages/extension/src/model-tracker.ts:203-224`, through the shared `readPkgVersionByWalkUp`) and `readPiEnginesFloor` (`packages/shared/src/platform/spawn-runtime.ts:214`, which today tests membership in `MANAGED_PI_PACKAGES`). Without the latter, a fork entry spawned from PATH would silently lose its `engines.node` floor. The dependency's below-floor requirement already says "nearest pi-coding-agent manifest". The `pi-version-skew.ts` registry fallback (`:99-113`) already reads whatever manifest the resolved `pi` binary realpaths into. A running fork therefore reports its true version and gets flagged, with no fork literal and no identity check. Only by-name resolution (`createRequire(...).resolve("<pkg>/package.json")`, managed/global probes) drops the fork. The alternative, keeping the fork name in `PI_PKG_NAMES`, would leave a fork literal in code. Dropping the fork without the scope-agnostic match would silently disable the flag for fork sessions.
4. **Collapse single-entry alias arrays only where it is simpler.** Keep the exported names `MANAGED_PI_PACKAGES` and `PI_PKG_ALIASES` as one-element arrays for their by-name consumers: the managed jiti-anchor walk (`binary-lookup.ts:402`) and the `pi-installs/*` location probes. Membership tests move to `isPiCodingAgentName` (decision 3). Inline the call-site-local loops (`pi-version-skew.ts` alias loop, `UnifiedPackagesSection.isPiCorePkg`) to a single name. `model-tracker.ts` follows decision 3. Keep `moduleDefWithAliases` in `definitions.ts`, passing one name per module.
5. **Spec mechanics.** openspec forbids a MODIFIED block that drops scenarios. Requirements whose fork scenarios must disappear are therefore REMOVED and re-ADDED under a new name, following the dependency change's precedent. This also covers the dependency's lockstep requirement, whose fork-accepting scenario would block archive. `dashboard-server` "Resolver supports upstream jiti package name" is REMOVED outright: it describes deleted resolver functions and contradicts the new loader error. Requirements where the fork appears only as an example (package-install, pi-core-version-ui) are MODIFIED in place with the earendil name.
6. **Error and install messages name only earendil.** `JitiNotFoundError` (`packages/shared/src/server-launcher.ts:41-45`) is the single loader error and is the one the bridge requirement refers to. It changes to "Is @earendil-works/pi-coding-agent installed?".
7. **Purpose text.** The `server-session-reader` Purpose names the fork, and deltas cannot change a Purpose. Edit `openspec/specs/server-session-reader/spec.md` directly in the same change.

## Risks / Trade-offs

- [A fork-only user upgrades and silently runs an unrecognised pi: no Packages entry, no update check, package-manager features fail with "not installed"] → **BREAKING** CHANGELOG entry with the one-line fix (`npm i -g @earendil-works/pi-coding-agent`). The dependency's below-floor flag is the runtime signal. The owner chose this over an identity check.
- [A machine with both forks still has `@mariozechner` on disk, which can collide on the `bin/pi` symlink] → Out of scope. The removed legacy-cleanup feature had handled it; the earendil-first `which("pi")` behaviour is unchanged.
- [Archive order: the piCompatibility MODIFIED block targets a requirement that only exists after `update-pi-core-1-0-adopt-apis` archives] → Task 1.1 gates on it. `openspec validate` passes now only because it skips MODIFIED/REMOVED blocks with no current target. Archiving this change first would fail at archive time; there is no silent mis-apply.
- [Stale specs still name the fork] → `bootstrap-install`, `dependency-installer`, `dashboard-server` "Bootstrap install lists exclude tsx", `electron-shell` and `electron-build-pipeline` describe contracts that `eliminate-electron-runtime-install` deleted or superseded: `bootstrapInstall`, `installStandalone`, `packages/electron/src/lib/dependency-installer.ts`, the offline cache, `offline-packages.json`, `resolveJitiFromPi`, and the managed-dir-only pi. `shouldUrlWrapEntry` itself is live, but its 0.70.x pin contract is not. Re-asserting them with a renamed package would codify dead behaviour, and the old texts already contradict each other on `tsx`. They are recorded as follow-up drift for a dedicated stale-spec change.
- [A test fixture or comment still names the fork, including split path forms like `"@mariozechner", "pi-coding-agent"`] → Task 6 sweeps every gate hit. The canonical gate matches per token (`@mariozechner(?![\\/]jiti)`), so it covers both path separators and is not fooled by a line that also contains `@mariozechner/jiti`.
- [Historical spec text] → `package-install` "Only the busy lock produces a 409" mentions the `@mariozechner → @earendil-works` rename as history. It is left as is.
- [`PI_SKIP_VERSION_CHECK` loses its only consumer with pi.dev] → Task 7.3 sweeps docs and AGENTS mentions. `PI_OFFLINE` still gates the remote changelog fetch.
- [The `legacyPiInstalls` field and allowlist entry predate this change] → They are removed anyway because they are fork-named protocol and test surface, which is this change's subject, not unrelated cleanup.

## Migration Plan

Single PR. There is no data migration, and the persisted config does not store package names. Rollback = revert the PR. The direct `## Purpose` edit to `openspec/specs/server-session-reader/spec.md` (decision 7) is part of the same commit, so a revert restores it too. The dependency change's floor is unaffected.
