### D2 — Card error label, ended sessions untouched (confirmed, owner, 2026-11-20)

`activityContent` gains a `hasError` arg (default `false`, so existing 3-arg callers/tests keep type-checking) and the exported `ActivityIndicator` wrapper gains a `hasError` prop; the card passes it at both render paths (desktop status row `SessionCard.tsx:1498`, mobile line 2 `:1246`), so mobile no longer prints `Idle` beside the error shape either. The label reuses the existing `common.failed` key (already in the hu/zh-CN catalogs; default text `Failed`) and the error glyph `statusShapeIcon.error` (`SessionCard.tsx:29`) tinted `--status-error` — `StatusGlyph`'s `status` prop widens to include `"error"`. This changes the enumerated label list of `session-card-header` (MODIFIED) and the "Idle" requirement of `ask-user-card-indicator` (MODIFIED, scoped to no-error). the `Failed` label replaces only the final `Idle` label (idle/active status with `hasError`): resuming, ended, needs-you, retry, current-tool and streaming keep precedence, because `lastError` persists across an agent continuation (`event-reducer.ts:1861`) and a live tool/thinking label is the more current fact. Ended sessions keep the ended-reason pill and the ended bucket (process gone is the more actionable fact). Alternative: route ended+error to the `error` lane — rejected for now (changes the lane spec "non-ended sessions" and dead-session triage).

### D3 — Visible failure for overlay claims

`SlotErrorBoundary` gains an optional `fallback` prop (default `null`, so every other slot is unchanged). `ShellOverlayRouteRender` does not build the boundary: it calls the module-private `renderClaim(claim, slotId, props, fallback)` whose 4th parameter is the **Suspense** fallback. `renderClaim` therefore gains a 5th optional `errorFallback` (default `undefined` → boundary renders `null`, all other callers unchanged) threaded to `SlotErrorBoundary`; `ShellOverlayRouteRender` passes the error panel with Back; the panel names the claim by its raw `claim.pluginId` (always available, no manifest lookup) and does not render the thrown error's message. `renderClaim` also returns `null` when `claim.Component` is undefined (`slot-consumers.tsx:105`): for overlay routes `ShellOverlayRouteRender` renders the same error panel in that case (`Component` is optional on `ShellOverlayRouteClaim`, `:957`). The loading state keeps the existing `ContentClaimSkeleton` (`content-claim-loading`, `aria-busy`); it is transient and already visible as a top-bar frame, so it is not replaced. Alternative: a generic non-null default for all slots — rejected, would surface errors in sidebar/badge slots.

### D4 — Chip address text (confirmed, owner, 2026-11-20)

Show `127.0.0.1:<port><path>` as secondary text: host is the fixed probe host (S29: never agent-announced), not chip data. The `127.0.0.1:<port>` part is `shrink-0`; only the path (and then the label) truncates, so the address never ellipsizes. The tooltip and `aria-label` are `<title> — 127.0.0.1:<port><path>` plus the existing probe hint (label-in-name). A root `/` (or absent) path is omitted from both the visible address and the tooltip, preserving current behaviour (`CanvasServerChip.tsx:33`), so visible text and accessible name stay identical. Alternative: keep bare `:port`.
### D5 — Board load state machine
`AutomationBoard` keeps `loadState` (`loading|error|ready`) replacing `loaded`: only the initial load (mount / `cwd` change) and Retry set `loading` first (blocking state). Mutation-driven `refresh()` bumps (`onDelete`, `onToggleEnabled`, `onRunNow`, `onStop`'s `finally`, `onCreated`) revalidate in place: `loadState` stays `ready` and the stale list stays rendered, so card-local state (`AutomationCard` `notice`, `stopPending`, history/menu/`expanded`) survives — e.g. the `doStop` notice set after `onStop`'s `finally { refresh() }` must still show. Implementation: Retry/initial reset `loadState` to `loading` explicitly (e.g. a separate `retry()` that sets `loading` then bumps `reloadKey`); `refresh()` only bumps `reloadKey`. A failed `fetchAutomations` (any trigger) sets `error`, clears the stale `automations` list and skips the two `listRuns` calls; success sets `ready`. A `cwd` change is an initial-load trigger that also clears the list; responses are applied last-request-wins (a request token/cancel guard in the existing effect, also covering Retry racing a mutation refresh), so a stale cwd-A result can never render under cwd B. `listAutomations` stays as-is for `FolderAutomationSection`, whose error-swallow is intentionally unchanged (out of scope).
