Error card: visible waiting · one Stop retrying · collapse, never vanish

v4 — pi owns the retry loop; the dashboard configures it and renders it. “Retry forever” is now just retry.maxRetries in pi's own settings, exposed in Settings below. There is no dashboard-side loop: re-driving a turn is impossible (resume mode:"continue" is refused for a live session and only reopens an ended one idle), and pi never settles the turn while its budget remains — so nothing needs re-driving. No phase mark, no error fingerprinting, and the waiting-between-attempts phase is finally visible.

what changed since v3 — all of it measured, not assumed
The phase mark is gone. There is only one retry phase (pi's), so there is nothing to disambiguate.
The 5–60 s ceiling is gone. pi's delay is baseDelayMs · 2^(n-1), hardcoded and uncapped; capping it needs an upstream change we cannot make. Robert's measured 5–60 s window survives only as the abort-latch.ts rationale, not as a schedule.
The one-shot Retry is gone. It needed the same missing re-drive mechanism.
Settings arrived. v3 said “zero settings”; the settings ARE the feature now.

Settings → Provider retry new — this IS the feature now

The exact inversion of v3. These are pi's own knobs, written merge-preserving to ~/.pi/agent/settings.json. Ships with pi's defaults, so installing the dashboard changes nothing until you opt in.

pi retries transient provider failures. Off = a turn dies on the first error.

pi default 3. No clamp — verified: maxRetries: 8 produced 9 attempts.

pi default 2000. The delay doubles every attempt and has no ceiling.

Delay before each attempt — total before the turn finally fails: 388.4 days
2 s → 4 s → 8 s → 16 s → 32 s → 1.1 min → … → 194.2 days
24 attempts keeps one turn alive for ~388 days. That is allowed — Stop ends it instantly — but the last gap alone is 194 days. Warned, never capped: a UI cap is bypassed by editing the file, so it buys nothing.
Global setting. Also applies to pi sessions you start outside the dashboard. Saving reloads connected sessions — pi reads its settings only at session construction, so a write alone would do nothing.

Deliberately not exposed: retry.provider.*. That layer honors the provider's own retry-after exactly — but emits no event and no callback, so the session would render as “streaming” for hours.

Lifecycle — one phase, pi's

 MEASURED event shape (pi 0.81.1) — one FULL agent turn per attempt:

   agent_start ─▶ message_end(error) ─▶ agent_end          attempt 1  ┐
   [sleep base·2^0]                                                   │
   agent_start ─▶ message_end(error) ─▶ agent_end          attempt 2  │ chain
   [sleep base·2^1]                                                   │
   agent_start ─▶ message_end(error) ─▶ agent_end ─▶ agent_settled   ┘ TERMINAL

 THE BUG THIS FIXES: the tracker treats each agent_end as terminal and wipes the
 pending failure, so observeMessageStart never fires → auto_retry_start emitted: 0.

 CORRECTED RULE
   error message_end   ─▶ record pending failure           (unchanged)
   error agent_end     ─▶ attempt over, ANOTHER IS COMING:
                          emit auto_retry_start + waiting signal,
                          nextAttemptAt = agent_end ts + base·2^(n-1)   → [B] countdown
                          (suppressed once attempt >= maxAttempts)
   agent_settled       ─▶ SOLE terminal signal: emit auto_retry_end, clear    → [E]

 "Stop retrying" / session Stop
   ─▶ ctx.abort() → AgentSession.abort() → abortRetry() cancels the sleep
      MEASURED: abort sent 15806ms into a 16s sleep → auto_retry_end at 15808ms (2 ms)
   ─▶ [E] settled. No Retry control.
 dismiss (✕) while pending ─▶ [D] COLLAPSE, never hide. Sticky for this chain only.
 dismiss (✕) once settled  ─▶ real clear.

Accepted consequence

Overshoot on long outages — up to ~1× the outage length. pi's delay doubles with no ceiling, so the next attempt always lands at roughly 2× elapsed time. For a 5 h quota reset at defaults, attempt 13 fires at 4.55 h (still locked out) and attempt 14 at 9.1 h — about 4 h late. This is scale-invariant: tuning baseDelayMs shifts which attempt lands where, never the ratio. A 60 s ceiling would fix it and needs a one-line upstream change we cannot make.
What is NOT a consequence any more: a deterministic failure does not loop forever. v3's dashboard loop re-drove anything without judging it; pi's own classifier still governs here, so a bad API key, insufficient_quota or a context overflow settles immediately instead of retrying.
