S1: Stop always works. When the engine has no record of a run (for example after a server restart) but run.json says running, the board marks it orphaned and explains why. Stop then falls back to the on-disk record: it kills by sessionId (or spawn token), finalizes the record as stopped, and frees the concurrency slot. Today's no-op becomes a confirmed result.

If the kill can't be confirmed (e.g. a Windows non-headless run), the record says "stop requested, process may still be running" and offers Force kill. It never claims success.
S2: runs survive a server restart (adds to S1). The engine saves sessionId and the declared completion event into run.json. At boot it rebuilds a lightweight run context. When the still-alive session reconnects, it is rebound instead of un-archived, so a later flow_complete finalizes the run normally (kill pi, archive the card). The UI only needs a run timeline that shows the restart honestly.
