## Decisions

### D1 (was D26 in add-multi-user-identity-plane) — Social-login broker: the dashboard is its own authorization server (oidc-provider)

Explored 2026-10-04 (supersedes the 18.22 `github-login` sketch in D22). Goal: an OAuth-authenticated admin connects the browser, the Electron shell and MCP/CLI clients **without device pairing**, using GitHub / Google, configured from a settings page.

- **Why a broker, not a GitHub/Google resolver.** GitHub is plain OAuth2 (no `id_token`, opaque tokens); Google tokens are not audience-bound to the dashboard; neither offers browser PKCE without a client secret or Dynamic Client Registration (needed for MCP clients). So no resolver can verify their tokens as dashboard credentials. The plugin brokers instead: upstream login (confidential, secret server-side) → dashboard-signed token → its own resolver verifies locally.
- **One issuer, one plugin (`social-login`).** Upstreams GitHub, Google and generic OIDC sit behind ONE issuer / signing key / JWKS. A single authorization server is what MCP clients expect; it also lets a user table link several upstream identities to one principal (same `(iss, sub)` whichever button was used). Per-provider plugins would mint N issuers ⇒ N principals per person.
- **Engine: `oidc-provider` (panva, OpenID-certified), embedded.** Mounted on Fastify via `@fastify/middie` (`fastify.use(prefix, provider.callback())`, documented for Fastify 5). Federated login runs in its *interaction* step: login page lists enabled upstreams → upstream code exchange (`openid-client` for Google/OIDC; plain `fetch` for GitHub `/login/oauth/access_token`, `/user`, `/user/emails`, `/user/orgs`) → allowlist → `provider.interactionFinished({ login: { accountId } })`. `findAccount().claims()` emits `sub`, `name`, `email`, `tier`. Library features reused: PKCE, `features.deviceFlow` (RFC 8628, CLI), `features.registration` (RFC 7591, MCP), refresh tokens.
- **Compared and rejected** (explore session): hand-roll on `jose` (cheap for browser-only, owns the whole AS surface — highest risk once MCP OAuth is in scope); better-auth (most batteries incl. passkey, but brings a DB + framework-owned user model, AS/MCP plugin maturity unverified); Dex (no dynamic registration, static connectors ⇒ no live settings page); Keycloak-as-broker (zero code, already works via the existing resolver, but external and not configurable from the dashboard — remains the answer when Keycloak already runs).
- **Client paths, no pairing.** Browser: existing D22/D25 handoff (descriptor `loginUrl`/`tokenUrl`). Electron shell: RFC 8252 native-app PKCE (system browser + loopback redirect). CLI: device flow. MCP: RFC 9728 protected-resource metadata on `/mcp` 401 → AS metadata (RFC 8414) → dynamic registration + PKCE. Paired-device bearers remain for devices without a user (headless bridges).
- **Tier.** Allowlist entries map to `observe|control|operate`: GitHub user / org / org-team, Google verified email / `hd` domain, OIDC claim value. No match ⇒ login refused (never a default tier). Re-checked at refresh so revocation lands within the access-token TTL.
- **Settings page.** Plugin settings section: per upstream enable, client id, client secret (masked; config file `0600`), the exact callback URL to register (copy control), allowlist → tier. Arming guard on top of D21: enforcement for this provider arms only after a successful **test sign-in** by an allowlisted `operate` user; an ephemeral public base (zrok without reserved share) is warned, because the registered callback would break.
- **Callback / issuer origin from configured public base, never `Host`** (18.34 open finding). `.well-known/oauth-authorization-server` + `openid-configuration` must resolve for the chosen issuer path.
- **Coexistence.** Legacy `auth.providers` disarms identity (D8); the settings page offers a one-shot import of existing GitHub/Google client id/secret/allowed users, then removes the legacy entry. Passkeys (`add-passkey-user-auth`) can later become another upstream of this broker.
- **Persistence.** oidc-provider needs an adapter (its in-memory one is dev-only): JSON-file adapter under `~/.pi/dashboard/` for grants/sessions/clients, signing keys `0600`, user/link table `{ userId, links: [{upstream, upstreamId}], tier }`.
- **Prerequisites.** `harden-trust-and-credential-boundaries` B5 (login CSRF/state + returnUrl) and B25 (config `0600`) land first — the broker makes OAuth the key to every client.
- **Open (spike 18.22a decides).** Can a plugin reach the root Fastify instance to register middie + root `.well-known`? Do the network guard (`trusted-networks` jurisdiction), the D24 identity floor and the route→tier map leave the public AS routes (`/authorize`, `/token`, `/jwks`, `/interaction/*`, `/reg`, device endpoints) reachable while everything else stays gated?
