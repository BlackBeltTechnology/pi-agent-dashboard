## Context

The client is a wouter SPA. Its routes:
- Session: `/session/:id`, `/session/:id/diff`, `/session/:id/editor`.
- Folder: `/folder/:encodedCwd`, `/folder/:encodedCwd/openspec`, `/folder/:encodedCwd/openspec/specs`, `/folder/:encodedCwd/openspec/:changeName/:artifactId`.

They are matched by `useRoute` calls in `packages/client/src/App.tsx` and `packages/client/src/components/shell/ShellContent.tsx:93-108`; archive routes come from `packages/client/src/lib/nav/useArchiveRoute.ts:28-30`. The server SPA fallback serves `index.html` for every non-API GET, so `BASE/session/<id>` deep-links work today (verified manually).

Current behaviour that matters:

## Goals / Non-Goals

**Goals**
- An agent that has only `BASE` and `GET /api/sessions` can open the right session view in its browser pane with no guesswork.
- A wrong or short deep-link id produces a visible, explained state, not a silent home redirect.
- A narrow pane shows the session, not the sidebar.

**Non-Goals**
- Server-side id-prefix resolution on REST routes (`/api/session/:id/*` stays exact-match).
- Resolving prefixes of archived sessions. Archived links need the full id; `/session/<prefix>?archived=1` is documented as unsupported.
- `uiUrl` on `GET /api/sessions/archived` rows. The skill documents `/session/<id>?archived=1` instead.
- MCP `list_sessions` (`packages/mcp-server-plugin/src/server/index.ts:100`, a separate implementation). Left for a follow-up.
- iframe embedding. CSP sends `frame-ancestors 'self'` (`packages/server/src/auth/csp.ts:51`). The Claude desktop pane is a top-level context: opening `BASE/session/<id>` in it rendered the chat, which a cross-origin frame would have blocked.
- Token-in-URL or one-time-link login.
- Changing the push payload `url`.
- Changing the not-found behaviour of non-session routes. Folder routes keep their existing rules.

## Decisions

### D1 — `uiUrl` / `diffUrl`: the origin the caller actually used

Each `GET /api/sessions` row gains two fields, computed in the route's response mapping after `filterOwned` and never stored:
- `uiUrl` = `<base>` + `sessionUiPath(id)`
- `diffUrl` = `<base>` + `sessionUiPath(id, "diff")`

The route also takes an optional `id` query parameter (D3 lookup):
- it must be a single string, otherwise the response is 400;
- it is lowercased;
- a row is returned when its lowercased id equals the value, or, for values of 8 or more characters, starts with it;
- the filter applies after `filterOwned`;
- without the parameter, the response is unchanged.

The response type becomes `ApiResponse<SessionListItem[]>` with `SessionListItem = DashboardSession & { uiUrl: string; diffUrl: string }`. `DashboardSession` itself is not widened, so the compiler enforces "no WebSocket change".

A pure `resolveRequestUiBase(input)` (`packages/server/src/routes/ui-link-base.ts`) computes `<base>`. Its inputs:
- the raw `Host` and `X-Forwarded-Host` headers;
- `request.protocol`;
- `configuredOrigins`: `resolvePublicBaseUrls(config)`, all live tunnel origins (the same `getLiveTunnelOrigins` provider host-admission uses), and `auth.redirectBaseUrl` when set;
- an `isAdmitted(host)` callback bound to `isHostAdmitted` with the server's current options;
- the server `port`.

Resolution:

1. **Configured match.** Normalize two candidate hosts with `parseHostname` (lowercase, port stripped): the first comma-separated value of `X-Forwarded-Host`, then `Host`. Take the first candidate that equals `hostnameFromUrl` of a configured origin and return that origin with its scheme and port. If several origins match, the first in the order listed above wins.
2. **Admitted direct host.** When `Host` passes `isAdmitted` (checked here even when the host gate runs in `report` mode), return `${request.protocol}://<host>[:<port>]`. `<host>` is the `parseHostname` result, re-bracketed when it is IPv6. `<port>` is parsed from the `Host` header's trailing `:digits` (after the `]` for IPv6), included only when it is numeric and in 1–65535, and dropped otherwise. The output never reflects the raw header bytes. Without `trustProxy`, `request.protocol` is accurate for direct connections, both the plain listener and the dashboard's own TLS listener (verified in Fastify `request.protocol`, socket-based).
3. **Otherwise** (no `Host`, or not admitted) → `${request.protocol}://localhost:<port>`. This is deliberately *not* `resolveRedirectBase`, which would hand the tunnel origin to an unadmitted caller in report mode.

The result never has a trailing slash.

**Why**
- A local agent gets `http://localhost:8000`.
- A tunnel or public caller gets the configured https origin, because its host matches.
- `X-Forwarded-Host` can only *select* a configured origin. It never mints one, and branch 2 reads only `Host`.
- **Reflection oracle (accepted).** A caller that sets `X-Forwarded-Host` by hand can probe which hostnames are configured origins, since a match is reflected back. Every such origin is already public:
  - the tunnel URL through the ungated `GET /api/tunnel-status` (`packages/server/src/routes/system-routes.ts:868`);
  - public bases, which by definition are advertised.
  No secret is exposed.
- `trustProxy` stays off, because the `request.ip` bypasses depend on it.

**Trade-off (accepted)** — an https reverse proxy that is *not* configured as a public base gets an `http://` link (branch 2). The fix is operator config: add the origin to `publicBaseUrls`. This is documented in the reference.

**Rejected**
- "Any proxy-forwarding header plus a live tunnel → tunnel URL", with no host match. `localhost-guard.ts:28-34` treats those headers as untrusted evidence of a proxy hop, and this rule would pick an origin from mere header presence rather than from a named host.
- A relative path only. It is still the documented fallback (`BASE` + `/session/<id>`), but the user asked for an absolute link that works through a tunnel.

**Gate (task 2.1)** — zrok's Host / `X-Forwarded-Host` behaviour has not been verified. If a live share carries the share host in neither header, branch 1 cannot select the tunnel and tunnel callers get a localhost link. In that case `ship-it` hands back (`SHIP_IT_BLOCKED.md`) for a design revision. There is no silent fallback.

**Gate result (task 2.1, passed)** — a live `zrok share public` (v2, `shares.zrok.io` frontend) to a header-echo listener showed `Host: <share>.shares.zrok.io` (the share host, no port), no `X-Forwarded-Host`, and `X-Forwarded-Proto: https`. Branch 1 therefore matches on `Host`; the `X-Forwarded-Host` candidate stays as a harmless extra for other proxies. The spike share and listener were torn down afterwards.

### D2 — Shared `sessionUiPath(id, view?)`

`packages/shared/src/session-ui-path.ts` exports `sessionUiPath(id, view?: "diff" | "editor")`, which returns `/session/${encodeURIComponent(id)}` plus `/${view}`. It is pure and has no base.

- `add-ntfy-push-transport` can reuse **only this path helper**. Its base precedence (first public base, else tunnel, else no `absoluteUrl`) is deliberately not request-derived.
- Client navigate calls are untouched.

### D3 — Resolution in App: sticky canonical id, server lookup on a miss, not-found for unknown ids

App owns a single hook, `useSessionRouteResolution(routeId)`. Its inputs are the raw route id (from the `/session/:id`, `/diff` or `/editor` match), `sessions`, `snapshotGeneration` and `archivedReadOnlyId`. `archivedReadOnlyId` is now derived from the **raw** param, so it does not depend on the hook's own output.

It returns `{ status, canonicalId?, candidates? }`, where `status` is one of `pending`, `ok`, `ambiguous`, `notFound` or `vanished`. A pure `resolveSessionRouteId(routeId, ids)` (D4) does the matching.

Per **route visit** (the raw route id is unchanged), the hook keeps:
- `resolvedRef`: the last canonical id, sticky across reconnects and server switches;
- `wasHeldRef`: whether that id has ever been in `sessions` during this visit.

Order:
1. **Archived.** `archivedReadOnlyId` set → `ok` with `canonicalId = routeId`. This is unchanged; the archived path hydrates by exact id.
2. **Match against held `sessions`.** An exact or unique-prefix match → `ok`.
3. **Snapshot not yet received for this connection** (`snapshotGeneration === 0`):
   - with `resolvedRef` set → `ok` with `canonicalId = resolvedRef`. A reconnect never blanks an open session.
   - otherwise → `pending`.
4. **Miss after the snapshot → server lookup.** Issue one `GET /api/sessions?id=<routeId>` per route id per connection (D1) and stay `pending` while it is in flight. With `resolvedRef` set, stay `ok` instead.
   - Returned rows have `notifyLog`, `uiUrl` and `diffUrl` stripped, matching the snapshot / page row shape (`stripNotifyLog`).
   - They are merged into `sessions` only: overwrite by id. `sessionOrderMap`, `endedTotals` and paging state are not touched.
   - Merged ids join a `lookupOnlyIds` set. The paging offset and the held-ended count compared with `endedTotals` exclude them (session-listing "Looked-up sessions do not affect paging"). Otherwise the next `sessions_page` offset would shift and skip a session. An id leaves the set when a `sessions_page_result` or snapshot delivers it.
   - Resolution then reruns. This closes the windowed-snapshot gap: an older ended session that `GET /api/sessions` lists is reachable by its `uiUrl`, also after a reconnect drops it again from the replaced Map.
   - **401 / 403** → the existing auth-loss path (`loginRedirectFor`), not not-found.
   - **Network failure or 5xx** → `notFound` with a retry hint. It never redirects.
5. Several matches → `ambiguous`.
6. No match, **only after this connection's lookup has returned empty**:
   - if `wasHeldRef` is set → `vanished`, and App performs `navigate("/", {replace:true})`. This keeps today's redirect for a session archived while viewing, and for a server switch to a server that does not know the id.
   - otherwise → `notFound`.

**Pending render.** A neutral placeholder (`data-testid="session-resolving"`) shows in the session content area. It is never the landing page and never the not-found state.

**Canonical selection.** `canonicalId` is the held (live-cased) full id when `status === "ok"`, and `undefined` otherwise. It is computed **synchronously during render**, not in an effect, and replaces the raw route id at every reader:
- `selectedId` (the `deriveSelectedSessionId` call site, `App.tsx:672`);
- `selectViewedSessionId` (`:699`);
- `diffSessionId` / `editorSessionId` (`:617-618`), which feed the desktop `FileDiffView` (`:2537`) and the editor pane;
- `ShellContent`, through a new `sessionRoute` prop. `ShellContent` passes `canonicalId` to `renderSession`, `renderDiff` and the editor renderer, and renders `renderSessionNotFound` / the pending placeholder for the other statuses. This includes the mobile diff branch (`ShellContent.tsx:149`).

The desktop App-level diff and editor branches render the same not-found / pending arms. Subscription, history loading, drafts, mark-read, the viewed tracker and the diff fetch therefore never see a prefix or a mis-cased id.

**Cost (accepted).** A full-id deep link on a fresh page subscribes once the snapshot arrives, not at socket open. The snapshot is the connection's last bootstrap frame, so the delay is one frame. Reconnects are unaffected because the id is sticky.

When `canonicalId` differs from `routeId` (a prefix or a different case), an effect performs `navigate(<path with canonicalId + original suffix + original query>, {replace:true})`. The nav tracker overwrites its stack top on replace.

**Scope.** Only `/session/:id`, `/session/:id/diff` and `/session/:id/editor`. Other routes keep their rules.

`SessionNotFound` shows:
- a "Session not found" heading;
- the id in monospace;
- a hint that full ids come from `GET /api/sessions` and archived sessions open with the full id and `?archived=1`;
- candidate links when the prefix is ambiguous;
- a retry action after a failed lookup;
- a "Back to sessions" control (`navigate("/")`);
- `data-testid="session-not-found"`.

**Why not a redirect with a toast** — the agent observes the page through snapshots and screenshots. A redirect erases the evidence. This also follows the existing OpenSpec-preview precedent ("render a Not found inline component … NOT redirect").

**Why a REST lookup, not a WebSocket message** — `GET /api/sessions` already lists the full non-archived registry with the owner filter. An `id` filter is the smallest addition and keeps the "no WebSocket protocol change" invariant.

### D4 — Matching rules (`resolveSessionRouteId`)

- An exact match on the raw `routeId` wins.
- Otherwise compare case-insensitively: lowercase both `routeId` and each held id.
  - An exact case-insensitive match → that id.
  - Else, when `routeId.length >= 8`, collect held ids that start with it:
    - exactly 1 → that id;
    - more than 1 → `ambiguous`.
- Fewer than 8 characters → no match.
- The returned id is always the held (live-cased) id.
- The server lookup (D1 `id` parameter) applies the same 8-character floor and lowercasing, so client and server agree.

If a later `sessions` update turns a unique prefix ambiguous before the replace effect runs, resolution re-renders as `ambiguous` and no navigation happens.

**Why ≥ 8** — a stable floor. A shorter paste never silently lands on an unrelated session as more sessions appear, and the first UUID group (8 hex characters) is what an agent naturally copies.

### D5 — Embed mode: `?embed=1`, sticky per tab, list content swapped in both shells

`useEmbedMode()` (`packages/client/src/hooks/useEmbedMode.ts`) reads `embed` from the search on every location change:
- `1` → `sessionStorage["pi-dash-embed"]="1"`;
- `0` → remove the key;
- returns whether the key is present.

When it is on, App keeps the **viewport's own shell** (mobile or desktop, chosen by `useMobile()` as today) and changes only where the session list appears:

- **Desktop branch.** Omit the `hidden md:flex` `ResizableSidebar` wrapper, `HamburgerButton` and `MobileOverlay`. The content column is unchanged: `connectionBanner`, `ShellContent`, `ShellOverlayRouteSlot`, settings, the route-backed overlay container and dialogs.
- **Mobile branch.** `MobileShell` still renders with the same depth and back navigation and all root banners and hosts (`PluginStalenessBanner`, the full `ConnectionStatusBanner`, `Toast`, `SpawnErrorToastHost`, …). Its list panel shows the **embed home message** instead of the install / missing-required banners and the session list. At depth ≥ 1, the detail panel is unchanged.
- **Home.** At `/` on desktop, the content-area home placeholder becomes the same embed home message ("No session selected") with the exit control.
- **Exit.** An "Open full dashboard" control (`data-testid="embed-exit"`) navigates with **replace** to the current path with the current query, with `embed` replaced by `embed=0`; `archived`, `focus` and other parameters are kept. On mobile it is shown in the embed home message and the detail header area.

So every client route, plugin overlay and route-backed overlay works in embed. The mobile-layout requirements keep holding: `MobileShell` with list and detail panels and depth. The only spec change is the desktop sidebar omission and the list-panel content swap (MODIFIED `app-decomposition` "Layout component extraction").

**Accepted trade-offs**
- **Back button.** The depth-1 back action still goes to `/` per the unmodified back-action table, which lands on the embed home message: a dead end with an exit link, not a broken state. On mobile, the swipe-back gesture does the same.
- **Hidden list-panel banners.** In mobile embed, the list panel's `InstallBanner` and `MissingRequiredBanner` are not shown.
- **Inherited flag.** `sessionStorage` is copied into tabs opened *from* the embed tab (`window.open`, `target=_blank` with an opener, duplicated tabs). Such tabs inherit embed mode until `?embed=0`. Independent tabs never do.

**Why query plus stickiness, not `/embed/session/:id`** — in-app navigation (the diff button, file links, `navigate("/session/…")` after spawn) builds unprefixed paths, so a route prefix would be lost on the first click and every route would need a duplicate.

**Why not the `chat-embed` barrel** — that is a source-import contract for sibling workspace bundles (`docs/embedding-chat-view.md`). This is the dashboard app itself with the session list removed, so it reuses the same `ChatView` through the existing render path, with no second provider tree or WebSocket.

**Login.** Two paths, both keeping the flag:
- Mid-page auth loss uses `loginRedirectFor(status, pathname, search)` (`packages/client/src/lib/identity/login-session.ts:166`), which preserves path and query.
- The OAuth flow carries `return=` / the stashed return-to (oauth-authentication "Login with return URL", browser-principal-client "Pre-auth callback mount and return-to restore").

Independently, the flag lives in this tab's `sessionStorage`, which survives a same-tab OAuth round trip. No credential is ever placed in the URL.

## Risks / Trade-offs

- **Host reflection (D1)** → a configured origin is chosen only on a normalized host match, and a direct host only after `isHostAdmitted`, including in report mode. Unit-tested with spoofed and multi-value `X-Forwarded-Host`, ports and mixed case.
- **http link behind an unconfigured https proxy** → accepted; documented operator fix.
- **zrok header behaviour unknown** → gated by spike 2.1, which hands back on failure.
- **Sticky embed** → per-tab, inherited only by opened-from tabs, with a visible exit and `?embed=0`.
- **Prefix collision** → ≥ 8-character floor, ambiguity listing, exact match wins, re-evaluation on `sessions` change. Resolution covers the whole registry through the server lookup, not just the snapshot window.
- **UUIDv7 prefix collisions** → session ids are UUIDv7: the first 8 hex characters are the top 32 bits of a millisecond timestamp, so sessions created within about 65 s share them (seen in the L3 harness). The 8-character floor therefore resolves only when the prefix is unique; otherwise the not-found state lists the candidates. The reference tells agents to prefer `uiUrl`. Not a defect of the rule, but "first UUID group is what an agent naturally copies" does not give uniqueness.
- **Delayed subscribe** → a fresh full-id deep link waits for the snapshot (one frame). Reconnects keep the sticky id.
- **Looked-up rows outside the order map** → a later `sessions_page_result` that contains the id must still place it in order. Pinned by a test (task 3.x).
- **Redirect semantics** → `url-routing` "Deep-link session on refresh" is modified. The vanish-while-viewing redirect is kept and pinned by scenarios. `add-persistent-onboarding-card` only navigates to ids it just received, which are live.

## Migration Plan

All changes are additive except that the deep-link redirect is replaced by a not-found state for unseen ids. This is client-only, so no data migration is needed. Rollback = revert. REST consumers ignore unknown fields.
