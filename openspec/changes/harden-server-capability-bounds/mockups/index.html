A. Terminal limit reached

Today a rejected create_terminal is a server log line only: the user clicks "+" and nothing happens (Nielsen #1 visibility of status, #9 help users recover). Proposal: a dismissible inline notice directly under the tab bar, naming the scope, the limit and what to do. Needs one new server-to-browser message, terminal_limit_reached {scope, limit}. Idle-reaped terminals reuse the existing terminal_removed path: the tab simply disappears, no new UI.

zsh - pi-agent-dashboard zsh - docs
~/Project/pi-agent-dashboard $ npm test
A2 per-folder cap rejected
zsh 16 zsh 15
!
Terminal limit reached for this folderThis folder already has 16 terminals (the maximum). Close one you no longer need, then try again.
~/Project/pi-agent-dashboard $ (no new terminal was started)
A3 global cap rejected (other folder)
zsh - api
!
Terminal limit reached32 terminals are open across all folders (the maximum). Close one in any folder, then try again. Terminals nobody is attached to are closed automatically after 6 hours of silence.
~/Project/api $

Rules: notice is role="status" (polite, not an alert), uses --severity-warning-* plus a "!" glyph (never colour alone), stays until dismissed or the next successful spawn, and is not stacked: a second rejection replaces it. The "+" is never disabled, because the client does not know the server cap in advance.

B. Folder picker at the allowed-root boundary

Browse is now limited to $HOME and pinned folders. Three things change for users: (B1) at a root there is no .. row, so the picker must say why; (B2) a typed path outside the roots needs a plain-language refusal instead of a raw red path outside allowed roots; (B3) you chose a "Request access" affordance, mocked here by reusing the existing cwd-plane grant dialog (its copy already reads "This directory is not pinned..."; Allow always = pin). That needs a server change not in the current spec: a refused browse must raise a grant request instead of only a 403.

C. Recovery page refusal

The recovery page is server-rendered with its own inline style (no client bundle, no tokens at runtime). Its buttons post to the gated actions. If the page was reached through a tunnel or a rewritten Host, today the user sees the bare 403 text in a grey line. Proposal: keep the same status line, but say what is wrong and the fix, and re-enable the buttons.
