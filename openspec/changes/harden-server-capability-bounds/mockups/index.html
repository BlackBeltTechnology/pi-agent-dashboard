harden-server-capability-bounds: UX surfaces

A Terminal cap B Remote folder picker C Recovery

A. Terminal limit reached

Today a rejected create_terminal is invisible: the user clicks "+" and nothing happens (Nielsen #1 visibility of status, #9 help users recover). Proposal: a dismissible inline notice directly under the tab bar, naming the scope, the limit and what to do. Needs one new server-to-browser message, terminal_limit_reached {scope, limit, cwd, inline}, sent to the requesting socket only. Tab terminals are never reaped: detached shells (dev servers, watchers) live until the user closes them, so the notice asks the user to close one. Only orphaned inline cards (no viewer for 10 min) are reaped, through the normal exit path (card freezes with its transcript).

A1 normal under the cap
zsh - pi-agent-dashboard zsh - docs
~/Project/pi-agent-dashboard $ npm test
A2 per-owner cap rejected (multi-user only)
zsh 16 zsh 15
!
You have reached your terminal limitYou already have 16 terminals open (the maximum per user), across all folders. Close one you no longer need, then try again.
~/Project/pi-agent-dashboard $ (no new terminal was started)
A3 global cap rejected
zsh - api
!
Terminal limit reached32 terminals are open on this dashboard (the maximum), including inline terminal cards. Close one in any folder, then try again.
~/Project/api $

Rules: notice is role="status" (polite, not an alert), uses --severity-warning-* plus a "!" glyph (never colour alone), stays until dismissed or the next successful spawn, and is not stacked: a second rejection replaces it. The "+" is never disabled, because the client does not know the server cap in advance. While the identity plane is inert (single user) only the global cap applies, so A2 never appears. An inline-terminal card refused at the cap shows the same notice text in the chat card slot.

B. Folder picker over a tunnel / paired device

Confinement applies only to requests that are not genuinely local (tunnel, LAN, relayed loopback). On the machine itself the picker is unchanged: no hint, no refusal, .. up to /. Remotely, browsing is limited to the shared folders: $HOME, pinned folders, folders with sessions, folder-workspace and worktree-init roots, and access grants. Two remote-only states: (B1) at the top of a shared folder there is no .. row, so the picker says why; (B2) a typed path outside the shared folders gets a plain-language refusal instead of a raw path outside allowed roots. No "Request access": a remote device must not grant itself access.

B1 remote, at $HOME top of a shared folder
📂 /Users/robson
CONTENTS
📁 Project ›
📁 Documents ›
📁 Downloads ›
iFrom this device you can browse the folders this dashboard shares. To use another folder, pin it on the host.
B2 remote, refused typed path outside the shared folders
(!)/ is outside the folders this dashboard shares. Ask the host to pin it.

Contract: the browse response carries confined: true when the request was confined, and parent: null at a shared-folder top; the picker shows the B1 hint only when confined and parent === null. A 403 path outside allowed roots maps to B2. A refused mkdir ("New folder") shows the same B2 text inline.

C. Recovery page refusal

The recovery page is server-rendered with its own inline style (no client bundle, no tokens at runtime). Its buttons post to the gated actions. If the page was reached through a tunnel or a rewritten Host, today the user sees the bare 403 text in a grey line. Proposal: keep the same status line, but say what is wrong and the fix, and re-enable the buttons.
