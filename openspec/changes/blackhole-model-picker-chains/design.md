## Context

See proposal.md — Why. Current state that shapes the approach:

- `ChainEditor.tsx` is index-addressed over `ModelRef[]`; `chain-model.ts` already owns the pure algebra (`readChain`/`writeChain`/`moveEntry`/`removeEntry`/`canRemove`/`normalizeModel`). There is no append operation and no add control.
- `BlackholeSettings.tsx` holds `draft.baseModel` and passes it to every `ChainEditor` as the tail; `buildPayload` already emits `model` (with `null` = unset) when it is file-set or user-edited. Only the UI for editing it is missing.
- The roles plugin is the reference consumer of the paired picker: `useUiPrimitive(UI_PRIMITIVE_KEYS.modelSelector)` (`current: "provider/id"`, `models: ModelInfo[]`, `onSelect(label)`) + `useUiPrimitive(UI_PRIMITIVE_KEYS.thinkingLevelSelector)` (`current`, `supportedLevels?`, `onSelect(level)`). Its model list arrives via `usePluginConfig` from a WS `models_list` targeted at the roles plugin — not reachable from another plugin.
- `GET /api/models` (`models-introspection-routes.ts`) serves the registry session-free: `{ object: "list", data: [{ id: "provider/id", provider, reasoning?, contextWindow?, thinkingLevelMap?, ... }] }`. 503 when pi-ai is unresolvable.
- `ModelRef.thinking` enum is `off|minimal|low|medium|high|xhigh` (blackhole's own); the level primitive's canonical set is the same; the roles plugin treats `off` as "no override".
- Server validator (`validateBlackholeConfig`) and `PUT` are unchanged — the client keeps sending the same `ModelRef` shape.

## Goals / Non-Goals

**Goals:**
- Make an empty or one-deep chain repairable from the page in under a minute, with model ids that are guaranteed to exist in the registry.
- Reuse the shell's picker primitives so the blackhole page looks and behaves like the roles page.
- Keep the security boundary where it is (server validator); no new write path.

**Non-Goals:**
- Writing `~/.pi/agent/settings.json` or any file other than `pi-blackhole-config.json`.
- A free-text escape hatch for models absent from the registry (explicitly declined by the user; an existing off-registry entry is preserved, not editable by id).
- Cross-plugin sharing of the roles plugin's model list.
- Changing blackhole's resolution semantics or the `sessionFallback` tail.

## Decisions

**D1 — Model list source: `GET /api/models`, fetched by the blackhole client.**
Rationale: session-free (works with zero live pi sessions, which is exactly when a user is repairing config), already exists. It is NOT the same list the roles plugin shows (roles reflects the live session's registry via the bridge; `/api/models` is the server-side registry filtered by `getAvailable()` credentials) — see Risks. Mapping: row `id` is `provider/id` → `ModelInfo { provider, id: id.slice(provider.length + 1), reasoning, contextWindow }` (slice by provider length, never split on `/` — ids may contain slashes). Write direction: `onSelect(label)` resolves the picked row by exact match `find(m => \`${m.provider}/${m.id}\` === label)` against the fetched list, never by string-splitting the label. `thinkingLevelMap` is NOT consumed (it is a sparse override table whose canonical derivation lives in `provider-register.ts` under the single-derivation guard; a second copy would drift). Alternatives: (a) push `models` into the blackhole plugin config via `models_list` — requires a live session and server plumbing; (b) new plugin route proxying the registry — duplicate of an existing route. Fetch lives in `blackhole-api.ts` as `getModels()` returning a discriminated result (`ok | unavailable`), consistent with `getConfig`'s "a failure is a RESULT" style.

**D2 — Registry state is four-state and gates controls, never hides entries.**
`pending | ok | empty | unavailable` (`empty` = 200 with `data: []`, i.e. zero credentialed models). Registry-dependent controls = the add control, the base-model picker, every per-entry model picker, and the defaults action. In `pending`, `empty`, `unavailable` all of them are non-interactive. The shell `ModelSelector` is deliberately clickable with an empty/undefined list (it opens its own catalogue-recovery body and fires a session-scoped `request_models`, pinned by `ModelSelector.test.tsx` 1.1/1.2), so the primitive is **not mounted** outside `ok`: the plugin renders the stored `provider/id` as its own plain-text span (`data-testid="blackhole-chain-<worker>-<i>-model"`), and the add control / base-model row render a disabled plugin-owned button. The primitive is mounted only when the registry is `ok`. `unavailable` renders a message + retry; `empty` renders a distinct message ("no credentialed models in the registry") without retry. Per-entry `thinking`, `cooldownHours`, `contextWindow`, move and remove stay editable in every state. Existing entries always render from stored values. Rationale: the page must never make a saved config look emptier than it is (same doctrine as the parse-error state: don't fabricate).

**D3 — Picker `current` is the stored `provider/id` even when off-registry.**
`ModelSelector` accepts any `current` string; it shows it as the trigger label without requiring a match. An off-registry stored entry therefore survives round-trips untouched until the user explicitly picks a replacement. Each entry's picker is wrapped in a labelled group (`role="group"`, accessible name "Model for <worker> entry <n>") because the primitive exposes no label prop; this replaces the removed `mProvider`/`mModelId` labels for a11y and tests.

**D4 — Thinking mapping: plugin-local override toggle + shell level picker.**
The shell `ThinkingLevelSelector` renders `current ?? "off"` and only ever emits a concrete level — it has no placeholder/inherit state. So each entry gets a plugin-local checkbox "Override thinking level": unchecked → `thinking` absent (via `normalizeModel`, which omits `undefined`) and the level picker is not rendered (text "inherit"); checked → `thinking` initialised to `"off"` (what the primitive would display anyway) and the level picker is rendered with `current = entry.thinking`. `off` is a real blackhole level, so it is written verbatim. `supportedLevels` passed to the primitive is always clamped to blackhole's own six-level `THINKING_LEVELS` (never `max`, which the server validator rejects); when the picked registry row reports `reasoning: false` it is `["off"]`. No other per-model level derivation is done (see D1). On a model pick: if the new row is non-reasoning and the entry's `thinking` is not `off`, `thinking` is cleared (toggle off) and a per-entry notice is shown (mirrors `roles-level-drop-notice`); `contextWindow` is always cleared on a model pick (a per-model override does not transfer to a different model); `cooldownHours` is kept.

**D5 — Add-entry flow and empty state.**
The add control (accessible name "Add model to <worker> chain") reveals a single model picker — only the model picker, no level/number fields — in an "adding" row beneath the list; the entry `{ provider, id }` is appended (`appendEntry(entries, ref)` in `chain-model.ts`) on the pick and the adding row closes, so a cancelled add never creates a half-entry and there is nothing to bind a level or number to before a model exists. The user then edits the new entry like any other. When `entries.length === 0` the list is replaced by an empty-state line (`data-testid="blackhole-chain-<worker>-empty"`, i18n key `chainEmpty`) stating the worker currently resolves to the base/session tail only, followed by the add control. `appendEntry` on an empty chain yields a one-entry chain, which `writeChain` already maps to `<worker>Model`. Rationale: index-addressed editor stays index-addressed; no placeholder entries with blank ids that the server validator would reject.

**i18n rule (all decisions).** Every new user-visible string — empty state, registry unavailable/empty messages, retry, override-thinking label, level-drop notice, add control, defaults action label/explanation/fewer-than-3 copy, confirm-dialog text, "not listed?" copy — goes through `i18n.ts` with `zh-CN`/`hu` keys plus the inline English fallback at the call site (`t(key, vars, fallback)`; parity enforced by `scripts/i18n-parity.mjs`). Accessible names (`aria-label`) follow the existing `ChainEditor` convention.

**D6 — Recommended defaults are a pure function of the registry.**
`recommendedDefaults(models: ModelInfo[]): { chain: ModelRef[]; found: boolean }` in `chain-model.ts`: rank each model by first matching `/flash/i` → 0, `/haiku/i` → 1, `/mini/i` → 2 on the bare id (non-matching rows dropped); dedupe by `provider/id`; stable-sort by rank preserving registry order; select greedily preferring a provider not yet selected (so a single provider's 429/quota does not exhaust the chain), then if fewer than 3 were selected fill from the remaining ranked rows; cap 3; each entry `{ provider, id, cooldownHours: 1 }` (no `thinking`, no `contextWindow`). When fewer than 3 are staged the page copy says so. Applied to the draft as: `observer|reflector|dropper` chains = same array (fresh copies), `debug = true`, `debugLog = true`; nothing else touched. Confirmation dialog via `ui:confirm-dialog` when any chain is non-empty. Dirty state stays payload-derived (`buildPayload` vs baseline): if the file already equals the staged result the action is a no-op and Save stays disabled — accepted, the spec scenario is worded for a differing draft. Rationale: the earlier failure was an empty chain; the value is resilience (≥2 flash-class candidates), not a specific vendor. Hardcoding `gemini-3.8-flash` would rot and would fail on instances without that credential. Alternatives: cost-based ranking from `cost` — not consistently populated; declined.

**D7 — Base model control lives above the chains, once.**
A single model-picker row for `model` (no thinking toggle — the base model carries no `thinking` today and this change does not add one) with a clear control (writes `draft.baseModel = null`). Emission follows the existing `shouldEmit` rule unchanged: when `model` was set in the file (`userSet` has it) `buildPayload` emits `model: null` → server unsets; when the file never had `model`, clearing an untouched unset value emits nothing, which is correct — there is nothing on disk to unset. The tail rendering in `ChainEditor` is unchanged and reads the draft, so it reflects an unsaved pick immediately (the spec's "and saves" scenarios assert the written value, not the tail timing). Rationale: it is one shared key; editing it inside each chain's tail would imply per-worker scope.

**D8 — Tests are L1 component + pure tests; no new server tests.**
`chain-model.test.ts`: `appendEntry` (empty → primary; non-empty → last fallback), `recommendedDefaults` (ranking, dedupe, distinct-provider preference then fill, cap of 3, empty registry → `found: false`, no mutation of input). `ChainEditor.test.tsx`: add flow (model-only adding row, cancel leaves chain unchanged), empty state, picker-backed provider/id via exact-match lookup (slash-bearing id), off-registry entry preserved, thinking override toggle (absent ↔ `off`), non-reasoning row → `["off"]` + drop notice, `contextWindow` cleared on pick, registry gating in `pending|empty|unavailable`, keyboard/a11y names on the add control and entry groups. `BlackholeSettings.test.tsx`: base-model set/clear payload (file-set → `model: null`; never-set → key absent), defaults action stages + dirty + confirm path, disabled-with-explanation when no candidate, `GET /api/models` mocked in all four states. Payloads round-trip through the real `validateBlackholeConfig` as the existing tests do.

## Risks / Trade-offs

- [`GET /api/models` returns 503 when pi-ai is unresolvable, and `getAvailable()` filters by credential] → D2 unavailable state; the page still edits everything that does not need the registry. Retry control re-fetches.
- [Registry lists a model the extension's own resolver cannot use (e.g. proxy-only provider)] → blackhole cools it down and moves on; the defaults action prefers distinct providers so one dud does not exhaust the chain. Documented in the page copy next to the action.
- [Inverse divergence: a model a pi session CAN resolve but the dashboard's `getAvailable()` cannot credential is NOT listed, and free-text entry is declined scope] → that model cannot be configured for blackhole from this page; the stored entry is preserved (D3) if it was hand-written. Accepted trade-off; the page copy under the picker names it ("not listed? the dashboard has no credential for it").
- [Ranking heuristic picks an unexpected "flash" model on exotic registries] → the staged chain is visible and editable before save; nothing writes until Save. `doubt-driven-review` before landing D6.
- [Removing free-text inputs breaks a user who relied on typing an unlisted id] → explicitly declined scope; stored off-registry entries are preserved (D3). Noted in the change log.
- [Same chain for all three workers is not optimal per worker] → it is a starting point, labelled as such; each chain remains independently editable afterwards.
- [`thinking: "off"` vs inherit ambiguity] → D4 makes inherit a plugin-local toggle state, visually distinct from `off`; tests pin both writes.

## Migration Plan

No data migration; on-disk shape unchanged. Deploy = client build + `/api/restart` (plugin client bundle). Rollback = revert the change; a config written by the new UI is valid for the old UI (it only ever emits the existing `ModelRef` shape).
