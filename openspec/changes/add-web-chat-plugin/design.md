## Goals / Non-Goals

**Goals:** customer chat from a third-party site; per-customer isolation from the operator and from each other; read-only knowledge + business data; human handover; operator control and visibility; fail closed on any missing prerequisite.

**Non-Goals:** customer write actions in business systems; customer file upload; multi-tenant (several businesses) in one plugin instance; voice; operator live takeover of a customer conversation (escalation hands over by ticket, not by session control); a separate dashboard instance (user decision: same instance).

## Decisions

### D1 — Architecture: standalone `web-chat` plugin (DECIDED: A, doubt review cycle 1, both reviewers)
- **A. Standalone plugin (chosen).** Customer-specific auth, isolated spawns, egress allowlist, widget, escalation inbox, own policy plugin. Shared logic stays copies of small pure functions (guard predicate, frame filter — spike precedent), not a shared behavioural package.
- **B. `web` adapter in chat-gateway (rejected).** Chat-gateway's chokepoint is L1 allowlist/pairing (`packages/chat-gateway/src/server/auth.ts:44-47`) + tiers with `observe` as floor (`src/server/team/team-config.ts`, `authorize.ts`) + `allowedRoots` workspace binding (`src/server/binding.ts`) + tool approval by the chat user (`src/adapters/base.ts` `userId` on interactive responses). Customers need the opposite on each axis (no enrollment, sub-`observe`, no approval path, ownerless isolated spawns), so B would put a second trust model into the gateway's single authorization path and change its spawn model; a regression there would expose operator chat-platform control to unauthenticated externals. `PlatformAdapter.start(callbacks)` is also platform-shaped, not HTTP/SSE-shaped.
- Revisit only if a second customer channel needs the same shape — then extract a customer-session library, still not a gateway adapter.

### D2 — Customer identity: two modes, one customer id
- `identity` mode: widget sends `Authorization: Bearer <OIDC access token>`; host resolves; customer iff `principal.iss ∈ config.customerIssuers` (exact). Non-customer principals (operators) are refused by the public API (`403`) so an operator token never creates customer sessions.
- `token` mode: business backend mints `wct1.<base64url(json)>.<base64url(hmac)>` with HMAC-SHA256 over a secret stored in `ctx.credentials` (key `token-secret`, ≥32 bytes, rotatable with one previous secret accepted for 24 h). Claims: `sub` (1–128 chars), `iat`, `exp` (`exp − iat ≤ 900 s`), `aud = "web-chat"`, optional `name`. Clock skew ±60 s. Sent as `X-Web-Chat-Token`. Customer id = `("web-chat-token", sub)`.
- Both ⇒ `CustomerId = { iss, sub }`; registry keys on `sha256(iss + "\n" + sub)`.

### D3 — Serving gate (fail closed)
Public API answers `503 {code}` unless: plugin enabled; for each enabled mode its prerequisites hold — identity: `ctx.identity.isEnforced() && ctx.identity.hasHostPolicy?.() === true && customerIssuers.length > 0`; token: secret present — and model credential configured; and the prerequisite seams are present (activation-time member detection: `ctx.dataDir`, `registerPublicRoute`, `openEventStream`, `onSessionResolved`, `subscribeSession`, `registerPiRequestHandler` (the lane's server side, `server-context.ts:1118`), `ctx.vault`, `ctx.credentials`, `ctx.identity?.hasHostPolicy`); per-spawn enforcement remains the `isolated === true` assertion. Evaluated per request (cached ≤5 s) AND by a ≤5 s background watcher that ends a mode's live conversations when its gate closes. `ctx.identity` is optional — absent ⇒ identity mode closed.

### D4 — Conversation = one isolated session
Public API = fixed routes (the host namespace allows only fixed `GET`/`POST` paths): `POST conversations`, `POST messages {conversationId,text}` (→ `202`, async), `POST close {conversationId}`, `GET stream?cid=`, `GET widget.js`; all with `allowHeaders` incl. `X-Web-Chat-Token`. Spawn: per conversation dir `<ctx.dataDir>/customers/<hash>/conv-<n>/` holding `agent/`, `workspace/` (cwd, 0700, empty) and `sessions/`; extension bundle and persona file copied into `<ctx.dataDir>/runtime/` at activation (packaged installs live under `~/.pi/agent/npm/…`, which change (a) refuses as `isolated_path_invalid`); `scope = { agentDir, tools: ["kb_search"?, ...apiToolNames, "escalate_to_human"] (concrete names, no globs), extensions: [<web-chat extension>], extensionConfig: { "web-chat-guard": { tools: [...], apiTools: "<JSON string of public declarations>" } }, appendSystemPrompt: [<persona file>], noMcp: true, sessionDir }` — `extensionConfig` values are strings/string arrays only (`server-context.ts:343`), and no secret or KB path is projected: `kb_search`, API tools and `escalate_to_human` all execute in the plugin server over the plugin-message lane (kept in isolated mode by change (a)), `pluginRef`, `recover: false`, no owner — ownerless sessions are invisible to human principals (`identity/session-access.ts:71`), which is the visibility control (`lifecycle.hidden` is defined for owned sessions and is not relied on); the operator inspects via escalation excerpts and the local/break-glass operator. Agent dir provisioned per spawn: `settings.json` `{}` (no packages), `auth.json` 0600 with the customer-traffic model credential read from `ctx.vault` (binding `web-chat-model-key`), `models.json` only if the configured provider needs it. Result must be `{success:true, isolated:true}` else shut the session down (host shutdown hook) and answer `503`. Messages are queued and delivered after the guard reports ready (spike `web_chat_guard_ready`) — never via `initialPrompt` (refused for isolated spawns by core); ready timeout 25 s (below the host's 30 s non-stream bound, so `POST messages` answers `202` immediately). The plugin must be trusted (manifest `priority <= 100`, like chat-gateway, `server.ts:3400`) for spawn/subscribe/shutdown hooks; an untrusted spawn hook just returns `{success:false}`, indistinguishable from other refusals, so it surfaces as `503 spawn_failed` per request (documented), not as a distinct gate code.

### D4b — Session correlation and the extension lane
`spawnSession` returns no session id (`server-context.ts:652-657`). Each spawn carries `pluginRef: { webChat: { conversationId } }`; the plugin subscribes `onSessionResolved` at activation and binds conversation → session id on resolution (team-agent-sessions convention). Delivery queue drains only after (resolved AND guard-ready). Spawns set `recover: false` so a cold-start recovery never resurrects a customer session. Extension ⇄ server messages over the plugin-message lane: `guard_ready {}`; `tool_request { id, tool, args }` → `tool_reply { id, ok, text }` (12 s extension timeout), for `kb_search`, `api_<name>`, `escalate_to_human`; server identifies the conversation by the sending session id — never by a value the model controls.

### D5 — Registry, caps, limits
Owner-exact authorize (spike `registry.ts`): unknown, foreign, ended or pre-restart conversation ⇒ identical `404` (no existence oracle). Caps: live ≤ `maxLiveConversations` (default 100 — each is a pi process sharing the operator's instance; below core's 256 isolated cap), per customer ≤ 3 open and ≤ 6 created/hour; messages ≤ 4000 chars; per customer 10/min + 60/hour; idle end 30 min; hard end 4 h. Sybil caveat: in identity mode per-customer caps are only as strong as the IdP's account creation; the global cap bounds the damage. Registry persisted 0600; boot marks all ended (core spawn credentials are not persisted). Retention: agent dir + workspace deleted at end, session files after 30 d, registry entries after 30 d, closed escalations after 90 d. Gate open→closed ends that mode's live conversations.

### D6 — Stream and egress
`GET /public/conversations/:id/stream` via `openEventStream`; frames from `subscribeSession`/`onEvent` pass `toCustomerFrame`: `message` (assistant text, final per turn; streamed deltas allowed), `status` (`thinking` | `ready` | `ended` | `escalated`), `error` (generic code only). Everything else dropped. Assistant text passes a post-filter that removes absolute paths and redacts strings matching configured secret patterns (defense in depth; the isolated session has no operator data to leak).

### D7 — Customer tools (extension, in-session)
Deny-first guard (`tool_call` ⇒ `{block:true}` for anything not allowlisted; null/garbage policy ⇒ deny all). `kb_search`: plugin-server BM25 over `.md`/`.txt` under `kbDir` (absolute, outside the operator `~/.pi` tree, else gate `kb_invalid`), ≤10 000 files / 50 MB, rebuilt on change, top 5 snippets ≤ 2000 chars, doc title only. API tools: config `apiTools: [{ name, description, urlTemplate, params: {name: {type, pattern}}, headers: {name: vaultBinding}, unscoped? }]`; `https` only, host exact-equal to an `allowedApiHosts` entry (no suffix match); template must contain `{customerSub}` unless `unscoped: true`; `{customerSub}` only in path/query positions (placeholder in scheme/host/port ⇒ rejected at load), percent-encoded from the authenticated subject (subjects 1–128 chars, no controls, not `.`/`..`), final host re-checked exact before attaching secrets; params pattern-validated + URL-encoded; `GET`, no redirects, 10 s, ≤ 64 KiB, JSON/text; secrets from vault injected server-side (never enter the pi process). Request/response over the plugin-message lane with correlation id and a 12 s extension-side timeout. `escalate_to_human({ reason })`: plugin records an escalation (D8), returns a fixed acknowledgement to the model.

### D8 — Escalation inbox
Escalation = `{ id, conversationId, customerDisplay (name claim or hashed id), reason ≤ 500 chars, transcriptExcerpt (last 10 customer/assistant turns), createdAt, status: open|claimed|closed }`, stored 0600 under the plugin data dir; ≤1 open escalation per conversation; stream emits `status: escalated`. Operator UI: settings-section claim "Web chat" with an Escalations list (claim/close, view excerpt). No core notification seam exists (none on `ServerPluginContext`), so v1 notifies inside the plugin panel only; an operator-configured webhook (`escalationWebhookUrl`, POST JSON, 5 s timeout, no retries) is optional.

### D9 — Widget
Single `GET /public/widget.js` (built bundle, no external deps, ≤ 50 KB gzip). Host page: `<script src="https://dash.example/api/plugins/web-chat/public/widget.js" async></script>` and `window.WebChat.init({ endpoint: "https://dash.example", getCredential: async () => ({ bearer } | { token }), title?, locale? })` — `endpoint` only via `init`. Renders in a shadow root; launcher button + panel; WCAG 2.2 AA (focus trap in panel, Esc closes, `aria-live="polite"` for new messages, contrast ≥ 4.5:1, keyboard-only operable); streams via `fetch` + `ReadableStream` with the credential header; reconnect with exponential backoff (1 s → 30 s); credential re-fetched before expiry. The widget origin must be listed in the core `allowedOrigins`.

### D10 — `web-chat-policy` plugin + confinement probe
Registers the single host access policy (a refused registration now throws — change (a) — and is logged), from its OWN config `customerIssuers` (confinement must hold even when `web-chat` is disabled; a plugin cannot read another's config). Customer issuer ⇒ allow only `plugin:web-chat:public`; deny every other non-session action including `plugin:web-chat:read|write` (operator panel routes, classified by `identity/http-road-classification.ts:130-133,176-184`); other principals ⇒ allow. Session roads are owner-gated, and web-chat sessions are ownerless. `web-chat` does NOT trust a published signal (`provide`/`consume` is a shared last-write-wins map, `server.ts:3701`, forgeable by any plugin). Its gate PROBES the registered policy: for each customer issuer, `ctx.identity.authorize(syntheticPrincipal, "public")` must be `true` and `"read"`/`"write"` must be `false`; probe at activation, on `hasHostPolicy()`/config change and every 5 minutes (deny audit events accepted, low rate). Required in BOTH modes whenever identity is enforced and `customerIssuers` is non-empty, because customer OIDC principals exist independently of token mode. A composing policy passes if it confines; a non-confining one keeps the gate closed. One-policy-per-server (`PolicyDuplicateError`) means an operator with an existing policy must compose rather than run both — documented.

### D11 — Observability
Structured log lines (no message content): conversation created/ended (reason), spawn failure (code), isolation assertion failure, guard block (tool name), API tool call (name, host, status, latency), escalation created, rate-limit hit; counters exposed on the plugin's operator panel (live conversations, messages/min, blocks, escalations open).

## Risks / Trade-offs
- **Prompt injection by customers** can steer the model within allowed tools: KB and declared GET endpoints only; API params pattern-validated; results capped. Accepted: the model may say wrong things — persona instructs to escalate when unsure.
- **Business API data exposure**: an API tool returns whatever the endpoint returns for the given params; operators must only declare endpoints scoped by customer (template may include `{customerSub}`, filled by the plugin from the authenticated id, never by the model).
- **Same-instance deployment** (user decision): customer traffic shares the operator's dashboard process; isolation relies on change (a)'s guarantees; DoS bounded by caps.
- **Grounding is persona-level (user decision)**: the tool allowlist bounds what the model can *do*, not what it *says*; answers may go beyond KB/API content. Persona instructs to escalate when unsure; residual risk accepted and stated in the operator guide.
- **Storage under sybil accounts**: bounded globally — 300 creations/h, 500 open escalations (14-day expiry), 16 KB transcript excerpts, 2 GB session-file budget (oldest pruned).
- **Plugins are mutually trusted** (a plugin could still interfere in-process); confinement is verified by probing the policy, not by trusting another plugin's signal.
- **Token replay** until `exp` (≤ 15 min, no `jti`) — accepted; documented.
- **Customer issuer overlapping the operator's issuer** would confine the operator to the public API (break-glass local operator still works) — operator guide warns; the panel shows the issuers in force.
- **Tunnel/proxy deployments**: set core `maxStreamsPerPeer: 0` (all customers share one socket peer); per-customer limits here bound each customer.
- **Token-mode secret compromise** lets an attacker mint any customer id: rotation supported; tokens short-lived.
