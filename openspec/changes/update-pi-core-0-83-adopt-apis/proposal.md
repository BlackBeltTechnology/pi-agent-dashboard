## Why

The dashboard pins `@earendil-works/pi-coding-agent@^0.81.1` (server dep + `piCompatibility.recommended`), and the same `0.81.1` is baked into `docker/Dockerfile` and `scripts/verify-release-deps.mjs`; the electron server bundle inherits the range from the server dep at build time. Upstream is now `0.83.0` (0.82.0 → 0.82.1 → 0.83.0). We want to move the recommended pin to `0.83.0` across every single-source location and the electron app, adopt the genuinely-applicable new APIs behind runtime feature-detection so a session running on an older pi (down to the unchanged `minimum: 0.78.0`) keeps working the old way with no crash and no behavior regression, and correctly handle the **breaking** TypeBox 1.3.7 bump (`#7243`) plus the new `"pending"` streaming stop reason (`#7151`).

Two capabilities that a naïve reading treats as "adopt" are, on inspection, **not applicable as-is** to this codebase and are scoped accordingly:

- **Streaming `bash_execution_update`** (0.82.0) fires **only for direct RPC bash commands correlated by request id** (per `docs/rpc.md`). The dashboard never issues RPC bash — dashboard-initiated `!`/`!!`/slash-exec commands run through `handleBashCommand` via `pi.exec(...)` and emit the dashboard's **own synthetic `bash_output` event** (`BashOutputData` in `packages/shared`); LLM tool bash renders via `tool_execution_*`. So `bash_execution_update` cannot fire on any dashboard bash path today. This adoption is a **documented feasibility spike**, not a committed change.
- **`outputPad`** is a **TUI horizontal-padding setting** (`docs/settings.md`, `#6168`) that predates the current pin — **not** a "custom message renderer" API and **not** new in 0.82/0.83. The dashboard renders in the web client, not pi's TUI, so `outputPad` has no dashboard surface. Adoption resolves as a **documented no-op with the corrected rationale** (kept per decision, not dropped).

## What Changes

- **Version bump (single-source pins).** `packages/server/package.json` dep `^0.81.1 → ^0.83.0` and `piCompatibility.recommended 0.81.1 → 0.83.0` (`minimum` stays `0.78.0`, `maximum` stays `null`). `scripts/verify-release-deps.mjs` `minVersion` + rationale string. `docker/Dockerfile` global install pin. All other workspace packages keep their `"*"` peer on pi. The electron app inherits the bump through the bundled server (`packages/electron/scripts/bundle-server.mjs` resolves the server's `^0.83.0` from the registry at build time — no independent electron pin exists).
- **Extend `verify-release-deps.mjs` to actually enforce pi pin coherence.** Today its pi rule checks only the server-dep floor via a loose `includes()` test — it does **not** read `piCompatibility.recommended` or the `docker/Dockerfile` pin. This change extends the checker to assert those **three pi-version pins** resolve to the same normalized version (reusing the existing `floorOf()`-style normalizer, since the syntaxes differ: `^0.83.0` / `0.83.0` / `@0.83.0`) so a future bump that touches some and forgets others fails CI. The extension `typebox` devDep (below) is a separate test-fidelity pin, not part of pi-version coherence; `verify-release-deps.mjs`'s own `minVersion` is the script's own value.
- **BREAKING (upstream) — TypeBox 1.3.7 compatibility (`#7243`).** The bump removed `Type.Base/Awaited/Promise/AsyncIterator/Iterator/Options` and `Value.Mutate`, and **fixed compiled validation of nullable-array tool arguments**. A repo audit shows **zero** usage of the removed APIs. The real risk is the nullable-array validation fix changing how the extension's optional-array tool args (e.g. `ask-user` `options: Type.Optional(Type.Array(...))`) accept/reject `null`/missing values at runtime. **Load-bearing gap:** the extension's test-time TypeBox is the devDep `typebox ^1.1.33` (resolves ~1.1.x), while runtime resolves pi's bundled 1.3.7 via the `"*"` peer — so "run tests against 0.83.0" does **not** exercise the 1.3.7 validator unless the devDep is bumped too. This change **bumps the extension devDep `typebox` to `^1.3.7` (+ lockfile)** — a fifth pin — so the suite actually validates against the runtime version.
- **Adopt `ctx.scopedModels` (`#7191`) — narrows, never empties.** Per upstream docs, `ctx.scopedModels` "is **empty** when no scoping is configured, meaning every available model is usable." Detection therefore uses **non-empty length** (`Array.isArray(ctx.scopedModels) && ctx.scopedModels.length > 0`), NOT presence (`typeof … !== "undefined"`) — presence-detection would route every default 0.83.0 session into the constrain branch and **empty `list_models`**. When the scope is non-empty, `list_models` intersects it with `cachedModelRegistry.getAvailable()` (refs preserved, `registryReady` discriminator untouched); when absent **or empty**, output is byte-identical to today.
- **Guard the `"pending"` stop reason (`#7151`).** `"pending"` is a partial-**streaming** stop reason. Before changing `turn-actionability.ts`, verify whether `"pending"` ever reaches the terminal `agent_end` message the classifier runs on (`bridge.ts`). If it does, classify it as in-progress so a mid-stream partial is never misread as `empty-actionable` — **without** blanket-suppressing the empty-actionable guard for genuinely idle turns. Note `#7272` already converts unmapped terminal provider reasons to **errors pi-side**, so the classifier no longer receives raw terminal strings for those.
- **Streaming `bash_execution_update` — feasibility spike (not committed).** Investigate during implementation whether any dashboard bash path can surface `bash_execution_update` (it cannot today — no RPC bash). Record the outcome; land code only if a real path exists.
- **`outputPad` — documented no-op (corrected rationale).** Record in the feature-detection spec that `outputPad` is a TUI-only padding setting with no web-client surface; no renderer is introduced and no code lands.

## Impact

- Affected specs: `pi-core-version-check` (MODIFIED requirement + ADDED coherence requirement), `agent-role-model-tools` (ADDED requirement to existing capability), `bash-execution` (ADDED spike requirement to existing capability), `pi-api-feature-detection` (ADDED — fallback governance + corrected `outputPad`/`"pending"`).
- Affected code: `packages/server/package.json`, `scripts/verify-release-deps.mjs` (pin + coherence check), `docker/Dockerfile`, `packages/extension/package.json` (typebox devDep), `pnpm-workspace.yaml` (`minimumReleaseAgeExclude` pi entries), `packages/extension/src/role-model-tools.ts`, `packages/extension/src/provider-register.ts` (scoped-models capture), `packages/extension/src/turn-actionability.ts`. Docs: `docker/AGENTS.md` version row (DocScribe).
- Compatibility / rollback: every committed adoption is feature-detected — `minimum` stays `0.78.0`, so sessions on `< 0.83.0` keep the pre-0.83 code path. Rollback = revert the pin edits + lockfile; no data migration, no protocol break. **Watch item:** the recommended bump may push standalone/electron users onto a pi whose own Node floor exceeds theirs; `bundled-node-meets-pi-floor.test.ts` keys on `minimum` only, so a recommended→Node-floor check is a follow-up guard.
