## Goals / Non-Goals

Goals: one bot serving N servers, each with its own record and mode; fail-closed default for unknown servers; per-server admins, tiers, provisioning and disarm; zero-touch upgrade; fail-closed rollback; no hardcoded limits on touched code.

Non-Goals: multiple tokens. `query` read commands, the message index and admin chat commands (B). Agent tools (C). Moderation (D). Per-server overrides of `threadPerConversation`/`mirrorDashboardSessions`/`sessionVisibility`, which stay global and apply to `interactive` servers.

## Decisions

### D1. Config shape (`guilds`, `limits`, binding `guildId`)

```json
{
  "guilds": {
    "type": "object",
    "propertyNames": { "pattern": "^[0-9]+$" },
    "additionalProperties": {
      "type": "object",
      "additionalProperties": false,
      "properties": {
        "enabled":   { "type": "boolean", "default": false },
        "mode":      { "type": "string", "enum": ["interactive", "query"], "default": "query" },
        "label":     { "type": "string" },
        "admins":    { "type": "array", "items": { "type": "string", "pattern": "^[0-9]+$" }, "default": [] },
        "allowlist": { "type": "array", "items": { "type": "string", "pattern": "^[0-9]+$" } },
        "channels":  { "type": "array", "items": { "type": "string", "pattern": "^[0-9]+$" }, "default": [] },
        "principals":{ "type": "object", "additionalProperties": { "enum": ["observe", "control", "operate"] }, "default": {} },
        "roles":     { "type": "object", "additionalProperties": { "enum": ["observe", "control"] }, "default": {} },
        "ceiling":   { "type": "string", "enum": ["observe", "control", "operate"] },
        "provisioning": {
          "type": "object", "additionalProperties": false,
          "properties": { "enabled": { "type": "boolean", "default": false } }
        },
        "query":      { "type": "object", "description": "Reserved for B. Preserved verbatim, never interpreted by A." },
        "index":      { "type": "object", "description": "Reserved for B. Preserved verbatim, never interpreted by A." },
        "moderation": { "type": "object", "description": "Reserved for D. Preserved verbatim, never interpreted by A." }
      }
    }
  },
  "limits": {
    "type": "object",
    "additionalProperties": { "type": "integer", "minimum": 0 },
    "properties": {
      "maxGuilds":              { "type": "integer", "minimum": 0 },
      "maxBindings":            { "type": "integer", "minimum": 0 },
      "maxMappings":            { "type": "integer", "minimum": 0 },
      "maxDiscoveredGuilds":    { "type": "integer", "minimum": 0 },
      "maxReservedBytes":       { "type": "integer", "minimum": 0 },
      "refusalRepliesPerMinute":{ "type": "integer", "minimum": 0 },
      "legacyResolveTimeoutMs": { "type": "integer", "minimum": 0 },
      "pairingTtlMinutes":     { "type": "integer", "minimum": 0 },
      "pairingMaxAttempts":    { "type": "integer", "minimum": 0 },
      "configWriteTimeoutMs":  { "type": "integer", "minimum": 0 }
    }
  },
  "teamControls": { "properties": { "bindings": { "additionalProperties": {
    "properties": { "guildId": { "type": "string", "pattern": "^[0-9]+$" } } } } } }
}
```

- **No schema `default` on `guilds` or `limits`** (the objects themselves). The host materializes a top-level default on every partial write (facts table), which would make `guilds` present-but-empty after any unrelated save (e.g. `steerPrefix`) and permanently skip legacy normalization and adoption (D5). Nested defaults (`enabled`, `mode`, ...) apply only inside an existing record and are fail-closed. The documented defaults of `limits.*` live in `LIMIT_DEFAULTS` in code, not in the schema. `limits` allows unknown keys whose value is an integer ≥ 0, so a later change's `limits.*` keys survive a rollback to A (validator **preserves** unknown `limits` keys, like reserved record keys).
- Keyed by guild snowflake (a decimal string). `propertyNames` `^[0-9]+$` already rejects `__proto__`/`constructor`/`prototype`, so the id check is the only gate and fails as `invalid_guild_id`. Guild-record id lists (`admins`, `allowlist`, `channels`, principal and role ids) are snowflakes too: a non-snowflake entry such as `<@123>` can never match, so it is rejected (`invalid_snowflake`) rather than silently inert.
- **Reserved keys are preserved (rollback safety).** A's record validator is closed for unknown keys **except** the reserved keys `query` and `index` (owned by B) and `moderation` (owned by D). Each must be a plain object; A stores and re-emits it and never interprets it, so a later change's settings survive a rollback to A and the server stays loadable. A copies a reserved value with `structuredClone` (never a spread or `Object.assign` of parsed input), rejects `__proto__`, `constructor` and `prototype` keys at any depth inside it, and bounds its serialized size by `limits.maxReservedBytes` (default 262144, `0` = unlimited), measured as the UTF-8 byte length of the compact `JSON.stringify` output (so 150 000 `é` is 300 000 bytes, not 150 000); a violation is `invalid_reserved_key`. Any other unknown key is rejected as `unknown_guild_key`. C adds no per-record key (its settings are top-level `agentTools`); A's writers never touch top-level keys they do not own. A reserved key that is not an object is rejected on the write lane (`invalid_reserved_key`). On the TOTAL boot read it is dropped alone from the in-memory record (feature off, fail-closed) and the record stays loaded, with a `problems` entry. Writes are record-level patches (D8) that carry the reserved keys over from the **raw persisted record as stored on disk**, not from the post-drop in-memory copy, so a malformed or dropped reserved key is never stripped by an unrelated save; the owning change repairs or overwrites it. Reserved values are exempt from A's `limits.maxMappings`: the owning change counts its inner id lists (B: `query.workspaces`, `index.channels`) against `limits.maxMappings`, and A counts the blob as nothing. The reserved set is a closed list in `guilds.ts`; a later change that needs a new record key extends it in its own delta.
- **Duplicates, free text and `limits` key names.** An id list written with a repeated id is stored de-duplicated and counted after de-duplication against `limits.maxMappings` (a duplicate is never an error). `label` and the `guilds` object itself are NOT bounded by A (only the host request-body limit applies; reserved blobs keep `limits.maxReservedBytes`), which is stated rather than silently assumed. A `limits` key named `__proto__`, `constructor` or `prototype` is rejected `invalid_limit` on the write lane and dropped on the boot read, the same hardening as reserved keys. A record field of the wrong JSON type (`enabled: "yes"`, `label: 5`, `provisioning: "on"`, a non-array `clear`, a non-object upsert value) is rejected `invalid_guild_record`, naming the field path, with nothing persisted. A `teamControls.bindings.<ws>.guildId` that is not a snowflake is rejected `invalid_guild_id`.
- **Defaults are fail-closed.** A record without `enabled` is disabled, and a record without `mode` is `query`. There is no global mode setting, which is owner decision 2.
- `allowlist` absent ⇒ inherit the global `allowlist`; present (even `[]`) ⇒ replaces it for that server.
- `ceiling` absent ⇒ the global `teamControls.ceiling`. Present ⇒ `min(guild.ceiling, global)`.
- `teamControls.guildId` becomes **legacy**. It is read only by D5 normalization and removed on adoption.
- New module `src/server/guilds.ts` provides `validateGuilds(raw, limits)` (TOTAL on the boot read: it drops only the offending record, or for `channel_in_multiple_guilds` removes that channel id from every record claiming it, and reports each as a `problems` entry), `validateGuildsWrite` (strict: `{ok:false, reason, path}` like `team-config.ts`; refuses a missing payload), and `guildPolicy(guildId): GuildPolicy | undefined`, which returns only configured **and** enabled guilds. A boot rejection never discards the whole `guilds` map.
- Validation reasons: `invalid_guild_id`, `invalid_guild_record`, `invalid_snowflake`, `too_many_guilds`, `invalid_guild_mode`, `invalid_tier`, `role_cannot_map_to_operate_requires_explicit_identifier` (reused), `channel_in_multiple_guilds`, `unknown_guild_key`, `invalid_reserved_key`, `invalid_limit`, `too_many_mappings`, `too_many_bindings`, `revision_changed` (D8), `revision_required` (D8), `invalid_clear` (D8), `legacy_unresolved` (D5), `allowlist_choice_required` (D6), `server_not_adopted` (D5/D8), `config_write_timeout` (D8). `validateGuildsWrite` judges a write on what it changes (D8): it checks every upserted record strictly, and `channel_in_multiple_guilds` / `too_many_guilds` only for the ids and records the write adds. Which list returns which overflow reason: guild-record id lists (`admins`/`allowlist`/`channels`/`principals`/`roles`) → `too_many_mappings` (`limits.maxMappings`); the **existing binding codes are kept verbatim** (`too_many_bindings` for the bindings map, `too_many_principals`/`too_many_roles` for a binding's maps, `team-config.ts:104`, `:125`, `:215`), now bounded by the same `limits` settings. `channel_in_multiple_guilds` means a channel id appears on two records, which is rejected so one channel can never take two policies. `reserved_guild_id` is not a reason: the `propertyNames` pattern rejects those ids first as `invalid_guild_id`.

### D2. "Unlimited" convention and `limits`

**`0` means unlimited for every count, size or duration limit setting** in this plugin, in A and in B/C/D. An absent value uses the documented default. A negative or non-integer value is rejected on the write lane and falls back to the default on the TOTAL boot read. `limits.maxMappings` replaces `MAX_MAPPINGS_PER_BINDING` and applies to every list or map of ids on a record: binding `principals`/`roles`, guild `principals`/`roles`/`admins`/`allowlist`/`channels`. `limits.maxBindings` replaces `MAX_BINDINGS`. `limits.maxGuilds` caps **configured** records and defaults to `0` (unlimited), which is owner decision 15. A cap is opt-in. Discovered servers are bounded only by Discord membership, but the settings **projection** of them is bounded by `limits.maxDiscoveredGuilds` (default 100, `0` = unlimited): beyond it the surface lists the first N plus `discoveredOmitted: <count>`. Further A limits: `limits.maxReservedBytes` (default 262144, per reserved record object, D1), `limits.refusalRepliesPerMinute` (default 6 per opted-in channel, threads count against their parent, `0` = unlimited, D4) and `limits.legacyResolveTimeoutMs` (default 15000 per legacy channel id, `0` = no timeout, D5), `limits.pairingTtlMinutes` (default 15, `0` = a pairing code never expires) and `limits.pairingMaxAttempts` (default 10, `0` = no lockout). The two pairing keys convert the constants at `auth.ts:72-73` because A modifies "Layered authorization" and edits `auth.ts`: the gateway passes them to `createPairing` (`ttlMs = minutes × 60000`, `0` → no expiry; `maxAttempts`, `0` → never lock) when it creates the pairing state at start, so a change applies at the next start (the Behaviour hint says so). `0` attempts is the operator's explicit risk: the code space is 10^6 and the lockout is the only brute-force brake (security notes). `limits.configWriteTimeoutMs` (default 30000, `0` = no timeout) bounds one configuration write (D8). **Timer clamp (shared rule).** Any millisecond or second setting above the Node timer maximum is clamped to 2147483647 ms at runtime with the stored value kept (the settings hint says so), so `setTimeout` never wraps to 1 ms. **When a key applies.** Every `limits` key is read live, on the next message or write, except `pairingTtlMinutes`, `pairingMaxAttempts` and `legacyResolveTimeoutMs`, which are read at start:

  | key | applies |
  |---|---|
  | `maxGuilds`, `maxBindings`, `maxMappings`, `maxReservedBytes`, `maxDiscoveredGuilds`, `refusalRepliesPerMinute`, `configWriteTimeoutMs` | next message / write |
  | `pairingTtlMinutes`, `pairingMaxAttempts`, `legacyResolveTimeoutMs` | next start |

  The discovered list is ordered by ascending numeric snowflake (compared as `BigInt`, so `9` sorts before `10`): the first N are listed and the rest are counted in `discoveredOmitted`. A's `limits` has **one writer** (`patchLimits` in `guilds.ts`, D8). Drop counters are keyed by reason, plus per guild id only for configured records, so their cardinality is bounded by the records. `MAX_AUDIT_RETENTION` (`team-config.ts:23`), `READY_TIMEOUT_MS`/`MAX_TRACKED_SPECS` (`discord.ts:136-138`) and `LIST_LIMIT` are not touched here. Whichever change touches them converts them. Discord's 2000-character message limit is a platform fact, not a setting.

### D3. Discovery (auto-listed, inert)

The `Guilds` intent already delivers the bot's guild list (`client.guilds.cache` after `ClientReady`) plus `GuildCreate`/`GuildDelete`/`GuildUpdate`. The adapter gains `listGuilds(): {id, name}[]` and `onGuildsChanged(cb)` as optional members of the port (`src/adapters/base.ts`). The fake adapter returns a fixed list. Discovery is **runtime state, not config**: nothing is written when the bot joins a server, so there is no race with operator writes. The surface projects a `GuildView` per id in (configured ∪ present):

`{ id, name (live, else label), label?, present, discovered, legacy, enabled, mode, effectiveCeiling, provisioning, disarmed, problems[] }`. The surface also carries `revision` (D8), `discoveredOmitted` (D2) and the per-reason drop counters.

- `discovered: true` means present but with no record. It is shown as `mode: "query"`, `enabled: false` and is inert.
- `present: false` means the record exists but the bot is not in that server. The record is kept and a warning is shown.
- Enabling a discovered server writes a record `{enabled: true, mode: "query"}`. Switching to `interactive` is a separate, explicit operator choice.

### D4. Drop rule, outbound gate, mode gate

```mermaid
flowchart TD
  M[Discord message / interaction] --> DM{DM?}
  DM -- yes --> P[existing DM path: pairing / enrollment-only]
  DM -- no --> G{guildPolicy(guildId) defined? configured AND enabled}
  G -- no --> X[DROP silently; counter dropped.guild_not_enabled]
  G -- yes --> C{channel or thread parent in THIS guild's channels?}
  C -- no --> X2[DROP silently; counter dropped.channel_not_opted_in]
  C -- yes --> L1{effective allowlist has user?}
  L1 -- "no, interactive server" --> R["Refused: not_allowlisted (throttled, limits.refusalRepliesPerMinute)"]
  L1 -- "no, query server" --> R2[DROP silently; counter dropped.not_allowlisted]
  L1 -- yes --> MO{mode}
  MO -- interactive --> T[today's path: tier chokepoint, spawn/resume/attach/threads/mirror]
  MO -- query --> Q{whole-message ! command?}
  Q -- "!disarm" --> DIS["per-server latch, observe+ (both modes)"]
  Q -- yes --> RQ["Refused: query_mode. (throttled; B answers its read commands first)"]
  Q -- no --> I[ignore silently]
```

- **Edge enforcement.** The adapter replaces `allowedChannels` with a live getter `inboundScope(): ReadonlyMap<guildId, ReadonlySet<channelId>>`, which contains only enabled guilds. `handleMessage` (`discord.ts:608-628`) checks guild then channel and tags `metadata.guildId`. `handleInteraction` (`:630`) tags `guildId` on `InteractiveResponse`. An interaction with `interaction.guildId == null` is a **DM interaction** and follows the DM path unchanged (a literal `!guildPolicy(null)` must not drop it); a guild interaction from a non-enabled server is acknowledged with `deferUpdate()` and then dropped (so the user sees no "interaction failed", and nothing is edited, posted or answered), counted as `guild_not_enabled`. The same holds for the DM **message** path: `isDM` messages never consult `guildPolicy`. The gateway repeats the guild check (`auth.ts` L4 receives `guildId`) as defence in depth. A drop never replies, and nothing is logged per message: a counter is kept per reason and exposed on the surface (observability without log flooding).
- **Outbound gate.** `sendableChannel` (`discord.ts:709`) resolves `channel.guildId` and throws `guild_not_enabled` for a non-DM channel outside an enabled guild. It covers only `sendMessage`/`editMessage`/`setTyping`/`sendInteractive` (call sites `:342-369`, `:543`, `:598`). **`startThread` and `archiveThread` fetch the channel directly** (`:324`, `:336`), and `channelOps()` create/overwrite and `guilds.fetch` (`:433`, `:502`, `:510-519`) take a guild or channel id with no gate, so each of these WRITE paths gets the same guild check at the adapter (`startThread`, `archiveThread`, channel create, permission-overwrite set, role operations). Read-only calls (`guildIdFor`, delegation enumeration) stay ungated because legacy resolution (D5) and the discovery view need them before a server is enabled. Mirroring (`gateway.ts:1202`, `:1509`), thread creation (`:963-968`) and provisioning additionally require `mode === "interactive"` at the gateway.
- **Callers of a refused send.** `guild_not_enabled` is deterministic, not transient: mirror, streaming-edit, typing-loop and provisioning call sites catch it, **do not retry and do not log per event**, and stop mirroring state for that channel. The deterministic Discord errors `10003` (Unknown Channel), `10004` (Unknown Guild) and `50001` (Missing Access) at those same sites are handled identically: no retry, ONE warning per channel (not per event), mirroring state for that channel stops and resumes on the next `onGuildsChanged` or record change. **Pending prompts in a server that stops being interactive: local cleanup only.** When a server is disabled or switched to `query`, the gateway drops its own state for the prompts rendered there (the `prompts` records and any multiselect/batch sequence, as `dropSequence` does) and removes the Discord controls best-effort (`cleanupInteractive` is an adapter write that the gate may refuse; the refusal is swallowed, not retried). It does **not** call `seam.sendPromptResponse`: the shipped `prompt_dismiss`/`prompt_cancel` path never answers the session either (`gateway.ts:1815-1830`), and a synthetic `cancelled` answer would resolve a PromptBus prompt that the dashboard could still answer, with no authorization, as the side effect of a config toggle. The PromptBus prompt therefore stays pending and answerable from the dashboard; a late Discord click finds no record and is ignored. Switching back does not re-render an old prompt. Which prompts belong to a server is read from `prompts.guildId` (D6), never inferred from the channel.
- **A/B boundary for `query`.** In A, an enabled `query` server is allowed outbound (it must answer in place), but every interactive verb is refused **before** the tier chokepoint: `spawn_session`, `resume_session`, `send_prompt`, `abort`, `attach_session`, `close_session`, `prompt_response`, plus thread open, mirror and provision. **Ordering:** the L1/L4 checks (flowchart) run **before** the mode gate, so `query_mode` is only ever sent to an allowlisted user in an opted-in channel and a stranger never learns the server is in `query` mode. In a `query` server a non-allowlisted user's message is dropped silently (counter `not_allowlisted`); in an `interactive` server the existing `Refused: not_allowlisted.` reply is kept but throttled by `limits.refusalRepliesPerMinute` (default 6 per minute, `0` = unlimited; counted per **opted-in channel, a thread counting against its parent** (`parentChannelId`), so opening threads never multiplies the budget and the key set is bounded by the configured `channels`, idle keys pruned when their window expires; the `minute` is the unit of the setting, as in `agentToolReadsPerMinute`, not a separate constant, and the window is **sliding and half-open** `(now − 60 000 ms, now]` (a reply is posted when fewer than the limit were posted in the preceding 60 000 ms, so a reply exactly 60 000 ms after the first is allowed and no burst-at-boundary exists; shared window-edge rule for every per-minute setting, B and C included); applies to every refusal reply in a guild channel, including `query_mode`; the throttled reply is dropped, not queued and counted as `refusal_throttled`; the default of 6 is decided (owner round 4). Shipped replies were unthrottled, so this is a documented behaviour change, and `0` restores the shipped behaviour exactly; see Migration). A **whole-message `!` command** means a message whose first non-whitespace character is `!` immediately followed by a word character, where a word character is ASCII `[A-Za-z0-9_]` only (`!sessions`, `!attach 1`, `!hello there` all qualify, `! hi`, `!` and `!état` do not; a non-ASCII letter or digit after the bang is plain text); the `!` steer prefix has no meaning in a `query` server. The reply is the placeholder `Refused: query_mode.` and it is sent only for such a message. Plain text gets no reply and no log entry. A refused command is one audit entry with `reason: "query_mode"` **only when its refusal reply is actually posted**. A refusal reply whose send FAILS (429, 50013, 50001) is not posted: it writes no audit entry, consumes no throttle budget (the budget counts successful sends only) and is not retried; a throttled refusal is counted (`refusal_throttled`) and not logged, so spam from an allowlisted user cannot rewrite the whole log file per message (`audit.ts` `persist()` rewrites the file on every append) or evict real history from the ring buffer (retention 10 000). With `limits.refusalRepliesPerMinute = 0` the audit is unbounded by the throttle too, which is the owner's explicit unlimited choice. The entry is written by a new controller method `recordRefusal({author, guildId, channelId, verb, reason})` (today only `authorizeRequest` appends, `controller.ts:195-211`) and `query_mode` is added to the `RefusalReason` union (`authorize.ts:30`). The audit volume is thereby bounded by the throttle and then by `auditRetention` (min 1, no `0`; its conversion is the touching change's, see D2). `!disarm` is the one exception: it is an emergency brake, not an interactive verb, and works in **both** modes (D10). B owns the read commands, which are likewise answered in both modes (owner decision 20). B replaces the placeholder handling with read and admin commands and owns everything about what `query` answers.
- **Mode switch at runtime.** Switching `interactive` → `query` or disabling a server keeps the session bindings and provisioned channels. Mirroring and driving stop immediately, because every path reads `guildPolicy` through a getter. Switching back resumes. No session is killed. **Work in flight** when the switch lands is not cancelled: a spawn already accepted completes and its binding is stored, a thread opened but not yet answered stays, and nothing is posted to the server after the switch (the outbound gate refuses it); the dashboard can still see and stop that session. **No latency budget:** the drop path and the settings projection have no p95/p99 requirement; only the bounded-memory invariants hold (drop counters bounded by configured records, throttle keys pruned, discovered list bounded by `limits.maxDiscoveredGuilds`).
  - **Where the gate gets a guild.** Mirror/stream/typing frames start from `sessionId` → binding → `channelId` (`gateway.ts:983-988`), which names no guild. A's `Binding` therefore gains an optional persisted `guildId` (`shared/types.ts:205-228`), set at all three bind sites (`gateway.ts:613-625`, `:888-898` via a `guildId` on `SpawnMeta`, `:1060-1071`) from `InboundMessage.guildId`; for auto-mirror, from the workspace binding's `guildId` (`team.bindingFor(channelId).binding.guildId`). `bindings.json` stores whole objects, so older versions ignore the field (`routing.ts:37-77`). A binding written before the upgrade has none: the gateway **back-fills** it lazily with `channelOps().guildIdFor(parentChannelId ?? channelId)` at `ClientReady`/`onGuildsChanged` and persists it (DM bindings have no guild). Until resolved, such a binding is **not mirrorable and its prompts are not rendered or answerable** (fail-closed, counted `binding_guild_unresolved`), then retried on every later `ClientReady`/`GuildCreate`. The helper `guildOfSession(sessionId)` is the one lookup every mirror/stream/typing/prompt site uses; it never guesses and never treats "unknown" as a match.
  - **Auto-mirror is re-evaluated on a transition.** `maybeAutoMirror` marks a session "considered" before any check and the set is cleared only at `stop()` (`gateway.ts:1202-1210`, `:1524`), so skipping a session because its server is `query` or disabled would suppress mirroring forever after switching back. The server gate therefore runs **before** the consideration mark, and a skip for "server not enabled + `interactive`" does **not** mark the session. In addition, a guild-policy change that makes a server enabled and `interactive` (config write or `onGuildsChanged`) re-runs the eligible-session sweep (the loop over `seam.listSessions()` that `start()` runs), which is idempotent: persisted bindings and the considered set prevent a second thread.

### D5. Legacy normalization (read time) and adoption (first write)

**Legacy mode** is defined on content, not on presence of the key: the gateway is in legacy mode when **no guild record exists AND at least one legacy key is non-empty** (`groupChannels`, `admins`, `teamControls.guildId`). `guilds` being `{}` (for example after the host materialized a default, see D1) with legacy keys set is still legacy mode. When any record exists, the records are authoritative and legacy keys are ignored (they are normally empty after adoption). **A `guilds` value that is present but not an object** (string, array, `null`, number) is neither "no record" nor legacy mode: every server is inert (fail-closed), the surface sets `guildsConfigError`, and the legacy keys are ignored while it stays malformed, so a bad write can never revive legacy channels. The operator repairs it by writing a valid `guilds` through the lane.

**Read-time normalization** (legacy mode):
1. At `ClientReady`, resolve each `groupChannels` id to its guild via `channelOps().guildIdFor` (`discord.ts:518-525`), each with a timeout of `limits.legacyResolveTimeoutMs` (default 15000, `0` = no timeout). An id that is unresolvable (deleted, no access, timed out) stays **unresolved**: it is kept in `groupChannels`, listed in `problems` (`legacy_resolving` while pending, `legacy_unresolved` after a timeout/failure) and retried on every later `ClientReady`/`GuildCreate`. It is never discarded by normalization.
2. Synthesize one `legacy` record per resolved guild, plus `teamControls.guildId` if set: `{enabled: true, mode: "interactive", channels: <its groupChannels>, admins: <global admins>, allowlist: absent (inherit), provisioning: {enabled: guild === teamControls.guildId}}`.
3. A binding without a `guildId` inherits `teamControls.guildId`, else the `guildId` stored on its `channels.json` record (D7), else it has none and provisioning fails with `provisioning_requires_guild_id`; the gateway never guesses.

The resulting behaviour matches today's. The only difference is that a channel is now counted only in its own guild, which was already true physically because channel ids are globally unique. **Readiness is per server, not global.** A legacy server goes live as soon as one of its own `groupChannels` ids resolves (its record is synthesized then, with the ids resolved so far); a channel whose id is still unresolved is simply not in any record, so its messages are dropped (fail-closed) and the surface shows it as pending. A slow, failed or hung id (including `limits.legacyResolveTimeoutMs = 0`, which means that id waits without a timeout) therefore delays only itself, never another server, and is retried on every later `ClientReady`/`GuildCreate`. Normalization never writes config.

**Adoption**: the first accepted dashboard `upsert` of a server record in legacy mode (D8). An upsert is the trigger because a record's mere existence ends legacy mode ("when any record exists, the records are authoritative"), so the write must carry the legacy servers over or they would silently stop. It does **not** run on a `limits`-only patch (limits are not server records and work in legacy mode without adopting), on `remove` (refused `server_not_adopted` in legacy mode; the UI hides Remove on `Legacy` rows) or on a chat-origin write (D8: refused `server_not_adopted`, so an emergency `!mode query` never forces the one-way rewrite and never fails on an unresolved legacy id). It runs inside the single write queue (D8) and **re-reads** the live `teamControls`, `groupChannels` and `admins` at that point, so a team-panel edit made since the surface was built is not clobbered or resurrected. One `updatePluginConfig` call does three things:
- writes `guilds` (the synthesized records plus the edit);
- writes `teamControls` with every binding's `guildId` filled and `guildId` removed from `teamControls`;
- sets `groupChannels: []` and `admins: []`.

**Adoption is refused with `legacy_unresolved` while any legacy `groupChannels` id is unresolved**, unless the write carries `adopt: {discardUnresolved: true}` (an explicit operator action in the UI, listing the ids). A transient Discord failure at boot therefore can never silently drop an operator's opt-ins; a discarded id is named in the reply. The global `allowlist` stays because DM pairing writes it. If the persist fails, memory reverts, following the same pattern as `applyWrite` (`index.ts:401-430`).

### D6. Per-server admins, allowlist and tiers

- **L1**: `effectiveAllowlist(g) = guilds[g].allowlist ?? config.allowlist`. DMs use the global list. Pairing (DM) appends to the **global** list, so a server without its own `allowlist` admits every globally paired user. The **Enable action therefore requires an explicit choice** in the UI, "inherit the global allowlist" or "own allowlist" (written as `allowlist: []` plus entries), so a newly enabled, possibly unrelated community never silently admits every paired user. **The validator enforces the choice**, not only the UI: a write that turns `enabled` from false/absent to true, or creates an enabled record, must carry `allowlist` (even `[]`) or the transient field `inheritAllowlist: true`, else it is rejected `allowlist_choice_required`. `inheritAllowlist` is accepted by the write validator and never stored; it is also the wire form of "inherit" for an **already enabled** record (`inheritAllowlist: true` deletes the stored `allowlist`, D8), and sent together with `allowlist` it is ambiguous and rejected `allowlist_choice_required`. Exempt from the enable check: an upsert that adopts a legacy record (synthesized already enabled, inherit = today's behaviour) and an edit of an already-enabled record that does not touch the allowlist; switching an enabled record from its own allowlist to inheriting needs the explicit `inheritAllowlist: true` (or `clear: ["allowlist"]`), never an omission. A `guilds` value written out of band bypasses this (the boot read inherits the global list), which is the documented out-of-band caveat (D8).
- **L2**: bind authority requires `userId ∈ guilds[g].admins` **and** L1. The L2 bind site (`gateway.ts:549-560`) passes that server's `admins` and `channels`; global `admins` is no longer consulted for guild traffic. A Discord guild owner or administrator is **not** implicitly a gateway admin. Admin rights in one server confer nothing in another. The cwd scope stays the single global `allowedRoots`: an admin of any `interactive` server can bind any cwd under `allowedRoots`, including a workspace another server uses. This is accepted and documented (owner decision A-T1: keep the global `allowedRoots`, no per-server narrowing now; a per-server `allowedRoots` can later be added as a reserved record key without breaking rollback), so the operator should enable `interactive` only on servers whose admins they trust with that code-execution scope.
- **Prompt answers.** The `prompts` record (`gateway.ts:1229`, `:1803`) gains the `guildId` of the rendering channel, copied from the session's binding at render time (`guildOfSession`, D4; the record's `isDM` stays as today). A prompt whose binding has no resolvable guild is not rendered (counted `binding_guild_unresolved`), so a record's `guildId` is always defined for a guild prompt and an "undefined matches anything" hole cannot exist; a DM prompt (`rec.isDM`) is answered only by a DM response (no `resp.guildId`). `onInteractiveResponse` (`gateway.ts:1408-1450`) (a) ignores a response whose `resp.guildId` differs from the record's (a click from another server, or a DM click on a guild prompt); (b) resolves L1/L4 from `guildPolicy(rec.guildId)` (not `config.groupChannels`/`config.admins`, which are `[]` after adoption); (c) passes `guildId` into `team.authorizeRequest`, so a disarmed server refuses the click like any other action; and (d) refuses silently when the server is no longer enabled and `interactive`. A refused click does not consume the prompt (shipped behaviour). When a server is disabled or switched to `query`, its pending prompts are cleaned up locally (D4: no `sendPromptResponse`, the dashboard can still answer). This is stated as an additive rule in `chat-gateway-guilds` ("Bindings and prompt answers are checked against their server"), not as a MODIFIED copy of "Interactive prompts rendered natively via PromptBus": it only refuses more, and leaving that block alone avoids churn with `add-supervised-tool-approval` and with C/D, which re-copy it. Collateral checked: PromptBus, Verb tiers, Sticky routing and Hard in-session tool policy are unchanged in meaning.
- **Binding-scoped tiers** (today's chokepoint): unchanged resolution from the binding's own `principals`/`roles`. `AuthorizeRequestInput` gains `guildId`. The ceiling becomes `min(binding.ceiling, guild.ceiling ?? global, global)`. The controller refuses `unbound_channel` unless the binding's `guildId` **equals** the message's `guildId`; a binding with no `guildId` is refused too (refuse-unless-equal, never skip), which is why normalization (D5) gives every legacy binding its guild.
- **Server-scoped tiers** (new `team.authorizeServerRequest({author, guildId, channelId, verb})`): resolve from `guilds[g].principals` (identifier first) and `roles` (capped at `control`), highest wins. Clamp to `min(guild.ceiling ?? global, global)`. Then the same steps 1, 6-10 as `authorize.ts:104-149` apply: non-human, disarm (the server's latch OR the global latch, D10), non-delegable, allowlist, tier.
- **Which verbs are server-scoped.** `tier.ts` gets a closed set `SERVER_SCOPED_VERBS`; A ships `{disarm}` and each later change extends it with its own verbs (B's read/admin verbs, D's moderation verbs). A server-scoped verb always resolves through `authorizeServerRequest`, **even inside a bound channel**, from the server record only; binding mappings never satisfy it. Every other verb in a channel with a binding resolves from the binding only, so server mappings never add a tier to a binding verb and the "a principal mapped for one binding gains nothing in another" invariant holds. **`disarm` is the one exception that takes the highest of both**: in a bound channel an `observe`+ principal on the binding **or** on the server may brake, so the emergency brake of decision 19 is never weaker inside a binding than outside it.
- **Session pointers are per server (decided).** `!sessions` shows a session's thread, and `!attach` answers with a pointer to the existing thread, only when that thread is in the SAME server as the command (the lookup is scoped by `guildId`). A session attached only in another server is listed as attachable with no thread and no link, and `!attach` opens a second thread in this server. No thread id or link of one server is ever shown in another, which keeps the per-server isolation of decision 6.
- Delegation disclosure (`index.ts:479-497`) enumerates per guild: a binding's roles in `binding.guildId`, and a server's roles in that server.

### D7. Per-server provisioning

`provisionNew` (`provisioner.ts:125-136`) takes `binding.guildId`. When the id is absent it returns `provisioning_requires_guild_id` (existing reason, kept). It fails with the new `provisioning_guild_not_enabled` unless `guildPolicy(g)` is defined and its `mode` is `interactive` with `provisioning.enabled`. `ChannelBinding` (`provisioning-store.ts:22-40`) gains an optional `guildId`, back-filled from `guildIdFor` on the next reconcile; `channels.json` is the recovery source for a binding whose `guildId` was stripped (D5 step 3, Rollback). The store key stays `workspaceId`, which means a workspace binds into at most one server (spec "One channel per bound workspace" holds). Health reports failures per guild.

- **Reconcile is per binding.** Today `reconcileOnce` returns on the first failing binding (`provisioner.ts:265` `if (failure) return failure;`, `:262-264`), which would let one server's disabled binding starve every later binding in other servers and skip `deactivateUnbound`. The loop now records each binding's outcome under its server and continues. `convergeExisting` (rename + `setChannelOverwrites` on an EXISTING channel, `:202-228`) gets the same server gate as `provisionNew`: a binding whose server is not enabled + `interactive` + `provisioning.enabled` is **skipped** with `provisioning_guild_not_enabled` (no platform call, so a `query` server's old channel gets no further permission change, decision 5). A skip is reported in health per guild and is **not** a reconcile failure. That matters because `applyWrite` reverts the whole team-controls write when reconcile is not ok (`index.ts:410-418`), and a mode switch keeps bindings (D4), so a failing skip would block every later team-controls edit. Genuine platform failures and the shipped `provisioning_requires_guild_id` stay failures (the write is still rejected as today) but no longer stop other servers' bindings; the result carries the first failure reason plus per-guild failures.
- **An access change is never silently skipped (A-T7, decided).** Skipping `convergeExisting` also skips `setChannelOverwrites` (`provisioner.ts:204-228`), so a principal REMOVED from a binding in a skipped server would keep view access of the existing private channel while the team-controls write reported success, contradicting the shipped requirement "Channel visibility is reconciled when the mapping changes" (the write SHALL NOT succeed until overwrites match). The rename/create/re-provision skip above is unchanged; **access** is different. `applyWrite` (`index.ts:401-430`) therefore compares the previous and the candidate binding's access signature (`accessSignature`, `provisioner.ts:82`, exported with a shared `provisionable(guildId)` predicate that `provisionNew`/`convergeExisting` also use) BEFORE it swaps config or reconciles: when a binding with an ACTIVE provisioned channel in a server that is not `provisionable` changes its principals or role mappings, the write is refused `access_unreconciled` (naming the server, telling the operator to enable it as `interactive` with provisioning, or to revert the change) and nothing changes, so the stored mapping and the channel's access stay consistent. The check is judged on what the write changes: an unrelated write is unaffected, and a stale mismatch from an out-of-band edit or a change made while the dashboard was down is only a health problem `access_unreconciled` on that binding (non-failing, like the other skips) until the server is re-enabled or the mapping reverted. Inactive records are exempt (no commands run there). No platform call is made in a non-enabled server, which keeps decision 3 (inert) and the outbound gate intact; the cost is that removing a principal from a binding in an inert server needs the server enabled first.
- **A provisioned channel stays in its server.** The store is keyed by `workspaceId` and `convergeExisting` never compared guilds. When the stored record's `guildId` (back-filled first via `guildIdFor`) differs from the binding's `guildId`, the binding is skipped with `binding_guild_changed` (no channel created, renamed or re-permissioned in either server; health reports it) and, when the stored server cannot be resolved, with `binding_guild_unverified`. Without this the old channel would live on while the controller refuses `unbound_channel` forever, or a re-provision would orphan a channel that keeps the old principals' access. Moving a workspace to another server is deliberately not automatic (it needs an explicit release of the old channel, outside this change); the panel's Server select is disabled once a channel exists (task 6.3).

### D8. Live write lane and settings UI

- New wire constants `GUILDS_SURFACE_MESSAGE = "chat_gateway_guilds_surface"`, `GUILDS_CONFIG_MESSAGE = "chat_gateway_guilds_config"` and `GUILDS_DISARM_MESSAGE = "chat_gateway_guilds_disarm"` (`src/shared/types.ts`), registered in both lanes of `registerSurfaceLane` (`index.ts:352`). The inert lane can show and edit records but has no discovery.
- **Record-level patch with a revision.** The host replaces whole top-level keys with a shallow merge (`plugin-config-routes.ts:107-118`), so a whole-map `guilds` write from a stale tab would overwrite concurrent changes. The write payload is therefore a patch: `{expectedRevision, upsert?: {<guildId>: <partial record> (+ transient inheritAllowlist?: true, clear?: [...])}, remove?: [<guildId>], limits?: {<key>: int}, clearLimits?: [<key>], adopt?: {discardUnresolved?: boolean}}`. Only the named records and `limits` keys change. `clearLimits` removes the named `limits` keys so their documented default applies (an unknown prototype name, or a key both set and cleared, is `invalid_limit`); it is the wire form of an emptied limit input, because `null` is not a valid limit value.
  - **Merge rule.** An upserted partial record is merged over the **raw persisted** record by **top-level key**: a named key REPLACES the stored value whole (arrays and maps are replaced, never merged element-wise), an unnamed key is unchanged, reserved keys included (D1). JSON has no `undefined` and the record schema rejects `null`, so clearing is explicit: the transient `clear: ["allowlist" | "ceiling" | "label"]` deletes those optional keys (so the UI's "inherit global" toggle has a wire form on an already-enabled record), and `inheritAllowlist: true` deletes `allowlist` (D6). Any other name in `clear`, a required or reserved key, is rejected `invalid_clear`; naming a key in both `clear` and the record is `invalid_clear`; `clear` and `inheritAllowlist` are never stored. A never deletes a reserved key (the owning change repairs or overwrites it).
  - **Revision is mandatory.** `revision` is a hash of the canonical JSON of the persisted `guilds` and `limits`, carried on every surface message. A dashboard write that omits `expectedRevision` is rejected `revision_required` and one with a stale value `revision_changed`; nothing changes in either case, so a client that forgets the field cannot bypass the stale-tab protection. The surface carries a revision in legacy mode too (the hash of the empty state). Only `patchGuildFromChat` (below) is exempt, because it changes two fields of one record and takes the latest stored record inside the queue. A `limits` write by another lane (C's `agentTools` limits go through `patchLimits`) changes the revision too, so a stale Behaviour tab gets `revision_changed` and reloads. A chat-origin write (B's `!mode`, `!bind`) is **not** the dashboard patch with the revision dropped, which would hand chat the full surface (any guild id, `remove`, `limits`, `adopt`, `enabled`, `admins`, `principals`). It goes through a distinct writer in `config-writer.ts`, `patchGuildFromChat({originGuildId, senderId, fields: {mode?, channels?}})`: the guild id is the message's own server and the only record touched; the field allowlist is `mode` and `channels` (nothing else, no reserved keys, no `limits`/`remove`/`adopt`/`enabled`); it re-checks `isGuildAdmin(originGuildId, senderId)` itself (`not_admin`, so a lax caller cannot skip it); it refuses `server_not_adopted` while that record is synthesized from legacy keys (never triggers adoption, D5). It carries no `expectedRevision`, takes the latest stored record inside the queue and changes only those fields, so a stale tab's next write fails `revision_changed` instead of reverting an emergency `!mode query`. B owns the commands and their extra refusals (`channel_not_in_server`, `last_channel`) and must call this writer.
- **A write is judged on what it changes.** `validateGuildsWrite` validates each upserted record strictly. For the cross-record rules it checks only what the write adds: `channel_in_multiple_guilds` when a channel id on an upserted record is held by another record (reply names both servers and the channel, also in `guildsConfigError`); `too_many_guilds` only when the write adds records and the result exceeds `limits.maxGuilds`. An existing conflict between untouched records (an out-of-band write, or the boot read's in-memory removal, D1) never blocks an unrelated write, is shown as a problem on both servers, and a patch that edits an offending record can repair it. This keeps one bad record from freezing the whole lane while the UI (which only shows the in-memory view) cannot show why. **Team-controls writes follow the same rule:** `validateTeamControls(raw, limits)` judges a write (adoption included) against `limits.maxBindings` / `limits.maxMappings` only for what it adds, so an unrelated team write, or adoption, is accepted over a cap lowered after bindings were stored, and adding beyond the cap is `too_many_bindings`. The boot read loads every stored record regardless of `limits.maxGuilds` (the cap judges additions only), so lowering a limit never drops a configured server. **`remove` is never blocked by references:** a `remove` of a server still referenced by team bindings, persisted session bindings, a provisioned channel, mirrored threads or a disarm latch succeeds; the references are kept and fail closed (`provisioning_guild_not_enabled` skip, no mirror, latch kept per D10, the message index purged per decision 8), so the operator always has an emergency exit.
- **One write queue, one module.** All config writes of this plugin run through ONE serialized writer, a promise-chain queue exported from `src/server/config-writer.ts`; each step reads the live state when it starts. A's guilds lane, the team-controls lane (`index.ts:401-430`), B's lane and C's `chat_gateway_agent_tools_config` lane all enqueue on it, so adoption (D5) and any `teamControls` or `limits` rewrite cannot interleave with another lane's write. **A hung write cannot wedge the queue:** each step's `updatePluginConfig` is bounded by `limits.configWriteTimeoutMs` (default 30000, `0` = no timeout, clamped per D2); on timeout the write fails `config_write_timeout`, memory reverts and the queue continues, so an emergency chat `!mode query` is never stuck behind a hung host call.
- **Write sequence** (same as team-controls): validate → swap the in-memory policy → reconcile provisioning → `updatePluginConfig` → revert on failure. No restart is needed. `patchLimits(patch)` is the **only** writer of `limits` (A's Behaviour fields, B's and C's limit keys go through it). The host replaces a top-level key whole with a shallow merge (`packages/server/src/server.ts:4771`, `{...current, ...partial}`; `plugin-config-routes.ts:107-118`), so a `limits` write that carried only its own keys would drop every other lane's. The rule for **every lane that writes `limits`**: read the current stored `limits` object (not the defaults-resolved view) inside the queue, patch only its own keys, write the WHOLE object back, carrying every unknown `limits.*` key over verbatim (D1: the validator preserves them). Later changes' keys (B: `listRows`, `indexFlushMs`, `indexSweepMs`, `maxAskCalls`; C: `agentToolReadsPerMinute`, `agentToolSendsPerMinute`, `agentToolReadsPerSessionPerMinute`, `agentToolSendsPerSessionPerMinute`, `agentToolReadMessages`, `agentToolSearchScan`, `agentToolResults`, `agentToolRequestDeadlineMs`, `agentToolConfirmPendingS`, `agentToolLogSuppressS`, `agentToolReadLogEntries`) therefore survive a save of A's Behaviour fields and a rollback to A.
- **Disarm lane.** `chat_gateway_guilds_disarm` carries `{action: "disarm"|"rearm"|"rearm_all", guildId?}` (D10). It is dashboard-only like the other lanes.
- **Out-of-band writes.** The generic `plugin_config_write`/REST route validates only the body against the JSON schema (`plugin-config-routes.ts:97-118`): it does not run `channel_in_multiple_guilds` or any cross-record rule. No host config-change hook is verified, so live policy follows **only** the guilds lane; a `guilds` value written another way takes effect at the next boot read, where per-record validation (D1) drops only offending records fail-closed and reports each as `record_rejected:<reason>` in that server's `problems` and in a surface `guildsConfigError` (the analogue of `teamConfigError`). The settings UI and the docs name the lane as the supported write path.
- `ChatGatewaySettings.tsx`: a new **Servers** `SettingsGroup` renders `GuildView[]`. Each row has a name/id, a status pill (`Discovered · inert` / `Enabled · interactive` / `Enabled · query` / `Disabled` / `Not in server` / `Legacy`), an Enable toggle (which asks the inherit-vs-own allowlist question, D6), a Mode select, Admins, an Allowlist with an "inherit global" toggle, Channels, server tiers (principals/roles/ceiling) and a Provisioning toggle that is shown for `interactive` only. ### D9. Discord permissions and intents

Unverified: the existing delegation enumeration calls `guild.members.fetch()` (`discord.ts:442`) without the `GuildMembers` intent, so it already reports "unavailable" on failure. This change does not alter that.

  - Provisioning servers: add Manage Channels and Manage Roles (overwrites).

### D10. Per-server disarm latch

The latch becomes a set: one **global** latch (disarm-all) plus one latch **per guild id**. `authorize()` is unchanged (it takes one boolean, `authorize.ts:68`, `:133`). The controller passes `globalLatch || guildLatch(guildId)` for the request's server, which it knows from the message `guildId`. Direct messages see only the global latch for ordinary requests, but a **disarm command carries no server in a DM and is refused**: `disarm` is server-scoped, so `authorizeServerRequest` needs a `guildId`; `controller.disarm(guildId)` takes a required guild id (the global latch is set only by the dashboard lane and boot seeding), so a DM can never drive the global latch. The shipped path refused a DM disarm only as `unbound_channel` (`gateway.ts:1668` `dmScopedOut`), which no longer applies to a server-scoped verb; the reply reuses the DM hint ("use a server channel"), no latch changes, and the guild-less attempt is counted as `guild_not_enabled`. A request in server B is therefore unaffected by a disarm in server A. The dashboard lane validates its `guildId` as a snowflake (`invalid_guild_id` when missing for `disarm`/`rearm` or not `^[0-9]+$`, including `__proto__`); a snowflake with no record is accepted, so a discovered server can be latched.

- **Chat.** `!disarm` (same chokepoint check, `gateway.ts:1651`) is matched by the **shipped pattern unchanged**, `/^\s*!\s*disarm\s*$/i` (`gateway.ts:1626`), which tolerates spaces after the bang, evaluated **before** the whole-message `!` rule (D4, where `! hi` is plain text) and before the mode gate. So `! disarm` still brakes in both modes, never spawns a session in an `interactive` server and is never `query_mode`-refused; the lenient match is deliberate for an emergency brake and is not widened (`!disarm now` stays a steer prompt). It latches **only the server it was sent from**. The reply names it: `Disarmed this server. Other servers are unaffected. Actions here are refused until an operator re-arms from the dashboard.` A request refused as `disarmed` in that server answers `Already disarmed.` as today (`gateway.ts:1655-1658`). The tier needed is unchanged (`observe` on the binding, `tier.ts:75-79`). `!disarm` works in **both** modes and is never refused with `query_mode`. `disarm` is a server-scoped verb (D6): it is authorized through `team.authorizeServerRequest` at `observe` using the server-scoped `principals`/`roles`, and **in a bound channel the highest of the binding tier and the server tier applies** (the only exception to the no-widen rule), so anyone `observe`+ in that server may brake from any opted-in channel, bound or not (owner decision 19); it is not an admin-only command. Only the dashboard re-arms.
- **Dashboard.** Disarm-all stays a dashboard action and keeps the shipped flag: `teamControls.disarmed: true` sets the **global** latch (`index.ts:452-467`). `shouldApplyDisarm` (`index.ts:105`) keeps comparing a written `disarmed` with the **global** latch only. The `disarmed` field is a stored, schema-defaulted global-only field and the team panel spreads `config.teamControls` into every write (`team-controls-panel.tsx:199`), so a `teamControls` write carrying `disarmed: false` while only a server latch is live must **never** clear server latches. A `teamControls` write therefore never touches a per-server latch. The dashboard is the **only** re-arm path, through the explicit lane `chat_gateway_guilds_disarm` `{action: "disarm"|"rearm"|"rearm_all", guildId?}`: `rearm` clears one server's latch, `rearm_all` clears the global latch and every server latch. `rearm` while the global latch is live is refused `global_disarm_active` (re-arm all first), so a server never appears re-armed while the global latch still refuses it. A chat caller can never re-arm (`rearmFromChat` stays, `controller.ts:161-164`). **Read helper for callers outside the team controller (C).** `disarmStateFor(guildId?): "armed" | "disarmed" | "unknown"` is exported from `src/server/team/disarm-store.ts` and works when `teamControls` is not configured: **the live controller is the source whenever it exists**: `index.ts` registers it with the store module when it builds it (`team.isGuildDisarmed(guildId)`, or the global latch when no `guildId`) and unregisters it on shutdown, so the helper never disagrees with the process. The file is consulted only when no controller is registered (before it is built, or an inert install): the global latch, or global-or-that-server's when `guildId` is given; a missing file falls back to the global `teamControls.disarmed` config value; an existing unreadable or corrupt file is `"unknown"`. This matters because `save()` is best-effort and swallows failures (`disarm-store.ts:43-57`): after a failed save the file can say armed while the live latch is set, and a file-first helper would report `"armed"` for a disarmed server, a fail-OPEN for C's send path. A live latch always reads `"disarmed"`. A caller that must fail closed (C's agent tools) refuses on `"disarmed"` and on `"unknown"`. A failed save does not make the helper `"unknown"`: the live state is true, and `disarm_state_unwritable` already tells the operator the latch may not survive a restart.
- **Not config.** Latches are runtime state, never written to plugin config: a chat disarm must not write config (`disarm-store.ts:3-9`). `GuildView.disarmed` and the existing surface `disarmed` (global) show them. Mirroring continues in a disarmed server (`chat-gateway-output-filter`).
- **Persistence and migration of `disarm.json`.** The shipped file is `{"disarmed": boolean}` (`disarm-store.ts:49`), read by `load()` which returns `undefined` for a missing/corrupt file so boot falls back to `teamControls.disarmed` (`:31-42`, `index.ts:292-294`). The new shape is `{"disarmed": <any latch>, "all": <global>, "guilds": {"<id>": true}}`. `load()` returns `{all, guilds}`: when `all` or `guilds` is present it reads them; otherwise it reads the legacy shape, where `disarmed: true` becomes `all: true` (a top-level `disarmed: true` with `all` false/absent and no `guilds` entry, such as a torn or rollback-written file, is treated the same way: any `disarmed: true` that names no explicit latch is the global latch, fail-closed) (the old halt was global, so it **stays global** and fail-closed until the dashboard re-arms) and `false` becomes no latch. `load()` now **distinguishes** the two failure cases: a **missing** file stays `undefined` (seed `all` from `teamControls.disarmed`, shipped behaviour), but an **existing file that is unreadable or corrupt** latches the global latch (fail-closed, since per-server latches may have been lost; owner decision A-T3, a deliberate change from the shipped seed-from-config behaviour) and adds a surface problem `disarm_state_unreadable`, until the dashboard re-arms (`rearm_all`), whose next successful `save()` rewrites the file. A failed `save()` stays swallowed on the message path (a full disk must not stop the bot answering) but is counted and surfaced as `disarm_state_unwritable` in the surface problems, so a latch that may not survive a restart is visible. Nothing is migrated at boot: the file is rewritten in the new shape by the next `save()` (every transition goes through the single writer, `controller.ts:117-121`), keeping the atomic 0600 write and best-effort error swallowing (`disarm-store.ts:43-57`). Latches are not pruned when a server is removed from config, so re-adding it stays fail-closed. Re-arm-all clears them.
- **Rollback.** The top-level `disarmed` is written `true` whenever any latch is live, so an older version, which reads only that key (`disarm-store.ts:35`) and ignores `all`/`guilds`, treats it as its single global latch and halts **every** server. That fails closed. An older version's dashboard re-arm writes `{disarmed:false}`, which a newer reader parses as the legacy shape with no latch.

## Security notes

- **Fail-closed default.** The default is inert, and enabling a server is an explicit dashboard action. A message from an unconfigured or disabled server never reaches L1, a session or the log. The silent drop prevents answering every channel of every server (noise, 429s, ban risk).
- **Cross-server isolation.** Admins, allowlist, tiers and channel opt-in are all keyed by guild. A channel id may belong to only one record. A binding is checked against the message guild.
- **Adoption cannot widen on rollback** (see Rollback). A `query` server can never be driven interactively by an older version, because adoption clears `groupChannels`.
- **Untrusted content.** Guild names and labels come from Discord or the operator. They are rendered as React text and never put into prompts, logs or paths. A drops no new content into any model context. Prompt-injection posture for channel content is B's (`!ask`).
- **Spam.** The L1/L4 checks run before the mode gate, so `query_mode` replies only to whole-message `!` commands from allowlisted users in opted-in channels, and plain text is never answered with `query_mode`. In a `query` server (usually busy human chat) a non-allowlisted user is dropped silently. In an `interactive` server the shipped `Refused: not_allowlisted.` reply is kept (`gateway.ts:1573-1590`), but every refusal reply in a guild channel is throttled by `limits.refusalRepliesPerMinute` (default 6 per opted-in channel, threads against their parent, `0` = unlimited), so a busy channel cannot make the bot answer every message (429 / ban risk).
- **Allowlist inheritance.** A server without its own `allowlist` admits every globally paired user. Enabling a server requires an explicit inherit-or-own choice (D6).
- **Code-execution scope.** `allowedRoots` is global (D6): an admin of any `interactive` server can bind any cwd under it. Enable `interactive` only on servers whose admins hold that trust.
- **Pairing brake.** `limits.pairingMaxAttempts = 0` disables the pairing lockout and `limits.pairingTtlMinutes = 0` makes a code never expire. The code is 6 digits (10^6) and the lockout is the only brute-force brake, so `0` there is the operator's explicit, documented risk (the owner's unlimited convention applied to a security control). Defaults keep today's 15 minutes / 10 attempts.
- **Reserved-key hardening.** Reserved record objects are cloned with `structuredClone`, size-bounded and checked for prototype-pollution keys (D1).
- **Privacy.** No message content is persisted by A. The audit entry gains only `guildId`.

## Migration, compatibility, rollback

- **Upgrade.** No action is needed (D5 normalization). The panel shows `Legacy` records until the operator saves once.
- **Older plugin versions with new config (rollback).** The host validates only the written body (`plugin-config-routes.ts:97`), and an older `resolveConfig` reads named keys only (`config.ts:57-95`), so `guilds`/`limits` are ignored, not rejected. An older `validateTeamControls` ignores a binding's `guildId` (`team-config.ts:168-188`), and its team-controls write strips it.
  - **Rollback before adoption**: identical behaviour.
  - **Rollback after adoption**: `groupChannels`/`admins`/`teamControls.guildId` are empty, so the old version is **inert in every guild** (fail-closed), new provisioning fails with `provisioning_requires_guild_id`, and existing provisioned channels remain but receive nothing. DM pairing still works.
  - **Rollback from B, C or D to A**: A preserves the reserved record keys (D1), so `guilds.<id>.query`, `.index` and `.moderation` survive an A-only version's reads and writes untouched, and every server stays loadable with its `enabled`, `mode`, `channels` and tiers. The later features are simply off (an A-only build never reads those keys). Top-level `agentTools` is not part of `guilds` and A's write lanes never rewrite it. Re-upgrading finds the settings intact. Without this rule an A-only validator with `additionalProperties: false` would reject the whole record and make the server inert.
  - **Rollback, an older team-controls save, re-upgrade.** An older `validateTeamControls` ignores a binding's `guildId` and its save strips it, while `teamControls.guildId` was already removed by adoption. On re-upgrade normalization (D5 step 3) recovers each binding's guild from the `guildId` stored on its `channels.json` record (D7 back-fill) before it reports `provisioning_requires_guild_id`; only a binding that never had a stored guild needs the operator to pick one in the panel.
  - **Recovery**: copy each `interactive` server's `channels` into `groupChannels`, its `admins` into `admins`, and one guild id into `teamControls.guildId`. This is documented in `docs/chat-gateway.md`.
- **Behaviour change on upgrade: refusal throttle.** Shipped refusal replies (`Refused: not_allowlisted.` and the others) are unthrottled (`gateway.ts:1573-1590`). After this change they are limited to `limits.refusalRepliesPerMinute` (default 6 per opted-in channel per minute, threads against their parent). An operator who wants the exact old behaviour sets it to `0`. Documented in `docs/chat-gateway.md`.
- **Behaviour change on upgrade: corrupt latch file.** A corrupt `disarm.json` used to re-arm silently at boot. It now latches globally and reports `disarm_state_unreadable` until the dashboard re-arms.
- **Persisted files.** `bindings.json` entries gain an optional `guildId` (D4), written whole by the store and ignored by older versions (`routing.ts:37-77`); a pre-upgrade binding is back-filled lazily and fails closed until resolved (`binding_guild_unresolved`). `channels.json` records gain an optional `guildId`, which older versions ignore. `command-log.json` entries gain an optional `guildId`, which older readers load unchanged; `isEntry` checks only principal/verb/channelId/outcome (`audit.ts:58-71`).

## Risks / Trade-offs

- Channel resolution at ready can be slow when there are many `groupChannels`. A server is dark until one of its ids resolves, and an unresolved id is dropped (a fail-closed window), but no id delays another server (D5). Calls run concurrently, each bounded by `limits.legacyResolveTimeoutMs`; a timed-out id is reported, retried later and blocks adoption (D5) rather than being dropped.
- Disarm is per server (D10), so a principal's `!disarm` cannot halt another server. The cost is that a halt of one server does not stop a compromised principal acting in another. The dashboard disarm-all covers that. Latch state has a second shape in `disarm.json`; rollback and legacy files stay fail-closed (D10).
- Adoption is a one-way config rewrite. It is mitigated by the explicit save, the refusal while any legacy id is unresolved, the re-read inside the write queue, the documented recovery, and the fact that it fails closed.

## Contract (normative for B, C, D)

- **Config keys**: `guilds.<guildId>.{enabled=false, mode="query", label?, admins=[], allowlist? (absent=inherit global), channels=[], principals={}, roles={}, ceiling? (absent=global), provisioning.enabled=false}`; `limits.{maxGuilds=0 (unlimited), maxBindings=200, maxMappings=500, maxDiscoveredGuilds=100, maxReservedBytes=262144, refusalRepliesPerMinute=6, legacyResolveTimeoutMs=15000, pairingTtlMinutes=15, pairingMaxAttempts=10, configWriteTimeoutMs=30000}` (`limits` allows and preserves unknown integer keys; **`patchLimits` is its only writer**, B and C add their keys through it); `teamControls.bindings.<ws>.guildId`. No schema `default` on `guilds`/`limits`. Disarm: per-server latch in `disarm.json` (not config), `teamControls.disarmed` = global disarm-all, dashboard-only re-arm.
- **Reserved record keys for later changes (preserved verbatim by A's validator, rollback-safe).** B: `guilds.<id>.query`, `guilds.<id>.index`. D: `guilds.<id>.moderation`. C's settings are top-level `agentTools` (no per-record key). New keys are optional, default fail-closed, and never repurpose A's keys. New limit keys go in `limits` (gateway-wide) or on the owning record object (per-server).
- **Unlimited**: `0` = unlimited for all count, size and duration limits. A ms/s setting above the Node timer maximum is clamped to 2147483647 ms at runtime (stored value kept). Per-minute windows are sliding and half-open `(now − W, now]`. Clearing a limit input in a settings panel removes the key (default applies); `0` is written only when typed.
- **Runtime API**: `guildPolicy(guildId)` (enabled-only), `effectiveAllowlist(guildId)`, `isGuildAdmin(guildId, userId)`, `team.authorizeServerRequest({author, guildId, channelId, verb})`; `InboundMessage.guildId?`, `InteractiveResponse.guildId?`, `CommandLogEntry.guildId?`; adapter `listGuilds()`, `onGuildsChanged()`, `inboundScope()`.
- **Reasons**: `query_mode` (refusal, added to `RefusalReason`), `guild_not_enabled` / `channel_not_opted_in` / `not_allowlisted` (silent drop counters in a `query` server, never replied), `provisioning_guild_not_enabled`, `binding_guild_changed`, `binding_guild_unverified`; validation reasons from D1 (including `unknown_guild_key`, `invalid_reserved_key`, `invalid_snowflake`, `invalid_limit`, `too_many_bindings`, `revision_changed`, `revision_required`, `invalid_clear`, `legacy_unresolved`, `allowlist_choice_required`, `server_not_adopted`, `invalid_guild_record`, `config_write_timeout`; `reserved_guild_id` is dropped); `access_unreconciled` (a team-controls write that changes access of a provisioned channel in a non-provisionable server; also a health problem), silent counter `binding_guild_unresolved`; chat-write refusal `not_admin` (reused); counter `refusal_throttled`; `global_disarm_active`. The refusal `disarmed` is reused, per server or global. Silent drop counter `guild_not_enabled` stays reserved for a guild-only action that arrives without a `guildId` (D's `!mod` or a click from a DM). Reason codes owned by C (informational, A never emits them): `agent_tools_disabled`, `discord_unavailable`, `not_readable`, `not_sendable`, `cross_guild_denied`, `spawned_session_denied`, `unknown_session`, `rate_limited`, `blocked`, `denied`, `message_too_long`, `empty_message`, `discord_error`, `invalid_agent_tools`, `invalid_limit`.
