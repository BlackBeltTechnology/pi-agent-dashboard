## Goals / Non-Goals

**Goals:** one shared, typed kit for secret-holding API plugins; no per-connector client bundle; writes confirmed in the UI and re-checked on the server; stable error codes the agent can act on; the confirm card closes when the tool stops waiting.

**Non-Goals:** provider code; OpenAPI/catalog/gateway (`add-connector-layer`); OAuth connectors (they can call `ctx.oauth.startFlow` themselves); a sandbox (`ctx.ui.confirm` is a UX guard, not isolation); a countdown on the dashboard card.

## Decisions

### D1. One `./connector` subpath, erasable TS, structural types

The new subpath `packages/dashboard-plugin-runtime/src/connector/index.ts` exports `registerConnectorTools`, `registerConnectorServer`, `ConnectorError`, `toFailure`, `redact` and re-exports the shared types. It imports nothing from React, the `./server` barrel (which pulls the loader, Ajv and Fastify types) or pi. Its context types are structural slices (`ConnectorServerContext`, `ConnectorPiLike`), as in the reference, so a plugin that bundles a copy keeps working against a newer host. All code passes `erasableSyntaxOnly` (no `enum`/`namespace`/parameter properties; `import type`), because runtime plugins import package sources as `.ts` (`packages/dashboard-plugin-runtime/package.json` `exports` → `./src/*.ts`).

*Alternatives:* put the helpers in `./bridge` and `./server`. `./server` is a heavy host-internal barrel and `./bridge` is documented as lane-only. Rejected.

### D2. Error contract lives in `packages/shared`

`packages/shared/src/dashboard-plugin/connector.ts` holds `ConnectorErrorCode` (a string-literal union plus a frozen `CONNECTOR_ERROR_CODES` array), `OpResult`, `ConnectorField`, and `ConnectorConfigView` (the GET body). Reason: `UiPrimitiveMap` (shared) must type the `ui:connector-settings` props with `ConnectorField`, and spec `plugin-host-api` "Shared contracts live in non-plugin packages" requires shared contracts outside plugin packages. The codes are the reference union with one addition:

- `lane_timeout` (new) means **outcome unknown**. It is used when the lane returns `timeout` or `disconnected` (the frame was sent, D10), and when a **write** operation hits the server deadline (D4). For a write the message says the write may have been applied and the agent must check before retrying. The reference maps every lane failure to `lane_unavailable`, which wrongly suggests nothing happened. `reply_too_large` / `reply_not_serializable` mean the handler ran: for a write they also map to `lane_timeout`, for a read to `lane_unavailable` (decision H4).
- `lane_unavailable` is for lane errors where the request never reached a handler: `unavailable` (incl. a frame that could not be sent, D10), `no_handler`, `request_too_large`, `request_not_serializable`, and any unknown lane error.
- `keychain_unavailable` / `credential_unreadable` are produced only by mapping a `ctx.credentials` failure or an unknown record version (D5). The kit never touches a keychain itself.

`ConnectorField` is `{name, label, kind: "text" | "secret" | "select" | "boolean", required?, options?, help?, default?}`. `options` only and always on `select`. `required` applies to `text`/`secret`/`select`. `default`: string for `text`/`select` (select default within `options`), boolean for `boolean`, never on `secret`. Stored string values are capped at 4 KiB (UTF-8) each; the store's own 64 KiB record cap stays as a backstop. One pure `validateConnectorFields` in the shared module serves the server helper and the client primitive.

### D3. Bridge: `registerConnectorTools`

- One tool per `ToolSpec`: name `<connectorId>_<tool>` (validated against `^[a-z][a-z0-9_]*$`, total ≤ 64 chars; an invalid name throws at registration), `label` `<title>: <tool>`, `exposure: "codemode"`, `namespace {name: connectorId, description}`, `annotations {readOnlyHint: !write, destructiveHint: !!destructive, idempotentHint: !write, openWorldHint: true}`, and description prefix `[WRITE]` for writes.
- **Write confirmation.** No `ctx.hasUI` or no `ctx.ui.confirm` → `confirmation_unavailable`. The body is the pretty-printed params inside one fenced code block (language tag `json`) whose backtick fence is longer than any backtick run in the JSON. Reason: the dashboard card renders the body as markdown (`ConfirmRenderer.tsx` → `MarkdownContent` with `rehype-raw` + sanitize; the message travels via `prompt-meta.ts` `buildPromptMeta`), so raw agent values such as `<!-- x -->` or `[a](http://b)` could hide or disguise content. The literal guarantee covers the dashboard card only; TUI and chat-gateway rendering is unverified (follow-up). If the pretty-printed JSON (UTF-8 bytes, what the user reads) exceeds 4 KiB (4096 bytes) the tool fails `invalid_input` **before** confirming: the user must see exactly what will be sent, so the body is never truncated. Otherwise the kit creates an `AbortController` plus its own timer (default 5 min; the option must be a positive finite integer ms, otherwise `registerConnectorTools` throws before registering anything) and calls `ctx.ui.confirm(title, body, {timeout, signal, toolCallId, pluginMeta: {pluginId, kind: "connector-write", connector, tool, destructive}})`. If the tool's own `signal` (pi `execute` 3rd arg) aborts, the kit aborts too and the tool fails `declined` (message `aborted`); the signal is re-checked after `confirm` resolves `true` and before the lane send, so an abort in that window sends nothing. The kit also races the promise against its timer, for hosts that ignore the options. Attribution: the effective timeout is `min(kit timeout, ctx.ui.promptTimeoutMs)` (a missing or non-positive bus value counts as infinite; D6 exposes it). The result is `confirmation_timeout` when the kit timer fired, or when `confirm` returned a non-`true` answer after the effective timeout elapsed (strict: elapsed ≥ effective timeout, measured from the call on the same monotonic clock the kit armed its timer with). It is `declined` when the answer was not `true` before that, and otherwise continue. The patched `confirm` cannot tell a decline from a bus cancel (Finding), so elapsed time is the only signal. The `finally` block aborts the controller, so a host that honours `signal` (the D6 fix) always removes the card. Destructive tools add a "cannot be undone" line to the body.
- **Lane call** `requestPluginServer(pluginId, "<connectorId>/<tool>", {params})` (injectable for tests). Reply mapping: `ok:false` + `timeout`/`disconnected` → `lane_timeout` (sent, outcome unknown); `reply_too_large`/`reply_not_serializable` → `lane_timeout` for a write, `lane_unavailable` for a read (the handler ran); other `ok:false`, incl. `unavailable` for a frame never sent (D10) → `lane_unavailable`; malformed `result` → `internal`; `OpFailure` → its code, except a code outside `CONNECTOR_ERROR_CODES` → `internal` with the message kept; success → text content (JSON) plus `details {connector, tool}`.
- Failures throw `Error("[<code>] <message>")`. pi reports a thrown error as a tool error, and the code prefix is what the agent keys on. This matches the reference.

### D4. Server: `registerConnectorServer`

- **Plugin id and host checks.** The helper uses the host-supplied `ctx.pluginId` (new, D8) for routes, lane types and the intent. A plugin-supplied `spec.pluginId` that differs throws at activation, so a plugin cannot register another plugin's config routes or settings intent through the kit. Missing `ctx.pluginId` or `ctx.registerPiRequestHandler` throws `[host_unsupported]` at activation, before anything is registered. Operation names must match `^[a-z][a-z0-9_]*$` and be unique; the whole operation and field lists are validated before any route, handler or intent is registered. A missing `ctx.credentials` keeps the softer behaviour (routes and ops answer `host_unsupported`) so the settings page can explain it.
- Routes `GET|PUT|DELETE /api/plugins/<pluginId>/config` on `ctx.fastify`. The path is concrete, so a generic `:id` row in `ROUTE_TIERS` or the MCP denylist would never match it (Context). The controls are: the fail-closed `operate` default for unlisted routes, and MCP advertising only reviewed manifest rows. The first-party fixture plugin (D9) adds concrete `operate` rows for its three routes and a concrete denylist prefix `/api/plugins/connector-kit-fixture/`, because the completeness test requires every first-party route to be tiered and bound or denylisted.
- **Stored record:** `ctx.credentials` key `connector-config` → `{v: 1, values, writesEnabled, savedAt}`. Non-secret values are stored here too (one atomic record). Nothing goes to `~/.pi/dashboard/config.json`, so `plugin_config_update` broadcasts never carry connector values.
- **GET** returns `ConnectorConfigView {title, configured, writesEnabled, savedAt, fields, values (non-secret only), secretsSet: Record<name, boolean>}`. It never returns a secret value.
- **PUT** sanitises against the field list. Unknown keys are dropped. A `select` value outside `options` → 400 `invalid_input`. An empty or absent secret keeps the stored value. An absent non-secret keeps the stored value. An explicit empty string clears a non-secret. A value over 4 KiB → 400 `invalid_input`. Missing required fields → 400 `invalid_input` naming the field labels (never values). A non-object `values` (array, string, number, `null`) or non-object body → 400 `invalid_input`, nothing stored. `writesEnabled` absent keeps the stored switch, or persists `false` when no record exists; a non-boolean → 400 `invalid_input`. GET always returns a boolean `writesEnabled` (`false` without a record). A store `record_too_large` / `invalid_record` rejection → 400 `invalid_input`. The write uses `ctx.credentials.update` (atomic RMW, `packages/dashboard-plugin-runtime/src/server/server-context.ts:877-880`), so two PUTs cannot interleave. Its callback is synchronous, so all validation runs inside it on `prev` with no await; a validation failure is thrown from the callback and nothing is written. A previous record that the store returns but that fails the kit schema (for example a pre-kit envelope from `pi-hu-connectors`) is treated as empty, so the user can overwrite it. A record with a numeric `v` above the kit's version, or a store rejection, is never treated as empty (D5).
- **DELETE** removes the record → view with `configured:false`.
- **Status mapping:** `invalid_input` → 400, `host_unsupported` → 501, `keychain_unavailable` → 503, others → 500. The body is `{error: code, message}` only.
- **Operations:** one `ctx.registerPiRequestHandler("<connectorId>/<op>")` per operation. The handler loads the record. Missing or incomplete → `missing_credential`. A write with `writesEnabled !== true` → `writes_disabled` (re-checked server-side even though the bridge confirmed). Otherwise it runs `op.run(params, values, {signal})` under a deadline (default 12 s; a configured value is a finite integer with 0 < ms < 15000, else `registerConnectorServer` throws). The deadline covers the whole handler including the `ctx.credentials.get` read: expiry during the read → `keychain_unavailable` and `run` never starts. On expiry during `run` it aborts the signal. A read returns `provider_unavailable` with "timed out". A write returns `lane_timeout` with "outcome unknown — check before retrying", because the provider may have applied it. It **never throws**: every failure becomes an `OpFailure` through `toFailure(e, secretValues)`. Redaction replaces each stored secret of length ≥ 4 in a failure's message and details **and in a success's `data`** by a structural walk with no re-parse, so it cannot throw (iterative walk, so 10 000-deep nesting is safe; an object that contains itself gets `"[Circular]"` for the repeated reference; no performance budget): string leaves and object keys get each secret replaced, longest first; a number or boolean is untouched unless `String(value)` equals a secret, then it becomes the string `[REDACTED]`. A non-`ConnectorError` keeps only its message under code `internal` (no stack).
- **Observability:** one structured log line per op (`connector`, `op`, `code|ok`, `ms`) through the plugin logger. It never logs params, values or provider bodies.
- **Settings intent:** at activation the helper broadcasts `plugin_intents {pluginId, sessionId: null, slot: "settings-section", intent: {primitive: "ui:connector-settings", props: {title, fields, writesToggle}}}` through `ctx.broadcastToSubscribers` (`packages/dashboard-plugin-runtime/src/server/server-context.ts:1042`). `writesToggle` is `ops.some(op => op.write)`; there is no separate spec flag. The server's intent cache replays it to reconnecting clients.

### D5. Secrets: `ctx.credentials`, encrypted by the host

The reference wraps records in its own AES-GCM envelope with a per-plugin keychain key (`pi-hu-connectors/packages/core/src/secure-store.ts`). This change drops that. `encrypt-credentials-at-rest` encrypts `plugin-credentials.json` transparently, so the kit stores plain records through `ctx.credentials`. One host key replaces N plugin keys and N keychain prompts. When `ctx.credentials` is absent (older host), routes and ops return `host_unsupported`. 

**Boundary with `encrypt-credentials-at-rest`.** That change rejects every store call on a locked file, and every write while no data key is available, with `PluginCredentialError` code `store_locked` carrying a non-secret `reason` (its spec `plugin-credential-store` and design D3; reasons incl. `keychain_unavailable`, `keychain_timeout`, `key_missing`, `key_mismatch`, `envelope_damaged`, `unsupported_format`). The kit matches structurally (`code === "store_locked"`, string `reason`), because it cannot import server classes. One rule:

- `store_locked` with reason `keychain_unavailable` or `keychain_timeout` → `keychain_unavailable` (503 on routes).
- `store_locked` with any other reason → `credential_unreadable`, with `details.reason` set to the reason.
- any other read failure → `credential_unreadable`.
- a stored record with a numeric `v` above the kit's record version → `credential_unreadable`.

In all four cases PUT and DELETE fail without writing, and ops fail with the code. A locked store is **never** overwritten: "treat as empty" applies only to a record the store returned that fails the kit schema without claiming a newer version (D4).

*Alternative:* store keys in the vault through `ctx.vault`. The vault is read-only for plugins and gated per binding by user approval, so it fits user-managed shared secrets and not plugin-owned config. Not chosen. A connector may still read a vault binding inside `run`.

### D6. Bridge dialog fix: honour `opts.timeout` / `opts.signal`

`PromptBus.request` gains optional `{timeoutMs?, signal?}`. A per-request timeout below the bus timeout wins (an infinite bus timeout counts as larger). A signal already aborted at call time resolves `{cancelled: true}` **before dispatch**: no adapter `onRequest`, no `prompt_request` frame, nothing pending. A signal aborted later calls `cancel(id)`. The listener is removed when the prompt settles. Every patched dialog method in `packages/extension/src/bridge-handlers/ui-prompt-patch.ts` passes `opts.timeout` (positive finite numbers only) and `opts.signal` (objects with `aborted` + `addEventListener` only). Cancel resolves `cancelled: true`, so `confirm` → `false` and `select`/`input`/`editor` → `undefined`, the same values pi returns on its own dialog timeout. Card removal reuses `prompt_cancel` (see Finding). No wire change. The second argument goes to `bus.request` only when a valid `timeout` or `signal` is present. That keeps the call shape that existing specs pin (`bridge-extension` "Bridge SHALL patch `ctx.ui.multiselect`…", `multiselect-dialog`) for option-less calls. Adapters (the TUI, the chat gateway) already handle `onCancel`, so a per-call cancel reaches them the same way a bus timeout does. Spec `ask-user-tool` "Configurable PromptBus timeout" said every method "inherits the same" bus timeout. It is MODIFIED so the bus timeout becomes an upper bound, and its method list gains `inputWithImages` and `batch`, which the bridge already routes through the bus (`packages/extension/src/bridge-handlers/ui-prompt-patch.ts:115,163`).

The patched `confirm` returns `false` for a decline and a bus cancel alike, so a caller cannot attribute a `false`. At `session_start` the bridge also sets read-only `ctx.ui.promptTimeoutMs` to the resolved bus timeout (`resolveAskUserTimeoutMs`, `packages/extension/src/bridge-handlers/lifecycle.ts:369-371`). It is informational only. The kit uses it to compute its effective timeout (D3).

### D7. Settings UI: host primitive via intent, no plugin bundle

`ui:connector-settings` is a host component in `packages/client/src/components/primitives/ConnectorSettings.tsx`, registered in `packages/client/src/lib/plugins/host-primitives.tsx`.

- **Plugin id comes from `usePluginSettingsPageId()`, never from props.** The intent is plugin-authored, and `plugin_intents.pluginId` is set by the emitter, so the primitive must not let one plugin's intent drive another plugin's config route. Outside a plugin settings page it renders nothing.
- It loads `GET /api/plugins/<id>/config` and renders `fields` with `TextField` (`type=password`, `autoComplete="new-password"` for secrets, placeholder "Saved — leave empty to keep" when set), `SelectField` and `ToggleField`. A "Allow write tools (each write still asks)" switch is shown when `writesToggle`. Labels and help are rendered as plain text.
- It registers draft source `plugin:<id>` and commits one PUT on the host Save bar (spec `plugin-settings-consistency` "Configuration values save through the host Save bar"). Blank secrets are not sent. Typed secrets are cleared after commit, on discard and on reset, and are never put in "Copy details".
- "Remove credentials" is an immediate action with a confirm (side-effect class (a) of the same requirement).
- Status is a worded pill (Configured / Needs setup). Errors are one sentence, with the code behind Copy details.
- Field-list limits enforced by the primitive: ≤ 32 fields, unique `name` `^[A-Za-z][A-Za-z0-9_]{0,63}$`, label ≤ 80 chars, help ≤ 300 chars, ≤ 50 select options. Invalid entries are dropped individually, one console warning each: the first 32 fields are kept, the first of duplicate names is kept, an entry with an unknown `kind` or `required` on a `boolean` is dropped (the server throws on the same inputs). With `writesToggle: false` there is no switch and PUT omits `writesEnabled`. After a plugin is disabled the host already hides its settings page, so the kit adds no intent-clearing (verified by test, no kit work). The same validation runs in `registerConnectorServer`, where an invalid spec throws at activation.

*Alternatives:* (a) a manifest `connectorSettings` field. That touches the manifest validator, the registry hash and `PluginRow` claims for no added safety. (b) The reference per-plugin `settings-form.js`. That needs bundle trust per connector, which is the cost this change removes.

### D10. Lane: a frame that was never sent is `unavailable`

`packages/extension/src/plugin-request-client.ts:88` resolves `disconnected` when `send` returns `false`. That is the same string as an in-flight close (`packages/extension/src/bridge.ts:1088`), so the kit cannot tell "nothing applied" from "outcome unknown". The not-sent case changes to the existing `unavailable` code ("the request never left the bridge"). No new string: current consumers already treat `unavailable` as "not connected" (`packages/gmail-plugin/src/bridge/lease-client.ts:33`) or retry it like `disconnected` (`packages/flows-plugin/src/bridge/flow-files-reporter.ts:90`). MODIFIED `plugin-bridge-request-lane` "Bounded waiting and payloads".

### D9. Fixture plugin

`packages/connector-kit-fixture-plugin` (`fixture: true`, gated by `PI_DASHBOARD_FIXTURE_PLUGINS=1`). It has one read op that echoes a non-secret field and one write op that records the call in memory. It serves as an executable example and the E2E target. No network.

## Risks / Trade-offs

- **Threat model: both gates are consent, not a boundary.** The in-bridge confirm and the server-side `writesEnabled` switch protect against an agent that uses the connector tools as offered: no write without a visible prompt on that path, writes off by default, and a stable code the agent can act on. They do **not** stop same-user code that goes around them:
  - *Agent bash.* A bare `curl` to `PUT /api/plugins/<id>/config` is refused under the default `requireLocalProof` (Context, verified). But `pi-dashboard api PUT /api/plugins/<id>/config --data '{"writesEnabled":true}'` mints a proof from the same-user-readable `~/.pi/dashboard/local/token` and is admitted. So an agent with bash can flip the switch.
  - *Other in-process extensions.* The lane function sits on a global symbol (`packages/dashboard-plugin-runtime/src/bridge/index.ts:8`, `Symbol.for("pi-dashboard.pluginRequest")`). Any extension in the same pi process can call `<connectorId>/<op>` directly and skip the confirm. The handler authorises from the payload, as the lane spec requires.
  - The real fixes are bash sandboxing (the `encrypt-credentials-at-rest` follow-up) and a server-verified approval token per write. The approval token is a follow-up, not in this change. `docs/plugin-seams.md` states this threat model (task 7.1).
- **Double prompt in gateway sessions.** Spec `chat-gateway` "Hard in-session tool policy for spawned sessions" escalates a tool that is neither hard-allowed nor hard-denied to a `ctx.ui.confirm` approval. A connector write in such a session asks twice: the gateway approval, then the kit confirm. Cross-change note only; no mechanism in this change.
- **Prompt injection through provider data.** Provider responses are returned verbatim to the agent. The kit cannot sanitise semantics. Mitigation: write tools always confirm with the exact params shown.
- **Redaction is best effort.** It misses secrets shorter than 4 chars or transformed (base64, URL-encoded). Mitigation: connectors raise `ConnectorError` with their own messages. The kit never forwards raw provider error bodies unless the connector puts them in `details`.
- **15 s lane ceiling.** Slow providers hit the 12 s op deadline. Long jobs need an async op pattern (start + poll), which is out of scope.
- **Intent spoofing.** Any server plugin can broadcast an intent under another id. Mitigated by D7: the plugin id comes from the page, and the routes are the page plugin's own.

## Migration Plan

No host data migration. `pi-hu-connectors` replaces `@pi-hu/core` with `/connector` and deletes its `secure-store` + `settings-form.js`. Users enter each connector key again once (old envelope records are ignored and then overwritten). Rollback: revert. Kit records stay inert in the plugin's credential namespace.

## Decisions on former open questions

All accepted by the human (decision sheet C2).

- **Q1 — Confirm default timeout:** kit default 5 min, overridable per connector; effective timeout is `min(kit, bus)`; a shorter bus timeout is reported as `confirmation_timeout` (D3, D6).
- **Q2 — Writes switch:** one switch per plugin, default off. Per-tool control waits for a real need.
- **Q3 — Card countdown:** not in this change; follow-up (needs `metadata.expiresAt`, a client renderer change and an i18n string).
- **Q4 — Example:** a fixture plugin (the only way to E2E the primitive without provider code), D9.
- **Q5 — Bus timeout exposure:** read-only `ctx.ui.promptTimeoutMs` set at `session_start` (D6).
- **Q6 — Not-sent lane error:** reuse `unavailable` (D10).
- **H1–H13 scenario gaps:** applied in D3/D4/D7 and the specs: kit timeout = positive integer ms (H1); 4 KiB cap = bytes of the shown pretty JSON (H2); op deadline 0 < ms < 15000 (H3); `reply_too_large`/`reply_not_serializable` → `lane_timeout` for writes (H4); tool abort → `declined` + re-check before send (H5); deadline covers the credential read (H6); duplicate op names throw up front (H7); unknown server code → `internal` (H8); invalid field entries dropped individually, `required` boolean invalid (H9); disabled plugin hidden by the host (H10); redaction walk with `[Circular]`, no perf budget (H11); non-object `values` → 400 (H12); `writesToggle:false` → PUT omits `writesEnabled` (H13).
