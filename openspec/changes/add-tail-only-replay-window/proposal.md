## Why

Issue #521's reporter, after testing the shipped `lazy-load-session-history` window, asked for one more thing: *"I personally prefer it work as a chat app, which only lazy loads the latest N messages, and when user scrolls up, it loads the next N message, rather than load from session head."* The follow-up change `fix-lazy-history-backfill-ux` gives him the *direction* (tail-anchored backfill) but not the *shape*: a windowed replay still opens with the session's first ~20–200 events pinned above a mid-transcript divider. That head segment is exactly what he does not want, and no configuration can remove it — `HEAD_MIN = 20` plus `MIN_REPLAY_WINDOW = 100` were chosen specifically to make a head-free window unreachable (`lazy-load-session-history` D3).

D3's reasoning was sound and stays intact as a *default*: this repo deliberately protects the chat head (`preserve-chat-head-on-event-trim` raised `maxEventsPerSession` 5000 → 20000) because the first user message is the session's intent, the single most orienting row for a returning reader. But that is a value judgement, not an invariant. A user running multi-day sessions under `billion-context-pi` weighs it differently: for him the head is archaeology and the divider sitting above it is noise. Two defensible answers to the same question is the signature of a setting, not of a bug.

This change makes the head/tail split a **configured shape** rather than a hard-coded one, and adds the top-anchored scroll-triggered loading that only becomes coherent once the head is gone.

## What Changes

- **New config field `memoryLimits.replayWindowMode: "head-tail" | "tail-only"`**, defaulting to `"head-tail"` — today's behaviour, unchanged for everyone who does not opt in. Only meaningful when `maxReplayEvents > 0`; inert otherwise, exactly like the rest of the window machinery.
- **The setting is server-global, and the Why above overstates it as personal.** `memoryLimits` lives in server config and reaches `BrowserHandlerContext` beside `maxReplayEvents`; flipping it in one browser changes the transcript shape for *every* client of that server — the Electron shell, paired mobile/neutral shells through the gateway, and any other operator. That is acceptable for the single-operator deployment this repo targets, and it matches how `maxReplayEvents` already behaves, but it must be stated rather than implied: this is a **deployment** setting, not a per-user preference, and the specs phase either accepts that or makes a scope decision this proposal deliberately does not make.
- **`computeReplayWindow` gains a head-free split.** In `tail-only`, `headEnd = 0` and the whole budget goes to the tail. D3's `HEAD_MIN` floor and the head-edge `message_end` snap become inapplicable rather than violated: there is no head edge to snap. The fits-entirely short-circuit and the tail-edge forward snap are untouched.
- **The gap becomes one-sided.** `history_window` reports `headMaxSeq: 0`, which today's protocol comment declares impossible ("always >= 1 when a window applies"). The field keeps its type and name; its *invariant* widens to `>= 0`, with `0` meaning "nothing above the gap".
- **`oldestGapSeq` is promoted from vestigial to load-bearing.** With no head, nothing else bounds the gap from below: it is both the backfill termination bound and the only discriminator between the two exhausted outcomes (`=== 1` → the session's real beginning; `> 1` → retention trimmed the rest). `fix-lazy-history-backfill-ux` records it as "never read anywhere in the client" and leaves **task 1.3 open on drop-vs-keep** — so this change's dependency is bidirectional: task 1.3 must resolve to KEEP, and the client must start reading the field. If it lands as "drop", this change's core mechanism is invalidated.
- **`MIN_REPLAY_WINDOW` is re-justified, not silently reused.** The `100` floor exists (per `shared-config` spec) "so a configured window can never be too small to contain a head segment" — a rationale that is vacuous in `tail-only`. The proposal's position: the clamp stays, on the *replacement* rationale that a sub-100 tail is a degenerate transcript regardless of head, and a mode switch silently doubling a user's configured `50` would be a worse surprise than a documented floor. This is a spec-text change either way, so `shared-config`'s requirement must be amended rather than left contradicting itself.
- **The divider becomes a top-anchored loading head.** `HistoryGapDivider` currently documents itself as "an interstitial, not a header" — explicitly *not* the Slack/WhatsApp load-older pattern, "because their missing region is unbounded upward" and this gap is not. In `tail-only` it is the transcript's first row, and it gains an **auto-load trigger on scroll proximity** — the behaviour `lazy-load-session-history` recorded as resolved-against ("Divider vs auto-fetch on scroll proximity? RESOLVED: explicit click-to-load"), reopened here because its stated cost (backfill-loop risk, nondeterministic tests) is now bounded by the server's single-flight latch and the terminating `remainingGapCount` loop. Click-to-load remains the fallback whenever the trigger is disarmed (pending, failed, unservable) and remains the only affordance in `head-tail`.
- **Exhaustion is a terminus, not a disappearance.** With no head above it, a fully drained one-sided gap cannot splice itself out of existence the way a two-sided one does — the top row must resolve to a truthful "beginning of loaded history" / "earlier messages were trimmed" state, discriminated by `oldestGapSeq`. **The empty-final-response branch is the hard case:** a tail-anchored walk whose floor is `headMaxSeq + 1 = 1` can issue a last request entirely below `oldestGapSeq`, returning `events: [], remainingGapCount: 0`. Today that sets `unservable: exhausted` (`useMessageHandler.ts:826`) — the A5 "cannot be loaded" state — which in `tail-only` would mislabel a *reached the floor* outcome as a *nothing-servable* one. Either the client floors its request at `oldestGapSeq` so the branch is unreachable, or the branch must resolve to the terminus; the proposal takes no position, but the specs phase must.
- **This collides with a requirement the prerequisite is adding, and the collision is deliberate.** `fix-lazy-history-backfill-ux` ADDs: the unservable divider's "wording SHALL remain truthful whether the events were dropped by retention or removed by replay compaction, *since the client cannot distinguish the two*". Promoting `oldestGapSeq` to a read field manufactures exactly the discriminator that requirement says does not exist — but only for the *floor* question (is there anything below?), never for the *cause* question (retention vs compaction), which stays indistinguishable. The requirement must be amended to say so explicitly rather than left to contradict this change's terminus.
- Not in scope: changing the default mode, changing `maxReplayEvents`' default (owned by `fix-lazy-history-backfill-ux`), or any new retention behaviour. Nothing is removed; `head-tail` remains the shipped default and the rollback lever.

## Capabilities

### New Capabilities

None. Every behaviour extends an already-specified capability; no new spec directory is created.

### Modified Capabilities

- `on-demand-session-replay`: the replay window gains a head-free shape; `history_window.headMaxSeq` may be `0`; the head-edge snap requirement is scoped to windows that have a head. Specifically, "the delivered events SHALL comprise a head segment **beginning at the lowest stored seq** and a tail segment" is flatly violated by `tail-only` and must be conditioned on the mode, not left as an unqualified SHALL.
- `session-history-backfill`: the gap may be bounded only above by the tail; backfill terminates at `oldestGapSeq` (which becomes a read field, not a written-and-ignored one) rather than at a head edge; edge crediting must not credit a head that does not exist; the splice requirement — worded "between the head and tail segments" today, "adjacent to the tail segment" after the prerequisite — must stop presuming a head segment exists; the unservable-divider requirement's indistinguishability clause is narrowed to cause-only (see above); the divider gains a scroll-proximity auto-trigger and a terminal exhausted state.
- `shared-config`: `memoryLimits.replayWindowMode` added, parsed, defaulted, and coerced from an unknown value to the default; the `MIN_REPLAY_WINDOW` requirement's stated rationale is amended (see above).
- `settings-panel`: Memory Limits exposes the mode and states its tradeoff — that `tail-only` drops the session's opening messages from the initial view.
- `chat-transcript-virtualization`: its "deterministic scroll-to-top affordance lands on the first row (index 0)" requirement changes meaning when index 0 is a mutating loading head rather than a message; a scroll-proximity trigger also reads virtualizer scroll state without reintroducing the jump `fix-lazy-history-backfill-ux` removes.
### Adjudicated and dropped

Seven further capabilities were examined against the specs artifact and resolved as *interacts with* rather than *changes*. Recorded so the exclusions are arguable rather than silent:

- `chat-scroll-lock` — its predicate is bottom-relative ("within 50px of the bottom"); a splice above the viewport does not move the bottom edge, so neither scenario changes.
- `chat-view` — its scroll-anchor requirement already covers insertion above the reading position; the trigger is a new *cause* of an already-specified effect.
- `chat-selection-preservation` and `content-copy` — suppressing the selection-anchor compensator for a splice commit is already owned by `fix-lazy-history-backfill-ux`; the automatic trigger changes when that path runs, not what it must guarantee.
- `chat-history-loading-indicator` — the arming rule the trigger depends on lives in `session-history-backfill` ("the backfill affordance arms only after replay completes"), which this change does amend.
- `mobile-resilience` and `responsive-viewport` — the touch/momentum hazard is real but is a property of the trigger, so it is specified as a scenario on the new trigger requirement rather than as a change to a viewport capability.

## Impact

- `packages/shared/src/config.ts` — `MemoryLimits.replayWindowMode`, its default, and a parser that coerces an unknown string to `"head-tail"` rather than throwing.
- `packages/shared/src/browser-protocol.ts` — `HistoryWindowMessage` gains one **additive optional** field announcing the window shape, because the client needs it in three places and never sees `memoryLimits` (design D2a); `headMaxSeq`'s documented invariant widens to `>= 0` (a doc-comment contract, not a validated one). No field is removed or retyped; an older client ignoring the new field falls back to `head-tail`.
- `packages/server/src/browser-handlers/subscription-handler.ts` — `computeReplayWindow` takes the mode; `HEAD_MIN`/`HEAD_CAP`/`HEAD_RATIO` apply only in `head-tail`; the head-edge snap is skipped when `headEnd === 0`.
- **The cold-hydration replay path has NO reset and tail-only breaks its implicit one.** D5's explicit `session_state_reset` guards only two sites — the stale-`lastSeq` branch (`:562`) and the warm windowed branch (`:601`). The disk-hydration loop (`:690`, "Cold hydration is ALWAYS a full stream — window it") calls `sendEventBatches(sub, …, maxReplayEvents)` with no reset in front of it, relying entirely on the reducer's `firstSeq === 1` rule (`useMessageHandler.ts:839`) — which holds today only because a head-tail window always starts at seq 1. In `tail-only` the first delivered seq is `tailMinSeq > 1`, so a client holding any prior state gets the tail **appended onto stale rows** instead of replacing them. This is the single sharpest correctness item in the change; the reset must be extended to the hydration path.
- **Edge-credit corruption in `tail-only` (`subscription-handler.ts:499`).** `headAdjacent = from === current.headMaxSeq + 1` is *true* for the final slice of an untrimmed tail-only gap (`from === 1`, `headMaxSeq === 0`), so the head credit fires on a head that does not exist and sets `headMaxSeq = to`, poisoning every later `remainingGapCount` read. `fix-lazy-history-backfill-ux` task 2.2 makes crediting orientation-based and covers this incidentally; this change must assert it as a requirement rather than inherit it by luck.
- `packages/server/src/server.ts`, `packages/server/src/cli.ts`, `packages/server/src/pairing/browser-gateway.ts` — the mode must reach `BrowserHandlerContext` alongside `maxReplayEvents`.
- `packages/client/src/lib/chat/history-gap.ts` — post-dependency, `nextBackfillRange` is `toSeq = tailMinSeq - 1; fromSeq = max(headMaxSeq + 1, toSeq - SPAN + 1)`, where `headMaxSeq === 0` needs no special handling; the real change is that the walk terminates at the **store floor** (`oldestGapSeq`) instead of at a head edge, and that the terminal state is distinguished from the two-sided "splice the divider out" path.
- **The durable replay cache is permanently missed for windowed sessions, and the auto-trigger changes what that costs.** `useMessageHandler.ts:899` skips `replayPersister` writes whenever `gapCount > 0` (D12: caching a windowed transcript would make the gap invisible and unrecoverable on reload), and `history_backfill_result` deliberately never writes to it (D10). Correct in both modes — but with click-to-load, re-walking after a reload costs one deliberate click, whereas an auto-trigger makes every reload, in every tab, silently re-fetch and re-reduce the gap down to `oldestGapSeq`. The proposal does not propose changing D10/D12; it flags that the trigger converts a user-priced cost into an invisible one, which the specs phase must bound (e.g. the trigger fires once per viewport dwell, not per frame, and does not auto-fire on first paint).
- **Gap state is per-WebSocket, so the auto-trigger multiplies server work by open tabs.** `gapStates` is a `WeakMap<WebSocket, …>` and `history_window` is emitted per subscriber. The "terminating `remainingGapCount` loop" argument is per-socket and says nothing about aggregate load when N tabs each auto-walk the same gap, nor about two tabs holding divergent terminus state mid-walk.
- `packages/client/src/App.tsx` — `handleLoadEarlier` (`:843-858`) is the **sole** `history_backfill` dispatch site and owns the disarm guard (`!gap.armed || gap.pending || gap.unservable`) plus the `toSeq < fromSeq` inversion guard. The scroll-proximity trigger must route through it, not duplicate it; the trigger's own disarm conditions must include `armed`, which the What-Changes list above elides.
- `packages/client/src/hooks/useMessageHandler.ts` — divider placement (`seq >= gap.tailMinSeq`, `:854`) lands the row above the first delivered event, which is correct as written and must be covered as such; the A6 divider removal (`:806-812`, already conditional on `remainingGapCount === 0 && events.length > 0`) must resolve to the terminus state in `tail-only` instead of removing the row.
- `packages/client/src/components/chat/HistoryGapDivider.tsx` — top-anchored presentation, the exhausted terminus, and its documented "not a header" contract inverted for this mode.
- `packages/client/src/components/chat/ChatView.tsx` — the scroll-proximity trigger, its disarm conditions, and its interaction with the grow-pin and the virtualizer's estimated row sizes. **The predicate must be extracted as a pure function** (`lib/chat/`, alongside the existing gap helpers) rather than living inline in a layout-dependent component: jsdom reports no layout, so an in-component assertion is vacuous — the same reason `captureScrollAnchor` was extracted in the first place. Without the extraction the central new behaviour of this change has no unit-testable surface at all, and `tests/e2e/max-replay-events-setting.spec.ts` covers the setting, not the trigger.
- **A divider-less splice is a silent no-op that still advances bookkeeping.** `history_backfill_result` splices at `findIndex(HISTORY_GAP_ROW_ID)` and returns unchanged when absent, yet `publishGap` still advances the edge and decrements `gapCount`. Under click-to-load the divider necessarily exists before the button can be pressed; an auto-trigger firing around a session switch — where placement waits for an `event_replay` carrying `seq >= tailMinSeq` — may reach it and desync gap state from `messages[]`. Not demonstrated reachable; named so the specs phase must rule it in or out rather than inherit it.
- `packages/client/src/components/settings/SettingsPanel.tsx` + `packages/client/src/lib/i18n/` — the control, its help text, and strings for all three shipped languages (`Language = "en" | "zh-CN" | "hu"`), not Hungarian alone.
- Sequencing: **depends on `fix-lazy-history-backfill-ux`**, bidirectionally. Tail-anchored backfill, the `elided` tool status, orientation-based edge crediting (task 2.2), and the scroll-anchor deletion are prerequisites — building a second window shape on the head-first path would mean fixing both. In the other direction, that change's **open task 1.3 (`oldestGapSeq` drop-vs-keep) must land as KEEP**; this proposal is the reason the field stops being vestigial, and task 1.3 should be annotated accordingly rather than decided in isolation.
- Existing coverage to extend: `packages/server/src/__tests__/subscription-handler-window.test.ts`, `subscription-handler-backfill.test.ts`, `packages/client/src/hooks/__tests__/useMessageHandler.history-gap.test.tsx`, `packages/shared/src/__tests__/config.test.ts`, `tests/e2e/max-replay-events-setting.spec.ts`.

## Discipline Skills

- `doubt-driven-review` — this change deliberately reverses two recorded decisions (D3's head-free rejection, and the resolved-against auto-fetch-on-scroll). Both reversals must survive an adversarial pass before they stand.
- `scenario-design` — the interesting cases are combinatorial (mode × `maxReplayEvents` × `maxEventsPerSession` × trimmed store × exhausted gap) and will not fall out of a happy-path test.
- `performance-optimization` — a scroll-proximity trigger runs on the per-frame path; verify by measurement that it neither fires repeatedly during a flick nor regresses scroll smoothness.
- `review-code` — non-trivial change spanning config, wire invariant, server window computation, and virtualized rendering.
- **Accessibility is unaddressed and must not stay that way.** Content auto-inserted above the reading position needs a screen-reader announcement story, focus preservation across the splice, and a way for a programmatic load to be distinguishable from a user-initiated one. `head-tail`'s click-to-load got this for free — a button press is an explicit user action with an obvious ARIA story; the auto path does not.
