## Why

The chat gateway today only reacts to Discord messages. A pi agent working in the dashboard can't look anything up in a Discord server or post an answer there. To do that the operator has to copy text by hand. The Discord bot token already lives on the server (`packages/chat-gateway/src/adapters/discord.ts`). The shipped Gmail plugin already shows the safe pattern: a plugin bridge entry registers pi tools that call the plugin's server entry over the private request lane, and every write asks the user first (`openspec/specs/gmail-plugin`, `openspec/specs/plugin-bridge-request-lane`).

This is change C of the stack A `chat-gateway-multi-guild` → B `chat-gateway-query-mode` → C. It uses A's per-server records (`guilds.<id>`, `0` = unlimited, reason codes) and B's persisted message index.

## What Changes

- **Five pi tools**, namespace `discord`: `discord_servers`, `discord_channels`, `discord_read`, `discord_search`, `discord_send`. A new chat-gateway **bridge entry** registers them. They call the chat-gateway server over the shipped plugin request lane (`requestPluginServer`). Every handler is registered `hubLocalOnly`. **The bot token never leaves the server.** The server runs every Discord call on its existing discord.js client and returns only data.
- **Operator switch** `agentTools.enabled`, default `false`. While it is off, the bridge registers no tools and every lane handler refuses with `agent_tools_disabled`. The server's answer is authoritative.
- **Exposure setting** `agentTools.exposure`: `direct` (default), `codemode` or `deferred`, for the token budget. The tool descriptions are kept terse.
- **Scoping.** Tools see only servers that A has **enabled**. Reads need the read allowlist: `agentTools.read.guilds` (a whole server) or `agentTools.read.channels`. Sends need the send allowlist: `agentTools.send.channels` (channel ids) or `agentTools.send.users` (user ids, as a DM). A session bound to the gateway (spawned or attached) reads and lists only its own server, even after a spawned session's binding closes; several servers, any DM binding (alone or beside a server binding) or an unresolvable server means refused (`cross_guild_denied`), and an unknown session `unknown_session`. For a bound session a whole-server grant (`read.guilds`) exposes only public channels `@everyone` can view, and a private thread only by its own id. A session that may be a child of a gateway-spawned session (no binding, same `cwd` as a live spawned session, when the host exposes no parent link) is confined the same way and cannot send. Reads of a disarmed server are refused, and so are all reads and sends of a session whose own server is disarmed (the emergency brake).
- **Read source.** A channel that B's message index covers is read and searched from the index (continuing live past the index's coverage start). Every other channel is read from live Discord history, bounded by `limits.*` settings, the 256 KiB reply cap and a request deadline (every loop also stops at the lane's own 15 s timeout, even with `0` settings). Results state their source, coverage and completeness. Every result lands in the pi session transcript and goes to that session's model provider; the settings UI and docs say so. Discord offers bots no message-search endpoint, so a live search scans a bounded window of history and reports whether the scan was complete.
- **Untrusted results.** Reads and lists are declared `untrusted` to the untrusted-content guard registry, and each result also carries `details.untrusted: true` and a header saying the content is external. `discord_send` is declared `selfConfirming`.
- **Send safety.** Every send needs a `ctx.ui.confirm` that shows the full text and the resolved target. With no UI the send is `blocked`. Text over Discord's 2000-character platform limit is refused before the confirm, never chunked. Every send uses `allowedMentions: { parse: [] }`. The disarm latches (A) refuse sends. A send chain (preview, send or cancel) counts once toward the send rate limits and the sent text is the previewed one. Every send chain is written to the command log (principal `session:<id>`, verb `agent_send`, server, target, outcome including a user denial; never the text).
- **Agent-tool confirmations are never answerable from chat, via one shared marker, a fixed title prefix and a server-side backstop.** C owns the marker `AGENT_TOOL_CONFIRM_META` = `pluginMeta {pluginId:"chat-gateway", kind:"agent-tool-confirm"}`, defined once in the shared entry and named generically so D's moderation confirm reuses it. `discord_send`'s confirm carries it, and the gateway does not render a prompt with that marker in Discord. Because the bridge can drop the metadata, the gateway also skips any prompt titled with the fixed prefix `Discord send:` (stateless, so it holds after a restart and after any timer), and the server also tracks one pending confirmation per server-issued preview id (so parallel sends are covered) and the gateway renders no prompt of that session meanwhile, and remembers every prompt it skipped so a replayed prompt never renders. It is answered on the dashboard or the terminal only. This is a MODIFIED "Interactive prompts rendered natively via PromptBus" and composes with `add-supervised-tool-approval`'s exclusion.
- **L3: gateway-spawned sessions cannot send.** (1) Server: the `discord/send` lanes refuse a session that the gateway spawned (spawn `pluginRef` or a `source:"spawn"` binding) with `spawned_session_denied`. This also covers spawns that have no guard configured. (2) Guard: the chat-gateway guard wrapper hard-denies `discord_send` before the policy decision, whatever `toolPolicy` says (MODIFIED "Hard in-session tool policy for spawned sessions"). `decideToolCall` and the guard core are unchanged, so `add-supervised-tool-approval`'s extraction is unaffected.
- **Read audit is opt-in.** `agentTools.auditReads` (default `false`): when on, each read or listing request writes one id-and-outcome `agent_read` entry to a separate read-audit ring (so reads cannot evict send evidence), never content or search terms.
- **Non-blocking registration.** The bridge refreshes the server's tool status without awaiting it, caches it, and hides the tools when the server says off or the session is remote.
- **Limits as settings** (A's convention, `0` = unlimited): gateway-wide and per-session read/send rates (documented code defaults, never written into the stored config by a save; `limits.agentToolReadsPerMinute` 60, `agentToolSendsPerMinute` 5, `agentToolReadsPerSessionPerMinute` 30, `agentToolSendsPerSessionPerMinute` 3), `agentToolReadMessages` (50), `agentToolSearchScan` (500), `agentToolResults` (25), `agentToolRequestDeadlineMs` (12000), `agentToolConfirmPendingS` (600), `agentToolLogSuppressS` (5) and `agentToolReadLogEntries` (10000). Two touched shipped constants become settings: the guard readiness timeout (`GUARD_READY_TIMEOUT_MS`, 30 s) becomes `limits.guardReadyS` (default 30, `0` = unlimited) and `teamControls.auditRetention` accepts `0` = unlimited (default 10 000 kept, the 1 000 000 ceiling dropped). Probes and previews count toward the rates. The id lists are bounded by A's `limits.maxMappings`.
- **Live settings.** A new write lane `chat_gateway_agent_tools_config` and an "Agent tools" group in `ChatGatewaySettings`, with no restart. The write is all-or-nothing and patches only the agent-tool `limits` keys, through A's `patchLimits` (the host merge is shallow). The surface projection shows problems and counters per tool and reason.
- **Tool annotations** (`readOnlyHint` for reads, accurate hints for send) so generic approval hooks classify them correctly.
- **Manifest.** `pi-dashboard-plugin.bridge` → `./src/bridge/index.ts` and an `exports["./bridge"]` entry. `priority` stays `100` (it must be `<= 100`).

## Capabilities

### New Capabilities
- `chat-gateway-agent-tools`: the tool set and its exposure, the operator switch, the server-held token, read and send scoping, the read source (index or live), untrusted results, confirmed sends without mentions, the spawned-session send denial on the server side, audit, limits, and the live settings lane.

### Modified Capabilities
- `chat-gateway`: "Hard in-session tool policy for spawned sessions" (`discord_send` is hard-denied no matter what the policy says), "Interactive prompts rendered natively via PromptBus" (prompts carrying the agent-tool-confirm marker or a confirm title prefix, or of a session with a pending agent-tool confirmation, are not rendered in chat), "Configuration surface" (agent-tool settings, on top of B's text), and the spawned-session readiness timeout inside "Hard in-session tool policy for spawned sessions" (now `limits.guardReadyS`).
- `chat-gateway-audit`: "Log entries identify by stable identifier" (agent entries use `session:<id>` and list the session's bound channels) and "Append-only command log" (agent principals `session:<id>`, verbs `agent_send`/`agent_read`, empty channel id, `discord_error:<code>` reasons, `user_denied` logged), and "Log survives restarts and does not grow without bound" (`0` = unlimited retention).

## Impact

- **Code** (`packages/chat-gateway` only): a new `src/bridge/{index,tools,lane-client}.ts`, a new `src/server/agent-tools.ts`, plus `src/server/index.ts`, `src/server/gateway.ts` (prompt skip), `src/server/config.ts`, `src/guard/index.ts` (hard-deny wrapper), `src/server/seam.ts` (expose `pluginRefs`), `src/server/team/audit.ts` consumers (agent principals), `src/adapters/{base,discord,fake}.ts` (history fetch, guarded send with no mentions, DM open), `src/shared/types.ts`, `src/configSchema.json`, `src/client/ChatGatewaySettings.tsx`, `package.json` (bridge entry and export). There is no core, protocol or `dashboard-plugin-runtime` change.
- **Dependencies:** none new (`discord.js` and `dashboard-plugin-runtime` are already dependencies).
- **Docs:** `docs/chat-gateway.md` (via DocScribe), and the `packages/chat-gateway/**/AGENTS.md` rows, including a new `src/bridge/AGENTS.md`.
- **Compatibility:** off by default. Existing installs see no change until an operator enables agent tools. Sessions pick up the bridge entry on their next start or reload.
- **Rollback:** an older plugin version has no bridge entry and no handlers. Tools that were already registered fail with `no_handler`, and the `agentTools` and `limits.agentTool*` keys are ignored, the same posture as A's `limits`. Nothing persisted needs migration.
- **Cross-change:** blocked by A (servers, `limits`, disarm latches, `sendableChannel` gate) and by B (message index; C task 3.2a needs a page read with a `before` cursor and a per-channel coverage start from B's index store, requested from B and implemented by C if B lands without it). D reuses this bridge entry, the lane client and the hard-deny list. `add-supervised-tool-approval` also MODIFIES "Interactive prompts rendered natively via PromptBus". The two paragraphs compose, and whichever change archives second re-copies the block with both. `add-plugin-connector-kit` (`registerConnectorTools`) is an optional later adoption, not a dependency. `add-web-chat-plugin` has no overlap.
