/apps/wall — join & access states

What a participant sees when opening /apps/wall/#/s/<token>. The page is served by the dashboard; data comes from /api/plugins/voice-wall/* admitted by the share-token guard seam.

← All screens

1 · Connecting

Joining the live wall…

Checking the link with the meeting host.

The token sits in the URL fragment, which browsers never send to servers or put in Referer headers. The app sends it as a header on its own requests (same idea as the shell's hash-routing contract).

2 · Link expired

This link has expired

It was valid until the meeting ended at 15:42. Ask the host for a new link if the meeting is still running.

Each dead-end says why and who can help, never a generic 403 (Nielsen #9). No dashboard chrome or login page is shown to anonymous viewers.

3 · Revoked (mid-meeting)

The host stopped sharing this wall

You were disconnected. If you still need access, ask the host for a new link.

An open viewer is pushed out instantly on revoke: the SSE stream closes with a revoked reason and the app swaps to this state. No polling until the next refresh.

4 · Meeting ended

The meeting has ended

Thanks for joining. The wall is no longer live and its content is not kept here.

The ended state does not leave the last board on screen. A shared room screen shouldn't keep showing content after the meeting.

5 · Invalid link

This link doesn't work

It may be incomplete. Copy it again from the message you received, or scan the QR code on the room screen.

Invalid, expired and revoked tokens get the same generic server response (no oracle). The wording differs only where the app already knows the reason, from its own stored state or the stream's close reason.

6 · Connection lost (transient)

Reconnecting… the board below may be out of date.

(last known board)

Stale content stays visible but is visibly dimmed, and a banner says it may be outdated (Nielsen #1). It recovers automatically and resyncs from the event log.
