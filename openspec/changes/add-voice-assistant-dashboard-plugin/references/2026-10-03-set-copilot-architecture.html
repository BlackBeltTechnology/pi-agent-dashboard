Architecture · set-copilot · October 2026

set-copilot signal path

How a spoken sentence becomes a chat alert, a line of commentary, or a diagram on a wall in front of an audience. Every stage below is a real process boundary or a real file. There is no server in the middle and no second AI: the intelligence is a Claude Code session running a skill.

microphone (you)system audio (the other party) Claude Code sessionfast lane wallfile in the runtime dir

The idea in six points

The session is the copilot

There is no backend and no second AI. A Claude Code session runs a skill, reads the transcript in batches, and decides what to say. Everything else is plumbing that feeds it and carries its output.

Files are the boundaries

Capture, session and wall are separate processes that share only append-only files in one runtime directory. Any stage can be stopped, inspected, restarted or replayed without the others noticing.

Two channels, never mixed

Your microphone and the other party's system audio stay separate from the first byte to the last line. "Who said it" is the one fact every later feature relies on.

Instructions skip the queue

Reacting to conversation needs judgement, so it waits for a pause or a few complete sentences, then a model turn: many seconds. An instruction needs none, so spoken commands and wall input reach the session at the next 250 ms tick.

Mechanics in code, judgement in config

How to poll, flush and emit is engine code. What is worth saying, which categories exist, how much to talk and what to draw is project configuration, rendered into the session's policy.

The direction of harm decides

The public wall fails closed: when in doubt, withhold. A dictation fails open: when in doubt, print the raw text. A mistake on the wall publishes something; a mistake in dictation would swallow what you said.

The whole path

Three processes talk only through append-only files in one per-session runtime directory, .set/copilot/<session-id>/. The capture writes the transcript, the session reads it, and anything that should appear on the wall is appended to a second log that the wall server tails. Because the boundary is a file, every stage can be restarted, inspected or replayed on its own.

Talking to it: the built-in commands

Most of the time the copilot listens and decides for itself. When you want something specific, there are four routes, and three of them skip the waiting that ordinary reactions go through.

Figure 2. The command routes. Spoken and typed instructions arrive as events; the session acts on the event, not on the transcript line that also records the words.

1 · Capture

set-copilot capture --detach starts a background process in its own session, so it outlives the tool call that started it (the harness kills background commands at its time limit; a real two-hour meeting lost its capture that way). It writes capture.pid and refuses to start a second capture in the same directory, because overwriting the PID file would orphan a process that is still recording.

Two channels

The microphone and the system monitor are recorded as two independent 16 kHz mono streams. The mic / system tag is the primitive every later feature builds on. Dictation uses --mic-only.

Platform binaries

Linux uses /usr/bin/parec (a PATH-shadowing build hangs silently against PipeWire). macOS uses sox over CoreAudio, with BlackHole for system audio; without it the capture degrades to mic-only with one hint.

It diagnoses itself

Zero bytes after 5 s, a deaf signal after 30 s, a level line every minute, and at stop an EMPTY TRANSCRIPT explanation that says which of three failures it was. On macOS the Microphone permission belongs to the enclosing app, which doctor names.

2 · Speech to text

Each channel opens its own WebSocket to Soniox stt-rt-v5 and streams raw PCM. Final tokens come back with their own leading space, which is the only evidence of a word boundary, so tokens are concatenated, never joined with spaces. A dropped socket reconnects with backoff from 0.5 s up to 8 s, replays the last ~15 s of audio buffered during the gap, and writes a {"type":"reconnect"} line so a reader can see that words may be missing there. A ping every 20 s, with 15 s to answer, catches half-open sockets. A 10-second chunked Soniox mode and an offline whisper.cpp backend emit the same events.

Figure 3. Each channel's client recovers on its own. Up to about 15 s of audio from the gap is replayed; the reconnect line says how much.

3 · Building sentences

The transcript-writer keeps one token buffer per speaker and writes a JSONL line when that speaker's utterance ends. That happens on a sentence boundary (. ? ! …), after 3 seconds of that speaker's own silence or past 80 tokens (both marked partial:true), or when the capture closes. One silence event is written per pause, once both channels are quiet.

Figure 4. The decision each final token goes through. The other channel's buffer is never touched.

Why per speaker? Speech overlaps. If one shared buffer were cut whenever the speaker changed, the other side's constant "mhm" would chop your sentences wherever the token stream happened to stand, often in the middle of a word.

Figure 5. Each channel flushes on its own rules; a backchannel "mhm" on one channel never cuts the other channel's sentence.

FieldMeaning
startTs / tsStart and end of the utterance. With two channels, completion order is not speaking order, so readers sort on startTs.
partialCut without a sentence boundary; the thought continues in that speaker's next line.
cont / midWordThe resuming line continues the previous one; midWord means the two adjoining words are halves of one word and must be joined without a space.
topicsKeywords matched against the knowledge digest (page titles, headings, tags, decision ids such as dec 3 → DEC-003). Word boundaries are Unicode letters and digits, never \b, which breaks accented words.
urgency / questionFlags from configurable patterns (detect.urgency, detect.question); defaults cover English and Hungarian.

The fast lane

Everything else the copilot does is inference, and inference is deliberately gated. A spoken instruction needs no judgement, so it skips that cost. The fast lane reads the raw token stream, not the written lines, through its own rolling buffer per speaker that no flush touches; a marker split across a flush ("CSI" | "NÁLD") is still seen. A span opened by copilot or start and closed by csináld, stop or vége becomes a {"type":"command"} event. The closing word matters: speech has no reliable end of thought, and acting on half an instruction is the failure it prevents. A span that never closes dies out loud as command-abandoned (over 600 characters, or older than 45 s when that speaker next speaks or the capture closes), so a lost command is never mistaken for a dead microphone.

Figure 6. The fast lane per speaker. The words also stay in the ordinary transcript line, because the transcript is a record; the policy tells the copilot to act on the event only.

What the copilot knows

Before the capture starts, set-copilot digest turns the project's own documents into three files in the runtime directory. The keyword index is what lets a transcript line arrive already tagged with the topics it touches, so the session can route a sentence without reading it twice.

The runtime directory

Everything a session produces lives in .set/copilot/<session-id>/, scoped to one Claude Code session so parallel sessions never overwrite each other. Every command in a session uses the same path, byte for byte; that is how stop finds the capture it has to stop.

4 · Poll and the session

set-copilot poll is a long-poll that the skill wraps in a Monitor loop. It keeps a line offset in the runtime directory, drops mic/system echo duplicates and empty lines, and returns early on anything worth an immediate reaction: an urgent line, a question, a line that addresses the copilot by name, a spoken command, a silence after speech, or two waiting speech lines during continuous talk. Otherwise it returns within 60 seconds. When the capture process is gone it emits capture-dead and the loop ends. Each returned batch becomes one notification, which wakes one model turn.

Figure 8. The poll decision, run every 250 ms. During continuous speech the two-line bound keeps a sentence from waiting half a minute for a pause.

At session start the skill loads the project's policy with set-copilot prompt: the alert taxonomy (⚠ contradiction, 📋 context, ✏ new decision, ❓ question), the engagement level (silent, reactive, participant), the line limit, and the drawing contract. The policy is config, not prompt text in the skill, so a project changes what the copilot says without forking the skill. The turn order is fixed: the reaction goes out first, everything else is composed after it.

Figure 9. What the session does with one batch, in order.

Chat alerts

Short (at most 3 lines) and chat-only. No filler: a batch with nothing to add ends the turn with no visible text.

Direct wall lines

One narration line per batch and the pinned box (agenda, open questions, decisions) go out with wall-emit directly, in about a second.

Drawings

Anything that has to be composed, such as a graph or a chart, goes to a fork, so the main session never stops listening while it draws.

5 · Forking

A producer is a fork of the main session (subagent_type: "fork"), not a second model with its own briefing. It inherits the whole conversation, which is its grounding, so its prompt is a single-line mandate: draw this category for what we just discussed, emit, stop. The fork also inherits the "Drawing the wall" block that set-copilot prompt put into the session at start (the categories, the payload shapes, when a graph or a chart is warranted), which is why nothing about drawing has to be repeated in the mandate. Immediately before spawning, the session marks the target box pending, because a silent "working" box looks exactly like a dead wall.

Figure 10. A fork-based drawing. The main session keeps handling batches while the fork works.

Predicting the next visual

A fork draw is slow, so during a silence window the copilot may pre-draw the likely next visual. The guess is staged to the private zone only. It reaches the public wall only through an explicit promote when the conversation actually arrives there, which is a cheap server-side zone lift of the already drawn visual, run through redaction again. An unpromoted prediction expires after 120 seconds, decided by the clock at the moment of the promote, with a sweep every 5 s that tells private views it expired. There is no confidence threshold: a guess never publishes itself.

With the default single public wall, a staged visual is shown nowhere until it is promoted. The producer asks what it has prepared with set-copilot wall-staged, and lifts one with a promote line:

{"kind": "promote", "category": "előrejelzés", "visual": "export-flow", "zone": "public"}

6 · The wall

wall-emit validates each event and appends it to wall-events.jsonl, stamping emittedAt. The wall server tails that log and runs every line through one ingest funnel, so a producer that bypasses the CLI still meets the same checks. On restart the server rebuilds its whole state by replaying the log, which is why the log is rotated aside and never truncated.

Figure 11. The ingest funnel. Redaction runs once, before anything is broadcast or stored.

Window → layout → box

A layout is geometry only (named positions in a CSS grid). A box is content only: its categories, pacing and policy. The renderer follows the event's payload, so one presentation box can show a graph, then a chart, then an image.

Audience is declared

Each window is public or operator; an undeclared one is treated as public. A public surface never receives a private event, whatever its zone filter admits. The shipped default has only the public wall; the operator's private view is the Claude Code terminal.

Delivery

Server-sent events with resumable ids and a 1-second heartbeat, so a reloading or reconnecting viewer gets the accumulated state back without duplicates.

The default wall at /wall uses three regions. A category reaches a region only if that region's box subscribes to it:

The chat mirror

set-copilot mirror-follow watches the Claude Code session's own transcript and emits every new assistant text block as it is written, mid-turn included. A policy filters filler and lines under 40 characters, a long message is split on block boundaries into chunks of up to 600 characters rather than cut, and aligned tables are fenced so they keep their columns. Offsets advance only after the wall confirms delivery, and every decision is logged to wall-mirror.log. It replaced a turn-end hook that was measured to be permanently one message behind.

Figure 12. The mirror: a loss is the bug, a repeat is cosmetic, so delivery is confirmed before it is forgotten.

Dictation uses the same capture

Figure 13. /ds and /dd. The printed text becomes the user's message in the chat.

Unlike a meeting transcript, a dictation is an instruction. It is stitched before printing, because a separator guessed wrong corrupts the instruction before the model reads it, and the file is renamed on hand-over so a second /dd cannot replay it.

After the meeting

/meeting-copilot stop writes the closing summary first (anything written after the wall is down has nowhere to go), drains the mirror, stops the capture and the wall, and renames the transcript to an archive name. The archived file is then stitched into a readable Markdown transcript and a sentence-level JSONL (the stitch figure below). transcript-recover later reads each archived meeting once to find what was said but never reached the notes; a ledger keyed by the content's SHA-256 makes sure that model pass runs once per transcript: a run claims a transcript, delivers its findings with recovery mark --findings-file (there is no way to produce findings without writing the record), and a Stop hook refuses to end the turn while a claim is open. A new stitch version is reported, never forced to redo the work. set-repair is the cheap mechanical check for orphaned PIDs and transcripts nobody handed over.

Figure 15. The stitch. Each channel is complete on its own; only the interleaving destroyed readability, so the channels are rebuilt first and merged last.

Everything project-specific lives behind these seams. The engine is language- and domain-neutral.
