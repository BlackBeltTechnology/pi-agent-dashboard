## Why

Issue: https://github.com/BlackBeltTechnology/pi-agent-dashboard/issues/840

The "A device wants to connect" dialog cannot approve in most setups. `POST /api/pair/approve-pending` is guarded by `createApprovalGuard` (`packages/server/src/routes/pairing-routes.ts:142`), which — by design (`harden-trust-and-credential-boundaries` D6) — admits only a login session, the `pi_dash_local` proof cookie, or a verified local credential. The proof cookie is minted only by `pi-dashboard open` (`cmdOpen`, `packages/server/src/cli.ts:935`) or Electron `loadWithLocalProof` (`packages/electron/src/lib/local-proof-bootstrap.ts:97`).

Two things make this a dead end rather than a speed bump:

1. **The pending feed is NOT guarded the same way.** `GET /api/pair/pending` and `POST /api/pair/deny` run under `operatorGuard` (`pairing-routes.ts:100`, bare-loopback branch at `:116-123`), which *does* have a bare-loopback branch. So a plain `localhost:8000` tab is shown the dialog, can deny — and only Approve fails with 401. Every setup in the issue's audit table that reports "can't approve" still gets the dialog.
2. **The dialog's only answer is prose.** `nextFromOutcome` (`PairingApprovalDialog.tsx:93`) prints "Approval needs an operator credential…" and stops. The 401 body is `{success,error}` with nothing the client can act on, and the client cannot start the proof flow itself.

Electron loses the proof it already minted: `createMainWindow` calls `loadWithLocalProof` (`packages/electron/src/main.ts:569`), but every handoff out of the loading page navigates to the plain URL — `location.href = serverUrl` (`packages/electron/resources/loading.html:154`) and the known-servers click at `:97`. So server-not-yet-up, restart, startup-failure and known-server paths all land proofless.

## What Changes

- **New CLI approval path usable from any shell on the host that runs the server** — headless/SSH, Docker (`docker exec`), and WSL *when the CLI runs on the same OS as the server*. `pi-dashboard pair list | approve | deny`. The CLI reads (never creates) the host-only local token and mints `X-Pi-Local-Proof` per request (`localCredentialHeaders`, `cli.ts:895`); the approval guard already admits a verified local credential (`hasLocalProof` → `hasLocalCredential`). When no credential header can be built (e.g. a host-name `host` bind, `cli.ts:895-909`) the CLI refuses upfront and sends nothing. **No guard change, no new route, no new trust.** The operator still TYPES the 8-digit code shown on the device (D12 invariant), read from a prompt rather than argv by default.
- **The 401 refusal becomes actionable.** The approval guard's body gains `reason` and an ordered `remedies` list (`authorize-browser`, `approve-on-host`, `sign-in`), mirroring the vocabulary of `operate-required-remedy` and its disclosure rule (nothing beyond the caller's own network position and whether a login method exists). The new keys are attached only when the request's `Host` passes the guard's own `isHostAdmitted` check; a non-admitted Host (reachable when the host gate is opted into `report` mode) gets today's two-key body.
- **Deny moves to the approval guard.** The main `qr-device-pairing` requirement "Operator can deny a pending device" already says denial SHALL require *the same operator authentication as approval*, but `POST /api/pair/deny` runs under `operatorGuard` (`pairing-routes.ts:435`), whose bare-loopback branch (`:116-121`) lets any local process — or a rebinding page on an admitted Host — burn a pairing code. The route moves to `approvalGuard`, restoring the existing contract; its 401 carries the same `reason`/`remedies` body. `GET /api/pair/pending` stays on `operatorGuard` (out of scope). The CLI `pair deny` already sends `X-Pi-Local-Proof`, so it is unaffected.
- **The dialog renders the remedies** — a copyable `pi-dashboard open --url <this tab's origin>` (the proof cookie is host-only, so the command must target the origin the dialog is on; `--url` is accepted only for a loopback host on the **configured server port**, refused before any code is minted otherwise), a copyable `pi-dashboard pair approve <pendingId>`, and a sign-in link when a login method is configured — while keeping the typed code, the countdown and the Approve action live, so approval can be retried in place once the credential is obtained. The `authorize-browser` remedy is offered only when the request's `Host` header itself passes the launcher's origin rule (loopback host + configured port), so an SSH `-L` forward or other non-configured local origin is never shown a command the launcher would refuse. A Deny refused for want of a credential renders the same rows.
- **`GET /auth/local-proof` accepts a same-origin `next=` path** so the proofed tab returns to where the operator was instead of `/`, validated by the **existing** `sanitizeReturnUrl` (`packages/server/src/auth/auth-plugin.ts:99-110`) — the same predicate the Login OAuth `returnUrl` uses, no second copy. The Login OAuth requirement is modified to state that full predicate (incl. control characters and origin re-parse), so both requirements describe one rule.
- **Electron re-establishes the proof on every handoff to a local dashboard URL** (loading page → server, launch-outcome redirect, restart/startup-failure recovery, known-server pick). The new IPC channel is sender-gated (`trustedHandler` + `isTrustedSender`, like every privileged `dashboard:*` channel), because the main-window preload is attached to remote content in remote mode. The **main process performs the navigation itself** and returns only an acknowledgement: the renderer never receives the bootstrap URL or the single-use code. Targets are restricted to an allowlist — the configured local server origin, the server URL the window was created for (the remote URL in remote mode), or a configured known-servers entry — and anything else is refused with no navigation, so the channel cannot be used to replace the dashboard with an external page (`loadURL` from main bypasses `will-navigate`). A credential is minted only for the configured server host *and* port.
- **FAQ gains a per-setup "approve a pairing" section** (Docker `docker exec`, WSL, headless Linux, `localhost` vs `127.0.0.1`, tunnel origin, `--dev` Vite port).

## Non-goals

- **No in-dialog "Authorize this browser" (issue option A).** Letting a bare-loopback request mint its own proof code reintroduces exactly the path D6 removed: the dialog runs inside the untrusted browser, and a DNS-rebinding page or any local process that cannot read the 0600 token would gain approval power. The approval guard keeps its shape; see design D1.
- **No `pi-dashboard://approve?id=` deep link (issue option B).** A custom scheme is OS-registered and invocable by any local app and by web content; it would be a second, weaker approval entry point. The CLI covers the same desktop case with no new attack surface.
- **No change to who is admitted — except deny.** `createApprovalGuard` and `createOperatorGuard` keep their current predicates; the approval guard's refusal *body* changes. The one admission change is `POST /api/pair/deny` moving from `operatorGuard` to `approvalGuard`, which restores the existing main-spec rule that denial needs the same authentication as approval (a bare-loopback tab loses Deny until it obtains a credential). `GET /api/pair/pending` and its bare-loopback admission are unchanged.
- **Windows token-file ACL verification** (issue checklist item) stays out: it belongs to `local-ipc-allowlist-token`, affects every local-token consumer and not just pairing, and does not block this fix. Tracked separately.
- **Cross-platform VM/E2E approval scenario** (issue checklist item): named here as follow-up QA work, not implemented by this change.

## Impact

- **Server:** `packages/server/src/routes/pairing-routes.ts` (refusal body; `POST /api/pair/deny` preHandler `operatorGuard` → `approvalGuard`), `packages/server/src/routes/local-proof-routes.ts` (`next=`, via the existing `sanitizeReturnUrl`), `packages/server/src/auth/local-token.ts` (new read-only `readLocalTokenIfPresent`), `packages/shared/src/` (refusal body type + remedy vocabulary + the shared invisible-character class), `packages/server/src/cli.ts` (`pair` subcommand dispatch alongside the existing pre-switch `token` / `service` / `login` dispatch, and `open --url`).
- **Refusal-path coupling:** the `sign-in` remedy reads the `loginAvailable` thunk composed at `packages/server/src/server.ts:2069`. That accessor is best-effort: if it is absent or throws, the remedy is omitted and the 401 is still returned — never a 500. The guard checks the credential BEFORE Host admission (`pairing-routes.ts:155-164`) and the global host gate can be switched to report-only (`server.ts:1903`; `host-admission` spec), so the remedy builder itself re-checks `isHostAdmitted`; a non-admitted Host gets the legacy two-key 401 and learns nothing about whether a login method exists. Guard order is not changed.
- **Client:** `packages/client/src/components/pairing-approval/PairingApprovalDialog.tsx`, `packages/client/src/lib/pairing/pairing-approval-api.ts` (surface `remedies` from the 401 of both `approvePending` and `denyPending`), `packages/client/src/components/pairing-approval/PairingApprovalHost.tsx` (deny refusal path, `:165`).
- **Electron:** `packages/electron/src/main.ts` (new `dashboard:navigate-to-server` IPC handler that calls `loadURL` itself), `packages/electron/src/lib/local-proof-bootstrap.ts`, `packages/electron/src/preload-main.ts` (main-window preload — NOT the wizard `preload.ts`), `packages/electron/resources/loading.html` (three navigations: `:97`, `:154`, `:174`).
- **Docs:** `docs/faq.md`, `README.md` pairing section.
- **Migration:** none. No config, no persisted state, no new route. One guard change: a bare-loopback client without a credential now gets 401 (with remedies) on Deny instead of 200 — intended, per the existing deny requirement. Rollback of that line alone is a one-word preHandler revert. Older clients ignore the new `reason`/`remedies` keys; the `error` string stays `operator credential required` so existing client branches keep matching.
- **Compatibility:** an older Electron build keeps working (it just keeps losing the proof); an older server answers a `pair approve` call normally — the CLI only uses routes that already exist, so it works against any server that has `/api/pair/approve-pending`.
- **Rollback:** revert the client remedy block and the CLI subcommand independently; the server change is additive keys on a 401 body and a validated optional query param, both safe to revert alone.
- **Sequencing:** gated on `retire-trusted-networks-bypass` (task 0.1 — re-check and re-base its trust delta before merge) and on `close-loopback-legacy-window`, which MODIFIES the same two requirements (`Compare-code approval…`, `Opt-in local proof for loopback trust`) — whichever archives second rebases (task 0.2); must not conflict with it (same trust surface, different requirements) and `add-request-access-remedy` (extends `operate-required-remedy`, which this change deliberately does not touch). See design "Ordering".
