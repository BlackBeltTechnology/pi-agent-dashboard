## Purpose

Dashboard-managed, project-local OpenSpec workflow schema `pi-spec-driven`. It is generated from the OpenSpec package `spec-driven` schema of the CLI the dashboard resolves, plus versioned patches. It is enabled per project without changing the workflow of any existing change, kept current across teammates without downgrades, and reported as a non-blocking status separate from OpenSpec readiness.

## ADDED Requirements

### Requirement: Workflow schema is generated from the package base, stamped and validated

The server SHALL generate the schema in a fresh scratch directory, never inside the repository. Every CLI call of generation (`--version`, `schema which`, `schema fork`, `schema validate`) SHALL run with the scratch root as cwd and `XDG_DATA_HOME` set to an empty scratch directory, so no project or user schema can shadow the package base:

1. Run `openspec schema which spec-driven --json`. Abort unless it reports `source: "package"` and an empty `shadows` list.
2. Run `openspec schema fork spec-driven pi-spec-driven --force` there.
3. Apply the current patch set to the scratch `schema.yaml` with a comment-preserving YAML edit. If a patch's anchor text is not found, generation SHALL abort (a stamp never claims a patch that was not applied).
4. Write the stamp `x-pi-dashboard: { derivedFrom: "spec-driven@<version>", patch: <CURRENT_PATCH>, previousDefault: <name> }`:
   - `<version>` is the `openspec --version` of the CLI that ran;
   - `<name>` is the value supplied by the calling action (see "Schema names are validated before use"): enable passes the default it recorded; Update passes the request's `previousDefault` when given, else the existing stamp's; Adopt and an Update without a stamp (`generated: none`) require the request's `previousDefault` (the UI preselects `spec-driven`).
5. Run `openspec schema validate pi-spec-driven` there.

Only after validation SHALL the result be copied to the sibling `<root>/openspec/schemas/.fork-staging-<rand>/` (a failed copy removes the staging directory and aborts) and swapped in:

1. If `pi-spec-driven/` exists, re-check that its whole-directory fingerprint (every file's relative path and content hash, as OpenSpec's own fork does) is unchanged since its status was read; otherwise abort.
2. If it exists, rename it to `pi-spec-driven.fork-backup-<pid>-<ts>`.
3. Rename the staging directory to `pi-spec-driven/`.
4. Delete the backup, if one was made.

On Windows, every rename (including a restore) failing with `EPERM` / `EBUSY` / `EACCES` SHALL be retried up to 5 times within 2 s. A failure in step 1 or 2 SHALL remove the staging directory and leave the previous schema untouched. A failure in step 3 SHALL rename the backup back (when one exists) and remove the staging directory, leaving the previous schema byte-identical; if that restore itself fails after retries, the backup directory SHALL be left in place (OpenSpec discovery ignores it) and named in the error. A failure in step 4 SHALL NOT roll back: the backup is left and a warning returned. The scratch directory SHALL be removed in every case.

Patch v1 SHALL replace, in the `design` artifact instruction, the line `When to include design.md (create only if any apply):` with `When a full design.md is warranted (otherwise still create design.md containing one line "Not needed: <reason>"):`. This is author guidance only; the CLI only checks that the file exists.

#### Scenario: Fresh generation

- **GIVEN** a project without `openspec/schemas/pi-spec-driven/`
- **WHEN** generation runs
- **THEN** the directory SHALL contain `schema.yaml` (with the `x-pi-dashboard` stamp) and the forked templates
- **AND** `openspec schema validate pi-spec-driven` SHALL report valid in that project

#### Scenario: User-level shadow is ignored

- **GIVEN** a user-level schema named `spec-driven` exists in the real `XDG_DATA_HOME`
- **WHEN** generation runs
- **THEN** the package `spec-driven` SHALL be forked, because the scratch `XDG_DATA_HOME` is empty

#### Scenario: Non-package base aborts

- **WHEN** `schema which spec-driven --json` in the scratch root reports a `source` other than `package`, or non-empty `shadows`
- **THEN** generation SHALL abort and the repository SHALL be untouched

#### Scenario: Validation or swap failure keeps the previous schema

- **GIVEN** an existing generated schema
- **WHEN** validation fails, or the final rename fails after retries and the restore succeeds
- **THEN** `openspec/schemas/pi-spec-driven/` SHALL be byte-identical to before
- **AND** no `.fork-staging-*` or `*.fork-backup-*` directory SHALL remain

#### Scenario: Update preserves the previous default

- **GIVEN** a stamp with `previousDefault: team-flow` and `config.yaml` naming `pi-spec-driven`
- **WHEN** the schema is regenerated by Update
- **THEN** the new stamp SHALL keep `previousDefault: team-flow`

#### Scenario: Design skip declaration counts as done

- **GIVEN** a change on `pi-spec-driven` whose `design.md` contains only `Not needed: single-file fix`
- **WHEN** `openspec status --all` runs
- **THEN** the `design` artifact SHALL be `done` from the CLI verdict alone

### Requirement: Stamp comparison never downgrades

The server SHALL compare a generated schema's stamp `(base, patch)` with `(version of the resolved OpenSpec CLI, CURRENT_PATCH)` component-wise: base by semver, patch numerically.

| Comparison | Status | Meaning |
|---|---|---|
| Both components equal | `current` | — |
| Neither component newer, at least one older | `outdated` | eligible for Update |
| Either component newer, neither older | `newer` | never regenerated |
| One component newer, the other older | `conflict` | never regenerated (no action may regenerate it; resolve by aligning dashboard/CLI versions) |

Further statuses:
- `none`: no `pi-spec-driven/` directory exists.
- A `pi-spec-driven/` that is a symlink, or that has no parseable stamp, SHALL be `unmanaged`. It is never overwritten, except through an explicit Adopt action the user confirms (Adopt is refused for a symlink).
- For `newer` and `conflict`, the server SHALL run `openspec schema validate pi-spec-driven` with the local CLI and cwd = the repository root, on the main thread through the spawn semaphore, memoized by (cwd, whole-directory fingerprint, resolved CLI version) so it runs at most once per combination. If that fails, the status SHALL be `incompatible` and a notice SHALL tell the user to update their OpenSpec CLI.

#### Scenario: Teammate on a newer dashboard

- **GIVEN** a stamp `spec-driven@1.12.0`, patch 2, and a local CLI 1.11.0 with CURRENT_PATCH 1
- **WHEN** the status is evaluated, or Update or Enable is requested
- **THEN** the status SHALL be `newer` (or `incompatible` if local validation fails)
- **AND** the schema SHALL NOT be regenerated

#### Scenario: Mixed versions are a conflict, not a downgrade

- **GIVEN** a stamp `spec-driven@1.11.0`, patch 2, and a local CLI 1.12.0 with CURRENT_PATCH 1
- **WHEN** the status is evaluated
- **THEN** the status SHALL be `conflict`
- **AND** no regeneration SHALL drop patch 2

#### Scenario: Outdated stamp

- **GIVEN** a stamp `spec-driven@1.11.0`, patch 1, and CURRENT_PATCH 2 on the same base
- **WHEN** the status is evaluated
- **THEN** the status SHALL be `outdated` and Update SHALL be offered

### Requirement: Enable pins file-less changes to the previous default before switching

Enable is never required to regenerate an existing schema, and it only changes changes that exist in the checkout at enable time. A change that has no `.openspec.yaml` and arrives later through a merge follows the new default; it is reported in `unpinnedChanges` (a known limitation of file-less changes).

Enable SHALL run under the per-cwd lock and the write guard ("Every writing action verifies the root first"), then:

1. (part of the write guard)
2. Additionally refuse unless all of the following hold:
   - `openspec/config.yaml` or `openspec/config.yml` exists (when both exist, `config.yaml` is read and edited, as the CLI does).
3. If the configured schema is already `pi-spec-driven`, return the current status and write nothing (unpinned changes are handled by the Pin action).
4. Otherwise:
   1. Record the configured default as `previousDefault`: the config's `schema:` value, or `spec-driven` when the key is absent (the CLI's implicit default). It SHALL pass "Schema names are validated before use", else refuse.
   2. If the status is `none`, generate the schema with that `previousDefault`. If it is `current`, `outdated`, `newer` or `conflict` (the latter two only when the local `schema validate` passes), keep the existing schema without regenerating (an outdated schema is reported, and changed only by an explicit Update). If the kept stamp's `previousDefault` differs from the recorded one, refuse and tell the user to run Update with `previousDefault: <recorded>`, which rewrites the stamp. Refuse when `unmanaged` or `incompatible`.
   3. For every active change directory under `<root>/openspec/changes/` that has NO `.openspec.yaml`, create `.openspec.yaml` with no-clobber semantics (exclusive create; an existing file is never replaced), serialized by the YAML library as `{ schema: <previousDefault> }`. Active means excluding `archive/`, dot-directories and symlinks, matching OpenSpec's change enumeration. Existing `.openspec.yaml` files SHALL never be modified.
   4. Set the config file's `schema:` to `pi-spec-driven` with a comment-preserving edit.

Every write SHALL be atomic (temporary file + rename, or exclusive create for pins) and contained by `realpath(<root>)/openspec/`. The response SHALL list every written path and carry `worktree: { isWorktree: boolean, branch: string | null }`; the UI SHALL show the branch the files land on when `isWorktree` is true. The server SHALL NOT create git commits. A forced OpenSpec refresh SHALL follow every action.

If a step fails after generation, the already-written schema and pins SHALL remain. They are harmless, because the default has not switched. The response SHALL report the partial state, and re-running enable SHALL complete it.

#### Scenario: Existing changes keep their workflow

- **GIVEN** 104 active changes on default `spec-driven`, 33 of them without `.openspec.yaml`
- **WHEN** the project is enabled
- **THEN** exactly 33 `.openspec.yaml` files SHALL be created, each containing `schema: spec-driven`
- **AND** a subsequent `openspec status --all` SHALL report every pre-existing change with its previous `schemaName`
- **AND** `config.yaml` SHALL name `pi-spec-driven`

#### Scenario: Custom previous default is preserved

- **GIVEN** `config.yaml` names `team-flow` and change `x` has no `.openspec.yaml`
- **WHEN** the project is enabled
- **THEN** `x/.openspec.yaml` SHALL contain `schema: team-flow`
- **AND** the stamp's `previousDefault` SHALL be `team-flow`

#### Scenario: Enabling an enabled project changes nothing

- **GIVEN** `config.yaml` already names `pi-spec-driven` and the schema is `current`
- **WHEN** enable runs
- **THEN** no file SHALL be created or modified

#### Scenario: Enable never regenerates an outdated schema

- **GIVEN** a disabled project whose `pi-spec-driven/` is `outdated` and change `foo` pinned to `pi-spec-driven`
- **WHEN** enable runs
- **THEN** `pi-spec-driven/` SHALL be byte-identical afterwards
- **AND** the response SHALL report the schema as `outdated`

#### Scenario: New changes use the new schema

- **GIVEN** an enabled project
- **WHEN** `openspec new change foo` runs
- **THEN** `foo/.openspec.yaml` SHALL contain `schema: pi-spec-driven`

#### Scenario: Foreign or symlinked root is refused

- **GIVEN** a cwd whose status-call `root.source` is `"store"` or `"declared"`, or whose `openspec/changes/` is a symlink
- **WHEN** enable is requested
- **THEN** the server SHALL refuse and write nothing

### Requirement: Disable restores the previous default without breaking pinned changes

Disable SHALL require the configured schema to be `pi-spec-driven`; otherwise it SHALL write nothing and report the current default. It SHALL set the config file's `schema:` to the stamp's `previousDefault` and SHALL keep `openspec/schemas/pi-spec-driven/`. When the stamp is absent or unparseable (`none` / `unmanaged`), Disable SHALL require a request `previousDefault` plus `confirm: true` instead of assuming `spec-driven`. The value written SHALL pass "Schema names are validated before use", else Disable refuses.

The `remove` action SHALL rename `pi-spec-driven/` to a `pi-spec-driven.fork-backup-<pid>-<ts>` name (ignored by OpenSpec discovery) and then delete it recursively, so an interrupted delete never leaves a partial schema. It SHALL be refused when:
- the schema is `unmanaged` or `none`;
- the config names `pi-spec-driven`;
- any active change's `.openspec.yaml` names it.

When only archived changes reference it, the response SHALL warn and require explicit confirmation. The response SHALL always warn that unmerged branches may still pin the schema.

#### Scenario: Pinned changes survive disable

- **GIVEN** an enabled project with change `foo` pinned to `pi-spec-driven`
- **WHEN** the project is disabled
- **THEN** `config.yaml` SHALL name the previous default
- **AND** the schema directory SHALL still exist and `foo` SHALL report status without error

#### Scenario: Disable after the user switched the default is a no-op

- **GIVEN** `config.yaml` names `team-flow` although the stamp exists
- **WHEN** disable is requested
- **THEN** nothing SHALL be written

#### Scenario: Remove refused while referenced

- **WHEN** `remove` is requested while `foo` still pins `pi-spec-driven`
- **THEN** the server SHALL refuse and name `foo`

### Requirement: Every writing action verifies the root first

Every action that writes (`enable`, `disable`, `update`, `adopt`, `pin`, `remove`) SHALL, under the per-cwd lock, run a fresh `openspec status --all --json` and refuse unless:
- the call returned a `root`, so a CLI without `status --all` cannot write;
- `root.source` is `"nearest"`;
- `realpathSync.native(root.path)` equals `realpathSync.native(cwd)`;
- `openspec/`, `openspec/changes/`, `openspec/schemas/` (when present) and the config file are not symlinks.

#### Scenario: Foreign root refused for every action

- **GIVEN** a cwd whose status-call `root.source` is `"declared"`
- **WHEN** any of `pin`, `update` or `disable` is requested
- **THEN** the server SHALL refuse and write nothing

### Requirement: Schema names are validated before use

Every schema name the server writes or records (`previousDefault` in a stamp or a request, `pinTo`, a value written to the config) SHALL be a kebab-case id, SHALL NOT be `pi-spec-driven` where it denotes a previous default, and SHALL resolve from the project schema directory or the package built-ins with the local CLI. A name that resolves only from the user schema directory (`XDG_DATA_HOME`) SHALL be refused, because teammates cannot resolve it. A stamp `previousDefault` that fails these rules SHALL be treated as absent.

#### Scenario: User-level schema cannot become a committed default

- **GIVEN** `team-flow` exists only in the operator's `XDG_DATA_HOME`
- **WHEN** enable records `team-flow` as `previousDefault`, or a pin requests `pinTo: team-flow`
- **THEN** the server SHALL refuse and write nothing

### Requirement: Actions are allowed only in defined states

The REST endpoint SHALL enforce, before any write:

| Action | Allowed when |
|---|---|
| `enable` | configured ≠ `pi-spec-driven`; generated ∈ {`none`, `current`, `outdated`, `newer`*, `conflict`*} (* local validate passes) |
| `disable` | configured = `pi-spec-driven` |
| `update` | generated ∈ {`outdated`, `current`} (re-stamping `previousDefault`), or `none` while configured = `pi-spec-driven` |
| `adopt` | generated = `unmanaged`, not a symlink, `confirm: true`, request `previousDefault` given |
| `pin` | configured = `pi-spec-driven` |
| `remove` | generated ∈ {`current`, `outdated`, `newer`, `conflict`, `incompatible`}, plus the reference rules of Disable/remove |

Any other combination SHALL be refused with the current status in the response.

Adopt SHALL regenerate `pi-spec-driven` from the package base through the full generation and swap procedure, replacing the unmanaged content (any hand customizations are discarded; the confirmation names this), and stamp it with the request's `previousDefault`.

#### Scenario: Update refused on a conflict

- **GIVEN** the schema status is `conflict`
- **WHEN** `update` is requested
- **THEN** the server SHALL refuse and the schema SHALL be unchanged

#### Scenario: Update re-stamps the previous default

- **GIVEN** a `current` schema whose stamp has `previousDefault: spec-driven`, after the repository default was changed to `team-flow` and the project disabled
- **WHEN** `update` is requested with `previousDefault: team-flow`
- **THEN** the stamp SHALL record `team-flow` and a following `enable` SHALL succeed

### Requirement: Pin only creates missing metadata

The `pin` action SHALL be allowed only while the configured schema is `pi-spec-driven`. It SHALL create `.openspec.yaml` (exclusive create, YAML-serialized `{ schema: <pinTo> }`) only for the requested changes that have none. Change names SHALL come from the filesystem enumeration used by enable, not from cached poll data. `pinTo` SHALL be `pi-spec-driven` or the stamp's `previousDefault`, and SHALL resolve with the CLI. An existing `.openspec.yaml` SHALL never be modified.

#### Scenario: Already-pinned change is left alone

- **GIVEN** `foo` has `.openspec.yaml` naming `spec-driven`
- **WHEN** `pin` names `foo` with `pinTo: pi-spec-driven`
- **THEN** `foo/.openspec.yaml` SHALL be unchanged and the response SHALL report it as skipped

#### Scenario: Unresolvable target refused

- **GIVEN** the stamp's `previousDefault` names a project schema that was since deleted
- **WHEN** `pin` uses it as `pinTo`
- **THEN** the server SHALL refuse and write nothing

### Requirement: Workflow schema status is reported separately from readiness

Every successful-poll payload, and the cached state served on demand, SHALL carry `OpenSpecData.workflowSchema` with the fields:
- `configured: string | null`;
- `generated: "none" | "current" | "outdated" | "newer" | "incompatible" | "conflict" | "unmanaged"`;
- `missing: boolean` — the config file the CLI reads (`config.yaml`, else `config.yml`) names a schema that resolves in none of the project, user or package schema directories;
- `unpinnedChanges: string[]` — the active changes (as enumerated by enable) without `.openspec.yaml`, detected by `stat` only, and computed only when `configured === "pi-spec-driven"`.

Failure, disabled, opted-out and global-off payloads SHALL omit it. It SHALL be recomputed whenever the poll rebuilds data, and whenever the resolved CLI version changes. The filesystem part is computed in the poll worker; any CLI call it needs (`schema validate` for `newer`) runs on the main thread through the spawn semaphore, memoized.

This status SHALL NOT alter `OpenSpecData.readiness` or any readiness-gated control. In particular, per-change errors caused by a missing schema ("Unknown schema …") SHALL NOT turn a successful status call into a readiness failure.

The actions are offered in Settings (see `settings-panel` "OpenSpec Workflow Schema section"). The OpenSpec folder section SHALL show a non-blocking notice chip whenever any of these holds: `missing`, `outdated`, `newer`, `incompatible`, `conflict`, `unmanaged`, or a non-empty `unpinnedChanges`. The chip is a navigation link that opens that Settings section for the cwd; it performs no action itself.

#### Scenario: Outdated schema does not disable session controls

- **GIVEN** a READY project whose generated schema is `outdated`
- **WHEN** the session card renders
- **THEN** readiness SHALL remain `READY` and every OpenSpec control SHALL behave as before
- **AND** the folder section SHALL show the notice chip linking to the Settings section

#### Scenario: Unpinned change arrives by merge

- **GIVEN** an enabled project and a merged change `bar` without `.openspec.yaml`
- **WHEN** the poll completes
- **THEN** `workflowSchema.unpinnedChanges` SHALL be `["bar"]`
- **AND** a `pin` with `pinTo: spec-driven` (the stamp's `previousDefault`) SHALL create `bar/.openspec.yaml` with `schema: spec-driven`

#### Scenario: Missing schema keeps readiness READY

- **GIVEN** a READY project whose `config.yaml` names `pi-spec-driven`, the schema directory absent, and two changes pinned to it
- **WHEN** a poll's status call succeeds with per-change "Unknown schema" errors for those two
- **THEN** readiness SHALL remain `READY`, `workflowSchema.missing` SHALL be `true`, and the other changes SHALL render normally

#### Scenario: Failure payload carries no schema status

- **WHEN** a poll ends in a whole-call failure
- **THEN** the payload SHALL NOT contain `workflowSchema` and SHALL otherwise equal the failure shape defined by `server-openspec-polling`

### Requirement: Workflow schema REST endpoint is gated, contained and serialized

The endpoint is `POST /api/openspec/workflow-schema`, with body `{ cwd, action, confirm?, pinTo?, changes?, previousDefault? }` and `action` one of `enable`, `disable`, `update`, `adopt`, `pin`, `remove`. Registration:
- `preHandler: networkGuard`, like the other `/api/openspec/*` routes;
- a `control`-tier entry in `packages/shared/src/route-tiers.ts`;
- the MCP manifest completeness rules.

It SHALL check, in order: the cwd is tracked or pinned (the init endpoint's known-target set, a membership check with no filesystem access); OpenSpec is enabled; the cwd is not opted out. Only then SHALL it touch the filesystem, starting with `realpathSync.native(cwd)` and the `<cwd>/openspec/` existence check.

Request validation:
- `pinTo` SHALL be `pi-spec-driven` or the stamp's `previousDefault`.
- `changes` SHALL be a subset of the active change names from the filesystem enumeration.
- `previousDefault` (Update / Adopt without a stamp) SHALL be a kebab-case id that resolves with the CLI.
- Every schema name written SHALL be a kebab-case id.

Execution rules:
- Every target path SHALL be contained by `realpath(<root>)/openspec/`.
- No shell interpolation SHALL be used.
- A per-cwd lock, keyed by `realpathSync.native(cwd)` and shared with the init endpoint (whose lock key becomes the same canonical path once its own tracked check has passed), SHALL reject a concurrent call with `409`. When REST init chains into enable, enable SHALL run inside init's held lock; init's admission gates count for it, and the write guard still applies.
- Each call SHALL log the cwd, action, written paths, and stamp before and after.

#### Scenario: Untracked cwd is rejected without filesystem access

- **WHEN** a request names a cwd that is neither tracked nor pinned
- **THEN** the server SHALL respond with an error and SHALL NOT stat or write anything below that cwd

#### Scenario: Concurrent calls are serialized

- **WHEN** two `enable` calls for the same cwd arrive at once
- **THEN** exactly one SHALL proceed and the other SHALL receive `409`

#### Scenario: Injected schema name is rejected

- **WHEN** a `pin` request carries `pinTo: "spec-driven\nretire_capabilities: true"`
- **THEN** the server SHALL reject it and write nothing

#### Scenario: Symlinked change directory is skipped

- **GIVEN** `changes/evil` is a symlink to a directory outside the repository
- **WHEN** enable or pin runs
- **THEN** nothing SHALL be written through `changes/evil`

### Requirement: Global default applies only to newly initialized projects

`DashboardConfig.openspec.workflowSchema.defaultForNewProjects` (boolean, default `false`) SHALL make `POST /api/openspec/init` run the enable flow after a successful initialization, inside the init's held lock, but only when `<cwd>/openspec/` did not exist before that initialization. A failure of the enable flow SHALL NOT fail the init and SHALL be reported in the init response. (project-init runs `openspec init` itself and requests enable separately; see `project-init-skill`.)

#### Scenario: New directory with the default on

- **GIVEN** `defaultForNewProjects` is `true` and `/repo/new` has no `openspec/`
- **WHEN** the dashboard initializes OpenSpec there
- **THEN** the enable flow SHALL run and `config.yaml` SHALL name `pi-spec-driven`

#### Scenario: Existing project repaired with the default on

- **GIVEN** `defaultForNewProjects` is `true` and `/repo/old/openspec/` already exists
- **WHEN** the dashboard re-runs OpenSpec init (repair or overwrite)
- **THEN** the enable flow SHALL NOT run
