## Accepted decisions (owner)

- **A1.** Tests whose pass or fail depends on a wall-clock duration or a process-memory measurement leave the blocking lanes for a nightly-only lane. Classification goes by assertion type, not filename. Deterministic budgets (byte and bundle size, counts, the skill-frontmatter size budget) stay. PR `ci.yml`, `npm test` as ship-it uses it, and the publish tag gate do not run the lane. Mixed files are split, for example blender `real-binary.test.ts`. A mechanical guard is required. `blender-real` and `ci-scenarios` stay in `ci-result`. No `continue-on-error`. No trend store.
- **A2.** A local CodeQL model-pack timeout stays an ERROR (exit 2). The default is raised and made configurable by env, with the same trust model as the existing overrides. A task measures and records the root cause. No cross-worktree lock. The pack-download timeout → SKIPPED rule is unchanged.
- **A3.** `nightly-tests.yml` reruns a failed job once. It opens an issue only when a job fails twice, and it lists "passed on rerun" tests separately without raising an issue for them. The retry policy and the report requirements are amended by explicit MODIFIED deltas. A regression that fails twice still blocks. The rerun's `actions: write` is granted with least privilege where the rerun is triggered; a separate small workflow is acceptable and preferred, and the report job's permissions need not change. The mechanism is fail-closed: if the rerun cannot be triggered or its result cannot be read, the night is reported red and the issue opened. Nightly only, so PR `ci.yml` gets no retry.
- **A4.** Folded into A1: knip-scan #P1 and blender P1–P3 are budget tests.
- **A5.** A budget assertion is an UPPER bound only. A lower-bound wait (`elapsed >= delay`) is not a budget assertion and stays blocking.
- **A6.** Real-process liveness deadlines stay blocking (e.g. `cli-stop-real`, `cli-foreground-real`, `shutdown-terminates-any-strategy`, `rpc-keeper/keeper`). Each is on the guard's allow-list with a written reason. The allow-list is for liveness deadlines only, with a stated admission rule.
- **A7.** The nightly budget lane runs on `ubuntu-latest` only. Blender P1–P3 are no longer measured on macOS or Windows: an accepted loss.
- **A8 (split).** The full migration of every existing upper-bound time or memory assertion (MOVE / REWRITE / ALLOW-LIST, no baseline at the end) is the goal of `migrate-budget-assertions`, which depends on this change. This change contains only the lane mechanism (A1), the move of the budget cases already observed failing (A9), the guard in warn-only mode (A10), the nightly rerun (A3) and the CodeQL timeout (A2).
- **A9.** This change moves only the budget cases observed failing, each verified by reading its assertion: `kb-search-perf` (S61 timing bound and P1), `browser-gateway-broadcast-serialize-once` P2, `ladder-perf` #P4, `graph-layout` #P1, `knip-scan` #P1, blender `real-binary` P1–P3 (E-cases stay), `provisioning` #P1, `dependency-declarations` P1/P2. A listed case that is not a wall-clock or process-memory upper bound stays and is named as a separate flake. Mixed files are split so functional cases stay blocking.
- **A10.** The guard ships warn-only. It lists upper-bound time and memory assertions in blocking lanes (its `--list` output is the future inventory source) and reports them without failing any job or ship gate. It becomes blocking in `migrate-budget-assertions`. Until then a NEW budget assertion can still land in a blocking lane. The allow-list (A6) and its admission rule are designed now and enforced only when the guard is blocking.
- Observed-failing names are leads, not classifications. A test that asserts a count or runs under fake timers stays blocking and is a separate flake outside this change.

## Goals / Non-Goals

**Goals:** no `*.budget.test.*` file runs under `npm test`, PR CI or the tag gate: the vitest configs that collect one exclude it unless `RUN_BUDGET_TESTS=1`, and a blocking check refuses a budget file that a blocking run would collect (D1). So none of the eight observed-failing budget files can turn those runs red on host speed. A budget regression in them stays visible the next morning. A guard that fails nothing lists, in every `ci.yml` run, the budget assertions it can see in blocking lanes; D5 lists the forms it cannot see, two of which exist in the tree today (`proximity-perf.test.ts:37-58`, the `withinBudget` predicate form). A slow but healthy `codeql resolve extensions` no longer stops a headless ship.

**Non-Goals (design level):** no migration of the other budget assertions (`migrate-budget-assertions`). No blocking guard, no baseline, no `// budget-exempt:` marker and no opt-in-variable exception (they existed only to let a blocking guard pass; the follow-up decides them). No new vitest project or config. No change to `ci-result`, `check-result.mjs` or the select job outputs. No change to thresholds inside moved tests. No dataflow analysis across modules in the guard.

## Budget lane contract (consumed by schedule-release-rehearsal)

- **Lane name:** `budget`. It is the nightly job id in `.github/workflows/nightly-tests.yml`, the job key for `assigned.mjs` and `verify-executed.mjs`, and the artifact `vitest-report-budget`. The selection field is `budgetFiles` in `selection.json`.
- **Placement:** a test is in the lane when its file is named `<name>.budget.test.<ts|tsx|mts|mjs|js>` (the D2 regex `isBudgetFile`; a non-code name such as the vitest snapshot `<name>.budget.test.ts.snap` is not a budget file, and neither the lane check nor the selector considers it: owner decision C3) and sits where an existing vitest project collects it. Membership in CI selection is by filename alone (D2). The file carries no env gate of its own; a runtime gate such as blender `describeReal` is allowed (D3).
- **Exclusion (the lane switch):** `vitest.workers.ts` exports `BUDGET_TEST_EXCLUDE`, which is `["**/*.budget.test.*"]` unless `process.env.RUN_BUDGET_TESTS === "1"`, and `[]` then. Every vitest config whose project collects a budget file spreads it into `test.exclude` (with `configDefaults.exclude`). In this change those are `packages/kb-plugin/vitest.config.ts`, `packages/server/vitest.config.ts`, `packages/server/vitest.real-process.config.ts`, `packages/skill-atlas-plugin/vitest.config.ts`, `packages/blender/vitest.config.ts` and `scripts/vitest.config.ts` (D1).
- **Structural check (blocking):** `scripts/check-budget-lane.mjs` exits 1 when (1) `vitest list --filesOnly` for the root config or for `packages/server/vitest.real-process.config.ts`, run with `RUN_BUDGET_TESTS` removed from the environment, lists any budget file, or (2) a git-tracked budget file (a path `isBudgetFile` matches, D2) is in no root-config project that excludes it with the budget entry, judged statically from the resolved project configs (D1 "Blocking check"; it would run nowhere, since `test:budget` runs the root config only), or (3) that static test disagrees with vitest's own collection on the other tracked test files. The check never sets `RUN_BUDGET_TESTS`. It runs as a step of the `ci.yml` `ci` job, which `ci-result` needs, and through the vitest wrapper `scripts/__tests__/budget-lane.test.mjs` inside `npm test`. It is separate from the warn-only assertion guard (D5) and is not warn-only.
- **Run the suite WITHOUT the lane:** any vitest run with `RUN_BUDGET_TESTS` unset or not exactly `1`. Concretely: `pnpm test` / `npm test`, `pnpm run test:parallel`, `pnpm run test:real-process` and `pnpm run test:ci-scenarios`. Budget files are not collected there, so none of their code runs. `publish.yml:120` `pnpm test` therefore excludes the lane with no edit. **Where `RUN_BUDGET_TESTS` is set:** of the repo's scripts, configs and workflows, only the `test:budget` script in `package.json` sets it; the nightly `budget` job runs that script, and a developer may also set the variable by hand to run one budget file. No vitest config, test, script, selector step or workflow step that `npm test`, PR `ci.yml` or `publish.yml` runs sets it; the selector lists budget files by `git ls-files` (D2) and the blocking lane check judges lane membership statically (D1). `schedule-release-rehearsal` must only ensure `RUN_BUDGET_TESTS` is never set in `publish.yml`, and may pin that in a contract test. In CI selection, budget files are in no shard, real-process or ci-scenarios list.
- **Run ONLY the lane:** `pnpm run test:budget`, defined as `RUN_BUDGET_TESTS=1 HOME=$(mktemp -d -t pi-test-XXXXXX) NODE_OPTIONS="--no-experimental-webstorage --localstorage-file=$(mktemp -t pi-test-ls-XXXXXX)" vitest run --no-file-parallelism --passWithNoTests .budget.test.` The nightly job appends the explicit assigned files: `pnpm run test:budget "${FILES[@]}"`. Only budget files execute, one file at a time (D3 "Seriality"). A case that also sits behind a runtime gate (blender `describeReal`, which needs `BLENDER_WASM_E2E=1` and JSPI) skips on a machine without that runtime; the nightly job provides the runtime and fails on any skip (D3).
- **Platform:** the nightly `budget` job runs on `ubuntu-latest` only (A7).
- **Outside the lane:** `KB_MEASURE`-gated measurement harnesses (Context) stay opt-in and run in no CI lane.
- **Stability promise:** the names `budget`, `RUN_BUDGET_TESTS`, `test:budget`, `*.budget.test.*` and `BUDGET_TEST_EXCLUDE` are the interface. Renaming any of them is a breaking change for `schedule-release-rehearsal`.

## Reporter interface (consumed by schedule-release-rehearsal)

This section is the single description of the command-line interface of `scripts/test-selection/nightly-report.mjs` as this change leaves it. Today `main` reads flags with `argv[argv.indexOf(k) + 1]` (`nightly-report.mjs:157`), so an absent flag returns `argv[0]`, not `undefined`: `--expected` absent but another flag present does not throw. Task 5.3 fixes the reader: an absent flag is `undefined`, and a boolean flag is true when present.

| Flag | Task | Mode | Value | Default when absent |
|---|---|---|---|---|
| `--reports <dir>` | today | report | directory of `vitest-report-*` artifacts; `timings.json` is written there | none: required in report mode |
| `--expected <k1,k2,…>` | today | report | comma-separated job keys expected to upload a report | none: required in report mode |
| `--defer-first-attempt` | 6.1 | report | boolean | off: attempt 1 never defers and writes no record; today's behaviour |
| `--previous <dir>` | 6.1 | report | directory holding `attempt-1.json` | absent: on attempt >= 2 treated as "record missing" (D7) when `--defer-first-attempt` is given; ignored otherwise |
| `--watchdog` | 6.1 | watchdog | boolean | off |
| `--dry-run` | 6.1 | watchdog | boolean: print the decision, write no issue | off; ignored outside watchdog mode |

- **Modes.** `--watchdog` selects watchdog mode; otherwise the script is in report mode. A mode flag added by a later change is checked before both: when it is present, that mode runs and `--watchdog` has no effect (`schedule-release-rehearsal`'s `--jobs-only` works this way, its design.md D2).
- **Required together.** In report mode `--reports` and `--expected` are both required. A missing one prints a `usage:` line and exits 1, without reading reports, writing `timings.json` or calling the API. Watchdog mode needs neither and ignores both, and ignores `--defer-first-attempt` and `--previous`. `--previous` has an effect only together with `--defer-first-attempt`; `--dry-run` only together with `--watchdog`.
- **Exit codes.** Report mode: 0 when the summary is green; 1 when it is red, when attempt 1 deferred (D7), or on a usage error. Watchdog mode: 0 when there is nothing to report (D7 "`--watchdog`"); 1 when it created or updated the issue. `--dry-run` returns the exit code the same decision would return without it, and writes nothing. Any uncaught error, an API error included, exits 1 in both modes (`nightly-report.mjs:191-193`).
- **Absent and unknown flags.** A call that passes none of the flags added by task 6.1 behaves as today, except for the usage error above. An unknown flag is ignored and changes no output, file, API call or exit code. Attempt logic (`GITHUB_RUN_ATTEMPT`, record, deferral, passed-on-rerun lists) runs only with `--defer-first-attempt`; without it every attempt is judged on its own verdict, as today.
- **Constants this change keeps:** workflow file `nightly-tests.yml` for the bisect-anchor query and the watchdog (`nightly-report.mjs:26`), issue label `nightly-tests` (`:25`), today's issue title, close comment and step-summary heading (`:105`, `:108`, `:181`).
- **If the spike fails** (D7 "If the spike fails"), task 6.1 is not carried out and the interface is the two `today` rows plus the reader fix and exit codes above.
- **Later changes.** `schedule-release-rehearsal` adds its own flags on top of this version. It may add a mode, selected only by its own flag and checked before `--watchdog`, in which `--reports` and `--expected` are not required. It must not change the meaning, default or exit code of any flag in the table, the behaviour of a call that passes none of its flags, or the watchdog's binding to `nightly-tests.yml`.

## Decisions

### D1. Placement = filename suffix + per-config exclusion (default off) + blocking structural check

The filename makes the lane discoverable without vitest, which the fallback needs (as `scanGatedFiles` does), and gives `test:budget` a one-token filter. Budget files keep their package's environment (jsdom, setup files) because they stay in their own project.

B3 needs `pnpm test` never to run a budget case, so exclusion is structural, not an in-file gate that a file can forget:
- **Exclusion.** `vitest.workers.ts` exports `BUDGET_TEST_EXCLUDE` (Budget lane contract). Each config whose project collects a budget file spreads it into `exclude`: the six configs the contract names. With `RUN_BUDGET_TESTS` unset, vitest does not collect a budget file at all, so neither its cases nor its module top level run. A run given only excluded paths exits 1 with "No test files found", so a budget file wrongly assigned to a blocking job fails loudly. Checked on vitest 4.1.11 with a two-project scratch config: an env-driven `exclude` hides the file from `vitest list --filesOnly`, `vitest run` and `createVitest(…).globTestSpecifications()`, and `RUN_BUDGET_TESTS=1` brings it back.
- **Blocking check.** A config that forgets the spread is the remaining hole, for example a future budget file in a package not listed above. `scripts/check-budget-lane.mjs` closes it from vitest's own collection and resolved configs, not from config text, and never sets `RUN_BUDGET_TESTS`: (1) it fails when either command `npm test` runs collects a budget file (`vitest list --filesOnly`, variable unset). (2) It fails when a tracked budget file would run nowhere: it loads the root config in-process with `createVitest` as `buildTestIndex` does (`scripts/test-selection/graph.mjs:141,153`), and a file is in the lane when some project's resolved `exclude` holds `**/*.budget.test.*` and the file, relative to `config.dir || config.root`, matches an `include` glob and no other `exclude` glob under Node's `path.matchesGlob`. That is the include/exclude test vitest's `TestProject.matchesTestGlob` applies with picomatch (`node_modules/vitest/dist/chunks/cli-api.CnMVyzaz.js:10907-10914`, vitest 4.1.11). Only root-config projects count, because `test:budget` runs the root config; a budget file listed in `REAL_PROCESS_TESTS` therefore fails. (3) It fails closed when the static test drifts from vitest: applied without the budget condition to every other tracked `*.test.*`/`*.spec.*` file, it must select exactly the tracked files that command (1) listed for the root config. Checked during planning on Node v24.15.0 and vitest 4.1.11 (CI uses Node 26, `unverified` there): over 66 projects and 3,616 tracked test files, the static test and `globTestSpecifications()` selected identical sets, in 1.4 s. If the CI run of task 2.7 shows a drift that cannot be fixed, (2) and (3) are dropped rather than set the variable for a listing; an orphan budget file is then caught only by the nightly `budget` job, which assigns it by filename and fails in `verify-executed` when it does not run, and the scenario "A budget file no project collects fails the check" is withdrawn first (trade-off T-A18). It runs as the step "Budget lane check" of the `ci.yml` `ci` job, right after "Fixed-tick wait guard" (`ci.yml:132-133`); the `ci` job installs dependencies first (`ci.yml` "Install dependencies") and is a `ci-result` need, so a PR that adds an unexcluded budget file cannot merge. The PR step does not depend on affected selection. Ship-it and the tag gate reach it through `scripts/__tests__/budget-lane.test.mjs`, which spawns the script and asserts exit 0; that file is collected by `npm test`. The wrapper spawns `node scripts/check-budget-lane.mjs` with `RUN_BUDGET_TESTS` and every `VITEST*` variable removed from the child's environment; that a nested `vitest list` behaves the same under a vitest worker is `unverified` and checked by task 2.7. Test seams: the script exports the comparator of part (3) (static set and listed set in, findings out) and accepts `--root <dir>` (default: the repo root), so tests run it against a fixture mini-workspace, a temp git repository with a root vitest config and two project configs (test-plan E6–E10, E13b, X4).
- **No in-file gate.** With the exclusion, an in-file `describe.skipIf(RUN_BUDGET_TESTS !== "1")` could never be true where the file is collected. It is dropped. A developer runs one budget file with `RUN_BUDGET_TESTS=1 npx vitest run <path>`; `npm run test:budget <path>` runs every budget file, because vitest ORs its filename filters and `test:budget` already passes `.budget.test.` (checked: `vitest list --filesOnly kb-search-perf ladder-perf` lists both files).

Alternatives rejected:
- *A dedicated vitest project or config* (like real-process). Budget tests live in client (jsdom), plugin, kb, scripts and blender packages, each with its own environment and setup. One config cannot host them without copying every package's settings.
- *An in-file `describe.skipIf` gate as the only switch* (the earlier design). A file that forgets the gate runs in every blocking lane and in the tag gate; a check on the gate was warn-only under A10, so B3 could not rely on it. The file would also still be collected, so its module top level would run in blocking lanes.
- *The exclusion in every project config (66 root entries).* Only six configs collect a budget file today; the blocking check names the config to edit when another is needed. Editing the other configs that collect none adds churn and no protection.
- *Set `RUN_BUDGET_TESTS=1` for listing only* (the previous design, in the lane check and in `buildTestIndex`). It ran no budget case, but the variable then appeared inside `npm test`, the PR `select` job and the tag gate, which made the sibling's pin "the release path never sets `RUN_BUDGET_TESTS`" false. The static test (part 2) and the filename scan (D2) give the same answers without it.
- *Root `test.exclude`.* Projects given as config paths do not inherit it (Context).
- *Vitest CLI `--exclude` on every blocking command.* It is not passed to projects (Context), and every caller (ci.yml, publish.yml, ship-it, developers) would have to remember it.
- *Env gate without a filename marker.* Running "only the lane" would need a source scan, and mixed files could not be told apart from budget files.
- *Tag or name filter (`-t "#P"`).* Names are not a contract, and A1 rules out filename or name classification as the membership rule.

### D2. Selector: budget files are routed like gated files, but to no PR job

`decide()` adds `isBudgetFile(path)` = `/\.budget\.test\.[cm]?[jt]sx?$/` (filename only). It removes those files from the gated set, `realProcess` and `parallel` (`decide.mjs:244-247`), so they reach no unit shard, real-process list or `ciScenariosFiles`, and returns `budgetFiles` = every git-tracked budget file, sorted, in every mode. The list comes from a filename scan (`scanBudgetFiles`, `git ls-files`), not from the vitest index: the configs exclude budget files (D1), the selector does not set `RUN_BUDGET_TESTS`, and `buildTestIndex` (`scripts/test-selection/graph.mjs:139-155`) is unchanged, so the index never holds a budget file. The filter in `decide()` is defensive: a config that forgot the exclusion would put a budget file in the index, and the blocking lane check (D1) fails that PR anyway. Membership is by filename alone, so the nightly runs every budget file whatever the diff; the selector never needs a budget file's import graph. PR `ci.yml` never reads `budgetFiles`, so no PR job, `ci-result` need, select output or `check-result` entry is added. Keeping them out of PR shards saves runtime. A PR that edits a budget file runs none of its cases; the nightly does (A1 accepts this). The file is still type-checked and linted by the `ci` job (`unverified` which typecheck covers test files; recorded, not relied on).

### D4. Classification rule (checkable)

A **budget assertion** is an assertion whose failure means "too slow" or "too much memory". It bounds from above a value M (or a ratio or difference of such values), or bounds M by another measurement (a relative bound such as `statusMs * 1.25` at `browser-gateway-broadcast-serialize-once.test.ts:373`, or `4 * p95Of(r.idleSearchTimes)` at `kb-search-perf.test.ts:153`), where M is derived from:

- (a) a real-clock reading: `performance.now()`, `Date.now()`, `new Date()` used in arithmetic or through `.getTime()`/`.valueOf()`, `process.hrtime()`, `process.hrtime.bigint()`, `process.uptime()`. A reading does not count in a case where its clock is faked. A clock is faked for a case when the case itself, a `beforeEach` of any enclosing `describe`, or a module-level `beforeEach`/top-level statement of the file calls `vi.useFakeTimers()` with no argument, `vi.useFakeTimers({toFake: [...]})` naming that clock, or `vi.setSystemTime(` (`Date` only). A no-argument `vi.useFakeTimers()` fakes `Date`, `performance` and `hrtime` in vitest 4.1.11: it installs every timer key of its bundled `@sinonjs/fake-timers` except `nextTick` and `queueMicrotask` (`node_modules/vitest/dist/chunks/test.DNmyFkvJ.js:3299-3304`; `timers.hrtime` `:2053`, `timers.performance` `:2061`), unless the project's vitest config sets `fakeTimers.toFake` (none checked; `unverified` for all ~60 configs). A file-level fake applies to every case of the file (`packages/client/src/lib/chat/__tests__/follow-glide.test.ts:47`, module-level `beforeEach(() => vi.useFakeTimers())`). A fake installed only in one case, or one that names only `setTimeout`/`setInterval`, leaves the other readings real: `packages/extension/src/__tests__/sudo-askpass-install.test.ts` fakes `Date` at `:102` but `:281` runs on the real clock; `packages/server/src/__tests__/sudo-credential-wiring.test.ts:122` fakes only `setTimeout`/`clearTimeout`, so `:41` is a real-clock bound. A fake installed by a setup file or a helper is not seen (D5 limits);
- (b) a process-memory reading: `process.memoryUsage()` (any field), `process.memoryUsage.rss()`, `v8.getHeapStatistics()`/`getHeapStatistics()`, `process.resourceUsage()`, or a child-process RSS read through a named helper on the guard's helper list;
- (c) a call of a named measurement helper on the guard's helper list: `rssBytes` (blender `real-binary.test.ts:123`, moved by task 3.6 into `helpers/real-binary-session.ts`) and `startLagMonitor` (`packages/server/src/test-support/event-loop-lag.ts`, used at `packages/server/src/attachments/__tests__/display-fit-perf.test.ts:73,116`).

"Bounds from above" means `expect(M…).toBeLessThan|toBeLessThanOrEqual(X)`, `expect(X).toBeGreaterThan|toBeGreaterThanOrEqual(M…)`, or `assert`/`expect(…).toBe(true)` over `M < X` / `M <= X`. A **budget test** is a test case with at least one budget assertion.

Not budget tests: byte sizes of files, bundles or serialized values (`mdi-chunk-size`; `JSON.stringify(stored).length` at `packages/server/src/__tests__/memory-event-store.test.ts:609,642`), counts (calls, renders, rows, dialogs, entries), lower bounds (`elapsed >= delayMs`, A5), ordering checks whose bound side is a bare reading with no arithmetic (`expect(x.createdAt).toBeLessThanOrEqual(Date.now())`), values not derived from a reading (store-internal byte counters such as `getBufferBytes` in `packages/server/src/__tests__/memory-event-store.test.ts:2161`, or the injected cost clock at `packages/kb/src/__tests__/index-batch-budget.test.ts:143-150`), polls and deadlines (`waitFor`, `expect.poll`, deadline loops) that fail through the runner timeout, vitest `testTimeout`/`hookTimeout`, arithmetic on a faked clock (above), and `process.cpuUsage()`. CPU time is not wall-clock, and its one use (`packages/server/src/__tests__/git-operations.test.ts:638`) is not an assertion bound.

Upper-bound-only is owner-confirmed (A5). A lower-bound check fails only when code fires early, not when the host is slow.

Example of a lead that is not a budget test: `SessionList.actions-menu.test.tsx` P1 (`:169-196`) runs under `vi.useFakeTimers()` (`:170`) and asserts a commit count, `expect(commits - before).toBe(0)` (`:195`). It stays blocking. Its observed CI failure is a separate flake outside this change (proposal.md Non-Goals). A liveness deadline is still a budget assertion by this definition; A6 keeps the real-process ones blocking through the allow-list (D5), and the rest are dispositions of `migrate-budget-assertions`.

### D5. Guard: `scripts/check-budget-assertions.mjs`, warn-only (A10)

Shape copies `check-fixed-tick-waits.mjs`: an exported per-file analyzer and a CLI. The analyzer takes a path and that file's text and reads no file system, so tests drive it with fixture strings; the CLI accepts `--root <dir>` (default: the repo root) for a fixture tree, and its exported runner takes the analyzer as a parameter, so a test can inject one that throws (test-plan E35–E57, X3). Scope: `git ls-files` test files (`*.test.{ts,tsx,mts,mjs,js}`), minus `tests/e2e/`, `qa/` and `**/fixtures/**`; optional path-prefix arguments narrow it.

**Modes and exit codes.**
- `--warn` (the only mode this change wires): prints one `::warning file=<path>,line=<n>::budget assertion in a blocking lane: <form>` line per finding. When `GITHUB_STEP_SUMMARY` is set, it appends `### Budget assertions in blocking lanes: <count>` and a table of every finding (`file:line`, form, case title). It exits 0 whatever it finds. An internal error (an unreadable file, a crash in the analyzer) is printed as `::warning::budget guard error: <message>` and also exits 0, so the guard cannot fail a job.
- `--list`: prints every hit, including allow-listed ones with the entry that matched. This is the starting input for `migrate-budget-assertions`' inventory, not a complete one: it misses every form in "What the guard cannot detect" below, among them the predicate form of `dependency-declarations` P1/P2 (`expect(withinBudget(elapsed, n), …).toBe(true)`, `dependency-declarations.test.mjs:434`), which this change moves although the guard never saw it. The follow-up's hand pass covers those forms. Exits 0.
- No flag: exits 1 when it finds anything. This change wires it nowhere; `migrate-budget-assertions` switches the `ci.yml` step to it and adds it to ship-it.

**Where the output appears.** One step in the `ci.yml` `ci` job, "Budget assertion guard (warn-only)", right after "Budget lane check" (D1), which follows "Fixed-tick wait guard" (`ci.yml:132-133`): `node scripts/check-budget-assertions.mjs --warn`. Findings show as warning annotations on the run and as the full list in the job summary. The step has no `continue-on-error`; it cannot fail because `--warn` always exits 0. Nothing else runs the guard in this change: it is not added to ship-it step 4.4 (`.pi/skills/ship-it/SKILL.md:203-214`), to `npm test`, or to any vitest test that asserts zero findings. A unit test of the analyzer on fixture strings is allowed (tests are folded later); it must not scan the tree. So no job, no `ci-result` input and no ship gate treats a finding as a failure.

**Analysis, per file.**
1. Collects source readings (D4 a/b/c).
2. Taints, iterated to a fixed point: (i) identifiers declared or assigned (`const|let|var x =`, `x =`, `x +=`, destructuring) from an expression that holds a reading or a tainted identifier, with `...` spreads read as plain identifiers; (ii) a collection that receives a reading or a tainted value as an argument of `.push(…)` or `.set(…)` (argument read up to three lines on), as in `sudo-credential-load.test.ts:41,45` (`Map.set(…, performance.now())`); (iii) same-file functions (`function f(`, `const f = (…) =>`) whose body holds a reading or a tainted identifier, so a call `f(…)` is tainted, such as `readWhileWorkerWrites` (`kb-search-perf.test.ts:99`). The scope is the case: the lines of the enclosing `it(`/`test(` call up to the assertion (found from the call, also when the title is on the next line), every declaration at a shallower indentation, and every assignment to a name declared there (for example `elapsedMs` set in a `beforeAll`, `knip-scan.test.mjs:43`, before task 3.1 moves it). Scoping is textual (indentation), not a parser.
3. Reads each assertion statement from `expect(` or `assert` to the end of its matcher call by balancing parentheses, across lines, so a split form such as `expect(\n elapsed, msg\n).toBeLessThan(1000)` (`packages/server/src/__tests__/auth-redirect-base.test.ts:562-565`) is one statement.
4. Flags each upper-bound comparison (D4) whose measured side holds a reading, a tainted identifier or a tainted call, when either (a) its bound side holds none, or (b) its bound side holds one and also arithmetic (`*`, `/`, `+`, `-`): a relative budget such as `statusMs * 1.25`. A bound side that is a bare reading or tainted identifier with no arithmetic is an ordering check and is not flagged. A reading of a clock faked for that case (D4) is not a reading.
5. Skips `*.budget.test.*` files. Their structural rules are not this guard's job: the blocking check of D1 enforces them.
6. Drops a flagged occurrence that matches an allow-list entry (below). Reports a bad entry (empty reason, no matching statement, or more than one) as a finding; the entry's file is not checked (owner decision C4, "Liveness allow-list" below); an ambiguous entry exempts nothing.

**Liveness allow-list (A6).** An exported constant `LIVENESS_ALLOW` in the guard. Each entry is `{file, assertion, reason}`. `assertion` is the normalized text of the line where the flagged assertion statement begins (the line holding its `expect(` or `assert`; for a split statement, step 3, its first line). Normalized means: leading and trailing whitespace removed, then a trailing `// …` comment removed, then a trailing `;` removed, then trailing whitespace removed again. The guard normalizes each flagged statement's first line the same way and compares for equality. An entry admits exactly one statement: it matches when exactly one flagged statement's normalized first line equals its text; an entry equal to two or more is a finding (ambiguous) and exempts nothing. Each seed entry below equals the normalized line it cites; `cli-foreground-real.test.ts:80` is the one whose source line carries a trailing comment (`; // classify budget + boot slack`). Admission rule: **a real-process liveness deadline with a written reason.**

### D7. Nightly rerun: a `workflow_run` requester, an attempt-aware reporter, and a separate watchdog

A run cannot rerun itself while it is in progress: `gh run rerun --failed` needs a completed run (`unverified` against GitHub docs; consistent with the spike in task 1.1). So the rerun is requested by a separate workflow, which A3 prefers. The watchdog lives in a third workflow file, so that one broken file cannot stop both safety nets ("Two files, two enabling conditions" below). The design is fail-closed: every path where the rerun does not happen or its outcome is unreadable ends in an opened or updated issue.

```mermaid
sequenceDiagram
    participant Cron as schedule 03:00
    participant NT as nightly-tests.yml (attempt 1)
    participant RR as nightly-tests-rerun.yml
    participant NT2 as nightly-tests.yml (attempt 2)
    participant WD as nightly-tests-watchdog.yml (cron 07:47)
    participant Issue as nightly-tests issue
    Cron->>NT: run jobs (unit×4, real-process, ci-scenarios, budget)
    NT->>NT: report: write attempt-1 record {deferred, failingTests, failedJobs, noReport}
    alt scheduled, red, before the deferral deadline, rerun AND watchdog workflows active
        NT->>NT: deferred: true, no issue sync, exit 1
    else otherwise (green, dispatch, past the deadline, or either workflow inactive/unreadable)
        NT->>Issue: deferred: false, report as today
    end
    NT-->>RR: workflow_run completed (failure)
    RR->>RR: download nightly-attempt-1, read deferred
    alt record says deferred: true
        RR->>NT2: gh run rerun <id> --failed (actions: write)
        NT2->>NT2: failed jobs + report rerun; uploads overwrite
        alt record missing in attempt 2 (attempt 1 may have deferred)
            NT2->>Issue: create/update ("first-attempt record unavailable")
        else still red
            NT2->>Issue: create/update (failing + "Passed on rerun")
        else green
            NT2->>Issue: comment + close if open (lists passed on rerun)
        end
    else deferred: false, or record unreadable
        RR->>RR: no rerun (attempt 1 already reported, or the watchdog reports)
    end
    WD->>Issue: latest scheduled run not green and no open issue names it → create/update
```

- **`nightly-tests-rerun.yml`** (new). Trigger: `workflow_run: {workflows: ["Nightly tests"], types: [completed]}` only. Top-level `permissions: {}`. One job, `rerun`: `if: github.event.workflow_run.conclusion == 'failure' && github.event.workflow_run.run_attempt == 1 && github.event.workflow_run.event == 'schedule' && github.event.workflow_run.head_branch == 'develop'`. `permissions: {actions: write}`, `timeout-minutes: 5`, no checkout, no cache. Two steps, with `RUN_ID` and `GH_TOKEN` passed through `env:` and never interpolated into a script:
  1. `record` (`id: record`): `gh run download "$RUN_ID" --name nightly-attempt-1 --dir rec --repo "$GITHUB_REPOSITORY"`, then `jq -e '.deferred == true' rec/attempt-1.json` sets the step output `deferred` to `true` or `false`. A failed download or an unparsable file fails the step, and with it the job.
  2. `rerun`: `if: steps.record.outputs.deferred == 'true'`, runs `gh run rerun "$RUN_ID" --failed --repo "$GITHUB_REPOSITORY"`.
  So the trigger condition is the job `if:` AND the record's `deferred: true`. A night whose first attempt did not defer (deadline passed, a workflow inactive, green, or a dispatch) is never rerun automatically: attempt 1 has already opened or updated the issue, and nothing reruns or closes it before the next scheduled run. A night that deferred but whose record the `rerun` job cannot read is not rerun either; the watchdog reports it (fail-closed, later). Reading the triggering run's artifact with only `actions: write` is spike item (i). Least privilege: the token can rerun or cancel workflow runs, but cannot write contents, issues or packages. Untrusted input: only the numeric run id from the event. A `workflow_run` workflow runs the default-branch (`develop`) copy of its file, so a branch cannot change it.
- **`nightly-tests-watchdog.yml`** (new). Trigger: `schedule: cron "47 7 * * *"` and `workflow_dispatch` (for a manual check; a dispatch run is `--dry-run`). Top-level `permissions: {}`. One job, `watchdog`: `permissions: {contents: read, issues: write, actions: read}` (the report job's set), `timeout-minutes: 10`, checkout, `actions/setup-node` with no cache. Runs `node scripts/test-selection/nightly-report.mjs --watchdog`, plus `--dry-run` when `github.event_name != 'schedule'`.
  Both new files comply with `workflow-token-cache-contract.test.ts` rule 0 (explicit permissions) and rule 1 (no cache in a job that holds a write scope; `packages/shared/src/__tests__/workflow-token-cache-contract.test.ts:18-19,31-32`).
- **Two files, two enabling conditions (A3 fail-closed).** With `rerun` and `watchdog` in one file, one bad merge into that file (a YAML or expression error that GitHub rejects while the file stays `active`) would stop both while attempt 1 kept deferring: a red night with no issue. So:
  - attempt 1 defers only when BOTH `nightly-tests-rerun.yml` and `nightly-tests-watchdog.yml` answer `state: "active"`; any other answer, or an HTTP error, means no deferral and today's issue on the first red attempt;
  - a broken rerun file leaves the watchdog working: no attempt 2 runs, so the watchdog opens the issue at 07:47;
  - a broken watchdog file leaves the rerun path working: attempt 2 reports red or green itself;
  - both broken at once needs two faulty edits to two files. Task 6.4 makes `npm test` parse both files and pin their triggers, `if:` expressions, permissions and commands (`nightly-tests-workflow-contract.test.ts`), so a YAML syntax error or an edited condition fails before merge.
  - What stays `unverified`: the `state` GitHub reports for a file it rejects (assumed `active`), and that a rejected file shows a failed run in the Actions UI. Neither is relied on: the independence above holds either way. Fail-closed fallback if the owner wants more: drop the deferral (no rerun), which returns to today's behaviour.
- **Where `actions: write` lives:** only in the `rerun` job. The report job keeps `{contents: read, issues: write, actions: read}` (`nightly-tests.yml:175-178`; pinned at `nightly-tests-workflow-contract.test.ts:48-49`). Moving `actions: write` onto the report job was rejected: it holds `issues: write` already, and a same-run rerun is impossible anyway.
- **Reporter (`nightly-report.mjs`).**
  - `summarizeReports` also returns `failingTests: [{job, file, test|null}]` from `assertionResults` with `status === "failed"` (`test: null` for a file that failed without a failed assertion, such as an import error).
  - In `main`, `attempt = Number(GITHUB_RUN_ATTEMPT || 1)`. With `--defer-first-attempt` (passed only in `nightly-tests.yml`), attempt 1 ALWAYS writes `reports/attempt-1.json` = `{deferred, failingTests, failedJobs, noReport}`, whatever the event or verdict. It sets `deferred: true` only when `event === "schedule"`, the summary is red, the reporter runs at or before the deferral deadline, which is `DEFER_DEADLINE_UTC_MINUTE` minutes after 00:00 UTC of the UTC date of the run's `created_at` (an exported constant; "Timing" below; owner decision C1), so a reporter after that instant, on the next UTC day included, does not defer; `created_at` is read from `GET /repos/{repo}/actions/runs/{run_id}` (`actions: read`), and an HTTP error there counts as "deadline passed"; and `GET /repos/{repo}/actions/workflows/<file>` (`actions: read`) answers `state: "active"` for both `nightly-tests-rerun.yml` and `nightly-tests-watchdog.yml`. Then it writes a "deferred to rerun" step summary, skips `syncIssue` and exits 1. In every other case it writes `deferred: false` and reports as today. An HTTP error counts as "not active". `main` takes its GitHub API client, its clock and its environment as injectable parameters (defaults: the real client, `() => new Date()`, `process.env`), as `syncIssue({ api })` already takes the client (`nightly-report.mjs:97`), so tests drive report and watchdog mode with a fake API and a fixed time.

    - Present with `deferred: true`: this attempt is the rerun of a deferred night. It computes the two passed-on-rerun lists below and reports on its own verdict (issue only on `schedule`, as today).
    - Present with `deferred: false`: attempt 1 already reported, and the `rerun` job never reruns such a night, so this is a manual re-run. It reports on its own verdict as today. The two lists are still computed and shown as on a deferred night: in the step summary, and in the issue body when the run is red.
    - Missing or unparsable: it reads attempt 1 through `GET /repos/{repo}/actions/runs/{run_id}/attempts/1` (`actions: read`). When attempt 1's `event` is not `schedule`, or its `conclusion` is `success`, attempt 1 cannot have deferred. The reporter then judges this attempt on its own verdict, and the step summary says "first-attempt record unavailable; attempt 1 did not defer (<event>, <conclusion>)". Otherwise, an API error included, the run is red and the issue body says "first-attempt record unavailable — passed-on-rerun not computed" (fail-closed, A3).
    So a manual re-run of a green night, of a dispatch run, or of a night whose attempt 1 reported without deferring is judged on its own result. Only a night that may have deferred is forced red when its record is lost. (The simpler rule, every `attempt >= 2` without a record is red, would turn a manual re-run of a green night red. It is the fallback if spike item (f) fails.)
  - Two passed-on-rerun lists. `passedOnRerun` holds the previous `failingTests` whose `(job, file, test)` is not failing now and whose job report exists now. `jobsPassedOnRerun` holds the previous `failedJobs` and `noReport` entries whose job now has `result: "success"` in `NEEDS_JSON` and a report: a job that failed on attempt 1 with no failed assertion in a readable report (timeout, cancellation, install failure, `verify-executed` failure, no report) and then passed. Today `failedJobs` is read only for the verdict (`nightly-report.mjs:60-62`); this makes it visible.

  - `--watchdog`: lists the latest `schedule` run of `nightly-tests.yml` on `develop` (`actions: read`). If it started more than 24 h ago, or ended `success`, it exits 0. Otherwise it reads the open `nightly-tests` issues; if one body contains the run URL (`<server>/<repo>/actions/runs/<id>`, the form `main` already builds at `nightly-report.mjs:179`), it exits 0. Otherwise it creates or updates the issue with the run URL, the run's attempt, status and conclusion, and the reason ("rerun not performed or not reported"), then exits 1. `--dry-run` prints the decision without writing.
  - The run URL does not change across attempts, so an issue updated by attempt 2 already satisfies the watchdog.
  - The watchdog sees only the latest scheduled run. A scheduled run that starts after the watchdog's cron (a GitHub start delay of more than 4 h 47 min) is checked by no watchdog: the next one sees the next night. The deferral deadline closes that hole: such a run's first attempt reports after 04:05 UTC of its creation date, the next day included (owner decision C1), so it does not defer and reports itself as today.

## Risks / Trade-offs

- [A real performance regression in a moved case no longer blocks the PR that caused it] → The nightly budget job reports it within a day, and the bisect range in the issue names the commit window. A1 accepts this.
- [Until `migrate-budget-assertions` lands, a NEW budget assertion can enter a blocking lane, and about 300 existing ones still can flake a PR] → Stated in the proposal (A10). The warn-only step lists every finding in each `ci.yml` run's job summary, but it does not separate new findings from the ~300 existing ones, and GitHub caps the warning annotations a step can show (cap `unverified`). So a reviewer cannot reliably spot a new one; only the follow-up's blocking guard closes this.
- [A budget file reaches a blocking run] → Closed structurally (D1): the six configs exclude budget files unless `RUN_BUDGET_TESTS=1`, and the blocking "Budget lane check" fails the `ci` job and `npm test` when either `npm test` command would collect one. Residual: a lane leak that does not go through vitest collection, such as a job that sets `RUN_BUDGET_TESTS=1` around a blocking command; `schedule-release-rehearsal` pins that `publish.yml` never sets it.
- [The guard misses a budget assertion (D5 limits)] → Nothing depends on completeness in this change; the follow-up's hand pass covers the listed gaps.
- [A budget file that fails to load is seen only by the nightly] → Blocking runs no longer collect budget files (D1), so an import or collection error in one shows first in the nightly `budget` job, the next morning. The `ci` job still type-checks and lints the file (`unverified` which typecheck covers test files, D2). Recorded as trade-off T-A10.
- [The rerun request fails, `workflow_run` does not fire, or attempt 2's report does not run] → The watchdog, in its own file, opens or updates the issue the same morning (D7). A disabled or missing rerun or watchdog workflow stops the deferral itself, so attempt 1 opens the issue. If the watchdog's own run fails, that run is red in the Actions UI; nothing else watches the watchdog (T-A4).
- [The issue opens later than today on a real regression: up to about 80 minutes later through the rerun (worst case 05:35 instead of 04:15, D7 "Timing"), up to about three and a half hours later through the watchdog (07:47)] → Accepted by A3: one rerun, then the issue.
- [Attempt 2 cannot read attempt-1 artifacts, or another spike item fails] → The spike (task 1.1) runs before group 6. D7 "If the spike fails" gives each item's disposition; for the blocking ones, group 6 is not carried out and ship-it stops for the owner.
- [Rerun doubles cost on deterministic failures and delays the issue by one job duration (≤ 50 min)] → Accepted by A3.
- [`actions: write` token misuse] → Single step, no checkout, no third-party action, numeric input via env, runs only from the `develop` copy of the file.
- [A flaky budget test that fails twice still opens an issue] → Intended: two failures are a signal. Its threshold is then re-tuned in a follow-up.
- [Blender P1–P3 lose macOS and Windows coverage] → Accepted loss (A7). The `blender-real` legs on all three OSes keep running the functional real-runtime cases; spec `blender-mcp-server` "Performance budget" is modified to say where the budget is measured.
- [A 300 s bound hides a slow JVM] → The root-cause task measures it, and the bound still turns a hang into exit 2.
- [Conflicts with `schedule-release-rehearsal` in `nightly-report.mjs`] → That change depends on this one and lands second; "Reporter interface" fixes what it builds on.

## Migration / Rollback

- **Order:** rerun spike (1, in parallel with 2–4) → selector, verify, `test:budget`, config exclusion and blocking lane check (2) → nightly budget job, flag reader and concurrency (5, after 2) → the A9 moves (3.1–3.7 and the doc task 3.9, after 5 is merged; each file can land on its own) → `budget` timeout and seriality check (3.8, after 3.1–3.6 are all merged; until then the timeout is the provisional 40 of task 5.1) → warn-only guard (4, any time after 2) → rerun and watchdog (6, after 1 passes and after 5) → CodeQL (7, independent). Group 5 lands before group 3 so that a moved case is never in a budget file while no nightly job runs it: from the moment a case leaves its blocking file, the `budget` job asserts it, which the three MODIFIED deltas (`blender-mcp-server`, `dead-code-detection`, `publish-correctness-verification`) state. The budget job runs vitest also with an empty list (D3), so group 5 before group 3 leaves a green `budget` job, not "budget: no report". Docs land with each group. Revert in reverse dependency order: group 6 before group 5 (6 builds on 5's reader and workflow edits), and group 3 before group 5 (see "Turn the lane off"). Groups 4 and 7 revert on their own.
- **Turn the lane off:** first revert group 3 (each moved case goes back into its original file, without a gate) together with the three MODIFIED deltas `blender-mcp-server` "Performance budget", `dead-code-detection` "Whole-graph Knip scan" and `publish-correctness-verification` "The check completes within a CI time budget", which say the budget is asserted in the nightly budget lane. Then delete the `budget` job and its entry in report `needs`/`--expected`. Deleting the job first would leave the moved cases running in no lane, because the configs exclude budget files everywhere else, while those three requirements still say the nightly asserts them. The config exclusion and the blocking check may stay: with no budget file they exclude nothing and pass.
- **Turn the guard off:** remove the `ci.yml` step. It fails nothing, so leaving it in is also safe.
- **Concurrency:** restoring the `concurrency` block in `nightly-tests.yml` reverts that edit (and the contract check in task 5.5 must be reverted with it).
- **Turn the rerun off:** disable `.github/workflows/nightly-tests-rerun.yml` or `.github/workflows/nightly-tests-watchdog.yml`. The deferral checks both workflows' state, so attempt 1 then records `deferred: false` and opens the issue on the first failure, as today. If only the watchdog file is disabled, the rerun file still runs on a red night, but its `record` step reads `deferred: false` and requests no rerun (D7), so nothing reruns or closes that issue before the next scheduled run. Dropping `--defer-first-attempt` from the report step (`nightly-tests.yml:199`) is the clean-up; it also stops the deferral by itself. The watchdog is needed only while the deferral is live.
- **CodeQL:** `PI_CODEQL_RESOLVE_TIMEOUT_MS=60000` restores today's bound without a code revert.
- **Compatibility:** no published API or package changes. `selection.json` gains one field. Readers ignore unknown fields (`assignedFor`, `check-result.mjs`). `nightly-report.mjs` keeps today's behaviour when no new flag is given, except that an absent `--reports`/`--expected` is now a usage error instead of reading `argv[0]`.
