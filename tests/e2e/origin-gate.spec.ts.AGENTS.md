# origin-gate.spec.ts — index

L3 cross-site gates in browser reality (#F1-#F3). Attacker page served by a local `http.createServer` and reached through Chrome launch arg `--host-resolver-rules=MAP attacker.test 127.0.0.1` — NOT `page.route` fulfilment: a fulfilled route has no resolved IP, so Chrome files the page under the PUBLIC address space and its own Private Network Access check blocks the request before it leaves the browser, making the assertion pass while proving nothing about the server (verified empirically). Hostile `new WebSocket(ws://localhost:<dashboardPort>/ws)` never opens and the harness `server.log` carries `[ws-gate] rejected upgrade origin=…`; blind `fetch POST /api/tunnel-connect` leaves `/api/tunnel-status` byte-identical and logs `[csrf-gate]`; the dashboard's OWN origin still opens `/ws` (receives `sessions_snapshot`) with no `[ws-gate]` line. `waitForLogLine` polls `docker exec cat $HOME/.pi/dashboard/server.log` — the gate's `console.error` reaches the file a beat after the socket dies. Deliberately does NOT drive the inline-terminal UI for #F1: `terminal.spec.ts` fails on develop in this harness, so that path would import a pre-existing flake into a security gate. See change: fix-ws-origin-cswsh.
