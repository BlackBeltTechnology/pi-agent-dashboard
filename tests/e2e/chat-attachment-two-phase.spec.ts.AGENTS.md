# chat-attachment-two-phase.spec.ts — index

Two-phase attachment render E2E (change: fit-attachments-for-display). Injects an image via the REAL user path — a synthetic `ClipboardEvent` carrying a `File`, which is what `useImagePaste.handlePaste` consumes — then asserts F1/F2 (row renders, placeholder converges to a fitted `<img>`) and F7 (image still renders after reload, proving the hydration path is fitted too). Asserts fitted-ness by POLLING `naturalWidth <= 768`: immediately after send the client renders its own optimistic full-resolution echo of the pasted file, so a single sample reads the un-fitted image. Uses high-entropy noise pixels so PNG cannot compress the fixture away. Also covers F3 (garbage bytes claiming image/png -> explicit failed state, never a stuck placeholder), F5 (zoom loads the session-scoped ORIGINAL, asserted by naturalWidth > 768 vs the 768px transcript copy) and F6 (page.route 404s the originals endpoint -> lightbox `data-degraded=true`, transcript image untouched). Sends via `composer.press("Enter")`, NOT the send button: with a multi-MB base64 in composer state the button's actionability check intermittently stalls (visible+enabled+stable but the click never lands), which burned the retry budget and made runs 7x slower. Also covers F4 (reload racing an in-flight fit -> attachment must settle ready-or-failed, never stay pending) and F8 (image row keeps its height across scroll-out/scroll-back, guarding the virtualized-row collapse/overlap invariant). P5 (image-heavy replay, 8 attachments) asserts `/api/health` droppedFrames.serverToBrowser is unchanged across replay; it originally FAILED and exposed the task-9.4 reducer bug (identical images share one content hash -> only the first row resolved). F8 measures the anchor row while it is still MOUNTED — measuring after the filler turns races the virtualizer, which may already have unmounted it.
